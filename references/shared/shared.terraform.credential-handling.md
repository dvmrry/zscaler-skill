Provider credentials for the SDK itself are covered in [[shared.sdk-go.auth-lifecycle]]; this subject is about secrets that pass through resources and data sources. Secrets can show up in three different places when a Terraform provider handles a credential: in the state file, in plan and CLI output, and in logs. The `Sensitive` flag on a schema attribute affects how Terraform displays the value in plan and CLI output. It does not change what is written to state or to a provider's own log lines. The claims below keep those apart, and each states which of them the code shows.

**ZIA data sources hand credentials to state as ordinary values.** The Cloud-to-Cloud incident receiver data source has no `Sensitive` marking on its authorization attributes, and its flattener copies them from the response. {{c2c-ir-secrets-not-sensitive}} {{c2c-ir-secrets-copied-to-state}} Two more data sources do the same for a Cloud NSS authentication token and client secret and for an administrator's mobile-app token. {{cloud-nss-and-admin-token-in-state}} Not every ZIA data source is like this. The location data source marks its pre-shared key `Sensitive`, and the VPN credentials data source has the marking and the assignment both commented out. {{zia-psk-handled-differently}} {{zia-data-source-secret-attributes-unmarked}} Whether any of this reaches state in practice depends on whether the API returns the secret on read, which the sources do not say. This repository only shows what the provider would do with a value it receives.

**One ZIA data source also logs them.** {{c2c-ir-entity-log-includes-secrets}} The neighboring log line over the whole response looks like it should do the same but does not, because a nested pointer prints as an address. {{c2c-ir-response-log-prints-pointer-only}}

**The ZPA PRA credential resource sends a sentinel in place of two of its three secrets.** A sanitizer helper (its name and the log call after it suggest it is meant to keep secrets out of logs) is applied to the request before it is sent, so the create call carries `***REDACTED***`. {{pra-create-sanitizer-mutates-request}} The matching is by field name and misses the private key, which means the private key goes out as configured and, because the request is logged after sanitizing, into the log line. {{sanitizer-misses-private-key}} {{pra-create-log-prints-private-key}} The helper is called in two places. {{sanitizer-call-sites}} Because the resource's read never refreshes the secrets, a create that sent the sentinel does not produce drift on the next plan. {{pra-read-never-sets-secrets}} What ZPA does with the sentinel is not established here.

**Updates cannot clear a secret.** The update path sends real values but leaves out empty ones. {{pra-update-omits-empty-secrets}} The PRA credential data source declares `password` and never fills it. That is a missing output today, and the reason to set it carefully if someone adds the assignment. {{pra-data-source-password-declared-not-set}}

**The SDK can log everything regardless.** With `TF_LOG=DEBUG` or `TRACE` (or both `ZSCALER_SDK_LOG` and `ZSCALER_SDK_VERBOSE` set), request and response bodies are dumped whole, so provider-level redaction does not protect against that log. {{sdk-logs-full-bodies-when-enabled}}

What to check: which of these data sources and resources your configuration uses; whether debug-level provider logging (`TF_LOG=DEBUG` or `TRACE`) or both SDK log variables are turned on in CI; whether state storage is access-controlled; and, for PRA credentials, whether a credential created through the provider actually authenticates. Related: [[shared.sdk-go.auth-lifecycle]] covers how the SDK gets its own API credentials, and [[zia.sdk-go.write-encoding]] covers the `omitempty` behavior behind the update trap.
