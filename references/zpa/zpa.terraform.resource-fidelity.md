Several ZPA resources do not do what their schema promises: an argument is dropped on the way out, a response field is dropped on the way back, or one logical write is split into several requests with no way back. Each instance is small. The common effect is that Terraform reports success while the remote object differs from the configuration, so after any apply on these resources, read the object from the API instead of trusting state. Application segment resources have their own version of this problem in [[zpa.terraform.app-segment-lifecycle]].

Success-shaped results. These return success without the work being done or checked. {{cloud-config-read-error-is-success}} {{cloud-config-destroy-is-noop}} The Service Edge and App Connector assistant schedules are singleton settings with the same shape (the claims quote the Service Edge resource; the App Connector resource and SDK are identical apart from the endpoint). {{schedule-delete-is-noop}} The SDK also refuses to update a disabled schedule ([[zpa.sdk-go.service-defects]]). {{schedule-create-discards-server-id}} {{schedule-read-never-sets-id}} For this resource, check the remote setting directly after create, import or destroy; an empty resource ID is the first symptom.

Arguments that never reach the API. {{redirection-create-skips-policy-set-lookup}} {{redirection-edge-group-expand-flatten-asymmetry}} {{private-cloud-no-exporter-group-field}} {{server-group-update-name-only-on-change}} The server group case depends on how ZPA treats a PUT without a name, which no captured source shows. {{lss-false-values-not-sent}} The wider omission mechanism is in [[shared.sdk-go.zero-value-writes]].

Response fields that never reach state. {{redirection-read-omits-microtenant}} {{portal-capabilities-read-checks-wrong-field}} {{capabilities-read-never-clears}} {{pra-console-read-never-clears-application}} {{lss-read-drops-policy-rule-resource}} A Read that sets a block only inside a conditional cannot show that the remote value went away; a plan after an out-of-band change can come back empty. Policy rule reads that go through the v2 converter have a related loss, covered in [[zpa.terraform.policy-rule-writes]].

One logical write, several requests. {{private-cloud-create-then-fire-drill-put}} {{user-code-verification-after-write}} When one of these applies fails, the first request has already taken effect. Look at the object before retrying. Cleanup sequences that fail midway on destroy are in [[zpa.terraform.delete-paths]].

Import and validation. Provisioning-key import by name probes only three of the five association types the schema accepts ([[zpa.sdk-go.service-defects]]). {{pra-approval-end-not-checked-against-start}} For a key of an unprobed type, check that import actually found it rather than assuming the association type was read. The approval validator runs at apply, so a backwards window is reported by the API, if at all, not by the provider.
