Every ZIA rule resource that supports ordering hands its declared order to one shared, in-process registry and then blocks until a background worker says the order is applied. How the registry is keyed, who starts the worker, and when entries are marked done or removed decides whether an apply finishes, hangs, or finishes with a rule in the wrong place. This subject covers that shared machinery; how a single update is parked and put back, and why the worker cannot report failure, is in [[zia.terraform.rule-order]] and is not repeated here.

**Keys and what the worker sees.** {{registry-key-is-a-string}} A resource that picks the wrong key, or one key for things the API lists separately, is judged by callbacks that cannot see its rule. {{traffic-capture-create-uses-firewall-key}} {{traffic-capture-joins-firewall-cycle}} Rule types are the second case. {{cloud-app-control-one-key-for-all-types}} {{cloud-app-control-key-fixed-per-type-at-pin}} {{casb-rules-one-key-for-all-types}} {{mixed-subtype-cycle-skips-rules}} When you see a rule of one type not take its order in a mixed apply, check which type registered first for that key.

**Races.** {{done-channel-read-after-unlock}} {{done-channel-capture-fixed-in-v4-8-7}} {{join-after-final-snapshot}} The starting-order state has its own races. {{starting-order-state-read-outside-lock}}

**Entries that never settle.** {{worker-waits-forever-on-undone-entry}} {{create-registers-before-read-then-marks}} {{create-registers-before-read-sites}} {{undone-entry-hangs-later-waiters}} On the other side, entries are not cleaned up. {{registry-entries-are-never-removed}} {{registered-rule-missing-from-list-is-skipped}} {{deleted-rules-skew-later-cycles}}

**Create-time order allocation.** New rules are posted at a staging order before the worker moves them. {{staging-order-is-occupied-maximum}} {{staging-order-never-reserved}} {{staging-order-collision-effect}} A retried create then forgets what was asked for. {{create-retry-loses-declared-order}} {{create-retry-loses-declared-order-sites}} The failed-read retry that triggers it is described in [[zia.terraform.error-handling]], as is create order taken from an ignored list error.

**Rank and the bounded exit.** {{rank-comparison-without-rank-write}} {{rank-mismatch-never-repaired}} The newer breaker bounds some loops but not all. {{oscillation-breaker-guard}} {{mixed-skip-write-path-is-unbounded}}

What to check when an apply hangs or a rule lands in the wrong place: whether an earlier create of the same resource type failed its read, whether the resource shares a registry key with a different resource or rule type, whether a rule deleted earlier in the run is still registered, and whether the rule's rank differs from its declared rank. After the apply, re-read the order and rank of every rule in the policy rather than trusting the apply result, as [[zia.terraform.rule-order]] advises for terminal rules.
