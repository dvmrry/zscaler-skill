# ZIA SCIM Provisioning — ZIA-specific behavior

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`.

This document covers behavior specific to ZIA's SCIM ingestion: how provisioned objects land in ZIA, how SCIM groups relate to ZIA departments, which rule types can match on SCIM-derived identity, and operational constraints and gotchas that are distinct from ZPA.

For protocol-level mechanics (SCIM 2.0 wire format, pagination, authentication, cross-product `active=false` semantics, Okta first-sync gotcha, Python vs Go SDK coverage), see [`../shared/scim-provisioning.md`](../shared/scim-provisioning.md). For ZPA-specific SCIM group-to-policy operand mapping, see [`../zpa/scim-policy-mapping.md`](../zpa/scim-policy-mapping.md).

---

## 1. Scope — what makes ZIA SCIM different from ZPA

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-help/about-scim-zpa.md`.

ZIA and ZPA both accept SCIM 2.0 pushes from an IdP. Their internal handling diverges in three fundamental ways:

**User deactivation semantics.** When an IdP sends `active=false`, ZIA *disables* the user (the account persists in the database, accessible for re-enabling). ZPA *deletes* the user. A SCIM client sending `active=false` expecting "disabled" semantics gets destructive behavior on ZPA but safe/reversible behavior on ZIA.

**Attribute surface.** ZIA's SCIM user schema is smaller and structured differently from ZPA's. ZIA does not expose `costCenter`, `division`, `organization`, `title`, or `userType` as first-class Zscaler fields with policy impact. ZPA supports those fields but the SCIM Attributes page in ZPA is read-only and does not allow custom attributes. ZIA is similarly constrained.

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`.

**Group model.** ZPA treats SCIM groups as first-class read-only policy operands (operator filter `SCIM_GROUP` — see [`../zpa/scim-policy-mapping.md`](../zpa/scim-policy-mapping.md)). ZIA does not expose an equivalent `SCIM_GROUP` policy operand. SCIM groups land in ZIA's user database as the `groups` attribute on the user record; the `department` field is a separate object. ZIA policy rules reference users, groups, and departments — not SCIM groups as a distinct concept.

## 2. ZIA SCIM user object — what gets persisted

### Attribute mapping

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

The following is the ZIA SCIM-to-Zscaler field mapping as documented by the vendor.

| SCIM attribute | Zscaler field | Notes |
|---|---|---|
| `id` | `<unique_id>` | UUID-like identifier generated by Zscaler (e.g., `1a234567-1b23-1200-1234-123c`). Read-only; IdP cannot set this. |
| `externalId` | `scim_externalid` | IdP-side external ID stored in the Zscaler database. Preserved as-is. |
| `userName` | `login_name` (User ID) | Format `user@domain`. The domain part must be pre-registered with Zscaler via Support. |
| `displayName` | `user_name` | User's display name. |
| `active` | Enable/disable state | `false` = disable (not delete). `true` = re-enable. |
| `groups` | Groups | Group memberships. Subject to the 128-group-per-user cap. |
| `department` | Department | The department the user belongs to. |
| `name.givenName` | First name | Note singular `name.` prefix — differs from ZPA's `names.givenName` (plural). |
| `name.familyName` | Last name | Same singular `name.` prefix. |
| `emails.value` | `scim_emails` | Email stored for reference; not used as the login identifier. |

### What the Go SDK SCIMUser struct reveals

Source: `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`.

The Go SDK's `SCIMUser` struct (`vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go:24-31`) declares six top-level fields on a SCIM user response:

- `Schemas` (`[]string`) — the SCIM schema URN list the resource declares (SCIM core plus any extension, e.g. the enterprise extension).
- `ID` (`string`) — the Zscaler-generated user ID.
- `UserName` (`string`).
- `DisplayName` (`string`).
- `EnterpriseExtension` (`*EnterpriseUser`) — the `urn:ietf:params:scim:schemas:extension:enterprise:2.0:User` extension object, which carries `Department` (`scim_user_api.go:33-35`).
- `Meta` (`*Meta`).

The `department` attribute is therefore not a top-level core field: it lives inside the **SCIM Enterprise User extension** object reached via `EnterpriseExtension`. The `Schemas` array is the on-the-wire evidence of whether the extension is present at all — a connector that omits the enterprise extension will not list its URN in `schemas` and will not populate `EnterpriseExtension`, which directly underpins the operational point below (and in section 5) that such a connector never sends `department`.

Source: `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`; `vendor/zscaler-help/understanding-scim-zia.md`.

This matters operationally: SCIM connectors that do not emit the Enterprise User extension will not send `department` to ZIA at all, even if they correctly send `userName`, `displayName`, and `groups`. The ZIA user record will have an empty department field, and any ZIA policy rule scoped by department will not match that user. This is one of the most common misconfigurations for tenants migrating from LDAP provisioning.

### Required attributes for ZIA policy evaluation

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

The vendor doc states only `userName` is marked as a required attribute. The domain pre-registration constraint means a SCIM push for `user@example.com` will fail if `example.com` is not registered to the ZIA tenant.

For identity-aware ZIA policy to function, the following additional attributes are needed:

- `groups` — required if ZIA rules will scope by group.
- `department` (via Enterprise User extension) — required if ZIA rules will scope by department. Not sent by default by all IdPs; operators must verify the SCIM connector's attribute mapping is configured to emit the Enterprise User extension.

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-help/about-scim-zpa.md`.

Custom SCIM attributes beyond the documented mapping are not persisted in ZIA. ZIA does not support operator-defined custom attributes on the SCIM user object. This is inferred from the documented ZIA mapping and the ZPA vendor doc's explicit custom-attribute limitation; the ZIA doc does not describe an operator-defined custom attribute surface.

## 3. ZIA group vs. department — the SCIM mapping distinction

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-help/about-scim-zpa.md`.

ZIA's SCIM mapping splits group membership and department into two separate ZIA object types: SCIM groups land in a ZIA group object, and the Enterprise User `department` attribute populates a separate ZIA department object on the user record. ZPA's SCIM mapping carries `department` as a user attribute rather than as a separate object, and ZPA exposes SCIM groups via the `SCIM_GROUP` policy operand (see [`../zpa/scim-policy-mapping.md`](../zpa/scim-policy-mapping.md)).

### How ZIA represents group and department

ZIA maintains two separate identity objects in its user database:

- **Groups** — a flat label associated with users. SCIM-provisioned groups map to ZIA groups. ZIA policy rules can reference these groups directly by name. Groups do not have a parent-child hierarchy in ZIA's standard model.
- **Departments** — a separate ZIA object. Departments are distinct from groups. The SCIM `department` attribute (delivered via the Enterprise User extension) populates the user's ZIA department field.

### What SCIM sends and where it lands

Source: `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_group_api.go`.

When an IdP sends a SCIM group via `POST /Groups` or `PUT /Groups/{id}`, ZIA stores it as a **ZIA group object** with a Zscaler-generated `id`, a `displayName`, and an `externalId`. The Go SDK `SCIMGroup` struct (`vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_group_api.go`) confirms the fields: `id` (Zscaler UUID), `displayName`, `externalId`, and `members` (list of `{value, $ref}` pairs where `value` is the Zscaler user ID).

When an IdP sends `department` on a user record via the SCIM Enterprise User extension, that string value maps to the user's ZIA `Department` object. ZIA matches the incoming `department` string against the name of an existing ZIA department object. If no ZIA department object with that name exists, the department association may not resolve correctly — the behavior when the department name has no matching ZIA department record is not documented in available sources (deferred — see "## Open questions").

### Key distinction from ZPA

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-help/about-scim-zpa.md`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_group_api.go`.

ZPA exposes two distinct policy operand types for SCIM-sourced identity: `SCIM_GROUP` (membership check against a synced group object) and `SCIM` (flat string attribute match). ZIA has no equivalent `SCIM_GROUP` operand type. In ZIA, synced groups become queryable via the standard `groups` criterion on policy rules — the same object type used by manually-created groups. There is no separate "SCIM group as policy operand" concept in ZIA.

## 4. Which ZIA rule types use SCIM-derived identity as a match condition

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-sdk-go/zscaler/zia/services/firewallpolicies/filteringrules/filteringrules.go`; `vendor/zscaler-sdk-go/zscaler/zia/services/urlfilteringpolicies/urlfilteringpolicies.go`.

ZIA policy rules reference the *resolved ZIA objects* (users, groups, departments) — not raw SCIM constructs. Because SCIM provisioning populates those ZIA objects, SCIM-provisioned identity flows into any rule type that supports user/group/department criteria.

### Firewall Filtering (Advanced tier only)

Source: `vendor/zscaler-sdk-go/zscaler/zia/services/firewallpolicies/filteringrules/filteringrules.go`.

Firewall Filtering rules accept `users`, `groups`, and `departments` as criteria — declared in the SDK struct as plain `[]common.IDNameExtensions` with no count limit stated in the struct or its comments (`filteringrules.go:88-94`). These reference the ZIA user, group, and department objects respectively. A SCIM-provisioned user's group memberships and department assignment make them matchable by firewall rules without any additional configuration beyond SCIM sync being active. The per-criterion caps (32 users, 32 groups, 32 departments per rule) are documented and sourced in [`./firewall.md § Firewall Filtering rule criteria`](./firewall.md) — they are not derivable from the Go SDK struct and belong with the firewall reference, not here.

Note: identity-aware firewall rules require the Advanced Firewall license. Basic Firewall rules can only scope by IP/port/location; they cannot reference SCIM-derived user or group identity.

### URL Filtering

Source: `vendor/zscaler-sdk-go/zscaler/zia/services/urlfilteringpolicies/urlfilteringpolicies.go`.

URL Filtering rules support `users`, `groups`, `departments`, `device_groups`, and `devices` as criteria. Users, groups, and departments populated via SCIM sync are available as criteria in URL filtering rules. The rule references the resolved ZIA object — SCIM-provisioned users are indistinguishable from manually-created users from the rule's perspective.

### DLP (Web DLP Rules)

Source: `vendor/zscaler-sdk-go/zscaler/zia/services/dlp/dlp_web_rules/dlp_web_rules.go` (criteria fields); `vendor/zscaler-help/configuring-dlp-policy-rules-content-inspection.md:136` (unauthenticated-traffic constraint).

DLP Web Rules support `departments`, `groups`, `users`, `locations`, and `location_groups` as criteria. The same SCIM-provisioned user/group/department objects are referenced. One constraint documented in the DLP reference: a DLP rule that applies to unauthenticated traffic must set `Any` for both groups and departments — SCIM-derived group/department scoping requires authenticated user context. The vendor source states this directly: "Any rule that applies to unauthenticated traffic must apply to all groups and departments" (`configuring-dlp-policy-rules-content-inspection.md:136`); the Go SDK struct only declares the criteria fields, not this save-time constraint. See [`./dlp.md`](./dlp.md) for the full DLP treatment.

### Forwarding Control

Source: `vendor/zscaler-sdk-go/zscaler/zia/services/forwarding_control_policy/forwarding_rules/forwarding_rules.go`.

Forwarding Control rules support `users`, `groups`, `departments`, `device_groups`, `locations`, and `location_groups` as criteria. SCIM-provisioned identity flows into forwarding rules in the same way as other rule types. This is operationally relevant for Source IP Anchoring (SIPA) configurations where specific user groups should route through a ZPA gateway rather than default ZIA egress.

### Summary table

| Rule type | User | Group | Department | Notes |
|---|---|---|---|---|
| Firewall Filtering | Yes | Yes | Yes | Advanced Firewall license required for identity criteria; per-criterion caps in [`./firewall.md`](./firewall.md) |
| URL Filtering | Yes | Yes | Yes | Standard |
| DLP Web Rules | Yes | Yes | Yes | Unauthenticated-traffic rules must use `Any` for group/dept |
| Forwarding Control | Yes | Yes | Yes | Standard |
| SSL Inspection | Yes | Yes | Yes | (Tier D — consistent with general ZIA rule model; not directly confirmed in available SSL Inspection doc) |

## 5. Attribute constraints

### Attribute set limits

ZIA's SCIM schema exposes a documented set of attributes (section 2 above). Custom attributes are not supported. There are no documented limits on the character length of individual attribute values (e.g., `displayName` or `department` string length) in the sources reviewed. (Deferred — see "## Open questions".)

### Group membership cap

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

A single ZIA user cannot belong to more than 128 groups. If an IdP provisions a user with more than 128 group memberships, the behavior above that cap is not documented in available sources — the constraint is stated as a hard limit.

Operationally: tenants with deep LDAP group structures or role-group sprawl in their IdP should audit group counts before enabling SCIM. An IdP-side group consolidation or scoping (provisioning only the groups ZIA actually needs for policy) is the recommended mitigation before hitting this cap.

### Multi-valued attributes

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`.

The `groups` and `emails.value` attributes are multi-valued in SCIM 2.0. ZIA accepts multi-valued `groups` (up to 128 members as noted above) and `emails.value`. Other documented attributes (`userName`, `displayName`, `department`, `name.givenName`, `name.familyName`) are single-valued.

### The `department` attribute via Enterprise User extension

As noted in section 2, `department` is delivered via the Enterprise User SCIM extension, not as a top-level SCIM attribute. SCIM connectors configured to send only the core schema will not send `department`. This is an attribute constraint that is connector-configuration-dependent, not a ZIA platform limit.

## 6. Push model — IdP initiates all SCIM writes

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

ZIA's SCIM ingestion is **push-based**: the IdP authenticates to Zscaler's SCIM endpoint and pushes user and group records. ZIA does not poll the IdP. All changes (create, update, delete, membership changes) are initiated by the IdP's SCIM connector.

### Supported connectors

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

Zscaler publishes per-IdP SCIM configuration guides for: Microsoft Entra ID (formerly Azure Active Directory), Okta, PingFederate, PingOne, Google Workspace, AD FS (SAML only — SCIM guide not listed), OneLogin (SAML only — SCIM guide not listed), CA Single Sign-On (SAML only). Custom SCIM clients using REST API calls directly to Zscaler's SCIM endpoints are also supported.

Any SCIM 2.0-compliant IdP can be used, not only the listed partners (e.g., SailPoint). (Tier A — `vendor/zscaler-help/about-scim-zpa.md` states this explicitly for ZPA; ZIA doc implies same by listing a non-exhaustive set.)

### SAML prerequisite

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

SCIM in ZIA requires SAML as the authentication method. An organization that authenticates users via a non-SAML method cannot use ZIA SCIM provisioning.

### IdP-specific notes

The vendor doc calls out no ZIA-specific IdP quirks beyond the general Okta ZPA gotcha documented in [`../shared/scim-provisioning.md § Okta-specific gotcha (ZPA)`](../shared/scim-provisioning.md). Per-IdP attribute mapping nuances (how Entra ID vs Okta vs PingFederate populate the Enterprise User extension for `department`) are covered in per-IdP configuration guides not captured in available vendor sources. (Deferred — see "## Open questions".)

## 7. Deactivation behavior

When the IdP marks a user inactive — by sending `active=false` or by deleting the user record — ZIA's behavior differs from ZPA's:

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-help/about-scim-zpa.md`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`.

- **`active=false` → ZIA disables the user.** The user record persists. The user cannot authenticate via SAML. Policy evaluations will treat the user as inactive. No session termination is documented as occurring automatically — the user's current session may persist until it expires normally.

- **`active=true` → ZIA re-enables the user.** Because ZIA preserves the user record on `active=false`, re-enabling is a simple attribute flip. This contrasts sharply with ZPA where `active=false` deletes the user and re-activation requires a full re-provisioning cycle.

- **`DELETE /Users/{id}` → ZIA removes the user.** A hard delete via the SCIM DELETE verb removes the user record from ZIA. This is distinct from the soft-disable path above.

### Why this matters in practice

An IdP that "deprovisions" users by sending `active=false` (common in Okta and Entra ID lifecycle workflows) achieves a soft disable in ZIA but a destructive delete in ZPA. Tenants running SCIM to both products from the same IdP connector need to be aware that the same provisioning action has different effects per product. The shared provisioning doc covers this in more detail: [`../shared/scim-provisioning.md § ZPA vs ZIA differences`](../shared/scim-provisioning.md).

## 8. Group membership change propagation

### Sync cadence

SCIM sync in ZIA is IdP-driven. The frequency of group membership updates depends on the IdP's SCIM sync schedule — typically minutes to tens of minutes for event-triggered pushes from Okta or Entra ID, but potentially longer for scheduled batch syncs. ZIA provides no mechanism to force an immediate re-sync from the Zscaler side. Operators needing faster propagation should trigger a resync from the IdP's admin console. (Tier A for the "ZIA cannot force a sync" statement, from the push-model architecture in the vendor doc. Exact cadence per IdP is not consolidated in available sources — deferred.)

### Idempotency

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

ZIA SCIM endpoints support both `PUT` (full replace) and `PATCH` (partial update) for users and groups — Update User is `PUT /Users/{UserID}` or `PATCH /Users/{UserID}` (`vendor/zscaler-help/understanding-scim-zia.md:48-50`) and Update Group is `PUT /Groups/{GroupID}` or `PATCH /Groups/{GroupID}` (`vendor/zscaler-help/understanding-scim-zia.md:58-60`). The `/Bulk` endpoint (Bulk Modify Resources: `POST`) is available for high-volume provisioning operations, reducing the number of individual requests needed during large group membership changes (`vendor/zscaler-help/understanding-scim-zia.md:62-63`).

**SDK coverage caveat.** Neither vendor SDK wraps `PATCH` or `/Bulk`. The Go SDK SCIM API implements only `GetUser`/`GetUserByName`/`CreateUser` (POST)/`UpdateUser` (PUT)/`DeleteUser`/`GetAllUsers` and the matching group functions — there is no `Patch*` or `Bulk*` method anywhere in `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/` (`scim_user_api.go:44-113`, `scim_group_api.go:39-107`). The Python SDK exposes no `scim_api` at all (see section 11). So programmatic `PATCH` or `/Bulk` against ZIA requires hand-rolled direct HTTP against the SCIM endpoints; the SDKs cover only `GET`/`POST`/`PUT`/`DELETE` on individual `/Users` and `/Groups` resources.

### Rate limiting

ZIA API rate limits apply to SCIM endpoints, but SCIM-specific rate limit guidance is not published in available vendor sources. The `/Bulk` endpoint is the recommended mitigation for large provisioning batches. Treat tenant-specific throttling behavior as deferred until confirmed against live API responses or current vendor documentation.

### Pagination cap

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_group_api.go`.

The `GET /Users` and `GET /Groups` endpoints return up to 1,000 entries per response. Use `startIndex` to paginate. The Go SDK's `GetAllUsers` and `GetAllGroups` functions use a page size of 100 via the `/.search` POST endpoint, consistent with the comment in the source: "100 // max per Zscaler SCIM API".

### SCIM query and discovery surface

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

Beyond the user/group CRUD covered above, ZIA's SCIM server implements the standard SCIM 2.0 filter and discovery endpoints. These are what a connector relies on for targeted reconciliation and incremental (delta) sync — none of them are wrapped by the Go SDK's high-level CRUD methods, so a connector or a custom client uses them directly.

**Server-side filtering on `GET /Users`** (`vendor/zscaler-help/understanding-scim-zia.md:44-47`):

- `GET /Users?filter=userName eq <value>` — equality match on `userName`; the primary lookup for reconciling a known account.
- `GET /Users?filter=externalID eq <value>` — equality match on the IdP-side external ID, the stable cross-system join key.
- `GET /Users?filter=id eq <value>` — equality match on the Zscaler-generated ID.
- `GET /Users?filter=meta.lastModified gt <value>` — returns users modified after a timestamp. This is the support for **incremental / delta sync**: a connector can pull only what changed since its last successful run instead of re-reading the full directory.

`GET /Groups` supports a combined display-name and membership filter: `GET /Groups?filter=displayName eq <value> and members.value eq <value>` (`vendor/zscaler-help/understanding-scim-zia.md:57`).

**Discovery endpoints** (`vendor/zscaler-help/understanding-scim-zia.md:64-73`):

- `GET /ServiceProviderConfig` — the SCIM service provider's capability document (`:67-68`); a connector reads this to learn what the server supports (e.g. PATCH, bulk, filtering).
- `GET /Schemas` and `GET /Schemas/{SchemaID}` — the resource schemas the server exposes (`:65-66`).
- `GET /ResourceTypes` and `GET /ResourceTypes/{ResourceTypeID}` — the resource types served (`:70-71`).
- `[prefix]/.search` (`POST`) — server-side search (`:72-73`). This is the endpoint the Go SDK `GetAllUsers`/`GetAllGroups` functions actually call (`/Users/.search`, `/Groups/.search` — `scim_user_api.go:108`, `scim_group_api.go:103`).

Operationally: if a connector cannot do incremental reconciliation against ZIA, the lever is `meta.lastModified gt` (delta) plus the `externalId`/`userName`/`id` equality filters (targeted lookups); if it cannot negotiate capabilities, check what `GET /ServiceProviderConfig` reports.

## 9. SCIM vs SAML attribute flow — a common conflation

SAML attributes and SCIM attributes arrive via completely different mechanisms:

| | SAML | SCIM |
|---|---|---|
| Trigger | User's authentication event | IdP's out-of-band provisioning push |
| Frequency | Every login | Periodic / event-driven (IdP-controlled) |
| Attributes available | Whatever the IdP includes in the SAML assertion | The mapped SCIM attribute set |
| User creation | JIT (first login creates the user if not present) | Pre-populated before first login |
| User deletion | Never (SAML does not deprovision) | `active=false` or `DELETE` |
| Session binding | At login time | Reflects last sync; may lag current IdP state |

Operators commonly ask why a user's group membership or department "changed in Okta but ZIA policy is still wrong." When SCIM is active, ZIA uses the SCIM-provisioned group and department values, not what's in the SAML assertion at login. If SCIM sync is delayed, ZIA policy will evaluate against stale group/department data even if the user's current SAML assertion contains updated attributes. This is the reverse of the ZPA problem where stale SCIM data can cause policy mismatches — in ZIA the same timing gap can manifest as stale department/group policy matches.

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-help/about-scim-zpa.md`.

The `userName` field must match the SAML `nameID` for the authentication to succeed and for ZIA to link the SAML session to the SCIM-provisioned user record. If these diverge (e.g., because a user's email address changed and only the SAML nameID was updated), the SCIM-provisioned record will not be linked to the user's session.

## 11. Operational gotchas

### First-time provisioning sync size

Source: `vendor/zscaler-help/understanding-scim-zia.md`.

For large tenants, the initial SCIM provisioning push may involve thousands of user and group records. The `/Bulk` endpoint (`POST /Bulk`) reduces round-trip overhead for large initial syncs. Operators should monitor the IdP's provisioning logs for error counts rather than treating the first sync as a fire-and-forget operation. ZIA admin console visibility into SCIM sync errors is not detailed in available vendor sources.

### ZIA user database as the policy resolution layer

Source: `vendor/zscaler-help/understanding-scim-zia.md`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_group_api.go`.

ZIA policy rules reference ZIA user, group, and department *objects* (by their Zscaler-side integer IDs). SCIM provisioning creates and updates these objects. When a SCIM connector is configured to scope only a subset of groups or users (a common IdP setting to limit what gets pushed to a given application), groups not in scope are never created in ZIA. ZIA policy rules that reference those groups will silently never match anyone. Unlike ZPA (which surfaces this as a stale-group reference issue), ZIA's problem manifests as "the group doesn't exist in the policy dropdown at all."

### Department name matching — potential silent failure

The `department` SCIM attribute is a string. ZIA matches it to an existing ZIA department object by name. If the string value the IdP sends does not exactly match an existing ZIA department name, the department association fails silently. The ZIA user record will exist but have no department assignment, causing department-scoped policy rules to miss that user. Operators should pre-create ZIA department objects with names matching what the IdP will send before enabling SCIM sync. (Tier D inference from SCIM object model and attribute mapping; exact match-or-fail vs match-or-create-new behavior is unconfirmed — deferred.)

### `department` requires the Enterprise User SCIM extension

Source: `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`.

As noted in section 2 and 5, the `department` attribute is carried in `urn:ietf:params:scim:schemas:extension:enterprise:2.0:User`. Some SCIM connectors send only the core schema (`urn:ietf:params:scim:schemas:core:2.0:User`) by default. Operators must verify their IdP's attribute mapping configuration includes the Enterprise User extension and maps the department attribute.

### `active=false` does not immediately kill sessions

ZIA's `active=false` sets a disabled flag on the user record. Whether this immediately terminates any active ZIA inspection session for that user is not documented in available vendor sources. Operators who need immediate access revocation (e.g., for terminated employees) should not rely on SCIM `active=false` alone as a session kill mechanism. (Deferred — see "## Open questions".)

### SCIM deprovisioning does not revoke tokens

Disabling or deleting a ZIA user via SCIM removes their access going forward but does not invalidate OAuth tokens or SAML sessions they may already hold. Hard revocation requires a ZIdentity token revocation call. See [`../zidentity/api-clients.md § Revocation`](../zidentity/api-clients.md).

### Python SDK gap for ZIA SCIM

Source: `vendor/zscaler-sdk-python/zscaler/zia/zia_service.py`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_user_api.go`; `vendor/zscaler-sdk-go/zscaler/zia/services/scim_api/scim_group_api.go`.

The Python SDK has no `scim_api` module exposed through `ZIAService`. Programmatic SCIM operations against ZIA (user or group CRUD via the SCIM endpoints) require either the Go SDK SCIM API service or direct HTTP. This is a notable parity gap since the Python SDK covers most other ZIA services.

## Open questions

These came up while documenting ZIA SCIM and could not be backed from any vendor file in this pass. All five are tracked together as `zia-64` in [`../_meta/clarifications.md`](../_meta/clarifications.md#zia-64-scim-department-matching-attribute-length-activefalse-session-kill-and-caps):

- **Department name that has no matching ZIA department object** — the `department` string is matched by name against an existing ZIA department object (section 3). Whether ZIA matches-or-fails (silent no-association) or matches-or-creates a new department when no match exists is not stated in any mined source. (Referenced inline in section 3 and the section 11 "Department name matching" gotcha.)
- **Attribute value length limits** — no mined source states a maximum character length for individual SCIM attribute values such as `displayName` or `department` (section 5).
- **Per-IdP Enterprise User extension mapping nuances** — how Entra ID vs Okta vs PingFederate populate the enterprise extension for `department` lives in per-IdP configuration guides not captured in available vendor sources (section 6).
- **`active=false` and live session termination** — whether disabling a user via `active=false` immediately terminates that user's active ZIA inspection session, or only blocks future authentication, is not documented (sections 7 and 11). For immediate revocation, do not rely on SCIM `active=false` alone.
- **SCIM-specific rate limits and tenant caps** — no published per-tenant max-users / max-groups cap or SCIM-endpoint-specific rate-limit guidance was found (section 10); treat as deferred until confirmed against live API responses or current vendor docs.
