# How the Go SDK retries requests (and replays writes) (shared.sdk-go.retries)
Also called: sdk retries; duplicate rule created; retry replays post; giving up after attempts; retryablehttp; api error lost after retries

These are claims about the Go SDK's HTTP client, shared by every product's OneAPI calls and so by the Terraform providers built on it.

**Retry policy.** The SDK's OneAPI client decides whether to retry from the context, the response and the error, never from the HTTP method: its policy stops once the context is done, retries configured status codes and edit-lock conflicts, then defers to the retryablehttp default. From v3.8.43 it also stops retrying a 5xx that carries a deterministic API verdict; before that, every 5xx except 501 was retried. [shared.sdk-go.retries:retry-policy-ignores-method] The retryablehttp default policy (`DefaultRetryPolicy`) does not retry once the request's context is cancelled or past its deadline; otherwise it defers to `baseRetryPolicy`, which retries transport errors other than redirect, scheme, header and certificate failures, 429, and 500-range responses other than 501. [shared.sdk-go.retries:default-retries-connection-errors] `ExecuteRequest` reads the request body into memory once and builds the request from a reader over that buffer. retryablehttp reads the body into its own buffer and gives every attempt a fresh reader over it, so POST and PUT bodies are resent intact by the inner retry loop in every audited SDK version. [shared.sdk-go.retries:body-buffered-for-replay] If the server commits a POST or PUT but the client then sees a transport error or a retryable 5xx, the SDK sends the same write again (through retryablehttp's inner loop in every audited version). A create can therefore be applied twice, or report failure after it succeeded. [shared.sdk-go.retries:write-replay-on-lost-response] Because the retry decision ignores the HTTP method, a GET is replayed on the same triggers as a POST or PUT, but the duplicate-change hazard needs a write the server may have committed: a replayed GET changes nothing on the server, and a request answered with 429 was declined rather than applied. The hazard is therefore confined to writes whose outcome the client did not see, or that failed with a retried 5xx or transport error. [shared.sdk-go.retries:replay-hazard-limited-to-writes] Whether a replayed create is rejected as a duplicate or creates a second object is open [gap:shared.sdk-go.retries:replay-outcome].

**Older SDK builds.** Before v3.8.43, when retries ran out the SDK returned retryablehttp's bare "giving up after N attempt(s)" error and lost the API's status and error body, and it retried 5xx responses that were permanent errors: the retry policy retried every 5xx except 501, and the OneAPI outer retry loop retried every 5xx. v3.8.43 (#449) hands the final response back and stops retrying deterministic 5xx. [shared.sdk-go.retries:exhaustion-hid-api-error-before-3-8-43] In the audited releases before v3.8.43 (v3.8.37, v3.8.40 and v3.8.42), the outer retry loop's rate-limit and 5xx paths resent the already-consumed request without rebuilding it, which for a POST or PUT means an empty body. v3.8.43 rebuilds the request from the buffered body on those paths. [shared.sdk-go.retries:outer-retry-reused-consumed-body-before-3-8-43] In practice this was rarely reached in the audited releases before v3.8.43: the inner retry loop runs first, and without the v3.8.43 error handler an exhausted inner loop returns an error, so the outer 5xx path saw mainly responses the inner loop never retries, such as 501. v3.8.43 made the outer paths reachable and fixed the body in the same release. [shared.sdk-go.retries:empty-body-resend-rarely-reached] Which SDK each audited provider build carries decides whether it has the v3.8.43 fix: ZIA provider 4.8.3 uses v3.8.44 (fixed); ZPA 4.4.10 uses v3.8.42, ZCC 0.1.0-beta.1 uses v3.8.37, and ZTC 0.2.0 uses v3.8.40 (all before the fix). ZTC 0.2.0 is still the pinned ZTC release. [shared.sdk-go.retries:provider-sdk-pins]

The OneAPI client's retry policy and the ZCC, ZDX, ZIA, ZPA, ZTW and ZWA v2 clients' retry policies all hand a 5xx response without a transport error to the shared `errorx.IsRetryableServerError` helper. [shared.sdk-go.retries:shared-5xx-classifier] The classification itself is [The legacy client's retry check hands every 5xx response to `IsRetryableServerError`. It never retries a status below 500 or 501, always retries 502, 503 and 504, retries any other 5xx whose body contains a transient marker (EDIT_LOCK_NOT_AVAILABLE, Resource Access Blocked, an org-barrier failure or a failed-precondition message), and otherwise refuses the retry only when the body is a JSON object with a nonempty string `code`.](kb:zia.sdk-go.legacy-retry-classification:five-xx-classification).

`MaxNumOfRetries` defaults to 10 and is the cap for both the retryablehttp inner loop (`RetryMax`) and the `ExecuteRequest` outer loop, which returns the last response's API error once the outer count passes the configured maximum. [shared.sdk-go.retries:max-retries-both-layers]

So with the default of 10, a request that keeps failing on a path both loops retry can be sent up to 110 times: ten outer executions, each an initial attempt plus ten inner retries. This is a client-side ceiling, not server behavior. [shared.sdk-go.retries:attempt-budget-110]

The ZCC client's `getHTTPClient` builds its retrying HTTP client, with the error handler that hands the final response back on exhaustion, only when no custom HTTP client is configured and `BackoffConf` is present and enabled; otherwise this function does not build it and returns `cfg.HTTPClient` as it is. [shared.sdk-go.retries:zcc-handler-conditional]

The ZPA provider's go.mod requires Go SDK v3.8.55 at both v4.4.14 and v4.4.15, and v3.8.56 at v4.4.16. [shared.sdk-go.retries:zpa-provider-sdk-pin-4-4-14]
