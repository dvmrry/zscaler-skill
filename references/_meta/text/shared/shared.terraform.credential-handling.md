# How the Zscaler Terraform providers store, log, and send secrets (shared.terraform.credential-handling)
Also called: terraform secret in state; terraform sensitive attribute; credential in terraform state; REDACTED password; ***REDACTED***; pra credential password wrong; terraform debug log secrets; ZSCALER_SDK_LOG secrets; pra credential password not cleared

Provider credentials for the SDK itself are covered in [How the Go SDK obtains and renews OneAPI tokens](kb:shared.sdk-go.auth-lifecycle); this subject is about secrets that pass through resources and data sources. Secrets can show up in three different places when a Terraform provider handles a credential: in the state file, in plan and CLI output, and in logs. The `Sensitive` flag on a schema attribute affects how Terraform displays the value in plan and CLI output, and whether it changes what is written to state or to a provider's own log lines is open [gap:shared.terraform.credential-handling:sensitive-flag-scope].

**ZIA data sources and state.** The ZIA `zia_dlp_cloud_to_cloud_ir` data source declares the nested `tenant_authorization_info` attributes `client_secret`, `user_pwd`, `secret_token`, `access_token` and `bot_token` as plain Computed strings. Unlike the provider's own `client_secret` argument, the schema does not set `Sensitive` on them. [shared.terraform.credential-handling:c2c-ir-secrets-not-sensitive] The same data source's flattener copies the secret-bearing members of the API response (`client_secret`, `secret_token`, `user_pwd`, `org_api_key`, `cred_json`, `credentials`, `access_token`, `bot_token`) into those attributes, so whatever the API returns for them is written into the data source's state. [shared.terraform.credential-handling:c2c-ir-secrets-copied-to-state] Two more ZIA data sources export credentials as plain Computed strings and write them to state: `zia_cloud_nss_feed` (`authentication_token`, `client_secret`; defined in `data_source_zia_cloud_nss_server.go`) and `zia_admin_users` (the `token` inside `exec_mobile_app_tokens`). [shared.terraform.credential-handling:cloud-nss-and-admin-token-in-state] Whether any of this reaches state in practice is open [gap:shared.terraform.credential-handling:api-returns-secrets].

**Other ZIA data sources.** The ZIA data sources are not uniform. In `zia_location_management` the nested `pre_shared_key` is marked `Sensitive: true`. In `zia_traffic_forwarding_vpn_credentials` the `Sensitive: true` line is commented out, and so is the line that would set `pre_shared_key` from the response, so that data source declares the attribute but does not populate it. [shared.terraform.credential-handling:zia-psk-handled-differently] No ZIA data source schema marks any of the secret-named attributes above `Sensitive`. Searching the ZIA data sources for attribute names containing secret, password, pwd, passphrase, token, api_key, psk, private_key, cred_json or credentials finds these unmarked instances: the Cloud-to-Cloud IR authorization attributes, `zia_cloud_nss_feed` `authentication_token` and `client_secret`, and `zia_admin_users` `token`. The matches that are not secrets (such as `is_password_login_allowed`) are ignored. A name search also misses values that can carry secrets under other names, such as the cloud NSS server's `connection_headers`. [shared.terraform.credential-handling:zia-data-source-secret-attributes-unmarked]

**ZIA data source logging.** The same data source logs `resp.OnboardableEntity` with `%+v`. That value is a pointer to a struct that holds `TenantAuthorizationInfo` by value, whose string members include `ClientSecret`, `SecretToken` and `UserPwd`, so the formatted line prints the secret-bearing members' contents. The line is prefixed `[DEBUG]` and has no redaction. [shared.terraform.credential-handling:c2c-ir-entity-log-includes-secrets] The line above it logs the whole response with `Retrieved cloud-to-cloud IR: %+v`. In the SDK's response struct, `OnboardableEntity` is a pointer field. [shared.terraform.credential-handling:c2c-ir-response-log-prints-pointer-only] So that line does not print the secrets: `%+v` prints a pointer field nested in a struct as an address, not the value it points to. [shared.terraform.credential-handling:c2c-ir-response-log-omits-secrets]

**PRA credential create.** `zpa_pra_credential_controller` create expands the configured secrets into the request struct, then calls `sanitizeFields(&req)` before sending it. `sanitizeFields` writes the literal `***REDACTED***` into the request's string fields whose lowercased name contains `password` or `passphrase`. The mutated struct is what is passed to `pracredential.Create`, so the create request carries the sentinel in `password` and `passphrase` instead of the configured values (including when those fields were left empty in the configuration). [shared.terraform.credential-handling:pra-create-sanitizer-mutates-request] The sanitizer compares the lowercased Go field name with `private_key`, but the struct field is `PrivateKey`, which lowercases to `privatekey` and does not contain `private_key`. So on create the SSH private key is not replaced: it is sent as configured, while `password` and `passphrase` are replaced. [shared.terraform.credential-handling:sanitizer-misses-private-key] The create path logs the request after sanitizing it, with `%+v`. Because the sanitizer leaves `PrivateKey` unchanged, that INFO log line contains the SSH private key in clear text when one is configured, while `password` and `passphrase` show the sentinel. The line is logged on every create, at INFO level. [shared.terraform.credential-handling:pra-create-log-prints-private-key] `sanitizeFields` is called in two places in the ZPA provider: PRA credential create and PRA credential pool create. The update path of the PRA credential does not call it. In the pool, the request struct has no field whose name contains `password`, `passphrase` or `private_key`, so the call changes nothing there. [shared.terraform.credential-handling:sanitizer-call-sites] The resource's read sets `name`, `description`, `credential_type`, `username` and `microtenant_id` and nothing else. The three secret attributes are `Sensitive: true` in the schema but are never refreshed from the API, so their state is whatever the configuration supplied. After a create that sent the sentinel, the next plan shows no difference for the secrets. Read does log the whole API response at INFO with `%+v`, which would print any secret the API returns (gap api-returns-secrets). [shared.terraform.credential-handling:pra-read-never-sets-secrets] What ZPA does with the sentinel is open [gap:shared.terraform.credential-handling:api-pra-sentinel].

**Updates and the PRA data source.** On update the provider expands the secrets with `d.Get` and passes the request to `pracredential.Update`. A secret that is empty in config becomes an empty Go string, and the SDK struct tags are `omitempty`, so the field is left out of the PUT body. An update cannot send an explicit empty value to clear a stored `password`, `passphrase` or `private_key`. [shared.terraform.credential-handling:pra-update-omits-empty-secrets] Whether the API clears a stored secret when the field is absent from a PUT, or keeps it, is open [gap:shared.terraform.credential-handling:api-pra-empty-secret]. The `zpa_pra_credential_controller` data source declares `password` as a Computed string without `Sensitive`, but its read never sets it, so the attribute is always empty. This is a missing output, and as written it keeps the password out of state. If it were set without also adding `Sensitive: true`, it would be a plain-text state value like the ZIA cases. [shared.terraform.credential-handling:pra-data-source-password-declared-not-set]

**SDK request and response logging.** When `ZSCALER_SDK_LOG` and `ZSCALER_SDK_VERBOSE` are both true, the SDK dumps API requests including their bodies, and API responses, in full. The OneAPI client leaves the body out for sandbox (`/zscsb`) requests and for its token request, whose response it does not log. Up to Go SDK v3.8.52 the dumps redacted neither secret fields nor the Authorization header. From v3.8.53 (#468) the SDK masks the values of credential headers (`Authorization`, `Cookie`, `Set-Cookie` and others) in the dumps, but only the header block is masked: bodies are still logged unredacted. The ZIA provider builds against the masking SDK from v4.8.11 (SDK v3.8.54) and documents the masking from that version; the ZPA provider v4.4.14 builds against SDK v3.8.55. The ZIA and ZPA providers set both variables through `WithDebug` whenever `TF_LOG` is DEBUG or TRACE, so ordinary provider debug logging is enough on the OneAPI path. The dumps are taken from the outgoing request (`DumpRequestOut`) and the received response (`DumpResponse`), so they show what is on the wire. [shared.terraform.credential-handling:sdk-logs-full-bodies-when-enabled] With the SDK dumps on, a PRA credential create dump shows the request body as sent: the `***REDACTED***` sentinel in `password` and `passphrase`, and the configured `privateKey`. A read dump shows any credential the API returns. [shared.terraform.credential-handling:pra-create-dump-shows-sent-secrets]

Related: [How the Go SDK obtains and renews OneAPI tokens](kb:shared.sdk-go.auth-lifecycle) covers how the SDK gets its own API credentials, and [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding) covers the `omitempty` behavior behind the update trap.

What to check:
1. Which of the ZIA data sources and PRA credential resources the configuration uses, since each one handles its secrets differently.
2. Whether debug-level provider logging (TF_LOG=DEBUG or TRACE), or both SDK log variables, is turned on in CI.
3. Whether state storage is access-controlled.
4. For PRA credentials, whether a credential created through the provider actually authenticates.

Inferred, not quoted (say so when an answer rests on one):
- [shared.terraform.credential-handling:c2c-ir-response-log-omits-secrets] Tier B: Rests on Go's fmt formatting, which prints the top-level pointer as &{...} but nested pointer fields as addresses; no vendor source states it.
- [shared.terraform.credential-handling:zia-data-source-secret-attributes-unmarked] Tier B: Absence claim from a search at tf-zia v4.8.3: `git grep -n -i -E '"[a-z_]*(secret|password|pwd|passphrase|token|api_key|psk|private_key|cred_json|credentials)[a-z_]*": *\{' v4.8.3 -- 'zia/data_source_*.go'`, with `git grep -n 'Sensitive: *true'` returning, among data sources, only `pre_shared_key` in `data_source_zia_location_management.go`. Attribute-name matching misses secrets with other names, and the search covers v4.8.3 only. The list names every unmarked secret attribute found, not every secret the API can return. Data source name corrected from zia_cloud_nss_server to the registered zia_cloud_nss_feed (zia/provider.go).
- [shared.terraform.credential-handling:pra-create-log-prints-private-key] Tier B: Depends on the provider's log output being enabled for that line (the INFO-prefixed line is written by the standard logger; how Terraform surfaces it is not shown here), and on the private key being set.
- [shared.terraform.credential-handling:pra-read-never-sets-secrets] Tier B: Absence search at tf-zpa v4.4.10 and HEAD: `git grep -n 'Set("password"\|Set("passphrase"\|Set("private_key"' <ref> -- zpa/resource_zpa_pra_credential_controller.go` returns nothing. That unset attributes keep their prior state value is Terraform plugin SDK behavior, not shown in this repository.
- [shared.terraform.credential-handling:pra-data-source-password-declared-not-set] Tier B: Absence search at tf-zpa v4.4.10 and HEAD: `git grep -n 'Set("password"' <ref> -- zpa/data_source_zpa_pra_credential_controller.go` returns nothing. The last sentence is a consequence of changing the code, not something the code does now.
- [shared.terraform.credential-handling:sanitizer-call-sites] Tier B: Search at tf-zpa v4.4.10 and HEAD: `git grep -n sanitizeFields <ref> -- zpa` returns the definition in zpa/utils.go, `zpa/resource_zpa_pra_credential_controller.go:126` and `zpa/resource_zpa_pra_credential_pool.go:109`.
- [shared.terraform.credential-handling:pra-create-dump-shows-sent-secrets] Tier B: Needs both SDK log variables true, which the ZIA and ZPA providers set through `WithDebug` when `TF_LOG` is DEBUG or TRACE on the OneAPI path. Request bodies are dumped unmasked in every audited SDK version, since the v3.8.53 masking covers only the header block. A read dump carries a credential only if the API returns it (gap api-returns-secrets).
