# ZIA admin roles and scope: rank, permissions, functional scope and the one-scope rule (shared.admin-rbac.zia)
Also called: zia admin scope; admin rank; department admin; location group admin; zia admin role types; default admin login; why can't this admin edit this rule

A ZIA admin is a role, which says what the admin can do, plus a scope, which says where. Each ZIA admin account comprises a role (an admin role or an SD-WAN partner API role), which sets which Admin Console features the admin can access, and a scope, which sets which areas of the organization, such as departments or locations, the admin can configure policies or settings for. [shared.admin-rbac.zia:role-and-scope]

**The role.** Zscaler provides a default super admin role with full access to the Admin Console and the Executive Insights App; every additional role is defined by an admin rank, permissions and a functional scope. [shared.admin-rbac.zia:role-parts] Admins who may manage roles can add, edit or delete only roles with less scope and lower rank than their own, and rank-based roles keep a lower-ranked admin from modifying the settings of a higher-ranked one. [shared.admin-rbac.zia:less-scope-lower-rank] A role's admin rank is shown only if admin ranking is enabled in Advanced Settings, and rank does not apply to SD-WAN partner API or API roles. Admin ranking is disabled by default and is enabled on the Advanced Settings page; if it is not enabled, only super admins (rank 0) can manage roles and permissions for other admins. [shared.admin-rbac.zia:rank-visibility] Admin role types are Standard Admin, SD-WAN Partner API, Executive App Admin and Standard & Executive App Admin; an API role has the type API Client. [shared.admin-rbac.zia:role-types] An API role, added in the Admin Console and then configured in an external OAuth 2.0 authentication server, dictates a client application's access to the API categories of the cloud service API, instead of the API passing an admin user, password and API key. [shared.admin-rbac.zia:api-role-oauth] How the Terraform provider validates role type and rank is in [The `role_type` validator on `zia_admin_roles` accepts ORG_ADMIN, EXEC_INSIGHT, EXEC_INSIGHT_AND_ORG_ADMIN, SDWAN and PUBLIC_API, so a role can declare PUBLIC_API in HCL without failing validation.](kb:zia.terraform.admin-identity:role-type-values) and [The `rank` attribute of `zia_admin_roles` is an optional integer with no range validator in the schema; its description gives 7 as the default and lowest rank and says it applies only when admin rank is enabled in Advanced Settings.](kb:zia.terraform.admin-identity:rank-unvalidated).

**The scope.** The default admin has scope over the whole organization; every other admin gets one scope of four kinds (Organization, Department, Location or Location Group), and location, location group and department cannot be combined. [shared.admin-rbac.zia:scope-kinds] Admins can define rules and settings only for their assigned locations, location groups or departments, and can edit a rule or setting only if their scope is equal to or greater than the scope assigned to it; admin rank also affects which rules and settings an admin can edit. [shared.admin-rbac.zia:scope-limits-rules] An admin who may manage admins can assign other admins only scope within their own scope. [shared.admin-rbac.zia:scope-limits-delegation] Only admins with scope over the entire organization can create or edit organization-wide policies, settings and resources, such as security policies and custom URL categories. [shared.admin-rbac.zia:org-scope-for-org-wide] Location groups, which a scope can name, are in [Location groups: manual and dynamic, conditions, limits, predefined groups](kb:zia.locations.groups).

**Admin rank.** Admin rank ranges from 0 (high) to 7 (low); the highest rank, 0, belongs to the super admin, and each additional role can be given a rank between 1 (high) and 7 (low). [shared.admin-rbac.zia:rank-range] [shared.admin-rbac.zia:rank-visibility] Admin rank creates a hierarchy between admins and ensures that policies and settings configured by admins with a higher rank cannot be overridden by admins with a lower rank. [shared.admin-rbac.zia:rank-purpose] The admin rank page lists the rule-based policies Sandbox (which requires Advanced Sandbox), URL & Cloud App Control, File Type Control, Bandwidth Control, Data Loss Prevention, Mobile App Control, Firewall Control and DNS Control, and says an admin creating a rule in those policies must assign it an admin rank lower than their own; the rule's admin rank in turn automatically determines the rule order, so rules with a higher admin rank are always given precedence, and rules with the same admin rank can be manually moved before or after another rule with the same rank. [shared.admin-rbac.zia:rule-rank-sets-order] The pages differ on the bound for a new rule [divergence:shared.admin-rbac.zia:new-rule-rank-bound], and the rank of a rank 7 admin's rules is open [gap:shared.admin-rbac.zia:rank-seven-rule-rank]. An admin can edit a rule, or change its place in the rule order, only if the rule's admin rank is equal to or lower than the admin's own admin rank. [shared.admin-rbac.zia:rule-edit-by-rank] The admin rank page says admins with permission to manage roles can only create or edit roles with a lower rank, and admins with permission to manage other admin accounts can only create, edit or view accounts with a lower rank. [shared.admin-rbac.zia:rank-roles-and-accounts] The obfuscation pages allow an equal rank for another admin's account [shared.admin-rbac.zia-obfuscation:equal-rank-vs-lower-rank](kb:shared.admin-rbac.zia-obfuscation:equal-rank-vs-lower-rank). Admins are also users that can be specified in a rule's criteria (for example, an admin can be chosen as a user to whom a URL Filtering rule applies); if an admin adds another admin as a user for a rule, they can only select admins that have a lower admin rank. [shared.admin-rbac.zia:rank-admins-as-rule-users] A role's default rank is open [gap:shared.admin-rbac.zia:default-role-rank].

**Setting it up.** Zscaler recommends adding roles before admins, because each admin needs a role. The configuration order is: admin roles or SD-WAN partner API roles; then users or SD-WAN partner API clients (the SD-WAN partner API role is selected when adding the client); then the Internet & SaaS administrative entitlement, where the admin role is selected; then, optionally, auditors. [shared.admin-rbac.zia:roles-before-admins] The permissions a role carries are in [ZIA admin role permissions: logs limit, dashboard, reporting, insights and alerts access, and the feature categories](kb:shared.admin-rbac.zia-permissions), who sees obfuscated user names and device information is in [Who sees real user names, device information and Gen AI prompts in ZIA: role obfuscation and auditors](kb:shared.admin-rbac.zia-obfuscation), and API roles and SD-WAN partner API roles are in [ZIA API roles, SD-WAN partner API roles and SD-WAN partner API clients](kb:shared.admin-rbac.zia-api-roles).

**Admin accounts.** The default admin account has full access and full scope; it can be enabled or disabled but not deleted. The new default admin login ID has the form admin@<Organization ID>.<Zscaler Cloud>.net, cannot be used to log in to the Zscaler service and browse the internet, and is the only admin for which password reset is supported. [shared.admin-rbac.zia:default-admin] On the ZIA Administrators page an existing admin's scope and update-notification enrollment are the only things that can be edited; admins themselves are configured with Authentication Service, while SD-WAN partner API clients are created on that page. [shared.admin-rbac.zia:admins-page-scope-only] Removing admin privileges while keeping the user is a separate call from deleting the admin: [The API specification describes `POST /adminUsers/{userId}/convertToUser` as removing a user's admin privileges while keeping them as a regular user, as an alternative to DELETE, which removes the admin and also removes them as a user. It says the admin user's details are first obtained with `GET /users` and then sent in the convert request.](kb:zia.sdk-python.service-behaviors:convert-to-user-spec). Failed sign-ins and their lockout are recorded in the audit log: [An admin account that makes 5 unsuccessful login attempts within 1 minute is locked out for 5 minutes, and the failed attempts are recorded in the audit log.](kb:zia.audit-logs.what-is-recorded:lockout-recorded).

What to check:
1. The admin's scope kind and value against the rule's locations, location groups or departments: an admin edits a rule only with equal or greater scope, and rank also counts.
2. Whether the change needs organization scope (security policies, custom URL categories, organization-wide settings).
3. For an admin who must cover a region, whether one location group can express it, since location, location group and department scopes cannot be combined; otherwise a second admin account or organization scope.
4. For a role edit that fails, whether the editing admin's own scope and rank exceed the role's.

Sources disagree (name both sides):
- What rank an admin may give a new rule: the admin rank page says lower than the admin's own, while the URL Filtering and Cloud App Control rule pages say the admin cannot select a rank higher than their own, which allows an equal rank. The existing claims are [[zia.url-filtering.rule-order:admin-rank-precedes]], [[zia.cloud-app-control.precedence:admin-rank]] and [[zia.casb.dlp-rules:admin-rank]], which quote the same wording for their policies. [divergence:shared.admin-rbac.zia:new-rule-rank-bound]
  - zscaler-help: Admin rank page: the rule's admin rank must be lower than the admin's own.
  - zscaler-help: URL Filtering policy page: the admin cannot select a rank higher than their own.
  - zscaler-help: Cloud App Control consumer rule page: the admin cannot select a rank higher than their own.
  Impact: Whether an admin can give a new rule a rank equal to their own is not settled; the rank page elsewhere lets an admin edit a rule of equal rank ([[shared.admin-rbac.zia:rule-edit-by-rank]]).
