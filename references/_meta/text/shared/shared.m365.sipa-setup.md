# Configuring Source IP Anchoring for Microsoft 365 sign-in (shared.m365.sipa-setup)
Also called: configure sipa for office 365; office 365 application segment source ip anchor; login.microsoftonline.com app segment; m365 sipa client forwarding policy; m365 sipa access policy zia service edge; m365 sipa forwarding rule zpa gateway

The vendor's Microsoft 365 article specialises the general Source IP Anchoring setup in the same order, Private Access first and then Internet & SaaS. Where the two articles agree, this subject links the general claim.

## Private Access side

1. **Initial setup, if Private Access is used only for anchoring.** [When Private Access is used solely for Source IP Anchoring, the initial setup still needs company and administrator information, App Connector enrollment certificates (only those are sufficient) and configured App Connectors.](kb:zia.forwarding-control.sipa:pa-solely)
2. **Application segment.** The hosts and ports: [The Office 365 application segment for anchoring names login.microsoftonline.com (login.windows.net or login.microsoft.com are alternatives), on TCP 80 and 443.](kb:zia.saas-apps.conditional-access:login-hosts) The Source IP Anchor option and the bypass setting: [On the Private Access application segment, the Source IP Anchor option must be enabled and Use Client Forwarding Policy selected under Bypass.](kb:zia.forwarding-control.sipa:segment-settings)
3. **Segment group and server group.** The Office 365 application segment needs a segment group and a server group, and the server group must be associated with the configured App Connector group. [shared.m365.sipa-setup:segment-and-server-group]
4. **Client forwarding policy.** The Microsoft 365 article says to select Only Forward Allowed Applications as the rule action of the client forwarding policy for the Office 365 application segment. [shared.m365.sipa-setup:client-forwarding-action] The general article prescribes a different rule pair for a domain-based segment such as this one [divergence:shared.m365.sipa-setup:client-forwarding-rules].
5. **Access policy.** The access policy for the Office 365 application segment allows access only to the ZIA Service Edge client type. [shared.m365.sipa-setup:access-zia-service-edge-only] User-based SAML or SCIM criteria stay off this rule: [If Source IP Anchoring traffic is restricted to certain users in the Zscaler Admin Console, do not add user-based SAML/SCIM criteria to the access policy for the Source IP Anchoring application segment.](kb:zia.forwarding-control.sipa:no-user-criteria)

## Internet & SaaS side

1. **Private Access gateway and forwarding rule.** The Private Access gateway for the Office 365 segment selects the server group created for it, and a forwarding rule uses the ZPA forwarding method, takes trust criteria such as location and users on its General tab, selects the Office 365 segment on its Destination tab, and selects that gateway under Forward to ZPA Gateway. [shared.m365.sipa-setup:gateway-and-forwarding-rule] The gateway object and its segment list: [The Private Access gateway object in ZIA](kb:zia.forwarding-control.zpa-gateway).
2. **DNS Control.** The two predefined resolver rules, enabled and ranked first: [Anchoring for Microsoft 365 also needs the preconfigured DNS Control rules enabled and ranked first: ZPA Resolver for Locations for location users and ZPA Resolver for Road Warrior for remote users. If the Road Warrior rule is disabled, remote traffic falls under the Locations rule rather than being blocked.](kb:zia.saas-apps.conditional-access:dns-resolver-rules) Their relative order and the case against disabling the Road Warrior rule: [The Road Warrior resolver rule should be a higher rule (lower number) than the Locations resolver rule; for example Road Warrior at rule 4 and Locations at rule 5 or later.](kb:zia.dns-control.predefined-rules:road-warrior-above-locations), [Zscaler does not recommend disabling ZPA Resolver for Road Warrior: road warrior traffic then falls under the Locations resolver rule instead of being blocked, is resolved from the Locations IP pools, and is not routed as intended.](kb:zia.dns-control.predefined-rules:dont-disable-road-warrior). The DNS rules enabled for anchoring, ZPA Resolver for Locations and ZPA Resolver for Road Warrior, are each associated with their preconfigured IP pool, and a change to the pool shows in the rule's Action column while the rule is enabled. [shared.m365.sipa-setup:ip-pool-in-action]
3. **Z-Tunnel 1.0 and PAC remote users.** [To support Source IP Anchoring for Z-Tunnel 1.0 traffic, Enable Firewall for Z-Tunnel 1.0 and PAC Road Warriors must be on in Advanced Settings.](kb:zia.forwarding-control.sipa:ztunnel1-option)

The Microsoft side (named locations and the Conditional Access policy) has no captured source; its open questions are in [Why a Microsoft 365 sign-in is still challenged or blocked with Source IP Anchoring](kb:shared.m365.troubleshooting).

What to check:
1. Which client forwarding rules the Office 365 segment's segment group actually has: one Only Forward Allowed Applications rule, or the Bypass ZPA and Forward to ZPA pair. Record which, since a disaster recovery switch changes them differently.
2. That the gateway names the server group whose connector group holds the anchoring App Connectors, and the forwarding rule names that gateway and the Office 365 segment.
3. That both ZPA resolver DNS rules are enabled at the top of DNS Control, Road Warrior above Locations, and which IP pool each shows in its Action column.

Sources disagree (name both sides):
- The Microsoft 365 article gives the Office 365 segment, which is defined by domain names, the Only Forward Allowed Applications action; the general Source IP Anchoring article reserves that action for IP address-based segments and gives domain-based segments a Bypass ZPA and Forward to ZPA rule pair. [divergence:shared.m365.sipa-setup:client-forwarding-rules]
  - zscaler-help: Select Only Forward Allowed Applications in the client forwarding policy for the Office 365 application segment.
  - zscaler-help: Only Forward Allowed Applications is for IP address-based applications; domain-based applications get Rule 1, Bypass ZPA for all client types except ZIA Service Edge, and Rule 2, Forward to ZPA for only the ZIA Service Edge client type.
  Impact: Which client forwarding rules to build for the Microsoft sign-in segment, and therefore which rule the disaster recovery switch to Source IP Anchoring Direct has to change. Neither article says what Client Connector traffic to the sign-in hosts does under the other form.
