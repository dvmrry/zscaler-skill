# How the Zscaler MCP server confirms deletes: elicitation, HMAC tokens and request state (shared.mcp-server.delete-confirmation)
Also called: mcp delete confirmation; confirmation_token; ZSCALER_MCP_SKIP_CONFIRMATIONS; ZSCALER_MCP_REQUEST_STATE_KEYS; ZSCALER_MCP_CONFIRMATION_TTL; mcp elicitation; InputRequiredResult; requestState; mcp hmac token; mcp multi-replica writes

Registration decides whether a write tool exists at all ([Which tools a Zscaler MCP server registers: toolsets, entitlements and the write gate](kb:shared.mcp-server.tool-inventory)); this covers what happens when one is called. Only delete tools carry the confirmation channel; create and update tools execute directly once the operator has enabled them through `--write-tools`. The delete gate runs before any SDK mutation. [shared.mcp-server.delete-confirmation:creates-updates-direct] Version 0.15.0 removed `ZSCALER_MCP_SKIP_CONFIRMATIONS`, so delete confirmation cannot be switched off; to deny deletes, leave them out of `--write-tools` / `ZSCALER_MCP_WRITE_TOOLS`. [shared.mcp-server.delete-confirmation:skip-confirmations-removed]

## Native elicitation

For a client that supports MCP elicitation, a delete asks a person to choose `delete` or `cancel`, and anything other than `delete` aborts without calling the Zscaler API. [shared.mcp-server.delete-confirmation:elicitation-choice] On revision `2026-07-28` and later the question is returned as an `InputRequiredResult` and the call resumes when the client retries with `input_responses` plus the sealed `request_state`; on `2025-11-25` and earlier a standalone `elicitation/create` request is sent mid-call. [shared.mcp-server.delete-confirmation:revision-transport] A declined, cancelled or unrecognized elicitation outcome, or an answer other than `delete`, returns text saying the operation was NOT performed; an unanswered confirmation must never fall through to the mutation. [shared.mcp-server.delete-confirmation:fail-closed] If checking the client's elicitation capability fails for an unexpected reason, the delete is refused as a server-side fault instead of falling back to the token. [shared.mcp-server.delete-confirmation:capability-check-failure]

## The token fallback

A client that did not advertise the `elicitation` capability falls back to the HMAC confirmation token: the first call returns a confirmation prompt carrying a token, and the agent retries with `confirmation_token`. [shared.mcp-server.delete-confirmation:token-fallback] The token is bound to the tool and its parameters (a mismatch is rejected), expires after `ZSCALER_MCP_CONFIRMATION_TTL` seconds (default 300), and is single-use; it is not bound to a principal, so any authenticated caller holding it can redeem it. [shared.mcp-server.delete-confirmation:token-properties] The agent receives the token and can redeem it in the same turn, so the fallback does not ensure a person approved the delete; the prompt tells the agent to ask the user and wait, which the code describes as advisory, not enforcement. [shared.mcp-server.delete-confirmation:token-agent-redeemable] The token's signing key and its spent-token ledger exist only in the process that minted it, so a token is not valid on another replica or after a restart; the key is deliberately not configurable. [shared.mcp-server.delete-confirmation:token-single-process]

## Request state across replicas

`requestState` is sealed with AES-256-GCM plus expiry, request binding and principal binding, so an answered confirmation cannot be moved to a different call or principal. [shared.mcp-server.delete-confirmation:request-state-sealing] Sealed request state is not single-use: re-sending an identical approved call within the TTL executes again, limited by the bindings to the same delete of the same resource by the same caller. [shared.mcp-server.delete-confirmation:request-state-not-single-use] Without `ZSCALER_MCP_REQUEST_STATE_KEYS` each process uses a key generated at startup, so a restart invalidates pending confirmations and another replica cannot decrypt them. With it, the first key seals and every listed key unseals, allowing rotation; it accepts a JSON array or a comma-separated list, and the SDK requires at least 32 bytes per key. [shared.mcp-server.delete-confirmation:request-state-keys] A shared key ring is required for multi-replica HTTP deployments with write tools; sticky sessions do not substitute on `2026-07-28`, whose requests carry no session ID. [shared.mcp-server.delete-confirmation:request-state-replicas] Request state is bound to the authenticated caller in every HTTP auth mode: verified token claims for `jwt` and `oidc`, the OneAPI client ID for `zscaler`, and a domain-separated fingerprint of the key for `api-key`; with authentication disabled there is no principal to bind. [shared.mcp-server.delete-confirmation:principal-binding]

What to check:
1. Whether the client advertises the MCP elicitation capability; without it, deletes fall back to a token the agent can redeem itself.
2. For HTTP deployments with more than one replica and write tools, whether ZSCALER_MCP_REQUEST_STATE_KEYS is set to a shared key ring.
3. To forbid deletes outright, whether delete patterns are left out of the write allowlist, since confirmation itself cannot be turned off.
