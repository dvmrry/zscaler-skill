# What the ZIA deployment and operations guides say about authentication, bandwidth, Cloud App Control, URL filtering, DNS, firewall, IPS and Isolation (shared.deployments.zia.policy-controls)
Also called: zia deployment and operations guide; zia d&o guide

IP Surrogacy maps a private IP to a new user when a different user logs in from it; if the mapping changes more than three times in a minute, the service stops mapping users to that IP for 5 minutes and applies location policies to transactions that do not support authentication. Zscaler discourages IP Surrogacy on shared hosts. [shared.deployments.zia.policy-controls:auth-ip-surrogacy-churn] The surrogate IP mechanics are in [Surrogate IP: mapping a private IP to an authenticated user](kb:zia.authentication.surrogate-ip).

**Authentication.** The refresh time for revalidating IP Surrogacy must be shorter than the DHCP lease time, otherwise ZIA might apply the wrong user policies; Zscaler recommends a Refresh Time shorter than Idle Time to Disassociation. [shared.deployments.zia.policy-controls:auth-surrogacy-refresh-vs-dhcp] Without Zscaler Client Connector, Zscaler uses cookie-based authentication for most traffic; with cookie-based authentication SSL inspection must be enabled for TLS-encrypted destinations, and where it is not, IP Surrogacy maps transactions to the previously authenticated user. [shared.deployments.zia.policy-controls:auth-cookie-ssl-requirement] URL Filtering assumes an implicit Allow All rule as a last resort, so unauthenticated traffic is allowed by default; restricting it needs specific URL filtering rules. [shared.deployments.zia.policy-controls:auth-unauthenticated-allowed] Zscaler recommends SCIM-based provisioning for real-time synchronization and Identity Federation using SAML for authentication; SAML auto provisioning does not support real-time synchronization, so new groups must be synchronized manually and users must reauthenticate. [shared.deployments.zia.policy-controls:auth-recommended-methods] Users that are not correctly mapped in Insights and Interactive Reports: check whether IP Surrogacy is enabled and multiple users authenticate from the same private IP. [shared.deployments.zia.policy-controls:auth-unmapped-users-fix]

**Bandwidth Control.** Bandwidth Control requires ZIA Business Edition and later or the Bandwidth Control Add-On. [shared.deployments.zia.policy-controls:bw-subscription] The Bandwidth Control deployment guide says about five to seven percent of TCP traffic is overhead that Bandwidth Control does not count, and sets a location's ZIA bandwidth 10 to 15 percent below the measured traffic (100 Mbps measured becomes 85 Mbps). [shared.deployments.zia.policy-controls:bw-overhead-setting] The margin below measured bandwidth is [divergence:shared.deployments.zia.policy-controls:bw-margin]. On a sub-location with Enforce Bandwidth Control disabled, it uses the shared bandwidth; with Override, its defined bandwidth is dedicated and no other sub-location can use it whether or not it has traffic; with Disabled no Bandwidth Control policies are applied, while they are applied for Use Location Bandwidth. [shared.deployments.zia.policy-controls:bw-sublocation-modes] When Bandwidth Control is not applied as expected, one check is the user's location, because Bandwidth Control policies are not enforced for remote users. [shared.deployments.zia.policy-controls:bw-troubleshoot-remote] For a bandwidth-controlled productivity app with performance issues at peak hours, the guide suggests increasing the policy's minimum bandwidth percentage in five percent steps, testing between steps. [shared.deployments.zia.policy-controls:bw-min-tuning] The product-level behavior is in [Which traffic Bandwidth Control covers: locations and limits](kb:zia.bandwidth-control.location-scope).

**Cloud App Control.** The default Cloud App Control policy behavior is Allow All, and rules are evaluated top to bottom; Cloud App Control policies do not support custom End User Notifications. [shared.deployments.zia.policy-controls:cac-defaults] A rule that explicitly allows a cloud app applies only Cloud App Control and not URL Filtering unless Allow Cascading to URL Filtering is enabled; for an allowed cloud app that Zscaler is blocking, the troubleshooting step is to verify that Allow Cascading to URL Filtering is enabled and, if so, that a corresponding URL filtering rule allows the traffic. [shared.deployments.zia.policy-controls:cac-cascading] For users who can still access a blocked cloud app, the guide says to verify that their transactions are visible in Web/Firewall Insights (if not, it is possible the traffic goes direct and bypasses the rules; the PAC file / Proxy settings can block the traffic), and to check Firewall Insights for QUIC, disabling QUIC in browser settings if it is used. [shared.deployments.zia.policy-controls:cac-quic-bypass] Precedence against URL Filtering is in [Cloud App Control versus URL Filtering: which applies](kb:zia.cloud-app-control.precedence).

**URL Filtering.** By default the Cloud App Control policy takes precedence over the URL filtering policy; URL filtering rules are applied on a first-match basis, and the Zscaler default policy allows access. [shared.deployments.zia.policy-controls:url-precedence-and-first-match] More specific custom category entries take precedence: a rule on a wildcard category is not applied if the destination is defined more specifically in another category, even when the wildcard rule is higher in the rule order (example: .example.com in CUSTOM_C1 and www.example.com in CUSTOM_C2). [shared.deployments.zia.policy-controls:url-custom-category-specificity] ZIA might not enforce rules on certain criteria without SSL inspection or Zscaler Client Connector; Enforce SafeSearch requires SSL Inspection; rules with Request Method or Protocol criteria may misbehave on uninspected transactions. [shared.deployments.zia.policy-controls:url-ssl-dependent-criteria] A troubleshooting item in the guide: where the category check shows a site as MISCELLANEOUS_OR_UNKNOWN but other rules apply, check whether AI/ML categorization is enabled, which automatically assigns certain categories to uncategorized sites. The guide also notes that blocking miscellaneous URLs might impact users until the URL is categorized. [shared.deployments.zia.policy-controls:url-misc-aiml] See [ZIA URL Filtering](kb:zia.url-filtering).

**DNS Control.** The DNS Control proxy model has a Transit option (passes DNS requests through the proxy, hiding the customer IP from third parties including the external resolver, security policy still applied) and a Resolver option (intercepts and resolves the request at the Public Service Edge); Zscaler recommends Resolver. [shared.deployments.zia.policy-controls:dns-modes] Traffic can reach Zscaler's Trusted DNS Resolver by enabling a NAT control rule or using Z-Tunnel 2.0 with specified DNS exclusions and inclusions. [shared.deployments.zia.policy-controls:dns-reach-trusted-resolver] Internal domains blocked or inaccessible: check whether they are in DNS exclusions. Iterative queries unresolved: disable the default NAT Control rule or create a higher-precedence rule so iterative queries can transit ZIA. [shared.deployments.zia.policy-controls:dns-troubleshooting] See [ZIA DNS Control](kb:zia.dns-control).

**Firewall and IPS.** Firewall deployment starts from a Standard or Advanced Firewall subscription; rules should be built with specific rules first and less specific last, and should be created in a disabled state then gradually enabled with a controlled per-location test. [shared.deployments.zia.policy-controls:fw-subscription-and-order] Firewall is enabled for Z-Tunnel 1.0 and PAC remote users via the advanced settings, and the guide also lists ensuring traffic is forwarded to the ZIA Firewall from Zscaler Client Connector using Z-Tunnel 2.0; transactions logged as Allow due to insufficient app data in Firewall Insights might relate to a match from the DPI mechanism and a specific rule. [shared.deployments.zia.policy-controls:fw-remote-and-insufficient-data] IPS Control requires ZIA Transformation Edition and later or an Advanced Firewall subscription; Firewall Control and IPS Control are enabled by default for Client Connector Z-Tunnel 2.0 remote users, and IPS can be enabled for Z-Tunnel 1.0 and PAC remote users by enabling Firewall Control. [shared.deployments.zia.policy-controls:ips-subscription-defaults] Detected threats for web and non-web traffic display in Firewall Insights > Logs, while web-only threats also appear in the Security Dashboard; SSH tunneling is blocked or allowed for the whole tenant and cannot be allowed for specific users or groups. [shared.deployments.zia.policy-controls:ips-logs-and-ssh] The Firewall guide's product limits are open [gap:shared.deployments.zia.policy-controls:firewall-product-limits]. See [ZIA Firewall Control](kb:zia.firewall) and [IPS Control](kb:zia.firewall.ips).

**Isolation.** Isolation needs a ZIA subscription and the Isolation add-on; HTTPS destinations need SSL inspection to be redirected to Isolation; Isolate is available only for known user agents (Other cannot be chosen); it works only with HTTP and HTTPS in the web browser; latency should be below 100 ms, which the guide says to check through the isolation browser menu. [shared.deployments.zia.policy-controls:isolation-requirements] The menu item that shows Isolation latency is open [gap:shared.deployments.zia.policy-controls:isolation-latency-measure]. Isolation requires configuring the service URLs in its table, including .files.rbi.zscaler.com (shares files between isolation and the user machine, bypassed from isolation) and .isolation.zscaler.com (connects to the isolation service; SSL inspection bypassed by default), both on 443/HTTPS. [shared.deployments.zia.policy-controls:isolation-service-urls]

Sources disagree (name both sides):
- How much of a location's bandwidth to set as the Bandwidth Control limit: the deployment guide says 10 to 15 percent below measured traffic (85 of 100 Mbps), the Bandwidth Control article says only 70–80% of the overall bandwidth per location. [divergence:shared.deployments.zia.policy-controls:bw-margin]
  - zscaler-help: Set the location bandwidth 10 to 15 percent less than the measured traffic, for example 85 Mbps for a 100 Mbps location.
  - zscaler-help: Only 70–80% of the overall bandwidth per location is the ideal setting for upload and download limits.
  Impact: A location limit of 85% sits outside the 70–80% range, so the value to configure depends on which page is followed; neither page reconciles the two.
