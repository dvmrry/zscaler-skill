# What the ZIA deployment and operations guides say about Sandbox, Threat Protection, DLP, SaaS Security and SSL inspection (shared.deployments.zia.threat-and-data)
Also called: zia deployment and operations guide sandbox; zia d&o guide threat protection

**Advanced Sandbox.** Advanced Sandbox scans more file types than .exe and .dll (including .jar, archives, scripts in MS files, MS macros, .pdf, .swf and .apk), scans files larger than 2 MB, and quarantines files via configuration rules; it requires ZIA Transformation Edition and later or the Advanced Sandbox Add-On. [shared.deployments.zia.threat-and-data:sandbox-advanced-vs-basic] For unknown PDF or Microsoft Office files the service does an initial static analysis for active content: files with active content go to the Sandbox for behavioral analysis, others are classified benign and allowed. Allowing subsequent downloads lets a user download a Sandbox-classified malicious file; Zscaler recommends disallowing them except for testing. [shared.deployments.zia.threat-and-data:sandbox-static-analysis] Any Sandbox rule that applies to unauthenticated traffic must apply to all groups and departments. [shared.deployments.zia.threat-and-data:sandbox-unauth-rules] See [ZIA Sandbox](kb:zia.sandbox).

**Threat Protection.** ATP security exceptions also apply to Malware Protection but not vice versa, and ATP exceptions also cover Sandbox policies; allowing a destination across all of Zscaler requires exceptions in ATP, URL Filtering and File Type Control policies; threat protection policies are global for all users. [shared.deployments.zia.threat-and-data:threat-exceptions] Malware Protection, ATP and Mobile Malware Protection work separately from the URL and Cloud App policies and are handled by separate Zscaler features. [shared.deployments.zia.threat-and-data:threat-separate-from-url]

**DLP.** DLP requires ZIA ELA Edition or a Data Loss Prevention subscription; new policies should be monitored first and the action changed to Block when false positives are low; the guide suggests starting with alerts for a small subset of users and applications. [shared.deployments.zia.threat-and-data:dlp-subscription-and-rollout] A DLP policy can monitor or block with Zscaler DLP engines, with or without forwarding to a third-party DLP solution, or use criteria and forward to a third party without Zscaler engines; the guide says a policy can be used with or without content inspection. [shared.deployments.zia.threat-and-data:dlp-third-party-options] The message 'Error: unable to update SSH public key' is directed to the Configuring the Zscaler Incident Receiver article. [shared.deployments.zia.threat-and-data:dlp-ssh-key-error] See [ZIA Data Loss Prevention](kb:zia.dlp).

**SaaS Security.** SaaS Security API is an out-of-band CASB that prevents data exposure and ensures SaaS app compliance; it scans data repositories and retains historical data for cloud applications, while the inline (proxy-based) solution is through ZIA Cloud App Control, Threat Protection, Sandboxing, DLP and URL Filtering. [shared.deployments.zia.threat-and-data:saas-out-of-band] A SaaS Security DLP policy requires DLP to be configured first; exceptions fail to work when the username assigned in ZIA does not match the username of the scanned folder in the SaaS tenant (for example joe.blogs@xyz.com versus joe.blogs@abc.com). [shared.deployments.zia.threat-and-data:saas-dlp-first-and-exceptions] See [ZIA CASB (SaaS Security API): scanning data at rest in sanctioned SaaS applications](kb:zia.casb).

**SSL inspection.** Mobile applications often use certificate pinning, which prevents SSL Inspection from working correctly; for a pinned app, the SSL Inspection deployment guide says to exempt it by removing the cloud application or the individual domains from SSL Inspection using custom URL categories. Web transaction content inspection takes place in memory and is never written to disk; Zscaler supports private keys in cloud hardware security modules (HSM). [shared.deployments.zia.threat-and-data:ssl-guide-pinning-and-troubleshoot] What to do with a pinned app is [divergence:shared.deployments.zia.threat-and-data:pinned-app-handling]. A legitimate site being blocked can come from policies that are too restrictive on the minimum Transport Layer Security (TLS) version; using the default Zscaler intermediate certificate requires clients to install the Zscaler root certificate or they see browser and application warnings. [shared.deployments.zia.threat-and-data:ssl-guide-minimum-tls] See [ZIA SSL/TLS inspection](kb:zia.ssl-inspection) and [What the Internet & SaaS TLS and SSL Inspection Leading Practices Guide recommends for rollout, rule layout, bypasses and certificates](kb:shared.deployments.zia.tls-leading-practices).

Sources disagree (name both sides):
- What to do with an application that uses certificate pinning: the SSL Inspection deployment guide says to exempt it from SSL Inspection, while the SSL Inspection leading practices guide says to replace the application, bypass only if it is of high value, and otherwise deny the traffic. [divergence:shared.deployments.zia.threat-and-data:pinned-app-handling]
  - zscaler-help: If certificate pinning is in place, exempt the applications from SSL Inspection by removing the cloud application or the individual domains from SSL Inspection.
  - zscaler-help: Replace the application if possible; bypass inspection only if the application is of such high value that the risks of not inspecting are worth it; otherwise deny the traffic.
  Impact: Whether a pinned app is exempted by default or only as an exception to a deny decides whether its traffic goes uninspected; the two guides do not reconcile this.
