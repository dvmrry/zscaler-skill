# How the Go SDK pages through ZPA, ZCC and ZTC lists, and when it stops early (shared.sdk-go.list-pagination)
Also called: sdk pagination; list returns only first page; missing objects in list; totalPages; startIndex itemsPerPage; ReadAllPagesV2; ztw pagination; zcc pagination skip; import by name not found

These are claims about the Go SDK's list helpers and the Terraform providers built on them, not about how ZPA, ZCC or ZTC behave. The helpers decide when a list is "finished" from the response they get. When one of these helpers returns a truncated list without an error, an object that exists but sits beyond the returned part is absent from the result, and a caller that searches the result for it gets the same outcome as for an object that does not exist. [shared.sdk-go.list-pagination:truncated-list-reads-as-absent-object]

**ZPA paging.** ZPA list pages are decoded with `totalPages` as an untyped value; it is turned into an int by formatting it as text and parsing, and the parse error is discarded. A missing, null or non-numeric `totalPages` becomes 0, and the helper returns that page's list with no error. [shared.sdk-go.list-pagination:zpa-total-pages-parse-error-ignored] The ZPA page loop starts at page 2 and runs while `page <= totalPages`, where `totalPages` is overwritten by every page it reads. If page 1 reports 0 pages, no further page is requested; if a later page omits the field, the loop ends there. Either way the result is returned as a success. [shared.sdk-go.list-pagination:zpa-loop-trusts-latest-total-pages] The POST-search variant of the ZPA helper ignores the same parse error and stops when `page >= totalPages`, so a response without a usable `totalPages` ends the walk after its first page. [shared.sdk-go.list-pagination:zpa-post-search-same-parse]

**ZPA SCIM paging.** The ZPA SCIM helper moves to the next page by adding the requested `itemsPerPage` to `startIndex`, not the number of resources the page returned. A page that returns fewer resources than requested leaves a gap of unread resources before the next start index. [shared.sdk-go.list-pagination:zpa-scim-advances-by-requested-count] The same helper stops when `startIndex+itemsPerPage > TotalResults` or the page is empty. `TotalResults` is a plain int, so a response without it reads as 0 and the loop stops after the first page even when that page holds resources. [shared.sdk-go.list-pagination:zpa-scim-stops-on-total-results]

**Silent truncation and callers.** A ZPA list, name lookup, import, data source or SCIM read can return only the first page (or a page range with gaps) and report success, if the API response carries missing, null, non-numeric or inconsistent paging metadata. Nothing in the SDK result or error distinguishes this from a complete list. [shared.sdk-go.list-pagination:zpa-silent-truncation] The ZPA paging helpers are the list path for most ZPA SDK services, so the behavior above applies wherever they are called, including the microtenant lookups and the SCIM group and user readers. [shared.sdk-go.list-pagination:zpa-helper-callers] Whether ZPA endpoints send such paging metadata is open [gap:shared.sdk-go.list-pagination:zpa-paging-metadata-shape].

**ZCC v1 paging.** The ZCC v1 list helper (`ReadAllPages`) clamps the page size (0 or less becomes 50, more than 5000 becomes 5000), starts at page 1 and stops at the first page with fewer items than it asked for; the device list calls it with a page size of 1000. [shared.sdk-go.list-pagination:zcc-v1-stops-on-page-shorter-than-requested] Because the ZCC v1 helper stops only on a short page, a list whose size is an exact multiple of the page size costs one more request that returns an empty page. [shared.sdk-go.list-pagination:zcc-v1-extra-request] If a ZCC v1 list endpoint returns fewer items than the helper asked for on a full page (a server cap below the 1000 the device list requests, for example), the helper reads that page as the last one and returns a partial list with no error. [shared.sdk-go.list-pagination:zcc-v1-capped-page-truncates] When the helper applies a JMESPath filter, and which Go services call it, is in [`common.ReadAllPages` applies any JMESPath filter from the context only after all pages are collected.](kb:zcc.sdk-go.paging-and-requests:v1-readallpages) and [The v1 helper backs the Go reads of admin roles, admin users, the fail-open policy, ZDX and ZPA group entitlements, and devices.](kb:zcc.sdk-go.paging-and-requests:v1-callers).

**ZCC v2 paging.** The ZCC v2 drain helper clamps its page size like the v1 helper (0 or less becomes 50, more than 5000 becomes 5000), and all three v2 callers pass the default of 50. The single-page `ReadPageV2` turns 0 or less into 50 but does not cap a larger value. [shared.sdk-go.list-pagination:zcc-v2-page-size] The ZCC v2 helper advances `Skip` by the page size it asked for, after a page that is neither empty, short against `Limit`, nor past `Total`. It never advances by the returned `Count` or `Limit`. [shared.sdk-go.list-pagination:zcc-skip-advances-by-requested-size] Two of the ZCC v2 helper's three exits depend on envelope metadata: `Limit > 0` for the short-page check and `Total > 0` for the total check. A non-empty page whose `limit` and `total` are 0 triggers neither, so the helper keeps requesting pages until one comes back empty. The first exit, `Count == 0`, needs no metadata beyond `count`: a server that omits `count` stops the walk after one page. [shared.sdk-go.list-pagination:zcc-guards-need-envelope-metadata] With a server that caps the page below the requested size, a ZCC v2 read can skip the records between the capped page and the next `Skip`. With a server that omits `limit` and `total` but still sends a non-zero `count`, and ignores `skip`, the same read does not terminate. [shared.sdk-go.list-pagination:zcc-skip-records-or-loop] Three ZCC SDK services read through the v2 helper: notification templates, trusted networks (v2) and ZIA posture profiles. [shared.sdk-go.list-pagination:zcc-v2-callers] Whether ZCC v2 endpoints cap the page or fill the envelope is open [gap:shared.sdk-go.list-pagination:zcc-v2-envelope-behavior].

**ZTC paging.** The ZTC (ztw) `ReadAllPages` helper requests `pageSize=1000` on every page and stops at the first page with fewer than 1000 items. [shared.sdk-go.list-pagination:ztw-stops-on-page-shorter-than-1000] If a ZTC list endpoint returns fewer than 1000 items for a full page (a server cap), the helper reads that page as the last one and returns a partial list with no error. [shared.sdk-go.list-pagination:ztw-capped-page-truncates] The ztw fixed-page helper backs the ZTC SDK's list calls for edge-connector groups, locations, forwarding gateways, IP and network groups, policy rules, provisioning and partner-integration lists, among others. [shared.sdk-go.list-pagination:ztw-helper-callers] Whether a ZTC endpoint caps its page is open [gap:shared.sdk-go.list-pagination:page-size-caps].

**ZIA paging.** The ZIA helper stops the same way, covered for URL Filtering in [Listing URL Filtering rules and URL categories without truncation](kb:zia.url-filtering.list-pagination). Apart from a request error, the ZIA helper ends only on a page shorter than its page size. When the last page is exactly full (the total is a multiple of the page size), it requests one more page. [shared.sdk-go.list-pagination:zia-readallpages-extra-request] That request is an extra API call that returns nothing new, presumably an empty page, which then ends the loop. [shared.sdk-go.list-pagination:zia-readallpages-extra-request-empty]

**ZCC forwarding profiles.** The ZCC forwarding-profile list call makes one GET to `listByCompany` with optional `page` and `pageSize` and returns that single response; it does not walk pages. The provider's Read, and its post-create and post-update lookups, call it with no page or page size. [shared.sdk-go.list-pagination:zcc-forwarding-profile-single-request] The forwarding-profile resource's Read removes the resource from state when its ID is not in the list it fetched, and the create and update lookups fail after five tries when the profile is not in it. [shared.sdk-go.list-pagination:zcc-forwarding-profile-read-drops-state] If the forwarding-profile endpoint returns only a first page by default, a profile outside it would be dropped from state on refresh, or make an otherwise successful create or update fail on re-read. [shared.sdk-go.list-pagination:zcc-forwarding-profile-outside-first-page] Whether the endpoint pages its response by default is open [gap:shared.sdk-go.list-pagination:zcc-forwarding-profile-default-page].

**ZIA posture profiles.** Importing a ZCC ZIA posture profile by a non-numeric ID calls `GetByName`, which fetches the list through the v2 paging helper and compares names client-side. A numeric ID imports without any list call. [shared.sdk-go.list-pagination:zia-posture-import-by-name-uses-list-helper] The ZCC provider's own notes say the `/zia-posture-profiles` list endpoint mishandles pagination and silently returns a truncated set, which is why its data source accepts only a numeric ID. The same documentation tells users to find the ID through the resource's import handler, which it describes as calling a different list endpoint. The code does not support that last point: the import handler's name lookup uses the same list helper and endpoint. [shared.sdk-go.list-pagination:provider-documents-posture-list-truncated] Importing a ZIA posture profile by name can fail to find a profile that exists, because the lookup reads the list the provider documents as truncated. The documented workaround (discover the ID by importing) goes through that same helper and the same `/zia-posture-profiles` endpoint when a name is used, contrary to the documentation's "different list endpoint"; importing by numeric ID makes no list call. [shared.sdk-go.list-pagination:zia-posture-import-by-name-can-miss] Whether the truncation is server paging or the SDK helper is open [gap:shared.sdk-go.list-pagination:zia-posture-truncation-cause]. The same pattern of a truncated list feeding a decision appears in [How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order), where the "last rule" comes from a list that may be partial.

What to check:
1. After an import by name, data-source lookup or refresh reports an object missing, count the objects through the console or a separate API call before concluding it is absent.
2. Whether a count that is an exact multiple of a helper's page size is a page cap or a full last page.
