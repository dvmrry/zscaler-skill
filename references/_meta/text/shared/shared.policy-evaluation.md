# How ZIA and ZPA evaluate policy, side by side (shared.policy-evaluation)
Also called: policy evaluation; zia vs zpa policy; default allow vs default block; first match; rule precedence across products; why was this allowed; why was this blocked; policy evaluation order

The two services share first-match rule lists but differ in what happens when nothing matches, where evaluation runs, and how many policies one request meets. The defaults are opposite: ZIA allows a request that no policy blocks, while ZPA blocks access when no access rule matches or none is defined. [shared.policy-evaluation:default-contrast]

| Dimension | ZIA (internet and SaaS traffic) | ZPA (private applications) |
| --- | --- | --- |
| Nothing blocks or matches | Outbound web traffic that violates no Firewall and no Web policy is allowed to the internet, and outbound non-web traffic that violates no Firewall policy is allowed to the internet. [shared.policy-evaluation:allow-unless-violated] | [If no access policy rule matches, or no rule is defined at all, access to the application is implicitly set to Block Access.](kb:zpa.policy.evaluation-order:default-access-block) |
| Where it runs | ZIA Public Service Edges use Single Scan Multi-Action (SSMA) to inspect traffic; policy enforcement takes place in the edge's web and Firewall modules, and after SSMA inspection completes the edge executes policies with a specific precedence. [shared.policy-evaluation:edge-modules] | ZPA evaluation spans the client and the Service Edge: Client Connector applies segment ports and the client forwarding decision before traffic reaches the cloud, and Public or Private Service Edges enforce user policies. [shared.policy-evaluation:where-zpa-runs] |
| Order inside a rule list | [Evaluation of the policy rules stops at the first match.](kb:zia.url-filtering.rule-order:first-match) | [Private Access evaluates policy rules using the most specific application segment and a top-down, first-match principle: the first rule whose criteria match is enforced and all later rules, including conflicting ones, are disregarded.](kb:zpa.policy.evaluation-order:first-match-most-specific-segment) |
| Decryption | [The SSL inspection policy is evaluated on the same CONNECT or SNI information and decides whether the connection is decrypted.](kb:zia.ssl-inspection.pipeline:ssl-decision-between) | [In Private Access the Service Edge does not inspect the data as traffic flows through it, unlike a Service Edge in Internet & SaaS.](kb:zpa.private-service-edges.what-it-is:no-inspection) |

## ZIA: modules, then policies in a fixed order

1. **Firewall, then web.** [All web traffic is evaluated in the firewall module first, and only traffic that does not violate a firewall policy is forwarded to the web module.](kb:zia.firewall.traffic-path:firewall-first) [Outbound traffic to ports other than 80/443 (or other HTTP or HTTPS ports) goes directly to the firewall module and is blocked if it violates a firewall policy.](kb:zia.firewall.traffic-path:nonweb-firewall-only) [If a web policy allows a transaction but a conflicting firewall policy blocks it, the firewall policy applies: for example, Cloud App Control allowing Box.com does not help when the firewall blocks it.](kb:zia.firewall.traffic-path:firewall-beats-web-allow)
2. **Web policies in order, first violation stops.** [When the web module finds a transaction violates a policy, the Public Service Edge blocks it immediately and does not enforce the policies that follow; the firewall module does not evaluate it, though firewall logs still show the web transaction as blocked.](kb:zia.atp.enforcement-order:first-violation-blocks) The GET, POST and response orders are in [Where Malware Protection and ATP checks fall in the web enforcement order](kb:zia.atp.enforcement-order); how they apply to streaming and multiplexed HTTP is open [gap:shared.policy-evaluation:modern-http].
3. **HTTPS evaluates twice.** A domain-only pass before the SSL decision and a full pass after decryption: [On inspected HTTPS, URL Filtering therefore evaluates twice: first on the domain, then on the full decrypted request. "SSL inspection happens before URL Filtering" is wrong: the SSL decision sits between the two URL Filtering passes and gates only the second.](kb:zia.ssl-inspection.pipeline:url-filtering-twice). The domain-only pass lists Cloud App Control before URL Filtering, so a Cloud App Control allow on the domain is expected to skip URL Filtering in that pass too, unless cascading is enabled. [shared.policy-evaluation:cac-first-on-domain-pass]
4. **Cloud App Control before URL Filtering.** [By default, when a Cloud App Control rule explicitly allows the transaction, URL Filtering is not applied at all, so a URL Filtering block on the same site does not fire.](kb:zia.cloud-app-control.precedence:cac-allow-skips-url-filtering) [Enabling Allow Cascading to URL Filtering in Advanced Settings makes the service apply the URL Filtering policy even when a Cloud App Control rule allows the transaction, so a URL Filtering block then applies.](kb:zia.cloud-app-control.precedence:cascading-allow-path) [In the help's example, with Allow Cascading to URL Filtering enabled, Facebook blocked by a Cloud App Control rule stays blocked even though URL Filtering allows it.](kb:zia.cloud-app-control.precedence:cac-block-final)

## ZPA: segment first, then rules

1. **Segment.** The most specific segment wins and carves the host out of wider ones: [The same carve-out applies to IP addresses: the moment an application segment is created for 10.0.0.1/32, that host is carved out of the segment for 10.0.0.0/24.](kb:zpa.app-segments.matching:carve-out-ip), with the port-mismatch case in [If there is no match in the more granular application segment for the destination port, Zscaler Client Connector bypasses Private Access and sends the traffic directly.](kb:zpa.app-segments.matching:port-mismatch-bypass).
2. **Forwarding before access.** [Client forwarding policy rules are evaluated before access policy rules, and a match in client forwarding policy makes Private Access disregard the other policy rules, including conflicts.](kb:zpa.policy.evaluation-order:client-forwarding-before-access) [If a forwarding rule bypasses the traffic, the access policy rule is never evaluated for it, so a bypass for an application defeats an access rule that would block it.](kb:zpa.policy.evaluation-order:bypass-skips-access)
3. **Rules.** [When a request arrives, Private Access identifies the matching rule first, choosing the rule that corresponds to the most specific application segment for the domain name or IP address if segments are part of the criteria.](kb:zpa.policy.evaluation-order:segment-then-rules) Defaults for the other policy types are in [Evaluation order across ZPA policy types](kb:zpa.policy.evaluation-order), and their order relative to access policy is open there: [Evaluation order of timeout, isolation, inspection and the other policy types relative to access policy](kb:zpa.policy.evaluation-order:remaining-type-order).

Using NameID as a SAML attribute in access and timeout rules is not supported: [Using the SAML NameID as a SAML attribute within access and timeout policy rules is not supported; the same value can be used by defining it as a user attribute.](kb:zpa.policy.criteria:nameid-unsupported).

## What the products share

Both products stop at the first matching rule within a rule list: ZIA URL Filtering at the first rule whose criteria match, ZPA at the first matching rule for the most specific segment. [shared.policy-evaluation:first-match-both] In both products specificity is resolved before rule order: in ZIA the more specific custom category entry decides a URL's category whatever the rule order; in ZPA the rule for a more specific FQDN (specific.web.com) wins over an earlier rule for a wildcard of its parent domain (*.web.com), while a wildcard and the bare name of the same domain (*.specific.web.com and specific.web.com) rank top-down. [shared.policy-evaluation:specificity-both]

**Disabled rules.** [A disabled rule is skipped but keeps its position in the order.](kb:zia.url-filtering.rule-order:disabled-holds-slot) A ZPA access policy rule has a Rule Status toggle that enables or disables it. [shared.policy-evaluation:zpa-rule-status] Whether a disabled ZPA rule is skipped in place or removed from evaluation is open [gap:shared.policy-evaluation:zpa-disabled-rule].

## Where they meet

Inspect Traffic with ZIA and Source IP Anchor are separate segment settings that cannot both be on: [Inspect Traffic with ZIA lets a segment use a single posture for securing internet or SaaS and private applications and applies Data Loss Prevention policies to it.](kb:zpa.app-segments.settings:inspect-zia-purpose) [Source IP Anchor and Inspect Traffic with ZIA cannot both be enabled on a segment; Source IP Anchor must be disabled first.](kb:zpa.app-segments.settings:sipa-inspect-zia-exclusive) For anchored traffic, ZPA takes the country from the ZIA Public Service Edge's address: [For Cloud Connectors, Source IP Anchoring traffic and Private Access multi-hop, the country criterion uses the last NATed layer 3 public IP address, so SIPA traffic takes its country from the Internet & SaaS Public Service Edge's public IP.](kb:zpa.policy.criteria:country-last-nat-ip).

Client Connector decides per network type where traffic goes for each service: [A forwarding profile tells Client Connector how to treat traffic from users' systems in different network environments, for the Internet & SaaS and Private Access services.](kb:zcc.forwarding-profiles:purpose). Whether both services see the same user identity and device posture for one device is open [gap:shared.policy-evaluation:consistent-identity].

What to check:
1. Name the product first: an unmatched ZIA request is allowed unless a policy blocks it, an unmatched ZPA access request is blocked.
2. For ZIA, walk firewall, then the web policies in order for the request type, and for HTTPS both passes; stop at the first violation.
3. For ZPA, find the most specific segment and its ports, then the client forwarding rule, then the first matching access rule.
4. A disabled ZIA rule keeps its slot; do not assume the same of a disabled ZPA rule.
