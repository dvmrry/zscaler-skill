# ZSDK architecture: Service Edges, App Connectors and the mobile client (shared.zsdk.architecture)
Also called: zsdk public service edge; zsdk private service edge; zsdk app connector; zsdk microtunnel; zsdk mtls; zsdk components; zsdk how it works

ZSDK's infrastructure consists of ZSDK Public Service Edges, ZSDK Private Service Edges, App Connectors and the Mobile Client SDK. [shared.zsdk.architecture:components] ZSDK runs on a dedicated multi-tenant infrastructure, and all communication is encrypted end to end to isolate the organizations using the same service. [shared.zsdk.architecture:multi-tenant]

**Service Edges.** ZSDK Public Service Edges are cloud components maintained by Zscaler and deployed globally, the primary interface between ZSDK apps and protected back-end services. They authenticate mobile applications and their App Connectors with public keys only; private keys are never stored or used except for the Service Edge's own identity. [shared.zsdk.architecture:public-service-edges] ZSDK Private Service Edges are single-tenant brokers with functions similar to Public Service Edges, hosted by the organization on premises or on a cloud service but managed by Zscaler; they authenticate mobile applications with provisioning keys. [shared.zsdk.architecture:private-service-edges]

**The mobile client.** The Mobile Client SDK is the client-side component integrated into the app; among its functions are device posture checking and certificate and key management, and it creates a unique device fingerprint and application signature to prevent unauthorized copies or modifications of the app. [shared.zsdk.architecture:mobile-client]

**How a request travels.** APIs and back-end services are deployed behind App Connectors, which create inside-out mTLS microtunnels to the Zscaler cloud. [shared.zsdk.architecture:backend-behind-connectors] ZSDK verifies the token's signature against the security certificate and confirms that the JSON Web Token contains the required claims before granting app access. [shared.zsdk.architecture:identity-before-tunnel] After the user's identity is verified, ZSDK creates mTLS microtunnels that route network requests through the ZSDK cloud, where the ZSDK Public Service Edge brokers the connection through the App Connector's microtunnel. [shared.zsdk.architecture:tunnel-through-pse] The calls that start each tunnel are in [The ZSDK developer API: classes, tunnels, lifecycle and notifications](kb:shared.zsdk.developer-api).

**App Connectors.** App Connectors only connect outbound and need no inbound open ports; they authenticate with a provisioning key pair and keep persistent mTLS connections to the nearest Public Service Edge. [shared.zsdk.architecture:connector-outbound] App Connectors can be co-located with the applications or deployed in any location with connectivity to them, typically on network segments that can reach both the applications and the ZSDK cloud, such as a Demilitarized Zone. [shared.zsdk.architecture:connector-placement] ZSDK selects the closest App Connector given the location of the user and the App Connector-to-application latency. [shared.zsdk.architecture:connector-selection] App Connectors are always active and typically deployed in a redundant configuration, but they never communicate with each other; the configuration guide recommends deploying them in pairs to keep availability during software upgrades. [shared.zsdk.architecture:connector-redundancy] Zscaler distributes App Connectors as a standard VM image and as packages for supported Linux distributions; the listed platforms are AWS, Google Cloud Platform, Linux (Red Hat Enterprise Linux 8 or 9), Microsoft Azure, VMware vCenter or vSphere Hypervisor (ESXi), Nutanix, Docker and OpenShift. [shared.zsdk.architecture:connector-platforms] The ZSDK maintenance guide checks a deployed App Connector through the `zpa-connector` systemd service, which reports itself as the Zscaler Private Access App Connector. [shared.zsdk.architecture:connector-zpa-software] ZSDK App Connectors reach the ZSDK Public Service Edges on *.prod.zpath.net, which must be in the SSL bypass list for App Connector traffic because certificate verification cannot be configured. [shared.zsdk.architecture:connector-zpath-hosts] The ZSDK API also reports errors when no Private Access (ZPA) service is registered: [Private Access (ZPA) errors: 2003 `noZpaService` means no Private Access service is registered (register for it); 2004 `multipleZpaService` means several are registered; 2023 `hmacSecretFailed` is a failure to fetch the HMAC secret from Private Access; 2024 `hmacValidationFailed` is a failure to validate the HMAC payload.](kb:shared.zsdk.error-codes:api-private-access).

What to check:
1. Whether the App Connectors serving the app have outbound connectivity to the ZSDK cloud, since they accept no inbound connections.
2. Whether App Connectors are deployed at least in pairs, as the configuration guide recommends for upgrades.
