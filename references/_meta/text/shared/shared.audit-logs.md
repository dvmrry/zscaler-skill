# Admin audit logs across Zscaler products: what exists and how to get it (shared.audit-logs)
Also called: who changed what; admin audit trail; cross-product audit; audit log api; did zscaler support change something; audit log siem; cross-product audit logs

Every product keeps its own admin audit trail, with its own access path and retention. No cross-product audit stream is documented [gap:shared.audit-logs:unified-audit-bus], so a change investigation starts by naming the product.

## Per product

| Product | Pull | Stream | Where |
| --- | --- | --- | --- |
| ZIA | Asynchronous CSV report | Cloud NSS ADMIN_AUDIT feed | [ZIA audit logs: who changed what](kb:zia.audit-logs), [An admin audit report is generated asynchronously: POST /auditlogEntryReport starts it, GET /auditlogEntryReport reports status until it is COMPLETE, then GET /auditlogEntryReport/download returns the CSV; DELETE /auditlogEntryReport cancels the request.](kb:zia.audit-logs.report-api:lifecycle), [A Cloud NSS feed can stream admin audit logs: ADMIN_AUDIT is an accepted nss_log_type in the Terraform provider and in the Go SDK's supported feed types.](kb:zia.audit-logs.streaming:cloud-nss-admin-audit) |
| ZPA | None; console view and CSV download | LSS zpn_audit_log | [ZPA admin audit logs](kb:zpa.audit-logs), [ZPA has no pull-based audit-log export in its API specification, SDKs or Terraform provider; the audit log is read in the Admin Console (with a CSV download) or streamed by the Log Streaming Service.](kb:zpa.audit-logs.what-is-recorded:no-pull-api), [A log receiver's source log type for audit logs is `zpn_audit_log`; the Python SDK reaches it through the `audit_logs` key.](kb:zpa.audit-logs.streaming:audit-source-type) |
| Cloud & Branch Connector | Asynchronous CSV report | Not documented | The Cloud & Branch Connector API has an audit report: POST /auditlogEntryReport starts a CSV export, GET reports its status, DELETE cancels it, and GET /auditlogEntryReport/download returns the CSV data. [shared.audit-logs:cbc-audit-report], [Cloud & Branch Connector audit logs in the console: what is recorded, retention, lockout, filters and CSV](kb:cloud-connector.audit-logs) |
| ZDX | Asynchronous CSV report | Not documented | The ZDX API has an audit log report under /v1/config/auditlogEntryReport: a POST starts a background CSV report for a time period and filters, a GET fetches its status, a DELETE cancels it and the download returns the CSV. Its action types include ACTIVATE and FORCED_ACTIVATE, and its page and pageSize fields are described as not supported in /auditlogEntryReport. [shared.audit-logs:zdx-audit-report], [ZDX admin audit logs in the console: what is recorded, retention, lockout and filters](kb:zdx.audit-logs) |
| Unified RBAC | Query API | Not documented | The Unified RBAC API has an audit log query, POST /v1/auditlog/query, filtering on roleName and actionId; each record carries the action, before and after state, client IP, status, tenant, user and timestamp. [shared.audit-logs:urbac-audit-query], [A separate audit log records the activity of each admin who uses the Role Management page: creating, updating and deleting admin roles. Its page (Data Explorer > Audit Logs > Role Management) filters by timestamp, action and result; the actions are Create Role, Update Role and Delete Role; each entry has a Target Role Name (the administrator role that was created, updated or deleted), a User (the admin's login ID or the internal API user), a Client IP and a Result of Success or Failure; and the changes made to a role can be viewed if it was updated.](kb:unified.audit-logs:role-management-log) |
| Experience Center | Console view and CSV download | Not documented | The Experience Center audit log is a console view on the Audit Logs page (Data Explorer > Audit Logs > Experience Center) that can be downloaded as a CSV file; the audit logs are stored for up to 6 months. [shared.audit-logs:ec-audit-console], [Experience Center and Role Management audit logs: what is recorded, categories, actions, record fields, lockout, retention, search and export](kb:unified.audit-logs) |
| Authentication Service | Not documented | NSS and Cloud NSS log streaming | Authentication Service has an Audit Logs permission module whose levels are View Only (view audit logs) and None. [shared.audit-logs:zidentity-audit-module] No audit log endpoint is documented for Authentication Service: its API specification has no audit path and neither SDK has an audit client for it. [shared.audit-logs:zid-no-audit-api] [NSS and Cloud NSS integration lets Authentication Service stream authentication, admin audit and SCIM logs in real time to SIEMs linked with Zscaler services such as ZIA; on the Log Streaming page (Data Explorer > Log Streaming > Authentication Service Log Streaming), enabling Authentication Service Log Streaming streams them to the Internet & SaaS tenant, whose linked tenants are listed with their IDs.](kb:zidentity.audit-logs:log-streaming) |
| Zscaler Cellular | Audit log search | Not documented | The Zscaler Cellular API has an audit log search, POST /api/v1/audit/customers/{id}/search, described as searching customer audit logs by criteria such as operation type, object type, time ranges and visibility; the Python SDK exposes it as list_audit_customers_search. [shared.audit-logs:cellular-audit-search] |
| ZCC | Not documented | Not documented | ZCC admin roles carry an auditLogs permission and the company settings a hideAuditLogs field, but the ZCC API specification has no audit log path. [shared.audit-logs:zcc-audit-permission-no-api], [Client Connector audit logs in the Admin Console: what is recorded, retention, columns, actions, categories and filters](kb:zcc.audit-logs) |
| ZWA | Customer audit query | Not documented | [Workflow Automation audit logs: the customer audit search, what it records, and how the SDKs read it](kb:zwa.audit-logs) |

**SDKs.** Of these report and query APIs the SDKs implement the ZIA audit report (Go adminauditlogs, Python audit_logs), the ZWA customer audit and, in Python only, the Zscaler Cellular audit search; neither SDK has a client for the Cloud & Branch Connector, ZDX or Unified RBAC audit APIs. [shared.audit-logs:sdk-coverage] The ZDX report's status GET and cancel DELETE take optional statusId and timestamp query parameters, while the Cloud & Branch Connector report's status GET and cancel DELETE define no parameters. [shared.audit-logs:report-status-id] How the Cloud & Branch Connector and ZDX reports otherwise behave next to ZIA's is open [gap:shared.audit-logs:report-parity], as is what the Unified RBAC audit covers [gap:shared.audit-logs:urbac-audit-scope].

**Retention.** ZIA keeps audit logs for up to 6 months: [Audit logs are stored for up to 6 months.](kb:zia.audit-logs.what-is-recorded:retention). ZPA keeps them for up to 6 months, and the LSS page words it differently: [The ZPA Audit Logs page states that audit logs are stored for up to 6 months, and its date-range filter defaults to 6 Months.](kb:zpa.audit-logs.what-is-recorded:retention). ZDX's console audit logs are stored for 6 months: [ZDX audit logs are stored for a period of 6 months.](kb:zdx.audit-logs:retention). The audit log article for the Audit Logs page at Data Explorer > Audit Logs > Branch and Cloud lists, among the benefits of audit logs, storing them for up to 6 months. [shared.audit-logs:cbc-console-retention] The Client Connector console audit logs are also stored for up to 6 months: [The Client Connector audit logs are stored for up to 6 months.](kb:zcc.audit-logs:retention). The Experience Center console audit logs are stored for up to 6 months too: [shared.audit-logs:ec-audit-console]. Retention for the other products is not documented [gap:shared.audit-logs:other-retention].

**Session source.** ZIA's authenticated-session read returns an authType ("Login type") of ADMIN_LOGIN, SUPPORT_ACCESS_PARTIAL, SUPPORT_ACCESS_FULL, PARTNER_ACCESS, INTEGRATION_PARTNER_ACCESS, DEFAULT_LOGIN, ADMIN_SAML_SSO_LOGIN, SUPPORT_ACCESS_READ_ONLY or MOBILE_APP_TOKEN. [shared.audit-logs:auth-type] When no session exists the field is absent: [GET /authenticatedSession checks for a session: when one exists the response carries `authType`, and when `authType` is absent the session has expired or does not exist.](kb:shared.legacy-api.zia-session:session-check). What each value grants is not documented [gap:shared.audit-logs:auth-type-meanings]. The authType describes the caller's own current session; the audit report request has no authType filter, so Zscaler Support sessions cannot be isolated in the report by that field. [shared.audit-logs:auth-type-not-in-report]

**Correlation.** A ZIA entry's Trace ID ties it to a OneAPI transaction: [Trace ID is generated and logged for transactions associated with Internet & SaaS API requests made via Zscaler OneAPI; it correlates API transactions with the OneAPI platform.](kb:zia.audit-logs.what-is-recorded:trace-id-oneapi). Whether the same ID appears in other products' audit records is open [gap:shared.audit-logs:trace-id-propagation], and so is a single audit surface across products [gap:shared.audit-logs:unified-audit-bus]. Where a change to an admin's entitlements is audited is open [gap:shared.audit-logs:entitlement-change-audit].

**Device events.** The Go SDK describes ZDX per-device events as Zscaler, Hardware, Software and Network event changes for a device, each with prev and curr values, and says the endpoint defaults to the last 2 hours when no time range is given. [shared.audit-logs:zdx-device-events] Admin changes in ZDX are in its audit report instead: [shared.audit-logs:zdx-audit-report].

What to check:
1. Which product the change was made in, and that product's audit path from the table.
2. For ZIA, the entry's Admin ID, Interface (Admin UI or API) and Trace ID; an OAuth client shows as an internal oauth- admin ID.
3. Whether the change falls inside the retention window, and whether a stream (Cloud NSS for ZIA, LSS for ZPA) kept it longer.
4. Do not join audit records across products on Trace ID until it is shown to propagate.
