# Zscaler PAC file variables: gateways, hosts, load-balancing tokens, subclouds and Client Connector (shared.pac-files.variables)
Also called: pac variables; ${GATEWAY}; ${SECONDARY_GATEWAY}; ${GATEWAY_HOST}; ${GATEWAY_FX}; gateway_fx; gateway index tokens; ${COUNTRY_GATEWAY}; ${SRCIP}; ${ZS_CUSTOM_PORT}; ${TRUSTED_NETWORK}; ${ZT2_REQUEST}; subcloud pac variable; pac server geolocation; pac manual failover

A Zscaler-hosted PAC file is not served as written: the PAC server fills in variables for each request. The default files use them, and custom files should.

**How substitution works.** When a browser requests the default PAC file, the service uses geolocation to find the Public Service Edges closest to the user and inserts their IP addresses into the file it returns; the browser then forwards web traffic to the primary Public Service Edge. [shared.pac-files.variables:substitution-flow] The Zscaler-specific variables work only when the PAC file is hosted on the Zscaler cloud. [shared.pac-files.variables:hosted-only] How the server geolocates a client that fetches the file through a VPN is open [gap:shared.pac-files.variables:vpn-egress-geolocation].

**Gateways and failover.** ${GATEWAY} and ${SECONDARY_GATEWAY} resolve to the Public Service Edges closest to the client with the quickest response, found by geolocation; naming both provides failover when one is unavailable. [shared.pac-files.variables:gateway-vars] Failover to the secondary data center is automatic when the primary is down; to move users for other reasons, such as ISP or latency issues, the vendor reverses the order: PROXY ${SECONDARY_GATEWAY_FX}:80 before PROXY ${GATEWAY_FX}:80, then DIRECT. [shared.pac-files.variables:manual-failover]

**Host names.** The ${GATEWAY_HOST} variable resolves to a host name instead of an IP address, and the page's example returns ${GATEWAY_HOST} with ${SECONDARY_GATEWAY_HOST} as the fallback proxy. It is a recommended configuration for Kerberos authentication and for IPv6: Zscaler recommends the host-name variable to forward IPv6 traffic, with IPv6 support enabled for the organization and its locations and Enable IPv6 Resolution for Zscaler Domain enabled. [shared.pac-files.variables:gateway-host] Kerberos use is in [The Kerberos PAC file: host-name variables, port 8800 and required bypasses](kb:shared.pac-files.kerberos).

**Load-balancing tokens.** Load balancing is typically based on the source IP address and the destination IP address, which results in the overloading of a single Public Service Edge instance in the data center when many users share an egress IP; to distribute PAC forwarded traffic over multiple instances in a data center, the PAC server returns multiple VIP addresses within the same data center as the destination IP address. The page says Zscaler supports up to 8 VIP addresses in a cluster and up to 64 clusters in a data center. [shared.pac-files.variables:why-multiple-vips] The same page gives two VIP figures [divergence:shared.pac-files.variables:vips-per-cluster-or-dc]. For many users behind one egress IP, the suffixes _F0 to _F7 on ${GATEWAY} return up to 8 healthy gateway IP addresses (reused round-robin when a data center has fewer than 8). These load-balancing variables are for non-tunnel traffic, and regional surcharge data centers are not in the gateway variable. [shared.pac-files.variables:index-tokens] The vendor's splitPublicTraffic() sample uses the myIpAddress() function to determine the client source IP address, splits the client private IP address into its octets and performs last octet%8 to get an index between 0 and 7; the sample returns DIRECT for FTP and for 100.64.0.0 with mask 255.255.0.0. [shared.pac-files.variables:fn-split-format] The _FX suffix (${GATEWAY_FX}, ${SECONDARY_GATEWAY_FX}) makes the PAC server issue gateway addresses by client fingerprint, giving all users behind one egress IP addresses from a pool of healthy gateway IPs and keeping a device on the same gateway; it balances on the useragent, x-forwarded-for and z-client headers and is effective only for Client Connector clients, and other clients can use the index tokens. [shared.pac-files.variables:fx-tokens] When Zscaler Client Connector connects to the PAC server to download a PAC file, it sends a unique device identifier with the request; when the same device connects again to download the PAC file, the PAC server allocates the same VIP address that was allocated to the device earlier based on its unique identifier. [shared.pac-files.variables:fx-device-identifier] Dedicated proxy ports also require the _FX variables: [When PAC files send traffic to a dedicated proxy port, the file must use the ${GATEWAY_FX} and ${SECONDARY_GATEWAY_FX} variables and not name specific Public Service Edges by host name or IP, so that failover and nearest-edge selection keep working.](kb:zia.traffic-forwarding.pac:dedicated-port-variables).

**Source, country and country gateways.** ${SRCIP} gives the client's public IP address and ${COUNTRY} its country (countries as listed on GeoNames); ${COUNTRY_GATEWAY} and ${COUNTRY_SECONDARY_GATEWAY} give the closest Public Service Edge in the client's country, and ${COUNTRY_GATEWAY} behaves like ${GATEWAY} when no Service Edge is configured there. [shared.pac-files.variables:source-and-country]

**Subclouds.** A PAC file for a subcloud must not use ${GATEWAY} or gateway.<Zscaler cloud> in its return statement, or traffic goes to the nearest Public Service Edge, which may be outside the subcloud; it uses ${GATEWAY.<Subcloud>.<Zscaler cloud>} and ${SECONDARY.GATEWAY.<Subcloud>.<Zscaler cloud>}, with _HOST forms for Kerberos and plain host names for applications that do not support PAC files. [shared.pac-files.variables:subcloud-vars] The documents spell the secondary subcloud variable two ways [divergence:shared.pac-files.variables:subcloud-secondary-syntax]. How long a subcloud change takes to reach clients is [A change to a subcloud's data center list takes about 5 minutes to reach Zscaler-hosted PAC files; Client Connector refreshes the app profile PAC every 15 minutes, so users are redirected about 10 to 20 minutes after the change, and Update Policy in the app syncs the app profile PAC immediately.](kb:shared.pac-files.hosting:subcloud-propagation).

**Client Connector variables.** ${ZS_CUSTOM_PORT} returns a custom port by country and Z-Tunnel version (in China 9401 for Z-Tunnel 2.0 and 9400 for 1.0, elsewhere 443 for both; the ports are subject to change). It needs Use Preferred Port from PAC enabled in the Client Connector Windows profile and Client Connector 4.2.0 or later. [shared.pac-files.variables:zcc-port-variable] ${TRUSTED_NETWORK} gives Client Connector's network type (ON_TRUSTED, OFF_TRUSTED, VPN_TRUSTED, SPLIT_VPN_TRUSTED) only in an app profile PAC file, and NOT_AVAILABLE in a forwarding profile or proxy PAC file or when no type is known; it needs Client Connector 4.2.0 or later. ${ZT2_REQUEST} is true when the PAC file is requested for Z-Tunnel 2.0 and false for Z-Tunnel 1.0. [shared.pac-files.variables:zcc-network-variables] The PAC files Client Connector uses are listed from [PAC files across Zscaler: where each question is answered](kb:shared.pac-files).

What to check:
1. Whether the file is hosted on the Zscaler cloud; a self-hosted copy gets no variable substitution.
2. For a subcloud tenant, whether every return statement uses the subcloud form rather than ${GATEWAY}.
3. Whether _FX tokens are used for clients that are not Client Connector, where they do not balance load.

Sources disagree (name both sides):
- The load-balancing article gives the VIP limit per cluster in one sentence and per data center in another. [divergence:shared.pac-files.variables:vips-per-cluster-or-dc]
  - zscaler-help: Up to 8 VIP addresses in a cluster and up to 64 clusters in a data center.
  - zscaler-help: Each data center can have up to 8 unique VIP addresses assigned to it.
  Impact: With several clusters per data center the two sentences give different totals of VIPs per data center; the page does not reconcile them.
- How the secondary gateway variable for a subcloud is written. [divergence:shared.pac-files.variables:subcloud-secondary-syntax]
  - zscaler-help: The PAC writing article uses ${SECONDARY.GATEWAY.<Subcloud>.<Zscaler cloud>.net}, with a period after SECONDARY; the subclouds article uses the same form.
  - zscaler-help: The PAC best practices article writes ${SECONDARY_GATEWAY.organization_name.zscaler.net}, with an underscore.
  Impact: A file copied from the best practices article may use a secondary subcloud variable that differs from the one the other two articles document; whether the PAC server substitutes the underscore form is not stated, so the secondary entry may not resolve to a subcloud Service Edge.
