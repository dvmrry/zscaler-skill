# ZIA legacy OAuth 2.0 through an external identity provider (shared.legacy-api.zia-oauth)
Also called: zia oauth 2.0 external idp; zia api roles; cloud name org id api role scope; oauth-<rolename>$@ admin id; pingfederate okta entra zia api; oauth 2.0 authorization servers zia

Before OneAPI, ZIA's cloud service API could already take OAuth 2.0 tokens, issued by the customer's own identity provider rather than by Authentication Service. ZIA supports OAuth 2.0 for the cloud service API with the Client Credentials flow, using PingFederate, Okta or Microsoft Entra ID as the authorization server. [shared.legacy-api.zia-oauth:external-idps] This OAuth 2.0 method is supported only for the cloud service API, and the vendor recommends it over the API key method for that API. [shared.legacy-api.zia-oauth:cloud-service-only]

**Why use it.** The vendor lists as advantages that it needs no ZIA admin credentials, scopes access with API roles tied to client applications, and needs no client-side key obfuscation. [shared.legacy-api.zia-oauth:advantages]

**Prerequisites.** It needs an API subscription, API roles configured in ZIA, client applications registered on the authorization server with the required scope, and the authorization server added to ZIA. [shared.legacy-api.zia-oauth:prerequisites]

**Scope.** The scope must be `<Zscaler Cloud Name>::<Org ID>::<API Role>`, for example `zscalerbeta.net::8956412::sampleRole`. [shared.legacy-api.zia-oauth:scope-format] The scope claim may be named `scope`, `scp` or `roles` and is required; `iss`, `aud` and a client ID claim (`client_id`, `cid` or `appid`) are optional, and claim names vary with the OAuth vendor. [shared.legacy-api.zia-oauth:claims-table] API roles are not assigned to Internet & SaaS (ZIA) admin users; they are associated with the client applications that call the API. [shared.legacy-api.zia-oauth:api-roles-on-clients] The OneAPI flow uses an audience instead: [The token request must include an `audience` parameter with the value `https://api.zscaler.com`, for both the client-secret and the client-assertion methods.](kb:shared.oneapi.authentication:audience-required).

**Token request.** The client POSTs to its identity provider's token endpoint with `grant_type` client_credentials and the scope, presenting its client ID and secret by HTTP Basic authentication or in the body; a failed request returns 400. [shared.legacy-api.zia-oauth:token-request] The access token's lifetime is configured on the OAuth provider's console. [shared.legacy-api.zia-oauth:token-lifetime]

**Validation.** ZIA verifies the JWT signature with the authorization server's public key, then validates the scope claim: its API role must match an API role configured in ZIA or the request is rejected; it may also verify claims such as audience, issuer and client ID. The authorization servers must be added in ZIA for this. [shared.legacy-api.zia-oauth:validation] ZIA caches the identity provider's public key set briefly; after the cache expires or the keys rotate, validation may fail until ZIA refetches the JWKS, so the client should resend a request after a minute if authorization fails the first time. [shared.legacy-api.zia-oauth:jwks-cache-retry]

**Authorization servers in ZIA.** An organization can have up to two OAuth 2.0 authorization servers with only one enabled at a time, and JWT verification takes place only while the authorization server configuration is enabled. [shared.legacy-api.zia-oauth:server-limit] Managing authorization servers needs an admin role with the API Key Management permission enabled. [shared.legacy-api.zia-oauth:server-permission] An authorization server's name can contain only alphanumeric characters without spaces and cannot exceed 64 characters, and its description cannot exceed 256 characters. The public key set at the JWKS location is fetched by ZIA on a regular basis to verify JWTs, and the Save button appears only after Validate confirms the JWKS endpoint is configured correctly. [shared.legacy-api.zia-oauth:server-fields] [shared.legacy-api.zia-oauth:validation] When a value is specified for the audience, issuer or client ID field, requests are accepted only if the JWT contains a matching aud, iss or client_id claim. The client ID field is left blank when several client applications need access to the API, and where an identity provider uses cid or appid in place of client_id, ZIA matches the configured client ID against the available claim. [shared.legacy-api.zia-oauth:optional-claim-checks] If the authorization server uses a TLS certificate signed by an unrecognized CA, or has a root certificate issued by an unrecognized CA, a TLS handshake error occurs when ZIA connects to the JWKS endpoint; to avoid it, the JWKS Certificate Authentication option can be disabled or the server certificate changed. [shared.legacy-api.zia-oauth:jwks-certificate-authentication] The authorization servers page shows each server's Status (enabled or disabled) and its Last Successful Fetch Time, the date and time its public key was last fetched from the JWKS endpoint. [shared.legacy-api.zia-oauth:last-fetch-time] How often the key set is fetched is open [gap:shared.legacy-api.zia-oauth:jwks-fetch-period].

**Changing or losing a server.** If an authorization server configuration is already in use, changes to it may disrupt the API service, and deleting a server in use stops client applications from accessing the cloud service API with OAuth 2.0. [shared.legacy-api.zia-oauth:change-impact] A valid API subscription is required to add or manage authorization servers; after expiry the page is readable but not editable, and the configuration is re-enabled on renewal. Zscaler can disable the configuration for exceeding the API call threshold or violating its terms, after which the servers appear disabled, cannot be added, edited or deleted, and all API requests with a JWT from a disabled server are rejected. [shared.legacy-api.zia-oauth:subscription-and-disable] What happens to tokens when the other server is enabled is open [gap:shared.legacy-api.zia-oauth:second-server-tokens].

**Identity provider setup.** Setting up Okta, Microsoft Entra ID and PingFederate is in [Setting up Okta, Microsoft Entra ID and PingFederate as the ZIA OAuth 2.0 authorization server](kb:shared.legacy-api.zia-oauth-idp-setup); the guides differ on where the client credentials go [shared.legacy-api.zia-oauth-idp-setup:credentials-location](kb:shared.legacy-api.zia-oauth-idp-setup:credentials-location). The API role object is in [ZIA API roles, SD-WAN partner API roles and SD-WAN partner API clients](kb:shared.admin-rbac.zia-api-roles).

**Audit.** Operations authenticated this way are recorded in the audit logs under an auto-generated admin ID, one per API role, of the form `oauth-<rolename>$@<orgid>.<cloud_domain>`. [shared.legacy-api.zia-oauth:audit-admin-id]

What to check:
1. For a rejected OAuth call, whether the token's scope (or scp or roles) claim is cloud::org ID::API role and names an API role configured in ZIA.
2. For a first-call authorization failure after the identity provider rotated keys, whether the client retried after a minute.
3. To attribute OAuth API changes in audit logs, which oauth-<rolename>$@<orgid>.<cloud_domain> admin ID they appear under.

Not known (open gaps):
- How often the JWKS is fetched [gap:shared.legacy-api.zia-oauth:jwks-fetch-period]: settled by lab-test or support-ticket
- What happens to tokens from one server when the other of the two is enabled instead [gap:shared.legacy-api.zia-oauth:second-server-tokens]: settled by lab-test
