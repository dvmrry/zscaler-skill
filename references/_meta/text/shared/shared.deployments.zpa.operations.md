# What the ZPA deployment and operations guides say about App Connector, Application Discovery, Browser Access, Client Forwarding Policy, log streaming and provisioning (shared.deployments.zpa.operations)
Also called: zpa deployment and operations guide; zpa d&o guide

**App Connector.** App Connector deployment requires ZPA Professional, Business or Transformation Edition; certificate verification is not configurable by design, and *.prod.zpath.net must be in the SSL bypass list for App Connector traffic. [shared.deployments.zpa.operations:ac-subscription-and-cert] The customer maintains the host an App Connector runs on; Zscaler maintains only the App Connector application, not the underlying operating system. [shared.deployments.zpa.operations:ac-os-responsibility] For ZPA with ZDX, App Connector firewall rules must allow the configured report protocols to egress towards the application port and to the Zscaler Public Service Edge on port 443. [shared.deployments.zpa.operations:ac-zdx-egress] For a connector that no longer connects to the cloud, the guide stops the zpa-connector service, then (under its step to delete the App Connector) runs rm -f /opt/zscaler/var/*, and restarts the service; logs are collected with journalctl -u zpa-connector. [shared.deployments.zpa.operations:ac-reset-and-logs] See [ZPA App Connectors](kb:zpa.app-connectors).

**Application Discovery.** ZPA discovers an application only when a user requests access to it; applications defined with only a wildcard (*) are not available for application discovery; discovery works with wildcard-format domains or CIDR subnets and wider port ranges excluding TCP and UDP 53. [shared.deployments.zpa.operations:ad-prereq-and-wildcards] The Application Discovery guide says On Access health reporting is available for only discovered applications; the App Connector reports health from the user's access until up to 30 minutes after use; discovered application data is no longer listed in User Activity Diagnostics after 14 days. [shared.deployments.zpa.operations:ad-health-and-retention] Where On Access can be chosen is [divergence:shared.deployments.zpa.operations:on-access-scope]. ZPA always matches an application to the most specific app segment even if it could match a wildcard segment; a new specific segment (file.exapp.company.com) is not covered by the access policy of the wildcard segment (*.exapp.company.com) and needs its own policy, and ports on subnet or wildcard segments are not applied to more specific segments. [shared.deployments.zpa.operations:ad-specific-segment] If the IdP is defined as an application within an app segment, its Authentication Timeout must be Never, and an IdP domain overlapping a discovery domain must be bypassed in ZPA to avoid reauthentication failure; DNS search domains are needed for hostname-only access (e.g. DFS) so an FQDN is sent for discovery. [shared.deployments.zpa.operations:ad-idp-and-search-domains] If an application is not discovered, check it was accessed in the last 14 days, the discovery segment covers its ports, and the discovery criteria cover its destination. [shared.deployments.zpa.operations:ad-not-discovered-checks] See [How application discovery works and how a discovered application is defined](kb:zpa.app-segments.discovery).

**Browser Access.** Browser Access needs possibly an additional license, application servers supporting TLS 1.2, and every user (including contractors and third parties) provisioned in the ZPA IdP; it reaches only web-based applications (Privileged Remote Access covers other protocols). [shared.deployments.zpa.operations:ba-prerequisites] With different external and internal hostnames, internal hostnames are not on public DNS and backend SSL cannot be verified, so a web server certificate error is shown to end users; with the same hostname, internal hostnames are exposed on public DNS and backend SSL can be verified without a certificate error. [shared.deployments.zpa.operations:ba-hostnames] Browser Access cookies are session-based and cleared when the browser session ends; users reauthenticate based on the Authentication Timeout of the ZPA timeout policy rule; a 403 Forbidden can occur when an application fails to load a domain with CORS headers enabled. [shared.deployments.zpa.operations:ba-cookies-cors] See [Browser Access: clientless ZPA access to web applications](kb:zpa.browser-access).

**Client Forwarding Policy.** ZPA evaluates Client Forwarding Policy rules using the most specific application segment and top-down first match, before Access Policy rules; once a match is found other Client Forwarding Policy rules, including conflicts, are disregarded. [shared.deployments.zpa.operations:cfp-evaluation] Bypass ZPA bypasses applications for ZPA so Client Connector does not send their requests to ZPA (equivalent to Always for the segment Bypass setting); Only Forward Allowed Applications has Client Connector learn and forward traffic for applications the user is allowed to access, with other applications' requests going to the local network and not logged in ZPA; Forward to ZPA forwards application requests to ZPA, including for applications the user is not authorized to access, and by default these requests are logged in the Diagnostic logs as Policy not configured for access. [shared.deployments.zpa.operations:cfp-actions] The Client Forwarding Policy guide says that if Bypass ZPA and Forward to ZPA rules apply to the same application segment, Forward to ZPA takes precedence; for application segments the bypass setting takes precedence over any new Client Forwarding Policy rule; the Application Segment bypass behavior must be set to Use Client Forwarding Policy. [shared.deployments.zpa.operations:cfp-precedence] Which action wins is [divergence:shared.deployments.zpa.operations:cfp-bypass-vs-forward]. Criteria options include Client Connector Posture Profiles, Client Connect Trusted Networks, Client Types, Machine Groups and SAML and SCIM Attribute; Client Connector re-evaluates posture checks at startup and every 15 minutes thereafter; AND versus OR operators can explain unmet criteria. [shared.deployments.zpa.operations:cfp-criteria-and-posture] Only Forward Allowed Applications is recommended for a Client Forwarding Policy used as part of Source IP Anchoring in ZIA; the policy fails to apply when that action is selected and no Access Policy allowing access exists, because the application is absent from the downloaded list. [shared.deployments.zpa.operations:cfp-sipa-and-troubleshoot] See [ZPA client forwarding policy rules: actions, precedence and criteria](kb:zpa.policy.forwarding-rules).

**Log streaming.** The ZPA SIEM integration guide says that by default Zscaler retains User Activity, User Status and App Connector log information for up to 14 days and audit log information for up to 6 months, and that LSS integrated with a SIEM gives access beyond those periods. [shared.deployments.zpa.operations:lss-retention] Whether those periods are a ceiling or a floor is [divergence:shared.deployments.zpa.operations:lss-retention-bound]. A single Connector Group for both user traffic and log streaming is supported only in proof of concept scenarios and not for production; dedicated App Connectors for LSS log types are recommended, and connectors should be deployed in pairs for availability during upgrades. [shared.deployments.zpa.operations:lss-connectors] LSS does not transmit log data generated during a ZPA-to-App Connector connection loss; after restoration it can retransmit the last 15 minutes of log data but delivery is not guaranteed; it does not transmit data during an App Connector-to-SIEM loss, except Audit Log data. [shared.deployments.zpa.operations:lss-loss-behaviour] TLS between the log receiver and App Connector should be used across an untrusted network; it requires a client certificate for mutual TLS using a public root CA, and an untrusting receiving component can be diagnosed by temporarily disabling TLS. [shared.deployments.zpa.operations:lss-tls] See [ZPA log receivers and the Log Streaming Service](kb:zpa.log-receivers).

**Provisioning and authentication.** Zscaler supports only SCIM version 2.0 and SAML version 2.0 and later; SAML auto-provisioning provisions users and attributes each time a new user authenticates into Client Connector, while SCIM pushes users and attributes from the IdP to the ZPA user database. [shared.deployments.zpa.operations:prov-versions-and-methods] When SCIM is enabled for the first time or the SCIM provisioning option is toggled, the SCIM database is synchronized, which might impact authentication until all users are synced from the IdP. [shared.deployments.zpa.operations:prov-scim-switch] Users might get a Client Connector connection error when enabling SCIM sync with Okta, because Okta does not sync users to ZPA before SCIM is enabled so users do not initially appear in the SCIM user database. [shared.deployments.zpa.operations:prov-okta-scim] Authentication domains are added by submitting a provisioning ticket with Zscaler Support. [shared.deployments.zpa.operations:prov-auth-domains] See [ZPA authentication: IdP configuration, authentication settings and user risk scores](kb:zpa.authentication).

Sources disagree (name both sides):
- Whether the ZPA log retention periods are a ceiling or a floor: the SIEM integration guide says up to 14 days and up to 6 months, the ZPA log retention articles say at least 14 days and at least 6 months. [divergence:shared.deployments.zpa.operations:lss-retention-bound]
  - zscaler-help: Zscaler retains User Activity, User Status and App Connector logs for up to 14 days and audit logs for up to 6 months.
  - zscaler-help: Zscaler retains User Activity, User Status and App Connector logs for rolling periods of at least 14 days.
  Impact: Whether logs older than 14 days can still be present in the console, or are guaranteed to be gone, depends on which page applies; LSS to a SIEM avoids the question.
- Where On Access health reporting can be chosen: the Application Discovery guide and the discovery article say only for discovered applications, while the application segment settings article makes On Access the console default for any segment. [divergence:shared.deployments.zpa.operations:on-access-scope]
  - zscaler-help: On Access health reporting is available for only discovered applications.
  - zscaler-help: Health reporting can be Continuous, On Access or None for an application segment, and the default setting is On Access.
  Impact: An admin cannot tell from the pages whether On Access is selectable on a segment that is not an discovered-application segment, or whether the default applies there.
- Which Client Forwarding Policy action wins for the same application segment: the Client Forwarding Policy guide says Forward to ZPA takes precedence over Bypass ZPA, the client forwarding policies article says Bypass ZPA takes precedence for a domain with different ports, and the guide's own evaluation says the first match in top-down order wins. [divergence:shared.deployments.zpa.operations:cfp-bypass-vs-forward]
  - zscaler-help: If Bypass ZPA and Forward to ZPA rule actions apply to the same application segment, Forward to ZPA takes precedence.
  - zscaler-help: For a given domain with different ports, the Bypass ZPA rule action takes precedence.
  Impact: The two statements cover different scopes (same segment versus same domain with different ports), and the guide's first-match rule sits beside its Forward-wins rule; neither page reconciles them.
