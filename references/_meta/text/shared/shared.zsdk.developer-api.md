# The ZSDK developer API: classes, tunnels, lifecycle and notifications (shared.zsdk.developer-api)
Also called: startZeroTrustTunnel; startPreLoginTunnel; ZscalerSDK; ZscalerConfiguration; ZscalerProxyInfo; ZscalerSDKException; ZscalerError; zsdk prelogin tunnel; zsdk zero trust tunnel; zsdk notifications; zsdk suspend resume; ZSCALERSDK_TUNNEL_AUTHENTICATION_REQUIRED; ZscalerSDKTunnelResourceBlocked; failIfDeviceCompromised; ZscalerSDKConfiguration; ZscalerSDKProxyInfo; ZscalerSDKNotificationEnum; ZSCALER_RECEIVER_ID; ZscalerSDKProxyStartFailed

The ZSDK developer reference documents the classes ZscalerSDK (the primary class for ZSDK methods and properties), ZscalerConfiguration (the configurable properties), ZscalerProxyInfo (proxy details) and ZscalerError on iOS or ZscalerSDKException on Android (errors). [shared.zsdk.developer-api:classes] On Android, `init` establishes the connection between the application and ZSDK and is required before calling other methods; iOS uses `sharedInstance()` to return the shared instance. [shared.zsdk.developer-api:initialization]

## Tunnels

`startPreLoginTunnel` takes the app key and device UDID and starts a Prelogin tunnel, for which Zscaler issues a client certificate valid for 180 days; `startZeroTrustTunnel` also takes an access token and starts a Zero Trust tunnel, whose client certificate is valid for 7 days. `stopTunnel()` terminates any active tunnels. [shared.zsdk.developer-api:tunnel-types] The client certificate lifetimes per tunnel type are in dispute with the access policy article [shared.zsdk.configuration:client-certificate-validity](kb:shared.zsdk.configuration:client-certificate-validity). From ZSDK version 2.0, `startZeroTrustTunnel()` can be called while a Prelogin tunnel is running, and ZSDK upgrades the existing tunnel connection to Zero Trust. [shared.zsdk.developer-api:tunnel-upgrade] `status()` returns a ZscalerSDKTunnelStatus with tunnelConnectionState (ON, OFF or CONNECTING) and tunnelType (0 Prelogin, 1 Zero Trust, -1 Unknown). [shared.zsdk.developer-api:tunnel-status]

## Configuration and lifecycle

ZscalerConfiguration properties include failIfDeviceCompromised, which prevents the mTLS tunnels on jailbroken or rooted devices, blockZPAConnectionsOnTunnelFailure, which blocks ZPA connections when any tunnel fails, useProxyAuthentication, and on iOS automatic configuration of URL sessions and WebViews. [shared.zsdk.developer-api:configuration-properties] `suspend()` suspends ZSDK and stops active tunnels: on iOS it is called before app suspension, on Android when the app enters the background with no network operation pending or in progress. `resume()` is called when the app returns to the foreground (on Android, when it is ready to resume network operations). [shared.zsdk.developer-api:suspend-resume] `exportLogs` exports logs as a ZIP file, `clearLogs()` clears them, and `resetProxyPortAndRequireSessionRecreation()` resets the proxy port when setup fails, after which all HTTPS sessions and WebView requests must be recreated. [shared.zsdk.developer-api:maintenance] The Android sample app registers a process lifecycle observer in Application.onCreate that calls `ZscalerSDK.resume()` on ON_START, as soon as the app comes to the foreground or network requests are going to be resumed, whichever is earlier, and `ZscalerSDK.suspend()` on ON_STOP, when the app goes to the background or ongoing network requests are finished, whichever is later. [shared.zsdk.developer-api:android-lifecycle-hooks] The Android ZscalerSDKConfiguration is built with the named arguments useProxyAuthentication, failIfDeviceCompromised, blockZPAConnectionsOnTunnelFailure, enableDebugLogsInConsole and logLevel (a ZscalerSDKConfiguration.LogLevel); the sample app's defaults set failIfDeviceCompromised and enableDebugLogsInConsole to true and the log level to debug. [shared.zsdk.developer-api:android-config-constructor] The Android sample app calls `ZscalerSDK.init(application, ...)` in MainActivity.onCreate inside a try block that catches ZscalerSDKException and abandons startup on failure, can change settings afterwards with `ZscalerSDK.setConfiguration(...)`, and reads the numeric error from the exception's errorCode property. [shared.zsdk.developer-api:android-init-errors] In the Android sample app's manual mode, the app must call its WebView proxy setup after starting either tunnel so WebView traffic goes over the tunnel: it applies the host and port from ZscalerSDKProxyInfo through the androidx.webkit ProxyController (feature PROXY_OVERRIDE), and the code comment says WebView connections are not guaranteed to use the new proxy immediately, so wait for the success listener before loading a page. [shared.zsdk.developer-api:android-webview-manual-proxy] The iOS public headers declare ZscalerSDKProxyInfo (proxyHost, proxyPort and optional username and password, built with initWithHost:port:username:password:), ZscalerSDKTunnelStatus (a tunnelConnectionState string and a tunnelType) and the tunnel types ZscalerSDKTunnelTypeUnknown, ZscalerSDKTunnelTypePreLogin and ZscalerSDKTunnelTypeZeroTrust. [shared.zsdk.developer-api:ios-header-types]

## Notifications

ZSDK reports tunnel state through notifications (Android enum, iOS NSNotification): `ZSCALERSDK_TUNNEL_CONNECTED` / `ZscalerSDKTunnelConnected` when the tunnel is ready and the app can send HTTPS and WebView traffic through it; `ZSCALERSDK_TUNNEL_DISCONNECTED` / `ZscalerSDKTunnelDisconnected` when it has stopped; `ZSCALERSDK_TUNNEL_RECONNECTING` / `ZscalerSDKTunnelReconnecting` when connecting to the Public Service Edge had an issue and ZSDK keeps trying. [shared.zsdk.developer-api:notifications-state] Three notifications call for action: `ZSCALERSDK_TUNNEL_AUTHENTICATION_REQUIRED` / `ZscalerSDKTunnelAuthenticationRequired` means the client certificate and proof of authentication or authorization have expired, resolved by calling `startZeroTrustTunnel()` with a new valid access token; `ZSCALERSDK_TUNNEL_RESOURCE_BLOCKED` / `ZscalerSDKTunnelResourceBlocked` means access is blocked by the access policy, resolved by making sure the application segment is configured; `ZSCALERSDK_PROXY_START_FAILED` / `ZscalerSDKProxyStartFailed` means proxy initialization failed, resolved by calling `resetProxyPortAndRequireSessionRecreation()`. [shared.zsdk.developer-api:notifications-action] The iOS headers declare the notification names ZscalerSDKTunnelDisconnected, ZscalerSDKTunnelConnected, ZscalerSDKTunnelReconnecting, ZscalerSDKTunnelAuthenticationRequired, ZscalerSDKTunnelResourceBlocked and ZscalerSDKProxyStartFailed, with the userInfo keys ZscalerSDKNotificationNameUserInfoKey and ZscalerSDKNotificationMessageUserInfoKey. [shared.zsdk.developer-api:ios-notification-names] The iOS header says ZscalerSDKProxyStartFailed means ZSDK failed to set up its proxy and requests using the proxy will fail; recovery is either to wait and try to restart the tunnel, or to call resetProxyPortAndRequireSessionRecreation() and then invalidate and recreate all ZSDK-configured sessions, which with automatic configuration means all URLSessions. [shared.zsdk.developer-api:ios-proxy-start-failed] In the Android sample app, notifications arrive as broadcasts: the app registers a receiver for the `ZscalerSDK.ZSCALER_RECEIVER_ID` action as not exported, reads the integer extra `ZscalerSDK.NOTIFICATION_CODE`, which it uses as an index into `ZscalerSDKNotificationEnum.values()`, and the string extra `ZscalerSDK.NOTIFICATION_MESSAGE`. [shared.zsdk.developer-api:android-notification-broadcast]

## Vendor best practices

Zscaler recommends using the shared instance of the SDK class, setting ZscalerConfiguration before starting any tunnel, handling errors through ZscalerError or ZscalerSDKException and their codes, completing network operations before suspension, subscribing to tunnel-state notifications (BroadcastReceiver on Android, NSNotification on iOS), and exporting and clearing logs as needed. [shared.zsdk.developer-api:best-practices] Error codes raised through `ZscalerError` and `ZscalerSDKException` are listed in [ZSDK error codes: SDK errors 9001-9505 and ZSDK API errors 2001-2999](kb:shared.zsdk.error-codes). The repositories that carry the SDK are covered in [Adding the ZSDK to an app: Android, iOS, React Native and SwiftUI packages, prerequisites and sample apps](kb:shared.zsdk.sdk-integration). The help page and the code disagree on two class names [divergence:shared.zsdk.developer-api:class-names].

What to check:
1. Which tunnel the app started (Prelogin or Zero Trust) and the matching certificate lifetime, from the status call.
2. Whether the app handles the authentication-required notification by calling the Zero Trust start method with a fresh access token.
3. Whether the app calls suspend and resume at the platform-specific points.
4. Whether an Android WebView is given the proxy after the tunnel starts, and that its success listener fires before the first page load.

Sources disagree (name both sides):
- Whether the proxy and configuration classes are named ZscalerProxyInfo and ZscalerConfiguration. [divergence:shared.zsdk.developer-api:class-names]
  - zscaler-help: The developer reference names the classes ZscalerConfiguration and ZscalerProxyInfo.
  - zsdk-android: The Android sample code imports ZscalerSDKConfiguration and ZscalerSDKProxyInfo.
  - zsdk-ios: The iOS header declares ZscalerSDKProxyInfo.
  Impact: A search for the help page's class names finds nothing in app code; the type names to look for are ZscalerSDKConfiguration and ZscalerSDKProxyInfo.
