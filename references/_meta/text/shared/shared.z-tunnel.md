# Z-Tunnel 1.0 and 2.0: where each question is answered (shared.z-tunnel)
Also called: z-tunnel; ztunnel; z-tunnel 1.0 vs 2.0; z-tunnel 2.0 migration; z-tunnel 2.0 falling back to 1.0; ztunnelversion

Z-Tunnel is how Client Connector carries traffic to the service in Tunnel mode. The protocol, bypass and rollout detail lives in the Client Connector subjects; this subject routes the cross-product questions.

1. **What does each version carry?** Z-Tunnel 1.0 is CONNECT-based for proxy-aware or port 80 and 443 traffic, Z-Tunnel 2.0 a DTLS or TLS packet tunnel for all ports and protocols: [Z-Tunnel 1.0 forwards traffic by CONNECT requests, like a traditional proxy, sending all proxy-aware traffic or port 80/443 traffic depending on the forwarding profile; it is selected in a forwarding profile in Tunnel mode with the packet filter driver enabled.](kb:zia.traffic-forwarding.zcc:z-tunnel-1), [Z-Tunnel 2.0 sends packets over DTLS or TLS and can carry all ports and protocols; using it means deploying a supported Client Connector version, selecting Z-Tunnel 2.0 in a Tunnel-mode forwarding profile with the packet filter driver enabled, and configuring bypasses in App Profiles.](kb:zia.traffic-forwarding.zcc:z-tunnel-2), with the selection rules in [Z-Tunnel 1.0 and 2.0: what each carries and how a profile selects one](kb:zcc.z-tunnel.versions).
2. **Which network types use which version?** The version is set per forwarding profile and the action per network type: [For each network type (On-Trusted, VPN-Trusted, Off-Trusted, Split VPN-Trusted) the profile sets one Internet & SaaS action: Tunnel, Tunnel with Local Proxy, Enforce Proxy or None.](kb:zcc.forwarding-profiles.internet-actions:four-actions), [In Tunnel mode the forwarding profile's Tunnel Version Selection chooses the Z-Tunnel version, and the field appears only when the Packet Filter-Based driver is selected; choosing Z-Tunnel 2.0 opens the Advanced Z-Tunnel Configuration settings.](kb:zcc.z-tunnel.versions:version-select-needs-pf).
3. **Where do bypasses go?** Not in the app profile PAC for Z-Tunnel 2.0, but in VPN gateway bypasses and destination exclusions, with domain bypasses through PAC files and the listening proxy: [Bypasses for Z-Tunnel 2.0: VPN gateway bypasses, destination exclusions and inclusions, domain bypasses](kb:zcc.z-tunnel.bypasses).
4. **How is a tenant migrated?** The vendor's phased procedures for a new deployment and a migration from 1.0: [Rolling out Z-Tunnel 2.0 and migrating from 1.0](kb:zcc.z-tunnel.deployment).
5. **What happens when Z-Tunnel 2.0 cannot be set up?** Transport fallback and the configurable setup failure behavior: [Z-Tunnel 2.0 transport: DTLS and TLS, fallback, MTU, and what happens when the tunnel cannot be set up](kb:zcc.z-tunnel.transport).

**Why a device is on Z-Tunnel 1.0.** A NAT that does not keep one IP per device splits the control and data connections and Z-Tunnel 2.0 falls back: [Z-Tunnel 2.0 needs a NAT device that uses a single IP for all connections from one device; otherwise control and data connections can land on different Service Edges, Z-Tunnel 2.0 fails to establish and the client falls back to Z-Tunnel 1.0.](kb:zia.traffic-forwarding.zcc:z-tunnel-2-single-ip-nat); GRE egress with several IPs or ECMP is one way that happens: [A site whose egress uses several GRE tunnels with different public source IPs, or ECMP, can present one device's Z-Tunnel 2.0 control and data connections from different IPs; per the vendor that splits them across Service Edges and Z-Tunnel 2.0 falls back to 1.0.](kb:zia.traffic-forwarding.mixed-deployments:gre-ztunnel2-egress). A Z-Tunnel 2.0 profile also sends some web traffic over 1.0 by design: [A profile set to Z-Tunnel 2.0 still sends web traffic over Z-Tunnel 1.0 when 2.0 cannot be set up and the setup failure behavior falls back to 1.0, when Redirect Web Traffic is on without Use Z-Tunnel 2.0 for Proxied Web Traffic, and when a request arriving on the Client Connector listening proxy matches an app profile PAC statement that sends it to a specific Public Service Edge.](kb:zcc.z-tunnel.versions:web-on-1-under-2). Whether a device keeps running 1.0 when the policy changed before its client was upgraded is open [gap:shared.z-tunnel:client-version-lag].

**What Z-Tunnel 1.0 leaves out.** Z-Tunnel 1.0 carries only proxy-aware or port 80 and 443 traffic: [Z-Tunnel 1.0 forwards traffic by CONNECT requests, like a traditional proxy, sending all proxy-aware traffic or port 80/443 traffic depending on the forwarding profile; it is selected in a forwarding profile in Tunnel mode with the packet filter driver enabled.](kb:zia.traffic-forwarding.zcc:z-tunnel-1); QUIC then does not reach Zscaler: [So when the only traffic sent to Zscaler is Client Connector traffic on Z-Tunnel 1.0, or TCP 80 and 443 over a tunnel, QUIC UDP does not reach Zscaler at all, and no Zscaler Firewall Filtering rule inspects or blocks it.](kb:zia.saas-apps.quic-conferencing:tunnel1-udp-leaves). What happens to the rest of the traffic (other UDP, ICMP, non-web TCP and non-standard ports) is open [gap:shared.z-tunnel:tunnel-1-other-traffic].

**Seeing the version.** The NSS web and firewall log formats both carry `ztunnelversion`, the Z-Tunnel version of Client Connector traffic, with ZTUNNEL_1_0 as the documented example value. [shared.z-tunnel:log-field] Whether Z-Tunnel 2.0 traffic is logged as ZTUNNEL_2_0 is open [gap:shared.z-tunnel:log-value-2]. The field definitions are in the log types [ZIA web log (NSS web feed)](kb:zia/web-log) and [ZIA firewall log (NSS firewall feed)](kb:zia/firewall-log).

**GRE sites.** Zscaler's guidance is [Zscaler says not to route Z-Tunnel 2.0 through GRE tunnels; to prevent performance issues where GRE exists, either have the forwarding profile fall back to Z-Tunnel 1.0 when the trusted network criteria are met, or exclude Z-Tunnel 2.0 traffic from the GRE tunnel with a policy-based route.](kb:zcc.z-tunnel.deployment:gre-guidance), and the GRE side is [GRE tunnels to Zscaler: where each question is answered](kb:shared.gre). The legacy explanation that double encapsulation inside GRE causes the performance problem is open [gap:shared.z-tunnel:gre-double-encapsulation].

**Business Continuity Cloud.** Z-Tunnel 2.0 is not supported in business continuity mode: [Zscaler Tunnel 2.0 is not supported in business continuity mode.](kb:zia.private-service-edge.business-continuity:z-tunnel-2-unsupported), with the supported methods in [Private Service Edges in the Business Continuity Cloud](kb:zia.private-service-edge.business-continuity).

**Upstream proxies.** Whether Z-Tunnel 1.0 works through an enterprise proxy on the network path is open [gap:shared.z-tunnel:tunnel-1-upstream-proxy].

What to check:
1. Which Z-Tunnel version the traffic actually used, from the ztunnelversion field of the web or firewall log.
2. Whether the device's egress keeps one public IP for all its connections (no ECMP or several GRE source IPs on the path).
3. Whether the device runs a Client Connector version that supports Z-Tunnel 2.0.
