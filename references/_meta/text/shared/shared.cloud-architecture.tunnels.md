# Z-Tunnel and Microtunnel: the two tunnel layers of Private Access (shared.cloud-architecture.tunnels)
Also called: z-tunnel vs m-tunnel; microtunnel; m-tunnel; synthetic ip; zpa synthetic ip; zpa dns interception; mpls label

Private Access carries traffic in two layers: a point-to-point Z-Tunnel, and Microtunnels inside it. [The Z-Tunnel is defined as a mutually authenticated point-to-point connection between Zscaler Client Connector and a Zscaler-managed Public Service Edge, or between an App Connector and an organization-managed Private Service Edge. It carries no direct IP data and can carry multiple Microtunnels.](kb:zpa.private-service-edges.data-path:ztunnel-endpoints)

**Z-Tunnel.** [All communication between Private Access components travels within a mutually pinned, client and server certificate-verified TLS connection, and a microtunneling protocol runs inside that Zscaler Tunnel (Z-Tunnel).](kb:zpa.private-service-edges.data-path:ztunnel-mutual-tls) An additional Z-Tunnel is created between Zscaler Client Connector and a Public Service Edge, or between an App Connector and a Private Service Edge, to support multi-tenancy: Client Connector establishes a Z-Tunnel with the tenant and a separate one with the partner tenant, and the second works without additional setup. [shared.cloud-architecture.tunnels:second-ztunnel] Client Connector's Z-Tunnel 1.0 and 2.0 for Internet & SaaS are a different subject: [Z-Tunnel](kb:zcc.z-tunnel).

**Microtunnel.** [A Microtunnel is an end-to-end channel that is created on demand between Zscaler Client Connector and an internal application, through a Public or Private Service Edge and an App Connector.](kb:zpa.troubleshooting.access-path:mtunnel-path) Public and Private Service Edges create and manage Microtunnels, including authentication, policy, setup, teardown and data forwarding; M-Tunnels are end-to-end encrypted connections designed to keep all traffic separate. [shared.cloud-architecture.tunnels:edges-manage-mtunnels] [An M-Tunnel originates in Zscaler Client Connector, extends to the Private or Public Service Edge using a tag Client Connector created, extends to the App Connector using a different tag the connector chose, and the App Connector connects it to the application server. At no point is actual IP identification data passed.](kb:zpa.private-service-edges.data-path:mtunnel-stitching) The tags created by Client Connector and the App Connector work like the label stack of an MPLS network: as a label-switched path identifies a connection, the tags identify a unique connection for each application request. [shared.cloud-architecture.tunnels:mpls-analogy] The Public Service Edge that sets an M-Tunnel up is [For any Microtunnel, the Control Service Edge is the Public Service Edge that handles cloud-level system messages to establish the M-Tunnel.](kb:zpa.public-service-edges.what-it-is:control-service-edge).

**How the client gets there.** [Zscaler Client Connector recognizes the internal applications that are available via Private Access (access to them is defined in Private Access policies), intercepts the user requests for them and forwards those requests to the Zero Trust Exchange.](kb:zpa.troubleshooting.no-access:zcc-intercepts-defined-apps) An organization can specify whether resources must go through Private Access at all times, only on an untrusted network, or never. [shared.cloud-architecture.tunnels:zcc-intercepts] Client Connector associates permitted internal applications with a set of synthetic IP addresses: when a client application sends a DNS request for a domain protected by Private Access, Client Connector intercepts it and answers with the synthetic IP address associated with that application. [shared.cloud-architecture.tunnels:synthetic-ip] The client application therefore connects to a synthetic address and is never given the application server's real IP: the DNS answer is synthetic and the M-Tunnel passes no IP identification data along its path. [shared.cloud-architecture.tunnels:client-never-sees-app-ip]
