# How the Go SDK builds requests and interprets responses: client options, bodies, status codes, bulk deletes (shared.sdk-go.request-handling)
Also called: sdk proxy ignored; terraform http_proxy not used; WithProxyHost no effect; WithHttpClientPtr ignored; NewZccRequestDo empty body; NewRequestDo always 200; 204 returns EOF; unexpected response bulk delete; bulk delete truncates ids; object returned from api was not a pointer; CreateResource content-type

These are claims about the Go SDK (the same client whose retries are in [How the Go SDK retries requests (and replays writes)](kb:shared.sdk-go.retries))'s request and response handling, shared by the Terraform providers built on it. They are about what the client does with options, bodies and status codes.

**Client options.** `NewConfiguration` builds every per-service HTTP client (`setHttpClients`) before it applies the caller's option functions. Options therefore see clients that already exist, and the options that call `setHttpClients` again rebuild them. [shared.sdk-go.request-handling:clients-built-before-options] `WithProxyHost`, `WithProxyPort`, `WithProxyUsername`, `WithProxyPassword` and `WithTestingDisableHttpsCheck` only assign configuration fields; they do not rebuild any client. The proxy and TLS-skip settings are read inside `getHTTPClient`, which fixes them into the transport it builds. A setter that runs after the last client build does not reach the live transport, which keeps the proxy chosen at build time (by default, proxy-from-environment). [shared.sdk-go.request-handling:proxy-and-tls-options-only-set-fields] `WithRequestTimeout`, `WithRateLimitMaxRetries`, `WithRateLimitMinWait`, `WithRateLimitMaxWait` and `WithRateLimitRemainingThreshold` each call `setHttpClients` again, building fresh clients from the configuration as it stands at that moment. [shared.sdk-go.request-handling:rate-and-timeout-options-rebuild-clients] A client passed with `WithHttpClientPtr` is stored only as the generic client, and any later rebuilding option overwrites it. Requests to ZIA, ZPA, ZCC, ZTW and ZDX endpoints use the per-service clients chosen by `getServiceHTTPClient`. The client holds its configuration as `oauth2Credentials`, so a caller-supplied client is used only where that function returns `oauth2Credentials.HTTPClient`: admin endpoints, the default branch, and endpoints whose service type cannot be detected. [shared.sdk-go.request-handling:custom-http-client-not-used-for-service-endpoints]

**Proxy options in providers.** In the OneAPI option list of each audited provider (ZIA, ZPA, ZTC, ZCC), the proxy options are appended after the timeout and rate-limit options that rebuild the clients, and none of the four sets the TLS-skip option. The configured proxy host and port are therefore recorded in the configuration but absent from the transports that carry service requests; a proxy set through the standard environment variables is unaffected, because the transport defaults to reading them. The SDK's own `ZSCALER_CLIENT_PROXY_HOST` and `ZSCALER_CLIENT_PROXY_PORT` environment variables are read before the first client build and do take effect, and the default transport still honors `HTTP_PROXY`/`HTTPS_PROXY`; only the proxy passed through the provider's configuration is lost. [shared.sdk-go.request-handling:providers-append-proxy-after-rebuilds] Whether a configured proxy is used for service requests is open [gap:shared.sdk-go.request-handling:proxy-effect].

**Request bodies and response status.** `NewZccRequestDo` JSON-marshals its `body` argument unconditionally on the OneAPI (non-legacy) path, and four SDK methods (admin-user update, both entitlement updates, manage-pass update) pass it a `bytes.NewBuffer` of bytes they have already marshaled. A `*bytes.Buffer` has no exported fields, so it marshals as `{}`, and the request carries an empty object instead of the payload. [shared.sdk-go.request-handling:zcc-request-do-double-marshals] The audited ZCC provider build does not call the affected methods, so the double-marshal is reached only by code that calls those SDK functions directly. [shared.sdk-go.request-handling:zcc-double-marshal-not-reached-by-provider] The ZPA, ZCC and ZDX request helpers discard the response object that `ExecuteRequest` returns and build a new `http.Response` holding only `StatusCode: http.StatusOK` and the body. Whatever success status the API sent, such as Created or No Content, reaches the caller as `http.StatusOK`, and response headers are lost. [shared.sdk-go.request-handling:request-do-fabricates-200] Because the wrapper always reports 200, status checks written after it, such as the ZCC service methods' `resp.StatusCode != http.StatusOK` guards, can never fire. A real failure status is already turned into an error inside `ExecuteRequest`, so the guard adds nothing; a success status other than 200 is indistinguishable from 200. [shared.sdk-go.request-handling:fabricated-200-disables-status-checks] When a caller passes a decode target and the response body is empty (such as a 204), the ZPA, ZCC and ZDX wrappers still run the decoder over zero bytes, which returns `io.EOF`; the wrapper returns that as an error even though the request succeeded. [shared.sdk-go.request-handling:empty-success-body-decoded-as-eof]

**Create responses.** ZTW `CreateResource` decodes the response into the typed object only when the `Content-Type` header equals `application/json` exactly (case-insensitive). Any other value, including a valid `application/json; charset=utf-8`, takes the else branch, which returns the raw `*http.Response` with a nil error. [shared.sdk-go.request-handling:ztw-create-requires-exact-content-type] ZTW service create methods type-assert the value `CreateResource` returns. If the response header did not match exactly, the assertion fails and the method returns an error after the POST was already sent, so the caller sees a failed create for a request the server may have accepted. [shared.sdk-go.request-handling:ztw-create-type-assert-fails-after-post] The ZIA `Create` helper has the same exact-match `Content-Type` comparison and the same raw-response fallback, and ZIA service create methods type-assert its result the same way. The ZIA provider builds on v3.8.44 and reaches it wherever its resources call these service create methods (75 files use `Client.Create`, not individually traced). [shared.sdk-go.request-handling:zia-create-same-exact-content-type] Whether the APIs send the parameterized content types or empty bodies that trigger these is open [gap:shared.sdk-go.request-handling:server-response-shapes]. The same post-write failure is described in [How the Go SDK retries requests (and replays writes)](kb:shared.sdk-go.retries).

**Bulk deletes.** The ZTW `BulkDeleteResource` and ZIA `BulkDelete` helpers treat any nonempty body after a successful request as an error: they return a 200 response together with an "unexpected response" error. Only an empty body counts as success. [shared.sdk-go.request-handling:bulk-delete-rejects-nonempty-success] Nothing in the ZTW services calls `BulkDeleteResource`, and the ZTC provider does not either, so that helper is reached only by direct SDK callers. ZIA's `BulkDelete` is called by three ZIA service helpers (locations, VPN credentials, users); the ZIA provider's only use is a sweeper test, not a resource. [shared.sdk-go.request-handling:bulk-delete-helpers-reach] Three ZIA bulk-delete helpers cut the ID list to a local maximum (100 for locations and VPN credentials, 500 for users) and send only the first IDs. They do not chunk the rest and report nothing about the dropped IDs: they return only the bulk-delete call's own result, and the only trace is an INFO log line. The users helper's comment says "first 100" while its constant is 500. [shared.sdk-go.request-handling:bulk-delete-helpers-truncate-ids] Those three are the only ID-list truncations found in the ZIA, ZPA, ZCC and ZTW services, and no provider resource calls them: the ZIA provider's one caller is a sweeper test that batches the IDs itself. [shared.sdk-go.request-handling:bulk-delete-truncation-scope]

Two retry-loop details are not covered by [How the Go SDK retries requests (and replays writes)](kb:shared.sdk-go.retries). In the 401, edit-lock (409/412) and 403 LIMIT_EXCEEDED branches of the outer retry loop, the SDK reads the response body with `io.ReadAll`, then replaces `resp.Body` with an in-memory reader without closing the original. Only the final success path drains and closes the body (`tryDrainBody`). Whether this holds connections open depends on the transport, since the body was read to its end. [shared.sdk-go.request-handling:retry-paths-replace-body-without-closing] The outer retry loop waits with plain `time.Sleep` in its rate-limit, edit-lock, 5xx and session-refresh branches. The rate-limit branch checks the context before it sleeps, but none of the sleeps can be cut short, so cancellation is noticed only after the wait ends. [shared.sdk-go.request-handling:retry-sleeps-ignore-cancellation]

Related: empty-body handling for ZIA updates is in [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding); token handling in [How the Go SDK obtains and renews OneAPI tokens](kb:shared.sdk-go.auth-lifecycle); response caching in [The Go SDK's response cache and request deduplication](kb:shared.sdk-go.cache).

`CheckErrorInResponse` extracts `code`, `message`, `id`, `reason` and `exception` from an error body only when the `Content-Type` header contains the literal `application/json` (a case-sensitive substring match); for any other content type the trimmed body text becomes the message, except that a non-JSON body containing "only through zscaler oneapi" (compared in lower case) returns a OneAPI fallback error instead. [shared.sdk-go.request-handling:error-json-content-type]

**Error exits.** In the Go SDK's OneAPI `ExecuteRequest`, four exits pass the HTTP response through `errorx.CheckErrorInResponse`, so the caller gets the API's own error: retries exhausted when a response exists, a tenant `LIMIT_EXCEEDED`, any other 4xx ("client error") and any other status of 300 or more ("API error"). These exits instead return a plain `fmt.Errorf` error with no response parsed: retries exhausted with no response, the request timeout, `SESSION_NOT_VALID` retries exhausted, a token refresh failure after session invalidation, a rate-limit wait the API requires, and a context cancelled during a rate-limit wait. [shared.sdk-go.request-handling:oneapi-exits-typed-vs-plain]

Inferred, not quoted (say so when an answer rests on one):
- [shared.sdk-go.request-handling:providers-append-proxy-after-rebuilds] Tier B: Rests on the order of entries in each provider's setter slice (applied in order by `NewConfiguration`) and on a search for the TLS option: `git -C vendor/<provider> grep -n 'DisableHttpsCheck\|InsecureSkipVerify' <tag> -- '*.go'` returns nothing outside tests for tf-zia v4.8.3, tf-zpa v4.4.10, tf-ztc v0.2.0 and tf-zcc v0.1.0-beta.1. Not observed against a running proxy. The per-product legacy clients under zscaler/zpa, zscaler/zia and zscaler/ztw have their own option functions and were not traced.
- [shared.sdk-go.request-handling:zcc-request-do-double-marshals] Tier B: The `{}` result is Go standard-library behavior, reproduced locally with `json.Marshal(bytes.NewBuffer(...))`; no request was sent. What the ZCC API does with a `{}` body is server behavior and was not tested.
- [shared.sdk-go.request-handling:zcc-double-marshal-not-reached-by-provider] Tier B: Absence: `git -C vendor/terraform-provider-zcc grep -n 'entitlements\|manage_pass\|UpdateAdminUser' v0.1.0-beta.1 -- '*.go'` returns no match, and the only `admin_users` use is the read-only `GetAdminUsers` in internal/framework/datasources/admin_user.go. Other SDK callers (for example the zscalerctl tool) were not searched. In the SDK, `git grep 'NewZccRequestDo(.*bytes\.' v3.8.37 -- zscaler/zcc zscaler/zpa` lists exactly these four call sites.
- [shared.sdk-go.request-handling:fabricated-200-disables-status-checks] Tier B: Depends on `ExecuteRequest` returning an error for statuses of 300 and above, which is read from its retry loop (`if resp.StatusCode < 300 { break }` followed by error returns) and not exercised. At v3.8.42 the ZPA `BulkReorder` functions do compare the status after `NewRequestDo` (policysetcontroller.go:332 and policysetcontrollerv2.go:410, quoted below), and by this claim those checks cannot fire. `git grep -n -E "StatusCode *(!=|==|<|>|>=|<=)" v3.8.42 -- zscaler/zpa/services ':!*_test.go'` returns only those two lines.
- [shared.sdk-go.request-handling:empty-success-body-decoded-as-eof] Tier B: The `io.EOF` result is Go standard-library behavior for `json.NewDecoder(...).Decode` on empty input, reproduced locally. It is reached only when a server answers a call that has a non-nil decode target with an empty body; which ZPA and ZCC endpoints do so is server behavior and was not traced per endpoint.
- [shared.sdk-go.request-handling:ztw-create-type-assert-fails-after-post] Tier B: Needs the ZTC API to send a `Content-Type` with parameters (or any value other than exactly `application/json`) on create responses, which is server behavior and not shown by the SDK. 18 ZTW service files call `CreateResource` (`git grep -l 'Client.CreateResource(ctx' v3.8.40 -- zscaler/ztw`); two were read in full. ZTC provider v0.2.0 builds on v3.8.40.
- [shared.sdk-go.request-handling:zia-create-same-exact-content-type] Tier B: The comparison is quoted; the type assertion was read in one ZIA service (url categories). `git grep -l 'Client.Create(ctx' v3.8.44 -- zscaler/zia` lists 75 files, none of which were individually checked. Whether the ZIA API sends a parameterized `Content-Type` on create is server behavior and was not tested.
- [shared.sdk-go.request-handling:bulk-delete-helpers-reach] Tier B: Absence searches: `git -C vendor/zscaler-sdk-go grep -n 'BulkDelete' v3.8.40 -- zscaler/ztw` (only the legacy client's own method), `git -C vendor/terraform-provider-ztc grep -n 'BulkDelete' v0.2.0 -- '*.go'` (none), and `git -C vendor/terraform-provider-zia grep -n 'BulkDelete' v4.8.3 -- '*.go'` (only zia/provider_sweeper_test.go). ZPA has its own bulk-delete helpers on `NewRequestDo` that were not traced here.
- [shared.sdk-go.request-handling:bulk-delete-truncation-scope] Tier B: Absence: `git -C vendor/zscaler-sdk-go grep -n 'ids\[:\|IDs\[:' v3.8.44 -- zscaler` returns only the three lines quoted above; slicing under other variable names was not searched. Direct SDK callers (scripts, other tools) are the exposed population.
- [shared.sdk-go.request-handling:retry-paths-replace-body-without-closing] Tier B: Absence of a `Close` in those branches: `git show v3.8.44:zscaler/oneapiconfig.go | grep -n 'Body.Close\|NopCloser\|tryDrainBody'` shows one `Body.Close` (inside the retryablehttp `ErrorHandler` in `getHTTPClient`) and one `tryDrainBody` (on the success path). No leak was measured; Go's HTTP/1 transport can reuse a connection once the body is read to EOF, so the practical effect is unproven. Retry behavior itself is in shared.sdk-go.retries.
