# The Go SDK's response cache and request deduplication (shared.sdk-go.cache)
Also called: sdk cache; stale read after write; terraform sees old rule order; in-flight request deduplication; WithCache

The SDK can cache GET responses and collapse identical GETs into one request. Providers that turn this on inherit its behavior on every read. The ZIA Terraform provider sets `zscaler.WithCache(true)`, a 10-minute cache lifetime and an 8-minute value it labels the idle timeout on the SDK configuration it builds for its OneAPI client. In the SDK, the first of those two durations is the entry lifetime and the second is the cleanup interval passed to `NewCache`. [shared.sdk-go.cache:zia-provider-enables-cache] An entry older than the cache lifetime can still be served until the next cleanup pass, which in the ZIA provider's settings runs on the 8-minute interval. [shared.sdk-go.cache:expired-entry-survives-cleanup]

**Deduplication.** With the cache enabled, when a non-sandbox GET for the same URL is already in flight, later GETs for that URL wait for it on a plain wait group, so a cancelled or timed-out caller stays blocked until the first request finishes. [shared.sdk-go.cache:waiters-ignore-cancellation] If the first in-flight GET fails, waiting callers do not receive its error: the error and response fields they check are never set, so each waiter sends the request again. [shared.sdk-go.cache:owner-error-not-shared] Claiming a URL as in flight is a separate check and store rather than one atomic step, so two GETs that miss the cache at the same moment can both send the request. [shared.sdk-go.cache:two-owners-possible]

**Invalidation on writes.** Up to v3.8.57, a write clears the cached entries for its URL and parent collection before it is sent, and caching a GET response is unconditional, so a GET that started before the write took effect can store the pre-write response after the invalidation, and that response is then served until it expires. From v3.8.58 the SDK registers each write and each GET, and a GET that overlaps a write affecting its key is not cached, unless the write starts between the overlap check and the store (gap cache-done-then-set-window). [shared.sdk-go.cache:write-invalidates-but-inflight-get-repopulates] A write also clears the parent collection's cached list. The SDK added this because a stale collection read after a child change broke the ZIA provider's rule reordering (SUP-3988). [shared.sdk-go.cache:parent-collection-invalidation]

**Smaller defects.** Invalidation matches cache keys by raw string prefix, and a write's parent key is its URL cut at the last `/`, so a create on a top-level collection such as `/zia/api/v1/firewallFilteringRules` clears every cached read under `/zia/api/v1`. Up to v3.8.57 the match only deletes entries; from v3.8.58 the same prefixes are also registered with the write tracker, which matches them by raw string prefix too. [shared.sdk-go.cache:prefix-invalidation-over-broad] When serving from cache, an error reading the cached body is ignored: the caller gets whatever was read, and no error. [shared.sdk-go.cache:cached-body-read-errors-ignored]
