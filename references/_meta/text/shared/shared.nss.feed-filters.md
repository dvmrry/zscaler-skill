# What each NSS log type's feed can filter on, and the rules for matching (shared.nss.feed-filters)
Also called: nss feed filters; nss filter wildcards; web policy action filter; firewall nss filters; dns nss filters; tunnel nss filters; saas security nss filters; sandbox verdict nss filters; dlp nss filters

**Matching rules.** The TCP web feed article says admins can configure multiple filter types and gives one example: if an admin selects the location HQ and the department Finance, the NSS selects logs that belong to both the HQ location and Finance department. It adds that a large number of filters or complex filters, such as string searches, can impact NSS performance. [shared.nss.feed-filters:filters-and] The web feed's Referer URLs filter accepts wildcards; the quoted rule is that *string is suffix matching, matching URLs ending with 'string'. Multiple strings are allowed, one per line, and string search is not case-sensitive. [shared.nss.feed-filters:wildcards] The URL Classes filter has an Include option, enabled by default with the default value Any, and an Exclude option whose default value is None. [shared.nss.feed-filters:include-exclude-defaults] The URL Categories filter falls under the same filter class as the Advanced Threats filter: if at least one advanced threat is selected, the specific URL categories to include must also be selected, and when at least one URL category is selected, the default Any option in the Advanced Threats filter does not apply. [shared.nss.feed-filters:category-threat-coupling] The general rule for combining filter fields and values is open [gap:shared.nss.feed-filters:value-logic].

**Entering values.** In the web feed's Users filter, Select All selects all results, deleted users appear with a strikethrough line, and Hide Deleted hides them from the list. [shared.nss.feed-filters:users-select-all] The Client IP Addresses filter accepts a range of IP addresses (for example 192.0.2.1-192.0.2.10), and for item lists up to 500 items can be viewed on a page. [shared.nss.feed-filters:ip-entry-forms]

**Web.** In the web feed's policy action filter, transactions for which the service displayed a Caution page are considered blocked, and if users proceed they are considered allowed. Policy Reason values are the policy reason strings that are in transaction drilldown. [shared.nss.feed-filters:web-policy-action] The internal IP address is available if traffic is forwarded to the service through a GRE or VPN tunnel or from the XFF header; if the internal IP address is not available, the value is the same as the client IP address. [shared.nss.feed-filters:public-ip-meaning] The web feed's supported protocols are HTTP, HTTPS, and FTP. Request size filters use bytes by default, and KB, MB, GB or TB can be specified, for example 10KB-1MB or 200. [shared.nss.feed-filters:web-transaction-filters] The Suspicious Content filter limits logs by the Page Risk Index score of a transaction, a single value or a range between 0 and 100. Encrypted File in the unscannable options means encrypted or password-protected files, and the Miscellaneous <Cloud Application Category> Apps option represents all the newly added lesser-known predefined applications for a category. [shared.nss.feed-filters:web-security-filters] The Cloud NSS web feed has an AI/ML Detection Source filter that limits logs by the AI/ML detection source for the transaction, and the HTTP web feed article's URL Classes filter says to select the classes to include, with multiple selections allowed. [shared.nss.feed-filters:cloud-aiml-http-url-classes] Whether the HTTP web feed lacks the AI/ML filter and the URL Include and Exclude options is open [gap:shared.nss.feed-filters:http-web-filter-absences].

**Firewall.** Firewall feed filters include Block/ICMP, packets dropped because they matched a Firewall rule and sent the client an ICMP error of Type 3 and code 9 or 10; Block/Reset, which for TCP traffic drops the matching packets and sends the client a TCP reset and for non-TCP traffic is the same as Block/Drop; IPS Reset, packets reset due to IPS policy; the DNAT Policy Action, for traffic on which the service performed destination NAT; and Client Destination Names, a destination FQDN filter for Advanced Firewall. [shared.nss.feed-filters:firewall-actions] For aggregated sessions, the client destination IP address filter value is that of the last session in the aggregate, and the Countries filter is the country code that corresponds to the server IP address. [shared.nss.feed-filters:firewall-aggregate-addresses] The Firewall Log Type choice is in [What a ZIA firewall log record is: aggregates, action and field names](kb:zia.logs.firewall-records).

**HTTP and Cloud Firewall feeds.** The HTTP Firewall and Cloud Firewall feed articles list the Firewall & IPS Policy Actions filter, which limits logs by the action the service took under the Firewall Filtering and IPS policies and accepts multiple actions: Allow, Block/Drop, IPS Drop, Block/ICMP, Block/Reset and IPS Reset. Separate filters select Firewall Filtering Rule Name and IPS Rule Name, and DNAT Destination Names limits logs to traffic redirected to specific FQDNs after destination NAT. [shared.nss.feed-filters:firewall-policy-actions-all] On the HTTP Firewall and Cloud Firewall feed articles, the bytes filters say that for aggregated sessions the value is the total bytes sent from, or received by, the server across all sessions in the aggregate; the Durations filter, in seconds, says that for aggregated sessions it indicates the average session duration; the client source and destination port and server source and destination port filters and the server's tunnel IP address say the value is that of the last session in the aggregate; and Number of Sessions filters aggregated logs by session count. [shared.nss.feed-filters:firewall-aggregate-filters] The Durations filter's average against the Insights sum, and the byte filters, are a further position on [zia.logs.firewall-records:aggregate-counters-source](kb:zia.logs.firewall-records:aggregate-counters-source). Whether the Durations filter compares seconds against the millisecond duration fields is open [gap:shared.nss.feed-filters:duration-filter-field]. The HTTP Firewall and Cloud Firewall feed articles list Server IP Classes, Server IP Super Categories and Server IP Categories (the URL class, super category or category that corresponds to the server IP address) and Traffic Forwarding (the forwarding method used to send traffic to the Zscaler Firewall; one or more methods or Any). Network Applications Include is enabled by default with default value Any and Exclude has default None. Threat Names takes *string (suffix), String* (prefix), *string* (substring) or an exact string, several allowed one per line, not case-sensitive. [shared.nss.feed-filters:firewall-classification-filters] The HTTP Firewall and Cloud Firewall feed articles say of the Client Public IP Addresses filter that the internal IP address is available if traffic is forwarded to the service through a GRE tunnel or from the XFF header, and that otherwise the value is the same as the client IP address. The TCP web feed article words the same sentence with "a GRE or VPN tunnel". [shared.nss.feed-filters:firewall-public-ip] Whether VPN tunnel traffic also makes the internal IP available is open [gap:shared.nss.feed-filters:firewall-public-ip-vpn].

**DNS.** DNS feed filters include Redirect, limiting logs to transactions in which the service redirected the DNS request or response, and Response Redirect, limiting logs to DNS responses the service redirected. Rule Names filter on specific rules in the DNS Control policy. The DNS Responses filter limits logs to sessions that contained specific data in the DNS responses, and domain names, IPv4 and IPv6 addresses can be specified there. [shared.nss.feed-filters:dns-actions] The Cloud DNS feed's Policy Actions filter has nine values: Allow, Block, Redirect, Request Allow, Request Block, Request Redirect, Response Allow, Response Block and Response Redirect, the request and response variants limiting logs to DNS requests only or DNS responses only; Rule Name limits logs to specific rules in the DNS Control policy. [shared.nss.feed-filters:dns-policy-actions-all] The Cloud DNS feed also filters IP Domain Classes, IP Domain Super Categories and IP Domain Categories by the URL class, super category or category with the domain in the request, plus Domains, DNS Request Types, DNS Response Codes, Server Ports (individual ports and a range of ports) and Durations, the session duration in seconds. [shared.nss.feed-filters:dns-session-filters] How the nine Cloud DNS filter values map to the action fields is open [gap:shared.nss.feed-filters:dns-filter-values-vs-fields].

**Tunnel.** A tunnel feed can send multiple tunnel log record types in a single feed: IKE Phase 1 (details for IPSec Phase 1 negotiation, IPSec only), Sample (statistics collected in 60-second sample windows, GRE and IPSec) and Tunnel Event (status change events, GRE and IPSec). [shared.nss.feed-filters:tunnel-records] The tunnel feed's Tunnel Type values include EAS Client Tunnel, the tunnel type for the extranet broker connection, and Z-Tunnel 2.0, which uses DTLS, TLS, or UDP, of which only Zscaler Cloud & Branch Connector supports UDP. There is no limit to the number of VPN credentials that can be selected. [shared.nss.feed-filters:tunnel-types]

**SaaS Security.** A SaaS Security feed's Application Category limits the data to a specific category. The listed applications include Microsoft Dynamics 365, Citrix ShareFile, Smartsheet, ChatGPT, Jira Software and Bitbucket. [shared.nss.feed-filters:saas-app-categories] By default the SaaS Security DLP and Malware policy types are not selected, so all incidents and violations, with or without a rule name, are exported through the NSS; DLP and Malware must be explicitly selected to export only incidents with valid rule names. [shared.nss.feed-filters:saas-policy-type-default] In the SaaS Security feed, Incident means a violation was detected in the scan and a configured DLP or malware rule was also triggered, and Violation means a violation was detected in the scan, either a DLP engine was matched or malware was detected. A feed configured with the earlier version of the filter remains supported until it is edited. [shared.nss.feed-filters:saas-event] The SaaS Security Scan Time filter, the time the Data at Rest Scanning policy took to scan content within the tenant, takes a specific value or a range with a dash; the default unit is milliseconds and MS or SEC can be specified, for example 10MS-100MS. [shared.nss.feed-filters:saas-time-units] The SaaS Security feed article says there is no limit to the number of users or departments that can be selected. [shared.nss.feed-filters:saas-unlimited-users] The users cap on the limits page differs [divergence:shared.nss.feed-filters:user-cap]. A SaaS Security Activity feed tracks activities, such as Create, Delete and Share, that users performed in the organization's sanctioned SaaS applications. If applicable the activity can have a second object listed, and the default option is None. [shared.nss.feed-filters:saas-activity] The HTTP SaaS Security Activity feed article lists User (search by username or email address, no limit to the number of users, deleted users shown with a strike through line), Tenant and Activity (several of each allowed), and Object 1 Type and Object 2 Type filters, each with the default option None. The Cloud article gives one combined Object 1 Type and Object 2 Type filter and also says there is no limit to the users. [shared.nss.feed-filters:saas-activity-filters] The HTTP SaaS Security article lists the Event filter values Any (any type of event in the scan), Incident, Scan (no violation was detected; the scan is considered normal) and Violation. A previous version of the Event filter, available for Internet & SaaS (ZIA) 6.2 and earlier, does not include Violation; a feed configured with it remains supported until it is edited or changed, when the filter is replaced by the latest version, and newly configured feeds support the latest version by default. [shared.nss.feed-filters:saas-event-version] Beyond the filters already claimed from the TCP article, the HTTP SaaS Security feed article lists External Recipients (outside the organization) and Internal Recipients (within it) under Collaboration, and Channel Name, Bucket Name, Project Name, Repository Name and Message Size (the size of the email message) filters. DLP filters cover DLP Engines, DLP Dictionaries and the Severity of incidents detected by the Data at Rest Scanning DLP policy; Malware filters cover Malware Classes, Malware Names and Threat Name; Application filters cover the sanctioned SaaS Application and the SaaS Application Tenant. [shared.nss.feed-filters:saas-category-filters] The HTTP SaaS Security Download Time filter limits logs by the file download time; the default unit of measure is milliseconds, and MS or SEC can be specified, for example 10MS-100MS. [shared.nss.feed-filters:saas-download-time] The HTTP SaaS Security article says that when a non-provisioned file owner within the organization is later provisioned to the Internet & SaaS, logs associated with that file owner can be filtered under the User field. [shared.nss.feed-filters:saas-nonprovisioned-owner] The HTTP SaaS Security article describes Internal Recipients twice, with different meanings [gap:shared.nss.feed-filters:saas-internal-recipients-defect]. The application lists differ between the TCP and the HTTP and Cloud articles [gap:shared.nss.feed-filters:saas-app-lists-differ], and whether the Users and Departments no-limit statement holds on the HTTP and Cloud SaaS Security feeds is open [gap:shared.nss.feed-filters:saas-users-departments-http-cloud].

**Data loss prevention.** The Endpoint DLP Record Type filter distinguishes DLP incidents, user activities in which DLP policy rules were violated, from sensitive activities, in which movement of sensitive data was detected based on the file content. [shared.nss.feed-filters:endpoint-dlp-record-type] The Email DLP Record Type includes Scan, meaning the scan is normal with no DLP rule violation or movement of sensitive data detected. The Policy Action option Custom Header Insertion limits logs to transactions that resulted in a different action, such as quarantine, taken by the email application as defined by a custom header such as X-Zscaler-Scan:Quarantine, and the Severity filter limits logs to transactions associated with a specific DLP rule severity as configured in the Outbound Email Policy. [shared.nss.feed-filters:email-dlp-filters]

**Sandbox.** The Sandbox Verdict Download File Type filter includes file types that are not eligible for Sandbox analysis, for which no log data is available. SHA limits logs by the SHA-256 hash of a file, and the verdicts filter covers Sandbox, Advanced Threat Protection and Malware Protection verdicts, optionally Benign for non-malicious verdicts. If no techniques are specified, verdicts associated with any possible MITRE ATT&CK technique are displayed. [shared.nss.feed-filters:sandbox-filters]

**Cloud App Governance and Posture.** Whether the Cloud 3rd-Party App Governance and Posture Management feeds can be filtered at all is open [gap:shared.nss.feed-filters:app-governance-posture-filters].

**MCAS.** The TCP, HTTP and Cloud web feed articles each list a Users filter under Who, which limits the logs to specific users who generated transactions. [shared.nss.feed-filters:web-who-users] The MCAS feed's Who group lists Locations where those articles list Users, which does not settle whether MCAS filters by user [gap:shared.nss.feed-filters:mcas-who-group].

Sources disagree (name both sides):
- The limits page caps users per NSS feed filter at 1,024, while the TCP SaaS Security article and the HTTP and Cloud SaaS Security Activity articles say there is no limit. [divergence:shared.nss.feed-filters:user-cap]
  - zscaler-help: The limits page lists 1,024 users per NSS feed filter (shared.nss.feeds:filter-caps).
  - zscaler-help: The SaaS Security feed article says there is no limit to the users that can be selected.
  - zscaler-help: The HTTP SaaS Security Activity feed article says there is no limit to the users that can be selected.
  - zscaler-help: The Cloud SaaS Security Activity feed article says there is no limit to the users that can be selected.
  Impact: Whether a SaaS Security feed filter is exempt from the 1,024 cap cannot be settled from the vendor text.
