# Advanced NSS VM settings: extra interfaces, local NTP, explicit proxy, hostname and SSH (shared.nss.vm-advanced-settings)
Also called: nss explicit proxy; dnsoverproxy; nss no default route; nss split interface; nss second management interface; nss second service interface; nss ntp; nss ssh key authentication

**Extra interfaces.** When the default management interface cannot be used for SSH due to VLAN restrictions, Zscaler recommends adding an additional interface just for management, so the first interface is used only for control connections to the cloud. The manual method lists em2 in network_interfaces="em0 em1 em2 lo0" and the default gateway is automatically added via the em0 interface. [shared.nss.vm-advanced-settings:second-management-interface] Some organizations might need one interface to connect to the Zscaler cloud and another to connect to the SIEM. The example sets smnet_dev=em2=zs1:192.168.223.41/24, and if the SIEM is in a different subnet an smnet_route line is added; if it is in the same subnet the second line is not required. [shared.nss.vm-advanced-settings:second-service-interface] To configure both a second management interface and service interface, the vSphere guide says first to run the command that establishes the network settings, and during a split-interface configuration the NSS asks for an smnet_route. [shared.nss.vm-advanced-settings:split-interface] Which platforms offer these is disputed in the vendor docs: [Deploying the NSS VM on AWS, GCP, Azure, Hyper-V, Nutanix and vSphere](kb:shared.nss.vm-platforms).

**Time.** A local NTP server is used through a crontab entry `*/10 * * * * ntpdate -u <ntp-server-name>`; the time synchronization command runs every 10 minutes and the logs for the NTP process are in /var/log/cron. [shared.nss.vm-advanced-settings:local-ntp]

**Explicit proxy.** Some customers have a no-default-route environment, which prevents the NSS from establishing connections to the Zscaler cloud. The article lists the Nanolog (SMSM), the Zscaler Central Authority (SMCA), the update server (SMCDSS) for software updates and the Kafka server for audit log streaming as connections, and says connections from the NSS to the SIEM and NTP connections are not tunneled. [shared.nss.vm-advanced-settings:explicit-proxy] With the dnsoverproxy flag set to 1, the NSS in explicit proxy mode makes a CONNECT request to msmca.<cloudname> for the Zscaler CA, zdistribute.<cloudname> for the update server and kproxy.hdeu1.zdataservices.net for the Kafka server, and the explicit proxy performs the name resolution. With the flag set to 0, the NSS needs DNS resolution for the connections to the current master CA IP address, update server and Kafka server. `nss configure proxy remove` is the quoted command for removing the configuration. [shared.nss.vm-advanced-settings:dnsoverproxy]

**Host and SSH.** The VM hostname is set with a hostname=<name> entry. [shared.nss.vm-advanced-settings:hostname] SSH can be limited to a source range with an entry such as AllowUsers zsroot@10.66.70.*. For key-based authentication the user public key file is uploaded to authorized_keys under /home/zsroot/.ssh and ChallengeResponseAuthentication and PasswordAuthentication are set to no, which the article says are set to yes by default. [shared.nss.vm-advanced-settings:ssh-hardening]
