# Setting up Okta, Microsoft Entra ID and PingFederate as the ZIA OAuth 2.0 authorization server (shared.legacy-api.zia-oauth-idp-setup)
Also called: zia oauth okta configuration; zia oauth entra id configuration; zia oauth pingfederate configuration; okta custom authorization server zia scope; entra app role zia api

Each identity provider is set up differently for the ZIA cloud service API; the ZIA side of the flow (scope, validation, authorization servers) is in [ZIA legacy OAuth 2.0 through an external identity provider](kb:shared.legacy-api.zia-oauth). The scope name each guide uses is the one in [After the API role is created, it is defined as a Scope on the authorization server in the <Zscaler Cloud Name>::<Org ID>::<API Role> format, where the Org ID is the Company ID from the company profile under Administration > Administration > Organization > General Information.](kb:shared.admin-rbac.zia-api-roles:scope-on-server).

**Okta.** In Okta the API client is registered as an app integration with API Services as the sign-in method, and the Require Demonstrating Proof of Possession (DPoP) header in token requests option must be disabled for the Proof of possession field. [shared.legacy-api.zia-oauth-idp-setup:okta-app] Okta needs a custom authorization server, and the Client Credentials flow needs custom scopes whose name takes the Zscaler format <Zscaler Cloud Name>::<Org ID>::<API Role>, for example zscalerbeta.net::272378::sampleRole. Zscaler recommends not selecting Set as a default scope when several clients access the API with different scopes. [shared.legacy-api.zia-oauth-idp-setup:okta-scopes] In Okta, the rules within an access policy assign an expiration time to an access token based on the grant type, scope and other parameters in the request; the first policy and rule that match the client's request apply, and a client that matches no policy fails to authenticate. [shared.legacy-api.zia-oauth-idp-setup:okta-access-policies]

**Microsoft Entra ID.** In Microsoft Entra ID the client and the resource server (the Internet & SaaS API) are separate application registrations, and the steps are completed for each API Role configured in the Admin Console; the client app's supported account types are set to single tenant. [shared.legacy-api.zia-oauth-idp-setup:entra-two-registrations] The Entra client secret value is displayed only once and cannot be retrieved after navigating away from the page. [shared.legacy-api.zia-oauth-idp-setup:entra-secret-once] On the Entra API application an app role is defined with Allowed member types set to Applications and a Value in the <Zscaler Cloud Name>::<Org ID>::<API Role> format; the client application is given Application permissions as the type of permission. [shared.legacy-api.zia-oauth-idp-setup:entra-app-role] The Entra guide gives the typical token endpoint (v2) format as https://login.microsoftonline.com/<Application ID>/oauth2/v2.0/token and the typical jwks_uri format as https://login.microsoftonline.com/<Application ID>/discovery/v2.0/keys; the JWKS endpoint value obtained through the jwks_uri parameter is entered as the OAuth 2.0 JWKS Location in ZIA. [shared.legacy-api.zia-oauth-idp-setup:entra-endpoints] The Entra guide's token request is a POST to the v2 token endpoint with a JSON payload in the request body holding grant_type client_credentials, client_id, client_secret and a scope of the Application ID URI appended with /.default; the access token can be presented in the Authorization header with the bearer scheme. [shared.legacy-api.zia-oauth-idp-setup:entra-token-request]

**PingFederate.** PingFederate needs a certificate for access token management configured in its admin console; its access token manager instance is of type JSON Web Tokens, signs with RSA using SHA-256, and uses scp as the Scope Claim Name. [shared.legacy-api.zia-oauth-idp-setup:ping-token-manager] For PingFederate, the ZIA API role name must match the name entered in the PingFederate admin console, the guide's example of the URL with the endpoint appended is https://zpf.zpingfed.com/.well-known/oauth-authorization-server, and the guide has the admin enable JWKS Certificate Authentication. [shared.legacy-api.zia-oauth-idp-setup:ping-zia-side]

**The token request.** The Okta and PingFederate guides each say the token request must carry the client ID and secret in the Authorization header using HTTP basic authentication, with at least one custom scope as scope, and that the client ID and secret cannot be in the request body. [shared.legacy-api.zia-oauth-idp-setup:okta-ping-token-request] Where the client credentials go differs between the guides and the getting-started page [divergence:shared.legacy-api.zia-oauth-idp-setup:credentials-location]; the existing claim is [The client POSTs to its identity provider's token endpoint with `grant_type` client_credentials and the scope, presenting its client ID and secret by HTTP Basic authentication or in the body; a failed request returns 400.](kb:shared.legacy-api.zia-oauth:token-request).

**Open questions.** Which claim carries the Entra app role value is open [gap:shared.legacy-api.zia-oauth-idp-setup:entra-role-claim]. The example responses in the Okta and PingFederate guides are unexplained [gap:shared.legacy-api.zia-oauth-idp-setup:example-responses].

What to check:
1. For a token request that fails at the identity provider, where the client credentials are sent (Authorization header or body) and which guide the identity provider follows; the guides disagree.
2. For Okta, whether the app integration is API Services with DPoP disabled and the scope is a custom scope in the Zscaler format on a custom authorization server.
3. For Entra ID, whether the resource server and client are separate registrations and the client app holds the app role as an Application permission.

Sources disagree (name both sides):
- Whether the client ID and secret may go in the token request body: the Okta and PingFederate guides say they must be in the Authorization header and cannot be in the body, while the Entra guide's request carries them in the body and the getting-started page offers the body as an alternative to HTTP Basic authentication. The existing claim is [[shared.legacy-api.zia-oauth:token-request]]. [divergence:shared.legacy-api.zia-oauth-idp-setup:credentials-location]
  - zscaler-help: Okta guide: the client ID and secret go in the HTTP Authorization header only.
  - zscaler-help: PingFederate guide: the client ID and secret go in the HTTP Authorization header only.
  - zscaler-help: Entra guide: client_id and client_secret are sent in the JSON request body.
  - zscaler-help: Getting-started page: the body is an alternative to HTTP Basic authentication.
  Impact: Which placement ZIA accepts is not settled; the Okta and PingFederate guides may describe those providers' own requirement, which the pages do not say.

Not known (open gaps):

- The example token responses in the Okta and PingFederate guides [gap:shared.legacy-api.zia-oauth-idp-setup:example-responses]: settled by source-read
