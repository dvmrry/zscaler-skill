# How the Python SDK builds a request: body and query key casing, ID lists (shared.sdk-python.request-handling)
Also called: python sdk camelcase; convert_keys_to_camel_case; FIELD_EXCEPTIONS; to_lower_camel_case; _prepare_body; python sdk snake_case body; transform_common_id_fields

The Python SDK takes snake_case arguments and rewrites key names before a request goes out; which keys it rewrites depends on the service and the client.

**Request bodies.** For a dictionary request body, the request executor camel-cases the keys with `convert_keys_to_camel_case`, except on the ZDX and ZTB legacy clients and on endpoints containing `/zdx/`, `/easm/` or `/ztb/`, whose bodies it sends as given. For `/zcc/` it converts selectively, leaving `WebPolicy.SNAKE_CASE_KEYS` as they are, and a body the ZCC serializer already produced (`_ZccWireBody`) is sent unchanged. [shared.sdk-python.request-handling:body-camel-case] The camel-casing helper returns a key from its exceptions table as mapped and leaves a key without an underscore unchanged; otherwise it splits on underscores, lowercases the first part, capitalizes every later part and joins them. [shared.sdk-python.request-handling:camel-rule] Product-specific consequences: ZIA's exceptions in [In the executor's `_prepare_body`, a dictionary request body for an endpoint that is not a ZDX, ZEASM, ZTB or ZCC one takes the generic path: its keys are camel-cased, except that keys inside `featurePermissions` are left as they are. The conversion maps keys listed in an exceptions table and otherwise lower-cases the first segment of a snake_case key and capitalizes each later segment; a key with no underscore is returned unchanged.](kb:zia.sdk-python.request-conventions:camel-case-body), ZCC's in [On the OneAPI client, the Python SDK camel-cases ZCC request body keys except those in `WebPolicy.SNAKE_CASE_KEYS`, and sends a body already serialized by the ZCC model serializer unchanged. On the legacy client a ZCC body goes through the general `convert_keys_to_camel_case`, which converts all keys recursively; a key the converter maps to itself, such as `exit_password`, keeps its form.](kb:zcc.api.conventions:python-body-casing), ZTB's in [The request executor does not camel-case ZTB request bodies: `_prepare_body` returns the body unconverted when the ZTB legacy client is in use and when the endpoint contains `/ztb/`.](kb:zero-trust-branch.api:snake-case-bodies).

**Query parameters.** For every service other than ZPA, the request executor camel-cases query parameter names with `convert_keys_to_camel_case` and removes `microtenantId`; on the ZDX legacy client it leaves the parameters as given. [shared.sdk-python.request-handling:query-params-camel-case] ZPA's own page-size and search handling is in [Paging through ZPA lists with the Python SDK](kb:zpa.sdk-python.pagination).

**ID lists.** `transform_common_id_fields` pops each snake_case key from the source dict and stores a list of `{"id": ...}` objects under the wire key; items that are already dicts with an id are kept. [shared.sdk-python.request-handling:id-list-helper] Which keys ZIA reshapes this way is in [`transform_common_id_fields` pops each listed snake_case key from the request body and rewrites its list of IDs as a list of `{"id": ...}` objects under the wire key, by default coercing numeric strings to integers. The shared list `reformat_params` names keys such as `users`, `groups` and `labels`.](kb:zia.sdk-python.request-conventions:id-list-reshape).

What to check:
1. Whether the product's endpoint is one whose body the executor leaves in snake_case (ZDX, EASM, ZTB) or converts selectively (ZCC) before predicting a wire key.
