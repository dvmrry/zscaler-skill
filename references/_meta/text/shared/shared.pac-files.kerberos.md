# The Kerberos PAC file: host-name variables, port 8800 and required bypasses (shared.pac-files.kerberos)
Also called: kerberos pac; kerberos.pac; port 8800; kdc proxy bypass; kerberos realm bypass; kerberos pac with ipsec tunnel

Kerberos authentication changes what the PAC file must contain and when a PAC file is needed at all. The Kerberos method itself, with its DNS and firewall requirements, is [SAML and Kerberos: what each needs to work](kb:zia.authentication.methods).

**PAC files even behind tunnels.** All users who authenticate with Kerberos must configure their browsers to forward through PAC files, even when their location has an IPSec or VPN tunnel to the service. [shared.pac-files.kerberos:browsers-need-pac] Zscaler provides a default Kerberos PAC file and strongly recommends using it, or a copy of it with the needed arguments and exceptions added. [shared.pac-files.kerberos:use-kerberos-pac]

**What the Kerberos file does.** Kerberos requires the Public Service Edges to be addressed by FQDN, so the Kerberos PAC file uses ${GATEWAY_HOST} and ${SECONDARY_GATEWAY_HOST}, which the service replaces with the domain names of the primary and secondary Public Service Edges. [shared.pac-files.kerberos:fqdn-variables] The Kerberos PAC file forwards web traffic to port 8800, and Public Service Edges challenge all traffic received on port 8800 for a Negotiate (Kerberos) ticket for the service. [shared.pac-files.kerberos:port-8800] The host-name variables in general are [The ${GATEWAY_HOST} variable resolves to a host name instead of an IP address, and the page's example returns ${GATEWAY_HOST} with ${SECONDARY_GATEWAY_HOST} as the fallback proxy. It is a recommended configuration for Kerberos authentication and for IPv6: Zscaler recommends the host-name variable to forward IPv6 traffic, with IPv6 support enabled for the organization and its locations and Enable IPv6 Resolution for Zscaler Domain enabled.](kb:shared.pac-files.variables:gateway-host); the subcloud forms are [A PAC file for a subcloud must not use ${GATEWAY} or gateway.<Zscaler cloud> in its return statement, or traffic goes to the nearest Public Service Edge, which may be outside the subcloud; it uses ${GATEWAY.<Subcloud>.<Zscaler cloud>} and ${SECONDARY.GATEWAY.<Subcloud>.<Zscaler cloud>}, with _HOST forms for Kerberos and plain host names for applications that do not support PAC files.](kb:shared.pac-files.variables:subcloud-vars).

**Required bypasses.** Where a KDC proxy (with Microsoft DirectAccess) is deployed for remote user access, its traffic is also sent to the Public Service Edge and authentication fails, so a new PAC file must bypass the KDC proxy host with a DIRECT return. [shared.pac-files.kerberos:kdc-proxy-bypass] Traffic destined within the realm must not be forwarded to the service, so the Public Service Edge challenges no realm traffic; a new PAC file must bypass the organization's realm. [shared.pac-files.kerberos:realm-bypass]

**Kerberos-enabled locations.** At a location with Kerberos enabled, traffic can be forwarded to the proxy ports 80, 443, 9400 and 9443 or to the location's dedicated port, and the service challenges all explicitly forwarded proxy traffic from that location for a Kerberos ticket. [shared.pac-files.kerberos:location-ports]

What to check:
1. Whether Kerberos users' browsers have a PAC file configured, including at locations with an IPSec or VPN tunnel.
2. Whether the file returns the host-name variables on port 8800 and bypasses the realm and any KDC proxy before that return.
