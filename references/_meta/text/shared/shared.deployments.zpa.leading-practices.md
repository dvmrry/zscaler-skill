# What the ZPA Leading Practices Guide recommends for connector sizing, segmentation rollout, application segments and Private Service Edges (shared.deployments.zpa.leading-practices)
Also called: zpa leading practices; zpa best practices

**App Connectors.** App Connector groups should be scaled for N+1 redundancy and a single App Connector can handle up to 500 Mbps total inbound and outbound; 1 Gbps needs at least three connectors. [shared.deployments.zpa.leading-practices:connector-capacity] Connectors in a connector group must share the same geographic location (latitude and longitude); all connectors at a site belong in one group, and a group per logical application domain (a single AWS VPC, data center, or isolated segment) is recommended. Not using location-based groups adversely impacts location-sensitive apps such as AD domain controllers for DFS. [shared.deployments.zpa.leading-practices:connector-grouping] Connectors must have ICMP access to servers, which is mandatory for optimal path selection for UDP-based apps and recommended for TCP-based apps; Zscaler does not recommend forwarding the App Connector's outbound traffic via a ZIA Public or Private Service Edge. [shared.deployments.zpa.leading-practices:connector-network] Connectors are automatically updated frequently; customers should select off-hour slots, and the ZPA cloud upgrades members of an App Connector group sequentially. [shared.deployments.zpa.leading-practices:connector-upgrades] See [ZPA App Connectors](kb:zpa.app-connectors) and [Monitoring App Connector performance: CPU, memory, throughput, source ports, application targets, disk and file descriptors](kb:zpa.app-connectors.performance).

**Segmentation rollout.** Two segmentation rollouts: Day 0 Trust (define every known FQDN/IP, app segment and group policy before rollout; risks blocking missed applications) and Discovery-Based Zero Trust (allow all authenticated users access to a pattern-based segment and refine from discovery); Zscaler says most organizations find the second a better fit. [shared.deployments.zpa.leading-practices:segmentation-approaches] Before discovery-based segmentation Zscaler recommends App Connectors for the majority of applications, Client Connector on most managed endpoints and over half of users actively using ZPA; the initial deployment within the first 60 days should include 60% of entitled users. [shared.deployments.zpa.leading-practices:discovery-prerequisites] Administrators should define an application discovery deadline (the example uses 60 or 90 days or a percentage of users deployed per user group); after it discovery is turned off, wildcards are removed, and least-privilege access is enforced; the example schedule removes the wildcard rule at Day 60. [shared.deployments.zpa.leading-practices:discovery-deadline] See [How application discovery works and how a discovered application is defined](kb:zpa.app-segments.discovery).

**Policy and segments.** ZPA evaluates policy rules using the most specific application segment and a top-down, first-match principle, so rule order matters. [shared.deployments.zpa.leading-practices:rule-order-evaluation] For business-critical applications the guide recommends early posture checks, Client Forwarding rules so access goes through ZPA even on the local corporate network, and changing the Authentication Timeout (for example to one hour or one day); the guide also notes the default Timeout Policy rule has all users authenticate every 7 days for any application. [shared.deployments.zpa.leading-practices:critical-apps] Avoid TCP port 53 in app segments (Diagnostics filter Application: Server Port = 53); app segments with a health check of None are reachable by any App Connector servicing an associated server group; Continuous can create high loads while continuously monitoring infrequently, and there is a limit of 6k targets (IP address and port) per Connector Group; app segments with large IP ranges such as 10.0.0.0/8 are strongly discouraged, with wildcard domains such as *.internal.corp.com preferred. [shared.deployments.zpa.leading-practices:segment-hygiene] The 6k target limit is stated per Connector Group here and per App Connector elsewhere: [divergence:shared.deployments.zpa.leading-practices:target-limit-scope]. For unmanaged laptops and contractor/vendor/third-party users Zscaler recommends browser-based access to a limited number of applications, possibly with Multiple IdP support, and Isolation access for critical apps accessed by unmanaged devices. [shared.deployments.zpa.leading-practices:unmanaged-devices]

**Private Service Edges and log streaming.** A Private Service Edge can facilitate local users, remote users reaching regional internal applications, and business continuity; Trusted Networks criteria on the Private Service Edge group redirect trusted-network users to it, and an FQDN resolving to the public IP externally and the private IP internally is used when it serves both user types. [shared.deployments.zpa.leading-practices:private-service-edge-use] Use dedicated connector groups for log streaming, separate from user traffic groups (ZPA traffic has higher priority than log streaming), and set the Log Receiver Log Stream Policy Session setting to reauthBlock to exclude log entries for authentication timeouts. [shared.deployments.zpa.leading-practices:lss-leading-practice]

Sources disagree (name both sides):
- What the 6,000-target limit applies to: the leading practices guide says per Connector Group, the App Connector performance and application segment articles say per App Connector. [divergence:shared.deployments.zpa.leading-practices:target-limit-scope]
  - zscaler-help: There is a limit of 6k targets (IP address and port) per Connector Group.
  - zscaler-help: An App Connector can only monitor a maximum of 6,000 application targets at any given time.
  Impact: Sizing a Connector Group against 6k targets in total, rather than 6,000 on each connector, changes how many segments fit; the pages do not reconcile the scope.
