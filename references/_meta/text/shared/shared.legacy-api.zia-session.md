# ZIA legacy API sessions: API key obfuscation, JSESSIONID and the cloud service API key (shared.legacy-api.zia-session)
Also called: authenticatedSession; JSESSIONID; obfuscateApiKey; zia api key obfuscation; zia legacy session expired 401; SESSION_NOT_VALID; cloud service api key; zsapi zscaler cloud name api v1; sandbox api token; 3rd-party app governance api key

The legacy ZIA cloud service API authenticates either with OAuth 2.0 through an external identity provider or with an admin login plus an obfuscated API key; this subject covers the second. The ZIA legacy help page lists OAuth 2.0 (recommended) or Basic authentication combined with an API key for the cloud service API, Basic authentication with an API token for the Sandbox Submission API, and an API key for the 3rd-Party App Governance API. [shared.legacy-api.zia-session:auth-methods]

**Base URL.** The legacy cloud service API's host and base path is `zsapi.<Zscaler Cloud Name>/api/v1`, for example zsapi.zscalertwo.net, using the cloud name provisioned for the organization. [shared.legacy-api.zia-session:base-url] In Authentication Service-enabled tenants, admins calling the ZIA APIs this way must be hosted on Authentication Service with roles assigned from ZIA; users provisioned through third-party identity providers cannot authenticate to the APIs. [shared.legacy-api.zia-session:zidentity-tenants]

**Obfuscating the key.** The obfuscation algorithm is published in the vendor's help page, with PHP, PowerShell, Python, Java, JavaScript and shell implementations. It takes the last six digits of the millisecond timestamp, picks key characters at those digits, then right-shifts the six-digit number by one, zero-pads it to six digits and appends the key characters at each digit plus two. [shared.legacy-api.zia-session:obfuscation-published] The Python SDK implements it in `obfuscate_api_key`: it takes the last six digits of the millisecond timestamp, right-shifts them by one into a zero-padded six-digit number, appends the key characters at each digit plus two, and returns the timestamp it used together with the key. [shared.legacy-api.zia-session:python-sdk-obfuscation] The service checks that the `timestamp` sent with POST /authenticatedSession is the one used to obfuscate the key and lies within two hours of Zscaler's measured epoch time; the timestamp is a string holding milliseconds since the Unix epoch. [shared.legacy-api.zia-session:timestamp-checks]

**The session.** POST /authenticatedSession with `username`, `password`, the obfuscated `apiKey` and `timestamp` creates a session and returns a `JSESSIONID` cookie in the Set-Cookie header, which must be passed on subsequent requests. [shared.legacy-api.zia-session:create-session] By default the `JSESSIONID` expires after 5 minutes, or at an explicit logout; a call after expiry returns 401, and the client re-authenticates with a new POST to /authenticatedSession. [shared.legacy-api.zia-session:session-expiry] An unsuccessful POST to /authenticatedSession returns 400, for example with code `INVALID_USERNAME_OR_PASSWORD`. [shared.legacy-api.zia-session:bad-credentials-400] GET /authenticatedSession checks for a session: when one exists the response carries `authType`, and when `authType` is absent the session has expired or does not exist. [shared.legacy-api.zia-session:session-check] DELETE /authenticatedSession ends the session and returns an activation status object. [shared.legacy-api.zia-session:session-end]

**Practices.** The vendor's practices for legacy sessions: always pass the `JSESSIONID` cookie, create a session only when a call returns 401 (`SESSION_NOT_VALID`), use a dedicated user per script rather than one user in several concurrent scripts, use UTF-8, and prevent caching with a random dummy URL argument. [shared.legacy-api.zia-session:session-practices] The page recommends a dedicated admin role and user with restricted functional scope for API access, to avoid conflicts between API and admin portal logins. [shared.legacy-api.zia-session:dedicated-admin]

**Activation.** After changes the client activates with POST /status/activate; the activation request is queued and does not override simultaneous changes by other admins. [shared.legacy-api.zia-session:activation-queued] The service activates saved changes automatically when the admin is inactive for the duration configured in Advanced Settings or logs out with DELETE /authenticatedSession. [shared.legacy-api.zia-session:auto-activation-triggers] The provider documentation describes the same session-end activation ([The ZIA platform activates pending changes on its own when a session ends, either because an API session reached the `api_session_timeout` or because an admin logged out; this applies to all API changes, including Terraform's.](kb:zia.terraform.activation-methods:session-end-autoactivation)) and the 5 to 20 minute API session timeout ([The API session timeout accepts 5 to 20 minutes and defaults to 5.](kb:zia.terraform.activation-methods:session-timeout-range)). The OneAPI side of activation is in [Writing through OneAPI: fetch before update, activation, edit locks](kb:shared.oneapi.write-practices), and the Python client's logout on exit is in [When the Python SDK ends a ZIA session and what that does to staged changes](kb:zia.sdk-python.activation-and-session). Whether accepting the EUSA is a prerequisite for API use is open [gap:shared.legacy-api.zia-session:eusa-prerequisite].

**The cloud service API key.** After the API subscription is enabled, Zscaler provisions the organization's cloud service API key; an organization can have only one, and the existing key must be deleted before a new one is added. Accessing and managing the key needs a valid API subscription, and the base URL and key are required to authenticate via the API and create a session. [shared.legacy-api.zia-session:one-key] The cloud service API can be authenticated with an API key (an alphanumeric key of 12 characters) combined with Internet & SaaS (ZIA) admin credentials (username and password); keys or secrets for Zscaler OneAPI endpoints come from Authentication Service instead. [shared.legacy-api.zia-session:key-plus-admin] The Cloud Service API Key page shows the base URL for the cloud service API and, for the key, the key string, the admin who last modified it and the date and time it was last modified. [shared.legacy-api.zia-session:key-page] An edited API key must be alphanumeric and exactly 12 characters long, and the vendor's Java implementation of the obfuscation fixes the key size at 12. [shared.legacy-api.zia-session:key-format] Editing, regenerating or deleting the key takes effect at once: the old key is invalidated immediately, and none of these actions can be undone. Adding a key also invalidates the old key immediately, and after a key is replaced or edited, references to the old key in the organization's code must be replaced. [shared.legacy-api.zia-session:key-changes-immediate] For multiple organizations that should keep the same key string, Zscaler recommends editing the key instead of adding a new one or regenerating it. [shared.legacy-api.zia-session:multi-org-edit] Zscaler or the service provider can disable the key, for example when the organization exceeds its threshold of API calls or its code violates Zscaler's terms; a disabled key cannot be added, regenerated or deleted, and re-enabling it needs Zscaler Support or the provider. [shared.legacy-api.zia-session:key-disabled] When the API subscription expires the key stays valid but disabled and the POST and PUT actions are lost, until the subscription is renewed. [shared.legacy-api.zia-session:subscription-expiry] Whether sessions opened with the old key survive an edit or regeneration is open [gap:shared.legacy-api.zia-session:key-change-sessions].

**Other ZIA APIs.** The Sandbox Submission API uses API tokens rather than the API key, at the host and base path `csbapi.<Zscaler Cloud Name>/zscsb`; an organization can have up to 5 Sandbox API tokens. [shared.legacy-api.zia-session:sandbox-token] The count of up to 5 stated by the getting-started page is not settled, because the pages disagree on how many tokens an organization can have [divergence:shared.legacy-api.zia-session:sandbox-token-count]. The Sandbox Submission API can be authenticated with a combination of API token and Internet & SaaS (ZIA) admin credentials. Managing the token needs a valid Sandbox subscription; when it is applied, Zscaler provisions and enables the token and displays it on the Sandbox API Token page along with the base URL. [shared.legacy-api.zia-session:sandbox-token-auth] A new Sandbox API token is displayed on the tab, named and saved, and is hidden by default until the View icon is clicked. After regeneration a randomized token string is immediately generated and the old string is invalidated, and the managing page says that action cannot be undone. Deleting needs CONFIRM typed in the Delete API Token window, after which the token is immediately removed and invalidated. [shared.legacy-api.zia-session:sandbox-token-lifecycle] Zscaler or the service provider can disable the Sandbox API token, for example if the organization exceeds the threshold number of API calls or its code violates Zscaler's terms; the ability to add, regenerate or delete the token is then removed, a Disabled status appears, and Zscaler Support or the service provider must be contacted to re-enable it. [shared.legacy-api.zia-session:sandbox-token-disabled] If the Sandbox subscription expires, the Sandbox API Token page is still accessible but no modifications can be made (the POST and PUT actions in the API are lost), and the existing token is still valid but disabled; it is re-enabled after the subscription is renewed. [shared.legacy-api.zia-session:sandbox-subscription-expiry] Sandbox submission limits are in [Advanced Sandbox allows 100 API file submissions per day by default; the quota can be raised through the Zscaler account team or Support.](kb:zia.sandbox.submission:daily-quota). The token's base URL value is open [gap:shared.legacy-api.zia-session:sandbox-base-url]. The 3rd-Party App Governance API uses its own API key, sent as an `X-API-KEY` header to https://api.apptotal.zscaler.com/v1/, and is limited to 25 calls per day on a trial and 1,000 per day with a license. [shared.legacy-api.zia-session:app-governance]

What to check:
1. For a 400 on POST /authenticatedSession, whether the timestamp sent is the one used to obfuscate the key and within two hours of Zscaler's clock, and whether the key used is the current one.
2. For a 401 mid-script, whether the five-minute default session lifetime ran out, and re-authenticate only on that 401.
3. For an Authentication Service-enabled tenant, whether the admin used for legacy API calls is hosted on Authentication Service rather than provisioned through a third-party IdP.

Sources disagree (name both sides):
- How many Sandbox API tokens an organization can have: the getting-started page and the About page say up to 5, the About page also says the existing token must be deleted before adding a new one, and the managing page says both only one token and only 5 tokens. The existing claim is [[shared.legacy-api.zia-session:sandbox-token]]. [divergence:shared.legacy-api.zia-session:sandbox-token-count]
  - zscaler-help: Getting-started page: up to 5 API tokens for the Sandbox Submission API.
  - zscaler-help: About Sandbox API Token: up to 5 tokens, yet adding one needs the existing token deleted first and invalidates the old token.
  - zscaler-help: Managing Sandbox API Token: one token in one sentence and a maximum of 5 in another, in the same article.
  Impact: The number of Sandbox API tokens an organization can hold is not settled by the pages, and neither is whether an add replaces the existing token.
