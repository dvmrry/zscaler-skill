# Which Zscaler products stage changes behind an activation (shared.activation)
Also called: activation gate; rule change not taking effect; do I need to activate; pending changes; cross-product activation; why is my change not taking effect; activation lifecycle

Whether a product stages a saved change until someone activates it decides whether an ignored change is an activation question at all. The OneAPI guide names ZIA and Cloud & Branch Connector, and says a queued activation cannot be cancelled: [For ZIA and Cloud & Branch Connector, configuration changes must be explicitly activated, through /status/activate and /ecAdminActivateStatus/activate respectively. A change cannot be reverted and a queued activation cannot be cancelled; the guide recommends grouping several changes and activating once.](kb:shared.oneapi.write-practices:activation-zia-cbc).

**Everywhere else.** Other products' API specifications have activate operations that act on one object: the ZCC web policy activate enables or disables a policy or app profile for a platform, the ZDX application activate activates one application by its ID, and the ZPA emergency-access activate activates one emergency access user. [shared.activation:object-activate-paths] Outside ZIA and Cloud & Branch Connector the captured API specifications have no call that activates staged configuration for the organization, so a saved change in ZPA, ZCC, ZDX or ZIdentity has no activation step to check. [shared.activation:no-other-gate] When a write in those products takes effect is not documented: [Whether writes to ZDX, ZIdentity and Business Insights are live without activation](kb:shared.oneapi.write-practices:other-products-no-activation), and for ZPA [Whether ZPA changes need an activation step](kb:zpa.api.activation).

**ZIA.** Saving versus activating, the status values and the activate call are in [How ZIA API changes become live: saving versus activating](kb:zia.api.activation). The platform also activates when an admin or API session ends, and a queued activation publishes every pending change in the tenant: [Activating ZIA changes from Terraform: methods, session end and concurrent applies](kb:zia.terraform.activation-methods). How the Terraform provider and the Python SDK trigger activation is in [When the ZIA Terraform provider activates configuration](kb:zia.terraform.activation), [The zia_activation_status resource: when it activates and what it cannot do](kb:zia.terraform.activation-resource) and [When the Python SDK ends a ZIA session and what that does to staged changes](kb:zia.sdk-python.activation-and-session).

**Cloud & Branch Connector.** The activate and forced-activate calls and the Terraform resource are in [Cloud Connector activation on the wire: activate, forced activate, and what the clients send](kb:cloud-connector.api.activation-wire), and the guide's POST against the contract's PUT is [shared.oneapi.write-practices:cbc-activate-method](kb:shared.oneapi.write-practices:cbc-activate-method). Its status read uses a different vocabulary from ZIA's: [Reading Cloud & Branch Connector activation status](kb:shared.activation.cbc).

**Writes refused before activation.** An edit-lock 409 and the maintenance read-only 403 stop a write before anything is staged: [When several admins edit at once only one change succeeds and the others may receive 409 `EDIT_LOCK_NOT_AVAILABLE`; the vendor recommends waiting a few seconds and retrying.](kb:shared.oneapi.write-practices:edit-lock-409), [When a ZIA call fails because of an upgrade or scheduled maintenance of the API service, it returns 403 with the header `x-zscaler-mode: read-only` and a body whose code is `STATE_READONLY`; during that period the API service supports only read operations via GET.](kb:shared.oneapi.response-codes:read-only-mode), [A maintenance 403 can therefore be told apart from a permission 403 by the `x-zscaler-mode: read-only` header or the `STATE_READONLY` code; a 403 without them points to the role, SKU or access causes.](kb:shared.oneapi.response-codes:read-only-distinguishable). The ZIA clients' retries on the lock are in [For ZIA a 409 whose body contains EDIT_LOCK_NOT_AVAILABLE, meaning another admin session holds the edit lock, is retried with a backoff of 5 seconds doubling per attempt and capped at 60.](kb:zia.api.rate-limits:zia-edit-lock-retry) and [Requests that cannot take the write lock are rejected with `EDIT_LOCK_NOT_AVAILABLE`, `Resource Access Blocked` or `Failed during enter Org barrier`; the provider retries them automatically, so contention typically appears as a progressively slower run rather than an immediate failure.](kb:zia.terraform.activation-methods:lock-errors-retried).

**Failures and tooling.** Why an activation fails and what then stays staged is open [gap:shared.activation:activation-failure], and so is how long the in-progress state lasts [gap:shared.activation:inprogress-duration]. The MCP server implements a ZIA activation-status tool and a ZIA activate tool, and its Cloud & Branch Connector tool modules include no activation tool. [shared.activation:mcp-zia-only]

What to check:
1. Which product the change was made in: only ZIA and Cloud & Branch Connector changes wait for an activation.
2. For ZIA, the activation status, and whether a session end has already activated the change.
3. For Cloud & Branch Connector, the organization edit status and the per-admin activation states, not a PENDING value.
4. Whether an activation queued behind other editing sessions, which cannot be cancelled, explains the delay.
5. Whether the write was refused with an edit-lock 409 or a maintenance 403 and never staged.
6. Whether a Terraform run created the activation resource after the last change.

Inferred, not quoted (say so when an answer rests on one):
- [shared.activation:no-other-gate] Tier B: Rests on a search of every captured OneAPI specification (ZIA, ZPA, ZCC, ZDX, Cloud & Branch Connector, ZIdentity, Unified RBAC, BI, EASM, Cellular, Event Monitoring, AI Guard, AI Security) for paths containing 'activat': only ZIA and Cloud & Branch Connector have an organization-wide activate, and the remaining matches act on one object. Absence of an activation call does not establish when a write in those products takes effect (gap shared.oneapi.write-practices:other-products-no-activation).
- [shared.activation:mcp-zia-only] Tier B: The Cloud & Branch Connector absence rests on listing src/zscaler_mcp/tools/ztw at the pin: account details, discovery service, IP destination, IP and IP source groups, admins, roles, network service groups, network services and public cloud info.
