# Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes (shared.sdk-go.zero-value-writes)
Also called: omitempty; cannot set false; cannot clear a field terraform; terraform cannot disable setting; empty string not cleared; empty list not cleared; zero value not sent; sends empty object; extranetDTO empty object; persistent drift after apply false

These are claims about what the Go SDK and the Terraform providers send, the client, not about how ZPA, Cloud and Branch Connector, or Client Connector react. The client side can be proven from code.

**Write path.** ZPA service creates, updates and deletes (for example the segment group's) call the one request function `NewRequestDo`, which serializes the caller's struct directly with `json.Marshal`, so the struct's JSON encoding decides which fields are sent. [shared.sdk-go.zero-value-writes:zpa-writes-marshal-caller-struct] The Cloud and Branch Connector (ZTW) create and update helpers (`CreateResource`, and `UpdateWithPutResource` through the shared `updateGeneric`) serialize the caller's struct directly with `json.Marshal`, and `UpdateWithPutResource`, which ZTW services such as locations, forwarding rules and IP groups use for updates, sends the whole struct. [shared.sdk-go.zero-value-writes:ztw-writes-marshal-caller-struct] Client Connector (ZCC) service creates and updates such as the trusted network v2, notification template, ZIA posture and forwarding profile ones call `NewZccRequestDo` with the caller's struct, which it serializes directly with `json.Marshal`. [shared.sdk-go.zero-value-writes:zcc-writes-marshal-caller-struct] ZIA does the same; see [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding), which this subject extends to the other products rather than restating.

**Field tags.** In every product, where a writer marshals the caller's struct and a field's type has no MarshalJSON of its own, a field tagged `omitempty` is left out of the request body when it holds false, 0, an empty string, or a nil or empty slice. So when a provider rebuilds such a struct from Terraform state and sends it as a full PUT, a user's change to false, zero, empty string or empty list reaches the SDK but never reaches the wire. [shared.sdk-go.zero-value-writes:omitempty-drops-zero-values]

**Setting a field to false.** The ZPA v2 policy rule request tags `extranetEnabled` as `omitempty`, and the access-rule resource always assigns the Terraform boolean to it, so switching `extranet_enabled` from true to false produces no `extranetEnabled` key in the PUT. [shared.sdk-go.zero-value-writes:zpa-policy-rule-extranet-enabled-false] Whether the stored value then stays, resets or clears is open [gap:shared.sdk-go.zero-value-writes:omission-semantics].

## Instances, by product

**ZPA enabled flags.** The ZPA provisioning key request tags `enabled` as `omitempty`, and the resource always assigns the Terraform boolean to it, so setting `enabled = false` on a key sends no `enabled` member. The same holds for private cloud group `enabled` and `overrideVersionProfile`. [shared.sdk-go.zero-value-writes:zpa-provisioning-key-enabled-false]

**ZPA text fields.** ZPA tag group, tag key and tag namespace requests tag `description` as `omitempty`, and the tag group resource always assigns the Terraform string to it, so changing a description to an empty string sends no `description` member. [shared.sdk-go.zero-value-writes:zpa-tag-descriptions-cannot-clear]

**Same pattern in other ZPA structs.** The same tag-and-assign pattern appears on further ZPA request structs: inspection app segment (`bypassOnReauth`, `autoAppProtectEnabled`, `passiveHealthEnabled`), PRA app segment (`bypassOnReauth`), private cloud (`enabled`, `fireDrillEnabled`), and User Portal AUP, controller and link (`enabled`). In each, a false written by Terraform produces no key. [shared.sdk-go.zero-value-writes:zpa-same-pattern-elsewhere]

**Exceptions.** Struct tags differ field by field, and the SDK sometimes handles it deliberately. The ZPA server group sends `enabled`, `dynamicDiscovery` and `extranetEnabled` without omitempty (it tags `readOnly` with it), the PRA app segment sends `passiveHealthEnabled` without it, and the tag group update replaces a nil `Tags` slice with an empty one because, per the SDK comment, the API requires tags even when empty. A false in these fields does reach the wire. [shared.sdk-go.zero-value-writes:zpa-some-structs-send-false]

**Cloud and Branch Connector.** The Cloud and Branch Connector forwarding gateway request tags `failClosed` as `omitempty`, the resource always assigns the Terraform boolean to it, and the update is a full PUT of the rebuilt struct, so setting `fail_closed = false` sends no `failClosed` member. [shared.sdk-go.zero-value-writes:ztc-gateway-fail-closed-false]

**Client Connector.** The ZCC trusted network v2 request tags `active` and every criterion list `omitempty`, so `active = false` and an explicit empty list send no key. The provider's own comment says its empty slices are omitted on the wire. [shared.sdk-go.zero-value-writes:zcc-trusted-network-active-and-lists] The ZCC notification template request tags `durationInSeconds` and `zpaReauthIntervalInMinutes` `omitempty` while its booleans are sent unconditionally, so a zero for either integer sends no key but a false boolean does. [shared.sdk-go.zero-value-writes:zcc-notification-template-int-zeros] The ZCC forwarding profile request encodes some booleans as integers and tags `sendTrustedNetworkResultToZpa` and `sameAsOnTrusted` `omitempty`, so the provider's 0 for false sends no key. `isSameAsOnTrustedNetwork` is a pointer, which is the form that can carry an explicit false. [shared.sdk-go.zero-value-writes:zcc-forwarding-profile-zero-ints]

## The empty-object variant

**Value structs.** A nested struct held by value (not a pointer) and tagged `omitempty` is never omitted by Go's JSON encoder. When the caller leaves it at its zero value, the request carries an empty object, for example `"extranetDTO":{}`, instead of no member. [shared.sdk-go.zero-value-writes:value-struct-omitempty-emits-empty-object]

**Empty objects in practice.** The ZPA server group request and the v2 policy rule request hold `ExtranetDTO` by value with `omitempty`. The server group and v2 policy rule resources fill it only when the user set `extranet_dto`, so otherwise every create and update carries `"extranetDTO":{}`. The v1 policy rule request has the same field and the v1 access rule resource never references it. [shared.sdk-go.zero-value-writes:zpa-extranet-dto-empty-object] The ZIA cloud app control rule request holds `CBIProfile` by value with `omitempty`, and the resource's expand function returns an empty `CBIProfile{}` when `cbi_profile` is not configured, so rules without a browser isolation profile are written with `"cbiProfile":{}`. [shared.sdk-go.zero-value-writes:zia-cloud-app-control-cbi-profile-empty-object] The ZCC ZIA posture request holds each trust tier (`highTrustCriteria`, `mediumTrustCriteria`, `lowTrustCriteria`) as a struct value whose only member is an `omitempty` list. The resource always builds all three tiers, and its helper returns an empty slice or nil for a missing or null tier, so a tier with no criteria is sent as `{}`, and an explicit empty `cs` list cannot be sent as `[]`. [shared.sdk-go.zero-value-writes:zcc-zia-posture-criteria-empty-object] Whether the server reads an empty object as no value, a validation error or a reset is open [gap:shared.sdk-go.zero-value-writes:empty-object-semantics].

**More ZIA fields.** Other ZIA request structs hold a nested struct by value with `omitempty`: advanced settings (`ecsObject`), browser control settings (`smartIsolationProfile`), endpoint DLP resources (`printer`, `removableStorage`, `application`), ZPA gateways (`zpaServerGroup`), SSL inspection rules (`action`) and workload groups (`expressionJson`). [shared.sdk-go.zero-value-writes:zia-value-struct-same-pattern] The endpoint DLP resource effects are traced in [ZIA Terraform resource fields that are not sent, not read back, or sent wrongly](kb:zia.terraform.field-fidelity).

See also [What the ZPA Terraform provider does when deleting objects with dependents](kb:zpa.terraform.delete-paths) for the delete-side behavior of the same ZPA provider.

What to check:
1. Which struct and field holds the value, then its tag. Some fields send false on purpose, so do not assume every field is affected.
2. Whether a ZPA provisioning key or group that the user believes is off was written with enabled set to false.
3. Whether the provider assigns the value unconditionally. A guard that sets it only when the user configures it means the zero value is not sent.
4. Whether the endpoint is a full PUT of a rebuilt struct, where a dropped member matters most.
5. Whether the symptom is persistent drift after apply, where a plan keeps showing the same change.
6. Before saying the server ignores or resets a field, say the SDK does not send it until omission-semantics and empty-object-semantics are settled.
