# What the ZPA disaster recovery deployment and operations guide requires, leaves unsupported and how activation is detected (shared.deployments.zpa.disaster-recovery)
Also called: zpa disaster recovery; zpa dr mode

ZPA disaster recovery prerequisites include Client Connector 4.0 or later for Windows, 3.7.1.38 or later for macOS, a customer-owned modifiable public DNS record, the Zscaler DNS Record Generator (Windows only) and a separate DNS domain name whose A record holds the public IP addresses of the Private Service Edges designated for disaster recovery. [shared.deployments.zpa.disaster-recovery:prereqs] An application segment with disaster recovery enabled must be associated with a server group, which must be associated with at least one App Connector Group designated for disaster recovery. [shared.deployments.zpa.disaster-recovery:segment-requirement] The console and record facts are in [Disaster recovery mode and Private Service Edge groups](kb:zpa.private-service-edges.disaster-recovery) and [Disaster recovery activation TXT records and the Zscaler DNS Record Generator](kb:zpa.private-service-edges.disaster-recovery.dns-records).

**DNS record.** The ZPA disaster recovery DNS TXT record needs at minimum v=1, b=on and k=zpa (or k=all for ZPA and ZIA); testing uses b=test; Zscaler recommends the lowest TTL, 30 seconds. [shared.deployments.zpa.disaster-recovery:txt-record] Activating disaster recovery via DNS disrupts existing Client Connector connections, and the services for both App Connector (zpa-connector) and ZPA Private Service Edges (zpa-service-edge) enabled for disaster recovery restart after activation via DNS; Client Connector checks the DNS TXT record every 200 seconds, and the guide says a command it prints as 'journaltctl -f', run on the ZPA Public Service Edge, shows the message 'DR mode is activated!'. [shared.deployments.zpa.disaster-recovery:activation-and-detection] The command that shows activation is open [gap:shared.deployments.zpa.disaster-recovery:activation-command].

**During an outage.** Disaster recovery does not support authentication and reauthentication, Browser Access, Client-Based Remote Assistance, Cloud Connectors, Dashboards and Diagnostics, enrollment of new App Connectors, ZPA Private Service Edges or Zscaler Client Connector, AppProtection for Private Application Traffic, Log Streaming Service, Machine Tunnels, policy or configuration updates, Source IP Anchoring, SCIM Configuration, user enrollments and Zscaler Deception. [shared.deployments.zpa.disaster-recovery:not-supported] During disaster recovery, by default the SAML assertion validity is extended by 14 days from the date the SAML assertion was issued, which is when a user reauthenticates; the value can be customized. [shared.deployments.zpa.disaster-recovery:reauth-extension] During a ZPA global outage, customers should assume the ZPA Admin Portal is unavailable and configuration changes, client enrollments or new user authentication are not possible; clients do not reconnect automatically after ZPA services are restored unless disaster recovery is disabled. [shared.deployments.zpa.disaster-recovery:outage-assumptions] The ZIA side is in [What the ZIA disaster recovery deployment and operations guide requires and how clients behave](kb:shared.deployments.zia.disaster-recovery), which records the macOS version spelling that differs between the two guides.
