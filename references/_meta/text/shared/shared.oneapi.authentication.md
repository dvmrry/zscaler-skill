# How a client gets and uses a OneAPI access token (shared.oneapi.authentication)
Also called: oneapi oauth; zslogin token endpoint; audience https://api.zscaler.com; client_assertion jwt; private key jwt oneapi; jwks url api client; oneapi 401 audience; token lifetime expires_in; how does zscaler authenticate api calls

OneAPI calls carry a bearer token issued by Authentication Service (ZIdentity). OneAPI uses the OAuth 2.0 Client Credentials flow, with Authentication Service, Zscaler's unified identity platform, as the authorization server: a client exchanges its credentials at the token endpoint for an access token, with no user authentication involved. [shared.oneapi.authentication:client-credentials-flow]

**Prerequisites.** Before using OneAPI, the organization needs a subscription to Authentication Service, and the client applications must be registered in Authentication Service with the necessary scope. [shared.oneapi.authentication:auth-service-subscription] API resources pair a Zscaler service with an RBAC role. An API client can be assigned one resource per product, which defines what it can do (read, write or restricted access), and can hold resources of several different products. [shared.oneapi.authentication:one-resource-per-product]

**Token request.** The client sends a POST to Authentication Service's token endpoint `https://<vanity-domain>.zslogin.net/oauth2/v1/token`, where the vanity domain is the one assigned to the organization (for example acme.zslogin.net). [shared.oneapi.authentication:token-endpoint] The token request must include an `audience` parameter with the value `https://api.zscaler.com`, for both the client-secret and the client-assertion methods. [shared.oneapi.authentication:audience-required] With a client secret, the credentials go either as HTTP Basic authentication (`clientID:ClientSecret`) or as `client_id` and `client_secret` parameters in the request payload. [shared.oneapi.authentication:secret-in-basic-or-body] The Authentication Service help describes the secret's form and place differently [divergence:shared.oneapi.authentication:secret-delivery]. An unsuccessful POST to the token endpoint returns a 400 error code, for the client-secret and the client-assertion methods alike. [shared.oneapi.authentication:failure-400] What happens when the audience is left out is open [gap:shared.oneapi.authentication:missing-audience].

**Client authentication methods.** Authentication Service accepts a client secret, which needs manual rotation, or a private key JWT assertion. The assertion is validated either with public keys fetched from a JWKS URL the client hosts, which lets the client rotate keys with no change in Authentication Service, or with public keys or X.509 certificates uploaded to Authentication Service, where rotation needs a manual update. [shared.oneapi.authentication:client-auth-methods] The guide calls a client secret best for testing, lab environments and proofs of concept, a JWKS URL best for production automation, and uploaded certificates or public keys best for environments with strict compliance or regulatory requirements. [shared.oneapi.authentication:method-fit] The Authentication Service help says OneAPI is based on the OAuth 2.0 authorization framework and that Authentication Service supports JWKS URL, Certificate or Public Key, and Client Secret authentication methods for OneAPI, any of which can be chosen. [shared.oneapi.authentication:help-methods] That help's JWKS and Certificate workflow: the client generates a JWT on its own system signed with a private key, the matching public key is hosted at the JWKS URL on a web server Authentication Service can reach and trusts, and Authentication Service retrieves it from the JWKS URL to verify the signature. [shared.oneapi.authentication:help-jwt-workflow] Where a certificate client's public key comes from differs between the two pages [divergence:shared.oneapi.authentication:certificate-key-source]. That help's Client Secret workflow: the secret is created when the API client is defined and stored on both sides; the client includes it in the request header, usually in an encrypted or hashed form, and Authentication Service validates it against its saved copy. [shared.oneapi.authentication:help-secret-workflow]

**Private key JWT.** With a private key JWT, the token request sends the signed JWT as `client_assertion` with `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, together with `client_id`, `grant_type=client_credentials` and the audience. [shared.oneapi.authentication:jwt-assertion-request] The guide's example of what signing a JWT typically looks like uses an RS256 header, `iss` and `sub` set to the client ID, `aud` set to `https://api.zscaler.com`, and an `exp` ten minutes ahead. [shared.oneapi.authentication:jwt-signing-example] Both SDKs build the client assertion themselves: signed RS256, with `iss` and `sub` set to the client ID, `aud` set to `https://api.zscaler.com`, and `exp` ten minutes after signing (Python `now + 600`, Go `10 * time.Minute`). [shared.oneapi.authentication:sdk-jwt-assertion] Because the SDKs set the assertion's `exp` ten minutes after their own clock, a caller whose clock runs more than ten minutes behind the token endpoint's sends an assertion that has already expired; a clock running ahead does not cause this. [shared.oneapi.authentication:assertion-clock-skew] Key handling differs between them: The Python SDK accepts the private key as a JWK JSON string (text starting with `{`), as PEM text containing `BEGIN PRIVATE KEY`, or otherwise as a path to a PEM file, and rejects an RSA key below 2048 bits with a ValueError before requesting a token. [shared.oneapi.authentication:python-private-key-forms] The Go SDK reads the private key only as PEM text, through `jwt.ParseRSAPrivateKeyFromPEM`, and applies no minimum key size. [shared.oneapi.authentication:go-pem-only]

**Token lifetime.** The token response carries `access_token`, `token_type` Bearer and `expires_in`; `expires_in` is the token expiration time configured for the API client in Authentication Service (3600 in the examples). [shared.oneapi.authentication:expires-in-configured] A client secret can be seen in Authentication Service only when it is first created. [shared.oneapi.authentication:secret-shown-once] The Python SDK sets its token expiry from the response's `expires_in`, using 3600 seconds when the field is absent, and refreshes the token proactively before that expiry. [shared.oneapi.authentication:python-expires-in-default]

**Using the token.** Every API call must present the access token in the Authorization header with the Bearer scheme. [shared.oneapi.authentication:bearer-header] On each request the Zscaler service extracts the JWT from the Authorization header, validates its signature and then verifies its claims before allowing access. [shared.oneapi.authentication:token-validation] The Analytics API's error guide lists an incorrect audience or issuer claim at token generation, an expired or revoked token, and a token from a different environment (beta or production) or tenant among the causes of a 401, and says to verify the audience is https://api.zscaler.com. [shared.oneapi.authentication:audience-401-cause]

**Clients.** Neither SDK leaves the audience to the caller: The Go SDK sends `audience=https://api.zscaler.com` in both its client-secret and its client-assertion token requests. [shared.oneapi.authentication:go-audience] The Python SDK does the same: [The Python OAuth client always sends `audience=https://api.zscaler.com` in the client-credentials and JWT-assertion token requests.](kb:zia.sdk-python.authentication:oauth-audience). How the Go SDK renews tokens is in [How the Go SDK obtains and renews OneAPI tokens](kb:shared.sdk-go.auth-lifecycle). Government-cloud token endpoints are in [Reaching OneAPI on government (FedRAMP) and non-production clouds](kb:shared.oneapi.government-clouds).

What to check:
1. Whether the token request carries audience=https://api.zscaler.com and goes to the tenant's own vanity domain.
2. For a 401 on an API call after a successful token request, whether the token's audience or issuer claim is wrong, or the token comes from another environment or tenant.
3. Read expires_in from the token response rather than assuming a lifetime, since the lifetime is configured per API client.
4. To rotate a private-key JWT client's key without changing Authentication Service, serve its public keys from a JWKS URL and rotate the keys behind it.
5. Before the old JWT public key is removed, confirm that tokens signed with the new key are accepted; whether both keys stay valid meanwhile is open.

Sources disagree (name both sides):
- How a client secret is sent: in the request header, usually hashed or encrypted (Authentication Service help), or as Basic credentials or in the request payload (OneAPI guide). [divergence:shared.oneapi.authentication:secret-delivery]
  - zscaler-help: The secret goes in the request header, usually in an encrypted or hashed form.
  - zscaler-help: The credentials go through Basic authentication as clientID:ClientSecret, or in the request payload as client_id and client_secret.
  Impact: The two differ on the place (header only, or header or payload) and the form (hashed or encrypted, or Basic credentials); neither page says whether the header form is Basic authentication.
- Where a certificate-based client's public key comes from: the help page groups Certificate with JWKS retrieval from the JWKS URL, while the OneAPI guide says the keys or certificates are uploaded to Authentication Service. [divergence:shared.oneapi.authentication:certificate-key-source]
  - zscaler-help: In the JWKS and Certificate workflow the public key is hosted at the JWKS URL and Authentication Service retrieves it from there.
  - zscaler-help: For Certificates/Public Keys the signature is validated with keys or certificates directly uploaded to Authentication Service.
  Impact: An answer about a certificate client that cites the JWKS retrieval gives a path the OneAPI guide assigns to the JWKS URL method only.
