# What the Internet & SaaS TLS and SSL Inspection Leading Practices Guide recommends for rollout, rule layout, bypasses and certificates (shared.deployments.zia.tls-leading-practices)
Also called: tls inspection leading practices; ssl inspection best practices

**Goals and limits.** Zscaler often sees companies achieve a 60-70 percent TLS inspection rate; the example project success criteria are 90%+ of users with inspection enabled, reported issues below one per 100 users per day and 65%+ of encrypted traffic inspected. [shared.deployments.zia.tls-leading-practices:inspection-rate] Zscaler cannot inspect TLS traffic from sites or applications using certificate pinning, client-authentication certificates (mTLS) or unsupported ciphers, nor devices that cannot install the certificate (IoT/OT, BYOD, guest networks). [shared.deployments.zia.tls-leading-practices:cannot-inspect] Some of the features that depend on TLS inspection for encrypted transactions are: Anti-Virus/Malware, Cloud Sandbox, Advanced Threat Prevention, Isolation, Data Loss Prevention, File Type Control, Inline CASB and Intrusion Prevention System. [shared.deployments.zia.tls-leading-practices:dependent-features] See [ZIA SSL/TLS inspection](kb:zia.ssl-inspection).

**Certificates.** Three root CA options exist: your own CA, your own CA with Zscaler Cloud HSM, or Zscaler's CA; using your existing CA requires an additional Zscaler subscription, and custom certificates must be added to application-specific trust stores for applications that do not use the system store. [shared.deployments.zia.tls-leading-practices:root-ca-options] On certificate failures the choices are Allow, Caution or Block and Zscaler recommends blocking; with OCSP enabled a revoked certificate is treated as untrusted, with the same action as failed trust, and Zscaler recommends enabling OCSP for all inspection rules and blocking undecryptable traffic unless there is a specific use case. [shared.deployments.zia.tls-leading-practices:certificate-handling] ChromeOS does not trust managed or user-installed certificates for OS-level communications, so only user traffic can be inspected and traffic between the device and Google's ChromeOS services must be exempted. [shared.deployments.zia.tls-leading-practices:chromeos-trust]

**Rules.** The recommended layout ends with an Inspect All rule (no criteria, blocking untrusted server certificates, enabling OCSP and blocking undecryptable traffic, minimum client and server TLS 1.2) before a Default rule of Do Not Inspect: Evaluate other policies. [shared.deployments.zia.tls-leading-practices:rule-layout] SSL/TLS inspection rules are evaluated top-down, first-match; a rule that must inspect traffic otherwise exempted is inserted before the exemption rule, and a final rule inspecting everything not exempted makes new groups, apps, categories or locations inspected automatically. [shared.deployments.zia.tls-leading-practices:rule-order-first-match] In the example rule table, rule 1 (Smart Isolation One Click Rule) and rule 2 (Zscaler Recommended Exemption Rule) set Minimum TLS Version TLS 1.0. [shared.deployments.zia.tls-leading-practices:rule-table-tls-minimums] User attributes (Group/Department) in SSL/TLS rules work only if traffic is routed by Client Connector, or if Enforce Surrogate IP is enabled for locations with traffic through GRE/IPSec; the Device OS Type is identified only via Client Connector, otherwise flagged No Client Connector. [shared.deployments.zia.tls-leading-practices:criteria-limits] Avoid Bypass Other Policies in custom exemption rules: besides not inspecting, matching traffic ignores Cloud App Control and URL Filtering policies and is Allowed. [shared.deployments.zia.tls-leading-practices:bypass-other-policies] Bypass guidance: avoid major shared domains such as (.s3).amazonaws.com, (.blob.core).windows.net and .cloudfront.net, avoid IP addresses in favour of FQDNs, bypass specific domains rather than wildcards, do not add file paths, and review all bypass entries at least annually. [shared.deployments.zia.tls-leading-practices:bypass-hygiene]

**Protocol versions.** Zscaler recommends initially allowing all supported protocols and ciphers to discover legacy use, then blocking all TLS versions earlier than 1.2 including legacy SSL services, with some services needing exception rules. [shared.deployments.zia.tls-leading-practices:min-tls-version] Zscaler's TLS/SSL inspection relies on TCP session information, so Google QUIC should be blocked with a Block/ICMP action (rather than Block/Drop or Block/Reset) so the application falls back to TCP; Zscaler's firewall and Client Connector both support blocking QUIC. [shared.deployments.zia.tls-leading-practices:quic-for-tls]

**Rollout and reporting.** Example pilot criteria: tested with 10 users for 5 business days, issues addressed within two hours, fewer than three issue reports in the last two days; the guide says organizations that prioritize and understand the importance of TLS inspection can reasonably expect successful deployment to most of their use cases within 45-90 days, depending on the environment's size, complexity and distance along their zero trust journey. [shared.deployments.zia.tls-leading-practices:pilot-criteria] The guide advises not including IT or development staff in the pilot group, because they often work around issues before reporting them and operate in non-average environments. [shared.deployments.zia.tls-leading-practices:pilot-users] TLS inspection can be reported in the Security Policy Audit Report (SSL/TLS Inspection row), Interactive Reports (Traffic Distribution by Protocol and SSL Traffic Overview with top ciphers and SSL/TLS versions) and Web Insights, where HTTPS versus SSL protocol indicates inspected versus not inspected; the Client SSL Handshake Failure Reason filter identifies transactions that failed inspection. [shared.deployments.zia.tls-leading-practices:reporting]
