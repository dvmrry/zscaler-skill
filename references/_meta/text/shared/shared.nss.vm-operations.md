# Operating and troubleshooting a deployed NSS VM: the nss command set, error codes and connection checks (shared.nss.vm-operations)
Also called: nss cli; sudo nss; nss troubleshoot; nss test-firewall; nss collect-diagnostics; nss support-access; nss update error 96 97 99; nss install-cert

By default root login is not permitted on the NSS VM, so admins must use the sudo utility to run a command with higher privileges. [shared.nss.vm-operations:sudo-only]

**Service and network.** `sudo nss start`, `sudo nss stop` and `sudo nss restart` control the service, and `sudo nss halt` shuts the OS down smoothly. `sudo nss enable-autostart` starts the NSS automatically after reboot and `sudo nss disable-autostart` disables that. [shared.nss.vm-operations:lifecycle-commands] `sudo nss configure` changes the network configuration (IP addresses, gateway information) for the service, `sudo nss configure --wipe` removes the network settings it configured, `sudo nss dump-config` displays the configuration file it changed, and `sudo nss reset-network` resets the network configuration. [shared.nss.vm-operations:network-commands]

**Updates.** `sudo nss checkversion` checks whether a new NSS version is available, `sudo nss update-now` manually updates to the latest version, and `sudo nss force-update-now` forces the update regardless of whether a new version is available. After the first NSS software deployment, the software is automatically updated with new versions. [shared.nss.vm-operations:update-commands] `sudo nss update-now` can return error code 96 (the client certificate is invalid), 97 (a timeout occurred while contacting the upgrade server) or 99 (a problem occurred while downloading and installing the latest version, and the force-update-now command needs to be explicitly issued). [shared.nss.vm-operations:update-error-codes]

**Diagnosing.** `sudo nss test-firewall` does active firewall configuration probing by attempting to resolve the DNS names and establishing outbound connections to the Zscaler cloud, and does not reset the management IP interface, so it can be run on an SSH connection. `sudo nss troubleshoot netstat` shows the active connections on the service IP address. `sudo nss troubleshoot connection` probes the connection status over a period of time and indicates whether connections are stable or flapping. `sudo nss troubleshoot feeds` shows the status of the TCP, HTTP and Cloud NSS feeds and determines whether logs are queued due to slow consumption by the SIEM. `sudo nss collect-diagnostics` collects the configuration, vital statistics regarding the health of the NSS, and error statistics, and downloads them to a local file. [shared.nss.vm-operations:diagnostic-commands] The troubleshooting article's Use Case commands check DNS resolution issues on the service interface and routes to the surface interface: `/sc/bin/smmgr -ys smnet='ping <IP address or Domain Name>'` checks reachability of an address using ICMP, `/sc/bin/smmgr -ys smnet=ifconfig` prints the interface IP address configuration, and `/sc/bin/smmgr -ys host="<FQDN of SIEM server>" -ys port=<Listening port> -ys connect=tcp` checks the port reachability of a server. [shared.nss.vm-operations:service-interface-probes] A working NSS lists a connection to the Zscaler cloud on port 443, the control connection that authenticates the NSS to the Zscaler Central Authority and downloads the configuration, which is also the data connection to the Nanolog. It also lists a long-lived TCP connection to the SIEM on the specified log data port; with multiple feeds configured, multiple connections must be listed. The absence of either, even after waiting a few minutes, usually indicates a firewall configuration issue and the logs cannot be streamed. [shared.nss.vm-operations:verify-connections]

**Support access.** An admin can allow Zscaler Support to log in to their NSS server without opening a firewall connection for inbound traffic. The feature is disabled by default and must be enabled explicitly for the duration that remote support assistance is required. `sudo nss support-access-start` creates a long-lived SSH tunnel to the Zscaler cloud and sets up remote port forwarding, `sudo nss support-access-status` checks that tunnel and `sudo nss enable-remote-debugging` enables a remote debugging session. [shared.nss.vm-operations:support-access]

**SNMP and MCAS.** `sudo nss snmp-admin-configure` changes the SNMP admin user configuration, `sudo nss snmp-trap-configure` the SNMP trap configuration and `sudo nss snmp-community-string <community string>` sets the community string, and `sudo nss configure-mcas2` sets up and enables MCAS. The article says the NSS must be restarted with the sudo nss restart command for each change to take effect, and that MCAS can be re-enabled by re-issuing the sudo nss configure-mcas2 command. [shared.nss.vm-operations:snmp-and-mcas-commands] The NSS MIB bundle, NSSMIBS.tgz, contains ZSCALER-NSSFEED-MIB (information specific to NSS feeds) and ZSCALER-NSS-MIB (information specific to the NSS instance) along with ZSCALER-OSNIC-MIB, ZSCALER-PROCESSHEALTH-MIB, ZSCALER-PROCESSWATCHDOG-MIB, ZSCALER-ROLEHEALTH-MIB, ZSCALER-SWAPINFO-MIB and ZSCALER-ZSCALERNIC-MIB. The MIB article says the steps for configuring NSS are identical to its Virtual Service Edge example, and to use the nss status command for NSS. [shared.nss.vm-operations:nss-snmp-mibs] The MIB article does not give the NSS admin-user command, only that the steps are identical to its Virtual Service Edge example [gap:shared.nss.vm-operations:nss-snmp-admin-command].

**Certificate and standby.** The AWS guide installs the SSL certificate with `sudo nss install-cert NssCertificate.zip` and says it must be installed on only one active NSS VM at a time, because several NSS VMs using one certificate cause cloud connection flapping that disrupts streaming. If the certificate is not removed from the VM, its file permission must be changed to readable only by the root user. [shared.nss.vm-operations:certificate-handling] The AWS guide says to run sudo nss start unless the instance is planned for passive backup, and that it can take a few minutes for the NSS to start streaming logs to the SIEM. [shared.nss.vm-operations:passive-backup-not-started] Standby and active-active layouts are in [What NSS delivers across an outage: VM buffer, Duplicate Logs and one-hour recovery](kb:shared.nss.reliability).
