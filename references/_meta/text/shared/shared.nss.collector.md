# NSS Collector: third-party firewall and proxy logs into the SaaS Security Report (shared.nss.collector)
Also called: nss collector; log collection; third-party firewall logs into zscaler; cef syslog to zscaler; nss collector rate limit; shadow it third-party logs

The NSS Collector runs the opposite way to a feed: it brings logs in. The NSS Collector collects logs in near real time from third-party firewall and web proxy devices inside the network perimeter and streams them to the Zscaler cloud; the functionality and its data are exclusive to the SaaS Security Report, and enabling it requires contacting Zscaler Support. [shared.nss.collector:collector-purpose]

**Prerequisites.** The NSS Collector requires a subscription to the NSS VM or Cloud NSS, must be deployed on VMware inside the network perimeter from a VM image obtained in the Admin Console, and uses a client certificate issued by Zscaler. [shared.nss.collector:collector-deployment] The collector deployment guide names the subscription differently [divergence:shared.nss.collector:collector-subscription].

**What it does with a log.** The collector listens on a fixed port for syslog feeds in CEF format over TCP from one or many firewalls; it resolves users through IdP integration, putting unmanaged users under Unidentified Users, resolves URL information for cloud application discovery, and sends the processed data to the Zscaler cloud over HTTPS. [shared.nss.collector:collector-processing] Third-party device logs are processed by Zscaler, retained for 6 months, and made available for cloud application discovery and analytics through the SaaS Security Report. [shared.nss.collector:collector-retention]

**The server and the VM.** Zscaler supports log ingestion from Palo Alto Networks, Blue Coat, and Fortinet, and the collector's third-party log vendor name is entered as PANFW, FORTIFW, or BLUECOAT after the command sudo nss collector-configure. [shared.nss.collector:supported-vendors] When disabled, the NSS Collector does not process or stream logs from third-party security solutions. When the server is added to the Admin Console, Zscaler generates the packaged software for installation and issues an SSL certificate, which must be installed on the collector VM so it can authenticate as a client with the Zscaler service. [shared.nss.collector:collector-record] The NSS Collector Servers page shows each server's Vendor, the third-party vendor of the firewall or web proxy services, and an SSL Certificate option to download the certificate for the server. [shared.nss.collector:collector-page] The vSphere collector guide lists 2 CPU cores, one for the control plane and one for the data plane, and 8 GB for up to 15K users. Its em1 (second network adapter) is the service IP address used for data connections to the Zscaler cloud, and communication from the collector to the Zscaler cloud must be excluded from SSL inspection. [shared.nss.collector:collector-vm] Users whose traffic traversed third-party vendor devices need to be provisioned through one of the mechanisms supported by Zscaler. The collector matches the user information with the Internet Access users and forwards the logs pertaining to those users to Zscaler, and the username and password information in the Palo Alto Networks firewall must match the user details configured in the Admin Console. [shared.nss.collector:user-provisioning] For Palo Alto Networks, the syslog server profile selects TCP as the transport, supports default and custom ports, selects IETF as the syslog format and LOG_USER as the facility. The traffic log uses a custom format beginning CEF:0|Palo Alto Networks|PAN-OS|$sender_sw_version|$subtype|$type|1|rt=$cef-formatted-receive_time, and the Log at Session Start and Log at Session End options are enabled. [shared.nss.collector:pan-syslog-profile]

**Limits and loss.** The collector keeps a one-hour buffer against communication issues with the Zscaler cloud and maintenance, sending buffered logs when the connection is re-established; the buffer grows in proportion to the RAM allocated to it. [shared.nss.collector:collector-buffer] An organization can have up to 4 NSS Collector servers; the collector does not support historical load, so records older than one hour are dropped from the stream, and it restricts streaming to the Zscaler cloud to 10K events per second, dropping events that exceed the rate. [shared.nss.collector:collector-limits] Whether the rate applies per collector or per organization, and whether drops are reported, is open [gap:shared.nss.collector:rate-scope].

What to check:
1. Whether the tenant holds an NSS VM or Cloud NSS subscription and had the feature enabled through Zscaler Support.
2. Whether the third-party devices send CEF syslog over TCP to the collector's port.
3. For missing third-party events, whether they were older than one hour or above the events-per-second limit when they arrived.
