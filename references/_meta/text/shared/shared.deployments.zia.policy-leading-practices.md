# What the ZIA Policy Leading Practices Guide recommends for module flow, policy types, advanced settings, URL filtering and firewall (shared.deployments.zia.policy-leading-practices)
Also called: zia policy leading practices; zia policy best practices

**Traffic flow.** Outbound web traffic goes to the firewall module and, if no firewall policy is violated, to the web module; outbound non-web traffic bound for ports other than 80/443 goes to the firewall module and is allowed to the internet if no firewall policy is violated; inbound web traffic (ports 80/443 in response to HTTP GET/POST requests) goes to the web module. [shared.deployments.zia.policy-leading-practices:module-flow] When web traffic violates a firewall policy both Firewall Insights and Web Insights show it blocked; if it passes the firewall policy and is blocked by a web policy, Firewall Insights still shows it allowed while Web Insights shows it blocked. [shared.deployments.zia.policy-leading-practices:insights-logging] The Policy for Non-Web Traffic Without Firewall Enabled section says the Public Service Edge inspects the traffic and applies the policy using only the firewall module if the organization has not enabled firewall policy for the location, and then that it neither scans nor applies any policy to the traffic. [shared.deployments.zia.policy-leading-practices:non-web-without-firewall]

**Order of operations.** Under the heading 'Web module policies are enforced in the following order of operations', the guide lists Firewall, SSL Inspection, Advanced Threat Protection (ATP), Malware/Antivirus (AV), Cloud App Control, URL Control, File Type Control, Data Loss Prevention (DLP) and Cloud Sandbox; the web module applies policies in an order based on the web traffic types, whether the traffic is encrypted or not, and whether SSL inspection is enabled or disabled, and a policy violation blocks the transaction immediately and other web policies are not applied. [shared.deployments.zia.policy-leading-practices:web-order-of-operations] In the guide's example a File Type Control policy blocks PDFs and a DLP policy blocks SSNs: a PDF containing SSNs is blocked by File Type Control, the DLP policy is not triggered and the auditor is not notified. [shared.deployments.zia.policy-leading-practices:enforcement-examples] The guide's flat list and the per-request orders in [Where Malware Protection and ATP checks fall in the web enforcement order](kb:zia.atp.enforcement-order) disagree on Cloud App Control and URL Control against ATP: [divergence:shared.deployments.zia.policy-leading-practices:web-order-vs-atp].

**Choosing a policy type and criteria.** The guide positions Cloud App Control for explicit allow/block/restrict of a known list of applications or aspects of user access, URL Filtering as the default access control space, File Type Control for limiting file types on permitted destinations, and Firewall for outbound non-web traffic. [shared.deployments.zia.policy-leading-practices:policy-type-selection] For user criteria the guide says to use Groups or Department and avoid specific users unless testing or access is limited to a small (less than 4) set; Location Groups are easier to manage than individual locations; time is based on the data center's time; ZIA device trust levels are High, Medium and Low. [shared.deployments.zia.policy-leading-practices:criteria-guidance]

**Advanced settings.** The guide recommends Disable for CIPA Compliance (unless K-12 education), Enable for Suspicious New Domains Lookup, AI/ML-based Content Categorization, Embedded Sites Categorization, SafeSearch (which requires SSL inspection) and Microsoft-Recommended Click-to-Run Microsoft 365 Configuration, and Optional for Identity-based Block Override. [shared.deployments.zia.policy-leading-practices:advanced-policy-settings] The guide recommends Disable for Cascading to URL Filtering (a global option that often causes more issues than it resolves), and Enable for Policy for Unauthenticated Traffic, Block Domain Fronting and Auto Proxy Forwarding for Non-Defined Ports (Enable All). [shared.deployments.zia.policy-leading-practices:advanced-settings-global] With Auto Proxy Forwarding for Non-Defined Ports enabled, non-standard traffic not already redirected to the SWG is redirected on the next session to that IP, port and protocol (example: HTTPS found on 2.2.2.2:32556); a Cloud Firewall rule permitting the traffic initially and an Allow rule with HTTPS as the network application are needed to discover it. [shared.deployments.zia.policy-leading-practices:auto-proxy-forwarding-mechanism]

**URL Filtering and Cloud App Control.** The URL Filtering baseline is Global > Specific > Global, ending in an unwritten, non-configurable default allow-all rule; the example rule set includes a Global Security-based Block rule with action Block listing the categories Newly Registered and Observed Domains, Peer-to-Peer Site, Anonymizer, Computer Hacking, Copyright Infringement, Custom Encrypted Content, Newly Revived Domains, Other Security and Spyware/Adware. [shared.deployments.zia.policy-leading-practices:url-baseline-shape] The guide suggests a risk profile for applications with a Risk Index of 4 or 5 in an Unsanctioned status, applied across Cloud Application categories to block or restrict risky applications. [shared.deployments.zia.policy-leading-practices:cac-risk-profile] By category: DNS Over HTTPS Services should be blocked if DNS Control is used; for File Sharing, allow the approved service in Cloud App Control and block others via URL Filtering File Host category; upload control within File Sharing, posting control in Social Networking and sending restriction in Webmail need SSL inspection. [shared.deployments.zia.policy-leading-practices:cac-category-notes] See [ZIA URL Filtering](kb:zia.url-filtering).

**Firewall and DNS.** Standard Firewall provides Layer 3, Layer 4 and FQDN rules with aggregate logging for all flows and detailed logging where a block action is selected; Advanced Firewall adds per-user conditions, DPI application identification, detection and redirection of non-standard web traffic, DNS controls, IPS controls for non-web traffic and detailed logging for each session and flow. [shared.deployments.zia.policy-leading-practices:firewall-tiers] The guide says all Zscaler tenants ship with the default Firewall Filtering Rule set to Block (default block), while historically ZIA Firewall shipped with a default Allow setting that many customers kept. [shared.deployments.zia.policy-leading-practices:firewall-default-rule] Under default block, system-defined allow rules for Zscaler proxy traffic, Microsoft 365 and Click-to-Run should rank highest (a rule above Zscaler proxy traffic stops the proxy functioning); the Recommended Firewall rule targets standard web (TCP:80, TCP:443) and DNS (TCP:53 or UDP:53) network services. [shared.deployments.zia.policy-leading-practices:firewall-rule-priority] Zscaler recommends blocking QUIC (mostly UDP:443, which is the current definition of the QUIC network service) and forcing communications into HTTP/2 or HTTPS; the guide says selecting the ICMP block drops the UDP packet and sends the client ICMP Type 3 (Destination Unreachable) Code 13 (Communication Administratively Prohibited), which gives the client a potentially faster switchover to another web transport method, and that QUIC also appears on UDP:80. [shared.deployments.zia.policy-leading-practices:quic-block] DPI application detection does not usually happen on the first packet, so several packets might be allowed before an action; network applications should be blended with another condition or placed lower in the rule list, otherwise many flow log entries can be Allowed due to insufficient app data. [shared.deployments.zia.policy-leading-practices:network-app-dpi-leakage] For DNS Control, DNS traffic can be forwarded via GRE or IPSec tunnels, via Z-Tunnel 2.0 on Client Connector with DNS included, or by forwarding recursive DNS requests from a DNS server (which loses all end user context). [shared.deployments.zia.policy-leading-practices:dns-forwarding-options] See [ZIA Firewall Control](kb:zia.firewall) and [ZIA DNS Control](kb:zia.dns-control).

Sources disagree (name both sides):
- Where ATP and Malware/Antivirus fall against Cloud App Control and URL Control: the leading practices guide lists ATP and AV before Cloud App Control and URL Control, while the policy enforcement article's HTTP GET order puts Cloud App Control and URL Filtering before most ATP checks. [divergence:shared.deployments.zia.policy-leading-practices:web-order-vs-atp]
  - zscaler-help: The web module order lists Advanced Threat Protection (ATP) and Malware/Antivirus (AV) before Cloud App Control and URL Control.
  - zscaler-help: For an HTTP GET request the order starts with Custom Malicious URLs (ATP), then Cloud App Control, then URL Filtering, with Country-Based Blocking and IPS Signature Detection later.
  Impact: Which block a user sees when both an ATP check and a Cloud App or URL rule match depends on which page applies; the guide's list is described as an order based on traffic type, encryption and SSL inspection, so it may be a summary rather than a conflict, but neither page says so.
