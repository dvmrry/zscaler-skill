# ZIA API roles, SD-WAN partner API roles and SD-WAN partner API clients (shared.admin-rbac.zia-api-roles)
Also called: zia api role; adding api roles; sd-wan partner api role; sd-wan partner api client; internal api user oauth-rolename; api role limit 16

An API role defines what a client application can reach in the ZIA cloud service API, and is distinct from an admin role. An API role defines a client application's permission and access to the API categories of the Zscaler cloud service API. It is not assigned to an admin; it is used when configuring an external OAuth 2.0 authentication server, where the role in the JWT issued by the server defines the role of the API application client. [shared.admin-rbac.zia-api-roles:api-role] The OAuth flow that carries it is in [ZIA legacy OAuth 2.0 through an external identity provider](kb:shared.legacy-api.zia-oauth), and the one existing summary claim is [An API role, added in the Admin Console and then configured in an external OAuth 2.0 authentication server, dictates a client application's access to the API categories of the cloud service API, instead of the API passing an admin user, password and API key.](kb:shared.admin-rbac.zia:api-role-oauth).

**Adding an API role.** An organization can add up to 16 API roles. [shared.admin-rbac.zia-api-roles:api-role-limit] Configuring API roles needs an admin role with full permission to Administration > API > Internet & SaaS API. [shared.admin-rbac.zia-api-roles:api-role-prerequisite] Admin rank cannot be specified for an API role because its admin rank is always 7, and API roles cannot modify any admin users. [shared.admin-rbac.zia-api-roles:api-role-rank] The rank claim on the role page is [A role's admin rank is shown only if admin ranking is enabled in Advanced Settings, and rank does not apply to SD-WAN partner API or API roles. Admin ranking is disabled by default and is enabled on the Advanced Settings page; if it is not enabled, only super admins (rank 0) can manage roles and permissions for other admins.](kb:shared.admin-rbac.zia:rank-visibility).

**Permissions.** An API role has Reporting Access and Alerts Access, each Full, View Only or None. The API categories take Full, View Only, None or Custom, where Custom assigns field-wise Full, View Only or None; Custom is available for Traffic Forwarding Methods and Traffic Forwarding Components, and the reporting features take View Only, None or Custom. [shared.admin-rbac.zia-api-roles:api-role-permissions] The API role form's field-wise lists are, in the page's order: Malware Protection, Advanced Threat Protection, Sandbox, IPS Control, Mobile Malware Protection, Secure Browsing; URL & Cloud App Control, Firewall Control, DNS Control, NAT Control, File Type Control, Mobile App Store Control, Bandwidth Control, FTP Control with Bandwidth Classes and Tenant Profiles as Policy Components; Nanolog Streaming Service, Virtual Service Edges; Proxies & Gateways, Subclouds & DC Exclusion, Traffic Capture; Advanced Settings, Administrator Management, Audit Logs, User Management, Remote Assistance Management, Authentication Settings, Identity Proxy Settings, Role Management; and Backup Controls with Backup and Restore. [shared.admin-rbac.zia-api-roles:api-role-categories] What the form lacks, compared with the admin role form, is open [gap:shared.admin-rbac.zia-api-roles:form-differences].

**After the role is created.** Creating an API role automatically creates an internal API user in the format oauth-<rolename>$@<orgid>.<cloud_domain> (for example oauth-apirole1$@64444.zscaler.net), used as the User context in any API operation. It is displayed in the audit log for API operations authenticated by an external OAuth 2.0 authentication server, but not on the Administrator Management or User Management pages. [shared.admin-rbac.zia-api-roles:internal-api-user] After the API role is created, it is defined as a Scope on the authorization server in the <Zscaler Cloud Name>::<Org ID>::<API Role> format, where the Org ID is the Company ID from the company profile under Administration > Administration > Organization > General Information. [shared.admin-rbac.zia-api-roles:scope-on-server]

**SD-WAN partner API roles.** An SD-WAN partner API role is a specific role for API access to the Internet & SaaS (ZIA) cloud service APIs. SD-WAN partner APIs cannot be users; only admins can be assigned to the role. They make API calls to endpoints that involve building tunnels and mapping tunnels to locations, have no interactive Admin Console login, perform only calls related to SD-WAN partners, and are assigned full or view-only permissions to the API endpoints group. [shared.admin-rbac.zia-api-roles:sdwan-role] SD-WAN partner APIs cannot update policy configurations, create or delete users or grant users access to the Admin Console, or change properties or settings within the Admin Console; an SD-WAN partner API is not the same as a System Integration partner. [shared.admin-rbac.zia-api-roles:sdwan-role-limits] An SD-WAN partner API role's traffic-forwarding permission is Full (view and edit the traffic-forwarding API resources), View Only, or Custom, which sets Full or View Only per endpoint: Locations, VPN Credentials, Static IPs and GRE Tunnels. Full or View Only applies to all the traffic-forwarding resources, and if a role has no access to an endpoint, the option to get or update its resources via the API is not available. [shared.admin-rbac.zia-api-roles:sdwan-role-permissions]

**SD-WAN partner API clients.** An SD-WAN partner API client has a login ID and an email, each with a selected domain name, and a Partner Role chosen from the SD-WAN partner API roles. Disabling the client clears its password, so a new one is needed on re-enabling, and with SAML enabled setting a password is optional; a password is 8 to 100 characters with at least 1 number, 1 special character and 1 uppercase letter. [shared.admin-rbac.zia-api-roles:sdwan-client] Limits on roles and clients, and how a client authenticates to the API, are open [gap:shared.admin-rbac.zia-api-roles:sdwan-limits-auth].

**SD-WAN partner keys.** An SD-WAN partner key enables partner access to the following resources within the cloud service API: Locations, where the partner can export all attributes of a service-defined location and make requests to add, update and delete locations, and VPN Credentials, where the partner can configure IPSec tunnel parameters including pre-shared keys, FQDNs and their associated location names. [shared.admin-rbac.zia-api-roles:sdwan-partner-key-scope] Before adding a partner key an SD-WAN partner API role with SD-WAN partner access enabled is configured, an SD-WAN partner API client with the proper partner role is configured, and the configured locations and VPN credentials are assigned to the proper partner, whose name then shows in the Managed By column. The partner is then given its SD-WAN partner API client credentials and the partner key. [shared.admin-rbac.zia-api-roles:sdwan-partner-key-prereqs] An organization can only have one partner key per SD-WAN partner, and the existing key must be deleted before a new one is added; the partners in the Add Partner Key list are Cisco Viptela, VMware SD-WAN, Citrix SD-WAN, CloudGenix, HPE Aruba, ngena, Riverbed SteelConnect, Silver Peak, VMware VeloCloud and Nile Secure, and for VMware SD-WAN an SSO URL must also be entered. A new key is immediately valid; an edited key must be alphanumeric (A-Z, a-z, 0-9), exactly 12 characters and different from the Current Partner Key, and after confirmation the old key is immediately invalidated. Regenerating gives a random key string and invalidates the old one, and deleting immediately removes and invalidates the key. [shared.admin-rbac.zia-api-roles:sdwan-partner-key-rules] The partner key list shows the Partner Name, the Key string, Last Modified By (the admin that last modified the key) and Last Modified On (the date and time it was last modified). [shared.admin-rbac.zia-api-roles:sdwan-partner-key-list]

What to check:
1. For an OAuth call that fails on role, whether the API role exists in the Admin Console and the authorization server's scope names it in the cloud::org ID::role form.
2. To find the user an OAuth API change is recorded against, the internal API user created with the role.
3. For an SD-WAN partner that cannot call an endpoint, whether its role has Full, View Only or Custom access to that endpoint.
