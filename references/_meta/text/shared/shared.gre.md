# GRE tunnels to Zscaler: where each question is answered (shared.gre)
Also called: gre tunnel; gre tunnels; gre to zscaler; gre deployment; gre mtu mss; gre failover; gre and z-tunnel 2.0

GRE is the unencrypted site tunnel from a router to ZIA Public Service Edges. Its behavior is held in the ZIA traffic forwarding subjects; this subject routes the questions.

1. **Is GRE the right method?** Router support, a static egress IP and the comparison with IPSec, PAC files and Client Connector: [Forwarding methods Zscaler supports and how to choose](kb:zia.traffic-forwarding.methods) and [The tunnel's egress port needs a static IP address: the perimeter router must support GRE and its egress port must have a static IP.](kb:zia.traffic-forwarding.gre:static-ip-required). The vendor's recommended combination of methods is [Zscaler recommends forwarding all internet traffic (all protocols, all ports) to the service, using a combination of tunneling, PAC files, Surrogate IP and Client Connector. The stated benefits are that all platform features (Bandwidth Control, Firewall, group and department policy) are available and that sublocations can apply different policy by IP address.](kb:zia.traffic-forwarding.methods:recommended-combination).
2. **Where is it built from?** An internal router behind the firewall (preferred), the border router with NAT disabled, or explicit proxy mode to the Global Public Service Edges where there is no default route: [Zscaler's recommended deployment is two tunnels from an internal router behind the firewall, a primary to a Public Service Edge in one data center and a secondary to another. The tunnel source is a public IP configured on the router's loopback interface, the firewall needs a rule allowing GRE from the router, and internal IP addresses stay visible for policy and logging.](kb:zia.traffic-forwarding.gre:internal-router), [If an internal router is not feasible, a tunnel can be built from the border router, which must send internet-bound traffic to the Public Service Edges and requires NAT disabled on the firewall so internal IPs remain visible.](kb:zia.traffic-forwarding.gre:border-router), [For explicit proxy mode over GRE in an environment with no default route, the tunnel is used with the Global Public Service Edge addresses 185.46.212.88 to .93, .97 and .98. These are dummy addresses that no Public Service Edge listens on but all know about, so traffic is routed to them through a GRE or IPSec tunnel and a PAC file directs users there.](kb:zia.traffic-forwarding.gre:explicit-via-global-edges).
3. **How much does a tunnel carry?** The 1 Gbps and 250 Mbps limits, the NAT reason and scaling with more source IPs: [Zscaler supports at most 1 Gbps per GRE tunnel when the internal endpoint addresses are not NATed and 250 Mbps when they are (source NAT, including source PAT).](kb:zia.traffic-forwarding.gre:bandwidth-limit), [Above 1 Gbps, Zscaler recommends more tunnels with different public source IP addresses, each with a backup: 2 Gbps is two primary and two backup tunnels, 3 Gbps is three and three.](kb:zia.traffic-forwarding.gre:scale-out).
4. **What MTU and MSS?** The 1,476-byte MTU and 1,436-byte MSS for a 1,500-byte WAN: [MTU and MSS for the tunnel are calculated from the WAN interface: for a 1,500-byte WAN, GRE MTU is 1,500 - 20 - 4 = 1,476 and GRE MSS is 1,476 - 20 - 20 = 1,436. An incorrect MTU causes fragmentation and degraded performance.](kb:zia.traffic-forwarding.gre:mtu-mss).
5. **How is failure detected and failed over?** Keepalives, Layer 7 health checks to the vpntest URL, and the fast and conservative failover profiles: [GRE tunnel health checks and failover](kb:zia.traffic-forwarding.gre-failover).
6. **How is the tunnel provisioned?** Static IP, VIP selection, the excluded premium data centers and the API: [A tunnel is provisioned either through a Zscaler Support ticket or by self-provisioning in the Admin Console; regional surcharge and premium data centers are excluded from the data center picker because of possible extra cost or specialized usage restrictions.](kb:zia.traffic-forwarding.gre:provisioning), [A tunnel names a primary and a secondary destination VIP; the Python SDK's add_gre_tunnel docstring says the closest recommended VIPs are chosen automatically when they aren't specified. The within-country flag restricts VIPs to the source IP's country, and the unnumbered flag supports automated SD-WAN provisioning with no internal tunnel addresses.](kb:zia.traffic-forwarding.gre:vip-selection), [Tunnels are managed at /greTunnels; recommended destination VIPs come from /vips/recommendedList (also grouped by data center at /vips/groupByDatacenter), and /orgProvisioning/ipGreTunnelInfo returns IP addresses with their tunnel details.](kb:zia.traffic-forwarding.gre:api-surface).

**Client Connector behind GRE.** Zscaler says not to route Z-Tunnel 2.0 through GRE: [Zscaler says not to route Z-Tunnel 2.0 through GRE tunnels; to prevent performance issues where GRE exists, either have the forwarding profile fall back to Z-Tunnel 1.0 when the trusted network criteria are met, or exclude Z-Tunnel 2.0 traffic from the GRE tunnel with a policy-based route.](kb:zcc.z-tunnel.deployment:gre-guidance). Why several egress IPs break Z-Tunnel 2.0 setup is [A site whose egress uses several GRE tunnels with different public source IPs, or ECMP, can present one device's Z-Tunnel 2.0 control and data connections from different IPs; per the vendor that splits them across Service Edges and Z-Tunnel 2.0 falls back to 1.0.](kb:zia.traffic-forwarding.mixed-deployments:gre-ztunnel2-egress); the Z-Tunnel side is [Z-Tunnel 1.0 and 2.0: where each question is answered](kb:shared.z-tunnel).

**Users and addresses.** How GRE inner addresses map to sublocations is [Which IP addresses a sublocation matches, overlap rules and XFF](kb:zia.locations.ip-scoping), and user identity on tunnel traffic comes from Surrogate IP: [Surrogate IP: mapping a private IP to an authenticated user](kb:zia.authentication.surrogate-ip). How the firewall sees tunnel traffic is [Where the firewall sits in the traffic path](kb:zia.firewall.traffic-path).
