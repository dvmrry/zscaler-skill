# Device posture across products: Client Connector evaluates, Private Access and Internet & SaaS consume (shared.device-posture)
Also called: device posture; posture profile; why did posture access break; posture failing today passed yesterday; posture and trusted network; posture evaluation frequency; machine tunnel posture failing; posture cross product

A posture question usually crosses three products: Client Connector runs the checks, and Private Access rules and Internet & SaaS trust levels act on the result. This subject walks that split and points at where each part is held.

1. **Where is the profile defined, and who uses it?** One definition serves both products: [Posture profiles for both Internet & SaaS and Private Access are created in the Device Posture section of the Zscaler Client Connector configuration, and they are used for Private Access access policies and for Internet & SaaS posture trust levels.](kb:zpa.posture-profiles.object-model:zcc-defined) It is evaluated on the device: [A device posture profile is a set of criteria evaluated on the device, and policies in both Internet & SaaS and Private Access can act on the outcome.](kb:zcc.device-posture:evaluated-on-device)
2. **Which checks exist on which platform?** Pass conditions and version floors are in [Device posture check types: what each checks, where it applies, and how it passes](kb:zcc.device-posture.check-types), and the per-platform lists in [Which device posture types each platform supports](kb:zcc.device-posture.platform-support). A type the selected platform does not support cannot be added to the profile: [A device posture profile names one or more platforms (Windows, macOS, Linux, Android, iOS); a posture type that a selected platform does not support is unavailable in the profile.](kb:zcc.device-posture.check-types:platform-selection) Ownership Variable and Unauthorized Modification are Android and iOS checks, not Windows ones: [Ownership Variable applies to Android or iOS and passes when the device holds the configured alphanumeric variable (at most 32 characters), which the device management system pushes at installation.](kb:zcc.device-posture.check-types:ownership-variable), [Unauthorized Modification applies to Android or iOS and passes when the device has no unauthorized modification such as jailbreaking or rooting.](kb:zcc.device-posture.check-types:unauthorized-modification), [Windows supports every posture type except Ownership Variable, Unauthorized Modification and Jamf Detection.](kb:zcc.device-posture.platform-support:windows-types).
3. **When is it evaluated?** Schedule, frequency setting and trigger events: [Zscaler Client Connector evaluates device posture profiles every 15 minutes, new connections are established on the updated posture, and existing connections are not affected by updates to security postures.](kb:zpa.posture-profiles.evaluation:cadence), [From Zscaler Client Connector 4.4 on Windows and 4.5 on macOS, the evaluation frequency can be set per posture type in one-minute steps, with a maximum default of 15 minutes and a minimum of 2 minutes.](kb:zpa.posture-profiles.evaluation:frequency-setting), [Network and device changes that trigger a posture evaluation are: the Zscaler service restarting, and a device rebooting, joining a network, coming out of hibernation, moving from non-domain joined to domain-joined, moving from Wi-Fi to Ethernet, or changing Wi-Fi networks.](kb:zpa.posture-profiles.evaluation:triggers). Only Process Check, Detect Carbon Black, Detect CrowdStrike, Detect SentinelOne and Detect Microsoft Defender are re-evaluated as soon as the posture changes on the device; any other type, Full Disk Encryption for example, keeps its last result until the configured frequency or a trigger event runs the evaluation again. [shared.device-posture:immediate-only-five] What a shorter frequency costs on the device is open [gap:shared.device-posture:frequency-cost].
4. **What happens to a session already open?** Existing connections are not affected by a posture update: [Zscaler Client Connector evaluates device posture profiles every 15 minutes, new connections are established on the updated posture, and existing connections are not affected by updates to security postures.](kb:zpa.posture-profiles.evaluation:cadence) Whether a Private Access reauthentication timeout bounds how stale the result can be is open: [Whether a ZPA reauthentication timeout bounds how stale a posture result can be](kb:zpa.posture-profiles.evaluation:reauth-bounds-staleness).
5. **Does it apply before login, or to a partner tenant?** The pre-login machine tunnel evaluates only the types listed for it: [On the Windows machine tunnel the posture types that apply are Client Certificate, Certificate Trust, File Path, Registry Key, Firewall, Full Disk Encryption, Domain Joined, AzureAD Domain Joined, Server Validated Client Certificate, OS Version and Zscaler Client Connector Version.](kb:zpa.machine-tunnels.posture:windows-types), [On the macOS machine tunnel the posture types that apply are CrowdStrike ZTA Score, Full Disk Encryption, File Path, Firewall, Domain Joined, OS Version and Zscaler Client Connector Version.](kb:zpa.machine-tunnels.posture:macos-types). What the machine tunnel does with a profile's other types is open [gap:shared.device-posture:machine-tunnel-unlisted-types], and so is why they are excluded: [Why some posture types cannot run on the pre-login machine tunnel](kb:zpa.posture-profiles.evaluation:user-context-types). Partner tenant tunnels are covered only when the profile says so: [Apply when added as Partner Tenant (Client Connector 4.6 and later on Windows, 5.0 and later on macOS) evaluates the posture type for the Private Access tunnel used to connect to a partner tenant; otherwise the type is evaluated only for the Private Access and Internet & SaaS tunnels.](kb:zcc.device-posture.check-types:partner-tenant)

## Private Access

An access rule names the profile by its posture UDID and asks for VERIFIED or VERIFICATION FAILED: [The POSTURE operand in ZPA policy rules](kb:zpa.posture-profiles.policy-operand). Posture condition sets in one rule are joined by AND, and profiles inside one set by OR unless toggled: [Multiple Cloud Connector groups and multiple posture profile condition sets in one rule are joined by AND, while profiles inside one condition set are joined by OR by default with a toggle to AND.](kb:zpa.policy.conditions:and-within-some-criteria) Rules are evaluated in order and the first match wins: [An allow rule for all applications for Marketing, listed above a rule denying Marketing the Operations Apps segment group, leaves Marketing with access to that group, because Private Access stops at the first matching rule.](kb:zpa.policy.access-rule-order:segment-group-allow-shadows-deny) A Private Access rule that carries both a posture condition and a trusted network condition matches only when both hold. A rule meant to admit on-premises devices without posture must not carry the posture condition and must be ordered above the rule that checks posture. [shared.device-posture:posture-and-trusted-network] Timeout rules can tier sessions by posture too: [The MCP skill's posture example gives devices that pass a posture check a longer timeout and non-compliant devices a shorter one, using two rules with the POSTURE rhs set to true and to false.](kb:zpa.policy.timeout-rules:posture-tiering-example)

## Internet & SaaS

Internet & SaaS policy uses posture through device trust levels, which are rule criteria in several policies: [Internet & SaaS device trust levels: how posture becomes a policy criterion](kb:shared.device-posture.trust-levels).

## When it fails

A check that failed, could not run, or has not been refreshed are separated in [Why a device fails posture, and what the user sees](kb:zcc.device-posture.failure-modes). Whether a missing CrowdStrike ZTA score fails the check is open: [What a CrowdStrike ZTA check reports when no score is available](kb:zcc.device-posture.failure-modes:zta-score-absent).

What to check:
1. For a device that passed yesterday and fails today: whether the type re-evaluates immediately or waits for the frequency or a trigger event (new network, Wi-Fi change, reboot), and when it last ran.
2. Whether the posture change moved the user to a different access rule in order, rather than failing one rule; put the strictest posture rule above the laxer ones.
3. For a session that survived a posture failure: whether the connection predates the failure, since existing connections keep the earlier result.
4. For a pre-login machine tunnel failing posture: whether Apply to Windows or macOS Machine Tunnel is selected, and whether every type in the profile is on that platform's machine tunnel list.
5. For a rule that combines posture with a trusted network: whether both conditions hold for the user, and whether an on-premises rule without posture sits above it.
