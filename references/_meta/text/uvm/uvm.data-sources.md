# UVM data sources: shared connector facts, availability, and the Jira, Zscaler, Okta, Code42, NetBox, runZero, SecurityScorecard and SFTP connectors (uvm.data-sources)
Also called: uvm connectors; uvm data source connectors; secops data source connectors; vendor connector configuration

The shared Configure > Sources procedure is in [Data from external tools (vulnerability scanners, asset inventories, cloud providers) is ingested by creating a data source from a tile on the Sources page; its setup has Details, Retrieval, Scheduling, Remediation Detection Settings and Suppression Rules sections and an optional connectivity Test, and data is retrieved on the next data run unless Process Now is used.](kb:portfolio.secops-platform:data-sources); the connector pages add the facts below. AnySource is in [Feeding UVM with AnySource: retrieval methods, file structure and the fields to include](kb:uvm.anysource) and the other connectors are in [UVM cloud data sources: the AWS, Azure, Google Cloud Platform and Google Sheets connectors, and the Aqua Security, Lacework and Cyera cloud-security connectors](kb:uvm.data-sources.cloud), [UVM endpoint, Microsoft and vulnerability-scanner data sources: CrowdStrike, Defender for Endpoint, Entra ID, Intune, Qualys, Rapid7 and Tenable connectors](kb:uvm.data-sources.endpoint), [UVM application-security, code and cloud-security data sources: Apiiro, Black Duck, Burp Suite, Endor Labs, GitHub, Invicti, JFrog Xray, Legit Security, Prisma Cloud, Wiz, Snyk, Veracode, Quokka, SentinelOne and Tanium connectors](kb:uvm.data-sources.appsec) and [UVM asset-inventory, attack-surface and ServiceNow data sources: Axonius, Armis, Flexera, Halo, HCL BigFix, Datto, Freshservice, Claroty xDome, Dragos, Bitsight, CyCognito, Ionix, Mandiant ASM, Horizon3.ai, Digital Shadows and ServiceNow connectors](kb:uvm.data-sources.inventory). Product overview: [Unified Vulnerability Management (UVM): what it does with findings, and what can be automated](kb:uvm.overview).

**Availability and credentials.** Among the connector pages, these state that the connector is in limited availability and to contact Zscaler Support: Aqua Security, Burp Suite Issues, Claroty xDome for Healthcare, CyCognito, Datto, Dragos, Endor Labs, GitHub Advanced Security, GitHub Repositories, Google Cloud Platform, Halo Assets, HCL BigFix - Computers, Ionix and Mandiant ASM; the Horizon3.ai page says this of its Weaknesses Evidence stream. [uvm.data-sources:limited-availability] [gap:uvm.data-sources:limited-availability-meaning]

For the Okta Workforce Identity and CrowdStrike Falcon Insights sources, once the data source is saved its authentication cannot be changed; to use a different authentication, delete the data source and create a new one. [uvm.data-sources:auth-immutable] On the pages for these connectors, the credential generated in the third-party product cannot be copied or viewed later (Apiiro token, Axonius API key and secret, Bitsight token, Black Duck token, Burp Suite API key, Claroty token, Code42 secret, CyCognito API key, Datto secret, Flexera refresh token, Horizon3.ai API key, Ionix token, Legit Security token); the Halo Assets page adds that saving the application before copying means the client secret must be regenerated while the client ID is unchanged. [uvm.data-sources:credential-shown-once] Several connector pages say the generated token or key carries the permissions of the creating user: Bitsight and Ionix tokens, and the AttackForge API key. [uvm.data-sources:token-inherits-user]

**Streams and lookback.** The Apiiro, Aqua Security, Armis, AWS, Bitsight, CrowdStrike, Cyera, Datto, Dragos and Endor Labs connector pages each say to select the streams that are based on your feature plan and use cases. [uvm.data-sources:stream-selection] Lookback behavior differs by page: by default the Aqua Security connector retrieves data from the last 7 days, the Digital Shadows connector from the last 30 days, and the Axonius connector retrieves all data; on the Bitsight page, if the field is left empty, all available data is retrieved. [uvm.data-sources:days-to-fetch-defaults] The Aqua Security and Digital Shadows pages warn that a larger date range can lead to longer processing times or potential timeouts. [uvm.data-sources:large-range-timeouts] [gap:uvm.data-sources:sync-behaviour]

**Jira Issues.** The Jira Issues stream retrieves standard issue and custom fields; its project setting is a comma-separated list of Jira project keys and, if left empty, issues from all projects accessible to the user are fetched. [uvm.data-sources:jira-issues-stream] The Jira Issues authentication takes an API Key (a secret), a Domain (for example yourcompany.atlassian.net), an Email, and a Verify SSL option that allows configuring a root CA certificate. [uvm.data-sources:jira-auth-fields] On the Jira Issues page, if left empty the connector retrieves all issues not filtered by a JQL condition; if a checkbox is enabled data volume might increase, and if it is not selected the connector retrieves a standard set of issue fields. [uvm.data-sources:jira-filters]

**Zscaler Advanced Detections.** The Zscaler Advanced Detections connector requires active Internet & SaaS and Agentic SOC subscriptions, and the Zscaler Account team sets it up on the customer's behalf. [uvm.data-sources:zad-prereq] When Zscaler Advanced Detections detects a threat it publishes an incident on the Incidents page with one source labeled Zscaler Advanced Detections. [uvm.data-sources:zad-incidents] Zscaler Advanced Detections uses two classes of analytics, indicators of compromise and behavioral detectors, and maps every detector to MITRE ATT&CK techniques. [uvm.data-sources:zad-analytics] Zscaler Advanced Detections lists unmanaged devices, insider threats, encrypted threats, "living off the land" attacks, and AI-driven and multi-stage attacks as the Zscaler-specific threats its detectors help detect earlier and stop faster. [uvm.data-sources:zad-threats]

**Okta Workforce Identity.** The Okta Workforce Identity connector retrieves system log activity from Okta (application, device, group, system, user authentication, user lifecycle, user MFA and zone activity) for use in the Agentic SOC application. [uvm.data-sources:okta-scope] The Okta Workforce Identity connector requires active Internet & SaaS (ZIA) and Agentic SOC accounts and offers two authentication types, Token Hostname and Okta OAuth 2.0. [uvm.data-sources:okta-auth] The Okta Workforce Identity page's authentication steps say "The Okta Users Authentication window appears." [uvm.data-sources:okta-auth-window-name]

**Code42.** The Code42 connector retrieves alerts from configured alert rules, including details on alert destinations and alert actors; creating the API client requires the Customer Cloud Admin role and the Alerts Read API permission, and the client ID, client secret and base URL are shown on creation. [uvm.data-sources:code42-scope] On the Code42 page, the number of days to retrieve data for during each run sets the lookback period (in days) from the current date. [uvm.data-sources:code42-days] The Code42 connector page's prerequisites say "To learn more, refer to the Mimecast documentation." [uvm.data-sources:code42-mimecast-reference]

**ZIA Devices and Users.** The ZIA Devices and Users connector retrieves devices and their owners from ZIA, and authenticates with the username and password of a ZIA admin account. [uvm.data-sources:zia-params] The ZIA connector needs an organization with an API subscription and an enabled API key; an organization can have only one API key, so a new one requires deleting the existing key. [uvm.data-sources:zia-api-key] For the ZIA admin who creates the API key, all permissions are set to View Only when possible, User Names and Device Information to Visible and Workflow Access to None; the user providing the username and password must be an admin with access to all functional scopes. [uvm.data-sources:zia-perms] The ZIA page says that if all required parameters and appropriate permissions are entered and saving the connector still errors, the user whose credentials are entered might need Password Based Login enabled; the steps are done by logging in to the ZIA Admin Portal as a super admin and going to Administration > Administration Management. [uvm.data-sources:zia-password-login] The ZIA company ID is viewed under Administration > Company Profile on the Organization tab, in the General Information section, and the cloud name is taken from the admin login URL (admin.zscalerbeta.net gives zscalerbeta.net). [uvm.data-sources:zia-cloud-company]

**Zscaler Client Connector Devices.** The Zscaler Client Connector Devices connector retrieves data on assets in the organization, including which Zscaler products are installed on which assets. [uvm.data-sources:zcc-purpose] The ZCC connector requires the API to be enabled for the organization by contacting Zscaler Support, and an admin whose role has full access to the public API resource in the Zscaler Client Connector Portal. [uvm.data-sources:zcc-prereq] A ZCC API key name must be alphanumeric, cannot contain spaces and has a maximum of 50 characters; the key status defaults to Enabled, the role to select is Read access, and the recommended session validity is at least 43,200 seconds (12 hours). [uvm.data-sources:zcc-api-key] The ZCC client secret is only available when the API key is created and not after the window is closed. [uvm.data-sources:zcc-secret]

**NetBox.** The NetBox connector has 3 streams: Devices, IP Addresses (IPAM data) and Virtual Machines. [uvm.data-sources:netbox-streams] The NetBox API token's user needs DCIM > Device for Devices, IPAM > IP Address for IP Addresses and Virtualization > Virtual Machine for Virtual Machines. [uvm.data-sources:netbox-perms] Creating a NetBox API token requires being a NetBox admin, and the token is created with Write enabled deselected; expiry and Allowed IPs are optional, and an expiring key must be refreshed to keep connectivity. [uvm.data-sources:netbox-token] The NetBox URL is the instance URL in the format https://<Your Instance>.cloud.netboxapp.com. [uvm.data-sources:netbox-url]

**runZero.** The runZero Assets stream retrieves the Get/export/org/assets.jsonl call and the Asset schema. [uvm.data-sources:runzero-assets] The runZero Vulnerabilities stream retrieves the Get/export/org/vulnerabilities.jsonl call. [uvm.data-sources:runzero-vulns] The runZero Assets source authenticates with a client ID and client secret from API Clients and an organization ID, found with GET /account/orgs after authorizing with OAuth2 clientCredentials. [uvm.data-sources:runzero-auth]

**SecurityScorecard.** The SecurityScorecard Alerts source has a Username field for the user that receives the relevant notifications. [uvm.data-sources:ss-pages] The SecurityScorecard source has Identifier and Category retrieval fields. [uvm.data-sources:ss-fields]

**SFTP.** The SFTP stream retrieves files from any remote server that supports SFTP, using a username, password and host (hostname or IP address). [uvm.data-sources:sftp] The SFTP source selects CSV or JSON files, takes an optional folder path (all relevant files if empty, so reports/2023 excludes reports/2024), a start date in YYYY-MM-DDT00:00:00Z format and a regex files pattern. [uvm.data-sources:sftp-filters]
