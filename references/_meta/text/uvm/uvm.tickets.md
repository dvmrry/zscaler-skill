# How UVM tickets work: the Tickets page, manual split and merge, automatic grouping rules, status buckets and ticket workflows (uvm.tickets)
Also called: uvm ticket; ticket drawer; grouping rules; ticket workflows; status bucket; locked ticket; resurface finding; split into a new ticket

A UVM ticket aggregates related findings into a single work item that can be fixed as one task, and can be dispatched to external work management platforms such as Jira or ServiceNow. [uvm.tickets:ticket-definition] A ticket's Severity Score is calculated from the severity scores of its findings (for example the highest or the average), and its Risk Mass is the sum of the findings' severity scores. [uvm.tickets:ticket-severity-risk-mass] A ticket's Remediation is the percentage of findings resolved within the ticket, based on those that are no longer detected by the sources; First Seen reflects the earliest detected finding in the ticket. [uvm.tickets:ticket-remediation-pct]

**Tickets page and drawer.** The Tickets page offers bulk actions on selected tickets: Update, Merge, Comment and Create 3rd party Issue; the list can be exported as CSV. [uvm.tickets:ticket-bulk-actions] The actions available in the ticket drawer depend on the user's UVM role, and admins can configure the drawer, so it might look different in an account. [uvm.tickets:ticket-drawer] In the ticket details drawer the owner is set from the Owner drop-down on the Details tab, comments are added on the Comments tab, and status is changed with the arrow next to the status progress bar. [uvm.tickets:drawer-edits] Ticket comments can be used to update the team on changes to a ticket, such as splitting findings from it, a change of assignee or a change of severity score. [uvm.tickets:comment-purpose]

## Manual grouping

Manual ticket grouping requires a role with Read, Create and Edit permissions under the Vulnerabilities App - Ticket Operational View resource. [uvm.tickets:manual-grouping-permission] Manual split and merge are unavailable for tickets that have exception requests and become available again when all the ticket's exception requests are closed or in a Closed status bucket; users with the Exceptions - Audit permission can still split and merge. [uvm.tickets:split-merge-blocked-by-exception]

**Split.** Splitting findings creates one new ticket or a separate ticket per finding, titled with a sequential number suffix when several are created; the original ticket is listed on the new ticket's Related Tickets tab, and selecting more than 20 findings uses Select all <#> rows. [uvm.tickets:split-findings] When findings are split from a ticket linked to an external case management issue, the original ticket's link is not affected and the new ticket is not linked; splitting is only possible if at least one finding remains in the linked ticket or the link is detached, and updating the external issue on manual grouping requires configuration by Zscaler Support. [uvm.tickets:split-external-link]

**Merge.** Tickets cannot be merged if more than one of them is linked to an external case management issue (such as a Jira issue); when at most one is linked, the other tickets are merged into the linked ticket. [uvm.tickets:merge-external-link]

**Result.** A ticket created by manual grouping is locked: it is not updated with new findings and its findings are not automatically grouped with other tickets, though manual grouping actions can still be performed on it; locked tickets show a Lock icon. [uvm.tickets:locked-scope] A manually grouped ticket's assignment, scoring, SLA and other attributes follow the same logic as automatically grouped tickets in the account. [uvm.tickets:manual-attributes] All manual adjustments made to tickets are saved in the ticket's activity log on the Activity tab. [uvm.tickets:manual-activity-log]

## Automatic grouping rules

On initial account setup grouping rules include a default active ruleset; only one ruleset can be active, and activating a new ruleset deactivates the active one. [uvm.tickets:default-ruleset] Every grouping ruleset includes a default fallback rule for findings that match no conditions; it can be edited but not removed or deleted, and a new ruleset needs at least one rule in addition to it. [uvm.tickets:fallback-rule] A grouping ruleset can be activated, cloned, edited or deleted, and the rules in it can be cloned, edited or deleted, except that the default fallback rule cannot be removed; changes to the grouping apply to the account once the updated ruleset is activated. [uvm.tickets:ruleset-actions]

**Rule parts.** A grouping rule has an If condition (a filter selecting findings), a Then action that aggregates findings into a single ticket if they have matching values in all selected fields, and a Define Ticket Title By setting; conditions can be combined with AND (all) or OR (any). [uvm.tickets:rule-components] One ticket is created per unique combination of the Group By field values; for example grouping by Asset Type with two findings on Server assets and three on Workstation assets yields two tickets, and adding Asset OS creates a ticket per unique Asset Type and Asset OS combination. [uvm.tickets:group-by-combination] Ticket titles are set by Smart Text (free text plus field names as tokens in double curly brackets) or by an Expression that applies custom value transformations. [uvm.tickets:title-methods]

**Order and activation.** Rules in a grouping ruleset run sequentially in order of appearance: a finding is aggregated by the first rule that applies, otherwise by the default fallback rule; order is changed by dragging. [uvm.tickets:rule-order] Saving a ruleset does not reaggregate tickets; an active ruleset takes effect on Run or the next data processing in the account, an inactive one changes nothing until activated and run, and Save & Activate applies it immediately. [uvm.tickets:save-activate-run] The rule Preview showing No findings match filter condition can mean the filters need adjusting or that a previous rule already applies to the findings, since grouping depends on rule order. [uvm.tickets:preview-empty]

## Ticket statuses and states

A ticket status bucket is a high-level container grouping tickets with similar states; buckets can carry Closed and Remediated labels that provide insight for metrics and calculations and allow viewing all closed tickets. [uvm.tickets:status-bucket] Only the most recently added status bucket or ticket status can be deleted, and a ticket status can be edited only when no ticket currently uses it. [uvm.tickets:status-edit-limits]

**State.** Ticket states are Active (at least one active finding), Inactive (all findings undetected, waiting to be confirmed as closed) and Archived (the ticket no longer contains any findings, for example after a grouping change or a merge). [uvm.tickets:states] Ticket status is set manually by the assignee or synced from an external case management system, whereas ticket state reflects whether the ticket has active findings detected in a recent scan, so a ticket can be Closed yet remain Active. [uvm.tickets:status-vs-state]

## Ticket workflows

Ticket Workflows has three primary categories (Ticket Status Management, Lock Ticket Scope Triggers and Auto-Dispatch to External Systems), shows default system logic on initial account setup, and requires Read, Create, Edit and Delete under the Vulnerabilities App - Ticket Settings resource. [uvm.tickets:workflow-categories] Automated ticket status workflows take precedence over manual status updates, so the system sets the workflow-defined status even if a user previously changed the status. [uvm.tickets:automation-precedence] Ticket Status Management and Lock Ticket Scope Triggers rules are processed sequentially and only the first matching rule applies, whereas Auto-Dispatch to External Systems evaluates all rules, so one ticket can dispatch to multiple destinations. [uvm.tickets:rule-evaluation] When workflows are currently managed through data unification, Unlink & Override enables local rule configuration. [uvm.tickets:workflow-save]

**Status management.** The Ticket Default Status applies to new tickets that meet no configured rule, and only statuses from non-closed and non-remediated buckets can be selected. [uvm.tickets:default-status] The Automatic Ticket Closure category closes tickets whose findings have all been undetected for a number of days, an optional condition (0 closes immediately), with a Ticket status is not condition that selects from the statuses in the Remediated or Closed buckets; findings count as Undetected per the source's Remediation Detection settings and, if enabled, Asset Aging settings. [uvm.tickets:auto-close] [gap:uvm.tickets:undetected-definition]

**Resurfaced findings.** The Resurface Finding - Create New Ticket category creates a new ticket that includes the resurfaced finding(s) when they remain active for the specified number of days; it starts a new remediation cycle so historical and MTTX measurements are tracked separately, and it can create a ticket even if the original ticket has an exception request. [uvm.tickets:resurface-new-ticket] The Resurface Finding - Create New Ticket rule is triggered even if only one finding is active for the specified number of days. [uvm.tickets:resurface-trigger] The Resurface Finding - Reopen Ticket category moves a closed ticket to a selected status when a finding becomes active again for the configured days, tracking it on the original ticket with the original assignment. [uvm.tickets:resurface-reopen] The same ticket status cannot be the input condition of both a Resurface Finding - Create New Ticket rule and any status-transition rule (Automatic Ticket Closure, Resurface Finding - Reopen Ticket or Custom Status Transition), so a trigger event has one outcome. [uvm.tickets:status-exclusivity]

**Lock and dispatch.** By default, manually splitting or merging a ticket locks its scope; that Lock Ticket Scope Triggers condition is selected by default and cannot be changed, and the THEN of locking the ticket also cannot be changed. [uvm.tickets:lock-scope] Auto-Dispatch to External Systems rules optionally select tickets by severity and assignee, and create an item through a configured outegration. [uvm.tickets:auto-dispatch]
