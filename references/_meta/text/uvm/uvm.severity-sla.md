# How UVM calculates severity scores, maps them to severity categories and sets SLAs (uvm.severity-sla)
Also called: uvm severity score; uvm sla; uvm severity categories; base score risk and mitigating factors; dynamic sla updates

UVM severity scores are calculated per finding from a base score (the initial value from the finding's score inputs, carrying most of the weight) plus risk and mitigating factors; risks such as public access raise the severity score, while mitigating factors such as firewalls lower it. [uvm.severity-sla:score-model]

**Score calculation.** Base score factors and risk and mitigating factors are calculated separately and the two results summed; the total score must be 100% or higher to save the score setting. [uvm.severity-sla:score-calc] If the total weight exceeds 100%, the risk and mitigating share is capped according to the base score percentage; for example raising the base score from 50% to 70% reduces the factors to 30%. [uvm.severity-sla:over-100] If risk and mitigating factors do not use their full allocated weight (for example a factor is null or not applicable to a finding), the unused portion is proportionally reallocated to the base score factors; in the documented example 10% unused moves the base score from 60% to 70%, CVSS gaining 6.67% and EPSS 3.33%. [uvm.severity-sla:under-100-realloc]

**Score settings.** The base score defaults to the factors CVSS, EPSS and the Original Severity Score received from a scanner; Zscaler recommends 60% for the base score and 40% for the mitigating score. [uvm.severity-sla:score-defaults] The severity score configuration page says the base score is most commonly configured to include the finding's CVSS and EPSS scores, typically a decimal value between zero and one, which are converted to a value on a scale from 1 to 10 by multiplying the decimal value by 10, and that the weighted base score is the sum of each base factor multiplied by its dynamically adjusted weight, on a 0 to 10 scale. [uvm.severity-sla:cvss-epss-scale] If all base score factors are null, the severity score is also null. [uvm.severity-sla:null-base] If the Original Severity Score is included in the base score with a weight of 0%, it receives the full weight as a fallback when all other base factors are null; if it is not included, no weight is reassigned to it. Its vendor-specific calculation methods are not incorporated into the UVM score calculation. [uvm.severity-sla:original-fallback] The weight assigned to risk and mitigating factors is capped based on the percentage remaining after the base score's weight is set (for example, 40% when the base score is assigned 60%); Boolean factors take weights for True, False and Else, and string factors take a weight per expected value. [uvm.severity-sla:factor-config] The score simulator takes numerical values for base factors and a drop-down value per risk factor (True, False, Else), and a risk factor with no value selected is counted as Else. [uvm.severity-sla:score-simulator] Admins can configure UVM score settings; if score settings are configured in the Data Model, the page prompts Unlink & Override. [uvm.severity-sla:score-admin]

**Severity categories.** Severity categories are Critical, High, Medium, Low and Info; each has a minimum score that is included and an optional maximum that is excluded, settings cannot be saved if there are gaps between ranges that are not assigned to a category, and severity ranges must be unique (non-overlapping) and ordered in ascending numerical value. [uvm.severity-sla:category-ranges] Severity settings require Read, Create and Edit under the Vulnerabilities App - Ticket Settings resource; severity categories apply on next processing of the finding or ticket, or immediately with Save & Run. [uvm.severity-sla:category-permission] A ticket's severity is derived from the severity categories of its findings; a ticket that includes a Critical finding is categorized Critical. [uvm.severity-sla:ticket-severity-derived]

**SLA settings.** SLA settings apply to either Findings or Tickets: with Findings the ticket SLA is calculated from the findings' SLAs (for example the earliest), with Tickets individual findings are not assigned SLAs. [uvm.severity-sla:sla-entity] For Tickets the default SLA start date can be a ticket date field or Third-Party Issue Created (when the ticket is dispatched to an external system); Dynamic SLA Updates, which recalculate deadlines when attributes such as severity or asset owner change, are not available when Third-Party Issue Created is the start date. [uvm.severity-sla:sla-start-date] The optional setting to calculate ticket SLA from active findings only keeps the SLA at its most recent value when all findings are inactive. [uvm.severity-sla:sla-active-only] Default SLA Rules are fixed-condition fallback rules, one per severity category, whose start dates and durations can be adjusted and which custom rules override when their conditions are met; a duration of 0 days applies no SLA and populates the SLA field with 'No SLA'. [uvm.severity-sla:sla-default-rules] In the documented example, with Ticket First Seen as the start date, a ticket first seen on October 1 with an SLA duration of 10 days has its SLA due on October 11. [uvm.severity-sla:sla-due-date] Custom SLA rules take precedence over Default SLA Rules when their conditions are met, can be reordered by drag and drop, and can apply to a chosen severity category by selecting the severity checkbox; with AND the SLA applies only if all specified conditions are met, and the page says SLA rule conditions are not case sensitive. [uvm.severity-sla:sla-custom-rules] SLA settings apply next time the finding or ticket is processed, or immediately with Save & Run; Reset restores all SLA configuration to the original system-defined values; SLA settings configured in the Data Model prompt unlink and override. [uvm.severity-sla:sla-save-reset]

Default weights and ranges are open [gap:uvm.severity-sla:score-defaults-unstated]. Default SLA durations are open [gap:uvm.severity-sla:sla-defaults-unstated].
