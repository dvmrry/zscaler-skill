# UVM outegrations: setup procedure, storage and streaming, Splunk, Teams and Email, and Tenable scan outegrations (uvm.outegrations)
Also called: outegration; outegrations; outegration wizard

**Freshservice setup.** On the Freshservice outegration page, setup starts at Configure > Outegrations, then Create and the vendor tile, which opens the Connect step. [uvm.outegrations:wizard-start] On the Freshservice outegration page, the Connect step takes, among its fields, a Display Name, Active, Domain and an Authentication that is an existing authentication or Create New; Test verifies the connection and Next advances to the Settings step once the test passes. [uvm.outegrations:connect-step] Ticketing outegrations are in [UVM ticketing outegrations (Jira, ServiceNow, Freshservice, Azure DevOps), the ServiceNow CMDB outegration, their webhooks and mapping](kb:uvm.outegrations.ticketing); sources are in [UVM data sources: shared connector facts, availability, and the Jira, Zscaler, Okta, Code42, NetBox, runZero, SecurityScorecard and SFTP connectors](kb:uvm.data-sources); the product is in [Unified Vulnerability Management (UVM): what it does with findings, and what can be automated](kb:uvm.overview).

**AWS S3.** The AWS S3 outegration sends data from Agentic SecOps Platform applications (e.g., UVM) to an S3 bucket, and each bucket needs a separate outegration configuration. [uvm.outegrations:s3-bucket] The AWS S3 outegration exports scheduled reports or dispatches items to S3 when criteria are met, and its steps are Connect, Settings and Configure Reports or Define Dispatch Criteria. [uvm.outegrations:s3-steps] The AWS S3 outegration role needs s3:PutObject, s3:AbortMultipartUpload and s3:ListMultipartUploadParts, and the example policy also grants s3:ListBucket. [uvm.outegrations:s3-perms] The AWS role trust policy must allow Zscaler's service principal to assume the role, with the ARN obtained from Zscaler Support and an sts:ExternalId condition; the details to retrieve include Role ARN, External ID, Region and Bucket. [uvm.outegrations:s3-trust]

**Google Cloud Storage.** The GCP Storage outegration is a report delivery method that dispatches files from SecOps applications (e.g., UVM) to a Google Cloud Storage bucket, and its name then appears in each report's Delivery Method menu. [uvm.outegrations:gcs-purpose] The GCS service account needs the Storage Object Creator and Storage Legacy Bucket Reader roles for the bucket, or at project level for write access across buckets in one project. [uvm.outegrations:gcs-perms] The GCP Storage outegration takes a bucket, a project ID, an optional path; a JSON key file is generated on the Service Accounts page in the Google Cloud console; Test verifies the connection and shows an error with remediation steps if credentials are invalid. [uvm.outegrations:gcs-fields]

**Apache Kafka.** The Kafka outegration publishes entity data from SecOps applications to an external Kafka topic, which must be created beforehand for each outegration. [uvm.outegrations:kafka-purpose] In the Kafka outegration setup, the SecOps entity that triggers the Kafka dispatch is set (e.g., ticket, policy violation). [uvm.outegrations:kafka-entity] Kafka outegration authentication is mutual TLS: the client private key is RSA-2048 (exactly 2048 bits) or ECDSA (256, 384 or 521 bits) in PEM format, optionally encrypted; an item is required only if the generated client private key is encrypted; the client certificate chain and the broker CA certificate (needed for a private CA) are PEM. [uvm.outegrations:kafka-mtls] The Kafka outegration publishes via transactions for exactly-once behavior, so the isolation level must be explicitly set to isolation.level=read_committed; otherwise consumers may read messages from rolled-back transactions. [uvm.outegrations:kafka-isolation] The Kafka cluster ACL rules must allow the transaction ID zscaler-producer-transactional, and the page's example ACL commands use WRITE and DESCRIBE operations and IDEMPOTENT_WRITE. [uvm.outegrations:kafka-acl] In Internet & SaaS network configuration, port 9094 is the only authorized port open to all IP addresses for Kafka traffic; other ports are requested from Zscaler Support. [uvm.outegrations:kafka-port] The Kafka outegration's Bootstrap Servers are entered in host:port format, with the page's example using port 9092 (e.g., kafka-broker1:9092). [uvm.outegrations:kafka-bootstrap] Port [divergence:uvm.outegrations:kafka-port-example]. The record value schema, message key and topic partitioning are open [gap:uvm.outegrations:kafka-record-shape].

**Splunk.** The Splunk outegration sends data from Agentic SOC to Splunk as a Splunk security incident, needs an HTTP Event Collector token and the port number if the HTTP Event Collector listens on a port, and has four steps ending in incident dispatch criteria. [uvm.outegrations:splunk] After the Splunk outegration is set up, Agentic SOC dispatches incidents to Splunk when certain criteria are met and dispatch runs can be viewed in the outegration's activity log. [uvm.outegrations:splunk-activity]

**Microsoft Teams.** The Microsoft Teams outegration sends exposure and remediation notifications into Teams. [uvm.outegrations:teams-purpose] The Teams outegration uses a multitenant Entra ID app registration with redirect URI https://app.avalor.io/oauth and Microsoft Graph delegated permissions ChannelMessage.Send, offline_access and Channel.ReadBasic.All. [uvm.outegrations:teams-app] The Teams Get link to channel URL contains the group ID and channel ID; in the page's example the channel ID is 19%3A7mtmyDCaMAD1h1tFFlWACNkFhW_m3ga7_4GnTobaOVU1%40thread.tacv2 and the group ID is 02ce587c-6d8b-4e69-87bd-8dfe827cadeb. [uvm.outegrations:teams-ids] The Teams outegration details are Display Name, Active (use in automation workflows), Group ID, Channel ID and an Authentication that shows a unique Authentication ID when successful. [uvm.outegrations:teams-fields]

**Email.** The Email outegration sends email notifications from the Agentic SecOps Platform to specified recipients; Recipients take email addresses (Enter for multiple), and Active controls use in automation workflows. [uvm.outegrations:email] The Email outegration maps data to email fields (e.g., Subject, Body or Recipients), any of which can be set mandatory, and the primary entity to create the email for is selected. [uvm.outegrations:email-mapping] Recipient limits, sender address and delivery format are open [gap:uvm.outegrations:email-limits].

**Tenable scans.** The Tenable scanner outegration triggers on-demand scans for specific assets from the SecOps platform, supports Tenable Vulnerability Management and Tenable Security Center, and is currently supported only for UVM. [uvm.outegrations:tenable-purpose] Using the Tenable outegration requires a role with Create and Edit permissions under the Vulnerabilities App - Asset Outegrations resource. [uvm.outegrations:tenable-role] The Tenable scanner outegration can trigger scans only on assets already managed in the platform, so the matching Tenable data source must be configured and actively ingesting assets. [uvm.outegrations:tenable-datasource] Tenable source credentials can be reused for the Tenable outegration, but the source connector requires only View permissions while the scanner outegration requires Scan permissions. [uvm.outegrations:tenable-creds] The Tenable Security Center outegration needs the instance base URL and API keys of a user able to create and launch scans; a gateway connection is requested through a support ticket, and Skip SSL and Gateway are marked Tenable Security Center only. [uvm.outegrations:tenable-sc-params] Tenable Vulnerability Management scan settings include a scan name (a system default is used if left blank), a maximum number of concurrent scans (default 1), a scan template populated from the connected instance and a folder (the main folder if left blank). [uvm.outegrations:tenable-settings-tvm] Tenable Security Center scan settings include a maximum number of concurrent scans (default 1), a Scan Policy populated from the connected instance, a Repository for results and an optional Proxy DNS. [uvm.outegrations:tenable-settings-sc] The default Tenable outegration mapping targets assets by IP address, passing the IP addresses of the selected assets to Tenable as targets, and can be customized to another field such as tags. [uvm.outegrations:tenable-mapping]

What to check:
1. Which Kafka port the outegration uses, since the page's authorized port and its bootstrap example differ.
2. Whether the Kafka consumer sets isolation.level=read_committed.
3. Whether the Tenable credentials carry Scan permissions, not only the View permissions of the source connector.

Sources disagree (name both sides):
- The Kafka outegration page names port 9094 as the only authorized port, while its Bootstrap Servers example uses port 9092. [divergence:uvm.outegrations:kafka-port-example]
  - zscaler-help: Port 9094 is the only authorized port open to all IP addresses for Kafka traffic.
  - zscaler-help: The bootstrap endpoint example uses port 9092.
  Impact: The example may be a format illustration; the page does not say whether 9092 is usable.
