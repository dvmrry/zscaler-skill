# Private Access isolation policy: when private application requests go to isolation, and what else they need (zbi.private-access-isolation)
Also called: zpa isolation policy; isolation policy rule; zpa cloud browser isolation; isolate private app; bypass isolation; zpa isolation timeout; zpa_policy_isolation_rule

Private Access isolation policy rules define when application requests are redirected to isolation; they require isolation to be enabled for the organization and an isolation profile to exist before the rule is set up. [zbi.private-access-isolation:purpose] Zscaler describes isolation policy as giving clientless access to critical applications through a containerized isolated browser so that the posture of the user's machine does not affect the applications, and as enforcing exfiltration controls that stop copy, paste, upload and download between the user's computer and the application. [zbi.private-access-isolation:clientless-access]

**Two policies.** Besides an isolation policy, an access policy must be defined for the application to be reachable from within the isolation environment; requests not directed to isolation are reviewed against access policies. [zbi.private-access-isolation:access-policy-too] What a user sees when the isolation rule matches but access policy denies the application is open [gap:zbi.private-access-isolation:isolated-but-denied].

**Rules.** A request must match all the conditions within an isolation rule, and isolation rules use only the AND and OR operators. [zbi.private-access-isolation:criteria-logic] Private Access applies isolation rules in the order listed on the Isolation Policy page, and the rule order can be changed by entering a new number. [zbi.private-access-isolation:rule-order] An isolation rule's action either allows or bypasses isolation. [zbi.private-access-isolation:rule-action] The isolation policy has a default rule that cannot be edited. [zbi.private-access-isolation:default-rule] The default rule's place in Private Access evaluation: [If no isolation rule matches, Private Access applies the default isolation policy rule.](kb:zpa.policy.evaluation-order:default-isolation). The wire actions are ISOLATE and BYPASS_ISOLATE: [A policy inspection rule needs zpn_inspection_profile_id when its action is INSPECT; inspection rule actions are INSPECT or BYPASS_INSPECT, and isolation rule actions are ISOLATE or BYPASS_ISOLATE.](kb:zpa.terraform.policy-rule-resources:inspection-profile-required-for-inspect).

**Criteria.** Whether a posture profile can be a criterion is disputed between sources: [zpa.posture-profiles.policy-operand:posture-isolation](kb:zpa.posture-profiles.policy-operand:posture-isolation). Whether SCIM operands are accepted is open: [Whether isolation rules accept SCIM_GROUP and SCIM operands](kb:zpa.scim.policy-criteria:zpa-68-isolation-scim).

**Configuring a rule.** An isolation rule's Rule Action is Allow Isolation or Bypass Isolation, and the isolation profile field is required when the Rule Action is Allow Isolation. Isolation rules implement controls based on isolation profiles. [zbi.private-access-isolation:rule-action-values] The Web Browser client type is required for isolation policy rules, it is the only client type available, and it is preselected for the rule. [zbi.private-access-isolation:web-browser-only] The Client Connector Posture Profiles, Client Connector Trusted Networks and Machine Groups criteria may appear in the drop-down menu, but the page says they are not supported with the Web Browser client type, which is required for isolation policies. [zbi.private-access-isolation:unsupported-criteria] The isolation rule page lists External IAM IdP, Applications (segments and segment groups), Chrome Enterprise Browser with an optional configured Chrome posture profile, Client Connector Posture Profiles, Client Connector Trusted Networks, Machine groups and Platforms as criteria. The SAML and SCIM Attributes criteria cannot be configured with the Cloud Connector Group criteria, and multiple Cloud Connector groups in a rule are joined by AND. [zbi.private-access-isolation:rule-criteria] An isolation rule name cannot contain special characters, with the exception of periods, hyphens and underscores. [zbi.private-access-isolation:name-characters] Which criteria isolation rules actually accept is open [gap:zbi.private-access-isolation:accepted-criteria].

**Session timeout.** Once the user is authenticated, the isolation session timeout is the minimum timeout across all configured timeout policies, after which the user must reauthenticate with Private Access to reach applications through isolation. [zbi.private-access-isolation:session-timeout] How this interacts with the container idle timeout is open [gap:zbi.private-access-isolation:timeout-vs-idle]. During a Private Access maintenance period, isolation might not be available. [zbi.private-access-isolation:maintenance]

**Forwarding internet traffic.** The forwarding article states that an isolation browser initiated from Private Access policies can send traffic only via Private Access. [zbi.private-access-isolation:pa-only-traffic-statement] Applications defined in Private Access are forwarded via the Private Access client on the isolation container and traffic not defined as a Private Access application is sent directly to the internet, which the article says creates a gap in the organization's security policies. [zbi.private-access-isolation:default-forwarding-gap] Zero Trust Browser supports sending non-private application traffic via Internet & SaaS even when the isolation session starts from a Private Access policy; the feature is enabled per Private Access isolation profile. [zbi.private-access-isolation:forward-via-zia-option] The Private Access profile setting Forward Internet Traffic via Internet & SaaS (Company Settings tab), when enabled, takes a Cloud Name | Organization ID and a recommended or custom PAC file URL; for remote users on Z-Tunnel 1.0 the Enable Firewall for Z-Tunnel 1.0 and PAC Road Warriors option in Advanced Settings applies firewall rules to traffic forwarded using dedicated IP addresses. [zbi.private-access-isolation:forward-profile-settings] Forwarding private application traffic via Internet & SaaS lets DLP and security policies apply to it and lets Internet & SaaS provide connectivity to the private applications through the Source IP Anchoring route. [zbi.private-access-isolation:forward-dlp-sipa] The User Portal article describes private application traffic differently [divergence:zbi.private-access-isolation:private-app-traffic-path].

**SaaS applications from unmanaged devices.** The User Portal is a portal where users see a catalog of all published private and SaaS applications published via Private Access Browser Access. [zbi.private-access-isolation:user-portal-catalog] To isolate a SaaS application whose domain the organization does not own, the admin defines a Private Access application segment with an application using a placeholder domain, configured for browser access; the URL is rewritten to its full extent when pushed into isolation. [zbi.private-access-isolation:saas-placeholder-domain] The isolation profile selected for the SaaS isolation policy must have Forward Internet Traffic via Internet & SaaS enabled under Company Settings; otherwise the SaaS traffic from the isolated browser is not forwarded via Internet & SaaS and is not inspected, logged or enforced by its policies. [zbi.private-access-isolation:saas-forward-option-required] From an unmanaged device, accessing the placeholder domain prompts authentication with the Private Access IdP, then redirects to an isolation session where the user authenticates to Internet & SaaS before the isolated browser reaches the original SaaS URL. [zbi.private-access-isolation:saas-auth-flow]

**Automation.** The Python SDK requires a profile ID only for the isolate action: [The Python `add_isolation_rule` requires `zpn_isolation_profile_id` when the action is isolate and checks nothing about the profile ID for other actions.](kb:zpa.policy.rule-fields:isolation-profile-required-for-isolate). The MCP server's isolation rule create tool raises an error when `action_type` is isolate and no `zpn_isolation_profile_id` is given, and creates the rule through the Python SDK's `add_isolation_rule_v2`. [zbi.private-access-isolation:mcp-create-requires-profile]

What to check:
1. Whether an access policy rule allows the application as well as the isolation rule sending it to isolation.
2. Which isolation rule matched first in rule order, or whether the uneditable default rule applied.
3. Whether the shortest configured timeout policy explains an unexpected reauthentication.

Sources disagree (name both sides):
- The forwarding article says private application traffic can be forwarded via Internet & SaaS (Source IP Anchoring route), while the User Portal article says traffic of applications defined on Private Access continues to be forwarded via Private Access's ZTNA service. [divergence:zbi.private-access-isolation:private-app-traffic-path]
  - zscaler-help: Zero Trust Browser can forward private application traffic via Internet & SaaS, which provides connectivity to the private applications via the Source IP Anchoring route.
  - zscaler-help: Traffic generated by applications defined on Private Access continues to be forwarded via Private Access's ZTNA service.
  Impact: An answer on which service carries private application traffic from an isolation session depends on which article is followed; the User Portal article may describe a different flow, which neither page settles.
