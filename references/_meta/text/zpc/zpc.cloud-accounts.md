# How ZPC cloud accounts and organizations are onboarded: AWS, Azure, GCP and OCI (zpc.cloud-accounts)
Also called: ZPC onboarding; onboard cloud account ZPC; ZPC organizations tab; ZPC OCI onboarding; ZPC write access

ZPC treats AWS accounts, Microsoft Azure subscriptions and GCP projects as cloud accounts, and AWS Organizations, Microsoft Azure tenants and GCP Organizations as organizations; multiple cloud accounts can be assigned to a business unit. [zpc.cloud-accounts:terms] The hub is [What Zscaler Posture Control (ZPC) is to administer: portal access, setup order, notifications and audit logs](kb:zpc.overview).

**Onboarding.** Onboarding cloud accounts establishes the integrations ZPC needs to collect configuration and identity metadata, and multiple accounts from any cloud service provider can be onboarded. [zpc.cloud-accounts:onboarding-purpose] The Accounts tab shows Write Access (whether remediation is enabled), Vulnerability Scan (whether scanning is configured), Status and Onboarded Date among its columns. [zpc.cloud-accounts:accounts-tab-columns] The cloud account, organization and Kubernetes exports are Excel files named Cloudaccounts_(timestamp), Organizations_(timestamp) and Kubernetes_(timestamp). [zpc.cloud-accounts:excel-export-names] The Organizations tab column Onboarded Accounts shows the onboarded and total number of cloud accounts in the organization. [zpc.cloud-accounts:org-onboarded-count] An organization can be deleted together with all the accounts in the organization. [zpc.cloud-accounts:org-delete] Business units that hold the accounts are in [Who can do what in ZPC: administrators, groups, roles, modules, business units and API keys](kb:zpc.roles), and cluster onboarding is in [How ZPC onboards and offboards EKS, AKS and GKE clusters, including private GKE and AKS local authentication](kb:zpc.kubernetes).

**Vulnerability scanning.** Vulnerability scanning of cloud workloads and cloud container registries needs permissions that ZPC grants through an automation script run on the cloud provider, started from Add Vulnerability Scanning. [zpc.cloud-accounts:vuln-scan-script] The scanning subject is [How Posture Control vulnerability scanning works: integrations, scanning rules, supported systems and the Vulnerability Management page](kb:zpc.vulnerability-scanning).

**AWS.** Onboarding an AWS account or organization requires access to the administrative AWS management account and being a ZPC administrator. [zpc.cloud-accounts:aws-prereqs] AWS onboarding uses an initial script and an onboarding script that run on AWS Cloud Shell, and supports onboarding an AWS organization or a single AWS cloud account. [zpc.cloud-accounts:aws-two-scripts] The AWS initial script creates a role named ZPC-ORG-${TENANT_HASH} and grants it the AWSOrganizationsReadOnlyAccess policy via sts:AssumeRole depending on an sts:ExternalId. [zpc.cloud-accounts:aws-initial-script] The AWS onboarding script checks it was run by the root user of the AWS management account, assigns AdministratorAccess and AWSOrganizationsFullAccess to the helper user, and creates a CloudFormation Stack and StackSet named ZPC-ORG-${TENANT_HASH} and a helper user zpc-onboarding-helper-${TENANT_HASH}. [zpc.cloud-accounts:aws-onboarding-script] ZPC creates the ZPCCustom role on all selected AWS accounts through the CloudFormation Stack and StackSet, or only the ZPCCustom role when onboarding a single AWS account, and assigns it the SecurityAudit managed policy. [zpc.cloud-accounts:aws-zpccustom-role] If CloudTrail is enabled, the role is assigned ZPCCloudTrailS3Access (including s3:GetObjectAcl) and ZPCCloudTrailS3AccessList (s3:ListBucket). [zpc.cloud-accounts:aws-cloudtrail-policies] If vulnerability scanning is enabled, the role gets Workloads permissions ec2:CreateSnapshot*, ec2:CreateTags, ec2:CopySnapshot, ec2:ModifySnapshotAttribute, kms:Decrypt, kms:Encrypt, kms:ReEncrypt*, kms:CreateGrant, kms:GenerateDataKeyWithoutPlaintext, kms:PutKeyPolicy and ec2:DeleteSnapshot. [zpc.cloud-accounts:aws-vuln-workload-policies] If vulnerability scanning is enabled, the role gets Containers permissions ecr:GetAuthorizationToken, ecr:ListImages, ecr:BatchGetImage, ecr:DescribeImages, ecr:DescribeRepositories, ecr:GetRepositoryPolicy, ecr:BatchCheckLayerAvailability, ecr:GetDownloadUrlForLayer and ec2:DescribeRegions. [zpc.cloud-accounts:aws-vuln-container-policies] Connecting AWS CloudTrail S3 buckets to ZPC is described as a mandatory step after onboarding AWS cloud accounts. [zpc.cloud-accounts:aws-cloudtrail-mandatory] ZPC detects the CloudTrail buckets configured for onboarded AWS accounts, may find multiple buckets for one account, and displays all of them for each account. [zpc.cloud-accounts:aws-cloudtrail-buckets] For CloudTrail S3 buckets encrypted with a KMS key, kms:Decrypt must be assigned to the ZPCCustom role and the key policy must be modified, adding the ZPCCustom role for each member account when an AWS organization is onboarded. [zpc.cloud-accounts:aws-cloudtrail-kms] The page tells the reader to add the S3 service and the bucket region in the kmspolicy section of the policy; its example kmspolicy statement names the services logs.us-east-2.amazonaws.com, cloudtrail.amazonaws.com, s3.<Bucket Region>.amazonaws.com and dynamodb.amazonaws.com. [zpc.cloud-accounts:aws-cloudtrail-kms-service] Write access allows the cloud service provider to remediate alerts generated for the cloud account; once the deploy script is run, the Write Access column changes from N/A to Enabled. [zpc.cloud-accounts:aws-write-access] Write access for an AWS account is disabled at the policy level on AWS by removing the zpc-remediation-policy from the account's IAM role. [zpc.cloud-accounts:aws-write-access-disable] On the Accounts tab, Add Write Access and Manage CloudTrail are listed under the Amazon Web Services actions. [zpc.cloud-accounts:aws-actions-aws] The custom policy list on the page is open [gap:zpc.cloud-accounts:aws-custom-policies]. Whether other providers have write access is open [gap:zpc.cloud-accounts:write-access-beyond-aws].

**Azure.** Onboarding an Azure account requires being a ZPC Administrator and a Microsoft Azure Global Administrator (needed only for onboarding and revocable afterwards), access to the Root Management Group, and an Azure Active Directory premium (P1) license to view identity information in ZPC. [zpc.cloud-accounts:azure-prereqs] Before onboarding, all Azure subscriptions must be made accessible by toggling Access management for Azure resources to Yes and signing out and back in to Azure. [zpc.cloud-accounts:azure-access-management] After Azure onboarding the Cloud Accounts page shows Success when onboarding worked and metadata is collected, and Role/Resource not Found if there are issues or no resources are found in the Azure account. [zpc.cloud-accounts:azure-status] The Azure initial script creates the custom role CSP_READ_ORG with Microsoft.Management/managementGroups/descendants/read, and a service principal ZPC_${TENANT_HASH} that gets Management Group Reader, Key Vault Reader and CSP_READ_ORG. [zpc.cloud-accounts:azure-initial-script] The Azure onboarding script creates a custom role ZPC-${TENANT_HASH} whose Actions are */read, Microsoft.Compute/disks/read and Microsoft.Compute/virtualMachines/read, and whose NotActions are the blobServices, fileServices and queueServices read operations of storage accounts. [zpc.cloud-accounts:azure-onboarding-script-role] With vulnerability scanning permissions granted, the Azure custom role also gets the Microsoft.Compute/snapshots actions beginGetAccess/action, endGetAccess/action, read, write and delete. [zpc.cloud-accounts:azure-vuln-actions] The page says the onboarding script creates a service principal and that its credentials expire in one year, and ZPC continues metadata collection for the Azure account only after new credentials are provided in the ZPC Admin Portal. [zpc.cloud-accounts:azure-credential-expiry] The page resets the service principal credentials with az ad sp credential reset, whose example sets --years=2. [zpc.cloud-accounts:azure-credential-reset] The service principal ID is found by display name ZscalerCollector-, or by display name ZPC_ for cloud accounts onboarded after January 2023. [zpc.cloud-accounts:azure-sp-name] The Azure page lists these Microsoft Graph roles with IDs: Application.Read.All, AuditLog.Read.All, Directory.Read.All, Reports.Read.All and UserAuthenticationMethod.Read.All. [zpc.cloud-accounts:azure-graph-roles] The Azure page lists these Azure Active Directory Graph roles with IDs: Azure Active Directory Graph, Directory.Read.All and Policy.Read.All. [zpc.cloud-accounts:azure-aad-graph-roles] What lifetime a reset grants is open [gap:zpc.cloud-accounts:azure-credential-lifetime]. What the Graph role tables are assigned to is open [gap:zpc.cloud-accounts:azure-graph-tables].

**GCP.** Onboarding a GCP account requires being an administrator, having the GCP owner role, and having the Cloud Assets API enabled on all GCP projects. [zpc.cloud-accounts:gcp-prereqs] The GCP initial script enables API services for ZPC on each selected project, including cloudresourcemanager and orgpolicy. [zpc.cloud-accounts:gcp-initial-script-apis] The GCP initial script creates a service account ZPC-${TENANT_HASH} in the project where it is run and binds roles/browser, roles/iam.organizationRoleViewer and roles/resourcemanager.folderViewer at the organization level, plus roles/iam.serviceAccountTokenCreator and roles/iam.securityReviewer on the ZPC service account. [zpc.cloud-accounts:gcp-initial-script-sa] The GCP onboarding script grants roles/viewer, roles/cloudasset.viewer, roles/bigquery.dataViewer and roles/actions.Viewer for the organization, folders or projects, and creates a custom role ZPC_${TENANT_HASH} with the storage.buckets.get permission. [zpc.cloud-accounts:gcp-onboarding-script] With vulnerability scanning enabled, the GCP service account additionally gets roles/containerregistry.ServiceAgent and roles/cloudkms.cryptoKeyEncrypterDecrypter. [zpc.cloud-accounts:gcp-vuln-roles] After the GCP script runs, clicking Grant Consent to Service Account allows the service account to collect configuration and identity metadata. [zpc.cloud-accounts:gcp-grant-consent] The full API list is open [gap:zpc.cloud-accounts:gcp-api-list].

**OCI.** For OCI, ZPC generates a Terraform template that creates a user and group, creates a new policy allowing the group to read all resources in the tenancy, assigns the user to the group, adds a public key as the user's API key, and returns the user OCID. [zpc.cloud-accounts:oci-terraform] OCI onboarding takes a Tenancy OCID (the root compartment ID), Home Region, User Name, Group Name and Policy Name; the ZPC Alias is optional and defaults to the OCI tenant name. [zpc.cloud-accounts:oci-inputs] For OCI onboarding, a previously created user name and group name can be entered but the user must not be assigned to the group, and an existing policy cannot be used so a new policy name must be provided. [zpc.cloud-accounts:oci-reuse-rules] After running the Terraform template on OCI, the User OCID taken from the oci_identity_user output is entered on the Download Template page in ZPC. [zpc.cloud-accounts:oci-user-ocid] The OCI actions on the Organizations tab are Provide User OCID (the Terraform output), Provide Tenancy OCID (root compartment, used to generate the template), and Download the Template. [zpc.cloud-accounts:oci-org-actions]
