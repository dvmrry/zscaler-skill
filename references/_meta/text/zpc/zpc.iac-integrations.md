# How each ZPC IaC Scan version control and CI/CD integration is set up and behaves (zpc.iac-integrations)
Also called: Version Control & CI/CD Systems; Fail Check Criteria; Scan on Push; Zscaler IaC Scan plugin

The About IaC Integrations article describes the Version Control & CI/CD Systems list as showing each integration's name, type, selected repository count, integration status (given there as Success or Pending) and the email of the user who created it. [zpc.iac-integrations:integration-list-fields] The repository details show repository name, status (Private or Public), default branch, whether Scan on Push is On or Off, whether Fail Check Criteria is applied to all repositories, and an action to delete the repository. [zpc.iac-integrations:repository-detail-fields] TeamCity and Circle CI are covered as other CI/CD tools. [zpc.iac-integrations:supported-platforms] The scan itself is in [What ZPC IaC Scan covers: entitlement, supported templates and operating systems, Bicep, skipping policies, disabling and alert status](kb:zpc.iac-scanning); the hub is [What Zscaler Posture Control (ZPC) is to administer: portal access, setup order, notifications and audit logs](kb:zpc.overview). Whether the service is still available is open [gap:zpc.iac-integrations:service-status].

**GitHub.** On GitHub, organization administrators must install and authorize the Zscaler IaC Scan app; after that any user with the required permissions can enable specific repositories for scanning in the ZPC Admin Portal. [zpc.iac-integrations:github-prereq] For GitHub, the app scans Terraform, Kubernetes, Helm, ARM and CloudFormation templates, and Scan on Push scans the default (main/master) branch. [zpc.iac-integrations:github-scan-triggers] On GitHub, Fail Check Criteria applies only to pull requests, takes a Critical, High, Medium or Low threshold per repository, and the alert notification is generated in both scenarios of the page example. [zpc.iac-integrations:github-fail-check] Include Paths restricts scanning to the given file or folder paths (a single-file path scans only that file) and accepts regular expressions; the regex table on the GitHub page includes ! to exclude matches, at the start of a pattern only. [zpc.iac-integrations:github-include-paths] Zscaler recommends selecting All repositories so subsequent repositories are automatically added to the list in the ZPC Admin Portal, but specific repositories still have to be chosen for scanning. [zpc.iac-integrations:github-all-repos]

**GitLab.** Only one GitLab integration can be configured per tenant, and an administrator with an owner role onboards GitLab accounts and authorizes the IaC Scan app. [zpc.iac-integrations:gitlab-single-integration] For GitLab, scans cover Terraform, Helm, Kubernetes and CloudFormation templates, and Fail Check Criteria applies only to merge requests. [zpc.iac-integrations:gitlab-templates-and-fail-check] A GitLab integration that stops working (for example, the app was unauthorized in GitLab or the token is corrupted in the ZPC Admin Portal) shows Integration Status Failed and can be reauthorized instead of deleted; a successful reauthorization sets the status to Success. [zpc.iac-integrations:gitlab-reauthorize] For a failed GitLab integration, if you offboard the tenant or unsubscribe from the IaC entitlement, the integration is deleted from ZPC but the webhooks stay in the GitLab repository and must be deleted manually; otherwise you might not be able to integrate the account when you subscribe again. [zpc.iac-integrations:gitlab-webhooks]

**Azure Repos.** For Azure Repos, only the Azure DevOps organization owner can onboard the organization and accounts, and third-party application access via OAuth must be enabled under Application connection policies first. [zpc.iac-integrations:azure-repos-prereq] Azure Repos organizations are added one at a time; already-onboarded organizations cannot be selected, and several organizations in the same Azure account need the integration steps repeated. [zpc.iac-integrations:azure-repos-one-org] On Azure Repos, Fail Check Criteria applies only to pull requests; with criteria Critical and High and only Medium or Low violations, the pull request is not failed. [zpc.iac-integrations:azure-repos-fail-check] Branch protection with the Zscaler IaC Scan status check on Azure DevOps becomes available after the IaC scan has run once on a pull request. [zpc.iac-integrations:azure-repos-branch-protection] A failed Azure Repos integration (for example unauthorized in Azure DevOps or a corrupted token) shows Failed and can be reauthorized; for a failed integration, after tenant offboarding or unsubscribing, webhooks stay in the Azure repository and must be deleted manually. [zpc.iac-integrations:azure-repos-failed]

**Bitbucket.** Bitbucket integration scans IaC templates for both pull and push requests, can scan the entire repository of a branch or newly added templates, and only an administrator can install and authorize it. [zpc.iac-integrations:bitbucket-scope] Whether regular expressions apply on Bitbucket is open [gap:zpc.iac-integrations:bitbucket-regex].

**GitHub Actions.** For GitHub Actions the ZPC Admin Portal generates a Client ID and Client Secret Key shown only once, and Regenerate issues another secret; the repository secret names must also be given in the YAML configuration file. [zpc.iac-integrations:github-actions-credentials] On the GitHub Actions page, the parameters are: region, given there as US or EU (case sensitive); iac_dir optional, with the whole repository scanned if not specified; fail_build set to true or false. [zpc.iac-integrations:github-actions-parameters] The GitHub Actions output_format parameter supports json, yaml, sarif, human, json+github-sarif and human+github-sarif, and the action exposes sarif_file_path and scan_status (passed or failed). [zpc.iac-integrations:github-actions-output] The GitHub Actions action scans Terraform, Kubernetes, CloudFormation and ARM templates. [zpc.iac-integrations:github-actions-templates]

**Jenkins.** Jenkins needs Jenkins version 2.319.1 and an administrator to install and authorize the Zscaler IaC Scan plugin; it supports freestyle and pipeline jobs. [zpc.iac-integrations:jenkins-prereq] A Jenkins integration account shows as Pending until configuration is completed on the Jenkins UI, after which the status changes to Success and the Jenkins URL is displayed; the generated Client ID and Client Secret Key are displayed only once. [zpc.iac-integrations:jenkins-status-pending] In the Jenkins plugin configuration the environment is EU or US, and Validate confirms the connection between the Jenkins server and the ZPC Admin Portal. [zpc.iac-integrations:jenkins-environment] For Jenkins freestyle jobs, Fail Build is enabled by default and fails the job on high severity violations; if disabled, the plugin still identifies misconfigurations but does not fail the job. [zpc.iac-integrations:jenkins-fail-build] In a Jenkins pipeline script the plugin scans the entire repository by default; to scan a specific file or directory give a file path or a directory path, but not both; failBuild true fails the build on violations and false does not. [zpc.iac-integrations:jenkins-pipeline-scope] The pipeline failBuild default is open [gap:zpc.iac-integrations:jenkins-pipeline-failbuild-default].

**Jenkins report.** The Jenkins report is available for single and multibranch pipeline jobs and can be downloaded as CSV or PDF; an error message in it can be due to IaC resources not available, a parsing error, a scan not initiated, or a scan that failed to complete. [zpc.iac-integrations:jenkins-report] The Jenkins report shows project details, scan status (Passed, Failed, Skipped), the overall severity level (Critical, High, Medium, or Low), and for each policy its name, scan status, policy ID and severity. [zpc.iac-integrations:jenkins-report-fields]

**Azure Pipelines.** For Azure Pipelines the region is EU, US or Custom; if no IaC directory is given the entire repository is scanned; output format is JSON, YAML, SARIF or human; the account shows Pending until configuration completes in Azure DevOps. [zpc.iac-integrations:azure-pipelines-config] For Azure Pipelines the Client ID and Client Secret can be added to Azure Key Vault and referenced in the YAML pipeline; the plugin is downloaded from the Visual Studio Marketplace. [zpc.iac-integrations:azure-pipelines-keyvault] The Azure Pipelines plugin scans Terraform, Kubernetes, Helm, ARM and CloudFormation templates for Azure pipeline jobs. [zpc.iac-integrations:azure-pipelines-templates]

**Terraform Cloud.** Terraform Cloud scans the Terraform plan template each time a run task triggers; the post-plan task is enabled by default and pre-plan can be enabled instead. [zpc.iac-integrations:terraform-cloud-run-task] On Terraform Cloud, a mandatory Run task fails on violations matching the selected thresholds, while an advisory Run task does not fail even with violations. [zpc.iac-integrations:terraform-cloud-enforcement] Terraform Cloud integration requires a user API token, without which you cannot proceed; the token can be replaced later for reauthorization. [zpc.iac-integrations:terraform-cloud-token] Terraform Cloud organizations are added one at a time; already-onboarded organizations cannot be selected. [zpc.iac-integrations:terraform-cloud-one-org] For a failed Terraform Cloud integration, after tenant offboarding or unsubscribing from the IaC entitlement, the integration is deleted from ZPC but the runtasks stay in the Terraform workspace and must be deleted manually, or the organization may not be integrable on resubscribing. [zpc.iac-integrations:terraform-cloud-runtasks]

**Other CI/CD tools.** For TeamCity and Circle CI, a binary script (zscaler-iac-scan.sh) is downloaded as a ZIP file and must be decompressed before use; it covers Terraform, Helm, Kubernetes and CloudFormation templates. [zpc.iac-integrations:other-cicd-script] For TeamCity, the build step parameters must be given in the same sequence; if the sequence is changed, the script does not execute and shows an error. [zpc.iac-integrations:other-cicd-parameters] For the TeamCity script, the output format is human (default), JSON, YAML or GitHub-Sarif; entering true for Fail Build means code changes cannot be committed to the build until the errors are fixed. [zpc.iac-integrations:other-cicd-output]

The template lists differ between the pages [gap:zpc.iac-integrations:template-lists-differ].

What to check:
1. Fail Check Criteria on GitHub and Azure Repos applies only to pull requests, and on GitLab only to merge requests.
2. For a failed integration, after tenant offboarding or unsubscribing from the IaC entitlement, the webhooks stay in the GitLab and Azure repositories and the runtasks stay in the Terraform workspace, to be deleted manually.
