# How Posture Control alerts work: types, statuses, attributes, threat categories, alert rules, ignore filters and remediation (zpc.alerts)
Also called: ZPC alerts; Posture Control alerts; alert rules; ignore filters; cloud alerts; IaC alerts

ZPC alerts are Cloud Alerts (security policy violations in cloud resources at runtime) or IaC Alerts (misconfigurations in IaC infrastructure at build time), triaged by severity Critical, High, Low or Medium. [zpc.alerts:alert-types-severity] When the All Contributing Factors option is not selected in a Cloud Alerts export to Excel, only the first 15 aggregated findings are included. [zpc.alerts:export-contributing-factors] The Notifications tab lists alert rules with Alert Type (Cloud or IaC), Integration Type (ServiceNow, Jira, Amazon Security Lake, AWS S3, Azure Blob, or Slack) and State; a rule added without configured notifications shows State Saved. [zpc.alerts:notifications-tab] The Ignore Filters tab lists filters with Alert Type, Filter Scope, Created By, Updated By and an End Date, the date when the filter is going to be disabled. [zpc.alerts:ignore-filters-tab]

**Statuses.** ZPC alert statuses are Open, Closed, Resolved and Reopened; new alerts are Open, and ZPC grants Reopened automatically to a previously resolved alert. [zpc.alerts:status-values] Only resolved alerts can be reopened; closed alerts cannot be reopened. [zpc.alerts:status-reopen-rule] Cloud alerts are Closed when they are no longer valid, for example when the cloud account is deleted or offboarded, the policy is deleted or deprecated, the custom policy query is edited, or the cloud resource is deleted. [zpc.alerts:status-closed-cloud] IaC alerts are Closed when the IaC Scan app or integration is deleted, the IaC subscription expires or is removed, the repository is permanently deleted or unsubscribed, or the resource or branch is deleted. [zpc.alerts:status-closed-iac] Whether the Alert Status attribute sample is the full list is open [gap:zpc.alerts:alert-status-sample].

**Attributes and threat categories.** The Alert Age attribute is the number of days an alert was in Open status, and the Alert Source is ZPC so third-party systems can identify the product that generated the alert. [zpc.alerts:attr-id-age-source] Alert Status Description describes the transition of an alert from one status to another, with sample values Auto Resolved and Manually Deleted. [zpc.alerts:attr-status-description] The remediation attributes are Supports Remediation, Remediation Allowed, Remediation Initiated By (Zscaler if remediated automatically through alert management flow) and Remediation Status, with sample values Progress, Success, Failed and Blank. [zpc.alerts:attr-remediation] The Trusted IP attribute is True when the alert is publicly exposed and associated with a trusted IP list, False when publicly exposed but not associated, and - when not publicly exposed and not associated. [zpc.alerts:attr-trusted-ip] Identity Power Category applies only to identities with a power score of more than 80, and Identity Power Score is a numeric score (sample 1-100) based on an internal Zscaler IP calculation of power. [zpc.alerts:attr-identity-power] Azure Resource IDs are displayed in lowercase in the Resource ID attribute, regardless of the case in which they were created. [zpc.alerts:attr-azure-resource-id] IaC alert attributes include Template Type (sample Terraform, CFT, ARM, Kubernetes YAML, Helm charts), Scan Plugin (sample GitHub, GitLab, Jenkins, Azure Pipelines, GitHub Actions, Azure Repos, Terraform Cloud) and Scan Type (sample Push, Pull, Build); Branch is not applicable for CI/CD integration. [zpc.alerts:attr-iac-fields] The Policy Source attribute is Predefined or custom (sample Zscaler or Custom), and Theme is the security policy theme (sample Compliance, Security Exposure, Security Events or blank). [zpc.alerts:attr-policy] ZPC assigns each policy violation a threat category and severity; the categories include Account Takeover, Authentication Misconfiguration, Crypto mining, Dormant Accounts, External Exposure, Multilayer Attack Paths, Permission Misconfiguration, Privilege Escalation, Ransomware, Reconnaissance and Evasion, Security Events and Attack Vector, Security Exposure, Service Misconfiguration, Stale Data and Assets, and Suspicious Activity. [zpc.alerts:threat-categories] Whether Misconfiguration is a threat category is open [gap:zpc.alerts:misconfiguration-category]. In the Cloud Alert drawer, Timeline alert data is captured every 5 minutes and alert history is by default shown for the last month; some repository details are not displayed for Jenkins Pipeline scans in the IaC Alert drawer. [zpc.alerts:drawer-timeline]

**Alert rules.** Alert rules define the criteria for generating an alert notification; the criteria could be the occurrence of specific security events, such as policy violations or misconfigurations in cloud resources. [zpc.alerts:alert-rule-definition] ZPC sends alert notifications only when the alert rule is enabled, and a rule can be configured first and enabled later. [zpc.alerts:rule-enable-required] An alert rule needs onboarded cloud accounts or a completed IaC integration; ZPC sends email notifications to recipients and can send alert notifications and data to ITSM, cloud storage and ChatOps tools. [zpc.alerts:rule-prereq-channels] A cloud alert rule scope can be set by Business Units, Clouds (AWS, Azure or GCP), Accounts, Regions and Select Policy, with policies filterable by Compliance, Severity, Threat Category or Policy Type. [zpc.alerts:rule-scope-cloud] Whether Tags are a cloud alert rule scope option is open [gap:zpc.alerts:cloud-rule-tags-scope]. An IaC alert rule scope can be set by Scan Plugin, Repository and Select Policy, with policies filterable by Compliance, Severity or Policy Type. [zpc.alerts:rule-scope-iac] The email notification of an alert rule has a Frequency of Daily or Weekly, a Send At time, a Timezone, an optional detailed report attachment and recipient addresses. [zpc.alerts:rule-email-options] In the Alert Rule Status step, the page says email notifications are sent every time the alert is triggered. [zpc.alerts:rule-status-email-each-time] The same page gives two email timings [divergence:zpc.alerts:rule-email-timing]. An ITSM notification in an alert rule selects ServiceNow or JIRA, an alert payload of Audit Procedure, Remediation and Resource Metadata, an assignee email, and checkboxes to send notifications for closed and resolved alerts. [zpc.alerts:rule-itsm-options] An alert rule's Slack notification selects Slack and then the channels to which the alert notifications must be sent. [zpc.alerts:rule-slack-option] Any configured cloud alert rule or IaC alert rule can be edited or deleted, and the list of alert rules is on the Notifications tab of the Alerts page; deleting asks for confirmation. [zpc.alerts:alert-rule-edit-delete] Editing an alert rule changes the Alert Rule Name or Alert Rule Status on the first page, then walks through the Resource Scope and Notifications pages and a review, then Finish. [zpc.alerts:alert-rule-edit-pages] Limits on alert rules and ignore filters are open [gap:zpc.alerts:alert-limits].

**Ignore filters.** Ignore filters are applied only to newly triggered alerts. [zpc.alerts:ignore-filter-newly-triggered] The page says all alerts matching the selected criteria are moved to ignored status. [zpc.alerts:ignore-filter-created-moves] Whether an ignore filter affects alerts that already exist differs within the Adding Alert Ignore Filters page [divergence:zpc.alerts:ignore-filter-existing-alerts]. By default only users with the admin and security operations (SecOps) role can add ignore filters; other ZPC users have view-only permission unless Ignore Rules permissions are added or modified in Global Modules. [zpc.alerts:ignore-filter-permission] An ignore filter is disabled after its end date, after which alerts are triggered for security policy violations. [zpc.alerts:ignore-filter-end-date] A cloud ignore filter needs at least one of Policies, Cloud Accounts, Cluster Names, Namespaces, Tags or Assets; Next is disabled if none is selected. [zpc.alerts:ignore-filter-scope-cloud] An IaC ignore filter needs at least one of Policies, Template Type, Scan Plugin or Repository, and Template Type options are Terraform, CloudFormation, Azure Resource Manager, Kubernetes, Helm Charts and Terraform Plan. [zpc.alerts:ignore-filter-scope-iac] In a cloud ignore filter the All Policies, All Accounts, All Kubernetes Clusters, All Kubernetes Namespaces, All Tags and All Assets options are selected by default. [zpc.alerts:ignore-filter-defaults] A deleted ignore filter is not applicable to newly triggered alerts, and alerts already ignored under it remain ignored. [zpc.alerts:ignore-filter-delete] An existing ignore filter for IaC or cloud alerts is enabled or disabled with the toggle in the State column after clicking Ignore Filters on the Alerts page, and ZPC asks for confirmation. [zpc.alerts:ignore-filter-toggle]

**Alerts grouped by policy or scan.** Cloud alerts grouped by policy are reached from the Cloud Alerts tab and its Alerts Grouped by Policy tab; clicking a Policy Name shows the Policy and Alert details. [zpc.alerts:grouped-by-policy-cloud] IaC alerts grouped by policy are reached from the IaC Alerts tab and its Alerts Grouped by Policy tab; clicking a Policy Name shows the Policy, Compliance and Alert details. [zpc.alerts:grouped-by-policy-iac] IaC alerts are also grouped by scan, in the Alert Grouped By Scan tab; clicking a Scan ID shows Scan Details (the repository details, the name of the developer who performed the scan, and the date and time of the scan) and Alert Details. [zpc.alerts:iac-grouped-by-scan]

**Ignoring, resolving and remediating.** When an alert is ignored, ZPC still triggers the alert whenever it detects the policy violation, but the alert notification is not sent to third-party tools; ignoring requires a reason and a duration. [zpc.alerts:ignore-alert-behavior] Resolving an alert requires a reason and changes the alert status to Resolved. [zpc.alerts:resolve-alert] Cloud alerts can be remediated manually only if write access is enabled for the cloud account, and only alerts with Open status or with remediation status Failure can be remediated. [zpc.alerts:remediate-prereq] Whether the failed remediation status is named Failure or Failed is open [gap:zpc.alerts:remediation-failed-name]. Cloud alerts can be remediated singly, in multiples, in bulk or all alerts for a specific policy violation, using Remediate All on the Alerts Grouped By Policy tab, with a reason entered. [zpc.alerts:remediate-scope] Whether Azure and GCP alerts can be remediated this way is open [gap:zpc.alerts:remediate-non-aws].

What to check:
1. Whether an alert is Resolved or Closed before trying to reopen it: only resolved alerts can be reopened.
2. Whether write access is enabled for the cloud account and the alert has Open status or remediation status Failure before remediating.
3. Whether an ignore filter applies to alerts that already exist: the Adding Alert Ignore Filters page says both that filters are applied only to newly triggered alerts and that all matching alerts are moved to ignored status.
4. Whether the alert rule is enabled, since ZPC sends alert notifications only when it is.

Sources disagree (name both sides):
- The Adding Alert Rules page says email notifications are sent every time the alert is triggered and also offers a Daily or Weekly email Frequency. [divergence:zpc.alerts:rule-email-timing]
  - zscaler-help: Email notifications are sent every time the alert is triggered.
  - zscaler-help: The email notification has a Frequency of Daily or Weekly.
  Impact: Whether an email goes out per trigger or on the Daily or Weekly schedule is not settled by the page.
- The Adding Alert Ignore Filters page says ignore filters apply only to newly triggered alerts and also that all alerts matching the selected criteria are moved to ignored status. [divergence:zpc.alerts:ignore-filter-existing-alerts]
  - zscaler-help: Ignore filters are applied only to newly triggered alerts.
  - zscaler-help: All alerts matching the selected criteria are moved to ignored status.
  Impact: Whether alerts that already exist are ignored when a filter is created is not settled by the page.
