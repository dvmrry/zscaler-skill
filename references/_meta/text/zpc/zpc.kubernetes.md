# How ZPC onboards and offboards EKS, AKS and GKE clusters, including private GKE and AKS local authentication (zpc.kubernetes)
Also called: ZPC KSPM; ZPC EKS onboarding; ZPC AKS onboarding; ZPC GKE onboarding; private GKE agent; Kubernetes tab cluster status

On the Cloud Accounts Kubernetes tab, cluster Status is Success (onboarded, metadata collected), Warning (onboarded but metadata for some services cannot be collected), Error (not onboarded yet), Suspended (onboarded but tenant license expired) or Failed (onboarded but cloud account deleted). [zpc.kubernetes:cluster-statuses] The hub is [What Zscaler Posture Control (ZPC) is to administer: portal access, setup order, notifications and audit logs](kb:zpc.overview) and the accounts that hold the clusters are in [How ZPC cloud accounts and organizations are onboarded: AWS, Azure, GCP and OCI](kb:zpc.cloud-accounts).

**Status.** ZPC cannot collect configuration metadata for suspended or failed Kubernetes clusters. [zpc.kubernetes:suspended-failed-no-collection] How the status sets relate is open [gap:zpc.kubernetes:status-sets].

**EKS.** ZPC's EKS onboarding covers public and hybrid clusters; its script updates the publicAccessCidr property of hybrid clusters with ZPC IP addresses, creates a cluster role binding in Kubernetes and creates an IAM identity mapping. [zpc.kubernetes:eks-scope] EKS onboarding requires the AWS account to be onboarded, being a Kubernetes Cluster Admin, permission to update the aws-auth configmap in the kube-system namespace and to create, update and delete the cluster role and binding, and for hybrid clusters UpdateClusterConfig and DescribeCluster permissions. [zpc.kubernetes:eks-prereqs] ZPC cannot onboard EKS clusters with private-only endpoint access, and needs the CloudShell IP address allowlisted when onboarding a public and private cluster. [zpc.kubernetes:eks-private-only]

**AKS.** ZPC's AKS onboarding covers public clusters; its script creates a cluster role and role binding with the service principal used for onboarding the Azure account and allowlists the ZPC IP addresses if authorized IP ranges are enabled. [zpc.kubernetes:aks-scope] AKS onboarding requires the Azure account to be onboarded, being a Kubernetes Cluster Admin, and, for Azure AD with Kubernetes RBAC, membership of the AAD group with the Cluster Admin Access role, or, for Azure AD with Azure RBAC, the Azure Kubernetes Service RBAC Cluster Admin role. [zpc.kubernetes:aks-prereqs] For AKS clusters without Azure AD integration, ZPC authenticates with a certificate and a secret key: it generates a bash script and a secret key, the secret key is submitted while the script runs, and the script sends a verification certificate to ZPC. [zpc.kubernetes:aks-local-auth] The secret key for AKS local authentication must be saved because it is needed for subsequent AKS cluster onboarding, and regenerating it has no impact on already onboarded clusters. [zpc.kubernetes:aks-secret-key] In AKS local-authentication onboarding, a Kubelet Collection toggle controls whether Kubelet configuration metadata is collected. [zpc.kubernetes:aks-kubelet]

**GKE.** For GKE, the ZPC script allowlists the ZPC IP address in the cluster's Control plane authorized networks property, and a public cluster with that property disabled is onboarded automatically. [zpc.kubernetes:gke-scope] GKE onboarding requires the Kubernetes Engine API enabled on the GCP service account project and the onboarded project, and the viewer role on the service account. [zpc.kubernetes:gke-prereqs] Selected public GKE clusters are onboarded automatically, while hybrid clusters need a bash script run on them; the page says ZPC cannot onboard clusters with private-only endpoint access, and needs the CloudShell IP allowlisted for a public and private cluster. [zpc.kubernetes:gke-public-hybrid] Whether private-only GKE clusters can be onboarded is in dispute [divergence:zpc.kubernetes:gke-private-only].

**Private GKE.** ZPC cannot make inbound API requests into the control plane of a private GKE cluster, so it uses a lightweight agent deployed on the cluster that sends configuration metadata back; the agent typically uses 100MB to 300MB and up to 500MB of memory. [zpc.kubernetes:pgke-agent] Private GKE onboarding requires ingress firewall rules for udp:53, tcp:53, tcp:22 and tcp:10250. [zpc.kubernetes:pgke-firewall] For private GKE clusters, Status is Success (agent sending all required information), Pending (agent deployed but not yet connected), Warning (only partial data received) or Error (agent cannot connect or cannot send any information). [zpc.kubernetes:pgke-statuses] ZPC generates a unique API key per private GKE cluster that cannot be viewed again; in Pending status the key can be regenerated or deactivated, and deactivating it stops ZPC collecting configuration metadata. [zpc.kubernetes:pgke-api-key] After Finish is clicked a private GKE cluster's status becomes Pending, and becomes Success when ZPC confirms the private-cluster onboarding on the GCP Cloud Console is completed; the CRD file can be downloaded for clusters in Pending status. [zpc.kubernetes:pgke-pending-success] The private GKE onboarding page includes the commands kubectl create ns zpc, kubectl create secret generic zpc-api-key-credentials and kubectl apply -f kubernetesagent.yaml; creating the operator requires the API key generated on ZPC. [zpc.kubernetes:pgke-agent-commands] Whether the hosts in the agent command are production endpoints is open [gap:zpc.kubernetes:pgke-agent-hosts].

**Offboarding.** After offboarding an EKS cluster, ZPC's access is removed with eksctl delete iamidentitymapping, deleting the zpc-reader cluster role binding and the zpc-read-role cluster role; for hybrid clusters ZPC's three allowlisted IPs are also removed. [zpc.kubernetes:offboard-eks] After offboarding an AKS cluster, the Azure Kubernetes Service Cluster User Role assignment is deleted with az role assignment delete and ZPC's cluster role binding is deleted with kubectl delete clusterrolebindings. [zpc.kubernetes:offboard-aks] If an offboarded GKE cluster had control plane authorized networks enabled, ZPC's allowlisted IPs 52.13.162.179/32, 52.12.66.25/32 and 34.212.243.119/32 must be removed. [zpc.kubernetes:offboard-gke]

- The GKE onboarding page says ZPC cannot onboard clusters with private-only endpoint access, while the private GKE page onboards private GKE clusters with an agent. [divergence:zpc.kubernetes:gke-private-only]
  - zscaler-help: ZPC cannot onboard GKE clusters with private-only endpoint access.
  - zscaler-help: Private GKE clusters are onboarded using a lightweight agent deployed on the cluster.
