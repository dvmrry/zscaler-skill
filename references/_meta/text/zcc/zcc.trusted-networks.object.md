# The Client Connector trusted network object and its v1 API (zcc.trusted-networks.object)
Also called: zcc trusted network object; webTrustedNetwork; trustedNetworkContracts; trusted network create returns no id; trusted network condition type; zcc trusted network csv; zcc_trusted_network
Former IDs: zcc-06

A trusted network is a named, reusable set of detection criteria that forwarding profiles select as predefined trusted networks. The v1 API under `webTrustedNetwork` is in the generated surface; this subject holds its behavior.

**What it is for.** Defining criteria once and selecting several networks in a profile: [Zscaler Client Connector identifies a trusted network by criteria defined for it on the Trusted Networks page, and a forwarding profile can select several predefined trusted networks.](kb:zpa.trusted-networks.zcc-relationship:zcc-defines-criteria). How the app evaluates them is [How Client Connector decides it is on a trusted network](kb:zcc.trusted-networks.detection).

**In the console.** On the Trusted Networks page (Infrastructure > Location Management > Trusted Networks) a trusted network has a unique alphanumeric Network Name and conditions defined as criteria that Client Connector uses to verify that it is one of the organization's trusted networks. [zcc.trusted-networks.object:console-definition] The page's conditions are DNS Server, DNS Search Domains, Hostname and IP, Network Range, Default Gateway, DHCP Server, Egress IP (applies only to Client Connector 4.6 and later for Windows) and Wi-Fi Name (applies only to 5.0 and later for Windows); with multiple conditions, Any has the app validate only one of them to decide the network is trusted and All has it validate all of them. [zcc.trusted-networks.object:console-conditions] The Trusted Networks page can be searched by Network Name, DNS Servers, DNS Search Domains, Hostname or IP, Network Range, Default Gateway, DHCP Server or Egress IP. [zcc.trusted-networks.object:search-criteria]

**Criteria are strings.** Each criterion is one comma-separated string: [In v1 each criterion of a trusted network (`dnsServers`, `dnsSearchDomains`, `hostnames`, `resolvedIpsForHostname`, `ssids`, `trustedDhcpServers`, `trustedGateways`, `trustedSubnets`, `trustedEgressIps`) is one comma-separated string, not a list: the contract and the Go SDK type them as strings, the Python SDK's examples pass values such as '10.11.12.13, 10.11.12.14' and '' for unused criteria, and the Terraform provider's v1 adapter splits and joins them on commas, noting that the v1 API returns values like "10.0.0.5, 10.0.0.6".](kb:zcc.api.trusted-networks-wire:v1-criteria-strings). The Go SDK omits `ssids` and `trustedEgressIps` from a written body when they are empty, while it always sends the other criteria, empty or not. [zcc.trusted-networks.object:go-omitempty]

**Condition type.** The trusted network's `conditionType` sets how its own criteria combine; the Go SDK sends it as an integer with no omitempty, so 0 is always sent. [zcc.trusted-networks.object:condition-type-int] The sources disagree on its wire type [zcc.api.trusted-networks-wire:condition-type-wire-type](kb:zcc.api.trusted-networks-wire:condition-type-wire-type), and which code means All is only partly settled [gap:zcc.trusted-networks.object:condition-type-values], by the provider mapping in [For v1 the provider sends `ALL` as 0 and `ANY` as 1, passes any other numeric string through unchanged, and reads unknown numbers back as their decimal string. Its comment says the 0=ALL, 1=ANY mapping was field-verified on a tenant serving both API generations.](kb:zcc.terraform.trusted-network-backend:v1-condition-type-mapping).

**Listing.** Both SDKs unwrap an envelope the contract does not show: [Both SDKs read the v1 list as an object and take the networks from its `trustedNetworkContracts` member (Go also reads `totalCount` and errors when it is positive but no networks came back).](kb:zcc.api.trusted-networks-wire:list-envelope), [zcc.api.trusted-networks-wire:v1-list-shape](kb:zcc.api.trusted-networks-wire:v1-list-shape). The Go SDK's lookups by name and by ID page through the list 1000 at a time until a page comes back short, comparing names exactly. [zcc.trusted-networks.object:name-lookup-pages]

**Create and update.** Create and edit answer with a status only: [The Go SDK documents that v1 create and edit return only a status such as {"success":"true","errorCode":"0"}, not the trusted network, so it resolves the record by name after create and by ID after update. Recorded responses from one test tenant agree that neither returns the record, but differ on the create: there the API answered `{"conditionType" : 0, "active" : false}`, while the edit answered `{"success" : "true", "errorCode" : "0"}`.](kb:zcc.api.trusted-networks-wire:mutation-response), read as [The Go SDK's trusted network create and update return an error when the mutation response's `errorCode` is non-empty and not "0"; an empty or "0" `errorCode` passes that check whatever `success` says.](kb:zcc.api.trusted-networks-wire:error-code). Update is a PUT to `edit` with the ID in the body: the Go SDK refuses to send an update without an ID, and the Python SDK sends whatever keyword arguments it is given without checking for one. [zcc.trusted-networks.object:update-needs-id] The Python SDK's add and update send the caller's keyword arguments, with keys camel-cased by the request executor (apart from a set of snake_case keys kept for web policies), rather than the model's full field set, so unset criteria are absent from the body rather than sent empty. [zcc.trusted-networks.object:python-sends-kwargs] The Python create's result therefore has no ID: [The recorded v1 create response carries only `conditionType` and `active`, so the object `add_trusted_network` returns has no ID or name of the new network.](kb:zcc.sdk-python.return-shapes:add-result-has-no-id). The Go SDK's name lookup after create, and its blind sleeps, are in [Creating a v1 trusted network resolves the new ID by name, six attempts, and sleeps two seconds after every failed attempt, including the last. The loop passes the request context to each lookup but never checks it itself, and waits with `time.Sleep`. A cancelled create keeps sleeping, and a lookup error is returned only after all six attempts.](kb:zcc.terraform.field-fidelity:trusted-network-create-sleeps-blindly).

**ZPA link.** The Terraform provider documents that the API also returns a linked ZPA tenant identifier, `zpaId`, populated lazily (absent from the create response, present on later reads), and that it does not exist on v1. [zcc.trusted-networks.object:zpa-id] The provider calls it a ZPA tenant identifier, so do not read it as a per-network ID that matches ZPA's trusted network records, which are described in [Trusted networks in ZPA and in Client Connector](kb:zpa.trusted-networks.zcc-relationship).

What `active`, `guid` and the audit fields guarantee is open [gap:zcc.trusted-networks.object:metadata-semantics].

What to check:
1. When listing trusted networks directly, unwrap `trustedNetworkContracts` and page until a short page.
2. After a create or update, re-read the record: the mutation response carries only a status.
3. Treat `errorCode` "0" as success, not as a failure flag.
4. Before reading All or Any from a v1 `conditionType`, whether the code has been checked against the console for that tenant.

Not known (open gaps):
- What active, guid and the audit fields guarantee [gap:zcc.trusted-networks.object:metadata-semantics]: settled by tenant-data or lab-test
- Which trusted network conditionType code is All and which Any [gap:zcc.trusted-networks.object:condition-type-values]: settled by lab-test or tenant-data. Blocks: saying from raw v1 data whether a trusted network needs all of its criteria
