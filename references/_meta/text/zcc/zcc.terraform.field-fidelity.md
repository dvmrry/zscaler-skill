# ZCC Terraform provider fields that are not sent, not read back, or collapsed (zcc.terraform.field-fidelity)
Also called: zcc forwarding profile ignored field; zcc terraform perpetual diff; zcc trusted_networks not applied; zcc data source false; zcc fail open policy removed from state; zcc terraform drift hidden; evaluate_trusted_network false; IntOrString truncates

The ZCC provider is a Plugin Framework provider whose forwarding profile resource round-trips a large nested object through a hand-written expand function (plan to request) and flatten function (response to state). Most defects here come from the two halves disagreeing: a setting that can be read but not written, or one that is written but never read.

**Accepted but never sent.** The forwarding-profile resource declares four ZIA action attributes as Optional and Computed, `system_proxy`, `send_all_dns_to_trusted_server`, `drop_ipv6_traffic_in_ipv6_network` and `optimise_for_unstable_connections`, and its flatten function fills them from the API response. [zcc.terraform.field-fidelity:action-fields-exposed-and-read] The unified-tunnel block declares `optimise_for_unstable_connections`, `drop_ipv6_traffic_in_ipv6_network` and `send_all_dns_to_trusted_server` as Optional and Computed, and its flatten function fills them from the API response. [zcc.terraform.field-fidelity:tunnel-fields-exposed-and-read] The four ZIA action attributes are never sent. The action request type the SDK posts has no field for them, and the provider's expand function for actions does not set them, so a value written in configuration does not reach the request body. [zcc.terraform.field-fidelity:action-fields-never-sent] The three unified-tunnel attributes are never sent either. The tunnel request type has no field for them and the provider's expand function for tunnels does not set them. [zcc.terraform.field-fidelity:tunnel-fields-never-sent] Of the three trusted-network lists on a forwarding profile, only `trusted_network_ids` is ever sent. `trusted_networks` and `trusted_network_ids_selected` are declared Optional and Computed, but the request type has no field for them, the expand function builds only `TrustedNetworkIds`, and flatten overwrites both from the API response. An unset `trusted_network_ids` is sent as an empty list. [zcc.terraform.field-fidelity:trusted-network-lists-read-only] For these nine attributes the provider accepts a configured value, sends nothing, and then writes whatever the API returns into state. Terraform plans one value, the API holds another, and the plan can show perpetual drift or the apply can fail with an inconsistent-result error, while the setting itself is not managed. [zcc.terraform.field-fidelity:configured-values-silently-ignored] What the API does with a setting it never receives is open [gap:zcc.terraform.field-fidelity:ignored-field-server-effect]. Zero-value clears on the fields that are sent are in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes).

**Settings hidden from drift.** On every read, the four ZPA latency settings (`latency_based_server_enablement`, `lbs_probe_interval`, `lbs_probe_sample_size`, `lbs_threshold_limit`) are replaced with the value already in state whenever that is known, so out-of-band changes to them do not appear. The workaround exists because it assumes the SDK response type has differently named tags; in SDK v3.8.37 and v3.8.47, the releases the provider's go.mod pins, the tags are the plain names the API returns. The same overlay applies to `is_same_as_on_trusted_network` (see the next claim's places). [zcc.terraform.field-fidelity:zpa-latency-overlay-masks-drift] The unified-tunnel `system_proxy_data` overlay is not limited to `proxy_action`. Every attribute that is known in the prior plan or state replaces the API value, so a changed PAC URL, proxy address or any other proxy field made outside Terraform is hidden on refresh. The code comment says the API resets nested systemProxyData fields and names only `proxyAction`, as the most notable. [zcc.terraform.field-fidelity:unified-tunnel-overlay-covers-every-attribute] The same pattern, a field the provider believes the API drops being filled from prior state instead of the response, appears in more places: `evaluate_trusted_network` and `is_same_as_on_trusted_network` on forwarding profiles, and `enforce_secure_pac_urls` and `enable_fqdn_match_for_vpn_bypasses` on web privacy. While the belief holds this avoids spurious diffs; if the API starts returning the field, or the belief is wrong, drift on it is never shown. In the web privacy resource the fields are sent; only their read-back is replaced. [zcc.terraform.field-fidelity:prior-state-overlays-elsewhere] A recorded forwarding-profile listing does return `evaluateTrustedNetwork` [divergence:zcc.terraform.field-fidelity:evaluate-trusted-network-echo]. Whether the list and GET responses really omit the other fields the provider restores from state is open [gap:zcc.terraform.field-fidelity:api-field-drop-claims].

**Data sources.** The forwarding-profile and web-privacy data sources map the raw response with no fallback, while the matching resources say the response does not carry `evaluateTrustedNetwork`, `enforce_secure_pac_urls` and `enable_fqdn_match_for_vpn_bypasses`. A missing key decodes as zero or empty, so the data source reports false for those fields even when the profile or setting is true. [zcc.terraform.field-fidelity:data-sources-report-false-for-dropped-fields] The forwarding-profile resource reads `active` and `enableLWFDriver` through a helper that accepts both "1" and "true" (any case), while the data source tests only for "1". If the API returns "true", the resource reports true and the data source reports false for the same profile. [zcc.terraform.field-fidelity:strict-versus-lenient-boolean-strings]

**Failed reads and creates.** If the fail-open policy cannot be read, the resource is removed from state. Read calls the by-ID lookup, and on any error calls the list again; if that list also errors, or is empty, it removes the resource without looking at what the error was, so a not-found and any other failure are treated alike. The by-ID lookup itself returns the list error unchanged. When the by-ID lookup errors and the list then returns policies, as when it has no policy with the stored ID, Read silently adopts the first policy in the list. [zcc.terraform.field-fidelity:failopen-read-error-removes-state] Forwarding-profile create does not check the `success` field the API returns. After a nil error the SDK logs the response object and returns it; the provider logs `success` and goes straight on to look the profile up by the returned ID and, if that fails, by name. [zcc.terraform.field-fidelity:create-ignores-success-flag] If the API answers a rejected write with HTTP 200 and `success` false with ID 0, create waits through the ID lookups, then adopts the first profile that has the same name, which can be an unrelated existing one, and records it in state as the new resource. [zcc.terraform.field-fidelity:create-can-adopt-same-name-profile] Whether the edit endpoint returns HTTP 200 with `success` false is open [gap:zcc.terraform.field-fidelity:success-false-response]. Reads removed because an ID is outside the first page of a list are in [How the Go SDK pages through ZPA, ZCC and ZTC lists, and when it stops early](kb:shared.sdk-go.list-pagination).

**Blocks that collapse.** Flatten keys the prior plan or state by `network_type` for actions, ZPA actions and unified tunnels, so if two blocks share a `network_type`, the later one overwrites the earlier in the map, and every API entry with that type is then filled from that single entry (the `is_same_as_on_trusted_network` value, the four ZPA latency values, the tunnel proxy overlay). [zcc.terraform.field-fidelity:duplicate-network-type-collapses] Nothing in the schema rejects two blocks with the same `network_type`, so a configuration with duplicates plans, sends all of them, and cannot represent them independently after refresh. [zcc.terraform.field-fidelity:duplicate-network-type-not-rejected]

**Defects on the SDK side.** The shared ZCC `IntOrString` type accepts a fractional JSON number or quoted number and truncates it to an integer with `int(f)` or `int(parsed)`, dropping the fraction. The code comment says the intent was values like `1.0`, but there is no check that the value is whole. [zcc.terraform.field-fidelity:intorstring-truncates-fractions] Creating a v1 trusted network resolves the new ID by name, six attempts, and sleeps two seconds after every failed attempt, including the last. The loop passes the request context to each lookup but never checks it itself, and waits with `time.Sleep`. A cancelled create keeps sleeping, and a lookup error is returned only after all six attempts. [zcc.terraform.field-fidelity:trusted-network-create-sleeps-blindly] [The ZPA SDK's emergency-access `Create` sets `ActivateNow` to false on the caller's struct, then posts that struct. The field is `omitempty`, so it is not sent at all.](kb:zpa.emergency-access.api-surface:sdk-go-create-clears-activate-now) These three SDK defects reach providers unevenly. The ZCC provider uses the shared `IntOrString` only through web-policy code it does not register, and reaches the v1 trusted-network create only through the backend added after v0.1.0-beta.1. The ZPA provider has an emergency-access resource that calls `Create` but sets no activation field, so for Terraform users `ActivateNow` is not an input. [zcc.terraform.field-fidelity:sdk-defects-reach] The ZCC provider's trusted-network resource calls the SDK's v1 create (`CreateTrustedNetwork`) only from its v1 backend, which serves tenants where the v2 trusted-networks endpoints are not enabled: the first trusted-network operation probes the v2 list endpoint once and caches the verdict for the provider's SDK service handle. [zcc.terraform.field-fidelity:v1-backend-serves-tenants-without-v2] Which probe failures select the v1 backend is [The provider treats a failed probe of the v2 list as 'v2 not served' when the error is a not-found (including a parsed `resource.not.found`) or carries status Bad Request, Forbidden, Not Found, Method Not Allowed or 501, and then uses the v1 backend; its unit test asserts this for each of those statuses, for a response status of Not Found and for a parsed `resource.not.found`.](kb:zcc.terraform.trusted-network-backend:probe-unavailable-statuses). Legacy-client routing for the same package is in [ZCC SDK calls in legacy-client mode routed to the ZIA client](kb:zcc.sdk-go.legacy-routing); ZIA's equivalent field-fidelity mechanisms are in [ZIA Terraform resource fields that are not sent, not read back, or sent wrongly](kb:zia.terraform.field-fidelity).

Whether the ZCC v2 create and update responses carry every field is open [gap:zcc.terraform.field-fidelity:partial-create-update-response].

What to check:
1. When an attribute shows a perpetual diff, or a configured setting has no effect on the client, check the request type first.
2. Before using a ZCC data source's boolean as a policy input for the fields named above, confirm it against the resource or a raw API read.
3. After a failed refresh of the fail-open policy, confirm in the console that the policy still exists before trusting a plan that proposes to create it.
4. Whether any block list has two blocks with the same network_type, which the schema does not reject.
