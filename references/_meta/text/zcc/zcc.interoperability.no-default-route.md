# Deploying Client Connector where the only egress is a proxy: the System PAC, spoofed DNS records and the four scenarios (zcc.interoperability.no-default-route)
Also called: no-default route environments; no default route; system pac; spoofed zscaler dns records; zscaler gvip

A no-default-route environment is one where the only way out is an edge proxy. In a no-default-route environment a default route is not propagated through the network and the only way to egress is via an edge proxy server; browser traffic is explicitly sent to a proxy using a PAC file served through a local web server, through the proxy itself or through Web Proxy Automatic Discovery (WPAD), and DNS resolution of public DNS records is restricted for all devices except the proxy server. [zcc.interoperability.no-default-route:definition] Client Connector supports operation in a no-default environment on Windows, macOS, Linux and iOS. [zcc.interoperability.no-default-route:platforms]

**What the app contacts.** In the article's table of a typical environment, Client Connector probes gateway.zscaler.net and gateway.<cloudname>.net for captive portal detection, makes an API call to login.<cloudname>.net to start login, makes an API call to mobile.<cloudname>.net and downloads the app profile PAC from pac.<cloudname>.net for policy, makes API calls to gateway.<cloudname>.net and mobile.<cloudname>.net for service discovery and enrollment, probes mobile.zscaler.net for tenant cloud discovery, and forwards Private Access traffic using a microtunnel (M-Tunnel) to the Broker or Public or Private Service Edge for Private Access. [zcc.interoperability.no-default-route:typical-endpoints]

**What the deployment needs.** The requirements the article lists: a System PAC for initial service discovery, enrollment, authentication and policy and PAC download using an explicit proxy IP address; spoofed Zscaler records pointing to the Zscaler global virtual IP (GVIP) or an internal NAT address so the app can resolve Zscaler cloud addresses; a GRE/IPSec tunnel for connectivity during initial configuration and for traffic forwarding for Internet & SaaS and Private Access, which is not used for forwarding if a Private Service Edge is present; a Private Service Edge for Internet & SaaS, highly recommended if Z-Tunnel 2.0 forwarding is required from on-premises; app and forwarding profiles configured with Tunnel Internal Client Connector Traffic and other features; and explicit proxies configured to bypass authentication to the IdP and Zscaler cloud, not to re-resolve DNS based on SNI, and to have SSL inspection disabled. [zcc.interoperability.no-default-route:requirements] The article's scenario table: scenario 1 is HTTP/HTTPS with Tunnel with Local Proxy, and scenario 2 is TCP 80 and 443 with Z-Tunnel 1.0, each needing the System PAC file, DNS records and a GRE/IPSec tunnel, with a third-party proxy, a Private or Virtual Service Edge and Private Access supported; scenario 3 is all ports and protocols with Z-Tunnel 2.0, with a Private or Virtual Service Edge required and a third-party proxy N/A; scenario 4 is all ports and protocols with Z-Tunnel 2.0, with a third-party proxy required and a Service Edge N/A. Private Access is supported in all four. [zcc.interoperability.no-default-route:scenarios] The scenario table's footnotes are not fully recoverable [gap:zcc.interoperability.no-default-route:scenario-footnote].

**Common setup.** The common setup: GRE/IPSec tunnel configurations in Internet & SaaS with tunnels from a router or firewall to the closest Zscaler data centers; Enforce Authentication Disabled for the newly created location; a Zscaler GVIP chosen from the bottom of https://config.zscaler.com/<cloudname>.net/cenr (the article uses 185.46.212.88 except when forwarding to a Private Service Edge for Internet & SaaS); and a route forwarding traffic to the GVIP via the GRE/IPSec tunnels. [zcc.interoperability.no-default-route:location-and-gvip] The article's spoofed DNS records are type A records to the GVIP for gateway.<cloudname>.net, gateway.zscaler.net, login.<cloudname>.net, mobile.<cloudname>.net, mobile.zscaler.net and pac.<cloudname>.net. In networks where an internal IP address can be used instead of the GVIP, with an upstream router or firewall performing Destination NAT to the GVIP, the spoofed records must reference the internal IP instead. [zcc.interoperability.no-default-route:spoofed-dns]

**The System PAC.** A System PAC file is created in the Admin Console and its PAC URL is assigned to internal devices using GPO or WPAD; it is required for initial discovery, enrollment, authentication, and app and forwarding profile policy and PAC file downloads, and lets the app communicate with the Zscaler cloud in an explicit proxy mode. After enrollment the app no longer uses it, and restores it upon exit. [zcc.interoperability.no-default-route:system-pac] The vendor's System PAC detects the device location with the ${SRCIP} macro, available only when the PAC file is hosted in the Zscaler cloud: a device at a location with a GRE/IPSec tunnel uses the Zscaler GVIP as the explicit proxy IP address, and a device on an Off-Trusted Network communicates directly with the closest Zscaler data center. It lists Zscaler public IP addresses to detect a GRE/IPSec tunnel, the special URL the app checks to enroll using an explicit proxy, and domains for support access, ZDX and certificate validation (mobilesupport.zscaler.com, *.zdxcloud.net, *.digicert.com), for Private Access (*.prod.zpath.net, *.private.zscaler.com), for software and module updates (a CloudFront host), and for authentication during enrollment (the example shows domains required by Entra; domains required for the organization's IdP are used). [zcc.interoperability.no-default-route:system-pac-logic]

**Authentication.** Client Connector must be able to authenticate with the IdP for enrollment and policy downloads to succeed, so the IdP URLs must be added to the Authentication Exemptions list in Internet & SaaS. The vendor's examples: for Entra ID login.microsoftonline.com, *.windowsazure.com, device.login.microsoftonline.com, login.microsoft.com, autologon.microsoftazuread-sso.com and login.windows.net; for Okta *.okta.com, *.oktacdn.com and *.oktapreview.com; for Private Access *.zpath.net and *.private.zscaler.com. [zcc.interoperability.no-default-route:auth-exemptions]

**Scenario 1.** Scenario 1: after enrollment, the app forwards Internet & SaaS HTTP/HTTPS using Tunnel with Local Proxy (TWLP/Z-Tunnel 1.0) and Private Access traffic using M-Tunnels to the Zscaler GVIP. The vendor's forwarding profile PAC sends 1.2.3.4 and *.prod.zpath.net to the GVIP at port 80 and everything else to ${ZAPP_LOCAL_PROXY}. The forwarding profile uses a Predefined Trusted Networks condition, which cannot be added with any other conditions, to detect the no-default-route environment; On-Trusted is Tunnel with Local Proxy, with Proxy Action Type Enforce and the PAC URL Location set to the forwarding profile's PAC URL. In the vendor's example Off-Trusted is Tunnel with Z-Tunnel 2.0 and Redirect Web Traffic to Zscaler Client Connector Listening Proxy enabled, and no PAC URL is required for an Off-Trusted Network. [zcc.interoperability.no-default-route:scenario-1-local-proxy] In Scenario 1, the app profile has Disable Loopback Restriction enabled in the Proxy Configuration section, Cache System Proxy on Startup enabled (which restores the System PAC after the user exits the app), Override WPAD and Restart WinHTTP Service enabled if WPAD is in use (both optional), and Tunnel Internal Client Connector Traffic enabled on the Advanced tab. [zcc.interoperability.no-default-route:app-profile-settings]

**Scenario 2.** Scenario 2: the app forwards Internet & SaaS TCP 80/443 traffic using Z-Tunnel 1.0 and Private Access traffic using M-Tunnels to the Zscaler GVIP. The article's directions do not cover a third-party proxy because third-party proxies are not required and can be deprecated in this scenario. For On-Trusted Network the forwarding profile selects Tunnel with Z-Tunnel 1.0, Proxy Action Type Enforce and the forwarding profile's PAC URL as the Custom PAC URL. [zcc.interoperability.no-default-route:scenario-2-tunnel-1]

**Scenarios 3 and 4.** Scenario 3: the app forwards Internet & SaaS traffic across all ports and protocols using Z-Tunnel 2.0 via the Private Service Edge for Internet & SaaS, and Private Access M-Tunnels and authentication traffic via the GVIP. The Internet & SaaS location associated with the Private Service Edge cluster has Force Authentication enabled so the Service Edge does not operate as an open proxy. On-Trusted is Tunnel with Z-Tunnel 2.0, Redirect Web Traffic to Zscaler Client Connector Listening Proxy disabled, All Proxied Web Traffic unselected under Use Z-Tunnel 2.0 for Proxied Web Traffic, and Proxy Action Type Apply on Trusted Network Type Change. In the app profile all internal IP subnets are added to IPv4 Exclusion, 0.0.0.0/0 is in IPv4 Inclusion, all internal domains are added to Domain Exclusion (DNS requests go to internal DNS servers) and * is added to Domain Inclusion (all external DNS requests are tunneled via Internet & SaaS). [zcc.interoperability.no-default-route:scenario-3-private-service-edge] Scenario 4: the app forwards Internet & SaaS traffic across all ports and protocols using Z-Tunnel 2.0 via a third-party proxy. When on-premises the Z-Tunnel 2.0 forwarding profile should use only TLS (instead of DTLS). The proxy must not attempt to authenticate requests destined for Zscaler IP addresses or for the IdP, must not attempt to re-resolve DNS based on SNI, and must have TLS inspection disabled and tunnel all Zscaler and IdP bound requests; a separate Internet & SaaS location is not required. For fallback to Z-Tunnel 1.0 at locations with a large number of users, the vendor suggests a Source-NAT IP address pool with multiple IP addresses whose load balancing uses sticky connections based on client IP addresses. [zcc.interoperability.no-default-route:scenario-4-third-party-proxy]

**Enrolling through a proxy (legacy).** If the device cannot connect to the Zscaler cloud directly, the app looks for a configured system proxy and attempts to connect through it. Proxy awareness is supported only for enrollment, not for user traffic after enrollment via a proxy; the proxy must not perform SSL inspection or authentication on Client Connector traffic. The article says proxy awareness is supported in 1.2.4 for Windows and macOS deployments and that mobile devices do not support it. [zcc.interoperability.no-default-route:proxy-aware-enrollment]

**Open.** Whether macOS, Linux and iOS need different app profile settings from the Windows steps is open [gap:zcc.interoperability.no-default-route:other-platform-settings]; the vendor example values are not the tenant's [gap:zcc.interoperability.no-default-route:example-values].

What to check:
1. Which of the four scenarios the deployment is, by the Internet & SaaS traffic type and the forwarding method in the scenario table.
2. That the IdP's URLs are in the Internet & SaaS Authentication Exemptions list, since enrollment and policy download need IdP authentication.
3. That the spoofed records resolve to the GVIP, or to an internal address that is destination-NATted to it where public prefixes cannot be injected.
4. For a third-party proxy: that it does not authenticate requests to Zscaler or the IdP, does not re-resolve DNS by SNI and has TLS inspection disabled.
