# How the ZCC provider picks the v1 or v2 trusted-network API and converts between them (zcc.terraform.trusted-network-backend)
Also called: zcc_trusted_network v1 fallback; tnbackend; trusted network v2 probe; condition_type ALL ANY 0 1; trusted network import partial name; multiple trusted networks match name; name must be set v1 trusted network; trusted network hostname ssid UseStateForUnknown; zcc_trusted_network v1 v2; trusted network v2 endpoint; condition_type ALL ANY; trusted network api version detection

The `zcc_trusted_network` resource and data source keep one v2-shaped schema on every tenant and talk to whichever trusted-network API the tenant serves. The two APIs' wire shapes are in [What goes on the wire for ZCC trusted networks: the v1 webTrustedNetwork and v2 trusted-networks APIs](kb:zcc.api.trusted-networks-wire).

**Choosing the API.** The probe and its cache are [The ZCC provider's trusted-network resource calls the SDK's v1 create (`CreateTrustedNetwork`) only from its v1 backend, which serves tenants where the v2 trusted-networks endpoints are not enabled: the first trusted-network operation probes the v2 list endpoint once and caches the verdict for the provider's SDK service handle.](kb:zcc.terraform.field-fidelity:v1-backend-serves-tenants-without-v2). The provider treats a failed probe of the v2 list as 'v2 not served' when the error is a not-found (including a parsed `resource.not.found`) or carries status Bad Request, Forbidden, Not Found, Method Not Allowed or 501, and then uses the v1 backend; its unit test asserts this for each of those statuses, for a response status of Not Found and for a parsed `resource.not.found`. [zcc.terraform.trusted-network-backend:probe-unavailable-statuses] Any other probe failure, such as a transport error, a 5xx or a token failure, fails the trusted-network operation with 'unable to detect the trusted-network API version for this tenant' rather than picking a version. [zcc.terraform.trusted-network-backend:probe-other-errors-fail] So a 403 or 400 on the v2 list for any reason, such as an API role without access to it, puts the provider on the v1 API for every trusted network it manages until the provider is configured again. [zcc.terraform.trusted-network-backend:forbidden-picks-v1] Whether a 400 or 403 from the probe really means the tenant has no v2 API is open [gap:zcc.terraform.trusted-network-backend:probe-4xx-meaning].

**Converting for v1.** For v1 the provider sends `ALL` as 0 and `ANY` as 1, passes any other numeric string through unchanged, and reads unknown numbers back as their decimal string. Its comment says the 0=ALL, 1=ANY mapping was field-verified on a tenant serving both API generations. [zcc.terraform.trusted-network-backend:v1-condition-type-mapping] The v1 API's string IDs are parsed into integers for the provider's model, and a non-numeric v1 ID is an error; the company ID is parsed leniently, and IDs go back to v1 as strings. [zcc.terraform.trusted-network-backend:v1-id-conversion] Converting v1 criteria, the provider splits each comma-separated string into a list, trimming spaces and dropping empty items, and joins lists back with bare commas. [zcc.terraform.trusted-network-backend:csv-trim] The v1 criteria strings themselves are [In v1 each criterion of a trusted network (`dnsServers`, `dnsSearchDomains`, `hostnames`, `resolvedIpsForHostname`, `ssids`, `trustedDhcpServers`, `trustedGateways`, `trustedSubnets`, `trustedEgressIps`) is one comma-separated string, not a list: the contract and the Go SDK type them as strings, the Python SDK's examples pass values such as '10.11.12.13, 10.11.12.14' and '' for unused criteria, and the Terraform provider's v1 adapter splits and joins them on commas, noting that the v1 API returns values like "10.0.0.5, 10.0.0.6".](kb:zcc.api.trusted-networks-wire:v1-criteria-strings).

**Finding by name.** A lookup by name takes a case-insensitive exact match first, otherwise accepts a single network whose name contains the given text, fails listing the candidates when several partially match, and reports not found when none does. [zcc.terraform.trusted-network-backend:name-selection] On v1 the provider scans every page of the list, 1000 at a time, and filters names locally; on v2 it asks the server for a NAME keyword match and applies the same selection to the result. [zcc.terraform.trusted-network-backend:name-search-per-backend]

**The v1 lifecycle.** The v1 backend has no read by ID: a read scans the list and reports not found when the ID is absent, and delete skips the pre-delete read it does on v2. [zcc.terraform.trusted-network-backend:v1-no-get-by-id] On v1 a create without a name fails before any API call, because the create response has no ID and the new record is found again by name. [zcc.terraform.trusted-network-backend:v1-create-needs-name] On v1 an update puts the resource ID into the request body, since the v1 `edit` call identifies the record by the body's ID, and the SDK then re-reads it by ID from the list. [zcc.terraform.trusted-network-backend:v1-update-injects-id] The SDK's v1 create resolves the new record by name with fixed sleeps: [Creating a v1 trusted network resolves the new ID by name, six attempts, and sleeps two seconds after every failed attempt, including the last. The loop passes the request context to each lookup but never checks it itself, and waits with `time.Sleep`. A cancelled create keeps sleeping, and a lookup error is returned only after all six attempts.](kb:zcc.terraform.field-fidelity:trusted-network-create-sleeps-blindly). Whether v1 and v2 records are the same objects is open: [Whether the v2 trusted-network API replaces v1 and shares its records](kb:zcc.api.trusted-networks-wire:v1-v2-coexistence).

**Planning.** `hostname` and `ssid` carry a use-state-for-unknown plan modifier, so when left unset they keep their prior state value in the plan instead of showing as known after apply. [zcc.terraform.trusted-network-backend:hostname-ssid-use-state]

The v2 request's empty-value handling is in [The ZCC trusted network v2 request tags `active` and every criterion list `omitempty`, so `active = false` and an explicit empty list send no key. The provider's own comment says its empty slices are omitted on the wire.](kb:shared.sdk-go.zero-value-writes:zcc-trusted-network-active-and-lists).

What to check:
1. Which API the provider chose for the run, from its INFO log line 'Auto-detected ZCC trusted-network API version', especially after a 403 from the v2 list.
2. Whether an import or data-source lookup by name matched several networks partially, which fails, or exactly one, which is taken.
3. Whether `condition_type` was written as ALL/ANY or as a raw number, since a raw number goes to the v1 API unchanged.
4. On v1, whether trusted network names are unique, since reads and imports resolve by name.
