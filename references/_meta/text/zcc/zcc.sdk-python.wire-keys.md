# How the Python SDK names ZCC keys on the wire: the model serializer and the parameter mapper (zcc.sdk-python.wire-keys)
Also called: zcc_to_wire; _ZccWireBody; zcc python snake_case camelCase; zcc_param_mapper; os_type invalid ValueError; device_type '3' ValueError; web_policy_edit result device_type None; MacOSPolicy disable_password

ZCC keys mix camelCase, snake_case and odd acronyms, and they differ by platform block, so the Python SDK carries its own key handling for ZCC bodies and query parameters. The general rule is [On the OneAPI client, the Python SDK camel-cases ZCC request body keys except those in `WebPolicy.SNAKE_CASE_KEYS`, and sends a body already serialized by the ZCC model serializer unchanged. On the legacy client a ZCC body goes through the general `convert_keys_to_camel_case`, which converts all keys recursively; a key the converter maps to itself, such as `exit_password`, keeps its form.](kb:zcc.api.conventions:python-body-casing); this subject holds how the serializer decides and where it falls short.

**The model serializer.** The ZCC serializer takes the model class as the single source of truth for wire keys, applies to ZCC only, and passes unknown keys through rather than dropping them. [zcc.sdk-python.wire-keys:serializer-scope] Each key is resolved in order: a snake_case attribute the model declares takes the model's wire key; a key that is already one of the model's wire keys is kept; a key in `WebPolicy.SNAKE_CASE_KEYS` stays snake_case; anything else is camel-cased by the generic helper, which leaves a key without an underscore unchanged. [zcc.sdk-python.wire-keys:resolution-order] So keys the set lists but a model declares in camelCase, such as `enable_zia_dr`, `truncate_large_udpdns_response` and `purge_kerberos_preferred_dc_cache`, go out as `enableZiaDR`, `truncateLargeUDPDNSResponse` and `purgeKerberosPreferredDCCache`; the set's membership does not decide the wire key. [zcc.sdk-python.wire-keys:snake-list-not-decisive] The attribute-to-wire-key map is found by running the model's `request_format` against a tracing object, so only entries whose value is a direct `self.<attr>` reference are mapped; literal or computed values are skipped. [zcc.sdk-python.wire-keys:field-map-traced] A nested dict or list whose key the model ties to a nested model class is serialized against that class; one with no declared class goes through the older selective camel-case converter instead. [zcc.sdk-python.wire-keys:nested-fallback] Two ZCC writes use the serializer: `web_policy_edit` with the `WebPolicy` model and `update_forwarding_profile` with the `ForwardingProfile` model. `zcc_to_wire` returns a `_ZccWireBody`. When the endpoint contains `/zcc/` (both modules' base endpoint is `/zcc/papi/public/v1`), the executor returns such a body as a plain dict with no key conversion, and any other non-empty dict body gets the selective camel-case conversion. [zcc.sdk-python.wire-keys:serializer-callers] No other ZCC method in the Python SDK calls the serializer. [zcc.sdk-python.wire-keys:serializer-callers-only-two] On the legacy ZCC client, every ZCC body, a serialized `_ZccWireBody` included, is camel-cased in full by the generic helper, where only FIELD_EXCEPTIONS entries such as `exit_password` stay as mapped, so snake_case wire keys such as top-level `device_type` and `pac_url` and the Windows `disable_password` and `install_ssl_certs` go out camelCase. [zcc.sdk-python.wire-keys:legacy-client-full-camel-case] Its effect on web policy writes is [On the OneAPI client, the Python SDK's web policy write converts snake_case input to the wire key each nested model class declares, so the same attribute can leave in different casings depending on the block, and it keeps keys listed in `WebPolicy.SNAKE_CASE_KEYS` in snake_case when the model does not declare them.](kb:zcc.api.web-policy-wire:python-per-class-serializer), and the casing disagreement it produces is [zcc.api.web-policy-wire:os-password-key-casing](kb:zcc.api.web-policy-wire:os-password-key-casing). Its effect on forwarding profile writes is [The Python SDK's `update_forwarding_profile` renames keys the model declares to their wire keys, keeps wire-form keys and the legacy snake_case set (`WebPolicy.SNAKE_CASE_KEYS`) unchanged, camel-cases any other key, and stores each value under its new key; a nested value is passed through the same key conversion.](kb:zcc.api.forwarding-profile-wire:python-keys-only).

**Platform blocks.** The Python `WindowsPolicy` model reads and writes `install_ssl_certs` and `disable_password` in snake_case, where the Linux model uses `installCerts` and `disablePassword`. [zcc.sdk-python.wire-keys:windows-reads-snake] The Python `MacOSPolicy` model reads the password from `disablePassword` but writes it as `disable_password`, and reads and writes the certificate setting as `installCerts`. [zcc.sdk-python.wire-keys:mac-read-write-asymmetry]

**Results read back.** The `WebPolicy` model reads `device_type`, `pac_url` and `reauth_period` under snake_case keys. [zcc.sdk-python.wire-keys:web-policy-snake-reads] `form_response_body` passes every key of a response through `to_lower_camel_case`, so a model attribute looked up under a snake_case key is not found on that path unless FIELD_EXCEPTIONS yields that key: `exit_password` maps to itself, and the camelCase `tunnelTwoForiOSDevices` maps to `tunnel_two_fori_os_devices`; `list_by_company` for web policies instead reads the response with `get_results()`. [zcc.sdk-python.wire-keys:response-keys-camel-cased] So the `WebPolicy` returned by `web_policy_edit` or `activate_web_policy`, built through `form_response_body`, has `device_type`, `pac_url`, `reauth_period` and the Windows `install_ssl_certs` and `disable_password` as None even when the response carries them, while the same policy read with `list_by_company` has them. [zcc.sdk-python.wire-keys:edit-result-loses-snake-keys]

**The parameter mapper.** `zcc_param_mapper` turns `os_type`/`os_types` and `registration_type`/`registration_types` names, and `device_type` names or integers, into numeric codes, converts each to a string with `str` and joins them with commas (so `deviceType` holds the string "3", not the integer 3), formats `start_date` and `end_date`, and moves `time_zone` to `Time-Zone`. [zcc.sdk-python.wire-keys:param-mapper] For `os_type`, the mapper keeps a string only when its lower-cased form is a platform name in its map, and raises ValueError when nothing is kept; for `device_type`, it keeps such names and integers (`isinstance(dt, int)`), and raises ValueError likewise. A numeric string such as "3" is neither, so it raises ValueError, although the `list_devices` and `activate_web_policy` docstring examples pass "3" and '3'. [zcc.sdk-python.wire-keys:numeric-strings-rejected] The mapper reads `query_params` only from keyword arguments, so a dict passed positionally is not mapped: a decorated method such as `list_devices` passes it on as the request's params, the request executor camel-cases its keys, and `{"os_type": "windows"}` goes out as `osType=windows`, the name not converted to its numeric code. [zcc.sdk-python.wire-keys:mapper-keyword-only] The download calls lose their filters to it: [Called with `query_params=` as a keyword, the Python `download_devices` and `download_service_status` send no OS or registration filter: the decorator replaces `os_types` and `registration_types` in that dict with `osTypes` and `registrationTypes`, and the method then builds its request parameters only from `os_types` and `registration_types`. Passed positionally, the dict skips the decorator's mapping and the method translates it itself.](kb:zcc.devices.exports:python-keyword-filters-dropped).

What to check:
1. Whether a missing value on a Python web policy came from the `web_policy_edit` or `activate_web_policy` result rather than from `list_by_company`, which keeps snake_case keys.
2. Whether an `os_type` or `device_type` was given as a numeric string, which the mapper rejects, and whether `query_params` was passed by keyword so the mapper saw it.
3. Which ZCC write the call made, since only the web policy and forwarding profile writes go through the model serializer.
