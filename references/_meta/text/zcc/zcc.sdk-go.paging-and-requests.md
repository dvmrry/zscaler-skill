# How the Go SDK sends ZCC requests and pages v1 and v2 lists (zcc.sdk-go.paging-and-requests)
Also called: NewZccRequestDo; zcc ReadAllPages; zcc ReadAllPagesV2; QueryParamsV2 skip perPage; GetDeviceTypeByName; zcc go pagination; zcc IntOrString

Go ZCC services are package functions that take a `*zscaler.Service`. Most go through `NewZccRequestDo`; some reads and deletes use the generic path: [Several ZCC services read or delete through the generic path: device details, trusted networks (v2), notification templates, ZIA posture, forwarding profiles, and web policies.](kb:zcc.sdk-go.legacy-routing:zcc-services-use-generic-path). Function names and endpoints are generated: run `node scripts/kb.mjs surface <package>`.

**The request helper.** `NewZccRequestDo` encodes its options struct as query parameters, JSON-marshals the body, sends the request, and decodes the response body into the target value when one is passed. [zcc.sdk-go.paging-and-requests:request-do-decodes] The response it hands back is synthetic: [The ZPA, ZCC and ZDX request helpers discard the response object that `ExecuteRequest` returns and build a new `http.Response` holding only `StatusCode: http.StatusOK` and the body. Whatever success status the API sent, such as Created or No Content, reaches the caller as `http.StatusOK`, and response headers are lost.](kb:shared.sdk-go.request-handling:request-do-fabricates-200) Methods that pass it pre-marshaled bytes send an empty object: [`NewZccRequestDo` JSON-marshals its `body` argument unconditionally on the OneAPI (non-legacy) path, and four SDK methods (admin-user update, both entitlement updates, manage-pass update) pass it a `bytes.NewBuffer` of bytes they have already marshaled. A `*bytes.Buffer` has no exported fields, so it marshals as `{}`, and the request carries an empty object instead of the payload.](kb:shared.sdk-go.request-handling:zcc-request-do-double-marshals) The Go legacy ZCC client also JSON-encodes whatever body it is given, so the four methods that pass an already-marshaled `bytes.Buffer` (admin-user update, both entitlement updates, manage-pass update) send an empty object in legacy mode as well as on the OneAPI path. [zcc.sdk-go.paging-and-requests:legacy-body-encoded-again] The legacy ZCC Go client builds `zccRateLimiter` with `NewRateLimiter(100, 3, 3600, 86400)` and passes it to its `getHTTPClient`, but that function never uses the limiter, so the legacy ZCC client applies no client-side rate limit. [zcc.sdk-go.paging-and-requests:legacy-zcc-limiter-not-installed] In legacy mode it routes as described in [ZCC SDK calls in legacy-client mode routed to the ZIA client](kb:zcc.sdk-go.legacy-routing).

**v1 lists.** How the v1 helper pages and stops is [The ZCC v1 list helper (`ReadAllPages`) clamps the page size (0 or less becomes 50, more than 5000 becomes 5000), starts at page 1 and stops at the first page with fewer items than it asked for; the device list calls it with a page size of 1000.](kb:shared.sdk-go.list-pagination:zcc-v1-stops-on-page-shorter-than-requested) and [Because the ZCC v1 helper stops only on a short page, a list whose size is an exact multiple of the page size costs one more request that returns an empty page.](kb:shared.sdk-go.list-pagination:zcc-v1-extra-request). `common.ReadAllPages` applies any JMESPath filter from the context only after all pages are collected. [zcc.sdk-go.paging-and-requests:v1-readallpages] The v1 helper backs the Go reads of admin roles, admin users, the fail-open policy, ZDX and ZPA group entitlements, and devices. [zcc.sdk-go.paging-and-requests:v1-callers] The forwarding-profile list makes one request: [The ZCC forwarding-profile list call makes one GET to `listByCompany` with optional `page` and `pageSize` and returns that single response; it does not walk pages. The provider's Read, and its post-create and post-update lookups, call it with no page or page size.](kb:shared.sdk-go.list-pagination:zcc-forwarding-profile-single-request).

**v2 lists.** The v2 query keys and list envelope are [The Go SDK pages v2 lists by offset with the query parameters `skip` and `perPage`, searches with `keyword`, and adds per-family filters: `type` for trusted networks and `platformType` for ZIA posture profiles.](kb:zcc.api.v2-wire:offset-query) and [The Go SDK's model says every v2 list endpoint wraps its records in an object with `items`, `total`, `offset`, `limit` and `count`, unlike the v1 lists, which it describes as bare JSON arrays.](kb:zcc.api.v2-wire:list-envelope). The page size it sends is [The ZCC v2 drain helper clamps its page size like the v1 helper (0 or less becomes 50, more than 5000 becomes 5000), and all three v2 callers pass the default of 50. The single-page `ReadPageV2` turns 0 or less into 50 but does not cap a larger value.](kb:shared.sdk-go.list-pagination:zcc-v2-page-size). How the v2 helper advances and stops is in [The ZCC v2 helper advances `Skip` by the page size it asked for, after a page that is neither empty, short against `Limit`, nor past `Total`. It never advances by the returned `Count` or `Limit`.](kb:shared.sdk-go.list-pagination:zcc-skip-advances-by-requested-size) and [Two of the ZCC v2 helper's three exits depend on envelope metadata: `Limit > 0` for the short-page check and `Total > 0` for the total check. A non-empty page whose `limit` and `total` are 0 triggers neither, so the helper keeps requesting pages until one comes back empty. The first exit, `Count == 0`, needs no metadata beyond `count`: a server that omits `count` stops the walk after one page.](kb:shared.sdk-go.list-pagination:zcc-guards-need-envelope-metadata); its callers are [Three ZCC SDK services read through the v2 helper: notification templates, trusted networks (v2) and ZIA posture profiles.](kb:shared.sdk-go.list-pagination:zcc-v2-callers).

**Values.** `common.GetDeviceTypeByName` turns a platform name, in any case, into its number (ios 1, android 2, windows 3, macos 4, linux 5), also accepts the numeric strings 1 to 5, returns 0 with no error for an empty string, and errors on anything else. [zcc.sdk-go.paging-and-requests:device-type-by-name] The shared `common.IntOrString` always marshals as a JSON number and decodes a number, a numeric string, null or an empty string (the last two as 0). Its comment says every ZCC write endpoint wants the number, and that quoted integers on the web-policy `/edit` endpoint fail silently with `{"success":"false","id":0}`. [zcc.sdk-go.paging-and-requests:common-intorstring] Fractions are truncated: [The shared ZCC `IntOrString` type accepts a fractional JSON number or quoted number and truncates it to an integer with `int(f)` or `int(parsed)`, dropping the fraction. The code comment says the intent was values like `1.0`, but there is no check that the value is whole.](kb:zcc.terraform.field-fidelity:intorstring-truncates-fractions).

What to check:
1. Whether a v1 list was drained with `ReadAllPages` or fetched as one page, and whether a v2 list carried paging metadata.
2. Whether a v2 call was given `page` or `search` keys, which v2 endpoints do not read.
