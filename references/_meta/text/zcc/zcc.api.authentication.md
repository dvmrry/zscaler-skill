# Reaching and signing in to the ZCC API: OneAPI gateway and legacy login (zcc.api.authentication)
Also called: zcc api authentication; zcc legacy login; zcc api key secret key; zcc jwtToken; zcc auth-token header; api-mobile zcc; zcc api base url; zcc api not enabled; zcc postman ZCCBaseUrl; zcc postman doubled papi public

The ZCC API is reached two ways: through the OneAPI gateway with a bearer token, or through the legacy Mobile Admin Portal login with an API key and secret. This subject records where each path lives and how its token is presented.

**Enabling the API.** Availability of the Zscaler Client Connector API is limited: the organization must have it enabled by contacting Zscaler Support or the account team, and must add an API key, before using it. [zcc.api.authentication:api-must-be-enabled]

**OneAPI path.** On the OneAPI path the ZCC API is served from the gateway host `https://api.zsapi.net` under `/zcc/papi/public/v1`: the captured contract's server is `https://api.zsapi.net/zcc` with paths under `/papi/public/v1`, and the Python SDK's default base URL is `https://api.zsapi.net` with ZCC endpoints prefixed `/zcc/papi/public/v1`. [zcc.api.authentication:oneapi-base-url] [The Python SDK sets the `Authorization` header to `Bearer` plus the OAuth access token when the client is not a legacy client and the endpoint does not contain `/zscsb`.](kb:shared.sdk-python.client-configuration:bearer-header) The OneAPI credential variables and token endpoint are common to the Python SDK: [The Python SDK reads OneAPI credentials from the environment variables ZSCALER_CLIENT_ID, ZSCALER_CLIENT_SECRET, ZSCALER_VANITY_DOMAIN, ZSCALER_CLOUD and ZSCALER_PARTNER_ID, and a private key from ZSCALER_PRIVATE_KEY.](kb:zia.sdk-python.authentication:oneapi-env-vars), [The vanity domain is the organization's Zidentity domain, and for the production cloud the OAuth token endpoint is built from it as https://<vanity_domain>.zslogin.net/oauth2/v1/token.](kb:zia.sdk-python.authentication:vanity-domain-token-url). Which roles or scopes an API client needs for ZCC is open [gap:zcc.api.authentication:oneapi-zcc-scopes].

**API keys.** An API key is required for the publicly available Client Connector APIs; it consists of a client ID and a client secret, both required for authentication. [zcc.api.authentication:api-key-parts] Generating an API key only occurs in the Admin Console from the Public API page (Administration > API > Client Connector API), where keys can be added, listed, copied to the clipboard, edited and deleted. Client IDs are always accessible from the page; client secrets are only displayed when the key is first created and are not available in the saved configuration. [zcc.api.authentication:api-key-page] Adding a key takes a Name (alphanumeric, no spaces, at most 50 characters), a Status (enabled by default; if Disabled is selected the key is unavailable to use), a Role of Read or Write access, and a Session Validity Interval (in seconds), the amount of time the key is available to use, in a range from 30 to 999,999,999 seconds. [zcc.api.authentication:api-key-fields] The Adding an API Key page says using an API key is available for Client Connector version 3.6 and later for Windows. [zcc.api.authentication:api-key-version] To obtain API keys or secrets for Zscaler OneAPI endpoints, the API key management page points to About API Clients in Authentication Service. [zcc.api.authentication:oneapi-elsewhere] How the Session Validity Interval relates to the legacy token's expiry [gap:zcc.api.authentication:session-validity-vs-token-expiry], what Read and Write allow per endpoint [gap:zcc.api.authentication:key-role-scope], what the version line means for a portal API key [gap:zcc.api.authentication:api-key-version-meaning] and whether disabling a key revokes issued tokens [gap:zcc.api.authentication:disable-revocation] are not stated. The roles an admin needs for the page are in [The Administration section's settings, each given a permission, are Client Connector App Store, Client Connector Notifications, Audit Logs, Forwarding Profile, Trusted Networks, Client Connector Support, Zscaler Service Entitlement, User Agent, Client Connector IdP, Device Posture, Business Continuity, Application Bypass Info, Dedicated Proxy Port, Public API, Platform Settings (formerly Authentication Settings), Device Groups, Private Access Partner Logins, Location-Based Policies and Administration Management. Admins must have full access to configure settings.](kb:shared.admin-rbac.zcc:administration-settings).

**Postman.** The OneAPI Postman collection defines `ZCCBaseUrl` as `{{oneAPIBaseUrl}}/zcc/papi/public`, with `oneAPIBaseUrl` set to `https://api.zsapi.net`; its "Client Connector" folder has requests such as `{{ZCCBaseUrl}}/v1/getDevices`, which resolves to `https://api.zsapi.net/zcc/papi/public/v1/getDevices`. [zcc.api.authentication:postman-base-url] The collection's second ZCC folder, "Zscaler Client Connector", writes the contract's full paths after the same variable, as in `{{ZCCBaseUrl}}/papi/public/v1/getDevices` and `{{ZCCBaseUrl}}/papi/auth/v1/login`; with the collection's own `ZCCBaseUrl` these resolve to `https://api.zsapi.net/zcc/papi/public/papi/public/v1/getDevices`, a doubled `/papi/public` that matches neither the contract server plus path (`https://api.zsapi.net/zcc` + `/papi/public/v1/getDevices`) nor the "Client Connector" folder's form. [zcc.api.authentication:postman-doubled-prefix]

**Legacy login.** The legacy API is signed in to with a POST to `/papi/auth/v1/login` carrying `apiKey` and `secretKey`; the response's `jwtToken` is the token passed on subsequent calls. [zcc.api.authentication:legacy-login-request] The legacy authentication token expires after 3600 seconds (one hour) by default. [zcc.api.authentication:legacy-token-expiry] The client secret of an API key can be copied only when the key is first created: the legacy getting-started page says it is accessible only in the Client Connector Portal then, and the Adding and Editing an API Key pages say it is not available by editing the key or in the Admin Console after the window is closed. [zcc.api.authentication:legacy-secret-shown-once] The Python SDK's LegacyZCCClient takes its API key and secret key from the environment variables ZCC_CLIENT_ID and ZCC_CLIENT_SECRET. [zcc.api.authentication:legacy-zcc-env] Whether ZCC_API_KEY is also read is open [gap:zcc.api.authentication:zcc-api-key-env].

On the legacy path the JWT is sent in an `auth-token` request header: the help article's example uses `auth-token`, and both SDKs' legacy ZCC clients set that header. [zcc.api.authentication:legacy-auth-token-header] The legacy host differs between the help article and the SDKs [divergence:zcc.api.authentication:legacy-host].

In the Go SDK's legacy mode, some ZCC calls are sent through the ZIA client: [ZCC SDK calls in legacy-client mode routed to the ZIA client](kb:zcc.sdk-go.legacy-routing).

3. Which host a legacy script logs in to, against the api-mobile or mobile hostnames the sources give.
4. Whether a request copied from the Postman "Zscaler Client Connector" folder went out with a doubled `/papi/public` in its URL.

Sources disagree (name both sides):
- Which host serves the legacy login and API: the help article uses `mobile.<cloudName>.net`, while both SDKs use `api-mobile.<cloud>.net` (Python maps the zscalerten cloud to `mobile6`). [divergence:zcc.api.authentication:legacy-host]
  - zscaler-help: The help article's sign-in example posts to `https://mobile.<cloudName>.net/papi/auth/v1/login`.
  - sdk-python: The Python legacy client builds `https://api-mobile.<cloud>.net` and logs in at `/papi/auth/v1/login`, except that the zscalerten cloud uses the `mobile6` subdomain.
  - sdk-go: The Go legacy client builds `https://api-mobile.<cloud>.net/papi` and logs in at `/auth/v1/login` under it.
  Impact: A legacy script built from the help article targets a different hostname from the SDKs. Which of `mobile` and `api-mobile` a given cloud answers on, and whether the OneAPI gateway, under which the captured contract lists every operation, accepts the legacy login, is not settled by these sources.
