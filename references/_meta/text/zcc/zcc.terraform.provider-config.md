# Configuring the ZCC Terraform provider: OneAPI credentials, environment variables and defaults (zcc.terraform.provider-config)
Also called: zcc provider credentials; zcc_client_id not supported; zcc terraform legacy auth; ZSCALER_VANITY_DOMAIN zcc; zcc provider max_retries default; zcc provider zscalergov; zcc client_secret private_key conflict

The provider's own arguments, their types and descriptions are generated: run `node scripts/kb.mjs surface provider:zcc`. This subject holds how they are resolved and what the code does that the schema does not show.

**OneAPI only.** The provider documentation says it authenticates only through OneAPI OAuth2 via Zidentity, offers no legacy path (`zcc_client_id`, `zcc_client_secret` and `zcc_cloud` are not supported), and that tenants must be migrated to Zidentity before the provider can manage them. [zcc.terraform.provider-config:oneapi-only-docs] The documentation says OneAPI and Zidentity are not currently supported for the `zscalergov` and `zscalerten` clouds. [zcc.terraform.provider-config:gov-clouds-unsupported] The SDK's environment switch can still put it in legacy mode: [The ZCC Terraform provider is built for the OneAPI flow only, so it does not normally inherit this defect. The SDK still reads `ZSCALER_USE_LEGACY_CLIENT` from the environment and the provider does not override it, so setting that variable would switch the provider into legacy mode. The provider never builds a legacy client and the SDK then skips OneAPI authentication, so every ZCC call, on the ZCC request path as well as the generic one, returns `errLegacyClientNotSet`.](kb:zcc.sdk-go.legacy-routing:zcc-provider-oneapi-only).

**Credentials.** Each credential and connection argument left unset in the provider block is read from an environment variable: `ZSCALER_CLIENT_ID`, `ZSCALER_CLIENT_SECRET`, `ZSCALER_PRIVATE_KEY`, `ZSCALER_VANITY_DOMAIN`, `ZSCALER_CLOUD` and `ZSCALER_HTTP_PROXY`. [zcc.terraform.provider-config:env-fallback] The client is built only from a client ID and a vanity domain together with either a client secret or a private key; otherwise configuration fails with 'invalid authentication configuration: missing required parameters'. The cloud is passed only when set. [zcc.terraform.provider-config:auth-combination] The documentation says `zscaler_cloud` is optional and needed only when authenticating to other environments such as `beta`. [zcc.terraform.provider-config:cloud-optional] The SDK loads `ZSCALER_PRIVATE_KEY` (and `~/.zscaler/zscaler.yaml`) into its own configuration and authenticates with a JWT whenever a private key is present, so a key in the environment wins even when the provider took the secret branch. In that case a file path in the variable is used as the key text, because the provider's `WithPrivateKey`, which reads a path, is not called. [zcc.terraform.provider-config:sdk-env-key-preferred] The documentation says the secret and the private key conflict, but the code does not enforce it [divergence:zcc.terraform.provider-config:secret-key-conflict].

**Retries and timeouts.** When unset, the code uses 100 retries, a 240-second request timeout, and a minimum and maximum retry wait of 2 and 10 seconds. An explicit 0 is replaced the same way, so `request_timeout = 0` becomes 240 seconds and `max_retries = 0` becomes 100. [zcc.terraform.provider-config:code-defaults] The documented defaults are different [divergence:zcc.terraform.provider-config:retry-timeout-defaults]. How the SDK applies these options and the proxy is in [In the OneAPI option list of each audited provider (ZIA, ZPA, ZTC, ZCC), the proxy options are appended after the timeout and rate-limit options that rebuild the clients, and none of the four sets the TLS-skip option. The configured proxy host and port are therefore recorded in the configuration but absent from the transports that carry service requests; a proxy set through the standard environment variables is unaffected, because the transport defaults to reading them. The SDK's own `ZSCALER_CLIENT_PROXY_HOST` and `ZSCALER_CLIENT_PROXY_PORT` environment variables are read before the first client build and do take effect, and the default transport still honors `HTTP_PROXY`/`HTTPS_PROXY`; only the proxy passed through the provider's configuration is lost.](kb:shared.sdk-go.request-handling:providers-append-proxy-after-rebuilds), and which SDK release each provider build carries is [Which SDK each audited provider build carries decides whether it has the v3.8.43 fix: ZIA provider 4.8.3 uses v3.8.44 (fixed); ZPA 4.4.10 uses v3.8.42, ZCC 0.1.0-beta.1 uses v3.8.37, and ZTC 0.2.0 uses v3.8.40 (all before the fix). ZTC 0.2.0 is still the pinned ZTC release.](kb:shared.sdk-go.retries:provider-sdk-pins).

What to check:
1. Whether the tenant is on Zidentity and a OneAPI cloud, since the provider has no legacy ZCC login and the government clouds are not supported.
2. Whether both a client secret and a private key are set, in configuration or the environment, and which one is in `ZSCALER_PRIVATE_KEY`, since nothing warns about the combination and a key in the environment wins.
3. Whether a slow failure came from the code's retry budget of 100 and 240-second timeout rather than the documented 5 and no limit.

Sources disagree (name both sides):
- Whether `client_secret` and `private_key` may both be set: the documentation says they conflict, while the code has no conflict check; the provider passes the secret when both are present, but the SDK still prefers a key it reads from the environment. [divergence:zcc.terraform.provider-config:secret-key-conflict]
  - tf-zcc: The argument reference says `client_secret` conflicts with `private_key`.
  - tf-zcc: The client builder tests the secret combination first and passes only the secret to the SDK when both are set, without an error; the SDK still authenticates with a key it reads from the environment itself (sdk-env-key-preferred).
  Impact: A private key set only in the provider block is silently unused when `ZSCALER_CLIENT_SECRET` is also in the environment. In reverse, a secret set in the provider block is ignored when `ZSCALER_PRIVATE_KEY` is in the environment, because the SDK authenticates with that key, and a key path there is used raw rather than read from the file. Both matter when rotating between secret and key authentication.
  Resolved (source-rank) by zcc.terraform.provider-config:auth-combination: The code decides what the provider does; the documentation states an intent the schema does not enforce.
- The defaults for `max_retries` and `request_timeout`: the documentation says 5 retries and a timeout of 0 (no limit, at most 300), while the code uses 100 retries and 240 seconds. [divergence:zcc.terraform.provider-config:retry-timeout-defaults]
  - tf-zcc: The argument reference gives a `max_retries` default of 5 and a `request_timeout` default of 0, meaning no limit, with a maximum of 300.
  - tf-zcc: The configure code defaults the retry count to 100 and the request timeout to 240 seconds.
  Impact: An apply against a rate-limited or unreachable API can keep retrying far longer than the documentation suggests. Set both arguments explicitly, and non-zero, when the bound matters: an explicit `request_timeout = 0`, documented as no limit, becomes 240 seconds, and `max_retries = 0` becomes 100 (code-defaults).
  Resolved (source-rank) by zcc.terraform.provider-config:code-defaults: The code is what runs.
