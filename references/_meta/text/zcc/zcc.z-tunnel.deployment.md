# Rolling out Z-Tunnel 2.0 and migrating from 1.0 (zcc.z-tunnel.deployment)
Also called: z-tunnel 2.0 rollout; migrate z-tunnel 1.0 to 2.0; z-tunnel 2.0 best practices; z-tunnel 2.0 over gre; z-tunnel 2.0 test group

Zscaler publishes two phased procedures, one for a new Z-Tunnel 2.0 deployment and one for a migration from 1.0; they share the first phase.

**Before starting.** Z-Tunnel 2.0 needs a supported Client Connector version. [zcc.z-tunnel.deployment:supported-version]

**Phase 1, test configuration.** Phase 1 starts with a small test group of users; groups configured in Internet & SaaS User Management are available in Client Connector's Directory Sync advanced settings, and can also be synced manually. [zcc.z-tunnel.deployment:test-group] The vendor recommends a new forwarding profile for the test with the Packet Filter-Based driver, Tunnel on On-Trusted Network, Z-Tunnel 2.0 selected, and VPN-Trusted and Off-Trusted set to Same as On-Trusted Network, changing the other network types only after initial testing. [zcc.z-tunnel.deployment:test-forwarding-profile] The test app profile has rule order 1 so the test users receive it first, is enabled, selects the test forwarding profile, enables Install Zscaler SSL Certificate, targets the test group, and leaves the Custom PAC URL and the logout and disable passwords empty; a Client Connector Store app update can be configured to assign the test users a supported version. [zcc.z-tunnel.deployment:test-app-profile]

**GRE sites.** Zscaler says not to route Z-Tunnel 2.0 through GRE tunnels; to prevent performance issues where GRE exists, either have the forwarding profile fall back to Z-Tunnel 1.0 when the trusted network criteria are met, or exclude Z-Tunnel 2.0 traffic from the GRE tunnel with a policy-based route. [zcc.z-tunnel.deployment:gre-guidance] Why several GRE egress IPs also break Z-Tunnel 2.0 setup is in [A site whose egress uses several GRE tunnels with different public source IPs, or ECMP, can present one device's Z-Tunnel 2.0 control and data connections from different IPs; per the vendor that splits them across Service Edges and Z-Tunnel 2.0 falls back to 1.0.](kb:zia.traffic-forwarding.mixed-deployments:gre-ztunnel2-egress).

**New deployment, phases 2 to 5.** A new deployment then blocks ICMP with a firewall rule and confirms the block in the logs (phase 2), adds internal network ranges to the app profile's IPv4 or IPv6 exclusions (phase 3), tests the top business applications with the group for one to two weeks (phase 4), and rolls out to everyone else in batches of 100 to 200 users, checking business applications after each (phase 5). [zcc.z-tunnel.deployment:deploy-phases]

**Migration, phases 2 to 6.** A migration copies the VPN gateway bypasses from the old app profile to the Z-Tunnel 2.0 app profile (phase 2), gathers the network address and range bypasses from the old app profile PAC and adds them to Destination Exclusions (phase 3), adds URL and domain bypasses gathered from the old app profile PAC to a new forwarding profile PAC that returns the Z-Tunnel 2.0 bypass and a new app profile PAC that returns DIRECT (phase 4), tests (phase 5), and rolls out in batches of 100 to 200 users (phase 6). [zcc.z-tunnel.deployment:migration-phases] The PAC statements those steps use are in [On Windows 3.7 and earlier, a domain bypass needs two PAC files: the forwarding profile PAC returns `PROXY ${ZAPP_TUNNEL2_BYPASS}` for the domain (the vendor's example then falls through to DIRECT for all other traffic, which its comment says tunnels using Tunnel2), and the app profile PAC returns DIRECT for the same domain.](kb:zcc.z-tunnel.bypasses:dual-pac).

What to check:
1. Whether on-premises users of a GRE site send Z-Tunnel 2.0 inside the GRE tunnel; if so, the profile's On-Trusted action or a policy-based route should keep it out.
2. For a migration: whether the VPN gateway bypasses, PAC network bypasses and PAC domain bypasses of the old app profile were all carried to their Z-Tunnel 2.0 places.
