# Z-Tunnel 2.0 transport: DTLS and TLS, fallback, MTU, and what happens when the tunnel cannot be set up (zcc.z-tunnel.transport)
Also called: dtls or tls; z-tunnel 2.0 transport; primary transport selection; allow tls fallback; z-tunnel 2.0 setup failure behavior; tunnel2FallbackType; mtu for zscaler adapter; z-tunnel 2.0 udp 443 blocked; dtls instability
Former IDs: zcc-101

Selecting Z-Tunnel 2.0 in a forwarding profile opens its advanced settings, which decide how the tunnel connects and what happens when it cannot.

**DTLS or TLS.** Primary Transport Selection sets how Z-Tunnel 2.0 connects to the cloud: DTLS over UDP port 443 or TLS over TCP port 443. [zcc.z-tunnel.transport:primary-transport] Client Connector 4.3 and later for iOS supports Z-Tunnel 2.0 over TLS; DTLS is not supported on iOS. [zcc.z-tunnel.transport:ios-tls-only] The DTLS and TLS connection timeouts, 5 to 60 seconds each, set how long the app waits before falling back to another transport. [zcc.z-tunnel.transport:connection-timeouts] Allow TLS Fallback (Windows 3.4+, macOS 3.9+, iOS 4.3+) applies when DTLS is the primary transport: if the app cannot connect with DTLS, it tries TLS. [zcc.z-tunnel.transport:tls-fallback] With DTLS primary and TLS fallback on, Enable DTLS Instability Detection and Fallback makes the app watch the DTLS connection and switch to TLS when it detects a data-rate restriction such as throttling; it applies only to Windows 4.8 and later and must be enabled by Zscaler Support. [zcc.z-tunnel.transport:dtls-instability] The integer that encodes the transport is open in [ZCC forwarding profile calls: integer codes, read and write types, and where the contract and SDKs differ](kb:zcc.api.forwarding-profile-wire).

**MTU.** MTU for Zscaler Adapter (client 2.1.2+) sets the Z-Tunnel 2.0 inner packet MTU between 800 and 1400 (1300 to 1400 for IPv6); the setting defaults to 0, and the default MTU is 1400 for a direct connection and 1360 behind GRE or 1300 behind IPSec tunnels. [zcc.z-tunnel.transport:mtu] On Windows, Z-Tunnel 2.0 in DTLS mode adjusts the TCP MSS from the configured MTU, because it uses the Windows filter driver rather than the Zscaler adapter. [zcc.z-tunnel.transport:windows-mss] Path MTU Discovery makes the app discover the optimal path MTU for Z-Tunnel 2.0, and can be used even with a configured adapter MTU. [zcc.z-tunnel.transport:pmtud]

**When Z-Tunnel 2.0 cannot be set up.** Z-Tunnel 2.0 Setup Failure Behavior (client 3.4+) chooses what happens when the app must switch away from Z-Tunnel 2.0: fall back to Z-Tunnel 1.0 for web traffic and bypass everything else; fall back to Z-Tunnel 1.0 for web traffic and block all other traffic except DNS; or block all traffic except DNS and control-channel traffic to the Zero Trust Exchange for policy, PAC files and software updates. [zcc.z-tunnel.transport:setup-failure-behavior] Send All DNS During Fail-Close to Trusted-DNS Server sends DNS to configured IPv4 and IPv6 servers during a Z-Tunnel 2.0 failure, or, with none entered, to the request's original or the system's first DNS server; it applies to Windows 4.7 with the bypass or block-all failure options and must be enabled by Zscaler Support. [zcc.z-tunnel.transport:fail-close-dns] The Terraform provider documents the action field `tunnel2_fallback_type` (wire `tunnel2FallbackType`) as the behavior when the Tunnel 2.0 transport fails, without listing its values. [zcc.z-tunnel.transport:fallback-field] Which code is which option is open [gap:zcc.z-tunnel.transport:fallback-type-values].

Why setup fails behind a multi-IP NAT is in [Z-Tunnel 2.0 needs a NAT device that uses a single IP for all connections from one device; otherwise control and data connections can land on different Service Edges, Z-Tunnel 2.0 fails to establish and the client falls back to Z-Tunnel 1.0.](kb:zia.traffic-forwarding.zcc:z-tunnel-2-single-ip-nat) and [A site whose egress uses several GRE tunnels with different public source IPs, or ECMP, can present one device's Z-Tunnel 2.0 control and data connections from different IPs; per the vendor that splits them across Service Edges and Z-Tunnel 2.0 falls back to 1.0.](kb:zia.traffic-forwarding.mixed-deployments:gre-ztunnel2-egress); what the vendor does not document about sessions on the Service Edge side is open [gap:zcc.z-tunnel.transport:session-internals]. The tenant-wide failover settings are in [Client Connector fail-open: captive portals, unreachable Service Edges and tunnel failures](kb:zcc.forwarding-profiles.fail-open).

What to check:
1. Whether UDP 443 is allowed out of the user's network when DTLS is the primary transport, and whether Allow TLS Fallback is on for the client version in use.
2. Which Z-Tunnel 2.0 Setup Failure Behavior the profile uses before explaining blocked non-web traffic.
