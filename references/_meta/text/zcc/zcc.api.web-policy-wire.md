# What goes on the wire for ZCC web policies (app profiles): /web/policy/edit and activate (zcc.api.web-policy-wire)
Also called: zcc web policy edit; web/policy/edit success false id 0; zcc app profile api; zcc web policy snake_case keys; disable_password install_ssl_certs; ziaDRMethod ziaDRRecoveryMethod; zcc device_type number; web policy duplicate name; zcc web policy 400 extra os block; pac_url snake case; install_ssl_certs vs installCerts; web policy success false; IntOrString; SNAKE_CASE_KEYS; ziaDRMethod; ziaDRRecoveryMethod; web policy payload; web_policy_edit; UpdateWebPolicy; activate_web_policy; ActivateWebPolicy; web policy activate; create app profile api; application-profiles patch; GetWebPolicyByID; zcc device_type values
Former IDs: zcc-77, zcc-78, zcc-79, zcc-88, zcc-89, zcc-90, zcc-98

A ZCC web policy is the API object behind an app profile, written per platform through one edit endpoint. Its body mixes camelCase and snake_case keys, numbers and quoted strings, and form-state objects copied from the admin UI, and the sources disagree about several of them.

## Create, update and activate

One endpoint, `PUT /web/policy/edit`, adds or updates a policy or app profile for a platform; the Go SDK's model says the API treats a body with no `id` key as a create. [zcc.api.web-policy-wire:edit-adds-or-updates] The Go SDK models the edit response as a bare object carrying only `success` and the policy `id` (for example `{"success":"true","id":205241}`), and treats any `success` other than "true" as a rejection. [zcc.api.web-policy-wire:edit-response] The Python SDK's release notes record that a create through `/web/policy/edit` with a name that already exists is rejected silently, with `success=false, id=0`, and that a successful call answers `success` "true" with a non-zero `id`. [zcc.api.web-policy-wire:edit-success-and-duplicates] The Terraform provider's maintainer notes say `/web/policy/edit` returns HTTP 200 with `{ "success": "false", "id": 0 }` when the payload contains any combination it does not like, without indicating which field is wrong. [zcc.api.web-policy-wire:edit-rejects-silently] The Go SDK calls no get-by-ID endpoint: `GetWebPolicyByID` lists the platform's policies and matches the id, and when a field's JSON type does not fit its struct it returns only id, name, description, device type and active, with a partial-decode error. Its comment says the listing sometimes drops the numeric id of an entry that came from a fresh `/edit` write, and the SDK then fills in the id it was asked for. [zcc.api.web-policy-wire:read-back] How the list encodes a policy's id is open [gap:zcc.api.web-policy-wire:list-id-encoding].

`PUT /web/policy/activate` enables or disables a policy or app profile for a platform; its body is a `deviceType` and a `policyId`. [zcc.api.web-policy-wire:activate] Whether an edit to an enabled policy is served without an activate call is open [gap:zcc.api.web-policy-wire:edit-needs-activate].

The list endpoint's `deviceType` query parameter is an integer; the Python SDK accepts the names `ios`, `android`, `windows`, `macos` and `linux` (or the integer) and sends the integer code as `deviceType`. [zcc.api.web-policy-wire:list-device-type-numeric] The platform codes themselves are [The contract gives numeric platform codes for `osType` on the soft- and force-remove endpoints (`removeDevices`, `forceRemoveDevices`): 1 iOS, 2 Android, 3 Windows, 4 macOS, 5 Linux, where null means all OS types; the Go SDK defines the same device-type constants.](kb:zcc.api.conventions:os-type-codes).

## Body shape

The contract's edit body defines three snake_case top-level keys, `pac_url`, `reauth_period` and `device_type`. The Go struct sends these and nine more at the top level that the contract lacks (`exit_password`, `billing_day`, `allowed_apps`, `custom_text`, `bypass_mms_apps`, `quota_in_roaming`, `wifi_ssid`, `bypass_android_apps` and `install_ssl_certs`), and the Python SDK keeps the same keys in snake_case: its `SNAKE_CASE_KEYS` lists the other eleven, and its key converter maps `exit_password` to itself. [zcc.api.web-policy-wire:snake-case-top-level] The Go SDK's model says the API rejects a web policy body that carries empty blocks for platforms other than its own with a 400, so the Go struct sends only the one platform block that is set. [zcc.api.web-policy-wire:extra-os-blocks-rejected] The Go SDK's model says every web policy write requires integer settings such as `ruleOrder`, `logMode` and `logLevel` as JSON numbers, while the GET response quotes some of them as strings; the SDK writes numbers and reads either form. [zcc.api.web-policy-wire:numbers-on-write] The contract types several of these integers as strings [divergence:zcc.api.web-policy-wire:scalar-types].

The Go SDK's model says many settings appear twice in the body, once at the top level and once inside `policyExtension` or a platform block, sometimes with different types, and that the UI generates both copies and the API expects both. The Go struct names the top-level copy with a `Top` suffix. [zcc.api.web-policy-wire:fields-twice] Among them, the Go SDK's `WebPolicy` struct, which `UpdateWebPolicy` sends as the PUT body, has a top-level `install_ssl_certs` field, alongside `install_ssl_certs` in `MacPolicy` and `installCerts` in `AndroidPolicy`, `LinuxPolicy` and `WindowsPolicy`. [zcc.api.web-policy-wire:go-top-level-install] Which copy wins when the two disagree is open [gap:zcc.api.web-policy-wire:top-vs-nested-precedence].

The Go SDK's model says `/web/policy/edit` expects the UI's `{label, value}` form-state objects (such as `ruleOrderSelectedOption`, `logModeSelected` and `ziaDRMethod`) echoed back in the PUT body, with `value` an integer for some pickers and a string for others. [zcc.api.web-policy-wire:label-value-echo] Whether these form-state fields are required on write is open [gap:zcc.api.web-policy-wire:selected-required]. The Go SDK's model says the API expects a `locationRulesetPolicies` block inside `policyExtension` with both of its entries present even when no ruleset is bound, their `id` then 0. [zcc.api.web-policy-wire:location-ruleset-fixed]

The Python SDK's 1.9.25 release notes describe the edit endpoint as asymmetric: requests carry flat `groupIds` and `userIds` lists, while responses return nested `groups` and `users` objects. The Python model nonetheless sends a caller's `group_ids` and `user_ids` under the keys `groups` and `users`, and reads the response's `groups` as group objects. [zcc.api.web-policy-wire:edit-group-user-asymmetry] The contract, the UI capture, the two SDKs and a recorded edit name a write's target groups and users differently [divergence:zcc.api.web-policy-wire:targeting-keys]. Which scope keys a listing returns on read, and in what element shape, is open [gap:zcc.api.web-policy-wire:scope-keys-on-read].

The Go SDK's model says the API expects all four toggles of `policyExtension.generateCliPasswordContract` (`enableCli` and the ZPA, ZIA and ZDX disable-without-password switches) to be present even when CLI disable is off, and that the UI capture always emits them; the Go struct also sends top-level copies of the ZPA and ZIA switches. The contract's object defines only `enableCli`, `allowZpaDisableWithoutPassword` and `policyId`. [zcc.api.web-policy-wire:cli-password-toggles]

The Go SDK leaves `ziaPostureConfigId` out of a body when unset; its comment gives the reason that a captured create body (`test.json`) does not include it. [zcc.api.web-policy-wire:zia-posture-omitted-on-create]

## Platform blocks

The password and certificate keys inside the per-platform blocks are cased differently by each source [divergence:zcc.api.web-policy-wire:os-password-key-casing]. The Python SDK's five UI captures of web policy bodies write the platform block's disable password as snake_case `disable_password` in every block, and the certificate setting as snake_case `install_ssl_certs` in the Windows, Linux, Android and macOS blocks, with no camelCase copies. [zcc.api.web-policy-wire:ui-capture-password-keys] The Go SDK sends the macOS block's password and certificate keys in snake_case (`disable_password`, `install_ssl_certs`, `logout_password`, `uninstall_password`), with `install_ssl_certs` a JSON number; its model says earlier camelCase tags were silently ignored by the API and produced `{"success":"false","id":0}` on `/edit`. [zcc.api.web-policy-wire:mac-snake-or-ignored] The Go SDK's model says browser auth type, use-default-browser and captive portal config are required by the API for macOS policy creates; the Go macOS block carries them as `browserAuthType`, `useDefaultBrowser` and `captivePortalConfig`. [zcc.api.web-policy-wire:mac-create-required] The Go SDK's model says the registry and other Windows-style top-level keys, such as `registryPath`, `registryName`, `install_ssl_certs` and `overrideWPAD`, are still required in macOS bodies and that the API echoes them; the contract's edit body defines none of these four at the top level. [zcc.api.web-policy-wire:go-windows-keys-on-mac] Which key a listing uses for the macOS block on read is open [gap:zcc.api.web-policy-wire:mac-block-read-key].

The Go SDK's iOS block comment says the password fields are serialized in snake_case, but its struct tags send them in camelCase (`disablePassword`, `logoutPassword`, `uninstallPassword`). The Python SDK's iOS UI capture uses the snake_case key `disable_password` in `iosPolicy`, as the comment says. [zcc.api.web-policy-wire:ios-comment-vs-tags] The Go SDK's model says its iOS UI capture carries a `notificationTemplateContract` block at the web policy root, with its 0/1 flags as quoted strings and its counters as numbers, and that the macOS capture omits it, so the SDK sends the block only when set. The Python SDK's iOS UI capture has no such block. [zcc.api.web-policy-wire:ios-only-blocks] The Go SDK's model says its iOS UI capture carries `ipv6Mode`, `showVPNTunNotification`, `useTunnelSDK4_3` and related keys at the top level as well as inside `iosPolicy`, with `useTunnelSDK4_3` a JSON number at the top level and a quoted string inside `iosPolicy`. The Python SDK's iOS web policy payload fixture (`ios_policy.json`, one of the real payloads its serializer tests use) has none of `ipv6Mode`, `showVPNTunNotification`, `useTunnelSDK4_3` or `deviceType` at the top level. [zcc.api.web-policy-wire:ios-top-level]

On the OneAPI client, the Python SDK's web policy write converts snake_case input to the wire key each nested model class declares, so the same attribute can leave in different casings depending on the block, and it keeps keys listed in `WebPolicy.SNAKE_CASE_KEYS` in snake_case when the model does not declare them. [zcc.api.web-policy-wire:python-per-class-serializer] On the Python legacy client every snake_case key of a web policy body goes out camelCase, in the platform blocks too (`device_type` as `deviceType`, `pac_url` as `pacUrl`, `reauth_period` as `reauthPeriod`, `billing_day` as `billingDay`, Windows `disable_password` as `disablePassword`); only `exit_password`, which the converter maps to itself, keeps its snake_case form. [zcc.api.web-policy-wire:python-legacy-camelcases-web-policy] How that serializer resolves each key is in [How the Python SDK names ZCC keys on the wire: the model serializer and the parameter mapper](kb:zcc.sdk-python.wire-keys).

## Device type

The Go SDK sends the web policy's `device_type` as a JSON number (1 iOS, 2 Android, 3 Windows, 4 macOS, 5 Linux); its model says reads also return a `deviceType` string such as `DEVICE_TYPE_MAC`, which it does not model. [zcc.api.web-policy-wire:device-type-number] The Go web policy struct also has a separate integer field on the `deviceType` key, sent only when non-zero, alongside the `device_type` integer. [zcc.api.web-policy-wire:device-type-alt] Which of the two integer fields a write honours is open [gap:zcc.api.web-policy-wire:devicetype-precedence]. The Python `web_policy_edit` docstring says `device_type` accepts the friendly names `ios`, `android`, `windows`, `macos` and `linux` through `zcc_param_mapper`, but that decorator is commented out on the method, so a name such as `windows` is sent as the string rather than the platform code. [zcc.api.web-policy-wire:python-device-type-names-unmapped] Whether reads actually carry that `deviceType` string is open [gap:zcc.api.web-policy-wire:devicetype-string-on-read].

## Disaster recovery

Both SDKs name the disaster-recovery keys `ziaDRMethod`, `ziaRSAPubKey`, `ziaRSAPubKeyName`, `zpaRSAPubKey` and `zpaRSAPubKeyName`; the Go model says these match a real `/listByCompany` response and that `ziaDRRecoveryMethod` is not the wire name. The Go model also sends a `ziaCustomDbUrl`, which it says custom DR setups use and which the contract does not define. [zcc.api.web-policy-wire:dr-wire-names] The contract still names the older keys [divergence:zcc.api.web-policy-wire:dr-key-names]. The contract and the Go SDK type the disaster-recovery switches (`enableZiaDR`, `enableZpaDR`, `allowZiaTest`, `allowZpaTest`, `useZiaGlobalDb`) as JSON booleans and Go types the DR method as an integer, while the Python `DisasterRecovery` model stores whatever value it is given. [zcc.api.web-policy-wire:dr-flag-types] The Go SDK leaves `policyId`, `ziaGlobalDbUrl`, `ziaGlobalDbUrlv2` and `ziaPacUrl` out of a disaster-recovery block when empty, because its model says the UI never sends them in a fresh create body and they appear only on reads. [zcc.api.web-policy-wire:dr-write-omits] What the disaster recovery settings do is in [App profile failover: disaster recovery, cloud unreachable, captive portals](kb:zcc.app-profiles.failover).

## Field meanings

The Python `web_policy_edit` docstring describes `reactivate_web_security_minutes` (`reactivateWebSecurityMinutes`) as the minutes after which Web Security is reactivated when the user has disabled it. [zcc.api.web-policy-wire:reactivate-minutes-meaning] The Go web policy body carries its own captive-portal and fail-open keys at the top level, `enableCaptivePortalDetection`, `enableFailOpen`, `captivePortalWebSecDisableMinutes` and `captivePortalUrlId`, none of which the contract's edit body defines. [zcc.api.web-policy-wire:go-captive-portal-keys] On Windows 4.5 and later, captive portal detection is set on the app profile: [On Windows 4.5 and later the profile enables captive portal detection; with Fail Open on, the app keeps its services disabled for 1 to 60 minutes after detecting a captive portal and then re-enables them.](kb:zcc.app-profiles.failover:captive-portal). The fail-open policy has its own captive-portal window: [If Captive Portal Detected, Disable Web Security for (In Minutes) takes 1 to 60 minutes, after which the app re-enables its services and forwards traffic to Zscaler; 0 turns captive portal detection off, and the app then does not fail over directly.](kb:zcc.forwarding-profiles.fail-open:captive-portal-minutes).

The contract and the Python docstring disagree on the unit of `reauth_period` [divergence:zcc.api.web-policy-wire:reauth-period-unit] and on what `groupAll` covers [divergence:zcc.api.web-policy-wire:group-all-scope]. The sources also disagree on what `logMode` -1 means [divergence:zcc.api.web-policy-wire:log-mode-minus-one].

## The forwarding profile reference

The app profile write carries the forwarding profile as `forwardingProfileId`, an integer in the API contract's web policy edit request; both SDKs model `forwardingProfileId` on the application profile. [zcc.api.web-policy-wire:join-field] In the API contract's application-profile listing, each policy embeds a forwarding profile object as `onNetPolicy`, with the trusted network criteria and both action lists. [zcc.api.web-policy-wire:onnetpolicy-embedded] The API contract's application-profile listing defines no `forwardingProfileId` member on a policy. [zcc.api.web-policy-wire:listing-lacks-forwarding-profile-id] What a tenant's listing returns is recorded for one tenant only [gap:zcc.api.web-policy-wire:join-on-read]. What the reference selects is in [Which forwarding profile a device uses, and when a change reaches it](kb:zcc.forwarding-profiles.assignment).

## A second surface

A second surface, `/application-profiles`, lists application profile policies, has a GET that takes a profile ID in the path, and patches one by profile ID. The PATCH accepts only an allowlist of properties (bypass, DNS and include or exclude lists, groups and user IDs, passwords, device type), and for arrays and comma-separated strings the existing values must be sent with the new ones. [zcc.api.web-policy-wire:application-profiles-surface] Whether it addresses the same records and IDs as `/web/policy` is open [gap:zcc.api.web-policy-wire:surface-equivalence]. Whether it carries the captive-portal settings is open [gap:zcc.api.web-policy-wire:application-profiles-captive-portal].

Go SDK calls in legacy-client mode route web policy reads and deletes to the wrong client: [ZCC SDK calls in legacy-client mode routed to the ZIA client](kb:zcc.sdk-go.legacy-routing). The Terraform provider has no web policy resource: [The ZCC Terraform provider registers no resource or data source for app profiles or web policies: the per-OS app profile resources and the application profiles data source are intentionally deregistered.](kb:zcc.terraform.coverage:no-terraform-resource).

What to check:
1. Whether an `/edit` that returned HTTP 200 also returned `success` "true" and a non-zero `id`, and if not, whether a policy with the same name already exists.
2. After a successful edit, read the policy back by listing the platform's policies, as the Go SDK does.
3. Send the platform as its integer code, both in the list query and in the activate body.
4. Whether the body carried only the block for its own platform, since extra platform blocks are rejected with a 400.
5. Compare a hand-built body with one the console produced, key for key, before trusting a success response.
6. Which casing the request used for the platform block's password and certificate keys, against what the SDK in use emits for that platform.
7. Whether integer settings were sent as JSON numbers, since the GET response may quote them as strings and the contract types some as strings.
8. In tenant data, join app profiles to forwarding profiles on `forwardingProfileId` where present, otherwise on the embedded `onNetPolicy`.

Sources disagree (name both sides):
- The casing of the password and certificate keys inside the platform blocks of a web policy write: the contract uses camelCase in every block, the Go SDK uses snake_case for macOS only, the Python SDK uses snake_case for Windows, Android and macOS passwords, and the UI captures use snake_case in every block. [divergence:zcc.api.web-policy-wire:os-password-key-casing]
  - api-specs: The contract's edit request defines `disablePassword` and `installCerts` in camelCase in the Windows, macOS, Linux and Android blocks, and `disablePassword` in the iOS block.
  - sdk-go: The Go SDK sends `disable_password` and `install_ssl_certs` in the macOS block, `disablePassword` and `installCerts` in the Windows, Linux and Android blocks, and `disablePassword` in the iOS block.
  - sdk-python: The Python SDK's Windows model writes `disable_password` and `install_ssl_certs` in snake_case; its Linux and iOS models write camelCase `disablePassword`.
  - sdk-python: The Python macOS model reads `disablePassword` but writes `disable_password`, next to camelCase `installCerts`.
  - sdk-python: The Python Android model writes `disable_password` and `allowed_apps` in snake_case, next to camelCase `installCerts`.
  - sdk-python: The Python SDK's Windows UI capture writes `disable_password` and `install_ssl_certs` in snake_case in `windowsPolicy`, with no camelCase copy; its Linux, Android, macOS and iOS captures use snake_case as well (claim ui-capture-password-keys).
  Impact: The UI captures, which come from the console, use snake_case in every platform block, so the contract's camelCase and the Go SDK's camelCase for Windows, Linux, Android and iOS are the outliers; the Go model says camelCase keys were silently ignored in the macOS block. A password or certificate setting sent under the losing casing may not be applied while the edit still answers HTTP 200 (edit-rejects-silently). On the Python legacy client every one of these keys goes out camelCase (python-legacy-camelcases-web-policy).
- Whether integer settings such as `ruleOrder`, `logMode` and `device_type` are sent as numbers or strings [divergence:zcc.api.web-policy-wire:scalar-types]
  - api-specs: The OpenAPI edit body types `ruleOrder`, `logMode` and `device_type` as strings.
  - sdk-python: The Python SDK's Windows UI capture sends `ruleOrder`, `logMode` and `device_type` as JSON numbers.
  - sdk-go: The Go SDK says every ZCC POST and PUT endpoint requires JSON numbers, and that quoted integers make `/web/policy/edit` answer `{"success":"false","id":0}`.
  - sdk-go: The Go SDK also says the GET response quotes some of these values as strings, so reads must accept both.
  Impact: A client generated from the API document sends quoted integers where the UI capture sends numbers, which by the Go SDK's account the edit endpoint rejects with a success flag of false rather than an HTTP error.
- The names of the disaster recovery method and key fields [divergence:zcc.api.web-policy-wire:dr-key-names]
  - api-specs: The OpenAPI edit body names the method `ziaDRRecoveryMethod` and the keys `ziaSecretKeyData`, `ziaSecretKeyName`, `zpaSecretKeyData` and `zpaSecretKeyName`, and has no `ziaDRMethod`, `ziaRSAPubKey` or `zpaRSAPubKey`.
  - sdk-python: The Python SDK's Windows UI capture sends `ziaDRMethod` and `ziaRSAPubKey` in `disasterRecovery`, not `ziaDRRecoveryMethod`.
  - sdk-go: The Go SDK uses `ziaDRMethod` and RSA public key fields (`ziaRSAPubKey`, `zpaRSAPubKey` and their names), and says these match a real list response.
  - sdk-python: The Python SDK sends `ziaDRMethod` and the RSA public key fields, like the Go SDK.
  Impact: A disaster recovery block written to the API document's names may not set the method or keys the API reads back; the UI capture and both SDKs use the other names.
- How a web policy write names its target groups and users: the contract uses flat `groupIds` and `userIds` lists, and a recorded edit that sent them succeeded; the UI capture and the Go SDK write `groups` and `users` collections instead, and the Python SDK at the pin sends its flat ID lists under `groups` and `users`. [divergence:zcc.api.web-policy-wire:targeting-keys]
  - api-specs: The contract's edit body has `groupIds`, `groupNames`, `userIds` and `userNames` lists and no `groups` or `users` member.
  - sdk-python: The Python SDK at the pin sends a caller's `group_ids` and `user_ids` as flat ID lists under the keys `groups` and `users`.
  - sdk-python: The Python SDK's Windows UI capture sends empty `groups` and `users` lists and no `groupIds` or `userIds`.
  - sdk-python: A recorded edit from one test tenant (recorded with Python SDK 1.9.25, Python SDK cassette) sent flat `groupIds` and `userIds`, the API answered `success` "true", and the next listing returned the policy with those groups as `groups` objects and the IDs again as `groupIds` and `userIds`.
  - sdk-go: The Go struct always sends `groups` and `users` and tags the ID and name lists `omitempty`, saying the UI replaced them with the new collections and that sending them empty trips some API validations.
  Impact: For one recorded tenant the API applied flat `groupIds` and `userIds`. Whether it also reads a flat ID list sent under `groups` or `users`, as the Python SDK at the pin sends it, or only the collection form the UI and Go send, is not shown; a targeting write in an unproven form may be ignored while the edit reports success. Read the policy back after a targeting write.
- The unit of the web policy's `reauth_period`: the contract says seconds, the Python docstring says hours, and the Go SDK's UI-captured defaults are small numbers. [divergence:zcc.api.web-policy-wire:reauth-period-unit]
  - api-specs: The contract's application-profile PATCH describes `reauth_period` as the automatic ZPA reauthentication time in seconds.
  - sdk-python: The Python `web_policy_edit` docstring gives the re-authentication period in hours.
  - sdk-go: The Go SDK's UI-captured defaults set `reauth_period` to 8 for macOS and 12 for iOS, values that read as hours rather than seconds.
  Impact: A client following the contract sends seconds where the docstring and the UI defaults suggest hours, which would set the reauthentication period 3600 times shorter or longer than intended. No source shows which unit the API applies.
- What the web policy's `groupAll` flag covers: the contract says all device groups, the Python docstring says all groups. [divergence:zcc.api.web-policy-wire:group-all-scope]
  - api-specs: The contract's application-profile PATCH describes `groupAll` as whether the rule applies to all device groups.
  - sdk-python: The Python `web_policy_edit` docstring describes `group_all` as whether the policy applies to all groups.
  Impact: Read one way the flag widens a policy to every user group, read the other to every device group, which reaches a different set of devices. Whether `groupAll` makes a populated list irrelevant is open (gap group-flags in zcc.app-profiles.selection).
- What `logMode` -1 means in a web policy body: the Python docstring and the Terraform provider say it disables logging, while the Go SDK says it means follow the log-mode picker, and the UI capture sends -1 with the picker set to Debug. [divergence:zcc.api.web-policy-wire:log-mode-minus-one]
  - sdk-python: The Python `web_policy_edit` docstring lists -1 as disabled.
  - tf-zcc: The Terraform provider describes its log mode argument as -1 to disable, otherwise the numeric mode, sent as a JSON number.
  - sdk-go: The Go SDK's UI-captured defaults leave the raw `logMode` at -1, which its comment says means follow the picker, with the picker (`logModeSelected`) set to Debug, value 3.
  - sdk-python: The Python SDK's Windows UI capture sends `logMode` -1 together with `logModeSelected` Debug, value 3.
  - sdk-python: A recorded edit from one test tenant (recorded with Python SDK 1.9.25, Python SDK cassette) sent `logMode` -1 with `logModeSelected` Debug.
  Impact: If -1 disables logging, a body copied from the console turns logging off; if it defers to the picker, the same body logs at Debug. A tool that reads `logMode` alone may report logging off on a profile the console shows at Debug.
