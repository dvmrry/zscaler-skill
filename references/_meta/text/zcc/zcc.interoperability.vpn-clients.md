# Running Client Connector with a corporate VPN client: forwarding action per platform and VPN mode, detection, DNS behavior (zcc.interoperability.vpn-clients)
Also called: vpn client interoperability; corporate vpn client; vpn gateway bypass; full-tunnel vpn; split-tunnel vpn

With a corporate VPN client, the forwarding profile action decides whether Client Connector competes with the VPN. With a corporate VPN client, the forwarding profile action decides whether Client Connector works at the network (IP) layer or the application layer. For Tunnel with Local Proxy and Tunnel (Packet Filter-Based) the app works at the application layer and does not compete with the VPN client at the IP layer, so users do not experience interoperability issues: the app allows the VPN to take traffic as needed but sets proxy settings or packet filters so that Zscaler still protects all user traffic. Tunnel mode works at the same IP layer as VPN clients and might cause interoperability problems. [zcc.interoperability.vpn-clients:layer-matters]

**What the page recommends per platform.** For Windows and macOS, the page recommends, for Windows, only Tunnel with Local Proxy with a full-tunnel VPN and either Tunnel with Local Proxy or Tunnel (Packet Filter-Based) with a split-tunnel VPN, and, for macOS, only Tunnel with Local Proxy. It highly recommends not selecting Tunnel (Route-Based) as the forwarding profile for VPN-Trusted Network. [zcc.interoperability.vpn-clients:windows-macos-recommendations] The existing Windows recommendation for VPN coexistence differs [divergence:zcc.interoperability.vpn-clients:windows-full-tunnel-action]. For iOS, Zscaler recommends the Tunnel forwarding profile action; Client Connector for iOS does not support Tunnel with Local Proxy. iOS allows multiple VPNs to run simultaneously as long as each is of a different type (personal, per-app or enterprise); Client Connector runs as an enterprise VPN, so another personal or per-app VPN can run alongside it, but not an enterprise VPN. [zcc.interoperability.vpn-clients:ios] On Android, Client Connector and any third-party VPN cannot run simultaneously because Android allows only one concurrent VPN at a time. [zcc.interoperability.vpn-clients:android]

**Linux.** For Linux with a VPN in full-tunnel mode, the page lists the headings Forwarding Profile Action for ZIA and Forwarding Profile Action for ZPA followed by two option sets. One: On-Trusted Network Tunnel with Local Proxy, VPN-Trusted Network Same as On-Trusted Network, Off-Trusted Network Same as On-Trusted Network. The other: On-Trusted Network Tunnel, VPN-Trusted Network None. The capture does not show which set goes with which heading. The page also says to disable the VPN client's route monitoring option (for example Cisco AnyConnect VPN) and, if Internet & SaaS loses connection when the VPN starts because the VPN client might have failed to install the bypass route for the Public Service Edge IP, to add that IP to the VPN Gateway Bypass field in App Profiles. [zcc.interoperability.vpn-clients:linux-full-tunnel] Which option set belongs to Internet & SaaS and which to Private Access is open [gap:zcc.interoperability.vpn-clients:linux-zia-zpa-pairing].

**How a VPN is detected.** Client Connector detects a full-tunnel VPN by looking for a default route in the routing table. If the VPN does not set a default route and captures all traffic another way, the app does not consider it full-tunnel and treats the user as Off-Trusted Network. The page says the app looks for these words in the default interface description to detect a VPN-Trusted Network: Cisco, Juniper, Fortinet, PanGP, Check Point and VPN, and treats the user as Off-Trusted Network if they are missing. For a VPN that does not set a default route the page says to select Tunnel with Local Proxy. [zcc.interoperability.vpn-clients:full-tunnel-detection] The keyword list differs from the one in [The app does not treat the network as VPN-Trusted, and treats the user as Off-Trusted, when the VPN captures all traffic without installing a default route, when the default interface description does not contain Cisco, Juniper, Fortinet, PanGP or VPN, or when the VPN runs in split-tunnel mode (routes for some subnets only, or a DNS for specific requests).](kb:zcc.forwarding-profiles.network-types:vpn-trusted-exclusions) [divergence:zcc.interoperability.vpn-clients:check-point-keyword]. When the VPN runs in split-tunnel mode, only some of the users' traffic is routed to the VPN client (for example the VPN can set routes only for specific subnets such as 10/8 or 192.168/16); Client Connector treats the device as Off-Trusted Network and applies the forwarding profile action chosen for that network. For a simpler configuration the page recommends Tunnel with Local Proxy or Tunnel (Packet Filter Based) in this scenario. [zcc.interoperability.vpn-clients:split-tunnel]

**VPN configuration the page requires.** The VPN client must not be configured to change proxy settings on users' devices, even if Tunnel with Local Proxy is selected as the forwarding profile action for VPN-Trusted Network; if VPN clients tamper with proxy settings in any way, Client Connector does not forward traffic properly. [zcc.interoperability.vpn-clients:vpn-proxy-tampering] If a third-party VPN operates in split-tunnel mode, DNS search domains must be configured in the VPN connection profile; otherwise Client Connector intercepts the VPN connection's DNS requests and forwards them to the system DNS server, which might be unable to resolve the VPN domains. [zcc.interoperability.vpn-clients:split-search-domains] If the VPN has any firewall functionality, it must be disabled or Client Connector allowlisted in it, because otherwise the VPN firewall can interfere with app tunnel processes. For the forwarding profile's Trusted Network Criteria, Zscaler recommends selecting DNS Server and DNS Search Domain. [zcc.interoperability.vpn-clients:vpn-firewall-and-criteria]

**Tunnel (Route-Based) with a VPN.** With a full-tunnel VPN, Zscaler strongly recommends against Tunnel (Route-Based). With Tunnel (Route-Based) and a split-tunnel VPN, Client Connector can forward traffic properly only if traffic to the VPN gateway bypasses it: the app sets the routing table to exclude that traffic, which requires the hostnames and IP addresses of all VPN gateways in the Hostname or IP Address Bypass for VPN Gateway field of the app profile, including all VPN hostnames or all IP addresses they can resolve to; any DNS the VPN uses must resolve both internal and external domains. [zcc.interoperability.vpn-clients:route-based-split] The Forwarding Profiles page says Client Connector 4.8 and later for Windows does not use the route-based driver and always uses the packet filter-based driver, so the Windows Route-Based behavior here concerns earlier versions. On Windows in Tunnel (Route-Based) mode, the app sets the interface DNS to 100.64.0.3, 100.64.0.4 and 100.64.0.5; when a VPN changes it, the app detects and reverts the change so 100.64.0.3 is again the prioritized DNS, and redirects any query that reaches 100.64.0.3 to the original prioritized DNS (the VPN client DNS). Some Windows programs do not redirect DNS queries to the next DNS in the priority list, so the page says all VPN clients should set DNS that can resolve both internal and external domains. [zcc.interoperability.vpn-clients:route-based-dns] The Forwarding Profiles page says Client Connector 4.8 and later for Windows always uses the packet filter-based driver, so the Windows Route-Based behavior here concerns earlier versions. Users can see momentary network instability when a VPN client launches while Client Connector is running: in Tunnel (Route-Based) on Windows the app removes all its own DNS settings if the VPN client runs in full-tunnel mode, or reconfigures them for Off-Trusted Network if it runs in split-tunnel mode; the VPN client detects the removal as a network change and can disconnect and try to reconnect, so the user can see connectivity issues until the app and VPN client reach equilibrium. [zcc.interoperability.vpn-clients:launch-instability]

The page names the gateway bypass field two ways [gap:zcc.interoperability.vpn-clients:gateway-field-name].

What to check:
1. For a VPN user shown as Off-Trusted: whether the VPN installs a default route and whether the default interface description contains one of the listed words; the sources disagree on whether Check Point is one of them.
2. Which forwarding action the profile uses on Windows with a full-tunnel VPN; the two vendor pages recommend different actions.
3. Whether the VPN client is configured to change proxy settings, and whether its firewall is disabled or allowlists Client Connector.
4. With Tunnel (Route-Based) and a split-tunnel VPN: that every VPN hostname or all IP addresses it resolves to are in the VPN gateway bypass field and that the VPN's DNS resolves internal and external domains.
