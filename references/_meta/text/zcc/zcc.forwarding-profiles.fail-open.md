# Client Connector fail-open: captive portals, unreachable Service Edges and tunnel failures (zcc.forwarding-profiles.fail-open)
Also called: fail open; fail-open policy; app fail open; captive portal detection; zia cloud not reachable; z-tunnel failover; user blocked at hotel wifi; strict enforcement notification; webFailOpenPolicy

Fail-open settings decide what the app does when it cannot protect traffic. They live in the tenant-wide App Fail Open settings and, on newer clients, in the app profile.

**When it applies.** The app may need to disable its Internet Security service and let users reach the internet directly in three situations: a captive portal requires payment or acceptance before connecting, the app cannot reach ZIA Public Service Edges, or it cannot set up its Z-Tunnel. [zcc.forwarding-profiles.fail-open:situations] Service Edge unreachable means the client cannot establish a connection because of network configuration, such as an isolated lab network; a Z-Tunnel setup issue means it can locate a Service Edge but cannot establish the tunnel, for example when DNS resolves but a firewall blocks tunnel setup. [zcc.forwarding-profiles.fail-open:unreachable-vs-setup]

**Service Edge or tunnel failure.** For ZIA Cloud Not Reachable and for Z-Tunnel Failover the choice is Direct Internet Access (users bypass the app) or Disable Internet Access, which blocks HTTP and HTTPS and allows all other traffic. [zcc.forwarding-profiles.fail-open:failover-options] After failing over, the app keeps trying to establish the tunnel, or reach the Public Service Edge, in the background and re-enables itself when it succeeds. [zcc.forwarding-profiles.fail-open:retry-in-background] What Z-Tunnel 2.0 does when it cannot be set up is a separate forwarding profile setting: [Z-Tunnel 2.0 Setup Failure Behavior (client 3.4+) chooses what happens when the app must switch away from Z-Tunnel 2.0: fall back to Z-Tunnel 1.0 for web traffic and bypass everything else; fall back to Z-Tunnel 1.0 for web traffic and block all other traffic except DNS; or block all traffic except DNS and control-channel traffic to the Zero Trust Exchange for policy, PAC files and software updates.](kb:zcc.z-tunnel.transport:setup-failure-behavior).

**Captive portals.** If Captive Portal Detected, Disable Web Security for (In Minutes) takes 1 to 60 minutes, after which the app re-enables its services and forwards traffic to Zscaler; 0 turns captive portal detection off, and the app then does not fail over directly. [zcc.forwarding-profiles.fail-open:captive-portal-minutes] Zscaler recommends enabling captive portal detection with a period long enough for users to complete the portal, measured from network change detection, but as low as is reasonable. [zcc.forwarding-profiles.fail-open:captive-portal-advice] Whether traffic is blocked once the window ends is open [gap:zcc.forwarding-profiles.fail-open:captive-portal-expiry]. What the app shows when a portal is not resolved in the time configured in the Admin Console: When the user has not resolved a captive portal within the time configured in the Admin Console, Client Connector shows Captive Portal Error in the Service Status; the message disappears when the user reconnects, and the action is Retry and then resolving the captive portal. The registry value CAPTIVE_PORTAL_ERROR for ZPA_State and ZWS_State means a captive portal is detected and the open timeout expires. [zcc.forwarding-profiles.fail-open:captive-portal-error-state] The full Service Status table is in [Error messages in Client Connector's Service Status field and the action for each](kb:zcc.troubleshooting.service-status-errors) and the registry values in [Client Connector state in the Windows registry: ZNW_State, ZPA_State, ZWS_State and ZPA_AuthState values](kb:zcc.troubleshooting.registry-keys). How the app detects a portal is not described [gap:zcc.forwarding-profiles.fail-open:captive-portal-detection-method].

**App profile settings.** On newer clients the app profile's failover settings take precedence: [Failover settings on the app profile take precedence over the global App Fail Open settings, from Client Connector 4.6 for Windows and 4.8 for macOS.](kb:zcc.app-profiles.failover:profile-failover-overrides-global); on Windows 4.5 and later captive portal detection is set there too: [On Windows 4.5 and later the profile enables captive portal detection; with Fail Open on, the app keeps its services disabled for 1 to 60 minutes after detecting a captive portal and then re-enables them.](kb:zcc.app-profiles.failover:captive-portal). Precedence outside those versions is open [gap:zcc.forwarding-profiles.fail-open:precedence-detail]. The app profile's own fail-close settings are in [App profile failover: disaster recovery, cloud unreachable, captive portals](kb:zcc.app-profiles.failover) and [A fail-close option makes the app fail close while a tunnel is starting or restarting, for example after login, Repair App or Restart Service.](kb:zcc.app-profiles.advanced-settings:fail-close-lockdown).

**Strict enforcement.** For clients installed in Strict Enforcement mode (Windows 4.6 and later), Notify End User shows a message to users who try to reach the internet before logging in, repeated after a rate limit (default 2 minutes), with text of at most 200 characters. [zcc.forwarding-profiles.fail-open:strict-enforcement-notify]

**In API data.** The fail-open object's fields are listed in the generated type, but the API contract describes none of them, and which field is which console setting is open [gap:zcc.forwarding-profiles.fail-open:field-mapping], and version floors from the legacy doc are open [gap:zcc.forwarding-profiles.fail-open:version-floors]. How the Terraform resource handles a failed read is in [If the fail-open policy cannot be read, the resource is removed from state. Read calls the by-ID lookup, and on any error calls the list again; if that list also errors, or is empty, it removes the resource without looking at what the error was, so a not-found and any other failure are treated alike. The by-ID lookup itself returns the list error unchanged. When the by-ID lookup errors and the list then returns policies, as when it has no policy with the stored ID, Read silently adopts the first policy in the list.](kb:zcc.terraform.field-fidelity:failopen-read-error-removes-state).

What to check:
1. The client version and platform, to know whether the app profile's failover and captive portal settings or the tenant-wide ones apply.
2. For a user without internet behind a failed tunnel: whether Disable Internet Access is set, which blocks HTTP and HTTPS but allows other traffic.
3. For a captive portal complaint: the configured minutes (0 turns detection off) and whether the user finished the portal within them.
