# What the Python SDK's ZCC methods return, and the ones that break the tuple convention (zcc.sdk-python.return-shapes)
Also called: get_web_privacy returns None; zcc download_devices returns filename; zcc python result shape; activate_web_policy empty WebPolicy; add_trusted_network no id; get_company_info list; get_company_info org_id None; remove_devices devices_removed None; sync_zia_zdx_admin_users dict

Most ZCC methods return the SDK's usual result, response and error tuple: [Python SDK methods return a three-element tuple of result, response and error rather than a bare result.](kb:shared.sdk-python.response-handling:tuple-return). The exceptions below change how a caller has to test for failure.

**Not a tuple.** `get_web_privacy` returns a bare None when the request cannot be built, when it fails, or when the body cannot be read, instead of a tuple with an error. [zcc.sdk-python.return-shapes:web-privacy-get-none] On success `get_web_privacy` returns the camel-cased response dictionary itself, not a `WebPrivacy` model or a tuple, so it carries any non-null key the API sends, including ones the model lacks. [zcc.sdk-python.return-shapes:web-privacy-get-dict] `download_devices`, `download_service_status` and `download_disable_reasons` return the file name they wrote, defaulting to a timestamped name, and raise an exception on any failure instead of returning an error value. [zcc.sdk-python.return-shapes:downloads-raise] Before writing, `download_devices`, `download_service_status` and `download_disable_reasons` each check that the response is `application/octet-stream` or text starting with `"User","Device type"`, raising 'Invalid response content type or unexpected response format.' otherwise, then write the raw bytes to the file. [zcc.sdk-python.return-shapes:downloads-content-check]

**Single objects and wrappers.** `get_device_details` builds one `DeviceDetails` object from the whole response body, treating the endpoint as returning a single object. [zcc.sdk-python.return-shapes:device-details-single] The Go SDK decodes the same call differently: [zcc.api.devices-wire:details-response-shape](kb:zcc.api.devices-wire:details-response-shape). `get_company_info` returns a list of `CompanyInfo` objects, each built again from a result the executor already wrapped as a `CompanyInfo`; a single-object response becomes a one-item list. [zcc.sdk-python.return-shapes:company-info-list] `get_company_info`, `remove_devices` and `force_remove_devices` wrap each result in their model twice, so only fields whose wire key equals the attribute name survive (`name`, `udids`, `username`); `org_id`, `business_name` and `devices_removed` come back None. [zcc.sdk-python.return-shapes:results-wrapped-twice] The removal calls it affects are in [Removing devices and machine tunnels through the API and SDKs](kb:zcc.devices.removal-api). `sync_zia_zdx_admin_users` and `sync_zpa_admin_users` return a list of camel-cased dictionaries, not model objects. [zcc.sdk-python.return-shapes:sync-raw-dicts] The trusted-network list envelope is [Both SDKs read the v1 list as an object and take the networks from its `trustedNetworkContracts` member (Go also reads `totalCount` and errors when it is positive but no networks came back).](kb:zcc.api.trusted-networks-wire:list-envelope).

**Writes that return little.** `activate_web_policy` returns an empty `WebPolicy()` when the response body is empty, rather than an error. [zcc.sdk-python.return-shapes:activate-empty-body] Python's `set_web_privacy_info` sends whatever keyword arguments it is given, camel-cased by the executor's selective ZCC conversion, so keys outside its model can be written, but it returns a model object that holds only the modeled settings. [zcc.sdk-python.return-shapes:python-set-kwargs] `add_trusted_network` returns a `TrustedNetworks` object built from the create response itself, with no follow-up lookup. [zcc.sdk-python.return-shapes:add-builds-from-response] The recorded v1 create response carries only `conditionType` and `active`, so the object `add_trusted_network` returns has no ID or name of the new network. [zcc.sdk-python.return-shapes:add-result-has-no-id] What the create and edit responses carry is [The Go SDK documents that v1 create and edit return only a status such as {"success":"true","errorCode":"0"}, not the trusted network, so it resolves the record by name after create and by ID after update. Recorded responses from one test tenant agree that neither returns the record, but differ on the create: there the API answered `{"conditionType" : 0, "active" : false}`, while the edit answered `{"success" : "true", "errorCode" : "0"}`.](kb:zcc.api.trusted-networks-wire:mutation-response).

What to check:
1. Whether the caller tested `get_web_privacy` for None rather than unpacking a tuple.
2. Whether a download call was wrapped in try/except, since it raises rather than returning an error.
3. Whether code read the new trusted network's ID from `add_trusted_network`'s result, which comes from a response with no record; list by name instead.
