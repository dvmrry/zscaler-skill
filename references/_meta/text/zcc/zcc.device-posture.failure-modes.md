# Why a device fails posture, and what the user sees (zcc.device-posture.failure-modes)
Also called: posture failing; posture verification failed; device posture failure notification; posture check fails closed; crowdstrike zta score missing; posture stale after change

A posture failure is either the check genuinely failing, the check being unable to run, or a result that has not been refreshed. Only the first is fully documented.

**The check failed.** Each type's pass condition is in [Device posture check types: what each checks, where it applies, and how it passes](kb:zcc.device-posture.check-types), including the cases where an unreadable registry key or a readable Linux key fails it: [Registry Key applies to Windows only and matches a key path or a value (name and data). The check runs in the user context, so a key users cannot read, such as under HKLM, must be created where they can.](kb:zcc.device-posture.check-types:registry-key), [Client Connector checks the private key file's permissions, and posture validation fails if non-root users can access the file.](kb:zcc.device-posture.linux-client-certificate:key-permission-enforced). Client Connector versions for macOS have a known issue with firewall posture checks on macOS Sequoia: due to changes in how macOS stores firewall configuration in macOS Sequoia, the firewall posture check for Zscaler Internet Access (ZIA) and Zscaler Private Access (ZPA) fails. The same vendor page says both that it is recommended to remove the firewall posture check from the policy until a fix is available, and that customers using earlier versions must upgrade to Client Connector version 4.2.0.294, 4.3.0.237 or 4.3.1.56 to ensure the fix is applied. [zcc.device-posture.failure-modes:macos-sequoia-firewall] Legacy (1.5.x mobile): for Client Connector version 1.5.2 for iOS and version 1.5.0 for Android, there is a known issue with the Unauthorized Modification device posture profile, where unmodified devices fail the posture check. To use this profile, the posture profile and ZPA access policy must be updated, and Client Connector version 1.5.3 for iOS and 1.5.3 for Android must be used. [zcc.device-posture.failure-modes:legacy-unauthorized-modification-15]

**The check could not run.** Whether a check Client Connector cannot run counts as a failure is open [gap:zcc.device-posture.failure-modes:unevaluable-check]. What a client below a type's version floor reports is open [gap:zcc.device-posture.failure-modes:below-version-floor]. Whether a missing CrowdStrike ZTA score is distinguishable from a low one is open [gap:zcc.device-posture.failure-modes:zta-score-absent].

**The result is stale.** Evaluation runs on a schedule and on triggers, and existing connections keep the earlier result: [Zscaler Client Connector evaluates device posture profiles every 15 minutes, new connections are established on the updated posture, and existing connections are not affected by updates to security postures.](kb:zpa.posture-profiles.evaluation:cadence), [Process Check, Detect Carbon Black, Detect CrowdStrike, Detect SentinelOne and Detect Microsoft Defender are evaluated immediately when the posture changes on the device, regardless of the frequency setting, and the client also keeps evaluating them on the configured frequency; the feature is on by default and Zscaler Support can disable it.](kb:zpa.posture-profiles.evaluation:immediate-checks).

**What the user sees.** A posture profile can carry an optional message, and a website URL, shown when a user is blocked from a Private Access app because posture failed: the user gets a pop-up with a Learn More link that opens the message in Client Connector's Notifications window. The message shows only when the access policy has Device Posture Failure Notification enabled and the user's app profile has a notification template with Show Device Posture Failure Remediation Notification enabled, only on Client Connector 4.8 and later for Windows and 5.0 and later for macOS, and Zscaler Support must enable the feature. [zcc.device-posture.failure-modes:failure-message] When the pop-up appears, and how it can be delayed: [Show Device Posture Failure Remediation Notification shows a pop-up when a Private Access app is blocked because a posture in the access policy failed and the access policy enables Device Posture Failure Notification; its Learn More link opens the posture profile's message in the app.](kb:zcc.notifications.templates:posture-remediation), [Delay Posture Failure Notifications holds back device posture failure pop-ups for up to 300 seconds (default 0), so that a check that fails only while, for example, CrowdStrike is still starting does not alarm the user. It delays only the pop-up, not the message in the app's Notifications window.](kb:zcc.notifications.templates:posture-delay).

What to check:
1. Whether the failing type is one that re-evaluates immediately on change or waits for the schedule, before concluding the device is still failing.
2. For a CrowdStrike ZTA failure, the Falcon agent's state and score on the device before the posture rule.
3. Whether the user should have seen a remediation message: the access policy's Device Posture Failure Notification and the app profile's notification template setting, on a supported client version.

Not known (open gaps):
- Whether a posture check that cannot run is reported as failed [gap:zcc.device-posture.failure-modes:unevaluable-check]: settled by lab-test or support-ticket. Blocks: telling a misconfigured check from a non-compliant device
- What a client older than a posture type's minimum version reports [gap:zcc.device-posture.failure-modes:below-version-floor]: settled by lab-test. Blocks: predicting posture results on a fleet with mixed Client Connector versions
- What a CrowdStrike ZTA check reports when no score is available [gap:zcc.device-posture.failure-modes:zta-score-absent]: settled by lab-test or support-ticket. Blocks: separating a CrowdStrike agent problem from a low-score device in posture investigations
