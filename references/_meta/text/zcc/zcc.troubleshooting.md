# Troubleshooting Client Connector: from symptom to the subject that holds the answer (zcc.troubleshooting)
Also called: zcc troubleshooting; client connector not working; zcc connected but no traffic; zcc stuck signing in; zcc api errors
Former IDs: zcc-74

A Client Connector report is worked from the symptom to the layer that holds the evidence.

1. **Connected, but traffic does not flow or skips ZIA.** Fail-open is in [Client Connector fail-open: captive portals, unreachable Service Edges and tunnel failures](kb:zcc.forwarding-profiles.fail-open) and the forwarding action for the current network in [Forwarding profile actions for Internet & SaaS (ZIA): Tunnel, Tunnel with Local Proxy, Enforce Proxy, None](kb:zcc.forwarding-profiles.internet-actions); trusted-network matching is in [How Client Connector decides it is on a trusted network](kb:zcc.trusted-networks.detection). IPv6 traffic dropped on a dual-stack network is in [Drop IPv6 in Dual Stack Network makes the app intercept and drop IPv6 packets from a dual-stack network (on Windows only in LWF mode); the vendor says to disable it when using IPv6, because when enabled it takes precedence over all IPv6 settings.](kb:zcc.forwarding-profiles.internet-actions:drop-ipv6-dual-stack).
2. **The PAC file is not applying.** Where the profile gets its PAC URL is in [A PAC file reaches the profile through the system proxy settings, as PAC URL Location: a PAC URL (at most 512 characters, https:// when Enforce Secure PAC URLs is on) that the app downloads directly, or a registry key on the device that holds the URL.](kb:zcc.forwarding-profiles.internet-actions:pac-url-location), and what happens when the PAC file is unreachable in [The Python SDK documents `allowUnreachablePac` as whether traffic is allowed when the PAC file is unreachable; the Go SDK calls it a legacy flag that the API still echoes on reads though the admin UI no longer renders it.](kb:zcc.app-profiles.failover:allow-unreachable-pac). With Z-Tunnel 2.0, network bypasses do not belong in the app profile PAC file: [For Z-Tunnel 1.0, network bypasses can go in the app profile PAC file; for Z-Tunnel 2.0 the vendor says not to put them there and to add them as VPN gateway bypasses or destination exclusions.](kb:zcc.z-tunnel.bypasses:pac-not-for-2). What the forwarding profile PAC and the app profile PAC each do in each forwarding mode is in [Client Connector's two PAC files: what the forwarding profile PAC and the app profile PAC do in Tunnel and Tunnel with Local Proxy modes, and the forwarding PAC in Enforce Proxy](kb:zcc.pac-files).
3. **Stuck on Signing In.** Strict enforcement and the policy token are in [Strict enforcement, the policy token, and the fail-close configuration](kb:zcc.install.strict-enforcement), the user domain in [Install parameters that identify the tenant and user at enrollment](kb:zcc.install.enrollment), and identity alignment in [ZIA SCIM provisioning](kb:zia.scim), [ZPA SCIM groups and attributes in policy](kb:zpa.scim) and [SCIM provisioning across ZIA and ZPA: where the two differ](kb:shared.scim). How users authenticate in the app (browser-based, WebView2, window resizing, user agent suffix) and the per-OS Platform Settings are in [Platform Settings: the per-OS console settings for sign-in, IPv6, ZDX upgrades, default UI and unattended-mode passwords](kb:zcc.platform-settings).
4. **Client Connector alongside a VPN, antivirus, firewall or proxy.** The hub is [Client Connector alongside other software and networks: where each interoperability answer lives, plus debugging proxies, alternative cloud domains and iCloud Private Relay](kb:zcc.interoperability): VPN clients in [Running Client Connector with a corporate VPN client: forwarding action per platform and VPN mode, detection, DNS behavior](kb:zcc.interoperability.vpn-clients), allowlists for antivirus and host firewalls in [Allowlisting Client Connector in antivirus and host firewalls: paths, processes, firewall directions and the 100.64 range](kb:zcc.interoperability.security-software), and an environment whose only egress is a proxy in [Deploying Client Connector where the only egress is a proxy: the System PAC, spoofed DNS records and the four scenarios](kb:zcc.interoperability.no-default-route). Debugging proxies, alternative cloud domains and iCloud Private Relay are in [Client Connector alongside other software and networks: where each interoperability answer lives, plus debugging proxies, alternative cloud domains and iCloud Private Relay](kb:zcc.interoperability) itself.
5. **A partner organization's Private Access tenant.** Partner logins, in either direction, are in [Private Access partner logins: who may log in to whose tenant, and what the user does and sees](kb:zcc.partner-tenants).
6. **What the user's app shows.** The Classic and Modern app, its menus and status are in [The Client Connector app as users see it: Classic UI and Modern UI menus, status, enrollment and notifications, by OS where the pages cover it](kb:zcc.end-user), the Private Access, Internet Security, Digital Experience and Data Protection windows in [What the Private Access, Internet Security, Digital Experience and Data Protection windows of the app show](kb:zcc.end-user.service-windows), and the user's Troubleshoot section, Report an Issue form and Zscaler Diagnostics in [What users get to troubleshoot: the Troubleshoot section, Report an Issue and Zscaler Diagnostics at the login screen](kb:zcc.end-user.troubleshooting).
7. **Every site shows a block page or a certificate error.** Block pages come from ZIA, not the client [Browser-based notifications (block, caution, AUP and quarantine) are provided by the Zscaler service, and their messages can be customized in multiple languages. Over HTTPS a block notification is shown only with SSL/TLS inspection; otherwise the user gets a 403 error in transparent mode or a Connection Refused error in explicit mode.](kb:zcc.notifications:browser-eun). On a captive-portal network, how long the app disables web security is in [If Captive Portal Detected, Disable Web Security for (In Minutes) takes 1 to 60 minutes, after which the app re-enables its services and forwards traffic to Zscaler; 0 turns captive portal detection off, and the app then does not fail over directly.](kb:zcc.forwarding-profiles.fail-open:captive-portal-minutes). Root certificate installation is in [Whether Client Connector installs the Zscaler root certificate](kb:zcc.app-profiles.ssl-certificate). If the profile was written through the API, check the certificate key's casing for the platform [zcc.api.web-policy-wire:os-password-key-casing](kb:zcc.api.web-policy-wire:os-password-key-casing): the Go SDK's model says a camelCase macOS certificate key was once silently ignored [The Go SDK sends the macOS block's password and certificate keys in snake_case (`disable_password`, `install_ssl_certs`, `logout_password`, `uninstall_password`), with `install_ssl_certs` a JSON number; its model says earlier camelCase tags were silently ignored by the API and produced `{"success":"false","id":0}` on `/edit`.](kb:zcc.api.web-policy-wire:mac-snake-or-ignored).
8. **Bypasses do not take effect, or Z-Tunnel 2.0 falls back.** Bypass precedence is in [Bypasses for Z-Tunnel 2.0: VPN gateway bypasses, destination exclusions and inclusions, domain bypasses](kb:zcc.z-tunnel.bypasses) and DTLS-to-TLS fallback in [Z-Tunnel 2.0 transport: DTLS and TLS, fallback, MTU, and what happens when the tunnel cannot be set up](kb:zcc.z-tunnel.transport); which push-MFA exclusions are needed is open [Whether push notifications (APNs, FCM) need destination exclusions on mobile Client Connector](kb:zcc.z-tunnel.bypasses:mobile-push), and GRE double encapsulation in [Rolling out Z-Tunnel 2.0 and migrating from 1.0](kb:zcc.z-tunnel.deployment).
9. **Posture fails or stays stale.** Why a device fails posture, and what the user sees, is in [Why a device fails posture, and what the user sees](kb:zcc.device-posture.failure-modes). Evaluation cadence for stale posture is in [When and how often posture is evaluated](kb:zpa.posture-profiles.evaluation), and posture-failure notifications in [Client Connector notification templates: per-profile notification settings](kb:zcc.notifications.templates).
10. **Step-up authentication does not prompt.** See [Step-up authentication and ZIdentity authentication levels](kb:zia.authentication.step-up).
11. **A changed setting has not reached the device.** See [When an app profile change reaches a device](kb:zcc.app-profiles.propagation).
12. **Driver, install-parameter or device-record problems.** Windows filter-driver parameters are in [Windows filter driver install parameters (LWF)](kb:zcc.install.windows-driver), macOS system extensions and profiles in [macOS system extensions, VPN payloads and privacy profiles for Client Connector](kb:zcc.install.macos-extensions), and device records in [Enrolled device states and what moves a device between them](kb:zcc.devices.lifecycle).
13. **The app shows an error code or a Service Status message.** Cloud, Admin Console and Report an Issue codes are in [Client Connector error codes: cloud authentication, cloud, Admin Console and Report an Issue](kb:zcc.troubleshooting.error-codes), Private Access enrollment errors (2008 and the 42xxx codes the vendor lists) in [Private Access authentication errors Client Connector users might see during enrollment: 2008 and the 42xxx codes the vendor lists](kb:zcc.troubleshooting.private-access-auth-errors), and the Service Status field's messages in [Error messages in Client Connector's Service Status field and the action for each](kb:zcc.troubleshooting.service-status-errors). The pop-up messages the app shows, with their meaning and user action, are in [Client Connector pop-up messages: type, meaning, user action and duplicate suppression](kb:zcc.notifications.pop-ups).
14. **Reading a Windows device's state.** The state values in the registry are in [Client Connector state in the Windows registry: ZNW_State, ZPA_State, ZWS_State and ZPA_AuthState values](kb:zcc.troubleshooting.registry-keys).
15. **A symptom tied to one version or OS.** Version- and OS-bound issues with their workarounds are in [Version- and OS-bound Client Connector known issues, with the vendor's workarounds and fix versions where given](kb:zcc.troubleshooting.known-issues).
16. **An API call fails.** Status codes are in [The ZCC API's documented status codes are 200, 400, 401, 403, 404, 415 (Unsupported Media Type), 429 and 500. 429 means too many requests: the rate limit or a device threshold was exceeded. The table labels 500 "Not Implemented".](kb:zcc.api.conventions:status-codes), rate limits and SDK back-off in [ZCC API rate limits: 100 calls an hour, 3 a day for downloads, and how the SDKs back off](kb:zcc.api.rate-limits), and sign-in in [Reaching and signing in to the ZCC API: OneAPI gateway and legacy login](kb:zcc.api.authentication). Whether the generic legacy API codes and 403 causes apply to the ZCC API is open [gap:zcc.troubleshooting:generic-legacy-codes].

**Evidence.** Collecting logs is in [Getting Client Connector logs to support: Report an Issue, Fetch Logs, packet captures](kb:zcc.logging.collection), raising verbosity in [Client Connector log modes as users and the API see them: Verbose, user choice, logMode and logLevel](kb:zcc.logging.log-modes), and what the client log can show in [What the Client Connector log on the device records](kb:zcc.logs.client-log).

**Out of scope.** ZIA URL policy decisions are in [ZIA URL Filtering](kb:zia.url-filtering) and ZPA access decisions in [Troubleshooting ZPA access: from symptom to layer](kb:zpa.troubleshooting).

What to check:
1. Before treating a 403, 405, 409 or 503 from the ZCC API with the generic legacy-API explanation, note that the ZCC table lists 403 only as Forbidden.

Not known (open gaps):
- Generic legacy API status codes on the ZCC API [gap:zcc.troubleshooting:generic-legacy-codes]: settled by lab-test or support-ticket
