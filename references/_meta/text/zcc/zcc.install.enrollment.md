# Install parameters that identify the tenant and user at enrollment (zcc.install.enrollment)
Also called: userDomain; USERDOMAIN; cloudName; cloudname; deviceToken; userName; UNAME; externalDeviceId; enableFips; authByTunnel; autoEnrollWithMDM; ownership variable install key; skip zcc enrollment page

These parameters tell Client Connector which tenant and which user it is enrolling before it has a policy. Most keys have the same name on every platform, with a few exceptions noted below.

**Domain.** userDomain (MSI `USERDOMAIN`) is the organization's domain name; with several domains it is the primary domain, which is valid only with a single IdP across those domains. It must be the exact domain in the SAML NameID. It lets users skip the enrollment page; when SSO is enabled they go straight to the SSO login page, and where SSO is integrated with the app (IWA on Windows, the Microsoft Enterprise SSO plug-in on macOS) users also skip the SSO page and are enrolled and logged in automatically. With non-persistent Citrix VDIs on Windows, this option requires IWA. [zcc.install.enrollment:user-domain]

**Cloud.** cloudName (MSI `CLOUDNAME`) names the cloud the organization is provisioned on, so users of an organization on more than one cloud do not have to pick a cloud during enrollment. It is not to be used when the organization is on one cloud, since the app then sends traffic to the right cloud by itself. It is required with strict enforcement on Windows, macOS and iOS. [zcc.install.enrollment:cloud-name]

**Client Connector as the IdP.** deviceToken carries a device token generated in the Admin Console, for using the Admin Console as the IdP: the service then provisions and authenticates users silently. It applies only to Internet & SaaS; on Windows, macOS and iOS Private Access supports it only together with Authentication Service, and on Android Private Access does not support it. [zcc.install.enrollment:device-token] The Admin Console can act as the identity provider for Internet & SaaS only. Users need not be tied to the organization's standard IdP to authenticate to the Zscaler service; where the organization uses SAML-based single sign-on, Client Connector can use a device token to auto-provision and silently authenticate users and devices. [zcc.install.enrollment:zcc-idp-scope] The device token is generated in the Admin Console and passed to Client Connector in an installer option, and the Zscaler Client Connector Portal must be selected as the authentication method. The app gathers the user ID and other parameters from devices and sends them to the Zscaler cloud in SAML requests, which the Admin Console parses and verifies so the cloud can provision and silently authenticate users. The device token, user domain and cloud name must all be passed to users' devices during installation. [zcc.install.enrollment:zcc-idp-mechanism] A new device token is created with Create Device Token from the Client Connector IdP page (Infrastructure > Client Connector > Client Connector IdP), where the list of created tokens can be viewed and a token deleted; Zscaler must enable the feature. The password entered to create a token must be at least six characters and include at least one alphabetic character and a number, is only for generating the token, and is unneeded after that. Up to 16 tokens can be created. [zcc.install.enrollment:device-token-creation] On iOS, authByTunnel sets auto-enrollment when the Admin Console is the IdP: 1 always auto-enrolls, even after a manual logout or removal from the Admin Console; 2 auto-enrolls once; 0 disables it. It applies only to Internet & SaaS; with Private Access enabled, users log in manually. [zcc.install.enrollment:ios-auth-by-tunnel] On Android, autoEnrollWithMDM configures auto-enrollment without user interaction when Client Connector is the IdP: 0 disables it, 1 always auto-enrolls, even after logout, and 2 auto-enrolls once. With 1 or 2, deviceToken, cloudName and userDomain must be set; without userName, or without the contacts permission granted from the MDM, users are prompted to give Zscaler access to their contacts so it can read the Google account username. [zcc.install.enrollment:android-auto-enroll] Whether a missing companion key fails visibly is open [gap:zcc.install.enrollment:auto-enroll-missing-keys].

**User and device.** userName (MSI `UNAME`) is the user's name without the domain, up to 255 alphanumeric and special characters, and can be filled by an MDM macro; userDomain must be set when it is used. With Intune on Android, Intune's `partialupn` token reuses the Intune enrollment username. [zcc.install.enrollment:user-name] externalDeviceId associates a device in an MDM with the same device in the Admin Console, can be filled by an MDM macro, and defaults to 0 (disabled). It is not supported on Client Connector 4.0 and earlier for Windows or 4.1 and earlier for macOS, and applies from 3.7 on Android and Android on ChromeOS. [zcc.install.enrollment:external-device-id] The ownership key feeds the Ownership Variable device posture type, with up to 32 alphanumeric characters. On iOS it must be pushed only through the MDM's managed app configuration, not in the VPN profile. [zcc.install.enrollment:ownership]

**Cryptography.** enableFips makes Client Connector use FIPS-compliant libraries for its communication with Zscaler infrastructure; it defaults to disabled, and the vendor advises enabling it only where FIPS-level security is required. [zcc.install.enrollment:enable-fips]

**Key spelling.** Key spelling differs on mobile: iOS spells the cloud and user keys `cloudname` and `username`, where Windows (EXE), macOS and Android use `cloudName` and `userName`; the posture key is `ownership` on iOS and `Ownership` on Android. [zcc.install.enrollment:mobile-key-casing]

Strict enforcement, which requires the cloud name, is in [Strict enforcement, the policy token, and the fail-close configuration](kb:zcc.install.strict-enforcement); how these keys are delivered per platform is in [Client Connector install parameters and deployment](kb:zcc.install). Partner logins to other tenants are in [Private Access partner logins: who may log in to whose tenant, and what the user does and sees](kb:zcc.partner-tenants).

What to check:
1. Whether the userDomain value is exactly the domain in the SAML NameID of the users being enrolled, and whether the tenant uses several IdPs.
2. Whether the tenant is provisioned on more than one cloud before setting cloudName, unless strict enforcement needs it.
3. On iOS and Android, whether the key is spelled with that platform's casing (cloudname, username, Ownership).

Not known (open gaps):
- What Android auto-enrollment does when a required companion key is missing [gap:zcc.install.enrollment:auto-enroll-missing-keys]: settled by lab-test or support-ticket. Blocks: telling a silent enrollment failure apart from other Android enrollment problems
