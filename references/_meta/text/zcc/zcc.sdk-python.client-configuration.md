# The Python SDK's two ZCC clients: OneAPI service and legacy helper (zcc.sdk-python.client-configuration)
Also called: zcc python legacy client; LegacyZCCClient; LegacyZCCClientHelper; ZCC_CLIENT_ID; client.zcc secrets missing legacy; zcc python 3 calls per day error; zcc python login failed
Former IDs: zcc-87

The Python SDK reaches ZCC through either the OneAPI client or a legacy helper that signs in with ZCC portal keys. How each path authenticates is in [Reaching and signing in to the ZCC API: OneAPI gateway and legacy login](kb:zcc.api.authentication); this subject holds what the Python clients themselves do.

**Which client answers.** On a OneAPI client, `client.zcc` is a `ZCCService` built on first use and kept. On a client constructed for legacy use, `client.zcc` returns the legacy ZCC helper object itself, and raises RuntimeError when no legacy helper was supplied. [zcc.sdk-python.client-configuration:two-client-paths] `LegacyZCCClient` takes `api_key`, `secret_key` and `cloud` from its config dictionary, falling back to the environment variables `ZCC_CLIENT_ID`, `ZCC_CLIENT_SECRET` and `ZCC_CLOUD`; the helper defaults the cloud to `zscaler` when none is given. [zcc.sdk-python.client-configuration:legacy-client-env] The legacy helper exposes the same ZCC service properties as `ZCCService` except `secrets`, so `get_otp` and `get_passwords` are not reachable through `client.zcc` on a legacy client. [zcc.sdk-python.client-configuration:legacy-missing-secrets]

**Legacy sign-in.** The legacy helper calls its token refresh before every request; it logs in again when it holds no token or the token has expired, and raises a plain Exception, 'Failed to login using provided credentials.', when the login fails. [zcc.sdk-python.client-configuration:legacy-token-refresh] Exiting the legacy ZCC helper as a context manager (its `__exit__`) only writes a debug log line; unlike the ZIA legacy client it sends no logout request. [zcc.sdk-python.client-configuration:legacy-exit-no-logout] The login call and token header are [The legacy API is signed in to with a POST to `/papi/auth/v1/login` carrying `apiKey` and `secretKey`; the response's `jwtToken` is the token passed on subsequent calls.](kb:zcc.api.authentication:legacy-login-request) and [On the legacy path the JWT is sent in an `auth-token` request header: the help article's example uses `auth-token`, and both SDKs' legacy ZCC clients set that header.](kb:zcc.api.authentication:legacy-auth-token-header); the host the helper builds is in [zcc.api.authentication:legacy-host](kb:zcc.api.authentication:legacy-host). The partner header is [When a partner ID is supplied through configuration or ZSCALER_PARTNER_ID the SDK adds an x-partner-id header to every request, on both the OneAPI and the legacy clients; without one the header is not sent.](kb:zia.sdk-python.authentication:partner-id-header).

**Legacy limits and retries.** The helper's counters and 429 handling are [The Python legacy ZCC client counts calls locally in `check_rate_limit`, which it calls before sending: 100 per hour for every path, and 3 per day for a path containing `/downloadDevices`. That function, which ends after incrementing the hourly counter, has no daily check for `/downloadServiceStatus` or `/downloadDisableReasons`, which the vendor article also limits to 3 calls per day.](kb:zcc.api.rate-limits:legacy-local-counters), [On a 429 from any path other than `/downloadDevices` and `/downloadServiceStatus`, the Python legacy client adds one to an attempt counter and raises a ValueError when the counter reaches three; otherwise it waits the `X-Rate-Limit-Retry-After-Seconds` value plus one second, or 60 seconds when the header is absent or not all digits, and sends again. The counter starts at zero for each call, and zero-remaining responses and network errors add to it too, so with only 429s the client gives up on the third.](kb:zcc.api.rate-limits:legacy-429-retry) and [For `/downloadDevices` and `/downloadServiceStatus` the Python legacy client does not retry a 429: it raises a ValueError at once whose message gives the `X-Rate-Limit-Retry-After-Seconds` value plus one second, or 86400 seconds when the header is absent or not all digits.](kb:zcc.api.rate-limits:legacy-download-raise). When a local counter is exhausted, the helper raises AttributeError ('str' object has no attribute 'isoformat') instead of its ValueError messages, because the exception class it raises requires a datetime. [zcc.sdk-python.client-configuration:legacy-preflight-message] On a transport error (`requests.RequestException`) the legacy helper sleeps five seconds and sends the same request again, up to three attempts in all, without checking the HTTP method. [zcc.sdk-python.client-configuration:legacy-network-retries] A POST or PUT whose response was lost to a transport error can therefore be applied twice. [zcc.sdk-python.client-configuration:legacy-network-retries-duplicate-writes]

**OneAPI retries.** The OneAPI executor's wait comes from [The Python OneAPI request executor treats 429 as retryable and, absent a `Retry-After` header, takes its wait, plus one second, from the first of `x-ratelimit-reset`, `X-RateLimit-Reset`, `RateLimit-Reset`, `X-Rate-Limit-Retry-After-Seconds` and `X-Rate-Limit-Remaining` that is present, the last read as seconds.](kb:zcc.api.rate-limits:oneapi-retry-headers). Whether an OneAPI-fronted ZCC 429 carries those headers at all is open [gap:zcc.sdk-python.client-configuration:oneapi-429-headers].

What to check:
1. Whether the script built a legacy client, since `client.zcc` is then the legacy helper and has no `secrets` service.
2. Whether a legacy-client error is a ValueError giving a wait in seconds on `/downloadDevices` or `/downloadServiceStatus` (a server 429) or an AttributeError about `isoformat` (an exhausted local counter).
3. Whether a write that failed on a network error was sent again by the legacy helper before the error surfaced.

Reproduced by constructing the class with a string; not run against a tenant.
- [zcc.sdk-python.client-configuration:legacy-network-retries-duplicate-writes] Tier B: Follows from legacy-network-retries: the helper resends any request, whatever its method, after a `requests.RequestException`. It rests on a transport error (a read timeout or a dropped connection) arriving after the server has received and applied the request, which no source states, and on the ZCC write endpoints not rejecting a repeated write; neither has been observed.
