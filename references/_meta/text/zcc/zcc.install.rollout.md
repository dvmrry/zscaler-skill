# Rolling out Client Connector: App Store downloads, deployment phases, pilot tests and update test groups (zcc.install.rollout)
Also called: zcc deployment best practices; zcc phased deployment; zcc pilot; zcc app store downloads; early adopter group zcc; zcc update best practices

IT admins can download Client Connector for Windows, macOS, Linux or Android from the Client Connector App Store in the Admin Console (Infrastructure > Client Connector > App Store), either the latest version or one of the older versions still available. App updates can also be configured to update Client Connector automatically on end users' Windows, Linux or macOS devices. [zcc.install.rollout:downloads] The iOS exception is in [Deploying Client Connector on iOS through an MDM: managed app configuration, the VPN profile, per-app VPN, dual tunnel, SSO and ZDX](kb:zcc.install.ios-deployment); update settings per user group are in [The App Store the vendor's macOS guides refer to is the Client Connector App Store in the Admin Console (Infrastructure > Client Connector > App Store). App updates are configured there for Windows, macOS and Linux only, per user group, with a version to install per OS, rolled out to the selected groups at the same time or as a phased rollout that upgrades devices gradually; iOS and Android updates come from the App Store, Google Play or the MDM. After enrolling, the app checks for an update every two hours and installs one if available.](kb:zcc.install.macos-deployment:app-store-updates).

**The App Store tabs.** The New Releases tab shows and enables the latest Client Connector versions for Windows, macOS and Linux; an enabled build is then listed under the Registered Devices tab, which shows released versions for Windows, macOS, Linux and Android (SDK file only), with the most recent release at the top of each table and versions that are not grayed out still available to download. Windows has EXE URL and MSI URL columns, macOS Download APP or Download PKG columns, and Linux a Download Link column. [zcc.install.rollout:app-store-tabs] The Android download is described differently by the MDM guides: [Deploying Client Connector on Android through an MDM: Android Enterprise, the APK, minimum OS and Always-on VPN](kb:zcc.install.android-deployment).

**What the App Store page controls.** The Client Connector App Store page controls which version, if any, is available when end users update the app manually or when automatic app updates are configured; it can deploy the latest version to a user group for testing, upgrade selected groups gradually with a phased rollout, and delay the base ZDX Module rollout so a selected group can test it. An admin without access to the page contacts the organization's support team. [zcc.install.rollout:app-store-control] The App Store page shows the latest released versions in the General Availability section and versions that are not yet fully qualified in the Limited Availability section; Zscaler Support enables versions in the Limited Availability section. [zcc.install.rollout:availability-sections] The relation of those sections to the New Releases tab is open [gap:zcc.install.rollout:availability-vs-new-releases]. Even when the latest version is selected to install on the Update Settings tab, the build must first be enabled on the New Releases tab; disabling a version on New Releases only disables it on the list and does not uninstall it from the system. [zcc.install.rollout:enable-before-install]

**The version list.** The App Store lists the available Client Connector versions for Windows, macOS, Linux and Android with the latest version always at the top, and its Registered Devices column shows the number of devices currently enrolled in the Zscaler service with each app version. [zcc.install.rollout:version-list] The Registered Devices count is calculated on the Unique-ID and can instead be based on the Hardware Fingerprint, which Zscaler Support changes: with 5 users sharing one laptop the count shows 5 on the Unique-ID and 1 on the Hardware Fingerprint. [zcc.install.rollout:device-count-basis]

**Before deploying.** Before deployment, Zscaler recommends gathering, for the Windows and macOS computers users will be on, the OS versions, browsers, VPN clients, antivirus solutions, firewalls, computer management mechanisms, key applications and how application packages are distributed, and testing Client Connector on as many different computers as possible in each phase. [zcc.install.rollout:platform-inventory]

**Phases.** Zscaler recommends a 4-phase deployment: Phase 1 IT Test with 25-50 users, Phase 2 Expanded IT Test with another 100 to 150 users, Phase 3 End User Group with another 200 to 300 users, and Phase 4 Remaining Users in groups of 1,000 users each. The success criterion for phases 1 to 3 is that no blockers exist for moving to the next phase, and for phase 4 that no blockers exist. [zcc.install.rollout:phases] The pages give no per-phase duration or rollback criteria [gap:zcc.install.rollout:phase-details].

**What to test.** The best-practices page's test items include VPN interoperability: for users running Client Connector with VPN clients or applications that function like VPNs (for example Microsoft Always ON VPN), it says Zscaler recommends selecting Tunnel with Local Proxy as the forwarding profile action. It also suggests forwarding profiles that disable the app on trusted networks that have GRE or IPSec tunnels forwarding traffic to Zscaler, PAC files to exempt some user traffic, and tests of functionality on and off trusted networks, SSL inspection and custom app profiles. [zcc.install.rollout:phase-1-tests] Other pages recommend a different forwarding action beside a VPN client: [Running Client Connector with a corporate VPN client: forwarding action per platform and VPN mode, detection, DNS behavior](kb:zcc.interoperability.vpn-clients). For SSL inspection of Client Connector traffic the page says to turn on Install Zscaler SSL Certificate in app profiles, which is not supported on devices running macOS Big Sur (11) and later; to enable SSL inspection for Client Connector users on each relevant platform in the Policy for Zscaler Client Connector section of the SSL Inspection page; and to specify applications that perform certificate pinning under Do Not Inspect these Applications. [zcc.install.rollout:ssl-inspection-tests]

**App profile recommendations.** For app profiles the page says to select Debug as the Log Mode in Phase 1 and Error in Phase 4. For Windows users whose app runs in Tunnel with Local Proxy mode, it says Disable Loopback Restriction is required for that mode, Zscaler recommends Override WPAD for fresh installations where WPAD is still present or received by DHCP unless the devices must utilize WPAD, and Zscaler recommends Restart WinHTTP Service to delete any cached WPAD settings. [zcc.install.rollout:app-profile-recommendations] The WPAD options are described differently for no-default-route environments [divergence:zcc.install.rollout:override-wpad-direction]; those environments are in [Deploying Client Connector where the only egress is a proxy: the System PAC, spoofed DNS records and the four scenarios](kb:zcc.interoperability.no-default-route) and [ZIA in a no-default-route network: PAC options, tunnels and where the SLA stops](kb:zia.traffic-forwarding.no-default-route).

**Updating to a new version.** Before deploying the latest Client Connector version to all user groups, Zscaler recommends first testing it on specific groups (for example an Early Adopter user group), which the page says prevents auto-updates and controls deployment to the organization's user groups. The steps are to create a user group for the latest version, sync the directory groups between Internet & SaaS and Client Connector, and set the version to install to Latest for the test group and to a specific version for the other groups. [zcc.install.rollout:update-test-group] During the update of Client Connector, established client connections might be affected, and clients might need to re-establish their connections after the update. [zcc.install.rollout:update-disrupts-connections] Reverting after an unsuccessful upgrade is in [Reverting Client Connector to the previous version: availability, enabling it, the commands and what a revert keeps](kb:zcc.install.revert). What preventing auto-updates means for the test group is open [gap:zcc.install.rollout:prevent-auto-updates].

Sources disagree (name both sides):
- The deployment best practices recommend Override WPAD unless devices must use WPAD, and Restart WinHTTP Service to delete cached WPAD settings; the no-default-route page's Scenario 1 makes both options optional and enabled if WPAD is in use. [divergence:zcc.install.rollout:override-wpad-direction]
  - zscaler-help: Select Override WPAD unless the devices must utilize WPAD, for fresh installations where WPAD is present or received by DHCP, and select Restart WinHTTP Service to delete cached WPAD settings.
  - zscaler-help: In Scenario 1, both options are optional and enabled if WPAD is in use.
  Impact: The pages give opposite conditions for the same Windows app profile options: one recommends Override WPAD unless devices must use WPAD, the other enables it if WPAD is in use. The contexts differ (a general Tunnel with Local Proxy rollout against a no-default-route Scenario 1), which the pages do not reconcile.
