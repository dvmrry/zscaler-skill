# Client Connector's two PAC files: what the forwarding profile PAC and the app profile PAC do in Tunnel and Tunnel with Local Proxy modes, and the forwarding PAC in Enforce Proxy (zcc.pac-files)
Also called: forwarding profile pac; app profile pac; pac files best practices; zapp_local_proxy

Client Connector uses two PAC files that do different jobs. Client Connector uses PAC files in the forwarding profile and in the app profile. The forwarding profile PAC file directs system, browser and application traffic to the app; when the app receives traffic, the app profile PAC file directs it to the Zscaler cloud, by changing the proxy return statement to the IP address of the geographically closest data center. [zcc.pac-files:two-pac-files]

**Tunnel mode.** In Tunnel mode a forwarding profile PAC file is commonly used to get web traffic on nonstandard ports to the app (the page's example sends ports 8080 and 8081 to PROXY ${ZAPP_LOCAL_PROXY} and everything else DIRECT). The page says to select Apply on Network Change or Never for the Proxy Action Type: Apply on Network Change applies proxy settings once when the network changes and does not enforce them, and Never applies no PAC file configuration to the system. Routes and filters direct browser, system or application traffic to the app, which intercepts any traffic heading to port 80 and port 443. [zcc.pac-files:tunnel-mode-fp-pac] The Proxy Action Type names the page uses differ from the Forwarding Profiles page [divergence:zcc.pac-files:proxy-action-type-names]. In Tunnel mode the app profile PAC file directs traffic that the app received to the Zscaler cloud: from it the app chooses the data center and tunnels the traffic to it with the Connect Tunnel method, and if the PAC file contains exceptions for traffic the app sends that traffic directly to the destination server. The page says to configure exceptions for traffic that must be bypassed and to keep the PAC file as simple as possible. [zcc.pac-files:tunnel-mode-app-pac]

**Tunnel with Local Proxy mode.** In Tunnel with Local Proxy mode the forwarding profile PAC file is responsible for directing system, browser and application traffic to the app, and an exception in it bypasses traffic so that it does not reach the app. When the app downloads this PAC file it replaces the macro with a loopback IP address and the port the app is listening to, then applies the PAC file to the system, browser and applications. If traffic does not follow the forwarding profile PAC file, it reaches neither the app nor the Zscaler cloud and is sent directly. When using the app profile PAC for this mode the page says to keep it as simple as possible. [zcc.pac-files:local-proxy-fp-pac]

**Enforce Proxy mode.** In Enforce Proxy mode, Client Connector acts similarly to a GPO pushing a PAC file on the system: it enforces the forwarding profile PAC file on the machine. [zcc.pac-files:enforce-proxy-pac]

**IPv6.** In an IPv6 environment, the page says IPv6 bypasses are required for Private Access apps in the app profile PAC file when the forwarding PAC is configured to send traffic to the Client Connector listener; it says so in both its Tunnel mode and its Tunnel with Local Proxy sections. [zcc.pac-files:ipv6-zpa-bypass]

**Bypasses.** SSL and authentication bypasses are applied in the Admin Console by configuring the SSL bypass list and the Authentication Bypass list; traffic that must not reach the Zscaler cloud and has to be bypassed on the client itself must be bypassed in the PAC files used for Client Connector. The page's example bypasses a domain and its subdomains with shExpMatch on host for both safemarch.com and *.safemarch.com. [zcc.pac-files:where-bypasses-go] To let users bypass Client Connector when they browse to the organization's identity federation URL for authentication, a custom PAC file is added to their app profile: on the PAC and Proxy tab, under PAC Configuration, its URL is entered as the Custom PAC URL. [zcc.pac-files:id-federation-bypass] The deployment best practices say that if the PAC file has a DNS resolve function, it should be added to the forwarding profile PAC file only, to avoid duplicating the DNS query; the URL for the exemption PAC file can be specified when configuring app profiles and forwarding profiles. [zcc.pac-files:dns-resolve-forwarding-only]

**Gateways and fallback.** For Zscaler Client Connector version 1.4 or later, multiple Public Service Edge for Internet & SaaS gateway destinations can be configured based on the destination the user is accessing. For optimal performance the page says not to define more than two return statements that contain Client Connector gateway IP addresses; its example, to send traffic for internal hosts to a specific data center and all other traffic to the geographically closest one, defines two return statements with the respective Public Service Edge for Internet & SaaS gateway IP addresses. [zcc.pac-files:two-gateway-returns] If the primary and secondary data center from the PAC file both fail, Client Connector attempts to connect to gateway.<cloudname>.net, unless the Fallback to gateway domain setting is disabled. [zcc.pac-files:gateway-fallback]

**Rolling out and slowness.** To prevent outages, Zscaler strongly recommends rolling out all PAC file changes to a small set of users before deploying them to all users. [zcc.pac-files:staged-rollout] The vendor's checks for slowness with Client Connector include: whether the data center has issues; traceroute for ISP issues; checking for and removing dnsResolve(), isResolvable() and isInNet() from the app profile PAC file; whether network firewalls or scanning interfere; browsing to a website without a proxy, with the PAC file only, and with Client Connector; whether another process such as a GPO also applies proxy settings, which can conflict with the app and cause performance issues; and that the PAC return statement has double quotes, since missing double quotes can cause errors. [zcc.pac-files:slowness-checks]

**Open.** Where the Fallback to gateway domain setting lives is open [gap:zcc.pac-files:fallback-setting-location].

What to check:
1. Which forwarding mode the profile uses, then which of the two PAC files holds the exception for the traffic in question.
2. For Tunnel mode, the Proxy Action Type value actually set on the profile, since the page names it differently from the Forwarding Profiles page.
3. For slowness, whether the app profile PAC uses dnsResolve(), isResolvable() or isInNet(), and whether another process such as a GPO also applies proxy settings.
4. In an IPv6 environment, whether the app profile PAC has IPv6 bypasses for Private Access apps.

Sources disagree (name both sides):
- The PAC best-practices page tells Tunnel-mode users to select Apply on Network Change or Never for the Proxy Action Type; the Forwarding Profiles page, cited by zcc.forwarding-profiles.internet-actions:proxy-action-types, names the options Apply on Trusted Network Type Change and Apply on Any Network Change, and the no-default-route page also uses Apply on Trusted Network Type Change. [divergence:zcc.pac-files:proxy-action-type-names]
  - zscaler-help: The options for Tunnel mode are Apply on Network Change and Never.
  - zscaler-help: The system proxy Proxy Action Type options in Tunnel mode (the scope of zcc.forwarding-profiles.internet-actions:proxy-action-types) are Enforce, Apply on Trusted Network Type Change, Apply on Any Network Change and Never; whether the page's other mode sections name these options differently was not checked.
  Impact: Apply on Network Change matches neither name on the Forwarding Profiles page; it may mean Apply on Any Network Change, which the PAC page's description (applies once when the network changes, does not enforce) resembles, but no page says so, and Apply on Trusted Network Type Change differs in when it applies.
