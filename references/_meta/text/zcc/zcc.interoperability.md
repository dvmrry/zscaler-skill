# Client Connector alongside other software and networks: where each interoperability answer lives, plus debugging proxies, alternative cloud domains and iCloud Private Relay (zcc.interoperability)
Also called: client connector interoperability; alternative cloud domains; icloud private relay; charles proxy; fiddler

Client Connector runs next to other software and networks, and each case has its own subject: a corporate VPN client is in [Running Client Connector with a corporate VPN client: forwarding action per platform and VPN mode, detection, DNS behavior](kb:zcc.interoperability.vpn-clients), allowlisting in antivirus and host firewalls is in [Allowlisting Client Connector in antivirus and host firewalls: paths, processes, firewall directions and the 100.64 range](kb:zcc.interoperability.security-software), and an environment whose only egress is a proxy is in [Deploying Client Connector where the only egress is a proxy: the System PAC, spoofed DNS records and the four scenarios](kb:zcc.interoperability.no-default-route); the PAC files involved are in [Client Connector's two PAC files: what the forwarding profile PAC and the app profile PAC do in Tunnel and Tunnel with Local Proxy modes, and the forwarding PAC in Enforce Proxy](kb:zcc.pac-files).

**iCloud Private Relay.** iCloud Private Relay encrypts client DNS traffic before Client Connector intercepts it, which interferes with the app's ability to process DNS requests and can disrupt both Internet & SaaS and Private Access traffic flows; Zscaler recommends disabling it when deploying Client Connector to iOS and macOS devices. [zcc.interoperability:icloud-private-relay] Administrators can Disable iCloud Private Relay in App Profiles (Client Connector 4.4 and later for iOS), can return an NXDOMAIN response for the hostnames used by iCloud Private Relay traffic to alert end users that they must disable it, and, when Jamf Pro or another MDM deploys Client Connector, can restrict it by distributing a configuration profile. [zcc.interoperability:icloud-admin-controls]

**Charles and Fiddler.** On macOS, Client Connector is interoperable with the Charles Web Debugging Proxy: if Charles is detected the app creates a proxy chain, automatically configuring external proxy settings in Charles so the system routes all traffic through Charles first and then to the app. If Charles is installed after Client Connector, users must restart Charles twice after installation so the app can modify its configuration; if Charles was installed before, users do not need to restart it. [zcc.interoperability:charles] To use Telerik Fiddler with Client Connector, the app must be configured to use a PAC file that points to a specific port, so that traffic flows Browser > Fiddler > Client Connector > Destination Page (the steps use Fiddler 5.0.20182.28034); the page's PAC returns PROXY 127.0.0.1:<Port for Fiddler> then PROXY ${ZAPP_LOCAL_PROXY}. To debug on a local web server the browser's PAC file may ignore the request for 127.0.0.1, and the workaround is a hosts file entry pointing to 127.0.0.1 (for example 127.0.0.1 server.local). [zcc.interoperability:fiddler-chain] For Fiddler the forwarding profile selects Tunnel with Local Proxy or Tunnel for any network, and the PAC step is not required if Fiddler automatically configures the system proxy; in that case Tunnel must be used and not Tunnel with Local Proxy, because Client Connector enforces its own system proxy in Tunnel with Local Proxy mode. The app profile must have Rule Order 1, must be enabled, and must have the Disabled Loopback Restriction switch enabled. [zcc.interoperability:fiddler-profiles] The port Client Connector listens on is added to Fiddler's proxy string (the page's example is http=127.0.0.1:9000;https=127.0.0.1:9000;ftp=127.0.0.1:9000;); with the Fiddler AutoResponder feature the Accept all CONNECTs option must be disabled. When Internet Security is ON Fiddler can be opened and used, and errors Fiddler shows during startup can be ignored. [zcc.interoperability:fiddler-gateway]

**Alternative cloud domains.** When a Client Connector user in China connects to a Zscaler server also located in China, the connection might be blocked because the cloud on which the organization is provisioned is not registered in China; an alternative cloud domain registered in China can override the default cloud domain when connecting to the Internet & SaaS service and the Private Access service. [zcc.interoperability:acd-why] Alternative cloud domains need Client Connector 4.4 or later for Windows or 4.2 or later for macOS. With Internet & SaaS and Z-Tunnel 2.0, the forwarding profile needs a Tunnel Driver Type of Packet Filter-Based (Client Connector for Windows only), a forwarding profile action of Tunnel and a Tunnel Version Selection of Z-Tunnel 2.0. [zcc.interoperability:acd-prerequisites] Client Connector determines whether an alternative cloud domain is configured as part of Service Edge Discovery, then uses the discovered domain to connect to the Service Edge for Internet & SaaS and the Service Edge for Private Access; it connects to it automatically if a compatible version is used, and Zscaler Support can disable the feature for the organization. [zcc.interoperability:acd-discovery] On Client Connector 4.7 or later for Windows, the app locates the alternative cloud name in the default return statement of the PAC file associated with the app profile. If the PAC file uses the ${GATEWAY_FX} macro or a similar macro, the PAC server replaces it with the alternative cloud domain along with the Public Service Edge for Internet & SaaS IP address and port; if the return statement does not include an alternative domain, the app uses the alternative domain in the HTTP response header of the PAC file and connects based on the app's location, not the Service Edge location. [zcc.interoperability:acd-pac-selection] Which domains exist and how they are provisioned is open [gap:zcc.interoperability:acd-provisioning].

What to check:
1. For DNS or traffic problems on an iOS or macOS device: whether iCloud Private Relay is enabled on it.
2. For a Fiddler chain: that the app profile has Rule Order 1, is enabled and has Disabled Loopback Restriction enabled, and that the forwarding action matches how Fiddler sets the system proxy.
3. For users in China: that the version and forwarding profile prerequisites for an alternative cloud domain are met.
