# Adaptive Access Engine integrations: Okta, CrowdStrike, Microsoft Defender and Silverfort signals and setup (unified.adaptive-access.integrations)
Also called: adaptive access okta integration; adaptive access crowdstrike integration; adaptive access microsoft defender integration; adaptive access silverfort integration; Test Integration; adaptive access integrations page

Each of the Okta, CrowdStrike, Microsoft Defender and Silverfort pages configures its integration from Policies > Common Configuration > Adaptive Access > Integrations, has a Status setting that enables the integration, and verifies the connection with Test Integration. [unified.adaptive-access.integrations:integrations-page] The profiles that use these signals are in [Adaptive Access Engine: what it is, prerequisites, profiles, signal history and overrides](kb:unified.adaptive-access).

**Okta.** Okta sends the engine user-related context signals, Credentials Change and Session Revoked (the page's field list names them Credentials Change and Session Revoke); the Okta page says the feature is in limited availability and to contact Zscaler Support. [unified.adaptive-access.integrations:okta-signals] The Okta integration is configured as Okta SSF settings in Experience Center. [unified.adaptive-access.integrations:okta-ssf] The Okta integration needs an Okta account with admin privileges, an Experience Center admin role that allows configuring the Okta settings, and an Okta app integration created with API Services as the sign-in method, whose Client ID is entered in Experience Center. [unified.adaptive-access.integrations:okta-prerequisites] In Experience Center the Okta integration takes a Base URL entered as <https://customeraccountname>-okta.com, the Client ID and a Public Keys URL produced with Generate Keys, which is entered in the Okta portal under Public Keys; Proof of Possession is selected by default under General Settings and must be disabled because it is currently not supported. [unified.adaptive-access.integrations:okta-fields] The Okta app must have the ssf.read, ssf.manage, okta.users.read and okta.sessions.read API scopes enabled, and the configuring Okta admin must be assigned the Super Administrator role (the page spells it Super Adminsitrator); for Apple services, if the SSF scopes are not shown, the Managed Apple ID Federation and Provisioning feature is located and enabled. [unified.adaptive-access.integrations:okta-scopes] The page names the second signal both Session Revoked and Session Revoke [gap:unified.adaptive-access.integrations:okta-signal-name].

**CrowdStrike.** CrowdStrike sends the engine user and device context signals CrowdStrike Operating System (OS) Score, Zero Trust Assessment (ZTA) Score, ZTA Sensor Score and Overall Score; the CrowdStrike page says the integration is in limited availability and to contact Zscaler Support. [unified.adaptive-access.integrations:crowdstrike-signals] CrowdStrike has deprecated the Incidents functionality, so the Adaptive Access integration to ingest CrowdStrike Incidents is defunct and its Incidents configuration is to be removed. [unified.adaptive-access.integrations:crowdstrike-incidents-defunct] The CrowdStrike Falcon API client needs the API scopes Workflows, API integration scope, Hosts and Zero Trust Assessment (ZTA) with Read permissions; the Client ID, Client Secret and Base URL are not shown again, and if they are not copied another API client must be created. [unified.adaptive-access.integrations:crowdstrike-api-client] A webhook is required to send context signals from the CrowdStrike Falcon platform to the engine: Experience Center generates the Webhook URL after the Base URL is entered, and the secret key added when configuring the webhook is entered as the Shared Secret, used to verify the authenticity and integrity of the data exchanged using the HMAC algorithm. [unified.adaptive-access.integrations:crowdstrike-webhook] The CrowdStrike integration in Experience Center takes the Base URL, Customer ID (from the Profile page on the CrowdStrike Falcon console), Client ID and Client Secret, and its connection status is disabled by default. [unified.adaptive-access.integrations:crowdstrike-fields] A workflow is an automated action initiated by a predefined trigger (security event); the page describes a Score Changed workflow whose trigger is a selected event (for example Zero Trust Assessment > Host assessment change) with Type Overall assessment, a Call webhook action and Data format Default, and whenever the trigger changes the workflow calls the webhook and signals are sent to the engine. [unified.adaptive-access.integrations:crowdstrike-workflow]

**Microsoft Defender.** Microsoft Defender for Endpoint evaluates and sends these signals to the engine: Risk Score (None, Informational, Low, Medium and High), Exposure Level (None, Low, Medium and High), Health Status (Active, Inactive, ImpairedCommunication, NoSensorData, NoSensorDataImpairedCommunication and Unknown), Device Tag (Machine Tag, a set of machine tags), RBAC Group (the machine group name) and RBAC Group ID (the machine group ID). [unified.adaptive-access.integrations:defender-signals] The Defender integration needs a Microsoft Entra user account with admin privileges, a Microsoft Defender for Endpoint account, a Microsoft Azure account with subscription for Event Hub and Logic App, and a Microsoft Entra application registered with the required permissions, with a service principal created in the Azure tenant account. [unified.adaptive-access.integrations:defender-prerequisites] The Service Permissions table lists the permissions Adaptive Access Engine needs to communicate with Microsoft Defender, starting with Microsoft Graph DeviceManagementManagedDevices.Read.All, Microsoft Threat Protection AdvancedHunting.Read.All and WindowsDefenderATP Ip.Read.All; it also lists SecurityEvents.Read.All, CustomDetections.ReadWrite.All, Incident.Read.All, Incident.ReadWrite.All, Machine.Read.All, Machine.ReadWrite.All, Machine.Scan, Alert.Read.All and Score.Read.All as Application permissions with admin consent required, and User.Read as a Delegated permission with no admin consent required. [unified.adaptive-access.integrations:defender-permissions] Zscaler Client Connector Windows 4.8 version or higher is required on devices using Microsoft Defender and Zscaler Client Connector that require Adaptive Access profiles for ZIA or ZPA policy enforcement. [unified.adaptive-access.integrations:defender-zcc-version] Azure resources are required to fetch the Microsoft Defender signals and transmit them to the engine: under Configure Azure Event Hub and Logic App, a resource group is created to store all resources related to the Zscaler Adaptive Access Engine application and a Bicep script hosted in Zscaler GitHub is run to create the resources. [unified.adaptive-access.integrations:defender-azure-resources] The Defender integration in Experience Center takes the Event Hub Instance, the Event Hub Host, a Consumer Group (the name should be $Default, or a different consumer group created on the event hub instance) and a Connection String for the shared access service (SAS) policy created in the event hub, copied with the Copy icon next to the Connection string-primary key field. [unified.adaptive-access.integrations:defender-fields]

**Silverfort.** Silverfort sends the engine user risk signals (User Risk Level). The integration needs Silverfort version 5.3 and above, a Silverfort account with admin privileges and an Experience Center admin role that allows configuring the Adaptive Access Engine settings, and takes a Bearer Token generated on the Silverfort console and the SSF Config Endpoint, the SSF well-known endpoint from Silverfort for the tenant. [unified.adaptive-access.integrations:silverfort]

**Open.** Limited availability is stated for Okta and CrowdStrike only [gap:unified.adaptive-access.integrations:limited-availability-scope], and which Falcon events to pick, the Client Connector floor on other platforms, refresh intervals and failure behavior are not stated [gap:unified.adaptive-access.integrations:integration-details]. The Signal History Value column's levels against the finer levels a source sends are in [Adaptive Access Engine: what it is, prerequisites, profiles, signal history and overrides](kb:unified.adaptive-access).

What to check:
1. That the integration was saved, its Status enabled and Test Integration run before building a profile on its signals.
2. For an Okta integration that does not connect, the app's API scopes, Proof of Possession (which must be disabled) and the Super Administrator role of the configuring admin.
3. For a CrowdStrike integration that sends nothing, the Webhook and Shared Secret, the Score Changed workflow, and that no Incidents configuration remains.
4. For a Defender integration that sends nothing, the Event Hub fields, the Azure resources and the application permissions with admin consent.
