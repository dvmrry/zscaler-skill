# Adaptive Access Engine: what it is, prerequisites, profiles, signal history and overrides (unified.adaptive-access)
Also called: adaptive access; adaptive access engine; AAE; adaptive access profile; context signals; signal history; adaptive access overrides

The Adaptive Access Engine ingests security signals and distributes adaptive access profiles in real time to policy decision points, so security policies can be evaluated and adapted by the nature of the identities, their profiles and the applications being accessed; adaptive access control is enforced at policy enforcement points in Internet & SaaS (ZIA) and Private Access (ZPA), and the events analyzed might occur inside or outside the Zscaler ecosystem. [unified.adaptive-access:what-it-is] The vendor lists as benefits using real-time signals from Zscaler and third-party security systems to adjust user access, and integrating user risk profiles, device postures and behavioral analytics into access decisions. [unified.adaptive-access:signal-sources]

**Prerequisites.** To use the Adaptive Access Engine an organization must have Authentication Service for end users enabled (or end user migration to it completed), the Zscaler Admin Console enabled, and Internet & SaaS or Private Access in use; for an organization that does not meet these, Zscaler recommends migrating its admins and its end users to Authentication Service. [unified.adaptive-access:prerequisites]

**Where signals come from.** The vendor integrations (Okta, CrowdStrike, Microsoft Defender and Silverfort), their setup and the signals each sends are in [Adaptive Access Engine integrations: Okta, CrowdStrike, Microsoft Defender and Silverfort signals and setup](kb:unified.adaptive-access.integrations). Which signals UEBA and Zscaler risk scores carry is not stated [gap:unified.adaptive-access:risk-score-signals].

**Profiles.** An Adaptive Access profile identifies user and device subjects with a set of conditions that combine context signals published by Zscaler and third-party sources using logical operators; profiles are made available to Internet & SaaS (ZIA) and Private Applications (ZPA), which enforce policies to control user and device access to applications. [unified.adaptive-access:profile-definition] The Profiles page (Policies > Common Configuration > Adaptive Access > Profiles) lists each profile with a Profile Name (unique), Description, Last Modified On and Criteria (context signals combined with logical operators), and profiles can be added, searched, edited, deleted and copied there. [unified.adaptive-access:profiles-page] The integrations with the third-party services relevant to the organization (such as Okta, CrowdStrike, Microsoft Defender or Silverfort) must be completed before profiles are defined, and only administrators can add profiles. [unified.adaptive-access:add-prerequisites] A profile takes a Profile Name, an optional Description and Criteria joined by All or Any; each criterion selects the third-party tool the context signal comes from, the event to monitor (the events differ for each tool) and an operator, logical expression, condition or numerical value, and a JSON expression is updated automatically as the criteria are defined. [unified.adaptive-access:criteria] The engine evaluates the context signals it receives against the profile criteria, and the signals are displayed on the Signal History page. [unified.adaptive-access:evaluation] Any user or device matching a profile's criteria is notified to the policy enforcement points, Internet & SaaS (ZIA) and Private Applications (ZPA); the page says UEBA and Zscaler risk scores can be added via the Adaptive Access Engine and attached to Internet & SaaS and Private Access policies. [unified.adaptive-access:enforcement] Deleting a profile requires entering YES in the Confirmation window and clicking Delete; edits are made in the Edit Profiles window and saved with Update. [unified.adaptive-access:delete-confirmation] The policy criteria that consume a profile are in [Criteria available on ZPA access policy rules](kb:zpa.policy.criteria), [How URL Filtering rule criteria combine](kb:zia.url-filtering.criteria) and [What a Cloud App Control rule matches on](kb:zia.cloud-app-control.rule-criteria). What subscribing to Experience Center changes for the criterion is open [gap:unified.adaptive-access:subscription-licensing].

**Signal History.** The Signal History page (Policies > Common Configuration > Adaptive Access > Signal History) shows the context signals for each Adaptive Access profile; each signal has a Subject (the username or device type), Subject Type (the user or device activity that triggered the event), Source (the page gives Okta, CrowdStrike, Microsoft Defender as the sources), Context Type (the type of signal received) and Creation (when the signal was generated), and the table can be filtered, searched, reset and its columns modified. [unified.adaptive-access:signal-history] The Signal History page describes the Value column as the risk (Low, High) associated with the user or device. [unified.adaptive-access:signal-history-value] Whether the Value column can show the finer levels a source sends, such as the Defender levels in [Microsoft Defender for Endpoint evaluates and sends these signals to the engine: Risk Score (None, Informational, Low, Medium and High), Exposure Level (None, Low, Medium and High), Health Status (Active, Inactive, ImpairedCommunication, NoSensorData, NoSensorDataImpairedCommunication and Unknown), Device Tag (Machine Tag, a set of machine tags), RBAC Group (the machine group name) and RBAC Group ID (the machine group ID).](kb:unified.adaptive-access.integrations:defender-signals), is open [gap:unified.adaptive-access:signal-history-value-levels]; retention, time ranges, export and the Context Type values are not stated [gap:unified.adaptive-access:signal-history-retention].

**Overrides.** Overrides are time-bound changes set by admins to a subject's (user or device) context signal value that temporarily replace the signal value from the context source, such as Okta or CrowdStrike, while retaining the original value for reference and auditing; they take effect immediately across the Adaptive Access Engine-driven evaluations (for example Internet & SaaS or Private Access), so the next access attempt reflects the change. [unified.adaptive-access:overrides] Overrides rectify inaccurate signal values from the context source or make urgent exceptions; they carry mandatory expiration and audit logging, and only context signals can be overridden, not profiles directly. [unified.adaptive-access:override-controls] The Overrides page (Policies > Common Configuration > Adaptive Access > Overrides) shows each Subject Identifier (the login ID of the user or device), Subject Type (user or device), Context Count (context signals received) and Override Count (the number of overrides). [unified.adaptive-access:overrides-page] The expiry limits and where the audit logging lands are not stated [gap:unified.adaptive-access:override-expiry-audit].

**Timing and APIs.** The latency from a signal to enforcement is described only as real time [gap:unified.adaptive-access:signal-latency]. The SDK, Terraform and legacy API surfaces for profiles have not been read [gap:unified.adaptive-access:profile-api-unmined].

What to check:
1. That the integrations for the third-party tools the profile uses were completed before the profile was defined.
2. That Authentication Service for end users, the Zscaler Admin Console and Internet & SaaS or Private Access are in use before expecting the engine to evaluate signals.
3. For a user or device whose signal value looks wrong, the Signal History row for its subject and the Overrides page for a time-bound override that replaces the source value.
4. For a Signal History Value, which source sent it, since the Value column's levels are given as (Low, High) while a source can send finer levels.
