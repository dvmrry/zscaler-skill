# App and user inventory in 3rd-Party App Governance: how apps get in, search, catalog sandboxing, bulk upload, custom views, client-ID exports (zia.app-governance.inventory)

The App Inventory page says the inventory can be automatically populated with apps by leveraging 3rd-Party App Governance's discovery capabilities, connecting SaaS platforms, manually uploading apps, and searching and adding from the 3rd-Party App Governance catalog. [zia.app-governance.inventory:population-methods] The portal is in [3rd-Party App Governance: governing third-party apps, add-ons and extensions connected to SaaS platforms, and its portal, roles and dashboard](kb:zia.app-governance), and connecting platforms is in [Connecting SaaS platforms to 3rd-Party App Governance: supported platforms, platform admin roles, permissions requested and tenant status](kb:zia.app-governance.platforms).

**Reading the inventory.** The inventory list shows, for each app, Status, App Name (which opens the App Panel), Publisher, Platform, Origin, Marketplace (whether the app is publicly available in the marketplace), Users, Usage, Risk Score (which can be changed), Access Type, Access Level, Findings, Classification (which can be changed) and Automated Workflow. The apps report can be exported to a CSV file and a link to the list can be shared. [zia.app-governance.inventory:inventory-columns] An app's origin is 1st Party (developed by the service provider integrated with 3rd-Party App Governance), 3rd Party (created by an external developer) or Internal App (developed for internal use within the organization). [zia.app-governance.inventory:origin-values] More than one filter can be applied to the inventory. Filter options that do not yet exist in the organization can still be selected when creating new views and policies, and a new app that matches such a policy triggers it. [zia.app-governance.inventory:filters] A custom view is a saved search criterion that can be used as a rule to trigger a policy, and a view marked as a favorite gets a shortcut under Reports > Predefined Reports. If a view is already used as a trigger for a policy, the confirmation window highlights that when it is edited. [zia.app-governance.inventory:custom-views]

**Finding and adding an app.** Apps can be searched by name, client ID or publisher, in the App Inventory and the 3rd-Party App Governance app catalog. A filter selects inventory, catalog or both, and by default the search results from the inventory are displayed. Apps in the catalog that are not currently in the inventory appear in blue. [zia.app-governance.inventory:search] An app that cannot be found in the inventory or catalog by name can be searched by client ID, and if it is still not found its client ID can be submitted for sandboxing. A summary shows the app as Pending and an email is received when it is uploaded. In a bulk upload, unrecognized apps are sent for sandboxing automatically and marked as pending. [zia.app-governance.inventory:sandboxing] Depending on the organization's policy, users might request approval for apps, third-party integrations and browser extensions before installing them, and an admin can manually add a vetted app to the inventory and classify it for future records. [zia.app-governance.inventory:pre-vetting] Apps are uploaded in bulk by entering the client IDs to add, separated by commas or any other delimiter, and apps in Pending mode are submitted for sandboxing. [zia.app-governance.inventory:bulk-upload]

**Getting client IDs out of the platform.** Atlassian does not have a straightforward way of exporting the client IDs of all connected apps. The Zscaler team prepares a dedicated script that is shared with clients, which extracts app IDs for Atlassian JWT apps and OAuth apps and exports them to the CSV file atlassian_app_ids.csv. [zia.app-governance.inventory:client-id-export-atlassian] The Microsoft Azure client ID export needs Administrator user credentials. After the CSV file is downloaded, app names are in the first column and client IDs are under App ID in the second column. [zia.app-governance.inventory:client-id-export-azure] In Google Workspace, admins can find all connected third-party apps under App Access Control, any Google user can find the apps with access to their account in account security settings, and the apps that accessed a Gmail inbox can be found in the inbox. [zia.app-governance.inventory:client-id-export-google] The Chrome extensions export method for admins is supported if the organization's Chrome browsers are cloud-managed: enroll users' browsers to be cloud-managed using MDM software and turn on Chrome browser reporting. The page's separate method for a user starts by opening Google Chrome and entering chrome://system/ into the address bar. [zia.app-governance.inventory:chrome-extensions-export]

**Users.** The User Inventory shows all the enabled users in 3rd-Party App Governance, with columns that include Apps (the number of apps enabled for the user) and Role. Users can be searched by email, display name or job title and the users report exported to a CSV file. [zia.app-governance.inventory:user-inventory] The User Panel has tabs that show the user's sign-in activities, the top apps and the user's permissions, and an activities view that can be filtered by User Activity, Security Event and Findings. [zia.app-governance.inventory:user-panel-tabs] The Files tab of the User Panel shows the Data Loss Prevention (DLP) violations for the user's files over a selected period, classified by document type. It is in limited availability, and needs a license for SaaS Security Data at Rest Scanning DLP with the DLP scan previously configured. [zia.app-governance.inventory:user-panel-files-tab] The scan requirement matches [A configured rule inspects nothing until it is added to a scan schedule: the Zscaler service does not inspect content until a scan is configured.](kb:zia.casb:no-scan-no-inspection).
