# Where a DLP match goes: notification, ICAP, Incident Receiver and Cloud-to-Cloud (zia.dlp.incident-forwarding)
Also called: dlp icap; dlp third party integration; can third party dlp block; zscaler incident receiver; cloud to cloud incident forwarding; c2c incident forwarding; dlp notification template; dlp email auditor; dlp end user notification; dlp zwa incidents; cloudToCloudIR

A rule's own decision and the places a match is reported are separate.

**The decision.** A DLP rule can detect data, allow or block the transaction, and notify the organization's auditor. Zscaler only monitors or blocks content according to the configured policy. [zia.dlp.incident-forwarding:native-action] The action and its enum are in [Web DLP policy rules: order, criteria and actions](kb:zia.dlp.rules) and [Web DLP rule API fields, enums and fields the contract does not document](kb:zia.dlp.rule-wire-shape).

**Third-party DLP over ICAP.** A rule can forward information about a violating transaction to a third-party DLP solution over secure ICAP, but Zscaler does not take ICAP responses back. Zscaler decides by its own policy and forwards the transaction information so the organization can remediate. [zia.dlp.incident-forwarding:icap-one-way] For the two rule kinds that forward to a third-party DLP solution (using Zscaler DLP engines, or based on specific criteria), the About DLP page lists what Zscaler sends: the client IP and username of users attempting to send data (via ICAP X-headers), and a copy of the HTTP POST request that contains the relevant file or content (if content is from HTTP Form data or a text file), which also includes the host URL the user was sending content to. [zia.dlp.incident-forwarding:icap-forwarded-content] The third-party solution needs a rule that detects the same data type, or the forwarded information does not appear in its dashboard. The other criteria of the two rules need not correspond. [zia.dlp.incident-forwarding:icap-needs-matching-rule] For a rule without content inspection, the third-party DLP solution needs a rule that detects the same file type as the Zscaler rule, or the information Zscaler sends about a rule violation does not appear in the solution's dashboard; the rules need not correspond exactly in other criteria. In the vendor's example, the on-premises rule must also block PDFs but need not specify the same URL category. [zia.dlp.incident-forwarding:without-ci-matching-file-type] The ICAP URI, the FCC cloud and mTLS are in [ICAP receivers for DLP: secure and unencrypted ICAP, the FCC cloud and mTLS](kb:zia.dlp.icap-receivers).

**Incident Receiver and Cloud-to-Cloud.** ICAP receivers are specified on Inline Web DLP policy rules. A Zscaler Incident Receiver can be added to a DLP policy rule with content inspection, without content inspection, or Data at Rest Scanning DLP, and an outbound email policy rule can select one. Cloud-to-Cloud Incident Forwarding configurations apply to policy rules for Inline Web DLP, Data at Rest Scanning DLP, Outbound Email DLP and Endpoint DLP. [zia.dlp.incident-forwarding:destinations-by-rule-type] A rule without content inspection offers three DLP Incident Receiver destinations: an ICAP receiver (which must be configured to complete the step), a Zscaler Incident Receiver, or Cloud-to-Cloud Forwarding, selected by tenant and Cloud-to-Cloud Forwarding Configuration. [zia.dlp.incident-forwarding:without-ci-destinations] A Zscaler Incident Receiver can be added to a DLP policy rule as a DLP Incident Receiver, and the web DLP article also offers it as an optional destination for content that triggers an outbound email policy rule, reached via secure ICAP. Zscaler does not take ICAP responses from it either. [zia.dlp.incident-forwarding:incident-receiver] The Zscaler Incident Receiver is only available for organizations that do not already own an ICAP server. [zia.dlp.incident-forwarding:ir-only-without-icap-server] Its deployment on a VM is in [Zscaler Incident Receiver: requirements per platform, storage, health check and VM commands](kb:zia.dlp.incident-receiver). Cloud-to-Cloud Incident Forwarding sends metadata and evidence about violating transactions directly to the customer's public cloud storage without appliances. It is selected on the rule by tenant and forwarding configuration. [zia.dlp.incident-forwarding:cloud-to-cloud] Onboarding AWS, Google Cloud and Azure storage is in [Cloud-to-Cloud Incident Forwarding: storage onboarding for AWS, Google Cloud and Azure](kb:zia.dlp.cloud-to-cloud-forwarding). Cloud-to-Cloud forwarding is a configurable API surface of its own (`/cloudToCloudIR`, with a lite list, a count and a validate-delete check), not only a back-end pipe. [zia.dlp.incident-forwarding:c2c-api] The rule's `receiver` field carries which of these a rule uses ([Web DLP rule API fields, enums and fields the contract does not document](kb:zia.dlp.rule-wire-shape)). The Cloud-to-Cloud data source exposes credentials as plain strings, covered in [How the Zscaler Terraform providers store, log, and send secrets](kb:shared.terraform.credential-handling).

**Supporting objects.** The Go SDK has separate endpoints for ICAP servers (`/icapServers`), Incident Receiver servers (`/incidentReceiverServers`), DLP notification templates (`/dlpNotificationTemplates`), IDM profiles (`/idmprofile`) and EDM schemas (`/dlpExactDataMatchSchemas`). [zia.dlp.incident-forwarding:supporting-objects-endpoints] Terraform data source output for these objects is in [What ZIA Terraform data sources return, drop, or get wrong](kb:zia.terraform.data-source-fidelity).

**Email and end user notification.** No notification is sent for a rule if an auditor and a notification template are not selected. Templates are configured separately beforehand. [zia.dlp.incident-forwarding:notification-needs-both] What a template holds is in [DLP notification templates: auditor email subject, macros, attachments and TLS](kb:zia.dlp.notification-templates). In a rule without content inspection, the Auditor Type is a Hosted database or External, and for a hosted-database auditor an auditor is selected or searched for. EUN is supported only with Block actions and requires an Advanced DLP rule, and if neither an auditor nor a Notification Template is selected, no notification is sent for the rule. [zia.dlp.incident-forwarding:auditor-type-and-eun-requirement] In default mode, a rule can enable an end user notification (EUN) triggered by the rule, with a default or custom message displayed to users, and EUN is supported only with Block actions and requires an Advanced DLP rule. The Evaluate All Rules article describes the same setting as a Show/Hide choice for an EUN message on endpoints, whose message type depends on the rule's action. [zia.dlp.incident-forwarding:end-user-notification]

**Workflow Automation.** Workflow Automation integrates with ZIA to capture the Data Protection incidents generated from the DLP policies defined in ZIA, and its Incidents page covers Inline, Endpoint, Email and SaaS Security DLP. [zia.dlp.incident-forwarding:zwa-captures-incidents] How ZWA ingests its incidents is open Workflow Automation takes its incidents through such a forwarding method, Incident Receiver or Cloud-to-Cloud: [On AWS, the DLP application integration uses Zscaler's incident-forwarding methods, Zscaler Incident Receiver or Cloud-to-Cloud Incident Forwarding, which send information about policy violations to the organization's S3 buckets.](kb:zwa.incidents:integration-methods)..
