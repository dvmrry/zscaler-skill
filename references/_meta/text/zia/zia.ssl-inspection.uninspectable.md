# What SSL/TLS inspection cannot inspect: pinned apps, client certs, QUIC, BYOD, IoT (zia.ssl-inspection.uninspectable)
Also called: cant inspect ssl; certificate pinning; undecryptable traffic; quic ssl inspection; byod guest network inspection; iot ssl inspection; ssl inspection fails for app; works in the browser but fails in the desktop app; desktop app fails behind zscaler

When inspection "fails" the question is whether it could ever have worked. Four populations cannot be inspected whatever the rule says.

**The endpoint cannot trust the certificate.** Inspection is not possible on devices that cannot reasonably install the Zscaler certificate, such as IoT/OT devices, BYOD and guest networks. [zia.ssl-inspection.uninspectable:cannot-install-cert] BYOD and guest networks are generally impossible to inspect because the root CA cannot be installed, so they should be completely segmented away from the organization's network with no access to anything but the internet. [zia.ssl-inspection.uninspectable:byod-guest-segmented] IoT devices are in a similar state: most do not accept trust-store changes, and if the devices are compatible inspection might still be possible, though it likely needs a custom policy and one or more sublocations for those devices. [zia.ssl-inspection.uninspectable:iot]

**The application refuses the certificate.** Applications that pin a certificate reject any other certificate, so Zscaler cannot inspect them; the guide names Apple, many Microsoft 365 apps, Adobe, Cisco WebEx and the Dropbox app, and says pinning is common in iOS and Android apps. The remedies are to replace the application, bypass it only if it is valuable enough to justify the risk, or deny it. [zia.ssl-inspection.uninspectable:cert-pinning] Zscaler's pinning article defines certificate pinning as a non-browser desktop or mobile application validating that the TLS certificates presented by its back-end TLS web servers match a known set pinned or hardcoded in the application. Zscaler dynamically issues trusted MITM certificates signed by the Zscaler intermediate CA or the customer's intermediate CA, which certificate-pinned clients might not be able to match to the pinned certificates, leading to a termination of the connection. [zia.ssl-inspection.uninspectable:pinning-definition] The Understanding SSL/TLS article defines Public Key Pinning (PKP), also known as certificate pinning, as the process of associating a host with its expected public key, and says it is typically seen only if a web service or web application provider owns both the server-side code and the client-side code. [zia.ssl-inspection.uninspectable:pkp-definition] What the pinned item is differs between the pages [divergence:zia.ssl-inspection.uninspectable:pinned-item-is-client-or-server-certificate]. Public Service Edges cannot detect certificate pinning because there is no specific messaging from the client indicating that it has a pinned certificate: there is no response to the server certificate sent to the client and the connection fails. There might be situations where the client closes the connection with a FIN or RST flag, but that is not sufficient to detect pinning and take corrective action. [zia.ssl-inspection.uninspectable:pinning-undetectable] Because certificate pinning is a client-side function the SSL/TLS connection fails between the client and the proxy, and clients show no standard behavior when terminating a connection: some end the handshake with a fatal error stating the reason as Unknown CA or generate an Encrypted Alert (close notify) after the handshake followed by a FIN, and in some cases the client just resets the connection without exchanging any application data. [zia.ssl-inspection.uninspectable:pinning-failure-signatures] The deployment best practices say client applications like Dropbox use a technique called certificate pinning, that apps which use it might not work with SSL/TLS Inspection, and that they should be included in the list of URL categories for which SSL/TLS transactions will not be decrypted. [zia.ssl-inspection.uninspectable:pinned-apps-deploying] When certificate pinning is in place, exempt the application by removing the cloud application from SSL inspection or the individual domains, using custom URL categories; for mobile apps, SaaS Security can inspect the data at rest instead of in transit. [zia.ssl-inspection.uninspectable:pinning-exempt-by-app-or-domain] Zscaler's table of native applications that use certificate pinning includes, among others, Adobe Acrobat Reader (Fill & Sign), Adobe Creative Cloud, Adobe Updates, Amazon Workspaces, Apple iMessage, Apple iTunes and App Store, Dropbox, Evernote, Google Shared Services and Drive, Google Hangouts, Google Play store (Android), GoTo Applications, Microsoft Defender, Microsoft 365, Signal, Windows Store and Xbox Live (Windows), and mobile applications Facebook, Instagram, Netflix, PayPal and Spotify. [zia.ssl-inspection.uninspectable:pinned-native-apps] The pinning table gives per-application remedies: iMessage on OSX and iOS fails to send or receive messages unless p24-keyvalueservice.icloud.com is bypassed; for Microsoft 365 the table's Notes column says to use Office365 One-Click Configuration in Policies > Access Control > Advanced Settings; Amazon Workspaces needs a firewall network service, Allow connection to PCoIP - Amazon Workspaces, for destination ports 4172 and 4195; Google Drive can be configured to ignore its certificate pinning with the CLI switch googledrivesync.exe --unsafe_network; and for Evernote the page says to select the Evernote Application instead of URLs. [zia.ssl-inspection.uninspectable:pinned-app-remedies] The pinning table's Error Message column records that Dropbox and PayPal (mobile) show Cannot log in. The table also says that without bypasses iTunes and App Store partially work but many icons do not appear and apps cannot be downloaded or purchased unless the listed URLs are bypassed; that Game updates and Battle.net updates are not downloaded, with no error message; and that the Windows Store and various apps built into Windows 8.x/10 do not load properly or allow sign in, and native Xbox Live on Windows 8.x/10 does not work or allow login, if their URLs are not bypassed. [zia.ssl-inspection.uninspectable:pinned-symptoms] The Amazon Workspaces row's domain list overlaps an exemption the guide warns against [divergence:zia.ssl-inspection.uninspectable:amazon-workspaces-cloudfront-exemption]. The trust-store article says Snowflake uses certificate pinning, which prevents inserting a custom CA certificate in the middle, and that for Snowflake traffic to work through Zscaler it must be put on an SSL/TLS Inspection bypass list. [zia.ssl-inspection.uninspectable:snowflake-pinning] The same page also gives a trust-store replacement for Snowflake [divergence:zia.ssl-inspection.uninspectable:snowflake-trust-store-or-bypass]. The second kind of refusal, an application that embeds its own CA bundle, is open [gap:zia.ssl-inspection.uninspectable:ca-bundle-pinned-vendor-apps].

**The protocol cannot be decrypted.** Zscaler cannot inspect sites and applications that use client-authentication certificates or unsupported ciphers, and recommends blocking undecryptable traffic unless the organization has a specific use case for it. [zia.ssl-inspection.uninspectable:client-certs-and-ciphers] The Zscaler service does not support SSL/TLS inspection of websites that mandate Mutual TLS. The deployment best practices say to update the global bypass list to bypass TLS sessions that use Client Certificate Authentication, because Zscaler does not support the decryption of mutually authenticated TLS sessions. [zia.ssl-inspection.uninspectable:mutual-tls] The Understanding SSL/TLS article says the actual hostname and domain name being accessed are not visible, and that how the Zscaler service determines the destination host name depends on whether it is operating in transparent mode or explicit mode. [zia.ssl-inspection.uninspectable:primer-hostname-not-visible] The proxy-mode page says differently for transparent mode [divergence:zia.ssl-inspection.uninspectable:hostname-visibility]. The supported versions and suites are in [Which TLS versions and cipher suites SSL/TLS inspection supports, and what happens to the rest](kb:zia.ssl-inspection.cipher-suites). The setting that blocks it is Block Undecryptable Traffic in [What an SSL/TLS inspection action does: Inspect, Do Not Inspect, Block and their settings](kb:zia.ssl-inspection.actions).

**The traffic never reaches the TCP path.** Google's QUIC protocol skips the TCP handshake and uses UDP while Zscaler's inspection relies on TCP session information, so Zscaler recommends blocking QUIC; the browser or device then falls back to TCP connections. Both the Zscaler firewall and Client Connector can block it. [zia.ssl-inspection.uninspectable:quic]

Everything not on this list should be inspectable once the root is trusted, which is the job of [SSL/TLS inspection certificates: who signs, and where the root must be trusted](kb:zia.ssl-inspection.certificates). Choosing to exempt a population instead is [Writing SSL/TLS inspection exemptions without exempting too much](kb:zia.ssl-inspection.exemptions), and what stops working for it is [What stops working when traffic bypasses SSL/TLS inspection](kb:zia.ssl-inspection.bypass-impact).

Sources disagree (name both sides):
- The SSL/TLS primer says the hostname and domain name being accessed are not visible; the proxy-mode page says that in transparent mode the service identifies the destination host using the Server Name Indication extension of the client hello when it includes SNI. [divergence:zia.ssl-inspection.uninspectable:hostname-visibility]
  - zscaler-help: The actual hostname and domain name being accessed are not visible, and the service's way of determining the destination host name depends on transparent or explicit mode.
  - zscaler-help: In transparent mode the Service Edge identifies the destination host using the SNI extension when the initial HTTPS request (client hello) includes SNI (existing claim zia.proxy-mode.transparent:host-identification).
  Impact: A reader of the primer alone concludes the host is hidden before decryption, while the proxy-mode page says that in transparent mode it is read from SNI when present; the primer's next sentence defers to the mode.
- The trust-store article says Snowflake traffic needs a custom CA PEM file replacing the PEM under the Snowflake ODBC driver and, on the same page, that Snowflake uses certificate pinning and must be put on an SSL/TLS Inspection bypass list. [divergence:zia.ssl-inspection.uninspectable:snowflake-trust-store-or-bypass]
  - zscaler-help: Snowflake traffic works over HTTPS in a proxy environment if the PEM file under the Snowflake ODBC Driver etc directory is replaced with the custom CA PEM file.
  - zscaler-help: Snowflake uses certificate pinning, so its traffic must be put on an SSL/TLS Inspection bypass list.
  Impact: The page gives a trust-store fix and a bypass for the same application; it does not say which applies to which Snowflake client or whether the PEM replacement is for the ODBC driver only.
- The deployment best practices say a pinning application is hard coded to accept one specific client certificate; the pinning article and the leading practices guide describe pinning of the server's certificates. [divergence:zia.ssl-inspection.uninspectable:pinned-item-is-client-or-server-certificate]
  - zscaler-help: The client application is hard coded to accept only one specific client certificate.
  - zscaler-help: The application validates that the certificates presented by its back-end TLS web servers match a known set pinned or hardcoded in the application.
  - zscaler-help: The application is hard-coded with a server certificate and treats any other certificate as invalid (existing claim cert-pinning).
  Impact: The deployment page's wording calls the pinned item a client certificate while the other two describe a server certificate; which certificate is pinned is stated differently.
- The pinning article lists .cloudfront.net among the Amazon Workspaces domains to exempt from SSL/TLS Inspection; the leading practices guide lists .cloudfront.net among exemptions to avoid. [divergence:zia.ssl-inspection.uninspectable:amazon-workspaces-cloudfront-exemption]
  - zscaler-help: To prevent pinned applications from breaking, exempt them from SSL/TLS Inspection; the Amazon Workspaces row lists .amazonaws.com, .amazonworkspaces.com, .awsapps.com and .cloudfront.net.
  - zscaler-help: Exemptions to avoid include .cloudfront.net; exempting these domains should not be done without serious consideration (existing claim zia.ssl-inspection.exemptions:shared-storage-domains).
  Impact: The pinning table's domain list includes a domain the guide advises against exempting without serious consideration; the guide's wording softens it, and the pages do not say how the two reconcile.
