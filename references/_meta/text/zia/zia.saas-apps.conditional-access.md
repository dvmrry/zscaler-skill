# Conditional Access blocks users behind ZIA: Source IP Anchoring (zia.saas-apps.conditional-access)
Also called: entra conditional access named location; microsoft 365 blocked from zscaler ip; trusted location corporate ip; sipa conditional access; ip based location trust saas; pse ip trusted list entra

When a SaaS identity provider only accepts sign-ins from named IP ranges, users behind ZIA fail the check even though they authenticate correctly. For Microsoft 365 the supported answer is Source IP Anchoring. Source IP Anchoring addresses Microsoft 365 Conditional Access that lets users in only from a trusted location such as a corporate network (with multifactor authentication) and blocks other locations; anchoring associates the traffic with the trusted location. [zia.saas-apps.conditional-access:ca-use-case]

**Why it fails.** Sign-ins routed through ZIA's shared Public Service Edge addresses fail an IP-based named-location check, because the destination sees a Zscaler address rather than a corporate one; anchoring makes it see the App Connector's address. [zia.saas-apps.conditional-access:shared-edge-ips-fail-named-location]

**What to anchor.** Anchoring only the initial login traffic to the Microsoft Azure AD domain is sufficient; after sign-in the application traffic uses an authenticated token and does not need to be redirected. [zia.saas-apps.conditional-access:anchor-login-only] The Office 365 application segment for anchoring names login.microsoftonline.com (login.windows.net or login.microsoft.com are alternatives), on TCP 80 and 443. [zia.saas-apps.conditional-access:login-hosts] Anchoring for Microsoft 365 also needs the preconfigured DNS Control rules enabled and ranked first: ZPA Resolver for Locations for location users and ZPA Resolver for Road Warrior for remote users. If the Road Warrior rule is disabled, remote traffic falls under the Locations rule rather than being blocked. [zia.saas-apps.conditional-access:dns-resolver-rules] The rest of the setup (the application segment with the Source IP Anchor option, the client forwarding and access policies, the gateway and the forwarding rule) is in [Source IP Anchoring: what it needs on each side](kb:zia.forwarding-control.sipa); the direct variant is [Source IP Anchoring Direct during ZIA disaster recovery](kb:zia.forwarding-control.sipa-direct).

Trusting the Zscaler edge IPs in Entra instead of anchoring is open [gap:zia.saas-apps.conditional-access:trusted-list-alternative]. Whether the same pattern applies to other IP-trusting SaaS is open [gap:zia.saas-apps.conditional-access:other-saas-ip-trust]. The layer at which Conditional Access SAML POST failures occur is open [gap:zia.saas-apps.conditional-access:ca-saml-post-inspection]. If the symptom is a personal account working rather than a corporate one being blocked, this is the wrong subject: see [Tenant restriction does nothing: bypass rule ahead of the login inspection rule](kb:zia.saas-apps.tenant-restriction-order).
