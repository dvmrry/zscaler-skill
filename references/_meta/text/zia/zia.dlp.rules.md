# Web DLP policy rules: order, criteria and actions (zia.dlp.rules)
Also called: dlp policy rule; web dlp rule criteria; dlp rule order; dlp rule admin rank; match only; inspect downloads; dlp unauthenticated traffic; dlp rule limit; dlp confirm action; why did this dlp rule not match; dlp rule save fails

A DLP rule answers "who, where, and what happens when an engine triggers". The detection itself lives in the engines the rule references ([DLP engines: the unit a rule references](kb:zia.dlp.engines)). The order below holds in the default mode; Evaluate All Rules mode changes it ([Why DLP did or did not fire: pipeline position, evaluation mode and exemptions](kb:zia.dlp.evaluation)).

**Order and rank.** DLP policy rules are evaluated in ascending rule order and, by default, evaluation stops at the first match; a disabled rule keeps its place in the order while the service skips it. Evaluate All Rules mode (see zia.dlp.evaluation) changes this. [zia.dlp.rules:ascending-order] Admin rank is 0 to 7, with 0 the highest. A rule with a higher admin rank always precedes a rule with a lower one, so the admin's rank limits which rule order values can be chosen. [zia.dlp.rules:admin-rank] Disabled rules still hold their slot, the same convention as [URL Filtering rule order and first match](kb:zia.url-filtering.rule-order). DLP policy falls under the limit for all other policy rules, 1,024 rules, which the Zscaler Account team can raise to 2,048. [zia.dlp.rules:rule-cap] The Terraform DLP web rules documentation warns that ZIA DLP supports a maximum of 127 Web DLP rules created via the API. [zia.dlp.rules:tf-docs-web-rule-cap-127] That cap does not match the generic 1,024-rule limit [divergence:zia.dlp.rules:web-rule-cap-127-vs-1024]. A rule can be associated with a rule label chosen from the existing labels; the label is an object reference, not free text. [zia.dlp.rules:rule-label] Terraform's ordering of DLP rules has its own behavior, covered in [How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order).

**Rule kinds.** The About DLP page lists four kinds of DLP policy rule, and says a policy can use one or more of them simultaneously: monitor or block data using Zscaler DLP engines; the same, then forward information to a third-party DLP solution; monitor or block data based on specific criteria, then forward information to a third-party DLP solution (a kind where Zscaler does not use its DLP engines); and monitor or block data based on data size to leverage Zscaler's DLP policy without scanning for specific data within the content. [zia.dlp.rules:rule-kinds-combinable] A rule's name is system-generated and editable and cannot exceed 63 characters, and a new rule's status is Disabled by default, so the rule must be enabled to be enforced on traffic; the articles for rules with and without content inspection both say so. [zia.dlp.rules:name-and-default-status]

**Choosing engines.** Content Matching selects DLP engines: Any selects all engines, otherwise up to 4 engines can be chosen for one rule. [zia.dlp.rules:engine-selection] In Evaluate All Rules mode, choosing None for DLP engines means the service does not scan content with engines and instead acts as a filter, flagging content only by the other criteria. [zia.dlp.rules:no-engines-filter-mode] Match Only applies to both Allow and Block rules. Deselected, one of the rule's engines triggering is enough for the service to act. Selected, all of the rule's engines must trigger and the transaction must not match any other engines from different rules, so a PCI-only rule does not fire when a transaction triggers both the PCI and HIPAA engines. [zia.dlp.rules:match-only] In the vendor's Match Only example, Rule 1 allows the finance team to send credit card numbers, Rule 2 allows human resources to send social security numbers and Rule 3 blocks the rest of the organization from sending both. When a finance team member sends a document containing both and Rules 1 and 2 have Match Only selected, the document does not match Rule 1, because Rule 1 only triggers if a document contains only credit card numbers and no additional content that triggers other engines from different rules, and it matches Rule 3, so the policy blocks it; when Match Only is not selected for Rules 1 and 2, the document matches Rule 1 and the policy allows it. [zia.dlp.rules:match-only-example] The page names the sender two ways [divergence:zia.dlp.rules:match-only-example-sender]. Some SDK docstrings describe `matchOnly` differently: [zia.dlp.rule-wire-shape:match-only-docstring](kb:zia.dlp.rule-wire-shape:match-only-docstring).

**Rules without content inspection.** In a rule without content inspection, Zscaler DLP engines are not used to detect data: Content Matching set to None hands inspection to a third-party DLP solution, and the service does not scan the content with its DLP engines but functions as a filter, only forwarding content based on specific criteria. The article does not apply to organizations with Evaluate All Rules mode enabled. [zia.dlp.rules:without-ci-filter-mode] A rule without content inspection has an Outbound Data choice: Select File Types, where any number of file types (searchable) and previously configured custom file types can be selected, or All, which applies the rule to all outbound data regardless of file type. [zia.dlp.rules:without-ci-outbound-data] To monitor or block outbound content by data size without scanning for specific data, the vendor's scenario uses the Rule Without Content Inspection option: the criteria Zscaler uses are specified and no ICAP server is specified, so Zscaler monitors or blocks outbound content on those criteria and sends no content to any external DLP engine. [zia.dlp.rules:data-size-without-inspection] Where such a rule sends what it detects is in [Where a DLP match goes: notification, ICAP, Incident Receiver and Cloud-to-Cloud](kb:zia.dlp.incident-forwarding).

**How criteria combine.** Within a rule, URL Categories and Cloud Applications combine with AND (the service must detect both selected categories and applications in the transaction), while Users, Groups and Departments combine with OR (at least one of the selected users, groups or departments must be detected). [zia.dlp.rules:criteria-and-or] The article on rules without content inspection says the logical relationship between the categories is AND, and gives: Who is [Users OR Groups OR Departments OR Workload Groups]; Source and Destinations is [URL Categories AND Cloud Applications AND ZPA Application Segment AND Source IP Groups AND Locations AND Location Groups]; When is Time; and What is [User Risk Score AND Content Matching AND File Types AND Minimum Data Size (KB) AND Protocols]. The article does not apply to organizations with Evaluate All Rules mode enabled. [zia.dlp.rules:without-ci-criteria] The two articles group the criteria differently [divergence:zia.dlp.rules:criteria-grouping]. Per-field limits: in default mode, Include takes Any or up to 4 users, Any or up to 8 groups, or Any or up to 8 departments, and each field's text, right after the Exclude option, allows selecting up to 256 users, groups or departments; Locations and Location Groups take up to 32; Time takes up to two intervals; the Evaluate All Rules article caps Include at Any or up to 32 users, groups or departments, and gives domain profiles, cloud application instances and workload groups 8 each, and ZPA application segments at 255. Support can raise the default Users, Groups, Departments and User Risk Profile limits. [zia.dlp.rules:scope-limits] In the article on rules without content inspection, ZPA Application Segment takes Any or up to 255 Private Access application segments, and the list shows only segments with the Source IP Anchor option enabled. Selecting the Inspect App Segments option applies the rule to all Private Access application segments paired to the Internet & SaaS (ZIA) tenant, and that option is only available if the SIPA App Segments subscription is enabled for the organization. [zia.dlp.rules:zpa-segments-sipa]

**Constraints that fail only at save time.** A rule that applies to unauthenticated traffic must apply to all groups and departments, so Groups and Departments must both be Any. [zia.dlp.rules:unauthenticated-needs-any] The About DLP page says that to apply a rule to unauthenticated traffic, the rule must apply to all locations. [zia.dlp.rules:unauthenticated-needs-all-locations] Inspect Downloads extends a rule to content downloaded from cloud apps. Enabling it requires Any for URL Categories and at least one cloud app; without it the rule applies only to content sent to cloud apps. It does not apply to Exact Data Match or Indexed Data Matching engines. [zia.dlp.rules:inspect-downloads]

**Other criteria.** A rule can inspect HTTP GET query parameters, only for these URL categories: Generative AI and ML Applications, Safe Search Engines, Translation Tools, Web Search, and user-defined custom URL categories. To enable it, choose Enable for Inspect HTTP GET Requests in the rule, then select a URL category from the drop-down menu. [zia.dlp.rules:http-get-query-parameters] Inspect HTTP GET Requests is obtained by contacting the Zscaler Account team. A user-defined custom URL category can be enabled in a policy for it only after the category is associated with Inspect HTTP GET Requests on the DLP Advanced Settings page. [zia.dlp.rules:http-get-custom-category-prerequisite] The prompt-capture settings that pair with this are in [Advanced URL Filtering settings that change outcomes](kb:zia.url-filtering.advanced-settings). A rule can target sections of a file or transaction by content location: Document Properties (file metadata such as MIP labels), File Content (not metadata), File Name, or HTTP Body (the non-file request body, which also requires the non-file file type). The feature is enabled by contacting Zscaler Support. [zia.dlp.rules:content-locations] Zscaler-defined file types are considered before custom file types, and custom file types are not detected inside archives. Rules that reference Zscaler DLP engines support different file types than rules that reference external DLP engines. [zia.dlp.rules:file-type-precedence] Minimum Data Size sets how large data must be before the rule applies; the default 0 KB means no minimum. The API field is `minSize`, in KB. [zia.dlp.rules:minimum-data-size] A rule can scope to up to 4 user risk profiles (Critical, High, Low and Medium); by default Low is 0 to 29, Medium 30 to 59, High 60 to 79 and Critical 80 to 100, and selecting no level ignores the criterion. [zia.dlp.rules:user-risk-levels] The rule's Protocols criterion offers HTTP, HTTPS, Native FTP, WebSocket and WebSocket SSL/TLS. The Evaluate All Rules article says the WebSocket protocol is supported only for the Microsoft Copilot application. [zia.dlp.rules:protocols] Its WebSocket scope differs between the articles [divergence:zia.dlp.rules:websocket-scope]. The article on rules without content inspection says Zscaler inspects bidirectional WebSocket traffic carrying supported text-based content across applications, and that enabling the feature means contacting Zscaler Support. The article does not apply to organizations with Evaluate All Rules mode enabled. [zia.dlp.rules:websocket-across-applications] That scope is the one in dispute {{divergence:websocket-scope|ref}}.

**Actions.** In Evaluate All Rules mode a rule's action is Allow (allow and log), Block (block and log) or Confirm (the user can justify and continue, or cancel; both are logged); the default-mode article lists only Allow and Block. [zia.dlp.rules:actions] If the Confirm message times out without the user acting, the service automatically cancels the transaction. [zia.dlp.rules:confirm-timeout-cancels] A rule description cannot exceed 10,240 characters. [zia.dlp.rules:description-limit]

Where a rule's size and archive limits stop inspection is in [DLP file size, archive and text limits: why DLP did not catch a large file](kb:zia.dlp.inspection-limits); where matches are sent is in [Where a DLP match goes: notification, ICAP, Incident Receiver and Cloud-to-Cloud](kb:zia.dlp.incident-forwarding); the API field names, enums and sub-rules are in [Web DLP rule API fields, enums and fields the contract does not document](kb:zia.dlp.rule-wire-shape).

What to check:
1. Whether the tenant is in Evaluate All Rules mode, which changes the first-match order.
2. Whether the rule applies to unauthenticated traffic, which requires Any for both Groups and Departments before it will save.
3. Whether Inspect Downloads is needed, given that it does not apply to Exact Data Match or Indexed Data Matching engines.
4. Whether the rule is one with or without content inspection before reading how its criteria combine, since the two articles group them differently.

Sources disagree (name both sides):
- How DLP rule criteria are grouped: Locations, Location Groups, Source IP Groups and user risk are OR with other fields in the content-inspection article and AND in the article on rules without content inspection. [divergence:zia.dlp.rules:criteria-grouping]
  - zscaler-help: The content-inspection article groups Users, Groups, Departments and User Risk Profile with OR, and Locations, Location Groups and Source IP groups with OR, joined to each other and to Time by AND.
  - zscaler-help: The article on rules without content inspection joins Source IP Groups, Locations and Location Groups with AND under Source and Destinations.
  - zscaler-help: The same article joins User Risk Score with AND under What, rather than with OR alongside Users.
  Impact: The two pages describe different rule kinds (with and without content inspection) and neither says the logic differs by kind, so whether several locations or a location plus a user risk level on one rule combine with OR or AND is not settled; do not state either grouping as fact for a rule.
- Whether DLP inspects WebSocket traffic only for Microsoft Copilot or across applications. [divergence:zia.dlp.rules:websocket-scope]
  - zscaler-help: The Evaluate All Rules article says the WebSocket protocol is supported only for the Microsoft Copilot application.
  - zscaler-help: The article on rules without content inspection says Zscaler inspects bidirectional WebSocket traffic carrying supported text-based content across applications, and to contact Zscaler Support to enable it.
  - zscaler-help: The Advanced Policy Settings article says Zscaler inspects bidirectional WebSocket traffic carrying supported content across applications, and to contact Zscaler Support to enable it.
  - zscaler-help: The July 2026 release summary says Zscaler inspects bidirectional WebSocket traffic across applications.
  Impact: Whether a WebSocket protocol selection covers applications other than Microsoft Copilot is not settled; the Evaluate All Rules article limits it to Copilot while three other pages say across applications, and the pages may describe different features. Do not state either scope as fact for a rule.
- How many Web DLP rules a tenant can hold. [divergence:zia.dlp.rules:web-rule-cap-127-vs-1024]
  - tf-zia: The Terraform resource documentation says a maximum of 127 Web DLP rules can be created via the API.
  - zscaler-help: The Ranges and Limitations help page gives a generic policy rule limit of 1,024 rules, raisable to 2,048.
  Impact: Do not quote 127 or 1,024 as the Web DLP rule cap without saying which source it comes from; the two figures may describe different things (a 127 API cap against a generic per-type limit) and the sources do not reconcile them.
- The Match Only example page names the sender's team two ways: a finance team member, and, in a parenthesis, a user in Human Resources. [divergence:zia.dlp.rules:match-only-example-sender]
  - zscaler-help: The sender is a finance team member who is not in Human Resources.
  - zscaler-help: The parenthesis on the Rule 1 bullet says the user is in Human Resources.
  Impact: The example works only with a finance sender; the parenthesis reads as a vendor error, so the example should not be cited for the behaviour of an HR sender.
