# SAML and Kerberos: what each needs to work (zia.authentication.methods)
Also called: SAML SSO; saml; kerberos; kerberos authentication; 407 negotiate; service provider; IdP exemption; kerberos PAC

Authentication method decides how a request gets an identity; whether it is demanded at all is [Requiring authentication per location and sublocation](kb:zia.authentication.location-enforcement).

**SAML.** With SAML single sign-on the Zscaler service is the service provider, and SAML SSO is used for provisioning and authenticating users. Before configuring it, the SAML SSL certificate must be obtained from the IdP and the XML metadata exported from it. [zia.authentication.methods:saml-sp] The IdP must be reachable without a user identity. With PAC-file forwarding, the redirected IdP URL must be in the PAC file's authentication exemption list or authentication fails; with transparent forwarding, the SAML IdP traffic must be exempted from the GRE or IPSec tunnel, for example by a route at the gateway router that sends it directly to the internet. [zia.authentication.methods:saml-idp-reachability] Org-level SAML switches (samlEnabled, autoProvision) are in [The organization-wide authentication settings object](kb:zia.authentication.settings).

**Kerberos.** Kerberos does not use cookies; it is ticket-based. When the Public Service Edge finds no Zscaler cookie for the domain in the request, it issues a 407 Negotiate challenge, and the client answers with a ticket in the proxy authorization header. [zia.authentication.methods:kerberos-no-cookie] Kerberos is supported only for traffic forwarded in explicit mode (a PAC file points the browser at the service). It is not supported for transparent forwarding through a GRE or IPSec tunnel when the browser is not using a PAC file, and users must already be provisioned: Kerberos authenticates, it does not provision. [zia.authentication.methods:kerberos-explicit-only] Kerberos lets the service authenticate applications that do not support cookies, such as Office 365 and Windows Metro apps, and apply user, group and department policy to FTP and to HTTPS without decrypting it. It is not supported on Windows XP, iOS or Android. [zia.authentication.methods:kerberos-clients] Kerberos needs the site's DNS to resolve the Zscaler service host names and the firewall to allow ports 88/8800, and the domain suffix of the client or server in the ticket must be a registered domain in the Zscaler account. [zia.authentication.methods:kerberos-network] The per-location Kerberos switch is in [Requiring authentication per location and sublocation](kb:zia.authentication.location-enforcement).

**Basic.** Basic authentication prompts users for a username and password, which are sent as a Base64 encoded string in the HTTP request header. It is not enabled by default; access is requested by submitting a support ticket from the Admin Console. [zia.authentication.methods:basic-what] A Public Service Edge calculates the HA1 value for the given credentials and authenticates the user upon successful validation. Basic authentication works with an HA1 value that must be initialized, so users need to be enrolled to the Admin Console via API; the article says this is necessary because Basic authentication is often used for workloads that may not be able to enroll interactively on a browser. [zia.authentication.methods:basic-ha1] To enroll a Basic user, Hosted DB must be selected for User Repository Type and Form-Based for Authentication Type on the Default Settings tab, and a user must be created and activated in the Admin Console; the enrollment call is POST /users/<userId>/enroll with payload { "authMethods" : ["BASIC"], "password" : "<password>" }. Saving and activating the changes computes an HA1 value and propagates it across the Zscaler service. [zia.authentication.methods:basic-enrollment] For Basic authentication traffic, the location must have Enforce Authentication and Enable Basic Authentication selected; if Enforce Surrogate IP for Known Browsers is enabled, Cookie and Proxy must be selected for Supported Authentication Methods for IP surrogacy to work. [zia.authentication.methods:basic-location-settings] The forwarding methods the pages give for Basic differ [divergence:zia.authentication.methods:basic-forwarding-scope].

**JWT.** Zscaler supports JSON Web Token (JWT) authentication for cloud workloads: the workload requests a JWT from the token provider, sends its request with the JWT through Zscaler Cloud & Branch Connector or GRE and IPSec tunnels, and the service checks the JWT against the token validators configured through the Authentication Service. JWT authentication can be enabled when configuring locations and bypassed on the Advanced Settings page; sessions with JWT authentication are logged in the Insights Logs with the user ID from the JWT. It is not enabled by default (submit a provisioning ticket to Zscaler Support). [zia.authentication.methods:jwt-workloads] Whether tunnel traffic must also be explicitly proxied is open [gap:zia.authentication.methods:jwt-forwarding-mode].

Hosted DB (form-based login with the service's own users) is the third method; its password fields are in [The organization-wide authentication settings object](kb:zia.authentication.settings). Which method tenants favour is open [gap:zia.authentication.methods:deployment-defaults].

What to check:
1. How the failing traffic is forwarded, PAC or tunnel, since Kerberos is supported only in explicit mode.
2. Whether the IdP host is exempted on that forwarding path.
3. Whether a Zscaler cookie was present on the request, since Kerberos challenges a request that has none.

Sources disagree (name both sides):
- The location page ties Basic authentication to explicitly forwarded traffic, while the Basic overview lists transparent forwarding such as GRE and VPN among the methods enrolled users can browse through. [divergence:zia.authentication.methods:basic-forwarding-scope]
  - zscaler-help: Basic authentication is enforced on web traffic explicitly forwarded from the location and its dedicated ports.
  - zscaler-help: Enrolled users can browse through a proxy with forwarding methods such as Static IP, DPCC, Virtual Service Edge, or transparent proxy such as GRE and VPN.
  Impact: Do not say Basic works, or does not work, over GRE or VPN tunnels without noting the pages disagree; see also the method switches in zia.authentication.location-enforcement.

Not known (open gaps):
- Whether JWT traffic through tunnels must also be explicitly proxied [gap:zia.authentication.methods:jwt-forwarding-mode]: settled by lab-test or support-ticket. Blocks: saying how a workload's JWT traffic must be forwarded
- Which authentication methods tenants use in practice [gap:zia.authentication.methods:deployment-defaults]: settled by support-ticket or operator-experience. Blocks: recommending a method for a given population
