# Proxy chaining to ZIA: setup, XFF handling and limits (zia.traffic-forwarding.proxy-chaining)
Also called: proxy chaining; upstream proxy; squid zscaler; xff; x-forwarded-for; internal ip logging; secondary.gateway

Proxy chaining is a way to send an existing proxy's traffic to the service without other network changes, which Zscaler does not recommend as a long-term production solution. Proxy chaining forwards traffic from an existing on-premises proxy to the service with no other network change. Zscaler supports it but does not recommend it as a long-term production solution, because multiple proxies add latency and proxies that support failover support only manual failover. [zia.traffic-forwarding.proxy-chaining:what-it-is] Chaining's stated limits: corporate-network users must still use another method, such as PAC files, to forward traffic to the service; the proxy's latency affects forwarding latency; and a caching proxy can cause downstream authentication problems and affect policy enforcement and reporting. [zia.traffic-forwarding.proxy-chaining:limitations]

**Setup.** The organization's public egress IP addresses must be registered with Zscaler Support (or the Zscaler representative during an evaluation); registration enforces IP uniqueness across organizations, and the gateway location is then defined in the Admin Console with those addresses. [zia.traffic-forwarding.proxy-chaining:registration] The proxy must name both gateway.<cloud_name>.net and secondary.gateway.<cloud_name>.net as primary and secondary upstream servers; Zscaler does not support configurations with a single proxy server. The service then picks the nearest Public Service Edge by geolocation. [zia.traffic-forwarding.proxy-chaining:primary-secondary] Government clouds support proxy chaining only when the traffic from the on-premises proxy goes through a GRE or IPSec tunnel; chaining directly over the internet is not supported. [zia.traffic-forwarding.proxy-chaining:government-clouds]

**Client identity.** When the service forwards a chained request onward it replaces the original X-Forwarded-For header with one holding the organization's public gateway IP; logs record the public IP of the sending firewall or router unless Internal IP Logging is enabled in Advanced Settings, which logs the XFF address. [zia.traffic-forwarding.proxy-chaining:xff-handling] The Advanced Settings option Log Internal IPs from XFF Headers (Internal IP Logging): a logged transaction's source IP is always the public IP of the firewall or edge router that sent the traffic, but with proxy chaining a proxy server can insert an X-Forwarded-For header in outbound HTTP requests, and with the option enabled the service logs the source IP in that header. When forwarding to the destination the service removes the original XFF header and replaces it with one holding the client gateway's IP address (the organization's public IP address). Zscaler Client Connector also sends IP addresses as part of the XFF headers. [zia.traffic-forwarding.proxy-chaining:internal-ip-logging] How the service uses the client address from XFF to find a sublocation, and the per-location switch that enables it, is in [Which IP addresses a sublocation matches, overlap rules and XFF](kb:zia.locations.ip-scoping); user mapping from that address is [Surrogate IP: mapping a private IP to an authenticated user](kb:zia.authentication.surrogate-ip).

The proxy mode of chained traffic is in [Which forwarding methods produce explicit or transparent mode](kb:zia.proxy-mode.forwarding-map).

The opposite direction, where ZIA forwards traffic on to a third-party proxy service through proxy gateways, is in [Third-Party Proxy Chaining from ZIA: proxies, proxy gateways and fail-close](kb:zia.forwarding-control.third-party-proxies).

What to check:
1. Whether both gateway names are configured as primary and secondary upstream servers.
2. Whether the egress IPs are registered with Support.
3. Whether, for sublocation or user policy, the proxy inserts XFF and the location has it enabled.
