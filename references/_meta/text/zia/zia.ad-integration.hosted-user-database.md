# Hosted User Database: adding users by hand, importing users, groups and departments by CSV, and one-time tokens and links (zia.ad-integration.hosted-user-database)
Also called: Hosted DB; hosted users; one-time token; one-time link; temporary authentication; users CSV import; Sample Import CSV

The Hosted User Database is the provisioning method where the Zscaler database itself holds the users. With the Hosted User Database, user information is uploaded to the Zscaler database by adding it manually in the Admin Console, importing it from a CSV file, or using the Zscaler Authentication Bridge (ZAB). When users are added directly to the Zscaler database, password-based authentication is the default method; the passwords are uploaded with the username, group and department information and stored in an encrypted format, and users can be required to enter a password different from their corporate password. [zia.ad-integration.hosted-user-database:what-it-is] The number of users it can hold differs between pages [divergence:zia.ad-integration.hosted-user-database:users-per-org].

**Authenticating.** With password-based authentication, the Central Authority (CA) displays the password request form after it receives the request with the username from the Public Service Edge, and authenticates the user when the submitted password matches the one in the database. Setup enables Enforce Authentication on the location and sets Directory Type to Hosted DB and Authentication Type to Form-Based, with One-Time Token or One-Time Link optionally chosen as Temporary Authentication. If a hosted user cannot authenticate, the article says to verify the User ID and Password on the Internet & SaaS Users page, and that the user might have entered an incorrect password so resetting it may help. [zia.ad-integration.hosted-user-database:password-auth-flow] The password strength and expiration settings are in [The organization-wide authentication settings object](kb:zia.authentication.settings).

**When the Users page is view-only.** If Active Directory or OpenLDAP is selected in the default authentication profile, or if the organization uses Authentication Service for Admins, users are listed view-only with limited options (download user data and search for users); with Authentication Service for Admins and Users, users are configured with Authentication Service. [zia.ad-integration.hosted-user-database:read-only-conditions]

**Adding by hand.** When adding users, their groups and departments must be specified, and new groups and departments can be added. The Password field must follow the guidelines defined when password is the selected authentication method, and Temporary Authentication Email appears only when One-time Token or One-time Link is selected as the temporary authentication method in Authentication Profile. [zia.ad-integration.hosted-user-database:add-user-form] The field limits and group rules are in [ZIA users, groups and departments: shape and limits](kb:zia.ad-integration.identity-objects).

**CSV.** Up to 3,000 users can be imported with a CSV file, which must have a .csv extension; each user's email address must have a domain defined in the Admin Console, and with a one-time token or link either that field or the Temp auth email field must contain a valid email address. The Action column takes + to add a new user or modify an existing one (Email-ID, User Name, Dept and Group must be filled in when adding) or - to delete a user (only Email-ID required); each group beyond the first goes in a new column, and a blank Password means the user logs in the first time with a one-time token or link. Override Existing Entries updates existing user information; adding a user that already exists without it gives an error message. [zia.ad-integration.hosted-user-database:csv-import-users] Up to 3,000 user groups can be imported at one time with CSV files, whose header row has Action, Name and Comments columns; a group is removed with - under Action and its name under Name. Up to 3,000 departments can be imported with a CSV file, and adding multiple users to an existing department or changing the department for multiple users goes through the user sample import CSV file. [zia.ad-integration.hosted-user-database:csv-import-groups-departments] The CSV downloaded for users, for groups and for departments cannot be used to import that object because it uses a different format; each of the three download pages says so for its own object. [zia.ad-integration.hosted-user-database:csv-download-not-importable]

**One-time token and link.** The service can email users a link or temporary password that they use to log in once, which the article says is useful when creating new users or resetting forgotten passwords. The service allows a user to request a new temporary password only once every 24 hours, and both the unique link and the unique password are valid for 24 hours. After a token login the user must enter a new password, which the CA stores before setting the gateway cookie. It works for users hosted by the service or synchronized from a directory server as long as the service has valid email addresses, and for synchronized users the service matches the password with the one in its database, not the directory server's. It does not apply to users with Zscaler Client Connector. The email goes to the Temporary Authentication Email, which need not belong to the organization's domain, or to the User ID if that field is empty. [zia.ad-integration.hosted-user-database:one-time-token-link] What a user sees on an expired token or link is open [gap:zia.ad-integration.hosted-user-database:one-time-expiry-behavior].

What to check:
1. Whether the repository type is Hosted DB and not Active Directory or OpenLDAP, since the latter make the Users page view-only.
2. Whether the CSV is the Sample Import format with the right Action, and not a downloaded CSV.
3. Whether the user has a valid email address before relying on a one-time token or link.

Sources disagree (name both sides):
- The Hosted User Database article says there is no limit to the users an organization can store, while the Users page and the limits table give 1,400K. [divergence:zia.ad-integration.hosted-user-database:users-per-org]
  - zscaler-help: There is no limit to the number of users an organization can store in the database.
  - zscaler-help: Up to 1400K users can be added.
  - zscaler-help: The limits table gives Users per Organization as 1,400K users.
  Impact: Do not tell a tenant planning a large Hosted DB population that there is no cap, or that 1,400K is the cap, without saying the pages disagree. The org-limits claim in zia.ad-integration.identity-objects holds the limits-table figure.
