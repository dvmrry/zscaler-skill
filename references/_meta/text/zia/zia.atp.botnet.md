# ATP Botnet Protection: C2 servers, C2 traffic, the alert toggle and DGA (zia.atp.botnet)
Also called: command and control; c2 detection; cobalt strike; mythic; brute ratel; poshc2; dga domains; alert for unknown c2; cmdCtlServerBlocked; botnet protection

Botnet Protection has four toggles, each covering a different detection.

**Known C2 servers.** Command & Control Servers allows or blocks connections to known C2 servers for profiles such as Cobalt Strike, Mythic, Brute Ratel and PoshC2. Known C2 botnet activity and the triggered policy actions can be viewed on the SaaS Security Insights Logs page (Data Explorer > Internet & SaaS > SaaS Security Insights). [zia.atp.botnet:known-c2-servers] The inspection uses rate-based control to detect and block connections for default profiles of popular security testing tools. [zia.atp.botnet:rate-based-profiles]

**C2 traffic to unknown servers.** Command & Control Traffic allows or blocks botnets sending or receiving commands to unknown servers, by examining the content of requests and responses to those servers. [zia.atp.botnet:c2-traffic] Because Command & Control Traffic detection reads request and response content, it does not see inside HTTPS that is not decrypted. [zia.atp.botnet:c2-traffic-needs-decryption]

**Alerting on traffic that matches nothing.** Alert for Unknown/Suspicious C2 Traffic sends alerts for C2-like traffic that matches no botnet callback or other blocking malware signature by reclassifying it to a new URL category, and is disabled by default. A matching alert subscription tells admins to investigate detections. [zia.atp.botnet:alert-unknown-c2] Ansible collection issue #87, still open, reports that switching `alert_for_unknown_or_suspicious_c2_traffic` in `zia_atp_settings` between `true` and `false` changes nothing in Experience Center; a repository member replied that regardless of the value configured in the UI the API always returns `alertForUnknownOrSuspiciousC2Traffic` as false and ignores an input of true, which causes Ansible to think there is a difference in configuration when there isn't, and that it needs escalating to API engineering. [zia.atp.botnet:issue-ansible-87-c2-flag-always-false] Whether the API writes it today is open [gap:zia.atp.botnet:c2-flag-api-write].

**DGA domains.** Domain Generation Algorithm (DGA) Domains allows or blocks domains suspected to be generated by domain generation algorithms, which malware families use to produce many domain names for reaching C2 servers. [zia.atp.botnet:dga] dgaDomainsCapture exists in the API next to dgaDomainsBlocked, so DGA has a Blocked and Capture pair, as Command & Control Servers and Command & Control Traffic do. [zia.atp.botnet:dga-has-capture]

**Counter-based detection.** Counter-based detection of known C2 profiles, counting occurrences over a period, is supported but enabled through the Zscaler Account team. [zia.atp.botnet:counter-based]

Reclassification by AI/ML can also move a URL into the botnet group: [ATP AI/ML recategorization: why a URL can start blocking with no policy change](kb:zia.atp.ai-ml-recategorization). The other groups are in [ATP detection categories and what each toggle covers](kb:zia.atp.categories).

What to check:
1. Whether the destination is a false positive on one of the named C2 or security-testing profiles.
2. Whether the traffic was decrypted, since Command & Control Traffic detection cannot read undecrypted HTTPS.
3. Whether the Alert for Unknown/Suspicious C2 Traffic toggle is on, since it is off by default and is the source of a reclassified URL category.
