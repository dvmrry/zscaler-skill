# Behavior When Partial Configuration Available: Fail Open, Fail Closed and Best Effort Policies (zia.advanced-settings.partial-configuration)
Also called: Behavior When Partial Configuration Available; Partial Configuration Handling Mechanism; Fail Open; Fail Closed; Best Effort Policies; Org Default location; Miscellaneous Unauthenticated Transactions user; Bypassed due to missing config; Timed out while waiting for config

When a new session from an organization first reaches the Zero Trust Exchange, the Service Edge connects to the Zscaler Central Authority to get the policy configuration in a hierarchy, starting with the organization policy, followed by location policy and user policy. Policy enforcement for traffic from an authenticated user or a known location requires the Service Edge to have the organization's full configurations, including security policies, locations and users, downloaded from the Central Authority. [zia.advanced-settings.partial-configuration:why-config-is-fetched] In rare scenarios caused by transient network disruptions or delays, a Service Edge might be unable to retrieve the full configurations from the Central Authority for a given session and might need to operate with incomplete or cached tenant, user or location configurations. The page calls this extremely unlikely under normal operating conditions and temporary, typically occurring when there is brief connection latency to the Central Authority as a new session reaches a Service Edge that has not finished retrieving its configuration. The Behavior When Partial Configuration Available setting defines how security policies are enforced in that state. [zia.advanced-settings.partial-configuration:when-partial]

**The three modes.** The setting has three modes. Fail Open, the default, skips policy evaluation for a session when complete configurations are not available and lets the traffic pass. Fail Closed blocks traffic unless a complete configuration is available to apply, at the risk of some sessions occasionally being blocked. Best Effort Policies applies the most specific policy rules available by falling back to a previously acquired policy. [zia.advanced-settings.partial-configuration:modes] The page describes Fail Closed as blocking traffic, and also lists a log action named for a bypass under Fail Closed [divergence:zia.advanced-settings.partial-configuration:fail-closed-bypassed].

**Best Effort Policies.** In the Best Effort Policies mode, the policy falls back to a global location (Org Default) or a general user type (Miscellaneous Unauthenticated Transactions) for a session when a more specific admin-configured user or location policy is not available. For rules with explicit location or user criteria, the Org Default location or the Miscellaneous Unauthenticated Transactions user, or both, must be added to the rule so it can match during evaluation and trigger the fallback; rules that match any locations or users do not require them. [zia.advanced-settings.partial-configuration:best-effort-fallback] The Org Default location and the Miscellaneous Unauthenticated Transactions user can be used in all Web and Firewall policy rules that support user- and location-based conditions. The mode can be changed from Best Effort Policies to other options only when no policy rules reference them. On the Locations page, only Enforce Firewall Control and Enable IPS Control can be edited on Org Default, Firewall Control must be enabled for Org Default for Firewall policies to use it, and it does not support sublocations. The Miscellaneous Unauthenticated Transactions user can be viewed only in policy rule conditions and is not editable. [zia.advanced-settings.partial-configuration:best-effort-objects]

**Sessions.** The selected mode applies to both secure web gateway and firewall traffic. Policy evaluation begins when a session is established and uses the policy available at that moment. When only an incomplete policy is available at session establishment and Best Effort Policies or Fail Open is active, the available policy is used for the entire session, and subsequent sessions trigger new attempts to retrieve the complete policy configuration. [zia.advanced-settings.partial-configuration:scope-and-session]

**In the logs.** When Best Effort Policies or Fail Closed mode is used, the policy actions Bypassed due to missing config and Timed out while waiting for config might additionally appear in Firewall logs under specific circumstances. In Best Effort Policies the actual authenticated user is logged (if Z-Tunnel 2.0 or cookie authentication is used) even if the policy was applied using the Miscellaneous Unauthenticated Transactions user; if the user identity is unknown (for example Z-Tunnel 1.0), the transaction is logged for that user. The traffic origin location is logged correctly even if Org Default was used. These transactions are made distinct by the Configuration column set to Partial in Web logs, a distinction not currently available in Firewall and DNS logs. [zia.advanced-settings.partial-configuration:logging] The log side is in [What a ZIA firewall log record is: aggregates, action and field names](kb:zia.logs.firewall-records) and [ZIA Insights Logs: log families, time frame, export and background queries, filters and console-only columns](kb:zia.insights.logs).

The page this setting sits on is routed in [ZIA Advanced Settings page: its sections, three settings explained here, and where other sections are routed](kb:zia.advanced-settings).

What to check:
1. Which of the three modes is selected before explaining why a session was allowed or blocked without the expected rule.
2. Whether a rule with explicit location or user criteria also lists the Org Default location or the Miscellaneous Unauthenticated Transactions user, when Best Effort Policies is expected to apply it.
3. Whether the Web log's Configuration column reads Partial for the transaction.

Sources disagree (name both sides):
- Fail Closed is described as blocking traffic unless a complete configuration is available, yet the same page says a Firewall log action Bypassed due to missing config might appear when Fail Closed is used. [divergence:zia.advanced-settings.partial-configuration:fail-closed-bypassed]
  - zscaler-help: Fail Closed blocks traffic unless a complete configuration is available to apply.
  - zscaler-help: With Best Effort Policies or Fail Closed, Firewall logs might show Bypassed due to missing config and Timed out while waiting for config.
  - zscaler-help: Bypassed due to missing config is logged when the Service Edge fails to connect to the Central Authority, and the traffic flow passes through Firewall or DNS without policy application.
  Impact: The Policy Reasons definition describes a bypass that passes traffic without policy application, while Fail Closed is described as blocking; neither page says which circumstances produce a bypass action under Fail Closed, so a Bypassed due to missing config record cannot be read as proof that Fail Closed allowed the traffic or that another mode was selected.
