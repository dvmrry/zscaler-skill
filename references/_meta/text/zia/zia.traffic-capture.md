# Traffic Capture Essentials and Traffic Capture for NDR: storage, rules, limits and obfuscation (zia.traffic-capture)
Also called: traffic capture; traffic capture essentials; traffic capture for ndr; traffic capture policy; pcap; pcapng; packet capture; trafficCaptureRules; pcapSettings; capture limit; txnSizeLimit; txnSampling; traffic capture settings

With Traffic Capture Essentials, traffic is captured as PCAP files that can be accessed later through an Amazon S3 bucket the organization manages, for supported actions in policies. With Traffic Capture for Network Detection and Response (NDR), traffic is captured as PCAPNG files with the Traffic Capture policy. [zia.traffic-capture:two-offerings] The Capture option for Traffic Capture Essentials is in Advanced Threat Protection, File Type Control, Firewall Filtering, DNS Filtering, IPS Control, Malware Protection and URL Filtering policies. [zia.traffic-capture:essentials-policies] Where Traffic Capture is switched on differs between pages [divergence:zia.traffic-capture:capture-enablement].

**Essentials storage and options.** Traffic Capture Essentials needs an S3 bucket configured to store capture data, with permissions that let capture files be uploaded and ingested; Zscaler recommends dual-stack storage endpoints for all cloud destinations. An optional HTTP header with a case-sensitive key adds metadata to the Amazon S3 REST request, for example for server-side encryption with customer-provided keys (SSE-C). [zia.traffic-capture:essentials-s3] The Essentials settings page and the NDR settings page each say the service does not support custom or directory-style bucket URLs (non-standard prefixes, additional subdomains such as s3express, or unconventional naming patterns such as double dashes) and require a general-purpose S3 bucket URL in the form https://<bucket-name>.s3.<region>.amazonaws.com/<path>. [zia.traffic-capture:s3-url-format] Traffic Capture Essentials has optional Per Occurrence Limits, to be set or left at the defaults: Storage Limit, the maximum amount of data kept in the file when a policy configured for Traffic Capture Essentials triggers, and Sampling, the percentage of traffic sampled for capturing when it is triggered. [zia.traffic-capture:per-occurrence-limits] The defaults and ranges of these limits are open [gap:zia.traffic-capture:limit-defaults]. Traffic Capture Essentials lets an admin choose whether usernames and device information in created PCAP files are Visible or Obfuscated; the NDR settings offer the same choice for user names and device information in created PCAPNG files. The Essentials page names the aims of keeping capture data to admins with the necessary privileges and limiting exposure of personally identifiable information. [zia.traffic-capture:obfuscation]

**NDR storage destinations.** The NDR settings page is reached from the navigation menu at Internet Access > Traffic Capture > Settings, where Status enables Traffic Capture for NDR. [zia.traffic-capture:ndr-enable] For NDR, Traffic Capture must be enabled and a cloud storage destination configured before the Traffic Capture policy is configured. A destination is AWS S3 storage or Azure storage (Azure takes a Tenant ID, Client ID and Client Secret), and Use Default Storage sets a destination as the organization's default. [zia.traffic-capture:ndr-destinations] The NDR settings page lists the container permissions needed for the test connection and for Traffic Capture: for AWS S3, s3:PutObject and s3:GetObject for the test connection and s3:PutObject for Traffic Capture; for Microsoft Azure, Blob write and read data actions for the test connection and Blob write data actions for Traffic Capture. The page says the permissions needed only for testing should be removed once the connection is tested and established. [zia.traffic-capture:ndr-permissions] Which other storage options exist is open [gap:zia.traffic-capture:storage-options].

**NDR policy rules.** With Traffic Capture for NDR, Traffic Capture policy rules capture network traffic as PCAPNG files with granular control of match criteria and of how much traffic is captured. Traffic Capture policy rules can only be used on locations that have Firewall enabled. [zia.traffic-capture:ndr-policy] In Traffic Capture policy rules the criteria on each tab have their own operators: Who, Where, & When is [(Users OR Groups OR Departments) AND (Locations OR Location Groups) AND Time]; Devices is (Devices OR Device Groups OR Workload Groups); Services is (Network Service Groups OR Network Services); Applications is [(Network Application Groups OR Network Applications) AND (Application Service Groups)]; Source IP is (Source IPv4 Groups OR Source IPv6 Groups OR IP Addresses OR Countries); Destination IP is (Destination IPv4 Groups OR Destination IPv6 Groups OR IP Address or FQDN OR Countries). The relationship between tabs is AND. Within an AND bracket, the rule bypasses fields set to Any when any one of the OR fields has criteria set, and triggers for all values if every OR field in the bracket is Any. [zia.traffic-capture:criteria-logic] On the Traffic Capture rule form, Users, Groups, Departments, Locations and Location Groups each take up to 32 selections (no users or no locations means Any), Zscaler Support can raise the limit for Users, Groups, Departments and Locations, Time takes up to two time intervals (none means Always), and Workload Groups take up to 8. Any rule that applies to unauthenticated traffic must apply to all groups and departments. [zia.traffic-capture:identity-limits] The two-interval limit is one side of [zia.time-intervals.rule-usage:time-intervals-per-rule](kb:zia.time-intervals.rule-usage:time-intervals-per-rule). What an empty field means differs by field on the rule form: selecting no network service groups, network application groups, application service groups, source IPv4 groups or destination IPv4 groups sets the field to None, which ignores the criterion during policy evaluation; selecting no network services, applications, devices or device groups sets it to Any, which applies the rule to all of them. [zia.traffic-capture:empty-none-vs-any] For Client Connector traffic, the Device Groups field selects the group matching the device platform; Cloud Browser Isolation or No Client Connector applies the rule to isolation traffic or to traffic not tunneled through Client Connector, respectively. The Cloud Browser Isolation group is available only if Zero Trust Browser (formerly Isolation) is enabled for the organization. [zia.traffic-capture:device-groups] For IPv6, the source and destination groups on the rule form are the predefined All IPv6 groups, and custom source and destination IPv6 groups are not currently supported. The IP Addresses and IP Address or Wildcard FQDN fields take IPv4 only, and individual, subnet or range IPv6 addresses are not currently supported. In the API, user-defined IPv6 groups are not supported in `srcIpv6Groups` and `destIpv6Groups`, and `srcIps` holds IPv4 addresses. [zia.traffic-capture:ipv6-criteria] A Traffic Capture rule's source country is determined from the geolocation of the client's IP address, and its destination country from the geolocation of the server's IP address. Countries take an Include option, matching the specified countries, or an Exclude option, matching all countries except those selected, and selecting countries is mandatory with Exclude. In the API, `excludeSrcCountries` set to true excludes the countries in `sourceCountries`. [zia.traffic-capture:countries] For FQDN criteria on the Traffic Capture rule form, including wildcard FQDNs written with an asterisk, FQDNs are resolved to IP addresses when the rule is activated and stored by the service. DNS queries are made until two consecutive DNS responses return no new IP addresses, and the resolved addresses are stored for twice the DNS record's TTL. The service matches non-web traffic by IP address and web traffic by FQDN against the HTTP/FTP hostname or the HTTPS SNI. Configuring wildcard FQDNs in policies needs all DNS traffic forwarded to the Zscaler service and a subscription or Internet & SaaS edition with DNS Control, included in Advanced Firewall and DNS Control and Internet & SaaS editions; the page says wildcard FQDN matching against web traffic can work without meeting these conditions. [zia.traffic-capture:fqdn-matching] Whether the rule form has a device trust criterion is open [gap:zia.traffic-capture:device-trust-criterion].

**Rule action and details.** On the Traffic Capture rule form, Capture set to Enabled captures traffic matching the rule and Disabled skips it; Sampling is the percentage of connections sampled each time the rule is triggered; Capture Limit is the maximum amount of traffic data, in MB, captured per connection. The rule table's Action column shows the action (Capture or Skip) or that the rule is disabled. [zia.traffic-capture:actions] The unit of Capture Limit is given two ways [divergence:zia.traffic-capture:capture-limit-unit]. A Traffic Capture rule's name must be unique or the default name is used, and its description cannot exceed 10,240 characters. Rules are evaluated in ascending numerical order and the default rule is evaluated last. An admin cannot select a rank higher than their own, and a rule's Admin Rank determines the rule order value that can be selected so that a higher admin rank always precedes a lower one. A disabled rule keeps its place in the order and is skipped. In the API, `timeWindows` defaults to Always. [zia.traffic-capture:rule-details]

**Rule API.** In the legacy API's Traffic Capture rule, a rule requires `action`, `name`, `order` and `rank`; `action` is CAPTURE or SKIP and `state` is DISABLED or ENABLED; `txnSizeLimit`, the maximum size captured per connection, is NONE, UNLIMITED, THIRTY_TWO_KB, TWO_FIFTY_SIX_KB, TWO_MB, FOUR_MB, THIRTY_TWO_MB or SIXTY_FOUR_MB; `txnSampling`, the percentage of connections sampled each time the rule is triggered, is NONE or ONE, TWO, FIVE, TEN, TWENTY_FIVE or HUNDRED_PERCENT; `predefined` and `defaultRule` are Boolean fields marking predefined and default rules. [zia.traffic-capture:rule-api-values] The legacy ZIA API (host `zsapi.[zscaler-cloud-name]`, base path `/api/v1`) manages Traffic Capture rules at `/trafficCaptureRules`: GET lists rules, taking a `deviceTrustLevel` parameter among others, and pages with `page` (default 1) and `pageSize` (default 5000); POST creates a rule; GET `/count` counts the rules matching the criteria or all rules when none are given; GET `/order` returns the admin rank and rule order mappings and the maximum configured rule order; GET `/ruleLabels` lists the rules' labels, with a `pageSize` default of 1024; GET, PUT and DELETE `/{ruleId}` read, update and delete one rule. [zia.traffic-capture:rule-api-endpoints] The captured OpenAPI document has no Traffic Capture path: [Traffic Capture rules (`/trafficCaptureRules`) also carry a `timeWindows` list in the Go SDK struct; the captured OpenAPI document has no Traffic Capture path.](kb:zia.time-intervals.rule-usage:traffic-capture-rules).

**Settings API.** The legacy API's `/pcapSettings` holds an organization's Traffic Capture settings (cloud storage destination, file limits and data obfuscation), applicable when traffic is captured as PCAP files: GET reads them, POST creates them and a PUT by ID updates them. POST `/testConnection` validates connectivity to a cloud storage provider with given credentials before the settings are created or updated; its body is used only for that one-time test and is not saved, `cloudProvider` is S3 (the default), AZURE or GCS, and the response carries a `status` (for example SUCCESS or FAILURE) and `details`. [zia.traffic-capture:settings-api-endpoints] A Traffic Capture settings record in the legacy API requires `masterKnob` (whether the master knob for Traffic Capture is enabled) and `storageLocation` (the cloud storage location for the produced PCAP files: NONE, ZSCALER, AWS_S3, AZURE or GCP). `accessId` and `secretKey` are write-only and not returned in responses, and the read-only `secretKeyPresent` indicates whether a secret key is stored. `folderUrl` is the folder inside the bucket where PCAP files are written and `bucketName` the bucket name; `accountName`, `containerName` and `tenantId` are required when `storageLocation` is AZURE; `gcpClientEmail` is a service account client email. [zia.traffic-capture:settings-storage] A Traffic Capture settings record in the legacy API has four limits, each an enum: `aggTimeLimit`, the aggregation time window for the produced PCAP files (NONE, SEVEN_DAYS, FIFTEEN_DAYS, THIRTY_DAYS, FOURTY_FIVE_DAYS, SIXTY_DAYS); `aggSizeLimit`, the maximum aggregated PCAP file size (NONE, TWO_FIFTY_SIX_GB, FIVE_TWELVE_GB, ONE_TB, TWO_TB, FIVE_TB); `txnSizeLimit`, the maximum size captured per transaction (NONE, FOUR_KB through TWO_FIFTY_SIX_KB); and `txnSampling`, the transaction sampling ratio (NONE, ONE_PERCENT through HUNDRED_PERCENT). [zia.traffic-capture:settings-limits] In the legacy API's Traffic Capture settings record, `userObfuscated` indicates whether the end-user identity in captured packets is obfuscated, `deviceObfuscated` whether the device identity in captured packets is obfuscated, and `httpHeaders` holds custom HTTP headers attached to the upload requests. [zia.traffic-capture:settings-obfuscation-headers] Whether the API lists or downloads captures is open [gap:zia.traffic-capture:capture-retrieval-api], and how it relates to the NDR destination is open [gap:zia.traffic-capture:offering-scope]. What the aggregation limits do is open [gap:zia.traffic-capture:agg-limits-meaning].

**Licensing and data handling.** Zscaler Traffic Capture is a SaaS product licensed by the number of seats and the amount of data captured. A seat is a subscription license for an individual authorized user; captured data is measured in aggregate monthly against the number of seats and the data allocated per seat; the seats required are the unique individual users of Traffic Capture over the previous rolling 90-day period. Zscaler monitors and periodically reviews seats and data usage for compliance, and use is expected to follow the Acceptable Use Policy. [zia.traffic-capture:licensing] The per-seat allocation is open [gap:zia.traffic-capture:licensing-allocation]. The Traffic Capture logs page says that using the service gives Zscaler the right to create PCAP files based on traffic and optionally decrypted content processed by ZIA. It names event-based capture, available for supported actions in ZIA policies when a violation is matched, and capture-control, available for Internet Access traffic based on the organization's criteria. A PCAP file holds the captured packet data, including headers and payload, for a specific policy criteria match, up to the connection depth created from a matching policy, and the data captured per matched policy and the capture frequency can be limited (for example sampling 1 out of 10 or 100 transactions). [zia.traffic-capture:capture-modes] The Traffic Capture logs page says PCAP files are delivered directly to an external storage location provided by the organization, that Zscaler retains the files in Streaming SIMD Extensions (SSE) memory for a limited period of time to ensure continuous delivery, and that Zscaler does not write PCAP files to disk. [zia.traffic-capture:delivery-no-disk] Whether Zscaler stores capture files is disputed [divergence:zia.traffic-capture:pcap-storage].

What to check:
1. Whether a Capture Limit value was read from the console's MB label or from the API enumeration, since the API values include KB sizes and Unlimited.
2. Whether an answer that says Zscaler holds no copy of capture files accounts for the API's storage location values.
3. Whether a bucket URL is the general-purpose form, since custom and directory-style bucket URLs are not supported.
4. Whether Traffic Capture is switched on, and which page shows the switch, before concluding a Capture action has no effect.

Sources disagree (name both sides):
- Whether Zscaler stores PCAP files: the Traffic Capture logs page says files go to the organization's external storage and Zscaler does not write them to disk, the Settings API offers a ZSCALER storage location, and the web log format says a PCAP file is downloaded from the Capture column of Web Insights Logs. [divergence:zia.traffic-capture:pcap-storage]
  - zscaler-help: PCAP files are delivered to the organization's external storage; Zscaler retains them in SSE memory for a limited period to ensure delivery and does not write them to disk.
  - zscaler-help: The settings API's `storageLocation` for the produced PCAP files can be ZSCALER as well as AWS_S3, AZURE or GCP.
  - zscaler-help: The PCAP file is downloaded from the Capture column on the Web Insights Logs page.
  Impact: Whether Zscaler keeps a copy of a capture, and where an admin retrieves it, differs by page; the pages do not say whether the ZSCALER value, the console download and the external bucket are the same offering.
- The unit of the per-connection Capture Limit: the rule form labels it in MB, while the API enumeration includes 32 KB, 256 KB and Unlimited as well as MB values. [divergence:zia.traffic-capture:capture-limit-unit]
  - zscaler-help: Capture Limit is the maximum amount of traffic data, in MB, captured per connection.
  - zscaler-help: The API's `txnSizeLimit` values are NONE, UNLIMITED, 32 KB, 256 KB, 2 MB, 4 MB, 32 MB and 64 MB.
  Impact: A limit read from the console label would miss the KB and Unlimited values the API accepts; the pages do not say how the console choices map to the API values.
- Where Traffic Capture is enabled: the IPS Control page says in Advanced Settings, while the Essentials and NDR settings pages go to Internet Access > Traffic Capture > Settings. [divergence:zia.traffic-capture:capture-enablement]
  - zscaler-help: The IPS Control page says the Capture action requires Traffic Capture to be enabled in Advanced Settings.
  - zscaler-help: The Essentials settings page goes to Internet Access > Traffic Capture > Settings and enables it with Enable Traffic Capture Essential.
  - zscaler-help: The NDR settings page enables Traffic Capture for NDR with Status at Internet Access > Traffic Capture > Settings.
  Impact: Which console page holds the enabling switch for the IPS rule's Capture action is not settled; the settings API's `masterKnob` puts a master switch in the settings object but does not name a console page.
