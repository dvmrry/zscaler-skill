# Custom IPS signatures: enablement, two-stage validation and statuses, supported Snort-like syntax, limits, CSV import and export, and custom threat categories (zia.firewall.ips-signatures)
Also called: custom ips signature; custom signature rules; snort-like syntax; static validation; dynamic validation; promote ready; custom threat category

Custom IPS signatures are written in Snort-like syntax, deployed in the Zscaler cloud without extra infrastructure, kept private to the organization, and applied to non-web traffic and to web traffic after SSL/TLS decryption on Public, Private and Virtual Service Edges. Enabling Custom IPS Signature Rules for an organization is done through the Zscaler Account team. [zia.firewall.ips-signatures:what-and-where] Each custom signature is assigned a threat category, and an IPS Control rule uses the signature by naming that threat category as a condition. [zia.firewall.ips-signatures:threat-category-binding] The IPS policy that references the categories is in [IPS Control](kb:zia.firewall.ips). The help pages give the signature cap two ways [divergence:zia.firewall.ips-signatures:custom-rule-cap].

**Lifecycle.** Signatures are validated in two stages before deployment. Static validation checks syntax, duplicate signatures and other predefined conditions, runs automatically on save even if not run manually, and a rule is saved only if it passes. Dynamic validation runs the signature against designated packet captures for resource use and performance, takes a few minutes, and is started with Save & Promote or Promote All. A failed dynamic validation shows the reason and remedies, and the rule must be changed and resubmitted. [zia.firewall.ips-signatures:two-stage-validation] A signature's status marks its lifecycle: Promote Ready (passed static validation, ready for dynamic), Validation Pending (dynamic validation running), Validation Failed, Enable Ready (dynamic validation passed), Enabled (usable in IPS rules through its threat category) and Disabled. Enabling is manual: the Enable Signature Rule toggle is unavailable until the rule is Enable Ready. [zia.firewall.ips-signatures:statuses] Enabled signatures propagate on the Zscaler cloud and are stored in the Zscaler Central Authority separately for each tenant; the Service Edge downloads the policies and signatures with the organization's configuration from the CA and enforces them inline. [zia.firewall.ips-signatures:storage-and-propagation] Zscaler's Escalation Engineers may disable a signature that exceeds processing or memory thresholds at the organization or user level. The rule is then marked Disabled with the reason shown in the Admin Console; the status change takes place at disablement with no prior notice, later notices through other channels might not follow, and the engineer might see the signature content to give guidance on improving it. [zia.firewall.ips-signatures:zscaler-may-disable] The resource thresholds are open [gap:zia.firewall.ips-signatures:disablement-thresholds].

**Fields and static validation.** A signature's name is unique, at most 255 characters, alphanumeric plus period, underscore and hyphen, with spaces allowed but not leading; a threat category is required; the description is optional and at most 255 characters; and the signature rule text cannot exceed 16,000 characters. [zia.firewall.ips-signatures:field-limits] The page's Static Validation Criteria include: content and PCRE patterns of at least 5 characters; a PCRE option only alongside at least one content option; at most 10 detection filters and 10 event filters, one track_by field per filter, and a seconds field of at most 3600 seconds; at most 5 rules matching any address and any port on both source and destination; at most 16 invocations per flow (request and response), with the 17th packet in a flow not having signature validation; no source or destination IPs in 127.0.1.0 to 127.255.255.255 or 240.0.1.0 to 255.255.255.254; no export or flowbits option; and no duplicate signatures. [zia.firewall.ips-signatures:static-validation-criteria] The help pages list the supported protocols two ways [divergence:zia.firewall.ips-signatures:signature-protocols]. Zscaler scans by default 4,000 bytes per session (both directions), up to a maximum set with the max_scan_size option in a rule, bidirectionally unless the rule sets flow:to_server or flow:from_server; the default packet limit is 16 packets across both directions. [zia.firewall.ips-signatures:scan-and-packet-limits] The maximum scan size is stated two ways [divergence:zia.firewall.ips-signatures:max-scan-size], and whether max_count can raise the packet limit is open [gap:zia.firewall.ips-signatures:packet-limit-max-count]. Whether a sid and rev are required is open [gap:zia.firewall.ips-signatures:sid-rev-requirement].

**Syntax.** The specifications page lists these supported Snort options and filters: byte_extract, byte_jump and byte_test (without the dce option), content (at least 5 bytes; repeated content needs the distance option between occurrences), depth, detection_filter and event_filter (tracked by Snort attributes plus Zscaler's by_srcport and by_dstport; event_filter only inside a rule), distance, dsize, fast_pattern (3 to 16 bytes; the longest content is used if unset; no negation), flags, flow (to_server, to_client, from_client, from_server, established always enabled, no_stream), isdataat, nocase, offset, pcre (needs a content keyword; limited flags and constructs), stream_size and within. [zia.firewall.ips-signatures:supported-options] The page's flow option list omits the stream keyword that two pages recommend [divergence:zia.firewall.ips-signatures:flow-stream]. The specifications page's table lists these HTTP options and keywords for custom signatures, each with a Snort3 equivalent: http_uri, http_upath, http_uquery, http_host, http_accept, http_accept_encoding, http_accept_language, http_connection, http_contentencoding, http_contentmd5, http_contenttype, http_cookie, http_location, http_referer, http_server, http_setcookie, http_useragent, http_resp_code (Int32), http_contentlength, http_header, http_request_body, http_request_header, http_request_line, http_response_body, http_response_header, http_response_line and http_urilen. Supported http_method values are options, get, head, post, put, delete, trace and connect. [zia.firewall.ips-signatures:http-options] The http_version values are stated two ways in one table row [divergence:zia.firewall.ips-signatures:http-version-values]. Only the PCRE flags i and R are supported as listed, G, m and s are always enabled, and other PCRE flags are not supported. Lookahead and lookbehind assertions (positive and negative), conditional patterns and capturing groups are not supported, and Zscaler strongly recommends against capturing groups. [zia.firewall.ips-signatures:pcre-limits] Only the alert rule action is supported, and IP addresses and port numbers do not support variables. Alerts for packets directed towards any destination (an any any combination) are limited to 5, and the bidirectional (<>) operator is not supported. A rule holds at most 16 payload detection options (byte_extract, byte_jump, byte_test, content, isdataat, pcre, stream_size). detection_filter and event_filter are each limited to 10. Traffic data is not buffered, though stream state is kept and pattern matches across a packet boundary are found, so negative offsets for pattern modifiers such as distance are not supported. [zia.firewall.ips-signatures:general-limitations]

**Decrypted web traffic.** Custom IPS inspects decrypted web traffic only when the request or response is Text, HTML, CSV or JavaScript content over HTTP/S (GET, POST or PUT) or FTP, scanning URL, HTTP headers and HTTP body up to 500 KB per invocation, with its URL Categories criterion given on the page only as Suspicious URL destinations. [zia.firewall.ips-signatures:decrypted-web-scope] What the suspicious URL destinations are is open [gap:zia.firewall.ips-signatures:decrypted-url-scope].

**CSV import and export.** Custom signatures can be imported (to add, modify and delete) and exported as CSV. Import values must be wrapped in three single quotes (''') rather than double quotes to prevent parsing errors with certain PCRE options, and the file must follow the Sample Import CSV file format; the exported CSV cannot be used for import because import requires a different format. [zia.firewall.ips-signatures:csv-import-export] The help and the Go SDK differ on how values are quoted [divergence:zia.firewall.ips-signatures:csv-quoting]. The API side of export, validate and import is in [Custom IPS signature rules: export, validate and import wire behavior in the legacy API](kb:zia.api.legacy-ips-signature-wire).

**Threat categories and visibility.** Besides the predefined threat categories, an organization can add a maximum of 64 custom threat categories, each with a unique name of up to 255 characters (any characters, spaces included) and an optional description of up to 255 characters; the Threat Categories page shows each category's IPS Signature Rule Count, the number of custom signature rules in it. [zia.firewall.ips-signatures:custom-threat-categories] The Custom Signature Rules and Threat Categories pages each display up to 500 entries per page. [zia.firewall.ips-signatures:page-pagination] Logs of IPS traffic matching custom signatures appear in Firewall and Web Insights, can be charted in the IPS Overview dashboard, and can be streamed to a SIEM through NSS. [zia.firewall.ips-signatures:visibility] The firewall log flag is in [What a ZIA firewall log record is: aggregates, action and field names](kb:zia.logs.firewall-records), and the caps are in [Firewall rule, criteria and group limits](kb:zia.firewall.limits).

What to check:
1. Whether a custom signature's cap and protocol list are read from the tenant's console or the API, since the help pages disagree.
2. Whether a CSV import is formatted from the Sample Import CSV file on the Custom Signature Rules page, since the help and the Go SDK differ on quoting.
3. Whether a rule that inspects both HTTP header and body is tested with flow:stream, since the supported-options list omits it.

Sources disagree (name both sides):
- The custom IPS signature rule cap is 1,000 on the About and Configuring pages and 500 on the import page and in Ranges & Limitations. [divergence:zia.firewall.ips-signatures:custom-rule-cap]
  - zscaler-help: A maximum of 1,000 custom IPS signature rules.
  - zscaler-help: A maximum of 1,000 custom signature rules, and the page points to Ranges & Limitations for the cap, which says 500.
  - zscaler-help: 500, the import limit and also the maximum allowed for an organization.
  - zscaler-help: 500 (the evidence behind the existing claim zia.firewall.limits:custom-ips-caps).
  Impact: An answer about how many custom signatures a tenant can hold depends on which page is used; the existing zia.firewall.limits:custom-ips-caps rests on the 500 side.
- The Configuring page says TCP, UDP and HTTP are the only supported protocols for a custom signature, while the Specifications page says TCP, UDP and IP. [divergence:zia.firewall.ips-signatures:signature-protocols]
  - zscaler-help: TCP, UDP and HTTP.
  - zscaler-help: TCP, UDP and IP.
  Impact: Whether a signature can use the http or the ip protocol in its rule header depends on which page is used; the parser's response to validation is the arbiter.
- The Specifications page's list of supported flow options has no stream, yet that page and the Configuring page tell rule writers to use flow:stream. [divergence:zia.firewall.ips-signatures:flow-stream]
  - zscaler-help: The supported flow options are to_server, to_client, from_client, from_server, established (always enabled) and no_stream; stream is not listed.
  - zscaler-help: To match a pattern over a stream, use the flow:stream keyword.
  - zscaler-help: Rules that inspect both HTTP header and HTTP body should use stream mode (flow:stream).
  Impact: Whether flow:stream is accepted by the parser is not settled by the supported-options list; a rule that inspects both header and body is the case where it matters.
- The help page says import values must be wrapped in three single quotes instead of double quotes, while the Go SDK documents RFC 4180 doubled inner double quotes. [divergence:zia.firewall.ips-signatures:csv-quoting]
  - zscaler-help: Wrap each field value in three single quotes rather than double quotes.
  - sdk-go: Inner double quotes in the rule text column are doubled per RFC 4180, not escaped with backslashes (the existing claim zia.api.legacy-ips-signature-wire:import-csv-format).
  Impact: How a CSV import file is quoted depends on whether the console help or the Go SDK documentation is followed.
- One row of the HTTP options table lists http_version values two ways: HTTP/1.0 and HTTP/1.1 in one column, and http_1_0, http_1_1, http_2 and http_3 in the description. [divergence:zia.firewall.ips-signatures:http-version-values]
  - zscaler-help: Supported versions HTTP/1.0 and HTTP/1.1.
  - zscaler-help: Supported versions http_1_0, http_1_1, http_2 and http_3.
  Impact: Whether a signature can match HTTP/2 or HTTP/3 through http_version depends on which part of the row is read.
- The Configuring page gives the maximum scan size as 32 KB, while the Specifications page gives 32,000 bytes per session. [divergence:zia.firewall.ips-signatures:max-scan-size]
  - zscaler-help: 32 KB.
  - zscaler-help: 32,000 bytes per session.
  Impact: The two figures differ by 768 bytes if 32 KB means 32,768; whether the difference is rounding or two limits is not stated.
