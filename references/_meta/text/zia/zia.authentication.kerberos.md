# Deploying and troubleshooting Kerberos authentication: ports, location behavior, trust, GPO and ticket checks (zia.authentication.kerberos)
Also called: Kerberos deployment; Kerberos PAC file; cross-realm trust; domain trust password; KDC proxy; DirectAccess Kerberos; port 8800; Kerberos GPO push; Kerberos troubleshooting

The deployment guidelines say that to enforce Kerberos authentication an organization must send its traffic to port 80, 443 or 8800; [zia.authentication.kerberos:ports] The set of ports Kerberos is enforced on differs between pages [divergence:zia.authentication.kerberos:kerberos-ports-list]. What Kerberos is and which clients and networks it needs are in [SAML and Kerberos: what each needs to work](kb:zia.authentication.methods); the error pages Kerberos failures produce are in [ZIA authentication error codes: generic, directory, Kerberos and Identity Proxy](kb:zia.authentication.error-codes).

**On a location.** For known locations the service enforces Kerberos on all explicitly forwarded traffic it receives on port 8800, unless the location does not have authentication enabled; SSL/TLS inspection and other settings are inherited from the location. If Kerberos is not enabled for a location but some of its users need it, their traffic can be sent to port 8800. [zia.authentication.kerberos:port-8800-known-locations] What conditions govern enforcement on port 8800 differs between pages [divergence:zia.authentication.kerberos:port-8800-enforcement]. Enabling Kerberos on a location enforces it on all traffic explicitly forwarded to the service from that location and its dedicated proxy ports, so traffic to port 80 or 443 is still enforced; authentication must be enabled on a location that deploys Kerberos for some or all of its users. [zia.authentication.kerberos:location-enabled] The service does not support Kerberos for traffic forwarded in transparent mode (through a GRE or IPSec tunnel with the browser not configured to use a PAC file), regardless of the location settings or destination port. Users' browsers must use PAC files to forward traffic even if their location has an IPSec or VPN tunnel to the service. [zia.authentication.kerberos:transparent-unsupported]

**Deployment choices.** The default Kerberos PAC file forwards traffic to port 8800, the default Kerberos port on Public Service Edges for Internet & SaaS (ZIA). To use port 80 instead, copy it and replace the gateway variables ${GATEWAY_HOST}:8800 and ${SECONDARY_GATEWAY_HOST}:8800 with port 80, or specify a subscribed dedicated proxy port. [zia.authentication.kerberos:deploy-all-users] To have only some users of a location authenticate through Kerberos because the location already has a primary mechanism (for example LDAP or SAML), distribute the default Kerberos PAC file URL to those users and configure Kerberos without enabling it for the location. [zia.authentication.kerberos:deploy-some-users]

**Remote users.** Remote users must use DirectAccess to connect to the KDC Proxy; the page says DirectAccess is only supported on Windows 11, older versions of Windows do not support it, and there are no native clients for macOS and Linux. Remote access without DirectAccess might work for other VPN solutions. [zia.authentication.kerberos:remote-directaccess] For remote users, copy the default Kerberos PAC file and add a bypass for the KDC Proxy hostname, retaining the default destination port 8800 so remote user traffic goes to that port on the Public Service Edge; where a dedicated proxy port is used, Kerberos must be enabled at the location associated with it. [zia.authentication.kerberos:remote-pac] The guidelines tell administrators to ensure remote users send their traffic to port 8800 and say the service doesn't perform SSL/TLS inspection on this traffic. [zia.authentication.kerberos:remote-port-8800] Whether the no-inspection statement covers all port 8800 traffic is open [gap:zia.authentication.kerberos:port-8800-inspection].

**Before the trust.** Before deploying Kerberos, the realm name on the General Information tab must match one of the domains in the Domains field. Users are provisioned by manually adding them to the Hosted User Database, importing them there, or synchronizing from an Active Directory or LDAP server. The sAMAccountName@Windows-Domain is sent as the Kerberos identifier, so the user login attribute in the synchronization settings might need to map to sAMAccountName. [zia.authentication.kerberos:prerequisites] Client workstations need TCP 88 or UDP 88 to the Central Authority IP addresses to authenticate against the Zscaler domain KDC (some clients fall back to the other protocol if one is blocked, which is not guaranteed), and TCP 8800 to the Public Service Edge IP address ranges, which is not required if Kerberos is enabled on a location. [zia.authentication.kerberos:outbound-firewall] Configuring Kerberos as an authentication mechanism (usable in addition to other methods) generates the domain trust password, shown in the Domain Trust Password field, which is required when establishing the cross-realm trust between the organization's domain and the Zscaler domain; the page says to copy it and store it securely. [zia.authentication.kerberos:domain-trust-password]

**Windows trust and GPO.** The Windows trust is one-way, so Zscaler trusts the domain's authenticated users and not the reverse, and creating it needs administrator access to the domain controller. In the wizard the trust name is the Zscaler cloud name in uppercase letters, the type is Realm trust, transitivity is Nontransitive, the direction is One-way: incoming, and the other domain is marked as supporting Kerberos AES encryption. [zia.authentication.kerberos:windows-trust-settings] The article's verification of a correct trust lists msDS-SupportedEncryptionTypes 24, objectClass trustedDomain, trustAttributes 1, trustDirection 1 and trustType 3. [zia.authentication.kerberos:windows-trust-attributes] The GPO values pushed to clients are, for the interoperable Kerberos V5 realm setting, <k>kerberos.<Zscaler Cloud></k> (in the example <k>kerberos.zscalerbeta.net</k>), and for the host name-to-realm mapping the Zscaler domain names (in the example .zscalerbeta.net; .gateway.zscalerbeta.net), both with leading dots to match all subdomains. [zia.authentication.kerberos:gpo-settings] The article checks the pushed settings in the registry under the Policies\System\Kerberos keys MitRealms and domain_realm, refreshes a client with gpupdate /force, and says the browser must be configured with the Kerberos PAC file URL. [zia.authentication.kerberos:gpo-registry-and-refresh]

**Linux clients.** On Linux, Kerberos support is provided by either the MIT Kerberos package or the Heimdal package, with its configuration file in /etc/krb5.conf. For Firefox the guide's example sets network.negotiate-auth.trusted-uris to gateway.zscalerbeta.net, .gateway.zscalerbeta.net, and the example command export MOZ_LOG=negotiateauth:5 enables logging. [zia.authentication.kerberos:linux-clients]

**Troubleshooting.** Zscaler recommends troubleshooting Kerberos first on the domain controller, with the administrator provisioned on the Zscaler service as a user so Kerberos authentication doesn't fail. If the time and date settings on the domain controller differ from the Zscaler KDC by more than five minutes, authentication will fail. [zia.authentication.kerberos:troubleshoot-start] The browser test uses Zscaler cloud on port 8800, the default Kerberos authentication port on Public Service Edges; Microsoft Edge and Mozilla Firefox support Kerberos by default, and misconfigured cross-realm settings produce a Public Service Edge page with an error code. After clearing the Kerberos ticket cache the ticket list should show a Zscaler KDC krbtgt ticket and the company's KDC krbtgt ticket, both from the organization's domain controller, and a Public Service Edge krbtgt ticket from the Zscaler KDC; if the last is missing the Public Service Edge is not issuing tickets and the page says to contact Zscaler Support. [zia.authentication.kerberos:troubleshoot-browser-and-tickets] The Zscaler domain, which has the same name as the Zscaler cloud name, must be on the domain trusts list as an inbound trust, and pinging kerberos.<Zscaler Cloud> must return the Zscaler Central Authority's IP address. There is no way to check the cross-realm password of an added trust; the domain trust must be deleted and re-added with the correct password. [zia.authentication.kerberos:troubleshoot-trust] Kerberos authentication can work on the domain controller but not on a user's device, in which case there might be an error with the GPO settings; the page says to check whether the GPO settings have been propagated from the domain controller to users. [zia.authentication.kerberos:controller-works-device-fails]

What to check:
1. Whether the failing traffic reaches port 80, 443 or 8800 and whether the location has Kerberos enabled.
2. Whether the traffic is transparently forwarded, since Kerberos is unsupported there regardless of location settings or destination port.
3. Whether the realm name matches a domain in the organization's Domains field and the trust name is the cloud name in uppercase.
4. Whether the three krbtgt tickets are present after clearing the ticket cache.

Sources disagree (name both sides):
- The deployment guidelines name ports 80, 443 and 8800 for enforcing Kerberos; the default Kerberos PAC file article lists proxy ports 80, 443, 9400 and 9443 plus the location's dedicated port. [divergence:zia.authentication.kerberos:kerberos-ports-list]
  - zscaler-help: Traffic must go to port 80, 443 or 8800; a Kerberos-enabled location also enforces it on its dedicated proxy ports.
  - zscaler-help: If the location has Kerberos enabled, traffic can go to the proxy ports 80, 443, 9400, 9443 or the location's dedicated port.
  Impact: Whether ports 9400 and 9443 enforce Kerberos is stated by one page and absent from the other's list; the pages do not say which list is complete.
- The pages give different conditions for Kerberos enforcement on port 8800. [divergence:zia.authentication.kerberos:port-8800-enforcement]
  - zscaler-help: For known locations, 8800 traffic is enforced unless the location has authentication disabled.
  - zscaler-help: Public Service Edges challenge all traffic received on port 8800, with no location condition stated.
  - zscaler-help: For a Virtual Service Edge, port 8800 enforces Kerberos whether or not Kerberos is enabled for the location (and irrespective of the spnego_krb_noport_bypass parameter).
  Impact: Whether 8800 traffic from a location with authentication disabled, or with Kerberos not enabled, is challenged depends on the page and on the edge type; the Virtual Service Edge page is scoped to Virtual Service Edges.

Not known (open gaps):
- Whether the no-SSL/TLS-inspection statement covers all port 8800 traffic [gap:zia.authentication.kerberos:port-8800-inspection]: settled by lab-test or support-ticket
