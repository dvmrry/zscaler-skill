# Directory (LDAP/AD) synchronization behavior (zia.ad-integration.directory-sync)
Also called: ldap sync; active directory sync; directory synchronization; sync frequency; nested groups; sync now; lastSyncStartTime; users deleted from directory

"I added the user to the AD group, why does the rule not match yet?" Directory synchronization runs an LDAP search with the configured directory parameters and imports users that have a user or email attribute and are in the account's configured domain. It adds users, groups and departments present in the directory but not in the service, deletes those in the service but not in the directory, and modifies service data to match the directory. [zia.ad-integration.directory-sync:sync-actions] User data can be synchronized periodically or on demand. The ZAB can be set to synchronize on demand, daily, weekly or monthly. [zia.ad-integration.directory-sync:periodic-or-on-demand] User information and group information is updated when either a user is authenticated or the Zscaler server synchronizes data from the directory server; with Only Once as the authentication frequency, user and group information is only updated when synchronization is performed. [zia.ad-integration.directory-sync:change-lag] How long a directory change takes to reach policy is open [gap:zia.ad-integration.directory-sync:change-propagation-time]; the schedule options are [zia.ad-integration.directory-sync:sync-frequency-options]. The last run is visible in the settings object: lastSyncStartTime and lastSyncEndTime are epoch-second timestamps of the start and end of the last LDAP sync, applicable only to directory-based authentication. Both are reset when the authentication type is changed to a different directory authentication type. [zia.ad-integration.directory-sync:last-sync-fields] The Lite variant of that object omits these fields, see [The organization's default authentication settings are one object, read and written at /authSettings. A separate GET /authSettings/lite returns the same model, but authFrequency, authCustomFrequency, lastSyncStartTime and lastSyncEndTime are not applicable to the Lite API.](kb:zia.authentication.settings:org-object).

**Authentication of synced users.** By default synchronized users authenticate by an LDAP Bind to the directory server with their Distinguished Name and password, so passwords stay on the directory server and are never synchronized. [zia.ad-integration.directory-sync:ldap-bind-auth] The default authentication method for synchronized users is LDAP Bind; the synchronization article says another method can be configured instead from a list it gives. If a one-time token or one-time link authenticates users whose information was synchronized from a directory server, the passwords are stored in the Zscaler database and not in the directory server. [zia.ad-integration.directory-sync:sync-auth-methods] The pairing table in [ZIA provisioning methods and which authentication each allows](kb:zia.ad-integration.provisioning-methods) lists fewer methods for directory sync than these pages do: [zia.ad-integration.provisioning-methods:directory-sync-auth-pairing](kb:zia.ad-integration.provisioning-methods:directory-sync-auth-pairing).

**Users removed from the directory.** Users removed from the directory are deactivated, not deleted: the service invalidates their authentication cookies so they can no longer authenticate. [zia.ad-integration.directory-sync:deactivate-not-delete] The two captured articles word this differently [gap:zia.ad-integration.directory-sync:delete-vs-deactivate-wording].

**Scope.** Synchronization uses configured directory parameters: the limits table lists a Base DN, a User Search Filter and a Group Search Filter among the AD and OpenLDAP fields. [zia.ad-integration.directory-sync:scope-fields]

**Nested groups.** The directory synchronization article says the Zscaler service does not support nested groups, and that specific group names within each nested group must be manually identified and added to the Group filter. [zia.ad-integration.directory-sync:sync-nested-groups] The ZAB article describes flattening nested groups, which the sync article does not mention [divergence:zia.ad-integration.directory-sync:nested-groups-support]. Whether flattening depends on the agent hosting is open [gap:zia.ad-integration.directory-sync:nested-groups].

**Connecting.** On the directory server, the Zscaler service must be granted read-only access on a specific port (Zscaler provides the IP addresses) and allowed to connect to the appropriate ports when it performs an LDAP Bind. All the organization's email domains must be added to the Zscaler account because the service synchronizes data only from the configured domains. The user whose DN is used to bind to or query the directory does not require privileged access. [zia.ad-integration.directory-sync:sync-prerequisites] Authentication agent hosting is Cloud (the central authority queries the directory server directly) or Enterprise (the organization installed a Zscaler Authentication Bridge). The port options are 3268 (the Global Catalog of an AD server), 3269 (the Global Catalog over SSL/TLS), 389 (an LDAP server; the AD default listening port) and 636 (an LDAP server over SSL/TLS); for multiple domains from an AD server, port 3268 or 3269 is selected so the service can access the Global Catalog. Zscaler strongly recommends enabling the option that secures LDAP communications between the service and the directory server. [zia.ad-integration.directory-sync:agent-hosting-and-ports] The service can synchronize data for up to two sets of users; a secondary directory server is for a directory without duplicate user or group information, and the article says not to set one up for redundancy. When an FQDN resolves to multiple IP addresses, the service ignores inactive or unavailable servers and synchronizes with the one that is active or available. [zia.ad-integration.directory-sync:two-directory-sets]

**What is read.** The Zscaler service can synchronize user information from one forest in an organization; with multiple forests an AD proxy can be set up, and otherwise Zscaler recommends integrating with SAML. It can synchronize data from multiple domains as long as they are all registered with Zscaler Support. [zia.ad-integration.directory-sync:forest-and-domains] The service only retrieves objects from the branch specified in the Base DN field. With pagination Auto (recommended) the service detects whether the directory server supports pagination and pages results that exceed 1,000 items, returning only the first 1,000 items if it does not; with pagination Disabled the directory server returns the first 1,000 items only. [zia.ad-integration.directory-sync:base-dn-and-pagination] The login attribute must be in the form of an email address, though not necessarily a valid one. If the value is not an email address the service creates one by appending the domain name when the organization has registered a single domain; with multiple registered domains and a value that is not an email address, the synchronization fails. Zscaler recommends userPrincipalName regardless of the number of domains, sAMAccountName only with one hosted domain, and otherwise proxyAddresses, userPrincipalName or mail. [zia.ad-integration.directory-sync:login-attribute-form] In the group filter syntax the asterisk (*) is required so the filter automatically completes the Common Name (cn) value, the pipe character (|) means at least one criterion must match, and the ampersand (&) means all criteria must be true. [zia.ad-integration.directory-sync:group-filter-syntax] The directory synchronization article states that the service synchronizes up to 16 groups per user. [zia.ad-integration.directory-sync:sync-groups-per-user-16] The per-user group cap differs between pages: [zia.ad-integration.identity-objects:groups-per-user-cap](kb:zia.ad-integration.identity-objects:groups-per-user-cap).

**Schedule.** The Synchronization Frequency options are Manual (synchronize only when Sync Now is clicked), Daily (every 24 hours at midnight in the organization's time zone), Weekly (every Sunday at midnight in the organization's time zone) and Monthly (on the first day of every month at midnight in the organization's time zone). If the directory server is unavailable at the scheduled time, the service tries to synchronize at the next scheduled time. [zia.ad-integration.directory-sync:sync-frequency-options] With Active Directory or OpenLDAP, Sync Now on the Default Settings page synchronizes the Zscaler service with the AD or OpenLDAP server, and Last Synchronization Time shows when the service last synchronized, depending on the Synchronization Frequency configured. [zia.ad-integration.directory-sync:sync-now-console] Whether an API triggers a synchronization is open [gap:zia.ad-integration.directory-sync:sync-now-api].

**Filters and AD options.** The User Authentication Filter finds the user's DN when the user authenticates, and unlike the User Search Filter and Group Search Filter the service uses it only when it authenticates a user, not when it synchronizes users; the article says the filter can be parameterized, such as (&(objectClass=user)(sAMAccountName=${USER})). If Advanced Search Filter is disabled, the service uses the User Search Filter for synchronizing and authenticating users. [zia.ad-integration.directory-sync:auth-filter-vs-search-filter] For Active Directory only, Enable Password Change Sync scans the AD for password changes, and a Password Last Set Attribute field that appears with it takes the attribute that represents the password last-changed time stamp (for example pwdLastSet); in addition, Enable User Deactivation Checks detects whether a user account is deactivated on the AD, polled at the Active Directory Poll Frequency in seconds; that field cannot be modified for the secondary directory server, which uses the primary's frequency. [zia.ad-integration.directory-sync:ad-password-and-deactivation-options] Clicking Finish in the Authentication Wizard overwrites the existing user authentication configuration with the new configuration. [zia.ad-integration.directory-sync:authentication-wizard-overwrite]

**Disabled accounts and failures.** Users marked disabled in the Active Directory are still returned by the AD server for the filters the article lists, so they are not deleted from the Zscaler user database and their cookies remain valid, allowing them to use the service to browse. The article's fix is to add (&(objectClass=User)(!(UserAccountControl:1.2.840.113556.1.4.803:=2))) to both the User Search Filter and Search Filter fields. [zia.ad-integration.directory-sync:disabled-ad-users-keep-browsing] When synchronization fails, the troubleshooting article says to verify the connectivity between the Zscaler Central Authority server and the directory server and that the Bind password is correct; when a user's password was changed on the AD or LDAP server but the user still uses the old one, it says to reset the password on the AD or LDAP server. [zia.ad-integration.directory-sync:sync-failure-checks]

If immediate propagation matters, the documented alternative is SCIM, where the client pushes changes: [How fast SCIM changes reach ZIA](kb:zia.scim.propagation). To move a tenant off directory sync, see [Enabling ZIA SCIM: prerequisites, base URL and token](kb:zia.scim.setup) and the migration flag in [The organization-wide authentication settings object](kb:zia.authentication.settings).

What to check:
1. The last sync timestamps on the org settings object, and whether a sync has run since the directory change; with an authentication frequency other than Only Once, also whether the user has authenticated since.
2. Whether the user is in the synced domain with a user or email attribute.
3. Whether a user in a nested group matches a rule on the parent group before relying on nesting.

Sources disagree (name both sides):
- The directory synchronization article says nested groups are not supported, while the ZAB deployment article describes flattening nested groups. [divergence:zia.ad-integration.directory-sync:nested-groups-support]
  - zscaler-help: The service does not support nested groups; group names within each nested group must be added to the Group filter by hand.
  - zscaler-help: Enabling nested groups on the ZAB lets the service flatten and sync user group membership for nested groups.
  Impact: The sync article does not limit its statement to cloud-hosted agents, and the ZAB article does not say whether flattening applies only with the Enterprise (ZAB) agent hosting. Do not say nested groups work or fail for directory sync without saying which agent hosting the tenant uses.
