# Sending traffic to a Virtual Service Edge: GRE, PAC, L2 redirect, home users and Kerberos host names (zia.virtual-service-edge.forwarding)
Also called: forward traffic to vse; vse gre tunnel; vse pac file; vse l2 forwarding; vse wccp; vse kerberos; forbid_nongvzt_users; spnego_krb_noport_bypass

The forwarding page covers how traffic is sent to a Virtual Service Edge. Zscaler recommends deploying Virtual Service Edges behind the organization's firewall, though they can be deployed in the DMZ as well. [zia.virtual-service-edge.forwarding:placement-behind-firewall] The forwarding page says Virtual Service Edges support IPv6 traffic if it is only forwarded via GRE tunnels. [zia.virtual-service-edge.forwarding:ipv6-gre-only-page] The same statement on other pages names IPSec as well, see [Addresses, interfaces, outbound connectivity and ports for a Virtual Service Edge](kb:zia.virtual-service-edge.network-requirements).

**GRE.** Zscaler recommends a GRE tunnel from the internal router to the Virtual Service Edge cluster IP address. Because the tunnel uses internal IP addresses the tunnel IPs need not be registered with Zscaler, backup GRE tunnels between the internal router and Public Service Edges are also possible. GRE tunnels configured on Virtual Service Edges are dynamically established with no internal IP addresses, similar to unnumbered GRE tunnels, which requires Virtual Service Edges to be configured as locations. Zscaler uses any internal IP address on the router side of the tunnels for routing purposes only, so proxy settings or ICMP ping on those ranges are not supported, and tunnel monitoring must use GRE keepalives and ICMP pings to the Virtual Service Edge VIP. [zia.virtual-service-edge.forwarding:gre] The VIP-unnumbered tunnel detail is in [GRE tunnels to ZIA: requirements, bandwidth and deployment](kb:zia.traffic-forwarding.gre).

**PAC.** A PAC file can be edited to add the Virtual Service Edge cluster IP address as the proxy; the page's example is Return "PROXY 10.84.0.188:80; PROXY ${GATEWAY}:80; PROXY ${SECONDARY_GATEWAY}:80;DIRECT"; and it suggests adding the variable ${SRCIP} to direct the browser to send traffic to the Virtual Service Edge. The addresses are the vendor's examples. [zia.virtual-service-edge.forwarding:pac] PAC syntax and variables are in [PAC file forwarding: limits, versions and what it cannot cover](kb:zia.traffic-forwarding.pac).

**Layer 2.** If a router or switch is in the same subnet as the Virtual Service Edge cluster IP address it can be configured to use L2 forwarding to redirect packets to the Virtual Service Edge. Cisco Web Cache Communication Protocol (WCCP) configurations do not work with Virtual Service Edges. [zia.virtual-service-edge.forwarding:l2-and-wccp]

**Home users.** A location for a Virtual Service Edge created to allow home users to use it could lead to a Denial of Service (DoS) attack. Parameters can be configured on the Virtual Service Edge so that only the users' Zscaler Client Connector and GRE tunnel traffic are processed, with `forbid_nongvzt_users=1` in the SME section of the configuration file. [zia.virtual-service-edge.forwarding:home-users] What the parameter name refers to is not defined [gap:zia.virtual-service-edge.forwarding:nongvzt-meaning].

**Kerberos.** The Enable Kerberos option appears in the Edit Location window only after Kerberos is enabled. For cluster deployment mode the Kerberos host name uses the cluster IP address and for standalone deployment mode the proxy IP address of the Virtual Service Edge instance, in the format vzen-<Proxy IP Address>-<Company ID>.gateway.<Cloud Name>.net; the page's cluster example is vzen-10-66-63-22-370255.gateway.zscalertwo.net. [zia.virtual-service-edge.forwarding:kerberos-hostnames] If Kerberos is enabled only in Authentication Settings and not in the Virtual Service Edge location configuration, forward proxy traffic landing on ports 80/9443/DPPC-Port using the host name format does normal authentication, except port 8800. The page also says the Virtual Service Edge redirects traffic to gateway authentication for ports 8800 and 8443 if Kerberos is enabled for the location, and that adding spnego_krb_noport_bypass=1 to the vzen_custom.conf file avoids bypassing Kerberos for these ports. If Kerberos is enabled for a location with that parameter set, all the ports the Virtual Service Edge listens on enforce Kerberos authentication. The pauth_port (8080) enforces digest authentication irrespective of that parameter or of Kerberos or digest being enabled for the location, and the Kerberos port (8800) enforces Kerberos authentication irrespective of that parameter or of Kerberos being enabled for the location. [zia.virtual-service-edge.forwarding:kerberos-ports] The page's port statements differ [divergence:zia.virtual-service-edge.forwarding:kerberos-ports-scope]. Two terms on the page are not defined [gap:zia.virtual-service-edge.forwarding:kerberos-terms].

Sources disagree (name both sides):
- Which ports use Kerberos when the Virtual Service Edge location has Kerberos enabled. [divergence:zia.virtual-service-edge.forwarding:kerberos-ports-scope]
  - zscaler-help: If the location has Kerberos enabled, all ports use Kerberos authentication.
  - zscaler-help: With Kerberos enabled for the location, ports 8800 and 8443 are redirected to gateway authentication.
  - zscaler-help: The pauth_port 8080 enforces digest authentication irrespective of the setting.
  Impact: "All ports use Kerberos" does not hold for 8080 (digest) and 8443 (redirected to gateway authentication) as the page describes them; port 8800 enforces Kerberos either way and so agrees. The page gives a vzen_custom.conf parameter for the 8800 and 8443 redirect, and whether 8080 can be changed is not stated.
