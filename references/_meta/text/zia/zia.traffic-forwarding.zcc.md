# Client Connector as a forwarding method: benefits, limits and Z-Tunnel modes (zia.traffic-forwarding.zcc)
Also called: zscaler client connector forwarding; z-tunnel 1.0; z-tunnel 2.0; remote users forwarding; ztunnel fallback; road warrior

Client Connector is the method that follows the user. Zscaler recommends Client Connector on user devices to protect web traffic from an unknown location (a remote user): the app detects when the user leaves the secure network and creates a connection to the service from an unknown location. [zia.traffic-forwarding.zcc:remote-users] Client Connector covers Windows, macOS, Linux, iOS, Android and virtual desktops, supports every authentication mechanism the service supports, fingerprints devices, detects trusted networks and can disable itself there, forwards all ports and protocols, can be prevented from being disabled or uninstalled, and supports SSL Inspection for its users. [zia.traffic-forwarding.zcc:benefits]

**Costs and prerequisites.** Where a public IP is mapped to the user's location, some location-based policies (Firewall, Forwarding Control, DNS) apply to the user's Client Connector traffic, but the vendor says Sublocations, Surrogate IP and Bandwidth Control "cannot be enabled for your organization", and the software must be deployed, managed and maintained on every device. [zia.traffic-forwarding.zcc:limitations] Users must be provisioned and have an authentication method configured; Private Access through the app requires SAML authentication, and the firewall must allow the connections the app needs for internet security. [zia.traffic-forwarding.zcc:requirements] Deploying Client Connector for Internet & SaaS includes managing admin access to Client Connector using role-based administration. To use the Zscaler service an authentication mechanism must be configured and users provisioned on the Internet & SaaS service; an organization without an authentication mechanism installed must use the Admin Console as its identity provider (IdP) to provision and authenticate users. [zia.traffic-forwarding.zcc:zia-deployment-tasks] Among the deployment page's optional tasks, to enable SSL/TLS Inspection for Client Connector the feature must first be enabled in the Admin Console for each relevant platform. [zia.traffic-forwarding.zcc:ssl-inspection-per-platform] Among the deployment page's optional tasks, PAC files can be used in Client Connector profiles and forwarding profiles to determine how to direct the organization's traffic; for custom PAC files Zscaler highly recommends starting from the Admin Console default PAC file and customizing it, and a custom PAC file can then be hosted in the Admin Console. [zia.traffic-forwarding.zcc:pac-files] The old reference said every forwarding method ends as a Location; for this one the vendor describes the app connecting 'from an unknown location' ([What a ZIA location is and what the console enforces for it](kb:zia.locations.model) has the Road Warrior tag for such traffic).

**Tunnel modes.** Z-Tunnel 1.0 forwards traffic by CONNECT requests, like a traditional proxy, sending all proxy-aware traffic or port 80/443 traffic depending on the forwarding profile; it is selected in a forwarding profile in Tunnel mode with the packet filter driver enabled. [zia.traffic-forwarding.zcc:z-tunnel-1] Z-Tunnel 2.0 sends packets over DTLS or TLS and can carry all ports and protocols; using it means deploying a supported Client Connector version, selecting Z-Tunnel 2.0 in a Tunnel-mode forwarding profile with the packet filter driver enabled, and configuring bypasses in App Profiles. [zia.traffic-forwarding.zcc:z-tunnel-2] Z-Tunnel 2.0 needs a NAT device that uses a single IP for all connections from one device; otherwise control and data connections can land on different Service Edges, Z-Tunnel 2.0 fails to establish and the client falls back to Z-Tunnel 1.0. [zia.traffic-forwarding.zcc:z-tunnel-2-single-ip-nat] The mechanism and bypass design are in [Z-Tunnel](kb:zcc.z-tunnel) and [ZCC forwarding profiles](kb:zcc.forwarding-profiles). Which proxy mode each tunnel mode corresponds to is in [Which forwarding methods produce explicit or transparent mode](kb:zia.proxy-mode.forwarding-map); how a site's GRE egress can trigger the fallback is in [Mixed forwarding deployments and where they break](kb:zia.traffic-forwarding.mixed-deployments).

Whether trusted-network detection defers to a GRE tunnel is open [gap:zia.traffic-forwarding.zcc:zcc-covers-gre-fallback].

SSL Inspection rules are in [SSL/TLS inspection rule criteria and the ones that silently don't match](kb:zia.ssl-inspection.criteria).

What to check:
1. Which tunnel mode the device is really in, since a silent fallback to Z-Tunnel 1.0 changes what traffic is covered.
2. Whether the NAT device in front of the client uses a single IP for all connections from one device.
3. Whether SSL Inspection rules reach Client Connector users.

Not known (open gaps):
- Client Connector as a second layer behind tunnels [gap:zia.traffic-forwarding.zcc:zcc-covers-gre-fallback]: settled by operator-experience
