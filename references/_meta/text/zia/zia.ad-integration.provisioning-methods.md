# ZIA provisioning methods and which authentication each allows (zia.ad-integration.provisioning-methods)
Also called: provisioning methods; SCIM vs LDAP sync; hosted user database; ZAB; authentication bridge; which provisioning method; provisioning and authentication pairing

Provisioning (getting users into the Zscaler database) and authentication (identifying traffic) are separate choices, but not independent ones. The service supports five provisioning methods: Identity Federation using SCIM, SAML, the Hosted User Database, synchronization with a directory server, and the Zscaler Authentication Bridge (ZAB). [zia.ad-integration.provisioning-methods:five-methods] Zscaler recommends SCIM for provisioning and SAML identity federation for authentication. Directory synchronization is recommended if SAML is not feasible and the organization has more than 100 users; the hosted user database if SAML or SCIM are not feasible and the organization has up to 100 users. [zia.ad-integration.provisioning-methods:recommendation]

**Pairing.** Each provisioning method allows only some authentication methods. SCIM: SAML only. Hosted User Database: passwords (default), Kerberos, one-time link, one-time token. Directory server synchronization: LDAP BIND, one-time link, one-time token. ZAB: Hosted User Database, SAML, LDAP BIND, one-time link, one-time token. [zia.ad-integration.provisioning-methods:auth-pairing] The pairing table lists SAML as the only authentication method for SCIM, and for directory server synchronization it lists LDAP BIND, one-time link and one-time token, without SAML or Kerberos. [zia.ad-integration.provisioning-methods:pairing-consequences] Other pages pair directory-synchronized users with SAML [divergence:zia.ad-integration.provisioning-methods:directory-sync-auth-pairing].

**Hosted User Database and ZAB.** Manual and CSV provisioning, and one-time tokens and links, are in [Hosted User Database: adding users by hand, importing users, groups and departments by CSV, and one-time tokens and links](kb:zia.ad-integration.hosted-user-database). ZAB deployment is in [Deploying the Zscaler Authentication Bridge (ZAB): requirements, certificates, commands and renewal](kb:zia.ad-integration.authentication-bridge).

**Directory synchronization.** Directory server synchronization requires the firewall to allow the Zscaler service to reach the directory server, with read-only access to the directory. Passwords are never synchronized. [zia.ad-integration.provisioning-methods:directory-sync-needs-reach] What it does once connected is in [Directory (LDAP/AD) synchronization behavior](kb:zia.ad-integration.directory-sync).

**ZAB.** The ZAB is a virtual appliance that imports users from an AD or LDAP server without requiring inbound connections to the directory server: it opens a long-living outbound tunnel to the Zscaler Central Authority, downloads the organization's authentication profile and synchronizes on demand or as scheduled. It can be used only to provision, alongside SAML or Kerberos authentication, or also to authenticate with LDAP. [zia.ad-integration.provisioning-methods:zab-outbound] When the ZAB provisions and SAML authenticates, only the primary IdP in the Admin Console can have SAML auto-provisioning enabled, and SCIM cannot be enabled on any IdP while the ZAB is used for provisioning. [zia.ad-integration.provisioning-methods:zab-exclusions] A tenant moving from ZAB provisioning to SCIM cannot run both at once: SCIM cannot be enabled on any IdP while the ZAB is used for provisioning, so the move is a cutover rather than an overlap. [zia.ad-integration.provisioning-methods:zab-to-scim-cutover]

**SAML and SCIM** are covered in [SAML auto-provisioning: what login creates and overwrites](kb:zia.ad-integration.saml-auto-provisioning) and [ZIA SCIM provisioning](kb:zia.scim). The org-level migration switch from directory sync to SCIM is [directorySyncMigrateToScimEnabled disables directory synchronization for the user repository type so that SCIM provisioning or SAML auto-provisioning can be enabled; it is the setting for migrating from directory synchronization to SCIM.](kb:zia.authentication.settings:scim-migration-flag), with its reversibility question open in [The organization-wide authentication settings object](kb:zia.authentication.settings).

What to check:
1. Which method the tenant actually provisions with, in the Identity Providers and directory settings of the Admin Console.
2. Whether the authentication method in use is one the pairing allows.
3. Whether a move from the ZAB to SCIM is planned as a cutover, since SCIM cannot be enabled while the ZAB provisions.

Sources disagree (name both sides):
- The pairing table lists LDAP BIND, one-time link and one-time token for directory server synchronization, while other pages pair directory-synchronized users with SAML or another configurable method and list directory synchronization as a way to provision Kerberos users. [divergence:zia.ad-integration.provisioning-methods:directory-sync-auth-pairing]
  - zscaler-help: The supported authentication methods for directory server synchronization are LDAP BIND, one-time link and one-time token.
  - zscaler-help: The synchronization article names LDAP Bind as the default and says another method can be configured, which the pairing table's list does not reflect.
  - zscaler-help: The AD-to-SCIM migration guide's prerequisite is SAML for authentication with AD for provisioning.
  - zscaler-help: The Kerberos deployment page lists synchronizing user data from an AD or LDAP server among the ways users are provisioned for Kerberos.
  Impact: Do not conclude from the pairing table that directory-synchronized users cannot use SAML or Kerberos. The default settings page also lets an AD or OpenLDAP repository select SAML (zia.authentication.settings:auth-type-preconditions), so the table is not a complete list.
