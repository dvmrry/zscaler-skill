# Python SDK service-specific behavior for ZIA: admin, AppTotal, browser control, smart isolation and GRE tunnel VIPs (zia.sdk-python.service-behaviors)
Also called: smart_isolation_users_ids ignored; update_smart_isolation; convert_to_user; browser control endpoint python; dedicated ip gateways python; apptotal get_app; feature_permissions; admin user role_id python sdk; add_gre_tunnel

These are claims about the Python SDK's service helpers, not about ZIA. Each covers one behavior a reader would otherwise have to infer from the method signature.

**Admin roles and users.** In the admin role create and update helpers a `feature_permissions` dict is renamed to the wire key `featurePermissions` before the request is built; the rename happens only when the value is a dict. [zia.sdk-python.service-behaviors:admin-role-permissions-key] The admin user create and update helpers turn a `role_id` keyword into `{"role": {"id": ...}}`. The docstring says `scope_entity_ids` need not be given when the admin scope is ORGANIZATION. [zia.sdk-python.service-behaviors:admin-user-role-id] The API specification describes `POST /adminUsers/{userId}/convertToUser` as removing a user's admin privileges while keeping them as a regular user, as an alternative to DELETE, which removes the admin and also removes them as a user. It says the admin user's details are first obtained with `GET /users` and then sent in the convert request. [zia.sdk-python.service-behaviors:convert-to-user-spec] Password-expiry support is in [When the Python SDK ends a ZIA session and what that does to staged changes](kb:zia.sdk-python.activation-and-session).

**Update helpers.** The alert subscription and bandwidth control rule update helpers write the path ID into the request body (`body["id"]`) before sending the PUT. [zia.sdk-python.service-behaviors:update-injects-id]

**AppTotal.** `get_app` on the AppTotal client searches the catalog by app ID; if the app is absent the call submits it for analysis, and a later call is needed to read the result. [zia.sdk-python.service-behaviors:apptotal-submit-on-miss] The `search_app` and `app_views` docstrings state that at most 200 results are returned. [zia.sdk-python.service-behaviors:apptotal-result-cap]

**Browser control and Smart Browser Isolation.** The older `browser_control_settings` client and the newer `secure_browsing` client both read and write the same path `/browserControlSettings`; the Go `browser_control_settings` and `secure_browsing` packages each set their endpoint constant to `/zia/api/v1/browserControlSettings`. [zia.sdk-python.service-behaviors:browser-control-shared-endpoint] `update_smart_isolation` remaps ID lists with `transform_common_id_fields(reformat_params, ...)`, and `reformat_params` lists the keys `smart_isolation_user_ids` and `smart_isolation_group_ids` for that. [zia.sdk-python.service-behaviors:smart-isolation-id-keys] The `update_smart_isolation` docstring and its example name the keyword arguments `smart_isolation_users_ids` and `smart_isolation_groups_ids`. [zia.sdk-python.service-behaviors:smart-isolation-doc-keys] The names disagree [divergence:zia.sdk-python.service-behaviors:smart-isolation-kwarg-names]. The provider's two-step write is in [ZIA Terraform operations that take several API writes with no rollback](kb:zia.terraform.multi-step-writes).

**Scope of the web DLP client.** The web DLP rule client's docstrings say its get and list-lite calls exclude SaaS Security API DLP policy rules, and that its update is not applicable to them. [zia.sdk-python.service-behaviors:dlp-web-rule-excludes-saas]

**Dedicated IP gateways.** The Python dedicated IP gateway client defines `list_dedicated_ip_gw_lite`, which reads `/dedicatedIPGateways/lite`. [zia.sdk-python.service-behaviors:dedicated-ip-lite-only] The Python dedicated IP gateway client has no get, add, update or delete method. [zia.sdk-python.service-behaviors:dedicated-ip-no-crud]

**GRE tunnels.** `add_gre_tunnel` and `update_gre_tunnel` document the VIPs as `primary_dest_vip` and `secondary_dest_vip` (the add docstring's example passes `primary_dest_vip` as a dict), use their keyword arguments as the body, and decide whether to pick VIPs by testing for the camelCase keys `primaryDestVip` and `secondaryDestVip`. When either camelCase key is absent they call `get_closest_diverse_vip_ids` with the source IP, which lists the recommended VIPs and raises ValueError when none is returned or none is in a second city, and they write the IDs it returns under `primaryDestVip` and `secondaryDestVip`. [zia.sdk-python.service-behaviors:gre-vip-auto-select-tests-camel-keys] So a call that passes both VIPs under the documented snake_case names still runs the VIP lookup, and fails with its ValueError when the lookup finds no diverse pair; otherwise the body holds both the caller's `primary_dest_vip` and the added `primaryDestVip`, both become the wire key `primaryDestVip` when the executor camel-cases the body, and the added key, written later, replaces the caller's value. The secondary VIP is replaced the same way, so the tunnel is sent with the recommended VIPs, not the ones passed. [zia.sdk-python.service-behaviors:gre-documented-vips-replaced] The ZIA Ansible collection at v2.2.4 passes a configured tunnel's VIPs to `add_gre_tunnel` and `update_gre_tunnel` as `primary_dest_vip` and `secondary_dest_vip`, so VIPs set in a playbook are subject to that replacement. [zia.sdk-python.service-behaviors:ansible-gre-reaches-vip-replacement] The tunnel fields and VIP selection are in [GRE tunnels to ZIA: requirements, bandwidth and deployment](kb:zia.traffic-forwarding.gre).
