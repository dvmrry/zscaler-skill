# PAC file forwarding: limits, versions and what it cannot cover (zia.traffic-forwarding.pac)
Also called: pac file; hosted pac; pac limits; pac versions; last known good; pac vs zcc; explicit proxy pac; kerberos pac
Former IDs: shared-23, shared-24, shared-25

A PAC file points browsers at the service; how that traffic is treated once it arrives is in [Explicit proxy mode: CONNECT and the PAC file](kb:zia.proxy-mode.explicit). A PAC file is a text file that directs the browser to forward traffic to a Public Service Edge; it can exclude destinations (for example intranet sites) so they go direct, and it can be installed per user to cover them outside the corporate network. [zia.traffic-forwarding.pac:what-it-is] PAC files are supported by all major browsers, protect users on and off the corporate network, can be enforced through Active Directory Group Policy for Internet Explorer settings, make exclusions easy, and allow a location when traffic comes from a static public IP; Surrogate IP can be used if the router can use XFF headers and that is enabled at the location. [zia.traffic-forwarding.pac:benefits]

**What it cannot do.** PAC forwarding cannot use features that need a tunnel (Bandwidth Control and Firewall), covers only applications that support PAC files, can be bypassed by end users disabling the file, loses internal IP visibility and sublocation policy unless XFF headers are inserted (group and user policy still apply), and can affect SLAs and performance without GRE or IPSec. [zia.traffic-forwarding.pac:limitations] When PAC-forwarded traffic arrives from an unknown location, features such as the firewall, sublocations and Surrogate IP are unavailable. [zia.traffic-forwarding.pac:unknown-location-limits] PAC-forwarded traffic that goes through a GRE or IPSec tunnel is subject to the tunnel's throughput limit. Government clouds support PAC files only when the proxy traffic is sent through a GRE or IPSec tunnel, not directly over the internet. [zia.traffic-forwarding.pac:over-tunnel] What PAC forwarding carries beyond HTTP and HTTPS is open [gap:zia.traffic-forwarding.pac:non-web-traffic], and client behavior under enforced authentication is open [gap:zia.traffic-forwarding.pac:auth-challenge-behavior]. Authentication behavior is in [SAML and Kerberos: what each needs to work](kb:zia.authentication.methods) and [Requiring authentication per location and sublocation](kb:zia.authentication.location-enforcement).

**Hosting and changes.** Zscaler hosts four default PAC files (recommended.pac, proxy.pac, mobile_proxy.pac, kerberos.pac) that forward all browser traffic to the nearest Public Service Edge. They cannot be edited but can be copied into custom files, and the Kerberos file is recommended when Kerberos authentication is deployed. [zia.traffic-forwarding.pac:default-files] The Internet Explorer, Google Chrome, Mozilla Firefox and Safari PAC articles each say the default PAC file the Zscaler service hosts uses geolocation technology to forward traffic to the nearest Public Service Edge for Internet & SaaS (ZIA), and describe a PAC file as a text file that directs a browser to forward traffic to a proxy server before going to the destination server. [zia.traffic-forwarding.pac:default-geolocation] The Internet Explorer article (example Internet Explorer 20H2, OS Build 19042.1526) has the PAC file URL pasted into the Local Area Network (LAN) Settings window under Use automatic configuration script. The Google Chrome article, whose steps might vary for different versions, opens the system settings: under Windows 7 (example Chrome 53.0.2785.143 m) the Internet Properties window and LAN Settings with Use automatic configuration script, and under Windows 8 or later (example Chrome 96.0.4664.45) the Proxy settings page with Use setup script and the URL pasted into the Script address field. [zia.traffic-forwarding.pac:browser-settings-ie-chrome] The Mozilla Firefox article (example Firefox 94.0.2) has the PAC file URL pasted in the Connection Settings window under Automatic proxy configuration URL. The Safari article (example Safari 11.0.1 (13604.3.5)) has it pasted in the Network window under Automatic Proxy Configuration, and says to restart Safari to enact changes. [zia.traffic-forwarding.pac:browser-settings-firefox-safari] The browser articles' steps name dated example versions [gap:zia.traffic-forwarding.pac:browser-steps-versions]. By default an organization can have 256 PAC files (Support can raise this to 1,024), each up to 256 KB (Support can raise it to 2 MB), with up to 10 versions per file. [zia.traffic-forwarding.pac:limits] A PAC version can be deployed, staged or marked last known good; only one version can be staged at a time and it is served from a different hosted URL than the deployed one, and deployed, staged or last-known-good versions cannot be deleted. The API actions are DEPLOY, STAGE, LKG, UNSTAGE and REMOVE_LKG. [zia.traffic-forwarding.pac:version-states] The request body of the version action differs across sources [divergence:zia.traffic-forwarding.pac:version-action-body]. The console checks PAC syntax with Verify PAC File but still lets a file with errors be saved; the Python SDK validates content before it adds a file. [zia.traffic-forwarding.pac:validation] PAC file changes immediately affect the organization's traffic, so they should be verified and applied in a maintenance window, with a copy of the current file saved first. Staging serves a test version from its own hosted URL, different from the deployed version's. [zia.traffic-forwarding.pac:changes-immediate] Users whose browsers use the deployed PAC URL do not receive a staged version. [zia.traffic-forwarding.pac:staged-not-on-deployed-url] When clients pick up a changed file is open [gap:zia.traffic-forwarding.pac:client-cache], the default hosted URL is open [gap:zia.traffic-forwarding.pac:default-pac-url], and WPAD or MDM delivery is open [gap:zia.traffic-forwarding.pac:delivery-methods].

**Dedicated proxy ports.** When PAC files send traffic to a dedicated proxy port, the file must use the ${GATEWAY_FX} and ${SECONDARY_GATEWAY_FX} variables and not name specific Public Service Edges by host name or IP, so that failover and nearest-edge selection keep working. [zia.traffic-forwarding.pac:dedicated-port-variables] The port service itself is in [Dedicated proxy ports](kb:zia.forwarding-control.proxy-ports).

**Automation.** The Terraform provider has a zia_pac_files resource and data source. [zia.traffic-forwarding.pac:terraform-resource] Creating a file may or may not deploy it [divergence:zia.traffic-forwarding.pac:create-vs-deploy], and the resulting state is open [gap:zia.traffic-forwarding.pac:pac-create-resulting-state]. Go v3.8.46 types the PAC file `lastModifiedBy` as a nullable pointer to the shared ID/name/extensions struct, which has no `externalId` member. The Python PAC model decodes `lastModifiedBy` through the shared `CommonBlocks`, which reads `externalId`, and the Automate response schema for the PAC list includes `externalId` on that object. [zia.traffic-forwarding.pac:go-lastmodifiedby-nullable] Whether tenants populate that `externalId` is open [gap:zia.traffic-forwarding.pac:pac-externalid-populated]. The PAC file source is in [PAC files across Zscaler: where each question is answered](kb:shared.pac-files).

Whether a location is required for PAC traffic is not stated (gap `location-not-required`); what the sources say about unknown sources is in [What a ZIA location is and what the console enforces for it](kb:zia.locations.model).

2. Whether sublocation-scoped rules are expected to match PAC traffic, since PAC forwarding loses sublocation policy unless XFF headers are inserted.
3. Which device-side authentication behavior applies when the location enforces authentication.

Sources disagree (name both sides):
- Request body of the PAC version action (DEPLOY, STAGE, LKG, UNSTAGE, REMOVE_LKG) [divergence:zia.traffic-forwarding.pac:version-action-body]
  - sdk-go: Go v3.8.46 sends the commit message as the raw request body and says serializing an object corrupts the stored commit message.
  - sdk-python: Python builds a dictionary from the keyword fields (including pac_commit_message) and sends it as the JSON object body.
  - api-specs: The Automate operation takes the pacId, pacVersion, pacVersionAction path parameters and an optional newLKGVer query parameter, and declares no request body.
  Impact: Go callers pass only the commit message. The Go change is wrapper behavior, not a reproduced tenant test, so do not infer that Python fails or that the service accepts only one representation.
- Whether creating a PAC file deploys it [divergence:zia.traffic-forwarding.pac:create-vs-deploy]
  - tf-zia: The provider says the service always deploys the initial version, rejects any pac_version_status other than DEPLOYED on create, and sends pacVersionStatus DEPLOYED in the create request.
  - api-specs: The Automate create operation says it only adds a PAC file, which must be transitioned to the Deploy state to be deployed.
  Impact: Whether a created PAC file is live (and affects traffic) immediately is not settled; the provider sentences are local validation and request facts, not proof of backend state.
