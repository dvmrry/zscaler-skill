# Intermediate CA certificates for SSL/TLS inspection: protection types, limits, key types, CSR signing, chain upload and the default (zia.ssl-inspection.intermediate-ca)
Also called: intermediate ca certificates page; ssl intermediate certificate; software protection intermediate ca; cloud hsm protection intermediate ca; sign csr active directory certificate services; default intermediate ca certificate

The Intermediate CA Certificates page (Internet Access > Resources > SSL Intermediate Certificate) manages the custom or default intermediate CA certificate for SSL/TLS Inspection. It lists each Software Protection or Cloud HSM Protection certificate with Name, Protection Type, Region, Validity Start Date, Expiration Date, Description, Key Type and Status (enabled or disabled), and searches by name, protection type, region, key type or status. [zia.ssl-inspection.intermediate-ca:page-and-columns] Zscaler offers subscriptions to software and cloud HSM protection types for configuring intermediate CA certificates for SSL/TLS Inspection, and an organization can subscribe to one or both. [zia.ssl-inspection.intermediate-ca:protection-types] Without the cloud HSM protection subscription, an organization can create up to two software intermediate CA certificates with the enabled status for SSL/TLS Inspection. With both software and cloud HSM subscriptions it can create up to 8 intermediate CA certificates, but only 4 can be enabled at a time and used for interception. [zia.ssl-inspection.intermediate-ca:certificate-limits] There can be only one default intermediate CA certificate, either Zscaler's default intermediate certificate or an enabled custom intermediate CA certificate. The Default Certificate option makes a certificate the default, on the Zscaler Intermediate CA Certificate page and in the Software Protection and Cloud HSM Protection configuration pages. [zia.ssl-inspection.intermediate-ca:one-default] A custom intermediate CA certificate can be edited or deleted and the Zscaler Intermediate CA Certificate can be edited and viewed, but a draft or the default intermediate CA certificate cannot be deleted. [zia.ssl-inspection.intermediate-ca:delete-rules]

**Keys and signing.** On both the Software Protection and Cloud HSM Protection pages the Key Type can be RSA 2048 or EC P-256, and the EC P-256 option is available if Custom Certificate Compliance is enabled for the organization. Key type and size cannot be edited in the step after that choice, and the signature algorithm is set to SHA-256 by default. [zia.ssl-inspection.intermediate-ca:key-type-and-signature] On the Software Protection page the Region is set to Global by default and the Path Length Constraint can be set to 0 or 1. On the Cloud HSM Protection page the admin selects the Region and the Path Length Constraint is set to 0 by default. [zia.ssl-inspection.intermediate-ca:region-and-path-length] For a Cloud HSM Protection certificate the admin can optionally download an attestation bundle, the statement that verifies the private key is generated and protected inside the HSM. [zia.ssl-inspection.intermediate-ca:hsm-attestation] On both the Software Protection and Cloud HSM Protection pages the CSR must be signed as a Subordinate Certification Authority or Intermediate Certification Authority; if OpenSSL is used, basicConstraints=CA:TRUE and keyUsage=keyCertSign, cRLSign must be set during signing; and the intermediate certificate is uploaded in PEM format. [zia.ssl-inspection.intermediate-ca:csr-signing-requirements] Zscaler's Active Directory Certificate Services example signs the CSR as a subordinate or intermediate CA with certreq -submit and the SubCA certificate template; the issued certificate can be saved as a .cer file so long as the admin has domain administrator access permissions, and the Zscaler service only accepts certificates with the .pem extension. [zia.ssl-inspection.intermediate-ca:adcs-signing-example]

**Uploading and replacing.** Uploading the intermediate certificate chain is optional on both the Software Protection and Cloud HSM Protection pages. When it is uploaded the service sends the intermediate root certificate with the chain and the signed server certificate to users' machines; without it the service sends only the organization's intermediate root certificate and its signed server certificate. Zscaler says the chain lets users' machines validate even if browsers hold only the root, and lets certificates be rotated without a new key ceremony or certificate push. [zia.ssl-inspection.intermediate-ca:chain-upload] The Software Protection and Cloud HSM Protection pages both say the organization's root certificate must be installed on users' browsers, and that if an uploaded custom certificate is invalid (for example the common name does not match) the service does not use the Zscaler root certificate and continues to use the previously uploaded self-signed certificate. [zia.ssl-inspection.intermediate-ca:invalid-upload-keeps-previous] On both the Software Protection and Cloud HSM Protection pages the intermediate certificate or the chain of an existing custom certificate can be replaced, provided the new intermediate certificate is not the default certificate and is associated with an SSL/TLS policy. [zia.ssl-inspection.intermediate-ca:replace-certificate] With a custom intermediate certificate the service does not use the organization's root certificate or private keys; it uses the intermediate signed by the organization's own CA, so a trusted CA already deployed on the organization's machines can be used, and the intermediate's validity period can be controlled or the certificate revoked in the Admin Console at any time. [zia.ssl-inspection.intermediate-ca:custom-intermediate-no-root-key]

Who signs the certificate, where the root must be trusted and where the key is stored are in [SSL/TLS inspection certificates: who signs, and where the root must be trusted](kb:zia.ssl-inspection.certificates); a rule chooses its own intermediate in [What an SSL/TLS inspection action does: Inspect, Do Not Inspect, Block and their settings](kb:zia.ssl-inspection.actions). What Custom Certificate Compliance is, which gates the EC P-256 key type, is not described [gap:zia.ssl-inspection.intermediate-ca:custom-certificate-compliance]. How the eight certificates split between the two protection types is not stated [gap:zia.ssl-inspection.intermediate-ca:software-hsm-split]. What an invalid upload falls back to for a tenant with no earlier upload is not stated [gap:zia.ssl-inspection.intermediate-ca:no-previous-upload].
