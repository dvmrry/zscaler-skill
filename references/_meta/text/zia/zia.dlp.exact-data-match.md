# Exact Data Match: index templates, data types, primary and secondary fields, dictionary matching and template processing (zia.dlp.exact-data-match)
Also called: EDM; exact data match; EDM index template; EDM template; primary field; secondary field; EDM with no primary keys

EDM index templates let the Zscaler service identify a record from a structured data source that matches predefined criteria, by identifying and correlating the multiple tokens that contribute to a record to identify ownership of the data. A template is defined in the Index Tool by importing a CSV file and can then be applied to a custom DLP dictionary or engine, which uses the criteria to match against the records; the service then evaluates the EDM-defined DLP rule with the appropriate action for outbound traffic. [zia.dlp.exact-data-match:what-it-is] An organization can create up to 64 EDM templates. The cell usage shown in the Admin Console and the Index Tool helps size a template's data records; in the vendor's example, a CSV file with 40K records of 3 columns each uses 120K cells. The number of records in a template affects how much memory (RAM) to allocate for the Index Tool VM. [zia.dlp.exact-data-match:template-and-cell-limits] The VM that hosts template creation is in [DLP Index Tool: configuration object, VM requirements and deployment notes for VMware, AWS and Azure, SSO and VM commands](kb:zia.dlp.index-tool), and the dictionary kinds that use templates are in [DLP dictionaries: predefined, cloned and custom](kb:zia.dlp.dictionaries).

**The Index Templates page.** The Exact Data Match page lists each template's Template Name (as specified in the Index Tool), VM Name (the VM ID as specified in the Index Tool Configuration), the Number of Cells currently in use by the template, Last Modified and Modified By, and lets an admin view a template's details or delete it. [zia.dlp.exact-data-match:index-templates-page]

**Defining fields.** Each field included in a template takes a data type that should best match the data: in the vendor's example, a field of US-format SSN data such as 123-45-6789 might need the Social Security Number (US) type, not Numeric. For all data types the Index Tool removes leading and trailing spaces in the data after submission. The supported types include Alphabetical, Alphanumeric, Email Address, Multi-Alphanumeric Identity, Multiple Alphanumeric, Multi-Word Alphabetical, Numeric, Credit Card Numbers and Social Security Number (US). [zia.dlp.exact-data-match:data-type-selection] Alphabetical, Alphanumeric and Numeric data must include at least three characters. If selected as a primary field, Alphabetical data cannot be longer than 24 characters, and Alphanumeric and Numeric data can include up to 8 separate variable lengths and cannot be longer than 24 characters. [zia.dlp.exact-data-match:type-length-limits] Multi-Alphanumeric Identity is any combination of at most 4 alphanumeric character groupings, each of at least three alphanumeric characters; on upload the strings are normalized and a match occurs only if all of the data appears in the same order as the normalized character grouping, and a field of this type can be a primary field. Multiple Alphanumeric can match even if the data does not appear in the same order, cannot be a primary field, and Zscaler recommends Multi-Alphanumeric Identity instead. Multi-Word Alphabetical is any combination of at most 4 words and three spaces and cannot be a primary field. [zia.dlp.exact-data-match:multi-token-types] For credit card numbers without the popular format check, the Index Tool performs a Luhn check on the data after submission. The Email Address type follows the RFC 5321 syntax definition but does not support international (UTF-8) email addresses. A Brazilian CPF number in the dotted format "401.757.431-93" does not match, because '.' (dot) is an EDM numeric delimiter. [zia.dlp.exact-data-match:type-format-notes] A template must have at least one and no more than two primary fields, and a primary field must be unique for the selected data type. The primary field is a unique key that DLP policy rules are based on and is required unless EDM is configured to work without primary or secondary fields; it can be a recognized standard format of variable length (for example credit card numbers) or a custom format of fixed length (for example alphabetical values). [zia.dlp.exact-data-match:primary-fields]

**How a dictionary matches.** Before EDM fields can be added to a custom dictionary, an EDM index template that defines the data must be created and submitted. The dictionary selects a Data Template, a Primary Field to match against when scanning content and any Secondary Fields to match if the dictionary detects a valid match for the Primary Field; a primary field not selected in the first step appears as a Secondary Field option. Secondary Match On is None (primary field only), Match at Least 1 from Secondary Fields, Match at Least 2 from Secondary Fields or All Fields, and Add Template applies fields from another EDM template to the same dictionary. [zia.dlp.exact-data-match:dictionary-fields] The service assumes AND between the Primary Field and the Secondary Fields; for Secondary Match On, the "Any" options (Match at Least 1 and Match at Least 2 from Secondary Fields) assume OR and "All" (All Fields) assumes AND. In the vendor's examples, a definition is evaluated as "SSN AND (FName AND LName)" and as "CCN AND (FName OR LName)". [zia.dlp.exact-data-match:boolean-semantics] When evaluating data records, the service evaluates only strings of three or more characters and ignores blank cells; it does not consider blank cells to be implicit matches. In the vendor's example of a definition that needs the primary field and at least one secondary field, the match does not occur if the secondary field is blank. [zia.dlp.exact-data-match:short-strings-and-blanks] For reporting, the service provides a total matchCount and the triggers that help determine that count. The total matchCount logic is based on the number of unique sets of matches found in the content, and also applies to multiple templates used in the same dictionary. [zia.dlp.exact-data-match:match-count-reporting]

**Submitting and updating a template.** The service's processing of a template checks it for data errors, primary field duplication errors and communication errors. If it finds none, a status of Completed is shown for the template in the Index Tool and the template is available in the Admin Console; if it finds issues, an error status is shown in the Index Tool. The Template Details page shows the process details for a template. [zia.dlp.exact-data-match:processing-and-status] The vendor's examples use a limit of 512 duplicate primary keys for an individual EDM template and 2,048 across multiple EDM templates. In the examples, a template over its limit receives an error status in the Index Tool with Too many primary key duplicates as the error type. In the example of duplicates exceeded across multiple templates using a single field, EDM Template 6 receives an error status with a primary key limit error type and an EDM Indexing Failed Schemas notification naming it appears in the Admin Console's Notification pane; correcting it means analyzing the templates that preceded it as well as that one. [zia.dlp.exact-data-match:duplicate-key-limits] After creation a template's name cannot be changed, and its included fields and selected primary fields cannot be updated; changing them requires a new template. The page says the data types, included fields and primary fields originally selected are not updated and a new template must be created to modify them, and that the ability to edit a template becomes available only if there was an error when the data was originally submitted, when the data types and selected fields can be modified. [zia.dlp.exact-data-match:template-immutability-and-resubmit] After a template is uploaded successfully, regular updates can be scheduled and an Alert can be requested for missed updates. The schedule has a File Path (populated with the upload location, where the file must still be), a Status of Enable or Disable, a Repeat of Monthly, Weekly or Daily, a time (At), a Time Zone and an Update Now option. Monthly index updates are converted to and trigger in UTC and are skipped in a month that does not contain the converted date; Zscaler recommends scheduling monthly updates between the 2nd and the 27th. [zia.dlp.exact-data-match:scheduled-updates]

**DLP Advanced Settings modes.** EDM uses index templates with primary and secondary fields by default. With EDM with No Primary Keys enabled, an admin selects the fields from the template that must match, the fields that are optional and how many optional fields are required to match, and the Index Tool needs no primary or secondary fields; all existing EDM schema (templates, dictionaries, engines and policies) must be deleted or unassigned before enabling it, and new schema with this functionality can be created after it is enabled. A DLP EDM dictionary created with no primary keys enabled must select at least one of Fields that must Match On or Optional Fields to Match On. [zia.dlp.exact-data-match:no-primary-keys-mode] The DLP Advanced Settings page says that with Enable EDM Check for Popular Formats enabled, EDM scans SSN, SIN and CCN dictionaries for a popular format, and the EDM match succeeds only if the entered format matches the popular data format type. The same page says that for Fields that must Match On, the data type (for example SSN, CCN or CSIN) is specified as the primary field and Name as the second field. For Social Security Number (US) the template page gives a separate "With popular format check" format, which is a 9-digit number separated in parts by a delimiter (hyphen or space) or not separated at all, and a number not in the popular format is not supported. [zia.dlp.exact-data-match:popular-format-check] Which data types the popular-format check covers differs between the two pages [divergence:zia.dlp.exact-data-match:popular-format-coverage]. The Advanced Settings page itself is covered under [Why DLP did or did not fire: pipeline position, evaluation mode and exemptions](kb:zia.dlp.evaluation).

What to check:
1. Whether the template's data records have strings of at least three characters, and whether blank cells are being relied on to match.
2. Whether the tenant uses EDM with No Primary Keys or the popular-format check, read before reasoning about which fields a dictionary must match.
