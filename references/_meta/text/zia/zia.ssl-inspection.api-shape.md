# SSL/TLS inspection rule wire format: the nested action object, tokens and casing (zia.ssl-inspection.api-shape)
Also called: ssl inspection action object; decryptSubActions; doNotDecryptSubActions; PASS_THRU; showEUN; ssl rule jq; ssl inspection mcp tool; ssl rule validation

Reading or writing SSL rules programmatically starts with the shape of `action`, because one string in the console is a nested object on the wire. In the API response schema an SSL rule's `action` is a required nested object, not a string: `type` is `DECRYPT`, `DO_NOT_DECRYPT` or `BLOCK`, and the object carries `decryptSubActions`, `doNotDecryptSubActions`, `overrideDefaultCertificate`, `showEUN`, `showEUNATP` and `sslInterceptionCert`. [zia.ssl-inspection.api-shape:action-nested-required] The console's Inspect is `DECRYPT`, Do Not Inspect is `DO_NOT_DECRYPT`, and Evaluate versus Bypass Other Policies is `doNotDecryptSubActions.bypassOtherPolicies` false or true; Block is `BLOCK`. [zia.ssl-inspection.api-shape:console-to-api-mapping]

**What goes in each block.** `decryptSubActions` holds `serverCertificates`, `ocspCheck`, `blockSslTrafficWithNoSniEnabled`, `minClientTLSVersion`, `minServerTLSVersion`, `blockUndecrypt` and `http2Enabled`, in camelCase on the wire. Client and server TLS floors are separate fields. [zia.ssl-inspection.api-shape:decrypt-fields] `doNotDecryptSubActions` holds `bypassOtherPolicies`, `serverCertificates`, `ocspCheck`, `blockSslTrafficWithNoSniEnabled` and `minTLSVersion`. [zia.ssl-inspection.api-shape:dnd-fields] Which block you send must match `type`: a sub-action block under the wrong `type` is rejected by the Go SDK before any request (see the validator in [ZIA Go SDK service functions that return wrong results, mutate inputs, or reject valid input](kb:zia.sdk-go.service-defects)), and "why isn't my TLS floor enforced?" starts with checking `type`, then that the matching block is the one set.

**Tokens.** `serverCertificates` takes `ALLOW`, `BLOCK` or `PASS_THRU` under `decryptSubActions`, but only `ALLOW` or `BLOCK` under `doNotDecryptSubActions`. [zia.ssl-inspection.api-shape:server-certificates-tokens] The console's Pass Through option is the token `PASS_THRU`, so a filter on `PASSTHROUGH` never matches. [zia.ssl-inspection.api-shape:pass-thru-console-name] TLS floors are enumerated tokens: `minClientTLSVersion` takes `CLIENT_TLS_1_0` to `CLIENT_TLS_1_3`, while `minServerTLSVersion` and the Do Not Inspect `minTLSVersion` take `SERVER_TLS_1_0` to `SERVER_TLS_1_3`. [zia.ssl-inspection.api-shape:tls-version-tokens]

**Validator rules not recorded elsewhere.** The required-field and bypass-exclusion rules are in [ZIA Go SDK service functions that return wrong results, mutate inputs, or reject valid input](kb:zia.sdk-go.service-defects); the Terraform plan-time checks are there too. Beyond the required-field rules recorded in the SDK defects, the Go validator also rejects a `DECRYPT` rule that sets `showEUN` or `showEUNATP`, a `BLOCK` rule that carries either sub-action block or sets `showEUNATP`, and a `DECRYPT` or `BLOCK` rule with `overrideDefaultCertificate` false that attaches `sslInterceptionCert`. [zia.ssl-inspection.api-shape:go-validator-block-and-cert-rules] The Python SSL inspection `add_rule` assigns `body = kwargs`, turns `enabled` into `state`, rewrites the common ID fields with `transform_common_id_fields` and passes that body to `create_request`. [zia.ssl-inspection.api-shape:python-no-client-validation] So the Python SDK checks no action combination before sending: a `decryptSubActions` block on a `DO_NOT_DECRYPT` rule, or a combination the Go validator rejects such as a sub-action block on a `BLOCK` rule, reaches the API as the caller wrote it. [zia.ssl-inspection.api-shape:python-action-combinations-unchecked]

**Casing.** The Python SDK takes snake_case keyword arguments and camelCases the whole request body before sending; an explicit exception table makes `show_eun`, `show_eunatp`, `min_tls_version`, `min_client_tls_version` and `min_server_tls_version` become the contract spellings. [zia.ssl-inspection.api-shape:python-kwargs-casing] The contract spells the notification flags `showEUN` and `showEUNATP`, and the Python SDK emits exactly those on writes; its model accepts several alternate spellings when parsing, a sign that an SDK key-conversion step has been in the path. [zia.ssl-inspection.api-shape:eun-casing]

**Reading through MCP.** The MCP list and get tools for SSL inspection rules return the SDK model converted with `as_dict()` and passed through `shape_many`/`shape_one`, which never drop attributes, so the nested `action` and its sub-action blocks are present whenever the SDK supplies them. [zia.ssl-inspection.api-shape:mcp-full-records] The MCP server declares no fixed output schema for ordinary API records, because the set of attributes a resource carries is owned by the API. [zia.ssl-inspection.api-shape:mcp-no-output-schema] The SSL rule list tool takes no filter arguments because the API offers neither server-side search nor pagination; the MCP bridge adds an optional JMESPath `query` that filters client-side after the API call, and its keys are the returned records' keys, usually snake_case even where the API documents camelCase. [zia.ssl-inspection.api-shape:mcp-list-query]

The meaning of each setting is in [What an SSL/TLS inspection action does: Inspect, Do Not Inspect, Block and their settings](kb:zia.ssl-inspection.actions). Predefined and default rule flags, and what to strip on a PUT, are in [SSL/TLS inspection rule order, predefined and default rules, limits](kb:zia.ssl-inspection.rules).
