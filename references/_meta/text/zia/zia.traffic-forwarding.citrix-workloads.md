# Forwarding Citrix XenDesktop and XenApp workloads to ZIA (zia.traffic-forwarding.citrix-workloads)
Also called: citrix xendesktop zscaler; citrix xenapp zscaler; hosted shared desktops; citrix virtual apps; citrix vdi zscaler

Traffic from Citrix workloads can be forwarded to Internet & SaaS with GRE or IPSec tunnels, PAC files or Zscaler Client Connector, though in some situations an option might not be feasible or must be configured in a certain way. For tunnels, the XenDesktop page and the XenApp and Hosted Shared Desktops page each say they can be treated like any Windows user device going through Internet & SaaS, and that likely only a sublocation for these workloads is needed. [zia.traffic-forwarding.citrix-workloads:methods]

**PAC files and SSL/TLS Inspection.** On both the XenDesktop and the XenApp and Hosted Shared Desktops pages, the Zscaler authentication cookies must be retained across sessions; the XenDesktop page adds that this way a user does not need to reauthenticate each time they launch a new desktop. Both pages say that if needed the Zscaler root certificate can be deployed centrally to the Citrix master images or via GPO as for any other domain-joined machine. [zia.traffic-forwarding.citrix-workloads:pac-and-ssl]

**XenDesktop.** XenDesktop workloads are typically Windows client operating systems, and for them the page says Client Connector, given its enrollment process, only works well with a dedicated VDI and does not support multiple simultaneous user sessions from a single host operating system. With non-persistent VDIs, where users get fresh desktops each time, users must re-enroll each time, which might quickly reach the limit of 16 devices per user; the page says to configure Device Cleanup in the Admin Console to remove the oldest enrolled device. [zia.traffic-forwarding.citrix-workloads:xendesktop-zcc] On XenDesktop each user has a one-to-one mapping with a virtual desktop, so IP Surrogacy can bind a username to an internal IP for transactions that would normally show only the Internet & SaaS location name; the page says the threshold should typically be much lower than on normal device networks, such as only a few hours. [zia.traffic-forwarding.citrix-workloads:xendesktop-surrogate] Device Cleanup is in [Automated device cleanup: device threshold, inactive removal, permanent deletion](kb:zcc.devices.cleanup).

**XenApp and Hosted Shared Desktops.** XenApp and Hosted Shared Desktop workloads are typically Windows Servers. Client Connector currently supports Windows client operating systems and is not supported with Virtual Apps and Hosted Shared Desktops, because Zscaler does not support concurrent user sessions on a device with Client Connector installed: it establishes a single Internet & SaaS tunnel from the first enrolled Windows user session, and concurrently connected users on the server can enroll but their Internet & SaaS and Private Access tunnels fail. IP Surrogacy needs to be disabled for the sublocation containing the XenApp workloads, because all users on the server share one source IP address, so with user authentication enabled it can flip between users and eventually stop working. [zia.traffic-forwarding.citrix-workloads:xenapp] How surrogate IP maps users is in [Surrogate IP: mapping a private IP to an authenticated user](kb:zia.authentication.surrogate-ip).

What to check:
1. Whether the workload is a dedicated desktop (XenDesktop) or a shared server (XenApp or Hosted Shared Desktops) before choosing Client Connector or setting IP Surrogacy.
