# What a DNS Control rule can match on (zia.dns-control.criteria)
Also called: dns control criteria; dns rule conditions; dns record types; dns request types rule; resolved ip location

DNS Control rules can use conditions such as users, groups, or departments, client locations, categorization of domains and IP addresses, DNS record types, and the location of resolved IPs. [zia.dns-control.criteria:condition-list] A DNS rule scopes by identity, location and time through the array fields `users`, `groups`, `departments`, `locations`, `locationGroups` and `timeWindows`, and carries its rule labels in `labels`. [zia.dns-control.criteria:scope-reference-fields] The DNS Application conditions include DNS Tunnels & Network Apps, DNS Application Group, Resolved IP-Based Countries (destination identified by server location), Request/Response Categories (URL and TLD categories), DNS Request Type, Protocols, and endpoint application conditions. [zia.dns-control.criteria:console-dns-conditions] Rule conditions are grouped into categories (Who/Where/When, Source IP, Destination/Resolved IPs, DNS Application); categories combine with AND, and each category has its own AND/OR operators inside. [zia.dns-control.criteria:condition-logic] A condition left at its default (Any) is ignored during policy evaluation. [zia.dns-control.criteria:unset-ignored] A rule can select up to 32 users, 32 groups, 32 departments, 32 locations and 32 location groups; Zscaler Support can raise the limits for users, groups, departments and locations. [zia.dns-control.criteria:limits-32]

The rule resource carries the DNS request types the rule applies to in `dnsRuleRequestTypes`. [zia.dns-control.criteria:request-types-field] The DNS Insights Logs article says the HTTPS DNS resource record type must be blocked to stop Encrypted Client Hello (ECH) and prevent unmanaged encrypted traffic flows through the secure web gateway. [zia.dns-control.criteria:https-rr-ech] The rule resource carries a list of IP categories in `resCategories`; the SDK comment calls it destination IP categories. [zia.dns-control.criteria:res-categories-field] The mapping between the console's resolved-IP conditions and those fields is open [gap:zia.dns-control.criteria:resolved-ip-field-mapping]. Whether identity criteria need Advanced Firewall is open [gap:zia.dns-control.criteria:advanced-firewall-criteria].

DNS requests and responses are categorized into predefined super categories divided into specific categories. Zscaler provides a set of immutable test FQDNs for DNS request categories and for DNS tunnels and network apps that can be used to validate DNS Control policies; these test domains resolve to Google, and errors might occur when accessing them through a browser. [zia.dns-control.criteria:test-domains] What a matching rule does is in [DNS Control actions and what each API action requires](kb:zia.dns-control.actions); domain classification for newly registered domains is in [Newly registered domains and classification delay in DNS Control](kb:zia.dns-control.nrod); tunnels as a matchable item are in [DNS tunnel detection](kb:zia.dns-control.tunnel-detection).

What to check:
1. Whether a console condition is inferred from a field name, since the mapping between them is open.
2. Whether a condition left at Any is set on purpose, since it is ignored during evaluation.
3. Whether identity criteria need Advanced Firewall for this rule, which is untested.

Not known (open gaps):
- Which rule fields implement 'categorization of IP addresses' and 'location of resolved IPs' [gap:zia.dns-control.criteria:resolved-ip-field-mapping]: settled by lab-test or tenant-data. Blocks: saying which API field a console 'resolved IP' condition corresponds to
- Which identity criteria require Advanced Firewall [gap:zia.dns-control.criteria:advanced-firewall-criteria]: settled by support-ticket or lab-test. Blocks: saying whether users, groups and departments work on an Essential-tier tenant
