# The Virtual Service Edge cluster: limits, object, build order and Location binding (zia.virtual-service-edge.clusters)
Also called: vse cluster; virtual service edge cluster; vse cluster ip; vse standalone; vse cluster size; vse cluster subscription; vse ipsec local termination; vse remove node; disable vse cluster
Former IDs: zia-34, zia-36, zia-38

**What counts as production.** For production, a Virtual Service Edge is deployed in a cluster. A cluster requires at least two Virtual Service Edges for active-active redundancy and load balancing, which provides N+1 redundancy for production. [zia.virtual-service-edge.clusters:production-needs-cluster] A Virtual Service Edge in standalone mode, which does not support failover, is for evaluation with test traffic. Zscaler does not support standalone Virtual Service Edges for production environments with live user traffic. [zia.virtual-service-edge.clusters:standalone-for-evaluation-only] A Virtual Service Edge cluster can contain a maximum of 16 Virtual Service Edge instances. [zia.virtual-service-edge.clusters:max-16-instances] Each Virtual Service Edge in a cluster requires a separate Virtual Service Edge subscription, and all Virtual Service Edges in a cluster must have the Large subscription type. [zia.virtual-service-edge.clusters:subscription-per-instance] Budget the subscriptions before the VMs: a cluster of N instances is N subscriptions, all of the Large type. Only some platforms can create one at all ([Where a Virtual Service Edge runs and which platforms can cluster](kb:zia.virtual-service-edge.platforms)).

**The object.** A cluster is defined by a name, an enabled or disabled status (enabled by default), the Virtual Service Edge instances it includes, IPSec Local Termination, a cluster IP address, a subnet mask and a default gateway. [zia.virtual-service-edge.clusters:cluster-fields] The cluster IP address provides fault tolerance and listens for user traffic; the interface does not explicitly get an IP address, and the cluster IP address must be in the same VLAN as the proxy and load balancer IP addresses. The cluster, proxy, load balancer and gateway addresses must be in the same subnet. [zia.virtual-service-edge.clusters:cluster-ip-same-vlan] IPSec Local Termination, off by default, terminates client IPSec traffic at the selected Virtual Service Edge instances of the cluster. For an instance in Cluster deployment mode the instance-level option is read-only and shows the actual status; it is changed on the Virtual Service Edge Clusters page. [zia.virtual-service-edge.clusters:ipsec-local-termination] Field names and API behavior are in [The vZEN API: Virtual Service Edge clusters and nodes](kb:zia.virtual-service-edge.api-surface). The addresses behind these fields are in [Addresses, interfaces, outbound connectivity and ports for a Virtual Service Edge](kb:zia.virtual-service-edge.network-requirements).

**Build order.** A cluster is built by creating at least two Virtual Service Edge instances and downloading each one's SSL certificate (each VM needs its own unique certificate), downloading the VMs, adding the cluster, binding it to a Location, adding a Firewall Filtering rule that allows the Virtual Service Edge addresses, and then configuring each VM. [zia.virtual-service-edge.clusters:build-order] A Virtual Service Edge cluster, or a standalone Virtual Service Edge, is bound to a Location so the organization can enable authentication, firewall, SSL/TLS inspection and location-level policies; the service associates the traffic the Virtual Service Edge receives with that Location and applies its policies. [zia.virtual-service-edge.clusters:bind-to-location] The Location itself is [What a ZIA location is and what the console enforces for it](kb:zia.locations.model); unlike the hardware form factor, this binding is self-service and needs no Support ticket in the captured procedure (compare [Binding a Private Service Edge cluster to a Location, and the open-proxy hazard](kb:zia.private-service-edge.location-binding)).

**Health.** The load balancer sends ICMP and HTTP probes to the Virtual Service Edge to monitor its health and ensure traffic is distributed appropriately. [zia.virtual-service-edge.clusters:health-probes-icmp-http] A Virtual Service Edge that fails the load balancer's health probes stops receiving traffic and the remaining members absorb the load. [zia.virtual-service-edge.clusters:unhealthy-member-removed] Probes only work if the firewall lets them through, which is why the build order includes a Firewall Filtering rule: [How a Virtual Service Edge cluster spreads and returns traffic](kb:zia.virtual-service-edge.load-balancing).

**What is not documented.** Which settings are cluster-level versus per-VM ([Which settings are cluster-scoped and which are per VM](kb:zia.virtual-service-edge.clusters:cluster-vs-vm-settings)), what removing a member or disabling the cluster does to live sessions ([What removing a VM from, or disabling, a cluster does to live traffic](kb:zia.virtual-service-edge.clusters:removal-and-disable-behavior)), and what the cluster object means on public cloud ([Whether the cluster object means anything on Azure, AWS and GCP](kb:zia.virtual-service-edge.clusters:public-cloud-cluster-object)). Whether disabling a cluster is a safe maintenance path is open [gap:zia.virtual-service-edge.clusters:removal-and-disable-behavior]. Upgrade sequencing, by contrast, is documented: [How Virtual Service Edges and their clusters upgrade](kb:zia.virtual-service-edge.upgrades).
