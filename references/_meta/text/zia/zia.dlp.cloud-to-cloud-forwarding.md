# Cloud-to-Cloud Incident Forwarding: storage onboarding for AWS, Google Cloud and Azure (zia.dlp.cloud-to-cloud-forwarding)
Also called: cloud-to-cloud incident forwarding; c2c incident forwarding; c2c incident receiver; dlp incident forwarding to s3; dlp evidence bucket; Zscaler_GCP_SMIR_Role; zscaler connector user arn

Cloud-to-Cloud Incident Forwarding sends information about transactions that violate DLP policy rules directly to public cloud storage accounts defined in the Admin Console, without deploying appliances. The storage accounts are set up first, and DLP policy rules are then configured to use it. [zia.dlp.cloud-to-cloud-forwarding:what-it-is] A Cloud-to-Cloud Incident Forwarding configuration has a configuration name, a cloud storage tenant name, the SaaS application that hosts the public cloud storage, a bucket name for evidence, a bucket name for metadata JSON, and a status that shows whether it is enabled or disabled. [zia.dlp.cloud-to-cloud-forwarding:config-fields] How a rule selects it and its API surface are in [Where a DLP match goes: notification, ICAP, Incident Receiver and Cloud-to-Cloud](kb:zia.dlp.incident-forwarding).

**Across the three providers.** The SaaS Application Provider chosen when configuring Cloud-to-Cloud Incident Forwarding is Amazon S3 for AWS, Google Cloud Platform for Google Cloud and Microsoft Azure for Azure. [zia.dlp.cloud-to-cloud-forwarding:providers] The AWS, Google Cloud and Azure pages each say Cloud-to-Cloud Incident Forwarding does not support using the same public cloud account to onboard multiple tenants hosted on the same Zscaler cloud. The AWS page's example is that pre-production and production tenants hosted on the same Zscaler cloud cannot use the same Azure account to onboard both, and all three pages say that to use the same Azure account each tenant must be hosted on a separate Zscaler cloud. [zia.dlp.cloud-to-cloud-forwarding:one-account-per-cloud] Each provider page creates one bucket or container for evidence data and one for metadata, named <bucketNamePrefix>-data and <bucketNamePrefix>-metadata, and the pages say no periods can be used in the name. [zia.dlp.cloud-to-cloud-forwarding:two-buckets-naming]

**AWS.** On the AWS page, in the Block Public Access settings for this bucket section, the Block all public access checkbox is selected. When the AWS storage account is configured with Workflow Automation, two separate S3 buckets are created during the creation of the CloudFormation stack in AWS, and when the Incident Receiver is not used with Workflow Automation, a single S3 bucket can hold data and JSON files or separate buckets can be used. [zia.dlp.cloud-to-cloud-forwarding:aws-buckets] AWS authorization uses the Zscaler Connector Account Number, Zscaler Connector User ARN and External ID from the Admin Console. The IAM role is created for Another AWS account with Require external ID checked and no permissions policy attached, an inline policy grants s3:ListBucket on both buckets and s3:PutObject on each bucket's /* resource, and the trust policy's Principal AWS is the Zscaler Connector User ARN with sts:AssumeRole conditioned on sts:ExternalId. The Role ARN is entered in the Admin Console when registering the SaaS application. [zia.dlp.cloud-to-cloud-forwarding:aws-iam-trust] When using Workflow Automation and KMS keys, the AWS page gives an alternative JSON string whose Action is kms:Decrypt and kms:GenerateDataKey* and whose Resource is the bucket KMS key ARN. [zia.dlp.cloud-to-cloud-forwarding:aws-kms-variant] Registering the AWS storage in the Admin Console takes the AWS Account ID and the IAM Role ARN of the role just created, and the region must match the region the created bucket is in. [zia.dlp.cloud-to-cloud-forwarding:aws-registration-fields] The KMS sample on the AWS page is malformed [gap:zia.dlp.cloud-to-cloud-forwarding:vendor-defects].

**Google Cloud.** Google Cloud onboarding has an Enterprise ID step that takes the Google Cloud Admin Email ID used to log in to the Google Admin console. If the Google Cloud Platform account is already used with Workflow Automation, the necessary resources were already created when the DLP Application Integration was configured. [zia.dlp.cloud-to-cloud-forwarding:gcp-enterprise-id] The Google Cloud page gives a custom role titled Zscaler_GCP_SMIR_Role with the permissions storage.objects.create, storage.multipartUploads.create and storage.objects.delete, and says to use the role name exactly as provided without modifying or renaming it. An Organization-level role can be granted to resources in any project of the organization and is recommended if the role may be needed in other projects, while a Project-level role is confined to a single project and is recommended for more scoped access. [zia.dlp.cloud-to-cloud-forwarding:gcp-custom-role] The role and file names the page uses differ [divergence:zia.dlp.cloud-to-cloud-forwarding:gcp-role-names]. On the Google Cloud page the service account is created without granting access or permissions to the project, and its private key is downloaded as a JSON key because it is required later for fetching the OAuth token. The service account must be added as an IAM member in the organization set up for storage scan, the remaining steps must be completed for the Metadata JSON bucket as well, and the Cloud Storage API is enabled with gcloud services enable storage.googleapis.com. [zia.dlp.cloud-to-cloud-forwarding:gcp-service-account] On the Google Cloud page the Admin Console step selects the type of SaaS Connector, and a later step enters the Organization ID and uploads the Private Key JSON file downloaded when creating a service account. [zia.dlp.cloud-to-cloud-forwarding:gcp-connector-types]

**Microsoft Azure.** The Azure page says the storage account must be accessible to the necessary IP addresses, set under Security + networking > Networking, and points to Zscaler Hub IP Addresses to learn which IP addresses to connect to. [zia.dlp.cloud-to-cloud-forwarding:azure-storage] On the Azure page, the admin clicks Provide Admin Credentials and signs in with Microsoft Azure account credentials, copies the application name matching the Zscaler SaaS Connector ID, and adds it as a member to Storage Blob Data Contributor and Storage Account Contributor. [zia.dlp.cloud-to-cloud-forwarding:azure-zscaler-defined] For the Azure Custom connector the app registration's supported account types must be Accounts in any organizational directory (Any Microsoft Entra ID tenant - Multitenant), and the Application (client) ID and Directory (tenant) ID from the Overview page are saved for the Admin Console. The app needs two permissions, Azure Storage and Azure Service Management, each mapping to the user_impersonation permission. The Admin Console Add page asks for an Application Type: one path enters the Client ID, Client Secret and Tenant ID, and another uploads the Private Key Certificate File and enters the Client ID and Tenant ID. For the private key, the page's file table lists private_key.pem as an AES-256 encrypted RSA private key, certificate.pem as a self-signed certificate to upload on the Azure portal, and combined.pem as the combined key and certificate to upload on the Internet & SaaS onboarding page. A bucket name is entered as the container URL https://<storage_account>.blob.core.windows.net/<container_name>. [zia.dlp.cloud-to-cloud-forwarding:azure-custom-connector] Which roles the Custom connector needs is unclear [divergence:zia.dlp.cloud-to-cloud-forwarding:azure-role-assignment]. Azure onboarding has an optional Workflow Automation checkbox. If the Azure application tenant is onboarded for Workflow Automation and a private key is used, a new DLP Azure integration in disabled state is automatically added in Workflow Automation. [zia.dlp.cloud-to-cloud-forwarding:azure-zwa]

Sources disagree (name both sides):
- The Google Cloud page names the role and its file differently in different steps. [divergence:zia.dlp.cloud-to-cloud-forwarding:gcp-role-names]
  - zscaler-help: The role file is created as Zscaler_GCP_SMIR_role.yaml.
  - zscaler-help: The create command reads the file zscaler_readwrite_role.yaml.
  - zscaler-help: The bucket grant selects a custom role named Zscaler_ReadWrite_Role.
  Impact: The page says to use the role name exactly as provided, but the file and role names it gives differ between steps, so which name the role should carry is not settled by the page.
- The Zscaler Defined path adds the application to two roles, while the Custom path's steps search for one role and add the application to the other. [divergence:zia.dlp.cloud-to-cloud-forwarding:azure-role-assignment]
  - zscaler-help: The Zscaler Defined connector's application is added as a member to Storage Blob Data Contributor and Storage Account Contributor.
  - zscaler-help: The Custom connector steps search for and select Storage Account Contributor.
  - zscaler-help: The same Custom connector steps then add the application as a member to Storage Blob Data Contributor only.
  Impact: Whether the Custom connector needs both roles, as the Zscaler Defined path assigns, or only one is not clear from the page.
