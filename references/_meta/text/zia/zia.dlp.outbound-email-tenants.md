# Outbound Email DLP email tenants and mail-server setup (SEG, Gmail, Exchange) (zia.dlp.outbound-email-tenants)
Also called: email tenant; email tenants; key for transport rules; smart host fqdn; X-Zscaler-TenantID

An email tenant is the Outbound Email DLP object that makes the Zscaler service the smart host for the organization's outbound email. Email tenants let the Zscaler service act as a smart host for inspecting email content sent to external domains as part of outbound email policy rules. Adding a tenant is the first step in setting up an outbound email policy, tenants can be included in or excluded from rules, and editing one carries over to every setting that uses it. [zia.dlp.outbound-email-tenants:what-tenants-are] A tenant's email service provider is a Secure Email Gateway, Gmail or Exchange. A SEG tenant (for example Mimecast or Cisco IronPort) can be onboarded, and once onboarded on the Email Tenants page it can be selected when creating outbound email policy rules. [zia.dlp.outbound-email-tenants:providers] The tenant name must be unique. Under Email Tenant Security Options, Outbound Email Security is selected automatically and is not configurable. The Workflow Automation option is available for Exchange only (Exchange Online), lets admins review and manage quarantined emails from Workflow Automation, and makes the Authorize the SaaS Application and Assign Role sections available. [zia.dlp.outbound-email-tenants:security-options] The tenant page shows the Smart Host FQDN and the Key for Transport Rules. The key is unique to each email tenant and the service uses it to verify the source of email messages received by the Zscaler smart host. [zia.dlp.outbound-email-tenants:configuration-info] The Next Hop Address is where the service sends email content after inspection and can be an IPv4 address, an IPv6 address or a valid domain name, with a port number for the email domain. The page's examples are port 587 for the SEG and Gmail tenants and 25 for Exchange, and Gmail's next hop address is smtp-relay.gmail.com. [zia.dlp.outbound-email-tenants:next-hop-address] For next-hop validation, the service strictly enforces SSL/TLS for secure SMTP connections. It requires the presented server certificate to be valid and trusted and does not allow self-signed, expired or otherwise invalid certificates. [zia.dlp.outbound-email-tenants:next-hop-tls] The Editing Email Tenants page lists strictly enforcing SSL/TLS for secure SMTP connections, a server certificate validation that requires the presented certificate to be valid and trusted, and not allowing self-signed, expired or otherwise invalid certificates; it also says the tenants being edited are used as part of the mail flow rules configured on the email server. [zia.dlp.outbound-email-tenants:edit-page-next-hop-validation] The rules that use tenants are in [Outbound Email DLP policy: smart host flow, per-recipient evaluation, criteria and header actions](kb:zia.dlp.outbound-email-policy).

**Secure email gateway.** A SEG tenant must be onboarded in the Admin Console before the SEG is configured, and the basic configuration process and workflow is the same across SEG products. The email server routes outbound email to the SEG, the SEG routes it to the smart host, the smart host adds a verdict header (for example X-Zscaler-Block or X-Zscaler-Quarantine) and sends it back to the SEG as the configured next hop, and the SEG applies its policy based on the header. [zia.dlp.outbound-email-tenants:seg-flow] For a SEG tenant, the service uses the source IP address of the incoming connection to determine the next hop for explicitly configured domains. Domains not configured explicitly are default domains; if Default domain is selected the source IP maps messages to the next hop servers, and for this routing the SEG must include the X-Zscaler-TenantID: <tenant-key> header in messages sent to the smart host. [zia.dlp.outbound-email-tenants:seg-domain-routing] The Client Certificate Common Name field does not support wildcard characters for subdomain matching, but if the connecting client has a wildcard certificate, the configured common name should match it exactly, including the wildcard characters. [zia.dlp.outbound-email-tenants:client-cert-cn] The Source IP Allow list takes the IP addresses allowed to send SMTP traffic, in CIDR form in the page's example (10.20.30.0/24 allows traffic originating from 10.20.30.0 to 10.20.30.255). [zia.dlp.outbound-email-tenants:source-ip-allow-list] The SEG is configured to add X-Zscaler-TenantID: <tenant-key> on messages routed to Zscaler, and to accept processed email from the smart host by allowlisting the smart host egress IPs or validating the client certificate Common Name presented by Zscaler. The page says this ensures only authorized smart host connections can relay scanned emails back to the SEG. [zia.dlp.outbound-email-tenants:seg-tenant-header-and-accept] The SEG article says the service appends one of three headers to each outbound email: X-Zscaler-Block: 0, which the SEG should deliver; X-Zscaler-Block: 1, which it should block; or X-Zscaler-Quarantine: 1, which it should quarantine. The SEG should use the headers to detect messages already processed, to prevent mail routing loops, and a rule can attach a custom header such as X-Zscaler-Encrypt:1. [zia.dlp.outbound-email-tenants:verdict-headers] The Email DLP page lists all of the outbound connections that need to be configured for the Zscaler smart host to communicate with the SEG, and with the Gmail server. [zia.dlp.outbound-email-tenants:smart-host-ips] If the email is visible in Email DLP Insights Logs, the SEG article says this indicates the SEG is successfully routing mail to the Zscaler smart host and the email flow is working as expected. [zia.dlp.outbound-email-tenants:seg-validation]

**Gmail.** Gmail needs routing for bidirectional communication with the smart host and compliance rules for the mail flow in both directions; Google Admin console changes can take up to 24 hours to propagate. The host route selects Require mail to be transmitted via a secure (TLS) connection (Recommended). The SMTP relay rule allows only addresses in the organization's domains and accepts mail only from the specified IP addresses. The outbound compliance rule matches Source IP is not within the range, adds the header key Zscaler-Tenantid with the Key for Transport Rules as value, and changes the route to the host. [zia.dlp.outbound-email-tenants:gmail-routing] In Gmail, a compliance rule that matches the text X-Zscaler-Block: 1 rejects emails returned with that Block header value, and the sender receives a rejection message. An optional rule modifies emails returned with a Block header value of 0 according to the configured actions. [zia.dlp.outbound-email-tenants:gmail-reject-and-modify] With Gmail, the service blocks the notification emails Google sends when a Google Drive file is shared unless google.com is added as a known domain for the organization. The page says this does not affect the file being shared, only the notification email. [zia.dlp.outbound-email-tenants:gmail-drive-notifications]

**Exchange.** For an Exchange tenant with Workflow Automation, after the SaaS application is authorized the Tenant ID is populated in the Admin Console, and an Exchange admin role must be assigned (Exchange Administrator) to the Zscaler SaaS Connector ID in the Azure portal to grant assignments and access. [zia.dlp.outbound-email-tenants:exchange-zwa-authorization] Exchange needs connectors for bidirectional communication with the smart host and mail flow (transport) rules. The send connector goes from Office 365 to a Partner organization, is used only when a transport rule redirects messages to it, routes through the smart host FQDN, and requires a certificate issued by a trusted certificate authority whose subject name or SAN matches the Zscaler cloud domain (e.g., *.zscloud.net). Zscaler recommends disabling it until all connectors and mail flow rules are configured. The receive connector comes from the organization's email server and authenticates by the sender domain matching the Zscaler cloud domain. [zia.dlp.outbound-email-tenants:exchange-connectors] The Exchange outbound mail flow rule applies to recipients outside the organization whose sender domain is one of the domains in the Organization profile, redirects the message to the send connector, and has the admin enter X-Zscaler-TenantId for the message header value. It needs an exception that includes the default Allow and Block header values (1 and 0), so already-inspected email is not returned to the smart host, and it is created with Rule mode set to Test without Policy Tips. [zia.dlp.outbound-email-tenants:exchange-outbound-rule] After the service inspects an email it sends it back to the Exchange server at the next hop address configured on the email tenant. The inbound mail flow rule matches the value 1 in the header to indicate the message is blocked, selects reject the message and include an explanation, and is set to Enforce mode. With connectors and rules in place, the page says the earlier outbound rule's mode can safely be set. [zia.dlp.outbound-email-tenants:exchange-inbound-rule] If an outbound email policy rule uses the Quarantine action, the service attaches the X-Zscaler-Quarantine:1 header to triggering emails, and the page says this header must be mapped in Exchange so that affected emails are quarantined on the Exchange server. [zia.dlp.outbound-email-tenants:exchange-quarantine-mapping]

**The tenant key header.** The pages spell the header that carries the tenant key differently [divergence:zia.dlp.outbound-email-tenants:tenant-key-header]. Whether a quarantined message also carries a Block header, and so is recognized as processed, is open in [Outbound Email DLP policy: smart host flow, per-recipient evaluation, criteria and header actions](kb:zia.dlp.outbound-email-policy).

What to check:
1. Which spelling of the tenant key header the mail server rule uses before comparing it to what reaches the smart host.
2. Whether the tenant's next hop uses a valid, trusted certificate, since self-signed, expired or otherwise invalid ones are not allowed.

Sources disagree (name both sides):
- The pages spell the header that carries the tenant key as X-Zscaler-TenantID, X-Zscaler-TenantId and Zscaler-Tenantid. [divergence:zia.dlp.outbound-email-tenants:tenant-key-header]
  - zscaler-help: The SEG page, like the tenant page, writes X-Zscaler-TenantID: <tenant-key>.
  - zscaler-help: The Exchange page writes X-Zscaler-TenantId, with a lowercase d.
  - zscaler-help: The Gmail page enters Zscaler-Tenantid as the header key, without the X- prefix.
  Impact: Whether the service matches the header name case-insensitively, and whether the X- prefix is required, is not stated, so a tenant header that differs from the SEG page's spelling is not shown to be wrong by the pages.
