# NSS runbook: VM-based NSS Unhealthy server, alerts and build upgrade checks (zia.logs.nss-runbook.vm-health)
Also called: NSS showing Unhealthy; Operational Issue with NSS VM

**Unhealthy server.** For a VM-based NSS server showing Unhealthy in the Admin Console, the runbook starts with sudo nss status, then sudo nss dump-config if the service is not running, and later checks all granular NSS roles with /sc/bin/smctl.sh. [zia.logs.nss-runbook.vm-health:unhealthy-first-checks] The runbook lists common causes of an Unhealthy NSS server state: network connectivity loss to the Zscaler cloud, configuration errors, resource constraints, certificate errors, service crashes, a version mismatch (running an outdated NSS software version, which the runbook says can sometimes cause unhealthy conditions), and the server being disabled on the UI. [zia.logs.nss-runbook.vm-health:unhealthy-causes] [divergence:zia.logs.nss-runbook.vm-health:outdated-version-effect] To validate the NSS certificate, the runbook has the admin run an openssl command against /sc/conf/zscaler_nss_certificate.crt, compare it with the certificate downloaded from the UI, and look for duplicate certificates. [zia.logs.nss-runbook.vm-health:certificate-check] The runbook has the admin run sudo /sc/bin/smmgr -g smca_cur_nss_orgid -d stats and try to reinstall the NSS client certificate if the issue persists; it also lists checking for Zscaler Central Authority related connectivity issues. [zia.logs.nss-runbook.vm-health:orgid-check] The runbook says that above 75K users Zscaler recommends the 64GB VM type, and that an organization averaging more than 1 billion daily transactions needs additional Nanolog clusters, requested through Zscaler Support. [zia.logs.nss-runbook.vm-health:sizing-guidance] For disk space issues on VM-based NSS, the runbook uses df -h or ls -ltrh /sc, then checks smcdsc.core* output; CPU details come from sysctl hw | grep cpu. [zia.logs.nss-runbook.vm-health:disk-and-core-files] The runbook checks /sc/log/zscaler.log for service restarts or stops and /sc/log/smmonitor.log for HUNG states, and says to capture information and contact Zscaler Support if the service is frequently hung. [zia.logs.nss-runbook.vm-health:service-logs]

**Alerts.** For the CPU utilization high, Memory is low and Memory swap is high alerts, the runbook has the admin run top (CPU, memory) or swapinfo (swap), and can also check the processwatch_cur_cpu_use_inpercentage counter for historical CPU use. [zia.logs.nss-runbook.vm-health:alert-cpu-memory-swap] For the Disk space is low alert the runbook checks df -h or ls -ltrh /sc, and if /sc/log is overutilized, the smcdsc.core* files; for the connection between the NSS and the SIEM is poor alert it says the connection is not stable and to check that average bandwidth requirements are met if NSS and SIEM are on different networks. [zia.logs.nss-runbook.vm-health:alert-disk-and-siem-link] Historical Zscaler alerts can be read from the nss_alert_generated counter, with /sc/bin/smmgr -g nss_alert_generated -d stats, and alerts for connectivity down to the SIEM, Nanolog or CA are handled with the Network Connectivity Checks. [zia.logs.nss-runbook.vm-health:alert-history] Which section the alert steps' Scope 2 reference points to [gap:zia.logs.nss-runbook.vm-health:alert-scope-2-anchor] is open. SNMP monitoring can be used for NSS health and connectivity; /var/log/snmpd.log shows SNMP alerts generated on the NSS, and the mitigation steps are the same as for Zscaler alerts. [zia.logs.nss-runbook.vm-health:snmp-alerts] When a historical issue has no monitoring alerts configured, the runbook checks the nss_alert_generated counter at the issue timestamp, /var/log/messages, /sc/log/zscaler.log for runtime errors and /sc/log/smmonitor.log for HUNG states. [zia.logs.nss-runbook.vm-health:historical-no-alerts]

**Build upgrade.** To validate NSS build upgrades, sudo nss checkversion shows the current and available build (alternate: /sc/bin/smcdsc -V) and sudo nss update-now upgrades manually. [zia.logs.nss-runbook.vm-health:build-upgrade-validation] For a failing NSS build upgrade the runbook checks that smcdsc (responsible for build updates) is running, tests zdistribute connectivity with sudo nss test-firewall, checks disk space and /sc/core files, and reads /sc/log/autoupgrade.log for historical failures. [zia.logs.nss-runbook.vm-health:build-upgrade-troubleshooting]

  - zscaler-help: A system not on the latest version would not be able to communicate with the Zscaler cloud.
  Impact: The first line is about the NSS software build and the second about all Zscaler systems including the ZSOS version, and the page does not say whether they are the same requirement. Do not tell an admin that an outdated build always makes the server unhealthy or always breaks communication.
