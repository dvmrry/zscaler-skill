# NSS runbook: missing and delayed logs on VM-based NSS, smstat counters and where the loss occurs (zia.logs.nss-runbook.log-loss)
Also called: NSS Feed missing logs; Logs Delayed (VM-based NSS); smstat counters

**Triage order.** For missing NSS feed logs the runbook asks first whether the NSS server is unhealthy, then whether there are network connectivity issues, and only if both are fine does it quantify the log loss. [zia.logs.nss-runbook.log-loss:missing-logs-triage-order] To quantify log loss, the runbook takes the transaction count from the Admin Console: Logs > Insights, Web Insights or Firewall Insights depending on log type, and the Overall Traffic for the issue time frame. [zia.logs.nss-runbook.log-loss:ui-transaction-count]

**Counters.** The smsmclt_cur_transactions_count counter gives transactions received on NSS from the Nanolog server, and is generally higher than the UI total because it counts all log types before NSS filters apply. [zia.logs.nss-runbook.log-loss:counter-cur-transactions] The smsmclt_tot_transactions_count counter gives transactions on NSS after the filter is applied; it is often close to, but not exactly, the UI total because of factors like Web Delay, which is reviewed with smsmclt_cur_datatimestamp and smsm_cur_weblog_time. [zia.logs.nss-runbook.log-loss:counter-tot-transactions] The smsmclt_tot_events_flushed counter gives transactions sent from NSS to the SIEM, and for multiple feeds the command filters on the impacted feed with -j <feedname>. [zia.logs.nss-runbook.log-loss:counter-events-flushed] The runbook says comparing counters localizes the loss: fewer smsmclt_cur_transactions_count than the UI total means loss between Nanolog server and NSS; smsmclt_tot_transactions_count or smsmclt_tot_events_flushed below smsmclt_cur_transactions_count means the logs are dropped on the NSS; matching counters with missing SIEM logs mean loss between NSS and SIEM. [zia.logs.nss-runbook.log-loss:localize-loss-by-counters] [divergence:zia.logs.nss-runbook.log-loss:cur-count-drop-rule]

**Where the loss is.** For loss between Nanolog server and NSS, the runbook checks the Nanolog connection with netstat; if the Admin Console transactions and the transactions received on NSS match, it checks smsmclt_tot_transactions_count and, if that shows a significant difference, the NSS feed filters; if NSS is not receiving all the logs it says to contact Zscaler Support to take simultaneous captures on the Nanolog server and NSS and run an MTR trace from the Nanolog server to the NSS IP. [zia.logs.nss-runbook.log-loss:loss-nanolog-to-nss] If there is a significant difference between transactions received on NSS and sent to the SIEM, the runbook says the SIEM is likely consuming slowly so NSS buffers and can overflow; it checks Send-Q and sudo nss troubleshoot feeds, and if the SIEM is slow, whether the feed has SIEM Rate configured. [zia.logs.nss-runbook.log-loss:loss-on-nss] [divergence:zia.logs.nss-runbook.log-loss:received-on-nss-counter] If NSS has forwarded everything but the SIEM lacks logs, the runbook says the logs could be dropped on the SIEM due to parsing errors or by an intermediate network device, and suggests simultaneous captures on the SIEM and the NSS service interface. [zia.logs.nss-runbook.log-loss:loss-nss-to-siem]

**Case study.** In the vendor's case study (web logs suspected lost for 2 hours on 30 June 2025), the UI showed about 7.3M transactions, smsmclt_cur_transactions_count about 10M, smsmclt_tot_transactions_count and smsmclt_tot_events_flushed about 7.2M, and a Web Lag of 15 minutes on average at 900 per second was found, and the runbook says a very minor difference in the logs received is fine. [zia.logs.nss-runbook.log-loss:case-study-web-logs]

**Delayed logs.** For delayed logs the runbook compares smsmclt_cur_datatimestamp and smsm_cur_weblog_time, tests for unusually high latency to the Nanolog server with connect=tcp, and runs sudo nss troubleshoot feeds for a lagging feed; if the SIEM is consuming slowly it checks whether the feed has SIEM Rate configured. [zia.logs.nss-runbook.log-loss:logs-delayed-vm] [NSS runbook corner cases: private and multi-cluster Nanolog, SIEM rate, explicit proxy, log replay, password reset and third-party software](kb:zia.logs.nss-runbook.corner-cases)

Sources disagree (name both sides):
- The runbook says tot_transactions or tot_events_flushed below smsmclt_cur_transactions_count means logs are dropped on NSS, while its own case study and counter notes say the cur counter counts all log types before filters, so a filtered feed shows a lower tot count with no loss. [divergence:zia.logs.nss-runbook.log-loss:cur-count-drop-rule]
  - zscaler-help: A tot or flushed count below the cur count means logs are dropped on NSS.
  - zscaler-help: In the case study the cur count is about 10M and the tot and flushed counts about 7.2M, because cur is before filtering, and the runbook treats it as fine.
  Impact: Do not tell an admin that tot or flushed below cur proves NSS dropped logs; when the feed has filters the cur count is expected to be higher. Compare the tot count to the UI total, as the case study does.
- The runbook defines transactions received on NSS as smsmclt_cur_transactions_count, while its NSS-loss steps use smsmclt_tot_transactions_count for the received count. [divergence:zia.logs.nss-runbook.log-loss:received-on-nss-counter]
  - zscaler-help: Transactions received on NSS come from smsmclt_cur_transactions_count.
  - zscaler-help: The logs received on NSS are given as smsmclt_tot_transactions_count, with a garbled counter name in the comparison to the SIEM.
  Impact: Which counter is the received count for the NSS-to-SIEM comparison is not settled by the page. Name the counters when relaying the check, and do not assume the garbled clt_tot_transactions_count names smsmclt_cur_transactions_count.
