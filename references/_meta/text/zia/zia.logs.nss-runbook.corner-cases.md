# NSS runbook corner cases: private and multi-cluster Nanolog, SIEM rate, explicit proxy, log replay, password reset and third-party software (zia.logs.nss-runbook.corner-cases)
Also called: Corner Cases; private Nanolog (smsm) cluster; multi-cluster Nanolog; SIEM rate limit

**Private Nanolog.** A private (smsm) Nanolog cluster stores logs on-premises instead of Zscaler public clusters; Zscaler recommends dedicated Nanolog clusters, hosted and managed by Zscaler, as an alternative. [zia.logs.nss-runbook.corner-cases:private-nanolog-definition] With a private Nanolog the cluster hostname must be resolvable and reachable from the NSS server with firewall rules allowing it; hardware replacement requests go to Zscaler Support with the cluster hostname. [zia.logs.nss-runbook.corner-cases:private-nanolog-requirements] Troubleshooting commands such as netstat or nss troubleshoot connection generally show an established connection to the Zscaler smsm IP on port 443; with a private Nanolog this IP is customer-managed, and smsm_cur_smsm_svr_ip holds the historical smsm server IP. [zia.logs.nss-runbook.corner-cases:private-nanolog-ip-in-output]

**Multi-cluster Nanolog.** For multi-cluster private or dedicated Nanolog clusters Zscaler recommends log spraying, load balanced on the modulus of Zscaler user IDs so a given user's logs sit on one cluster. [zia.logs.nss-runbook.corner-cases:multi-cluster-spraying] In a multi-cluster setup the commands run on all primary NSS servers, the SIEM total is the sum across NSS servers, and ideally one Nanolog cluster maps to one NSS server, set by Zscaler Operations at deployment. [zia.logs.nss-runbook.corner-cases:multi-cluster-troubleshooting] Zscaler recommends one Nanolog cluster for every 1 billion transactions per day, for example three clusters for three billion. [zia.logs.nss-runbook.corner-cases:cluster-sizing-per-billion] In the vendor example of 4 dedicated clusters on 29 May 2025, the UI showed 3.2B transactions and the totalcount-val values from the four NSS servers, read with the smsmclt_cur_transactions_count counter, summed to 3,219,277,807; the example notes NSS server time was IST while output was GMT. [zia.logs.nss-runbook.corner-cases:multi-cluster-example] [divergence:zia.logs.nss-runbook.corner-cases:cur-count-vs-ui-total]

**SIEM rate and EPS.** A SIEM rate limit throttles logs from NSS to the SIEM; it is unlimited by default, should be chosen against SIEM licensing limits, and a suboptimal limit can cause consistent or intermittent log loss. [zia.logs.nss-runbook.corner-cases:siem-rate-default] In the vendor example without a SIEM rate, a SIEM with a 10K EPS licensing limit and a required average of 25K EPS cannot consume the stream, causing intermittent log loss, with high Send-Q in netstat and a large lag in sudo nss troubleshoot feeds as symptoms. [zia.logs.nss-runbook.corner-cases:siem-eps-no-rate-example] How that example arrives at 25K EPS [gap:zia.logs.nss-runbook.corner-cases:eps-arithmetic] is open. A SIEM rate limit far below the actual log volume (example: 10K limit, 25K volume) makes the NSS buffer logs and overflow; the example's fix is raising the SIEM EPS to the 25K peak-hour average and setting the same rate limit on NSS. [zia.logs.nss-runbook.corner-cases:siem-rate-too-low]

**Explicit proxy.** NSS can tunnel Zscaler cloud connections through an explicit proxy with sudo nss configure proxy during deployment, useful in No Default Route environments; the tunneled connections include SMCA, SMSM, SMCDSS and Kafka (kproxy.hdeu1.zdataservices.net). [zia.logs.nss-runbook.corner-cases:explicit-proxy-mode] Reachability of a host through the explicit proxy is tested with smmgr using proxy_host, proxyport and host kproxy.hdeu1.zdataservices.net. [zia.logs.nss-runbook.corner-cases:explicit-proxy-operations] nss configure proxy remove removes the explicit proxy, and in Explicit mode the cloud connections (SMCA/SMSM) are seen toward the proxy IP instead of the Zscaler IP. [zia.logs.nss-runbook.corner-cases:explicit-proxy-remove-and-view]

**Log replay and bulk downloads.** For a log replay request the runbook wants a genuine, strongly justified ask, Duplicate Logs configured in the NSS feed so logs are buffered and replayed on SIEM connectivity issues, and the remote support tunnel enabled for VM-based NSS but not Cloud NSS. [zia.logs.nss-runbook.corner-cases:log-replay-requirements] Whether Duplicate Logs applies to Cloud NSS [gap:zia.logs.nss-runbook.corner-cases:duplicate-logs-cloud-scope] is open. For timeouts downloading bulk logs from the UI the runbook suggests a Host Contains filter instead of a URL match, keeping the client awake, extra filters on the URL search, pre-aggregated counter searches, and DNS insights where DNS goes to Zscaler. [zia.logs.nss-runbook.corner-cases:bulk-log-download-practices] Zscaler recommends fetching transaction logs from the Admin Console for troubleshooting or forensics only, and using SIEM (NSS) tools for bulk logs. [zia.logs.nss-runbook.corner-cases:forensic-log-fetch]

**Password reset.** To change a known NSS root password use passwd; for a lost one Zscaler Operations can reset it remotely through Zscaler Support without necessarily enabling remote access, or the admin can boot single-user mode. [zia.logs.nss-runbook.corner-cases:password-reset-options] In the single-user-mode reset, the admin interrupts boot with the space bar and presses 2, remounts the root file system read-write with the mount command, and the runbook gives fsck -y, mount -u / and mount -a as the commands that fix any issues in that step; exit; exit then boots multi-user mode. [zia.logs.nss-runbook.corner-cases:password-reset-single-user] zsroot and root are different accounts and both passwords must be reset one at a time, with Zscaler recommending the same password for both; if the procedure fails the options are redeploying NSS or contacting Zscaler Support. [zia.logs.nss-runbook.corner-cases:password-reset-accounts]

**Third-party software.** Installing third-party applications such as endpoint security or EDR on NSS is not supported or recommended; if AV/EDR must be deployed the NSS service connections must be tested as allowed, and Zscaler does not troubleshoot or remove the software. [zia.logs.nss-runbook.corner-cases:third-party-software]

Sources disagree (name both sides):
- The runbook's multi-cluster example uses smsmclt_cur_transactions_count and finds its sum matches the UI total, while the counter notes say that counter is generally higher than the UI total because it counts all log types before filters. [divergence:zia.logs.nss-runbook.corner-cases:cur-count-vs-ui-total]
  - zscaler-help: The smsmclt_cur_transactions_count values summed across the four NSS servers are approximately the 3.2B UI total.
  - zscaler-help: The smsmclt_cur_transactions_count counter is generally higher than the UI total.
  Impact: The page does not say why the example's cur counter matches the UI total. Do not tell an admin the cur counter should match the UI total, or that it should exceed it, without saying the page shows both.
