# Connecting SaaS platforms to 3rd-Party App Governance: supported platforms, platform admin roles, permissions requested and tenant status (zia.app-governance.platforms)

The platforms that can be connected to 3rd-Party App Governance are Atlassian, Databricks, GitHub, Google Workspace, Microsoft Azure, Okta, Salesforce and Slack. [zia.app-governance.platforms:supported-platforms] Connecting to a platform needs a user with admin privileges on it, not necessarily the user used to sign in to 3rd-Party App Governance (some clients use dedicated service accounts). Onboarding can be self-onboarding or a concierge onboarding scheduled with Zscaler Support. [zia.app-governance.platforms:connecting-user] The connection depends on the license {{zia.app-governance:license-dependent|ref}}. The portal and its roles are in [3rd-Party App Governance: governing third-party apps, add-ons and extensions connected to SaaS platforms, and its portal, roles and dashboard](kb:zia.app-governance).

**Platform-side roles.** The platform-side privileges each integration page requires are Atlassian Admin (with Jira User Access Admin, Confluence Product Admin and User Access Admin, and Jira Administration Product Admin) for Atlassian, Account Admin for Databricks, an Organization Owner role for GitHub, Google Admin for Google Workspace, Global Administrator for Microsoft Azure and Microsoft 365, Okta Admin plus an Okta API token for an administrative account for Okta, Admin for Salesforce, and Admin or Owner roles for Slack. [zia.app-governance.platforms:platform-admin-roles]

**Two ways to connect.** For Google Workspace, GitHub and Microsoft Azure, clicking Add in the Add Integration window redirects to the Add SaaS Application Tenant page in the Zscaler Admin Console, where the tenant details are entered and the configuration steps for a new SaaS application tenant are completed. The edit steps on those pages say to edit the tenant details and click Save. The Google Workspace and GitHub pages mark a following step as not required for legacy connections, a redirect to the SaaS Application Tenants page where a confirmation window appears, and the Microsoft Azure page marks its following steps as not required for legacy connections. [zia.app-governance.platforms:admin-console-tenant-flow] The Okta, Salesforce and Slack pages each say the SSPM Scan checkbox on the Add SaaS Application Tenant page in the Zscaler Admin Console must be selected to enable the SSPM scan feature for the tenant. [zia.app-governance.platforms:sspm-scan-checkbox] Tenant features in the Admin Console: [When adding a tenant the administrator selects the functionality to enable, from App Governance, DLP and Malware scanning SaaS API, SSPM Scan, or Workflow Automation, where the application supports it. The /casbTenant/lite filterByFeature parameter filters tenants by feature: CASB, WORKFLOW_AUTOMATION, SSPM, ACTIVITY_REPORT, TP_APP_REPORT, RT_DLP, APP_GOVERNANCE, REDACTION and CASB_ENTITY_GROUP.](kb:zia.casb.tenants:onboarding-features). Tenant states: [CASB tenants: connecting a SaaS application, states and reauthorization](kb:zia.casb.tenants). The other platforms connect inside the portal's Add Integration window. Atlassian takes the Atlassian subdomain and an API token, Okta takes the Okta URL and Token, Databricks takes the account ID and the client ID and secret of an account-level service principal assigned the Account Admin role, and Salesforce and Slack show a consent window where all privileges are read-only. Salesforce also offers a Sandbox login. [zia.app-governance.platforms:direct-credential-flow] For Okta the integration page recommends creating a dedicated service account for integration and assigning it the minimum required privileges. [zia.app-governance.platforms:okta-service-account] The role that account is given in the same page's steps differs from that recommendation [divergence:zia.app-governance.platforms:okta-service-account-role]. For Atlassian and Okta, the API token or key cannot be viewed in plain text and must be stored securely. If an Atlassian API token that is in use is revoked, it can be replaced with a new token. [zia.app-governance.platforms:api-token-not-viewable]

**Consent and what is requested.** Additional consent steps are required for revoking and banning applications. On the Atlassian page the first consent step only allows reading of the apps in the workspace, and by default users who are not explicitly granted revocation rights cannot perform revoke operations. [zia.app-governance.platforms:read-consent-vs-revoke] Google Workspace requests the scopes admin.reports.audit.readonly (Admin, Token and Login activity audit reports), admin.reports.usage.readonly (Login activity reports), admin.directory.group.readonly (groups), admin.directory.user.readonly (users) and admin.directory.user.security (OAuth grants users give to third-party applications). [zia.app-governance.platforms:permissions-google] GitHub requests the scopes read:org (read-only access to organization membership, organization projects and team membership), user:email (read access to a user's email addresses) and read:audit_log (read access to the audit log data). [zia.app-governance.platforms:permissions-github] Microsoft Azure requests offline_access, AuditLog.Read.All, Directory.Read.All, User.Read.All and Reports.Read.All. Application.ReadWrite.All is an optional permission that is not required for initial onboarding and is only requested for specific activities, such as an admin revoking an app or restricting a particular app's access. [zia.app-governance.platforms:permissions-azure] The Atlassian page's Permissions and Data Collected table lists the permissions used, including offline_access, a global OAuth scope that lets 3rd-Party App Governance refresh the token on expiration without asking for consent repeatedly, and read:me, read:audit-log:jira, read:user:jira, read:permission:jira, read:configuration:confluence and read:group:confluence. The table lists further scopes that are not named here. [zia.app-governance.platforms:permissions-atlassian] The Okta integration reads /users, /users/…/roles, /groups, /groups/…/users, /groups/…/apps, /apps, /apps/…/users, /apps/…/grants and /api-tokens, where /api-tokens lists API tokens generated in the tenant with their metadata such as token name, the user who generated it, and creation and expiration dates. [zia.app-governance.platforms:permissions-okta] Salesforce requests two scopes. The first allows access to the logged-in user's account using APIs such as REST API and Bulk API 2.0 and includes chatter_api, and the second manages user data via web browsers, allows use of access_token on the web, and includes Visualforce. [zia.app-governance.platforms:permissions-salesforce] Slack requests a permission to view information about your identity, and team:read, users:read, users:read.email, usergroups:read and admin (Administer a workspace). The page says 3rd-Party App Governance uses a very limited set of the APIs granted by the admin permission, designed only to read audit and activity logs. [zia.app-governance.platforms:permissions-slack] The Databricks page lists no permissions table [gap:zia.app-governance.platforms:databricks-permissions].

**After connecting.** After a connection is achieved, pulling and ingesting all relevant application data might take a while depending on the size of the tenant. The Settings page then updates the integration status, first connected time and last synced time, Zscaler emails when the application data and initial insights are viewable in the inventory, and a failed connection shows an error message with the reason. [zia.app-governance.platforms:ingest-delay] The Atlassian page says it might be necessary to reconnect if an error such as Grant Expired displays. The Google Workspace, GitHub and Microsoft Azure pages say the Reconnect option is available only for legacy tenants, which are the existing tenants onboarded via the 3rd-Party App Governance Admin Portal. [zia.app-governance.platforms:reconnect] The error This app is blocked can appear when connecting 3rd-Party App Governance to Google Workspace, because company settings might prevent connecting third-party apps without explicitly trusting them. The page resolves it by adding 3rd-Party App Governance to the trusted apps in the Google Admin Console under Security > API Controls, entering client ID 1017448667100-p63ee1484o66sdnfreusoafl8hp9oci5.apps.googleusercontent.com with Trusted: can access all Google services selected. [zia.app-governance.platforms:google-app-blocked] Segregating a Google Workspace integration by organizational units (OUs) is a feature in limited availability. [zia.app-governance.platforms:google-ou-segregation] How platforms named only in the App Panel risk table get into the inventory is open [gap:zia.app-governance.platforms:chrome-and-extra-platforms].

**The Settings page.** The Settings page shows the SaaS tenants added in 3rd-Party App Governance and Advanced SSPM. The tenants can be filtered by Status, Platform or Enabled Features and exported to a CSV file, and Enabled Features can be App Governance, SSPM Scan, or both. [zia.app-governance.platforms:settings-tenants] A tenant's integration status is Healthy (the integration completed successfully), Unhealthy (failure to achieve a connection; contact Zscaler Support) or Onboarding (connection achieved and data being ingested). If the tenant has yet to sync, N/A displays for the last sync, and if the duration of the sync is excessive, the last sync time is highlighted in red. [zia.app-governance.platforms:settings-tenant-status] What counts as an excessive sync is open [gap:zia.app-governance.platforms:sync-cadence].

Sources disagree (name both sides):
- The Okta page's heading and recommendation describe a dedicated read-only service account with minimum privileges, and its steps then assign that account the Super Administrator role. [divergence:zia.app-governance.platforms:okta-service-account-role]
  - zscaler-help: The service account is described as read-only, with the minimum required privileges.
  - zscaler-help: The step sets the service account's role to Super Administrator.
  Impact: The page does not say whether Super Administrator is the minimum role the integration needs or a documentation error, so the privilege to grant the Okta service account is not settled by this page.
