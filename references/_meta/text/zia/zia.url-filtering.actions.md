# URL Filtering actions and their prerequisites (zia.url-filtering.actions)
Also called: url filtering actions; url filter rule action; allow caution block isolate conditional; allow override; block override; override users not prompted; ICAP_RESPONSE

The five console actions are Allow, Caution, Block, Isolate, and Conditional. Allow and Block need no explanation; the other three carry prerequisites that decide whether the action can take effect at all. Caution shows an end-user notification (default or a redirect page) before letting the user through. [zia.url-filtering.actions:caution] Isolate sends matching traffic through a remote browser using a chosen isolation profile, and exists only when Zero Trust Browser is enabled for the organization. [zia.url-filtering.actions:isolate-needs-zbi] Conditional enforces step-up authentication before access. It needs Authentication Service for end users and Client Connector forwarding; through Private or Virtual Service Edges the category is blocked instead, and it does not apply to isolation traffic. [zia.url-filtering.actions:conditional-prereqs]

**Allow Override.** Override users and groups take effect only when `blockOverride` is true and the action is BLOCK; override users additionally require that no override groups are set. [zia.url-filtering.actions:override-conditions] With the Allow Override option, some users or groups can be allowed to override a block; in the page's example, teachers are prompted to enter their override password, which can be company-provided credentials such as single sign-on credentials or hosted database credentials based on the Enable Identity-based Block Override settings. Permitted users can access the blocked page only during their current browser session and must reauthenticate in another browser session. [zia.url-filtering.actions:override-prompt-session] Traffic matching an Allow Override is permitted without restriction when SSL inspection is off and Show End User Notifications is off in the corresponding SSL inspection rule. [zia.url-filtering.actions:override-unrestricted-without-inspection] Whether a rule's action is enforceable on HTTPS at all depends on the inspection path: see [Where SSL inspection sits in ZIA web policy evaluation (the two passes)](kb:zia.ssl-inspection.pipeline).

Through the API, `action` also accepts `ICAP_RESPONSE` and the sentinels `ANY` and `NONE`. [zia.url-filtering.actions:api-action-values] Reading an ISOLATE rule by ID may lack its isolation profile [divergence:zia.url-filtering.actions:isolate-cbi-profile-get-by-id]. HTTP header insertion on an Allow rule works only for custom URL categories. [zia.url-filtering.actions:header-insertion-custom-only] Allow and Isolate rules can carry a daily bandwidth quota (10 to 100,000 MB) and a daily time quota (15 to 600 minutes), after which the sites are blocked. [zia.url-filtering.actions:quotas] For an Allow rule, the daily time quota is based on the time that the rule is created: for example, if the rule is created at 11:00 AM PST, the quota is renewed at 11:00 AM PST the next day. [zia.url-filtering.actions:quota-renewal] The EUNs specified in the rules take precedence over the default EUN configured on the Administration > End User Notification > End User Notifications page. [zia.url-filtering.actions:rule-eun-precedence]

What to check:
1. Whether override users never receive the prompt, which is checked first on the rule's action and blockOverride fields.
2. Whether a rule's Allow Override traffic is unrestricted, which depends on SSL inspection and end-user notifications being off.

Sources disagree (name both sides):
- Whether GET-by-ID returns cbiProfile for ISOLATE rules [divergence:zia.url-filtering.actions:isolate-cbi-profile-get-by-id]
  - sdk-go: The Go SDK says GET by ID does not return cbiProfile for ISOLATE rules while GetAll does, and falls back to GetAll to fill it in.
  - sdk-python: The Python get_rule issues one GET and parses the rule; it has no fallback.
  Impact: A Python read of an ISOLATE rule by ID can come back without its isolation profile object; read it from the list or use the Go fallback pattern. The Go comment is the only statement of the bug; no capture shows it.
