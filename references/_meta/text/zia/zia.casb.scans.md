# CASB scan schedules: states, historical data, stop and restart (zia.casb.scans)
Also called: saas security scan configuration; scan schedule; scan initialized; scan stopped; historical scan; duplicate results after restart; data at rest scan
Former IDs: api-casb-03

A scan schedule is what makes a policy inspect anything. The Data at Rest Scanning DLP and Malware Detection policies inspect content only through a SaaS Security scan schedule; the policy rules are configured first, and the schedule then selects the Data at Rest Scanning policy for a tenant. [zia.casb.scans:schedule-needs-policy]

**What a schedule holds.** A scan schedule is listed with its SaaS application tenant, a schedule criteria of policy and data to scan (the amount of historical data inspected), an optional description, a status, and start, stop, edit and delete actions. [zia.casb.scans:schedule-columns] Every SaaS application tenant supports historical scanning and both DLP and Malware scanning, but only the Report action is the same across tenants; remove, quarantine, remove collaborators and similar actions depend on the application. [zia.casb.scans:actions-vary-by-app] Only one scan can be configured per SaaS application tenant, though scans can be configured for multiple application tenants, and a scan schedule must choose at least one policy. [zia.casb.scans:one-scan-per-tenant] A scan schedule has a Chat Bots option, available only for Slack tenants, to include or exclude chatbots from the scan. [zia.casb.scans:slack-chat-bots] A Polling Intervals setting sets how often the system scans the SaaS application tenant, at 5, 10, 15, 20, 25 or 30 minutes, and is currently available for Salesforce, ServiceNow and Jira. [zia.casb.scans:polling-intervals] A scan schedule's description cannot exceed 10,240 characters. [zia.casb.scans:schedule-description-limit] The default polling interval and the Chat Bots default are open [gap:zia.casb.scans:schedule-defaults].

**Resources to scan.** For Amazon S3, Atlassian Bitbucket, GitLab, Google Cloud Platform, Microsoft Azure and SharePoint tenants, the scan schedule has a section listing the tenant's buckets, repositories, blob containers or sites, which can be set to be scanned automatically for DLP or Malware rules or chosen manually. For Amazon S3, selecting bucket names creates the list of available buckets from which the DLP and Malware Detection policies specify buckets for inspection. Quarantine buckets, repositories, blob containers and sites cannot be selected, nor can CloudTrail buckets for Amazon S3. The bucket, repository and blob container tables show Exposure as external, internal, private or public, and SharePoint custom sites are entered by name. [zia.casb.scans:resource-selection] For Bitbucket, if a user account's public repository is not shared with the admin, the admin does not know its exact path even though it is accessible, because Bitbucket cloud has no API to list all users; when a user shares a private repository with the admin, the admin can discover public repositories in that user's account. [zia.casb.scans:bitbucket-discovery-limit] Buckets, bucket owners and blob containers on a rule are in [For a public cloud storage application rule, Buckets, Bucket Owner, Blob Containers and Blob Container Owner cannot be changed when the rule is first defined: after saving the rule, a scan schedule is created for the tenant and bucket or blob container names are selected there to create the list available to the DLP and Malware Detection policies, and only then can the rule be edited to configure those fields.](kb:zia.casb.dlp-rules:storage-containers-after-schedule).

**States.** A scan shows one of three states: Scan Initialized (prerequisites verified), Running (initialization completed successfully, with the start time shown) and Scan Stopped (with the stop time and the reason shown). [zia.casb.scans:scan-states] Scan Initialized does not indicate that scanning has started. [zia.casb.scans:initialized-is-not-started] The integer behind the scan action is open [gap:zia.casb.scans:scan-action-encoding].

**Active and historical data.** When a scan is started, its start date separates active content (created, modified, sent or received after that date) from historical content (before it); a historical file modified after the date counts as active, and starting later than a rule was created still uses the start date. [zia.casb.scans:active-vs-historical] Adding or editing a policy rule while a scan runs moves the active/historical date to the time of the change, and content the scan already processed becomes historical and is not covered by the new or edited rule; deleting a rule leaves the date unchanged. [zia.casb.scans:rule-edits-reset-date] A started scan always inspects active content continuously; historical content is inspected only if configured, with All Data, Data Created or Modified After a chosen date, or New Data Only, and no more than 6 years back. [zia.casb.scans:historical-options] For Webex Teams tenants, a historical file can be scanned only if a user downloads it before the scan is started from the SaaS Security API Scan Configuration page, because the Webex API returns only download events for files. Only 15 days of historical data before the scan's start date can be scanned, so choosing an older date with Data Created or Modified After, or All Data, still inspects only those 15 days; in the vendor's example the scan inspects only data created or modified from November 7, 2025, to November 22, 2025. [zia.casb.scans:webex-historical-limits]

**Scanning exceptions.** Data at Rest Scanning (scanning) exceptions for file sharing applications exempt specific folders or users from the Data at Rest Scanning policy, which consists of the DLP and Malware Detection policies: the service completely ignores the files within an exempted folder and does not evaluate an exempted user. A folder exception takes the folder's full path and a user exception the owner, and up to 64 exceptions for folders and users can be added. [zia.casb.scans:scanning-exceptions] Whether the 64 exceptions are one shared pool for folders and users is open [gap:zia.casb.scans:scanning-exception-pool]. The per-policy exceptions are in [Data at Rest Scanning DLP policy exceptions are optional for sanctioned SaaS applications, for example for a CEO whose sent emails should not be inspected or a security research group's malicious files repository. Each application type's section has a user field plus Groups and Departments: Senders for collaboration and email applications, Owners for CRM, file sharing and ITSM applications, and Editors for source code repository applications.](kb:zia.casb.dlp-rules:dlp-policy-exceptions) and [Data at Rest Scanning Malware Detection policy exceptions are optional for sanctioned SaaS applications, for example for a CEO whose received emails should not be inspected. Each application type's section has a user field plus Groups and Departments, each taking Any or up to 32 entries, with Zscaler Support able to increase the limit of users, groups or departments: Senders for collaboration and email applications, Owners for CRM, file sharing and ITSM applications, and Editors for source code repository applications.](kb:zia.casb.malware-rules:malware-policy-exceptions).

**Stopping and restarting.** Stopping a scan flushes its processing queue. [zia.casb.scans:stop-flushes-queue] After a stop, the scan can be restarted either over all historical data, which processes everything from the beginning and might duplicate results for data already inspected, or from the date at which the Insights logs show it stopped processing historical data, which skips data already processed. [zia.casb.scans:restart-options] The run and scan identifiers that show where a scan stopped are in [CASB SaaS Security Insights logs: what the records mean, filtering, export and streaming](kb:zia.casb.insights-logs).

**How current findings are.** How far behind an upload a finding can be is open [gap:zia.casb.scans:scan-latency].

The tenant a schedule names is in [CASB tenants: connecting a SaaS application, states and reauthorization](kb:zia.casb.tenants); what quarantine does to a file is in [CASB quarantine and tombstone files](kb:zia.casb.quarantine).

What to check:
1. Whether a schedule exists and shows Running for the tenant, since a configured policy inspects nothing without one.
2. Whether a rule was added or edited while the scan ran, which moves the date after which content is active and leaves earlier content to the historical setting.
3. Whether a restart over all data explains duplicate results, and use the Insights logs to restart from the stop date instead.
4. Whether the question needs finding latency or the `scanAction` values, which no source states.
