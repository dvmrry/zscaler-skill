# ZIA Terraform operations that take several API writes with no rollback (zia.terraform.multi-step-writes)
Also called: terraform partial apply zia; apply failed but change applied; ADD_TO_LIST REMOVE_FROM_LIST; vzen cluster delete; static ip geo_override; user enrollment auth_methods; url category update failed halfway; browser control smart isolation partial; no rollback

Several ZIA Terraform resources change one logical thing with more than one API request. Neither the provider nor the SDK has a transaction, a compensating write, or a re-read to confirm the result. For which fields a write drops, see [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding); for swallowed read errors, see [When the ZIA Terraform provider reports success after an error, or crashes](kb:zia.terraform.error-handling).

**Lists updated by delta.** The SDK's malicious-URL and exempted-URL updaters do not send the desired list. Each reads the current list, computes additions and removals locally, then sends any additions as one write and any removals as a second write, in that order. An error from either write is returned immediately. [zia.terraform.multi-step-writes:delta-helpers-read-then-add-then-remove] The ATP malicious URLs resource and the authentication settings URLs resource pass the whole desired list to these helpers on create and on update, so every apply starts with the read and sends an add and/or a remove when the delta is non-empty. [zia.terraform.multi-step-writes:provider-calls-delta-helpers] When the addition write succeeds and the removal write fails, Terraform reports an error but the list already holds the additions and still holds the entries meant to be removed. Nothing in the helper undoes the first write. For the authentication settings list this is an exempted-URL list. [zia.terraform.multi-step-writes:delta-partial-apply] The additions and removals are computed from a list read earlier in the same call, so a change another writer makes between the read and the writes is not seen by the delta. [zia.terraform.multi-step-writes:delta-stale-snapshot] When the second write of a delta update or of a custom category update fails, the object on the server holds neither its previous contents nor the intended ones: the additions are present while the entries meant to be removed remain, or the old entries are gone while the new ones are absent. [zia.terraform.multi-step-writes:partial-apply-leaves-neither-old-nor-new]

**Two endpoints, written one after the other.** The SDK updates the security policy allowlist and denylist with two independent PUTs to different endpoints, allowlist first. An error from the allowlist PUT stops before the denylist is sent; an error from the denylist PUT is returned after the allowlist was already written. The provider's update calls this one function. [zia.terraform.multi-step-writes:security-policy-urls-two-writes] The browser control policy resource writes its settings with one PUT to the base browser control endpoint and then, only when Smart Isolation is configured or changed, a second PUT to the `/smartIsolation` endpoint. This is the same on create and on update, and an error from the second write is returned after the first was sent. [zia.terraform.multi-step-writes:browser-control-two-endpoint-write]

**Virtual Service Edge cluster deletion.** Deleting a Virtual Service Edge cluster through the SDK is three requests: a GET of the cluster, a PUT of an update payload whose node list is the empty slice, and a DELETE. The provider's delete handler calls this function and then clears the ID and optionally activates. A failed PUT returns an error reading "failed to update VZEN cluster ... before deletion" and a failed DELETE one reading "failed to delete VZEN cluster". [zia.terraform.multi-step-writes:vzen-delete-is-detach-update-delete] The SDK's cluster delete is written to detach nodes before it deletes: its comments describe the PUT as a minimal update payload with empty `VirtualZenNodes` "to detach" and as an update "to remove associations", ahead of the DELETE step. [zia.terraform.multi-step-writes:vzen-delete-comments-state-detach-intent] The node list in the cluster model is tagged `omitempty`, and the detach PUT the delete path builds sets it to an empty slice with the comment `// Detach all service edges`. [zia.terraform.multi-step-writes:vzen-detach-list-omitted-on-wire] Because ZIA updates marshal the caller's struct with `json.Marshal` and a field tagged `omitempty` that holds an empty slice is left out of the body, that detach PUT does not carry `virtualZenNodes` at all, whatever the code comment says it does. [zia.terraform.multi-step-writes:vzen-detach-body-omits-nodes] So the PUT before the DELETE does not express the intended empty node list. If the API treats an omitted list as unchanged, the cluster is deleted (or the DELETE is refused) with nodes still attached; if the PUT succeeds and the DELETE then fails, the cluster remains and other fields were rewritten from the earlier GET. [zia.terraform.multi-step-writes:vzen-delete-effect]

**Node update.** The VZEN node resource's update sends the node PUT and then returns the cluster resource's Read function. That Read looks up `cluster_id` and returns an error when it is not set, and the node resource's schema has no `cluster_id` attribute. After a successful node update the apply can therefore report an error and not refresh node state. [zia.terraform.multi-step-writes:vzen-node-update-calls-cluster-read]

**Static IP coordinate discovery.** When coordinates must be discovered, the provider looks the address up with `GetByIPAddress` and takes any error as the address not existing. The SDK returns an API error and a no-match result as plain errors, so the provider cannot tell a transient or permission failure from absence and goes on to create a temporary static IP. [zia.terraform.multi-step-writes:static-ip-any-lookup-error-is-not-found] Coordinate discovery creates the static IP, reads it back, and updates it, as three requests inside the create handler (apply). A failed read or update after the create returns an error before the resource ID is stored. [zia.terraform.multi-step-writes:static-ip-temp-object-sequence] So a failure of the read or the update after the temporary create leaves a static IP in ZIA that Terraform has no ID for, and no code deletes it. A retried apply may find it by address, but even then it reuses its coordinates and goes on to a normal create of the same address, so the orphan is not adopted and the retry can fail or duplicate it. [zia.terraform.multi-step-writes:static-ip-orphan-on-failure] A transient lookup failure for an address that already exists leads to a second create of the same address, which the API may reject or may accept as a duplicate. [zia.terraform.multi-step-writes:static-ip-transient-lookup-duplicates]

URL category updates matter beyond Terraform state, because entries decide which category a URL belongs to ([Which URL category a URL belongs to](kb:zia.url-categories.membership)). When a custom URL category update both removes and adds entries, the provider sends a REMOVE_FROM_LIST write and then an ADD_TO_LIST write. Through v4.8.16 each carries the desired category with its URL list replaced by the delta; from v4.8.17 each also empties its `dbCategorizedUrls` and `ipRanges`. An error from the add is returned after the removals were sent. From v4.8.16 the two writes are skipped when every current URL is removed, and from v4.8.17 also when `db_categorized_urls` or `ip_ranges` change or when the current or desired category has keyword-retaining, IP-range-retaining, regex or regex-retaining entries; those updates send the category as a whole. [zia.terraform.multi-step-writes:custom-category-remove-then-add] If the removal succeeds and the addition fails, the category has lost its old entries and does not hold the new ones, and the apply reports an error. Because a category's entries decide which category a URL falls into, the half-applied category changes rule matching for those URLs until a later apply repairs it. [zia.terraform.multi-step-writes:custom-category-partial-state] A predefined category update can send up to three separate writes in a fixed order: REMOVE_FROM_LIST for URL and IP entries, then ADD_TO_LIST for them, then a plain PUT that replaces the keyword lists. Each runs only if its part of the diff is non-empty, and an error at any step is returned with the earlier steps already sent. [zia.terraform.multi-step-writes:predefined-category-three-mutations]

**User authentication enrollment.** User create and update send the user and then, when authentication methods are set (on update, only if the password or auth methods changed), enroll them as a separate call. If the enrollment call fails, the provider only logs it and goes on to refresh; the error is not returned. [zia.terraform.multi-step-writes:user-auth-enrollment-error-logged] Both create and update call enrollment only when the configured `auth_methods` set is non-empty, so removing every method from the configuration sends no enrollment change. [zia.terraform.multi-step-writes:user-auth-empty-set-sends-nothing] The resource's `auth_methods` element validator is a `StringInSlice` over `BASIC` alone, while the SDK's enrollment function accepts `BASIC` and `DIGEST`. [zia.terraform.multi-step-writes:user-auth-validator-basic-only] A configuration that sets `DIGEST` in `auth_methods` is rejected during plan-time validation. [zia.terraform.multi-step-writes:user-auth-digest-rejected-at-plan] The user request builder does not carry `auth_methods`, and the user Read never sets it, so the attribute exists only as input to the separate enrollment call. State cannot show what the tenant has enrolled, and a failed or skipped enrollment is not visible as drift. [zia.terraform.multi-step-writes:user-auth-methods-not-in-request-or-state]

**Custom category deletion.** Deleting a custom URL category first detaches it from the URL filtering, SSL inspection, sandbox, file type control, firewall DNS, firewall IPS and DLP web rules, the bandwidth classes and the FTP control policy, by reading each type (the list of rules or bandwidth classes, or the single FTP control policy) and writing back the objects that reference it, using the object as read. The URL Filtering detacher does this per rule with no re-read before the write. All detachers run concurrently, and an error from one is reported only after all finish. [zia.terraform.multi-step-writes:detach-writes-list-snapshot] A change another writer makes to a rule between the list and the write can be overwritten by the detacher's full-rule write. [zia.terraform.multi-step-writes:detach-stale-snapshot-overwrites] The group-style detach helper is in [How the ZIA Terraform provider detaches references before deleting objects](kb:zia.terraform.delete-detach).

Coverage of the sequences, and the limits of the search: Beyond the quoted functions, the places in the ZIA provider and SDK that send ADD_TO_LIST or REMOVE_FROM_LIST are, in the searched code, the ATP malicious URL helper, the exempted URL helper, the security policy helper declares the names ADD_TO_LIST and REMOVE_FROM_LIST but does not send them, the custom URL category update and the predefined URL category update. The two-endpoint and multi-request sequences covered here are these plus browser control, VZEN cluster deletion, static IP coordinate discovery and user enrollment. [zia.terraform.multi-step-writes:multi-write-places] Among the multi-request sequences found in the searched ZIA code, the list-by-delta shape is the most frequent: four sequences send ADD_TO_LIST and REMOVE_FROM_LIST writes (malicious URLs, exempted URLs, custom URL categories, predefined URL categories), two send paired writes to different endpoints (security policy lists, browser control), and Virtual Service Edge cluster deletion, static IP coordinate discovery and user enrollment are one sequence each. [zia.terraform.multi-step-writes:delta-lists-are-commonest-sequence]

Zscaler activation, if enabled, publishes whatever state the failed apply left ([When the ZIA Terraform provider activates configuration](kb:zia.terraform.activation)).

What to check:
1. Whether the live object matches the configuration after a failed apply: read it (the list, the cluster and its nodes, the category's entries, the user's enrollment) before retrying.
2. Whether another writer's change to a list survives the delta write, since the delta is computed from an earlier read.
3. Whether a static IP for the address exists after a failed static IP create: list the static IPs for the address.
4. Whether the cluster's node list is still attached after a failed cluster delete: check the cluster's node list.

That the first write stays committed depends on the API applying each ADD_TO_LIST or REMOVE_FROM_LIST call as it arrives and not holding it until activation; the absence of any compensating call is read from the two helper functions, not searched across the SDK.

- [zia.terraform.multi-step-writes:vzen-detach-body-omits-nodes] Tier B: Rests on the `omitempty` tag and the empty slice the delete path sets (vzen-detach-list-omitted-on-wire), on ZIA updates serializing the caller's struct with `json.Marshal`, and on encoding/json omitting an empty slice tagged `omitempty`, which is Go standard-library behavior no cited source states (see omitempty-drops-zero-values).
