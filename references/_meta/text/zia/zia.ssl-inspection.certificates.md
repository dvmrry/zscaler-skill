# SSL/TLS inspection certificates: who signs, and where the root must be trusted (zia.ssl-inspection.certificates)
Also called: ssl inspection certificate; zscaler root certificate; intermediate ca; custom trust store; firefox ssl inspection; ssl inspection hsm; ssl inspection chromeos; python pip certificate zscaler

For inspection to work without browser warnings the client has to trust whatever signs the leaf certificate. The Zscaler Central Authority is a private CA that acts as both root and intermediate for the ZIA service, or as an intermediate under the customer's private CA, and it authorizes Public Service Edges to act as intermediate CAs that issue certificates to end users for their requested destinations. [zia.ssl-inspection.certificates:central-authority] When inspecting, the Public Service Edge acts as a short-lived intermediate CA and issues a certificate on demand for each requested application, which the browser accepts because the Zscaler trust chain is in the device's certificate store. [zia.ssl-inspection.certificates:per-request-certificates] So the real question is who is in the chain and where it is installed. With the default Zscaler intermediate certificate every client must have the Zscaler root certificate installed; otherwise browsers and applications show warnings or the traffic cannot be inspected properly. [zia.ssl-inspection.certificates:root-must-be-trusted]

**Which CA.** Zscaler offers two CA choices that are functionally equivalent and differ in deployment: Zscaler's own CA, whose root must be installed on machines, or the customer's existing CA with Zscaler as an intermediate, which needs an additional Zscaler subscription but lets clients already holding that root start immediately. [zia.ssl-inspection.certificates:ca-options] Neither CA choice changes how SSL inspection rules match: the rule match expression has no CA or certificate term. [zia.ssl-inspection.certificates:ca-choice-not-a-match-criterion] An Inspect rule can override the default intermediate CA by choosing another intermediate CA from the list; on Block and Do Not Inspect + Evaluate rules the override appears only when the notification setting is on. In the API this is `overrideDefaultCertificate` with an `sslInterceptionCert` reference. [zia.ssl-inspection.certificates:override-intermediate]

**What the browser receives.** With SSL/TLS Inspection enabled, the Zscaler service functions as a full SSL/TLS (man-in-the-middle) proxy and establishes a separate SSL/TLS tunnel with the user's browser and with the destination server. It sends the browser the Zscaler intermediate certificate or the organization's custom intermediate root, as well as a server certificate signed by the Zscaler intermediate CA, and the browser validates the certificate chain in its certificate store. [zia.ssl-inspection.certificates:proxy-model] The Zscaler service dynamically generates and signs the server certificate it presents to the client. The certificate contains the same fields as the original destination server certificate except the issuer distinguished name (DN), which is set to the name of the Zscaler intermediate certificate, and the browser receives it signed by the Zscaler intermediate certificate along with that intermediate certificate. [zia.ssl-inspection.certificates:generated-certificate-fields] The choosing-CA page says the generated certificate's issuer is set to the organization name and the Zscaler service generates the certificate once per site and caches these certificates on the Public Service Edge for Internet & SaaS (ZIA); the cached certificates are usually valid until their expiration date. [zia.ssl-inspection.certificates:generated-certificate-caching] Whether the certificate is generated each time or once per site differs between the pages [divergence:zia.ssl-inspection.certificates:generated-certificate-lifetime]. Zscaler-issued certificates (leaf or short-lived issuing CA) contain a CRL Distribution Point (CRLDP) hosted by Zscaler for certificate revocation. The service provides a CRL distribution point for every certificate it generates so client applications can locate the CRLs, and the Zscaler-hosted CRLs provide the serial numbers of revoked certificate issuers. [zia.ssl-inspection.certificates:crl-distribution-point]

**Key custody and storage.** A customer who will not upload an intermediate certificate to Zscaler nodes can keep the private key in a cloud hardware security module (HSM). [zia.ssl-inspection.certificates:hsm] Web transaction content inspection takes place in memory and is never written to disk. [zia.ssl-inspection.certificates:in-memory] The service generates a CSR with a key pair and encrypts the private key using AES. The private key is stored securely in the Zscaler Central Authority for the software intermediate certificate and the Zscaler intermediate certificate, and in the cloud HSM solution for the cloud HSM intermediate certificate, while the CSR contains the public key. [zia.ssl-inspection.certificates:key-storage-by-type] When the administrator of an organization requests a CSR for an intermediate Central Authority, the Zscaler CA generates a 2048-bit private and public key pair. The private key is immediately encrypted with AES encryption using a password, which is not transmitted or stored on disk on any system and is held in the system's memory only. [zia.ssl-inspection.certificates:key-generation] The key pair size differs between the pages [divergence:zia.ssl-inspection.certificates:intermediate-key-size]. The Zscaler CA encrypts the private key and stores it in an SQL database that contains the organization's policies, accessible only to the organization by logging in with authorized admin credentials. Any write operation to the CA database is immediately replicated to two other identical CA servers in physically separate locations in the US, and the keys are never in the decrypted state on the CA server after they are encrypted. [zia.ssl-inspection.certificates:key-storage-replication] For a user's HTTPS request the Public Service Edge requests the organization's key pair from the CA, which sends the key pair with the organization's intermediate certificate over a 2048-bit TLS connection, only to the requesting Public Service Edge. If a location's traffic is sent to an organization's private Public Service Edge only, the CA sends the private key to the private Public Service Edges only and does not send the keys and intermediate certificate to public Public Service Edges in the Zscaler cloud. [zia.ssl-inspection.certificates:key-distribution] The Public Service Edge maintains the private key unencrypted in its RAM to generate certificates for the websites the user visits; the safeguarding page says these certificates are dynamically generated each time in RAM and not stored in any storage medium. The Service Edge caches the intermediate certificate it received from the CA until it receives a new one. [zia.ssl-inspection.certificates:key-in-service-edge-ram] A Public Service Edge allocates memory from a special region for all SSL/TLS operations, zeroed as soon as the memory is released (packet buffers and key storage areas); it does not allow a data dump from this area from the command line, and all data is zeroed if a process core must be dumped due to a software error. The page says that due to these precautions the Zscaler cloud is invulnerable to SSL/TLS Heartbleed attacks, and that keys are only ephemerally present in Public Service Edge RAM and zeroed after being unused for a short period of time. [zia.ssl-inspection.certificates:key-memory-zeroing] When a new intermediate certificate is generated a new key is generated as well, and the old key and intermediate certificate are removed from the database and its backup. The organization sets the certificate's expiration date and can revoke it at any time; administrators cannot use the intermediate certificate issued to Zscaler to sign any other certificate because the private key never leaves the Zscaler CA or Public Service Edge. [zia.ssl-inspection.certificates:key-rotation-and-revocation] If all CA servers in a cluster are unavailable due to a catastrophic event while the Public Service Edges are still active, the Public Service Edges continue to perform SSL/TLS Inspection as long as the organization's policies, certificates and keys already reside in their memory; a Public Service Edge without the policy and keys does not decrypt the SSL/TLS traffic. If both the CA and the Public Service Edge are unavailable, the service supports a proxy bypass capability where all traffic is allowed without protection. [zia.ssl-inspection.certificates:ca-outage-behavior] Zscaler operation processes and its Information Security Management System (ISMS) are ISO 27001 and SOC 2 Type II certified, all Public Service Edges and CAs are monitored for 24 hours, and access to the CA and Public Service Edges is highly restricted and controlled. [zia.ssl-inspection.certificates:operations-certifications]

**Where the root must be installed.** Some applications keep their own certificate trust store, so installing the Zscaler root in the operating system is not enough: Firefox, Python and developer tooling are the named examples, and for non-browser applications that show SSL errors the check is whether the Zscaler root is installed in the proper repository for them. [zia.ssl-inspection.certificates:own-trust-stores] For applications with custom trust stores Zscaler recommends installing the Zscaler root (or custom intermediate) certificate into the application's store, manually or with a tool such as SCCM; disabling certificate validation is advised only for short-term testing, and the other alternatives are exempting the developer users' traffic, which the guide calls less desirable, or exempting the destination domains. [zia.ssl-inspection.certificates:own-trust-store-remedies] ChromeOS does not trust managed or user-installed certificates for OS-level communication, so only user traffic can be inspected; the traffic between the device and Google's ChromeOS services must be exempted, using a custom URL category of the required domains. [zia.ssl-inspection.certificates:chromeos] The Zscaler service does not install a Zscaler root certificate or a custom root certificate on the user's machine for SSL/TLS Inspection. Customers who use Client Connector for traffic forwarding can use the Client Connector App Profile configuration for Windows and macOS to deploy the certificates; customers without Client Connector on their Windows or macOS machines can push the certificate using Microsoft Active Directory, Group Policy Object or another MDM solution; and the certificates need to be installed manually on Android and iOS devices or with MDM solutions. [zia.ssl-inspection.certificates:root-deployment-channels] Whether the certificate to install is the root or the intermediate is stated two ways [divergence:zia.ssl-inspection.certificates:root-or-intermediate-on-workstation]. The macOS route has a version restriction on the Client Connector side [divergence:zia.ssl-inspection.certificates:macos-app-profile-scope]. The Zscaler root certificate is downloaded from the Root Certificate field of the View Zscaler Intermediate CA Certificate page, reached from Internet Access > Resources > SSL Intermediate Certificate, as a ZIP file named ZscalerRootCerts.zip. [zia.ssl-inspection.certificates:root-download] Firefox browsers do not accept SSL/TLS certificates installed in Internet Explorer browsers, so certificates must be installed on Firefox separately if the organization allows Firefox; Google Chrome uses the same certificate store as Microsoft Edge. [zia.ssl-inspection.certificates:browser-stores]

**Mobile devices and servers.** Installing the certificate on mobile devices requires Mobile Device Management, which is also commonly the best way to deploy Client Connector. [zia.ssl-inspection.certificates:mobile-mdm] Server networks are typically left out of the first inspection projects and added once user inspection is mostly done, because the root CA must reach the hosts, their containers and custom-trust-store applications. Zscaler recommends restricting server access to explicitly permitted destinations and blocking all other access. [zia.ssl-inspection.certificates:servers-deferred]

**Custom root certificates.** With a third-party proxy service or an isolated browser, administrators can upload root certificates of their choice for SSL/TLS inspection: the third-party proxy's roots to sign the MITM certificates, and roots associated with isolation profiles created in the Admin Console. The isolation browser trusts all the well-known certificate authorities trusted by Chromium. [zia.ssl-inspection.certificates:root-certs-purpose] The Root Certificates page lists each certificate's name, uploaded date and time, expiration date and time, and type. Certificates other than the default root can be downloaded, edited or deleted; the default's full details can be viewed. [zia.ssl-inspection.certificates:root-certs-page] The Root Certificates page already carries the default Zscaler Root Certificate, which cannot be edited, and an organization can add up to 10 root certificates. [zia.ssl-inspection.certificates:root-certs-default-and-limit] If the upstream proxy (third-party proxy service) performs SSL/TLS Inspection, Zscaler requires installing the proxy service's root certificates to sign the MITM certificates; the certificate is added with Type Proxy Chaining from a PEM file. [zia.ssl-inspection.certificates:root-certs-proxy-chaining] The isolation-profile steps and type are missing from the capture [gap:zia.ssl-inspection.certificates:root-certs-zero-trust-browser], and the other type values are not listed [gap:zia.ssl-inspection.certificates:root-certs-types]. Editing a custom root certificate changes its Name and Type; the PEM file in the certificate cannot be changed, so a different PEM file needs a new root certificate. The default Zscaler Root Certificate is the only one that cannot be edited. [zia.ssl-inspection.certificates:root-certs-edit-limits] The Deleting Root Certificates page says all custom root certificates except the default Zscaler Root Certificate can be deleted, and that a root certificate associated with an isolation profile cannot be deleted until it is first disabled from the isolation profile; the delete button is greyed out for the default certificate or one associated with an isolation profile. [zia.ssl-inspection.certificates:root-certs-delete-page] Whether a root associated with an isolation profile can be deleted is stated both ways on the editing page [divergence:zia.ssl-inspection.certificates:root-cert-delete-while-associated]. What happens when a custom root expires is not stated [gap:zia.ssl-inspection.certificates:root-certs-expiry], and an API object for Root Certificates was not checked [gap:zia.ssl-inspection.certificates:root-certs-api].

The per-tool commands are in [Installing the inspection root in applications that keep their own trust store, per tool](kb:zia.ssl-inspection.app-trust-stores); three legacy mechanisms are still open [gap:zia.ssl-inspection.certificates:toolchain-trust-mechanisms]. The intermediate CA object (protection types, limits, key types, CSR signing, chain upload) is in [Intermediate CA certificates for SSL/TLS inspection: protection types, limits, key types, CSR signing, chain upload and the default](kb:zia.ssl-inspection.intermediate-ca). Traffic that never accepts the root at all (pinned apps, IoT, guest networks) is in [What SSL/TLS inspection cannot inspect: pinned apps, client certs, QUIC, BYOD, IoT](kb:zia.ssl-inspection.uninspectable); the settings that govern what a rule does with a bad upstream certificate are in [What an SSL/TLS inspection action does: Inspect, Do Not Inspect, Block and their settings](kb:zia.ssl-inspection.actions).
