# Which IP addresses a sublocation matches, overlap rules and XFF (zia.locations.ip-scoping)
Also called: sublocation ip addresses; sublocation overlap; inner ip; xff sublocation; use xff from client request; sublocation ip range format; same ip in multiple locations

**What a sublocation matches.** A sublocation matches on IP addresses encapsulated within a GRE or IPSec tunnel, or on client addresses taken from X-Forwarded-For headers. [zia.locations.ip-scoping:matches-inner-ips] The API takes parent-location `ipAddresses` as single egress IPs; for a sublocation each entry is a single IP, a CIDR (`10.10.33.0/24`) or a range (`10.10.33.1-10.10.33.10`), and the description lists egress, internal or GRE tunnel addresses. The console also accepts ranges such as 10.10.20.2 to 10.10.20.250. [zia.locations.ip-scoping:formats] A sublocation can hold at most 2,000 IP address ranges. [zia.locations.ip-scoping:ranges-per-sublocation]

**Overlap.** Sublocations of one location cannot have overlapping IP addresses, but the same IP address can exist in more than one location. [zia.locations.ip-scoping:no-overlap-within-location] Scoped Workload sublocations are the exception that allows overlapping ranges: [AWS workload sublocation scopes (VPC endpoint, VPC, account, namespace)](kb:zia.locations.workload-scopes).

**Forwarding.** In the API, `vpnCredentials` and `ports` apply to parent locations only; `ipAddresses` applies to both.  [zia.locations.ip-scoping:forwarding-fields-parent-only] In the location CSV format GRE tunnels are bound to locations only, not sublocations, and a SubLocation row cannot carry a VPN type, dedicated port, Virtual Service Edge name or Virtual Service Edge cluster name (each is left as an empty comma) and must name its parent location. [zia.locations.ip-scoping:sublocation-no-forwarding-fields] Whether a sublocation can have a forwarding method of its own is partly answered [gap:zia.locations.ip-scoping:sublocation-own-forwarding], and so is whether a static-IP-only parent can have sublocations [gap:zia.locations.ip-scoping:static-ip-parent].

**XFF.** Use XFF from Client Request is set per location for proxy-chained deployments: the service reads the client RFC 1918 address from the XFF header an on-premises proxy inserts, uses it to identify the client's sublocation, applies that sublocation's policy, then replaces the XFF header with the gateway's public IP before forwarding. [zia.locations.ip-scoping:xff-opt-in] For a sublocation the XFF setting is read-only and inherited: [Which location settings a sublocation has of its own and which it takes from the parent](kb:zia.locations.inheritance).

Traffic that matches no sublocation range goes to `other`: [Sublocations: what they are, the auto-created other sublocations, naming and limits](kb:zia.locations.sublocations).
