# ZIA Terraform resource fields that are not sent, not read back, or sent wrongly (zia.terraform.field-fidelity)
Also called: terraform field ignored; terraform attribute not applied; terraform attribute dropped; capture_pcap not applied; terraform silently ignores; phantom block terraform; only first block sent; terraform expand missing field; terraform attribute not in state

A Terraform attribute can be accepted, shown in a plan, and even stored in state without ever reaching the ZIA API, or without ever being read back. Terraform cannot tell the difference, so the apply succeeds (the SDK side of this is in [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding)). Each case below is a gap between the schema, the expand function (config to request), the flatten code (response to state), and the SDK request model.

## Fields the request never carries

**Forwarding control rules.** The forwarding control rule resource accepts `src_ipv6_groups`, `dest_ipv6_groups`, `zpa_application_segments` and `zpa_application_segment_groups`, but its expand function never assigns the matching SDK fields, so they are never sent. The IPv6 groups are flattened on read; the two ECZPA fields are not flattened on read either. The SDK fields are slices tagged `omitempty`. [zia.terraform.field-fidelity:fwd-control-ipv6-eczpa-never-expanded] Because the IPv6 and ECZPA selectors are dropped from the update body (ECZPA selectors apply only to the ECZPA forwarding method), an update of a rule that has them configured (in HCL or out of band) sends a body without them. Whether the API then clears the restriction, which would widen what the rule matches, or keeps it, depends on how the API treats omitted members. [zia.terraform.field-fidelity:fwd-control-update-drops-selectors]

**Selectors under the wrong key.** The CASB DLP rule resource declares `excluded_domain_profiles` and reads it back under that name, but its expand function reads the key `exclude_domain_profiles`, which is not in the schema. The domain exclusion is therefore not read from configuration on create or update. [zia.terraform.field-fidelity:casb-dlp-excluded-domains-wrong-key] A CASB DLP rule created with `excluded_domain_profiles` set is sent without that domain exclusion, so the rule is created without the narrowing the configuration asked for and applies more broadly than configured. [zia.terraform.field-fidelity:casb-dlp-wrong-key-drops-scope-exclusion]

**Attributes with no SDK field.** The cloud NSS server resource declares `web_applications_exclude` and `nw_applications_exclude`, but the SDK `NSSFeed` model has no member for them, and the resource neither expands nor reads them. A configured exclusion cannot reach the API and cannot round-trip. The inclusion fields beside them are mapped. [zia.terraform.field-fidelity:cloud-nss-exclusions-dead]

## Fields forced to a fixed value

**Fixed false values.** The firewall DNS rule resource exposes `capture_pcap` and sets it from the API response on read, but its expand function never assigns `CapturePCAP`. The SDK field has no `omitempty`, so the request always carries `capturePCAP:false`. [zia.terraform.field-fidelity:dns-capture-pcap-read-not-sent] The firewall IPS rule resource exposes `capture_pcap` but neither reads it from the response nor assigns it in the expand function. The SDK field has no `omitempty`, so the request always carries `capturePCAP:false`, and state cannot show a server-side value. [zia.terraform.field-fidelity:ips-capture-pcap-not-read-or-sent] The file type control rule resource has no `password_protected` attribute and never references the field, while the SDK model sends `passwordProtected` without `omitempty`. Every create and update therefore carries `passwordProtected:false`. [zia.terraform.field-fidelity:file-type-password-protected-never-mapped] For the DNS and IPS `capture_pcap` fields and the file type `passwordProtected` field, an unmapped non-`omitempty` bool is serialized as `false` on every write. Configuration cannot turn the setting on, and an update may turn off, if the API applies the false, a value that was enabled out of band. [zia.terraform.field-fidelity:non-omitempty-bools-force-false] Whether the API applies that false is open [gap:zia.terraform.field-fidelity:api-bool-write-effect]. The reverse trap (zero values dropped) is in [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding).

## Fields the state cannot show

**Attributes never read back.** The CASB DLP rule's `redaction_profile` and `casb_email_label`, and the CASB malware rule's `casb_email_label`, are expanded into the request but never set from the response on read. Import and refresh cannot populate them, and an out-of-band value is invisible to state. [zia.terraform.field-fidelity:casb-labels-expanded-not-flattened]

## Several blocks, one slot

The admin user resource declares `role` as a set, but its expand function sends only element zero of the set, and the SDK model holds a single role. Additional configured roles never reach the API, and which element is first is the set's iteration order, not the order written in configuration. [zia.terraform.field-fidelity:admin-user-role-first-element-only] Two more schemas accept several blocks while the SDK model holds one, and expansion keeps the first: the cloud app control rule's `cbi_profile` list, and the DLP dictionary's `adp_idm_profile` set inside each `idm_profile_match_accuracy` entry. [zia.terraform.field-fidelity:first-block-truncation-elsewhere]

## Empty objects on the wire

**Zero-value structs.** The endpoint DLP resource request model holds `printer`, `removableStorage` and `application` as value structs tagged `omitempty`, and the expand function fills `Printer` and `RemovableStorage` with a zero struct when that block is absent and never sets `Application`. A resource configured for one channel is therefore built with zero-value objects for the other channels. Go's `encoding/json` does not omit zero structs, so the body carries empty `printer`, `removableStorage` and `application` objects. Every field inside those structs is also `omitempty`, so each absent channel is sent as an empty object (`"printer":{}`, `"removableStorage":{}`, `"application":{}`). [zia.terraform.field-fidelity:endpoint-dlp-zero-struct-channels] The custom endpoint application resource requires an `application` block, but every attribute inside it is optional, and an empty block expands to a zero `Application` struct that is sent as an empty `application` object. On read, the `application` block is always written to state, populated or not. [zia.terraform.field-fidelity:endpoint-dlp-custom-app-empty-application] How the API reacts to these is open [gap:zia.terraform.field-fidelity:api-empty-object-reaction]. The general mechanism, and the other ZIA request fields held this way (cloud app control's `cbiProfile` among them), are in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes).

Rule-order effects of the same edits are in [How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order); changes still need activation ([When the ZIA Terraform provider activates configuration](kb:zia.terraform.activation)).

What to check:
1. Whether a setting that did not apply is dropped in the schema, the expand function, the read function, or the SDK JSON tag: find the attribute in each, in that order.
2. Whether the expand function names the attribute at all, since a key that is not in the schema cannot be set by any configuration.
3. What the service holds after an apply, by re-reading the object from the API rather than state, since state cannot show a server-side value.
