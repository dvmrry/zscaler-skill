# Why DLP did or did not fire: pipeline position, evaluation mode and exemptions (zia.dlp.evaluation)
Also called: dlp didn't fire; dlp not triggering; dlp ssl bypass; evaluate all rules; dlp exception rules; dlp sub rule; dlp pipeline position; cloud apps and url exceptions for dlp; enableEvaluateAllDlpRules

Three separate things decide whether a DLP rule gets a say, in this order: whether DLP is reached, which evaluation mode the tenant uses, and what is exempted.

**Is DLP reached?** For a POST request the Public Service Edge applies policies in a listed order in which Cloud App Control, URL Filtering, Malware Protection and File Type Control all come before Data Loss Prevention. [zia.dlp.evaluation:dlp-after-url-and-file-type] In the vendor's example, where File Type Control blocks outbound PDFs and the DLP policy blocks documents containing US Social Security numbers and notifies auditors, a PDF containing credit card numbers is blocked by File Type Control rather than DLP: the DLP policy is never triggered, and the auditor is not notified that a user attempted to send Social Security numbers out of the organization. [zia.dlp.evaluation:earlier-block-skips-dlp] So when an earlier policy blocks a transaction, the DLP policy is not triggered and sends no notification. [zia.dlp.evaluation:earlier-block-no-dlp] Earlier policies are in [ZIA URL Filtering](kb:zia.url-filtering) and [Cloud App Control versus URL Filtering: which applies](kb:zia.cloud-app-control.precedence). Payload-based checks, DLP among them, do not run on traffic that SSL inspection does not decrypt, so an SSL inspection bypass upstream silently removes DLP for that traffic. [zia.dlp.evaluation:decrypt-dependency] A DLP rule cannot reach traffic that SSL inspection does not decrypt, so its effective scope is the decrypted subset regardless of its own criteria. [zia.dlp.evaluation:scope-bounded-by-decryption] The decrypt side is in [Where SSL inspection sits in ZIA web policy evaluation (the two passes)](kb:zia.ssl-inspection.pipeline). Whether this is the most common cause is open [gap:zia.dlp.evaluation:ssl-bypass-most-common-cause].

**Which mode?** By default inline DLP rules are evaluated in rule order and evaluation stops at the first match. In Evaluate All Rules mode (enabled through the Zscaler account team) the service evaluates all rules and enforces the rule with the most restrictive action; the Evaluate All Rules article says that mode uses rule order only when multiple rules with the same action are matched. [zia.dlp.evaluation:evaluate-all-default-vs-mode] Whether rule order matters among parent rules in that mode differs between the articles [divergence:zia.dlp.evaluation:parent-rule-order]. The mode is set on the DLP Advanced Settings page, and all existing inline DLP rules must be deleted before the evaluation method is changed. The API exposes it as the `enableEvaluateAllDlpRules` flag of the `webDlpGlobalOptions` resource. [zia.dlp.evaluation:evaluate-all-switch] The Inline DLP Rule Evaluation setting on the DLP Advanced Settings page appears only in organizations with Evaluate All Rules mode enabled. With By Rule Order, DLP engines rely on rule order and evaluation stops when a matching rule is found; with Evaluate All Rules, if multiple rules match the rule engine selects the rule with the most restrictive action. The method applies to all of the organization's inline DLP rules, and changing it requires first deleting all existing inline DLP rules. [zia.dlp.evaluation:rule-evaluation-setting] The API shape of sub-rules is in [Web DLP rule API fields, enums and fields the contract does not document](kb:zia.dlp.rule-wire-shape). In Evaluate All Rules mode an admin can add exception rules, child rules that exclude specific users or groups from a parent rule, with no limit on how many a parent can have. The API accepts exception rules only when the tenant's inline DLP evaluation is set to evaluate all rules. [zia.dlp.evaluation:exception-rules] The About DLP page says that when the service is configured to evaluate all rules, rule order is not enforced for parent rules, exception rule evaluation stops at the first match, and an exception replaces a parent rule upon match; it also says parent rules and exception rules apply only when Evaluate All Rules mode is enabled. [zia.dlp.evaluation:exception-rule-first-match] The About page's parent-rule order statement is the other side of that difference {{divergence:parent-rule-order|ref}}.

**What is exempt?** To exempt a specific website, custom URL category or cloud application from DLP evaluation, add it to the Cloud Apps & URL Exceptions for DLP list. [zia.dlp.evaluation:exemption-list] Adding cloud applications and websites to the Cloud Apps & URL Exceptions for DLP list on the DLP Advanced Settings page stops the service inspecting them, and these exemptions override the rules created for the DLP policy: in the vendor's example, another admin's rule to inspect an exempted application has no effect, because the service does not inspect those transactions. [zia.dlp.evaluation:exemptions-override-rules] The exemption list takes up to 256 cloud applications, up to 256 URLs (each added separately) and up to 256 custom URL categories. Enabling Exempt URL Encoded Data exempts all URL encoded data from DLP evaluation. [zia.dlp.evaluation:exemption-limits] What URL encoded data covers is open [gap:zia.dlp.evaluation:url-encoded-data-scope]. The EDM modes on the same Advanced Settings page are in [Exact Data Match: index templates, data types, primary and secondary fields, dictionary matching and template processing](kb:zia.dlp.exact-data-match), and the OCR switches in [DLP file size, archive and text limits: why DLP did not catch a large file](kb:zia.dlp.inspection-limits).

Size, archive and text limits that stop inspection of a file that was reached are in [DLP file size, archive and text limits: why DLP did not catch a large file](kb:zia.dlp.inspection-limits); timeouts on large uploads are open [Unverified legacy statement: large uploads time out before DLP completes](kb:zia.dlp.inspection-limits:large-upload-timeout). Rule criteria are in [Web DLP policy rules: order, criteria and actions](kb:zia.dlp.rules).

What to check:
1. Whether the tenant evaluates rules in order to the first match or evaluates all rules, read from webDlpGlobalOptions before assuming first match.
2. Whether rules written for one evaluation mode still give the same result after the other mode is enabled.
3. Whether an exemption on the DLP Advanced Settings page, which overrides rules, covers the application, URL or custom category before reasoning over the rules that target it.
4. Which statement about rule order among parent rules in Evaluate All Rules mode is being relied on, since the articles differ.
