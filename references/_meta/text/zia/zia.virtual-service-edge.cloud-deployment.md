# Deploying a Virtual Service Edge on Azure, AWS (with or without GWLB) and GCP (zia.virtual-service-edge.cloud-deployment)
Also called: vse azure; vse aws; vse aws gwlb; vse gcp; vse ec2 instance type; vse azure load balancer; vse gcp internal load balancer; vse gateway load balancer; vzen_with_gwlb

Each public cloud has its own configuration page, and each claim here quotes its own platform's page. The Azure, AWS, AWS with Gateway Load Balancer and GCP pages each say Zscaler supports a standalone Virtual Service Edge for production deployments on that platform. [zia.virtual-service-edge.cloud-deployment:standalone-production-public-cloud] The cluster article says the opposite [divergence:zia.virtual-service-edge.cloud-deployment:standalone-production].

**Interfaces.** On Azure the first network interface is the management IP address, used for control connections to the Zscaler cloud and SSH to the VM, and the second is the service IP address; two public IPs are listed and are not required when using a NAT, which works correctly as long as it has sufficient network bandwidth. On AWS the EC2 instance has one interface (eth0) by default but a Virtual Service Edge requires an additional interface (eth1) in the same subnet; eth0 is used for control connections and SSH and eth1 for proxy services, and the two Elastic IP addresses are not required when using a NAT. The GCP page lists 3 interfaces: NIC0 for the Virtual Service Edge, NIC1 for management and an optional NIC2 for the dual arm interface. [zia.virtual-service-edge.cloud-deployment:cloud-two-nics] Which interface carries the control connection differs between pages [divergence:zia.virtual-service-edge.cloud-deployment:control-interface]. The VM specifications differ from the specifications table [divergence:zia.virtual-service-edge.cloud-deployment:vm-resources].

**Microsoft Azure.** The Azure page lists VM size Standard_E8as_v4 or Standard_E8ads_v5 for 64 GB RAM, 4 CPU cores, instance memory of 48 GB or 64 GB, Premium SSD storage, a 500 GB data disk, and the image Zscaler Internet Access Virtual Service Edge - x64 Gen1 set by default. [zia.virtual-service-edge.cloud-deployment:azure-vm] With an Azure Load Balancer the Azure page selects an availability set for VMs with Azure LB, adds each VM's service IP address to the backend pool, uses the port exposed in the health probe, offers session persistence of None, Client IP, or Client IP and protocol, and leaves the idle timeout at the default 4 minutes and Floating IP (direct server return) at the default Disabled. For health probes to work a Firewall Filtering policy rule must allow Azure proxy and load balancer IP addresses. [zia.virtual-service-edge.cloud-deployment:azure-lb]

**Amazon Web Services.** On AWS the Virtual Service Edge AMI is subscribed to from the AWS Marketplace AMIs tab and is unavailable in the China region. The page lists instance memory of 64 GB, a data disk of 501 GB with General Purpose 3 (GP3 SSD) recommended, and an EC2 instance with Elastic Network Adapter (ENA) enabled; the r7i.2xlarge type (64 GB, 8 cores, up to 12.5 Gbps, EBS-only) is listed and r8i.2xlarge is also supported based on regional availability. The instance is accessed via SSH only as the zsroot user with the private key of the selected key pair, and after deployment it receives automatic software updates from the Zscaler cloud. [zia.virtual-service-edge.cloud-deployment:aws-vm] The AWS page says it is mandatory to deploy the instance behind a VM network security group; the instance requires only outbound connections to the Zscaler cloud and no inbound connections to the organization's network from it. SSH needs port 22 open for inbound connections, and in production only a specific IP address or range should be authorized, not 0.0.0.0. [zia.virtual-service-edge.cloud-deployment:cloud-security-group] On AWS, scaling up instance memory impacts traffic through the Virtual Service Edges and must be done during a maintenance window; the page does it by selecting r7i.2xlarge and Change Instance Type. The instance might take up to 5 minutes to stop and up to 5 minutes to be SSHable again. [zia.virtual-service-edge.cloud-deployment:aws-memory-scale-up]

**AWS with Gateway Load Balancer.** On the AWS with GWLB page, the AMI is obtained by asking Zscaler Support for a share, providing the AWS account ID and region, and is then found under Ownership by checking Shared with me; a second EC2 instance is launched. The target group uses the IP addresses target type with protocol GENEVE, a health check port overridden to an unknown port (for example 50000) and the service IP addresses of both Virtual Service Edges, and the endpoint service selects Acceptance required. Each Virtual Service Edge then gets `serv_port=<Health check port configured>` in its SME configuration, and the target group status must be healthy. The page uses the Deployment Template (vzen_with_gwlb) to deploy what it calls a cluster Virtual Service Edge setup. [zia.virtual-service-edge.cloud-deployment:aws-gwlb] The health check port example differs on the page [gap:zia.virtual-service-edge.cloud-deployment:gwlb-health-port].

**Google Cloud Platform.** The GCP page lists 4 CPU cores with n2-highmem-8 as the recommended instance type, 64 GB RAM for production, and a 501 GB disk for which Zscaler recommends SSDs. The image comes from Zscaler Support, an image-family in the creation command yields a VM from the latest version of the OS image, IP forwarding is enabled and VirtIO is selected for the network interface card, and the firewall requirements are at config.zscaler.com/<Zscaler Cloud Name>/fcr. [zia.virtual-service-edge.cloud-deployment:gcp-vm] For the GCP Internal Load Balancer the page creates a health check doing a TCP port check for port 443 or 80, an unmanaged instance group holding the VM instances, and an ILB with the front end for all ports and the instance group as backend. It adds smnet_route entries for 35.191.0.0/16 (for health check probes) and 130.211.0.0/22 through the internal network gateway, and the ILB configuration can be removed with the vzen gcp-ilb-clear command. A later step runs `vzen delay-upgrade HH:MM` to stagger the upgrades on the Virtual Service Edges, which the page says avoids parallel upgrade outages as all nodes of GCP Virtual Service Edges are stand-alone. [zia.virtual-service-edge.cloud-deployment:gcp-ilb] The ingress ports are not quotable from the page [gap:zia.virtual-service-edge.cloud-deployment:gcp-ingress-ports].

The install sequence on the VM is [The Virtual Service Edge install sequence on the VM: image, certificate, network, build and verification](kb:zia.virtual-service-edge.bring-up). The Terraform modules for AWS and Azure are in [Reference Terraform modules for Virtual Service Edges on AWS and Azure](kb:zia.virtual-service-edge.reference-modules).

Sources disagree (name both sides):
- Whether Zscaler supports a standalone Virtual Service Edge for production. [divergence:zia.virtual-service-edge.cloud-deployment:standalone-production]
  - zscaler-help: The cluster article says standalone Virtual Service Edges are not supported for production environments with live user traffic.
  - zscaler-help: The Azure page says standalone is supported for production on Azure.
  - zscaler-help: The AWS page says standalone is supported for production on AWS.
  - zscaler-help: The GCP page says stand-alone is supported for production on GCP.
  - zscaler-help: The Hyper-V page says standalone is supported for production on Hyper-V.
  - zscaler-help: The Private versus Virtual comparison page says Virtual Service Edges are deployed either in clusters or standalone for production.
  - zscaler-help: The location CSV page says a single Virtual Service Edge is for testing purposes only and production environments must use clusters.
  Impact: The platform pages and the comparison page cannot all hold alongside the cluster article's statement; confirm with Zscaler before planning a production standalone.
- The VM resources the specifications table gives against the platform pages. [divergence:zia.virtual-service-edge.cloud-deployment:vm-resources]
  - zscaler-help: The specifications table gives 4 V-CPUs, 3 virtual interfaces and 500 GB of disk for every platform column.
  - zscaler-help: The AWS page lists an instance type with 8 cores, a 501 GB data disk and two network interfaces (eth0 and eth1).
  - zscaler-help: The GCP page lists a 501 GB disk.
  - zscaler-help: The Azure page lists two network interfaces.
  Impact: A sizing plan that uses the table's per-platform values (3 interfaces, 500 GB) does not match the AWS, GCP and Azure pages; the platform page is the more specific source for that platform, but the pages do not say which governs.
- Which interface carries the outbound control connection to the Zscaler cloud. [divergence:zia.virtual-service-edge.cloud-deployment:control-interface]
  - zscaler-help: In the cluster article the proxy IP address is used for the outbound control connection to the Zscaler cloud, and the load balancer IP address also makes an outbound control connection, on a three-interface VM.
  - zscaler-help: On the two-interface AWS VM the management interface carries control connections and SSH, and the service interface carries proxy services.
  - zscaler-help: On the two-interface Azure VM the management IP address is used for control connections and SSH.
  Impact: The pages come from three-interface and two-interface layouts, so a firewall or routing plan that sends the control connection from the proxy address is wrong for the cloud pages' management interface; keep each statement's platform.
