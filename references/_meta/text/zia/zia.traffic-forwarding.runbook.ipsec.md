# Runbook: IPSec tunnel hard down, Tunnel Insights status and event values, flapping and up-but-no-traffic (zia.traffic-forwarding.runbook.ipsec)
Also called: IPSec Tunnel is Hard Down; IPSec Tunnel Flapping; IPSec Tunnel is UP, but Traffic is Not Working

**Hard down.** New tenants of an organization can no longer establish IKEv1 IPSec tunnels; when setting up an IPSec tunnel for the first time, a device that only supports IKEv1 needs a Zscaler support case to enable IKEv1 for the organization, otherwise use IKEv2 (recommended for all new deployments). [zia.traffic-forwarding.runbook.ipsec:ikev1-new-tenants] In the runbook's section on troubleshooting Zscaler public DC issues, for an IPSec tunnel that will not come up, the runbook says to ping the Zscaler IPSec VIP from the customer gateway; if unreachable, check firewalls and ACLs, capture packets on the edge device and engage the ISP about IPSec restrictions. [zia.traffic-forwarding.runbook.ipsec:hard-down-reachability] The runbook says VPN credentials must be configured in the Admin Console and mapped to the location: IP-based credentials for a static IP and FQDN-based credentials for a dynamic IP. [zia.traffic-forwarding.runbook.ipsec:vpn-credentials] The gateway device must be configured with parameters compatible with Zscaler's requirements, including encryption algorithms, hash settings, phase settings and NAT-T compatibility. [zia.traffic-forwarding.runbook.ipsec:gateway-parameters]

**Tunnel Insights.** To find why an IPSec tunnel is down, the runbook says to open Analytics > Insights > Tunnel Insights and filter on Metrics Received Bytes, the IPSec source IP as Tunnel Source IP and Tunnel Type IPSec. [zia.traffic-forwarding.runbook.ipsec:tunnel-insights-filters] [divergence:zia.traffic-forwarding.runbook.ipsec:tunnel-insights-path] In Tunnel Insights for IPSec tunnels the listed Tunnel Status enum values are UP (localized name 'IPSec tunnel up'), DOWN ('IPSec tunnel down'), REKEY ('IPSec tunnel renogiated'), PHASE1_DOWN ('Phase1 is down'), PHASE2_DOWN ('Phase2 is down'), PHASE1_ERROR ('Error While Establishing Phase 1') and PHASE2_ERROR ('Error While Establishing Phase 2'). [zia.traffic-forwarding.runbook.ipsec:tunnel-status-values] The Event Reason column in Tunnel Insights takes the enum values EXPIRED ('LIfetime EXPIRED'), PSKEY_NOTFOUND ('Preshared Key NOTFOUND'), PSKEY_MISMATCH ('Preshared Key MISMATCH'), INVALID_PROPOSAL ('INVALID PROPOSAL'), DPD_TIMEOUT ('DPD TIMEOUT') and TIMEOUT ('TIMEOUT'); in its sample an Event Reason indicating a Phase 2 proposal mismatch means validating the customer's IPSec parameters against Zscaler proposals. [zia.traffic-forwarding.runbook.ipsec:event-reason-values] What each phase failure means for each reason is open [gap:zia.traffic-forwarding.runbook.ipsec:localized-names-only].

**Additional checks.** If the customer gateway is behind NAT, the runbook says NAT-T must be invoked (UDP port 4500 in packet captures and logs) and FQDN-based VPN credentials used instead of IP-based, with the FQDN configured as the IKE ID. [zia.traffic-forwarding.runbook.ipsec:nat-t-and-credential-type] Zscaler supports a maximum of 8 child security associations (Security Protection Data entries) per direction; if exceeded, traffic subnets should be consolidated into fewer policies, and entries beyond the limit are not added, which can leave traffic unrouted over the tunnel. [zia.traffic-forwarding.runbook.ipsec:sa-limit] How the 8 per direction limit relates to the Cisco ASA guide's 8 Phase 2 SAs is open [gap:zia.traffic-forwarding.runbook.ipsec:sa-limit-units]. In its additional IPSec checks the runbook says Phase-II should be configured with NULL encryption unless encrypted VPN traffic is required (additional subscription needed); aggressive mode uses PSK plus FQDN and main mode uses PSK plus IP. [zia.traffic-forwarding.runbook.ipsec:phase2-null-and-modes] Which IKE version the aggressive and main mode lines apply to is open [gap:zia.traffic-forwarding.runbook.ipsec:modes-ike-version].

**Flapping and no traffic.** For a flapping IPSec tunnel, the runbook recommends an Active/Standby pair with automatic failover based on application-layer health monitoring and HTTP probes for health (ICMP probes if the gateway does not support HTTP probes); it also says to confirm the health probes are targeting gateway.<cloudname>.net/vpntest and to enter show ip sla summary on a Cisco gateway to confirm the status of IP SLA probes. [zia.traffic-forwarding.runbook.ipsec:flapping] Scheduled maintenance on the Zscaler data center might temporarily affect IPSec tunnels, and observable packet loss can cause Layer 7 health monitoring to fail and the IPSec tunnel to flap. [zia.traffic-forwarding.runbook.ipsec:maintenance-and-loss] For an IPSec tunnel that is up but passes no traffic, the runbook says to verify static routes or policy-based routing send traffic over the tunnel, run a packet capture on the gateway, and check that encapsulated/decapsulated packets increment (show crypto isakmp sa, show crypto ipsec sa). [zia.traffic-forwarding.runbook.ipsec:up-no-traffic] MTR and latency checks are in [Runbook: MTR collection, WinMTR for Client Connector and PAC, and latency checks for GRE and IPSec gateways](kb:zia.traffic-forwarding.runbook.tunnel-path).

  Impact: The two pages give different console paths to the same Tunnel Insights view. Do not give an admin one path as the only one; check which menu the tenant's Admin Console shows.
