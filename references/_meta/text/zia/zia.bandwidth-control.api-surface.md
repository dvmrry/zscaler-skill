# Bandwidth Control API, SDK and Terraform shape (zia.bandwidth-control.api-surface)
Also called: bandwidthClasses api; bandwidthControlRules api; bandwidth class type enum; minBandwidth maxBandwidth; terraform zia_bandwidth_classes; BANDWIDTH_CAT_LARGE_FILE; bandwidth rule protocols

Bandwidth Control is fully API-manageable; the console is not the only plane. This subject holds names and enums; behavior is in the sibling subjects.

**Operations.** Bandwidth classes have list, lite list, add, get, update and delete operations: GET and POST /bandwidthClasses, GET /bandwidthClasses/lite, and GET, PUT and DELETE /bandwidthClasses/{bandwidthClassId}. [zia.bandwidth-control.api-surface:class-endpoints] Bandwidth Control rules have list, lite list, add, get, update and delete operations: GET and POST /bandwidthControlRules, GET /bandwidthControlRules/lite, and GET, PUT and DELETE /bandwidthControlRules/{ruleId}. [zia.bandwidth-control.api-surface:rule-endpoints]

**Rule fields.** The rule's minimum and maximum are the integer fields minBandwidth and maxBandwidth, documented as percentages of a location's bandwidth per selected class, covering uploads and downloads together. [zia.bandwidth-control.api-surface:min-max-fields] Those are the console's guaranteed and maximum percentages ([How Bandwidth Control allocates bandwidth: minimum, maximum, contention](kb:zia.bandwidth-control.allocation)). Besides locations, location groups, time windows, labels, bandwidth classes and protocols, the rule schema also carries devices, deviceGroups and deviceTrustLevels. [zia.bandwidth-control.api-surface:rule-scope-fields] The console Help groups the rule conditions as Where (locations or location groups), When (time) and What (bandwidth classes and protocols), so the schema's device, device group and device trust level fields have no counterpart among the conditions it documents. [zia.bandwidth-control.api-surface:device-fields-not-in-help] The API schema lists these rule protocol values: ANY_RULE, DOHTTPS_RULE, TUNNELSSL_RULE, HTTP_PROXY, FOHTTP_RULE, FTP_RULE, HTTPS_RULE, HTTP_RULE, SSL_RULE and TUNNEL_RULE. [zia.bandwidth-control.api-surface:protocols-spec] The Terraform bandwidth rule resource requires at least one protocol and validates it with the URL Filtering protocol list, `supportedURLFilteringProtocols`: SMRULEF_ZPA_BROKERS_RULE, ANY_RULE, TCP_RULE, UDP_RULE, DOHTTPS_RULE, TUNNELSSL_RULE, HTTP_PROXY, FOHTTP_RULE, FTP_RULE, HTTPS_RULE, HTTP_RULE, SSL_RULE, TUNNEL_RULE, WEBSOCKETSSL_RULE and WEBSOCKET_RULE. [zia.bandwidth-control.api-surface:protocols-terraform] The Adding Rules article offers the Protocols condition "If you have the Firewall subscription", with eleven choices: DNS over HTTPS, FTP over HTTP, HTTP, HTTP Proxy, HTTPS, Native FTP, SSL/TLS (SSL/TLS traffic that isn't decrypted, for example hosts exempted from SSL/TLS Inspection), Tunnel (unidentified encrypted traffic, for example tunneling applications encapsulated in HTTP or HTTPS), Tunnel SSL/TLS (an undecodable protocol within an SSL/TLS connection), WebSocket and WebSocket SSL/TLS. [zia.bandwidth-control.api-surface:help-protocol-choices] The protocol lists disagree [divergence:zia.bandwidth-control.api-surface:protocol-vocabulary]. The Terraform bandwidth rule schema allows at most 8 locations and 32 location groups per rule. [zia.bandwidth-control.api-surface:tf-location-caps] The Help location limit differs [divergence:zia.bandwidth-control.api-surface:locations-per-rule]. Rule order, state and rank semantics: [Bandwidth Control rules: terms, order and rank](kb:zia.bandwidth-control.rules); provider reorder behavior: [The ZIA provider's reorder registry: keys, locks and lifecycle across rule resources](kb:zia.terraform.rule-order.registry).

**Class typing.** A bandwidth class has a read-only type with the values ANY, NONE, BANDWIDTH_CAT_WEBCONF, BANDWIDTH_CAT_VOIP, BANDWIDTH_CAT_GENERAL_SURFING, BANDWIDTH_CAT_LARGE_FILE, BANDWIDTH_CAT_SALES, BANDWIDTH_CAT_FINANCE, BANDWIDTH_CAT_MEDIA and BANDWIDTH_CAT_FSHARE. [zia.bandwidth-control.api-surface:class-type-enum] The eight non-generic type values appear to correspond to the eight predefined classes: five Cloud Applications classes (General Surfing, Sales/Support Apps, Finance, Streaming Media, File Share), Large Files, Web Conferencing and VoIP. [zia.bandwidth-control.api-surface:types-match-predefined] The Large Files size values are ANY, NONE, FILE_5MB, FILE_10MB, FILE_50MB, FILE_100MB, FILE_250MB, FILE_500MB and FILE_1GB in the API; the Terraform resource accepts FILE_5MB, FILE_10MB, FILE_50MB, FILE_100MB, FILE_250MB, FILE_500MB and FILE_1GB (not ANY or NONE). [zia.bandwidth-control.api-surface:file-size-enum] The class applications field takes ANY, NONE, NETSUITE, DROPBOX, BOXNET, YOUTUBE, METACAFE, HULU, DAILYMOTION, SHOUTCAST, SALESFORCE_1, SKYPE, WEBEX, GOTOMEETING, LIVEMEETING, CONNECT and INTERCALL. Terraform accepts only WEBEX, GOTOMEETING, LIVEMEETING, INTERCALL and CONNECT for a web conferencing class, and only SKYPE (or an empty value) for a VoIP class. [zia.bandwidth-control.api-surface:application-values]

**Terraform.** Terraform splits the class object into three resources: zia_bandwidth_classes (urls, url_categories, web_applications; no type or applications field), zia_bandwidth_classes_file_size (defaults type to BANDWIDTH_CAT_LARGE_FILE) and zia_bandwidth_classes_web_conferencing (type BANDWIDTH_CAT_WEBCONF or BANDWIDTH_CAT_VOIP, plus applications). [zia.bandwidth-control.api-surface:tf-class-resources] The file-size and web conferencing resources do not create a class: each finds the existing class by name and updates it with PUT. Destroying either is a no-op. [zia.bandwidth-control.api-surface:tf-wrappers-update-existing] The Terraform bandwidth control rule documentation says the resource is only supported through Zscaler OneAPI. [zia.bandwidth-control.api-surface:tf-rule-oneapi-only] Whether the class resources share the restriction is not stated [gap:zia.bandwidth-control.api-surface:tf-classes-oneapi-only]. Terraform destroy semantics in general: [How the ZIA Terraform provider detaches references before deleting objects](kb:zia.terraform.delete-detach). The Large Files size field is named differently in the schema and the SDK [divergence:zia.bandwidth-control.api-surface:file-size-field-name].

What to check:
1. Whether the live response for a class matches the type and size names before relying on them.
2. Whether the protocol values in use are accepted by the service, given that the schema and the provider lists differ.

Sources disagree (name both sides):
- Which protocol values a Bandwidth Control rule accepts [divergence:zia.bandwidth-control.api-surface:protocol-vocabulary]
  - api-specs: The API schema lists ten values and none of WEBSOCKET_RULE, WEBSOCKETSSL_RULE, TCP_RULE, UDP_RULE or SMRULEF_ZPA_BROKERS_RULE.
  - tf-zia: The provider validates against the URL Filtering list, which includes the WebSocket values.
  - zscaler-help: The Adding Rules Help article lists eleven protocol choices including WebSocket and WebSocket SSL/TLS, which the API enum lacks and the provider list includes; its eleven choices contain no TCP, UDP or ZPA value, which the provider list includes (claim help-protocol-choices).
  Impact: A configuration using a value only the provider accepts may be rejected by the service, and a value the provider rejects cannot be sent through Terraform even if the service accepts it.
- How many locations one rule can reference [divergence:zia.bandwidth-control.api-surface:locations-per-rule]
  - tf-zia: The Terraform schema caps locations at 8 per bandwidth rule.
  - zscaler-help: Ranges and Limitations lists 32 locations per rule for all policy rule types.
  - zscaler-help: The Adding Rules Help article says a rule takes up to 32 locations.
  Impact: A rule that needs 9 to 32 locations cannot be written through the provider; use location groups (32) or split the rule, even if the service would accept more.
- Name of the file-size field on a class [divergence:zia.bandwidth-control.api-surface:file-size-field-name]
  - api-specs: The API schema names the field getfileSize.
  - sdk-python: The Python SDK model reads fileSize.
  Impact: One of the two spellings may never be populated; code that reads or writes the Large Files size should confirm the wire name against a live response.
