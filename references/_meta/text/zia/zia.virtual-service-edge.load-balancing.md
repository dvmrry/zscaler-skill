# How a Virtual Service Edge cluster spreads and returns traffic (zia.virtual-service-edge.load-balancing)
Also called: vse load balancer; vse carp; vse dsr; vse external load balancer; vse promiscuous mode; vse forged transmits; vse cloud load balancer; vse multi-cluster load sharing; vse firewall bypass rule

**Inside the cluster.** Each Virtual Service Edge has a load balancer bundled in, designed to distribute user traffic evenly across the Virtual Service Edges. [zia.virtual-service-edge.load-balancing:bundled-lb] The load balancers use CARP for active-passive fault tolerance: all Virtual Service Edge instances in the cluster are active, one load balancer instance is active at a time, it receives ingress traffic through the cluster IP address and directs it to the appropriate Virtual Service Edge, and if it fails the passive load balancer takes over automatically with no service disruption. [zia.virtual-service-edge.load-balancing:carp-active-passive] In a cluster, Virtual Service Edges run in Direct Server Return mode: requests go through the load balancer to the Virtual Service Edge, but the response flows from the Virtual Service Edge to the user, skipping the load balancer on the return. [zia.virtual-service-edge.load-balancing:dsr] This is the same CARP and DSR model as the hardware cluster ([How a Private Service Edge cluster is built and fails over](kb:zia.private-service-edge.cluster-architecture)); the difference is that the customer runs it. As with the hardware cluster, the return path does not come back through the load balancer, so stateful devices between the cluster and clients must tolerate it.

**What must be true on ESXi for CARP to work.** On ESXi, Promiscuous Mode (Accept), MAC Address Changes and Forged Transmits must be enabled on the vSwitch or port group; promiscuous mode is required because the Zscaler load balancers and Service Edges use CARP. Zscaler recommends a dedicated port group, because vSwitch-level promiscuous mode can let other VMs on the vSwitch sniff Virtual Service Edge traffic. [zia.virtual-service-edge.load-balancing:esxi-vswitch-settings] If a vSwitch has multiple physical ports, the ESXi host advanced option Net.ReversePathFwdCheckPromisc must be enabled (set to 1); otherwise multicast traffic loops back to the host, CARP does not function properly, and 'link states coalesced' messages are sent. [zia.virtual-service-edge.load-balancing:esxi-reverse-path-check]

**Probes.** The load balancer checks each member (see [The Virtual Service Edge cluster: limits, object, build order and Location binding](kb:zia.virtual-service-edge.clusters)). For the load balancer's health probes to work, a Firewall Filtering rule must allow all Virtual Service Edge proxy, load balancer and cluster IP addresses as sources, with the Allow action. [zia.virtual-service-edge.load-balancing:health-probe-firewall-rule] Firewall policy semantics are [ZIA Firewall Control](kb:zia.firewall).

**Which platform gets which model.** In the VMware ESXi and Microsoft Hyper-V environments, Zscaler recommends the in-built load balancer for Virtual Service Edges deployed in cluster mode; in public cloud environments the native cluster mode is not supported, and public cloud load balancers can provide the redundancy. [zia.virtual-service-edge.load-balancing:inbuilt-lb-recommended-on-esxi] Platform cluster support, including the Hyper-V disagreement, is [Where a Virtual Service Edge runs and which platforms can cluster](kb:zia.virtual-service-edge.platforms).

**External load balancers.** Zscaler does not recommend external load balancers; an organization that must use one is pointed to a separate article, Using an External Load Balancer with Virtual Service Edges. [zia.virtual-service-edge.load-balancing:external-lb-discouraged] If clustering fault tolerance is required, a Standalone deployment needs an external load balancer; the specifications article notes that Virtual Service Edges with an External Load Balancer are deployed in certain situations. [zia.virtual-service-edge.load-balancing:standalone-needs-external-lb-for-ha] If the organization's compliance requirements do not allow the required changes to the virtual switches to use the built-in load balancer, an external load balancer can be used instead. [zia.virtual-service-edge.load-balancing:external-lb-when]

**The built-in load balancer.** The VM images include a load balancer along with the Virtual Service Edge, and Zscaler recommends using the built-in load balancer, which distributes traffic on a per-session basis, monitors health and prunes Virtual Service Edges that fail health checks (adding them back when they report good health), and updates cluster members consecutively with zero downtime. Using it requires enabling Promiscuous mode on the virtualization platform, which can instead be restricted to a dedicated port group containing just the Zscaler VMs. [zia.virtual-service-edge.load-balancing:builtin-lb-benefits]

**Using an external load balancer.** Whether Zscaler recommends external load balancers at all differs between pages [divergence:zia.virtual-service-edge.load-balancing:external-lb-recommendation]. Of the two options the external load balancer page gives for using an external load balancer, it marks clustered Virtual Service Edges without the required switches "(Recommended)"; that label applies among the external options only. Because the instances cannot talk to each other, each assumes it is the only cluster member, becomes the primary member and owns the cluster IP. The external load balancer forwards traffic directly to the Virtual Service Edge IP (not the cluster IP), balances per session with optional Client IP persistence, and monitors the Virtual Service Edge IP address (not the cluster IP). From the cloud's point of view the instances are individual members of the same cluster, so updates occur consecutively with zero downtime. [zia.virtual-service-edge.load-balancing:external-lb-clustered] Virtual Service Edges can be deployed in standalone mode with an external load balancer to distribute the load, and updates for standalone instances behind one should be scheduled to avoid downtime. [zia.virtual-service-edge.load-balancing:external-lb-standalone] For an external load balancer the page lists three probes to use one of: an ICMP ping to the service IP, a TCP port check to the proxy ports, and HTTP probes to an externally hosted web server via proxy, which need a suitable policy on the Virtual Service Edge to allow the probes. [zia.virtual-service-edge.load-balancing:external-lb-probes]

**Multi-Cluster Load Sharing.** Multi-Cluster Load Sharing is described for Public Service Edge clusters in Zscaler data centers: several clusters in different network address blocks serve the same VIP, so Zscaler can add capacity without customers moving their GRE tunnels. [zia.virtual-service-edge.load-balancing:mcls-is-public-se-only]

Sources disagree (name both sides):
- Whether Zscaler recommends an external load balancer. [divergence:zia.virtual-service-edge.load-balancing:external-lb-recommendation]
  - zscaler-help: The clusters article says Zscaler does not recommend using external load balancers.
  - zscaler-help: The external load balancer article labels the clustered-without-switches external option "(Recommended)" and also says Zscaler recommends using the built-in LB.
  Impact: The two pages agree that the built-in load balancer is preferred; the "(Recommended)" label ranks the two external options against each other, so it should not be read as a recommendation of external over built-in.
