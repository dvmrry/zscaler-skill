# ZIA Data Loss Prevention (zia.dlp)
Also called: dlp; data loss prevention; inline dlp; web dlp; why didn't dlp fire; dlp policy; zia data protection

DLP has three layers, and a question about "why did or didn't DLP act" has to be asked in order.

1. **What is detected?** Dictionaries are the detection primitives ([DLP dictionaries: predefined, cloned and custom](kb:zia.dlp.dictionaries)). They are grouped into engines with Boolean expressions ([DLP engines: the unit a rule references](kb:zia.dlp.engines)), and a rule references engines, not dictionaries ([DLP policy rules and Endpoint DLP policy rules must reference engines, not dictionaries. To use a custom dictionary in a rule, put it in an engine first.](kb:zia.dlp.engines:rules-reference-engines)).
2. **Which rule applies and what does it do?** Order, criteria, Match Only, Confirm and the save-time constraints are in [Web DLP policy rules: order, criteria and actions](kb:zia.dlp.rules); the API names and enums are in [Web DLP rule API fields, enums and fields the contract does not document](kb:zia.dlp.rule-wire-shape).
3. **Was DLP reached, and in which mode?** Upstream blocks, the decrypt dependency, Evaluate All Rules mode, exception rules and exemptions are in [Why DLP did or did not fire: pipeline position, evaluation mode and exemptions](kb:zia.dlp.evaluation), with the SSL side in [Where SSL inspection sits in ZIA web policy evaluation (the two passes)](kb:zia.ssl-inspection.pipeline) and the URL side in [ZIA URL Filtering](kb:zia.url-filtering). If DLP was reached but a large file was not inspected, see [DLP file size, archive and text limits: why DLP did not catch a large file](kb:zia.dlp.inspection-limits).

Authoring a custom Patterns & Phrases dictionary is in [Custom Patterns & Phrases dictionaries: pattern syntax, phrase matching, match types and sub-dictionaries](kb:zia.dlp.dictionary-patterns), the Index Tool that builds EDM and IDM index templates in [DLP Index Tool: configuration object, VM requirements and deployment notes for VMware, AWS and Azure, SSO and VM commands](kb:zia.dlp.index-tool), Exact Data Match templates and dictionaries in [Exact Data Match: index templates, data types, primary and secondary fields, dictionary matching and template processing](kb:zia.dlp.exact-data-match), Indexed Document Match templates in [Indexed Document Match: IDM templates, limits, scheduling and match accuracy](kb:zia.dlp.indexed-document-match), and Microsoft Information Protection accounts and label retrieval in [Microsoft Information Protection (MIP) accounts and label retrieval](kb:zia.dlp.mip-labels).

After a match, notification, ICAP, Incident Receiver and Cloud-to-Cloud forwarding are in [Where a DLP match goes: notification, ICAP, Incident Receiver and Cloud-to-Cloud](kb:zia.dlp.incident-forwarding), and the auditor email templates and their macros are in [DLP notification templates: auditor email subject, macros, attachments and TLS](kb:zia.dlp.notification-templates). The ICAP receivers are in [ICAP receivers for DLP: secure and unencrypted ICAP, the FCC cloud and mTLS](kb:zia.dlp.icap-receivers), the Incident Receiver's deployment in [Zscaler Incident Receiver: requirements per platform, storage, health check and VM commands](kb:zia.dlp.incident-receiver) and Cloud-to-Cloud storage onboarding in [Cloud-to-Cloud Incident Forwarding: storage onboarding for AWS, Google Cloud and Azure](kb:zia.dlp.cloud-to-cloud-forwarding).

Endpoint DLP and Outbound Email DLP are separate API families: [Endpoint DLP API families in the SDKs and Terraform provider](kb:zia.dlp.endpoint-dlp), [Outbound Email DLP rules in the SDKs and Terraform provider](kb:zia.dlp.outbound-email). How Outbound Email DLP policy works is in [Outbound Email DLP policy: smart host flow, per-recipient evaluation, criteria and header actions](kb:zia.dlp.outbound-email-policy), its email tenants and mail-server setup in [Outbound Email DLP email tenants and mail-server setup (SEG, Gmail, Exchange)](kb:zia.dlp.outbound-email-tenants), and the domain and recipient profiles in [DLP domain profiles and recipient profiles](kb:zia.dlp.email-profiles).

How Endpoint DLP policy reaches endpoints and a rule is chosen is in [How Endpoint DLP reaches the endpoint: prerequisites, policy delivery, offline enforcement, scans, and what the vendor says about evaluating all rules and exception rules](kb:zia.dlp.endpoint-enforcement), its rules in [Endpoint DLP policy rules: channels, criteria, actions (Allow, Block, Confirm, Protect) and notifications](kb:zia.dlp.endpoint-rules), its resources in [Endpoint DLP resources and resource tags: network shares, printers, removable storage, endpoint applications](kb:zia.dlp.endpoint-resources) and its settings in [Endpoint Data Scan configuration: scan reporting, End User Reports, continuous and real-time classification, exemption, trusted applications, channel exceptions, activation](kb:zia.dlp.endpoint-settings). Endpoint Data Scan reports are in [Endpoint Data Scan reports: the daily data-at-rest report, User and Device Investigation, DLP Operational and the End User Report](kb:zia.dlp.endpoint-data-scan), the endpoint inventory in [Endpoint inventory and Application Investigation: detected removable storage, printers, portable devices and applications](kb:zia.dlp.endpoint-inventory), Endpoint IDM, EDM and Share Files Externally in [Endpoint IDM, Endpoint EDM and Share Files Externally](kb:zia.dlp.endpoint-sensitive-information), Indicators of Intent in [Indicators of Intent: predefined risky-behaviour rules on the endpoint and their exceptions](kb:zia.dlp.endpoint-intent), and Device Control in [Device Control rules per device class, the default rule, first-match evaluation and device control resources](kb:zia.dlp.endpoint-device-control). Endpoint Context, the application telemetry that shares the resources page, is in [Endpoint Context: endpoint application telemetry from Client Connector, the policies that use it, and the Application Investigation page](kb:zia.endpoint-context).

Paging pitfalls for ZIA lists are in [How the Go SDK pages through ZPA, ZCC and ZTC lists, and when it stops early](kb:shared.sdk-go.list-pagination).

- decided-by references/_meta/text/zia/zia.dlp.evaluation.md (Why DLP did or did not fire: pipeline position, evaluation mode and exemptions): By default inline DLP rules are evaluated in rule order and evaluation stops at the first match. In Evaluate All Rules mode (enabled through the Zscaler account team) the service evaluates all rules and enforces the rule with the most restrictive action; the Evaluate All Rules article says that mode uses rule order only when multiple rules with the same action are matched. [zia.dlp.evaluation:evaluate-all-default-vs-mode]
- decided-by references/_meta/text/zia/zia.dlp.rules.md (Web DLP policy rules: order, criteria and actions): DLP policy rules are evaluated in ascending rule order and, by default, evaluation stops at the first match; a disabled rule keeps its place in the order while the service skips it. Evaluate All Rules mode (see zia.dlp.evaluation) changes this. [zia.dlp.rules:ascending-order]
- depends-on references/_meta/text/zia/zia.ssl-inspection.pipeline.md (Where SSL inspection sits in ZIA web policy evaluation (the two passes)): Payload-based checks, DLP among them, do not run on traffic that SSL inspection does not decrypt, so an SSL inspection bypass upstream silently removes DLP for that traffic. [zia.dlp.evaluation:decrypt-dependency]
