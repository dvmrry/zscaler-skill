# Forwarding methods Zscaler supports and how to choose (zia.traffic-forwarding.methods)
Also called: traffic forwarding methods; gre vs ipsec; which forwarding method; how does traffic reach zia; pac vs zcc; forwarding best practice

Zscaler describes seven ways to get traffic to the service, and a tenant normally uses several at once. Zscaler supports Client Connector, GRE tunnels, IPSec tunnels, PAC files, proxy chaining, Cloud Connector and Branch Connector as traffic forwarding mechanisms; a tenant can use one or a combination. [zia.traffic-forwarding.methods:supported-set] Zscaler recommends forwarding all internet traffic (all protocols, all ports) to the service, using a combination of tunneling, PAC files, Surrogate IP and Client Connector. The stated benefits are that all platform features (Bandwidth Control, Firewall, group and department policy) are available and that sublocations can apply different policy by IP address. [zia.traffic-forwarding.methods:recommended-combination] Where the full combination cannot be deployed at every location, Zscaler lists three alternatives for some locations: tunneling with PAC files and Surrogate IP, tunneling with PAC files, and tunneling with Surrogate IP; PAC files sent to a dedicated proxy port are a fourth pattern. [zia.traffic-forwarding.methods:alternative-combinations]

Choosing for a site: A GRE tunnel needs a router or switch that supports GRE and whose egress port has a static address; IPSec is the option when the router does not support GRE or the site uses dynamic IP addresses. [zia.traffic-forwarding.methods:tunnel-choice] The numbers that separate them (per-tunnel bandwidth) are in [GRE tunnels to ZIA: requirements, bandwidth and deployment](kb:zia.traffic-forwarding.gre) and [IPSec tunnels to ZIA: limits, IKE and device settings](kb:zia.traffic-forwarding.ipsec). GRE and IPSec tunnels both forward all ports and protocols, fail over when the primary Public Service Edge is unavailable, need no configuration on computers, and cannot be bypassed by users on a known corporate network. [zia.traffic-forwarding.methods:tunnel-benefits] The limitations the guide lists for a combination of tunneling and Surrogate IP include that there is no protection for remote users outside the office, because that traffic cannot be forwarded to the service, and that managing applications that need to be excluded from the service becomes difficult without PAC files. [zia.traffic-forwarding.methods:tunnels-do-not-follow-users] Remote users are covered by [Client Connector as a forwarding method: benefits, limits and Z-Tunnel modes](kb:zia.traffic-forwarding.zcc) or by a PAC file ([PAC file forwarding: limits, versions and what it cannot cover](kb:zia.traffic-forwarding.pac)); an existing on-premises proxy can be chained ([Proxy chaining to ZIA: setup, XFF handling and limits](kb:zia.traffic-forwarding.proxy-chaining)).

Cloud Connector establishes zero trust access for server-to-server traffic, east-west traffic in a public cloud, IT/OT networks and data centers, and is supported on AWS and Azure; Branch Connector is a virtual machine that forwards branch traffic directly to the Zero Trust Exchange. [zia.traffic-forwarding.methods:connector-products]

The throughput threshold for choosing GRE over IPSec is open [gap:zia.traffic-forwarding.methods:throughput-threshold], the recommended pairings by site type are open [gap:zia.traffic-forwarding.methods:combined-patterns], and whether every method surfaces as a Location is open [gap:zia.traffic-forwarding.methods:location-per-method]. Traffic from an unconfigured source is remote user traffic: [What a ZIA location is and what the console enforces for it](kb:zia.locations.model).

What to check:
1. Which method each site actually uses, read from the location's tunnel or credential rather than from the architecture diagram.
2. Whether remote users have a second method, since a tunnel does not protect users outside the office.
