# When the ZIA Terraform provider reports success after an error, or crashes (zia.terraform.error-handling)
Also called: terraform provider panic; provider crashed nil pointer; index out of range update; terraform refresh succeeds but api failed; error swallowed terraform read; duplicate rules after terraform create; terraform destroy succeeded but rule still in state; plugin crashed zia; dlpWebRulesLock; Update returned nil, nil

The ZIA provider (writes it makes are activated separately, see [When the ZIA Terraform provider activates configuration](kb:zia.terraform.activation)) in some places reports success when an API call failed, and in a few places it crashes instead of returning an error. Both are bad for policy work: the operator sees a clean apply or refresh, or a dead provider, and the tenant is in a state nobody confirmed.

**Refresh and Read.** The FTP control policy Read returns `nil` diagnostics when the SDK getter fails, before it touches the resource data. The SDK getter returns `(nil, err)` on a failed request, so a failed refresh produces no error and no change to what Terraform holds. [zia.terraform.error-handling:read-error-returns-nil] The same swallow is repeated in 12 settings-style resources and 10 data sources: ATP (malicious URLs, malware inspection, malware policy, malware protocols, malware settings, security exceptions, settings), browser control, DLP global options, FTP control, security policy settings, URL filtering and cloud app settings; and the data sources for ATP malware inspection/policy/protocols/settings, ATP settings, browser control, DLP global options, sandbox behavioral analysis advanced settings, security policy settings and URL filtering and cloud app settings. [zia.terraform.error-handling:read-error-returns-nil-sites]

**Writes after a failed check.** Update first calls the object's Get and only reacts when the error is an object-not-found response (clearing the ID and returning). Any other Get error is dropped and execution continues straight into the write with the request built from configuration. [zia.terraform.error-handling:update-preflight-ignores-errors] The same preflight shape (Get, react only to object-not-found, then write) is used in at least 46 resources (about 50 files and 52 handlers by a looser search, which adds admin users, the two bandwidth classes and the DC exclusions Delete), including 2 Delete handlers (email profile and extranet; a Delete that falls through still reports its own error). Resources: admin_roles alerts bandwidth_classes bandwidth_control_rules casb_dlp_rules casb_malware_rules cloud_app_control_rules cloud_application_instance cloud_nss_server custom_file_types dlp_dictionaries dlp_engines dlp_notification_templates dns_application_groups email_profile endpoint_dlp_rules extranet file_type_control_rules firewall_dns_rules firewall_filtering_rules firewall_ips_rules forwarding_control_proxies forwarding_control_rule forwarding_control_zpa_gateway fw_filtering_ip_source_groups fw_filtering_network_application_groups fw_filtering_network_services fw_filtering_network_services_groups ips_signature_rules location_management nat_control_rules nss_server risk_profiles rule_labels sandbox_rules ssl_inspection_rules tenant_restriction_profile traffic_capture_rules traffic_forwarding_gre_tunnels traffic_forwarding_vpn_credentials ueba_alert_definitions url_filtering_rules user_management_users vzen_cluster vzen_nodes workload_groups. [zia.terraform.error-handling:update-preflight-sites]

**Destroy on not-found.** When the DLP web rule delete call fails with RESOURCE_NOT_FOUND, Delete treats the rule as already gone and returns `nil` diagnostics. It returns before `d.SetId("")` and before the activation step, so nothing triggers activation for this destroy. [zia.terraform.error-handling:not-found-destroy-keeps-id] The same early return on not-found is in the Delete handlers of endpoint DLP rules, endpoint DLP sub-rules and outbound email DLP. [zia.terraform.error-handling:not-found-destroy-keeps-id-sites]

**Create retries and starting order.** In DLP web rule create, after the POST succeeds and the ID is set, a Read that returns an error diagnostic makes the create loop sleep and `continue` while time remains in the create timeout. The `continue` returns to the top of that `for` loop, whose body calls `dlp_web_rules.Create` with `&req` again; the object from the first POST is not adopted before it. [zia.terraform.error-handling:create-reposts-after-read-error] The same post-then-Read-error retry loop is in seven rule resources: bandwidth control, CASB DLP, CASB malware, DLP web, endpoint DLP (parent rules), NAT control and outbound email DLP. [zia.terraform.error-handling:create-reposts-after-read-error-sites] A second POST of the same rule may create a duplicate policy rule, or may be rejected (for example on a name clash), leaving the first rule created but the apply failing. The code shows only that the second POST is sent. [zia.terraform.error-handling:duplicate-post-result] Bandwidth control create discards the error from listing existing rules, treats an empty list as no rules, falls back to order 1, and POSTs the rule at that order; a failed list is therefore indistinguishable from an empty policy. From v4.8.15 the cached starting order is incremented after each successful POST. [zia.terraform.error-handling:create-order-from-ignored-list-error] Create paths discard the list error the same way in file type control, firewall DNS, firewall IPS, forwarding control, NAT control, sandbox, SSL inspection, traffic capture, DLP web, endpoint DLP and outbound email DLP (via GetAll), and in CASB DLP, CASB malware and cloud app control (via GetByRuleType). URL filtering did so up to v4.8.13; from v4.8.14 its create gets the starting order through `urlFilteringEndPosition`, which returns the list error. Firewall filtering did so up to v4.8.14; from v4.8.15 its create returns the list error. [zia.terraform.error-handling:create-order-from-ignored-list-error-sites] Where a rule ends up afterwards is decided by the reorder worker; see [How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order).

**Crashes on update.** Before v4.8.11, sandbox rule update logged a failed list of existing rules, removed the default rule from whatever came back, sorted, and read the last element with no length check, so an empty result (a failed list) panicked with an index out of range instead of returning an error. v4.8.11 returns the list error before the filter and the index (#610); at v4.8.13 the index itself still has no length check. v4.8.14 replaces the index: after the default rule is filtered out, the end of the list comes from `endOfList`, which starts at order 1, and that end-of-list read is made only when `rank` changed. [zia.terraform.error-handling:sandbox-update-index-after-logged-error] Before v4.8.11 the same log-then-index-last-element update code was in eight more rule resources besides URL Filtering and the sandbox rules above: cloud app control, file type control, firewall filtering, firewall DNS, firewall IPS, forwarding control, SSL inspection and traffic capture. v4.8.11 makes all of them return the list error before the index (#610). Endpoint DLP update has a `len(existingRules) > 0` guard and does not share the index panic; at v4.8.13 its list error is still only logged. v4.8.14 removes the index from all of these: the end of the list comes from `endOfList`, which starts at order 1, and a list error is returned. [zia.terraform.error-handling:update-index-panic-sites] Up to v4.8.13, in the sandbox rules and firewall DNS rules update paths, the order of the last rule in the sorted list of existing rules was taken as `nextAvailableOrder`, and the rule was then updated with rank 7 and that order, so it was parked at the end of the policy before the reorder helper was called. From v4.8.14 neither update does this on every update: each takes the end of the list from `endOfList` and writes there with rank 7 only when `rank` changed. [zia.terraform.error-handling:update-parks-at-last-rule-order] Up to v4.8.13 the same park-at-the-end sequence (`nextAvailableOrder` from the last element, rank 7, that order) followed the same index in the other rule resources listed under the index-panic claim. From v4.8.14 none of them has it: they take the end of the list from `endOfList`, and only when `rank` changed. [zia.terraform.error-handling:update-parks-sites] URL Filtering is covered in [How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order).

**Empty update replies.** Rule label update in the SDK ignores the result of its type assertion and reads the object's ID from it, the same shape as URL Filtering Update. An empty update response (nil result, nil error) makes it dereference a nil pointer. [zia.terraform.error-handling:rule-labels-update-same-assertion] The unchecked assertion followed by a field read is in about 68 SDK service functions across about 66 files, mostly each service's Update. Among them are the services behind the provider's admin roles, alerts, bandwidth control, CASB rules, DLP web rules, endpoint DLP, firewall and DNS rules, forwarding, IPS, location management, NAT control, sandbox rules, SSL inspection, traffic capture, GRE tunnels, static IPs, VPN credentials, URL categories, users, VZEN and workload group resources. [zia.terraform.error-handling:empty-body-panic-sites] The nil dereference on an empty update reply happens after the SDK has received the server's answer to the PUT, so the panic cannot undo a change the server has already applied. [zia.terraform.error-handling:empty-reply-panic-follows-server-answer] The mechanism and the URL Filtering instance are in [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding).

**DLP web rule create.** DLP web subrule create takes the global rule lock, then fetches the parent rule and discards the error. The SDK Get returns `(nil, err)` on failure, so the next line reads `SubRules` through a nil pointer and panics while the lock is held. [zia.terraform.error-handling:dlp-web-subrule-create-nil-deref-under-lock] Inside that locked section, a failed Get of any subrule returns the error directly, and the panic above also unwinds, without releasing `dlpWebRulesLock`. The lock is released only by one explicit `Unlock` later in the loop body. Every later DLP web rule create (parent or subrule) then blocks on the same lock for the life of the provider process. [zia.terraform.error-handling:dlp-web-lock-not-released-on-error]

For the settings and omitted-value side of these update paths, see [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes); for the delete-side detach helper, [How the ZIA Terraform provider detaches references before deleting objects](kb:zia.terraform.delete-detach). Activation after each change is in [When the ZIA Terraform provider activates configuration](kb:zia.terraform.activation).

What to check:
1. Whether a clean refresh or apply actually read these settings, by re-reading them from the API, since a failed read returns no error.
2. Whether a rule was posted twice after a create that took unusually long or errored: list the rules by name and look for a second copy or an unmanaged first one.
3. Whether a failed parent or subrule read happened earlier in the run, when DLP web rule creates hang or a subrule create crashes the provider.
