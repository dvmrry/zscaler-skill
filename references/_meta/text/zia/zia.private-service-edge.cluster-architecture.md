# How a Private Service Edge cluster is built and fails over (zia.private-service-edge.cluster-architecture)
Also called: pse cluster design; pse carp; pse direct server return; pse dsr; pse vip; pse load balancer; standalone pse; pse n+1; pse asymmetric return

A Private Service Edge comprises two Zscaler components: Service Edge instances and Zscaler load balancers (LBs). [zia.private-service-edge.cluster-architecture:two-components] The Service Edge instance processes upload (the request: user traffic from the LB instance to the destination) and download (the response: traffic from the destination to the user). The LB instance distributes the users' upload transactions evenly across the Service Edge instances. [zia.private-service-edge.cluster-architecture:upload-download-roles] Standard deployments of all the models use integrated LB instances that process upload and download transactions in the same hardware. Larger deployments with significant upload and download throughput require the Private Service Edge 5 with the Dedicated LB cluster design. [zia.private-service-edge.cluster-architecture:integrated-vs-dedicated-lb]

**Failover.** All Private Service Edge cluster designs are deployed with a minimum of N+1 hardware. [zia.private-service-edge.cluster-architecture:n-plus-one] The LB instances run active-passive and share a virtual IP (VIP) address using Common Address Redundancy Protocol (CARP). [zia.private-service-edge.cluster-architecture:carp-lb-pair] All Service Edge instances are active-active behind the cluster VIP and are removed from the load-balancing pool automatically, through active health monitoring, if an instance or node fails. [zia.private-service-edge.cluster-architecture:service-edges-active-active] Zscaler does not support standalone Private Service Edge deployments. Each cluster must have a minimum of two Private Service Edges, and if dedicated LBs are included they must also be deployed as a minimum of two. [zia.private-service-edge.cluster-architecture:no-standalone] The per-design minimum and maximum node counts are in [Choosing a Private Service Edge design and node count](kb:zia.private-service-edge.sizing).

**Addressing.** All traffic destined for the cluster must be sent to the cluster VIP addresses; the active LB instance listening for the VIP forwards each packet to one Service Edge instance in the pool. [zia.private-service-edge.cluster-architecture:traffic-to-vip] In each of the three example cluster designs, the LB and Service Edge instances are all connected to the same L2 switching fabric. [zia.private-service-edge.cluster-architecture:same-l2-fabric]

**Return path.** The service uses the Direct Server Return (DSR) method of load balancing: the Service Edge instance that handled the request returns the response directly to the user, and the response does not traverse the LB on the return path. [zia.private-service-edge.cluster-architecture:dsr] Because of DSR, request and response take different paths: return traffic bypasses the LB; which source address the response carries is not documented. [zia.private-service-edge.cluster-architecture:asymmetric-return] Switch-side settings for this are in [Where to place a Private Service Edge and how to configure the network around it](kb:zia.private-service-edge.deployment).

The virtual form factor uses the same CARP and DSR model with customer-operated nodes: [How a Virtual Service Edge cluster spreads and returns traffic](kb:zia.virtual-service-edge.load-balancing).
