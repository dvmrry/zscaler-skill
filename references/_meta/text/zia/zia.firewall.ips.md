# IPS Control (zia.firewall.ips)
Also called: ips; ips control; intrusion prevention; default ips rule; custom ips signature; snort; firewallIpsRules; ipsSignatureRules; atp vs ips

IPS Control is the signature half of Firewall Control. IPS Control uses signature-based detection over all ports and protocols, with signatures built and updated by Zscaler's security research team plus signatures from industry-leading vendors. [zia.firewall.ips:signature-detection] IPS Control covers web and non-web traffic: HTTP, HTTPS, FTP, DNS, TCP, UDP and IP-based ports and protocols. [zia.firewall.ips:protocol-coverage] IPS Control requires Advanced Firewall ([IPS Control is available only with Advanced Firewall.](kb:zia.firewall.licensing:ips-needs-advanced)). IPS Control policies are enabled per location. [zia.firewall.ips:per-location] Forwarding through Z-Tunnel 1.0 or PAC needs the firewall option enabled first: see [Where the firewall sits in the traffic path](kb:zia.firewall.traffic-path).

**The default rule.** Zscaler provides a default IPS rule that blocks all traffic. Rules of higher precedence allow specific traffic past it, for example the IT Security group's traffic matching threats. [zia.firewall.ips:default-blocks-all] The IPS Control page lets an admin view the recommended IPS Control policy. [zia.firewall.ips:recommended-policy-view] Rule order is in [Firewall rule order, admin rank and predefined rules](kb:zia.firewall.rule-order).

**ATP and IPS.** If a tenant has both IPS Control and Advanced Threat Protection, the rules created for ATP are evaluated first. [zia.firewall.ips:atp-first] Whether an ATP block appears in the IPS logs is open [gap:zia.firewall.ips:atp-preempt-in-ips-logs].

**Custom signatures.** Customers can create custom IPS signatures in Snort-like syntax, and the signatures take effect through threat categories referenced by the IPS Control policy. [zia.firewall.ips:custom-signatures] The MCP tool describes a custom signature body as Snort/Suricata syntax that must include a unique `sid:` and `rev:`. [zia.firewall.ips:signature-needs-sid] The MCP tools create a custom IPS signature from `name`, `rule_text` and an optional `description`. Update is a PUT-replace: when the caller omits `name` or `rule_text`, the tool fetches the existing signature and backfills both before sending. [zia.firewall.ips:mcp-signature-tools] The Python SDK validates `rule_text` against the dynamic-validation endpoint before creating a signature, but does not do so on update, because the check would flag the rule's own `sid` as a duplicate. The Terraform provider validates on every create and update. [zia.firewall.ips:create-validates-update-does-not] The relevant caps are in [Firewall rule, criteria and group limits](kb:zia.firewall.limits). Custom signature definitions and IPS policy rules are separate API resources: definitions at `/ipsSignatureRules` and rules at `/firewallIpsRules`. A rule carries the action and criteria; a definition carries its text, category and enabled state. [zia.firewall.ips:two-resources] The actions an IPS rule can take are in [Firewall rule actions](kb:zia.firewall.actions). The help's signature lifecycle, supported syntax and limits, CSV import and custom threat categories are in [Custom IPS signatures: enablement, two-stage validation and statuses, supported Snort-like syntax, limits, CSV import and export, and custom threat categories](kb:zia.firewall.ips-signatures).

**Logs.** Threats detected in network traffic are shown under Firewall Insights > Logs, and threats detected in web-only traffic also appear on the Security dashboard. The firewall log records the IPS rule name and whether a custom signature applied. [zia.firewall.ips:logging]

**The rule form: scope.** IPS Control criteria categories are ANDed together, each with its own operators: [(Users OR Groups OR Departments) AND (Locations OR Location Groups) AND Time]; [(Network Service Groups OR Network Services) AND Advanced Threat Category]; (Source IP Groups OR IP Addresses); (Destination Groups OR IP Address/FQDN OR Countries OR URL Categories). [zia.firewall.ips:criteria-expression] The expression omits the Applications category that the form offers [gap:zia.firewall.ips:criteria-applications]. An IPS rule takes up to 32 users, groups, departments, locations and location groups; unset identity and location fields are Any and the criterion is ignored in evaluation. Zscaler Support can raise the user, group, department and location limits. [zia.firewall.ips:who-where-when-caps] The page and the limit for all policy rule types disagree on time intervals per rule, a divergence recorded with the other policy pages in [zia.time-intervals.rule-usage:time-intervals-per-rule](kb:zia.time-intervals.rule-usage:time-intervals-per-rule). Selecting Road Warrior for Locations limits an IPS rule to remote user traffic, which also needs Enable Firewall for Z-Tunnel 1.0 and PAC Road Warriors in Advanced Settings; rules for other locations also apply to remote user traffic from those locations. [zia.firewall.ips:road-warrior] After IPS rules are configured, IPS Control has to be enabled for location traffic and for remote user traffic. [zia.firewall.ips:enable-for-locations-and-remote-users] Network Service Groups default to None and Network Services to Any. The ZPA Application Segment criterion is Any or up to 255 Private Access application segments with Source IP Anchor enabled; Inspect App Segments applies the rule to every segment paired to the Internet & SaaS (ZIA) tenant and is available only if SIPA App Segments is enabled. Application Service Groups take predefined and custom groups. An unset Advanced Threat Category is Any and the criterion is ignored. [zia.firewall.ips:services-and-applications] Source and destination IP address criteria are IPv4 only: individual, subnet or range IPv6 addresses cannot be specified, source IPv6 addresses are controlled with the All IPv6 group, and custom source and destination IPv6 groups are not supported. Source IPv4 and IPv6 groups and Destination IPv4 groups default to None. FQDN entries are available with Advanced Firewall, wildcard FQDNs are also supported with an asterisk, and rules based on wildcard FQDNs need client DNS requests forwarded to the Zscaler service. Countries identify a destination by server location and default to Any. [zia.firewall.ips:source-destination-ip]

**The rule form: actions and logging.** IPS Network Traffic actions: Allow passes the packets through the IPS; Block/Drop silently blocks matching packets; Block/Reset drops matching TCP packets and sends the client a TCP reset, and for non-TCP traffic is the same as Block/Drop; Bypass IPS allows the packets without scanning and cannot be combined with an Advanced Threat Category. [zia.firewall.ips:action-semantics] The console names are not tied to the API tokens in these pages [gap:zia.firewall.ips:action-tokens]. The IPS rule's Capture action requires Traffic Capture to be enabled in Advanced Settings and appears only when Allow or Block actions are selected for Network Traffic. [zia.firewall.ips:traffic-capture] The Traffic Capture Essentials page names a different place to enable it [zia.traffic-capture:capture-enablement](kb:zia.traffic-capture:capture-enablement). What the Capture option stores is described two ways [divergence:zia.firewall.ips:capture-scope]. An IPS rule logs either Aggregate (sessions grouped by user, rule and network service and recorded periodically, about every 15 minutes) or Full (every session of the rule individually, except HTTP(S)). In Standard Firewall, full logging is supported only for Block rules; full logging for all other rules requires Full Logging or Advanced Firewall. [zia.firewall.ips:logging-modes] An IPS rule can show a Client Connector end user notification, with a default or custom message, for traffic it allows or blocks. EUN is supported only for Allow and Block, not Bypass IPS. The page says EUN is supported on Windows devices running Client Connector 4.8 or later over Z-Tunnel 2.0. [zia.firewall.ips:eun]

**The rule form: name, rank and status.** An IPS rule's name is system-generated and editable, up to 63 characters; its description is up to 10,240 characters. Admin rank runs 0 to 7 (0 highest), appears only with Admin Ranking enabled, and the rule's admin rank determines the rule order value that can be selected. A new rule's status is Disabled by default; a disabled rule keeps its place in the order and is skipped. [zia.firewall.ips:rule-details] The default IPS rule blocks all traffic and logs sessions with aggregate logging. It always keeps the lowest precedence, cannot be deleted, and can be modified only with the super admin role; traffic is allowed through by modifying it or by a higher-order rule. [zia.firewall.ips:default-rule-details] Zscaler's recommended IPS rule has a Rule Order of 1 (evaluated first), is enabled, selects Any or specific threat categories, and uses the Block/Drop action. [zia.firewall.ips:recommended-rule] The help pages use two meanings for a rule of higher precedence than the default rule [divergence:zia.firewall.ips:higher-precedence-meaning].

**Threat categories.** IPS threat categories group common threats; Zscaler provides predefined categories, each associated with a collection of custom IPS signature rules: Advanced Security (threats in no other category), Adware/Spyware Sites, Anonymizer, Application Detection (TOR, Ultrasurf, VPN apps etc), Reconnaissance Attempts, Botnet Callback, Browser Exploit, Brute Force Attack, Cross-site Scripting, Crypto Mining, Denial of Service Attack, Domain Generation Algorithm (DGA) Domains, Exploit (known non-web vulnerabilities), Malicious Content, Malware, Peer-to-Peer, Phishing, Policy Violation, Ransomware, Risky Behaviors, Suspected Spyware or Adware, Suspicious Destinations, Unauthorized Communication and Webspam. [zia.firewall.ips:predefined-threat-categories] Risky Behaviors holds signatures considered risky that might have legitimate use (for example websockets-to-SSH detection as with Chisel) and can match legitimate traffic, so an organization might exclude it from blocking with a higher-order IPS rule on that category set to Allow or Bypass IPS. The Suspicious Destinations category is the URL categories Nudity, Pornography, Anonymizer, FileHost, Shareware Download, Web Host, Miscellaneous or Unknown and Other Miscellaneous. [zia.firewall.ips:risky-behaviors-and-suspicious-destinations]

What to check:
1. Whether rules that allow ordinary business traffic sit above the default block, and the rank of each.
2. Whether a rule needs more than two time intervals, which the help and the firewall limits give differently.
3. Whether the recommended IPS Control policy has been compared with the tenant's policy before enabling.
4. Whether the tenant also has ATP, since its rules are evaluated first.
5. Whether a custom signature is accepted by the parser, since its Snort compatibility is open.
6. Whether the firewall log shows the IPS rule name for a blocked flow.

Sources disagree (name both sides):
- One IPS Control help page says Capture stores traffic allowed or blocked by the policy, and then describes the Capture option as storing traffic captured during a block action. [divergence:zia.firewall.ips:capture-scope]
  - zscaler-help: Traffic allowed or blocked by the policy can be stored as PCAP files.
  - zscaler-help: The Capture option stores traffic captured during a block action.
  Impact: Whether a Capture-enabled Allow rule stores traffic is not settled by the page, although the Capture option is described as appearing for Allow or Block actions.
- The recommended-policy page says a rule of higher precedence than the default rule means a higher rule order, while the IPS Control overview says it means a higher admin rank. [divergence:zia.firewall.ips:higher-precedence-meaning]
  - zscaler-help: Higher precedence means higher rule order.
  - zscaler-help: Higher precedence means higher admin rank (the wording zia.firewall.ips:default-blocks-all and zia.firewall.rule-order:ips-allow-rules-need-precedence rest on).
  Impact: Which of rule order or admin rank must place an allow rule above the default rule depends on which page is used.
