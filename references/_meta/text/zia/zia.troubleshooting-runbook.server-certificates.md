# Runbook: bad server certificates and untrusted certificates that are allowed (zia.troubleshooting-runbook.server-certificates)
Also called: Access denied due to bad server certificate; Untrusted Server Certificate gets allowed

**Bad server certificate.** The bad server certificate block implies one of four scenarios for the website's certificate: an incomplete chain during the handshake, a revoked certificate in the OCSP check, an expired certificate, or a self-signed certificate. [zia.troubleshooting-runbook.server-certificates:bad-cert-scenarios] The website must provide all the intermediate certificates, because Zscaler does not manually add intermediates to its trust store and only root CA trust anchors are stored in its nodes' trust stores. [zia.troubleshooting-runbook.server-certificates:intermediates-not-in-trust-store] In the page's three-certificate chain, validation requires the leaf CN or a SAN to match the domain part of the URL, the leaf issuer to match the intermediate's CN, and the intermediate's issuer to match the root's CN. [zia.troubleshooting-runbook.server-certificates:chain-validation-names] In the page's example, a complete chain still fails validation because the server certificate was issued by Network Solutions RSA DV SSL CA 3 while the chain includes the intermediate Network Solutions DV Server CA 2. [zia.troubleshooting-runbook.server-certificates:chain-mismatch-example] This page says Zscaler uses OCSP stapling to obtain revocation status; when enabled in the SSL Inspection policy the Service Edge checks it regardless of other certificate attributes, treats a revoked certificate as untrusted, and applies the Untrusted Server Certificates configuration. The policy article words the option as OCSP Revocation Check for the Inspect action (using OCSP) and as OCSP stapling for Do Not Inspect with Evaluate Other Policies. [zia.troubleshooting-runbook.server-certificates:ocsp-stapling]

**Web log columns and intermittent results.** The web log columns the page uses are Certificate Chain Validity (Fail suggests an incomplete chain), Server Certificate Self Signed (must not be Yes), Certificate Expiry (Yes explains a bad mark) and Server Connection OCSP Result (Revoked explains it). [zia.troubleshooting-runbook.server-certificates:weblog-cert-columns] The page lists reasons why transactions for the same domain through the same data center can show Pass or Fail in the chain column: the intermediate CA cert cache, multiple physical servers behind one VIP where some serve the complete chain and some do not, or sites offering more than one trust chain; browsers doing AIA fetching can hide an incomplete chain. [zia.troubleshooting-runbook.server-certificates:chain-intermittent-causes] An SSL Labs URL with the d= and s= parameters validates the certificate on one specific server IP for a website. [zia.troubleshooting-runbook.server-certificates:ssllabs-single-server]

**Fixes.** Zscaler recommends a Pass Through SSL policy or an allow policy for untrusted certificates only for URLs the business trusts; the OCSP check can be disabled per domain in the SSL policy rule, which Zscaler does not recommend. [zia.troubleshooting-runbook.server-certificates:bad-cert-solutions]

**Untrusted certificate allowed.** When a Block action is configured for Untrusted Server Certificates but some connections with such certificates are allowed, the expected behavior is blocking with the Policy Action Access denied due to bad server certificate. [zia.troubleshooting-runbook.server-certificates:untrusted-allowed-expected] When SSL inspection for a domain is manually set to Do Not Inspect, the service does not decrypt it and cannot read the certificate, so the browser must show any certificate warnings. [zia.troubleshooting-runbook.server-certificates:untrusted-allowed-do-not-inspect] Whether a Do Not Inspect rule has any certificate handling is in dispute [divergence:zia.troubleshooting-runbook.server-certificates:do-not-inspect-cert-handling]. If a web server requests a client certificate and the undecryptable traffic option is disabled, the Service Edge aborts decryption and bridges the connection; with TLS 1.3 it cannot read the certificate while bridging, so the connection is allowed regardless of the certificate's validity. [zia.troubleshooting-runbook.server-certificates:untrusted-allowed-mtls-tls13] The page's fixes are to set the rule action for the domain to Inspect if business policy permits, or to block such domains with an SSL Inspection rule that has Block Undecryptable Traffic enabled. [zia.troubleshooting-runbook.server-certificates:untrusted-allowed-solutions]

Sources disagree (name both sides):
- The untrusted-certificate runbook says the service cannot read the certificate of a domain set to Do Not Inspect, while the SSL/TLS Inspection policy article offers Untrusted Server Certificates and an OCSP check under Do Not Inspect with Evaluate Other Policies. [divergence:zia.troubleshooting-runbook.server-certificates:do-not-inspect-cert-handling]
  - zscaler-help: With the domain manually set to Do Not Inspect, the service does not decrypt it and cannot read the certificate.
  - zscaler-help: For Do Not Inspect with Evaluate Other Policies, the rule offers an Untrusted Server Certificates setting for untrusted certificates.
  Impact: Whether a Do Not Inspect rule can allow or block on an untrusted certificate depends on which page is read; the pages do not say whether the policy settings apply only with Evaluate Other Policies.
