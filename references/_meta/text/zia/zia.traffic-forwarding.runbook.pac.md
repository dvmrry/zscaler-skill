# Runbook: PAC file, explicit proxy and DPP outages, PAC causes and authentication loops (zia.traffic-forwarding.runbook.pac)
Also called: PAC File Causes; Authentication Causes

**Reachability.** In the runbook's section on troubleshooting Zscaler public DC issues, in an internet-down situation with PAC, the runbook says to validate DNS resolution and connectivity for pac.<cloudname>.net, login.<cloudname>.net, gateway.<cloudname>.net and the authentication server, on 80/443/DPP using ping and Telnet. [zia.traffic-forwarding.runbook.pac:reachability-hosts] The runbook lists a failed Telnet to DPP (its example port is 10938) as 'not provisioned', alongside a successful Telnet to port 80/443. [zia.traffic-forwarding.runbook.pac:dpp-telnet-expected] When the Telnet client is not enabled and the end device has restrictive permissions, the runbook says PowerShell can be used to check network reachability. [zia.traffic-forwarding.runbook.pac:powershell-alternative]

**PAC download and fragmentation.** The runbook says to copy the PAC URL from the Admin Console and confirm the affected device can download the PAC file; if it can, open the file to identify the primary and secondary data center and run ping and Telnet reachability tests towards both. [zia.traffic-forwarding.runbook.pac:download-pac] If the device cannot download the PAC file although pac.<cloudname>.net is reachable, the runbook says to run a client packet capture and check for IP fragmentation; the filter icmp.type==3 and icmp.code==4 indicates a fragmentation issue and the Wireshark filter ip.flags.mf == 1 shows all fragmented packets. [zia.traffic-forwarding.runbook.pac:fragmentation] The runbook says to determine the IP packet size the network supports, using Path MTU discovery or setting the Maximum Segment Size (MSS), to avoid IP fragmentation. [zia.traffic-forwarding.runbook.pac:avoid-fragmentation]

**PAC causes.** To test whether an issue is PAC-related, the runbook says to find the data center the customer is connected to at http://ip.zscaler.com, log out of Client Connector, take the FQDN of the PAC VIP for the DC from config.zscaler.com, set it as a manual proxy on port 80/443 with the relevant IdP authentication domains in the bypass, and visit an HTTP site; if the test page loads, troubleshooting focuses on the PAC file. [zia.traffic-forwarding.runbook.pac:manual-proxy-test] The runbook says a PAC parsing issue could cause applications to send traffic direct, which might drop at the customer firewall. [zia.traffic-forwarding.runbook.pac:parsing-direct] To check for recent PAC changes the runbook points to Administration > Admin Management > Audit Logs with the PAC File Sub-Category filter; to revert, open Hosted PAC Files, Manage Versions, then Actions > Deploy on the previous version. A PAC-only scenario needs the browser cache cleared and might need a browser restart. [zia.traffic-forwarding.runbook.pac:audit-and-revert] WinMTR collection for PAC is in [Runbook: MTR collection, WinMTR for Client Connector and PAC, and latency checks for GRE and IPSec gateways](kb:zia.traffic-forwarding.runbook.tunnel-path).

**Authentication loop.** The runbook describes an authentication loop that can occur when the IdP request is both forwarded via Internet & SaaS and redirected for authentication; it is identified in a packet capture or browser trace by a 307 redirection for an IdP request. [zia.traffic-forwarding.runbook.pac:auth-loop] Zscaler recommends bypassing IdP traffic from forwarding to Internet & SaaS, or at least configuring it in Authentication Exemptions; the runbook says to add a bypass for the authentication domain in the PAC file or add the domains under Administration > Advance Settings > Authentication Exemptions. [zia.traffic-forwarding.runbook.pac:auth-loop-fix]
