# What happens to traffic with no user identity (zia.authentication.unauthenticated-traffic)
Also called: unauthenticated traffic; anonymous user; enable_policy_for_unauthenticated_traffic; gateway cookie; domain cookie; AUP cookie; traffic marked against location; user rule did not match; CONNECT without user; authentication before policy

Without Surrogate IP, the location's policies apply to traffic from a user that cannot be authenticated; with it, the user's policies apply instead. [zia.authentication.unauthenticated-traffic:location-policy-fallback]

**Why traffic ends up without an identity.** The service uses a gateway cookie (login state and count), a per-domain cookie set after login for each domain the user browses, and an Acceptable Use Policy cookie set when the user accepts the AUP. [zia.authentication.unauthenticated-traffic:cookie-types] Traffic that cannot carry the authentication cookie is marked against the user's location instead of the user: all CONNECT requests, requests from unknown user agents that do not support cookies, traffic to globally exempted sites (the Exempted URL Categories), traffic to locally exempted sites (the Exempted URLs list), and SSL traffic that is not decrypted. [zia.authentication.unauthenticated-traffic:no-cookie-traffic] A user who is logged in can still have a transaction judged as the location rather than as the user, when the transaction is one that cannot carry the authentication cookie; a user rule does not match that transaction. [zia.authentication.unauthenticated-traffic:logged-in-user-misses-user-rule] Surrogate IP exists to cover exactly these cases: [Surrogate IP: mapping a private IP to an authenticated user](kb:zia.authentication.surrogate-ip). Destinations that never get a challenge are in [Destinations that skip authentication](kb:zia.authentication.exemptions).

**Whether user rules can apply anyway.** The advanced setting enable_policy_for_unauthenticated_traffic controls whether policies that include user and department criteria can be configured and applied for unauthenticated traffic. [zia.authentication.unauthenticated-traffic:unauthenticated-policy-setting] The service might not authenticate user traffic to URLs or cloud apps selected to be exempt from authentication, or traffic that is encrypted when SSL/TLS Inspection is not enabled. For policies where users and departments can be specified in the criteria, the service lets an admin specify which rules it applies to such unauthenticated traffic. With a default block on web traffic (a URL Filtering rule that blocks all traffic not explicitly allowed through the URL Filtering policy), the feature can help ensure that lack of authentication does not lead to an unnecessary block of user traffic. [zia.authentication.unauthenticated-traffic:when-unidentified] The feature must be explicitly enabled in Advanced Settings before it can be used. Any rule that applies to unauthenticated traffic also applies to specific users, groups and departments if they are selected. The feature only applies to locations that have authentication enabled. Any rule that applies to unauthenticated traffic must apply to all locations: a rule cannot apply to unauthenticated traffic and select particular locations. [zia.authentication.unauthenticated-traffic:policy-conditions] The Advanced Settings page that holds the setting is routed in [ZIA Advanced Settings page: its sections, three settings explained here, and where other sections are routed](kb:zia.advanced-settings).

**Choosing which unauthenticated traffic a rule covers.** When the feature is enabled in Advanced Settings, a rule's application to unauthenticated traffic is specified under the Department criteria by selecting Unauthenticated Transactions under Special Departments, alone or combined with regular departments; for more granularity, the types of unauthenticated traffic are specified under the Users criteria, under Special Users. For either Users or Departments, a group must not be selected from the Groups drop-down menu, and a criterion with no value selected is ignored in the policy evaluation. [zia.authentication.unauthenticated-traffic:departments-vs-users] The Special Users types of unauthenticated traffic are: Unauthenticated User Agent (the configured authentication method cannot authenticate the user agent); Unsupported Method (HTTP methods not normally supported, such as FIND or PROPBIND); Unauthenticated Protocol (for example, un-decrypted HTTPS traffic); Unauthenticated Proxy Port User (traffic coming from port 9480); Miscellaneous Unauthenticated Transactions (miscellaneous issues); Authentication Bypass URL (traffic to URLs or cloud apps exempted from authentication); and Unknown Kerberos User. The page adds that HTTP requests that do not support cookie-based authentication, such as CONNECT and OPTIONS, are logged in this category. [zia.authentication.unauthenticated-traffic:special-user-types] The Miscellaneous Unauthenticated Transactions user is also the fallback in [Behavior When Partial Configuration Available: Fail Open, Fail Closed and Best Effort Policies](kb:zia.advanced-settings.partial-configuration). Whether CONNECT and OPTIONS requests are attributed to the location or logged in the Authentication Bypass URL category is not reconciled [divergence:zia.authentication.unauthenticated-traffic:connect-options-attribution].

**Port 9480.** Public Service Edges accept web requests on ports 80, 443, 9400, 9480 and 9443. Any traffic generated from a known gateway location and destined to Public Service Edges with the proxy port of 9480 bypasses authentication. [zia.authentication.unauthenticated-traffic:port-9480-bypass]

**Guest users.** In general, policies are applied to authenticated traffic, regardless of location. In the page's Guest Inc. and Host Corp. example, when the Guest Inc. user is authenticated, all of the Guest Inc. user's URL, Cloud App, Firewall, DLP and security policies are applied, all transactions are logged against the Guest user, and an Acceptable Use Policy configured for the Guest user is displayed after authentication. The Guest user cannot use the Guest DPPC port, all Host Corp. bandwidth limitations and SSL/TLS and authentication bypasses apply, and if Host Corp. has SSL/TLS Inspection enabled at the location, the Guest user's traffic is intercepted and decrypted using the Host Corp. SSL certificate. [zia.authentication.unauthenticated-traffic:guest-authenticated] In the page's Guest Inc. and Host Corp. example, the Guest user cannot be authenticated if Host Corp. has authentication disabled at the location; if the Guest Inc. user cannot be authenticated for any reason, all of Host Corp.'s URL, Cloud App, Firewall, DLP and security policies are applied to that unauthenticated traffic, all unauthenticated transactions are logged against Host Corp., all Host Corp. SSL and authentication bypasses apply, and an AUP configured for the Guest user is not displayed because the user is not authenticated. [zia.authentication.unauthenticated-traffic:guest-unauthenticated]

**A location mapped to an identity provider.** When a location is assigned to an IdP, location-based policies are enforced even when users are not authenticated. [zia.authentication.unauthenticated-traffic:idp-location-policy]

**Early in an HTTPS connection.** At the CONNECT request or TLS Client Hello, user context exists only with Surrogate IP or Zscaler Client Connector. If there is no user context and authentication is enabled for the location, the Public Service Edge skips policy evaluation at that stage to avoid a wrong decision; if the policy for unauthenticated traffic is enabled, it evaluates the policy there instead. [zia.authentication.unauthenticated-traffic:connect-sni-skip] How that interacts with decryption is in [Where SSL inspection sits in ZIA web policy evaluation (the two passes)](kb:zia.ssl-inspection.pipeline).

What to check:
1. Which kind of transaction it was (CONNECT, an unknown user agent, an exempted destination, or undecrypted SSL), since each of these is attributed to the location.
2. Whether Surrogate IP is on for the source.
3. Whether enable_policy_for_unauthenticated_traffic is set in the tenant, before concluding whether user and department rules can apply.
