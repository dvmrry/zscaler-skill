# The ZIA SAML identity provider object: limits, default IdP, criteria, fields, migration and Client Connector Portal as IdP (zia.authentication.identity-providers)
Also called: identity provider; IdP configuration; multiple IdPs; default IdP; IdP criteria; SAML portal URL; org-specific entity ID; migrate IdP; Client Connector Portal as IdP

The Zscaler service redirects users to different SAML URLs based on configured IdP criteria, and can support up to 64 different SAML IdPs per organization. [zia.authentication.identity-providers:idp-limit] The Identity Providers page is not available if the organization is subscribed to the Authentication Service. [zia.authentication.identity-providers:idp-page-availability] To add multiple IdPs, Enable SAML Auto-Provisioning must be disabled for the existing IdP, or the User Repository Type changed to Hosted DB on the Authentication Settings page. [zia.authentication.identity-providers:second-idp-precondition]

**Which IdP a user is sent to.** When adding an IdP the only required criteria are the user authentication domains. A non-default IdP must have at least one authentication domain or it cannot be enabled, which does not apply to the default IdP, and when a new user authenticates the service checks the user's domain and redirects the user to the appropriate IdP. [zia.authentication.identity-providers:domain-criteria] Known locations can optionally be assigned to an IdP, mapping IdPs to specific office locations (the article's example assigns European locations to a European AD FS server and US locations to a US one). Users redirected to a location-mapped or default IdP are not required to enter a username and domain, and locations not assigned to an IdP are mapped to the default IdP. [zia.authentication.identity-providers:location-criteria] Location policy before authentication at an IdP-mapped location is in [What happens to traffic with no user identity](kb:zia.authentication.unauthenticated-traffic).

**The default IdP.** There can be only one default IdP, and the first IdP added becomes it. With multiple IdPs configured the default IdP is the catchall: a location or domain not specifically assigned to an IdP is mapped to it, and for the default IdP the unselected-locations field is set to Any and cannot be modified. [zia.authentication.identity-providers:default-idp-catchall] Setting an existing IdP as the default makes the service remove any specific location or domain mappings associated with that IdP. The default IdP cannot be deleted; another existing IdP must be set as the default first. [zia.authentication.identity-providers:default-idp-changes]

**IdP fields.** The SAML Portal URL should be publicly resolvable if users are to authenticate from the internet, and protected using HTTPS. Login Name Attribute is the SAML attribute that maps to the login name users enter; it is typically NameID, entered as one word with no spaces, and the field is case-sensitive. [zia.authentication.identity-providers:portal-url-and-login-attribute] Org-Specific Entity ID is enabled when more than one organization instance exists on the same Zscaler cloud. The page's example is Microsoft Entra ID, where the same entity ID cannot be used for multiple apps, so the setting must be enabled for both instances to generate a unique organization-specific entity ID. [zia.authentication.identity-providers:org-specific-entity-id] The IdP SAML certificate must be in base-64 encoded PEM format, with the file extension .pem and no other periods in the file name. The IdP SAML Certificate Expiration Date field shows if the certificate is about to expire or has expired. [zia.authentication.identity-providers:idp-certificate] Sign SAML Request is enabled if the IdP expects the SAML request to be signed, with a SHA-1 (160-bit) or SHA-2 (256-bit) signature algorithm. Zscaler recommends choosing the request-signing SAML certificate with the longest validation period. [zia.authentication.identity-providers:request-signing] SP Metadata downloads the Zscaler service's metadata, which advertises its SAML capabilities and is used for auto-configuration. Device Trust Attribute and Device Trust Attribute Value are the SAML attribute and value that map to the trust attribute and value defined on the IdP, used for identifying managed devices; both fields are case-sensitive. [zia.authentication.identity-providers:sp-metadata-and-device-trust] The auto-provisioning attribute fields are in [SAML auto-provisioning: what login creates and overwrites](kb:zia.ad-integration.saml-auto-provisioning).

**What the IdP is given.** In the Entra ID guide the SP identifier is typically the Zscaler cloud name (for example zscalerbeta.net when logging in to https://admin.zscalerbeta.net), the reply URL is https://login.<Zscaler Cloud Name>:443/sfc_sso, and an organization-specific entity ID has the form https://login.zscalerbeta.net/sfc_sso/3829920. The Google Workspace guide gives the ACS URL https://login.<Zscaler cloud name>.net:443/sfc_sso and the cloud name as the entity ID. [zia.authentication.identity-providers:sp-endpoints] In the Entra ID guide, if IPv6 support is enabled for the organization, Zscaler authentication uses IPv6-only URLs, and the IdP is given https://login6.<Zscaler Cloud Name>.net/sfc_sso and, if applicable, https://logout6.<Zscaler Cloud Name>.net/sfc_sso. [zia.authentication.identity-providers:ipv6-endpoints] In the Entra ID guide, entering https://login.<Zscaler Cloud Name>/clstart?version=1&_domain=<Tenant Domain>&redrurl=https://mobile.<Zscaler Cloud Name> on the device and being redirected to the Zscaler Admin Console means the SAML configuration is successful, possibly after authenticating with the IdP. The logout test, which ends at ip.zscaler.com showing the username, applies only when forwarding traffic with PAC files, GRE tunnels or IPSec tunnels and Enforce Authentication is enabled for the location or sublocation. [zia.authentication.identity-providers:test-url]

**Migrating to a new IdP.** Zscaler recommends editing the existing IdP to migrate to a new IdP, because adding a new IdP for migration can duplicate groups and departments and existing policies might no longer apply. The same users, groups and departments must be present in both IdPs, and the NameID mapping (SAML) and userName mapping (SCIM) must be defined the same way in both, with the same expression if defined from the email or UPN attribute. [zia.authentication.identity-providers:migration-advice] The migration option takes the existing SAML IdP to migrate and replaces its SAML Portal URL and Vendor with the new ones; SCIM provisioning is then started on the new IdP to sync all user data, and the new IdP should be running without error before the old IdP is disabled. To revert, edit the IdP back to the previously configured details and perform a SCIM sync in the IdP. [zia.authentication.identity-providers:migration-steps] How to clean up duplicated groups and departments is not stated [gap:zia.authentication.identity-providers:migration-duplicates].

**Client Connector Portal as the IdP.** If the Zscaler Client Connector Portal is configured as the IdP, users automatically enroll with Zscaler Client Connector, which uses a device token generated in the Client Connector Portal to authenticate users and their devices for the Zscaler service. User identities cannot be federated with other external IdPs because users are hosted locally within the tenant, and the method only works with Zscaler Client Connector. [zia.authentication.identity-providers:ccp-idp] Using the Client Connector Portal as IdP requires disabling SAML auto-provisioning for the existing IdP or changing the User Repository Type to Hosted DB on the Authentication Profile page. It cannot share a domain with the default IdP, so Zscaler recommends provisioning a separate domain for token-based authentication and creating a Support ticket in the Admin Console to associate the domain with the tenant. [zia.authentication.identity-providers:ccp-idp-preconditions] The Client Connector side of the device token is in [Install parameters that identify the tenant and user at enrollment](kb:zcc.install.enrollment). Per-vendor specifics for Entra ID, Okta, Ping, Google Workspace, AD FS, OneLogin and CA SSO are in [Per-IdP configuration specifics: SAML and SCIM for Entra ID, Okta, Ping and Google Workspace; SAML only for AD FS, OneLogin and CA SSO](kb:zia.authentication.idp-integrations). What holds the IdP settings under Authentication Service is not covered [gap:zia.authentication.identity-providers:authentication-service-scope].

What to check:
1. Whether the tenant is subscribed to Authentication Service, since the Identity Providers page is not available then.
2. Which IdP the user's domain and location map to, and whether that IdP is the default, before judging a redirect.
3. Whether a migration edited the existing IdP or added a new one, and whether NameID and userName mappings match in both.
