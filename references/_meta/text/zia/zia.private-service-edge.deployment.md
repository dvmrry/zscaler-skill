# Where to place a Private Service Edge and how to configure the network around it (zia.private-service-edge.deployment)
Also called: pse deployment; pse dmz; pse behind firewall; pse gre tunnel; pse gratuitous arp; pse vlan tagging; pse lldp; pse switch settings; pse pac file; pse backup tunnel

Placement is a choice between three firewall relationships. A Private Service Edge can be deployed inside the DMZ, outside the corporate firewall, or behind the network firewall. [zia.private-service-edge.deployment:placement-options] Zscaler recommends the DMZ, see [Addresses, NAT, IPv6 and ports a Private Service Edge needs](kb:zia.private-service-edge.ip-requirements).

**Inside the DMZ.** Deploying inside the DMZ needs firewall changes to allow Zscaler cloud communications and Zscaler Operations access. Internet traffic crosses the firewall to the Private Service Edge and then again to the internet, which can lead to port or session table exhaustion. [zia.private-service-edge.deployment:dmz-firewall-load]

**Outside the corporate firewall.** Deploying outside the corporate firewall: Zscaler highly recommends sending HTTP/HTTPS traffic through a GRE or IPSec tunnel from the firewall to the Private Service Edges, which needs no firewall changes for the Private Service Edge's communications. Only HTTP/HTTPS goes to the Private Service Edges, all other traffic goes directly to the internet, and the traffic sent through the tunnels should be un-NATed for visibility. [zia.private-service-edge.deployment:outside-firewall-tunnels]

**Behind the network firewall.** Deploying behind the network firewall also needs firewall changes, and requires multiple public and multiple RFC 1918 addresses per Private Service Edge together with 1:1 static NAT on the organization's NAT devices. [zia.private-service-edge.deployment:behind-firewall-nat]

**Redundancy and firewall lists.** For redundancy, the DMZ method calls for a backup tunnel to Private Service Edges at another data center or to Public Service Edges for Internet & SaaS; the outside-firewall method calls for backup tunnels to Private Service Edges at another data center or to Public Service Edges; the behind-firewall method calls for a backup tunnel to Private Service Edges at another data center or to a Public Service Edge. [zia.private-service-edge.deployment:backup-tunnel] If the Private Service Edges are deployed in the DMZ, inside the internal network or behind any network device that might filter or interfere with communication to and from the Zscaler service, the relevant network devices must allow the traffic in the firewall rules posted at config.zscaler.com/<zscaler cloud name>/fcr. [zia.private-service-edge.deployment:firewall-rules-published] The organization must configure its corporate firewall to allow remote access if the Private Service Edges are deployed in the DMZ or behind the network firewall, or if PAC files forward traffic from the internal network to the Private Service Edges. The page points to its Firewall Config Requirements and Cloud Enforcement Node Ranges sections. [zia.private-service-edge.deployment:firewall-for-remote-access] With PAC forwarding, the corporate firewall needs a policy to allow devices to retrieve PAC files from the Zscaler PAC servers; if the PAC files are used only when users are remote or telecommuting, this step is not required. [zia.private-service-edge.deployment:pac-retrieval-rule] Which of the published lists applies is open [gap:zia.private-service-edge.deployment:firewall-list-source].

**Switch settings.** For Direct Server Return load balancing to function correctly, Gratuitous ARP (GARP) must be enabled on the network switches directly connected to the Private Service Edges. [zia.private-service-edge.deployment:dsr-needs-garp] Switch ports connecting to the Private Service Edges or LBs must be in Access mode so traffic between the Private Service Edges and the LB NIC ports is not VLAN tagged; the Private Service Edges and LBs do not support VLAN tagging. [zia.private-service-edge.deployment:access-mode-no-vlan-tags] Link Level Discovery Protocol (LLDP) must be disabled on the switch ports connected to the Private Service Edges, and Layer 2 flow control must be disabled on all switch ports serving the Internet and SaaS Private Infrastructure VLANs; the help adds that the service has its own Layer 4 flow control embedded in the TCP stack. [zia.private-service-edge.deployment:lldp-and-flow-control-off] The reason GARP matters is the return path described in [How a Private Service Edge cluster is built and fails over](kb:zia.private-service-edge.cluster-architecture).

**Who does what.** After the customer installs the hardware Zscaler sends, Zscaler Operations provisions the Private Service Edges, tells the organization when they are operational, and is responsible for ongoing maintenance. [zia.private-service-edge.deployment:zscaler-provisions]

**Forwarding to the cluster.** Private Service Edge VIP addresses can be selected on the GRE Tunnels page, but self-provisioning of GRE tunnels toward a Private Service Edge cluster is supported only for clusters on public IP space (non-NAT). A GRE tunnel toward a cluster in a NAT environment needs a support ticket. [zia.private-service-edge.deployment:gre-self-provisioning-public-ip-only] If the organization uses PAC files to forward traffic to the Zscaler service, the PAC variables that point to the Private Service Edges must specify the subcloud Zscaler configured for the organization. [zia.private-service-edge.deployment:pac-subcloud] When an organization uses Private Service Edges, the Zscaler service creates a subcloud that maps the domain names GATEWAY.<Subcloud Name>.<Cloud Name> and SECONDARY.GATEWAY.<Subcloud Name>.<Cloud Name> to the IP addresses of the Private Service Edges and any Public Service Edges the organization wants to use; the page's PROXY statement uses the _FX forms of those names. [zia.private-service-edge.deployment:pse-subcloud-fx] Forwarding methods in general are [Forwarding methods and their required fields](kb:zia.forwarding-control.methods).

**Verify.** The documented acceptance test is: browse to an external site and confirm the service requests credentials if authentication is enabled for the location, confirm a policy block is enforced, check the logs in the Admin Console dashboard, and, with a ZDX subscription, check the ZIA PSE Health Dashboard. [zia.private-service-edge.deployment:acceptance-test] Then bind the cluster to a Location, and do that part with Zscaler Support: [Binding a Private Service Edge cluster to a Location, and the open-proxy hazard](kb:zia.private-service-edge.location-binding).

What to check:
1. Whether GARP is enabled on the switches directly connected to the Private Service Edges, the switch ports are in Access mode, and LLDP is off on those ports.
