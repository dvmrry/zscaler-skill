# ICAP receivers for DLP: secure and unencrypted ICAP, the FCC cloud and mTLS (zia.dlp.icap-receivers)
Also called: icap receiver; dlp icap server; secure icap; unencrypted icap; stunnel; icap fcc cloud; icap mtls ca certificate; dlp server icap

Secure or unencrypted ICAP receivers can be configured on the DLP Incident Receiver page for Inline Web DLP policy rule violations, and Zscaler recommends sending transaction information via secure ICAP. ICAP receivers for web traffic filtering are a separate feature, described in About ICAP Receivers for URL Filtering. [zia.dlp.icap-receivers:secure-or-unencrypted] An ICAP receiver has a name, a status that shows whether it is enabled or disabled, and a DLP server URI. If a receiver is disabled, the Service Edge cannot send information to it. [zia.dlp.icap-receivers:receiver-fields] Where an ICAP receiver sits among the other places a DLP match can go is in [Where a DLP match goes: notification, ICAP, Incident Receiver and Cloud-to-Cloud](kb:zia.dlp.incident-forwarding).

**The receiver URI.** The Receiver URI must follow the format icap://<FQDN or IP address>:<port number>/<servicepath>, and the Unencrypted ICAP page gives the same format. The field is prepopulated with icaps:// because Zscaler recommends secure ICAP, and icap:// can be used where plain text is preferable, for example for debugging. FQDNs and IP addresses of DLP servers and load balancers are accepted. A port number must be included and must match the port on which the network firewall accepts ICAP traffic from the service. The service path specifies whether the DLP server monitors outgoing or incoming traffic, and for Vontu the example is reqmod (Request Mode) for outgoing traffic. [zia.dlp.icap-receivers:uri-format] The recommended port is stated inconsistently [divergence:zia.dlp.icap-receivers:secure-icap-port].

**How the information reaches the DLP server.** The Service Edge that inspected a transaction does not send the information to the DLP server itself; it forwards it to a Service Edge on a different cloud, called the FCC cloud, which sends it to the DLP server. The network firewall must accept communications from the Service Edges on the FCC cloud, on a designated port that must match the port specified in the Admin Console when the DLP servers are defined, and https://config.zscaler.com/zscaler.net/icap has the traffic details. [zia.dlp.icap-receivers:second-service-edge] The second Service Edge sends the client IP and username via ICAP X-headers, a copy of the HTTP POST request that contains the file that violated the DLP policy (or, for HTTP Forms data, a copy of the violating content), and the host URL the user was sending to. The service can send the information to an on-premises or cloud-based DLP server. [zia.dlp.icap-receivers:what-is-sent] The Secure ICAP page says to place the DLP server in a DMZ where it can have a public IP address. The Adding an ICAP Receiver page defines the receiver by providing the DLP server's public IP address with the port number on which the network firewall initially accepts the secure ICAP traffic sent by the Zscaler service. [zia.dlp.icap-receivers:dmz-public-ip] Which kind of Service Edge must reach the server differs between the two enabling pages [divergence:zia.dlp.icap-receivers:reaching-service-edge].

**Secure and unencrypted.** Because most DLP servers can only read unencrypted information, Zscaler recommends installing the open-source stunnel application on the DLP server to decrypt the transaction information for secure ICAP. The Secure ICAP page says the stunnel port is usually 11344 and the DLP server's accepting port is usually 1344, a successful configuration shows "Configuration successful" in the stunnel console or debug logs, and the certificate generated by stunnel does not need to be imported into the Admin Console. [zia.dlp.icap-receivers:stunnel] With unencrypted ICAP, the second Service Edge does not encrypt the transaction information it sends to the DLP server, so the stunnel application is not needed and the DLP server can accept the information as is. [zia.dlp.icap-receivers:unencrypted-mode] The Unencrypted ICAP page says as many DLP servers as needed can be configured, but only one server needs to be specified for each DLP policy, and load balancers in front of a DLP server can be configured as well. [zia.dlp.icap-receivers:servers-per-policy]

**Rules on both sides.** Two kinds of DLP rule forward transaction information to the organization's DLP server. Rules with content inspection use Zscaler's DLP engines to scan content before forwarding. Rules without content inspection bypass scanning by the DLP engines and filter content on the specified criteria, which for that option must include one or more file types. [zia.dlp.icap-receivers:two-forwarding-rule-kinds] The organization's DLP product must have rules that detect the same data type as the DLP rules with content inspection, or the information sent for a rule violation is not reported as an incident in that product. It must have rules that detect the same file types as the DLP rules without content inspection, or the information for a rule violation does not appear in it. [zia.dlp.icap-receivers:matching-third-party-rules] The wire shape of a rule without content inspection is in [Web DLP rule API fields, enums and fields the contract does not document](kb:zia.dlp.rule-wire-shape).

**Mutual authentication.** The MTLS CA certificate that the ICAP receivers article offers for download is optional and only required if the ICAP server uses mutual authentication, and it is installed in the ICAP server's tunnel configuration. It is a root CA certificate, not a server certificate. Client certificate verification is part of the SSL server configuration on the customer's side, and if the SSL server does not request it the Zscaler SSL client does not send a certificate. The client certificate is signed with an intermediate CA certificate that is signed with the root and is sent with the client certificate during the SSL handshake. The SSL server must use the root CA certificate to send the acceptable CA names, and a minimal set of root CA certificates is recommended for the ICAP SSL server. [zia.dlp.icap-receivers:mtls-ca]

**Open.** The ICAP X-header names are open [gap:zia.dlp.icap-receivers:x-header-names], and the config.zscaler.com ICAP page is not captured [gap:zia.dlp.icap-receivers:config-pages-not-captured].

What to check:
1. Whether the firewall port, the console URI port and the stunnel or DLP server port are the same value, before relying on a recommended port.
2. Whether the third-party DLP product has rules for the same data types (rules with content inspection) or file types (rules without), since information without a matching rule does not appear as an incident.

Sources disagree (name both sides):
- The Secure ICAP page recommends 11344 for secure ICAP and 1344 for ICAP, and the Incident Receiver URI defaults to 1344; the Unencrypted ICAP page recommends 1344. [divergence:zia.dlp.icap-receivers:secure-icap-port]
  - zscaler-help: For secure ICAP the recommended port is 11344.
  - zscaler-help: The same page's URI bullet, which says the URI port must match the firewall's ICAP port, recommends 1344 for ICAP.
  - zscaler-help: The Unencrypted ICAP page recommends 1344.
  - zscaler-help: The Incident Receiver URI defaults to port 1344.
  Impact: The page text leaves open whether 11344 is only the stunnel listening port while the URI port is 1344, or whether the console URI port for secure ICAP is 11344, so a port cannot be read off one sentence.
- The Secure ICAP page says the Public Service Edge must reach the DLP server, and the Unencrypted ICAP page says Private Service Edges must, while both pages say elsewhere that a Service Edge on the FCC cloud sends the information. [divergence:zia.dlp.icap-receivers:reaching-service-edge]
  - zscaler-help: The Public Service Edge must be able to reach the DLP server using its public IP address.
  - zscaler-help: Private Service Edges for Internet & SaaS (ZIA) must be able to reach the DLP server using its public IP address.
  - zscaler-help: A Service Edge on the FCC cloud sends the information to the DLP server.
  Impact: Which kind of Service Edge to allow through the firewall to the DLP server is not settled by the two pages; the FCC cloud's Service Edges are the sender both pages describe.
