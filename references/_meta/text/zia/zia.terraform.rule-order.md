# How the ZIA Terraform provider applies rule order (zia.terraform.rule-order)
Also called: terraform reorder; terraform rule order wrong; terraform apply reordered rules; rule moved to the bottom; reorderAll; rank 7

The ZIA provider does not write a rule's declared order directly: it hands the declared position to a background worker that moves the rule there. Up to v4.8.13 every update first moved the rule out of the way, and from v4.8.14 only a rank change does. Up to v4.8.13 every URL Filtering rule update, whatever field changed, was first sent with rank 7 at the order of the last rule (sorted by rank, then order), and only afterwards moved back to its declared order by the reorder worker; the rule was written at that order, not after it. From v4.8.14 an update that changes only `order` writes nothing, an update that changes other attributes but not `rank` is written at the rule's current position, and only an update that changes `rank` is written at the end of the list with rank 7; the declared position is then handed to the reorder engine. [zia.terraform.rule-order:update-parks-every-update] Before v4.8.11, if listing the existing rules failed during an update, the error was only logged and the code read the last element of whatever came back: if the first page failed, the list was empty and the index panicked; if a later page failed, the rule was parked using a partial list. v4.8.11 returns the list error from the update before the index is read (#610). From v4.8.14 the update no longer indexes the last element: the end of the list comes from `endOfList`, which starts at order 1, and that end-of-list read is made only when `rank` changed, with a failed read returned as an error. [zia.terraform.rule-order:list-error-then-panic] The order used to park a rule comes from a list read through the Go SDK's GetAll, which can return a truncated list; up to v4.8.13 on every URL Filtering update, from v4.8.14 only on an update that changes `rank`. With more rules than one page holds, the "highest existing order" can be a position inside the policy rather than its end. [zia.terraform.rule-order:parking-spot-from-truncated-list] Before v4.8.14, deleting a rule and changing the order of the remaining rules in one apply could fail with `INVALID_INPUT_ARGUMENT` `Rule is not allowed at order N`, and the documentation advised deleting the rule with `-target` first. v4.8.14 fixed this: a rule whose only change is `order` is no longer rewritten, and a write the API rejects because the rule list changed is retried, at most three times. [zia.terraform.rule-order:delete-renumber-same-apply]

**Putting it back.** Declared orders are applied by one background worker per rule type. It rescans on a 30-second ticker, sleeping for half the interval between checks, and each pass reads current positions once. [zia.terraform.rule-order:background-worker] The reorder worker has no way to report failure: up to v4.8.14 `reorderAll` returns no value, and from v4.8.15 it returns only the registry revision that the goroutine uses to decide whether to run again. Waiting resources are released by closing a channel. [zia.terraform.rule-order:worker-cannot-report-failure] A pass is judged only on the rules registered by this apply: it is "clean" when none of them needed a move, was skipped, or failed, and the number registered did not change since the previous pass. From v4.8.14, a cycle in which no PUT has been issued ends after one pass in which no registered rule needed a move, was skipped or failed; otherwise it needs two consecutive clean passes. [zia.terraform.rule-order:converges-on-registered-rules-only] From v4.8.15, after reading current positions and before moving any rule, the worker counts the registered rules whose declared order exceeds the number of rules with an API order of 1 or more. If there are any it logs the deferral and returns without issuing order PUTs, so later creates can extend the list. [zia.terraform.rule-order:defers-batch-when-targets-exceed-orderable] Whether the apply reports anything when a declared order stays unreachable is open [gap:zia.terraform.rule-order:unreachable-target-deferral-effect]. A rule the apply did not register is never compared with a declared position or moved by the worker; it enters a pass only through the read of current positions. [zia.terraform.rule-order:unregistered-rules-not-compared] Up to v4.8.14, within a pass each rule is compared against the positions read at the start of the pass; positions are not refreshed after a move, so later rules in the same pass are judged against stale positions. [zia.terraform.rule-order:stale-positions-within-a-pass] From v4.8.15 the worker updates its snapshot of rule positions after every successful move, so the following rules in the pass are compared against where they now are. Phase 1 leaves the longest run of rules already in the right relative order where they are and moves only the others. [zia.terraform.rule-order:pass-snapshot-updated-after-each-move] The worker gives up and returns, reporting no error (up to v4.8.14 it returns no value, and from v4.8.15 only the registry revision), in several situations: after six ticks in which registered rules stay deferred or their moves fail with no progress, or after two ticks in which only deferred rules remain. From v4.8.15 it also returns at once without any order PUT when a registered declared order exceeds the number of orderable rules; the provider describes this as releasing the batch so later creates can extend the list, and the troubleshooting guide says placement is deferred while registered targets exceed the available positions. From v4.8.7 an oscillation breaker (SUP-4231) also logs the still-misplaced rules and returns after repeated passes that issue PUTs without improving on the best at-target count. From v4.8.11 it also returns after six consecutive passes in which the current rule order could not be read (#610); before v4.8.11 a failed read only logged the error and continued, so a read that kept failing kept the worker looping. The v4.8.11 comment says the waiting create or update then reads the rule back and reports the API error. [zia.terraform.rule-order:gives-up-silently] So an apply can finish successfully with rules out of their declared order, and only a later plan's drift shows it. [zia.terraform.rule-order:wrong-order-reported-success] From v4.8.15 the state written when a rule is created or updated records the order and rank registered with the reorder engine, not the position the API reported at that moment. A later refresh reads the API's position and reports any divergence that remains. Before v4.8.15 a large deployment could record rules in state at the interim position they held while the remaining rules were still being ordered. [zia.terraform.rule-order:state-records-registered-target]

**Rules the apply did not touch.** Up to v4.8.13, editing any field of a rule placed above a terminal deny could leave the deny no longer last: the edit parked the rule below it, and if moving it back failed or gave up, the apply still reported success. From v4.8.14 only an edit that changes `rank` parks the rule at the end of the list. [zia.terraform.rule-order:terminal-rule-can-be-displaced] Product-side rule order semantics are in [URL Filtering rule order and first match](kb:zia.url-filtering.rule-order).

What to check:
1. Whether the terminal rules are still last after an apply that edited ordered rules, by re-reading the whole policy's order rather than only the edited rules.
2. Whether a later plan shows rules out of their declared order after an apply that reported success.
