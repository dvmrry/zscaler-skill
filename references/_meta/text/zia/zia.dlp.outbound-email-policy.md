# Outbound Email DLP policy: smart host flow, per-recipient evaluation, criteria and header actions (zia.dlp.outbound-email-policy)
Also called: outbound email policy; outbound email dlp policy; email dlp rule; zscaler smart host; email dlp headers; X-Zscaler-Block

Outbound Email DLP is policy on outbound email sent to external domains, enforced by the customer's email server. Zscaler Outbound Email DLP enforces policy rules on outbound email content sent to external domains, including content in subject lines, body text and attachments. The customer's email server sends email to, and receives it from, the Zscaler smart host using connectors and rules, and the smart host sends it to the Zscaler DLP service for inspection. [zia.dlp.outbound-email-policy:what-it-is] Rules on the email server instruct Gmail, Microsoft Exchange or a secure email gateway (SEG) to send the email to the Zscaler smart host over SMTP for DLP inspection. The DLP service inserts headers based on the verdict, the email server enforces the action from its mail flow or transport rules and the headers, and an allowed email is delivered to the next hop MTA or the intended recipient. [zia.dlp.outbound-email-policy:smart-host-flow] The DLP service adds headers that define DLP actions to emails that trigger outbound email policy, and the email server uses those headers to determine enforcement actions when it receives the inspected email back. [zia.dlp.outbound-email-policy:headers-enforce] Outbound Email DLP lets admins use the same DLP policy tools they use across other channels, which the page lists as Inline Web DLP, Endpoint DLP and SaaS Security API DLP. [zia.dlp.outbound-email-policy:same-policy-tools]

**Which rule applies.** The service evaluates all outbound email policy rules on a per-recipient basis. If several rules match a recipient it applies the rule with the most restrictive action, and among rules with the same restrictive action the one with the highest rule order. Before executing it, the service checks whether the matching rule has exception rules, evaluating them in rule order and stopping at the first match, and a matching exception replaces the parent rule. One email can therefore be allowed for one recipient and blocked for another. [zia.dlp.outbound-email-policy:per-recipient-evaluation] In the vendor's first scenario R1 and R3 both match, R1 having the higher rule order and R3 the most restrictive action. The service executes R3, with an action of Block and a severity of High, and R1 is logged as having matched. This is an example from the page. [zia.dlp.outbound-email-policy:matched-rules-logged-example] The rule list page words the order differently [divergence:zia.dlp.outbound-email-policy:evaluation-order]. When Stop Rule Evaluation is enabled and a DLP rule is triggered, policy evaluation stops and no further DLP rules are evaluated for the same transaction. [zia.dlp.outbound-email-policy:stop-rule-evaluation] What Stop Rule Evaluation does together with per-recipient evaluation is open [gap:zia.dlp.outbound-email-policy:stop-rule-per-recipient], and so is which way a higher rule order points [gap:zia.dlp.outbound-email-policy:highest-rule-order].

**Exception rules.** Exception rules are child rules that exclude specific users or groups that must perform tasks as part of a necessary workflow. A parent outbound email rule can have up to 32 exception rules, each inherits the parent's rule name, which cannot be changed, and takes its own Exception Rule Name. A disabled exception rule keeps its place in the rule order and the service skips it. [zia.dlp.outbound-email-policy:exception-rules]

**Criteria.** A rule selects where to send the email to the Zscaler smart host for DLP inspection, with options Outlook Add-in and SMTP Smarthost, and selects the email tenants it applies to. [zia.dlp.outbound-email-policy:evaluation-scope] A rule's Users, User Groups and Departments each take Any or up to 32 entries. The text says Zscaler Support can be contacted to increase the limit of Users or Departments. [zia.dlp.outbound-email-policy:who-limits] The User Risk Profile levels are Low (scores 0 to 29), Medium (30 to 59), High (60 to 79) and Critical (80 to 100); selecting no value ignores the criterion in the policy evaluation. [zia.dlp.outbound-email-policy:user-risk-levels] Personal Email Detection can be enabled or disabled to detect when a user attempts to send sensitive data to a personal email address. [zia.dlp.outbound-email-policy:personal-email-detection] Content Matching selects up to 4 DLP engines. If None is selected the service does not use DLP engines and instead flags content on the criteria specified. Match Only is available only when Select DLP Engines is chosen; when enabled the service acts only on content that exclusively matches the rule's engines, and when disabled it can also consider content that matches engines in other rules. [zia.dlp.outbound-email-policy:content-matching] A rule specifies where the service looks for sensitive data: Email Attachments, Email Body or Email Subject. [zia.dlp.outbound-email-policy:content-locations] In the Outbound Email DLP rule article, the available File Type list changes based on whether DLP engines are used for content inspection, and the article says Zscaler DLP engines can scan files of up to 100 MB, with individual files in an archive also a maximum of 100 MB when decompressed. This is the article's wording for Outbound Email DLP rules. [zia.dlp.outbound-email-policy:file-type-and-size] Other pages give a different engine file size [DLP file size, archive and text limits: why DLP did not catch a large file](kb:zia.dlp.inspection-limits). Minimum Data Size (KB) is the minimum size data must meet before the rule applies; its default of 0 KB means there is no minimum. [zia.dlp.outbound-email-policy:minimum-data-size] A rule can select up to 8 email recipient domain profiles and up to 8 email recipient profiles. Recipient Scope and Threshold selects which recipient fields are subject to the external recipient limits and the minimum number of external recipients required to trigger the policy, and appears only when the Evaluation Mode is Outlook Add-in. [zia.dlp.outbound-email-policy:recipient-criteria] A rule's Time is Always, which applies it to all time intervals, or up to two time intervals. [zia.dlp.outbound-email-policy:time] Outbound email rules can use Zscaler custom and predefined DLP engines to detect sensitive data, allow or block user activities, or add custom headers to emails. Without DLP engines the service functions as a filter, only flagging content based on specific criteria. [zia.dlp.outbound-email-policy:filter-without-engines] The Outlook Add-in mode and the available file types are not described [gap:zia.dlp.outbound-email-policy:criteria-undescribed].

**Actions and headers.** Depending on how the rules are configured, the headers instruct the email server to take a default action (allow or block content) or an action mapped to a custom header configured on the server. [zia.dlp.outbound-email-policy:header-enforcement-model] The Allow action adds the default header X-Zscaler-Block:0 (0=Allow) and Block adds X-Zscaler-Block:1 (1=Block) to emails that trigger the rule. Custom Header Insertion includes a custom header on those emails, which is designed to take an action mapped to the header on the email server. [zia.dlp.outbound-email-policy:actions-and-headers] The Quarantine action is described differently across the vendor's pages [divergence:zia.dlp.outbound-email-policy:quarantine-representation]. On the rule configuration page the Quarantine action includes the X-Zscaler-Quarantine:1 default header to quarantine emails that trigger the rule. The page says the option is available for Microsoft Exchange only and that the Block action takes precedence over Quarantine regardless of prior Rule Order configurations. [zia.dlp.outbound-email-policy:quarantine-action] Whether Quarantine is Exchange only is not consistent either [divergence:zia.dlp.outbound-email-policy:quarantine-scope]. The custom header format also differs between the parent and exception rule text [divergence:zia.dlp.outbound-email-policy:custom-header-format]. For Microsoft Exchange only, optional quarantine release with Zscaler Workflow Automation sends potentially sensitive emails to be quarantined on Microsoft Exchange. After quarantine, incidents are created in Workflow Automation where administrators review them and release or delete the quarantined emails. [zia.dlp.outbound-email-policy:quarantine-release-zwa] The Workflow Automation side is in [Release Email Quarantine releases quarantined emails to all recipients for Email incidents whose action is Quarantine; applied to other incidents, the action completes successfully but nothing is done to them, and an error details window lists why.](kb:zwa.incidents:quarantine-release). Which action a Quarantine rule logs is open [gap:zia.dlp.outbound-email-policy:quarantine-log-action], and so is whether a quarantined message also carries X-Zscaler-Block [gap:zia.dlp.outbound-email-policy:quarantine-with-block-header].

**After a match.** A rule can select a Zscaler Incident Receiver from a drop-down, or a tenant and a Cloud-to-Cloud Forwarding configuration from drop-downs; the page says each must be configured to complete the step. Zscaler does not take ICAP responses from the Incident Receiver: the service only monitors or blocks content according to the policy, then forwards information about activities. [zia.dlp.outbound-email-policy:incident-forwarding] Whether ICAP receivers can be chosen on these rules is not stated [gap:zia.dlp.outbound-email-policy:icap-on-email-rules]. If an auditor and notification template are not selected for a rule, a notification is not sent for this rule. The auditor type is a Hosted database auditor or one External to the organization, identified by an email address. [zia.dlp.outbound-email-policy:notification] NSS feeds can be configured to specify the data from the Outbound Email DLP Policy logs that NSS sends to a SIEM. An Incident Receiver configured in the policy rules can be integrated with Workflow Automation to capture and remediate incidents generated by policy violations. [zia.dlp.outbound-email-policy:logs-and-zwa]

**Before configuring.** To enable granular user management, users must be onboarded in the Admin Console. For organizations that onboard users by User Principal Name, SCIM-based user lookup is supported for both Exchange and Gmail, which requires email attributes to be synchronized between the Zscaler service and the email server. The domains used in the policy must be set up in the Company Profile. [zia.dlp.outbound-email-policy:prerequisites] A rule has a unique name or the default name, a description of at most 10,240 characters, a severity of High, Medium, Low or Information, and a status; a disabled rule is not actively enforced but keeps its place in the rule order, and the service skips it. [zia.dlp.outbound-email-policy:rule-details] The email tenants a rule uses are in [Outbound Email DLP email tenants and mail-server setup (SEG, Gmail, Exchange)](kb:zia.dlp.outbound-email-tenants) and the domain and recipient profiles in [DLP domain profiles and recipient profiles](kb:zia.dlp.email-profiles). The SDK and Terraform surface is in [Outbound Email DLP rules in the SDKs and Terraform provider](kb:zia.dlp.outbound-email).

What to check:
1. Which rule is applied to a recipient: compare the recipient's matching rules by action first, then rule order, with exceptions checked before the parent runs.
2. How a Quarantine rule is represented before relying on its header or its log action.
3. Whether a Quarantine rule is aimed at a Microsoft Exchange tenant and whether the Exchange mail flow maps the quarantine header.

Sources disagree (name both sides):
- The vendor's pages disagree on how Quarantine is represented: a Quarantine action with an X-Zscaler-Quarantine:1 header, or the Custom Header Insertion action with an X-Zscaler-Scan:Quarantine header. [divergence:zia.dlp.outbound-email-policy:quarantine-representation]
  - zscaler-help: Quarantine is an action of its own that adds the default header X-Zscaler-Quarantine:1.
  - zscaler-help: The NSS feed filter treats quarantine as an action taken by the email application and defined by a custom header, with the example X-Zscaler-Scan:Quarantine, selected as Custom Header Insertion.
  - zscaler-help: The enforcement article lists the DLP actions as Allow, Block and Custom Header Insertion, without Quarantine.
  Impact: The header name and the action list differ between the pages, so which header a Quarantine rule inserts, and whether such a rule appears in logs as Quarantine or as Custom Header Insertion, is not settled by the vendor's pages.
- One article says outbound email rules are evaluated in ascending numerical order; the enforcement article says all rules are evaluated per recipient and the most restrictive action wins. [divergence:zia.dlp.outbound-email-policy:evaluation-order]
  - zscaler-help: Outbound email policy rules are evaluated in ascending numerical order.
  - zscaler-help: All rules are evaluated per recipient and the rule with the most restrictive action applies.
  Impact: Whether rule order alone decides, or only breaks ties between rules with the same action, depends on which page governs; the enforcement article and the rule configuration page's Rule Order text describe the per-recipient model.
- The rule page says Quarantine is available for Microsoft Exchange only; the SEG article tells the SEG to quarantine emails that carry the quarantine header. [divergence:zia.dlp.outbound-email-policy:quarantine-scope]
  - zscaler-help: The Quarantine option is available for Microsoft Exchange only.
  - zscaler-help: The SEG should quarantine emails that carry X-Zscaler-Quarantine: 1.
  Impact: Whether a Quarantine rule can be used with a SEG tenant is not settled: the SEG page describes the header as one a SEG acts on, while the rule page restricts the option to Exchange.
- The parent rule text and the exception rule text give different custom header formats. [divergence:zia.dlp.outbound-email-policy:custom-header-format]
  - zscaler-help: The parent rule's custom header format is X-name:value.
  - zscaler-help: The exception rule's custom header format is name:value, and its example is the Quarantine default header X-Zscaler-Quarantine:1.
  Impact: Whether the custom header name must carry an X- prefix on an exception rule is not settled, and the exception example reuses the Quarantine default header as a custom one.
