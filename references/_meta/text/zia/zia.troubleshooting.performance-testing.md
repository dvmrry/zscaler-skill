# Measuring ZIA performance: the Cloud Performance Test and why common speed tests mislead (zia.troubleshooting.performance-testing)
Also called: speedtest.zscaler.com; cloud performance test; zscaler speed test; speedtest slow through zscaler; iperf zscaler; measuring zscaler performance; data trickling

The Zscaler Cloud Performance Test is a browser-based tool for collecting performance troubleshooting information for end users connecting to the internet through Internet & SaaS; it runs tests such as download or upload bandwidth between the browser and the Public or Private Service Edge the traffic is forwarded to. Zscaler recommends it, powered by Digital Experience (ZDX), over third-party speed tests such as Speedtest.net, because those add latency and variables that make troubleshooting difficult. [zia.troubleshooting.performance-testing:cloud-performance-test] The user must be authenticated to Internet & SaaS to use the tool; a user who is not authenticated (the page's example is working remotely with Client Connector enabled) is prompted for a user ID and password. The tool is hosted only on HTTP, not HTTPS: entering http://speedtest.zscaler.com redirects automatically to the user's Public or Private Service Edge, which acts as the speed test server. The username is hidden and only the domain part is visible. [zia.troubleshooting.performance-testing:access]

**What the page shows.** Before the test the page shows the user's email ID with the username hidden, the proxy server's Proxy Hostname and the Cloud Name, plus a geolocation map of the user and the connected data center with the traffic forwarding method at the bottom of the map. [zia.troubleshooting.performance-testing:page-details] The test reports HTTP Ping (average application-layer HTTP round-trip time to the test server on the Service Edge, over multiple small requests, in milliseconds), HTTP Jitter (variation across the pings, in milliseconds, where lower means more consistent) and Download and Upload Bandwidth (average Mbps from multiple simultaneous large transfers with a Zscaler-hosted HTTP test server, excluding outliers). It also reports a Cloud Path, an ICMP Traceroute Latency and summarized ZDX path from a reverse ICMP traceroute started at the Service Edge toward the device. Results download as a CSV file, and the date and time of the last test appear at the bottom of the page. [zia.troubleshooting.performance-testing:results] Clicking More Diagnostics shows the Cloud Path in the other direction, calculated with a forward ICMP traceroute, whatever the Z-Tunnel version. When the user is connected through Z-Tunnel 2.0 a More Client Connector Diagnostics section also appears, with File Download Speed (Z-Tunnel and direct download speed between the device and the Zscaler data center, from a single large file download from a Zscaler-hosted HTTP test server) and UDP Throttling (speed throttling information such as latency, jitter and packet loss percentage). [zia.troubleshooting.performance-testing:more-diagnostics]

**Common speed tests.** Common network performance tools such as Speedtest and Iperf can give inaccurate results when using the Zscaler service. Zscaler recommends the Zscaler Cloud Performance Test tool, one of the browser's network analysis tools, or Wireshark. [zia.troubleshooting.performance-testing:common-tools-inaccurate] As the page's example of test length, Speedtest runs for only 10 seconds, which matters because many internet service providers boost the available bandwidth for a short period or for a portion of a transaction; the page says the file that can be moved in 10 seconds usually falls within that boosting window, the page says this can provide results that are much higher than the true average speed. [zia.troubleshooting.performance-testing:speedtest-length] With data trickling, Zscaler sends a small amount of data to the browser to keep the session open while the rest is buffered for scanning. The page says this can cause problems because Speedtest leaves the fastest 10% and the slowest 30% of data out of its analysis, so the buffer release is likely to be treated as an outlier and not included in the results. [zia.troubleshooting.performance-testing:data-trickling] The page names caching as another cause of misleading test results: many types of services and software cache content known to be safe, and when that type of data is included in a test it gives results with much higher speeds than could be achieved without caching. [zia.troubleshooting.performance-testing:caching] Iperf shares many of the same issues as Speedtest and is also highly susceptible to server limitations and limitations on a single session. [zia.troubleshooting.performance-testing:iperf] Zscaler does not recommend ping tests to measure end user performance, because it implements ICMP deprioritization in its data centers. [zia.troubleshooting.performance-testing:no-ping-tests]

**What to expect.** The Zscaler service inspects content on an individual user session basis, so one user should not be expected to fill the entire network pipe the enterprise has available; a 10 Gbps internet egress does not automatically give a user 10 Gbps. The page says its video codec table shows a 4 Mbps connection can provide HD-quality video, and that the major video streaming and video conferencing companies it names all recommend 5 Mbps or more; the page footnotes the table with "Refer to the Microsoft documentation." [zia.troubleshooting.performance-testing:expectations]

**Causes outside the service.** The page says packet loss in MTR results does not necessarily indicate a connectivity problem; in its example the loss begins at the end of the trace, which is the customer's gateway, and it concludes the problem is with the customer's ISP. [zia.troubleshooting.performance-testing:mtr-loss] With transparent forwarding the browser is not aware of a proxy, so every site users access must be resolved by the computer itself, which increases dependency on DNS. With PAC files pac.<cloudname>.net must be resolved, and logic such as dnsResolve(host) or isInNet makes every new domain accessed need resolving. The page says that with high DNS dependency a delayed response from the DNS server negatively affects page loading times. [zia.troubleshooting.performance-testing:dns-dependency] Performing NAT on the gateway device before forwarding traffic to the Public Service Edge can also affect performance, because the device performing the NAT overload could run out of source ports. [zia.troubleshooting.performance-testing:gateway-nat] How the edge is verified is in [ip.zscaler.com and the vendor's causes when traffic does not land on the nearest Public Service Edge](kb:zia.traffic-forwarding.verification).

What to check:
1. Whether the figure the user quotes came from Speedtest, Iperf or a ping test, which the vendor says can mislead through the service, before treating it as the service's throughput.
2. Whether the expectation is one user filling the enterprise's whole egress pipe, which the vendor says should not be expected.
