# Runbook: GRE tunnel hard down, flapping and up-but-no-traffic (zia.traffic-forwarding.runbook.gre)
Also called: GRE Tunnel is Hard Down; GRE Tunnel is Flapping; GRE Tunnel is UP but Traffic Not Working

**Hard down.** For a GRE tunnel that will not come up, the runbook says to ping the Zscaler GRE VIP from the customer gateway; if it is unreachable, check firewalls and ACLs, capture packets on the edge device to verify traffic leaves the network, and engage the ISP about GRE restrictions. [zia.traffic-forwarding.runbook.gre:hard-down-reachability] In the runbook's section on troubleshooting Zscaler public DC issues, if the GRE VIP is reachable, the runbook says to ping the Zscaler GRE internal IP sourced from the tunnel interface (example: ping 172.21.37.162 source tun1); if it is unreachable, validate the tunnel configuration, addresses and routing against the location's GRE Tunnel Information, found by searching Locations for the GRE source IP. GRE tunnels configured on Virtual Service Edges are established with no internal IP addresses, like unnumbered GRE tunnels. [zia.traffic-forwarding.runbook.gre:hard-down-internal-ip] The runbook says GRE internal ranges are auto-assigned using a /30; in the vendor's example the network address is 172.21.37.160, the customer GRE internal IP .161, the Zscaler GRE internal IP .162 and the broadcast .163. [zia.traffic-forwarding.runbook.gre:internal-range] [divergence:zia.traffic-forwarding.runbook.gre:internal-range-size] In the vendor's primary tunnel sample, the tunnel source is optional and defaults to the outbound interface IP if not specified, and the tunnel destination must point to the correct GRE VIP as per the config page. [zia.traffic-forwarding.runbook.gre:tunnel-config-sample]

**Keepalives.** GRE keepalives are not supported if the GRE tunnel traverses NAT, and the runbook says to ensure they are disabled in that case; where the gateway uses NAT, GRE packets must be NAT'd to the IP defined as the GRE source. [zia.traffic-forwarding.runbook.gre:keepalive-nat] The runbook says a GRE tunnel might remain down due to failed IP SLA probes or GRE keepalives; on a Cisco router it names 'debug tunnel keepalive' and 'show interface tunnel <tunnel-number>' for keepalive status (Up/Down), and 'show ip sla summary' for IP SLA probe status and failures. [zia.traffic-forwarding.runbook.gre:cisco-commands] For a physical link MTU of 1500 the runbook says to configure the GRE tunnel MSS as 1436. [zia.traffic-forwarding.runbook.gre:mss]

**Flapping.** For a flapping GRE tunnel (frequent up/down transitions), Zscaler recommends an Active/Standby pair with automatic failover based on application-layer health monitoring and HTTP probes for health (ICMP probes if the gateway does not support HTTP probes); the runbook also says to confirm the health probes are targeting gateway.<cloudname>.net/vpntest. [zia.traffic-forwarding.runbook.gre:flapping-monitoring] To test GRE failover the runbook says to ensure traffic shifts to the secondary tunnel when the primary fails, and to use show ip sla summary and show ip sla statistics on a Cisco gateway. [zia.traffic-forwarding.runbook.gre:flapping-failover-test] Scheduled maintenance on the Zscaler data center might temporarily affect GRE tunnels, and observable packet loss can cause Layer 7 health monitoring to fail and the GRE tunnel to flap. [zia.traffic-forwarding.runbook.gre:maintenance-and-loss] What marks a flap in the sample IP SLA output is open [gap:zia.traffic-forwarding.runbook.gre:ip-sla-flap-threshold]. MTR and latency checks are in [Runbook: MTR collection, WinMTR for Client Connector and PAC, and latency checks for GRE and IPSec gateways](kb:zia.traffic-forwarding.runbook.tunnel-path).

**Up but no traffic.** For a GRE tunnel that is up but passes no traffic, the runbook says to review the Tunnel Insight logs with Tunnel Type and Tunnel Source IP filters, validate static or policy-based routing sends traffic over the tunnel, and check that Rx/Tx bytes increment on the gateway; it also says to run PCAP on the gateway device to validate that the intended traffic is routed over the tunnel. [zia.traffic-forwarding.runbook.gre:up-no-traffic]

Sources disagree (name both sides):
- The troubleshooting runbook says GRE internal ranges are auto-assigned using a /30, while the GRE tunnel configuration article says Zscaler assigns a /29 that is split into two /30 subnets. [divergence:zia.traffic-forwarding.runbook.gre:internal-range-size]
  - zscaler-help: GRE internal ranges are auto-assigned using a /30 (4 IPs, including network and broadcast).
  - zscaler-help: Zscaler assigns a /29 subnet for the GRE tunnels, which you split into two /30 subnets.
  Impact: Both pages end at a /30 per tunnel, but they differ on whether the assignment is a single /30 or a /29 you split. Do not tell an admin the range is a /29 or an automatic /30 without checking the location's GRE Tunnel Information.
