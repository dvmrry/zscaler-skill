# How locations land in groups: location type, defaults, exclusion flags and Terraform support (zia.locations.group-assignment)
Also called: location type group; exclude_from_dynamic_groups; exclude_from_manual_groups; static_location_groups; dynamic_location_groups; profile default; policy scope changes without edit; other sublocation in dynamic group; terraform dynamic location groups
Former IDs: zia-46

A location can end up in a group, and so in a rule's scope, without anyone choosing that membership.

**At creation.** Choosing a Location Type on a location or sublocation assigns it to the matching predefined group automatically, without an explicit membership choice. [zia.locations.group-assignment:type-assigns-predefined] A location with a Location Type is therefore subject to every policy scoped to that predefined group from creation. [zia.locations.group-assignment:type-policy-from-creation] A sublocation added to a location created in the Zscaler Admin Console gets the Workload traffic type and the Workload Traffic Group by default; a sublocation added to an Extranet-type location gets the Extranet type and uses the extranet location's DNS server and traffic selector. [zia.locations.group-assignment:workload-default] When `profile` is omitted on the public API, the service sets CORPORATE if authentication is enabled, GUESTWIFI if authentication is disabled and the name contains "guest", and SERVER otherwise; with a partner API key it sets CORPORATE. [zia.locations.group-assignment:profile-default] A location created through the API without a profile therefore lands in the Corporate User Traffic, Guest Wifi or Server Traffic predefined group according to its authentication setting and name, whether or not the author intended that. [zia.locations.group-assignment:omitted-profile-picks-group]

**Over time.** A saved dynamic group keeps updating to include new matching locations and sublocations. [zia.locations.group-assignment:dynamic-auto-update] Changing a location setting that a dynamic group tests (for example Enforce Firewall Control or Enforce Bandwidth Control) can move the location into or out of that group, and with it into or out of the policies scoped to the group, without any edit to a rule. [zia.locations.group-assignment:attribute-change-moves-policy] The `other` sublocation is an ordinary location object, so a dynamic group whose conditions it satisfies can include it, subjecting it to that group's policy. [zia.locations.group-assignment:other-can-match-groups]

**Opting out.** Exclude from Manual Location Groups and Exclude from Dynamic Location Groups (`excludeFromManualGroups`, `excludeFromDynamicGroups`) stop a location being added to groups and remove it from groups it is already in. In Terraform they are `exclude_from_manual_groups` and `exclude_from_dynamic_groups`. [zia.locations.group-assignment:exclude-flags] Whether the dynamic flag also keeps a location out of the predefined groups is open [gap:zia.locations.group-assignment:exclude-dynamic-scope], and the sources disagree on its reach [divergence:zia.locations.group-assignment:exclude-dynamic-reach].

**Terraform and Ansible.** Terraform's docs say `dynamic_location_groups` and `static_location_groups` cannot be set when `exclude_from_dynamic_groups` and/or `exclude_from_manual_groups` is true; the provider enforces only the manual side, with a plan-time error when `exclude_from_manual_groups` is true and the plan changes `static_location_groups` to a non-empty set. The dynamic-side check is commented out in the source. [zia.locations.group-assignment:tf-exclusive-enforced-one-side] So the manual-side check does not catch an update that turns `exclude_from_manual_groups` on while an already non-empty `static_location_groups` stays as it is: the check runs only when `static_location_groups` changes, so that plan passes. [zia.locations.group-assignment:tf-manual-check-needs-a-change] In the provider source the resource's `dynamic_location_groups` schema entry, its read handling and its write handling are all commented out, while the resource documentation still lists the argument; only `static_location_groups` is wired. [zia.locations.group-assignment:tf-dynamic-field-not-in-schema] The provider changelog records a fix for drift in `static_location_groups` on `zia_location_management` (PR 496, release 4.6.0). [zia.locations.group-assignment:tf-static-drift-fix] The ZIA Ansible location module lists both exclude flags in the computed values it strips from the desired and current location before its idempotency comparison, so a difference in them is never detected. [zia.locations.group-assignment:ansible-reads-exclude-flags]

Sources disagree (name both sides):
- The console limits the dynamic exclusion to user-defined groups; the Terraform docs describe it as covering any dynamic group. [divergence:zia.locations.group-assignment:exclude-dynamic-reach]
  - zscaler-help: The exclusion applies to user-defined dynamic groups and leaves predefined group association alone.
  - tf-zia: The exclusion prevents assignment to, and removes from, any dynamic groups.
  Impact: Whether the flag is a way to keep a Workload or Corporate location out of its predefined group, and so out of that group's policies, depends on which is right.
- The Terraform documentation lists `dynamic_location_groups` for the location resource, while the resource source has it commented out. [divergence:zia.locations.group-assignment:dynamic-groups-docs-vs-schema]
  - tf-zia: The argument exists.
  - tf-zia: The schema entry is commented out.
  Impact: A configuration that sets `dynamic_location_groups` is rejected as an unsupported argument even though the docs describe it.
  Resolved (source-rank) by zia.locations.group-assignment:tf-dynamic-field-not-in-schema: The provider source decides what the provider accepts.
