# Activating ZIA changes from Terraform: methods, session end and concurrent applies (zia.terraform.activation-methods)
Also called: ziaActivator; zia_activation_status depends_on; api_session_timeout terraform; terraform apply activated mid-run; several terraform configurations one tenant; activation queue terraform

Activation from Terraform is tenant-wide, and the platform can also activate on its own. The provider documentation says a single ZIA activation call publishes every pending change in the tenant, regardless of how many resources Terraform created, updated or deleted. [zia.terraform.activation-methods:tenant-wide-call]

**Methods.** The provider documents three activation methods in order of preference: the out-of-band `ziaActivator` CLI, the `zia_activation_status` resource, and the `ZIA_ACTIVATION` environment variable. [zia.terraform.activation-methods:three-methods] The `ziaActivator` CLI is recommended for CI/CD and large configurations: it issues exactly one activation call for the whole run, run after Terraform finishes, and adds no activation traffic to the apply. [zia.terraform.activation-methods:activator-one-call] `zia_activation_status` cannot infer its dependencies: every resource whose changes must be activated has to be listed in `depends_on`, and a resource left out may be applied after activation and stay pending. [zia.terraform.activation-methods:status-resource-needs-depends-on] `ZIA_ACTIVATION=true` is discouraged and may be removed in a future major release: it triggers an activation call for every resource created, updated or deleted. [zia.terraform.activation-methods:env-method-discouraged] The provider documentation gives the activation endpoint a budget of 10 POST requests per minute and 40 per hour, which a configuration of any meaningful size exhausts when every resource activates in flight. [zia.terraform.activation-methods:activation-endpoint-budget] What the provider itself sends when it activates: [When the ZIA Terraform provider activates configuration](kb:zia.terraform.activation).

**Session end.** The ZIA platform activates pending changes on its own when a session ends, either because an API session reached the `api_session_timeout` or because an admin logged out; this applies to all API changes, including Terraform's. [zia.terraform.activation-methods:session-end-autoactivation] The API session timeout accepts 5 to 20 minutes and defaults to 5. [zia.terraform.activation-methods:session-timeout-range] A Terraform run longer than the API session timeout crosses a session boundary and has its pending changes activated part-way through, before the apply has written the rest; the provider then opens a new session and continues without failing. [zia.terraform.activation-methods:mid-run-activation] Activation on session end is native to the platform and cannot be disabled or overridden by the provider; a higher timeout only reduces how often a long run crosses a boundary. [zia.terraform.activation-methods:autoactivation-cannot-be-disabled] Running `ziaActivator` once at the end of a pipeline therefore does not suppress session-end autoactivation during the apply. [zia.terraform.activation-methods:activator-does-not-suppress] The guidance for large configurations is to raise the API session timeout to its 20 minute maximum, in the admin portal or with `api_session_timeout` on `zia_advanced_settings`, and to split very large work across smaller states. [zia.terraform.activation-methods:raise-timeout-to-20]

**Several configurations, one tenant.** A tenant has a single configuration-change lock and a single activation queue, so plans can run in parallel (reads do not take the lock) but only one apply should run against a tenant at a time, with CI concurrency keyed on the tenant. [zia.terraform.activation-methods:one-apply-per-tenant] Requests that cannot take the write lock are rejected with `EDIT_LOCK_NOT_AVAILABLE`, `Resource Access Blocked` or `Failed during enter Org barrier`; the provider retries them automatically, so contention typically appears as a progressively slower run rather than an immediate failure. [zia.terraform.activation-methods:lock-errors-retried] Lowering Terraform's `-parallelism` does not reduce the number of competing runs, and the longer run increases the chance of crossing an API session boundary. [zia.terraform.activation-methods:do-not-lower-parallelism] A queued activation waits until every editing administrator or API session has activated and cannot be cancelled, so activating at the end of each configuration does not publish that configuration independently. [zia.terraform.activation-methods:activation-queues] When the queue clears, all pending tenant changes are published, including those from a run still in progress or one that failed part-way, so for rule-based resources a partially created rule set can take effect with incomplete ordering. [zia.terraform.activation-methods:queue-publishes-partial-runs] A separate tenant is the only boundary that gives truly concurrent execution, since each tenant has its own write lock and activation queue. [zia.terraform.activation-methods:separate-tenant-boundary]

What to check:
1. Whether the run outlived the API session timeout when changes went live before the apply finished.
2. Whether `zia_activation_status` lists every resource or module it must follow in `depends_on`.
3. Whether more than one apply targets the tenant at once, before blaming rate limits for slow writes.
