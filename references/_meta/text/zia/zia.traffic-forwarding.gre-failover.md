# GRE tunnel health checks and failover (zia.traffic-forwarding.gre-failover)
Also called: gre failover; gre keepalive; ip sla zscaler; vpntest; tunnel health check; gre ha

A GRE tunnel that is up on the router can still be useless, so health has two layers. GRE interfaces have no built-in way to detect a tunnel failure, so GRE keepalives are configured on the physical or logical interface; they monitor the interface, not the service beyond it. [zia.traffic-forwarding.gre-failover:keepalive-limit] Zscaler requires monitoring of GRE tunnels, with monitoring tied to failover: when service monitoring is down the primary tunnel fails over to the backup, and it switches back when monitoring recovers. [zia.traffic-forwarding.gre-failover:monitoring-required] Service monitoring uses Layer 7 health checks where the vendor supports them (Cisco IP SLA, some Juniper devices through RPM), otherwise Layer 4 checks such as ICMP and PAC-based failover. The check is an HTTP raw request to http://gateway.<Zscaler cloud>.net/vpntest. [zia.traffic-forwarding.gre-failover:health-checks] Do not run Layer 7 health checks against commonly visited sites such as www.google.com: Google may denylist the service's IP addresses and enforce CAPTCHA on every user behind them. [zia.traffic-forwarding.gre-failover:no-popular-site-checks]

Zscaler publishes two failover profiles. Fast: keepalive 10 3 (30 seconds), ICMP echo every 10 seconds, track delay down 30 and up 45 seconds, best case 30-32 seconds and worst case 40-42 seconds, higher false-positive risk and CPU use, Layer 3 only. Conservative: keepalive 30 4 (120 seconds), HTTP raw every 60 seconds, delay down 120 and up 180 seconds, best case 120-125 and worst case 180-185 seconds, lower false-positive risk, tests the HTTP service. [zia.traffic-forwarding.gre-failover:failover-profiles] In the conservative example the router probes once every 60 seconds, marks the test down after 120 seconds (two consecutive failures) and up after 180 seconds (three consecutive successes), so short flaps do not trigger failover. [zia.traffic-forwarding.gre-failover:delay-down-up] The vendor's Cisco sample probes the primary and secondary Global Public Service Edge IP addresses with IP SLA HTTP raw requests (a round-trip-time threshold of 500 in the example, to be set from observed latency) and ties failover to the track objects with a route-map using set ip next-hop verify-availability. [zia.traffic-forwarding.gre-failover:sample-config]

**What the GRE configuration guides add.** The GRE guidelines say the router must detect a primary tunnel failure and switch its routing table or routing instance to the secondary tunnel and back, with keepalive settings neither too aggressive nor too slow. A router without GRE keepalives can use ICMP probes; Cisco routers can monitor tunnels with IP SLA and Juniper routers with RPM. [zia.traffic-forwarding.gre-failover:router-detection] The Cisco 881 ISR GRE example says GRE keepalives fail if the tunnel traverses NAT, and do not work if the tunnel source interface has a private IP address. [zia.traffic-forwarding.gre-failover:keepalive-nat]

**Cisco 881 ISR example.** The Cisco 881 ISR GRE example requires both GRE keepalives and IP SLA for tunnel failover. [zia.traffic-forwarding.gre-failover:cisco-keepalive-and-sla] In the Cisco 881 ISR GRE example the IP SLA HTTP raw probes target the internal Public Service Edge IPs of both tunnels (ip sla 1 the primary, ip sla 2 the secondary), the secondary probe with timeout 5000 and threshold 500 requesting http://gateway.<Zscaler Cloud Name>.net/vpntest, and track 1 uses delay down 120 up 180. [zia.traffic-forwarding.gre-failover:cisco-sla-example] The two Cisco samples probe different addresses [divergence:zia.traffic-forwarding.gre-failover:ip-sla-probe-target]. The Cisco 881 ISR example verifies failover by checking ip.zscaler.com for the data center receiving traffic and confirming failover to the secondary interface after each of: bringing the primary tunnel interface down, configuring a wrong primary DC VIP, blocking the GRE port on the upstream firewall or router ACL, and lowering the primary IP SLA thresholds to trigger a timeout. [zia.traffic-forwarding.gre-failover:failover-tests]

**Juniper SRX example.** In the Juniper SRX GRE example the hold time must be at least twice the keepalive time; the sample sets keepalive-time 10 and hold-time 60. [zia.traffic-forwarding.gre-failover:juniper-hold-time] The Juniper SRX GRE example monitors the GRE endpoints with an ICMP-based probe to the internal Public Service Edge IPs; when the data center under the GRE virtual IP address goes down, the SRX gets no keepalive response and the adjacency state goes down. [zia.traffic-forwarding.gre-failover:juniper-rpm] A Zscaler-side keepalive limit or rate is open [gap:zia.traffic-forwarding.gre-failover:keepalive-zscaler-side].

The tunnel design itself (primary and secondary in different data centers) is in [GRE tunnels to ZIA: requirements, bandwidth and deployment](kb:zia.traffic-forwarding.gre).

What to check:
1. Which failover profile the router runs, Fast or Conservative.
2. Whether the health check targets the Zscaler VPN test URL rather than a public site.
3. Whether the track is wired to the route, since failover happens only when monitoring drives it.

Sources disagree (name both sides):
- The Cisco 881 ISR GRE example probes the internal Public Service Edge IPs of both tunnels, while the best-practices sample probes the Global Public Service Edge IP addresses. [divergence:zia.traffic-forwarding.gre-failover:ip-sla-probe-target]
  - zscaler-help: The IP SLA probes target the primary and secondary internal Public Service Edge IPs.
  - zscaler-help: The IP SLA probe targets the primary Global Public Service Edge IP.
  Impact: Low: the two examples probe different addresses and neither says the other is wrong, so a probe target should not be generalized from either one.
