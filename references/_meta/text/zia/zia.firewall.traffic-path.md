# Where the firewall sits in the traffic path (zia.firewall.traffic-path)
Also called: firewall before web module; firewall vs web module; firewall block or web block; firewall insights vs web insights; z-tunnel 1.0 firewall; pac firewall

All web traffic is evaluated in the firewall module first, and only traffic that does not violate a firewall policy is forwarded to the web module. [zia.firewall.traffic-path:firewall-first] Outbound traffic to ports other than 80/443 (or other HTTP or HTTPS ports) goes directly to the firewall module and is blocked if it violates a firewall policy. [zia.firewall.traffic-path:nonweb-firewall-only] If a web policy allows a transaction but a conflicting firewall policy blocks it, the firewall policy applies: for example, Cloud App Control allowing Box.com does not help when the firewall blocks it. [zia.firewall.traffic-path:firewall-beats-web-allow] Firewall Filtering rules can be extended to traffic managed by the web proxy in specific cases: when the rules contain Layer 3, Layer 4 or FQDN conditions, or when non-web traffic appears in flows managed by the web proxy. Rules based on source IP address, destination IP address or destination FQDN apply to proxy-managed traffic in both Standard and Advanced Firewall, while handing non-web traffic over from the web proxy to the firewall needs Advanced Firewall; the page's example is SSH on destination port 443. [zia.firewall.traffic-path:extends-to-proxy-traffic] Identifying web traffic that is bypassing the web proxy and forwarding it to the web proxy for policy application needs Advanced Firewall and auto-proxy configuration in the Advanced Settings. [zia.firewall.traffic-path:web-bypass-identification]

The firewall module enforces on web traffic only when the traffic is outbound, from the user to the web, and the organization has enabled a firewall policy for the location. [zia.firewall.traffic-path:enforcement-conditions] For remote users on explicit forwarding, the firewall evaluates both the inner and the outer tuples. [zia.firewall.traffic-path:explicit-forwarding-tuples] With HTTP CONNECT tunnels, there are two 5-tuples associated with the traffic, the outer IP and the inner IP address. Zscaler removes the HTTP CONNECT request from the outer tunnel and applies the Firewall policies to the request inside the tunnel independently, so any 5-tuple that results in a blocking policy blocks the corresponding session. [zia.firewall.traffic-path:connect-inner-outer] For Z-Tunnel 1.0 and PAC traffic, the firewall must be enabled in Advanced Settings for this type of traffic: the option is Enable Firewall for Z-Tunnel 1.0 and PAC Road Warriors. [zia.firewall.traffic-path:ztunnel-pac-opt-in] Enabling the Enable Firewall for Z-Tunnel 1.0 and PAC Road Warriors option applies the following Firewall rules to remote user traffic forwarded via Z-Tunnel 1.0 or PAC: all the default Firewall rules, all the user-defined rules configured without any location criteria, and all the user-defined rules configured for the Road Warrior location, because Road Warrior applies only to Z-Tunnel 2.0 when the option is disabled. The page says to ensure these rules are relevant for Z-Tunnel 1.0 and PAC traffic before enabling it. [zia.firewall.traffic-path:ztunnel1-pac-rules] Whether Z-Tunnel 2.0 engages the firewall without an option is open [gap:zia.firewall.traffic-path:ztunnel-2-firewall].

**Connectivity to the Zscaler service.** Zscaler recommends GRE or IPSec tunnel connectivity from branch or headquarter location gateway devices, and installing Zscaler Client Connector for remote users to connect to the Zscaler service. Zscaler Client Connector should be implemented when users are off network using HTTP CONNECT tunnels to forward their traffic. [zia.firewall.traffic-path:recommended-connectivity] To allow connectivity to the Zscaler service, an organization's policies must use three predefined objects: the Zscaler Proxy Network Service, which includes all proxied network services (for example TCP 21, 80, 443, 9400, 9480) and the subscription to a DPPC port; the Zscaler Proxy IPs IP category, which includes all Public Service Edge service IPs in a particular cloud, the Public Service Edge's local IPs and global service IPs; and the Zscaler Proxy Traffic Firewall policy rule, which matches that category and that service. Zscaler Client Connector version 2.0 or later uses DTLS/TLS tunnels to forward traffic and does not support the Zscaler Proxy Traffic rule. [zia.firewall.traffic-path:proxy-connectivity-objects] The setting page that holds the Z-Tunnel option is routed in [ZIA Advanced Settings page: its sections, three settings explained here, and where other sections are routed](kb:zia.advanced-settings).

**Application layer gateway.** Some protocols currently cannot be fully handled by Public Service Edges and require an application layer gateway (ALG) feature to be tracked across control and bearer channels; the Zscaler service applies the ALG feature automatically to the protocols the page lists: FTP (passive), PPTP and RTSP. Traffic for protocols that are not fully supported by an ALG, like SIP, H.323, H.248, VOIP and TFTP, might need to be bypassed from Zscaler by changing the configuration when setting up forwarding methods such as IPSec, GRE or Z-Tunnel 2.0 (for remote users). The page says the best practice for those forwarding methods is generally to send all ports and protocols through the tunnels. [zia.firewall.traffic-path:alg]

**Telling the two modules apart in the logs.** When web traffic violates a firewall policy, both the Firewall Insights and Web Insights logs show it blocked. [zia.firewall.traffic-path:firewall-block-both-logs] When traffic passes the firewall policy but violates a web policy, Firewall Insights shows it allowed and Web Insights shows it blocked. [zia.firewall.traffic-path:web-block-firewall-allowed] Whether a web-module block also shows as blocked in the firewall log is open [gap:zia.firewall.traffic-path:web-block-firewall-log-conflict]. The firewall NSS feed records the action as Allowed or Blocked, and the name of the rule applied to the transaction. [zia.firewall.traffic-path:firewall-log-action]

**Order inside the firewall module.** Evaluation order among the firewall policies is open [gap:zia.firewall.traffic-path:module-internal-order]. The web side is covered in [ZIA URL Filtering](kb:zia.url-filtering) and [Where SSL inspection sits in ZIA web policy evaluation (the two passes)](kb:zia.ssl-inspection.pipeline), and Cloud App Control in [Cloud App Control versus URL Filtering: which applies](kb:zia.cloud-app-control.precedence).

Inbound web traffic (HTTP or HTTPS on ports 80/443 from the internet in response to GET or POST requests) is sent to the web module for policy evaluation, and is allowed into the organization if it violates no Web policy. [zia.firewall.traffic-path:inbound-web-module-only]

What to check:
1. Whether the location has the firewall enabled, since enforcement depends on it.
2. Whether the traffic is Z-Tunnel 1.0 or PAC, and the option to enable the firewall for it is on.
3. Whether the block appears in both logs, which marks a firewall block, or only in Web Insights, which marks a web-policy block.
4. Whether the web-rule attribution fields settle a disagreement between the firewall log and Web Insights.

Not known (open gaps):
- Does the firewall log show a web-module block as allowed or blocked [gap:zia.firewall.traffic-path:web-block-firewall-log-conflict]: settled by lab-test or tenant-data. Blocks: using the firewall log action alone to tell a firewall block from a web block
- Evaluation order among Filtering, NAT, DNS, IPS and FTP [gap:zia.firewall.traffic-path:module-internal-order]: settled by lab-test or support-ticket. Blocks: answering whether a NAT rewrite changes what Filtering sees
- Whether Z-Tunnel 2.0 engages the firewall without an option [gap:zia.firewall.traffic-path:ztunnel-2-firewall]: settled by support-ticket or lab-test. Blocks: explaining why firewall rules do or do not apply to a forwarding method
