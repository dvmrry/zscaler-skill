# Network services (port criteria) (zia.firewall.network-services)
Also called: network service; networkServices; nw_services; service type; srcTcpPorts; destTcpPorts; service tag; port tuple; uppercase service names

A network service is the port criterion that Firewall Filtering and IPS rules reference. A network service in the API carries, among other members, `name`, `type`, `tag` and four port arrays: `srcTcpPorts`, `destTcpPorts`, `srcUdpPorts` and `destUdpPorts`. [zia.firewall.network-services:object-shape] The API returns a network service's `type` as STANDARD, PREDEFINED or CUSTOM. The Go SDK model holds it as a free-form string. [zia.firewall.network-services:type-values] What STANDARD, PREDEFINED and CUSTOM mean is open [gap:zia.firewall.network-services:type-meanings]. The API's `tag` field is an enumeration of network service identifiers, such as HTTP, HTTPS, DNS, FTP, SSH, plus ICMP_ANY, UDP_ANY, TCP_ANY and OTHER_NETWORK_SERVICE. [zia.firewall.network-services:tag-values]

**Looking one up.** The MCP tool documents server-side `search` as case-sensitive and `name` as a client-side case-insensitive substring filter. Its lookup workflow says predefined service names are uppercase (HTTP, FTP, DNS) and that `search="http"` does not match `HTTP`. [zia.firewall.network-services:name-lookup-case] The list filter `protocol` accepts ICMP, TCP, UDP, GRE, ESP or OTHER. The MCP tool describes the values, uppercases the supplied value and forwards it without validating membership. [zia.firewall.network-services:protocol-filter-values] Network services are served at `/networkServices`, with a `/networkServices/lite` variant, in the API capture; the Go client uses the same path. [zia.firewall.network-services:endpoint] From Go SDK v3.8.57, `GetAllNetworkServices` and `GetByName` read `/networkServices` in a single request without `page` or `pageSize`, because the endpoint is not paginated and accepts only `search`, `protocol` and `locale`; some clouds rejected the page size with `INVALID_INPUT_ARGUMENT` `Invalid Page Size 1,000`. The Terraform data source lookup by `name`, `protocol` or `locale` had failed the same way, and provider v4.8.16 retrieves all network services in one request. [zia.firewall.network-services:lookup-single-request]

**Writing one.** The SDK and MCP accept ports as tuples of direction (src or dest), protocol (tcp or udp), start port and optionally end port; the end port is omitted for a single port. [zia.firewall.network-services:port-tuples] The Python SDK builds the request key from the tuple as direction plus the title-cased protocol plus `Ports`, so ('dest','tcp',...) becomes `destTcpPorts`. It does not validate direction or protocol before building the key. [zia.firewall.network-services:wire-key-built-from-tuple] A port entry with no `end` value is encoded differently by the two SDKs: the Python `PortRange` always emits both `start` and `end`, while the Go `NetworkPorts` tags both `omitempty`, so a zero `end` is left out and the entry is sent as `start` alone. [zia.firewall.network-services:single-port-encoding] The two SDKs model the object's fields differently [divergence:zia.firewall.network-services:sdk-field-sets]. Updating a network service without ports leaves the existing ports unchanged; supplying ports overwrites the existing ports entirely. [zia.firewall.network-services:update-replaces-ports]

**Size.** The limits table lists 832 firewall network services per organization, and the About Network Services page says an organization can add up to 832 custom network services in addition to the predefined ones. [zia.firewall.network-services:service-count-cap] The per-rule cap on services is in [Firewall rule, criteria and group limits](kb:zia.firewall.limits). The description length differs between the help pages [divergence:zia.firewall.network-services:description-length]. The Configuring Custom Ports page says a custom network service's description cannot exceed 10,240 characters, and Definition is automatically populated as Custom for admin-defined services. [zia.firewall.network-services:custom-description-cap]

**Predefined services.** Zscaler provides over 50 predefined network services along with the TCP and UDP ports (source and destination) over which they typically operate. [zia.firewall.network-services:predefined-set] The ports assigned to predefined network services can be customized by adding new ports and modifying or deleting existing ones, except for six view-only predefined services (ESP, GRE, ICMP, TCP, UDP and Zscaler Proxy Network Services). Predefined services cannot be deleted. Editing a service offers Description, TCP Ports and UDP Ports, and custom services can be edited the same way. [zia.firewall.network-services:predefined-editability] The About Network Services table gives TCP and UDP destination ports per predefined service, for example DNS on 53 for both, HTTP on TCP 80, HTTPS on TCP 443, HTTP Proxy on TCP 3128 and 8080, QUIC on UDP 443, FTP on TCP 21, SSH on TCP 22, NTP on UDP 123 and Traceroute on UDP 33400-34000; ICMP is listed N/A for both. [zia.firewall.network-services:predefined-ports] The predefined Zscaler Proxy Network Services entry lists TCP ports 21, 443, 80, 8080, 8800, 9400, 9443 and 9480, and includes all Zscaler-specific web proxy ports including customer-specific Dedicated Proxy Ports. [zia.firewall.network-services:zscaler-proxy-service]

**How the help says they match.** Network services with specific source or destination ports and protocols can be used to configure 5-tuple Firewall Filtering, NAT, IPS Control and Forwarding rules with allow, block or redirect actions, and custom network services let Firewall, DNS and NAT policies apply to non-standard traffic. [zia.firewall.network-services:services-uses] Network services are identified at the first packet, leading to immediate policy action, whereas deep packet inspection typically needs multiple packets to identify network applications. Zscaler recommends ranking Firewall Filtering rules for network services, and for network service groups, higher than rules for network applications. [zia.firewall.network-services:first-packet] A custom network service combines protocols and ports at the source and destination: entries within the source, or within the destination, have an OR relationship, and source and destination combine with AND, that is (TCP Source Ports OR UDP Source Ports) AND (TCP Destination Ports OR UDP Destination Ports). [zia.firewall.network-services:custom-match-logic] The Configuring Custom Ports page gives the same example as the Configuring Network Services page: traffic matches the network service only if it originates from TCP port 111 and is destined to either TCP port 444 or UDP port 333. [zia.firewall.network-services:custom-match-example] The TCP Source Ports field takes a port number (for example 50) or a range (for example 1000–1050), and the page says a maximum of 8 entries is allowed for each port. [zia.firewall.network-services:port-entry-format] The console populates Definition as Custom automatically for admin-defined services. [zia.firewall.network-services:definition-label] [To make the service accept traffic from other ports, an admin creates a custom service with the appropriate ports and then, in Advanced Settings, configures the service to accept traffic from those ports: the HTTP Services and HTTPS Services lists under Services Forwarded to HTTP Web Proxy, the DNS Services list under Services Applicable to DNS Transaction Policies, and the FTP Services, RTSP Services and PPTP Services lists under Services Forwarded to FTP Proxy, to RTSP and to PPTP. The Advanced Settings page says the configurations it lists can be modified as needed if the Firewall service is enabled.](kb:zia.firewall:custom-port-services) Whether the eight-entry cap is per field is open [gap:zia.firewall.network-services:port-array-precedence].

**Network service groups.** Predefined and custom network services can be grouped and reused across policies, and network service groups can be used to configure 5-tuple Firewall Filtering, NAT, IPS Control and Forwarding rules. [zia.firewall.network-services:service-groups] An organization can create up to 121 network service groups, each holding up to 8,000 network services; the add form lets any number of custom and predefined services be selected, and a group's description cannot exceed 10,240 characters. [zia.firewall.network-services:service-group-sizes]

What to check:
1. Whether a service type is treated as an enum, since the Go SDK holds it as a free-form string.
2. Whether a service is custom from its type, rather than from its name.
3. Whether the name is searched in uppercase, since the server-side search is case-sensitive.
4. Whether the complete port list is sent on an update, since supplying ports overwrites the existing ones.

Sources disagree (name both sides):
- The Configuring Network Services page limits a service description to 10,240 characters; the limits table gives 1,024 bytes. [divergence:zia.firewall.network-services:description-length]
  - zscaler-help: The description cannot exceed 10,240 characters.
  - zscaler-help: Network Service Description is limited to 1,024 bytes.
  Impact: A description between 1,024 bytes and 10,240 characters is allowed by one page and over the limit by the other; the pages do not say which governs.
- The Python and Go SDKs model different fields on a network service. [divergence:zia.firewall.network-services:sdk-field-sets]
  - sdk-python: Python carries `creatorContext` and no top-level `protocol` attribute.
  - sdk-go: Go carries `protocol` and no `creatorContext`.
  Impact: A read-modify-write through one SDK silently drops the field the other SDK models, and Python has no way to read `protocol` as an object attribute.
