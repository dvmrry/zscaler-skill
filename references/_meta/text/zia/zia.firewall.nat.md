# NAT Control (destination NAT) (zia.firewall.nat)
Also called: nat control; dnat; dnatRules; destination nat; redirect ip; redirect fqdn; redirect port; source nat firewall; masquerade

NAT Control rules are destination-NAT rules: the API and the SDKs manage them as `dnatRules`, and the firewall log records whether the destination NAT policy was applied and its name from the NAT Control page. [zia.firewall.nat:dnat-surface] Whether NAT Control also does source NAT is open [gap:zia.firewall.nat:source-nat-support].

**The redirect.** A NAT Control rule carries the redirect target: `redirectIp`, `redirectFqdn` and `redirectPort`. The FQDN is mutually exclusive with the IP, and an unset IP or port means no redirection to a specific IP or port. [zia.firewall.nat:redirect-targets] The redirect target fields `redirectIp`, `redirectFqdn` and `redirectPort` are on the NAT Control rule schema and are not among the Firewall Filtering rule schema's fields in the API capture; the other match criteria use the same shapes as a Filtering rule. [zia.firewall.nat:redirect-has-no-filtering-counterpart] `resCategories` restricts a NAT Control rule to resolved destination categories; if unset, the rule is not restricted to specific destination categories. [zia.firewall.nat:res-categories] The NAT Control rule schema in the API capture has no `action` key; it carries the redirect target, `state`, `accessControl` and `enableFullLogging`. The console's Action column describes the redirect to the specified destination and port. [zia.firewall.nat:no-action-field] NAT Control rules cannot select network applications. [zia.firewall.nat:no-network-apps] The service does not monitor the health or availability of the endpoint a NAT rule forwards to, so traffic is forwarded whether or not the destination is reachable. [zia.firewall.nat:no-health-check]

**The predefined DNS rule.** The predefined Zscaler Trusted DNS Resolver NAT rule is enabled by default, sends standard DNS (dest:53) to the Zscaler Trusted DNS Resolver and drops iterative DNS queries. A separate higher-rank NAT rule can send iterative queries to an external resolver, and the predefined rule can be disabled. [zia.firewall.nat:predefined-dns-rule] `trustedResolverRule` is true on the predefined rule for the Zscaler Trusted DNS Resolver. [zia.firewall.nat:trusted-resolver-rule] NAT activity is recorded in Firewall Insights Logs for all traffic except DNS, whose NAT logs appear in DNS Insights Logs. [zia.firewall.nat:nat-logs]

**In the console.** After configuring NAT Control policy rules, Firewall Control must be enabled for known locations to apply the rules to the corresponding location traffic. [zia.firewall.nat:needs-firewall-enabled] The logical relationship between NAT Control criteria categories is AND, and the conditions within each category have their own operators: (Departments OR Groups OR Users) AND (Locations OR Location Groups) AND Time AND (Network Service OR Network Services Groups) AND (IP Addresses OR Source IPv4 Groups OR Source IPv6 Groups) AND (Countries OR Destination Addresses OR Destination IP Categories OR Destination IPv4 Groups OR Destination IPv6 Groups). [zia.firewall.nat:criteria-logic] A NAT Control rule takes up to 32 users, 32 groups, 32 departments, 32 locations and 32 location groups, and Zscaler Support can be contacted to increase the limit of Users, Groups, Departments or Locations. Fields left at Any are ignored during policy evaluation, and unauthenticated traffic can be targeted, when the policy for unauthenticated users is enabled under Advanced Settings, through the Users and Departments fields. [zia.firewall.nat:identity-caps-and-any] Selecting Road Warrior for Locations applies a NAT Control rule only to remote user traffic, and for policies configured for remote users to take effect the Enable Firewall for Z-Tunnel 1.0 and PAC Road Warriors option must be enabled in Advanced Settings. Rules configured for locations other than Road Warrior also apply to remote user traffic from those locations. [zia.firewall.nat:road-warrior] A NAT Control rule's Time field takes up to two time intervals during which the rule applies, and is Always by default. [zia.firewall.nat:time-intervals] The time figure differs from the limits table: [zia.time-intervals.rule-usage:time-intervals-per-rule](kb:zia.time-intervals.rule-usage:time-intervals-per-rule).

**Services, addresses and actions.** A NAT Control rule's Network Services field is Any by default and Network Service Groups is None by default. If these fields exclusively match DNS network services defined in Advanced Settings, two additional actions are shown apart from DNAT IP Address or FQDN, available only when DNS is exclusively configured, without being combined with other network services. Selecting RTSP as a network service also applies the rule to RTP and RTCP traffic, since those connections are dynamically created by RTSP. [zia.firewall.nat:services-and-dns-actions] The IP Addresses field of a NAT Control rule accepts IPv4 only, and specifying individual, subnet or range IPv6 addresses is not currently supported. To control source IPv6 addresses the All IPv6 group is selected; custom source IPv6 groups and custom destination IPv6 groups are not supported. Source IPv4 Groups and Source IPv6 Groups are None by default. [zia.firewall.nat:ip-formats] NAT Control destinations can be identified by the location of a server (Countries) and by the URL category of the domain (Destination IP Categories), and wildcard FQDNs are supported with an asterisk. To evaluate wildcard FQDNs against non-web traffic, Zscaler requires the IP address to which the FQDN resolves, so all DNS traffic must be forwarded to the Zscaler service if wildcard FQDNs are configured in policies, and a subscription or edition with DNS Control is required; wildcard FQDN matching against web traffic (HTTP and TLS/SNI) can function without meeting these conditions. [zia.firewall.nat:destination-matching] DNAT IP Address or FQDN takes an IPv4 address in a listed format with an optional port number, and can take wildcard FQDNs for domains with multiple or frequently changing IP addresses. Redirect Request Using DoH redirects DNS requests using DoH to the external DNS service configured in the specified DNS Gateway (the page's Services section labels the extra DNS actions Redirect Using DoH and Redirect DNS & Keep Sender Protocol), translating UDP or TCP requests to DoH, and lists only DNS Gateways configured with DoH support. Redirect DNS & Keep Sender Protocol redirects DNS requests using the original user protocol, applies to DNS traffic over UDP or TCP, and needs the DNS Gateway configured to support the protocols of the incoming requests. [zia.firewall.nat:nat-action-options] A NAT Control rule's name is system-generated and can be edited, and cannot exceed 63 characters; the description cannot exceed 10,240 characters. [zia.firewall.nat:name-and-description-length]

**Matching and order.** A NAT Control rule can also match on source and destination addresses and groups, users, groups, locations, devices, time windows and network services, using the same criteria shapes as a Firewall Filtering rule. [zia.firewall.nat:matching-criteria] NAT Control rules are evaluated in ascending numerical order, and the page lists them in ascending rule order by default. [zia.firewall.nat:ascending-order] Rule order is in [Firewall rule order, admin rank and predefined rules](kb:zia.firewall.rule-order), and the rule count cap is in [Firewall rule, criteria and group limits](kb:zia.firewall.limits). How DNAT rules count against those caps is open [gap:zia.firewall.nat:dnat-count-bucket].

2. Whether the firewall log shows a destination NAT rule applied to the flow, as a first check when a Filtering rule looks right but does not fire.
