# Cloud App Control API and SDK surface: app entries, flags, duplicate (zia.cloud-app-control.api-surface)
Also called: underMigration; appNotReady; appCatModified; deprecated cloud app; cloud app val; cloud app lifecycle flags; duplicate cac rule; createDuplicate; add_duplicate_rule
Former IDs: zia-54

**Wire fields.** The cloud app control rule carries its on/off state as the string field `state` (ENABLED or DISABLED). The Python SDK accepts a boolean `enabled` argument and rewrites it to `state` before sending; the Go struct carries it as `State`. [zia.cloud-app-control.api-surface:state-wire-field] Every Python cloud app control rule call (list, get, add, update, delete and duplicate) is built under /webApplicationRules/{rule_type}, including get, update and delete by rule ID, and update is a PUT whose body is the caller-supplied fields after `transform_common_id_fields(reformat_params, ...)`. The Go rule functions (get by ID or type, create, update, delete and duplicate) likewise take `ruleType`. [zia.cloud-app-control.api-surface:rule-type-required-update-is-put] So there is no fetch by rule ID alone [zia.cloud-app-control.api-surface:rule-type-required-update-is-put]. The cloud app control rule lists its applications as plain strings (`applications`) in the Go model. The Python SDK's `add_rule` passes the caller kwargs through as the body after ID reshaping through `reformat_params`, whose entries map `application_ids` to `applications`. [zia.cloud-app-control.api-surface:applications-sent-as-strings] The MCP tools do not take the `cloud_applications` name their skill uses [divergence:zia.cloud-app-control.api-surface:mcp-applications-kwarg].

**Application entries.** Application entries in the availableActions request body (`cloudApps[]`) are objects with `val`, `webApplicationClass`, `backendName`, `originalName`, `name` and five booleans: `deprecated`, `misc`, `appNotReady`, `underMigration` and `appCatModified`. The Python SDK models the same ten fields as its Application class. The same boolean fields appear on application lists in the advanced settings response (for example `authBypassApps[]`), and the API reference describes only `webApplicationClass` among the ten fields. [zia.cloud-app-control.api-surface:app-entry-fields] The Python Application model reads the numeric `val` (int32 in the API reference) and writes it back unchanged in its request format. [zia.cloud-app-control.api-surface:val-echoed] What the flags mean is open [gap:zia.cloud-app-control.api-surface:flag-meanings]. The reference and the SDKs also disagree on the request shape for application entries [divergence:zia.cloud-app-control.api-surface:cloud-apps-element-shape]. The Python `Application` catalog model is annotated "USED IN /webApplicationRules/{rule_type}/availableActions", but the Python `list_available_actions` method requires the response to be a list and returns it as a list of strings, not as Application objects. [zia.cloud-app-control.api-surface:python-application-model-comment] See [Cloud App Control actions and action discovery](kb:zia.cloud-app-control.actions) for how discovery is used in practice.

**Model differences.** The two SDKs model different fields [divergence:zia.cloud-app-control.api-surface:go-python-model-fields] and disagreed on the shape of the risk profile until Python SDK v1.11.2 [divergence:zia.cloud-app-control.api-surface:risk-profile-shape], where the mismatch made rule listing fail [gap:zia.cloud-app-control.api-surface:python-risk-profile-runtime]. Python SDK v1.11.2 fixed ZIA `cloudappcontrol.list_rules` failing with `KeyError: 0` when a rule has a `cloudAppRiskProfile` (#586); from v1.11.2 the model parses `cloudAppRiskProfile` as a single object, as the Go struct does. [zia.cloud-app-control.api-surface:python-risk-profile-single-object]

**Rule name.** The Python `add_rule` docstring describes the rule name as "Name of the rule, max 31 chars."; the Go SDK model carries no length constraint on `name`. [zia.cloud-app-control.api-surface:python-name-31-docstring] The MCP create workflow skill states that ZIA enforces a hard 31-character maximum on the rule name and rejects longer names with `INVALID_INPUT_ARGUMENT` / "Name exceeds the max length 31 characters". The executable MCP create input declares `name` as an unconstrained string. [zia.cloud-app-control.api-surface:mcp-skill-name-31] Whether the API enforces the limit is open [gap:zia.cloud-app-control.api-surface:name-length-enforcement].

**Duplicating a rule.** The Go SDK's `CreateDuplicate` cannot send a request, so it is not a way to clone a rule: [ZIA Go SDK service functions that return wrong results, mutate inputs, or reject valid input](kb:zia.sdk-go.service-defects). The Python SDK has a working-shaped duplicate call: `add_duplicate_rule` posts to /webApplicationRules/{rule_type}/duplicate/{rule_id} with the new name as the `name` query parameter and the rule fields as the body. [zia.cloud-app-control.api-surface:python-duplicate-exists] MCP server issue #76 asked for `zia_list_cloud_app_control_rules` and `zia_get_cloud_app_control_rule` because the build the reporter tested exposed `zia_list_cloud_app_control_actions` but no tool to read configured Cloud App Control rules; it was closed as completed on 2026-06-03 with a reply from a member of the repository's organization, signed Zscaler DevRel, that both tools already shipped in v0.11.0. [zia.cloud-app-control.api-surface:mcp-read-rules-tools-request]

Listing cloud applications and custom tags, and bulk-updating applications' status and tags, are in [SaaS Applications page: application status, tags and custom cloud applications](kb:zia.cloud-app-control.custom-applications).

Sources disagree (name both sides):
- Element shape of cloudApps in the availableActions request [divergence:zia.cloud-app-control.api-surface:cloud-apps-element-shape]
  - api-specs: The API reference lists each cloudApps element as an object (val, name, flags, webApplicationClass).
  - sdk-go: The Go SDK, and with it the Terraform provider, sends cloudApps as a list of strings; the Python method also takes a list of application names.
  Impact: A hand-built request that follows the reference may differ from what the SDKs send. The reference capture predates allAvailableActions, so it may also be stale.
- Whether the MCP rule tools accept `cloud_applications` [divergence:zia.cloud-app-control.api-surface:mcp-applications-kwarg]
  - mcp-server: The create workflow skill says `cloud_applications` is the tool input and maps internally to the SDK applications kwarg.
  - mcp-server: The executable create and update inputs have no `cloud_applications` field; applications travel through the `advanced` passthrough, whose description names `applications` and `cloud_apps`.
  Impact: Calls shaped by the skill (`cloud_applications=[...]`) do not match the tool input model; put applications in the advanced passthrough as the tool describes.
- Fields one SDK models that the other does not [divergence:zia.cloud-app-control.api-surface:go-python-model-fields]
  - sdk-go: The Go rule struct carries `numberOfApplications` and has `sharingDomainProfiles` and `formSharingDomainProfiles` only as commented-out lines, so Go neither reads nor sends the two sharing-profile fields.
  - sdk-python: The Python rule model reads and writes `sharingDomainProfiles` and `formSharingDomainProfiles` and has no `numberOfApplications` attribute.
  Impact: A Python read of a rule drops numberOfApplications; a Go read drops both sharing-profile fields and does not send them on write.
- Single object or list for cloudAppRiskProfile [divergence:zia.cloud-app-control.api-surface:risk-profile-shape]
  - sdk-go: The Go struct holds `cloudAppRiskProfile` as one pointer to an ID object.
  - sdk-python: The Python model decodes the same key as a list of references through `form_list`, yet its request format calls `.request_format()` on the attribute as if it were a single object.
  Impact: The two SDKs disagree on the type; the Python side is internally inconsistent in source. Whether it raises at runtime has not been run.
  Resolved (fixed-upstream) by zia.cloud-app-control.api-surface:python-risk-profile-single-object: The Python position describes v1.10.0; v1.11.2 parses a single object, matching Go.
