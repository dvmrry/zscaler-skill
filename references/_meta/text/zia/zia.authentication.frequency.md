# Authentication frequency and cookie lifetime (zia.authentication.frequency)
Also called: authFrequency; auth_frequency; authCustomFrequency; auth_custom_frequency; DAILY_COOKIE; SESSION_COOKIE; PERMANENT_COOKIE; CUSTOM_COOKIE; cookie expiration; how often users re-authenticate; authentication profile

**What it controls.** authFrequency is how often users must authenticate, expressed as the cookie expiration after a user is first authenticated. It is not applicable to the Lite API. [zia.authentication.frequency:meaning] The service needs to authenticate a user only once to set the gateway cookie, but an organization can require authentication more often. [zia.authentication.frequency:set-once]

**Values.** The spec lists authFrequency as DAILY_COOKIE, PERMANENT_COOKIE, SESSION_COOKIE or CUSTOM_COOKIE. [zia.authentication.frequency:frequency-values] The console's Authentication Frequency offers Daily (authentication expires between 12 to 24 hours from the login time, depending on when the user authenticated the day before), Only Once (the default interval: users need not authenticate again as long as the cookie is saved in the browser, and the cookie typically expires in about two years; logging out needs an explicit logout or deleting the cookie), Once Per Session (authentication expires when the user closes the browser; no cookie is saved) and Custom (a number of days from 1 to 180 inclusive; authentication is requested when the user's cookie expires). These options do not apply to users with Zscaler Client Connector. [zia.authentication.frequency:console-frequency-options] Which API value each console option corresponds to is open [gap:zia.authentication.frequency:value-meanings].

**Custom.** A custom frequency is set in whole days in authCustomFrequency, valid range 1 to 180; the admin console field takes the same 1 to 180. [zia.authentication.frequency:custom-range] Whether a custom frequency without a valid day count is an error is open [gap:zia.authentication.frequency:custom-without-days].

**Per location.** A location with Enforce Authentication on can use a custom authentication timeout profile that sets the authentication frequency for that location. Authentication profiles are a feature with limited availability, enabled through the Zscaler account team. [zia.authentication.frequency:location-profile] By default the authentication timeout is shared across all locations; custom authentication timeout profiles can be created and assigned to locations. A maximum of 8 profiles can be created, each assignable to any number of locations, with an interval in minutes, hours or days: the minimum frequency is 5 minutes and the maximum is 999 days, and Zscaler recommends 30 minutes or higher. The feature is not available by default (contact the Zscaler Account team), a location picks a profile in its Gateway Options section, and the Authentication Profiles page is unavailable if subscribed to the Authentication Service. [zia.authentication.frequency:custom-timeout-profiles] Whether the profiles are exposed through the API is open [gap:zia.authentication.frequency:timeout-profile-api].

**Recommendation and load.** Zscaler recommends Only Once, the default interval. The authentication cookie issued for the gateway cloud is encrypted with SSL and can only be set and read from the gateway SSL site; when the gateway cookie is valid the proxy generates a domain cookie for that website, and the article says that domain cookie is rotated every 12 hours. Separately, it says a user who steals a domain cookie can browse to that website through Zscaler for up to 12 hours maximum. Private Access and Zscaler Client Connector do not use cookies for authentication. [zia.authentication.frequency:only-once-recommended] With Only Once, authentication is completely transparent to end users during maintenance or a downtime window of the AD server; the article's example is that with Daily every user must authenticate against the AD server every day, so the server must scale to those requests. [zia.authentication.frequency:directory-load]

**Forcing reauthentication.** Force Reauthentication has the Central Authority (CA) invalidate all authentication cookies for the users in the organization, which might take several minutes depending on the number of users; it does not apply to users with Zscaler Client Connector. Its status is Completed, In Progress, Error or None (never executed in the Admin Console). Zscaler recommends SCIM provisioning for complete user lifecycle management instead of forcing reauthentication. [zia.authentication.frequency:force-reauthentication] For users on SAML with auto-provisioning or Hosted DB authentication, reauthentication can be triggered by logging out at ip.zscaler.com, deleting the Zscaler cookies from the browser, deleting the user from the Admin Console, or using CSV import to delete the user from the Zscaler database; the article says to also choose one of these when SCIM is not supported for the IdP server in use. These methods apply only when forwarding traffic with PAC files and using cookie-based authentication. [zia.authentication.frequency:saml-logout-reauth]

**Where it does not apply.** Frequency governs the cookie, so it applies to flows that carry the Zscaler cookie; Kerberos does not use cookies, and traffic that cannot hold a cookie is attributed to the location instead. [zia.authentication.frequency:browser-scope] For clients that cannot hold a cookie at all see [What happens to traffic with no user identity](kb:zia.authentication.unauthenticated-traffic) and [Surrogate IP: mapping a private IP to an authenticated user](kb:zia.authentication.surrogate-ip).

What to check:
1. The live value of authFrequency against the spec's value list.
2. Whether the failing client carries a Zscaler cookie, since frequency governs the cookie.
3. Whether the location's authentication profile sets a frequency different from the organization default, before reading the organization setting.
