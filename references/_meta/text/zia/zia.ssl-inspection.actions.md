# What an SSL/TLS inspection action does: Inspect, Do Not Inspect, Block and their settings (zia.ssl-inspection.actions)
Also called: ssl inspection actions; untrusted server certificates; ocsp revocation check; block no sni; minimum tls version; enable http2 ssl; show end user notifications ssl; pass through; site blocked after enabling ssl inspection; https site fails only through zscaler; certificate error through zscaler; block page instead of the website; revoked certificate blocked; site works off network but fails on zscaler

The action decides whether a matching connection is decrypted and, if not, how much of ZIA still evaluates it. A rule's action is Inspect, Do Not Inspect, or Block, and Do Not Inspect has two variants: Evaluate Other Policies, which keeps URL Filtering and Cloud App Control in play and exposes certificate, SNI, OCSP, TLS-floor and notification settings, and Bypass Other Policies, which bypasses web policies for the TLS traffic; the help page lists no further settings for Bypass. [zia.ssl-inspection.actions:variants] The sequencing consequences of Evaluate versus Bypass (which policies still fire, what a domain block does) are in [Where SSL inspection sits in ZIA web policy evaluation (the two passes)](kb:zia.ssl-inspection.pipeline). The wire names of these actions, and the validator that rejects bad combinations, are in [SSL/TLS inspection rule wire format: the nested action object, tokens and casing](kb:zia.ssl-inspection.api-shape).

**Certificates and revocation.** Under an Inspect action, Untrusted Server Certificates lists three options: Allow (warnings only for expired certificates), Pass Through (certificate warnings are shown and the user can proceed) and Block. Under Do Not Inspect with Evaluate Other Policies, it lists Allow (the browser sees the invalid-certificate warning) and Block (the TCP connection is reset). [zia.ssl-inspection.actions:untrusted-certs] Zscaler recommends blocking on a certificate failure until the server-side issue is fixed, rather than letting the user continue; the guide words the options as Allow, Caution or Block where the rule page says Pass Through. [zia.ssl-inspection.actions:untrusted-certs-recommend-block] OCSP Revocation Check treats a revoked certificate as untrusted and applies the rule's Untrusted Server Certificates action. It runs even when the certificate is otherwise correct, and on a Do Not Inspect + Evaluate rule it relies on OCSP stapling. [zia.ssl-inspection.actions:ocsp] The Leading Practices example for the Zscaler Recommended Exemptions rule (Do Not Inspect, Evaluate Other Policies) shows OCSP Revocation Check enabled. [zia.ssl-inspection.actions:ocsp-on-in-example-exemptions]

**Handshake and protocol checks.** Block No Server Name Indication (SNI) blocks any handshake whose Client Hello carries no SNI; it is off by default and is offered on both Inspect and Do Not Inspect + Evaluate. [zia.ssl-inspection.actions:no-sni] Block Undecryptable Traffic, an option listed under the Inspect action, blocks traffic from servers that use non-standard encryption or require mutual TLS authentication. [zia.ssl-inspection.actions:block-undecryptable] An Inspect rule has separate Minimum Client TLS Version and Minimum Server TLS Version settings, each blocking connections below its threshold; a Do Not Inspect + Evaluate rule has one combined Minimum TLS Version. [zia.ssl-inspection.actions:min-tls] Zscaler recommends starting with all supported protocols allowed to discover what is in use, then blocking every TLS version earlier than 1.2 including legacy SSL. [zia.ssl-inspection.actions:tls-floor-recommendation] A TLS floor that is too strict is a named cause of a legitimate site being blocked; for example a partner site limited to TLS 1.0 behind an Inspect rule that requires 1.2 fails the connection. [zia.ssl-inspection.actions:tls-floor-blocks-legit-site] Enable HTTP/2 (Inspect only) makes HTTP/2 the web protocol, needs the feature enabled for the organization, and falls back to HTTP/1.1 for a location where Bandwidth Control is enabled, even when the rule enables HTTP/2. [zia.ssl-inspection.actions:http2]

Per-rule scope matters when auditing: Certificate, OCSP, SNI and TLS-floor settings belong to each rule, so an exemption rule can carry weaker TLS requirements than the catch-all Inspect rule below it; the Leading Practices rule set does this by giving the Zscaler Recommended Exemptions rule a TLS 1.0 floor against TLS 1.2 on Inspect All. [zia.ssl-inspection.actions:per-rule-settings]

**Notifications.** The end-user notification page on a Block rule or a Do Not Inspect + Evaluate rule needs the Zscaler or enterprise root CA in the client trust store; without it the browser shows an invalid-certificate warning instead. With notifications off, the service resets the connection with a generic failed-connection message and no notification. [zia.ssl-inspection.actions:eun-needs-root-ca] Show Notification for ATP Blocks, and the intermediate-CA override on a Do Not Inspect + Evaluate or Block rule, appear only when the parent notification setting is enabled, so there is no console path to them while it is off. [zia.ssl-inspection.actions:eun-dependent-options]

The intermediate CA a rule presents is covered in [SSL/TLS inspection certificates: who signs, and where the root must be trusted](kb:zia.ssl-inspection.certificates). Traffic that cannot be inspected at all, whatever the action, is in [What SSL/TLS inspection cannot inspect: pinned apps, client certs, QUIC, BYOD, IoT](kb:zia.ssl-inspection.uninspectable).

What to check:
1. Which option a rule uses, matched on the option's behavior rather than its label, since the rule page and the guide word them differently.
2. Whether the parent notification setting is on, before looking for a child option such as Show Notification for ATP Blocks.
