# Reference Terraform modules for Virtual Service Edges on AWS and Azure (zia.virtual-service-edge.reference-modules)
Also called: terraform aws vzen module; terraform azure vzen module; vzen terraform; vse terraform; vzen_vm_instance_type; vzen_vm_size; vzen gwlb; vse gwlb; vse azure load balancer; module defaults virtual service edge; vzen_count

Zscaler publishes Terraform modules that build Virtual Service Edge (VZEN) VMs and their cloud networking on AWS and Azure. The module code is the source here; the product's own sizing and platform rules are in [Where a Virtual Service Edge runs and which platforms can cluster](kb:zia.virtual-service-edge.platforms) and [How much a Virtual Service Edge VM can do](kb:zia.virtual-service-edge.sizing).

**AWS prerequisites.** The AWS VZEN modules require Terraform 1.5.0 or later, an AWS account with Administrator Access, acceptance of the Zscaler VZEN image terms in AWS Marketplace, and a Zscaler VZEN SKUs subscription. [zia.virtual-service-edge.reference-modules:aws-prereqs] The AWS modules ship two starter templates, standalone and with a Gateway Load Balancer (GWLB); Zscaler's stated recommended deployment method is GWLB, which distributes traffic across multiple VZENs and achieves high availability. [zia.virtual-service-edge.reference-modules:aws-recommended-gwlb]

**AWS VM.** The AWS VZEN VM module defaults to r7i.2xlarge and validates the type against m5.2xlarge, m6i.2xlarge, m7i.2xlarge, m8i.2xlarge, r5.2xlarge, r6i.2xlarge, r7i.2xlarge and r8i.2xlarge. [zia.virtual-service-edge.reference-modules:aws-instance-type] The AWS VZEN VM module creates 2 appliances by default, each with a 501 GB gp3 root volume at 3000 IOPS, EBS optimization on, and instance metadata tokens required. [zia.virtual-service-edge.reference-modules:aws-vm-defaults] Each AWS VZEN VM is built with a management interface (primary, attached first) and a service interface attached afterwards at device index 1, and each interface gets its own Elastic IP. [zia.virtual-service-edge.reference-modules:aws-two-nics] The accepted types are documented more narrowly than they are validated [divergence:zia.virtual-service-edge.reference-modules:aws-type-list].

**AWS network and access.** The AWS security-group module gives the management group an SSH (port 22) ingress rule from vzen_mgmt_sg_allowed_ssh_ips, whose default is 10.1.0.0/16, an outbound-all rule on both groups, and an ingress rule on the service group permitting all traffic from the VPC CIDR. [zia.virtual-service-edge.reference-modules:aws-sg] The AWS IAM module creates an EC2-assumable role and instance profile and attaches a policy whose description says it lets VZENs register to SSM Manager for Console Connect. [zia.virtual-service-edge.reference-modules:aws-iam]

**AWS GWLB.** The AWS GWLB module forwards over GENEVE on port 6081 to IP-type targets, registering each VZEN forwarding service IP as a target. [zia.virtual-service-edge.reference-modules:aws-gwlb-target] The GWLB target group health check is a TCP probe on http_probe_port (default 50000; must be 80 or 1024-65535) every 10 seconds with a 5 second timeout, 5 successes to become healthy and 2 failures to become unhealthy. [zia.virtual-service-edge.reference-modules:aws-gwlb-health] The AWS example creates one GWLB endpoint per VZEN subnet through a VPC endpoint service, and the service does not require manual acceptance by default. [zia.virtual-service-edge.reference-modules:aws-gwlb-endpoints]

**AWS image, zones, brownfield.** The AWS example locates the VZEN image as the most recent AWS Marketplace AMI with a fixed product code, unless set_your_own_ami_id overrides it; for the China regions cn-north-1 and cn-northwest-1 the product code is the placeholder china-vse-product-code-goes-here. [zia.virtual-service-edge.reference-modules:aws-ami] The AWS example takes az_count from 1 to 3 (default 1) and spreads the VZEN VMs across the zones: vzen_count 4 with az_count 2 yields two VZENs in each of two zones. [zia.virtual-service-edge.reference-modules:aws-az-spread] Brownfield mode on AWS needs byo_vpc_id, byo_igw_id and byo_subnet_ids together: the template asks for the Internet Gateway attached to a supplied VPC, and subnets as one per Availability Zone. [zia.virtual-service-edge.reference-modules:aws-brownfield] The AWS example generates an SSH key pair and writes the private key to a local .pem file with permissions 0600. [zia.virtual-service-edge.reference-modules:aws-key-local]

**Azure prerequisites.** The Azure VZEN modules need an Azure subscription ID, a service principal (client ID, tenant ID and client secret) and a Zscaler VZEN SKUs subscription; the README gives azurerm as v3.116.x with a minimum of 3.108.x. [zia.virtual-service-edge.reference-modules:azure-prereqs] The Azure modules ship two examples, with and without an Azure Load Balancer; Zscaler's stated recommended deployment method is Azure Load Balancer, which distributes traffic across multiple VZENs and achieves high availability. [zia.virtual-service-edge.reference-modules:azure-recommended-lb]

**Azure VM.** The Azure VZEN VM module defaults to Standard_E8-4ads_v5 and validates the size against Standard_E8-4ads_v5 and Standard_E8-4as_v4. [zia.virtual-service-edge.reference-modules:azure-vm-size] The Azure VZEN VM module deploys the Marketplace image from publisher zscaler1579058425289, offer zscaler-zia-vse and sku preview-zia-vse at version latest, unless vzen_source_image_id points at a custom image in the subscription. [zia.virtual-service-edge.reference-modules:azure-image] The Azure VZEN VM module accepts 1 to 250 VZENs, a validation that assumes a /24 subnet; the module default is 1 while the example tfvars comment says the default will be 2. [zia.virtual-service-edge.reference-modules:azure-count] Each Azure VZEN VM is built with a management NIC (primary, with a public IP) and a service NIC with IP forwarding enabled, and an administrator user zsroot that accepts SSH keys only. [zia.virtual-service-edge.reference-modules:azure-nics] With zones_enabled false (the default) the Azure module places the VMs in an availability set with 2 fault domains, or 3 in a listed set of regions; explicit zones apply only when zones_enabled is true and the region is in the module's supported-region list. [zia.virtual-service-edge.reference-modules:azure-zones]

**Azure load balancer and NSGs.** The Azure LB module creates a Standard SKU load balancer with a rule forwarding TCP 80 to TCP 80 on the backend pool. [zia.virtual-service-edge.reference-modules:azure-lb] The Azure LB health probe is TCP on lb_health_port (default 80, allowed 80-65535) every 15 seconds (minimum 5), with probe_threshold 2 and number_of_probes 1 by default. [zia.virtual-service-edge.reference-modules:azure-lb-probe] By default the Azure NSG module allows SSH (port 22) and ICMP to the management interface only from the VirtualNetwork source, adds SSH from listed addresses only when allow_ssh_from_existing_ips is set, and allows all VirtualNetwork traffic to the service interface. [zia.virtual-service-edge.reference-modules:azure-nsg]

**Against the help pages.** The modules build two interfaces per VM where the cluster article describes three [divergence:zia.virtual-service-edge.reference-modules:nic-count]. Their health probes are the cloud load balancers' own TCP probes, not the ICMP and HTTP probes of the bundled load balancer ([How a Virtual Service Edge cluster spreads and returns traffic](kb:zia.virtual-service-edge.load-balancing)). How a built VM is enrolled is not in the modules [gap:zia.virtual-service-edge.reference-modules:provisioning-handoff].

What to check:
1. Which instance type or VM size the module deploys; the AWS and Azure defaults and allow-lists differ.
2. How the GWLB or Azure load balancer decides a VZEN is healthy, and on which port.
3. Who can reach the management interface by default.
4. Whether the built VM matches the interface count the help describes.

Sources disagree (name both sides):
- How many network interfaces a Virtual Service Edge VM has. [divergence:zia.virtual-service-edge.reference-modules:nic-count]
  - zscaler-help: The cluster article lists 3 interfaces: management, the Virtual Service Edge and the load balancer.
  - tfmod-aws-vse: The AWS module builds two interfaces per VM, a management interface and a service interface.
  - tfmod-azure-vse: The Azure module attaches a management NIC and a service NIC; its comment says the service interface becomes the LB0 interface for Medium and Large VZEN sizes.
  Impact: A cloud VM built from these modules has two interfaces, not the three the cluster article describes; the cloud load balancer takes the load balancer role. Do not count a missing third interface as a build error, and note that the Azure comment implies size variants the sizing page does not describe.
- Which AWS instance types the VZEN module accepts. [divergence:zia.virtual-service-edge.reference-modules:aws-type-list]
  - tfmod-aws-vse: The validation accepts m5, m6i, m7i and m8i 2xlarge types as well as the r-family types.
  - tfmod-aws-vse: The example tfvars comment lists only the four r-family types and labels them the 64G variants.
  Impact: The code accepts more types than the example documents as allowed; the comment suggests the m-family types are not the 64 GB variants, so check the memory of the type before choosing one that the validation merely permits.
