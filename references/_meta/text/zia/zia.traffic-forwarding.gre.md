# GRE tunnels to ZIA: requirements, bandwidth and deployment (zia.traffic-forwarding.gre)
Also called: gre tunnel; gre bandwidth; gre static ip; gre mtu mss; border router gre; global public service edge; no default route

GRE is the tunnel for sites whose router can build it. This subject covers what the tunnel needs and how it scales; health checks and failover are in [GRE tunnel health checks and failover](kb:zia.traffic-forwarding.gre-failover), and which method to pick is in [Forwarding methods Zscaler supports and how to choose](kb:zia.traffic-forwarding.methods).

**What it is and what it needs.** A GRE tunnel functions like a VPN without encryption: a GRE-capable router encapsulates the packet and sends it across the public network to the Zscaler service. GRE adds a 4-byte header. [zia.traffic-forwarding.gre:overview] The tunnel's egress port needs a static IP address: the perimeter router must support GRE and its egress port must have a static IP. [zia.traffic-forwarding.gre:static-ip-required] A tunnel's source IP must already be provisioned as a static IP in the service, and the static IP list can be filtered to addresses not yet used by a tunnel. [zia.traffic-forwarding.gre:source-ip-provisioned] The GRE Tunnels page lists, for each tunnel, its primary and secondary data center VIPs, Managed By (self or a specific Zscaler partner) and the admin who last modified it. Primary and secondary tunnels are configured from a single static IP address so that one can take over if the other becomes unavailable. [zia.traffic-forwarding.gre:page-fields]

**How much it carries.** Zscaler supports at most 1 Gbps per GRE tunnel when the internal endpoint addresses are not NATed and 250 Mbps when they are (source NAT, including source PAT). [zia.traffic-forwarding.gre:bandwidth-limit] The NAT limit exists because the service load-balances GRE traffic over multiple servers by the internal IP addresses of the tunnel; when every packet carries the same internal source address the balancer cannot spread it across nodes. [zia.traffic-forwarding.gre:nat-limit-reason] Zscaler set the 1 Gbps limit because much of the internet infrastructure uses 1 Gbps links, and multilink technologies such as LACP still aggregate 1 Gbps interfaces, so more than 1 Gbps from a single source IP address becomes a bottleneck. [zia.traffic-forwarding.gre:one-gbps-reason] Above 1 Gbps, Zscaler recommends more tunnels with different public source IP addresses, each with a backup: 2 Gbps is two primary and two backup tunnels, 3 Gbps is three and three. [zia.traffic-forwarding.gre:scale-out] With several egress IPs, client persistence should be maintained (load balancer, ECMP or other), because a server that checks persistence refuses connections arriving from a different egress IP. [zia.traffic-forwarding.gre:client-persistence]

**Where to build it.** Zscaler's recommended deployment is two tunnels from an internal router behind the firewall, a primary to a Public Service Edge in one data center and a secondary to another. The tunnel source is a public IP configured on the router's loopback interface, the firewall needs a rule allowing GRE from the router, and internal IP addresses stay visible for policy and logging. [zia.traffic-forwarding.gre:internal-router] If an internal router is not feasible, a tunnel can be built from the border router, which must send internet-bound traffic to the Public Service Edges and requires NAT disabled on the firewall so internal IPs remain visible. [zia.traffic-forwarding.gre:border-router] Zscaler requires primary and backup tunnels from every internet egress location and, where applicable, from each internet service provider. [zia.traffic-forwarding.gre:primary-backup-per-egress] The GRE guidelines recommend policy-based routing, where supported, so that only internet-bound traffic enters the tunnel. Most routers apply PBR before NAT, which preserves internal client IP addresses; a router that NATs first should consider disabling NAT so the service sees internal addresses. A firewall ACL that blocks inbound connections needs a rule allowing GRE (protocol 47). [zia.traffic-forwarding.gre:routing-and-nat] A sublocation matches IP addresses carried inside the parent's tunnel (or XFF client addresses) and adds no forwarding path of its own ([Which IP addresses a sublocation matches, overlap rules and XFF](kb:zia.locations.ip-scoping)).

**No default route.** For explicit proxy mode over GRE in an environment with no default route, the tunnel is used with the Global Public Service Edge addresses 185.46.212.88 to .93, .97 and .98. These are dummy addresses that no Public Service Edge listens on but all know about, so traffic is routed to them through a GRE or IPSec tunnel and a PAC file directs users there. [zia.traffic-forwarding.gre:explicit-via-global-edges] What explicit mode means for the traffic is in [Which forwarding methods produce explicit or transparent mode](kb:zia.proxy-mode.forwarding-map).

**Provisioning.** A tunnel is provisioned either through a Zscaler Support ticket or by self-provisioning in the Admin Console; regional surcharge and premium data centers are excluded from the data center picker because of possible extra cost or specialized usage restrictions. [zia.traffic-forwarding.gre:provisioning] A tunnel names a primary and a secondary destination VIP; the Python SDK's add_gre_tunnel docstring says the closest recommended VIPs are chosen automatically when they aren't specified. The within-country flag restricts VIPs to the source IP's country, and the unnumbered flag supports automated SD-WAN provisioning with no internal tunnel addresses. [zia.traffic-forwarding.gre:vip-selection] What the Python SDK does with VIPs passed to a create or update is in [So a call that passes both VIPs under the documented snake_case names still runs the VIP lookup, and fails with its ValueError when the lookup finds no diverse pair; otherwise the body holds both the caller's `primary_dest_vip` and the added `primaryDestVip`, both become the wire key `primaryDestVip` when the executor camel-cases the body, and the added key, written later, replaces the caller's value. The secondary VIP is replaced the same way, so the tunnel is sent with the recommended VIPs, not the ones passed.](kb:zia.sdk-python.service-behaviors:gre-documented-vips-replaced). Tunnels are managed at /greTunnels; recommended destination VIPs come from /vips/recommendedList (also grouped by data center at /vips/groupByDatacenter), and /orgProvisioning/ipGreTunnelInfo returns IP addresses with their tunnel details. [zia.traffic-forwarding.gre:api-surface] To have Zscaler Support provision the tunnels, the organization gives the tunnel source's public IP address and the router's physical location; Zscaler then assigns the Virtual IP (VIP) addresses used as the source and destination inside the tunnel, from a non-routable pool it manages, so no two customers use the same addresses. [zia.traffic-forwarding.gre:support-provisioning-inputs] GRE destination VIPs are listed under GRE Virtual IP at config.zscaler.com/<Zscaler Cloud Name>/cenr; the admin finds the VIPs of the two data centers closest to the organization's location and chooses one as the primary tunnel destination and the other as the backup. [zia.traffic-forwarding.gre:finding-vips] The firewall module's view of tunnel traffic is in [Where the firewall sits in the traffic path](kb:zia.firewall.traffic-path); the bandwidth Bandwidth Control enforces per location is in [How a location and its sublocations share bandwidth limits](kb:zia.locations.bandwidth).

**Self-provisioning and CSV import.** In the self-provisioning wizard a GRE tunnel maps exactly one static IP address, which cannot be changed when the tunnel is edited, and a static IP that is already mapped to a location is not offered for a GRE tunnel. [zia.traffic-forwarding.gre:one-static-ip] In the self-provisioning wizard the Primary and Secondary Data Center VIP fields each list the 5 geographically closest data centers and by default auto-select an active VIP by geographical proximity. Domestic Preference prioritizes data centers in the IP address's country of origin even when they are farther away, and with it enabled each field auto-selects an active VIP in that country. The primary and secondary destinations must not point to the same data center. Organizations with Private Service Edges see Private Service Edge VIPs listed first, and data centers flagged Do Not Provision (DNP) on config.zscaler.com are not listed. [zia.traffic-forwarding.gre:dc-picker] On the Internal IP Range tab, Is Unnumbered IP is enabled when no internal IP address is needed on either side of the tunnel. Otherwise the admin selects an internal range from a default pool of 10 ranges on the Zscaler cloud or searches the other available RFC1918 ranges; when searching, the field displays the next available IP addresses by default, and for the 10.x.x.x series a range must take the form 10.aa.bb.cc with aa below 255 and cc 0 or a multiple of 8, otherwise the field displays the next IP address. [zia.traffic-forwarding.gre:internal-range] Self-provisioning a GRE tunnel to a Private Service Edge cluster is supported only for clusters deployed on public IP space (a non-NAT environment); a tunnel to a cluster inside a NAT environment is requested with a support ticket. [zia.traffic-forwarding.gre:pse-nat-self-provisioning] A CSV import can add up to 3,000 GRE tunnels. Its fields include Action (+ or -), Internal IP Range, VIPs Within Country Only (true or false, whether data centers in the IP address's country of origin are prioritized) and IP Unnumbered (true when no internal IP address is needed). Override Existing Entries is selected to update existing tunnels, including deleting them or adding new ones; adding a tunnel that already exists without it returns an error. [zia.traffic-forwarding.gre:csv-import]

**What the service does with the tunnel.** Each Public Service Edge listens specifically for traffic from the tunnel's source VIP addressed to its destination VIP, and associates those virtual addresses with the organization. [zia.traffic-forwarding.gre:vip-binding] The location's static IP is the public source address of both tunnels. Zscaler assigns a /29 for the tunnels, split into two /30 subnets; in the first /30, the first host address goes to the location and the second to the Zscaler data center. [zia.traffic-forwarding.gre:inside-subnets] Tunnel Insights (Data Explorer > Internet & SaaS > Tunnel Insights) shows data on, and the health and status of, configured GRE tunnels. [zia.traffic-forwarding.gre:tunnel-insights]

**Cisco 881 ISR example.** The Cisco 881 ISR GRE example sets the MSS to 1436, based on the path MTU, and configures no NAT on the interface, so the service can log internal IP addresses and sublocations can be configured. [zia.traffic-forwarding.gre:cisco-example-mss-nat] The Cisco 881 ISR GRE example says some Cisco routers forward PBR traffic in the software path, causing CPU spikes and performance issues; if that follows a PBR rollout, Zscaler recommends IP route-based forwarding instead. [zia.traffic-forwarding.gre:cisco-pbr-cpu]

**MTU and MSS.** MTU and MSS for the tunnel are calculated from the WAN interface: for a 1,500-byte WAN, GRE MTU is 1,500 - 20 - 4 = 1,476 and GRE MSS is 1,476 - 20 - 20 = 1,436. An incorrect MTU causes fragmentation and degraded performance. [zia.traffic-forwarding.gre:mtu-mss] A suboptimal MTU for a GRE or IPSec tunnel results in severe performance degradation. An optimal tunnel MTU is equal to or lower than the network appliance MTU and the path MTU, where Path MTU = MSS + 20 bytes (IP header) + 8 bytes (ICMP header); the tunnel header length is subtracted from the lower of the two values, 24 bytes for a GRE tunnel. If the organization experiences issues performing these tasks, Zscaler recommends a tunnel MTU of 1400. [zia.traffic-forwarding.gre:mtu-procedure] The MTU article gives ping-sweep commands: `ping -g [network appliance MTU value minus 50] -G 1600 -h 10 -D [destination]` (the page says the -g component of the ping command applies only to appliances running macOS), a `for /l` loop with `-f`, and a `for size in` loop with `-M do`. For GRE tunnels, Zscaler Customer Support can provide the IP addresses of the primary and secondary Public Service Edges to which the organization must forward traffic. [zia.traffic-forwarding.gre:mss-discovery] The article's worked example is open [gap:zia.traffic-forwarding.gre:mtu-example-conflict]. The symptom of an unclamped MSS is open [gap:zia.traffic-forwarding.gre:mss-symptom]. Whether premium data centers can be used with a Support ticket is open [gap:zia.traffic-forwarding.gre:premium-dc-support]. IPv6 traffic can be sent inside an IPv4 GRE tunnel with no additional tunnel configuration; for clients inside a location, both web and non-web IPv6 traffic can be forwarded inside an IPv4 GRE or IPSec tunnel. IPv6 support is in limited availability and is provisioned through Zscaler Support, it must be enabled at the organization level before other IPv6 settings, and it must be enabled for the location, because IPv6 traffic arriving at a location without it is dropped. [zia.traffic-forwarding.gre:ipv6-inside-gre] IPv6 across every forwarding method is in [IPv6 through ZIA: forwarding per method, prerequisites, processing and policy](kb:zia.traffic-forwarding.ipv6). What else IPv6 over GRE needs is partly open [gap:zia.traffic-forwarding.gre:ipv6-coverage]; IPSec's coverage is in [IPSec tunnels to ZIA: limits, IKE and device settings](kb:zia.traffic-forwarding.ipsec).

GRE tunnels configured on Virtual Service Edges are established dynamically with no internal IP addresses, like unnumbered GRE tunnels. [zia.traffic-forwarding.gre:vse-unnumbered] Virtual Service Edge clusters are [The Virtual Service Edge cluster: limits, object, build order and Location binding](kb:zia.virtual-service-edge.clusters).

What to check:
1. Whether the tunnel's source IP is a provisioned static IP.
2. Whether the inner addresses are NATed, which sets the tunnel to 1 Gbps or 250 Mbps.
3. Whether the primary and secondary VIPs are in different data centers.
