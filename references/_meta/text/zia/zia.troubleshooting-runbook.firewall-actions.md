# Runbook: Firewall Control outcomes Allow due to insufficient app data and Bypassed due to missing config (zia.troubleshooting-runbook.firewall-actions)
Also called: Allow Due to Insufficient App Data; Bypassed Due to Missing Config; Best Effort Policies

**Allow due to insufficient app data.** Allow due to insufficient app data is logged when the DPI engine could not identify the network application, typically because the connection ended before enough packets were processed. [zia.troubleshooting-runbook.firewall-actions:insufficient-cause] The Service Edge allows and processes the first packets of each flow so DPI can build the application tree; the page says the tree is typically completed with the first 5 packets for common applications. [zia.troubleshooting-runbook.firewall-actions:insufficient-first-packets] If a session ends before 12 packets without the service getting one packet with data, DPI is not triggered and the transaction is allowed or blocked by the firewall rules that contain no network applications, typically logging 0.0.0.0 as the Server Source IP. [zia.troubleshooting-runbook.firewall-actions:insufficient-no-data-packet] If a session ends before 12 packets and DPI could not build the app tree, the packets (fewer than 12) are allowed and logged as allowed due to insufficient app data, and the topmost applicable rule containing a network application is logged. [zia.troubleshooting-runbook.firewall-actions:insufficient-no-tree] For these entries the action and network application of the logged topmost rule do not matter because enforcement was postponed, but its other criteria must match; web traffic is first evaluated against Web Policy rules, and Blocked by Web Proxy Policy is logged if Cloud App or URL Filtering rules block it. [zia.troubleshooting-runbook.firewall-actions:insufficient-logged-rule-action] For sessions ending after 12 packets, the page says the most common outcome is that DPI built the app tree but stopped after the leaf application-layer node and transactions are allowed or blocked on all applicable firewall rules; failure to identify is very rare and returns ip.tcp.http, ip.tcp.ssl.https or ip.udp.dns. [zia.troubleshooting-runbook.firewall-actions:insufficient-after-12] What the packet counts include is open [gap:zia.troubleshooting-runbook.firewall-actions:packet-count-definition].

**Rule design.** The page's examples: a top rule allowing the IP network application allows all IP traffic regardless of other rules; a top rule blocking the HTTPS network service (TCP port 443) with a second rule allowing the HTTPS network application blocks all port 443 traffic. [zia.troubleshooting-runbook.firewall-actions:insufficient-rule-eval-examples] The page says TCP, UDP or IP should be specified as network services rather than network applications, and that network service rules should be placed before network application rules to limit the scope of DPI. [zia.troubleshooting-runbook.firewall-actions:insufficient-service-vs-app] If the network application is part of a higher-ordered rule, the page says to blend the network application condition with at least one other limiting condition, and to order rules with network applications lower than rules without them. [zia.troubleshooting-runbook.firewall-actions:insufficient-solution] An Advanced Firewall SKU is needed to enforce rules configured with network applications, and rules of that kind must be cleaned up after a downgrade from Advanced to Basic Firewall. [zia.troubleshooting-runbook.firewall-actions:insufficient-advanced-sku] In the page's example of a poorly defined Firewall rule set, Rule 1 is called too wide because it has no other criteria, so all traffic passing through Zscaler Firewall is subject to DPI and suffers delayed policy enforcement; the fix is to add criteria such as user, location or network service. [zia.troubleshooting-runbook.firewall-actions:insufficient-example-ruleset]

**Bypassed due to missing config.** On the Bypassed Due to Missing Config page, the action is logged in rare circumstances when the Public Service Edge fails to connect to the Zscaler Central Authority, so some traffic passes through Zscaler Firewall without policy enforcement; it typically happens when a user's or location's traffic first arrives and the policy config must be downloaded. The Policy Reasons article words the traffic as passing through Zscaler Firewall or DNS. [zia.troubleshooting-runbook.firewall-actions:missing-config-cause] The page computes the bypassed percentage as COUNT_BYPASSED x 100 divided by TOTAL_SESSIONS; above 25K bypassed sessions it suggests downloading a CSV, and for a CSV count of 100,000 it suggests reducing the time period or looking up the logs in the SIEM if NSS is deployed. [zia.troubleshooting-runbook.firewall-actions:missing-config-measure] The page describes a bypassed percentage at or below 0.05% of total sessions as the most general case, and says to submit a case to Zscaler Support when it is more than 0.05%. [zia.troubleshooting-runbook.firewall-actions:missing-config-threshold] The export the limits refer to is open [gap:zia.troubleshooting-runbook.firewall-actions:bypassed-export-limits].

**Modes.** The page names Fail-Open as the default mode (policy evaluation is bypassed for some transactions) and Fail-Closed as blocking by default and logging in Firewall Insights, and says the chosen mode is sent to Zscaler Support in a case. [zia.troubleshooting-runbook.firewall-actions:missing-config-modes] Whether the mode is chosen in the console or by a Support case is in dispute [divergence:zia.troubleshooting-runbook.firewall-actions:partial-config-mode-choice]. Best Effort Policies apply a subset of Firewall rules: those without user, group or location criteria, those with such criteria if the Service Edge received traffic from those users, groups or locations before the disconnection, and those for the Miscellaneous Unauthenticated Transactions user (noauth-misc). [zia.troubleshooting-runbook.firewall-actions:missing-config-best-effort] Which rules Best Effort Policies apply is in dispute [divergence:zia.troubleshooting-runbook.firewall-actions:best-effort-rule-set]; the Fail Closed logging contradiction is in [Behavior When Partial Configuration Available: Fail Open, Fail Closed and Best Effort Policies](kb:zia.advanced-settings.partial-configuration).

Sources disagree (name both sides):
- The advanced settings page describes Behavior When Partial Configuration Available as a setting an admin defines; the Bypassed Due to Missing Config runbook says Engineering is working on a console control and the mode is chosen by submitting a Support case. [divergence:zia.troubleshooting-runbook.firewall-actions:partial-config-mode-choice]
  - zscaler-help: A setting lets the admin define how security policies are enforced when a Service Edge operates with incomplete configurations.
  - zscaler-help: A solution to control these transactions from the Admin Console is still being worked on, and the mode is chosen by submitting a case to Zscaler Support.
  Impact: The runbook's Engineering line is a dated notice (runbook updated 2026-07-29, Advanced Settings page updated 2026-10-28), so the pages may differ by date rather than by tenant; neither page says which holds for a given tenant.
- The runbook says Best Effort Policies apply rules the Service Edge saw traffic for or that name the Miscellaneous Unauthenticated Transactions user, and limits the Bypassed Due to Missing Config action to Firewall; the Advanced Settings page says rules with explicit location or user criteria need Org Default or the Miscellaneous user added to them, and applies the mode to both web and firewall traffic. [divergence:zia.troubleshooting-runbook.firewall-actions:best-effort-rule-set]
  - zscaler-help: Best Effort Policies apply rules without user, group or location criteria, rules whose users, groups or locations the Service Edge had traffic from before the disconnection, and rules for the noauth-misc user.
  - zscaler-help: A rule with explicit location or user criteria matches the fallback only if the Org Default location or the Miscellaneous Unauthenticated Transactions user is added to it, and the mode applies to both secure web gateway and firewall traffic.
  Impact: Which rules still apply to a Service Edge without a full configuration depends on which page is read; the pages do not say whether the runbook's list is the same set described by the Org Default fallback, and the runbook speaks of Firewall only.
