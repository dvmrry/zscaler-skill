# SaaS Applications page: application status, tags and custom cloud applications (zia.cloud-app-control.custom-applications)
Also called: SaaS Applications page; custom cloud application; custom applications category; application status sanctioned unsanctioned; predefined cloud application; cloud applications API; bulk update of application status and tags

The SaaS Applications page allows adding custom cloud applications, and lists all supported cloud applications with their category and risk index so Cloud App Control rules can be defined for apps not yet discovered in the Shadow IT Report. It also edits the status of all cloud applications (as the Application Information page does), tags applications with predefined and custom labels, and creates cloud app instances that distinguish corporate and personal instances. [zia.cloud-app-control.custom-applications:saas-applications-page]

**Status.** An application's status is Sanctioned (approved for the organization's use because it meets all its security requirements) or Unsanctioned (not approved because of its attack vulnerability). The status is chosen when adding a cloud application risk profile, which a Cloud App Control rule then selects as a criterion; the page's status filter criterion also offers All, Unclassified and Under Review. [zia.cloud-app-control.custom-applications:application-status] What the Unclassified and Under Review statuses mean is open [gap:zia.cloud-app-control.custom-applications:status-values].

**Rows and editing.** Each application row shows its name, category, status (Sanctioned or Unsanctioned), type (All, Custom or Predefined), tags and description, and a risk index from 1 to 5 (1 the lowest risk). A predefined application's name links to its Application Information page, which shows its security attributes. A predefined application's Application Status, Risk Index and Tags can be edited, and a custom one's Cloud Application Name, Application Status, Risk Index, Tags, URLs and Description. A custom cloud application can be deleted. [zia.cloud-app-control.custom-applications:columns-and-editing]

**Custom cloud applications.** A custom cloud application adds an application not already present in Zscaler for discovery and usage metrics (for example number of users, bytes uploaded or downloaded), and associates it with the Custom Applications Cloud App Control rule. By default all custom applications are placed in the Custom Applications category, which is independent of other categories and so cannot be edited. [zia.cloud-app-control.custom-applications:custom-app-purpose] A custom cloud application has a name (displayed when configuring Custom Applications rules), a status of Sanctioned or Unsanctioned, a risk index from 1 to 5, tags, URLs or IP addresses added with Add Items, and an optional description of at most 10,240 characters. [zia.cloud-app-control.custom-applications:custom-app-fields] An organization can have 64 custom cloud applications, each with up to 128 URLs. [zia.cloud-app-control.custom-applications:custom-app-limits] How URLs are formatted and whether IP addresses count toward the URL limit is open [gap:zia.cloud-app-control.custom-applications:url-format-and-limit].

**Caveats.** Risk attributes are not captured for custom cloud applications, SSL/TLS Inspection must be enabled for the custom cloud application lookup, and Custom Applications is enabled by contacting Zscaler Support. If Zscaler creates a predefined cloud application with a URL used in a custom one, the predefined application takes precedence and rules created with the custom application are ineffective; Zscaler notifies customers about the categorization change through Trust Posts. [zia.cloud-app-control.custom-applications:custom-app-caveats]

**API.** Three calls under Shadow IT Report in the ZIA API reference read and update cloud applications and their tags: GET /cloudApplications/lite lists predefined and custom cloud applications, each by ID and name, a page at a time (pageNumber starts at 0, and limit, the page size, defaults to 1000); PUT /cloudApplications/bulkUpdate updates the status and tags of the applications whose IDs it names; and GET /customTags lists the custom tags available to assign, each by ID and name. A 2023 release added all three. [zia.cloud-app-control.custom-applications:api-calls] Two calls under Cloud Applications in the ZIA API reference list the predefined and user-defined cloud applications that policies use: GET /cloudApplications/policy for DLP, Cloud App Control, Advanced Settings, Bandwidth Classes and File Type Control rules, and GET /cloudApplications/sslPolicy for SSL Inspection rules. Each returns the applications' details when groupResults is false and a count per application category when it is true. [zia.cloud-app-control.custom-applications:policy-list-calls] A bulk update's body names the applications by ID (applicationIds), a status (sanctionedState, whose values are UN_SANCTIONED, SANCTIONED and ANY) and the custom tags to assign (customTags, each an ID and a name). [zia.cloud-app-control.custom-applications:bulk-update-body] What a bulk update does with existing tags, and what ANY does, is open [gap:zia.cloud-app-control.custom-applications:bulk-update-semantics]. The bulk update's rate limit is in [ZIA legacy API status codes and per-endpoint rate limits](kb:shared.legacy-api.zia-errors-and-limits). Both SDKs make these calls from their shadow IT report module: the Go package shadowitreport (GetAllCloudAppsLite, Update and GetAllCustomTags) and the Python module shadow_it_report (list_apps, bulk_update and list_custom_tags). Python's bulk_update requires a status (sanctioned, unsanctioned or any, sent as SANCTIONED, UN_SANCTIONED or ANY) and always sends it, so an update of tags alone from Python also writes a status; it takes the custom tags as a list of tag IDs. [zia.cloud-app-control.custom-applications:sdk-calls] The Go SDK names the page parameter differently [divergence:zia.cloud-app-control.custom-applications:lite-page-parameter-case], and the Python SDK sends tags in a different shape [divergence:zia.cloud-app-control.custom-applications:bulk-update-tag-shape]. The API cannot add a custom cloud application or set its URLs: its cloud application calls list applications, bulk-update status and tags, or manage cloud app instances, and a bulk update's body has no application name or URL member. Adding a custom application and editing its URLs are done on the SaaS Applications page. [zia.cloud-app-control.custom-applications:no-create-or-url-call]

The Custom Applications rule is in [Cloud App Control categories (rule types), limits and predefined rules](kb:zia.cloud-app-control.rule-types). Tags and risk profiles are in [Cloud Application Risk Profiles in Cloud App Control](kb:zia.cloud-app-control.risk-profiles). Instances of an application are in [Cloud application instances: identifiers, supported applications and limits](kb:zia.cloud-app-control.app-instances).

What to check:
1. Whether a rule written with a custom application is ineffective because Zscaler later created a predefined application with the same URL, and whether SSL/TLS Inspection is enabled for the custom application lookup.
2. Whether the application is Sanctioned or Unsanctioned, since a risk profile can use the status as a Cloud App Control criterion.
3. Whether the custom application is at the 64-application or 128-URL limit before adding one.
4. Whether a requested change can go through the API: status and custom tags can, by a rate-limited bulk update that names application IDs (whether it replaces or adds tags is open); adding a custom application or changing its URLs cannot.

- [zia.cloud-app-control.custom-applications:no-create-or-url-call] Tier B: Rests on absence. In the captured OneAPI spec the only paths naming cloud applications are /cloudApplications/lite, /cloudApplications/policy and /cloudApplications/sslPolicy (GET), /cloudApplications/bulkUpdate (PUT) and /cloudApplicationInstances; the legacy API reference lists the same /cloudApplications paths. Neither SDK's ZIA client calls any other cloud application path at its pinned version (`grep -rhoE '/cloudApplication[A-Za-z/{}]*' zscaler/zia` finds only lite, bulkUpdate, policy, sslPolicy and the instance paths). The Go package endpoint_dlp/endpoint_custom_apps creates Endpoint DLP custom applications (/endPointApplications/customApp), a different object. A newer API version may add a create call.

Sources disagree (name both sides):
- Name of the page-number query parameter on GET /cloudApplications/lite [divergence:zia.cloud-app-control.custom-applications:lite-page-parameter-case]
  - api-specs: The API reference names the parameter pageNumber.
  - sdk-go: The Go SDK's GetAllCloudAppsLite sends it as PageNumber.
  Impact: If the API matches parameter names exactly, a page number passed to the Go call is not applied. No source says whether the match ignores case.
- Shape of each custom tag in a bulk update's customTags [divergence:zia.cloud-app-control.custom-applications:bulk-update-tag-shape]
  - api-specs: The API reference types each tag's id as an integer, beside a name.
  - sdk-python: The Python SDK's bulk_update sends each tag as an id string with no name.
  Impact: A request built from the Python SDK differs from the reference's shape. No source says whether the API accepts a string ID or a tag without its name.
