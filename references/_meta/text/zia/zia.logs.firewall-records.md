# What a ZIA firewall log record is: aggregates, action and field names (zia.logs.firewall-records)
Also called: firewall log record; aggregated session; last session in the aggregate; firewall action allowed blocked; nwapp nwsvc; firewall log vs web log field names; inbytes outbytes; threat_severity

A firewall log record describes a firewall session, and one record can stand for several aggregated sessions. Field names also differ from the web log for the same data.

**Aggregated sessions.** The aggregate field indicates whether the Firewall session is aggregated, and numsessions is the number of sessions that were aggregated. [zia.logs.firewall-records:agg-flag] On an aggregated session, csip, csport, cdip, cdport, tsip, sdport, sdip, ssip and ssport each hold the value of the last session in the aggregate. [zia.logs.firewall-records:last-session] An aggregated record carries one set of addresses and ports for several sessions, so counting distinct addresses from aggregate records undercounts the addresses seen. [zia.logs.firewall-records:undercount] avgduration is the average session duration in milliseconds, if the sessions were aggregated. [zia.logs.firewall-records:avgduration] srcip_country is determined by the client IP address location, and logs carry no source country for aggregated sessions that are allowed. [zia.logs.firewall-records:srcip-country-agg] With the Standard Firewall subscription allowed sessions are logged in aggregate form and every blocked session gets its own detailed log; detailed logging of all sessions needs Advanced Firewall, while DNS transactions get detailed logs with both. Aggregation is done within a 15-minute window over User, Rule Slot, Network Service, Network Application and IP Category: consecutive sessions with the same values in these fields produce a single log whose remaining fields are taken from the last session in the window. [zia.logs.firewall-records:aggregation-rule] How the byte and duration counters behave on an aggregate is still open [gap:zia.logs.firewall-records:aggregate-counters]. Why allowed aggregates lack a country is open [gap:zia.logs.firewall-records:srcip-country-aggregate]. The Firewall Insights Logs columns article describes, for aggregated sessions, the bytes sent from the server and the bytes received by the server as totals across all sessions in the aggregate, and the duration as the sum of the individual session durations; the Extranet columns article says the same. [zia.logs.firewall-records:aggregate-totals] The Insights Logs columns and the NSS page describe the aggregate counters differently [divergence:zia.logs.firewall-records:aggregate-counters-source].

**Which records a feed sends.** A TCP Firewall feed's Firewall Log Type offers Full Session Logs, Aggregate Logs, or both, Full Session Logs being the option that log each session that matches the rule individually except web (HTTP/HTTPS) and FTP/FTPS sessions that match the same Allow rule over a time window, and Aggregate Logs, which group sessions by user, rule, network service and network application and record them periodically within an approximately 15-minute window. Full session logs do not include sessions recorded as part of aggregated entries, and the excluded web and FTP sessions are always available as aggregated entries, with detailed transactions in Web logs. [zia.logs.firewall-records:firewall-log-type] The HTTP Firewall and Cloud Firewall feed articles offer the same Firewall Log Type options as the TCP Firewall article: Full Session Logs (each matching session individually, except web (HTTP/HTTPS) and FTP/FTPS sessions that match the same Allow rule over a time window, which Firewall logs always record as aggregated entries), Aggregate Logs (sessions grouped on {user, rule, network service, network application} and recorded periodically within an approximately 15-minute time window), or Both Session and Aggregate Logs, which includes all log data from both. [zia.logs.firewall-records:firewall-log-type-http-cloud] The grouping keys differ between the feed articles and the NSS output format page [divergence:zia.logs.firewall-records:aggregation-keys].

**Action and threat.** The firewall action field is described as the action the service took on the transaction: Allowed or Blocked. [zia.logs.firewall-records:action-two-values] The firewall rulelabel is described as the rule applied to the transaction with no Block-only qualifier, unlike the web log rulelabel, which applies only to Block rules; its example is the Default Firewall Filtering Rule. [zia.logs.firewall-records:rulelabel-unqualified] Precedence among firewall, IPS and DNAT is open [gap:zia.logs.firewall-records:action-precedence]. The firewall field is threat_severity, and its description names that same field; severity relates directly to threat_score, so a score from 90 to 100 gives Critical. [zia.logs.firewall-records:severity-typo] threat_score runs from 0 to 100, from the least to the greatest threat, and ThreatLabz assigns the score to the threat in the Zscaler Threat Library. [zia.logs.firewall-records:threat-score-source] ips_custom_signature and bypassed_session are numeric flags with values 1 or 0; 1 means a custom IPS signature rule was applied, or that traffic bypassed Zscaler Client Connector. [zia.logs.firewall-records:flags-1-0]

**What the Insights Logs show.** The Insights Logs list more action values than the NSS description gives [divergence:zia.logs.firewall-records:action-value-set]. The Firewall Insights Logs Action filter, for firewall and IPS policy actions, includes the traffic that might be blocked due to a web policy violation after passing through the firewall module; its values include Allow due to insufficient app data, Block/Drop, Block/ICMP, Block/Reset, IPS Drop, IPS Reset, Dropped due to internal error, Bypassed due to missing config and Timed out while waiting for a config. [zia.logs.firewall-records:action-values] Dropped due to internal error is logged when the firewall received the user-side traffic but failed to establish the internet-side connection, so the flow was dropped; it might occur when the Service Edge infrastructure is momentarily overused. [zia.logs.firewall-records:internal-error] Bypassed due to missing config is logged when the Public Service Edge cannot establish a connection with the Zscaler Central Authority, so the flow passes through Zscaler Firewall or DNS without policy; it might occur when a specific user's or location's traffic arrives at the Service Edge for the first time. Timed out while waiting for a config is logged when the connection is established but the configuration does not arrive within the expected time, typically 5 seconds. The columns page says both might additionally appear under specific circumstances when Best Effort Policies or Fail Closed mode is used with partial configurations. [zia.logs.firewall-records:missing-config] The Firewall Insights Logs Rule Name column is displayed in the logs only when the traffic is blocked, and by default not for allowed traffic. [zia.logs.firewall-records:rule-name-blocked-only] The NSS page does not state whether the rule name is withheld for allowed traffic [gap:zia.logs.firewall-records:rulelabel-display]. The Zscaler Bypass Traffic rule appears in firewall logs when the web module does not accept control from the firewall module because the handshake ends abruptly during flow establishment, or when traffic comes from a firewall-enabled sublocation whose parent location or another sublocation under it is not firewall-enabled, owing to latency in identifying the location differences, as in X-Forwarded-For setups. [zia.logs.firewall-records:bypass-traffic-rule] The Firewall Insights Logs threat severity values follow the threat score: Critical for 90–100, High for 75–89, Medium for 46–74, Low for 1–45 and None for 0. [zia.logs.firewall-records:severity-buckets]

**Console columns.** For ICMP the Firewall Insights Logs source port shows the ICMP Identifier and the destination port shows as the ICMP Sequence Number. [zia.logs.firewall-records:icmp-ports] A blank User in Firewall Insights Logs means location-based authentication is set. [zia.logs.firewall-records:user-blank] With Source IP Anchoring for a URL or domain, the Firewall Insights Logs show the IP address 0.0.0.1 for the server to indicate the internal redirection, because the client request is forwarded to Private Access and the server IP is not logged at the proxy layer. [zia.logs.firewall-records:sipa-server-ip] Client Destination Name and DNAT Destination Name are FQDN columns for Advanced Firewall, each holding the last session's value on an aggregate. [zia.logs.firewall-records:advanced-firewall-fqdns] The console viewer is [ZIA Insights Logs: log families, time frame, export and background queries, filters and console-only columns](kb:zia.insights.logs).

**Network fields.** inbytes counts bytes sent from the server to the client and outbytes bytes sent from the client to the server. [zia.logs.firewall-records:bytes-direction] nwapp is described as the network application that was accessed and nwsvc as the network service that was used. [zia.logs.firewall-records:nw-fields] Their relation is open [gap:zia.logs.firewall-records:nwapp-vs-nwsvc]. srcip_country holds a country name such as United States, while destcountry holds an abbreviated code such as USA. [zia.logs.firewall-records:country-forms] Because srcip_country carries a country name and destcountry an abbreviated code, the two fields are not directly comparable without mapping one form to the other. [zia.logs.firewall-records:country-forms-not-comparable]

**Names against the web log.** Similar fields are named differently in the firewall and web logs: ttype and trafficredirectmethod, external_deviceid and external_devid, bypass_etime and bypassed_etime, bypassed_session and bypassed_traffic, and threat_severity and threatseverity. [zia.logs.firewall-records:names-differ]

What to check:
1. Whether the record is an aggregate before reading its addresses, ports or country as one session.
2. Which field carries the rule, IPS threat and DNAT result before reading action alone.
3. Which name a query uses when moving it between the web and firewall logs.
4. Whether nwapp or nwsvc names the application, and the direction of inbytes against outbytes.

Sources disagree (name both sides):
- The Firewall Insights Logs columns article describes aggregated byte counters as totals across all sessions in the aggregate and the duration as the sum of session durations, while the NSS firewall output format says an aggregated log's remaining fields are taken from the last session in the 15-minute window; the HTTP Firewall feed article's byte filters agree with the totals, and its Durations filter gives the average. [divergence:zia.logs.firewall-records:aggregate-counters-source]
  - zscaler-help: For aggregated sessions the bytes sent from the server are a total across all sessions in the aggregate and the duration is the sum of the individual session durations.
  - zscaler-help: A single log records the remaining fields from the last session in the 15-minute window, and inbytes is described as the number of bytes sent from the server to the client, with no aggregate wording.
  - zscaler-help: The HTTP Firewall feed article's byte filters say the value for aggregated sessions is the total bytes across all sessions in the aggregate, agreeing with the Insights Logs columns, while its Durations filter says it indicates the average session duration, against the Insights sum.
  Impact: Summing inbytes, outbytes and durationms over aggregate records gives different results if they hold the last session's values rather than totals; the HTTP Firewall feed article gives byte totals and an average Duration for aggregated sessions, and no page says which of these a feed's own inbytes, outbytes and duration fields hold.
- The HTTP and Cloud Firewall feed articles group aggregate logs on four keys, while the NSS firewall output format lists five aggregation fields; IP Category is clearly absent from the feed articles' list, and their "rule" may or may not be the output format's Rule Slot. [divergence:zia.logs.firewall-records:aggregation-keys]
  - zscaler-help: Aggregate Logs group individual sessions on user, rule, network service and network application, recorded within an approximately 15-minute time window.
  - zscaler-help: The Cloud Firewall feed article gives the same four keys.
  - zscaler-help: Logs are aggregated for User, Rule Slot, Network Service, Network Application and IP Category within a 15-minute time window.
  Impact: Whether sessions that differ only in IP Category aggregate into one record depends on which page is read; the pages do not say whether the feed articles' shorter list is complete (the TCP article's matching sentence is in firewall-log-type).
- The NSS firewall output format describes the action field as Allowed or Blocked, while the Firewall Insights Logs Action filter lists firewall and IPS policy actions beyond those two. [divergence:zia.logs.firewall-records:action-value-set]
  - zscaler-help: The action is Allowed or Blocked.
  - zscaler-help: The Action filter lists specific firewall and IPS policy actions, among them Block/Drop and IPS Drop.
  Impact: A query that matches the action field against Allowed and Blocked misses the console's other values if a feed carries them; the pages do not say whether the console values are what the feed's action field holds.
