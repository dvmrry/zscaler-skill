# IPv6 through ZIA: forwarding per method, prerequisites, processing and policy (zia.traffic-forwarding.ipv6)
Also called: ipv6 support; ipv6 forwarding; IPv6 Configuration; Other6; Block All IPv6

Zscaler extends IPv6 support according to the forwarding method and whether the client is inside a location. Inside a location, IPv6 traffic is forwarded inside an IPv4 tunnel using GRE or IPSec, web and non-web alike. Outside a location, web requests go through PAC files via a self-hosted or ISP-provided NAT64 gateway or directly over Client Connector Z-Tunnel 1.0, and web and non-web requests go directly over Z-Tunnel 2.0. Zscaler highly recommends Client Connector as the preferred IPv6 forwarding method whenever feasible. [zia.traffic-forwarding.ipv6:methods] Zscaler's cloud infrastructure can handle IPv6 traffic, but the outer packets of a tunnel arriving at the Service Edges must be IPv4 packets. [zia.traffic-forwarding.ipv6:outer-ipv4] Provisioning IPv6 and enabling it for the organization and each location is in [IPv6 traffic can be sent inside an IPv4 GRE tunnel with no additional tunnel configuration; for clients inside a location, both web and non-web IPv6 traffic can be forwarded inside an IPv4 GRE or IPSec tunnel. IPv6 support is in limited availability and is provisioned through Zscaler Support, it must be enabled at the organization level before other IPv6 settings, and it must be enabled for the location, because IPv6 traffic arriving at a location without it is dropped.](kb:zia.traffic-forwarding.gre:ipv6-inside-gre); IPv6 over IPSec needs the selectors in [To forward IPv6 over IPSec the device needs IPv6 traffic selectors for both IKEv1 and IKEv2, and IPv6 support must be enabled for the organization and its locations.](kb:zia.traffic-forwarding.ipsec:ipv6-selectors); NAT64 and DNS64 prefixes are in [NAT64 and DNS64 prefixes: custom prefixes, selection order and limits](kb:zia.traffic-forwarding.ipv6-prefixes).

**Prerequisites.** The prerequisites the Understanding IPv6 Support page lists include Client Connector 4.8 or later on Windows and 4.7 or later on macOS, allowlisting the IPv6 addresses of the Zscaler infrastructure on on-premises firewalls, selecting Packet Filter Based for Tunnel Driver Type in forwarding profiles, and disabling Drop IPv6 Packets for the forwarding profile. [zia.traffic-forwarding.ipv6:client-prerequisites] For clients outside a location, Client Connector users must enable Enable IPv6 Resolution for Zscaler Domains in the Admin Console, otherwise a NAT64/DNS64 service is needed; PAC file users must use a self-hosted or ISP-provided NAT64 gateway. [zia.traffic-forwarding.ipv6:remote-prerequisites] When Z-Tunnel 1.0 or Z-Tunnel 2.0 IPv6 traffic is forwarded without an intermediate NAT64 service, it must go only to IPv6-enabled data centers, and for Client Connector without a NAT64 service only to data centers in the IPv6-enabled subcloud Zscaler manages. With an intermediate NAT64 service, the page says to check whether the data center is IPv6-enabled by verifying on the Zscaler config page that it has an IPv6 virtual IP address. [zia.traffic-forwarding.ipv6:ipv6-data-centers] On-premises firewalls must allow IPv6 traffic to gateway6, secondary.gateway6, pac6, login6, logout6 and mobile6 under <cloudname>.net, to any6.broker.<cloudname>.net and to speedtest6.zscaler.com; the SAML IdP Reply URL is set for https://login6.<cloudname>.net/sfc_sso and, if applicable, https://logout6.<cloudname>.net/sfc_sso. [zia.traffic-forwarding.ipv6:firewall-domains] Which data centers are IPv6-enabled is open [gap:zia.traffic-forwarding.ipv6:ipv6-data-center-list].

**Client Connector and PAC setup.** For PAC files, the ${Gateway_Host} variable is configured in the PAC file. For Client Connector, IPv6 traffic must go only to data centers in the IPv6-enabled subcloud Zscaler manages, which the admin does with a custom PAC file used with the App Profile; its gateway variable names the public subcloud ipv6, for example ${GATEWAY.ipv6.zscalertwo.net}. [zia.traffic-forwarding.ipv6:pac-and-zcc-setup] In Client Connector forwarding profiles, Drop IPv6 in Dual Stack Network and Drop IPv6 in IPv6 Only Network must be disabled, for both Z-Tunnel 2.0 and Z-Tunnel 1.0; Drop IPv6 Include Traffic When not supported is recommended, for Z-Tunnel 2.0 only. In app profiles, IPv6 routes are not added to the inclusion settings by default, so all inclusions must be added explicitly, including [2000::/3]; and with * as the DNS Domain Inclusion, Enforce Firewall Control must be enabled for the locations or DNS resolution fails. [zia.traffic-forwarding.ipv6:zcc-profile-settings] Client Connector over Z-Tunnel 2.0 might let IPv6 traffic reach the destination by bypassing the Zscaler service when it connects to a data center that does not support IPv6 yet, or when IPv6 support is disabled in the Admin Console for the organization or the device's location; to prevent that, Client Connector is configured to drop IPv6 packets in its forwarding profiles. [zia.traffic-forwarding.ipv6:zt2-bypass] The Android version for these prerequisites is open [gap:zia.traffic-forwarding.ipv6:android-version].

**How the service connects.** The service prefers an IPv4 connection whenever possible and uses IPv6 for IPv6-only destinations. For web traffic from IPv6 clients arriving in explicit proxy mode via Client Connector over Z-Tunnel 1.0 or via PAC files, it connects over IPv4 when the destination is reachable only over IPv4 or over IPv4 or IPv6, and over IPv6 when the destination is reachable only over IPv6. [zia.traffic-forwarding.ipv6:prefers-ipv4] For traffic from IPv6 clients arriving in transparent proxy mode over a GRE or IPSec IPv4 tunnel, or via Client Connector (Z-Tunnel 2.0 only): if the destination IPv6 address matches a NAT64 prefix the organization supports, the IPv4 address is extracted from it and an IPv4 connection is established; if it is a regular IPv6 address, an IPv6 connection is established. [zia.traffic-forwarding.ipv6:transparent-connection] To establish an IPv4 connection to the destination, the service uses the NAT64/DNS64 mechanism to translate inbound IPv6 packets to IPv4; the translation depends on the type of traffic (DNS queries or non-DNS), the prefix used in the inbound IPv6 packets and the DNS64/NAT64 prefix configurations in the Admin Console. [zia.traffic-forwarding.ipv6:translation-inputs] For an IPv6 client outside a location reaching an IPv4-only or dual-stack destination over Z-Tunnel 2.0, the service connects over IPv4 using the DNS64/NAT64 mechanism for web traffic; for non-web traffic it connects over IPv4 if the destination IPv6 address contains a NAT64 prefix recognized by Zscaler, and over IPv6 otherwise. [zia.traffic-forwarding.ipv6:zt2-web-and-non-web] In the page's DNS response table, an IPv6 client reaching an IPv4 destination gets an IPv4 A response and a DNS64 AAAA response; an IPv4 + IPv6 client reaching an IPv6 destination gets an empty A response and a native IPv6 AAAA response; an IPv6 (CGNAT) client reaching an IPv4 + IPv6 destination gets an IPv4 A response and a DNS64 AAAA response. [zia.traffic-forwarding.ipv6:dns-response-table] What the service does when a DNS query has no A record is stated two ways on the page [divergence:zia.traffic-forwarding.ipv6:no-a-record].

**Policy.** When IPv6 is enabled for the organization, two predefined Firewall Filtering rules are created: Block All IPv6, which blocks traffic from all IPv6 clients to any destination and must be modified, or overridden by higher-order rules, to allow IPv6 traffic; and Allow IPv6 DNS Traffic, which lets DNS traffic from IPv6 clients sent via Client Connector reach the Service Edges. They use Source IP address conditions and do not affect destination-based IPv6 traffic, and Zscaler recommends the lowest precedence for them, after the Default Firewall Filtering Rule. DNS optimization settings for IPv6 connections are enabled for all URL categories and cloud applications in Advanced Settings. [zia.traffic-forwarding.ipv6:predefined-firewall-rules] The service enforces limited policies on IPv6 server-bound connections: Other6 as the location criteria covers all IPv6 traffic from a location; by URL categories, to which individual domains or IP addresses can be added; and by the predefined All IPv6 source and destination address groups. [zia.traffic-forwarding.ipv6:policies] Which policy types accept IPv6 criteria is open [gap:zia.traffic-forwarding.ipv6:policy-types].

**Private and Virtual Service Edges.** Which tunnels carry IPv6 to a Private or Virtual Service Edge is described two ways [divergence:zia.traffic-forwarding.ipv6:service-edge-tunnels]; the Virtual Service Edge page's side is [The forwarding page says Virtual Service Edges support IPv6 traffic if it is only forwarded via GRE tunnels.](kb:zia.virtual-service-edge.forwarding:ipv6-gre-only-page).

**Checking and logs.** Zscaler's My IP Address service is ipv6.zscaler.com. [zia.traffic-forwarding.ipv6:my-ip-v6] Web Logs have a Client IP filter that narrows transactions to devices with IPv4 addresses, IPv6 addresses or both, and DNS64 queries are found with the DNS Request Type filter set to IPv6 Address, which queries the AAAA DNS request and response types. [zia.traffic-forwarding.ipv6:logs] Whether ip.zscaler.com recognizes IPv6 is in [ip.zscaler.com and the vendor's causes when traffic does not land on the nearest Public Service Edge](kb:zia.traffic-forwarding.verification).

What to check:
1. Whether the client is inside a location, which decides between a GRE or IPSec tunnel and PAC files or Client Connector.
2. Whether the forwarding profile disables Drop IPv6 in Dual Stack Network and Drop IPv6 in IPv6 Only Network for Client Connector.
3. Whether an IPv6 design toward a Private or Virtual Service Edge assumes GRE only or GRE and IPSec, since the pages differ.

Sources disagree (name both sides):
- The Understanding IPv6 Support page gives two opposite outcomes for a DNS query whose domain has no A record. [divergence:zia.traffic-forwarding.ipv6:no-a-record]
  - zscaler-help: With no A record, an AAAA record is synthesized using DNS64 and an IPv4 connection is established using NAT64.
  - zscaler-help: With no A record, an AAAA record is used to establish an IPv6 connection.
  Impact: Both sentences start from the same condition and give opposite outcomes, a DNS64-synthesized IPv4 connection against a native IPv6 connection; the page does not say which applies, and its DNS response table is its only other statement of the behavior.
- The Configuring IPv6 Settings page says IPv6 to Private and Virtual Service Edges works over GRE and IPSec tunnels; the Virtual Service Edge forwarding page says only over GRE tunnels. [divergence:zia.traffic-forwarding.ipv6:service-edge-tunnels]
  - zscaler-help: IPv6 to Private Service Edges and Virtual Service Edges is supported only via GRE and IPSec tunnels.
  - zscaler-help: Virtual Service Edges support IPv6 traffic only if it is forwarded via GRE tunnels.
  Impact: An IPv6-over-IPSec design toward a Virtual Service Edge is allowed by one page and excluded by the other.
