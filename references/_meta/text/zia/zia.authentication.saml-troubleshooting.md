# SAML login failures: browser symptoms, Microsoft Edge security zones and the SAML error codes (zia.authentication.saml-troubleshooting)
Also called: SAML error codes; SAML error code table; Can't display the webpage SAML; SAML redirection loop; basic pop-up login SAML; Local intranet zone; Integrated Windows Authentication zones

When a SAML authentication request fails, SAML error codes are displayed in the browser, and a live HTTP header dump is helpful in all cases. [zia.authentication.saml-troubleshooting:error-codes-shown] The error codes for the other authentication methods and for directory synchronization are in [ZIA authentication error codes: generic, directory, Kerberos and Identity Proxy](kb:zia.authentication.error-codes).

**Browser symptoms.** The browser error "Can't display the webpage." can occur if the connection is redirected to Zscaler or the user's workstation can't connect to the URL. The article's fix is a PAC file exception that makes the connection to the server direct, bypassing the Zscaler service (its example is `if shExpMatch(host, "*.company.tld") return "DIRECT";`), and checking reachability with `telnet <Hostname> 443`. [zia.authentication.saml-troubleshooting:cant-display] A redirection page shown for more than 10 seconds means the SAML redirection is looping, which the article says might be due to the explicit proxy configuration; the connection to the server must be direct and not redirected to the Zscaler service. [zia.authentication.saml-troubleshooting:redirect-looping] A basic pop-up login means authentication is not transparent, and the article lists two causes it can occur from. If the user isn't authenticated on the organization's Federation Identity, the article has the user's computer registered in Active Directory and the user logged in to the Windows Domain. If the browser isn't configured to forward the user token to the SAML server (by default, Firefox and Chrome do not relay NTLM tokens to it), the article has the SAML server domain name added to `network.automatic-ntlm-auth.trusted-uris` for Firefox, `google-chrome --auth-server-whitelist="*.clientdomain.tld"` for Chrome (not normally required in a Windows environment, where Chrome uses the same parameters as IE), and the SAML server domain name added to the Local intranet security zone for Internet Explorer. [zia.authentication.saml-troubleshooting:basic-popup]

**Microsoft Edge security zones.** In the Zscaler article on Microsoft Edge security zone settings, with an explicit proxy configuration (a PAC file or proxy configuration with bypasses), any website that bypasses the proxy server is put into the Local Intranet zone, generally websites on the organization's network or the SAML server for authentication (ADFS/PingFederate/OKTA), so the browser automatically performs Integrated Windows Authentication (NTLM/Kerberos). Websites that do not bypass the proxy are treated as internet traffic and put into the Internet zone, where the user is prompted to re-authenticate with a username and password. [zia.authentication.saml-troubleshooting:zones-explicit-proxy] In the same Microsoft Edge article, when Zscaler Client Connector is enabled in Tunnel Mode (Z-Tunnel 1.0 or Z-Tunnel 2.0), the explicit proxy configuration is removed and all traffic is considered internet traffic, so the organization's internal domains must be added to the Local Intranet zone for the browser to perform automatic Integrated Windows Authentication. [zia.authentication.saml-troubleshooting:zones-tunnel-mode] For Microsoft Edge, the article's Local Intranet settings are to go to Internet Options > Security > Local Intranet, click Sites, enable Include all local (intranet) sites not listed in other zones and Include all network paths (UNCs), click Advanced, and add the organization's internal domains or websites in the next window. [zia.authentication.saml-troubleshooting:zones-local-intranet-steps] For Microsoft Edge, Zscaler recommends either enabling or disabling Protected Mode across all four security zones, and not adding any sites specific to the Zscaler cloud to the Trusted Sites zone or the Restricted Sites zone. For Trusted Sites it says to remove any Zscaler-specific sites from the Trusted Sites window and then enable Require server verification (https:) for all sites in that zone. [zia.authentication.saml-troubleshooting:zones-recommendations]

What to check:
1. Whether the page shows a SAML error code, and look the code up in its row before reading anything into it.
2. Whether the failing traffic is meant to reach the SAML server directly, since the PAC exception that makes that connection direct is the listed fix for both the 'Can't display the webpage' error and a looping redirection page.
3. Whether the user's connection is explicit proxy or Client Connector in Tunnel Mode before judging a basic pop-up login, since the zone behavior differs.
4. Whether a missing user is a provisioning problem (auto-provisioning off, SCIM activation pending, directory sync not finished) by the code's row.
