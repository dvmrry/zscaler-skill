# IPSec tunnels to ZIA: limits, IKE and device settings (zia.traffic-forwarding.ipsec)
Also called: ipsec tunnel; ipsec vpn zia; ike; ikev2; ikev1; nat-t; dpd; ipsec mtu; ipsec bandwidth

IPSec is the tunnel for routers that cannot do GRE and for sites with changing addresses. IPSec tunnels are the option when the router does not support GRE or the site has dynamic IP addresses. Compared with GRE it adds processing overhead on the customer's equipment, and the vendor must provide a VPN failover mechanism. [zia.traffic-forwarding.ipsec:when-ipsec] The credential that identifies the site is its own object: [VPN credentials for IPSec: types, immutability and keys](kb:zia.traffic-forwarding.vpn-credentials).

**Capacity and resilience.** IPSec tunnels support 400 Mbps per public source IP address. Above that, use multiple tunnels with different public source IPs, or multiple tunnels from the same public source IP with NAT-T and source port randomization using IKEv2; 800 Mbps is two primary and two backup tunnels. [zia.traffic-forwarding.ipsec:bandwidth-limit] Zscaler recommends two IPSec tunnels to two different Public Service Edges, a primary and a backup; if the primary or an intermediate connection fails, traffic is rerouted through the backup tunnel. [zia.traffic-forwarding.ipsec:two-tunnels] GRE's limits are in [GRE tunnels to ZIA: requirements, bandwidth and deployment](kb:zia.traffic-forwarding.gre).

**Negotiation.** Zscaler recommends IKEv2. New tenants cannot establish IKEv1 IPSec tunnels from a vendor product to forward traffic to Internet & SaaS unless Zscaler Support enables IKEv1 for them. [zia.traffic-forwarding.ipsec:ike-versions] With IKEv1 and a pre-shared key, a peer identified by FQDN must use Aggressive mode and a peer identified by a static IP must use Main mode; Main mode cannot be used where the peer's IP may change. [zia.traffic-forwarding.ipsec:ikev1-modes] For IKEv2 the supported Phase 1 values are AES-256/192/128 or 3DES, SHA-512/384/256/1, Diffie-Hellman groups 2, 5, 14, 19, 20 and 21, with a pre-shared key and 24-hour SA lifetime; Phase 2 supports ESP or AH in tunnel mode with AES-GCM, NULL or AES, 8 child SAs and an 8-hour lifetime. The table lists NAT-T and DPD as options (DPD timeout 20 seconds, 5 retries). [zia.traffic-forwarding.ipsec:ikev2-parameters] The Juniper SRX guide's lifetimes differ from the supported-parameters table [divergence:zia.traffic-forwarding.ipsec:srx-sa-lifetimes]. Whether the IPSec protocol is ESP only or also AH is described two ways [divergence:zia.traffic-forwarding.ipsec:ipsec-protocol]. Zscaler supports NAT-Traversal when the initiating device is behind a NAT device; the packets are then encapsulated in UDP with source port 4500. NAT-T is built into IKEv2 and an optional extension to IKEv1. [zia.traffic-forwarding.ipsec:nat-traversal] Zscaler expects peers to run explicit periodic liveness checks (DPD) where the devices support them, and recommends 10 to 20 second intervals with at least 3 retries; if only on-demand checks are supported the Zscaler IP must be allowlisted so Zscaler's DPD gets a response, and with no response Zscaler cleans up the connection. Ongoing traffic is not treated as proof the peer is alive. [zia.traffic-forwarding.ipsec:dpd] The device guides' own DPD settings differ from that recommendation [divergence:zia.traffic-forwarding.ipsec:dpd-device-guides]. The device's local ID can be a private IP address only when the VPN credential in the Admin Console is an FQDN; otherwise it should be the public IP provisioned as a static IP. A private local ID with a public IP credential makes the negotiation fail. [zia.traffic-forwarding.ipsec:local-id]

**Rules shared by the device configuration guides.** Each of the seven IPSec device guides (Cisco ASA 55xx, Cisco 881 ISR, Juniper SRX, Juniper SSG 20, FortiGate, Palo Alto Networks, SonicWall TZ 350) says tunnel interface configuration must use RFC 1918 addresses, not APIPA addresses. [zia.traffic-forwarding.ipsec:device-guides-rfc1918] All seven device guides say Zscaler does not support Extended Sequence Number (ESN) based proposals in IPSec tunnel negotiation; one section of the Cisco ASA guide says "configuration" where another says "negotiations". [zia.traffic-forwarding.ipsec:no-esn] The Cisco ASA guide says Zscaler supports up to 8 Phase 2 SAs: one is used for the connection between the ASA's public IP address and the Public Service Edges, leaving seven for subnets that flow through the tunnel. [zia.traffic-forwarding.ipsec:phase2-sa-count] The Cisco ASA guide says the public source IP address is required only to set up an IPSec tunnel in Phase 1 main mode. [zia.traffic-forwarding.ipsec:main-mode-source-ip]

**Cisco guides.** In the Cisco ASA guide's section for version 9.6, the policy numbered #1 must be the Zscaler policy or the tunnel negotiations fail; the ASA's default Phase 2 SA lifetime of 8 hours (28800 seconds) equals Zscaler's recommended value; and traffic through the tunnel must keep its source IP address. [zia.traffic-forwarding.ipsec:asa-specifics] The Cisco 881 ISR guide says both tunnels are configured at the gateway but only one is operational at a time; the second is a backup. [zia.traffic-forwarding.ipsec:one-tunnel-active] The Cisco 881 ISR guide says that when PAC files forward traffic through the tunnel, IP SLA monitoring and the PAC files must use different Global Public Service Edge IP addresses; with the same ones, the PAC files send all packets through the same tunnel whatever the tunnel interface state. [zia.traffic-forwarding.ipsec:pac-and-ip-sla] IKEv2 needs Cisco IOS 15.1.1T or later on a Cisco 881 ISR, and version 19.2R2.7 or later on a Juniper SRX 300. [zia.traffic-forwarding.ipsec:ikev2-device-versions]

**Other device guides.** The Palo Alto Networks guide says to keep the Enable option unchecked because Zscaler does not support life size; the Juniper SSG 20 guide enters 0 bytes for the Phase 2 lifetime in Kbytes. [zia.traffic-forwarding.ipsec:no-lifesize] The Cisco 881 ISR and Palo Alto Networks guides say to contact Zscaler Support if the admin is unable to ping both Public Service Edge IP addresses. [zia.traffic-forwarding.ipsec:ping-both-edges] The Palo Alto Networks guide says the Public Service Edge VIP locations must correspond to the Public Service Edge IP locations, that PAN-OS uses ICMP probes for tunnel and policy-based forward monitoring, and that the destination IP is the Virtual IP address of the primary tunnel (165.225.80.34 in the example). [zia.traffic-forwarding.ipsec:pan-monitoring] The Juniper SRX guide requires both DPD and VPN monitoring for failover; the Juniper SSG 20 and SonicWall TZ 350 guides require DPD, and the SonicWall TZ 350 does not support VPN monitoring and relies on DPD for failover. [zia.traffic-forwarding.ipsec:device-failover] The FortiGate guide says the network processor of some Fortinet devices does not support offloading VPN phase one traffic, which causes an unacceptable drop in tunnel performance. [zia.traffic-forwarding.ipsec:fortinet-np-offload] The Juniper SRX guide says ECMP flow-based forwarding can optionally be configured to load-balance the tunnels if multiple virtual IP addresses are configured in the Zscaler data center for the VPN tunnels. [zia.traffic-forwarding.ipsec:srx-ecmp]

**Destinations and Azure Virtual WAN.** Under VPN Host Name, the admin finds the two data centers closest to the organization's location and chooses one as the destination of the primary tunnel and the other as that of the backup, and the hostnames of those destinations are resolved when IP addresses are needed. The cloud name is in the URL admins use to log in. [zia.traffic-forwarding.ipsec:finding-vpn-hosts] Azure Virtual WAN locations and their tunnels are in [Azure Virtual WAN integration: prerequisites, limitations, service principal, hub sync and errors](kb:zia.traffic-forwarding.azure-vwan).

**MTU and IPv6.** The vendor's IPSec table gives an optimal MTU of 1400 bytes and an MSS of 1360 bytes for Phase 2, for both IKEv2 and IKEv1. [zia.traffic-forwarding.ipsec:mtu-mss] In the MTU calculation for GRE or IPSec tunnels, the IPSec tunnel header length is variable and can be up to 64 bytes; if the organization experiences issues performing the page's tasks, Zscaler recommends a tunnel MTU of 1400. [zia.traffic-forwarding.ipsec:header-length] The ESP overhead and effective payload MTU are open [gap:zia.traffic-forwarding.ipsec:esp-overhead-range], and whether missing MSS clamping fails more often than under GRE is open [gap:zia.traffic-forwarding.ipsec:failing-mss-symptom]. To forward IPv6 over IPSec the device needs IPv6 traffic selectors for both IKEv1 and IKEv2, and IPv6 support must be enabled for the organization and its locations. [zia.traffic-forwarding.ipsec:ipv6-selectors]

What to check:
1. Which IKE version the tunnel runs, and for IKEv1 which negotiation mode.
2. Whether the local ID matches the credential type.
3. Whether the site is under the 400 Mbps per public source IP limit.

Sources disagree (name both sides):
- Zscaler recommends DPD intervals of 10 to 20 seconds with at least 3 retries, but the device guides use values inside, below and above that range, and one uses on-demand DPD. [divergence:zia.traffic-forwarding.ipsec:dpd-device-guides]
  - zscaler-help: DPD intervals of 10 to 20 seconds with at least 3 retries; on-demand-only devices must allowlist the Zscaler IP address.
  - zscaler-help: The Cisco 881 ISR guide configures `crypto ikev2 dpd 10 5 periodic`: periodic DPD with an interval of 10 (inside the recommended range).
  - zscaler-help: The Juniper SRX guide sets interval 20 and threshold 5 (inside the recommended range).
  - zscaler-help: The Juniper SSG 20 guide enables DPD with an interval of 5 seconds (below 10).
  - zscaler-help: The Palo Alto Networks guide enables the liveness check with an interval of 5 (below 10).
  - zscaler-help: The SonicWall TZ 350 guide sets a DPD interval of 60 seconds with a failure trigger level of 3 (above 20).
  - zscaler-help: The FortiGate guide selects On Demand DPD.
  Impact: Copying a device guide can leave a device outside Zscaler's stated DPD expectation; under dpd, Zscaler cleans up a connection that gets no DPD response.
- The Juniper SRX guide sets IKE and IPSec proposal lifetimes of 3600 seconds, while the IKEv2 table lists SA lifetimes of 24 hours for Phase 1 and 8 hours for Phase 2, and the Cisco ASA guide says its 8-hour default equals Zscaler's recommended Phase 2 value. [divergence:zia.traffic-forwarding.ipsec:srx-sa-lifetimes]
  - zscaler-help: The Juniper SRX example sets both proposal lifetimes to 3600 seconds.
  - zscaler-help: The IKEv2 table lists an SA lifetime of 24 hours for Phase 1 and 8 hours for Phase 2.
  - zscaler-help: The Cisco ASA guide leaves its 8-hour default because it matches Zscaler's recommended Phase 2 value.
  Impact: Low: the table may give Zscaler's own lifetimes, which a shorter peer value negotiates under, but no page says whether 3600 seconds is acceptable.
- The NSS tunnel output format says Zscaler only supports ESP for the IPSec tunnel protocol, while the IKEv2 supported parameters table lists AH and ESP. [divergence:zia.traffic-forwarding.ipsec:ipsec-protocol]
  - zscaler-help: Zscaler only supports ESP.
  - zscaler-help: The IKEv2 table lists the protocol as AH ESP.
  Impact: Whether an AH tunnel is supported depends on which page is read; the pages do not say whether the table row lists supported or merely defined values.
