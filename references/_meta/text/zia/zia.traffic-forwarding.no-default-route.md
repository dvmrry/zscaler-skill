# ZIA in a no-default-route network: PAC options, tunnels and where the SLA stops (zia.traffic-forwarding.no-default-route)
Also called: no default route; no-default-route architecture; implementing zscaler without a default route; static routes to zscaler hub range

In a no-default-route architecture, although an individual client machine might have a default route configured, the edge router does not automatically forward all traffic upstream through the default route; it allows only specific devices to access the internet through static routes. Web browser traffic is explicitly sent to a proxy using a PAC file served through a local web server, through the proxy itself, or through Microsoft's Web Proxy Auto-Discovery (WPAD) protocol. [zia.traffic-forwarding.no-default-route:definition] Client Connector enrollment in these networks is in [Deploying Client Connector where the only egress is a proxy: the System PAC, spoofed DNS records and the four scenarios](kb:zcc.interoperability.no-default-route).

**Reaching the PAC files.** A web browser fetches PAC files over port 80, and Zscaler publishes the PAC IP addresses for a cloud as part of the Zscaler Hub IP address range (config.zscaler.com/<Zscaler Cloud Name>/hubs); the range can be used to define static routes and firewall rules that allow access to the PAC files, including the proxy port. [zia.traffic-forwarding.no-default-route:pac-fetch-port-and-ranges]

**Serving the PAC file locally.** PAC files can be served locally, but additional configurations are needed to provide dynamic failover and protect users outside the corporate network; the page highly recommends that the PAC file path resolve to the internal PAC file when inside the network and to the Zscaler PAC file server when outside. Zscaler does not recommend the internal PAC file only option for remote users because they are unprotected when using it. [zia.traffic-forwarding.no-default-route:local-pac]

**Where the SLA does not apply.** The article says the Zscaler SLA does not apply in these scenarios: dynamic failover is not possible because proxy addresses are hard-coded (including for the internally served PAC file); dynamic failover is not available through the use of the tunnels; and there are known issues with Microsoft caching DNS responses in violation of the TTL returned, though the SLA can be acceptable for server traffic. It adds that data center address ranges are subject to change. [zia.traffic-forwarding.no-default-route:sla-exclusions]

**PAC with tunnels.** In the Zscaler architecture a Public Service Edge processes traffic destined for any Service Edge in the cloud. PAC files can point to an internal IP address that is destination NATed to a Zscaler data center and forwarded over the configured GRE or IPSec tunnels, or can be hard-coded with a specific Global Public Service Edge IP address forwarded through the tunnel by policy-based routing; these Public Service Edge IP addresses are dummy addresses that every Public Service Edge is aware of and terminates the traffic for. [zia.traffic-forwarding.no-default-route:pac-and-tunnel] The Global Public Service Edge addresses are in [For explicit proxy mode over GRE in an environment with no default route, the tunnel is used with the Global Public Service Edge addresses 185.46.212.88 to .93, .97 and .98. These are dummy addresses that no Public Service Edge listens on but all know about, so traffic is routed to them through a GRE or IPSec tunnel and a PAC file directs users there.](kb:zia.traffic-forwarding.gre:explicit-via-global-edges).

**Servers and SOCKS.** Servers that cannot use PAC files can use special DNS names such as gateway.zscalertwo.net and secondary.gateway.zscalertwo.net, which resolve to available data centers based on the source IP address of the DNS resolver, and should also have static routes to allow access to the Zscaler data center ranges. Other protocols such as SOCKS, traditionally used in no-default-route architectures to send non-proxy-aware protocols via a proxy, should be handled differently; in many cases they can be sent directly to the internet or configured to use a standard proxy. [zia.traffic-forwarding.no-default-route:servers-and-socks]

What to check:
1. Before promising the Zscaler SLA in a no-default-route design, whether proxy addresses are hard-coded, explicit traffic goes through tunnels, or servers use the gateway DNS names (where the page cites Microsoft caching DNS responses beyond the TTL), and that the page also says data center address ranges are subject to change.
