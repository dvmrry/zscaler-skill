# Application service groups: predefined provider groups, custom groups, first-packet matching (zia.firewall.application-services)
Also called: application service group; application services; app service groups; Authoritative (AU); Custom (CU)

Zscaler provides predefined and custom application service groups for Firewall Filtering and Forwarding policies. They are defined by metadata (IP addresses, ports, protocols and domains) from the providers' published information, which Zscaler continuously updates and validates, and policies on them can allow, block or forward traffic. [zia.firewall.application-services:definition] The predefined application service groups are AWS, GCP, GoTo, Microsoft 365, RingCentral, Talkdesk, Webex, Zoom and Zscaler Cloud Endpoints. [zia.firewall.application-services:predefined-list] The suffix Authoritative (AU) marks a predefined application service and Custom (CU) a custom one, and the page lets an admin view details for read-only predefined application service groups. [zia.firewall.application-services:au-cu-suffix]

**Matching.** Application services are identified at the first packet, so the policy action can hit that first packet; the service assembles the first packet's metadata (domain and subdomains with destination IP addresses, protocol types and ports) to identify the application service. Policies using application services should therefore be in a higher priority rule than a similar policy using network applications. [zia.firewall.application-services:first-packet] Groups for cloud providers such as AWS and GCP identify traffic to those services and their subservices, and include all IP addresses for AWS- or GCP-based services. The general recommendation for Firewall Allow rules is a minimum of three conditions, with Application Service Groups as one of them. [zia.firewall.application-services:hyperscaler-broad] The application service criterion applies to web and non-web traffic: non-web traffic is matched by IP address, and web traffic by an FQDN match against the hostname in the HTTP/FTP header or the SNI for HTTPS. [zia.firewall.application-services:web-nonweb] To evaluate wildcard FQDNs against non-web traffic, Zscaler requires the IP address the FQDN resolves to, and the page says this functionality is included in the Advanced Firewall and DNS Control and Internet & SaaS editions. Wildcard FQDN matching against web traffic (HTTP and TLS/SNI) can function without meeting these conditions. [zia.firewall.application-services:wildcard-nonweb] What Zscaler Cloud Endpoints covers is open [gap:zia.firewall.application-services:cloud-endpoints].

**Custom groups.** Advanced Firewall is required for configuring custom application service groups. [zia.firewall.application-services:custom-licensing] An organization can configure up to 128 custom application service groups, each with at most 32 IP addresses or wildcard FQDNs, and 4,096 in total across the 128 groups. [zia.firewall.application-services:custom-caps] A custom definition takes IP addresses, wildcard FQDNs or both (for example 1.11.1.1, *.google.com). Addresses are IPv4 only, as an individual address, a subnet or an address range; IPv6 is currently not supported, and the same IP address or wildcard FQDN cannot be added twice in a group. [zia.firewall.application-services:custom-entries] A custom application service takes TCP destination ports, UDP destination ports, or both, each as a port number, a range or both (for example 25, 35-40 for TCP). [zia.firewall.application-services:ports] Whether the form has source-port fields is open [gap:zia.firewall.application-services:source-ports].
