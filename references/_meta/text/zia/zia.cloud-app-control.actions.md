# Cloud App Control actions and action discovery (zia.cloud-app-control.actions)
Also called: cac actions; granular actions; availableActions; allAvailableActions; zia_cloud_app_control_rule_actions; ALLOW_AI_ML_CHAT; cac custom eun; isolate actions cannot be mixed

**Console actions.** An AI & ML applications rule for Cloud App Control offers the console actions Allow, Caution, Block, Conditional and Isolate; Isolate is available only if Zero Trust Browser is enabled for the organization. [zia.cloud-app-control.actions:console-actions] Prerequisites for Isolate and Conditional are the same ones URL Filtering has: [URL Filtering actions and their prerequisites](kb:zia.url-filtering.actions).

**Action strings.** In the API the rule's `actions` field is a list of strings, not a single value, so one rule can carry several action strings. The Go SDK model and the Python model's request format use a list, and the provider's `actions` attribute is a set of strings. [zia.cloud-app-control.actions:actions-is-a-list] The provider documents the action prefixes ALLOW, DENY, BLOCK, CAUTION, ISOLATE and ESC (conditional access) for filtering actions, with examples ALLOW_AI_ML_CHAT, DENY_AI_ML_UPLOAD, BLOCK_FILE_SHARE_DOWNLOAD, CAUTION_AI_ML_WEB_USE and ISOLATE_AI_ML_WEB_USE; its example of an ESC action is AI_ML_CONDITIONAL_ACCESS. [zia.cloud-app-control.actions:action-string-shape] ISOLATE actions cannot be combined with other actions in one rule, and a rule using them needs a Cloud Browser Isolation profile (`cbiProfile`). [zia.cloud-app-control.actions:isolate-not-mixed]

**Finding the valid strings.** When several applications with granular controls are selected in one category, the console shows only the actions common to all of them. [zia.cloud-app-control.actions:common-actions-in-console] The Go SDK has two action-discovery calls, both taking a rule type and a request of `cloudApps` and `type` and returning a flat list of strings: `AvailableActions` (POST /{rule_type}/availableActions) and `AllAvailableActions` (POST /{rule_type}/allAvailableActions). The release notes describe the second as retrieving all available actions for each application type. [zia.cloud-app-control.actions:two-discovery-endpoints] The provider's rule-actions data source calls AllAvailableActions first and falls back to AvailableActions only when the error is a typed response with HTTP 404 or 405. Any other failure (any other status, or an error that is not a typed response) is returned to Terraform without a fallback. It applies a JMESPath filter to the actions, sets available_actions, splits ISOLATE_ actions from the rest, and applies the optional prefix filter. [zia.cloud-app-control.actions:provider-prefers-all-endpoint] The Python SDK exposes only the older availableActions call, and its request body carries `cloudApps` without a `type` key. It has no counterpart for allAvailableActions. [zia.cloud-app-control.actions:python-has-only-old-endpoint] At Go SDK v3.8.45 the exported `AllAvailableActions` posted to /{rule_type}/availableActions. From v3.8.46 the same exported name posts to /{rule_type}/allAvailableActions and `AvailableActions` holds the older /availableActions path, so a caller compiled against the earlier name selects a different endpoint after upgrading. [zia.cloud-app-control.actions:all-available-actions-reassigned] The captured Automate OpenAPI document describes POST /webApplicationRules/{rule_type}/availableActions ("Fetches the granular actions supported for the applications") and lists no allAvailableActions path. [zia.cloud-app-control.actions:automate-capture-availableactions-only] How the two endpoints differ is open [gap:zia.cloud-app-control.actions:all-vs-available-differs]. Provider issues #522 and #570 concern actions that can be used in a rule but that the `zia_cloud_app_control_rule_actions` data source does not return. In #522 the reporter wrote that the call was not returning all the actions that can be used in a specific Cloud App, and a MEMBER commenter confirmed that ALLOW_FILE_SHARE_UPLOAD and ALLOW_FILE_SHARE_VIEW are not returned by that endpoint, said an internal bug would be raised with the API team, and advised listing the actions manually in `actions` to stop the drift. In #570 the reporter quoted a note that some new actions may not be returned in the API response, and a MEMBER commenter called it an API issue under investigation, not addressable in the provider. Both issues were closed as completed; after #522 closed, a MEMBER replied there on 2026-08-13 to upgrade to v4.8.6, which "addresses the problem". [zia.cloud-app-control.actions:issue-522-actions-endpoint-omits-actions] What v4.8.6 changed is open [gap:zia.cloud-app-control.actions:actions-endpoint-fix-in-4-8-6], and so is what a multi-app request returns [gap:zia.cloud-app-control.actions:multi-app-aggregation]. Output-shape defects in the data source itself are in [What ZIA Terraform data sources return, drop, or get wrong](kb:zia.terraform.data-source-fidelity).

**Notifications.** The deployment guide states that Cloud App Control policies do not support custom End User Notifications. [zia.cloud-app-control.actions:no-custom-eun] A rule form still carries notification fields: a Browser Notification Template (which appears when the action is Caution or Block), an End User Notification Show/Hide choice (which appears when a granular action is blocked and is set to Show by default) and a Notification Message for the Zscaler Client Connector-based EUN. The rule model has `eunEnabled`, `eunTemplateId` and `browserEunTemplateId`. [zia.cloud-app-control.actions:rule-notification-fields] The two do not obviously agree [gap:zia.cloud-app-control.actions:custom-eun-meaning].

**Notification message wording.** Whether a rule's Client Connector notification message can be custom differs between sources [divergence:zia.cloud-app-control.actions:streaming-media-custom-message]. The Collaboration & Online Meetings, File Sharing, Social Networking, Streaming Media, System & Development and Webmail rule pages each carry a Client Connector End User Notification field, to show or hide the Client Connector-based EUN message, which appears when the granular action is blocked for the selected applications. [zia.cloud-app-control.actions:zcc-eun-granular-pages] What a user sees when a Login granular action is blocked on a page with no such field is open [gap:zia.cloud-app-control.actions:login-action-notification].

**Console actions across the category pages.** On the Consumer rule page, the Caution action can be selected for only one of the request methods CONNECT, GET or HEAD. [zia.cloud-app-control.actions:caution-one-method] On the Consumer rule page, Conditional Access allows access to the selected applications by enforcing step-up authentication, to an authentication level that must be configured in the Admin Console beforehand; Zscaler Client Connector shows a pop-up prompting the user to verify access. The option is available only if the organization is provisioned with the Authentication Service for end users and the traffic forwarding method is Client Connector. When traffic is routed via a Private Service Edge or Virtual Service Edge for Internet & SaaS, conditional access is not supported and user access is blocked with a notification from the browser; it does not apply to isolation traffic, and the page says to raise a provisioning support ticket to enable the feature. [zia.cloud-app-control.actions:conditional-step-up] On the Consumer rule page, the Isolation Profile field appears when Isolate is selected and lets the admin choose the isolation profiles to which the rule applies; the page says to ensure isolation profiles are created for the organization. [zia.cloud-app-control.actions:isolate-profile] The Isolate action is available only if Zero Trust Browser (formerly Isolation) is enabled for the organization and if the rule is not for DNS over HTTPS apps. The DNS Over HTTPS Services rule page's action descriptions include Allow, Block and Conditional. [zia.cloud-app-control.actions:isolate-not-doh] What the DNS Over HTTPS Services page leaves out is open [gap:zia.cloud-app-control.actions:doh-caution].

**Quotas.** On the Consumer rule page, the Allow, Caution, Conditional and Isolate actions each carry an optional Daily Bandwidth Quota (MB) and an optional Daily Time Quota (min). On the Allow action, the bandwidth quota counts data uploaded to and downloaded from the cloud application, from 10 MB to 100K MB. The Allow action's time quota is the time elapsed in a session while uploading and downloading data, ignoring idle time, from 15 to 600 minutes. The Allow action's page text says to enforce a quota on each location, select no specific users, groups or departments; to enforce it on specific users, groups or departments, SSL/TLS Inspection and authentication must be enabled. For a user from a known location the quota resets at midnight in the location's time zone, and for remote users it resets by the organization's time zone. [zia.cloud-app-control.actions:daily-quotas] A daily quota can be defined by bandwidth or time; when users browse the sites after their quota has been reached, the Zscaler service displays a message that explains that the content cannot be viewed because they exceeded their daily quota. [zia.cloud-app-control.actions:quota-exceeded] On the Collaboration & Online Meetings rule page, if a user exceeds the daily quota while in a web video conference over an SSL/TLS connection, the service allows the user to finish the meeting but blocks additional video conferences; if the conference is not over an SSL/TLS connection (HTTP), the service ends the connection immediately. [zia.cloud-app-control.actions:quota-video-conference] What a quota does on a rule that cautions, conditionally allows or isolates, and what it counts, is open [gap:zia.cloud-app-control.actions:quota-semantics].

**MCP workflow.** The per-category action vocabulary (for example IT_SERVICES, LEGAL, SALES_AND_MARKETING) is enumerated in the Python `add_rule` docstring; the Go model types `Actions` as a plain string list. The docstring lists `CAUTION_LEGAL_USE` under IT_SERVICES and `DENY_DNS_OVER_HTTPS_USE` under LEGAL. [zia.cloud-app-control.actions:python-docstring-action-vocabulary] The docstring entries `CAUTION_LEGAL_USE` under IT_SERVICES and `DENY_DNS_OVER_HTTPS_USE` under LEGAL look misfiled. [zia.cloud-app-control.actions:docstring-misfiled-entries] The MCP list-actions tool forwards `rule_type` and the optional `cloud_apps` list to the Python SDK `list_available_actions` and returns what comes back; it does no category-level probing. [zia.cloud-app-control.actions:mcp-actions-tool-forwards] The workflow skill does not reflect that [divergence:zia.cloud-app-control.actions:mcp-representative-app-probing]. The MCP create workflow skill says the create endpoint validates each `(rule_type, app, action)` tuple, that a multi-app create is frequently rejected with `INVALID_INPUT_ARGUMENT: "Invalid action provided for selected applications"`, that the first incompatible pair fails the entire create, and that one rule per app is the safe pattern. The executable create tool builds its payload with `build_rule_payload` and calls the SDK `add_rule`; it does no such validation. [zia.cloud-app-control.actions:mcp-skill-per-tuple-validation] Only that skill states the whole-create rejection, and the product contract is open [gap:zia.cloud-app-control.actions:per-tuple-validation-contract]. Whether discovery needs a category representative app is also open [gap:zia.cloud-app-control.actions:representative-app-actions].

2. For an exact answer about the actions one application offers, ask for one application at a time.
3. Whether a template set on a CAC rule is shown to users, which needs a test rather than a reading of the rule form.
