# What ZIA Terraform data sources return, drop, or get wrong (zia.terraform.data-source-fidelity)
Also called: zia data source returns nothing; zia data source fails to read; terraform data source panic zia; zia data source wrong object; data source missing attribute zia; data source returns first device; Invalid address to set zia; zia data source empty result no error; zia data source dropped field

A ZIA data source is supposed to be a faithful read-only view of an object. In the provider it is a hand-written pair of a schema and a flattener, fed by an SDK model, and the three drift apart in a few repeatable ways. When a data source gives a surprising answer, compare the schema, the flattener and the SDK model before suspecting the tenant (the write-side version of this is in [ZIA Terraform resource fields that are not sent, not read back, or sent wrongly](kb:zia.terraform.field-fidelity)).

## Reads that crash or fail

**Panicking reads.** In the sandbox report data source, each risk/signature entry declares `signature_sources` as a `TypeSet`, but the SDK field it is filled from is a single `string`, and the flattener assigns that string directly into the map handed to `d.Set`. [zia.terraform.data-source-fidelity:sandbox-rss-signature-sources-scalar-in-set] Writing a scalar string into a nested `TypeSet` through `d.Set` makes the Terraform plugin SDK panic on a failed type assertion instead of returning an error, so a sandbox report that has any spyware, networking, security-bypass, exploit, stealth or persistence entry can crash the provider process during the read. This applies only when `details = "full"`, the only branch that flattens the RSS. [zia.terraform.data-source-fidelity:sandbox-rss-scalar-set-panics] `required_count` in the GRE VIP recommendation data source has a default of 5 and no validation. After the SDK call the code compares the list length with it and slices `[:requiredCount]`, so a negative value always passes the comparison and reaches the slice expression. [zia.terraform.data-source-fidelity:gre-vip-negative-required-count-slices] A negative `required_count` makes that slice expression panic, crashing the provider during the read. [zia.terraform.data-source-fidelity:gre-vip-negative-count-panics]

**Undeclared keys.** In the DLP web rules data source, `excluded_groups`, `excluded_departments` and `excluded_users` declare only `id` and `extensions`. They are filled by the shared `flattenIDExtensions`, which always emits `id`, `name` and `extensions`, from SDK lists of `IDNameExtensions`. [zia.terraform.data-source-fidelity:dlp-web-excluded-lists-emit-undeclared-name] The forwarding control rule data source declares the ECZPA application segment description under the key `ddescription` while its flattener emits `description`. Separately, `ec_groups`, `locations` and `location_groups` declare only `id` and `name`, but those blocks are filled by `flattenIDNameExtensions`, which adds an `extensions` key whenever the SDK object carries a non-nil extensions map. [zia.terraform.data-source-fidelity:forwarding-control-segment-key-misspelled-and-extensions] The static IP data source declares `managed_by` with only `id` and `name`, but `flattenStaticManagedBy` always adds an `extensions` key, and the result goes to a checked `d.Set`. The SDK `ManagedBy` struct does carry an `Extensions` map. [zia.terraform.data-source-fidelity:static-ip-managed-by-emits-undeclared-extensions] The DLP dictionary, SSL inspection rule and Cloud App Control rule data sources each hand a checked `d.Set` a shape its schema does not declare. The DLP dictionary data source declares `primary_field` (an int) under `exact_data_match_details` but its flattener emits `primary_fields` carrying the SDK's `[]int`. SSL inspection `proxy_gateways` declares `id` as an int but its flattener returns one object whose `id` is a slice of ints. Cloud App Control `cbi_profile` is a `TypeList` but its flattener returns a single map, whose keys include `profile_seq`. [zia.terraform.data-source-fidelity:flatten-schema-shape-mismatch-elsewhere] The browser control data source declares `smart_isolation_profile_id` and `smart_isolation_profile` but no `smart_isolation_groups` or `smart_isolation_users`, and then calls `d.Set` on those two keys with checked errors. It never sets `smart_isolation_profile_id`, which the SDK model carries. [zia.terraform.data-source-fidelity:browser-control-data-source-sets-undeclared-keys] A checked `d.Set` that receives a key the schema does not declare returns an error, and these data sources return it as a diagnostic, so the whole read fails. Because the failing key is emitted per element, the data source fails only for responses that actually contain such an element (a populated excluded list, an ECZPA segment, a `managed_by` object, an EDM mapping, a CBI profile, a proxy gateway), and works on tenants whose objects are empty. The browser control data source is the exception to any data dependence: its two undeclared top-level keys fail whenever the API responds. [zia.terraform.data-source-fidelity:undeclared-key-write-errors] Whether real responses contain the objects that trigger these is open [gap:zia.terraform.data-source-fidelity:api-response-shape-for-flattener-failures].

**Endpoint resource group tag.** The DLP endpoint resource group tag data source declares its `id` as an integer, but when the result is not exactly one tag (as on an unfiltered channel read that returns several tags) it sets the resource ID to the channel name, for example `PRINTING`. [zia.terraform.data-source-fidelity:endpoint-tag-multi-result-id-not-numeric] When `id` is given, the same data source passes it to the SDK's `GetResourceGroupTag`, which requests `/dlpEndpointResource/{id}/groups` and whose doc comment (written under the name `GetResourceTags`) says it retrieves the tags to which the specified DLP resource is associated. The data source describes the value as a tag ID; the tag catalog is read by a different function from a different endpoint. [zia.terraform.data-source-fidelity:endpoint-tag-id-lookup-uses-association-endpoint]

## Selectors that do not select

**Ignored selectors.** The devices data source declares `hostname` and `device_group_type` as optional selectors, but its lookup branches test only ID, name, model, owner, OS type and OS version, and its "nothing was given" fallback tests only name, model, owner, OS type and OS version. A configuration that sets only `hostname` or only `device_group_type` therefore takes the fallback, lists the devices with `GetAllDevices` and binds to the first one. If that list is empty the read returns without setting an ID and without an error. [zia.terraform.data-source-fidelity:devices-unused-selectors-fall-back-to-first-device] The domain profiles data source declares the selector `profile_id`, but its read takes the integer from the key `id`, so `profile_id` is never consulted and an ID-only configuration reaches the not-found error. The selected profile's ID is never written back to `profile_id`. [zia.terraform.data-source-fidelity:domain-profiles-id-selector-never-read] The DC exclusions data source parses its string `id` with `strconv.Atoi` and treats a parse failure as if `id` had not been given. With no other selector the filter step is skipped and the full list is returned, so a mistyped ID widens the result to every exclusion. [zia.terraform.data-source-fidelity:dc-exclusions-invalid-id-selects-everything] The firewall filtering rule data source accepts `predefined_rule_count` and copies it into the SDK filter options, but the only SDK function that turns that option into a query parameter is the rule-count function, which the data source does not call. The list call it does make ignores the option. [zia.terraform.data-source-fidelity:predefined-rule-count-never-sent]

**Conflicting selectors.** The CASB email label and quarantine tombstone template data sources scan the list and stop at the first entry that matches the ID or matches the name. Nothing requires the two selectors to agree, so with both set the result is whichever matching entry comes first in the response. [zia.terraform.data-source-fidelity:id-and-name-first-match-wins]

**Filters built with GetOk.** The GRE VIP recommendation data source adds each boolean and coordinate filter, among them `within_country_only`, `latitude` and `longitude`, only when `d.GetOk` reports it set, and when `withinCountryOnly` is missing from the query the SDK sets it to `true`. [zia.terraform.data-source-fidelity:gre-vip-false-and-zero-filters-dropped] Because `GetOk` reports an explicit `false` or `0` as not set, `within_country_only = false` is never sent and the SDK then requests `true`, the opposite of the configured value; zero latitude or longitude is dropped the same way. [zia.terraform.data-source-fidelity:gre-vip-false-zero-inverted]

**GRE VIP source IP.** `source_ip` is optional on the GRE VIP recommendation data source; its read takes `sourceIP` from `source_ip` and, after the block that trims the list to the required count, calls `d.SetId(sourceIP)`. [zia.terraform.data-source-fidelity:gre-vip-empty-id-without-source-ip] So a configuration that omits `source_ip` finishes the read with an empty ID. [zia.terraform.data-source-fidelity:gre-vip-empty-id-when-source-ip-unset] Whether the SDK and Terraform accept an empty ID is open [gap:zia.terraform.data-source-fidelity:nonnumeric-or-empty-id-outcome].

**Name matching and required fields.** Six ZIA data sources look a name up with exact string equality over a fetched list, where the SDK's own by-name helper for the same object compares with `strings.EqualFold`: firewall time windows, rule labels, sub-clouds, UEBA alert definitions, departments and groups. A name that differs only in case is found by the SDK helper and not by the data source. [zia.terraform.data-source-fidelity:case-sensitive-name-lookups-diverge-from-sdk] The CASB DLP, CASB malware and Cloud App Control rule data sources declare `type` as optional (and computed for the CASB rules), and their read returns `type must be specified` when it is empty. A configuration that passes validation with only an ID or name fails at read time. [zia.terraform.data-source-fidelity:rule-type-optional-in-schema-required-at-read]

## Success-shaped empty and partial results

**Empty lookups.** The cloud applications data source treats an empty API response as an error, but applies its `app_name` filter after that check. A name that matches nothing leaves an empty `applications` list, an ID of the policy type, and no diagnostic. [zia.terraform.data-source-fidelity:cloud-applications-name-filter-empty-success] The datacenters data source and the name filter of the DC exclusions data source filter a fetched list and, when nothing matches, set a synthetic ID built from the filter (`name-%s`, `city-%s`, `id-%d`) and an empty list, with no not-found error. Only the ID filter of the DC exclusions data source errors on an empty result. [zia.terraform.data-source-fidelity:datacenter-lookups-no-match-succeed]

**Partial searches.** To look a category up by ID or name without an enum, the file type categories data source queries three enum scopes. A failure of any one scope is logged as a warning and skipped. If the category lives in the failed scope the result is a not-found error, and otherwise the lookup succeeds from the scopes that answered, with the failure shown only as a logged warning. [zia.terraform.data-source-fidelity:file-type-categories-swallow-enum-failure]

**Objects the API did not send.** Several data sources pass a value-typed (non-pointer) SDK sub-object to a flattener that always returns one block. The sandbox report wraps `Summary`, `Classification` and `FileProperties` unconditionally, and the SSL inspection rule flattens `Action` unconditionally, so a response that omits the object decodes to a zero value and is shown as a present block of empty values. At v4.8.3 the browser control data source did the same with the address of the value field `SmartIsolationProfile`, whose flattener returned a block for any non-nil profile. [zia.terraform.data-source-fidelity:value-structs-flattened-into-present-blocks] At v4.8.17 the browser control flattener returns no block when the profile has no ID, name or URL. [zia.terraform.data-source-fidelity:browser-control-pin-skips-empty-profile] At v4.8.17 the empty-block case described above (a response that omits the smart isolation profile shown as a present block of empty values) does not occur for the browser control data source. [zia.terraform.data-source-fidelity:browser-control-empty-block-fixed-at-v4-8-17]

## Fields declared but not returned

**Omitted criteria.** The SDK URL filtering rule model carries `sourceCountries`, `userRiskScoreLevels`, `httpHeaderProfiles` and `httpHeaderActionProfiles`. The URL filtering rules data source declares none of them and never sets them, although its documentation lists `source_countries` and `user_risk_score_levels`. A rule restricted by source country or user risk is returned without that restriction. [zia.terraform.data-source-fidelity:url-filtering-criteria-dropped] The SDK traffic capture rule model carries `srcIpv6Groups` and `destIpv6Groups`. The traffic capture rules data source declares and sets other criteria (it sets `source_countries`) but has no IPv6 group attributes, so a rule scoped by IPv6 address groups is returned without that scope. [zia.terraform.data-source-fidelity:traffic-capture-ipv6-groups-dropped] The SDK location model carries `dynamiclocationGroups`, `staticLocationGroups`, `virtualZenClusters` and `virtualZens`. The location management data source declares none of them and never sets them, although its documentation lists `virtual_zens` and `virtual_zen_clusters`. The links from a location to its location groups and Virtual Service Edges cannot be read through it. [zia.terraform.data-source-fidelity:location-association-arrays-dropped]

**Switched-off and unfillable fields.** The SSL inspection rules data source has its `access_control` attribute and the matching `d.Set` commented out, although the SDK model carries `accessControl`. [zia.terraform.data-source-fidelity:ssl-inspection-fields-switched-off-in-source] The SSL inspection, traffic capture and URL filtering rule data sources declare `workload_groups` with description, expression, expression JSON and audit fields, and fill it with `flattenWorkloadGroups`, which emits only `id` and `name` from the SDK's `IDName` list. The extra attributes cannot be populated. [zia.terraform.data-source-fidelity:workload-group-blocks-flattened-to-id-and-name] The receiver tenant block in the DLP web rules and CASB DLP rules data sources, and the `zscaler_app_tenant_id` block in the cloud-to-cloud incident receiver data source, declare a nested `external_id`. All three are filled by `flattenIDExtensionsList`, which emits only `id`, `name` and `extensions`, from an SDK type that has no external ID field. Those `external_id` attributes are always empty. [zia.terraform.data-source-fidelity:external-id-attributes-cannot-be-populated]

**Collection output.** The firewall filtering rule data source builds each element of its collection output with `flattenFirewallFilteringRuleToMap`, which omits `exclude_context_shield_end_point`, `is_eun_enabled`, `eun_template_id`, `end_point_applications` and `end_point_application_groups`, all of which its single-rule path sets. The same rule read by ID or name and read as part of the list therefore shows different content. [zia.terraform.data-source-fidelity:firewall-filtering-collection-mode-omits-fields]

**Other omissions.** Beyond the cases above, these data sources omit fields their SDK models carry, or declare attributes they never set: NAT control rules (`access_control`, `trusted_resolver_rule`); sandbox rules (`access_control`, `time_windows`, `device_groups`, `devices`, `default_rule`); firewall DNS rules (`access_control`, DNS gateway, ZPA IP group, EDNS ECS object, `is_eun_enabled`); firewall IPS rules (`access_control`); file type control rules (`password_protected`, browser EUN template ID); DLP EDM schema (`schema_status`); DLP web rules (`ocr_enabled`, `user_risk_score_levels`); Cloud App Control (`user_risk_score_levels`, and `device_trust_levels` declared but not set); CASB DLP rules (`redaction_profile` declared but not set); CASB email label (`label_desc`, `label_color`); devices (`hostname` never set); SSL inspection (`time_windows` declared but not set); browser control (`smart_isolation_profile_id` declared but not set); forwarding control rules (`devices`, `device_groups` declared but not set, `app_service_groups` omitted); GRE VIP list (`country_code`). (Forwarding control `devices` is declared but has no SDK field; the rest of the list is carried by the SDK models.) [zia.terraform.data-source-fidelity:declared-or-sdk-fields-never-populated]

Secrets exposed by data sources are in [How the Zscaler Terraform providers store, log, and send secrets](kb:shared.terraform.credential-handling); the resource-side counterparts of these fidelity gaps are in [ZIA Terraform resource fields that are not sent, not read back, or sent wrongly](kb:zia.terraform.field-fidelity), swallowed read errors in [When the ZIA Terraform provider reports success after an error, or crashes](kb:zia.terraform.error-handling), and the ZPA equivalents in [What ZPA Terraform data sources return, drop, or get wrong](kb:zpa.terraform.data-source-fidelity) and [Which object a ZPA Terraform data source actually returns](kb:zpa.terraform.data-source-selection).

What to check:
1. Whether the failing object has the shape that triggers a flattener failure, before concluding the data source is broken on every tenant.
2. Whether the two selectors given to a data source agree, since the first matching entry is returned.
3. Which policy criteria a rule read through a data source is missing, starting with the URL filtering, traffic capture and location data sources.
4. Whether an empty attribute is never set: search the data source file for its snake_case key, where one hit, in the schema, means it is never set.
