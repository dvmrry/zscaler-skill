# Installing the inspection root in applications that keep their own trust store, per tool (zia.ssl-inspection.app-trust-stores)
Also called: custom certificate application-specific trust store; pip certificate zscaler; npm cafile zscaler; java keytool zscaler root; git sslcainfo zscaler; docker zscaler certificate; firefox enterprise_roots; aws cli ca bundle zscaler

Some applications maintain a custom trust store instead of the default system trust store, so they cannot validate Zscaler-generated server certificates and the TLS connection fails; users then need to manually add the custom root CA to that store or disable server certificate validation. Administrators provide users with the applicable root CA certificate (Zscaler root CA or custom root CA), and if they need to deploy CA certificates for a large group of users, they use MDM solutions. [zia.ssl-inspection.app-trust-stores:why-and-remedy] Whether the root is already in the system store by default is stated differently across pages [divergence:zia.ssl-inspection.app-trust-stores:root-in-system-store].

**Languages and package tools.** Different Python modules or installers implement their own certificate stores separately. The page gives, for pip, `pip config set global.cert ~/ca_certs`; exporting SSL_CERT_FILE, SSL_CERT_DIR and REQUESTS_CA_BUNDLE; installing the pip-system-certs package, which patches pip and requests at runtime to use certificates from the default system store; and, as a listed option with a caveat, appending the Zscaler root to the certifi bundle with `cat ZscalerRootCA.pem >> $(python -m certifi)`, after which the page says a custom CA certificate cannot be added using the certifi package option and can only be overwritten when the certifi package is updated. Requests automatically searches for a valid certificate in the REQUESTS_CA_BUNDLE environment variable. [zia.ssl-inspection.app-trust-stores:python] For npm, whose commands the page says were tested and verified on version 10.2.5, `npm config set cafile <Path to Certificate>/ca-bundle.pem` points npm at a PEM bundle that must include both root and intermediate certificates; the page also says to set the NODE_EXTRA_CA_CERTS environment variable. [zia.ssl-inspection.app-trust-stores:npm] For Git, which the page says was tested and validated on version 2.34.1, `git config --global http.sslcainfo ~/ca_certs/custom-ca-bundle.pem` points Git at a PEM bundle. For Ruby, verified and tested on version 3.0.2p107, the page sets the SSL_CERT_FILE environment variable to the Zscaler root with the command [System.Environment]::SetEnvironmentVariable. [zia.ssl-inspection.app-trust-stores:git-ruby] For Composer (PHP) the page adds the Zscaler certificate to openssl.cafile in the INI file under the PHP folder, for example openssl.cafile="C:\ZscalerRootCertificate-2048-SHA256.crt", and says the command was tested and verified on PHP version 8.3.7 and Composer version 6.3.0. [zia.ssl-inspection.app-trust-stores:composer] For Java the page downloads the certificate bundle in DER format to the JAVA_HOME/bin directory using the keytool utility and imports it with `keytool -import -trustcacerts` into the cacerts keystore. A Gradle plugin is a Java app that runs from the JRE embedded in Android Studio, so the certificates go into the JRE local keystore, and in Android Studio 2024.1.1 Patch 1 or later the JRE directory might not be present and the JBR directory is used instead. For Salesforce Apex Data Loader the root is added in the JDK keystore, and IntelliJ IDEA provides its own storage for trusted certificates on Windows, Linux and Mac. [zia.ssl-inspection.app-trust-stores:java-keystores]

**Command-line and cloud tools.** For cURL the page adds `cacert=<Path to Certificate>/ZscalerRootCA.pem` to $HOME/.curlrc, passes `--cacert` on a curl command, or sets the CURL_CA_BUNDLE environment variable. For GNU Wget, which the page says was tested and verified on 1.20.3, it uses the `--ca-certificate=FILE` command or adds `ca_certificate` to $HOME/.wgetrc. [zia.ssl-inspection.app-trust-stores:curl-wget] For the AWS CLI the page runs `aws configure set default.ca_bundle` with a certificate in PEM format, and says Boto uses the AWS CLI config and the same environmental variables. For the Azure CLI it gives the certifi cacert.pem path for the 32-bit (x86) installation and the variable name REQUESTS_CA_BUNDLE. For the Google Cloud SDK it gives `gcloud config set core/custom_ca_certs_file`. [zia.ssl-inspection.app-trust-stores:cloud-clis] On Windows, macOS and Linux Docker uses the OpenSSL CA trust for its connections to download packages as a Dockerfile is processed; once the Dockerfile is loaded and processed, the containers make their connections, which need to trust the Zscaler certificate, so the container must have the Zscaler certificates installed. For a build in a development environment, the page locates OpenSSL and adds the Zscaler root certificate to the trusted root certificate store and updates it. [zia.ssl-inspection.app-trust-stores:docker]

**Operating system and browser stores.** The page gives three Linux locations for copying both root and intermediate certificates as individual PEM files: /etc/pki/ca-trust/source/anchors/, /usr/local/share/ca-certificates/ and /etc/pki/trust/anchors/. It gives the commands update-ca-trust and, after the /etc/pki/trust/anchors/ step, sudo update-ca-certificates. [zia.ssl-inspection.app-trust-stores:linux-system-stores] On macOS, which the page says was verified and tested on 14.4.1, the root is installed from the downloaded certificate file by opening it and clicking Install in the Keychain Access window. For OpenSSL the page passes `-CAfile` to openssl s_client, or saves a copy of the root named with its hash value and a .0 extension, because an application that meets a remote certificate checks for the cert.pem file or a file named after the certificate's hash value. For Rust, tested and verified on 1.75.0, and for Fastlane the page copies the root certificates into /usr/local/share/ca-certificates/. [zia.ssl-inspection.app-trust-stores:macos-openssl-rust-fastlane] For Microsoft Edge the page imports the Zscaler root certificate from the Trusted Root Certification Authorities tab. For Windows PowerShell, which the page says was tested and verified on version 5.1.19041.2673, it opens certmgr.msc from the Run command window and imports the root, which the page reports as imported to the Microsoft PowerShell directory. [zia.ssl-inspection.app-trust-stores:windows-store] For Firefox, which the page says was tested and verified on version 127.0.2, the profile includes a cert#.db file, where # is the version number of the .db file, and the page says to copy this file into the Firefox profiles of other users. Firefox running version 49 or later can be configured to use the Windows root certificate store to automatically import and install SSL/TLS root certificates by setting security.enterprise_roots.enabled, whose value is false by default, to true. [zia.ssl-inspection.app-trust-stores:firefox]

Which settings the page does not give is open [gap:zia.ssl-inspection.app-trust-stores:unverified-mechanisms]; the Ubuntu and Debian update step is printed as a different command [gap:zia.ssl-inspection.app-trust-stores:ubuntu-update-command]; what the page's certifi warning means is not stated [gap:zia.ssl-inspection.app-trust-stores:certifi-overwrite]. Why applications refuse the root, and what to do when no root can be installed, is in [SSL/TLS inspection certificates: who signs, and where the root must be trusted](kb:zia.ssl-inspection.certificates) and [What SSL/TLS inspection cannot inspect: pinned apps, client certs, QUIC, BYOD, IoT](kb:zia.ssl-inspection.uninspectable).

Sources disagree (name both sides):
- The trust-store page says the root and intermediate certificates are by default already in the end user's system certificate store; the choosing-CA page says the service does not install a root certificate on the user's machine, and the deployment guide says clients must have the root installed. [divergence:zia.ssl-inspection.app-trust-stores:root-in-system-store]
  - zscaler-help: By default the root and intermediate certificates are already in the end user's system certificate store.
  - zscaler-help: The service does not install a Zscaler or custom root certificate on the user's machine.
  - zscaler-help: With the default Zscaler intermediate certificate, all clients must have the Zscaler root certificate installed.
  Impact: Whether a machine already trusts the root without an administrator-driven install differs between the pages; the existing claim zia.ssl-inspection.certificates:root-must-be-trusted sits with the second and third positions, and the pages do not say what the first page's default refers to.
