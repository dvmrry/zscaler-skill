# Zscaler Incident Receiver: requirements per platform, storage, health check and VM commands (zia.dlp.incident-receiver)
Also called: zscaler incident receiver; dlp incident receiver; incident receiver vm; zirsvr; incident receiver ec2; incident receiver azure; incident receiver health check; incident receiver sftp; incident receiver mtls

The Zscaler Incident Receiver is a tool for receiving information about DLP policy violations securely. The Zscaler service sends the information to it via ICAP, and it can run on an AWS EC2 instance, an Azure VM or on-premises. [zia.dlp.incident-receiver:what-it-is] The Incident Receiver tool sends the policy-violating content and a JSON file with the metadata of the inline web and CASB DLP policy scan, for example the URL, collaborators, DLP dictionaries and DLP engines. [zia.dlp.incident-receiver:what-it-sends] Where it sits among the other places a DLP match can go is in [Where a DLP match goes: notification, ICAP, Incident Receiver and Cloud-to-Cloud](kb:zia.dlp.incident-forwarding).

**Storage.** The Incident Receiver does not store files locally. The About page says it requires an S3 storage bucket or a storage server, and the EC2 page says an S3 bucket or an SFTP server. [zia.dlp.incident-receiver:no-local-storage] On the on-premises deployment page, for each policy violation the storage server creates a directory containing the policy-violating file and a JSON file for the DLP policy scan metadata. The on-premises deployment page offers sample JSON files for Endpoint DLP, DLP with and without content inspection, Evaluate All Rules mode, and Data at Rest Scanning DLP. [zia.dlp.incident-receiver:storage-layout] The JSON metadata schema is open [gap:zia.dlp.incident-receiver:metadata-schema].

**The console object.** An Incident Receiver has a unique name, a URI, a status that shows whether it is enabled or disabled, and a certificate that can be downloaded. If it is set to Disabled, the Public Service Edge cannot send information to it. The page also offers adding a new client certificate. [zia.dlp.incident-receiver:object-fields] The Incident Receiver URI must follow the format icaps://<FQDN or IP address>:<port number>/. The field is prepopulated with icaps:// because Zscaler recommends secure ICAP, an FQDN or IP address is accepted, a port number must be included (the default is 1344, and changing it also needs the port configuration in the Incident Receiver updated to match), and the URI must end with a forward slash. [zia.dlp.incident-receiver:uri-format] On the on-premises VM, icaps_port is the Incident Receiver port number previously added to the receiver URI in the Admin Console, and a port changed on the VM requires the receiver's URI in the Admin Console to be updated to the new port. [zia.dlp.incident-receiver:port-must-match-vm] After the Incident Receiver is saved, its certificate is downloaded from the Zscaler Incident Receiver page or from the Edit window. If the URI is changed, the Incident Receiver VM must be updated, and if the certificate is regenerated, the VM must be updated with the new file. [zia.dlp.incident-receiver:certificate-lifecycle]

**On-premises VM.** The on-premises deployment page says a new or clean deployment of a Zscaler Incident Receiver requires a VM image running on Zscaler OS version 24. [zia.dlp.incident-receiver:os-version] An on-premises VM needs a hypervisor of VMware ESX/ESXi version 6.0 or later or Oracle VM VirtualBox, 4 CPUs, 8 GB RAM, a 600 GB disk and 1 virtual NIC. The image is an OVA downloaded from the Incident Receiver page, and the page lists f6793ec81fa7bcb3cd128ce37ced6fa9 as the official MD5 for /sc/adp/vm/adp_client.ova. [zia.dlp.incident-receiver:onprem-vm-spec] On-premises storage is either a server that supports SFTP/SCP and public key authentication, with a preconfigured account that has write access to the intended directory, or an Amazon S3 bucket. Zscaler recommends an SFTP storage server for on-premises Incident Receiver VMs, and to use S3 from an on-premises VM a /root/.aws/credentials file and a /home/zsroot/.aws/credentials file must be created manually on the VM with the aws_access_key_id and aws_secret_access_key. [zia.dlp.incident-receiver:onprem-storage] An on-premises Incident Receiver VM needs a static public IP address and a firewall rule allowing inbound ICAP messages from the FCC cloud to the correct TCP port (for example, port 1344), and a direct IP-based connection to the Zscaler Hub IP addresses must be allowed. [zia.dlp.incident-receiver:onprem-network]

**AWS EC2.** For AWS, the Incident Receiver AMI is requested from Zscaler Support for the customer's shared AWS account and region, and Support provides the shared AMI ID and description to use when launching the EC2 instance. [zia.dlp.incident-receiver:ec2-ami] The EC2 page requires a minimum t2.large or t3.large instance type with 8GB RAM, a security group allowing inbound ICAP messages from the FCC cloud to the correct TCP port (for example, port 1344), and an Incident Receiver already added in the Admin Console. A static public IP is optional but recommended, and the IP address can alternatively be associated with an FQDN used in the Admin Console. The AMI includes minimum specifications that can be increased. [zia.dlp.incident-receiver:ec2-spec] For S3 storage on EC2, the instance has list and write access (ListBucket and PutObject) to the S3 storage volume. With Zscaler Workflow Automation, two separate S3 buckets are created during the creation of the CloudFormation stack in AWS, and without it a single S3 bucket can hold data and JSON files or separate buckets can be used. [zia.dlp.incident-receiver:ec2-s3-iam] On the EC2 page, the addresses to allow are found on config.zscaler.com by selecting DLP Incident Receiver and clicking the Zscaler Hub IP Addresses link in the Source column, then copying IPs from the Required, Recommended and Combined columns as needed for the security group. [zia.dlp.incident-receiver:hub-ip-list] The capture of the EC2 page has headings with no body [gap:zia.dlp.incident-receiver:ec2-collapsed-steps].

**Azure VM.** For Azure, the Incident Receiver virtual hard disk (VHD) shared access signature (SAS) token must be obtained from Zscaler Support before deployment, and without it the Incident Receiver cannot be set up. [zia.dlp.incident-receiver:azure-sas-token] The Azure page requires a VM with a minimum of two CPUs and 8 GB of RAM (for example a D2as v4, and the steps select D2as_v4). Zscaler supports only Linux and only Generation 1 VMs for Azure instances. The steps select the Premium SSD (locally-redundant storage) storage type, a custom disk size of 500 GiB, Disable public and private access, and no public inbound ports. All resources for the Incident Receiver must use the region selected, and the VHD includes minimum specifications that can be increased. [zia.dlp.incident-receiver:azure-spec] The Azure page gives regional Zscaler storage URLs for the VHD: USA, Europe and Australia. [zia.dlp.incident-receiver:azure-vhd-sources] On Azure, a security group must allow inbound ICAP messages from the Feed Central Cloud (FCC) cloud to the correct TCP port on the Incident Receiver VM (for example, port 1344), and the inbound rule's destination port range is TCP port 1344. The Networking tab step says to ensure the Enable public access from all networks option is selected. [zia.dlp.incident-receiver:azure-network] The Azure page's prerequisite is access to a storage server that supports SFTP/SCP and public key authentication, and its steps specify that the Azure Incident Receiver uses SFTP storage. With Workflow Automation, the Filewatcher VM's information is used when configuring the SFTP storage. [zia.dlp.incident-receiver:azure-sftp-storage] On Azure, when a prompt to change the zsroot password appears in the serial console output, the Incident Receiver is ready to be configured. [zia.dlp.incident-receiver:azure-ready-signal] The Azure deployment page says the policy-violating files can be a maximum of 100 MB. [zia.dlp.incident-receiver:azure-evidence-file-max]

**Differences between the three pages.** The three deployment pages differ in what each states [gap:zia.dlp.incident-receiver:family-absences].

**On the VM.** On the on-premises VM, the first login is as user zsroot, whose initial root password is randomly generated, and the password is changed with the sudo zirsvr change-password command. [zia.dlp.incident-receiver:initial-login] On the on-premises VM, SFTP storage takes storage_sftp_fqdn (the storage server FQDN), storage_sftp_port (the upload port of the SFTP server), storage_dir (the storage server directory) and storage_sftp_username. The password is used temporarily and is not saved. If the SFTP server does not allow password-based authentication, an error says the service cannot update the public key on the server, and the contents of the file /.ssh/id_ed25519.pub are added to the end of /.ssh/authorized_keys on the SFTP server. [zia.dlp.incident-receiver:sftp-settings] On the on-premises VM, S3 setup asks whether the organization uses Zscaler Workflow Automation (y/n). It takes storage_s3_region_name, storage_s3_data_bucket_name and storage_s3_data_dir for data, and storage_s3_json_bucket_name and storage_s3_json_bucket_dir for the JSON files that contain incident details. [zia.dlp.incident-receiver:s3-settings] On the on-premises page, if the service was configured successfully it automatically downloads the latest build before it starts. If it was configured properly it installs the specified certificate and checks whether the service is configured correctly. [zia.dlp.incident-receiver:startup-and-update]

**Health check.** On the on-premises page the Incident Receiver Health Check is enabled by default and set to 5-minute intervals. A Health Status JSON file named <systmld>_<iphash>_ir_health_status_timestamp.json in the evidence folder verifies it, and disabling it requires contacting Zscaler Support. The page's example file has the keys ipAddress, version, updatedAt, systemId, lastIncidentReceivedAt, lastFileUploadSuccessAt, storageType, storageLocation and healthcheckIntervalInSec. The Azure page also sets the health check to 5 minute intervals. [zia.dlp.incident-receiver:health-check] What the health check notes and how a failure surfaces is open [gap:zia.dlp.incident-receiver:health-check-detail].

**Network modes and authentication.** On the on-premises page, in explicit proxy mode DNS and NTP connections are not tunneled, so an internal DNS server is needed. The Incident Receiver needs DNS resolution for the current Master CA IP address, the update server and the NTP server, and the host must resolve smcacluster.<cloudname>, update1.<cloudname>, update2.<cloudname> and zdistribute.<cloudname>. By default the VM has the FQDNs 0.freebsd.pool.ntp.org, 1.freebsd.pool.ntp.org and 2.freebsd.pool.ntp.org configured for NTP. Since the proxy configuration does not allow authentication, the proxy server must allow specific IP/MAC addresses without user and password authentication. [zia.dlp.incident-receiver:explicit-proxy] The command that sets the proxy differs between the pages [divergence:zia.dlp.incident-receiver:explicit-proxy-command]. On the on-premises page, mutual authentication for the Incident Receiver is optional and uses an MTLS CA Certificate provided by Zscaler for client authentication. It is enabled by setting icap_mtls_enabled to 1, and by default this parameter is disabled. [zia.dlp.incident-receiver:mtls]

**SFTP throughput.** On the on-premises page, multiple simultaneous SFTP connections can be allowed if SFTP upload is slower than expected or the Incident Receiver internal queue is full, whose logs are at /sc/log/zirsvr.log. The storage_sftp_conn_max parameter takes a value from 1-16 and is 1 by default, and the page advises thorough end-to-end testing before enabling it in production. If that does not stop the queue filling up, the SFTP server may need higher specifications or multiple Incident Receivers may need to be configured with load balancing. The Azure page also gives the range one to 16 and the default of 1. [zia.dlp.incident-receiver:sftp-connections]

**Maintenance.** On the on-premises page, an admin can allow Zscaler Support to log in to an Incident Receiver without opening a firewall connection for inbound traffic. The feature is disabled by default and must be enabled explicitly for the duration remote support assistance is required. sudo zirsvr support-access-start creates a long-lived SSH tunnel to the Zscaler cloud and sets up remote port forwarding, and sudo zirsvr support-access-stop and sudo zirsvr support-access-status stop it and check its status. [zia.dlp.incident-receiver:support-access] On the on-premises page, sudo zirsvr troubleshoot can warn that SFTP is configured with the older key type rsa, and sudo zirsvr update-sshkey then creates an SSH key with ED25519 in the file authorized_keys under /home/zsroot/.ssh and adjusts /sc/conf/sc.conf to use it. If the SFTP server does not support ssh-copy-id, a message says the operation was unsuccessful, and updating the public key then requires contacting Zscaler Support. [zia.dlp.incident-receiver:ssh-key-ed25519] On the on-premises page, an expired-certificate error is fixed by installing a new server certificate: create a certificate signing request with sudo zirsvr create-server-cert-csr, send it to a well-known CA for signing, install it with sudo zirsvr install-server-cert, and restart the Incident Receiver with sudo zirsvr restart. [zia.dlp.incident-receiver:expired-server-cert]

**Commands.** In the on-premises page's command table, sudo zirsvr update-now updates the service and requires the service to be stopped first, while sudo zirsvr force-update-now forces an update to the latest version regardless of the version on the VM and stops the service automatically before the update begins. [zia.dlp.incident-receiver:commands-update] In the on-premises page's command table, sudo zirsvr troubleshoot runs checks such as the installed certificate, the zcloud server configuration, all services and whether an update is needed, and sudo zirsvr collect-diagnostics creates a file with diagnostic information to send to Zscaler Support. [zia.dlp.incident-receiver:commands-diagnostics] In the on-premises page's command table, sudo zirsvr configure-syslog-server configures external syslog server forwarding of SFTP file events and critical changes to the configuration files the Incident Receiver monitors, and the forwarding happens over UDP port 514, which cannot be modified. The EC2 page's command table also lists sudo zirsvr configure-s3, which updates the S3 bucket the Incident Receiver uses. [zia.dlp.incident-receiver:syslog-forwarding] The meaning of the `flags` field on the receiver type is open [gap:zia.dlp.incident-receiver:flags-field].

What to check:
1. Which deployment page (on-premises, AWS EC2 or Azure) the receiver was built from before reading a specification or command off one of them, since the pages state different requirements.
2. Whether the console URI port and the port configured on the VM are the same value.

Sources disagree (name both sides):
- The on-premises page sets the explicit proxy with one command, while the EC2 and Azure pages use another. [divergence:zia.dlp.incident-receiver:explicit-proxy-command]
  - zscaler-help: The on-premises page runs sudo zirsvr configure-network for explicit proxy mode, and its command table does not list a configure-proxy command.
  - zscaler-help: The EC2 page runs sudo zirsvr configure-proxy.
  - zscaler-help: The Azure page runs sudo zirsvr configure-proxy.
  Impact: Which command sets an explicit proxy depends on which page is followed, and the on-premises command table does not list the EC2 and Azure command, so which platform accepts which command is unstated.
