# The ZIA provider's reorder registry: keys, locks and lifecycle across rule resources (zia.terraform.rule-order.registry)
Also called: reorderWithBeforeReorder; reorder registry; terraform apply hangs waitForReorder; concurrent map read and map write zia; traffic capture firewall_filtering_rules key; cloud app control rule type reorder; create retry lost order; staging order collision; stale reorder registry entry

Every ZIA rule resource that supports ordering hands its declared order to one shared, in-process registry and then blocks until a background worker says the order is applied. How the registry is keyed, who starts the worker, and when entries are marked done or removed decides whether an apply finishes, hangs, or finishes with a rule in the wrong place. This subject covers that shared machinery; how a single update is parked and put back, and why the worker cannot report failure, is in [How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order) and is not repeated here.

**Shared keys.** The provider keeps one package-level registry, `rules`, whose maps are keyed by the `resourceType` string the caller of `reorderWithBeforeReorder` passes in. A registration that finds no cycle running for its key starts the background reorder with its own `getCurrent` and `updateOrder` closures; a registration that finds the cycle still running only adds its rule to the registry. [zia.terraform.rule-order.registry:registry-key-is-a-string] So within one cycle, the getCurrent and updateOrder closures of every registration after the first are never called: the cycle reads and writes order through the first registration's closures only. [zia.terraform.rule-order.registry:later-closures-unused] From v4.8.15 the firewall filtering create runs the reorder closures on a context that the request's cancellation does not end, because other rules wait on the reorder. The changelog says shared ordering continues independently of the timeout of the individual rule that started it. [zia.terraform.rule-order.registry:reorder-runs-on-uncancellable-context]

**Traffic capture keys.** Up to v4.8.14, traffic capture create registers under the firewall-filtering registry key, `firewall_filtering_rules`, while its callbacks list and update traffic-capture rules. Traffic capture update registers under `traffic_capture_rules`, so one resource's create and update use different keys, and its create shares a key with a different resource. [zia.terraform.rule-order.registry:traffic-capture-create-uses-firewall-key] So up to v4.8.14 a traffic-capture create that runs while a firewall-filtering cycle is open joins that cycle: its rule is judged by the firewall callbacks, which never list it, and it is skipped. If it starts the cycle, the firewall rules registered afterwards are judged by traffic-capture callbacks. Either way the create can return without its order applied, and the entry stays in the shared registry. [zia.terraform.rule-order.registry:traffic-capture-joins-firewall-cycle] From v4.8.15 traffic capture create registers under `traffic_capture_rules`, the same key as its update, and the changelog says newly created traffic capture rules are ordered together with other traffic capture rules instead of with firewall filtering rules. [zia.terraform.rule-order.registry:traffic-capture-create-key-fixed-in-v4-8-15]

**Rule types under one key.** At v4.8.3 cloud app control create and update register every rule under the single key `cloud_app_control_rules` and keep one starting-order scalar, while the callbacks list and update rules through the endpoint scoped to the registering rule's `Type`. The first registration's type fixes which rules the cycle can see. [zia.terraform.rule-order.registry:cloud-app-control-one-key-for-all-types] From v4.8.7 the cloud app control registry key and starting-order seed are per rule type. The provider's own comment says the API orders rules independently per type. Up to v4.8.14 the seed is a map read after the lock is released (see starting-order-state-read-outside-lock). [zia.terraform.rule-order.registry:cloud-app-control-key-fixed-per-type-at-pin] SaaS Security DLP and malware rules still use one registry key and one starting-order scalar each (`casb_dlp_rules`, `casb_malware_rules`), while their callbacks and the SDK list and get functions are scoped by a `ruleType` query parameter taken from the registering rule. Not fixed as of v4.8.17. [zia.terraform.rule-order.registry:casb-rules-one-key-for-all-types] So when rules of two types are created or updated in one apply, a cycle keyed by a type-blind key lists only the first registrant's type. Rules of the other type are absent from that list, counted as skipped, and can finish without their order applied; the shared starting-order scalar also seeds one type's create from another type's highest order. [zia.terraform.rule-order.registry:mixed-subtype-cycle-skips-rules]

**Races.** At v4.8.3 the registration function releases the registry lock and only then reads the cycle's done channel from the shared `reorderDone` map. Concurrent registrations write that map under the lock; the v4.8.7 fix's comment says reading the map after Unlock races with them. [zia.terraform.rule-order.registry:done-channel-read-after-unlock] So at v4.8.3 that unsynchronized read can abort the provider with Go's fatal "concurrent map read and map write" error; it cannot return a different channel for the same key. [zia.terraform.rule-order.registry:done-channel-read-after-unlock-effect] From v4.8.7 the done channel is captured while the lock is still held, and the goroutine closes that captured channel. This closes the map race. [zia.terraform.rule-order.registry:done-channel-capture-fixed-in-v4-8-7] Up to v4.8.14 a registration decides whether to join a cycle with a non-blocking receive on the done channel under the registry lock. The channel is closed by the goroutine only after `reorderAll` has returned, and the worker's clean exit returns straight after a pass, without re-reading the registry under the lock. So a rule registered after the final pass took its registry snapshot, and before the channel closes, finds an open channel, starts no new worker, and is waited on by a cycle that never evaluated it. [zia.terraform.rule-order.registry:join-after-final-snapshot] From v4.8.15 each registration increments a per-key revision, and the worker records the revision it snapshotted. After `reorderAll` returns, the goroutine compares that revision with the registry under the lock and runs `reorderAll` again if a registration arrived, closing the done channel under the same lock only when the revision is unchanged. The v4.8.15 changelog says a rule registering during final verification is processed before waiting operations return. [zia.terraform.rule-order.registry:final-snapshot-window-closed-in-v4-8-15]

**Starting-order state.** Up to v4.8.14, in the DLP web, outbound email DLP and endpoint DLP sub-rule creates, the parent-keyed starting-order map is written while the rule lock is held and read into the create's `req.Order` after the lock is released; the per-type cloud app control seed follows the same pattern. [zia.terraform.rule-order.registry:starting-order-state-read-outside-lock] From v4.8.15 the DLP web, outbound email DLP, endpoint DLP sub-rule and cloud app control creates take the lock again to read the starting order into `req.Order`. The provider's guidance says the cached value is read under the lock too, because `-race` flags it otherwise. [zia.terraform.rule-order.registry:starting-order-read-under-lock-from-v4-8-15]

**Entries that never settle.** On each tick the worker sets `allDone` to false if any entry registered under its key is not done, and when `!(allDone && size > 0)` it unlocks and runs `continue` before calling `getCurrent`. A waiter receives from the key's done channel, which the goroutine closes only after `reorderAll` returns. [zia.terraform.rule-order.registry:worker-waits-forever-on-undone-entry] That `continue` comes before every counter and every give-up check, so one entry that is never marked done keeps the cycle running with no exit, and every waiter on that key's channel blocks with it. [zia.terraform.rule-order.registry:undone-entry-blocks-cycle] In bandwidth control create the rule is registered with the reorder engine first, then the resource is read, and `markOrderRuleAsDone` runs only after that read succeeds. If the read keeps failing until the create timeout, the function returns the read diagnostics and the registration stays not done. [zia.terraform.rule-order.registry:create-registers-before-read-then-marks] The same register, read, then mark order is in seven create paths: bandwidth control, CASB DLP, CASB malware, DLP web, endpoint DLP rules, NAT control and outbound email DLP. Each retries or returns on a failed read before it can mark the entry done. The other rule resources mark done immediately after registering. [zia.terraform.rule-order.registry:create-registers-before-read-sites] So a create that fails its post-POST read leaves a registration that is never done. The next create or update of the same resource type, in the same provider process, registers into the still-open cycle, marks itself done, and blocks in `waitForReorder` on a cycle whose worker can never proceed. The re-POST on a failed read (see the error-handling subject) adds a further registration for each new ID. A failed read followed by a successful retry also hangs: the retry re-POSTs and registers a new ID under the same key while the first stays undone, so the create's own wait blocks. [zia.terraform.rule-order.registry:undone-entry-hangs-later-waiters]

**Entries that are never removed.** Registry entries are added on every create or update and never removed: not when a cycle finishes, not when the rule is deleted. A rule destroyed or replaced later in the same provider process stays registered under its key. [zia.terraform.rule-order.registry:registry-entries-are-never-removed] The worker counts a registered rule that is absent from the freshly listed rules as skipped, every pass. A skipped rule blocks the clean-pass exit. [zia.terraform.rule-order.registry:registered-rule-missing-from-list-is-skipped] So a stale entry for a deleted rule makes every later cycle under that key count at least one skipped rule: it can never reach the clean exit, and ends through a skipped-rule give-up path, which returns without an error. [zia.terraform.rule-order.registry:deleted-rules-skew-later-cycles]

**Create-time order allocation.** NAT control and URL filtering create seed the staging order with the highest order already in the policy and post the rule at that order, not one past it. In URL filtering at v4.8.14 the seed is the order `endOfList` returns for the listed rules: the largest order, or 1 for an empty list. [zia.terraform.rule-order.registry:staging-order-is-occupied-maximum] Through v4.8.14: up to v4.8.13 the staging seed was a package-level scalar set once per provider process and never changed by a create. Every later create of that resource in the process posted the same order; no resource reserves the next slot. Firewall filtering and traffic capture add one when they first compute the seed, and also never advance it. At v4.8.14 that still holds for a create the API accepts; in firewall filtering, a create the API rejects with `not allowed at order` clears the scalar and reads it again before retrying, at most three times. [zia.terraform.rule-order.registry:staging-order-never-reserved] From v4.8.15 NAT control, URL filtering and traffic capture advance the cached starting order by one under its lock after a create. The bandwidth control create carries the comment that the next rule of this type is created after this one, at the end of the list, so creating it does not move the rules already placed. [zia.terraform.rule-order.registry:staging-order-advances-after-create] From v4.8.15 firewall filtering create holds its lock while it chooses the append position, POSTs and advances the position, so parallel creates cannot reuse a position. The v4.8.15 changelog says concurrent firewall filtering creates no longer reuse the same insertion position. [zia.terraform.rule-order.registry:firewall-filtering-create-position-is-atomic] Through v4.8.14, concurrent creates could therefore post the same order, and the first create posts an order that an existing rule already holds. Where each lands depends on the API. [zia.terraform.rule-order.registry:staging-order-collision-effect] In bandwidth control create the intended order is read from the request inside the retry loop, after the previous pass already replaced `req.Order` with the staging value. After an `INVALID_INPUT_ARGUMENT` retry, the order handed to the reorder engine is the staging order, not the one in the configuration. Cloud app control does the same for both order and rank: after the first pass `req.Rank` is 7, so the retry records 7 as the intended rank. For cloud app control the rank is lost only when the declared rank is below 7. From v4.8.14 a rejection of the staging order as `not allowed at order` is handled before that retry: bandwidth control and cloud app control clear the cached staging order and restore the intended order (and, for cloud app control, rank) before continuing, at most three times, so the intended values survive that retry. [zia.terraform.rule-order.registry:create-retry-loses-declared-order] The same capture-inside-the-loop shape, with a `continue` after it, is in 14 create paths: bandwidth control, CASB DLP, CASB malware, cloud app control, DLP web, endpoint DLP rules and sub-rules, firewall DNS, firewall IPS, forwarding control, NAT control, outbound email DLP, sandbox and URL filtering. The retry is taken on `INVALID_INPUT_ARGUMENT` in all 14, and also on a failed post-POST read in the 7 with an in-loop Read. [zia.terraform.rule-order.registry:create-retry-loses-declared-order-sites] The failed-read retry that triggers it is described in [When the ZIA Terraform provider reports success after an error, or crashes](kb:zia.terraform.error-handling), as is create order taken from an ignored list error.

**Rank mismatch.** The worker treats a rule as in place only when order and rank both match, but the bandwidth control and CASB DLP update callbacks return without a write whenever the order matches, and never assign the rank when they do write. The worker counts a callback that returns nil as an issued PUT. [zia.terraform.rule-order.registry:rank-comparison-without-rank-write] So when a registered bandwidth control or CASB DLP rule is at its declared order but not its declared rank, the worker reports a PUT each pass, no write happens, and the rank is never corrected. The pass is never clean; with the v4.8.3 worker nothing ends the cycle, and from v4.8.7 only the oscillation breaker does, abandoning the cycle with a WARN log and no error. [zia.terraform.rule-order.registry:rank-mismatch-never-repaired]

**The bounded exit.** The v4.8.7 oscillation breaker counts a pass only when it issued PUTs, did not improve the at-target count, and had no skipped rules and no PUT errors. Any PUT still counts as progress for the no-progress counter, and for the skipped-rule give-up. The count applies only while the registration count is unchanged. [zia.terraform.rule-order.registry:oscillation-breaker-guard] The breaker's threshold and what it does when it trips: The reorder helper stops after six consecutive non-improving passes (`maxNonImprovingPutTicks = 6`), meaning passes that issue PUTs without improving the best at-target count and have no skipped rules and no PUT errors; a change in the number of registered rules, a skip or a PUT error resets the count. At six it logs the contested rules and returns so the apply can complete; the provider comment says that without the breaker the cycle livelocks until Terraform's own context deadline. [zia.terraform.rule-order.registry:oscillation-breaker-six-passes] So a cycle with one permanently skipped rule and another rule whose PUT succeeds but does not converge has no exit: the breaker needs no skipped rules, the no-progress counter resets on every PUT, the skipped give-up needs a pass with no PUT, and a clean pass needs no skipped rules. At v4.8.3 there is no breaker, and the same mixed state also never ends. [zia.terraform.rule-order.registry:mixed-skip-write-path-is-unbounded]

What to check:
1. Whether an earlier create of the same resource type failed its post-POST read, when an apply hangs or a rule lands in the wrong place.
2. Whether the resource shares a registry key with a different resource or rule type, since the callbacks then judge rules they cannot list.
3. Which resource type registered first under a shared key, when a rule of another type does not take its order in a mixed apply.
4. Whether a rule deleted earlier in the run is still registered under its key.
5. Whether the rule's rank differs from its declared rank, which the worker reports on every pass without repairing.
6. Whether a create that posts at the staging order collides with an existing rule's order.
7. Whether the policy's order and rank match the declared values after an apply: re-read every rule in the policy rather than trusting the apply result.
