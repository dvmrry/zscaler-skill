# Transparent proxy mode: how the host is found from SNI or certificate (zia.proxy-mode.transparent)
Also called: transparent proxy; sni; server name indication; client hello; transparent mode; server certificate fallback

In transparent mode the client does not know a proxy exists. In transparent mode the browser has no proxy configured; traffic is directed to a Service Edge by other means, such as a GRE or IPSec tunnel at the organization's egress router, so the destination IP in the IP header is the origin server's address. [zia.proxy-mode.transparent:how-it-works]

**Finding the host.** The Service Edge identifies the destination host from the Server Name Indication extension in the TLS Client Hello when present, and otherwise from the server certificate sent during the SSL handshake. [zia.proxy-mode.transparent:host-identification] Most browsers send SNI when a server uses one certificate for several sites; for example, with a common *.google.com certificate the service can block drive.google.com while allowing mail.google.com and google.com. [zia.proxy-mode.transparent:sni-example] The certificate fallback can only happen after the server has answered during the handshake, which is later than a CONNECT host or a Client Hello SNI. [zia.proxy-mode.transparent:certificate-comes-later] Whether a client can declare a different SNI to bypass policy is open [gap:zia.proxy-mode.transparent:sni-spoofing]. Whether the certificate fallback adds a round trip before the first decision is open [gap:zia.proxy-mode.transparent:first-decision-latency].

**What changes for policy.** Domain-based policy runs on the SNI before decryption: [Where SSL inspection sits in ZIA web policy evaluation (the two passes)](kb:zia.ssl-inspection.pipeline). SSL inspection exemptions also evaluate the IP address in this mode: [Under transparent forwarding, SSL inspection exemption policies are evaluated on the IP address as well as the SNI, and most IP addresses are categorized Miscellaneous or Unknown, so exempting that category exempts almost all traffic. Under explicit forwarding only the SNI is evaluated.](kb:zia.ssl-inspection.pipeline:transparent-matches-destination-ip); the IP-group criterion is in [SSL/TLS inspection rule criteria and the ones that silently don't match](kb:zia.ssl-inspection.criteria).

**Identity and protocols.** The client cannot answer a proxy 407, so user identity comes from Surrogate IP or Client Connector and otherwise from the location: [Surrogate IP: mapping a private IP to an authenticated user](kb:zia.authentication.surrogate-ip), [What happens to traffic with no user identity](kb:zia.authentication.unauthenticated-traffic). Tunnels carry all ports and protocols ([Forwarding methods Zscaler supports and how to choose](kb:zia.traffic-forwarding.methods)); IPv6 over IPSec needs explicit configuration ([IPSec tunnels to ZIA: limits, IKE and device settings](kb:zia.traffic-forwarding.ipsec)). What the router needs for GRE and IPSec is in [GRE tunnels to ZIA: requirements, bandwidth and deployment](kb:zia.traffic-forwarding.gre) and [VPN credentials for IPSec: types, immutability and keys](kb:zia.traffic-forwarding.vpn-credentials).

What to check:
1. Whether the client sends SNI, which a capture of the Client Hello shows, since the host is taken from SNI when it is present.
2. Whether an SSL inspection exemption's outcome depends on the IP address, since in this mode exemption policies are evaluated on the IP address as well as the SNI.
