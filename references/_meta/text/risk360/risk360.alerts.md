# Risk360 alerts: rule criteria and throttling, alert lifecycle, causes, webhooks, email and the ServiceNow sample (risk360.alerts)
Also called: risk360 alert rules; risk360 ongoing alerts; risk360 alert history; risk360 webhooks

Alert rules can be configured for financial loss or risk score changes at organization, category, factor group or factor levels, and trigger an email or webhook notification. [risk360.alerts:rule-subjects] An alert rule's criteria choose All or Any, an item from Org, Category, Factor Group or Factor, and an operator from =, >, <, ≥, ≤, increases by or decreases by. [risk360.alerts:rule-criteria] Minimum Throttling Criteria is the number of days the criteria must persist before the alert notification is triggered. [risk360.alerts:throttling] An alert rule can start from an existing rule template or from Create New; a template skips the wizard to the Configure Delivery Method step, and its predefined values can be edited via Back. [risk360.alerts:rule-templates] A rule's severity is Critical, High, Medium or Low, its status Enabled or Disabled, and its delivery method Email and/or Webhook; the custom message applies to both email and webhooks. [risk360.alerts:rule-delivery]

**Lifecycle.** An alert rule's alert becomes ongoing, and is shown on the Ongoing Alerts tab, when the rule's criteria are satisfied for the throttling period defined in the rule; when the criteria are no longer satisfied the alert stops and is listed on the Alert History tab. [risk360.alerts:lifecycle] The Ongoing Alerts and Alert History tabs can be filtered for the last 1 day, 2, 5, 7, or 14 days. [risk360.alerts:time-window-filter] The About Alerts page says users receive a daily alert notification as long as the alert criteria are true, and words the end of that as "until the alert rule is not modified, disabled, deleted, or muted". [risk360.alerts:daily-notification] Disabling an alert rule stops the alerting engine evaluating its criteria while the rule stays configured; muting an ongoing alert stops notifications but not evaluation, and the alert stays trackable on the Ongoing Alerts tab; deleting an alert removes the rule from the Alert Rules page. [risk360.alerts:disable-mute-delete] The Alert Rules tab offers a way to mute or unmute notifications from an alert rule; the page describes this as ensuring the rule is enabled but no notification is initiated when the alert is triggered. [risk360.alerts:mute-semantics] In an alert notification, Started On shows when the alert started and Ended On shows Ongoing while the alert persists; when the alert ends, users receive a further notification whose Ended On shows the end date and time. [risk360.alerts:ended-on]

**Cause.** The Ongoing Alerts and Alert History tabs each say an alert's cause is due to risk score or financial loss changes at one level below the defined alert criteria, and that if the criteria is defined at the organization level the cause is due to changes in the 4 attack stages. [risk360.alerts:cause-level] The cause when the criteria sit at the organization level is not fully described [gap:risk360.alerts:org-level-cause]. For a composite rule with criteria at different levels, the alerting engine breaks the rule into each element and derives the cause for each element separately; for a rule with Org-level and factor group elements the causes are changes at the 4 attack stages and in the factors under the factor group. [risk360.alerts:composite-cause] In an alert's Cause, the change in risk score or potential loss at each level over the last 24 hours is colored red for an increase, green for a decrease and gray for no change. [risk360.alerts:cause-colors]

**Email.** The alert email shows the rule name, severity, criteria (highlighted when one or more criteria are met), Started On, Ended On (Ongoing if not ended), cause and the custom message. [risk360.alerts:email-fields]

**Webhooks.** A webhook's authentication type is Basic (username and password) or Token (a bearer token), and the webhook provider determines which is used. [risk360.alerts:webhook-auth] Several alert rules can be assigned to the same webhook, and a webhook's URL must not include spaces. [risk360.alerts:webhook-shared-url] The webhook configuration page says the Alert Status field on the Webhooks page displays Active if the webhook is configured successfully and Error if not, and to resolve the error check the URL and Authentication Type fields. [risk360.alerts:webhook-status-save] The Webhooks tab lists each integration's name, URL, authentication type (Basic or Token) and authentication status (Active, Error or In Progress). [risk360.alerts:webhook-list] Which field carries the Active and Error values differs between the pages [divergence:risk360.alerts:webhook-status-field], and the payload schema is documented only through the sample script [gap:risk360.alerts:webhook-payload].

**ServiceNow sample.** Zscaler's ServiceNow webhook configuration guide builds its sample on a ServiceNow developer instance, which automatically hibernates (wake every 24 hours) and is reclaimed if unused for 10 days. [risk360.alerts:servicenow-instance] In the ServiceNow sample, Basic authentication needs a non-admin ServiceNow user so admin credentials are not shared, and Token authentication needs the script's token edited to match the bearer token in the webhook configuration. [risk360.alerts:servicenow-auth] In the ServiceNow sample, the webhook URL is the ServiceNow instance hostname concatenated with the API name from the Scripted REST APIs page; each triggered alert then creates an entry in the ServiceNow Incident table. [risk360.alerts:servicenow-url] The ServiceNow sample Basic-authentication script reads these properties from the decoded webhook request body: alertId, ruleName, status, url, startTime, endTime, criteriaString, severity, alert_causes and custom_msg. [risk360.alerts:servicenow-payload-fields] In the ServiceNow sample Basic-authentication script, each alert_causes entry is branched on its type value: Org, Category, FactorGroup or Factor. [risk360.alerts:servicenow-cause-types] In the ServiceNow sample Basic-authentication script, alert status STARTED or ONGOING sets incident state 2 (in progress) and ENDED_ON_RULE_DEL or ENDED_ON_RULE_MODIFY sets state 8 (cancelled); the script also uses state 6 (resolved) and state 1 (new). [risk360.alerts:servicenow-status-mapping] The ServiceNow sample Basic-authentication script starts with impact 1 and tests severity High or Critical, then Medium, then Low, and contains impact = 2 and impact = 3 assignments. [risk360.alerts:servicenow-impact] The ServiceNow sample Basic-authentication script tests whether ruleName equals test (ignoring case), in a branch commented as a test webhook. [risk360.alerts:servicenow-test-webhook]

Throttling units, recipient limits and rule-count limits are not stated [gap:risk360.alerts:throttling-limits].

What to check:
1. Whether the rule's criteria have persisted for the Minimum Throttling Criteria number of days before expecting the first alert notification, and whether the rule is Enabled and not muted.
2. Whether the webhook's URL has no spaces and its Authentication Type (Basic or Token) matches what the webhook provider uses, when the webhook shows Error.

Sources disagree (name both sides):
- The webhook configuration page and the About Alerts page disagree on which Webhooks-page field shows Active and Error. [divergence:risk360.alerts:webhook-status-field]
  - zscaler-help: The Alert Status field on the Webhooks page displays Active or Error.
  - zscaler-help: Alert Status is whether the alert is enabled or disabled; Active, Error or In Progress belong to Authentication Status.
  Impact: Which column to read for a webhook error depends on the page; check both Alert Status and Authentication Status on the tenant.
