# Cloud Connector on Azure: internal load balancer, health probe and Gateway Load Balancer (cloud-connector.azure.load-balancing)
Also called: azure cloud connector ilb; azure cloud connector load balancer; cchealth; cloud connector health probe azure; http_probe_port; probe_threshold; azure gateway load balancer cloud connector; azure gwlb cloud connector; azure public load balancer cloud connector; terraform-zscc-lb-azure; terraform-zscc-gwlb-azure; terraform-zscc-public-lb-azure; cloud connectors per availability zone

Workload traffic reaches Azure Cloud Connectors through an internal Standard load balancer that health-probes each connector; newer reference modules add a Gateway Load Balancer path for inbound inspection. The values below are the reference module's defaults.

**The probe Cloud Connector answers.** The probe contract (the ?cchealth path, 200 for healthy, 503 or silence for unhealthy) is in [Cloud Connector listens on the configured port for HTTP health probes on a path the help capture renders as `?cchealth`.](kb:cloud-connector.overview.load-balancing:cchealth-path) and [A healthy Cloud Connector answers the probe with HTTP 200; an unhealthy one answers 503 or does not answer.](kb:cloud-connector.overview.load-balancing:health-codes); what happens to sessions on a connector that turns unhealthy is [New sessions should go to healthy Cloud Connectors, but existing connections through a Cloud Connector that becomes unhealthy might temporarily fail until the flow ages or times out and the load balancer sends the session through a healthy one.](kb:cloud-connector.overview.load-balancing:unhealthy-sessions).

**Reference internal load balancer.** The load balancer module creates a Standard SKU internal load balancer whose frontend takes a dynamic private IP in `var.subnet_id` and, when `zones_enabled` is true and the region is in the module's list of zone-supporting regions, is zone-redundant across zones 1, 2 and 3 unless a single zone is specified. [cloud-connector.azure.load-balancing:ilb-standard] The module's probe is HTTP on `http_probe_port` (default 50000, valid values 80 or 1024-65535) with request path /?cchealth, an interval of 15 seconds by default (minimum 5), `probe_threshold` 2 and `number_of_probes` 1. [cloud-connector.azure.load-balancing:ilb-probe] As the module describes them, `probe_threshold` is the number of consecutive failed probes that takes an endpoint out of rotation and the same number of consecutive successful probes needed to put it back, while `number_of_probes` is the number of unanswered probes that stops traffic to the endpoint. [cloud-connector.azure.load-balancing:probe-threshold-meaning] The load-balancing rule uses protocol All with frontend and backend port 0 and floating IP enabled; `load_distribution` defaults to Default and accepts SourceIP, SourceIPProtocol or Default. [cloud-connector.azure.load-balancing:ilb-rule]

**Changing the defaults.** Help's 15-second Azure default and its advice to involve Support before changing it are [Zscaler deployment templates use a recommended default health-check interval: 15 seconds on the Azure Load Balancer and 30 seconds on the AWS Gateway Load Balancer. The defaults are meant to take unhealthy Cloud Connectors out of rotation efficiently.](kb:cloud-connector.overview.load-balancing:probe-intervals) and [The default deployment templates are configurable, but Zscaler says to contact Zscaler Support before changing any settings.](kb:cloud-connector.overview.load-balancing:change-via-support).

**Marketplace deployment.** In the Azure Marketplace deployment, opting out of a load balancer is meant only for non-production environments, the HTTP probe port is 80 or 1024 to 65535 and must match an existing load balancer's, and connectors go into availability sets or availability zones. [cloud-connector.azure.load-balancing:marketplace-lb-settings]

**Availability zones.** The two-per-zone recommendation is [Zscaler recommends at least two Cloud Connectors per availability zone, across at least two availability zones.](kb:cloud-connector.overview.load-balancing:az-recommendation). One NAT gateway per zone is in [Cloud Connector on Azure: NICs, subnets, NSGs, NAT and routing](kb:cloud-connector.azure.network); one scale set per zone is in [Cloud Connector on Azure: VMSS autoscaling, health monitoring and resource sync](kb:cloud-connector.azure.vmss).

## Gateway Load Balancer and Public Load Balancer

The module changelog describes Azure Gateway Load Balancer support as enabling transparent inline inspection of ingress traffic, which the existing egress-only Private LB topology cannot do, and adds greenfield and brownfield GWLB examples and Public LB examples. [cloud-connector.azure.load-balancing:gwlb-purpose] The GWLB module creates a Gateway SKU load balancer with a private frontend, a backend pool with internal and external VXLAN tunnel interfaces, an HTTP probe on /?cchealth and a rule, intended to be chained to a consumer Public Load Balancer whose inbound traffic is VXLAN-encapsulated through the Cloud Connectors before returning to its destination. [cloud-connector.azure.load-balancing:gwlb-module] The Public Load Balancer module serves inbound DNAT (the fwd ZIA feature) either standalone, distributing to Cloud Connector NICs or scale-set instances, or as a consumer chained to the GWLB when `gateway_load_balancer_frontend_ip_configuration_id` is set; its rules enable floating IP, which DNAT for fwd ZIA requires. [cloud-connector.azure.load-balancing:public-lb-modes] Bringing a pre-existing GWLB (or Private LB) is out of scope for the load-balancer modules; an operator with an existing GWLB wires the Cloud Connector NIC to backend-pool association outside the module. [cloud-connector.azure.load-balancing:gwlb-byo-out-of-scope] The examples that use these modules, and their FIPS gap, are in [Zscaler's Azure Terraform package for Cloud Connector: image, VM sizes, provider constraint, examples and FIPS](kb:cloud-connector.azure.terraform-modules).

What to check:
1. Whether the load balancer probe targets the same HTTP port the connectors were provisioned with, on the /?cchealth path.
2. How many consecutive probes the load balancer needs to remove and to restore a connector, from probe_threshold and number_of_probes on the deployed probe.
3. Whether failing sessions started on a connector that was then marked unhealthy, which Help says can fail until the flow ages out.
