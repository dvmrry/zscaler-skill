# Cloud Connector Auto Scaling groups on AWS: scaling metric, policy, capacity limits (cloud-connector.aws.autoscaling)
Also called: cloud connector asg; cloud connector autoscaling aws; smedge_cpu_utilization; Zscaler/CloudConnectors namespace; cloud connector not scaling out; cloud connector asg max size 16; zonal_asg_enabled; target_cpu_util_value

Cloud Connector autoscaling is an AWS Auto Scaling group of small Cloud Connectors behind a GWLB, scaled on a CPU metric the Cloud Connectors publish themselves. Health checks are in [Cloud Connector autoscaling health: custom health metric, the Zscaler Lambda, grace period](kb:cloud-connector.aws.autoscaling.health); warm pools and lifecycle hooks in [Cloud Connector autoscaling lifecycle: launch and terminate hooks, warm pools](kb:cloud-connector.aws.autoscaling.lifecycle).

**What it is.** An AWS autoscaling deployment adds Cloud Connector VMs to an Auto Scaling group to meet current load and removes them when load decreases, within a configured desired capacity, minimum and maximum; settings can be changed in the EC2 console after deployment. [cloud-connector.aws.autoscaling:what-it-does] Autoscaling supports only the small Cloud Connector size: Help says only small instance types are supported for the autoscaling template, and the reference ASG module creates its launch template only when `cc_instance_size` is small. [cloud-connector.aws.autoscaling:small-only] Enabling it needs a Support-enabled provisioning template and the Lambda package in S3: [Cloud Connector on AWS: CloudFormation templates, order, and parameter defaults](kb:cloud-connector.aws.cloudformation).

**Topology.** In the documented topology the workloads and the Auto Scaling group sit in separate subnets of one VPC in a single availability zone, with multiple groups in multiple zones as the higher-redundancy alternative, and a NAT gateway with a dedicated IP in a public subnet for the Cloud Connectors' outbound traffic. [cloud-connector.aws.autoscaling:topology] The reference ASG module creates one Auto Scaling group spanning all Cloud Connector subnets by default; `zonal_asg_enabled` true creates one group per subnet and availability zone. [cloud-connector.aws.autoscaling:zonal-default] The CloudFormation template defaults the other way, to one group per zone: [Cloud Connector on AWS: CloudFormation templates, order, and parameter defaults](kb:cloud-connector.aws.cloudformation).

**The metric.** Each Cloud Connector reports its own CPU utilization to CloudWatch as a custom metric every minute, and autoscaling acts on the aggregate across the group rather than on VM-level metrics, because, per Help, custom metrics provide more detailed and precise information about CPU usage. [cloud-connector.aws.autoscaling:custom-cpu-metric] The CPU metric appears in logs and reports as smedge_cpu_utilization. [cloud-connector.aws.autoscaling:metric-name] What load the metric reflects beyond CPU is not documented [gap:cloud-connector.aws.autoscaling:cpu-metric-meaning]. Help and the module spell the namespace differently [divergence:cloud-connector.aws.autoscaling:metric-namespace].

**The policy.** The reference ASG module attaches a TargetTrackingScaling policy per group on the customized metric smedge_cpu_utilization in namespace Zscaler/CloudConnectors, dimension AutoScalingGroupName, statistic Average, unit Percent, with target `target_cpu_util_value` (default 80). [cloud-connector.aws.autoscaling:module-policy] The target tracking policy has a default target value of 80% and automatically creates the CloudWatch alarms for scale-out and scale-in. [cloud-connector.aws.autoscaling:target-80] Scale-out triggers when aggregate CPU is above 80% for 180 seconds; scale-in triggers when it is below 80% for 900 seconds. [cloud-connector.aws.autoscaling:alarm-timing] After a scaling event a cooldown, 300 seconds by default, ignores new metric changes, and error bands around the target keep small fluctuations (such as 80.1% or 79.9% against 80%) from triggering actions. [cloud-connector.aws.autoscaling:cooldown-tolerance]

**Capacity limits.** Desired capacity cannot exceed the maximum or fall below the minimum; once the group is at maximum, scale-out stops and a further spike can delay responses or drop random traffic. [cloud-connector.aws.autoscaling:capacity-bounds] The reference ASG module defaults `min_size` to 2 and `max_size` to 4, validates both between 1 and 16, and its max_size error message calls 16 a hard limit of Cloud Connectors per group. [cloud-connector.aws.autoscaling:module-min-max] The three autoscaling examples (base_cc_gwlb_asg, base_cc_gwlb_asg_zpa, cc_gwlb_asg) narrow `max_size` to 1 through 10 and leave `min_size` unvalidated, and the zsec helper accepts 1 to 10 for both. [cloud-connector.aws.autoscaling:wrapper-max-10] GCP Help calls 16 the Cloud Connector group limit, [Help gives a default instance-group maximum of 10 VMs and minimum of one, and says the maximum cannot exceed the Cloud Connector group limit of 16 VMs per group.](kb:cloud-connector.gcp.mig-autoscaling:help-group-size); whether that binds AWS groups and how it is enforced is open [gap:cloud-connector.aws.autoscaling:group-size-limit], with the enforcement question shared by [Service-side enforcement of 16 Cloud Connectors per group](kb:cloud-connector.gcp.mig-autoscaling:group-limit-enforcement). Other ASG module defaults: `instance_warmup` 0, `protect_from_scale_in` false, and the group ignores changes to desired capacity and target groups so Terraform does not reset them. [cloud-connector.aws.autoscaling:module-misc-defaults]

**Seeing it in the Admin Console.** The Auto Scaling group name and instance IDs map to the Cloud Connector group name and VM names in the Admin Console; the Cloud Connector Groups page shows Auto Scaling true for a group mapped to an ASG, and Geo View shows active VMs green and inactive ones orange. [cloud-connector.aws.autoscaling:console-mapping]

**CloudFormation template.** The CloudFormation autoscaling template defaults AsgMinSize to 2 and AsgMaxSize to 4, limits both to 1 through 10, and defaults the CPU target tracking value to 80 on smedge_cpu_utilization in the Zscaler/CloudConnectors namespace. [cloud-connector.aws.autoscaling:cfn-asg-sizes] The CloudFormation autoscaling template creates one Auto Scaling group per availability zone by default (AsgZonalEnabled true), and a single group spanning all selected zones when it is false. [cloud-connector.aws.autoscaling:cfn-zonal-default] The macro copies the autoscaling group, its scaling policy and its warm pool once per availability zone, giving each group the subnets of its zone, or creates one group over all Cloud Connector subnets when AsgZonalEnabled is false. [cloud-connector.aws.autoscaling:cfn-group-sizing] The Terraform module defaults the other way [divergence:cloud-connector.aws.autoscaling:zonal-template-default]. The template files and parameters are in [Cloud Connector on AWS: CloudFormation templates, order, and parameter defaults](kb:cloud-connector.aws.cloudformation).

What to check:
1. Whether the group is at its maximum size, in which case scale-out stops and traffic can be delayed or dropped.
2. Whether the scaling policy uses smedge_cpu_utilization from the Zscaler namespace rather than EC2 CPUUtilization, and its target value.
3. Whether aggregate CPU stayed above target for three minutes (scale-out) or below for fifteen (scale-in), allowing for the five-minute cooldown.
4. Whether the Cloud Connector group shows Auto Scaling true in the Admin Console and its VMs match the group's instance IDs.
5. Whether the stack came from CloudFormation or Terraform before reading min and max as per-zone or per-deployment capacity.

Sources disagree (name both sides):
- The CloudWatch namespace of the Cloud Connector custom metrics: Help writes it with a space, the reference module without. [divergence:cloud-connector.aws.autoscaling:metric-namespace]
  - zscaler-help: Instance metrics with CPU and other usage data from autoscaling VMs are in the Zscaler/Cloud Connectors namespace.
  - tfmod-aws-cloud-connector: The scaling policy reads, and the instance IAM policy restricts PutMetricData to, the namespace Zscaler/CloudConnectors.
  - cft-aws-cloud-connector: The CloudFormation scaling policy reads the metric smedge_cpu_utilization in the namespace Zscaler/CloudConnectors.
  Impact: A CloudWatch query, alarm or IAM condition written from the Help spelling would not match the namespace the working reference deployment uses; the module's spelling is the one its policy and IAM depend on.
- Whether autoscaling creates one group per availability zone by default: the CloudFormation template does, the reference Terraform module creates a single group. [divergence:cloud-connector.aws.autoscaling:zonal-template-default]
  - tfmod-aws-cloud-connector: The reference ASG module creates one group spanning all subnets by default.
  - cft-aws-cloud-connector: The CloudFormation template creates one group per availability zone by default.
  Impact: Because each per-zone group is a copy of the same definition, the minimum and maximum size are likely per-zone in a default CloudFormation stack and whole-deployment in a default Terraform one; read the group count before sizing.
