# Cloud Connector on GCP: MIG autoscaling, Health Monitor and Resource Sync (cloud-connector.gcp.mig-autoscaling)
Also called: gcp mig cloud connector; managed instance group cloud connector; cloud connector autoscaling gcp; min_replicas; max_replicas; target_cpu_util_value; smedge_cpu_utilization gcp; cloud_connector_aggr_health gcp; health monitor cloud run function; resource sync cloud run function; resource sync cadence; resource_sync_entry; 16 cloud connectors per group; terraform-zscc-cloud-function-gcp
Former IDs: cloud-connector-28

On GCP, Cloud Connector autoscaling is a zonal Managed Instance Group per zone, scaled on a custom CPU metric, plus two Cloud Run functions that replace unhealthy connectors and reconcile the Admin Console with the groups. Help and the pinned Terraform module state different defaults for several of these values; the module's values are what a deployment made from it runs with.

**What the instance group does.** A MIG with autoscaling adds Cloud Connector VMs as load increases and removes them as it decreases, replaces unhealthy VMs and VMs terminated manually from the Google Cloud console; stopping or rebooting a member from the console could cause it to be terminated. [cloud-connector.gcp.mig-autoscaling:mig-behavior] Zonal MIGs with autoscaling are deployed in each configured region or zone, and a Cloud NAT gateway is deployed in each region for the connectors' outbound access, with dedicated external IPs. [cloud-connector.gcp.mig-autoscaling:zonal-migs] The CCVM module creates a single instance template and, from it, one zonal instance group manager per zone, and when autoscaling is enabled one autoscaler per instance group, so replica limits apply to each zonal group. [cloud-connector.gcp.mig-autoscaling:module-one-mig-per-zone] The CCVM module README says connector health is monitored through the internal network load balancer and that Zscaler does not currently support GCP-specific MIG features such as instance-based autohealing with this module. [cloud-connector.gcp.mig-autoscaling:no-mig-autohealing]

## Scaling policy

Each connector posts its data-plane CPU utilization to Cloud Monitoring every minute as `smedge_cpu_utilization`, and the MIG autoscaler uses the aggregate across the group against a target that defaults to 80% over two to three minutes. [cloud-connector.gcp.mig-autoscaling:help-scaling-policy] The autoscaler's initialization (cooldown) period defaults to 900 seconds; scale-in decisions use data from all VMs including those still initializing, while scale-out ignores VMs in the cooldown period. [cloud-connector.gcp.mig-autoscaling:help-cooldown] The module's autoscaler scales on the GAUGE metric `custom.googleapis.com/smedge_cpu_utilization` with `target_cpu_util_value` (default 80) and `cooldown_period` (default 900 seconds). [cloud-connector.gcp.mig-autoscaling:module-autoscaler]

**Group size.** Help gives a default instance-group maximum of 10 VMs and minimum of one, and says the maximum cannot exceed the Cloud Connector group limit of 16 VMs per group. [cloud-connector.gcp.mig-autoscaling:help-group-size] The direct CCVM module defaults `min_replicas` to 2 and `max_replicas` to 4 and validates both to 1-16, the maximum's message calling 16 a hard limit of Cloud Connectors per group. [cloud-connector.gcp.mig-autoscaling:module-replicas] The autoscaling example roots `base_cc_asg`, `base_cc_asg_zpa` and `cc_asg` default `max_replicas` to 4 with validation 1-10, and `min_replicas` to 1 with no validation. [cloud-connector.gcp.mig-autoscaling:wrapper-replicas] The `zsec` helper prompts for the minimum and maximum per autoscale instance group with defaults 2 and 4, accepting only 1-10 for each and a maximum no lower than the minimum. [cloud-connector.gcp.mig-autoscaling:zsec-replicas] The defaults differ across these layers [divergence:cloud-connector.gcp.mig-autoscaling:replica-defaults]. Whether the service itself enforces 16 connectors per group was not tested [gap:cloud-connector.gcp.mig-autoscaling:group-limit-enforcement]. For deployment types whose names contain ilb or glb, `zsec` accepts 1-10 Cloud Connectors per zone but its rejection message says the value must be between 1 and 20. [cloud-connector.gcp.mig-autoscaling:zsec-cc-count]

## Health Monitor

Each connector publishes a VM-level health metric, `cloud_connector_aggr_health`, every minute as 0 (unhealthy) or 100 (healthy), and the Health Monitor function consumes it every minute and starts termination of VMs it finds unhealthy. [cloud-connector.gcp.mig-autoscaling:help-health-metric] Help's configurable Health Monitor defaults are a 10-minute sliding window, 5 consecutive unhealthy minutes, a flapping tolerance of 7 unhealthy counts in 10 minutes, and for missing metrics a warning log at two minutes, a critical log at 5 minutes and termination at 10 minutes. [cloud-connector.gcp.mig-autoscaling:help-health-thresholds] Unhealthy VMs are terminated in iterations of up to 16 VMs by default, and a terminated VM is replaced immediately. [cloud-connector.gcp.mig-autoscaling:help-termination] The Cloud Function module passes Health Monitor thresholds as environment variables with defaults of 2, 5 and 12 minutes for the missing-metric warning, critical and termination thresholds, a 15-minute evaluation window, 10 unhealthy metrics in the window and 8 consecutive unhealthy metrics. [cloud-connector.gcp.mig-autoscaling:module-health-thresholds] The autoscaling example roots (`base_cc_asg`, `base_cc_asg_zpa`, `cc_asg`) declare the same six Health Monitor defaults as the module and pass them through. [cloud-connector.gcp.mig-autoscaling:example-health-defaults] The two sets of thresholds disagree [divergence:cloud-connector.gcp.mig-autoscaling:health-thresholds]. When `enable_scheduler` is true (the default), the module creates a Cloud Scheduler job that POSTs to the Health Monitor function every minute (`* * * * *`, UTC) with an OIDC token for the function service account. [cloud-connector.gcp.mig-autoscaling:module-health-scheduler]

## Resource Sync

The Resource Sync function keeps the VMs registered in the Admin Console matched to each Cloud Connector instance group's membership: a connector in the console that belongs to no instance group is deleted through an API call. Help says it runs every 10 minutes by default. [cloud-connector.gcp.mig-autoscaling:help-resource-sync] The pinned module's Resource Sync Cloud Scheduler job runs every 30 minutes (`*/30 * * * *`, UTC), and its README describes the function as removing dangling VM resources from the Zscaler portal every 30 minutes. [cloud-connector.gcp.mig-autoscaling:module-resource-sync] The module caps Resource Sync at `sync_max_deletions_per_run` (default 16) deletions per run, with dry-run off by default and `sync_excluded_instances`, a list (empty by default) of GCP instance IDs never to delete from Zscaler. [cloud-connector.gcp.mig-autoscaling:module-sync-limits] The cadence differs [divergence:cloud-connector.gcp.mig-autoscaling:resource-sync-cadence], and which implementation Help describes is open [gap:cloud-connector.gcp.mig-autoscaling:resource-sync-default]. The Terraform module deploys Resource Sync with entry point `resource_sync_entry` from a ZIP object in Cloud Storage; the function body is not in the Terraform source. [cloud-connector.gcp.mig-autoscaling:resource-sync-code-external] A delete race in Resource Sync and its fix are not in any registered source [gap:cloud-connector.gcp.mig-autoscaling:resource-sync-race].

**Function packaging.** Each Cloud Function is packaged as a ZIP in Cloud Storage, uploaded to a bucket created during deployment or to an existing one, and the functions read their code from that bucket. [cloud-connector.gcp.mig-autoscaling:function-zip] The Resource Sync function talks to the Cloud Connector API endpoint over HTTPS, and the functions do not interact directly with individual connector VMs. [cloud-connector.gcp.mig-autoscaling:functions-via-api]
