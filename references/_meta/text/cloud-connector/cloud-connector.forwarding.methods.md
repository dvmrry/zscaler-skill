# Cloud Connector forwarding methods: ZIA, ZPA, Direct, Drop, Local, and their API tokens (cloud-connector.forwarding.methods)
Also called: cloud connector forwarding method; forwardMethod; forward_method; ECZPA; LOCAL_SWITCH; ECSELF; PROXYCHAIN; ENATDEDIP; GEOIP; local forwarding method; cloud connector east-west; cloud connector snat dnat; wan selection; workload to workload access failing

The Traffic Forwarding page shows each rule's forwarding method as one of Direct, ZIA, ZPA, Drop, or Local. [cloud-connector.forwarding.methods:console-methods] Each method is a different path for the matched traffic.

The networking-flows page lists five traffic forwarding rule types: Internet & SaaS (forwards internet-bound traffic matching an Internet & SaaS rule), Private Access (forwards private application traffic matching a Private Access rule), Direct (bypasses Internet & SaaS/Private Access and forwards traffic directly), Drop (discards packets matching the Drop rule) and Local. [cloud-connector.forwarding.methods:networking-rule-types] The same page states a count that does not match its list [divergence:cloud-connector.forwarding.methods:rule-type-count]. The networking-flows page describes Local as allowing subnet-to-subnet or VPC/VNET-to-VPC/VNET communication within a region, where the forwarding rule page describes it as across AWS, Azure and GCP. [cloud-connector.forwarding.methods:networking-local-scope]

- **ZIA.** The ZIA method forwards internet-bound traffic that matches the rule to Internet & SaaS gateways over a configurable encrypted or unencrypted tunnel. [cloud-connector.forwarding.methods:zia-method] A ZIA rule can also carry destination NAT options for AWS, Azure and GCP: DNAT from the internal load balancer's virtual IP to a Zscaler virtual IP solves forwarding problems caused by overlapping IP ranges, with a destination IP and optionally a port. [cloud-connector.forwarding.methods:zia-dnat] Tunnels and failover: [Cloud Connector tunnels to Service Edges: primary, secondary, tertiary, fail-close and fail-open](kb:cloud-connector.overview.gateway-failover).
- **ZPA.** The ZPA method forwards private application traffic that matches the rule to Private Access over an encrypted tunnel. [cloud-connector.forwarding.methods:zpa-method] A forwarding gateway cannot be configured for Private Access; only the default gateway is used, and the rule's Forward to ZPA Gateway field is fixed to Default Gateway. [cloud-connector.forwarding.methods:zpa-default-gateway] Private Access policy can name Cloud Connector groups as a criterion: [The help lists these access policy criteria: Adaptive Access Profiles, Applications, Branch Connector Groups, Chrome Enterprise Browser, Client Connector Posture Profiles, Client Connector Trusted Networks, Client Types, Cloud Connector Groups, Country Codes, Extranet, Federated Applications, Locations, Machine Groups, Platforms, Risk Scores, SAML Attributes, SCIM Attributes, SCIM Groups, Segment Groups, Tag Groups, Tag Value and Workload Groups.](kb:zpa.policy.criteria:criteria-list); what else a ZPA-forwarded flow needs is open [gap:cloud-connector.forwarding.methods:zpa-prerequisites]. Application segments on the Private Access side: [ZPA application segments](kb:zpa.app-segments).
- **Direct.** The Direct method bypasses Internet & SaaS or Private Access and forwards traffic directly to the destination server using the Zscaler service IP address. [cloud-connector.forwarding.methods:direct-method]
- **Drop.** The Drop method drops all traffic matching the rule: the Cloud or Branch Connector discards the packets, and the discarded packets appear in the Session Logs of the Cloud & Branch Connector Admin Portal. [cloud-connector.forwarding.methods:drop-method]
- **Local.** The Local forwarding method is available only for Cloud Connector and Zero Trust Gateways, not for Branch Connector. [cloud-connector.forwarding.methods:local-availability] Local supports subnet-to-subnet or VPC-to-VPC communication across AWS, Azure and GCP, permitting ingress traffic to publicly hosted applications, and controls east-west segmentation and macrosegmentation using 5-tuples. [cloud-connector.forwarding.methods:local-purpose] Local forwards traffic within the public cloud to the intended destination, such as an IP address or tag; the traffic does not leave the public cloud, can go from any IP or tag in a VPC to another in the same or a different VPC, and keeps the original client IP address. [cloud-connector.forwarding.methods:local-method] A Local rule can also apply source NAT, translating workload source IPs to the Cloud Connector service IP, and destination NAT and port translation to the virtual IP and fixed single port of the internal load balancer that spreads ingress traffic over the workload servers. [cloud-connector.forwarding.methods:local-nat]

The Traffic Forwarding overview lists NAT (SNAT and DNAT) for ingress traffic in Azure and GCP, including SNAT to the Cloud Connector service IP to resolve asymmetric routing. [cloud-connector.forwarding.methods:ingress-nat] Release notes reportedly extend Layer 4 ingress NAT to AWS as well [gap:cloud-connector.forwarding.methods:nat-cloud-scope].

**Action settings.** A rule's action can optionally forward to a proxy gateway; in the Go SDK the `proxyGateway` member applies only to the Proxy Chaining method, and under Proxy Chaining only TCP-based network services are considered for policy match. [cloud-connector.forwarding.methods:proxy-gateway] WAN Selection is None by default, which follows the Traffic Distribution setting of the branch configuration template; Balanced distributes traffic evenly and Best Link always uses the best-performing WAN link. It applies only to hardware devices deployed in gateway mode. [cloud-connector.forwarding.methods:wan-selection] The Terraform provider still sends WAN selection although the Go SDK and the contract call it deprecated: [cloud-connector.terraform.forwarding-rules:wan-selection](kb:cloud-connector.terraform.forwarding-rules:wan-selection).

## API tokens

In the Go SDK, the forwarding rule's ZPA application segment and segment group members are each documented as applicable only to the `ECZPA` forwarding method, which it describes as used for Zscaler Cloud Connector; the Terraform documentation's ZPA example uses `forward_method = "ECZPA"`. [cloud-connector.forwarding.methods:eczpa-token] The Terraform resource accepts `LOCAL_SWITCH` as a `forward_method`, and the Python SDK documents destination workload groups as valid for the `LOCAL_SWITCH` forward method. [cloud-connector.forwarding.methods:local-switch-token] The console's ZPA method is sent as `ECZPA`, and its Local method as `LOCAL_SWITCH` by Terraform and the Python SDK. [cloud-connector.forwarding.methods:console-to-token]

The API contract lists eight `forwardMethod` values for creating or updating a traffic forwarding rule (INVALID, DIRECT, PROXYCHAIN, ZIA, ZPA, ECZPA, ECSELF, DROP); rules read back may also carry ENATDEDIP and GEOIP. LOCAL_SWITCH is not among the request values. [cloud-connector.forwarding.methods:contract-enums] Terraform and the contract disagree on the token for Local [divergence:cloud-connector.forwarding.methods:local-token]; whether LOCAL_SWITCH is the wire value is open in [Whether LOCAL_SWITCH is the API value of the console's Local forwarding method](kb:cloud-connector.terraform.forwarding-rules:local-switch-wire-value) and [Whether the API accepts destination workload groups on a forwarding rule, and only on Local rules](kb:cloud-connector.api.rules-wire:local-switch-acceptance). What `ENATDEDIP`, `GEOIP` and `PROXYCHAIN` do for a Cloud Connector rule, and which values the endpoint accepts, is open [gap:cloud-connector.forwarding.methods:method-semantics]; for ZIA rules the ZIA provider documents the first two: [The Terraform documentation describes ENATDEDIP as the Dedicated IP method and GEOIP as Zscaler automatically selecting the nearest data center from the data center mappings on the Geo IP page. The documentation also says ZPA requires `zpa_gateway` and `zpa_app_segments`, and PROXYCHAIN requires `proxy_gateway`.](kb:zia.forwarding-control.methods:tf-doc-meanings).

Whether changing a rule's method drops sessions in flight is not stated [gap:cloud-connector.forwarding.methods:method-change-sessions].

What to check:
1. For a ZPA-method flow that fails (workload to an on-premises or other-cloud application), the Cloud Connector's Private Access enrollment first, then the application segment and access policy on the Private Access side.
2. The rule's `forwardMethod` as stored, mapped back to the console label (ECZPA is ZPA; LOCAL_SWITCH or ECSELF may appear for Local).
3. For dropped traffic, the Session Logs, where packets discarded by a Drop rule appear.
4. For Local, whether the deployment is a Cloud Connector or Zero Trust Gateway rather than a Branch Connector.
5. For WAN Selection, whether the rule applies to hardware devices in gateway mode; otherwise the setting has no effect.

Sources disagree (name both sides):
- The networking-flows page says there are four types of traffic forwarding rule, then lists five. [divergence:cloud-connector.forwarding.methods:rule-type-count]
  - zscaler-help: There are currently four types of traffic forwarding rule types.
  - zscaler-help: The same page lists five types: Internet & SaaS, Private Access, Direct, Drop and Local.
  Impact: The Traffic Forwarding page lists five methods in its Forwarding Method column (console-methods), so a count of four cannot be taken from the networking-flows page; which type the count leaves out is not stated.
- Whether `LOCAL_SWITCH`, the token Terraform sends for the console's Local method, is a valid `forwardMethod` on a traffic forwarding rule. [divergence:cloud-connector.forwarding.methods:local-token]
  - tf-ztc: Terraform validates `forward_method` against DIRECT, LOCAL_SWITCH, ZIA, ECZPA and DROP, so a Local rule is written as LOCAL_SWITCH; the Python SDK also lists LOCAL_SWITCH.
  - api-specs: The API contract's request enum has no LOCAL_SWITCH.
  Impact: A Local rule written by Terraform sends a value the contract's request enum does not list; the Go SDK's comment also lists no LOCAL_SWITCH (it has ECSELF, mapped to no console label). Which value the backend stores and returns for Local is unconfirmed; the open question is held in cloud-connector.terraform.forwarding-rules:local-switch-wire-value and cloud-connector.api.rules-wire:local-switch-acceptance.
