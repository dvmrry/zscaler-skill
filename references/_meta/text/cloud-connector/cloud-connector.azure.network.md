# Cloud Connector on Azure: NICs, subnets, NSGs, NAT and routing (cloud-connector.azure.network)
Also called: azure cloud connector nic order; azure cloud connector dual nic; azure cloud connector management nic; azure cloud connector service nic; ip forwarding cloud connector azure; azure cloud connector nsg; azure cloud connector nat gateway; azure cloud connector udr; azure cloud connector route table; bgp route propagation cloud connector; azure private dns resolver cloud connector; terraform-zscc-network-azure; terraform-zscc-nsg-azure; terraform-zscc-private-dns-azure; zssupport_server

How the Azure reference deployment wires a Cloud Connector into the network: two interfaces per VM, the security groups on them, NAT egress, and the routes that steer workloads to it. Most of this comes from Zscaler's Terraform modules, which are one valid deployment shape; the Help pages are cited where they state the same point.

**Two interfaces, in order.** The single-VM module attaches the management NIC first and the service NIC second; its source comment states that Cloud Connector requires the interface order #1 management, #2 service (or load balancer for medium and large connectors), then further service interfaces. [cloud-connector.azure.network:nic-order-required] No help page states that requirement for the VM itself, so a deployment built outside the module is not shown wrong by it [gap:cloud-connector.azure.network:runtime-nic-requirement]. The VMSS module declares the management interface first, marked primary, and the forwarding interface second, with IP forwarding enabled. [cloud-connector.azure.network:vmss-nic-order] The single-VM module creates the service NIC with `ip_forwarding_enabled = true` and accelerated networking taken from `accelerated_networking_enabled`, which defaults to true. [cloud-connector.azure.network:service-nic-forwarding] The management NIC resource sets neither IP forwarding nor accelerated networking, so it gets the azurerm provider defaults for both. [cloud-connector.azure.network:mgmt-nic-no-forwarding] Neither direct module offers a single-NIC path: every VM, and every scale-set instance, is given one management and one forwarding interface with no condition on either. [cloud-connector.azure.network:two-nics-always] What happens on a VM booted with the order reversed is not documented [gap:cloud-connector.azure.network:nic-order-consequence].

**One subnet by default.** Both direct modules note that by default they receive the same single subnet ID for the management and service subnets, keeping the two inputs separate in case a deployment puts the interfaces in individual subnets for isolation; the VMSS example passes the same subnet list to both. [cloud-connector.azure.network:same-subnet-default] Help states that Cloud Connector appliances have a dedicated management interface installed, by default, in the same subnet as the service interface, and that network operations such as ping use the management interface. [cloud-connector.azure.network:mgmt-same-subnet-help]

**IP forwarding.** Help states that IP forwarding must be enabled on the Cloud Connector service interface to avoid connectivity disruptions or unreachable destinations; it is enabled by default but can be disabled manually or by automation. [cloud-connector.azure.network:ip-forwarding-must-stay-on] What the load-balancer probe shows when it is off is not documented [gap:cloud-connector.azure.network:ip-forwarding-probe-effect].

**Address space.** The minimum IPv4 address space for the VNet is /24, and for the subnet the Cloud Connectors are deployed into (zsccSubnet) it is /28. [cloud-connector.azure.network:vnet-sizing]

## Security groups

A Cloud Connector instance requires only outbound connections to the Zscaler cloud and no inbound connections from it; the outbound access requirements for a specific account are at config.zscaler.com under the Zscaler cloud name and cloud-branch-connector. [cloud-connector.azure.network:outbound-only] The NSG module's management NSG allows inbound TCP 22 (priority 4000) and ICMP (priority 4001) from `VirtualNetwork`, and all outbound traffic (priority 4000). [cloud-connector.azure.network:mgmt-nsg] When `support_access_enabled` is true (the default), the management NSG adds an outbound TCP 12002 rule at priority 3000 to `zssupport_server`, described as required for Zscaler Support to assist remotely; the destination defaults to 199.168.148.101, the resolved address of remotesupport.<cloud>.net, commented as the value for commercial clouds. [cloud-connector.azure.network:support-access-rule] The service NSG allows all inbound traffic from `VirtualNetwork` (priority 4000) and all outbound traffic; when a public load balancer is deployed it also allows inbound TCP 80 (priority 4010) and 443 (priority 4015) from any source. [cloud-connector.azure.network:service-nsg] Gateway Load Balancer deployments get a separate service NSG that allows inbound UDP only from the `AzureLoadBalancer` service tag on the configured VXLAN port range and denies all other inbound traffic, because VXLAN traffic comes only from the GWLB data plane. [cloud-connector.azure.network:gwlb-service-nsg] Whether platform traffic (load-balancer probes, the Azure fabric addresses) needs explicit rules is not stated by the module or Help [gap:cloud-connector.azure.network:nsg-platform-traffic].

## NAT egress

The network module creates one NAT gateway and one static Standard public IP per distinct zone (zonal when `zones_enabled` is true in a region the module lists as zone-supporting) unless the deployment is base-only or existing ones are supplied (`byo_nat_gws`, `byo_pips`), and, unless `existing_nat_gw_subnet_association` is true, associates each Cloud Connector subnet with a NAT gateway. [cloud-connector.azure.network:nat-per-zone] In a VMSS deployment, a NAT gateway for the Cloud Connectors' outbound traffic is deployed in each configured zone with a dedicated IP address. [cloud-connector.azure.network:nat-per-zone-help] When a Cloud Connector shows the wrong geolocation in the Admin Console, Help says to verify that outbound NAT and routing take the expected egress path and to confirm the public IP address in the Admin Console, then contact Support if it is correct. [cloud-connector.azure.network:wrong-geolocation] The egress identity of the NAT address, and deployments without a NAT gateway, are not covered by these sources [gap:cloud-connector.azure.network:nat-egress].

## Routing workloads to the connectors

Help for VMSS deployments recommends deploying the security stack into its own Security VNet with workload VNets peered to it, and a user-defined route in the workload VNets steering traffic to the internal load balancer in front of the Cloud Connectors. [cloud-connector.azure.network:hub-spoke] After deployment, Help has the workload subnet's route table send 0.0.0.0/0 to next hop type Virtual appliance at the load balancer's front-end IP; the route table's Propagate gateway routes setting chooses whether gateway routes reach the subnet's interfaces. [cloud-connector.azure.network:help-workload-route] When the network module creates the workload subnet, it attaches a route table with BGP route propagation disabled and a default route 0.0.0.0/0 whose next hop is a virtual appliance at the load balancer frontend IP (when a load balancer is used) or a Cloud Connector service IP; in base-only deployments, or when that address is not supplied, the next hop is Internet. [cloud-connector.azure.network:module-route-tables] How routes learned from ExpressRoute or a VPN gateway interact with that default route is not covered by a captured source [gap:cloud-connector.azure.network:bgp-learned-routes].

## Private DNS Resolver

The private DNS module deploys an Azure DNS Private Resolver with a ruleset, forwarding rules and an outbound endpoint for conditional forwarding of Azure DNS queries to Cloud Connector, for ZPA resolution and/or ZIA DNS Controls; the network module creates a subnet delegated to the dnsResolvers service with a route table pointing 0.0.0.0/0 at the Cloud Connector service IP or the load balancer frontend IP. [cloud-connector.azure.network:private-dns-module] In the network module the resolver subnet and its route table are created only when `zpa_enabled` is set; the `base_1cc_zpa` example defaults `zpa_enabled` to true and is described as adding Private DNS Resolver capability. [cloud-connector.azure.network:private-dns-only-zpa] The resolver's forwarding targets default to 185.46.212.88 and 185.46.212.89, described as a pair of Zscaler Global VIP addresses. [cloud-connector.azure.network:private-dns-targets] The module README lists the Azure limits it works within: a ruleset holds up to 25 forwarding rules and links to up to 10 virtual networks in the same region, and a resolver subnet is between /28 and /24. [cloud-connector.azure.network:private-dns-azure-limits] The changelog notes that ZPA (Azure Private DNS Resolver) variants are intentionally not provided for the new Gateway Load Balancer and Public Load Balancer greenfield examples: ZPA conditional forwarding is paired with the Cloud Connector egress (Private LB) topologies, and the GWLB ingress-inspection and standalone Public LB topologies do not require a Private DNS Resolver in their reference deployment. [cloud-connector.azure.network:gwlb-no-zpa-variant]

What to check:
1. Whether each Cloud Connector VM has the management NIC first and the service NIC second, as the module comment requires.
2. Whether IP forwarding is still enabled on the service NIC, since manual or automated changes can disable it.
3. Whether the management NSG still has the outbound support-access rule, and which destination it points to for the tenant's cloud.
4. Whether the workload route table sends 0.0.0.0/0 to the load balancer frontend (or the single connector's service IP) and has gateway route propagation disabled.
5. Whether the connector's egress public IP matches the expected NAT gateway when the Admin Console shows the wrong geolocation.
6. For intermittent failures on a Cloud Connector built with one NIC, whether they line up with management and control-plane traffic or with workload (service) traffic, since separate management and service interfaces exist to keep the two apart; then confirm runtime support for the single-NIC build with Zscaler Support.
