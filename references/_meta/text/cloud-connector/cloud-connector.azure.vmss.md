# Cloud Connector on Azure: VMSS autoscaling, health monitoring and resource sync (cloud-connector.azure.vmss)
Also called: azure vmss cloud connector; cloud connector scale set; cloud connector autoscaling azure; vmss_max_ccs; vmss_min_ccs; vmss_default_ccs; smedge_cpu_utilization azure; cloud_connector_aggr_health azure; health monitoring function azure; resource sync function azure; orphan cloud connector cleanup azure; terminate_unhealthy_instances; asp_sku_name; flex consumption cloud connector function app; terraform-zscc-ccvmss-azure; terraform-zscc-function-app-azure

VMSS is the Azure form of Cloud Connector autoscaling: scale sets grow and shrink on a custom CPU metric, and a Function App replaces unhealthy connectors and removes orphaned ones from the Cloud Connector group. Help and the reference Terraform state the defaults separately, and they do not always agree.

**Enablement.** A Cloud Connector VMSS deployment requires the Terraform deployment template with VMSS and a new Cloud Provisioning Template with Auto Scaling enabled; to enable autoscaling, contact Zscaler Support. [cloud-connector.azure.vmss:vmss-requires-terraform] The provisioning template's Auto Scaling setting covers AWS Auto Scaling, Azure VMSS and GCP MIG autoscaling, and enabling any of them requires contacting Zscaler Support. [cloud-connector.azure.vmss:support-gated] The Marketplace names for each cloud's autoscaling are in [Autoscaling is called Auto Scaling in the AWS Marketplace, Virtual Machine Scale Sets (VMSS) in the Azure Marketplace, and a Managed Instance Group (MIG) with autoscaling in the Google Cloud Marketplace; the Admin Console's "autoscaling" covers all three, and enabling any of them requires contacting Zscaler Support.](kb:cloud-connector.overview.groups:autoscaling-names). What a template with Auto Scaling turned on does on a tenant where Support has not enabled it is not documented [gap:cloud-connector.azure.vmss:not-enabled-behavior].

**What a scale set does.** A VMSS adds Cloud Connector VMs as load increases and removes them as it decreases, removes unhealthy VMs and replaces them, and replaces a VM someone terminates manually from the Azure portal; stopping or rebooting a scale-set VM from the Azure portal could cause it to be terminated. [cloud-connector.azure.vmss:vmss-behavior] A scale set is created in each configured zone; the module creates one scale set per zone when zones are supported and enabled, and one otherwise. [cloud-connector.azure.vmss:vmss-per-zone] The module deploys scale sets as `azurerm_orchestrated_virtual_machine_scale_set` (Flexible orchestration) with a 5-minute termination notification. [cloud-connector.azure.vmss:flexible-orchestration]

## Scaling rules

Each Cloud Connector reports a custom CPU utilization metric to Azure Monitor every minute, and VMSS uses the aggregate across the scale set; Zscaler's recommended defaults are scale out above 70% and scale in below 50%, each after 10 consecutive minutes, with a 15-minute cooldown and one VM per event. [cloud-connector.azure.vmss:help-scaling-rules] The module's autoscale profile triggers on metric `smedge_metrics` in namespace `Zscaler/CloudConnectors`, filtered to `metric_name` = `smedge_cpu_utilization` and averaged per minute: scale out by 1 when above 70 over PT5M, scale in by 1 when below 50 over PT5M, each with a PT15M cooldown. [cloud-connector.azure.vmss:module-scaling-rules] The evaluation window differs between the two [divergence:cloud-connector.azure.vmss:scale-evaluation-window]. Help describes optional scheduled scaling (minimum instances, days, start and end time) for predictable load; in the module it is off by default (`scheduled_scaling_enabled` false) and otherwise defaults to Monday to Friday from hour 9 to hour 17, Pacific Standard Time, with a scheduled minimum of 2. [cloud-connector.azure.vmss:scheduled-scaling]

## Instance counts

The module creates one autoscale setting per scale set, each with capacity default, minimum and maximum from `vmss_default_ccs`, `vmss_min_ccs` and `vmss_max_ccs`; the `zsec` helper prompts for the minimum, default and maximum per VMSS and, for a zonal deployment, reports `$zones_count` scale sets each with those values. [cloud-connector.azure.vmss:per-vmss-capacity] In the direct VMSS module, `vmss_default_ccs` and `vmss_min_ccs` default to 2 and `vmss_max_ccs` to 4, and all three are validated to 1-16, with error messages calling 16 a hard limit of Cloud Connectors per group. [cloud-connector.azure.vmss:module-counts] The `base_cc_vmss` and `cc_vmss` example roots declare `vmss_max_ccs` with default 16 and no validation, and pass it to the VMSS module. [cloud-connector.azure.vmss:wrapper-max-16] The module README renders a different maximum default [divergence:cloud-connector.azure.vmss:vmss-max-default]. The `zsec` helper accepts 1-20 for the VMSS minimum, default and maximum (prompt defaults 2, 2 and 5) and requires the default to lie between minimum and maximum; for the load-balancer types (names containing lb, and cc_gwlb) it asks for a `cc_count` and accepts 1-20 (prompt default 2). [cloud-connector.azure.vmss:zsec-counts] A VMSS count of 17 to 20 passes the `zsec` prompt check and then fails the direct module's 1-16 validation; with the example roots' default of 16, a scale-set maximum of 16 reaches the module unless the helper or tfvars set another value. This is a tooling mismatch, not evidence of a 20-connector runtime limit. [cloud-connector.azure.vmss:zsec-exceeds-module]

## The Function App

A VMSS deployment has two Azure functions: Health Monitoring, which runs every minute, uses each connector's custom metrics to find unhealthy connectors and terminates and immediately replaces them; and Resource Sync, which runs every 30 minutes and removes from the Cloud Connector group any connector that is not in the VMSS. The functions call the Cloud Connector API server over REST and do not talk to connectors directly, and the Function App runs a ZIP from a storage account created at runtime or supplied at deployment. [cloud-connector.azure.vmss:function-app-roles] The VMSS deployment templates (`base_cc_vmss`, `base_cc_vmss_zpa`, `cc_vmss`) create an Azure Function App, a storage account and a Log Analytics workspace alongside one scale set, NAT gateway and scale-set settings per zone. [cloud-connector.azure.vmss:function-app-in-templates] A grace period lets a connector boot before its health is evaluated; it lasts until the VM has been alive more than 30 minutes or reports at least one healthy metric. [cloud-connector.azure.vmss:grace-period] After the grace period, a connector is unhealthy when its health metric is None or 0 for 7 of the last 10 samples, or for 5 consecutive samples, counting from the first healthy sample; each connector publishes the metric every minute as 0 (unhealthy) or 100 (healthy). [cloud-connector.azure.vmss:unhealthy-criteria] Unhealthy instances are terminated in iterations of at most 20% of the instances or one instance, whichever is greater, and each terminated VM is replaced immediately. [cloud-connector.azure.vmss:termination-iterations] The Function App module passes the provisioning URL, Key Vault URL, scale-set names and `TERMINATE_UNHEALTHY_INSTANCES` as app settings; `terminate_unhealthy_instances` defaults to true, and the app runs from the ZIP uploaded to a blob or from a public URL. [cloud-connector.azure.vmss:module-function-settings] The Health Monitoring and Resource Sync cadences and thresholds are not set by any Terraform variable or app setting of the Function App module; they come from the bundled function package. [cloud-connector.azure.vmss:schedule-not-in-terraform]

**Hosting plan.** `asp_sku_name` defaults to Y1, which the module recommends (calling it flex consumption) unless the Azure region does not support it, and accepts Y1, FC1, EP1 or B1; the changelog says the variable was added for VMSS deployments in regions without the Flex Consumption plan. [cloud-connector.azure.vmss:asp-sku] An example tfvars file says Y1 is not available in all Azure regions; without Y1, choose B1 if VNet integration is not required and EP1 if it is. [cloud-connector.azure.vmss:asp-sku-guidance] What a deployment loses when the Function App cannot be hosted is not documented [gap:cloud-connector.azure.vmss:function-app-degraded].

**Identities.** A VMSS deployment needs two user-assigned managed identities: the Cloud Connector identity (Network Contributor, Monitoring Metrics Publisher, Storage Queue Data Contributor) for operations such as network interface discovery and metric publishing, and the Function App identity (Network Contributor, Virtual Machine Contributor, Monitoring Contributor, Managed Identity Operator, Storage Blob Data Reader) for instance termination, replacement and metric reading. [cloud-connector.azure.vmss:managed-identities] A system-assigned identity must not be added: [Cloud Connector must not be assigned an Azure system managed identity, because that identity overrides the deployment requirements.](kb:cloud-connector.azure:no-system-identity).

**Metrics.** In namespace zscaler/cloudconnectors, each Cloud Connector's VM-level health metric is shown as `cloud_connector_aggr_health`. The scaling metrics include `smedge_cpu_utilization`, `smedge_mem_utilization`, `smedge_bytes_in` and `smedge_bytes_out`; Help's procedure for viewing VMSS metrics selects the metric `smedge_metrics` and filters on the property `metric_name` with the value `smedge_cpu_utilization`, and the scaling rules compare `smedge_cpu_utilization`. [cloud-connector.azure.vmss:metrics]

What to check:
1. Whether Zscaler Support enabled autoscaling for the tenant and the provisioning template has Auto Scaling enabled before a VMSS deployment.
2. Which evaluation window, thresholds and cooldowns the deployed autoscale setting actually uses, rather than the Help defaults.
3. How many scale sets were created (one per zone) and the capacity set on each, since minimum and maximum apply per scale set.
4. Whether the Function App is running and its Health Monitoring invocations show terminations, in Application Insights, when unhealthy connectors are not replaced or orphans remain in the group.
5. Whether the Cloud Connector VMs carry only the user-assigned identity, since a system-assigned identity overrides the deployment requirements.

Sources disagree (name both sides):
- How long the CPU threshold must hold before a VMSS scale event: Help's recommended duration versus the module's default evaluation window. [divergence:cloud-connector.azure.vmss:scale-evaluation-window]
  - zscaler-help: Zscaler recommends 10 consecutive minutes above or below the threshold for both scale out and scale in.
  - tfmod-azure-cloud-connector: The module averages the metric over a PT5M (5-minute) window for scale out and for scale in by default.
  Impact: A deployment made from the module reacts on a 5-minute average, not the 10 minutes Help describes; reasoning from Help over- or under-estimates how fast a scale set responds.
- The default of `vmss_max_ccs` in the direct VMSS module: its source declaration versus its generated README. [divergence:cloud-connector.azure.vmss:vmss-max-default]
  - tfmod-azure-cloud-connector: The source declaration defaults the maximum to 4.
  - tfmod-azure-cloud-connector: The generated README renders the default as 16.
  Impact: Sizing from the README overstates the direct module's maximum; the example roots, which default to 16, behave as the README says, so the effective value depends on which root called the module.
  Resolved (source-rank) by cloud-connector.azure.vmss:module-counts: The variable declaration is what Terraform evaluates; the README is generated documentation.
