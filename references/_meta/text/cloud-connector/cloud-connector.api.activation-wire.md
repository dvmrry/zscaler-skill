# Cloud Connector activation on the wire: activate, forced activate, and what the clients send (cloud-connector.api.activation-wire)
Also called: ztw activation; ecAdminActivateStatus; forcedActivate; cloud connector activate changes api; ztc_activation_status; ztw force activate

Cloud & Branch Connector stages configuration changes until they are activated, as ZIA does. The activation paths and the clients' functions are generated; this subject holds what the calls do and how the clients differ.

**Why activation exists.** The Activation API resources activate configuration changes by pushing them to the Central Authority (CA); for any configuration change to take effect, the service requires it to be activated. [cloud-connector.api.activation-wire:activation-pushes-to-ca] The OneAPI guide names Cloud & Branch Connector, with ZIA, as needing explicit activation: [For ZIA and Cloud & Branch Connector, configuration changes must be explicitly activated, through /status/activate and /ecAdminActivateStatus/activate respectively. A change cannot be reverted and a queued activation cannot be cancelled; the guide recommends grouping several changes and activating once.](kb:shared.oneapi.write-practices:activation-zia-cbc). The ZIA counterpart is [How ZIA API changes become live: saving versus activating](kb:zia.api.activation).

**The two operations.** The contract describes the activate operation only as "Activates configuration changes." and the forced activate operation only as "Force activates configuration changes." [cloud-connector.api.activation-wire:contract-descriptions] What forcing changes beyond that description is open [gap:cloud-connector.api.activation-wire:force-semantics]. The OneAPI guide says activate is a POST while the contract and both SDKs use PUT: [shared.oneapi.write-practices:cbc-activate-method](kb:shared.oneapi.write-practices:cbc-activate-method).

**Clients.** The Python SDK's `activate` takes `force` (default False) and sends a PUT to `/ecAdminActivateStatus/forcedActivate` when it is True and to `/ecAdminActivateStatus/activate` otherwise, with any keyword arguments as the body. [cloud-connector.api.activation-wire:python-force-flag] The Go SDK's `UpdateActivationStatus` and `ForceActivationStatus` each send a PUT whose body is the caller's `ECAdminActivation` struct; none of its four fields is tagged to be omitted when empty. [cloud-connector.api.activation-wire:go-sends-status-struct] The contract shows no request body for either operation [divergence:cloud-connector.api.activation-wire:activate-request-body]. The Go SDK's writes never activate on their own, [The Go SDK's ZTW create, update and delete functions do not activate; staged changes take effect only when the caller calls `activation.UpdateActivationStatus` or `activation.ForceActivationStatus`.](kb:cloud-connector.sdk-go.coverage:no-auto-activation), while a Python OneAPI client that wrote ZTW objects ends its session on exit in a way the SDK says activates them, [So a Python script that writes ZTW objects inside a with block may see its staged changes go live when the block exits, without calling activate, while a read-only script does not log out; the Go SDK has no such step and activates only on an explicit call.](kb:cloud-connector.sdk-python.client-configuration:exit-can-activate).

The ZTC provider's `ztc_activation_status` resource activates in its create function (calling `UpdateActivationStatus`), has no update function, and its delete is a no-op; its three settable arguments are ForceNew, and its fourth, `admin_status_map`, is computed only. [cloud-connector.api.activation-wire:tf-create-only] The ZTC provider never calls forced activation: the resource has no force option, and the provider does not call `ForceActivationStatus` or the forced activate path. [cloud-connector.api.activation-wire:tf-never-forces] What that means for an apply, and the out-of-band activator CLI, are in [Because the resource activates only in its create function and every settable argument forces replacement, an apply activates only when `ztc_activation_status` is created or replaced. Once it is in state, a later apply that changes other ZTC resources does not activate unless the status read back from the API differs from the configured arguments and forces a replacement.](kb:cloud-connector.terraform.activation:resource-activates-only-on-create) and [The provider documentation says the ZTC platform requires every configuration to be activated, and offers an out-of-band CLI (ztcActivator) or the `ztc_activation_status` resource for it.](kb:cloud-connector.terraform.activation:two-ways). In legacy mode the activation status read goes through the ZIA legacy client and fails in the provider: [The ZTC provider's legacy mode builds only a ZTW legacy client, so the generic ZIA-routed calls above find no ZIA legacy client and return the SDK's "legacy client not set" error. In that mode the activation status read (resource and data source) and the provisioning URL create, update, and delete fail while the other ZTC resources, which use the `...Resource` methods, work (except ZPA-resource lookups, which also go through the generic path).](kb:cloud-connector.sdk-go.service-defects:legacy-ztw-only-client-fails-generic-calls).

What to check:
1. Whether a Terraform run that changed Cloud Connector objects actually activated: the activation resource activates only when it is created or replaced, not on every apply.
2. Before using forced activation in automation, whether Zscaler has confirmed what it does differently from a normal activation.

Sources disagree (name both sides):
- Whether the activate calls carry a request body. [divergence:cloud-connector.api.activation-wire:activate-request-body]
  - api-specs: The contract's activate and forced activate operations define no request body.
  - sdk-go: The Go SDK sends the four-field activation status struct as the body.
  - sdk-python: The Python SDK sends the caller's keyword arguments, which are empty for a plain call.
  Impact: No source says whether the API reads the status fields a Go or Terraform caller sends; activation through either SDK is the tested path, and a raw call can follow the contract and send no body.
