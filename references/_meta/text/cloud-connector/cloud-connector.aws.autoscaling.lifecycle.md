# Cloud Connector autoscaling lifecycle: launch and terminate hooks, warm pools (cloud-connector.aws.autoscaling.lifecycle)
Also called: cloud connector warm pool; cloud connector lifecycle hook; pending:wait cloud connector; terminating:wait cloud connector; reuse_on_scale_in; warm_pool_max_group_prepared_capacity; cloud connector stuck pending wait

Lifecycle hooks hold a Cloud Connector in a wait state while it registers or is removed from the Admin Console; warm pools keep pre-initialized Cloud Connectors ready for scale-out.

**Launch.** The launch hook holds a new VM in Pending:Wait while custom actions register it and report it healthy; the VM stays there for 30 minutes by Zscaler default, and if the actions complete earlier the launch continues to Pending:Proceed and then InService. [cloud-connector.aws.autoscaling.lifecycle:launch-hook] The reference ASG module's launch hook has default_result ABANDON and a heartbeat timeout of `lifecyclehook_instance_launch_wait_time`, default 1800 seconds. [cloud-connector.aws.autoscaling.lifecycle:module-launch-hook] With ABANDON as the launch default, a Cloud Connector that has not completed the launch action when the wait expires is not put into service; with CONTINUE as the terminate default, termination proceeds when the terminate wait expires. [cloud-connector.aws.autoscaling.lifecycle:abandon-on-timeout]

**Termination.** The termination hook holds a VM in Terminating:Wait while custom actions remove it from the Cloud Connector group by API and notify the group; the VM stays there for 15 minutes by Zscaler default, and if the actions complete earlier the termination continues. [cloud-connector.aws.autoscaling.lifecycle:terminate-hook] The reference ASG module's terminate hook has default_result CONTINUE and a heartbeat timeout of `lifecyclehook_instance_terminate_wait_time`, default 900 seconds. [cloud-connector.aws.autoscaling.lifecycle:module-terminate-hook]

**Warm pool.** A warm pool holds pre-initialized VMs that the group draws from on scale-out; VMs leaving the pool count toward desired capacity. [cloud-connector.aws.autoscaling.lifecycle:warm-pool] Warm-pool VMs are Stopped or Running as chosen at deployment; Stopped saves cost, and stopped VMs show as inactive (red) in the Admin Console. [cloud-connector.aws.autoscaling.lifecycle:warm-pool-state] By default the warm pool size is the group's maximum minus its desired capacity; MaxGroupPreparedCapacity replaces the maximum in that calculation, and a warm-pool minimum, unset by default, makes the size static. [cloud-connector.aws.autoscaling.lifecycle:warm-pool-sizing] By default scale-in terminates a VM and launches a new one into the warm pool; the reuse policy instead returns already-configured VMs to the pool. [cloud-connector.aws.autoscaling.lifecycle:reuse-policy] A warm-pool VM passes Warmed:Pending and Warmed:Pending:Wait for a custom action before Warmed:Stopped (or Warmed:Running), then on launch pauses again at Pending:Wait before InService; if the pool is depleted and the group is below maximum, a VM can be launched directly into the group. [cloud-connector.aws.autoscaling.lifecycle:warm-lifecycle] In the reference ASG module the warm pool is off by default (`warm_pool_enabled` false) and is added only when enabled, with `warm_pool_state` Stopped, `warm_pool_min_size` 0 (validated 0 to 16), `warm_pool_max_group_prepared_capacity` null and `reuse_on_scale_in` false. [cloud-connector.aws.autoscaling.lifecycle:module-warm-pool]

**CloudFormation template.** The CloudFormation autoscaling template's launch hook defaults to ABANDON with a heartbeat timeout of 1800 seconds and its termination hook to CONTINUE with 900 seconds. [cloud-connector.aws.autoscaling.lifecycle:cfn-hooks] The CloudFormation autoscaling template enables the warm pool by default, with state Stopped (Stopped or Running allowed), minimum size 0, MaxGroupPreparedCapacity -1 and reuse on scale-in false. [cloud-connector.aws.autoscaling.lifecycle:cfn-warm-pool] The Terraform module defaults the warm pool the other way [divergence:cloud-connector.aws.autoscaling.lifecycle:warm-pool-template-default].

What to check:
1. Whether a launching Cloud Connector registered within the launch hook's 30-minute wait; one that does not is abandoned.
2. Whether a terminated Cloud Connector was removed from its Cloud Connector group in the Admin Console during the terminate hook.
3. Whether red, inactive VMs in the Admin Console are stopped warm-pool instances rather than failures.

Inferred, not quoted (say so when an answer rests on one):
- [cloud-connector.aws.autoscaling.lifecycle:abandon-on-timeout] Tier B: AWS lifecycle-hook semantics for default_result, which the module and Zscaler Help do not state.

Sources disagree (name both sides):
- Whether the autoscaling warm pool is on by default: the CloudFormation template enables it, the reference Terraform module does not. [divergence:cloud-connector.aws.autoscaling.lifecycle:warm-pool-template-default]
  - tfmod-aws-cloud-connector: The reference ASG module leaves the warm pool off unless warm_pool_enabled is set.
  - cft-aws-cloud-connector: The CloudFormation template enables the warm pool by default.
  Impact: A default CloudFormation stack keeps pre-initialized Stopped instances that a default Terraform deployment does not have, which changes scale-out latency, cost and the inactive VMs shown in the Admin Console.
