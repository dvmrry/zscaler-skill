# Cloud Connector on Azure: deployment methods, prerequisites and provisioning (cloud-connector.azure)
Also called: azure cloud connector; cloud connector azure deployment; deploy cloud connector azure; azure marketplace cloud connector; zscaler cloud connector application; cloud connector china azure; azure routing intent cloud connector; azure key vault cloud connector; azure managed identity cloud connector; cloud connector provisioning url azure; AZURE_VAULT_URL; AZURE_MANAGED_IDENTITY_CLIENT_ID

Cloud Connector runs in Azure as customer-deployed VMs, from the Azure Marketplace or from Zscaler's Terraform package. This subject covers which method fits, what has to exist first, and how a VM learns which tenant to register with; groups and load balancing in general are in [Cloud Connector groups: what they are for, autoscaling names, status and disabling](kb:cloud-connector.overview.groups) and [How cloud load balancers spread traffic across Cloud Connectors and take unhealthy ones out](kb:cloud-connector.overview.load-balancing).

**Deployment rules.** The template-type rule is [Deploy an autoscaling group only with an autoscaling (ASG) template, and a non-autoscaling deployment only with a non-ASG template.](kb:cloud-connector.overview.groups:template-match). Help says not to run VMSS and non-VMSS deployments within the same VNet. [cloud-connector.azure:template-match] The Azure Routing Intent and Routing Policies feature for secured virtual WAN hubs is incompatible with Cloud Connector. [cloud-connector.azure:routing-intent]

**Two methods.** Cloud Connector is deployed in Azure either from the Zscaler Cloud Connector Application in the Azure Marketplace, which is for static deployments, or with Terraform, which supports more functions and is required for VMSS. [cloud-connector.azure:two-methods] Marketplace availability outside China, and the China requirement, are in [The Zscaler Cloud Connector Application in the Azure Marketplace is available in all regions except China; deploying from the China region requires Terraform.](kb:cloud-connector.regions.deployment:azure-marketplace-regions). VMSS is the feature's name in the Azure Marketplace and the Terraform templates; the Cloud Provisioning Template calls the same feature Auto Scaling. [cloud-connector.azure:vmss-naming] Workload discovery for Azure accounts is in [Cloud Connector on Azure: workload discovery service, partner configuration, event grid and account details](kb:cloud-connector.azure.workload-discovery). VMSS specifics are in [Cloud Connector on Azure: VMSS autoscaling, health monitoring and resource sync](kb:cloud-connector.azure.vmss); the Terraform package is in [Zscaler's Azure Terraform package for Cloud Connector: image, VM sizes, provider constraint, examples and FIPS](kb:cloud-connector.azure.terraform-modules).

## Prerequisites

User-assigned managed identities are required: the Cloud Connector identity performs Azure operations such as network interface discovery and metric publishing, and a second, Function App identity exists only for VMSS; a deployment without VMSS needs only the Cloud Connector identity and the Network Contributor role. [cloud-connector.azure:managed-identities] The Terraform package's prerequisites give the Cloud Connector managed identity Network Contributor at subscription or resource-group scope, or with a custom role at minimum Microsoft.Network/networkInterfaces/read, and Get and List secret permissions on the Key Vault holding the Cloud Connector credentials. [cloud-connector.azure:custom-role-minimum] Cloud Connector must not be assigned an Azure system managed identity, because that identity overrides the deployment requirements. [cloud-connector.azure:no-system-identity] For a deployed Cloud Connector that does not appear in the Admin Console, Help's checks include user data and Key Vault entries (api-key, username, password, provisioning URL format), Get and List on the Key Vault for the user-managed identity, and the identity's privilege to enumerate network interfaces: Network Contributor or Microsoft.Network/networkInterfaces/read, with a scope that includes the appliance. [cloud-connector.azure:missing-from-console-checks] How the missing permission fails at boot is not described [gap:cloud-connector.azure:identity-bootstrap-failure]. The Cloud Connector credentials live in an Azure Key Vault as three secrets: api-key, holding the value from the API Key Management page, and username and password, holding the Zscaler Admin Console username and password; Cloud Connector uses the API key to authenticate and register the VM. [cloud-connector.azure:key-vault-secrets] Address-space minimums and the outbound-only firewall model are in [Cloud Connector on Azure: NICs, subnets, NSGs, NAT and routing](kb:cloud-connector.azure.network).

## Provisioning URL handoff

Saving a Cloud Connector provisioning template in the Admin Console creates a cloud provisioning URL, which is used to deploy Cloud Connector VMs in AWS, Azure and GCP. [cloud-connector.azure:provisioning-url] In a provisioning template, location creation and Cloud Connector group creation are automatic. [cloud-connector.azure:azure-template-defaults] The default VM size is in [In the cloud provisioning template, AWS offers Small, Medium or Large, with Small the default when autoscaling is enabled; for Azure and GCP the page says only that Small is set by default.](kb:cloud-connector.regions.deployment:vm-size). The Marketplace deployment takes the provisioning template URL, the Key Vault holding the Zscaler credentials, and a user-assigned managed identity with access to that vault and the Network Contributor role. [cloud-connector.azure:marketplace-prov-url] The `base_cc_vmss` example root builds the VM user data as a `[ZSCALER]` block with `CC_URL` (the provisioning URL), `AZURE_VAULT_URL`, `HTTP_PROBE_PORT`, `AZURE_MANAGED_IDENTITY_CLIENT_ID`, `GLB_VIP` when a public IP is present, and `FIPS_ENABLED`. [cloud-connector.azure:module-user-data] The VM module passes that user data to Azure base64-encoded as both `custom_data` and `user_data`; the VMSS module passes it as `user_data_base64` and as the OS profile's `custom_data`. [cloud-connector.azure:module-passes-user-data] Whether connectors added later by a scale set still register after the provisioning URL changes is not documented [gap:cloud-connector.azure:stale-provisioning-url].

**After deployment.** After a deployment from the Azure Portal, a routing table and a workload subnet must be created to redirect traffic to the load balancer. [cloud-connector.azure:post-deploy-route] The route, load balancer and NSG details are in [Cloud Connector on Azure: NICs, subnets, NSGs, NAT and routing](kb:cloud-connector.azure.network) and [Cloud Connector on Azure: internal load balancer, health probe and Gateway Load Balancer](kb:cloud-connector.azure.load-balancing).

What to check:
1. Whether the deployment mixes a VMSS and a non-VMSS deployment in one VNet, or pairs an autoscaling deployment with a non-autoscaling template.
2. Whether the target virtual WAN hub uses Routing Intent and Routing Policies, which Help calls incompatible with Cloud Connector.
3. Whether the Cloud Connector managed identity has Network Contributor (or at least Microsoft.Network/networkInterfaces/read) and Key Vault secret access, and no system-assigned identity.
4. Whether the user data on a connector that did not register carries the current provisioning URL, Key Vault URL and managed-identity client ID.

Not known (open gaps):
- Boot-time failure mode of missing NIC-read permission [gap:cloud-connector.azure:identity-bootstrap-failure]: settled by lab-test or support-ticket. Blocks: diagnosing a connector that never registers after an otherwise successful deployment
- Scale-out after the provisioning URL is regenerated [gap:cloud-connector.azure:stale-provisioning-url]: settled by lab-test. Blocks: explaining scale-out connectors that do not register
