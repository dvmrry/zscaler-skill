# Cloud Connector on GCP: workload discovery service (cloud-connector.gcp.workload-discovery)
Also called: gcp workload discovery; workload discovery service gcp; WDS gcp; gcp workload tags cloud connector; cloud asset inventory searchAllResources; gcp vm start notification; compute.instances.start; core_infra; centralized_grants

Workload discovery lets GCP workload metadata be used in Cloud Connector policy. It is a Zscaler-managed service reading the customer's projects through impersonation, with an optional Pub/Sub path for faster updates.

**What it collects.** The workload discovery service is a Zscaler-managed service that discovers workloads in a GCP account and fetches their user-defined tags and provider-generated attributes for use in security policies. [cloud-connector.gcp.workload-discovery:service] Supported attributes are labels, tags (network tags), networkInterfaces.network, networkInterfaces.subnetwork, serviceAccounts.email, machineType, zone and disks.sourceImage. [cloud-connector.gcp.workload-discovery:attributes]

**Access it needs.** The service uses the Cloud Asset Inventory searchAllResources API, which is rate-limited per project; other tools calling it should use a different quota (consumer) project to avoid shared rate-limit contention. [cloud-connector.gcp.workload-discovery:search-api-quota] The customer service account is granted Compute Viewer, Cloud Asset Viewer and Browser at organization, folder or project level, with Browser assigned only in the service account's project. [cloud-connector.gcp.workload-discovery:roles] The IAM Service Account Credentials, Cloud Resource Manager, Cloud Asset and Compute Engine APIs must be enabled per project; without them the service does not function correctly regardless of roles and permissions. [cloud-connector.gcp.workload-discovery:apis] The service uses service-account impersonation to get short-lived credentials instead of long-lived ones: on the customer's project service account, the Zscaler service account is granted Service Account Token Creator. [cloud-connector.gcp.workload-discovery:impersonation] Zscaler requires the roles/pubsub.editor role on the Cloud Connector service account, which the Cloud Connector VMs use to receive workload delta messages when workload metadata changes. [cloud-connector.gcp.workload-discovery:pubsub-editor-required] The Terraform package's handling of that grant is in [Zscaler's GCP Terraform package for Cloud Connector: image, NICs, Pub/Sub Editor, FIPS and zsec defects](kb:cloud-connector.gcp.terraform-modules).

**How it stays current.** The service enumerates the projects that the roles or permissions granted to its service account authorize, using resourcemanager.projects.list, then uses Compute Engine and other APIs to retrieve VM metadata, map tags for policy and keep an inventory in the Zscaler cloud. [cloud-connector.gcp.workload-discovery:project-discovery] By default the service polls for changes every 5 minutes; for near-instant updates it supports Pub/Sub-based VM start notifications, enabled by adding roles/pubsub.owner and roles/pubsub.viewer to the Cloud Connector VM. [cloud-connector.gcp.workload-discovery:polling] In the VM-start path, Zscaler creates a Pub/Sub topic in its SaaS project and shares it with the customer project, the Cloud Connector VM subscribes using roles/pubsub.owner, a logging sink publishes compute.instances.start audit events to the topic, and a poll trigger starts immediate discovery. [cloud-connector.gcp.workload-discovery:vm-start-flow]

**Onboarding package.** The Admin Console offers a Terraform deployment package with core_infra (service accounts, IAM roles, logging sinks) and centralized_grants (cross-project discovery permissions); it creates the service account and roles, grants impersonation to the Zscaler SaaS service account, sets up the VM-start logging sinks and configures the Pub/Sub subscriptions. [cloud-connector.gcp.workload-discovery:terraform-package] The account details page says the Download Script gives a Terraform deployment package that automates onboarding configuration for the workload discovery service, sets up logging sinks for VM start events and configures Pub/Sub subscriptions for workload change events. [cloud-connector.gcp.workload-discovery:download-script-terraform]

**Adding and managing an account.** The About GCP Accounts page says Zscaler configuration requires a service account called a GCP account (in its words, mapping to service principal credentials with access to a set of subscriptions in the same tenant), and that partner integrations enable the admin to configure permissions for the Zscaler service to discover workloads and associated metadata from a set of GCP projects and to associate a Cloud Connector with the workload information to enforce Zscaler security policies. [cloud-connector.gcp.workload-discovery:gcp-account] The GCP page (Zero Trust Cloud > Common Resources > GCP) lists for each account the number of GCP projects, Cloud Connectors and regions in the account. [cloud-connector.gcp.workload-discovery:gcp-page] Adding a GCP account shows a Zscaler Service Account Email (to be copied and saved only when deploying without Terraform), takes the Customer Service Account Email that grants the Zscaler service permission to use the service account to discover workloads, offers an optional Terraforming Script (Download Script) to create the service account, and then selects the projects visible to the service, the regions where the account operates and the Cloud Connectors to add. [cloud-connector.gcp.workload-discovery:add-account] Deleting a GCP account causes the Zscaler service to remove access information for that account. [cloud-connector.gcp.workload-discovery:delete-account] The page's description uses Azure terms for a GCP account [gap:cloud-connector.gcp.workload-discovery:account-azure-terms].

**Account details.** A GCP project's permission status in the account is Allowed, Pending, Denied or N/A and its status is Enabled or Disabled; selected projects can be disabled, enabled or refreshed. [cloud-connector.gcp.workload-discovery:project-status] The N/A permission state is not defined [gap:cloud-connector.gcp.workload-discovery:na-permission]. The region view gives the number of private IP addresses discovered in each GCP project and the discovery service status, which is Starting, Success or Error. [cloud-connector.gcp.workload-discovery:discovery-status] On the GCP account details page, Image ID (the SKU for the VM image assigned to the workload) and Platform (Linux/UNIX or Windows) are the attributes marked as usable in policies. [cloud-connector.gcp.workload-discovery:policy-attributes]

**Pub/Sub tab.** The Pub/Sub tab shows a Topic Discovery field, the information the topic discovery communicates to the tag service such as resource change notifications like VM creation, and a Topic Cloud Connector field, the information the topic Cloud Connector communicates such as changes to tags associated with the Cloud Connector. [cloud-connector.gcp.workload-discovery:pubsub-tab] The page says CloudFormation creates the topics but describes only subscriptions for the Terraform package [gap:cloud-connector.gcp.workload-discovery:pubsub-topic-creator]. The Azure counterpart of this subject is [Cloud Connector on Azure: workload discovery service, partner configuration, event grid and account details](kb:cloud-connector.azure.workload-discovery).

What to check:
1. Whether the four APIs are enabled in each project, since the service does not work without them regardless of roles.
2. Whether the Zscaler service account holds Service Account Token Creator on the customer service account, and that account holds Compute Viewer, Cloud Asset Viewer and Browser at the intended scope.
3. Whether other tools calling Cloud Asset Inventory searchAllResources use a different quota project, when discovery is slow or failing.
4. Whether new VMs are expected within 5 minutes (polling) or near-instantly (Pub/Sub VM-start notifications), and which roles the Cloud Connector VM has for that path.
5. Who created the Pub/Sub topics the Pub/Sub tab shows, since the page names CloudFormation for topics and a Terraform package only for subscriptions.
