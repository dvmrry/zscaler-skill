# Client Connector for VDI: the multi-session Windows agent that tunnels users' traffic to Cloud and Branch Connector (cloud-connector.vdi)
Also called: client connector for vdi; zscaler client connector for vdi; zcc vdi; zccvdi; zscaler vdi agent; vdi tunnels; p2p tunneling mode; a2a tunneling mode; 185.46.212.80

Zscaler Client Connector for VDI is a lightweight Windows application that runs in the user space of the VDI session host to authenticate multiple concurrent users, forward traffic to Cloud Connector or Branch Connector, and exchange user context within the Cloud Connector or Branch Connector. [cloud-connector.vdi:what-it-is] Client Connector for VDI inspects all ports and protocols for multisession, nonpersistent VDI deployments in the public cloud and on-premises data centers, and organizations can apply granular threat- and data-protection policies per individual user session. [cloud-connector.vdi:multisession-scope] The overview, the step-by-step configuration guide and the MSI install-options article each say that enabling the feature means contacting Zscaler Support. [cloud-connector.vdi:enable-via-support]

## What it needs

Client Connector for VDI currently supports only modern Windows operating systems: Windows 10 or Windows Server 2016 or later. The guide says only Azure Virtual Desktop and Citrix, on-premises and cloud-hosted, have been tested; other vendors might work but have not been tested. [cloud-connector.vdi:os-requirements] Before configuring Client Connector for VDI, Cloud Connector must be deployed to a cloud provider or Branch Connector to a hypervisor host. [cloud-connector.vdi:connector-prerequisite] The overview says Cloud Connectors operate within cloud environments such as AWS, Microsoft Azure and GCP, and Branch Connectors within on-premises environments such as VMware ESXi or Linux KVM. [cloud-connector.vdi:connector-platforms] The step-by-step configuration guide says Amazon Web Services (AWS) and Google Cloud Platform (GCP) are not supported by Client Connector for VDI. [cloud-connector.vdi:aws-gcp-unsupported] The vendor's own articles disagree on AWS [divergence:cloud-connector.vdi:aws-support].

## Identity, inspection and Private Access

The overview says the application supports all authentication mechanisms that the Zscaler service supports. [cloud-connector.vdi:auth-mechanisms] For SSL Inspection, Client Connector for VDI must have automatically installed the Zscaler Root CA certificate or the organization's own Root CA certificate. [cloud-connector.vdi:ssl-inspection-root-ca] Client Connector for VDI does not support Private Access features such as server-to-client connectivity for remote access, client forwarding policy for client types as Client Connector for VDI, and double encryption. Where client forwarding policy is required, the Cloud Connector or Branch Connector client type is supported and can be used in the same way. [cloud-connector.vdi:private-access-unsupported] Client Connector for VDI uses the IdP configured in the Internet & SaaS tenant for both Internet & SaaS and Private Access; for Private Access that IdP provides the authentication and passes a token to Private Access. SCIM and SCIM Attributes for Policy must be enabled for Private Access user attribution to function. [cloud-connector.vdi:private-access-identity] The guide says that for Private Access and wildcard FQDN forwarding to work, all DNS requests are sent through Cloud Connectors. [cloud-connector.vdi:dns-through-connectors]

The overview says common services handle operations such as the Active Directory service, DHCP, DNS resolution, Network Location Awareness (NLASVC), SMB file download, the Windows DNS client API, Windows Ping, the Winlogon service and traffic from a Windows service; when the Zscaler driver intercepts the connections these services initiate, Windows gives it NT AUTHORITY\SYSTEM as the user ID. For example, SMB traffic is handled by the LanmanWorkstation service, where services run under NT AUTHORITY\SYSTEM. [cloud-connector.vdi:system-account-traffic] How that traffic relates to the template's system user is open [gap:cloud-connector.vdi:system-user-vs-system-account]; the template side is in [VDI devices, dynamic VDI groups and VDI templates (authentication type, system user, provisioning URL and token)](kb:cloud-connector.vdi.groups-and-templates).

## The tunnels

Client Connector for VDI tunnels traffic through UDP encapsulation to the local Cloud Connector or Branch Connector; the tunnels carry user session data in the payload and user context in the UDP header, and are stateless so that they can fail over to other active appliances if a Connector fails. [cloud-connector.vdi:udp-encapsulation] The Cloud and Branch Connectors aggregate the tunnels from Client Connector for VDI in addition to encrypting and forwarding traffic to the Zero Trust Exchange. [cloud-connector.vdi:connector-aggregates] Client Connector for VDI connects on TCP 443 for the control channel, UDP 7443 for the data channel to Cloud Connector, and TCP 9090 on the Cloud Connector service endpoint for policy updates. The guide adds that user authentication with the Zscaler cloud uses TCP/443 and that UDP/7443 to the Connector and TCP/443 to the Zscaler cloud are required. [cloud-connector.vdi:ports] Cloud Connector and Branch Connector instances require only outbound connections to the Zscaler cloud, with no inbound connections from it; the outbound access requirements for an account are at https://config.zscaler.com/<Zscaler Cloud Name>/cloud-branch-connector, where the cloud name is in the URL used to log in to the Admin Console. [cloud-connector.vdi:outbound-only] Session capacity, keepalive and failover timing, and what the policy updates on TCP 9090 carry are open [gap:cloud-connector.vdi:tunnel-limits].

Point-to-Point (P2P) is the default mode of operation for Client Connector for VDI and Cloud & Branch Connector tunnels: the tunnel has a fixed destination IP address and destination port and copies the source port from the inner header, for use, the overview says, if fixed IP addresses are wanted for outer-header tunnels and destination IP addresses must be known. The Zscaler anycast Global VIP 185.46.212.80 is the outer header's destination IP address, and routing must make the Cloud Connector or Branch Connector load balancer the next hop for that VIP. [cloud-connector.vdi:p2p-default] Any-to-Any (A2A) copies the packet's inner header to the outer encapsulated header, preserving the source IP address, destination IP address and source port for better load balancing, and needs a default route pointing to the Cloud Connector or Branch Connector because the destination IP addresses are dynamic. A2A is not recommended and is being deprecated. [cloud-connector.vdi:a2a-deprecated] How MODE is written in the MSI is in [Installing Client Connector for VDI: download, MSI options, golden images, OnboardOnStart, Intune and processes to allowlist](kb:cloud-connector.vdi.install).

If load balancers distribute traffic to Cloud Connector or Branch Connector, Zscaler recommends source IP address affinity (2-tuple) hashing. The overview says that when Client Connector for VDI is enabled, the client IP address is entered as the session persistence setting for the Cloud Connector load balancer in Azure; with Private Access, Zscaler recommends P2P and 2-tuple tunneling. [cloud-connector.vdi:load-balancer-affinity] Which Azure load balancer distribution setting is the client IP address setting is open [gap:cloud-connector.vdi:azure-lb-setting]; the Azure load balancer is described in [Cloud Connector on Azure: internal load balancer, health probe and Gateway Load Balancer](kb:cloud-connector.azure.load-balancing) and the general mechanics in [How cloud load balancers spread traffic across Cloud Connectors and take unhealthy ones out](kb:cloud-connector.overview.load-balancing).

By default, Client Connector for VDI uses an MTU of 1,400 bytes. The overview says that if any additional tunneling or encapsulation is present in the network, the MTU might need adjusting from within the VDI Template. [cloud-connector.vdi:mtu-default] Where the MTU is set differs between the articles [divergence:cloud-connector.vdi:mtu-location]; the group form is in [VDI devices, dynamic VDI groups and VDI templates (authentication type, system user, provisioning URL and token)](kb:cloud-connector.vdi.groups-and-templates).

Among the best practices for Azure Virtual Desktop, the guide says that when configuring network security groups Zscaler recommends allowing traffic from Client Connector for VDI, and that NSGs should not have any other proxies, third-party tools, VPNs or software that can hinder the system network. [cloud-connector.vdi:azure-nsg] Cloud Connector's own Azure network security groups and routing are in [Cloud Connector on Azure: NICs, subnets, NSGs, NAT and routing](kb:cloud-connector.azure.network); the standard Client Connector on Azure desktops is in [Client Connector in Azure desktops: Windows 365 Cloud PCs and Azure Virtual Desktop](kb:zcc.install.azure-virtual-desktop).

Sources disagree (name both sides):
- The configuration guide says AWS is not supported by Client Connector for VDI; the MSI install-options article lists AWS as a deployment route and has an AWS golden-image section. [divergence:cloud-connector.vdi:aws-support]
  - zscaler-help: AWS and GCP are not supported by Client Connector for VDI.
  - zscaler-help: AWS is a deployment route for the MSI, and an AWS golden image can host pools in AWS VDI and AWS WorkSpaces.
  Impact: Whether Client Connector for VDI is supported for desktops hosted in AWS is unresolved; the guide also says only Azure Virtual Desktop and Citrix have been tested.
- The overview says the MTU is adjusted from within the VDI Template; the VDI group form carries the MTU field, and the guide says VDI groups apply MTU values. [divergence:cloud-connector.vdi:mtu-location]
  - zscaler-help: If any additional tunneling or encapsulation is present in the network, the MTU might need to be adjusted from within the VDI Template.
  - zscaler-help: The MTU is a field of the dynamic VDI group form, default 1,400 bytes.
  - zscaler-help: VDI groups apply MTU and forwarding profile values to VDI applications as devices register.
  Impact: The articles name the VDI template in one place and the VDI group in others as where the MTU is set, and do not say which governs; the template field list in Configuring VDI Templates names no MTU field.
