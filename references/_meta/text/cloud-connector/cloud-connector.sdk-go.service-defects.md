# Cloud Connector (ztw) Go SDK service functions with wrong assertions, nil payloads, or routing defects (cloud-connector.sdk-go.service-defects)
Also called: ztw sdk returns empty admin user; UpdateAdminUser zero value; UpdatePublicCloudChangeState nil payload; ztw legacy client routes to zia; errLegacyClientNotSet ztw; ztw update nil pointer dereference; ztw location vpcInfo empty object; location template editable false

These are defects in the Cloud and Branch Connector (ZTW) package of the Go SDK, where a helper decides what the caller sees or sends and the caller cannot tell. The ZTC provider at v0.2.0 (SDK v3.8.40) reaches some and not others; each claim says which. Content-Type matching and bulk-delete handling for ZTW are in [How the Go SDK builds requests and interprets responses: client options, bodies, status codes, bulk deletes](kb:shared.sdk-go.request-handling), paging in [How the Go SDK pages through ZPA, ZCC and ZTC lists, and when it stops early](kb:shared.sdk-go.list-pagination), and omitted zero values in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes); the ZIA equivalents of several items here are in [ZIA Go SDK service functions that return wrong results, mutate inputs, or reject valid input](kb:zia.sdk-go.service-defects) and [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding).

## Wrong result and unusable helpers

**Admin user update.** `UpdateAdminUser` in the ZTW package passes the admin user by value to the PUT helper, which builds its response object with `reflect.New` (a pointer), then asserts the response to the value type `AdminUsers`. The assertion fails, its failure is discarded, and whenever the PUT succeeds the function returns a pointer to a zero-value `AdminUsers` with a nil error, whatever body the server returned. [cloud-connector.sdk-go.service-defects:update-admin-user-zero-result] The ZTC provider at v0.2.0 does not call `UpdateAdminUser`, so the zero-value result does not reach Terraform state. The defect is observable only to other SDK callers. [cloud-connector.sdk-go.service-defects:admin-user-update-not-called-by-provider]

**Public-cloud change state.** `UpdatePublicCloudChangeState` sends its change-state PUT with a nil payload. The generic PUT helper (and the legacy ZTW client's) rejects a nil payload with an error before building any request, so the function returns an error on every call and can never change the state. [cloud-connector.sdk-go.service-defects:public-cloud-change-state-nil-payload] The ZTC provider at v0.2.0 does not call `UpdatePublicCloudChangeState`, so an operator of the provider does not meet the nil-payload error. The public cloud info resource updates through `UpdatePublicCloudInfo`, which sends a body. [cloud-connector.sdk-go.service-defects:change-state-not-called-by-provider]

## Legacy routing

**Generic calls in legacy mode.** Several ZTW services call the generic `Read`, `Create`, `UpdateWithPut`, and `Delete` on the client, which are the ZIA request methods. In legacy-client mode those hand the call to the ZIA legacy client (`LegacyClient.ZiaClient`), while their ZTW counterparts `ReadResource`, `CreateResource`, `UpdateWithPutResource`, and `DeleteResource` hand it to the ZTW legacy client. The affected services are activation, the provisioning URL, workload groups, and the shared `ReadPage` helper that the ZPA-resource lookup uses. [cloud-connector.sdk-go.service-defects:ztw-services-use-generic-legacy-path] The ZTC provider's legacy mode builds only a ZTW legacy client, so the generic ZIA-routed calls above find no ZIA legacy client and return the SDK's "legacy client not set" error. In that mode the activation status read (resource and data source) and the provisioning URL create, update, and delete fail while the other ZTC resources, which use the `...Resource` methods, work (except ZPA-resource lookups, which also go through the generic path). [cloud-connector.sdk-go.service-defects:legacy-ztw-only-client-fails-generic-calls] The generic ZIA-routed `Read`, `Create`, `UpdateWithPut`, and `Delete` return the "legacy client is not set" error only inside the branch guarded by `UseLegacyClient`; when that flag is not set they send the request through the shared OneAPI request path. The ZTC provider's `use_legacy_client` argument is an optional boolean with no default. [cloud-connector.sdk-go.service-defects:oneapi-mode-skips-legacy-client-check] The same defect in ZCC is in [ZCC SDK calls in legacy-client mode routed to the ZIA client](kb:zcc.sdk-go.legacy-routing).

## Update results dereferenced without a check

**Ignored assertion before dereference.** `forwarding_rules.Update` ignores the result of its type assertion and then reads the rule's ID. The shared update helper returns a nil result with a nil error for an empty reply body, so if the API answers the PUT with an empty body (for example 204 No Content) the call panics with a nil pointer dereference instead of returning an error. [cloud-connector.sdk-go.service-defects:ztw-update-deref-after-ignored-assertion] The same ignored-assertion-then-dereference update appears across the ZTW services: admin roles, DNS gateway, DNS forwarding gateway, ZIA forwarding gateway, location, location template, forwarding, DNS, and log rules, IP destination, IP, and IP source groups, network service groups and services, the provisioning URL, and workload groups. `UpdatePublicCloudInfo` and the activation functions check the assertion and return an error instead. [cloud-connector.sdk-go.service-defects:ztw-update-deref-same-pattern] The ZTC provider at v0.2.0 calls these update functions from the update paths of its forwarding, DNS, and log rule resources, gateways, groups, services, location template, and provisioning URL resources, and discards the returned value, so it relies on the SDK call not panicking. The provider installs no `recover`, so a panic ends the provider process. The rule resources also call `forwarding_rules.Update` from the reorder helpers. [cloud-connector.sdk-go.service-defects:provider-reaches-ztw-update-deref] Whether any ZTC endpoint answers a PUT with an empty body is open [gap:cloud-connector.sdk-go.service-defects:ztw-update-empty-reply]. The rule update path also interacts with reordering; see [How the ZTC (Cloud Connector) Terraform provider applies rule order](kb:cloud-connector.terraform.rule-order).

## Pointer arguments dereferenced before validation

`forwarding_rules.Create` and `Update` take a pointer and dereference it (`*rules`) when building the call to the generic helper. A nil pointer panics at that dereference. The generic helpers' own nil-payload checks cannot catch it, because the value passed to them is already a struct copy that is never a nil interface. [cloud-connector.sdk-go.service-defects:pointer-mutators-deref-before-nil-check] The same dereference of a pointer parameter precedes the generic call in the create and update functions of the other ZTW services: admin roles, DNS gateway, DNS forwarding gateway, ZIA forwarding gateway, location, location template, account groups, public cloud info (including `GenerateExternalID`), discovery permissions, DNS and log rules, IP destination, IP, and IP source groups, network service groups and services, API keys, the provisioning URL, and workload groups. [cloud-connector.sdk-go.service-defects:pointer-mutators-same-pattern] The ZTC provider's create and update paths pass the address of a locally built request (`&req`) or a rule taken from a list, so the provider does not hand these functions a nil pointer. [cloud-connector.sdk-go.service-defects:provider-passes-non-nil-pointers]

## Zero values in the written body

**VPC information.** The ZTW location request holds `VPCInfo` by value with `omitempty`, and `VPCInfo` holds `CloudMeta` by value with `omitempty`. Every member of both structs is itself `omitempty`. [cloud-connector.sdk-go.service-defects:location-vpc-info-value-structs] Creating or updating a location with the VPC information left unset therefore sends `"vpcInfo":{"cloudMeta":{}}` rather than omitting the member. The ZTC provider at v0.2.0 does not reach this: its location management resource is commented out and unregistered, and the location data source only reads. [cloud-connector.sdk-go.service-defects:location-write-emits-empty-vpc-object] What the location API does with an empty object is open [gap:cloud-connector.sdk-go.service-defects:ztw-empty-vpc-object-semantics].

**Location template.** The location template request carries `Editable` as a plain bool with no `omitempty`, and the provider's request builder never sets it. Every create and update of a location template therefore sends `"editable":false` (top level and in the nested `template` object), including an update of a template the server reported as editable. Whether the server honors or ignores that field on a PUT is not established. [cloud-connector.sdk-go.service-defects:location-template-editable-always-false] Whether a template PUT replaces the whole object or merges is open [gap:cloud-connector.sdk-go.service-defects:ztw-update-replaces-template].

What to check:
1. When a location template update changes fields the configuration never mentions, compare the PUT body with a fresh read.
2. Which ZTC update endpoints answer a PUT with an empty body, from live status codes, before treating the update panic as latent.

- [cloud-connector.sdk-go.service-defects:provider-passes-non-nil-pointers] Tier B: Same search as for the update call sites (`git grep -n -E '\.(Update|Create)[A-Za-z]*\(ctx' v0.2.0 -- ztc`); every match reviewed passes `&req`, `&rule`, or a rule variable from the enclosing list loop. The update does not read the template first, so response-only fields the schema lacks are also absent from the body. Effect on the server is gap ztw-update-replaces-template.
