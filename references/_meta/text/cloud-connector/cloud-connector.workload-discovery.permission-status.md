# AWS account permission status: Pending, Allowed, Denied, and refreshing it (cloud-connector.workload-discovery.permission-status)
Also called: aws account stuck pending; aws account denied workload discovery; permissionStatus; refresh aws account zscaler; latest sync aws account; verify discovery permissions

An account's permission status is Pending, Allowed or Denied. [cloud-connector.workload-discovery.permission-status:three-states] Allowed means the IAM role was correctly deployed and the service can discover tags. Denied means the service cannot assume the role provided; the role must be properly deployed and its trust policy must use the correct Zscaler role and external ID. Pending means the account was added but is waiting for the role to be deployed; once the role is deployed and the Zscaler admin syncs it, the status moves to Allowed or Denied. [cloud-connector.workload-discovery.permission-status:state-meanings]

**Moving out of Pending.** After an account is onboarded, the trusted role is set in AWS and the account is refreshed in the Admin Console; the status then updates from Pending to Allowed or Denied. [cloud-connector.workload-discovery.permission-status:refresh-moves-state] The Latest Sync column shows the last time the account synced; after refreshing, it displays the time when the user clicked the Refresh button. [cloud-connector.workload-discovery.permission-status:latest-sync-is-refresh-time] Deploying the role is therefore not described as enough on its own: the documented move out of Pending follows an admin refresh or sync. [cloud-connector.workload-discovery.permission-status:sync-needed] Whether the service ever re-checks on its own is not stated [gap:cloud-connector.workload-discovery.permission-status:automatic-recheck].

**What a status means for tags.** Tags are discovered for an Allowed account; a Denied account, whose role the service cannot assume, yields no tags for its workloads. [cloud-connector.workload-discovery.permission-status:denied-no-tags] An account whose external ID is regenerated without updating the role in AWS no longer matches the trust policy, so its next check is expected to end in Denied. [cloud-connector.workload-discovery.permission-status:regenerated-id-denies]

**Through the API.** The API verifies an AWS account's permissions with a PUT carrying the discovery role and the external ID. [cloud-connector.workload-discovery.permission-status:verify-endpoint] The SDKs and the contract name that path parameter three different ways [gap:cloud-connector.workload-discovery.permission-status:verify-path-id]. The API contract carries `permissionStatus` on the account, described as whether the provided credentials (external ID and AWS role name) have permission to access the AWS account, with no type or value list. [cloud-connector.workload-discovery.permission-status:permission-status-in-contract] The Go SDK's account struct has the permission status field commented out, so Go SDK callers cannot read it from a returned account. [cloud-connector.workload-discovery.permission-status:go-permission-status-commented-out] The Python SDK model reads `permissionStatus` into `permission_status`, and the create docstring lists `permission_status` as an optional string with the example value "TBD". [cloud-connector.workload-discovery.permission-status:python-permission-status]

What to check:
1. Whether the account was refreshed after the role was deployed; a Pending account with a deployed role may only need a refresh.
2. For a Denied account, whether the role exists in the account ID that was entered and its trust policy names the Zscaler trusted role and the current external ID.
3. Read the status with the Python SDK or the API, since the Go SDK does not expose it.
