# Cloud Connector on AWS: provisioning template, URL, Secrets Manager credentials, user data (cloud-connector.aws.provisioning)
Also called: cloud connector provisioning url aws; cloud connector secrets manager; cloud connector api_key username password secret; cloud connector user data; userdata.cfg cloud connector; CC_URL SECRET_NAME HTTP_PROBE_PORT; cloud connector not registering aws; imdsv2 cloud connector; cloud connector location template

An AWS Cloud Connector registers with Zscaler using the provisioning URL of an AWS provisioning template and admin credentials held in AWS Secrets Manager.

**Admin Console side.** Zscaler recommends a dedicated admin role for Cloud Connector deployment, with full access to Location Management and Cloud Connector Provisioning and all other permissions set to None. [cloud-connector.aws.provisioning:dedicated-admin-role] Cloud Connector uses the Cloud & Branch Connector API key to authenticate and register the AMI with Zscaler. [cloud-connector.aws.provisioning:api-key] The cloud provisioning template for AWS sets the cloud provider to AWS, location creation and Cloud Connector group creation to Automatic, a location template, a VM size and autoscaling; its cloud provisioning URL is copied for the deployment. [cloud-connector.aws.provisioning:provisioning-template] Locations are created automatically when Cloud Connector is deployed to AWS, so configuring a location template is optional. [cloud-connector.aws.provisioning:locations-automatic] The size chosen here must match the deployment: [Cloud Connector on AWS: VM size, EC2 instance type, and matching the provisioning template](kb:cloud-connector.aws.instance-sizing).

**AWS side.** The Secrets Manager secret is an other-type secret with the keys api_key (the Admin Console API key), username and password (the dedicated deployment admin's Admin Console credentials). [cloud-connector.aws.provisioning:secret-keys] The secret is encrypted with aws/secrets manager, the KMS key Secrets Manager creates by default, or with a custom-managed KMS key; with a custom key the IAM user or role must have kms:decrypt. [cloud-connector.aws.provisioning:custom-kms] The IAM role attached to the Cloud Connector instance must carry a Secrets Manager read policy (Help names it SecretsManagerRead); if it does not, Help says to attach the correct role and re-create the instance, and to replicate the secret from a working region to new regions. [cloud-connector.aws.provisioning:secret-iam]

**How the inputs reach the instance.** The reference CCVM module takes the bootstrap as a single `user_data` string described as "Cloud Init data" and passes it base64-encoded to the instance. [cloud-connector.aws.provisioning:module-user-data] The base_1cc and base_cc_gwlb_asg reference Terraform examples write user data as a [ZSCALER] section with CC_URL (the provisioning URL), SECRET_NAME, HTTP_PROBE_PORT and FIPS_ENABLED. [cloud-connector.aws.provisioning:example-user-data] The autoscaling module sets the user data, base64-encoded, on the launch template it creates, and the group launches from that template at version `$Latest` by default. [cloud-connector.aws.provisioning:asg-launch-template-user-data] The autoscaling Lambda module also receives the provisioning URL and secret name, as the CC_URL and SECRET_NAME environment variables. [cloud-connector.aws.provisioning:lambda-holds-url] Help says IMDSv2 is enforced by default for Cloud Connector on AWS; the reference CCVM module's `imdsv2_enabled` defaults to true and sets the metadata `http_tokens` to required. [cloud-connector.aws.provisioning:imdsv2] When the AMI reads these inputs is not documented [gap:cloud-connector.aws.provisioning:boot-time-read]. FIPS mode is one of these user-data settings: [Zscaler's Terraform modules for Cloud Connector on AWS: examples, defaults, FIPS, Transit Gateway](kb:cloud-connector.aws.reference-modules).

**When registration fails.** When a Cloud Connector does not appear after provisioning, Help says to confirm the provisioning template is for AWS and that the CloudFormation or Terraform run used the correct provisioning URL; if it used an incorrect one, remove the instance and create a new one. [cloud-connector.aws.provisioning:wrong-url-recreate] Help says to verify the bootstrap file was imported by running cat /etc/cloud/cloud.cfg.d/userdata.cfg over SSH and confirming the Terraform and CloudFormation variables are present; if they are not, re-create the appliance. [cloud-connector.aws.provisioning:userdata-cfg-check] Whether a regenerated URL leaves an autoscaling launch template stale is not documented [gap:cloud-connector.aws.provisioning:stale-url-launch-template]. The full not-registered checklist is in [Troubleshooting Cloud Connector on AWS: not registering, inactive, no tunnel, no Private Access](kb:cloud-connector.aws.troubleshooting).

**CloudFormation templates.** The CloudFormation launch user data is a [ZSCALER] section with CC_URL (the provisioning URL), SECRET_NAME taken directly from the secret-name parameter, HTTP_PROBE_PORT falling back to 50000 when the probe port is empty, and FIPS_ENABLED from the FipsEnabled parameter. [cloud-connector.aws.provisioning:cfn-user-data] Both CloudFormation deployment templates reject an empty provisioning URL and accept only a URL on an admin or connector host with an api/v1/provUrl path, and the autoscaling template notes that its provisioning template needs Auto Scaling enabled in Group Information. [cloud-connector.aws.provisioning:cfn-prov-url] Both CloudFormation launch templates require IMDSv2 (HttpTokens required) on the Cloud Connector instances, and the autoscaling launch template also enables instance metadata tags. [cloud-connector.aws.provisioning:cfn-imdsv2] The secret named in the stack is read by the macro at stack time through secretsmanager get_secret_value, so the secret has to exist in the stack's Region under that name, ZS/CC/credentials by default. [cloud-connector.aws.provisioning:macro-secret-read]

What to check:
1. Whether the provisioning template is an AWS template and the deployment used its URL.
2. Whether the Secrets Manager secret holds api_key, username and password for a deployment admin whose role has Location Management and Cloud Connector Provisioning access, in the region of the instance.
3. Whether /etc/cloud/cloud.cfg.d/userdata.cfg on the appliance contains the provisioning URL and secret name.
4. For an autoscaling group, whether the launch template and the Lambda still carry the current provisioning URL.
5. Whether the Secrets Manager secret named in a CloudFormation stack exists in the stack's Region before the stack is created.
