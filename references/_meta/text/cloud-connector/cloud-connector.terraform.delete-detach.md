# How the ZTC Terraform provider detaches references before deleting objects (cloud-connector.terraform.delete-detach)
Also called: ztc terraform destroy network service group; DetachRuleIDNameExtensions ztc; ztc_network_service_groups destroy; ztc destroy ip source group still referenced; ztc destroy ip pool group; group deleted but forwarding rule still references it

Before deleting a group-like object, the ZTC provider edits the forwarding rules that reference it to drop the object. The helper matches the ZIA one in structure, and so do most of its faults. Up to tf-zia v4.8.12 the ZTC helper had the same control flow as the ZIA helper: list all rules once, filter the target ID out of one field, sleep five seconds, re-read and discard, then PUT the stale copy only when the re-read succeeded. The differences were the rule type (forwarding rules here, firewall filtering rules there) and the number of callers (four here, nine there). From tf-zia v4.8.13 the ZIA helper also returns no error, skipping the sweep, when listing the rules fails with a 403 such as NOT_SUBSCRIBED, while the ZTC helper at the pin still returns the list error (#613). ZTC's helper carries no RESOURCE_IN_USE comment. [cloud-connector.terraform.delete-detach:ztc-helper-matches-zia-except-rule-type] The ZIA version is covered in [How the ZIA Terraform provider detaches references before deleting objects](kb:zia.terraform.delete-detach); the claims here are quoted from the ZTC code, not inherited. Four resources call this helper on delete: IP destination groups, IP source groups, network services, and network service groups. [cloud-connector.terraform.delete-detach:helper-callers] The `resource` string a caller passes to the helper is used only in a log line. Which field is swept is decided entirely by the getter and setter closures. [cloud-connector.terraform.delete-detach:helper-label-selects-nothing]

**Which rules are swept.** The helper lists forwarding rules and nothing else, and its getter and setter closures are typed on the forwarding rule model. It never lists the DNS rules or log rules. [cloud-connector.terraform.delete-detach:helper-sweeps-forwarding-rules-only] In the Go SDK, forwarding rules, DNS rules and log rules use three separate endpoints: `/ztw/api/v1/ecRules/ecRdr`, `/ztw/api/v1/ecRules/ecDns` and `/ztw/api/v1/ecRules/self`. [cloud-connector.terraform.delete-detach:rule-types-are-separate-endpoints] So listing forwarding rules does not return DNS or log rules. [cloud-connector.terraform.delete-detach:forwarding-list-excludes-other-rule-types] The DNS rule model has its own source and destination IP group fields, and the ZTC DNS rule resource writes them. They use the same field names and reference type as the forwarding-rule fields that the IP source group and IP destination group deletes sweep. [cloud-connector.terraform.delete-detach:dns-rules-reference-ip-groups] The IP source group and IP destination group deletes remove the group whenever the helper returns no error. Their closures cover only the forwarding rule's `SrcIpGroups` and `DestIpGroups` respectively. [cloud-connector.terraform.delete-detach:ip-group-delete-follows-detach] So deleting an IP source group or IP destination group never removes it from DNS rules that use it. The detach step edits only forwarding rules, and the delete follows regardless. [cloud-connector.terraform.delete-detach:ip-group-references-in-dns-rules-not-detached]

**Network service groups.** Deleting a network service group calls the helper labelled "NwApplicationGroups", with getter and setter closures over the forwarding rule's `NwApplicationGroups` field. [cloud-connector.terraform.delete-detach:service-group-delete-sweeps-nw-application-groups] The forwarding rule model has separate `NwApplicationGroups` and `NwServiceGroups` fields, and the ZTC forwarding rule resource writes its `nw_service_groups` argument to `NwServiceGroups`. [cloud-connector.terraform.delete-detach:forwarding-rule-separates-service-groups] The network service group delete calls `DeleteNetworkServiceGroups` only after the helper returns no error; a helper error is returned first and the delete call is not reached. [cloud-connector.terraform.delete-detach:service-group-delete-follows-detach] So deleting a network service group never removes the group from the `nwServiceGroups` of the forwarding rules that use it, and the delete follows regardless. [cloud-connector.terraform.delete-detach:service-group-references-not-detached] The same sweep removes any entry whose numeric ID equals the network service group's ID from the network application groups of every forwarding rule, a different kind of object. [cloud-connector.terraform.delete-detach:service-group-delete-can-strip-unrelated-application-groups]

**The detach loop.** For each rule that references the object, the helper first re-reads the rule. If that read fails, the rule is skipped: the update is inside `if err == nil`, and the failure is neither logged nor returned, so the helper still returns nil. [cloud-connector.terraform.delete-detach:get-failure-skips-update-silently] The re-read is only an existence gate: its result is discarded, and the update sends the rule copy taken from the earlier listing. [cloud-connector.terraform.delete-detach:reread-result-discarded] The helper sleeps five seconds for each rule that references the object, before re-reading it; the sleep runs even when that re-read returns an error and the rule's update is skipped. [cloud-connector.terraform.delete-detach:five-second-sleep-per-rule] In the Go SDK, the forwarding rule update is a PUT of the rule struct it is given. [cloud-connector.terraform.delete-detach:update-is-put-of-snapshot] So the detach writes back the rule as it was when the helper listed all rules, minus the one reference, after a five-second wait and a re-read it ignores. Edits made to that rule in between are not part of what is sent. [cloud-connector.terraform.delete-detach:stale-snapshot-put] So a transient failure re-reading one referencing rule leaves that rule attached, yet the group delete is still attempted and the resource reports success if ZTC accepts it. The operator sees either an in-use refusal on the delete or a deleted group still referenced in policy. [cloud-connector.terraform.delete-detach:masked-read-failure-reaches-delete]

**IP pool groups.** The IP pool group resource deletes the pool directly and does not call the detach helper. [cloud-connector.terraform.delete-detach:ip-pool-delete-calls-no-detach] Whether that matters, and whether DNS forwarding objects ever hold a pool reference, is not shown by the code [gap:cloud-connector.terraform.delete-detach:ip-pool-references].

Protection of predefined rules against deletion is in [Whether the ZTC Terraform provider protects predefined traffic rules](kb:cloud-connector.terraform.rule-protection); rule ordering is in [How the ZTC (Cloud Connector) Terraform provider applies rule order](kb:cloud-connector.terraform.rule-order).

What to check:
1. Which forwarding rules hold a network service group before destroying it (`nwServiceGroups`), and detach it by hand or in the same plan.
2. Which DNS rules hold an IP source or destination group before destroying it (`srcIpGroups`, `destIpGroups`).
3. Which rules and gateways reference an IP pool group before destroying it.
4. Whether the rules that used a destroyed object were re-read afterwards, rather than trusting a successful apply.
5. Whether any rule is edited while a destroy is detaching from it, since the PUT may replace the whole rule.
6. Whether a network service group ID can collide with a network application group ID, since the sweep matches on ID alone.
7. Whether ZTC refuses or accepts a delete of an object that live rules still reference.

- [cloud-connector.terraform.delete-detach:service-group-references-not-detached] Tier B: Depends on no other code in the delete path touching nwServiceGroups (the delete function body at both refs contains only the helper call and the group delete). What ZTC then does with a group that rules still reference is gap in-use-enforcement.
- [cloud-connector.terraform.delete-detach:service-group-delete-can-strip-unrelated-application-groups] Tier C: Code shows the match is on ID alone. It matters only if a network service group and a network application group can share a numeric ID (gap id-namespace).
- [cloud-connector.terraform.delete-detach:ip-group-references-in-dns-rules-not-detached] Tier B: Depends on no other code in the two delete functions touching DNS rules (each body at both refs contains only the helper call and the group delete), and on the DNS rules actually holding references to these groups on the server. What ZTC then does with a group that rules still reference is gap in-use-enforcement. Log rules were not found to have IP group fields in the SDK model (grep of srcIpGroups|destIpGroups over traffic_log_rules.go at v3.8.40 returned nothing).
- [cloud-connector.terraform.delete-detach:stale-snapshot-put] Tier B: Depends on ZTC treating the PUT as a replacement of the rule and not merging or rejecting a stale body (gap put-semantics). The listing is taken once, before the loop, so with several referencing rules the later snapshots are older still.
- [cloud-connector.terraform.delete-detach:masked-read-failure-reaches-delete] Tier B: Depends on how ZTC answers a delete of an object that rules still reference (gap in-use-enforcement); no captured source states it.
- [cloud-connector.terraform.delete-detach:ztc-helper-matches-zia-except-rule-type] Tier B: Line-by-line comparison of the helper bodies at tf-zia v4.8.3 and tf-ztc v0.2.0; the two differ only in the package names, the model type, and `GetAll(ctx, service)` versus `GetAll(ctx, service, nil)`.
