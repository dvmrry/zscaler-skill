# Troubleshooting Cloud Connector on GCP: not registering, inactive, routing by network tags, private apps and IP forwarding (cloud-connector.gcp.troubleshooting)
Also called: gcp cloud connector troubleshooting; cloud connector gcp not in console; cloud connector gcp inactive; cloud connector gcp wrong geolocation; pkg update cloud connector gcp; userdata.cfg cloud connector

This is the GCP counterpart of [Troubleshooting Cloud Connector on AWS: not registering, inactive, no tunnel, no Private Access](kb:cloud-connector.aws.troubleshooting); the deployment it troubleshoots is in [Cloud Connector on GCP: deployment, service accounts and network shape](kb:cloud-connector.gcp). For a deployed Cloud Connector missing from the console, the checks include verifying the user data (in GCP Secret Manager or in /etc/cloud/cloud.cfg.d/userdata.cfg on the appliance), that the provisioning URL has the correct format with no spaces, that the service account the Cloud Connector uses has the Secret Manager Secret Accessor role, and that sudo pkg update works to confirm the package repository is reachable and certificates are valid. [cloud-connector.gcp.troubleshooting:not-in-console]

**Deployment and registration.** When the Terraform script fails to create a VPC in a greenfield deployment, the troubleshooting table says to check whether the user has surpassed the VPC creation limit. [cloud-connector.gcp.troubleshooting:vpc-limit] For console sign-in failures, the troubleshooting table says to contact Zscaler Support when the Cloud Connector SKUs are not enabled, and when authentication failed to verify that the username and all credentials are valid and confirm in the Admin Console that the admin exists. [cloud-connector.gcp.troubleshooting:login-fails] The troubleshooting page says to configure SSH keys exclusively using Terraform during deployment. [cloud-connector.gcp.troubleshooting:ssh-keys]

**Inactive or misplaced connectors.** For an inactive Cloud Connector, the checks include that GCP Secret Manager has the correct secret credentials in case of a secrets rotation, that the network is connected (route tables, Cloud NAT and DNS), and that the firewall rule is not blocking the Cloud Connector TCP/UDP 443 traffic. [cloud-connector.gcp.troubleshooting:inactive] When a Cloud Connector shows the wrong geolocation in the Zscaler Admin Console, the troubleshooting table says to verify that the outbound NAT and routing take the appropriate egress path. [cloud-connector.gcp.troubleshooting:wrong-geolocation]

**Workload traffic.** For internet access failures, the ingress and egress checks include reviewing network tags, depending on the architecture chosen, so that workloads and Cloud Connectors use the correct default route. [cloud-connector.gcp.troubleshooting:routing-tags] For private application failures, the checks include that the Terraform template's Private Access endpoint parameters (specifically the GCP Cloud DNS forwarding rules) are accurate, that the application name matches the GCP Cloud DNS forwarding configuration, and, when FQDN-based Private Access App Segments are in use, that DNS is passing through the Cloud Connector. [cloud-connector.gcp.troubleshooting:private-apps] IP forwarding must be enabled on the Cloud Connector service interface to avoid connectivity disruptions and/or unreachable destinations; it is enabled by default on the service NIC with the Zscaler Terraform deployment script. [cloud-connector.gcp.troubleshooting:ip-forwarding] When traffic is not restored after a Cloud Connector failure, the checks include that the Cloud Connector instance is healthy in the GCP Load Balancing console and that the backup instance is in good health with the high-availability model. [cloud-connector.gcp.troubleshooting:traffic-not-restored]

**Vault credentials.** Credentials kept in HashiCorp Vault have their own troubleshooting table in [GCP Cloud Connector credentials in HashiCorp Vault: KV secret, service accounts, IAM auth role, VM metadata and troubleshooting](kb:cloud-connector.gcp.hashicorp-vault).

What to check:
1. For a connector missing from the console, whether the user data, provisioning URL format, Secret Manager Secret Accessor role and package repository reachability are in order.
2. For an inactive connector, whether Secret Manager holds the current credentials after a rotation and whether routes, Cloud NAT, DNS and firewall rules allow TCP/UDP 443.
3. Whether IP forwarding is enabled on the service interface and the network tags put workloads and connectors on the correct default route.
4. For private application failures, whether the Terraform Private Access endpoint parameters and application name match the GCP Cloud DNS forwarding configuration.
