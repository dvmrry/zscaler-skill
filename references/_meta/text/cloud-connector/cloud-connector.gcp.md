# Cloud Connector on GCP: deployment, service accounts and network shape (cloud-connector.gcp)
Also called: gcp cloud connector; google cloud cloud connector; cloud connector gcp deployment; deploy cloud connector gcp; cloud connector gcp service accounts; cloud connector gcp vpc; cloud connector gcp route; cloud connector gcp regions; gcp deployment templates cloud connector

This is the customer-deployed Cloud Connector VM path on GCP, distinct from the Zscaler-managed GCP Zero Trust Gateway in [GCP Zero Trust Gateway: managed service boundary and restrictions](kb:cloud-connector.gcp-ztg). It covers the deployment method, the identities involved and the network shape; autoscaling, the Terraform package and workload discovery have their own subjects.

**Deployment contract.** Deployment uses Terraform: [The GCP deployment guide deploys Cloud Connector as a VM using Terraform.](kb:cloud-connector.regions.deployment:gcp-terraform), from the Terraform repositories in [AWS deployment templates are available as CloudFormation and as Terraform, and Azure and GCP deployment templates as Terraform; the AWS Terraform templates deploy into a new or existing VPC.](kb:cloud-connector.aws:iac-paths). The template-type rule is [Deploy an autoscaling group only with an autoscaling (ASG) template, and a non-autoscaling deployment only with a non-ASG template.](kb:cloud-connector.overview.groups:template-match). The GCP provisioning template selects GCP as cloud provider, creates Cloud Connector groups automatically, and yields the cloud provisioning URL used for deployment. [cloud-connector.gcp:gcp-provisioning-template] The Marketplace image and its versions are in [Zscaler's GCP Terraform package for Cloud Connector: image, NICs, Pub/Sub Editor, FIPS and zsec defects](kb:cloud-connector.gcp.terraform-modules).

**Regions.** Supported regions for the GCP VM, and the uncaptured 2026 release note about the Marketplace image, are open in [Region availability of the customer-deployed Cloud Connector VM](kb:cloud-connector.regions.deployment:standard-cc-regions).

## Service accounts

- **Deployment.** The deployment service account runs Terraform and needs Compute Instance Admin (v1), Compute Network Admin, Compute Security Admin, Service Account Admin, Service Account User, Secret Manager Admin, Project IAM Admin, optionally DNS Administrator, and for autoscaling Cloud Functions Admin, Cloud Scheduler Admin and Storage Admin. [cloud-connector.gcp:deployment-sa]
- **Cloud Connector VM.** The Cloud Connector VM service account lets connectors read their secret credentials: it needs Secret Manager Secret Accessor (Secret Manager) or Service Account Token Creator with compute.instanceGroups.list, compute.instances.get and service-account read and signJwt permissions (HashiCorp Vault), and Monitoring Metric Writer, which the deployment guide marks autoscaling only. [cloud-connector.gcp:vm-sa] Each Cloud Connector VM needs a service account assigned, which Terraform can create during deployment or the operator can create beforehand. [cloud-connector.gcp:vm-sa-creation]
- **Cloud Run functions.** In autoscaling deployments a separate service account runs the Health Monitor and Resource Sync Cloud Run functions to read metrics and terminate and replace VMs; it needs Compute Instance Admin (v1) (or a custom role, which the Terraform modules create by default), Monitoring Viewer, Logs Writer, Cloud Run Invoker, and Secret Manager Secret Accessor or Service Account Token Creator. [cloud-connector.gcp:function-sa]

Before running Terraform, enable the Compute Engine, Cloud DNS, Cloud Resource Manager, IAM and Secret Manager APIs, and for autoscaling also the Cloud Functions, Cloud Scheduler, Cloud Monitoring, Cloud Logging and Cloud Build APIs. [cloud-connector.gcp:required-apis] The deployment credentials (username, password and api_key) are stored either in GCP Secret Manager, as one JSON secret with those three keys, or in HashiCorp Vault. [cloud-connector.gcp:credential-storage] Setting up Vault is in [GCP Cloud Connector credentials in HashiCorp Vault: KV secret, service accounts, IAM auth role, VM metadata and troubleshooting](kb:cloud-connector.gcp.hashicorp-vault), and troubleshooting a GCP connector is in [Troubleshooting Cloud Connector on GCP: not registering, inactive, routing by network tags, private apps and IP forwarding](kb:cloud-connector.gcp.troubleshooting).

## Network shape

The security stack goes in a dedicated GCP project or the workload project; because GCP requires a separate VPC for each interface of a multi-interface instance, a Cloud Connector deployment needs two VPCs, one for management and one for service and security, and workload VPCs need custom routes to the load balancer in front of the connectors. [cloud-connector.gcp:two-vpcs] After deployment, the workload instance gets a network tag and a static IPv4 route for 0.0.0.0/0 is created in the workload's VPC with next hop a forwarding rule of an internal TCP/UDP load balancer, with the network tag attached to the route. [cloud-connector.gcp:workload-route] Once deployment is verified, Traffic Forwarding, Log and Control Forwarding, and DNS Control policies can be configured for the GCP connectors. [cloud-connector.gcp:post-deploy-policies]

**Templates.** Help groups its GCP templates as Basic Deployment Templates (`base_1cc`, `base_1cc_zpa`), Deployment Templates with Load Balancer (`base_cc_ilb`, `base_cc_ilb_zpa`, `cc_ilb`) and Deployment Templates with Managed Instance Group (MIG) Autoscaling (`base_cc_asg`, `base_cc_asg_zpa`, `cc_asg`); the Basic group has a starter and a starter-with-Private-Access template, and each of the other two has a starter, a starter-with-Private-Access and a custom template. [cloud-connector.gcp:template-families] The GCP Starter Deployment Template (`base_1cc`) creates, among its resources, a Cloud Connector instance template and a user-managed service account attached to the Cloud Connector VM with access to Secret Manager or HashiCorp Vault depending on the chosen authentication method. [cloud-connector.gcp:template-resources]

What to check:
1. Whether the deployment matches the template type: an autoscaling deployment with an autoscaling template, a static one with a non-autoscaling template.
2. Which of the three service accounts holds which roles, and whether the credentials are read from Secret Manager or HashiCorp Vault.
3. Whether the workload route is a 0.0.0.0/0 static route to the internal load balancer forwarding rule, scoped to the workload network tag.
4. Which region the deployment targets, since no source lists the supported regions for standard Cloud Connector on GCP.
