# Zscaler's Azure Terraform package for Cloud Connector: image, VM sizes, provider constraint, examples and FIPS (cloud-connector.azure.terraform-modules)
Also called: terraform-azurerm-cloud-connector-modules; azure cloud connector terraform; azure cloud connector marketplace image; zia_cloud_connector; zs_ser_gen1_cc_01; az vm image terms accept; ccvm_instance_type azure; Standard_D2ds_v5; Standard_DS2_v2; azurerm provider version cloud connector; azure cloud connector examples; zsec azure; fips_enabled azure; LegacyVMNVA; enable_legacy_vm_nva_tag; MANA cloud connector

Zscaler's Azure Terraform package is a reference implementation: its modules, example roots and the zsec helper script each enforce their own defaults and checks, and those layers do not always agree with each other or with the package's own documentation. Nothing here is a Cloud Connector service limit unless a claim says so.

**Image.** Both direct modules default to the Azure Marketplace image with publisher `zscaler1579058425289`, offer `zia_cloud_connector`, SKU `zs_ser_gen1_cc_01` and version `latest`. [cloud-connector.azure.terraform-modules:image-defaults] Setting `ccvm_source_image_id` to a local subscription Microsoft.Compute image replaces the Marketplace image and plan. [cloud-connector.azure.terraform-modules:image-override] The package's prerequisites require accepting the Cloud Connector VM image terms in each subscription where Cloud Connector is deployed, for example with `az vm image terms accept --urn zscaler1579058425289:zia_cloud_connector:zs_ser_gen1_cc_01:latest`. [cloud-connector.azure.terraform-modules:image-terms] What a deployment without accepted terms fails with is not captured [gap:cloud-connector.azure.terraform-modules:image-terms-error].

**VM sizes.** Both direct modules default `ccvm_instance_type` to Standard_D2ds_v5; the VM module accepts Standard_D2s_v3, Standard_DS2_v2, Standard_DS3_v2, Standard_D2ds_v5 and Standard_D2ads_v5, and the VMSS module accepts the same list without Standard_DS2_v2. [cloud-connector.azure.terraform-modules:vm-sizes] In the Azure Marketplace deployment the instance type is Small by default and the VM size is set automatically to Standard D2ds v5, which can be changed. [cloud-connector.azure.terraform-modules:marketplace-vm-size] The `zsec` helper offers VM sizes by region: Standard_DS2_v2 in chinanorth and chinaeast; Standard_DS3_v2, Standard_D2ds_v5 and Standard_DS2_v2 in chinanorth2 and chinaeast2; those plus Standard_D2ads_v5 in chinanorth3 and chinaeast3; and Standard_D2ds_v5 or Standard_D2ads_v5 everywhere else. [cloud-connector.azure.terraform-modules:zsec-size-menu] The `base_cc_vmss` example root accepts Standard_DS2_v2 in its own `ccvm_instance_type` validation and passes the value to the VMSS module. [cloud-connector.azure.terraform-modules:vmss-wrapper-ds2] Choosing Standard_DS2_v2 for a VMSS deployment (which zsec offers in the China regions) passes the example root's validation and then fails the VMSS module's validation. This is a defect between the package's layers; it says nothing about whether Azure or the Cloud Connector service would accept the size. [cloud-connector.azure.terraform-modules:ds2-vmss-fails-in-child] The changelog says otherwise about the VMSS allow-list [divergence:cloud-connector.azure.terraform-modules:ds2-vmss-allow-list].

**Provider constraint.** Both direct modules, and the `base_1cc` example root, require the azurerm provider `>= 4.9.0, < 5.0.0`. [cloud-connector.azure.terraform-modules:azurerm-constraint] The changelog and the generated READMEs give older ranges [divergence:cloud-connector.azure.terraform-modules:azurerm-constraint-docs].

## Templates and examples

Which forms each cloud's deployment templates come in is [AWS deployment templates are available as CloudFormation and as Terraform, and Azure and GCP deployment templates as Terraform; the AWS Terraform templates deploy into a new or existing VPC.](kb:cloud-connector.aws:iac-paths). Help's Azure deployment templates are `base_1cc`, `base_1cc_zpa`, `base_cc_lb`, `base_cc_lb_zpa`, `cc_lb`, `base_cc_vmss`, `base_cc_vmss_zpa`, `cc_vmss` and the standalone `ztags_standalone`, which deploys an Event Grid system topic and event subscription and no Cloud Connector resources. [cloud-connector.azure.terraform-modules:help-azure-templates] At the pin the package ships 17 example roots besides `zsec`: greenfield `base`, `base_1cc`, `base_1cc_zpa`, `base_cc_lb`, `base_cc_lb_zpa`, `base_cc_vmss`, `base_cc_vmss_zpa`, `base_cc_gwlb`, `base_cc_gwlb_vmss`, `base_cc_public_lb` and `base_cc_public_vmss`; brownfield `cc_lb`, `cc_vmss`, `cc_gwlb`, `cc_gwlb_vmss` and `cc_public_lb`; and standalone `ztags_standalone`. [cloud-connector.azure.terraform-modules:package-examples] The package README's brownfield deployment-type list is `cc_lb`, `cc_vmss`, `cc_gwlb` and `cc_gwlb_vmss` (the cc_public_lb root is not in it), while the examples README lists greenfield types `base` through `base_cc_vmss_zpa` and brownfield types `cc_lb` and `cc_vmss` only. [cloud-connector.azure.terraform-modules:readme-type-lists] No captured source describes Bicep templates for Cloud Connector; the published Azure paths are the Terraform repository and the Marketplace application. [cloud-connector.azure.terraform-modules:no-bicep] Whether ARM templates sit behind the Marketplace wizard is not covered [gap:cloud-connector.azure.terraform-modules:arm-marketplace-path].

**What each example builds.**
- `base_1cc` adds to the base deployment one Cloud Connector private subnet associated to a NAT gateway, one Cloud Connector VM, and a workload subnet UDR repointed to the Cloud Connector's service interface IP. [cloud-connector.azure.terraform-modules:ex-starter]
- `base_cc_lb` creates two Cloud Connector private subnets with two NAT gateways, two Cloud Connector VMs and a Standard Azure Load Balancer, with the workload subnet UDR routing to the load balancer frontend IP; the README calls the Standard Load Balancer Zscaler's recommended deployment method. [cloud-connector.azure.terraform-modules:ex-lb]
- The `_zpa` greenfield variants add a Private DNS Resolver, ruleset, rules per entered domain, a virtual network link and an outbound endpoint in a dedicated outbound DNS subnet. [cloud-connector.azure.terraform-modules:ex-zpa]
- `base_cc_vmss` creates one or more Flexible Orchestration scale sets with scaling policies, one Function App for VMSS and a Standard Azure Load Balancer, with the workload UDR routing to the load balancer frontend IP. [cloud-connector.azure.terraform-modules:ex-vmss]
- `base_cc_gwlb` and `cc_gwlb` deploy Cloud Connectors with an Azure Gateway Load Balancer for transparent inline traffic inspection, and `base_cc_gwlb_vmss` and `cc_gwlb_vmss` add Virtual Machine Scale Sets. [cloud-connector.azure.terraform-modules:ex-gwlb]
- `base_cc_public_lb` fronts the Cloud Connectors with an Azure Standard Public Load Balancer for inbound traffic distribution (for example fwd ZIA DNAT), implementing a routed PLB to Cloud Connector to ILB ingress topology; `base_cc_public_vmss` fronts Cloud Connector scale sets with an Azure Standard Public Load Balancer for elastic inbound traffic handling. [cloud-connector.azure.terraform-modules:ex-public-lb]
- `cc_lb` and `cc_vmss` are intended for brownfield/production use, deploying into a new or existing VNet with at least one Cloud Connector subnet and NAT gateway and a Standard Azure Load Balancer (`cc_vmss` adds scale sets and a Function App), with optional Private DNS Resolver resources per `zpa_enabled`. [cloud-connector.azure.terraform-modules:ex-brownfield]

## FIPS through user data

The changelog adds a `fips_enabled` variable for enabling FIPS mode through user data, and the `base_1cc` example root writes `FIPS_ENABLED=${var.fips_enabled}` into the `[ZSCALER]` user data. [cloud-connector.azure.terraform-modules:fips-variable] At the pin, `fips_enabled` and `FIPS_ENABLED` appear in `base_1cc`, `base_1cc_zpa`, `base_cc_lb`, `base_cc_lb_zpa`, `base_cc_vmss`, `base_cc_vmss_zpa`, `cc_lb` and `cc_vmss`, and in none of `base_cc_gwlb`, `base_cc_gwlb_vmss`, `base_cc_public_lb`, `base_cc_public_vmss`, `cc_gwlb`, `cc_gwlb_vmss` and `cc_public_lb` (nor `base` and `ztags_standalone`). [cloud-connector.azure.terraform-modules:fips-roots] For every deployment type other than `base`, the `zsec` helper asks whether to enable FIPS mode and writes `TF_VAR_fips_enabled` ('True' or 'False') to .zsecrc. [cloud-connector.azure.terraform-modules:zsec-fips-prompt] For the seven GWLB and Public LB roots, answering yes to the zsec FIPS prompt has no effect: the roots declare no `fips_enabled` input, so Terraform does not use the exported value and their user data carries no FIPS setting. This is a helper and example defect; it does not show whether the service supports FIPS on those topologies. [cloud-connector.azure.terraform-modules:fips-noop-roots] The direct VM and VMSS modules take caller-built `user_data` and declare no `fips_enabled` variable, so FIPS coverage comes from the example roots, not from the modules. [cloud-connector.azure.terraform-modules:direct-modules-no-fips]

## MANA and the LegacyVMNVA tag

Both direct modules expose `enable_legacy_vm_nva_tag` (default true), described as emitting the LegacyVMNVA tag to be set to false once MANA host support is available; when true they merge `LegacyVMNVA = "true"` into the VM or scale-set tags. [cloud-connector.azure.terraform-modules:legacy-vm-nva-tag] Help's Marketplace procedure, on the Tags tab, says to enable LegacyVMNVA to opt out of Microsoft Azure Network Adapter (MANA)-enabled hardware. [cloud-connector.azure.terraform-modules:legacy-vm-nva-help]

**Bastion public IP.** The bastion module's public IP is `Static` with `sku` set to `Standard`. [cloud-connector.azure.terraform-modules:bastion-ip-standard-sku]

What to check:
1. Whether the Marketplace image terms were accepted in the target subscription before the first apply.
2. Whether the chosen VM size is in the allow-list of the module that will receive it (the VMSS module has no Standard_DS2_v2), not only the example root's list.
3. Whether the azurerm provider in use satisfies the modules' versions.tf, not the README range.
4. Whether the selected example root declares fips_enabled before relying on the zsec FIPS answer, by reading the rendered user_data for FIPS_ENABLED.

Sources disagree (name both sides):
- Whether Standard_DS2_v2 is in the VMSS module's VM-size allow-list. [divergence:cloud-connector.azure.terraform-modules:ds2-vmss-allow-list]
  - tfmod-azure-cloud-connector: The v0.9.0 entry says the legacy sizes, Standard_DS2_v2 included, remain in the VM and VMSS allow-lists.
  - tfmod-azure-cloud-connector: The VMSS module's validator has no Standard_DS2_v2.
  Impact: Trusting the changelog, a China VMSS deployment on Standard_DS2_v2 looks supported but fails the module's validation at plan time.
  Resolved (source-rank) by cloud-connector.azure.terraform-modules:vm-sizes: The validator is what Terraform evaluates.
- Which azurerm provider versions the Azure Cloud Connector modules accept. [divergence:cloud-connector.azure.terraform-modules:azurerm-constraint-docs]
  - tfmod-azure-cloud-connector: The modules' versions.tf require >= 4.9.0, < 5.0.0.
  - tfmod-azure-cloud-connector: The v0.9.1 changelog entry says the constraint is >= 3.108.0, < 5.0.0.
  - tfmod-azure-cloud-connector: The generated VM module README (like the VMSS module and base_1cc READMEs) renders >= 3.108.0, < 5.0.0.
  - tfmod-azure-cloud-connector: The GWLB module README (like the Public LB module README) renders >= 3.108.0, <= 3.116.
  Impact: Pinning azurerm to a 3.x release from the README or changelog fails terraform init against the modules' 4.9 floor.
  Resolved (source-rank) by cloud-connector.azure.terraform-modules:azurerm-constraint: versions.tf is the constraint Terraform enforces; the README tables and changelog line are documentation.
