# Troubleshooting Cloud Connector on AWS: not registering, inactive, no tunnel, no Private Access (cloud-connector.aws.troubleshooting)
Also called: cloud connector not showing in admin console aws; cloud connector inactive aws; cloud connector wrong geolocation; cloud connector private access enrollment failed; ec2br.prod.zpath.net; pkg-repo.zscaler.com; zsroot ssh cloud connector; cloud connector cloudformation stack failed

Help's AWS troubleshooting article sorts failures by symptom. Each symptom below names its checks; bootstrap inputs are in [Cloud Connector on AWS: provisioning template, URL, Secrets Manager credentials, user data](kb:cloud-connector.aws.provisioning).

**Instance never comes up.** An instance that is not running after 20 minutes, or without 2/2 status checks after 10, should have its system log and screenshot collected and be rebooted; if it still does not pass two of two checks, delete and re-create it. [cloud-connector.aws.troubleshooting:boot-timeouts] Help says to confirm the instance type is supported in the AWS Marketplace and recommends m6i.large or m6i.4xlarge. [cloud-connector.aws.troubleshooting:supported-types]

**Not shown in the Admin Console.** For a Cloud Connector missing from the console, Help says to verify route tables, NAT gateway and internet gateway by pinging or curling an internet destination from the appliance console, and that security groups and network ACLs permit the needed inbound, outbound and workload traffic. [cloud-connector.aws.troubleshooting:network-path] The URL, secret, role and user-data checks are in [Cloud Connector on AWS: provisioning template, URL, Secrets Manager credentials, user data](kb:cloud-connector.aws.provisioning). When the Cloud Connector does not update, Help says to test pkg-repo.zscaler.com on TCP 443 from the console, where a 500 response means connectivity succeeded and a timeout points at the NAT gateway, route table or internet gateway, then check the certificate bundle and run sudo pkg update. [cloud-connector.aws.troubleshooting:package-repo]

**Deployment tooling fails.** For CloudFormation rule failures caused by user input, Help's checks are that the VPC, subnet and availability-zone stack parameters do not mismatch, and that the provisioning URL field is not empty and is in the correct format. [cloud-connector.aws.troubleshooting:cfn-input] When the stack fails and is rolled back, Help says to read the event log, confirm permissions, and confirm the AWS Marketplace terms for the Cloud Connector offering were accepted before the first deployment in the account. [cloud-connector.aws.troubleshooting:cfn-stack-fails] IAM requirements for the deployer are in [Cloud Connector on AWS: IAM for the instance, the autoscaling Lambda, and the deployer](kb:cloud-connector.aws.iam).

**Wrong location, inactive, or no tunnel.** For a Cloud Connector in the wrong geolocation, Help says to ensure its service interface is associated with the correct NAT gateway and that gateway has the correct elastic IP, or, without a NAT gateway, that the public or elastic IP on its ENI is correct. [cloud-connector.aws.troubleshooting:wrong-geolocation] For an inactive Cloud Connector, Help's checks are registration and policy fetch (through Zscaler Support), the instance running, the Admin Console reachable from the VPC, Secrets Manager credentials current after any rotation, the network path, and a security group or network ACL not blocking TCP/UDP 443. [cloud-connector.aws.troubleshooting:inactive] When the Internet & SaaS gateway IP is not populated and no tunnel forms, Help's checks are TCP/UDP 443 not blocked, the gateway configuration set to Auto, Manual with the right data center, or Override with the right IP, and pac.<cloudname>.net reachable from the VPC. [cloud-connector.aws.troubleshooting:no-gateway-ip]

**Private Access.** Private Access enrollment fails when more than 100 Cloud Connectors are deployed in one group within the same VPC or availability zone; Help says to contact Zscaler Support. [cloud-connector.aws.troubleshooting:zpa-enrollment-limit] When a Cloud Connector has no Private Access service edge IP, Help says to check that ec2br.prod.zpath.net resolves from it and that TCP/UDP 443 is allowed by the network ACL. [cloud-connector.aws.troubleshooting:zpa-dns] When workloads cannot reach private applications, Help says to check the CloudFormation Private Access endpoint parameters, that the application name matches the Route 53 configuration, and that the application is available in the Admin Console. [cloud-connector.aws.troubleshooting:private-apps]

**Traffic.** For workloads that cannot reach the internet, Help's ingress checks are a default route on the workload subnet associated to the Cloud Connector service interface ENI, and no network ACL or service-ENI security group blocking the workload subnet. [cloud-connector.aws.troubleshooting:ingress-routing] When traffic does not return after a Cloud Connector failure, Help says to check that the backup instance is healthy under the high-availability model and that the Cloud Connector is healthy in the AWS Gateway Load Balancer console. [cloud-connector.aws.troubleshooting:traffic-not-restored] Source/destination check and device indexes are in [Cloud Connector on AWS: network interfaces, device indexes, source/destination check](kb:cloud-connector.aws.interfaces); GWLB target health is in [Cloud Connector behind AWS Gateway Load Balancer: target group, health probe, stickiness, cross-zone](kb:cloud-connector.aws.gwlb).

**Getting a shell.** CLI access over SSH uses the instance key pair and the administrative login zsroot, through a bastion host or an elastic IP on the management interface; Zscaler highly recommends restricting inbound rules to known management IP sources. [cloud-connector.aws.troubleshooting:cli-ssh] Whether an SSM session still works, and how it runs admin commands, is open since the page dropped it [gap:cloud-connector.aws.troubleshooting:ssm-shell].

**Not documented.** Whether a second scaling policy on EC2 CPUUtilization conflicts with the Cloud Connector policy is not documented [gap:cloud-connector.aws.troubleshooting:competing-scaling-policy].

What to check:
1. Whether the instance is running within 20 minutes with 2/2 status checks within 10.
2. From the appliance console, whether an internet destination and pkg-repo.zscaler.com on TCP 443 are reachable.
3. Whether the service interface sits behind the NAT gateway and elastic IP expected for the Cloud Connector's geolocation.
4. For Private Access failures, whether the group has more than 100 Cloud Connectors in one VPC or availability zone, and whether ec2br.prod.zpath.net resolves.

Not known (open gaps):
- A second Auto Scaling policy on EC2 CPUUtilization [gap:cloud-connector.aws.troubleshooting:competing-scaling-policy]: settled by lab-test or source-read. Blocks: advising on custom scaling policies for Cloud Connector groups
