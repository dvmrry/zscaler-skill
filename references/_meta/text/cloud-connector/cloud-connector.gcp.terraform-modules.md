# Zscaler's GCP Terraform package for Cloud Connector: image, NICs, Pub/Sub Editor, FIPS and zsec defects (cloud-connector.gcp.terraform-modules)
Also called: terraform-gcp-cloud-connector-modules; gcp cloud connector terraform; gcp cloud connector marketplace image; zs-cc-ga-2-08132026; mpi-zscalercloudconnector-publ; grant_pubsub_editor; roles/pubsub.editor cloud connector; fips_enabled gcp; zsec gcp; cloud function zip checksum; upload_cloud_function_zip; base_cc_ilb user data json

Zscaler's GCP Terraform package (direct modules, example roots and the zsec helper) is the documented way to deploy Cloud Connector on GCP. Its layers carry different defaults and some defects; none of them is a Cloud Connector service behavior unless a claim says so.

**Image.** The CCVM module README lists image zs-cc-ga-2-08132026 in project mpi-zscalercloudconnector-publ with release date 8/28/2026, marking it and zs-cc-ga-03092026 with `*` as the minimum required for Auto Scaling, and marks images zs-cc-ga-02022025 and zs-cc-ga-10292023 (`**`) as deprecated as of April 15, 2026. [cloud-connector.gcp.terraform-modules:image-table] The example roots look up the image in project mpi-zscalercloudconnector-publ unless `custom_image_name` is set, with `marketplace_image` defaulting to zs-cc-ga-2-08132026 and described as Zscaler recommending the latest image for new instances. [cloud-connector.gcp.terraform-modules:example-image-default]

**Interfaces and user data.** The CCVM module's instance template enables IP forwarding and lists the service subnetwork as the first network interface and the management subnetwork as the second. [cloud-connector.gcp.terraform-modules:instance-template] The module passes the user data to the VM as the `ZSCALER` metadata key, and the example roots build it as JSON with `cc_url`, `http_probe_port`, `fips_enabled` and `gcp_service_account`, plus `secret_name` for Secret Manager or `hcp_vault_addr`, `hcp_vault_secret_path`, `hcp_vault_role_name` and `hcp_gcp_auth_role_type` for HashiCorp Vault. [cloud-connector.gcp.terraform-modules:user-data-metadata]

## Pub/Sub Editor grant

In the IAM service-account module, `grant_pubsub_editor` defaults to true and is described as granting roles/pubsub.editor to the CCVM service account at project scope. [cloud-connector.gcp.terraform-modules:pubsub-editor-default] When enabled, the module creates the project IAM binding for roles/pubsub.editor on either the service account it creates or a caller-supplied (bring-your-own) one, so supplying an existing account does not avoid the grant. [cloud-connector.gcp.terraform-modules:pubsub-editor-byo] The `zsec` helper asks whether to enable Workload Discovery Service integration, warning that it grants roles/pubsub.editor project-wide to the VM service account; its default answer is no, which exports `TF_VAR_grant_pubsub_editor=false`, and yes exports true. [cloud-connector.gcp.terraform-modules:zsec-wds-prompt] The example roots default `grant_pubsub_editor` to true in `base_1cc`, `base_1cc_zpa`, `base_cc_asg`, `base_cc_asg_zpa`, `base_cc_ilb`, `base_cc_ilb_zpa` and `cc_ilb`, and to false only in `cc_asg`. [cloud-connector.gcp.terraform-modules:wrapper-pubsub-defaults] Workload discovery is the feature that needs the role: [Zscaler requires the roles/pubsub.editor role on the Cloud Connector service account, which the Cloud Connector VMs use to receive workload delta messages when workload metadata changes.](kb:cloud-connector.gcp.workload-discovery:pubsub-editor-required).

## FIPS

All eight Cloud Connector example roots (`base_1cc`, `base_1cc_zpa`, `base_cc_asg`, `base_cc_asg_zpa`, `base_cc_ilb`, `base_cc_ilb_zpa`, `cc_asg`, `cc_ilb`) declare `fips_enabled` and write it into both the Secret Manager and HCP Vault forms of the JSON user data. [cloud-connector.gcp.terraform-modules:fips-examples] The `zsec` helper asks whether to enable FIPS mode and exports `TF_VAR_fips_enabled` as 'True' or 'False'. [cloud-connector.gcp.terraform-modules:zsec-fips] The direct CCVM module takes generic `user_data` and has no `fips_enabled` input, so FIPS coverage is a property of the example roots and helper, not of the module. [cloud-connector.gcp.terraform-modules:direct-module-no-fips]

**Invalid JSON in two ILB roots.** In `base_cc_ilb` and `cc_ilb`, the default (Secret Manager) user data at commit e54dbca put `"gcp_service_account": ...` with no trailing comma directly before `"fips_enabled": ...,`, which itself ended with a comma before the closing brace; later commits put `fips_enabled` before `gcp_service_account` in both, so the last entry carries no comma. [cloud-connector.gcp.terraform-modules:ilb-userdata-defect-code] With the default `hcp_vault_enabled = false`, those two roots therefore rendered user data that was not valid JSON (a missing comma and a trailing comma) at the earlier pin, and `terraform validate` does not parse heredoc content, so it did not catch it. This was an example defect, not a service FIPS or JSON behavior. [cloud-connector.gcp.terraform-modules:ilb-userdata-invalid] What the Cloud Connector VM does with that payload is not established [gap:cloud-connector.gcp.terraform-modules:invalid-userdata-outcome].

## Cloud Function ZIP handling in zsec

When `zsec` downloads a missing Cloud Function ZIP, it fetches the selected URL's .sha256 companion, compares it with a local SHA-256 and deletes the ZIP and exits on mismatch; if no checksum file is published it only warns that integrity cannot be verified and continues. [cloud-connector.gcp.terraform-modules:zsec-zip-checksum] When `upload_cloud_function_zip` is false, the Cloud Function module skips the upload and looks up an existing bucket object named by `cloud_function_source_object_name`, from which the functions are built. [cloud-connector.gcp.terraform-modules:existing-object-branch] In `zsec`, answering yes to whether the Cloud Function ZIP is already in an existing bucket sets `upload_function_zip=false` and exports the object name, but the ZIP download loop's condition quotes the whole expression `"$upload_function_zip == true"`, and the loop then writes the downloaded or locally selected ZIP's name and path to `cloud_function_source_object_name` and `cloud_function_source_object_path`. [cloud-connector.gcp.terraform-modules:zsec-quoted-condition] Because a quoted non-empty string is always true in a bash `[[ ]]` test, an ASG `zsec up` run enters the ZIP flow even after the operator chose an existing bucket object, and can replace the chosen object name with a local or downloaded ZIP's name while the upload flag stays false, so the module may look up a wrong or nonexistent object. This is a helper defect, not Cloud Connector runtime behavior. [cloud-connector.gcp.terraform-modules:zsec-zip-flow-reentered]

What to check:
1. Whether grant_pubsub_editor is set as intended for the root in use, since most example roots default it to true and the grant is project-wide.
2. Whether the rendered user data is valid JSON before deploying base_cc_ilb or cc_ilb with Secret Manager credentials.
3. Which ZIP object the Cloud Functions were built from after an ASG zsec run that chose an existing bucket object.
