# GCP Cloud Connector credentials in HashiCorp Vault: KV secret, service accounts, IAM auth role, VM metadata and troubleshooting (cloud-connector.gcp.hashicorp-vault)
Also called: hashicorp vault cloud connector gcp; hcp vault cloud connector; hcp_vault_addr; hcp_vault_secret_path; hcp_vault_role_name; bound_service_accounts cloud connector; vault gcp auth method cloud connector

HashiCorp IAM authentication integrates a HashiCorp Vault with a new GCP Cloud Connector only: an existing Cloud Connector cannot be migrated from GCP Secret Manager to HashiCorp Vault, and a new one must be deployed using the Terraform wizard. [cloud-connector.gcp.hashicorp-vault:new-deployments-only] The article describes configuring a dedicated public HashiCorp Vault, and says the procedures may differ for self-managed Vault deployments; a Vault and Vault cluster must already exist and the Vault CLI must be downloaded to the local machine. [cloud-connector.gcp.hashicorp-vault:dedicated-vs-self-managed] The Secret Manager alternative is in [The deployment credentials (username, password and api_key) are stored either in GCP Secret Manager, as one JSON secret with those three keys, or in HashiCorp Vault.](kb:cloud-connector.gcp:credential-storage).

**The secret.** The credentials are stored in a KV secrets engine, with admin set as the current namespace, as three keys: username and password (the dedicated Cloud Connector deployment username and password) and api_key (the value copied from the API Key Management page in the Zscaler Admin Console). [cloud-connector.gcp.hashicorp-vault:kv-secret]

**Service accounts.** On the storing page, the service account used for Vault is given the Service Account Key Admin role, or a custom role with 5 required permissions listed as compute.instanceGroups.list, compute.instances.get, iam.serviceAccountKeys.get, iam.serviceAccounts.get and iamService.signJwt; its private key is created as JSON and the key file is selected when the Vault GCP auth method is configured. [cloud-connector.gcp.hashicorp-vault:vault-sa] Which account holds the five permissions, and how one of them is spelled, differ between pages [divergence:cloud-connector.gcp.hashicorp-vault:vault-permissions-account]. The Vault troubleshooting page names two service accounts: the Vault/GCP sync service account, whose secrets JSON file is exported from GCP and uploaded to HashiCorp with the Service Account Key Admin GCP role, and the Cloud Connector VM service account, assigned to the VM at deployment and referenced in HashiCorp as bound_service_accounts with the Service Account Token Creator GCP role. [cloud-connector.gcp.hashicorp-vault:two-service-accounts]

**Policy and role.** A Vault policy must be created that grants read and list capabilities to access the secrets path. [cloud-connector.gcp.hashicorp-vault:acl-policy] The GCP auth role is created with the Vault CLI as type iam, with the created policy, bound_service_accounts set to the email address of the Cloud Connector VM service account, and max_jwt_exp of 60m. [cloud-connector.gcp.hashicorp-vault:iam-role] The Terraform wizard asks for the Vault cluster public URL, the full API path of the secret, the name of the access role created for an IAM service account and, if one already exists, the Service Account email from the Vault service account details. [cloud-connector.gcp.hashicorp-vault:wizard-inputs]

**On the VM.** The metadata keys for Vault address, secret path and IAM auth role must match the Vault configuration; the page's example, headed ZSCALER, shows hcp_vault_addr, hcp_vault_secret_path and hcp_vault_role_name. [cloud-connector.gcp.hashicorp-vault:vm-metadata] The Vault address, protocol and port number (8200) must be correct and outbound traffic to the Vault address on port 8200 permitted in the firewall policies; reachability is tested with nc and with curl of <vault-address>:8200/v1/sys/health, which should return a JSON health response. [cloud-connector.gcp.hashicorp-vault:port-8200]

**Troubleshooting table.** When permission is denied or authentication fails, the troubleshooting table says to verify that the service account assigned to the Cloud Connector VMs has the Service Account Token Creator role, that it is included in the Vault's bound_service_accounts, and that max_jwt_exp is correctly set in the Vault. [cloud-connector.gcp.hashicorp-vault:symptom-auth-fails] When the Vault is unreachable from the VM, the troubleshooting table says to verify that firewall rules allow outbound traffic to the Vault on port 8200 and that the Vault address and DNS resolution are correct from the Cloud Connector. [cloud-connector.gcp.hashicorp-vault:symptom-unreachable] When access to the secret path is denied after authentication succeeds, the troubleshooting table says to verify that the policies attached to the IAM authentication role include read and list permissions for the secret path and that the secret exists at the specified path. [cloud-connector.gcp.hashicorp-vault:symptom-secret-denied]

**Not settled.** Self-managed Vault steps are not given [gap:cloud-connector.gcp.hashicorp-vault:self-managed-steps], and the storing article does not name the VM service account's Token Creator role [gap:cloud-connector.gcp.hashicorp-vault:token-creator-in-storing].

What to check:
1. Whether the connector is new: an existing connector cannot be moved from Secret Manager to Vault.
2. Whether the VM's ZSCALER custom metadata keys match the Vault address, secret path and IAM auth role.
3. Which service account holds Service Account Key Admin and which holds Service Account Token Creator, and where the five permissions were granted, since the pages place them differently.
4. Whether the VM can reach the Vault on port 8200 and the secret path grants read and list to the role's policy.

Sources disagree (name both sides):
- Help gives the same five permissions (compute.instanceGroups.list, compute.instances.get, iam.serviceAccountKeys.get, iam.serviceAccounts.get and a signJwt permission) as a custom-role alternative for two different service accounts, and spells the last one two ways. [divergence:cloud-connector.gcp.hashicorp-vault:vault-permissions-account]
  - zscaler-help: The five permissions are a custom-role alternative to Service Account Key Admin for the service account used for Vault, and the last is spelled iamService.signJwt.
  - zscaler-help: The same permissions sit on the Cloud Connector VM service account under Service Account Token Creator (for HashiCorp Vault), and the last is spelled iam.serviceAccounts.signJwt.
  Impact: A custom role built from one page's list may be granted to the wrong account, and whether a role created with the iamService.signJwt spelling works is untested; the Vault troubleshooting page puts Service Account Key Admin on the sync account and Service Account Token Creator on the VM account.
