# Cloud & Branch Connector DNS policies: scope, criteria, actions, predefined rules (cloud-connector.dns.policies)
Also called: cloud connector dns policy; cloud connector dns rule; dns forwarding rule; ecRules/ecDns; ztc_traffic_forwarding_dns_rule; REDIR_REQ; REDIR_ZPA; REDIR_RES; Default Connector DNS Rule; Redirect Resolution of Zscaler Domains to WAN CTR; ZPA Resolver

DNS policies are Cloud & Branch Connector's own DNS rule engine, separate from ZIA DNS Control. Cloud & Branch Connector has its own DNS Policies feature, configured on its own page (Zero Trust Cloud > Policy > DNS Forwarding), with rules evaluated in ascending order. [cloud-connector.dns.policies:cbc-has-dns-policies] DNS policies monitor and apply policy to all DNS requests and responses whatever the protocol and encryption, including UDP, TCP and DNS over HTTPS (DoH). [cloud-connector.dns.policies:scope-doh]

**What the help says it does.** The help names DNS conditions such as users, groups or departments, client locations, categorization of domains and IP addresses, DNS record types, and the location of resolved IP addresses. [cloud-connector.dns.policies:conditions] The help names condition-based actions such as allowing or blocking traffic, redirecting requests to specific DNS servers, and redirecting users by overwriting DNS responses. [cloud-connector.dns.policies:capability-actions] DNS policies are described as detecting and preventing DNS-based attacks and data exfiltration through DNS tunnels. [cloud-connector.dns.policies:tunnels] The help also names using the Zscaler Trusted DNS Resolver for domain resolution. [cloud-connector.dns.policies:trusted-resolver] How tunnel detection triggers and how DoH is identified are not described [gap:cloud-connector.dns.policies:criteria-tunnel-doh].

**The DNS Filtering rule page.** A DNS Filtering rule name has a maximum length of 31 characters, and reusing the name of a previously deleted rule makes the service display the logs for both the deleted rule and the new rule when the logs are viewed. [cloud-connector.dns.policies:rule-name-limit] A DNS Filtering rule description cannot exceed 10,240 characters. [cloud-connector.dns.policies:description-limit] A disabled DNS Filtering rule is not actively enforced and the service skips it and moves to the next rule, but the rule does not lose its place in the rule order. [cloud-connector.dns.policies:rule-status] A DNS Filtering rule's Location/Sublocation criterion is Any, which applies the rule to all locations, or up to 8 locations or sublocations, and its Cloud & Branch Connector Groups criterion is Any, which applies it to all groups, or specific groups. [cloud-connector.dns.policies:scope-criteria] Any number of source IP address groups can be selected, and if none is selected the rule applies to all source IP address groups; to prevent App Connector looping, either exclude the IP addresses the App Connector device uses to open connections or include the IP addresses of all non-App Connector devices. [cloud-connector.dns.policies:source-criteria] The DNS Filtering rule page says that although the Destination IPv4 Groups field can be configured, Zscaler does not support destination IPv4 groups for DNS Filtering rules; the page also has an FQDNs / Domains field taking one or more FQDNs/domains. [cloud-connector.dns.policies:no-dest-ipv4-groups] The help page differs from both the Terraform documentation and the Go model ([cloud-connector.dns.policies:go-struct-narrower]) on destination IP groups [divergence:cloud-connector.dns.policies:dest-ip-groups-support]. Whether a configured destination IPv4 group is ignored or rejected is open [gap:cloud-connector.dns.policies:dest-ip-groups-behavior].

**Actions.** The DNS Policies page shows each rule's action as Allow, Block, Resolved by ZPA, or Redirect Request. [cloud-connector.dns.policies:page-actions] On the DNS Filtering rule page, Resolved by ZPA asks the Cloud or Branch Connector to resolve DNS requests using the IP pool, selectable as the default ZPA IP pool or any other IP pool; Redirect Request redirects all DNS requests and responses to a DNS gateway, chosen in a DNS Gateway field that appears only when Redirect Request is selected; and Block silently blocks all matching DNS requests and responses. [cloud-connector.dns.policies:action-targets] The API contract lists eleven DNS rule `action` values: ALLOW, BLOCK, REDIR_REQ, REDIR_RES, REDIR_ZPA, REDIR_REQ_DOH, REDIR_REQ_KEEP_SENDER, REDIR_REQ_TCP, REDIR_REQ_UDP, BLOCK_WITH_RESPONSE and BLOCK_WITH_EUN. [cloud-connector.dns.policies:contract-actions] The Terraform DNS rule resource validates `action` against four values: ALLOW, BLOCK, REDIR_ZPA and REDIR_REQ. [cloud-connector.dns.policies:tf-actions] A DNS rule using any of the seven other contract actions (including REDIR_RES and the DoH, TCP and UDP redirects) cannot be written through the Terraform resource. [cloud-connector.dns.policies:tf-subset]

Whether the console's response overwrite is REDIR_RES, or another contract action, is not stated [gap:cloud-connector.dns.policies:response-overwrite].

**Redirect targets.** A REDIR_REQ rule names a DNS gateway and a REDIR_ZPA rule an IP pool group; the provider documents but does not check the combinations: [The `ztc_traffic_forwarding_dns_rule` documentation says `dest_ip_groups` is not supported with the REDIR_ZPA action, `dns_gateway` applies only to REDIR_REQ, and `zpa_ip_group` (an IP pool group) applies only to REDIR_ZPA.](kb:cloud-connector.terraform.forwarding-rules:dns-action-constraints-documented), [The DNS rule resource has no plan-time check for those combinations, so a configuration that breaks them is sent to the API as written.](kb:cloud-connector.terraform.forwarding-rules:dns-constraints-not-checked). The Terraform resource never sends its ZPA IP group: [The DNS forwarding-rule resource accepts a `zpa_ip_group` block (documented as applying to the `REDIR_ZPA` action) but never uses it. The request builder does not set the SDK's `ZPAIPGroup` field and the read path does not set `zpa_ip_group` in state, although the SDK model has the field and the matching data source does read it. A configured value is accepted by the schema and silently ignored on create and update, and a value present on the server never appears in state.](kb:cloud-connector.terraform.provider-behavior:dns-rule-zpa-ip-group-dropped).

**Criteria in the API.** The contract's DNS rule request carries user, group and department members, destination IP address categories (`resCategories`), destination IP categories, destination countries, and a `redirectIp` (the IP the traffic is redirected to when the rule triggers). [cloud-connector.dns.policies:contract-criteria] The Go SDK's DNS rule model has none of those members: its criteria are source IPs, destination addresses, locations, location groups, Connector groups, and source and destination IP groups, plus the DNS gateway and ZPA IP group references. [cloud-connector.dns.policies:go-struct-narrower]

**Default and predefined rules.** The default rule allows all DNS traffic and always keeps the lowest precedence; its action can be modified but it cannot be deleted. It is listed as the Default Connector DNS Rule, the catch-all that permits all queries. [cloud-connector.dns.policies:default-rule] The DNS Control policy's default rule allows all DNS traffic and always maintains the lowest precedence; its actions can be modified, but it cannot be deleted or duplicated. [cloud-connector.dns.policies:default-not-duplicable] Whether the first matching rule ends evaluation is not stated [gap:cloud-connector.dns.policies:first-match]. The predefined rule Redirect Resolution of Zscaler Domains to WAN CTR is disabled by default, matches Zscaler domains from the Zscaler Cloud Endpoints application service group, applies only to hardware devices in gateway mode, appears according to the tenant's licenses, and allows edits only to Rule Order, Rule Status, Location/Sublocation and Cloud & Branch Connector Groups. [cloud-connector.dns.policies:wan-ctr-rule] The Terraform provider names a third predefined rule, `ZPA Resolver`, which no captured help describes [gap:cloud-connector.dns.policies:zpa-resolver]; its deletion guard is commented out: [In the DNS-rule Delete, the code that fetches the rule and calls validatePredefinedDNSRules is commented out, and the function goes on to send the API delete.](kb:cloud-connector.terraform.rule-protection:dns-delete-guard-commented-out).

Rule order as written by Terraform: [How the ZTC (Cloud Connector) Terraform provider applies rule order](kb:cloud-connector.terraform.rule-order). What a rule does when the gateway it redirects to is deleted is not stated [gap:cloud-connector.dns.policies:deleted-gateway-reference].

What to check:
1. Whether the workloads' DNS, including any DoH, actually transits the Connector; traffic that bypasses it is outside these policies.
2. The matching rule's action and, for REDIR_REQ, the DNS gateway it names and that gateway's failure behavior.
3. Whether filtering rules sit above the Default Connector DNS Rule, which allows all queries.
4. For a rule whose action Terraform cannot express (such as REDIR_RES or the DoH, TCP and UDP redirects), whether it was made in the console or through the API.

Sources disagree (name both sides):
- The DNS Filtering rule help page says destination IPv4 groups are not supported for DNS Filtering rules, while the Terraform documentation for the DNS rule describes dest_ip_groups as supported except with the REDIR_ZPA action. [divergence:cloud-connector.dns.policies:dest-ip-groups-support]
  - zscaler-help: Zscaler does not support destination IPv4 groups for DNS Filtering rules, although the field can be configured.
  - tf-ztc: dest_ip_groups holds the destination IP address groups to which the rule is applied and is not supported when the action is REDIR_ZPA.
  Impact: A Terraform configuration that sets dest_ip_groups on a DNS rule with another action follows the provider documentation and the Go model (go-struct-narrower lists DestIpGroups) but not the help page; what the service does with the field is open in gap dest-ip-groups-behavior.
