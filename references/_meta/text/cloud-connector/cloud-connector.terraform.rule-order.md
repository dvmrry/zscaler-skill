# How the ZTC (Cloud Connector) Terraform provider applies rule order (cloud-connector.terraform.rule-order)
Also called: ztc terraform reorder; ztc rule order wrong; cloud connector terraform rule order; ztc apply reordered rules; ztc_traffic_forwarding_rule order; rank 7

The ZTC provider does not write a rule's order directly. For updates it moves the rule to the end first and puts it back later, in the background; for creates it stages the rule at one cached order. Every update of a ZTC traffic forwarding, DNS forwarding, or log forwarding rule, whatever field changed, is first sent with rank 7 and with the order of the last rule when the existing rules are sorted by rank, then order. The declared order and rank are held back and only applied afterwards by the reorder worker. Create differs: it forces rank 7 only when the declared rank is below 7. [cloud-connector.terraform.rule-order:update-parks-every-update] If listing the existing rules fails during an update, the error is only logged and the code indexes the last element of whatever came back, with no length check. When the first page fails the list is empty and the index panics; an empty successful list does the same. When a later page fails, the SDK returns the pages read so far together with the error, and the rule is parked using that partial list. [cloud-connector.terraform.rule-order:list-error-then-panic] The ZTC GetAll functions for DNS forwarding, traffic forwarding and log forwarding rules page through the endpoint until a page comes back shorter than the page size, so the parking order and the rule count are computed from the full list unless a page errors. [cloud-connector.terraform.rule-order:list-reads-all-pages] On create, the error from listing existing rules is discarded. After scanning that list for its highest order, the staging order is set to 1 if it is still 0, and the rule is submitted with `req.Order` set to the staging order. [cloud-connector.terraform.rule-order:create-list-error-seeds-order-1] The staging order for creates is a package-level variable computed from the list only while it is zero, then reused unchanged for every later create in the same provider process. Creates are therefore staged at the same order as each other, and at the order of the last existing rule rather than after it, and, if one process ever served several tenants, a value computed against one would be reused against the others (ordinary provider aliases each run their own process). [cloud-connector.terraform.rule-order:staging-order-cached-per-process]

**Putting it back.** Declared orders are applied by one background worker per resource type, started by the first registration (or by the first registration after the previous worker finished). It wakes on a 30-second ticker and sleeps for half the interval between checks. [cloud-connector.terraform.rule-order:background-worker] All reorder state is one package-level registry keyed by resource type and rule ID, with no client, tenant or service in the key. The first registration for a resource type starts the worker, which keeps that registrant's callbacks; a registration made while that worker is still running only adds its ID and desired order to the shared map. [cloud-connector.terraform.rule-order:registry-keyed-by-type-only] The worker is given a callback returning a rule count, a callback writing a rule's order, and an optional before-reorder hook that all three resources pass as nil; it has no callback that reads current positions. Each callback pair in the three resources reads the count as the length of the full rule list. [cloud-connector.terraform.rule-order:worker-reads-only-a-count] The worker cannot pass a failure to the resources waiting on it: `reorderAll` returns no value, and waiting resources are released by closing a channel that carries no result. The channel is closed whenever `reorderAll` returns, so a waiter then proceeds whatever the worker did. [cloud-connector.terraform.rule-order:worker-cannot-report-failure] The error from the count callback is discarded. On error the callback returns 0, and a registered rule is only written when its declared order is at most the count, so every rule with a declared order above zero is skipped without a log line and the pass still records the registry size as handled. [cloud-connector.terraform.rule-order:count-error-ignored] A failed order write is logged and the loop moves on; the pass then records the registry size as handled whatever the writes did, so within that worker the failed rule is written again only if a later registration changes the registry size and triggers a new pass. [cloud-connector.terraform.rule-order:write-error-logged-only] A write pass runs only once every registered rule is marked done and the number of registered rules differs from the number at the last pass. Each later tick that sees the same number counts toward stability, and when that count reaches 3 the worker logs the reorder as complete and returns, even if the pass skipped some writes or some writes failed. Each order-write callback ends by calling Update, discarding the returned rule, and returning only the error. [cloud-connector.terraform.rule-order:completes-on-quiet-ticks] Beyond the Update error, the worker has no signal that an order write took effect: it never reads a rule's position back after writing it. [cloud-connector.terraform.rule-order:write-effect-unknown] Registering a rule that is already in the registry overwrites its desired order but does not change the registry size, so while a cycle is open an order change for an already-registered rule triggers no further write pass. [cloud-connector.terraform.rule-order:same-size-reregistration-ignored] A pass sorts and writes only the rules in the registry. Rules the apply did not register are never written by the worker, and it only counts them, so the worker's notion of done says nothing about them. [cloud-connector.terraform.rule-order:writes-registered-rules-only] So a ZTC apply can finish successfully with rules out of their declared order and no diagnostic: when the count read fails, when writes fail, when a write is accepted but changes nothing, or when an order change arrives for an already-registered rule. Only a later plan's drift shows it. [cloud-connector.terraform.rule-order:wrong-order-reported-success]

**The shared registry.** Deleting a ZTC traffic rule removes the remote rule and the Terraform state but not the rule's entry in the reorder registry. The entry stays for the life of the provider process and counts toward the registry size. [cloud-connector.terraform.rule-order:deleted-ids-stay-registered] A worker started for a later registration begins with a zero processed size, so its first pass sorts and writes every entry in the registry for that resource type (those with order within the count), including entries from earlier in the same provider process whose rules were since deleted. The write for a deleted rule fails on its read and is logged only. Rules that still exist are also rewritten with the desired order and rank recorded at their earlier registration. [cloud-connector.terraform.rule-order:new-cycle-rewrites-whole-registry] If a single provider process serves two configurations (for example a reattached or development-override provider; ordinary aliases each get their own process) and update the same resource type together, they share the registry and the first registrant's callbacks. The worker then reads and writes through the first client only, treats the other configuration's rule IDs as unknown or skipped, and releases the other configuration's waiters. [cloud-connector.terraform.rule-order:two-configurations-share-registry] The worker takes the global registry lock at the start of each tick and releases it only at the end of the tick, so the count read, the optional before-reorder hook and every order write run with the lock held (in the three resources the count callback calls the SDK's GetAll; the DNS and log rule order-write callbacks call Get and then Update, and the traffic forwarding rule's calls `getRule`, which lists every rule with GetAll, and then Update). Registration, marking a rule done and the waiters' channel lookup take the same lock, so a slow API call blocks them, for every resource type. [cloud-connector.terraform.rule-order:worker-lock-held-across-network-calls]

**Rules the apply did not touch.** Editing any field of a rule placed above a terminal default rule can leave that rule no longer last: the edit parks the rule at the last rule's order, and if moving it back fails or is skipped, the apply still reports success. [cloud-connector.terraform.rule-order:terminal-rule-can-be-displaced]

**Differences from the ZIA provider.** The ZIA provider ([How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order)) follows the same park-then-reorder design. The ZTC worker never reads positions back [cloud-connector.terraform.rule-order:worker-reads-only-a-count], and its write pass is gated on the registry size [cloud-connector.terraform.rule-order:completes-on-quiet-ticks].

What to check:
1. Whether the terminal default rule is still last after an apply that edited ZTC forwarding, DNS forwarding or log forwarding rules, by re-reading the whole policy's order and rank rather than only the edited rules.
2. Whether a later plan shows rules out of their declared order after an apply that reported success.

- [cloud-connector.terraform.rule-order:write-effect-unknown] Tier B: Rests on the three order-write callbacks ending at the Update call and the worker having only a count callback; no source says what the API does with a write it accepts (gap api-order-shift).
- [cloud-connector.terraform.rule-order:new-cycle-rewrites-whole-registry] Tier B: Depends on a delete and a later registration of the same resource type occurring in one provider process (for example a destroy and an update in one apply, or a long-lived process), and on the API returning an error for a deleted rule ID (not shown by this code).

- [cloud-connector.terraform.rule-order:wrong-order-reported-success] Tier B: The accepted-but-unchanged case depends on the API honoring a write at the requested order (gap api-order-shift); the others follow from the code alone.
- [cloud-connector.terraform.rule-order:terminal-rule-can-be-displaced] Tier C: Depends on how the API renumbers the other rules when one is written at a given order, and on the API accepting a write at the last rule's order even when that is a predefined default rule (gap api-order-shift); on the edited rule not already being last; and on the move back failing or being skipped.
