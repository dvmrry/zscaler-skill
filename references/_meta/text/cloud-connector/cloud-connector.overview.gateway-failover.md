# Cloud Connector tunnels to Service Edges: primary, secondary, tertiary, fail-close and fail-open (cloud-connector.overview.gateway-failover)
Also called: cloud connector fail open; cloud connector fail close; cloud connector failover; cloud connector secondary gateway; cloud connector tertiary gateway; cloud connector cannot reach zia; cloud connector data plane; cloud connector zpa enrollment; cloud connector high availability; cloud connector ha
Former IDs: cloud-connector-08

Each Cloud Connector keeps its own tunnels to Zscaler Service Edges; the cloud load balancer in front of it is a different layer ([How cloud load balancers spread traffic across Cloud Connectors and take unhealthy ones out](kb:cloud-connector.overview.load-balancing)). The data plane processes and forwards workload traffic to Internet & SaaS and Private Access Service Edges, and is made of outbound connections from the service interface of each Cloud Connector. [cloud-connector.overview.gateway-failover:data-plane]

**Which Service Edge.** The Internet & SaaS and Private Access Service Edges are selected using geolocation; traffic forwarding rules can instead use specific Public Service Edges, Virtual Service Edges, or sub-clouds for given Cloud Connector groups and locations. [cloud-connector.overview.gateway-failover:geolocation-default] The default rule that sends internet-bound traffic to Internet & SaaS is described in [Predefined Cloud Connector traffic forwarding rules](kb:cloud-connector.forwarding.predefined-rules).

**Primary, secondary, tertiary.**
1. Workload traffic handled by rules with the Internet & SaaS forwarding method uses the primary gateway as the active tunnel to the Service Edges. [cloud-connector.overview.gateway-failover:primary-active]
2. On a failed connection, Cloud Connector marks the secondary gateway as the active tunnel and forwards workload traffic through it; when the primary is healthy again it is marked active and new sessions go through the primary tunnel. [cloud-connector.overview.gateway-failover:secondary-failover] Cloud Connector monitors its gateway connections, and if the active tunnel fails it fails over to the secondary tunnel in approximately 30 seconds. [cloud-connector.overview.gateway-failover:failover-30s]
3. By default, Cloud Connector automatically tries a tertiary Service Edge if the primary and secondary have failed; it is not limited to the two Service Edges selected for tunneling. [cloud-connector.overview.gateway-failover:tertiary] Whether the tertiary attempt can be turned off or chosen is open [gap:cloud-connector.overview.gateway-failover:tertiary-control].

What becomes of sessions already on the secondary when the primary returns is not stated [gap:cloud-connector.overview.gateway-failover:sessions-on-failback].

**When no Cloud Connector reaches a Service Edge.** The default gateway configuration fails closed: internet-bound workload traffic is dropped if none of the Cloud Connectors in the same group can establish connectivity to any Internet & SaaS Service Edge. [cloud-connector.overview.gateway-failover:fail-close-default] Customers can change this configuration to fail-open, which lets workloads accessing the internet continue to do so; the next sentence says the fail-open option means egressing traffic flows through Zscaler for inspection and policy control. [cloud-connector.overview.gateway-failover:fail-open-option] The two clauses of the fail-open description are hard to reconcile, and where the toggle lives is not named [gap:cloud-connector.overview.gateway-failover:fail-open-egress]. The Internet Access gateway page describes the disabled Fail Close setting as sending traffic directly to the server: [On the Internet Access gateway page, Fail Close Enable (the default) drops the traffic when both proxies are unreachable, and Disable allows the traffic directly to the server without forwarding it to the proxy service when both proxies are unreachable.](kb:cloud-connector.forwarding.gateways:iag-fail-close) [divergence:cloud-connector.overview.gateway-failover:fail-open-path].

**Tunnel encryption.** A Cloud Connector group's ZIA Tunnel Mode selects Unencrypted UDP, DTLS or TLS as the encryption type used when forwarding traffic to Internet & SaaS, and Unencrypted UDP is selected by default. [cloud-connector.overview.gateway-failover:zia-tunnel-mode] Fallback to TLS can only be enabled if Unencrypted UDP or DTLS is selected as the ZIA Tunnel Mode; Enable switches the tunnel type to TLS automatically if the tunnel becomes unhealthy, Disable deactivates the feature, and it is enabled by default. A Fallback to TLS entry also views the status as Enable or Disable. [cloud-connector.overview.gateway-failover:fallback-to-tls]

The API's forwarding gateway object (`/gateways`) has a `failClosed` boolean: true means traffic is dropped when both the primary and secondary proxies defined in the gateway are unreachable, false means it is allowed. [cloud-connector.overview.gateway-failover:gateway-fail-closed-field] The fail-close or fail-open choice the high-availability article describes may be this per-gateway `failClosed` setting, which would make it a property of the forwarding gateway a rule uses rather than a tenant-wide switch. [cloud-connector.overview.gateway-failover:fail-closed-is-the-toggle]

**Private Access.** Cloud Connectors enrolled with Private Access automatically establish a secure connection to an optimal Private Access Public or Private Service Edge; workloads reaching private applications are tunneled there, and the data path continues through the App Connectors configured for the application. [cloud-connector.overview.gateway-failover:zpa-enrolled] Like Zscaler Client Connector, Cloud Connector tries to resolve the most optimal or nearest Private Access Public Service Edge or Private Service Edge for private application access. [cloud-connector.overview.gateway-failover:zpa-nearest] That the Cloud Connector and the App Connector never connect directly is not stated [gap:cloud-connector.overview.gateway-failover:no-direct-path].

The console's Inactive status reflects a lost management plane while the data plane keeps forwarding: [A Cloud Connector is Inactive when it cannot contact its management plane; with a healthy data plane this has no service impact and the connector still processes data.](kb:cloud-connector.insights.connector-status:inactive-meaning). Control plane health checks are among the Event log triggers: [A Cloud or Branch Connector generates an Event log when a status change occurs for a connector health check, Zscaler data center reachability, a data plane health check, a software upgrade, a control plane health check, or a tunnel to Zscaler data centers.](kb:cloud-connector.logs.event-records:when-generated). The direction and ports of the control channel are not stated [gap:cloud-connector.overview.gateway-failover:control-plane].

What to check:
1. Whether any Cloud Connector in the group could reach an Internet & SaaS Service Edge; only when none could does the fail-close or fail-open setting decide the outcome.
2. The gateway the forwarding rule uses, and its `failClosed` value.
3. Whether an outage lasted less than the roughly 30 seconds the failover to the secondary tunnel takes.
4. For Private Access traffic, whether the Cloud Connector is enrolled with Private Access and an App Connector serves the application.
