# ZTC traffic forwarding and DNS rules in Terraform: forward methods, ZPA segment IDs, workload groups, WAN selection and labels (cloud-connector.terraform.forwarding-rules)
Also called: ztc_traffic_forwarding_rule forward_method; LOCAL_SWITCH; ztc local forwarding method terraform; ztc zpa_application_segments id; zparesources; ztc src_workload_groups id lookup; ztc_workload_groups data source; ztc wan_selection; ztc traffic forwarding rule labels; ztc_traffic_forwarding_dns_rule REDIR_ZPA; ztc_ip_pool_groups one cidr
Former IDs: cloud-connector-17, cloud-connector-26

The rule resources' arguments and validators are generated (`node scripts/kb.mjs surface ztc_traffic_forwarding_rule`); this subject holds where the forwarding-method value set, ID lookups and documented constraints differ between the provider, the SDKs and the API contract. How rules are ordered, protected and detached on delete is in [How the ZTC (Cloud Connector) Terraform provider applies rule order](kb:cloud-connector.terraform.rule-order), [Whether the ZTC Terraform provider protects predefined traffic rules](kb:cloud-connector.terraform.rule-protection) and [How the ZTC Terraform provider detaches references before deleting objects](kb:cloud-connector.terraform.delete-detach).

## Forwarding rules

**Forward methods.** Which forward-method values each source accepts, and which token the console's Local method is sent as, are in [The API contract lists eight `forwardMethod` values for creating or updating a traffic forwarding rule (INVALID, DIRECT, PROXYCHAIN, ZIA, ZPA, ECZPA, ECSELF, DROP); rules read back may also carry ENATDEDIP and GEOIP. LOCAL_SWITCH is not among the request values.](kb:cloud-connector.forwarding.methods:contract-enums) and [The Terraform resource accepts `LOCAL_SWITCH` as a `forward_method`, and the Python SDK documents destination workload groups as valid for the `LOCAL_SWITCH` forward method.](kb:cloud-connector.forwarding.methods:local-switch-token). The API contract's `GET /ecRules/self` operation lists `LOCAL_SWITCH` among the values of its `ruleForwardMethod` query parameter, while the same parameter on `GET /ecRules/ecRdr` does not. [cloud-connector.terraform.forwarding-rules:contract-self-filter-lists-local-switch] Whether the API accepts LOCAL_SWITCH as the Local method on a write is still open [gap:cloud-connector.terraform.forwarding-rules:local-switch-wire-value].

**Attributes per method.** At plan time the forwarding rule resource rejects `zpa_application_segments` and `zpa_application_segment_groups` when `forward_method` is ZIA, DIRECT, LOCAL_SWITCH or DROP, and rejects `dest_addresses`, `dest_countries`, `dest_ip_groups`, `dest_ip_categories`, `proxy_gateway`, `nw_services`, `nw_service_groups` and `app_service_groups` when it is ECZPA. [cloud-connector.terraform.forwarding-rules:method-attribute-guards]

**ZPA application segments.** The provider sends each `zpa_application_segments` entry as a segment reference carrying only `ID`, taken from the configured `id` values. [cloud-connector.terraform.forwarding-rules:zpa-segments-sent-by-id] The key the segments travel under also differs between the SDK and the contract [cloud-connector.api.rules-wire:zpa-segments-key](kb:cloud-connector.api.rules-wire:zpa-segments-key). The Go SDK's `zparesources` package reads ZPA application segments from /ztw/api/v1/zpaResources/applicationSegments with two functions, `GetZPAApplicationSegments` and `GetByName`, and returns each segment with two identifiers, `id` and `zpaId`. [cloud-connector.terraform.forwarding-rules:zparesources-two-ids] The ZTC provider registers no data source for ZPA application segments or segment groups, so the IDs for `zpa_application_segments` and `zpa_application_segment_groups` come from outside the provider: the ZTW endpoint above, or the ZPA side. [cloud-connector.terraform.forwarding-rules:no-zpa-segment-data-source] Which of those IDs a rule expects, and whether either equals the ZPA provider's segment ID, is open [gap:cloud-connector.terraform.forwarding-rules:zpa-segment-id-equivalence].

**Workload groups.** The provider registers a `ztc_workload_groups` data source that looks a workload group up by ID (through the full list) or by name, using the Go SDK's ZTW `workload_groups` package. [cloud-connector.terraform.forwarding-rules:workload-groups-data-source] The `ztc_traffic_forwarding_rule` documentation still tells users to look up `src_workload_groups` IDs with the ZIA provider's `zia_workload_groups` data source, saying it returns the same ID because the object is shared between ZIA and ZTC. [cloud-connector.terraform.forwarding-rules:doc-points-to-zia] The ZTC provider has no workload group resource, and the Go SDK's ZTW package cannot write workload groups, so they are created and changed outside the ZTC provider (in the console or on the ZIA side). [cloud-connector.terraform.forwarding-rules:no-workload-group-resource] Destination workload groups are not modeled by the provider or the Go SDK: [cloud-connector.api.rules-wire:workload-groups](kb:cloud-connector.api.rules-wire:workload-groups).

**WAN selection.** The forwarding rule resource accepts `wan_selection` (validated against five values: `SMRULEF_ZPA_BROKERS_RULE`, `SMRULEF_APPC_DYNAMIC_SRC_IPGROUP`, `SMRULEF_EXCL_SRC_IP`, `BALANCED_RULE` and `BESTLINK_RULE`), describes it as applicable only to a hardware device in gateway mode, and copies it into the request through `expandForwardingControlRule`, which both create and update call. [cloud-connector.terraform.forwarding-rules:provider-sends-wan-selection] The provider and the API disagree on whether the field is still configurable [divergence:cloud-connector.terraform.forwarding-rules:wan-selection].

**Labels.** The `ztc_traffic_forwarding_rule` resource has no labels argument, so rule labels cannot be managed through the provider. [cloud-connector.terraform.forwarding-rules:no-labels-argument] Provider issue #46 asked for rule label support on `ztc_traffic_forwarding_rule` as in the console; it was marked stale and closed as not planned on 2026-09-07. [cloud-connector.terraform.forwarding-rules:labels-request-closed-not-planned] The API contract's create body for forwarding rules carries a `labels` array whose description is "Not applicable to Cloud & Branch Connector." [cloud-connector.terraform.forwarding-rules:contract-labels-not-applicable] Whether labels can be written to forwarding rules is open [gap:cloud-connector.terraform.forwarding-rules:rule-labels].

## DNS rules

**Action constraints.** The `ztc_traffic_forwarding_dns_rule` documentation says `dest_ip_groups` is not supported with the REDIR_ZPA action, `dns_gateway` applies only to REDIR_REQ, and `zpa_ip_group` (an IP pool group) applies only to REDIR_ZPA. [cloud-connector.terraform.forwarding-rules:dns-action-constraints-documented] The DNS rule resource has no plan-time check for those combinations, so a configuration that breaks them is sent to the API as written. [cloud-connector.terraform.forwarding-rules:dns-constraints-not-checked] The `zpa_ip_group` block is ignored altogether: [ZTC Terraform provider: configuration, field handling and read behavior](kb:cloud-connector.terraform.provider-behavior). An IP pool group, the REDIR_ZPA target, holds one CIDR subnet: the documentation says only one is allowed and the schema caps `ip_addresses` at one item. [cloud-connector.terraform.forwarding-rules:ip-pool-one-cidr]

What to check:
1. Which forward_method value the configuration uses; the provider accepts only DIRECT, LOCAL_SWITCH, ZIA, ECZPA and DROP, and other sources list other sets.
2. For ECZPA rules, which ID the zpa_application_segments entries hold, compared with the id and zpaId the ZTW ZPA-resources endpoint returns.
3. For DNS rules, that dest_ip_groups is not combined with REDIR_ZPA and dns_gateway is used only with REDIR_REQ, since the provider does not check either.

Inferred, not quoted (say so when an answer rests on one):
- [cloud-connector.terraform.forwarding-rules:no-zpa-segment-data-source] Tier B: Absence: the provider's DataSourcesMap at the pin (20 entries) has no ZPA segment data source, and no provider file calls the zparesources package.
- [cloud-connector.terraform.forwarding-rules:no-workload-group-resource] Tier B: Absence: the provider's ResourcesMap at the pin (16 entries) has no workload group resource.
- [cloud-connector.terraform.forwarding-rules:no-labels-argument] Tier B: Absence: the resource schema at the pin (also in the generated surface) has no labels or rule_label argument. The legacy doc cites upstream issue zscaler/terraform-provider-ztc#46 asking for it; that issue is not a registered source.
- [cloud-connector.terraform.forwarding-rules:dns-constraints-not-checked] Tier B: Absence: resource_ztc_traffic_forwarding_dns_rule.go at the pin has no CustomizeDiff, ConflictsWith or action-dependent validation.

Sources disagree (name both sides):
- The provider and the console help treat WAN selection as a live gateway-mode setting, and the provider sends it; the Go SDK and the API contract call it deprecated and no longer configurable, and the contract's create body does not carry it. [divergence:cloud-connector.terraform.forwarding-rules:wan-selection]
  - tf-ztc: WAN selection applies when configuring a hardware device in gateway mode; the provider sends it.
  - zscaler-help: The console help documents WAN Selection (None by default, Balanced, Best Link) as applicable to hardware devices deployed in gateway mode.
  - sdk-go: The parameter was deprecated and is no longer configurable.
  - api-specs: The create body of a forwarding rule has no wanSelection member.
  Impact: Setting wan_selection in Terraform may be ignored or rejected by the API; the sources do not say which.

Not known (open gaps):
- Whether LOCAL_SWITCH is the API value of the console's Local forwarding method [gap:cloud-connector.terraform.forwarding-rules:local-switch-wire-value]: settled by lab-test or source-read. Blocks: Whether a Terraform or Python rule with LOCAL_SWITCH creates a Local forwarding rule, and whether the Go SDK and API contract simply omit the value.
- Which ZPA application segment ID a ZTC forwarding rule expects [gap:cloud-connector.terraform.forwarding-rules:zpa-segment-id-equivalence]: settled by lab-test. Blocks: How to fill zpa_application_segments without hard-coding: from the ZTW id, the ZTW zpaId, or the ZPA provider's segment ID.
- Whether Cloud and Branch Connector forwarding rules accept labels through the API [gap:cloud-connector.terraform.forwarding-rules:rule-labels]: settled by lab-test or source-read. Blocks: Whether rule labels shown in the console can be automated, through the API or a future provider argument.
