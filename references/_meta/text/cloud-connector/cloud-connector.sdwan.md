# Zero Trust SD-WAN: what Zscaler means by it and what the sources leave open (cloud-connector.sdwan)
Also called: zero trust sd-wan; zscaler sd-wan; branch connector sd-wan; is zscaler sd-wan a router; branch to branch zscaler; sd-wan replacement zscaler; site-to-site vpn replacement; cloud connector sd-wan

Zero Trust SD-WAN is Zscaler's name for its branch and cloud connectivity product family. Zscaler Zero Trust SD-WAN gives branches, on-premises data centers and public clouds access to the internet and private applications with a direct-to-cloud architecture, and connects users and IoT/OT devices to applications through the Zero Trust Exchange (ZTE). [cloud-connector.sdwan:definition] Zscaler Cloud and Branch Connector traffic is forwarded directly to the ZTE, where the admin can apply Internet & SaaS (ZIA) or Private Access (ZPA) policies depending on the traffic's destination, for full security inspection and identity-based access control of cloud, branch and data center communications. [cloud-connector.sdwan:traffic-to-zte] The help says Zero Trust SD-WAN combines lightweight virtual machines or plug-and-play devices with the ZTE to provide zero trust networking for sites and clouds without overlay routing or additional firewall appliances. [cloud-connector.sdwan:no-overlay]

**Branch Connector.** Branch Connector is a virtual machine that forwards traffic to Zscaler services; Zero Trust SD-WAN is deployed as a Branch Connector VM, which works similarly to Cloud Connector. [cloud-connector.sdwan:branch-connector-vm] Branch Connector establishes direct branch-to-internet and branch-to-private-app connections using a full proxy architecture, and its forwarding can send traffic to Internet & SaaS, Private Access, or Direct (bypassing Zscaler services). [cloud-connector.sdwan:branch-connector-proxy] Cloud Connector, the cloud-workload counterpart, is covered from [Cloud & Branch Connector: what Cloud Connector is and where each area is described](kb:cloud-connector.overview). Hardware devices, gateway and one-arm modes and zero touch provisioning are in [Zero Trust SD-WAN devices: gateway and one-arm modes, zero touch provisioning](kb:cloud-connector.sdwan.device-modes). Configuration templates are in [Branch Connector configuration templates: VM and hardware settings, HA, WAN uplinks, LAN, DHCP and static routes](kb:cloud-connector.sdwan.configuration-templates), the device inventory and per-device settings in [Branch device inventory and per-device settings: ZIA tunnel mode, support tunnel, DNS cache, traffic forwarding bypass](kb:cloud-connector.sdwan.devices), and VM deployment on VMware, Linux KVM and Hyper-V in [Deploying Branch Connector VMs on VMware, Linux KVM and Hyper-V: prerequisites, sizing, HA host settings, user data and IaC](kb:cloud-connector.sdwan.virtual-deployment). The Step-by-Step Configuration Guide orders Branch Connector setup as: update administrator and role management information, configure locations, configure a provisioning template (which creates provisioning URLs to deploy Branch Connector as a VM), configure firewall filtering (source IP groups, destination IP groups, IP pools and network services), gateways, forwarding methods (traffic forwarding, log and control forwarding, and DNS control rules), then analytics. [cloud-connector.sdwan:setup-sequence] Whether Zero Trust SD-WAN is licensed as a product of its own is not stated [gap:cloud-connector.sdwan:product-packaging].

**Branch to branch and VPN replacement.** Branches and data centers connect to each other through the ZTE, independent of the underlying corporate network, VPN or WAN; all branch communications forward to the ZTE and from there to any destination. [cloud-connector.sdwan:branch-to-branch-via-zte] As a site-to-site VPN replacement, branches connect to private applications in data centers or public clouds without extending the WAN or relying on VPNs; access goes through the ZTE to named entities after identity, context and policy are verified. [cloud-connector.sdwan:vpn-replacement] How much latency the path through the Zero Trust Exchange adds against a direct WAN path is not documented [gap:cloud-connector.sdwan:hairpin-latency].

**Inspection.** Branch communications are forwarded to the ZTE, where Internet & SaaS or Private Access policies can be applied for full security inspection and identity-based access control. [cloud-connector.sdwan:inspection-at-zte] Whether the connector itself inspects traffic is not stated [gap:cloud-connector.sdwan:connector-inspection]. Whether the connector optimizes WAN traffic itself is not stated either [gap:cloud-connector.sdwan:wan-optimization].

**Device visibility and OT access.** The help claims Zero Trust SD-WAN discovers and classifies shadow IoT devices with automatic device classification based on traffic profiles. [cloud-connector.sdwan:iot-classification] How classification works is not documented [gap:cloud-connector.sdwan:iot-classification-detail]. For OT, the help describes clientless browser-based access to SSH, RDP and VNC ports on OT assets, with Privileged Remote Access for RDP and SSH targets. [cloud-connector.sdwan:ot-access]

**Availability.** Branch Connector's feature list claims high availability with automatic failover and N+1 redundancy. [cloud-connector.sdwan:n-plus-one] The template settings for VM, LAN and WAN uplink failover are in [Branch Connector configuration templates: VM and hardware settings, HA, WAN uplinks, LAN, DHCP and static routes](kb:cloud-connector.sdwan.configuration-templates); failover timing and how a site with hardware devices is built end to end are not described [gap:cloud-connector.sdwan:branch-ha-model]. Cloud Connector gateway failover and the fail-close and fail-open setting are in [Cloud Connector tunnels to Service Edges: primary, secondary, tertiary, fail-close and fail-open](kb:cloud-connector.overview.gateway-failover). Upgrades run in a scheduled window: [By default the upgrade window starts every Sunday at midnight, local time of the deployed connector.](kb:cloud-connector.upgrades:default-window), [All connectors in a Cloud Connector group or Branch Connector group are updated within a two-hour window, and their upgrades are staggered to prevent service impact.](kb:cloud-connector.upgrades:two-hour-staggered); what happens to long-lived sessions on an upgrading connector is not stated [gap:cloud-connector.sdwan:upgrade-session-drop].

**Forwarding.** Forwarding methods are in [Cloud Connector forwarding methods: ZIA, ZPA, Direct, Drop, Local, and their API tokens](kb:cloud-connector.forwarding.methods), WAN selection in [WAN Selection is None by default, which follows the Traffic Distribution setting of the branch configuration template; Balanced distributes traffic evenly and Best Link always uses the best-performing WAN link. It applies only to hardware devices deployed in gateway mode.](kb:cloud-connector.forwarding.methods:wan-selection), and the gateway-mode predefined rules in [Predefined Cloud Connector traffic forwarding rules](kb:cloud-connector.forwarding.predefined-rules). The metric behind the device-level Traffic Distribution setting's Best Link is in [Traffic Distribution is Balanced or Best Link; Balanced is the default and distributes traffic across all WAN links using a flow-based distribution algorithm, and Best Link uses a link determined using probes that measure loss, latency and jitter. The setting is only applicable when there is more than one WAN interface and/or subinterface and both are set to active and operational, and any WAN link selected via traffic forwarding rules takes precedence for the matching traffic over this catch-all device-level setting.](kb:cloud-connector.sdwan.configuration-templates:traffic-distribution); the metric the forwarding rule's WAN Selection Best Link uses, and whether WAN selection ever applies outside hardware in gateway mode, are open [gap:cloud-connector.sdwan:wan-selection-detail]. Whether traffic markings such as DSCP survive the connector, or any per-link QoS exists, is not documented [gap:cloud-connector.sdwan:qos].

What to check:
1. Whether the requirement is internet and private-application access through the Zero Trust Exchange, which the product covers, or WAN transport functions the sources do not describe (overlay meshing, link QoS, MPLS integration).
2. For branch-to-branch access, whether the destination applications are reachable through the Zero Trust Exchange as private applications.
