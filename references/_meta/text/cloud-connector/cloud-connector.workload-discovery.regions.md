# Workload discovery regions, per-region status, and turning data collection off (cloud-connector.workload-discovery.regions)
Also called: workload discovery region not discovered; discovery service status; starting discovery status; regionStatus; supportedRegions workload discovery; disable data collection aws account; changeState publicCloudInfo

**Selecting regions.** Regions where workloads are deployed are selected when the account is added; if a region where workloads run is not selected, the discovery service does not discover those workloads and tag-based security policies are not applied to them. [cloud-connector.workload-discovery.regions:select-regions] The account details help says the supported AWS regions include us-east-1, us-east-2, us-west-1, us-west-2, eu-central-1, eu-west-1, eu-west-2, ap-southeast-1, ap-south-1 and ap-southeast-2. [cloud-connector.workload-discovery.regions:help-region-list] The API lists the regions discovery supports: [The API's `/publicCloudInfo/supportedRegions` operation is described as retrieving the AWS regions supported for workload discovery settings (WDS); its items are regions supported by Zscaler's Tag Discovery Service.](kb:cloud-connector.regions:wds-endpoint), with each entry's fields in [Each returned region has an `id`, a `name` and a `cloudType` whose values are AWS, AZURE and GCP, although the same field's description calls AWS the default and mandatory value.](kb:cloud-connector.regions:wds-cloud-types); whether that set matches the Zero Trust Gateway and Cloud Connector lists is open: [Whether the workload-discovery, Zero Trust Gateway and Cloud Connector region sets coincide](kb:cloud-connector.regions:region-set-parity). Clients select regions by ID: the Terraform resource's `supported_regions` is a set of IDs, and the Python SDK takes `supported_region_ids` and sends them as `supportedRegions`. [cloud-connector.workload-discovery.regions:regions-by-id] The account update request carries `supportedRegions`, as the create request does. [cloud-connector.workload-discovery.regions:update-carries-regions]

**Per-region status.** The account details page shows a Discovery Service Status per region; the most commonly displayed values are Success (running as expected), Disabled (re-enable data collection from the AWS Accounts page), Error (the service has discovered an issue) and Starting Discovery (data collection has not been started). [cloud-connector.workload-discovery.regions:status-strings] In the API contract and the Go SDK, each entry of the account's `regionStatus` has a boolean `status` described as the operational status of the region. [cloud-connector.workload-discovery.regions:region-status-boolean] How the console's strings relate to the boolean is unresolved [gap:cloud-connector.workload-discovery.regions:region-status-representation]. No of Private IP Addresses counts the workloads the discovery service found, one per IP address, so a workload with several IP addresses is shown as several workloads. [cloud-connector.workload-discovery.regions:private-ip-count] The duplicate IP counter is covered with namespaces: [When Zscaler detects a duplicate IP address, only one is shown and all others are disregarded; the region view's No of Duplicates IP counts them, and the help says to resolve duplicates in a region with namespaces.](kb:cloud-connector.workload-discovery.namespaces:duplicate-ip-one-shown).

**Turning data collection off.** An account's menu offers Disable Data Collection, which stops the tag discovery process, and Enable Data Collection, which starts it. [cloud-connector.workload-discovery.regions:data-collection-toggle] The API enables or disables an AWS account in all regions with a PUT on the account's change-state path, taking a boolean `enable` query parameter (true enables, false disables). [cloud-connector.workload-discovery.regions:change-state-api] What happens to tags already delivered while collection is off is not stated [gap:cloud-connector.workload-discovery.regions:disabled-tag-retention].

**Toggling from the SDKs.** The Go function for this call fails on every call: [`UpdatePublicCloudChangeState` sends its change-state PUT with a nil payload. The generic PUT helper (and the legacy ZTW client's) rejects a nil payload with an error before building any request, so the function returns an error on every call and can never change the state.](kb:cloud-connector.sdk-go.service-defects:public-cloud-change-state-nil-payload). The Python SDK's `change_state_public_cloud_info` documents `query_params.enable`, but it copies its keyword arguments into the request body and builds the request without query parameters. [cloud-connector.workload-discovery.regions:python-change-state-body] A Python call that passes `query_params={"enable": ...}` therefore sends it inside the JSON body, not as the `enable` query parameter the API reads. [cloud-connector.workload-discovery.regions:python-enable-not-query]

What to check:
1. Whether every region that holds the workloads is selected on the account.
2. The Discovery Service Status of the region on the account details page, and whether data collection was disabled for the account.
3. When toggling data collection by API, send `enable` as a query parameter directly rather than through the Go or Python helper.
