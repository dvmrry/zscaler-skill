# How cloud load balancers spread traffic across Cloud Connectors and take unhealthy ones out (cloud-connector.overview.load-balancing)
Also called: cchealth; cloud connector health probe; cloud connector health check interval; gateway load balancer health check; cloud connector sessions failed during unhealthy; cloud connector active active; cloud connector availability zones

Cloud Connectors sit behind the cloud provider's own load balancer, which decides per Cloud Connector whether it receives new traffic. Zscaler integrates with each cloud provider's native load-balancing service; the load balancers send HTTP health probes on a port selected during deployment to determine the health of each Cloud Connector. [cloud-connector.overview.load-balancing:native-lb-probes]

**The probe.** Cloud Connector listens on the configured port for HTTP health probes on a path the help capture renders as `?cchealth`. [cloud-connector.overview.load-balancing:cchealth-path] A healthy Cloud Connector answers the probe with HTTP 200; an unhealthy one answers 503 or does not answer. [cloud-connector.overview.load-balancing:health-codes] The health probe is meant to show that the VM is functional and can forward workload traffic to the Internet & SaaS and Private Access Service Edges, not only that the VM is up. [cloud-connector.overview.load-balancing:probe-checks-forwarding] The reference Terraform modules probe the path `/?cchealth`: [The target group health check is HTTP to the probe port at path /?cchealth.](kb:cloud-connector.aws.gwlb:health-check), [The module's probe is HTTP on `http_probe_port` (default 50000, valid values 80 or 1024-65535) with request path /?cchealth, an interval of 15 seconds by default (minimum 5), `probe_threshold` 2 and `number_of_probes` 1.](kb:cloud-connector.azure.load-balancing:ilb-probe). The probe port range outside those modules, and whether it can change after deployment, is open [gap:cloud-connector.overview.load-balancing:probe-port].

**Intervals.** Zscaler deployment templates use a recommended default health-check interval: 15 seconds on the Azure Load Balancer and 30 seconds on the AWS Gateway Load Balancer. The defaults are meant to take unhealthy Cloud Connectors out of rotation efficiently. [cloud-connector.overview.load-balancing:probe-intervals] The default deployment templates are configurable, but Zscaler says to contact Zscaler Support before changing any settings. [cloud-connector.overview.load-balancing:change-via-support]

**Scaling and sessions.** Cloud Connectors scale horizontally and are all active: adding Cloud Connectors to a group supports higher throughput per egress location. [cloud-connector.overview.load-balancing:all-active] New sessions should go to healthy Cloud Connectors, but existing connections through a Cloud Connector that becomes unhealthy might temporarily fail until the flow ages or times out and the load balancer sends the session through a healthy one. [cloud-connector.overview.load-balancing:unhealthy-sessions]

**Availability zones.** Zscaler recommends at least two Cloud Connectors per availability zone, across at least two availability zones. [cloud-connector.overview.load-balancing:az-recommendation] Zscaler also recommends enabling AWS Gateway Load Balancer cross-zone load balancing for all production deployments, so GWLB endpoints in several availability zones can use Cloud Connectors in all zones rather than only their own. [cloud-connector.overview.load-balancing:gwlb-cross-zone]

The console's Active or Inactive status is a different signal from this load-balancer health: [The console status and load-balancer health are different signals: the status follows management-plane contact, while the cloud load balancer keeps or removes a connector by its HTTP health probe answer. The console status therefore does not show whether the load balancer keeps the connector in rotation.](kb:cloud-connector.insights.connector-status:status-not-lb-health).

What happens on the Zscaler side of each Cloud Connector, its tunnels to the Service Edges, is separate: [Cloud Connector tunnels to Service Edges: primary, secondary, tertiary, fail-close and fail-open](kb:cloud-connector.overview.gateway-failover).

What to check:
1. Whether the load balancer marked the Cloud Connector unhealthy (a 503 or no answer on the health port) at the time sessions failed.
2. Whether the failed sessions were already established on that Cloud Connector, which can fail until the flow ages out, rather than new sessions.
3. Whether the deployment's health-check interval was changed from the template default (15 seconds Azure, 30 seconds AWS GWLB).
4. Whether each availability zone holds at least two Cloud Connectors and, on AWS, GWLB cross-zone load balancing is enabled.

Not known (open gaps):
- Health-probe port range outside the reference modules [gap:cloud-connector.overview.load-balancing:probe-port]: settled by lab-test or source-read. Blocks: configuring a custom load balancer or firewall rule for the health probe
