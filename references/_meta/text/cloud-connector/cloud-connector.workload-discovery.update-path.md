# How tag changes reach Cloud Connector: polling, EventBridge, SNS and SQS (cloud-connector.workload-discovery.update-path)
Also called: workload discovery polling interval; eventbridge zscaler bus; eventBusName; tag changes slow to apply; auto scaling group tags delay; cloud connector sqs permissions; cloud_tags_enabled

**Polling.** The default polling time of the workload discovery service is 5 minutes, so changes can take up to 5 minutes to be distributed for policy enforcement. [cloud-connector.workload-discovery.update-path:polling-5-min]

**EventBridge.** For deployments such as auto scaling groups that need Zscaler notified immediately, EventBridge can trigger an update within a few seconds of an EC2 notification. [cloud-connector.workload-discovery.update-path:eventbridge-for-fast-updates] The rule is configured in the operator account's EventBridge on the default bus and sends a notification to an EventBridge bus in the Zscaler account assigned to the tenant, whose name is shown on the account page. [cloud-connector.workload-discovery.update-path:rule-on-default-bus] The documented rule is a rule with an event pattern from AWS services: service EC2, event type EC2 Instance State-change Notification, specific state pending, any instance. [cloud-connector.workload-discovery.update-path:event-pattern] The rule's target is an EventBridge event bus in a different account or Region, given as the ARN from the Admin Console with its region field replaced by the region the rule is created in (the help's example is arn:aws:events:<REGION>:11111111111:event-bus/zscaler-bus-146530-zsdevel.net), with a new execution role created for it. [cloud-connector.workload-discovery.update-path:target-arn] The account's Event Bus Name is the name of the event bus that sends notifications to the Zscaler service using EventBridge, and the help calls it the target of the EventBridge; the API carries it as `eventBusName` in the account details. [cloud-connector.workload-discovery.update-path:event-bus-name-field] What happens to tag freshness when the rule is missing or targets the wrong bus is not documented beyond polling [gap:cloud-connector.workload-discovery.update-path:eventbridge-misconfigured].

**Delivery to Cloud Connector.** The service communicates through API calls and an SNS and SQS publish-subscribe mechanism: new tag discoveries are pushed through it to Cloud Connector, from an SNS topic in the Zscaler account that has all relevant changes to an account and is protected by a resource-based policy. [cloud-connector.workload-discovery.update-path:sns-sqs-push] Cloud Connector must be able to manage queues, receive messages and subscribe to SNS. For existing deployments the permissions to add to the Cloud Connector IAM role are sns:ListTopics, sns:ListSubscriptions, sns:Subscribe, sns:Unsubscribe, sqs:CreateQueue and sqs:DeleteQueue. [cloud-connector.workload-discovery.update-path:cc-role-permissions] The Zscaler AWS Cloud Connector Terraform modules added the optional tags policy in v1.2.0 with sqs:DeleteMessage, sqs:ReceiveMessage, sqs:GetQueueUrl, sqs:GetQueueAttributes, sqs:SetQueueAttributes, sqs:DeleteQueue, sqs:CreateQueue and sns:Subscribe, behind the `cloud_tags_enabled` variable; release 1.4.1 updated the CCAllowTags policy to its minimum SQS/SNS dependencies. [cloud-connector.workload-discovery.update-path:module-policy-history] The help says Cloud Connector must receive messages, yet the current lists hold no receive action [gap:cloud-connector.workload-discovery.update-path:receive-permission].

**New deployments.** The help says that in a new deployment using Terraform or CloudFormation Zscaler adds these permissions by default, and that in an existing deployment they must be added manually to the IAM roles associated with the Cloud Connector instances. [cloud-connector.workload-discovery.update-path:new-deployments-default] The Zscaler Terraform modules attach these permissions only when asked [divergence:cloud-connector.workload-discovery.update-path:new-deployment-permissions].

What to check:
1. Whether a delay of up to 5 minutes explains a tag change not yet applied, before suspecting the integration.
2. Whether an EventBridge rule exists on the default bus in each region the account uses, matching EC2 Instance State-change Notification for the pending state, targeting the Zscaler bus ARN with the region replaced.
3. Whether the Cloud Connector IAM role carries the SNS and SQS permissions, and for Terraform-built deployments whether `cloud_tags_enabled` was set.

Sources disagree (name both sides):
- The help says new Terraform deployments get the Cloud Connector SNS and SQS permissions by default; the Zscaler AWS Terraform IAM module creates that policy only when `cloud_tags_enabled` is true, and the variable defaults to false. [divergence:cloud-connector.workload-discovery.update-path:new-deployment-permissions]
  - zscaler-help: New Terraform or CloudFormation deployments receive the permissions by default.
  - tfmod-aws-cloud-connector: The tags policy (the same six SNS and SQS actions) is created and attached only when `cloud_tags_enabled` is set; by default it is not.
  - tfmod-aws-cloud-connector: The attachment of the tags policy is counted only when `cloud_tags_enabled` is true and the module builds the IAM role itself.
  Impact: A Cloud Connector built from the Terraform modules with defaults has no SNS or SQS permissions, so tag updates are not delivered to it until the variable is set or the permissions are added by hand.

Not known (open gaps):
- Behavior when the EventBridge rule is missing or misdirected [gap:cloud-connector.workload-discovery.update-path:eventbridge-misconfigured]: settled by lab-test. Blocks: Estimating tag staleness when the EventBridge rule is absent or wrong.
- How Cloud Connector receives SQS messages without a receive permission [gap:cloud-connector.workload-discovery.update-path:receive-permission]: settled by operator-experience or support-ticket. Blocks: Building a least-privilege Cloud Connector role that still receives tag updates.
