# ZTC Terraform provider: configuration, field handling and read behavior (cloud-connector.terraform.provider-behavior)
Also called: ztc provider configuration; ztc terraform parallelism ignored; ztc provider builds client twice; ztc description dollar sign; ztc description cannot be cleared; zpa_ip_group ignored; ztc_traffic_forwarding_dns_rule zpa_ip_group; nw_application_groups; ztc ip destination group countries error; ztc location template panic; non_editable data source; ztc provider user agent version

This subject collects the client-side behavior of the ZTC Terraform provider that is not about rule order: how it configures its SDK client, which arguments it quietly ignores, and where a read or update does something other than what its schema promises. Every claim is about what the provider and the Go SDK send and how they react; what the ZTC API does with it is stated as a gap where it matters.

**Client construction.** Provider configuration builds the SDK client twice. `providerConfigure` first calls `loadClients`, which builds a client through `zscalerSDKV3Client` and stores it on the config, then calls `Client()`, which builds a second client through the same function and returns that one to Terraform. `Client()` never uses the stored client. The legacy-client branch does the same with `zscalerSDKV2Client`. [cloud-connector.terraform.provider-behavior:configure-builds-client-twice] Unless the legacy client is configured, constructing a OneAPI client in the Go SDK authenticates immediately, requesting a token over HTTP when the configuration holds no valid one, and starts a token-renewal ticker goroutine when the token expires more than a minute later. Construction is therefore a network call with a background effect, not a cheap object build. [cloud-connector.terraform.provider-behavior:sdk-construction-authenticates] So every provider configuration performs two initial authentications, and the first client keeps its renewal goroutine for the life of the process: the provider never calls `Close` on any client and nothing but `SelectClient` reads the stored one. (The renewal goroutine runs when the token lifetime exceeds one minute.) [cloud-connector.terraform.provider-behavior:discarded-client-keeps-renewing] For token handling inside the SDK see [How the Go SDK obtains and renews OneAPI tokens](kb:shared.sdk-go.auth-lifecycle).

**The parallelism setting.** The provider schema advertises `parallelism` as the number of concurrent requests, and `providerConfigure` builds a package-level semaphore channel of that capacity, but no code ever sends to or receives from it. Setting `parallelism` changes a channel's size and nothing else. Terraform's own `-parallelism` flag and the SDK's rate limiting still apply. [cloud-connector.terraform.provider-behavior:parallelism-not-enforced]

**Text arguments.** The multi-line text normalizer trims every line, doubles every `$` (`$` becomes `$$`), and appends a newline. The inverse helper `unescapeTerraformVariables`, which converts `$$` back to `$`, is defined in the same file. [cloud-connector.terraform.provider-behavior:multiline-normalizer-doubles-dollar] Nothing in the provider calls `unescapeTerraformVariables`, so the `$$` doubling is never reversed by the provider. [cloud-connector.terraform.provider-behavior:unescape-helper-unused] The matching diff-suppress function returns true whenever the new text is empty, before it looks at the old text. By its own logic a change from a non-empty value to an empty one is never a difference. [cloud-connector.terraform.provider-behavior:multiline-diff-suppress-ignores-clears] Both helpers are attached to the `description` argument of nine resources as `StateFunc` and `DiffSuppressFunc`. On those resources a description cannot be cleared by removing it or setting it to an empty string, because the diff is suppressed and no update is sent. The `$$` form is computed for the plan and state; the plugin SDK keeps the configured text for apply, so the request carries `$` as written. [cloud-connector.terraform.provider-behavior:multiline-helpers-on-nine-resources] Omitted zero values and empty lists in SDK writes are the broader mechanism behind other clears that cannot be sent; they are in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes), not repeated here.

**Accepted but unused arguments.** The DNS forwarding-rule resource accepts a `zpa_ip_group` block (documented as applying to the `REDIR_ZPA` action) but never uses it. The request builder does not set the SDK's `ZPAIPGroup` field and the read path does not set `zpa_ip_group` in state, although the SDK model has the field and the matching data source does read it. A configured value is accepted by the schema and silently ignored on create and update, and a value present on the server never appears in state. [cloud-connector.terraform.provider-behavior:dns-rule-zpa-ip-group-dropped] The traffic-forwarding rule resource has no `nw_application_groups` argument, yet its request builder asks for one by that key. The key is not in the schema, so the lookup yields an empty list, and the SDK tags `NwApplicationGroups` `omitempty`, so the field is left out of every create and update body. The read path never sets it either. The resource therefore cannot declare the association and does not show an association made elsewhere. The audit's reading that an empty value is sent is not what the code does: the field is omitted. [cloud-connector.terraform.provider-behavior:forwarding-rule-no-nw-application-groups]

**Reads and updates.** The traffic-forwarding rule resource reads a rule by listing all rules and searching for its ID, and the lookup returns an error when the ID is absent. The read function returns that error before it reaches its own "no longer exists" branch, so that branch can never run. A rule deleted outside Terraform makes the refresh fail instead of removing the resource from state. The DNS and log-forwarding rule resources read by ID and clear state when the SDK reports the object as not found. [cloud-connector.terraform.provider-behavior:forwarding-rule-read-cannot-clear-state] For IP destination groups, create requires at least one category or country only when the type is `DSTN_OTHER`. Update applies the same requirement when the type is `DSTN_OTHER` or when `countries` or `ip_categories` changed, and it counts only those two arguments, not `addresses`. Removing the last category or country from a group of another type is rejected by the provider before any API call, with a message that talks about `DSTN_OTHER`. [cloud-connector.terraform.provider-behavior:ip-destination-update-gate-wider-than-create] The location template read tests a failed read for a 404 status by dereferencing `respErr.Response.StatusCode` on the SDK error with no nil check. The SDK's own `IsObjectNotFound` helper does check `Response == nil` first, and the SDK error type allows a nil `Response`, so an error of that shape makes the read panic instead of returning a diagnostic. The location management resource has the same line. [cloud-connector.terraform.provider-behavior:location-read-unguarded-response] Within the SDK the provider is built with, the only code that builds an error of this type always sets `Response`, so the unguarded dereference is a latent panic, not one the SDK triggers on its own. It would fire for an error of this type built without a response, for example by a different SDK version or a wrapper. [cloud-connector.terraform.provider-behavior:location-read-nil-response-reachability] Update-time list panics and the parking of rules are in [How the ZTC (Cloud Connector) Terraform provider applies rule order](kb:cloud-connector.terraform.rule-order); protection of predefined rules is in [Whether the ZTC Terraform provider protects predefined traffic rules](kb:cloud-connector.terraform.rule-protection).

**Data sources.** The location management data source declares a computed `non_editable` attribute that its read function never sets, and the SDK's location type has no field to take it from, so the attribute is never populated, whatever the API reports. The IP group data sources do set their `is_non_editable` from the SDK field. [cloud-connector.terraform.provider-behavior:location-management-non-editable-never-set]

**Version reported to the API.** The User-Agent the provider sends names the provider version from a hard-coded constant that reads `0.1.9` in the v0.2.0 tree. The release build's linker flags set `main.version`, a different symbol from the constant the User-Agent reads, so a build from the tag as written reports 0.1.9 to the API. A second constant, `ProviderVersion = "1.0.0"` in the provider package, is not read by the configuration path. [cloud-connector.terraform.provider-behavior:version-metadata-user-agent]

**Reorder coordinator synchronization.** The reorder coordinator replaces the per-type completion channel in a shared map while holding the registry lock, releases the lock, and only then reads the channel back out of the map to hand to the worker goroutine that will close it. The read is outside the lock that guards the writes. The wait path, by contrast, reads the same map under the lock. [cloud-connector.terraform.provider-behavior:reorder-done-channel-read-after-unlock] Because the done-channel map is read without the lock while registrations of any resource type write to it under the lock, the Go runtime can abort the provider with a concurrent map read and map write. Replacing a still-open channel in that window is not possible, so a double close or a waiter left on an unclosed channel does not follow. [cloud-connector.terraform.provider-behavior:reorder-race-outcomes] How the coordinator decides what to write, and what it leaves unwritten, is in [How the ZTC (Cloud Connector) Terraform provider applies rule order](kb:cloud-connector.terraform.rule-order); for the open questions on the server side see that subject's gaps.

The `ztc_public_cloud_info` resource declares `log_info_type` inside `account_details`, but neither its request builder nor its read copies that argument, so a configured value is never sent to the API and is never read back into state. [cloud-connector.terraform.provider-behavior:public-cloud-log-info-type-dropped]

The provider's 0.2.0 changelog records a fix for a panic of the `ztc_edge_connector_group` data source on the attribute type of `ec_instances.0.dns_ip`. [cloud-connector.terraform.provider-behavior:edge-connector-group-dns-ip-panic-fixed]

The documentation describes a worker pool that the code never builds [divergence:cloud-connector.terraform.provider-behavior:parallelism-doc-worker-pool].

What to check:
1. Whether a removed description is really removed on the server after editing one of the nine resources, since the diff is suppressed when the new text is empty.
2. Whether a plan run after applying a description containing `$` comes back clean.
3. Whether a rule created or updated through these resources matches the intent: read it back from the API and compare the ZPA IP group (DNS rules) and the network application groups (forwarding rules).
4. Which field decides whether a location can be changed, since the data source's non_editable attribute is never set.
5. Whether the provider release is identified by the tag that was installed, not by the version string in a request log.

- The provider documentation says parallelism sizes a worker pool that serializes API calls; the code only sizes a channel that nothing uses. [divergence:cloud-connector.terraform.provider-behavior:parallelism-doc-worker-pool]
