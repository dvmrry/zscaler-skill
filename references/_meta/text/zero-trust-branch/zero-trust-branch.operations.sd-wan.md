# How Zero Trust Branch forwards branch traffic: default and custom Internet & SaaS gateways, private application connectivity and site DNS policies (zero-trust-branch.operations.sd-wan)
Also called: ztb custom internet saas gateway; ztb dtls gateway; ztb private app connectivity; ztb site dns policies; ZIA-DTLS next hop

When provisioning appliances, they automatically select the nearest primary and secondary data centers for a DTLS/TLS tunnel; the Internet & SaaS gateway fails back to TLS when DTLS is blocked and back to DTLS once it is restored, and switches to the secondary tunnel if the primary fails. [zero-trust-branch.operations.sd-wan:dtls-default-gateway] The appliance's default Internet & SaaS gateway defaults to fail-close upon failure; for DTLS default gateways Fail-Close is the default if all DTLS tunnels are down, while a custom gateway's default is based on the user configuration. [zero-trust-branch.operations.sd-wan:default-gateway-fail-close] Automatic Internet & SaaS DTLS connectivity and custom Internet & SaaS gateways are each supported for appliances running Zero Trust Branch version 8.1.2 and later. [zero-trust-branch.operations.sd-wan:gateway-version-8-1-2] The wider operations area is in [Where Zero Trust Branch operations are documented: forwarding, Routed Tunnels, segmentation, integrations, logging, monitoring, the Debug Console, troubleshooting and upgrades](kb:zero-trust-branch.operations).

**Custom gateways.** A custom Internet & SaaS gateway defines primary and secondary proxies and how traffic is handled when both are unreachable; custom gateways support DTLS, standard and enhanced high availability modes, FQDNs and IP addresses, with up to two Internet & SaaS gateway objects per site including default and custom gateways. [zero-trust-branch.operations.sd-wan:custom-gateway-support] In a custom gateway the Primary Service Edge is Automatic (an automatic proxy), Manual (the selected data centers, supported for Internet & SaaS subdomains only) or Override (a specified IP address or domain name); the Secondary Service Edge is used when the primary is unreachable and becomes the primary proxy upon confirmation of reachability. [zero-trust-branch.operations.sd-wan:gateway-service-edge-options] On Failure sets the handling when both proxies of a custom gateway are unreachable: Fail-Close (Drop) drops the traffic, and Fail-Open (Allow) sends it directly to the server without the proxy service and should be used with caution. [zero-trust-branch.operations.sd-wan:gateway-on-failure] Using a custom gateway needs a site on a Z-tunnel and a PBR forwarding rule with Next Hop Interface Type ZIA-DTLS and the custom ZIA Gateway; the page says the Switch to Z-Tunnel change for a site using IPSec might take a few minutes to propagate, causing temporary downtime, and the forwarding method change is global for the tenant. [zero-trust-branch.operations.sd-wan:gateway-z-tunnel-pbr]

**Private application connectivity.** Private application connectivity for branches uses a Private Access App Connector, an outbound-only component, to reach private applications in other branches; the branch forwards traffic to the Zero Trust Exchange, which evaluates identity, device posture and policy context configured in Private Access. [zero-trust-branch.operations.sd-wan:private-app-connector] Configuring private application connectivity means adding an App Connector in Private Access for each branch site hosting private applications, deploying the connectors to the sites in the Admin Console, and defining application segments and access policies; the applications can use App Connector-based DNS resolution or a private DNS server in the branch behind its App Connector. [zero-trust-branch.operations.sd-wan:private-app-setup]

**Site DNS policies.** Site DNS policies monitor and apply policies to DNS requests and responses over UDP and TCP; default system policies route Zscaler and Airgap destinations to the WAN DNS gateway, and a system default rule that allows and forwards all DNS traffic has the lowest precedence. [zero-trust-branch.operations.sd-wan:dns-policy-scope-defaults] Site DNS rules can match on criteria such as source IP address or subnet, FQDN, wildcard domains or any domain, and can take actions such as allowing or rejecting queries, redirecting them to DNS gateways, or overriding responses. [zero-trust-branch.operations.sd-wan:dns-policy-criteria-actions] A VLAN IP address can be used as the source for DNS proxy requests so all outbound DNS queries use the same internal IP address, which is required for DNS servers accessed through a Routed Tunnel. [zero-trust-branch.operations.sd-wan:dns-policy-vlan-source] The Add Policy drawer's Action options are Reject (with a chosen error code), Redirect (forward to the selected DNS gateway, with a chosen cache level), Override (return the IP address entered in Override IP) and Skip (disable the policy). [zero-trust-branch.operations.sd-wan:dns-policy-actions] The overview and the drawer give different action lists [divergence:zero-trust-branch.operations.sd-wan:dns-policy-allow-action]. Site DNS policies are processed on first match and can be reordered; once a query matches, later policies are not evaluated. [zero-trust-branch.operations.sd-wan:dns-policy-first-match] The routed tunnel side of DNS proxying is in [How Zero Trust Branch connects sites over Routed Tunnels: hubs, spokes, activation, sharing, policy-based routing and verification](kb:zero-trust-branch.operations.routed-tunnels).

Sources disagree (name both sides):
- The site DNS policies overview lists allowing among the actions a rule can take, while the Add Policy drawer's Action options are Reject, Redirect, Override and Skip, with no Allow. [divergence:zero-trust-branch.operations.sd-wan:dns-policy-allow-action]
  - zscaler-help: Rules can take actions such as allowing or rejecting DNS queries, redirecting them to DNS gateways, or overriding responses.
  - zscaler-help: The Action field offers Reject, Redirect, Override and Skip.
  Impact: An admin looking for an Allow action in the drawer will not find one in the captured list; the overview's wording is a general description and the page does not say how a query is allowed other than by the system default rule.
