# How Zero Trust Branch forwarding (routing) policies and firewall (security) policies are defined and evaluated (zero-trust-branch.deployment.policies)
Also called: ztb forwarding policy; ztb routing policy; ztb security policy; ztb firewall policy

A new site automatically gets four default forwarding policies: Default-ZPA-PBR, Default ZIA Rule, Default-App-Segment-PBR and Default Zscaler Rule. [zero-trust-branch.deployment.policies:default-forwarding-policies] The deployment hub is [How a Zero Trust Branch appliance is deployed: activation, ZTP, virtual machines, mainland China, upgrades and admin roles](kb:zero-trust-branch.deployment) and the objects the policies match on are in [What Zero Trust Branch objects are and how each type is defined](kb:zero-trust-branch.deployment.objects).

**Forwarding policies.** A forwarding rule's Forwarding Method is LAN/WAN, Routed Tunnel, ZIA-DTLS or ZPA; ZIA-DTLS and Override NAT are available only on appliances running version 8.3.0 or later. [zero-trust-branch.deployment.policies:forwarding-methods] The forwarding rule page says that for a rule with WAN as both primary and secondary interface, Traffic Distribution is Best (decided programmatically), Balanced (load balanced between primary and secondary WANs) or None (primary takes as much load as possible). [zero-trust-branch.deployment.policies:forwarding-traffic-distribution] The Enhanced HA page defines the same values differently [divergence:zero-trust-branch.deployment.policies:traffic-distribution-modes]. Advanced options: Match return traffic applies the policy to return traffic, and Apply for locally generated traffic applies it to traffic originating from the appliance; a saved rule takes effect after Commit. [zero-trust-branch.deployment.policies:forwarding-advanced-options] The forwarding policies page says that with a SaaS Apps object as the destination of a forwarding policy, only traffic to the apps in the object is allowed and all other traffic is blocked (per the page's example); Zero Trust Branch Management maintains the SaaS app IP addresses. [zero-trust-branch.deployment.policies:app-based-forwarding] The pages disagree on whether a SaaS App object applies to forwarding [divergence:zero-trust-branch.deployment.policies:saas-app-forwarding-destination].

**Managing and testing forwarding.** Policy Routing Settings include a Prefer local learned routes over the ZIA and ZPA policies toggle and WAN Failover Settings with a Switchover Threshold (minimum WAN score difference to fail over; default 6) and Performance SLA Metrics of packet loss, latency and jitter. [zero-trust-branch.deployment.policies:wan-failover-settings] Forwarding policies can be reordered to change the order of evaluation (a drag icon appears for each custom policy), and deleting one requires entering DELETE. [zero-trust-branch.deployment.policies:forwarding-reorder-delete] The destination IPs of a forwarding policy can be checked on the console with iptables -nvL PBR-RULES -t mangle and then ipset list <destination-match-set-no>. [zero-trust-branch.deployment.policies:forwarding-verify-ipset] Forwarding policies can be tested by pinging from a source device while running sudo tcpdump -i <interface_link_name> icmp on the primary and secondary interfaces. [zero-trust-branch.deployment.policies:forwarding-test]

**Firewall policies.** Firewall policies can be Global (all sites), Template (all sites sharing a template) or Site (one site); new sites automatically get system (default) policies that are editable but cannot be reordered. [zero-trust-branch.deployment.policies:firewall-policy-levels] Firewall policies are evaluated site first, then template, then global; at each of these levels a match applies the policy and stops evaluation, and system (default) policies apply only if no match is found at the site, template and global levels. [zero-trust-branch.deployment.policies:firewall-policy-evaluation] A security policy action is Accept, Reject, Drop or Skip; zones are LAN or WAN, optional, and can be negated; fields also include ports (All, Allowed Ports, Custom Port or port objects) and time schedule group. [zero-trust-branch.deployment.policies:security-policy-fields] Security policies can be viewed, edited, cloned, deleted or reordered at global, template or site level; when reordering, a drag icon appears for each custom policy and step 4 of reordering is to click Save Policy Order. [zero-trust-branch.deployment.policies:security-policy-reorder] [gap:zero-trust-branch.deployment.policies:reorder-commit] For a security policy, edit, clone and delete changes are applied by clicking Commit, and deleting one requires entering DELETE in the confirmation window. [zero-trust-branch.deployment.policies:security-policy-commit-delete] With log throttling enabled, the log flows once per tuple per hour; a security policy can also set a Ransomware Kill Switch color code for its threat level. [zero-trust-branch.deployment.policies:security-policy-logging] The Ransomware Kill Switch color codes are in [How Zero Trust Branch segments devices: Airgap, Airgap-Lite and Airgap+ protection, /32 incompatibilities, assets, tags, the NAC MAC list and the Ransomware Kill Switch](kb:zero-trust-branch.operations.segmentation).

What to check:
1. Which level (site, template, global or system default) holds the matching firewall policy, since evaluation stops at the first match in that order.
2. Whether the appliance runs 8.3.0 or later before relying on ZIA-DTLS or Override NAT in a forwarding rule.

Sources disagree (name both sides):
- The forwarding policies page uses a SaaS Apps object as a forwarding policy destination, while the objects table lists SaaS App as Not applicable for routing policies. [divergence:zero-trust-branch.deployment.policies:saas-app-forwarding-destination]
  - zscaler-help: A forwarding policy can be defined with the SaaS Apps object as the destination.
  - zscaler-help: The SaaS App object type is a Destination for firewall policies and Not applicable for routing and DNS policies.
  Impact: An admin building an application-based forwarding rule cannot tell whether the SaaS Apps object is accepted as a routing destination.
- The forwarding rule page and the Enhanced HA page define the same Traffic Distribution values (Best, Balanced, None) differently. [divergence:zero-trust-branch.deployment.policies:traffic-distribution-modes]
  - zscaler-help: None means the primary interface takes as much load as possible, and Best means Zero Trust Branch decides programmatically.
  - zscaler-help: None means the system selects a path without active direction, and Best sends traffic to the single best-performing WAN link of either appliance.
  Impact: An admin choosing None for a rule or an Enhanced HA site cannot tell from the pages whether the primary interface carries the load or the system picks the path.
