# How Zero Trust Branch high availability works: standard HA, Enhanced WAN Edge HA, VRRP and ebond bonding interfaces (zero-trust-branch.deployment.high-availability)
Also called: ztb ha; WAN Edge HA; Advanced HA; ebond; ebond0; ebond1; WAN Transit Link

The standard HA page describes a cluster of two identical appliances, a primary (active) and a secondary (standby) node; traffic session state synchronization gives stateful failover and VRRP determines roles, monitors health and initiates failover. [zero-trust-branch.deployment.high-availability:ha-cluster-model] The deployment hub is [How a Zero Trust Branch appliance is deployed: activation, ZTP, virtual machines, mainland China, upgrades and admin roles](kb:zero-trust-branch.deployment).

**Standard HA.** Standard HA prerequisites: a dedicated unused VLAN for HA only, two switch ports on that VLAN, a cable from each appliance's GE4 to the switch, and the appliances connected through a switch rather than a crossover cable. [zero-trust-branch.deployment.high-availability:ha-prerequisites] For a standard HA cluster, connecting the appliances directly to each other is not supported: failover does not function properly; the HA link synchronizes TCP, UDP and ICMP connections. [zero-trust-branch.deployment.high-availability:ha-direct-connect-unsupported] An HA site requires an HA template (standard_mode_ha deployment type); the standard HA page says the appliance activated first becomes the primary node and the other the secondary, and during activation states such as Initializing and Post-update appear before primary Active and secondary Standby. [zero-trust-branch.deployment.high-availability:ha-template-and-activation-order] The pages disagree on how the primary is chosen [divergence:zero-trust-branch.deployment.high-availability:primary-selection].

**Enhanced WAN Edge HA.** The Enhanced HA page says Enhanced HA (WAN Edge HA) enables active-active WAN traffic distribution using a dedicated WAN Transit Link between the active and standby nodes and eliminates dependency on Layer 2 switches; LAN interfaces remain in standard HA active-standby mode. [zero-trust-branch.deployment.high-availability:enhanced-ha-model] Enhanced HA does not support stateful failover for traffic routed through the secondary appliance, so active TCP, HTTP or other session-based traffic is interrupted and must be re-established if it switches between the WAN links of the two appliances. [zero-trust-branch.deployment.high-availability:enhanced-ha-no-stateful-failover] Enhanced WAN Edge HA supports only ZT600, ZT800 and ZT8010 (not ZT400 or VMs); the WAN Transit Link uses GE5 on ZT600 and ZT800 and XE10 on ZT8010, on both appliances, and WAN links must go to separate ISPs. [zero-trust-branch.deployment.high-availability:enhanced-ha-prerequisites] The page's GE5 transit port does not match the deployment page's interface table for the ZT600 and ZT800 [gap:zero-trust-branch.deployment.high-availability:transit-port-vs-deployment-table]. The WAN Transit Link connects via a direct back-to-back Ethernet cable or a switch; if a switch is used, its ports must be on a different VLAN from the standard HA control link. [zero-trust-branch.deployment.high-availability:enhanced-ha-transit-link] The Enhanced HA topology has two connections between the appliances: the standard HA link for control plane communication and the WAN Transit Link for data plane traffic; failover scenarios revert to standard HA using the HA link, and the cluster reverts to standard HA on a WAN transit link failure. [zero-trust-branch.deployment.high-availability:enhanced-ha-two-links] In an Enhanced HA cluster the UI shows one appliance Active and the other Standby for their control-plane roles, but both can forward WAN traffic; the embedded Private Access App Connector runs active-active while the gateway is active-standby. [zero-trust-branch.deployment.high-availability:enhanced-ha-ui-roles] The Enhanced HA page says WAN HA Mode Enhanced enables active-active routing (the section appears only for sites using an Advanced HA template), and Traffic Distribution is Balanced (all selected WAN links on both appliances, Failover Group Active-Active Links), Best (single best-performing link, Active-Standby Links) or None (system selects a path without active direction). [zero-trust-branch.deployment.high-availability:enhanced-ha-traffic-distribution] The forwarding policies page defines the same values differently, see [How Zero Trust Branch forwarding (routing) policies and firewall (security) policies are defined and evaluated](kb:zero-trust-branch.deployment.policies). With Debug Logs set to High, the WAN interface scores from WAN monitoring can be read with cat /var/log/syslog | grep wan-mon. [zero-trust-branch.deployment.high-availability:enhanced-ha-wan-monitoring] How the WAN score is computed is not defined on these pages [gap:zero-trust-branch.deployment.high-availability:wan-score-scale].

**VRRP.** Before release 7.8 Zero Trust Branch ran VRRP over a WAN link, which the page calls less reliable; from release 7.8 a dedicated HA link makes VRRP independent of WAN issues. [zero-trust-branch.deployment.high-availability:vrrp-dedicated-ha-link] Without VRRP authentication, any appliance in the same broadcast domain could send advertisements with a higher priority and take over as master; a misconfigured appliance with an identical VRRP ID could disrupt an active group. [zero-trust-branch.deployment.high-availability:vrrp-auth-rationale] Changing the VRRP password on an existing site could trigger a VRRP switchover and should be done in a scheduled maintenance window. [zero-trust-branch.deployment.high-availability:vrrp-password-change] The VRRP page recommends a password of 6 characters or fewer because of known issues with longer passwords, and says the password may contain only printable ASCII characters (A-Z, a-z, 0-9). [zero-trust-branch.deployment.high-availability:vrrp-password-length] The VRRP Password field is optional and takes a maximum of 8 alphabetic characters. [zero-trust-branch.deployment.high-availability:vrrp-password-field] VRRP Group ID is a number between 1 and 255 that Zero Trust Branch fills in automatically; Priority is between 1 and 255 and the site with the highest number is primary. [zero-trust-branch.deployment.high-availability:vrrp-group-priority] The VRRP Advertisement Interval defaults to 1 second, and the secondary becomes primary if it misses three advertisements from the primary. [zero-trust-branch.deployment.high-availability:vrrp-advertisement] Enabling Preempt turns on interface tracking with a default weight of 10; if the tracked interface of the primary appliance goes down the secondary becomes primary; Advanced Track Options are shown only when Preempt is enabled and are supported only on appliances running version 8.3.0 or later. [zero-trust-branch.deployment.high-availability:vrrp-preempt-tracking]

**Bonding interfaces.** The two bonding interfaces ebond0 and ebond1 are logical interfaces combining multiple physical ports, with load balancing using 5-tuple hashing; settings configured once on the logical interface apply to the member interfaces. [zero-trust-branch.deployment.high-availability:ebond-model] Bonding limitations: members must be the same type (all LAN or all WAN) and same port speed; Q-in-Q is not supported; bonding on the primary WAN interface is for untagged interfaces only; all member links must terminate on the same node. [zero-trust-branch.deployment.high-availability:ebond-limitations] An ebond can connect to a port channel on a switch stack or MLAG, virtual Port Channel or VSS provided it is a single Layer 2 domain presenting one logical Layer 3 nexthop (SVI). [zero-trust-branch.deployment.high-availability:ebond-switch-side] Deploying with an ebond WAN interface is not supported on the ZT400 and requires LACP (802.3ad) to be configured on the switch where the WAN interfaces connect. [zero-trust-branch.deployment.high-availability:ebond-deploy-support] The VLAN configuration page says bonding interfaces support 802.1Q tagging (sub-interfaces) for both LAN and WAN, and that the SVI moves to Zero Trust Branch so VLANs are added after the appliance is registered. [zero-trust-branch.deployment.high-availability:ebond-vlan-tagging] The pages disagree on tagging over a primary WAN bond [divergence:zero-trust-branch.deployment.high-availability:ebond-wan-tagging]. No maximum number of member interfaces per ebond is stated [gap:zero-trust-branch.deployment.high-availability:ebond-member-limit].

What to check:
1. Whether the appliance is a ZT600, ZT800 or ZT8010 and not a ZT400 or VM, before planning Enhanced HA.
2. Whether the standard HA appliances are cabled through a switch and not directly to each other.
3. Whether the appliance is a ZT400 before planning an ebond WAN interface.

Sources disagree (name both sides):
- The standard HA creation page says the first appliance activated becomes primary, while the VRRP page ranks sites by priority to decide the primary and the HA model says VRRP determines the roles. [divergence:zero-trust-branch.deployment.high-availability:primary-selection]
  - zscaler-help: The appliance that is activated first becomes the primary node.
  - zscaler-help: The VRRP priority, with the highest number winning, determines the primary in the group.
  Impact: An admin who sets VRRP priorities may expect a different primary than the activation order gives.
- The VLAN page says bonding interfaces support 802.1Q tagging for both LAN and WAN, while the bonding page says bonding on the primary WAN interface supports untagged interfaces only. [divergence:zero-trust-branch.deployment.high-availability:ebond-wan-tagging]
  - zscaler-help: Bonding interfaces support tagging with 802.1Q sub-interfaces for both LAN and WAN.
  - zscaler-help: Bonding on the primary WAN interface is for untagged interfaces only, and VLAN-tagged subinterfaces on it are not supported.
  Impact: Planning tagged subinterfaces on a bonded primary WAN interface works from one page and fails from the other.
