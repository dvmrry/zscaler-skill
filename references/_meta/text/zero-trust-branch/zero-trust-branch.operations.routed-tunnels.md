# How Zero Trust Branch connects sites over Routed Tunnels: hubs, spokes, activation, sharing, policy-based routing and verification (zero-trust-branch.operations.routed-tunnels)
Also called: ztb routed tunnels; ztb hub and spoke; ztb site-to-site; ztb add hub; Share Over RT; User Reachable IP

Routed Tunnels connect branches in a hub-and-spoke design, with a physical or virtual appliance in a data center as the hub and branch appliances as spokes, and preserve the source IP addresses that applications such as VoIP phones, TACACS+ and Active FTP need. [zero-trust-branch.operations.routed-tunnels:rt-purpose-topology] In the page's example topology both spokes connect to a pair of identical hubs (hubA and hubB) for redundancy, and the hub appliances do not communicate with each other. [zero-trust-branch.operations.routed-tunnels:rt-example-redundancy] The wider operations area is in [Where Zero Trust Branch operations are documented: forwarding, Routed Tunnels, segmentation, integrations, logging, monitoring, the Debug Console, troubleshooting and upgrades](kb:zero-trust-branch.operations).

**Hubs.** Hubs can be physical or virtual Zero Trust Branch appliances, typically in the customer's data center and launched from the same image as the appliance; routed tunnel hubs cannot be deployed in a public cloud. [zero-trust-branch.operations.routed-tunnels:hub-requirements] The hub's User Reachable IP is the address the spokes use to communicate with it; if the hub and spokes are separated by an external network such as the internet, the hub's post-NAT address is entered, and an incorrect value can cause unexpected results or an end-to-end connectivity failure. [zero-trust-branch.operations.routed-tunnels:hub-user-reachable-ip] Adding an on-premises hub displays an activation code that is used when the gateway is activated. [zero-trust-branch.operations.routed-tunnels:hub-activation-code]

**Activation.** There are two ways to activate a Zero Trust Branch appliance: the Activation Code Method and the Activation URL Method. [zero-trust-branch.operations.routed-tunnels:rt-activation-two-methods] The activation code method uses the activation code saved when the site was added, and the appliance must first be configured with the same parameters configured when the site was created in the Admin Console. [zero-trust-branch.operations.routed-tunnels:rt-activation-code-method] The activation URL method uses the URL saved when the site was added, and the URL contains the configuration data for the WAN interface and the activation code. [zero-trust-branch.operations.routed-tunnels:rt-activation-url-method] Configuring the web proxy during activation is required only if the Zero Trust Branch appliance is deployed behind a firewall. [zero-trust-branch.operations.routed-tunnels:rt-activation-web-proxy] Zscaler supports one subinterface per WAN interface, and appliance activation is supported over the WAN interface on the main interface (tagged), not on a subinterface (untagged). [zero-trust-branch.operations.routed-tunnels:rt-activation-subinterface] The 8.1.2-P1 release note differs on tagged WAN activation [divergence:zero-trust-branch.operations.routed-tunnels:tagged-wan-activation]. The general deployment procedure is in [How a Zero Trust Branch appliance is deployed: activation, ZTP, virtual machines, mainland China, upgrades and admin roles](kb:zero-trust-branch.deployment).

**Spokes.** A spoke's routed tunnel is configured under Connectivity > Routed Tunnel by selecting the primary and secondary hubs and the WAN interfaces used to reach them and enabling Connect To Hub. [zero-trust-branch.operations.routed-tunnels:rt-spoke-config] Spokes enable sharing over RTs at the VLAN level (Share on Routed Tunnel) and per static route (Share Over RT), and a VLAN can be set to Use for DNS Proxy so DNS queries sent over the RT use that VLAN's IP address as source. [zero-trust-branch.operations.routed-tunnels:rt-sharing] A policy-based routing rule with Share Over RT directs spoke traffic over the site-to-site VPN; only spokes that initiate traffic need a rule, and response traffic is handled automatically. [zero-trust-branch.operations.routed-tunnels:rt-pbr-rule] DNS policies for the shared VLAN are in [How Zero Trust Branch forwards branch traffic: default and custom Internet & SaaS gateways, private application connectivity and site DNS policies](kb:zero-trust-branch.operations.sd-wan).

**Verification.** The routed tunnel verification commands are run from the Zscaler Admin Console using the Console tab on the site details page. [zero-trust-branch.operations.routed-tunnels:rt-verify-console] The pages name the console's location differently [divergence:zero-trust-branch.operations.routed-tunnels:console-location]. Routing table 500 manages the site-to-site tunnels (s2s overlays). [zero-trust-branch.operations.routed-tunnels:rt-table-500] To verify that the hubs' site-to-site BGP VRF is up the page runs show vrf, and to verify BGP peering with the spokes and the peer uptime it runs show ip bgp vrf vrf-s2s summary; BFD detects link failure. [zero-trust-branch.operations.routed-tunnels:rt-bgp-vrf-bfd] Traffic sent over the routed tunnel is verified in the flow logs at Data Explorer > Zero Trust Branch > Flow Logs. [zero-trust-branch.operations.routed-tunnels:rt-flow-log-verify]

**Example topology.** In the example topology the spoke interfaces are s2s_overlay0 and s2s_overlay1 (GRE tunnels to hubA and hubB) and wg_vpn_client0 and wg_vpn_client1 (routed tunnels to hubA and hubB). [zero-trust-branch.operations.routed-tunnels:rt-example-spoke-interfaces] In the example topology the hub interfaces are s2s_overlay0 and s2s_overlay1 (GRE tunnels to the Pod30 and Pod50 spokes) and wg_client (a routed tunnel to the Pod50 spoke). [zero-trust-branch.operations.routed-tunnels:rt-example-hub-interfaces] Capacity limits are not in the captured pages [gap:zero-trust-branch.operations.routed-tunnels:capacity-limits].

Sources disagree (name both sides):
- The Routed Tunnels page says activation is supported over the WAN interface on the main interface, which is tagged, while the 8.1.2-P1 release note says WAN interfaces previously did not support tagged VLANs for activation and that tagged activation is added for a physical WAN interface with a static IP address. [divergence:zero-trust-branch.operations.routed-tunnels:tagged-wan-activation]
  - zscaler-help: Activation is supported over the WAN interface on the main interface (which is tagged), not on a subinterface (which is untagged).
  - zscaler-help: From 8.1.2-P1 a VLAN tag can be configured on a physical WAN interface with a static IP address for appliance activation; previously WAN interfaces did not support tagged VLANs for activation.
  Impact: Tagged WAN activation depends on the release and on a static IP address; the Routed Tunnels page states neither, so on an appliance older than 8.1.2-P1 or using DHCP do not assume a tagged WAN activates.
- The pages name three places for the site console: the >_Console tab on the site details page, Troubleshooting > Console, and the Appliance Admin Console tab. [divergence:zero-trust-branch.operations.routed-tunnels:console-location]
  - zscaler-help: The Routed Tunnels page opens the console from the >_Console tab on the site details page.
  - zscaler-help: The Debug Console opens from the Troubleshooting left tab > Console top tab.
  - zscaler-help: The SIEM integration page opens the Appliance Admin Console tab and clicks Connect.
  Impact: The label to look for differs by page and possibly by release; the pages do not say whether these are one console or different ones.
