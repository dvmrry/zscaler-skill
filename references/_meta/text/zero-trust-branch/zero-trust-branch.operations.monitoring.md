# How Zero Trust Branch is monitored: the Insights dashboard, traffic flow chart, alarms, SNMP and interface health monitoring (zero-trust-branch.operations.monitoring)
Also called: ztb insights dashboard; ztb traffic flow chart; ztb alarms; ztb snmp; ztb snmpv3 profile; ztb interface monitoring; ztb link scoring

The Insights dashboard (Dashboard > Insights) has predefined Assets and Sites widgets showing totals, and widgets can be edited to a pie or bar chart with a TopN limit and a Group by field such as Assignment type, Brand, Capability, Category, Group, Location, Model or Network. [zero-trust-branch.operations.monitoring:insights-widgets] The default graphs are not fully listed [gap:zero-trust-branch.operations.monitoring:insights-default-graphs]. The wider operations area is in [Where Zero Trust Branch operations are documented: forwarding, Routed Tunnels, segmentation, integrations, logging, monitoring, the Debug Console, troubleshooting and upgrades](kb:zero-trust-branch.operations).

**Traffic flow chart.** The traffic flow chart is built on a graph database, with each endpoint a node and communication between endpoints an edge. [zero-trust-branch.operations.monitoring:traffic-flow-chart-graph] Edges are color-coded: red is blocked communication, green is allowed, grey uses a default policy, and black means multiple traffic flows with different protocols. [zero-trust-branch.operations.monitoring:traffic-flow-edge-colors] Communications between endpoints are logged and mapped onto the traffic flow chart, saved for 90 days by default, and it can take up to 10 minutes after an event before traffic appears in the chart, so flow logs are suggested for a more real-time response. [zero-trust-branch.operations.monitoring:traffic-flow-chart-retention] The log side of the chart is in [How Zero Trust Branch logs traffic: architecture, log types and formats, retention and limits, throttling and tenant isolation](kb:zero-trust-branch.operations.logging).

**Alarms.** Appliances detect critical events such as heartbeat or upgrade failures and send set or clear alarm requests to the API server, and alarms are stored in a dedicated per-customer alarms table with no alarm information shared between tenants. [zero-trust-branch.operations.monitoring:alarm-processing] Alarms are viewed on the Alarms page (Administration > Alerts > Zero Trust Branch); management notifies appliances of state changes over MQTT, appliances converge by eventual consistency, and an appliance that cannot converge sends asynchronous alarm notifications back. [zero-trust-branch.operations.monitoring:alarm-view-mqtt] The alarm types and history are not in the captured pages [gap:zero-trust-branch.operations.monitoring:alarm-coverage].

**SNMP.** SNMP supports the standard IF-MIB, SYS-MIB and standard Linux MIBs, and custom MIBs are not supported. [zero-trust-branch.operations.monitoring:snmp-mibs] Both SNMPv2 and SNMPv3 are supported and v3 is recommended; both can be enabled at once but only one version can be active on a site at a time, and versions 7.x and earlier use SNMPv2 while later versions use SNMPv3. [zero-trust-branch.operations.monitoring:snmp-versions] A site uses an SNMPv3 profile selected on the site details page under Settings > SNMPv3. [zero-trust-branch.operations.monitoring:snmpv3-site-profile] An SNMPv3 profile's security group level is authPriv (authentication and encryption) or authNoPriv (authentication but no encryption), and its security view lists OIDs to include and to exclude. [zero-trust-branch.operations.monitoring:snmpv3-security-level-view] SNMP traps go to the receiving server's UDP port, typically 162, while port 161 is used for queries from SNMP managers, and both ports must be enabled on the firewall. [zero-trust-branch.operations.monitoring:snmp-trap-ports] When monitoring branch appliances remotely from Private Access, Zscaler recommends the appliances' Management IP addresses for SNMP queries, which avoids manually adding multiple LAN IP addresses or subnets. [zero-trust-branch.operations.monitoring:snmp-private-access] The release notes limit which appliances can be monitored that way [divergence:zero-trust-branch.operations.monitoring:snmp-private-access-active-only]. The supported algorithm values are not enumerated [gap:zero-trust-branch.operations.monitoring:snmp-values]. Interface limits seen from the appliance are in [What the Zero Trust Branch Debug Console documents: site scope, command limits, NTP, IPSec, enrollment files, DNS proxy and SNMP interfaces](kb:zero-trust-branch.operations.debug-console).

**Interface health.** Interface health monitoring sends continuous probes to a predefined target to monitor interface link liveliness, configured per interface with a probe target (IP address or FQDN), a probe interval in seconds and a retry count. [zero-trust-branch.operations.monitoring:interface-health-monitor] Link scoring is on a scale of 0 to 30 based on jitter, latency and packet loss, normalized over a window of 30 iterations. [zero-trust-branch.operations.monitoring:link-scoring] The probe limits and score thresholds are not in the captured pages [gap:zero-trust-branch.operations.monitoring:interface-monitoring-limits].

Sources disagree (name both sides):
- The SNMP page recommends the appliances' Management IP addresses for remote monitoring from Private Access without limiting it to active appliances, while the 8.1.2 release note says only active appliances can be monitored that way. [divergence:zero-trust-branch.operations.monitoring:snmp-private-access-active-only]
  - zscaler-help: When monitoring branch appliances remotely from Private Access, use the appliances' Management IP addresses for SNMP queries.
  - zscaler-help: If the management interface is used to monitor appliances using SNMP over Private Access, only active appliances can be monitored.
  Impact: Standby appliances in an HA pair may not answer SNMP queries sent to their Management IP address over Private Access; the SNMP page states no such limit.
