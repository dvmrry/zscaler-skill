# What the Zero Trust Branch configuration and activation troubleshooting page documents: symptoms and the checks it gives (zero-trust-branch.operations.troubleshooting)
Also called: ztb activation issues; ztb appliance status red; ztb gwactivation; ztb ha active-active troubleshooting; ztb devices not receiving ip address

Adding a site can fail with the error "ZIAM SendLocationRequest: Error creating location response.", and the fix given is to check whether the site or location name already exists in Internet & SaaS (ZIA). [zero-trust-branch.operations.troubleshooting:location-not-recognized] The activation-issues checklist includes that DNS resolves gwactivation.goairgap.com, <customer name>-api.goairgap.com and hub3.goairgap.com, and that the web proxy is configured. [zero-trust-branch.operations.troubleshooting:activation-dns] If the gateway is not working after an update and DNS cannot resolve *-api.goairgap.com, the steps are to delete the site and then reconfigure the site, gateway, network and web proxy. [zero-trust-branch.operations.troubleshooting:activation-after-update] The deployment procedure is in [How a Zero Trust Branch appliance is deployed: activation, ZTP, virtual machines, mainland China, upgrades and admin roles](kb:zero-trust-branch.deployment), and the wider operations area is in [Where Zero Trust Branch operations are documented: forwarding, Routed Tunnels, segmentation, integrations, logging, monitoring, the Debug Console, troubleshooting and upgrades](kb:zero-trust-branch.operations).

**Connectivity.** A red appliance status in the Admin Console after an activation issue indicates that communication between the appliance and the console is severed and the appliance cannot reach the internet; the checks include storage utilization crossing the threshold level in the alarms and audit logs. [zero-trust-branch.operations.troubleshooting:connectivity-red-status] The appliance must be allowed outbound connections to hub.goairgap.com (TCP 1883) and wg.goairgap.com (UDP 51820), and App ID, IDS, IPS and SSL Forward Proxy should be disabled for the control traffic initiated from the appliance on the upstream L3 device. [zero-trust-branch.operations.troubleshooting:outbound-ports-upstream] The page and the deployment pages name different hub hosts for TCP 1883 [divergence:zero-trust-branch.operations.troubleshooting:hub-host-name]. For a gateway shown as disconnected, option 4 (Show Gateway Status) in the console checks the gateway status, a name resolution error must be resolved before the appliance reaches the cloud, and the upstream L3 device should not block the DNS (UDP 53) port. [zero-trust-branch.operations.troubleshooting:gateway-disconnected] The page numbers the console menu differently from the deployment pages [divergence:zero-trust-branch.operations.troubleshooting:configure-gateway-menu-number]. The Debug Console is in [What the Zero Trust Branch Debug Console documents: site scope, command limits, NTP, IPSec, enrollment files, DNS proxy and SNMP interfaces](kb:zero-trust-branch.operations.debug-console). The page's standby-standby mode is not defined [gap:zero-trust-branch.operations.troubleshooting:standby-standby-mode].

**High availability.** For appliances in active-active mode, HA troubleshooting checks that the appliances reach each other over the HA interface, the switch is not blocking VRRP messages, there are no MAC move or snooping violations, GARP messages are not blocked, and the SVI interface for the VLAN on the switch is disabled. [zero-trust-branch.operations.troubleshooting:ha-active-active]

**Devices and traffic.** If the appliance is a DHCP relay and devices are not receiving an IP address, the checks include that the DHCP server has a route and can reach the subnet and that no other DHCP servers or relays run in the VLAN. [zero-trust-branch.operations.troubleshooting:dhcp-relay-checks] Devices that get an IP address and ping the default gateway but cannot reach the internet is described as occurring when the upstream firewall or router has no return route to the VLAN with the appliance WAN virtual IP address as next hop. [zero-trust-branch.operations.troubleshooting:no-internet-return-route] If NAT is enabled, packets egressing the WAN interface must carry the WAN interface's source IP address, which the packet capture must show. [zero-trust-branch.operations.troubleshooting:nat-source-check] For east-west traffic with a Windows test device, the host firewall must not be blocking inbound traffic, and Windows has three firewall profiles. [zero-trust-branch.operations.troubleshooting:east-west-windows-firewall] Checking that a segmentation policy works includes confirming the policy hit count is increasing (requires version 7.7.x), disabling log throttling for the specific policies if no flow logs appear, and, when testing with Windows ICMP, waiting 5 minutes for the session to close because Windows ICMP uses the same ICMP ID. [zero-trust-branch.operations.troubleshooting:segmentation-policy-checks]

Sources disagree (name both sides):
- The activation-issues page lists hub.goairgap.com on TCP 1883 as the outbound destination, while its own DNS checklist and the deployment procedure use hub3.goairgap.com:1883. [divergence:zero-trust-branch.operations.troubleshooting:hub-host-name]
  - zscaler-help: The appliance must be allowed outbound connections to hub.goairgap.com (TCP 1883).
  - zscaler-help: The deployment procedure lists the web proxy as hub3.goairgap.com:1883.
  - zscaler-help: The 8.1.2-P1 release note refers to the hub3.goairgap.com:1883 proxy.
  Impact: A firewall rule built from the outbound-ports list alone may allow hub.goairgap.com but not the hub3 host the appliance's web proxy uses; the pages do not say whether both hosts are needed.
- The activation-issues page gives Configure Gateway as console menu item 1, while the deployment page gives it as item 2. [divergence:zero-trust-branch.operations.troubleshooting:configure-gateway-menu-number]
  - zscaler-help: In the console, enter 1 (Configure Gateway).
  - zscaler-help: In the console, enter 2 (Configure Gateway).
  Impact: Menu numbers, including 4 (Show Gateway Status) on the troubleshooting page, may differ by release; the pages do not tie the numbering to a version, so confirm the label on the menu before entering a number.
