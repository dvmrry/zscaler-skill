# The ZDX application on ServiceNow: roles, webhook URLs, Deep Tracing, Root Cause Analysis and incident settings (zdx.alerts.servicenow)
Also called: zdx servicenow; servicenow integration; zdx integration on servicenow; servicenow incident management; servicenow event management; zdx_management role; zdx_dt_management; servicenow root cause analysis; servicenow deep tracing; zdx servicenow settings module

ZDX alerts can feed ServiceNow, and the ZDX application on the ServiceNow store adds Deep Tracing, Root Cause Analysis and incident settings on the ServiceNow side. ZDX supports integration of IT Service Management (ITSM) via Incident Management (IM) and IT Operations Management (ITOM) via Event Management (EM); for Event Management the steps are to enable ITOM and to request the EM plugin and install it from the store when it is available. [zdx.alerts.servicenow:im-and-em] The integration article lists creating Deep Tracing sessions for deeper granularity and process-level information for a user, running a Root Cause Analysis to help identify the root cause of a drop in an application's ZDX Score, and mapping the categories and subcategories for incoming alerts or created incidents. [zdx.alerts.servicenow:integration-features]

**Roles and credentials.** The ServiceNow service user is created with the Web Services Access only checkbox selected (Zscaler recommends an email address in lieu of a user ID); web service users needing Incident Management get the x_zsca2_zdx_manage.zdx_management role, Deep Tracing users the x_zsca2_zdx_manage.zdx_dt_management role, web service users needing Event Management the evt_mgmt_integration role, and active users managing the application the x_zsca2_zdx_manage.zdx_em_admin and evt_mgmt_user roles. [zdx.alerts.servicenow:service-user] The ZDX role created for the ServiceNow webhook has Diagnostics Full, Webhooks Full, User & Device Names Visible, Configuration Access Full, Alerts Full and UCaaS Monitoring View Only. [zdx.alerts.servicenow:zdx-role] For Deep Tracing and Root Cause Analysis the integration article has a ZDX role with Dashboard Access View Only, Deep Tracing Full and Device and User Information Visible, then an API key created on the API Key Management page; the ServiceNow Settings module takes the Zscaler Admin Console URL as ZDX PORTAL URL (for example admin.zdxcloud.net), the ZDX Public API URL as ZDX API URL (for example api.zdxcloud.net), and the Key ID and Key Secret from the ZDX API key. [zdx.alerts.servicenow:api-key-and-urls] The permission names differ between the guides [gap:zdx.alerts.servicenow:permission-names].

**The webhook.** The webhook URL is https://<your-instance-ID>.service-now.com/api/x_zsca2_zdx_manage/incident_management_api for Incident Management or https://<your-instance-ID>.service-now.com/api/global/em/jsonv2 for Event Management; Basic authentication takes the username and password of the previously created service user, and OAuth takes the application ServiceNow and the Client ID of the previously created OAuth 2.0 API endpoint. [zdx.alerts.servicenow:webhook-urls] For OAuth, an OAuth API endpoint for external clients is created in ServiceNow under Application Registry with the redirect URL https://admin.<cloud name>/zdx/admin/webhooks; if the Client Secret is left empty it auto-generates one, and Zscaler recommends a refresh token lifespan of 5 years from the current date and an access token lifespan of 1 hour to maximize reuse. [zdx.alerts.servicenow:oauth-endpoint] For OAuth, Test Webhook does not post a test message on ServiceNow and instead acquires the OAuth token; to see whether a test webhook is recorded, the ServiceNow Incidents or ServiceNow Events module is selected from the menu. [zdx.alerts.servicenow:test-check] The generic webhook page is [ZDX alert webhooks: authentication, testing, platform guides and the payload fields the sample scripts read](kb:zdx.alerts.webhooks).

**Deep Tracing and Root Cause Analysis.** Deep Tracing is a type of Diagnostics session, and in ServiceNow only Deep Tracing can be configured. [zdx.alerts.servicenow:deep-tracing-only] A Deep Tracing session from ServiceNow runs for 5 minutes, 15 minutes, 30 minutes or 60 minutes; its name includes the current incident number by default, Device Probing gathers device data, and the impacted user, the application's Web probe and Cloud Path probe are selected, with Cloud Path Probe Thresholds for Packet Loss (%) and Latency (ms). [zdx.alerts.servicenow:deep-tracing-session] Under the Application section Analyze Score can be clicked on an existing application if a low score is detected (less than or equal to 34); when the Root Cause Analysis is completed a list of factors that determined the ZDX Score can be viewed. [zdx.alerts.servicenow:root-cause-analysis] In the integration article's Alert Impact view the impacted devices are sorted by Departments, Geolocations and Zscaler Locations; the Impacted Users page lists the impacted devices and their users that meet the alert rule's criteria, with a maximum of 100 devices displayed and a link to the impacted device page in the Zscaler Admin Console. [zdx.alerts.servicenow:impact-views] A sentence on which views appear for a ZDX Score alert is unclear in the article [gap:zdx.alerts.servicenow:impact-views-sentence]. The console's Diagnostics sessions are in [ZDX Diagnostics Sessions (deep traces): what they are and where each part is covered](kb:zdx.diagnostics).

**Mappings and settings.** To map ZDX alert types to ServiceNow categories, sys_choice.list is entered in the Filter Navigator in the Global Application scope, and each record's Element is category or subcategory, with, for a subcategory, the value of the root category as Dependent Value. [zdx.alerts.servicenow:category-mapping] Mapping for Zscaler Alerts maps all the ZDX alerts to one category and uses subcategories for specific ZDX types; for a per-type mapping such as Device, if the root mapping is not empty the value is mapped to the incident table's subcategory field, if it is empty to the category field, and if no mapping was provided at all the category field is mapped to Inquiry / Help. [zdx.alerts.servicenow:mappings-module] The article's mapping of a ZDX Score alert type sits beside the console's retirement of that type: [Configuring ZDX alert rules: types, filters, metrics, throttling, delivery, templates and labels](kb:zdx.alerts.rules). If users have emails or usernames that differ from the Client Connector login, the User Domain Settings can append or replace the domain; None, the default selection, requires no modification, and configuring the settings does not manipulate the existing data in the ServiceNow user record. [zdx.alerts.servicenow:user-domain] In the application's settings it is mandatory to use the user ID of the service user, otherwise the Caller name remains empty in incidents, and the resolver name or ID for automatically resolved incidents should be the web service user's ID; the transform script's logging level defaults to Information, incidents are created only for alerts at or above a minimum severity whose default is High, and the default resolution code is Closed/Resolved by the caller. For auto-resolve, if the value is Yes the incident state is set to Resolved, otherwise the state does not change but the Active field is set to false. [zdx.alerts.servicenow:settings-module]

**The developer sample.** The developer guide says its ServiceNow instance automatically hibernates so it should be woken every 24 hours, and is reclaimed if unused for 10 days; its Scripted REST API security steps involve the Requires authentication and Requires ACL authorization checkboxes, a later step deselects Requires authentication, and the token in the script (12345679 in the script) must be edited to the one the ZDX webhook uses. [zdx.alerts.servicenow:developer-instance] The developer sample script queries for an incident by the alert ID in the short description, uses the category ZDX Alerts, and sets the close code Alert resolved or Rule deleted or modified. [zdx.alerts.servicenow:developer-incident-mapping] The fields the script reads are in [The ServiceNow developer guide's sample script reads alertId, ruleName (returning without action when it equals test), zdxUrl, startTime and endTime (multiplied by 1000 before use as a date), a status tested against STARTED, ENDED_ON_RULE_DEL and ENDED_ON_RULE_MODIFY (anything else treated as resolved), a severity of High, Medium or Low, an alertType of Incident or ZProbe, geolocationCount, impactedDeviceCount, impactedUserCount, context with attribute and epicenter, zscaler_hosted_locations, deptCount, osverCount, and criteria with op and conditions holding conditionString, isHit and stats min, max and avg.](kb:zdx.alerts.webhooks:payload-servicenow-sample).

What to check:
1. For a ServiceNow user who cannot reach a feature, the roles on the service user against the roles each feature names.
2. For a webhook to ServiceNow, the URL form for Incident Management or Event Management and the authentication type, and for OAuth the redirect URL and token lifespans.
3. For incidents with an empty caller or an unexpected category, the Settings module's service user ID and the Mappings module's root mapping.
