# ZDX alert webhooks: authentication, testing, platform guides and the payload fields the sample scripts read (zdx.alerts.webhooks)
Also called: zdx webhook; alert webhook; webhook bearer token; test webhook; authenticate tenant; zdx webhook payload; zdx pagerduty; zdx slack webhook; zdx opsgenie; zdx splunk hec

A ZDX webhook is a destination an alert rule can deliver to instead of, or as well as, email; the webhook pages are one generic page and a guide per platform, and each platform's facts below come from its own guide. When an event occurs the webhook sends real-time data to a specific URL or API endpoint as an HTTP callback; webhooks can be configured for ZDX to deliver alerts about application, device or network performance, and multiple alert rules can be configured to the same webhook. [zdx.alerts.webhooks:what] A webhook has an Authentication Type (Basic, Token, OAuth) and a Status (Enabled, Disabled); its URL must not include any spaces, and the authentication type used is determined by the webhook provider. [zdx.alerts.webhooks:fields] The generic page says Basic takes a Username and Password; Token takes the bearer token from the webhook provider, and for webhooks that do not generate one any text (for example 1234) meets the field requirement; OAuth takes an application, Client ID, Client Secret and a Refresh Token Expiration date (default the current date) and Authenticate Tenant authorizes access, and OAuth 2.0 can be configured for ServiceNow. [zdx.alerts.webhooks:auth-types]

**Testing and what arrives.** Test Webhook checks the configuration; for OAuth it does not post a test message and instead acquires the OAuth token, and on a test error the URL and Authentication Type fields are the ones to check. [zdx.alerts.webhooks:test] After the webhook is configured on the provider's site, the alert information that can be viewed includes the alert start and end time, devices impacted, severity, rule name and alert criteria. [zdx.alerts.webhooks:delivered-fields] No article publishes the payload [gap:zdx.alerts.webhooks:payload-schema], and delivery behavior such as retries is not documented [gap:zdx.alerts.webhooks:delivery-behavior].

**Platform guides.** The Configuring Webhooks article gives guidance for a supported platform in the Microsoft Teams, OpsGenie, PagerDuty, Slack, Splunk and ServiceNow (for Developers) webhook configuration guides. [zdx.alerts.webhooks:platforms] The Microsoft Teams and PagerDuty guides each say the platform does not generate a bearer token and to enter any text (for example 1234) to meet webhook configuration requirements, and the Slack guide says to enter any text because a bearer token is not required. [zdx.alerts.webhooks:no-bearer-token-platforms] The Microsoft Teams guide requires a Microsoft Teams account and takes the webhook from a channel under Channel > Connectors > Incoming Webhook > Configure. [zdx.alerts.webhooks:teams] The OpsGenie guide's API key, also called the GenieKey, needs Read Access, Create and Update Access and Delete Access; the URL is normally https://api.opsgenie.com/v2/alerts?isOpsGenie=true, ?isOpsGenie=true must be appended to the URL for ZDX Integration (including an organization-specific URL), and the bearer token is entered as GenieKey followed by the key. The Alert Title might not display all characters if it exceeds 130 characters, in which case the fields are displayed within the description. [zdx.alerts.webhooks:opsgenie] To integrate with OpsGenie the alert rule's Actions section requires Muted to be disabled and Alert Delivery Method set to Webhook, with Email optional. [zdx.alerts.webhooks:opsgenie-rule] The PagerDuty guide selects the category Error Tracking, selects Yes for Event Integration and enters the event transformation script, and copies the Events API Endpoint address as the URL for the webhook in the Zscaler Admin Console. [zdx.alerts.webhooks:pagerduty] The Slack guide says the incoming webhook provides a unique URL that sends a JSON payload with the message text; a paid Slack subscription is required to use Slack Workflow Builder, where Webhook - Advanced is selected and the variables dictate which fields from the webhook notification are displayed in the Slack notification, and the app route enables Activate Incoming Webhooks. [zdx.alerts.webhooks:slack] The Splunk guide sets an HTTP Event Collector's All Tokens to Enabled, Default Source Type to _json and deselects the Enable SSL checkbox; for Basic authentication it enters any string as the username and the HEC Token Value, and for Token authentication the HEC Token Value as the Bearer Token. [zdx.alerts.webhooks:splunk] The Splunk guide's URL step is incomplete in the capture [gap:zdx.alerts.webhooks:splunk-url-parameter]. The ServiceNow guides are in [The ZDX application on ServiceNow: roles, webhook URLs, Deep Tracing, Root Cause Analysis and incident settings](kb:zdx.alerts.servicenow).

**Fields the sample scripts read.** The two samples below are example scripts that read fields of the alert body, not a published schema [gap:zdx.alerts.webhooks:payload-schema]. The PagerDuty guide's sample transformation script reads zdxUrl, ruleName, status, geolocationCount, deptCount, impactedDeviceCount, osverCount, severity, alertId and criteriaString from the webhook body, tests the status against STARTED, and sets the event not to be emitted when the lower-cased rule name is test. [zdx.alerts.webhooks:payload-pagerduty-sample] The ServiceNow developer guide's sample script reads alertId, ruleName (returning without action when it equals test), zdxUrl, startTime and endTime (multiplied by 1000 before use as a date), a status tested against STARTED, ENDED_ON_RULE_DEL and ENDED_ON_RULE_MODIFY (anything else treated as resolved), a severity of High, Medium or Low, an alertType of Incident or ZProbe, geolocationCount, impactedDeviceCount, impactedUserCount, context with attribute and epicenter, zscaler_hosted_locations, deptCount, osverCount, and criteria with op and conditions holding conditionString, isHit and stats min, max and avg. [zdx.alerts.webhooks:payload-servicenow-sample]

**Subscription and permission.** In the subscription table Webhooks are Not supported on Standard, 10 on Microsoft 365, 10 on Advanced and 50 on Advanced Plus, and Workflow Automation is Supported only on Advanced Plus. [zdx.alerts.webhooks:tier-limits] The Webhooks permission is in [For alerts, Full lets admins configure and view alerts and receive alert notifications, View Only lets them view alerts and receive notifications depending on rule configuration, and None allows neither managing, viewing nor receiving them; labels can be assigned to an alert rule and a Workflow Automation created or assigned as a delivery method. Webhooks has its own permission, where Full allows creating, managing and viewing webhooks.](kb:shared.admin-rbac.zdx:alerts-permission), and changing Integration settings needs Organization scope: [Only admins with scope over the entire organization can configure organization-wide alert rules, inventory settings and information; configuring Inventory or Self Service settings, changing the Integration settings (Data Collection, SaaS App Tenants and Webhooks) and changing Authentication settings each need Organization scope.](kb:shared.admin-rbac.zdx:organization-scope-only). Choosing a webhook in a rule is in [Configuring ZDX alert rules: types, filters, metrics, throttling, delivery, templates and labels](kb:zdx.alerts.rules).

What to check:
1. For a webhook that fails Test Webhook, the URL (no spaces) and the authentication type the provider requires; for OAuth, remember the test posts no message and only acquires the token.
2. For an alert that did not reach the platform, whether the rule has Muted disabled and the webhook selected, and the platform's own guide for its URL and token rules.
3. Do not treat a field name in a sample script as part of a published payload schema.
