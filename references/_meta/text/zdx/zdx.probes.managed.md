# Managed Monitoring and Zscaler Managed Probes: where they run, what they chart and their subscription limits (zdx.probes.managed)
Also called: managed monitoring; zscaler managed probes; zscaler managed locations; managed probe; managed view; companion probe; managed probe errors

Managed Monitoring is the part of ZDX that runs probes from Zscaler's own cloud rather than from a user's device; the Managed view of the Probes page is in [ZDX probes: Web and Cloud Path probes, what they measure and how they run](kb:zdx.probes). Managed Monitoring operates from within the Zscaler cloud infrastructure as a multi-tenant service that groups Web and Cloud Path probes into independent collections; Zscaler Managed Probes, an extension to the probes for predefined and custom applications, monitor a specific service or application directly from a Zscaler data center to an endpoint destination. [zdx.probes.managed:managed-service] In the subscription table Managed Monitoring is supported only as an add-on on Standard, Microsoft 365 and Advanced, with identical ranges and limitations across those add-ons, and on Advanced Plus allows 1 probe per 1,000 users for each managed location (columns in the order of the table's header row). [zdx.probes.managed:managed-tiers]

**Where a managed probe runs.** A managed probe is run from the Zscaler Managed Locations selected (all selected by default): Zurich, Frankfurt, Amsterdam, Chicago, San Jose, Washington DC, Sydney, Delhi, Mumbai, Chennai, Tokyo, Osaka, Paris, Singapore, London, Atlanta, Dallas, Los Angeles and New York. [zdx.probes.managed:managed-locations] Data Explorer names the Zscaler Managed Locations with city and country codes, for example Zscaler-Amsterdam-NE, Zscaler-Frankfurt-DE, Zscaler-San Jose-CA-US and Zscaler-Zurich-CH. [zdx.probes.managed:managed-locations-data-explorer]

**Before configuring.** Before configuring Zscaler Managed probes the ZDX subscription level must support Managed Monitoring, the ZDX role must have the proper permission level, and an application must be configured and associated with a collection; Zscaler Managed probes and companion probes count towards the Managed Monitoring probes. [zdx.probes.managed:managed-prerequisites] The collections that hold managed applications are in [ZDX collections: default collections, membership, ranking, criteria, deletion and limits](kb:zdx.probes.collections).

**Configuring a Web probe.** A Managed Web probe's destination is an HTTP or HTTPS URL or an IP address (IPv4 or IPv6); it is enabled by default, selects Informational (100-199) and Successful (200-299) responses by default, has a default timeout of 60 seconds and a default of 5 maximum redirects (Maximum Redirects is also disabled if Follow Redirect is), and runs from the Zscaler data centers chosen as Zscaler Managed Locations. [zdx.probes.managed:managed-web-probe] A Managed Web probe's additional options include the default HTTP version, an Override DNS setting (disabled by default) that lets the DNS Server or DNS Resolution be overridden when enabled, and Cache DNS Results (disabled by default). [zdx.probes.managed:managed-web-options] A Managed Web probe can be paired with an optional companion Cloud Path probe, which is enabled by default; when the Web probe resolves to an IP address the Cloud Path probe runs to the same IP address. [zdx.probes.managed:companion-probe]

**Configuring a Cloud Path probe.** A Managed Web probe's companion Cloud Path probe has its protocol chosen from a drop-down menu (for example ICMP, TCP) and defaults to TCP; its end-to-end metrics probing options depend on the protocol: under For TCP Protocol they include Prefer SACK, Force SACK and Force SYN, and under For ICMP Protocol they include ICMP; with TCP selected the Probing Type defaults to SYN, the other quoted method being SACK. [zdx.probes.managed:managed-cloud-path-protocol] A Managed Web probe's companion Cloud Path probe can capture Path Maximum Transmission Unit (PMTU) discovery to detect packet size-related issues along the network path, and offers the DSCP choices Best Effort (DSCP 0, default traffic prioritization), CS1-CS7, AF11-AF43, EF PHB (DSCP 46) and Voice Admit (DSCP 44). [zdx.probes.managed:managed-pmtu-dscp] A Managed Cloud Path probe's Hop Count defaults to 30 (minimum 10, maximum 64) and a probe run fails if the hop count exceeds it; its Packet Count defaults to 3 (minimum 1, maximum 11) and its Timeout (ms) to 500 (minimum 500, maximum 2000); the Host is the host IP address or fully qualified domain name, given as the IPv4 address with IPv6 not supported. [zdx.probes.managed:managed-cloud-path-limits] Whether the host can resolve to IPv6 is open, see [Whether a Cloud Path host that is an FQDN can resolve to IPv6](kb:zdx.probes.configuration:cloud-path-ipv6).

**Alerts.** A managed probe can take alert templates, either a new one created with Create New Template or an existing one with predefined criteria whose High, Medium or Low severity is shown by color; templates can also be added or edited directly from the probe collection table, whose Alert Rules column is the number of alert templates associated with the probe. [zdx.probes.managed:managed-alerts]

**Managing probes and collections.** The managed probe table gives the number of Zscaler managed locations a probe runs from (Locations), its status (Enabled or Disabled, an enabled probe being an active probe), the method for Web probes or the protocol for Cloud Path probes, and how often the probe is run (Frequency). [zdx.probes.managed:managed-table] Per Managing Zscaler Managed Probes, a collection can be enabled for active use or disabled for later use and to manage the amount of active Zscaler Managed probes, disabling a collection disables all probes within it, and deleting a collection deletes all probes and associated companion probes. [zdx.probes.managed:managed-collection-status] Deleting a managed collection is described two ways, see [zdx.probes.collections:managed-collection-delete](kb:zdx.probes.collections:managed-collection-delete). Disabling a probe also disables its companion probe; a companion probe cannot be enabled while the parent probe is disabled, and enabling the parent does not enable the companion immediately, as its status must be enabled in the Edit Probe - Companion Probe configuration; deleting a probe with a companion probe deletes the companion too, and a companion cannot be selectively deleted but can be disabled so that it does not count towards active probes. [zdx.probes.managed:companion-lifecycle] Whether a probe can be deleted on its own is described two ways, see [zdx.probes.collections:probe-deletion](kb:zdx.probes.collections:probe-deletion).

**Errors.** The end-user Web probe errors are in [Web probe error messages in ZDX: what each reports and what the help suggests](kb:zdx.probes.web-probe-errors). Zscaler Managed Web probe errors with a configuration fix: incorrect configuration (review and validate the configuration), invalid destination URL (check it is correct), maximum redirects reached (increase the maximum amount of redirects) and request timed out (increase the maximum allowed timeout). [zdx.probes.managed:web-config-errors] The managed error 'Not within the HTTP response code range', where the Web probe reached an error code that does not exist within the HTTP response code range, calls for no action. [zdx.probes.managed:web-no-action] These Zscaler Managed Web probe errors call for reporting to Zscaler Support: insufficient memory, invalid location, a system error while processing analytics and an unknown internal error. [zdx.probes.managed:web-support-errors] Managed Cloud Path errors about the destination: cannot connect to the host (review the probe configuration for a valid DNS name or IP address, then report to Zscaler Support if it persists), probe did not reach the destination (check the destination IP or domain is valid), destination unresponsive (review the timeout), destination for the Binary Search unresponsive (review the maximum hops), cannot read socket due to timeout (review the timeout field) and TCP maximum retries reached (review the probe timeout configuration). [zdx.probes.managed:cloud-path-destination-errors] Managed Cloud Path DNS errors: error resolving domain and non-existent domain (verify the DNS name for the probe destination), empty DNS response (verify the domain name is valid), DNS request timed out while waiting for a reply (report to Zscaler Support) and failed DNS response, an internal error (report to Zscaler Support). [zdx.probes.managed:cloud-path-dns-errors] Managed Cloud Path input errors: network protocol not supported (provide a supported one), protocol not supported because one other than TCP or ICMP was provided (provide TCP or ICMP), invalid IP address (check it) and a resolved IP address type that does not match the requested type (report to Zscaler Support). [zdx.probes.managed:cloud-path-input-errors] Two managed Cloud Path errors call for no action, TCP SYN packet received unexpectedly and an internal error that aborted the probe; the message Internal error on a Web probe instead calls for reporting to Zscaler Support. [zdx.probes.managed:cloud-path-no-action] These managed Cloud Path errors call for reporting to Zscaler Support: an error processing a timeout event, insufficient memory, a Cloud Path probe already in progress for the device, reaching maximum capacity for the hash table, being unable to create a socket handle, being unable to retrieve a socket address, and receiving an unexpected ICMP TIME EXCEEDED or ICMP DST UNREACHABLE message. [zdx.probes.managed:cloud-path-support-errors]

**What it charts.** Managed Monitoring charts Availability and Page Fetch Time by default for Web probes and End-to-End Latency for Cloud Path probes; the first chart on the page defaults to the previous 30 days, and its time-range widget runs from 2 to 48 hours, defaulting to 24 hours. [zdx.probes.managed:managed-charts] Web probe availability is reported month to date (with the change from the previous month), over the past 30 days (with the change from the prior 30 days) and over the widget's time range (with the change from the prior 30 days); in the Page Fetch Time metrics section, each data point in a scatter chart is an individual probe run. [zdx.probes.managed:managed-availability] A Web probe run's details give, in milliseconds, redirect time, DNS, TCP, SSL handshake, server response time (TTFB) and page fetch time, with a response code (the HTTP informational or success code) per redirected URL; a Cloud Path probe run's details give end-to-end latency, packet loss, maximum hop count and jitter, and, separately, a Cloud Path visualization consolidates all managed locations into one image. [zdx.probes.managed:managed-run-details]
