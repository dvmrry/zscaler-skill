# What the Python SDK's ZDX results contain: envelopes, missing fields and paging (zdx.sdk-python.response-models)
Also called: python zdx none fields; zdx model attributes none; form_response_body zdx; zdx next_offset python; zdx pagination python; call quality metrics python; MostImpactedRegion; python zdx as_dict
Former IDs: zdx-08

The Python ZDX methods turn each response into model objects whose attributes mirror the API's snake_case keys. How they get there decides which attributes survive.

**Envelopes.** List methods such as `list_ongoing`, `list_historical`, `list_devices` and `list_users` wrap the whole response body in one envelope object (`Alerts`, `Devices`, `ActiveUsers`) and return it as a one-element list. [zdx.sdk-python.response-models:list-envelopes] Methods that read one record also return a one-element list: `get_app`, `get_device`, `get_device_apps`, `get_device_app` and `list_top_processes` each build one model from the response body (`ApplicationScore`, `DeviceModelInfo`, `DeviceActiveApplications`, `DeviceAppScoreTrend`, `DeviceTopProcesses`) and wrap it in a list. [zdx.sdk-python.response-models:single-in-list]

**Multiword fields.** The SDK-wide mechanism is [`form_response_body` passes every key of a response through `to_lower_camel_case`, so a model attribute looked up under a snake_case key is not found on that path unless FIELD_EXCEPTIONS yields that key: `exit_password` maps to itself, and the camelCase `tunnelTwoForiOSDevices` maps to `tunnel_two_fori_os_devices`; `list_by_company` for web policies instead reads the response with `get_results()`.](kb:zcc.sdk-python.wire-keys:response-keys-camel-cased). ZDX models such as `DeviceDeepTraces`, `Devices` and `ActiveApplications` look their fields up under the API's snake_case keys (`trace_id`, `next_offset`, `total_users`), and methods such as `get_deeptrace` and `list_apps` build the models from `form_response_body` of the response. [zdx.sdk-python.response-models:models-read-snake] So on those methods a model attribute whose lookup key contains an underscore (a deep trace's `trace_id`, a device list's `next_offset`, an application's `total_users`, and the like) comes back None, and the MCP tools that return these models' records omit those fields. A key with no underscore passes through unchanged, so single-word keys such as `id`, `name` and `score` survive, and so do the camelCase keys some models read: the affected-devices `DeviceDetails` reads `userName` and `userEmail`, the form the contract returns, while `next_offset` on the same `list_affected_devices` result is lost. [zdx.sdk-python.response-models:multiword-attrs-lost] `list_deeptraces` and `get_call_quality_metrics` build their models from the raw response items, and `list_softwares` hands the raw body to its `SoftwareList` wrapper. [zdx.sdk-python.response-models:raw-exceptions]

**Narrow models.** The Python `MostImpactedRegion` model reads only `id` and `country`, while the contract's `most_impacted_region` also carries `city`, `region`, `state`, `geo_type`, coordinates and detection details. [zdx.sdk-python.response-models:most-impacted-region] The Python `Network` model reads `net_type`, `status`, `ipv4`, `ipv6`, `dns_srvs`, `dns_suffix`, `gateway`, `mac` and `guid` but none of the Wi-Fi fields the contract defines for a device's network (`wifi_adapter`, `wifi_type`, `ssid`, `channel`, `bssid`), which the Go `Network` struct does read. [zdx.sdk-python.response-models:python-network-no-wifi] The OS build goes the other way: [The Go `Software` struct reads `os_name`, `os_ver`, `hostname`, `netbios`, `user`, `client_conn_ver` and `zdx_ver` but not `os_build`, so a Go device read drops the OS build version the contract defines; the Python `Software` model reads it.](kb:zdx.sdk-go.service-defects:go-software-no-os-build). The Python `CallQualityMetrics` model forms its `metrics` as a list of `str`, which turns each metric object into its string form, while the contract defines each element as a `Series` object of `metric`, `unit` and `datapoints`. [zdx.sdk-python.response-models:call-quality-strings] The earlier question about the call-quality metric shape is settled by the contract except for a live check [gap:zdx.sdk-python.response-models:call-quality-shape]. Events and the device-application score follow the contract in Python: [Go SDK ZDX services: where the structs and functions disagree with the contract](kb:zdx.sdk-go.service-defects). The Python `list_devices` returns a `Devices` wrapper whose `devices` list is formed of `DeviceDetail` objects, which read only `id`, `name` and `userid`; the contract's device-list entries also carry fields such as `os`, `hw_model`, `private_ip` and `client_conn_ver`. [zdx.sdk-python.response-models:python-device-list-fields] The Python `DeviceModelInfo` model, which `get_device` returns, forms a device's `network` as a list of `Network` objects, and the contract's `network` is an array. [zdx.sdk-python.response-models:python-network-list]

**Paging.** The Python response object pages ZDX lists by `next_offset`: `has_next()` is true while a `next_offset` is present, the next request sends it as `offset`, and each page's records are read from the body's `items` key. [zdx.sdk-python.response-models:paging] No paged ZDX list response in the contract has an `items` key (they hold `alerts`, `devices`, `users` or `software` beside `next_offset`), so `next()` on a ZDX response returns no records and callers have to pass `next_offset` back as `offset` themselves. [zdx.sdk-python.response-models:paging-reads-items]

**Other readers.** The analysis reader returns a plain dict: [The Python `get_analysis` returns a one-element list holding `form_response_body` applied to the response body, with no model class around it; for a JSON object body `form_response_body` builds and returns a dict.](kb:zdx.diagnostics.analysis:python-get-raw). The start methods' results are in [The Python `start_deeptrace` builds its result as a `TraceDetails`, which reads only `session_name`, `user_id`, `username`, `device_id`, `device_name`, `session_length_minutes` and `probe_device` from the response; it has no trace ID or status attribute.](kb:zdx.diagnostics.start-request:python-start-result) and [The Python `start_analysis` sends its keyword arguments as the body and builds its result as a `DeviceApplicationAnalysis`, which reads only `device_id`, `app_id`, `t0` and `t1`.](kb:zdx.diagnostics.analysis:python-start).

What to check:
1. Whether a field that comes back None from a Python ZDX object is one its model looks up under a key with an underscore; read it from the raw response (`response.get_body()`) instead.
2. Whether a paged Python ZDX listing was walked with the response object's `next()`, which yields no records; pass `next_offset` as `offset` by hand.
