# ZDX applications: predefined, custom and network applications, and the application API (zdx.applications)
Also called: zdx application; zdx applications; zdx apps; predefined applications zdx; custom application zdx; network application zdx; zdx app score api; zdx app metrics; metric_name; most impacted region; zdx application configuration api; zdx application users; pending onboard; unified communication applications; teams transport relay

An application is the unit ZDX probes and scores. The service provides predefined applications, or a customized application can be configured; the console configures Custom Applications (customizable SaaS or web applications created and onboarded for the organization) and Network Applications (network applications whose Cloud Path is monitored), and each application is designed to have probes associated with it. [zdx.applications:app-kinds] The subscription table gives the total number of Internet Web Applications as 512 on Standard, Microsoft 365, Advanced and Advanced Plus. [zdx.applications:internet-web-app-limit]

## Kinds of application

**Probes each needs.** A custom application must have a Web probe created to be enabled; most applications have at least one Web probe and one Cloud Path probe, while network applications need only a single Cloud Path probe. Predefined applications have probes preconfigured by default, while custom applications need probes created manually. [zdx.applications:probe-requirements]

**Predefined.** Predefined applications are SaaS applications with predefined paths; Zscaler recommends configuring these paths to the organization's SaaS tenant for applications that require a tenant ID, and by default every predefined application has preconfigured Web and Cloud Path probes and is enabled automatically when onboarded. [zdx.applications:predefined-auto] Predefined applications cannot be deleted: the help says so, and the API contract's delete-by-ID is for custom applications, while deleting a predefined application by name is generally not allowed and results in 403 Forbidden. [zdx.applications:predefined-not-deletable] The predefined applications available depend on the ZDX subscription. The Microsoft 365 subscription's list includes Microsoft Teams Call Quality, Microsoft Teams Web App, Microsoft Login, OneDrive for Business, Outlook Online and SharePoint Online; the Advanced and Advanced Plus subscriptions' lists each include Webex Call Quality, Zoom Call Quality, ServiceNow, Salesforce Classic, Salesforce Lightning, Webex Web App and Zoom Web App; the Standard subscription's list includes ServiceNow, Salesforce Classic, Salesforce Lightning, Webex Web App and Zoom Web App. Only Microsoft Teams Call Quality is currently supported for UCaaS on the Microsoft 365 subscription. [zdx.applications:predefined-by-tier] A predefined application is added from the Predefined Apps Collection (Digital Experience > Settings & Configurations > Probes > End User) by selecting an application from the Predefined Applications list and clicking Add Probe; to use Real User Monitoring metrics, Real User Monitoring must be Enabled; the steps then configure the probe fields and click Submit, and changes need activation. [zdx.applications:predefined-app-rum]

**Custom and network.** A custom application's name is at most 64 characters, alphanumerics and a limited range of symbols: underscore, hyphen, space, forward slash, backward slash, period, at symbol, pipe symbol and parentheses; its Application Type is Custom or Network, and network applications do not require a Web probe and require only one Cloud Path probe; disabling an application disables its probes; and the Add Application link is disabled once the maximum number of allowed applications or probes for the subscription level is reached. [zdx.applications:custom-app-fields] For a custom application, a domain URL defined as https://domain.com is also defined as https://www.domain.com, a subdomain URL needs another custom application to capture metrics specifically for the subdomain, and a Session Timeout sets the duration at which a user's session in the application times out due to inactivity. [zdx.applications:custom-app-rum-domain] Choosing Select from existing lets an admin search for and select an existing application, but a disabled application cannot be selected. [zdx.applications:existing-app] When editing an application the name of any custom application can be changed but the name of a predefined application cannot, and the Application type cannot be edited. [zdx.applications:edit-app] The collections that hold applications are in [ZDX collections: default collections, membership, ranking, criteria, deletion and limits](kb:zdx.probes.collections), and how their probes are configured is in [Configuring end-user Web and Cloud Path probes in the console: fields, defaults, limits and protocols](kb:zdx.probes.configuration).

**Top Private Apps.** The list of Top Private Apps is created with readily available data from Private Access; it is searched by the port numbers a private application uses, separated by commas, sorted by users (the default) or bandwidth, and shows each application's protocol, bandwidth and Configured for ZDX status; an application whose Configured for ZDX is Yes cannot have its probe configured on the Top Private Apps page and is reached in Configuration > Probes. [zdx.applications:top-private-apps] ZDX can monitor top private applications accessed over IPv6 when integrated with Private Access, provided Zscaler Client Connector and the Private Access App Connectors are IPv6-capable and the private app segments are defined using IPv6 addresses or dual-stack DNS names; the Top Private Apps page provides visibility into response times, path health and error rates across both IPv4 and IPv6 access paths. [zdx.applications:top-private-apps-ipv6] Whether the Cloud Path host accepts IPv6 is described two ways, see [Configuring end-user Web and Cloud Path probes in the console: fields, defaults, limits and protocols](kb:zdx.probes.configuration).

**Unified communication.** For unified communication applications a tenant must be onboarded before their probes can be configured; the onboarding articles cover Microsoft Teams, Webex and Zoom call quality. [zdx.applications:uc-tenant-onboarding] How each Teams, Webex or Zoom tenant is onboarded is in [Onboarding Microsoft Teams, Webex and Zoom Call Quality tenants: prerequisites, authentication and monitoring criteria](kb:zdx.applications.uc-tenants). For Microsoft Teams, besides the application URL that monitors client connectivity and call signaling (teams.microsoft.com), an additional Cloud Path monitors the Teams Transport Relay service that handles media (world.tr.teams.microsoft.com). [zdx.applications:teams-transport-relay] The Microsoft Teams, Webex and Zoom Call Quality applications take only Cloud Path probes, as Web probes are not allowed for them; for Microsoft Teams ZDX Autosense can dynamically detect a destination IP address and provide an automated Cloud Path probe when a Microsoft Teams Call Quality tenant is onboarded. [zdx.applications:uc-cloud-path-only] In the subscription table UCaaS Monitoring is not supported on Standard, is Microsoft Teams Call Quality only on Microsoft 365, and is supported on Advanced and Advanced Plus, with a UCaaS tenant limit of 40 on those three tiers; ZDX Autosense is supported for Webex and Zoom Call Quality on Advanced and Advanced Plus only, and for Microsoft Teams Call Quality on Microsoft 365, Advanced and Advanced Plus (columns in the order of the table's header row). [zdx.applications:uc-tiers] The call-quality data itself is read per device: [ZDX call-quality metrics per device and meeting](kb:zdx.devices.call-quality).

**Status.** An application that is not yet fully activated shows the Status Pending Onboard. [zdx.applications:pending-onboard]

**Discovery.** Whether ZDX discovers applications by itself, beyond the predefined catalog and the Top Private Apps view, is only partly documented [gap:zdx.applications:auto-detection].

## Reading application scores

The API's application list returns all active applications configured for the tenant, with each one's ZDX score (by default for the last 2 hours), its most impacted location and the total number of users impacted. [zdx.applications:apps-list] Whether configured applications with no recent data are left out of that list is not stated [gap:zdx.applications:inactive-app-listing]. The single-application read returns the application's ZDX score for the last 2 hours, its most impacted locations and the total number of users impacted. [zdx.applications:app-detail] An application's stats count active users, active devices, and users with poor, okay and good scores. [zdx.applications:app-stats]

**Trends.** The application score read returns the application's ZDX score trend, for the last 2 hours if no time range is given. [zdx.applications:app-score-trend] The application metric read returns a metric trend: for Web probes Page Fetch Time, Server Response Time, DNS Time or Availability, defaulting to Page Fetch Time; for Cloud Path probes the latency for End to End, Client - Egress, Egress - Application, ZIA Service Edge - Egress and ZIA Service Edge - Application, defaulting to End to End; and the last 2 hours if no time range is given. [zdx.applications:app-metrics] Which `metric_name` value selects which metric is not settled by the contract [divergence:zdx.applications:metric-name-enum], and the full value set is open [gap:zdx.applications:metric-name-values]. The Python `get_app_metrics` docstring lists `pft`, `dns` and `availability` as the available `metric_name` values, as the contract's enum does, while the Go `GetAppMetrics` comment repeats the operation description's longer list (Server Response Time and the Cloud Path latency segments). [zdx.applications:python-metric-name-doc]

**Users of an application.** The application-users read lists the users, and the devices they used, that accessed an application, filterable by score category (Poor, Okay or Good), location, department or geolocation, for the last 2 hours if no time range is given. [zdx.applications:app-users] The application-user detail read returns the user's details with device information, active geolocations and Zscaler locations. [zdx.applications:app-user-detail] Paging and the shared time-range rules are in [Reading ZDX report data: time ranges, paging, users and what the reads return](kb:zdx.reports).

## Configuring applications through the API

The API contract has an Application Management area under /v1/config/applications: it lists configured applications, creates applications (the type decides the required fields), reads, updates and deletes one, activates and deactivates it, and lists and creates its monitors. [zdx.applications:config-api] In the contract an application's `type` is CUSTOM, NETWORK or PREDEFINED and acts as the discriminator that decides which other fields the request needs. [zdx.applications:app-class] The contract's application request carries `rumDetails`, the configuration for Real User Monitoring, with `rumEnabled`, `rumDomain` and `rumTimeout`. [zdx.applications:rum-config] What Real User Monitoring needs and what it shows is in [Real User Monitoring in ZDX: prerequisites, the Real User Score and the RUM views](kb:zdx.applications.rum). Neither SDK calls any /v1/config path: the configuration, monitor, collection and directory operations of the contract are reachable only by direct API calls. [zdx.applications:config-no-sdk]

What to check:
1. Whether a custom application has the Web probe it needs to be enabled, or a network application its Cloud Path probe.
2. Whether a unified communication application has its tenant onboarded before expecting probe or call-quality data.
3. Whether an application missing from the score list is merely inactive in the time range rather than deleted, by reading the configured applications.
