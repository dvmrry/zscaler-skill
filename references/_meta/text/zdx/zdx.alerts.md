# ZDX alerts: how rules trigger, what an alert's status means, and reading alerts through the API (zdx.alerts)
Also called: zdx alerts; alert status; completed by modified rule; completed by exceeded time; alert rule throttling; alert only if repeated; ongoing alerts api; historical alerts api; affected devices; client.zdx.alerts; why did my zdx alert not fire
Former IDs: zdx-31

An alert is raised by a rule when a metric crosses a threshold under the rule's throttling criteria, and the API reads alerts but does not define rules. The alert endpoints and SDK functions are generated (`node scripts/kb.mjs surface zdx`).

**What alerts are.** ZDX alerts monitor device, application, network performance and ZDX Score; admins create alert rules that trigger when a preset threshold is reached, and triggered alert details are sent by email or webhook. [zdx.alerts:about] Triggered alerts have a display delay of 30 minutes. [zdx.alerts:display-delay] The console shows alerts triggered over the past two weeks, with a time range of 2 hours to 14 days on the Alert History tab and a default of 2 hours. [zdx.alerts:history-window] The subscription table gives Total Alerts as 512 on every tier, and Total Active Alerts (Alerts with Incident Correlation) and Total Alert Rules as up to 3 on Standard, 10 on Microsoft 365, 25 on Advanced and 100 on Advanced Plus. [zdx.alerts:tier-limits]

**How a rule triggers.** Each alert rule type (Application, Device, Incident, Network or Call Quality) has its own trigger criteria based on its metrics, and when they are met the alert triggers and sends an alert email. [zdx.alerts:rule-types] The configuration article lists more types [divergence:zdx.alerts:rule-type-list], and the rule fields are in [Configuring ZDX alert rules: types, filters, metrics, throttling, delivery, templates and labels](kb:zdx.alerts.rules). Application, device and network rules add throttling criteria: Alert Only if Repeated (how many times the situation must repeat), the number of active devices, and the minimum number or percentage of devices impacted, the last two based on an In Group selection of departments, cities, organization, regions or Zscaler locations; a rule whose group has fewer active devices than required does not trigger. [zdx.alerts:throttling] An incident rule needs a minimum number of impacted devices globally (across the organization) or locally (per location) depending on the incident type, and incident types with both thresholds must meet both to trigger. [zdx.alerts:incident-thresholds] Dynamic alerting auto-baselines by referring to historical data and detects ZDX Score Drops based on the threshold sensitivity; a dynamic alert rule can be created whenever the Network or Applications rule type is applied, the feature is available based on subscription level, and the subscription table lists Dynamic Alerting as not supported on Standard and Microsoft 365 and supported on Advanced and Advanced Plus. [zdx.alerts:dynamic-alerting] How often rules are evaluated is open [gap:zdx.alerts:evaluation-cadence]. Whether one transient probe failure can raise and clear an alert is unconfirmed [gap:zdx.alerts:transient-flap].

**Status.** An alert's status is Started, Ongoing, Completed, Completed by Exceeded Time (it ended because a time duration expired), Completed by Rule Deletion or Completed by Modified Rule. [zdx.alerts:statuses] Which thresholds a historical alert shows after its rule was modified is open [gap:zdx.alerts:modified-rule-thresholds].

**Alert details and notifications.** For an end-user alert the details page shows the impacted departments (the number of devices by department and the total number of impacted devices) and the alert rule's expression triggers with the average and maximum values for the time period; the Alert Details page displays at most 128 devices and the View All dialog window at most 6,000. [zdx.alerts:details-end-user] The Impacted User Devices table displays the Device name, User ID, Department, Zscaler location, Geolocation and ZDX Score of the device, and the dotted reference line is based on the criteria set when configuring the alert rule. [zdx.alerts:details-devices] For Network Intelligence alerts the impacted geolocations that are anomalies are highlighted as red circles; the details also give the number of Zscaler data centers by geolocation, the name of the impacted Zero Trust Exchange and the impacted Internet Service Provider (ISP) or ISP links. [zdx.alerts:details-network-intelligence] An alert's Severity is shown as red for High, orange for Medium and green for Low, and its Monitoring Type is End User when the rule was created by the user and Managed when it was created for Managed Monitoring; depending on the criteria the details show latency, number of hops, packet loss or DNS Time from the selected managed probe. [zdx.alerts:details-managed] An alert email highlights the alert criteria met, indicates the alert start time and the end time or Ongoing, gives the alert rule's name (linking to the Zscaler Admin Console) and lists the impacted Geolocations, Departments, OS Versions and Devices, with devices no longer listed once the alert has ended; for an incident alert it adds the Incident Type and Epicenter and lists Geolocations, Devices and Users, and for call quality it lists Geolocations, Departments, Meetings and Users. [zdx.alerts:alert-email] If a rule is not muted, alerts can be sent via email or webhooks; if it is muted, the alerts can be viewed in the Zscaler Admin Console and no information is sent via email or webhooks. [zdx.alerts:muted] Webhook delivery is in [ZDX alert webhooks: authentication, testing, platform guides and the payload fields the sample scripts read](kb:zdx.alerts.webhooks) and the ServiceNow application in [The ZDX application on ServiceNow: roles, webhook URLs, Deep Tracing, Root Cause Analysis and incident settings](kb:zdx.alerts.servicenow).

**Reading alerts through the API.** The ongoing-alerts endpoint returns alerts that have no ended date, selected by their `started_on` time with the filters; it defaults to the last 2 hours and cannot exceed a 14-day API limit. [zdx.alerts:api-ongoing] The historical-alerts endpoint returns alerts that have an ended date, selected by that date with the filters; it also defaults to the last 2 hours and cannot exceed the 14-day API limit. [zdx.alerts:api-historical] Some alert reads also take at most 2 hours per request, while the alert-detail and affected-devices reads need no range: [Most Report API endpoints and some Alert API endpoints require a 2-hour time range, so a longer period takes one request per 2-hour window; /devices/{deviceid}/events, /alerts/{alert_id} and /alerts/{alert_id}/affected_devices need no time range.](kb:shared.log-export.zdx:two-hour-window). How the 14-day limit and the 2-hour window relate is open [gap:zdx.alerts:alert-window]. Paging is in [ZDX API conventions: time ranges, paging, reporting delay and how API numbers differ from the console](kb:zdx.api.conventions); sharing one alert outside the console is in [Sharing a ZDX snapshot of an alert or a user: the contract, the Python client and the path question](kb:zdx.alerts.snapshot).

What to check:
1. Whether the rule's throttling criteria were met: the repeat count, the number of active devices and the minimum impacted devices in the chosen group.
2. Which rule types to expect in the console, from both articles' lists rather than the trigger article's alone.
3. Whether the alert is still inside the 30-minute display delay before concluding it did not fire.
4. Whether a closed alert ended because its condition cleared or because its rule was deleted, modified or ran out of time.
5. Whether an API alert query asked for the ongoing or the historical list, which select on different dates, and whether its window stays within the documented limits.
