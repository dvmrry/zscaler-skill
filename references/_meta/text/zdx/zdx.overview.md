# ZDX at a glance: what it measures and which subject answers each question (zdx.overview)
Also called: zdx; zscaler digital experience; digital experience; zdx overview; what does zdx measure; zdx monitoring; end user experience monitoring

ZDX is the Zscaler product that observes user experience; this subject says what it measures and links the subject for each question. ZDX monitors the cloud application experience from the end-user perspective, with application performance monitoring for customer-defined applications and for predefined ones such as Zoom, Box, Salesforce, ServiceNow and the Microsoft 365 applications, including Microsoft Teams, SharePoint Online, OneDrive for Business and Outlook. [zdx.overview:monitors] The architecture page groups what ZDX measures into end-user device performance (resource utilization, health metrics and events such as CPU and memory use, including Wi-Fi connectivity issues), Cloud Path performance (hop-by-hop network path metrics from every user device to the application), application performance (response time, DNS resolution and availability) and the ZDX Score, an aggregated score tracked over time at the user, application, location, department and organizational level. [zdx.overview:measurement-areas] ZDX collects real-time device health information such as CPU usage, memory usage, Network IO, Disk IO and Wi-Fi signal strength; the article gives these as examples. [zdx.overview:device-health-metrics] The documented triage scope of ZDX is whether an issue is in the local network, a user's device, the ISP provider or the Zscaler cloud; remote troubleshooting capabilities include system process-level monitoring, full network path information including ASN, ISP and country hop information, and packet tracing. [zdx.overview:triage-scope]

**Setting it up.** The ZDX step-by-step guide orders setup as: authentication and provisioning in Internet & SaaS, role-based administration, allowlisting domains on the Zscaler cloud, Client Connector configuration, applications, probes, alerting, then diagnostics; Step 1 says to have users, authentication and provisioning set up in Internet & SaaS and to contact Zscaler Support if they cannot be configured in ZIA. [zdx.overview:setup-order] After Client Connector is configured, ZDX can also be enabled for a select group of users (Selective Entitlement). [zdx.overview:selective-entitlement] The minimum Client Connector and ZDX Module versions are in [Minimum Client Connector and ZDX Module versions per OS and ZDX feature](kb:zdx.compatibility.supported-versions).

**Architecture.** ZDX is a multi-tenant cloud monitoring platform whose synthetic probing runs through Client Connector; ZDX support is natively integrated within Client Connector as a standalone lightweight module upgraded independently of the Client Connector core process. [zdx.overview:module-architecture] ZDX is implemented through Client Connector on Windows, macOS, Android, Android on ChromeOS and iOS; to monitor general data center information and key SaaS applications, the overview names HTTP, ICMP or UDP synthetic probes running on user devices. [zdx.overview:platforms-and-probe-types] The components and the path telemetry takes are in [ZDX cloud architecture: components, the telemetry path and what is undocumented](kb:zdx.cloud-architecture), and ZDX Module releases and rollouts on Client Connector are in [ZDX Module upgrades: automatic, delayed, frozen and manual rollout](kb:zdx.cloud-architecture.module-upgrades).

**Score.** What the score and its bands mean, and the score types, are in [The ZDX Score: scale, bands, score types and what lowers it](kb:zdx.score); how it rolls up per application, place, organization and user is in [How the ZDX Score is calculated: 5-minute values, hourly lows and rollups per scope](kb:zdx.score.calculation).

**Probes.** Web and Cloud Path probes and what each measures are in [ZDX probes: Web and Cloud Path probes, what they measure and how they run](kb:zdx.probes), which users a probe runs for is in [Who a ZDX probe runs for: probing and exclusion criteria](kb:zdx.probes.criteria), how end-user probes are configured is in [Configuring end-user Web and Cloud Path probes in the console: fields, defaults, limits and protocols](kb:zdx.probes.configuration), and how applications and their probes are grouped into collections is in [ZDX collections: default collections, membership, ranking, criteria, deletion and limits](kb:zdx.probes.collections).

**Applications and devices.** Predefined, custom and network applications and the application reads are in [ZDX applications: predefined, custom and network applications, and the application API](kb:zdx.applications), and onboarding Microsoft Teams, Webex and Zoom Call Quality tenants is in [Onboarding Microsoft Teams, Webex and Zoom Call Quality tenants: prerequisites, authentication and monitoring criteria](kb:zdx.applications.uc-tenants). Device lists and details are in [ZDX devices: the device list, device detail and per-device application scores](kb:zdx.devices), with health metrics and events in [ZDX device health metrics and device events](kb:zdx.devices.health-and-events), geolocations in [ZDX geolocations: active geolocations, geo filters and coordinates](kb:zdx.devices.geolocation) and call quality in [ZDX call-quality metrics per device and meeting](kb:zdx.devices.call-quality).

**Reading data through the API.** Time ranges, paging and the user reads are in [Reading ZDX report data: time ranges, paging, users and what the reads return](kb:zdx.reports), and the department and location lookups are in [ZDX administration API: department and location lookups](kb:zdx.administration). Sign-in, rate limits and the SDKs are in [The ZDX API from a client's side: hosts, limits, conventions, coverage and wire notes](kb:zdx.api) and [The Python SDK for ZDX: where its ZDX behavior is covered](kb:zdx.sdk-python).

**Diagnostics and alerts.** Diagnostics Sessions, which the API calls deep traces ([The ZDX API calls its on-demand per-device trace a deep trace: POST /v1/devices/{id}/deeptraces starts one on a device, limited to one active session per device and 15 active sessions across all devices, counting sessions started from the UI.](kb:shared.terminology.product-names:zdx-deep-trace)), are in [ZDX Diagnostics Sessions (deep traces): what they are and where each part is covered](kb:zdx.diagnostics), and alerts are in [ZDX alerts: how rules trigger, what an alert's status means, and reading alerts through the API](kb:zdx.alerts); configuring alert rules, templates and labels is in [Configuring ZDX alert rules: types, filters, metrics, throttling, delivery, templates and labels](kb:zdx.alerts.rules), webhooks are in [ZDX alert webhooks: authentication, testing, platform guides and the payload fields the sample scripts read](kb:zdx.alerts.webhooks) and the ZDX application on ServiceNow is in [The ZDX application on ServiceNow: roles, webhook URLs, Deep Tracing, Root Cause Analysis and incident settings](kb:zdx.alerts.servicenow).

**Administration.** ZDX admin roles, permissions, obfuscation and scope are in [ZDX admin roles: predefined and custom roles, permissions, obfuscation and admin scope](kb:shared.admin-rbac.zdx), and the console's admin audit log is in [ZDX admin audit logs in the console: what is recorded, retention, lockout and filters](kb:zdx.audit-logs).

**Who reports data.** Which users and devices run ZDX at all is set by the Client Connector entitlement, [Digital Experience (ZDX) entitlement](kb:zcc.entitlements.zdx). Location collection is a separate User Privacy switch, [Collect Location Info for ZDX lets the app collect geolocation from ZDX-enabled devices; it works in conjunction with the ZDX service entitlement, is on by default, and is available only when ZDX is enabled for the company or selected groups.](kb:zcc.web-privacy.collection:zdx-location), and whether both are needed is open, [Whether ZDX location needs both the entitlement flag and the User Privacy switch](kb:zcc.entitlements.zdx:location-both-required).

**Console dashboards.** The Digital Experience dashboard, the Performance Dashboard, the Applications and Users Overviews, VIP tagging and Self Service are in [ZDX console dashboards and overviews: time ranges, filters, VIP tagging, Private Service Edge Health and Self Service](kb:zdx.dashboards), and so is the ZIA Private Service Edge Health dashboard, which is documented in the ZDX help; whether it covers Virtual Service Edges is open [gap:zdx.overview:pse-dashboard].

**Remediation.** Remote scripts run on devices, their jobs and their errors are in [ZDX Remediation: remote PowerShell scripts, jobs, signing, prerequisites and troubleshooting](kb:zdx.remediation).

What to check:
1. Whether the user or device is entitled to ZDX before treating missing data as a ZDX fault.
2. Read a ZDX question as one about measured experience (the score, probe metrics, Cloud Path hops, a Diagnostics Session), and take the question of which policy applied to the same traffic to the product that enforces it.

Not known (open gaps):
- Whether a separate Private Service Edge dashboard sits beside the ZDX dashboards [gap:zdx.overview:pse-dashboard]: settled by source-read. Blocks: answers about where Virtual Service Edge health is monitored
