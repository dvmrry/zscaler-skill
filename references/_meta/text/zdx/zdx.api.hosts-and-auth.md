# ZDX API hosts and sign-in: the OneAPI gateway, the direct ZDX host, and which paths go where (zdx.api.hosts-and-auth)
Also called: zdx api host; api.zdxcloud.net; api.zsapi.net zdx; zdx oauth token; zdx api key auth; zdx v1 or v2 base url; zdx api roles; zdx legacy vs oneapi; zdx service desk; zdx admin roles; zdx service desk tier 1
Former IDs: zdx-03

ZDX is reached either through the OneAPI gateway with a ZIdentity client or directly on the ZDX host with a ZDX API key. The two use different hosts and path prefixes.

**OneAPI gateway.** The gateway base path for ZDX is in [The guide's base paths are: ZIA `/zia/api/v1`; ZPA `/zpa/mgmtconfig/v1`, `/zpa/mgmtconfig/v2` and `/zpa/userconfig/v1` (the last for SCIM attribute and group endpoints); ZDX `/zdx/v1`; Authentication Service `/ziam/admin/api/v1`; Client Connector `/zcc/papi/public/v1`; Cloud & Branch Connector `/ztw/api/v1`; Business Insights `/bi/api/v1`; EASM `/easm/easm-ui/v1`; Cellular `/zcell/config/api/v1`; Event Monitoring & Notification `/event-monitoring`; Unified RBAC `/urbac/urbac`; AI Security `/aisecurity/aispm/v1` (AI Infrastructure) and `/aisecurity/airt/api/v2` (AI Red Teaming); AI Guard `/aiguard/v1`.](kb:shared.oneapi.base-urls:base-path-table) and its OAuth sign-in in [How a client gets and uses a OneAPI access token](kb:shared.oneapi.authentication). The Automate contract lists `https://api.zsapi.net/zdx` as its server, and it includes a sign-in at `/v1/oauth/token` that authenticates with the API key ID and the secret key. [zdx.api.hosts-and-auth:contract-server] For OneAPI, each ZDX admin role maps to a resource in Authentication Service: ZDX Super Admin (full access), ZDX Read-only Admin (view only) and ZDX Service Desk Tier 1 (restricted view with obfuscated user information and a limited time window). [zdx.api.hosts-and-auth:oneapi-roles] The ZDX help describes Service Desk Tier 1 differently [divergence:zdx.api.hosts-and-auth:service-desk-user-info]; the roles themselves are in [ZDX admin roles: predefined and custom roles, permissions, obfuscation and admin scope](kb:shared.admin-rbac.zdx).

**API keys.** ZDX API Key Management is a repository for an organization to store created API keys for admin roles; an API key consists of an API Key ID and Secret, both required for access to the ZDX APIs. The page is at Administration > API > Legacy API > Digital Experience API Keys, and for access to Zscaler OneAPI endpoints the article points to About API Clients. [zdx.api.hosts-and-auth:api-key-management] Each API key on the page shows the Role it is assigned to, the username that created it (Created By) and the timestamp of when it was last updated (Last Updated On). [zdx.api.hosts-and-auth:api-key-fields] After the API subscription is enabled the Digital Experience API Keys page is accessible to a ZDX admin; creating a key selects an admin role to be assigned the key, the API Key ID and Key Secret can be copied or downloaded as a JSON file and both are needed for authentication, viewing a key opens the API Key window, where the API Key ID can be copied, and editing changes the Name or the role. [zdx.api.hosts-and-auth:api-key-create] In the subscription table ZDX APIs are Not supported on Standard, Supported for Microsoft 365 events on Microsoft 365 and Supported on Advanced and Advanced Plus; the page's Organization table, which has one Limit column and no tier columns, gives API Keys as 50. [zdx.api.hosts-and-auth:api-tiers]

**Direct ZDX host.** The legacy reference's server, token and prerequisites are [The legacy ZDX reference posts `key_id` and `key_secret` to /oauth/token on the production server `https://api.zdxcloud.net/v1` and returns a token valid for 3600 seconds.](kb:shared.legacy-api.auth-models:zdx-legacy-token) and [The legacy ZDX API needs an API key (key ID and key secret) and the ZDX Advanced Plan; a bearer token lasts 3,600 seconds.](kb:shared.legacy-api.auth-models:zdx-prereqs); the signed key secret and its 15-minute window are [The OneAPI ZDX contract's /v1/oauth/token takes `key_secret` as SHA256 of the secret key and timestamp (`SHA256('secret key:timestamp')`) and a `timestamp` in epoch seconds, and requests sent after 15 minutes are invalid.](kb:shared.legacy-api.auth-models:zdx-signed-secret), and the JWKS and validate endpoints [The ZDX auth reference also has GET /oauth/jwks, returning the public keys that verify the JWT tokens, and GET /oauth/validate, which checks whether the token is valid.](kb:shared.legacy-api.auth-models:zdx-jwks-validate). The legacy ZDX getting-started guide says the base URL is the cloud's `/v1` or `/v2`, depending on what was provisioned for the organization, and its sign-in example posts to `https://api.zdxcloud.net/v2/oauth/token`. [zdx.api.hosts-and-auth:legacy-guide-versions] Both SDKs sign in under `/v1` only [divergence:zdx.api.hosts-and-auth:direct-api-version].

**Paths on each host.** So on the direct ZDX host both the sign-in and the data calls sit under `/v1` with no `/zdx` segment, while on the gateway both sit under `/zdx/v1`. [zdx.api.hosts-and-auth:direct-host-paths] The OneAPI Postman collection uses the gateway shape: The OneAPI Postman collection sets `{{ZDXBaseUrl}}` to `{{oneAPIBaseUrl}}/zdx/v1`, with `oneAPIBaseUrl` set to `https://api.zsapi.net`, so a request such as `{{ZDXBaseUrl}}/devices` carries no second `/v1`. [zdx.api.hosts-and-auth:postman-base-url] The clients' own settings are in [The Python SDK's legacy ZDX client: credentials, host and paths, token caching, and what happens when the token expires](kb:zdx.sdk-python.legacy-client) and [The Go SDK's direct (legacy) ZDX client: credentials, sign-in, retries and limits, and why the ZDX services do not use it](kb:zdx.sdk-go.legacy-client), and the Go ZDX services reach the API only through OneAPI: [So a service built with `NewLegacyZdxClient` cannot run the ZDX service functions: they reach the missing legacy ZPA client and return an error, and the direct ZDX client's sign-in, retries and limiter never apply to them; the SDK's ZDX example builds a OneAPI service instead.](kb:zdx.sdk-go.legacy-client:services-not-routed).

**Which host a tenant uses.** Whether a tenant's credentials work on one host, the other or both is open [gap:zdx.api.hosts-and-auth:token-host-per-tenant].

What to check:
1. Which credential the caller holds: a ZIdentity API client (gateway, `/zdx/v1`) or a ZDX API key ID and secret (direct host, `/v1`).
2. Whether the tenant was provisioned for the legacy API's v1 or v2 base URL before relying on an SDK that signs in under `/v1`.

Sources disagree (name both sides):
- What ZDX Service Desk Tier 1 sees of user information: the OneAPI getting-started page gives it obfuscated user information, while the ZDX help gives it the Users Dashboard and User Search, and says User Search needs the User Name permission to be Visible. [divergence:zdx.api.hosts-and-auth:service-desk-user-info]
  - zscaler-help: Tier 1 has restricted view access with obfuscated user information and a limited time window.
  - zscaler-help: Tier 1 has read permissions to the Users Dashboard and access to the User Search.
  - zscaler-help: An admin with access to User Name can access User Search.
  - zscaler-help: With User Name Obfuscated an admin does not have access to User Search.
  Impact: The OneAPI page does not say which user information is obfuscated, and the role article ties User Search to a Visible User Name; whether Tier 1 sees user names is unsettled.
- The direct host's API version: the legacy guide says a tenant's base URL is v1 or v2 by provisioning and signs in at `/v2/oauth/token`; both SDKs always sign in at `/v1/oauth/token`. [divergence:zdx.api.hosts-and-auth:direct-api-version]
  - zscaler-help: Tenants are provisioned for v1 or v2, and a v2 tenant's base URL ends in `/v2`.
  - sdk-python: The Python legacy client signs in at `/v1/oauth/token` on every tenant.
  - sdk-go: The Go direct client signs in at `/v1/oauth/token` on every tenant.
  Impact: If a v2-provisioned tenant does not answer under `/v1`, both SDKs' direct clients fail to sign in there; no source says whether `/v1` works for such a tenant.
