# Configuring ZDX alert rules: types, filters, metrics, throttling, delivery, templates and labels (zdx.alerts.rules)
Also called: zdx alert rule; alert rule configuration; alert rule type; alert rule criteria; zdx alert templates; zdx alert labels; managed monitoring templates; zdx score drops; predefined alert templates

An alert rule is what raises a ZDX alert: it has a type, a severity, optional labels, criteria over metrics, filters, throttling and a delivery method; how a trigger and an alert's status behave is in [ZDX alerts: how rules trigger, what an alert's status means, and reading alerts through the API](kb:zdx.alerts). The Configuring an Alert Rule article offers the types Applications, Call Quality, Device, Incident, Network, Network Intelligence and Real User Monitoring (RUM), and each rule has a severity of High, Medium or Low and optional labels. [zdx.alerts.rules:rule-types] The trigger article lists fewer types, and the two lists are set side by side in [ZDX alerts: how rules trigger, what an alert's status means, and reading alerts through the API](kb:zdx.alerts). The Editing an Alert Rule article says the ZDX Score alert rule type is no longer recommended and any pre-existing ZDX Score rule has migrated to an Applications rule; for an existing ZDX Score rule an Applications or Network rule is created with ZDX Score selected as a criterion, and the throttling and other field values remain the same. [zdx.alerts.rules:zdx-score-type-retired] The help describes the ZDX Score type differently in places [divergence:zdx.alerts.rules:zdx-score-rule-type].

**Scope and filters.** By type, Applications rules choose a predefined or custom application and its Web probe; Call Quality rules a predefined UCaaS application; Network rules a predefined or custom application of the network type and its Cloud Path probe; RUM rules a predefined or custom application with RUM enabled; Device, Incident and Network Intelligence rules take filters only. Incident rules filter by geolocations, devices and users, Network Intelligence rules by Zero Trust Exchange, geolocations and ISPs, and the other types by geolocations, Zscaler locations, location groups, departments, user groups, users and devices. [zdx.alerts.rules:parameters-and-filters] A rule's filter can include or exclude items but not both for the same filter, deleted or unknown users cannot be selected for the include and exclude criteria, and the limit for selected items in the Add Filter menu is 250 items. [zdx.alerts.rules:filters] For an Incident rule one or more checkboxes can be selected from the Incident Type drop-down menu; if multiple incidents are selected, the criteria are predefined based on their minimum thresholds. [zdx.alerts.rules:incident-types] Which rules an admin can configure depends on scope: [In the article's example, only an admin with scope over both Germany and France can configure an alert rule whose locations are Germany and France.](kb:shared.admin-rbac.zdx:scope-covers-rule).

**Criteria.** The criteria metrics the table lists include, for Applications, DNS Time, Page Fetch Time, Server Processing Time, Web Request Availability, ZDX Score, ZDX Score Drops and Zscaler Time to First Byte; for Call Quality, MOS and ZDX Score; for Network, Latency, Number of Hops, Packet Count, Packet Loss, ZDX Score and ZDX Score Drops; for Network Intelligence, Threshold Latency and Network Latency Deviation; and for Device the bandwidth, battery, CPU, disk, memory, received and sent bits and Wi-Fi Signal rows quoted in the article. Each incident type or subtype has a different minimum number of impacted devices. [zdx.alerts.rules:metrics] Selecting All (and) triggers the alert if all thresholds are reached and Any (or) if any is; depending on the metric a criterion uses the <, >, <= or >= symbols with time in ms or percent, a ZDX Score criterion is chosen between 1 and 100, and for ZDX Score Drops the threshold sensitivity (for example high, medium, low) is based on a baseline score. [zdx.alerts.rules:criteria-logic]

**Throttling.** For Applications, Device, Network or Real User Monitoring (RUM) rules, throttling has Alert Only if Repeated (the number of times a triggering event occurs before an alert is sent; Zscaler recommends 3 or more), Minimum Devices Impacted (by Number or Percentage; alerts trigger even if only one device is present in a specific group and meets the criteria) and an In Group of Departments, Cities, Organization, Regions or Locations. In the article's example the alert does not trigger because there must be at least 5 active devices in Cairo. [zdx.alerts.rules:throttling-device-groups] Call Quality rules throttle by the number of impacted meetings in a 15-minute rolling time duration (within 1 and 10), the minimum number of total active participants in a meeting (within 3 and 10) and the number of impacted active participants (within 1 and 20) from a selected group (Department, Cities, Organization, Regions, Zscaler Locations). [zdx.alerts.rules:throttling-call-quality] The throttling listed after the Call Quality options for Network Intelligence rules includes Alert Only if Repeated (Zscaler recommends entering 3 or more) and Minimum Users Impacted, which triggers the alert only if that minimum number of impacted users is reached. [zdx.alerts.rules:throttling-network-intelligence] The trigger article's throttling criteria are in [Application, device and network rules add throttling criteria: Alert Only if Repeated (how many times the situation must repeat), the number of active devices, and the minimum number or percentage of devices impacted, the last two based on an In Group selection of departments, cities, organization, regions or Zscaler locations; a rule whose group has fewer active devices than required does not trigger.](kb:zdx.alerts:throttling). Which meaning one throttling sentence has is open [gap:zdx.alerts.rules:incident-actions-sentence].

**Delivery.** If Muted is enabled no alerts are sent and the status of alerts can be viewed on the Alerts page; the delivery method otherwise is Email (an address, with an Email Preview of the email that will be sent) or a Webhook selected from previously configured webhooks or newly configured. [zdx.alerts.rules:delivery] Webhook setup is in [ZDX alert webhooks: authentication, testing, platform guides and the payload fields the sample scripts read](kb:zdx.alerts.webhooks). The Rules page shows when each rule last triggered an alert and its Alert Delivery Method (Email or webhook if configured, empty if the rule is muted or none is configured), can be filtered by severity (High, Medium or Low) and can edit, mute, copy or delete a rule. [zdx.alerts.rules:rules-page]

**Templates and labels.** ZDX templates save frequently used alert rule criteria and can then prefill an alert rule when configuring a Zscaler Managed probe; a template's Type is Predefined or Custom and its Probe Type is Cloud Path or Web, and a predefined template cannot be edited or deleted but can be copied. Managing templates needs an admin role that supports Alerts and Configuration and a subscription level that supports Managed Monitoring. [zdx.alerts.rules:templates] The predefined templates are Warning Availability (High, Web: Availability < 100% 2 times in 60 minutes across any 1 Zscaler Managed Location), Critical Page Fetch Time (High, Web: Page Fetch Time > 1000 ms 3 times in 15 minutes across any 2), Warning Page Fetch Time (Medium, Web: the same across any 1), Probe Failure (High, Web: Availability = 0% 3 times in 15 minutes across any 1), Critical Latency (High, Cloud Path: Latency > 5 ms 3 times in 15 minutes across any 2) and Warning Latency (Medium, Cloud Path: the same across any 1). [zdx.alerts.rules:predefined-templates] After a label is assigned to an alert rule it becomes part of the alert details and is seen in the delivered alert details when webhooks are configured; multiple labels can be applied to a rule for grouping, managing and assigning labels needs Full Alerts permission, and a label cannot be deleted if an alert rule is tagged with it. A new label's Name and Description can each be at most 120 alphanumeric characters including hyphen, space or underscore. [zdx.alerts.rules:labels]

What to check:
1. Which rule type the alert belongs to, and whether the trigger article's shorter type list or the configuration article's longer one applies to the tenant's console.
2. Whether a rule still shows a ZDX Score type or was migrated, before treating the type as current.
3. For a rule that did not trigger, the type's throttling fields: repeat count, active devices, minimum devices or users impacted and the group they apply to.
4. For an alert that was not delivered, whether Muted is enabled and which delivery method the rule has.

  - zscaler-help: The ServiceNow Mappings module maps alerts configured in the Admin Console as ZDX Score.
  - zscaler-help: The ZDX Score rule type is no longer recommended and existing ZDX Score rules migrated to Applications.
  Impact: Whether a tenant can still create or see a ZDX Score rule type is unsettled; an alert reported as a ZDX Score alert may be an Applications or Network rule with a ZDX Score criterion.
