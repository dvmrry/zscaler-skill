# ZDX API rate limits: the license tiers, the headers, and how the clients pace themselves (zdx.api.rate-limits)
Also called: zdx rate limit; zdx 429; x-ratelimit-remaining-second; zdx rate limit headers; zdx api tier; zdx throttling sdk

ZDX limits requests per tenant tier, and each client paces itself in its own way. The server side is documented once for all OneAPI products.

**The server's limits.** The tier table is [ZDX API limits depend on the tier level by license count: tier 1 (5,000 licenses) 5 per second, 30 per minute, 1,000 per hour and 10,000 per day; tier 2 (20,000) 5, 60, 3,000 and 15,000; tier 3 (100,000) 5, 120, 6,000 and 30,000; tier 4 (more than 100,000) 5, 180, 9,000 and 60,000. Every endpoint is called from a specific IP address.](kb:shared.oneapi.rate-limits:zdx-tiers), the windows start with the first call ([For ZDX and Business Insights, every rate-limit window starts with the first call, and calls may come more than once per second within the limits.](kb:shared.oneapi.rate-limits:window-starts-first-call)), and rate-limited clients must back off exponentially ([The ZDX and Business Insights pages say clients that are rate limited must back off exponentially; Business Insights adds waiting for the suggested retry period on a 429.](kb:shared.oneapi.rate-limits:back-off-exponentially)). The ZDX GraphQL API's rate limits are based on the license tier level and have five tiers: tier 3 is 40,000 licenses at 5 per second, 120 per minute, 6,000 per hour and 30,000 per day, tier 4 is 100,000 at 12, 300, 15,000 and 75,000, and tier 5 is more than 100,000 at 12, 450, 22,500 and 150,000. The ZDX API's own table has four tiers, with 100,000 licenses at tier 3 and more than 100,000 at tier 4 ([ZDX API limits depend on the tier level by license count: tier 1 (5,000 licenses) 5 per second, 30 per minute, 1,000 per hour and 10,000 per day; tier 2 (20,000) 5, 60, 3,000 and 15,000; tier 3 (100,000) 5, 120, 6,000 and 30,000; tier 4 (more than 100,000) 5, 180, 9,000 and 60,000. Every endpoint is called from a specific IP address.](kb:shared.oneapi.rate-limits:zdx-tiers)). [zdx.api.rate-limits:graphql-tiers] Whether the two tables number the same tiers is open [gap:zdx.api.rate-limits:tier-numbering]; the GraphQL limits are also in [The ZDX GraphQL API within Analytics is limited by license tier, from 5 per second, 30 per minute, 1,000 per hour and 10,000 per day at tier 1 (5,000 licenses) to 12 per second, 450 per minute, 22,500 per hour and 150,000 per day at tier 5 (more than 100,000).](kb:shared.analytics.graphql-errors-and-limits:zdx-graphql-limits).

**Headers.** The documented headers are [ZDX sends the rate-limit headers `x-ratelimit-limit`, `x-ratelimit-remaining` and `x-ratelimit-reset`, the last being the seconds remaining in the current window.](kb:shared.oneapi.rate-limits:zdx-headers). The SDKs' direct clients read differently named per-second headers [divergence:zdx.api.rate-limits:header-names], and which family each host sends is open [gap:zdx.api.rate-limits:header-family-per-host].

**How the clients pace.** The Go OneAPI client's ZDX limiter is [The Go SDK builds its ZDX limiter with the same arguments as the ZCC one, commented as 100 calls per hour and 3 per day for downloadDevices.](kb:shared.oneapi.rate-limits:go-zdx-limiter-copies-zcc). The Go direct client's fixed limiter paces only its sign-in ([So the fixed 100-per-60-seconds limiter paces only sign-in requests; API calls through this client are paced only by the backoff and the server's limits.](kb:zdx.sdk-go.legacy-client:limiter-auth-only)) and its backoff waits a fixed time chosen from the per-second headers and the status code ([Its backoff reads `X-Ratelimit-Remaining-Second` and `X-Ratelimit-Limit-Second`. When there is a response it waits 1 second plus up to 500 ms of jitter if fewer than the threshold (2 by default) requests remain, otherwise 2 seconds after a 429 and 500 ms for any other response; it backs off exponentially only when there is no response.](kb:zdx.sdk-go.legacy-client:backoff)). The Python executor's wait on a 429 comes from `Retry-After` or the reset header ([The retry wait comes from Retry-After plus one second, or else from the rate-limit reset header plus one second; with neither header the request is not retried and an error is returned.](kb:shared.sdk-python.retries:wait-from-headers)), and its legacy ZDX client reads the per-second headers only around sign-in ([The client reads `X-Ratelimit-Remaining-Second` only on a 429 to its sign-in and in its JWKS fetch; its general rate-limited GET helper, which also reads `X-Ratelimit-Limit-Second`, is defined but not called.](kb:zdx.sdk-python.legacy-client:second-headers)). Neither SDK reads the tenant's tier: the Go limiters are fixed constants (100 calls per hour on the OneAPI client, 100 per 60 seconds on the direct client's sign-in) and the other pacing reacts only to what a request gets back: response headers, a 429 or another status, or no response. [zdx.api.rate-limits:no-tier-awareness] The earlier question about reconciling the client limiters with the tier is closed by this reading [gap:zdx.api.rate-limits:tier-vs-client-limiter].

What to check:
1. Which tier the tenant's license count puts it in, and which window (second, minute, hour or day) a 429 came from.
2. Which header a hand-written client reads for its remaining budget, and whether that header is present on the host it calls.

Sources disagree (name both sides):
- The rate-limit header names: the ZDX rate-limiting page documents `x-ratelimit-limit`, `x-ratelimit-remaining` and `x-ratelimit-reset`; the SDKs' direct clients read `X-Ratelimit-Remaining-Second` and `X-Ratelimit-Limit-Second`. [divergence:zdx.api.rate-limits:header-names]
  - zscaler-help: The remaining budget is in `x-ratelimit-remaining`, for the current window.
  - sdk-go: The Go direct client reads the remaining budget from `X-Ratelimit-Remaining-Second`.
  - sdk-python: The Python legacy client reads `X-Ratelimit-Remaining-Second` on a sign-in 429.
  Impact: If the server sends only the documented headers, the SDKs' proactive per-second backoff never engages and they fall back to their 429 handling; a hand-written client that reads the SDKs' names would see nothing.
