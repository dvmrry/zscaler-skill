# Configuring end-user Web and Cloud Path probes in the console: fields, defaults, limits and protocols (zdx.probes.configuration)
Also called: configure a probe; configuring a probe; edit a probe; zdx autosense; packet count; resilient tcp; strict tcp; conventional tcp; force reverse cloud path; follow web probe; top private apps probe

This is how the console configures an end-user probe; what the probes measure is in [ZDX probes: Web and Cloud Path probes, what they measure and how they run](kb:zdx.probes) and the Zscaler Managed probes are in [Managed Monitoring and Zscaler Managed Probes: where they run, what they chart and their subscription limits](kb:zdx.probes.managed). A Web probe and a Cloud Path probe are automatically enabled by default when a predefined application is onboarded, and the Add Probe link is disabled once the maximum number of allowed applications or probes for the subscription level is reached. [zdx.probes.configuration:predefined-defaults] End-user probe types are End User Web and End User Cloud Path; the Probe Class (Predefined or Custom) is selected automatically from the application, and for a Network application the Cloud Path probe type is selected by default because network applications do not require Web probes. [zdx.probes.configuration:probe-types]

## Web probes

A probe name is at most 64 characters, alphanumerics and a limited range of symbols such as underscore, hyphen, space, forward slash, period, pipe symbol and parentheses. [zdx.probes.configuration:probe-name] GET is the only request type applicable to Web monitoring, POST is not supported and the field is view-only; the Destination URL is an HTTP or HTTPS URL, editable if the URL requires a tenant name; request headers take a name and value, for example to pass a security token, and are disabled for predefined applications. [zdx.probes.configuration:web-request]

**Success codes.** A Web probe can probe for specific HTTP status codes; per Configuring a Probe, codes not in the default list can be added by entering any number from 100 to 599, the default 1xx, 2xx and 3xx codes include 100 Continue, 101 Switching Protocol, 102 Processing, 103 Early Hints, 201 Created, 202 Accepted, 203 Non-Authoritative Information, 204 No Content, 205 Reset Content, 206 Partial Content, 207 Multi-Status, 208 Already Reported, 226 IM Used, 300 Multiple Choices, 301 Moved Permanently, 302 Found, 303 See Other, 304 Not Modified, 307 Temporary Redirect and 308 Permanent Redirect, and the default codes of a predefined app cannot be changed. [zdx.probes.configuration:web-status-codes] The range for adding codes differs between two articles [divergence:zdx.probes.configuration:custom-status-code-range]; the default list is set against the contract's and the error help's in [ZDX probes: Web and Cloud Path probes, what they measure and how they run](kb:zdx.probes).

**Attempts, timeout and redirects.** A Web probe's default is 1 attempt before the request is considered failed (it can be increased), a 60-second timeout and 5 maximum redirects, none of which can be changed for a predefined application; Maximum Redirects is also disabled if Follow Redirect is, and for the following predefined applications Follow Redirect is disabled by default and cannot be enabled: Microsoft Teams Web App, OneDrive for Business, Outlook Online, ServiceNow and SharePoint Online. [zdx.probes.configuration:web-retry-timeout-redirects] Whether the help's attempts are the contract's retries is open [gap:zdx.probes.configuration:attempts-vs-retries].

## Cloud Path probes

Cloud Path probes are sent every 15 minutes by default for Standard ZDX subscriptions and every 5 minutes for Advanced ZDX subscriptions, and the default Run Frequency varies with the subscription plan. [zdx.probes.configuration:cloud-path-frequency] For a Call Quality Monitoring (CQM) application the Cloud Path probe type shown automatically is the ZDX Autosense feature, which discovers the Cloud Path Host associated with the application and lets the application and its meetings be monitored; it is configured automatically as part of the Cloud Path probe when a CQM application is first onboarded, and ZDX Autosense must be enabled to use it. [zdx.probes.configuration:cqm-autosense] A Cloud Path probe can follow an accompanying Web probe to better visualize both together; if a Web probe is followed and TCP is chosen as the protocol, the port value cannot be edited. [zdx.probes.configuration:follow-web-probe]

**Protocol.** A Cloud Path probe's protocol is Adaptive (the best protocol for each leg in the cloud selected by auto-discovery, with TCP port 443 and UDP port 33434 shown and editable), ICMP (general connectivity using latency), UDP (real-time application pathways, port 33434, the RFC-defined port, editable) or TCP (port availability, with a TCP type and port configured). [zdx.probes.configuration:cloud-path-protocols] For a TCP Cloud Path probe the Resilient TCP type (the default) retries and falls back to the Conventional type, a SYN packet traceroute, when the TCP connection fails; Strict has no fallback and shows an error with the packet loss percentage; Conventional establishes no TCP connections and relies on SYN packets, so firewalls might block it; Resilient and Strict need a minimum version compatibility and the selection defaults to Conventional when it is not met. [zdx.probes.configuration:tcp-types] Adaptive for Private Access applications is described two ways [divergence:zdx.probes.configuration:adaptive-private-access]; what Adaptive mode does is in [ZDX probes: Web and Cloud Path probes, what they measure and how they run](kb:zdx.probes).

**Packets, interval and timeout.** Packet Count, the number of probe packets sent per hop discovery with the same TTL value, defaults to 5 (minimum 3, maximum 20); for Private Access 3 is recommended and 6 is the maximum; a higher count gives a more accurate measurement of packet loss. [zdx.probes.configuration:packet-count] Interval (ms), the time between probe packets with the same TTL, within which packets of incremental TTL are paced evenly, defaults to 1000 (minimum 1000, maximum 10000); at 6000 ms and a maximum of 30 hops the packets are paced every 200 ms. [zdx.probes.configuration:interval] Timeout (ms), the time to wait for a response to a probe packet before considering loss, defaults to 1000 (minimum 500, maximum 5000) with 500 recommended for Private Access; at 2000 ms the first probe times out at 2,000 ms, the second at 2,200 ms and the third at 2,400 ms. [zdx.probes.configuration:timeout]

**Host and reverse path.** The Cloud Path Host is the host IP address or fully qualified domain name, given as the IPv4 address with IPv6 not supported; Zscaler partially provides the domain name if the selected application is predefined, and the field is editable if a tenant name (such as for a CQM application) is required. [zdx.probes.configuration:cloud-path-host] Whether a host name can resolve to IPv6 is open [gap:zdx.probes.configuration:cloud-path-ipv6]. Force Reverse Cloud Path in Trusted Network forces a reverse traceroute in the trusted environment when a network device blocks the forward Cloud Path, and should be enabled only if a different device configuration cannot be implemented; it calculates reverse latency from the Internet & SaaS Public Service Edge to the egress, whose IP address comes from the location API, can differ from the forward path's and is noted as a Reverse Egress. [zdx.probes.configuration:reverse-cloud-path]

## Copying, deleting and editing

Configuring a Probe gives procedures to copy and to delete a probe for an application. [zdx.probes.configuration:copy-delete-scope] Whether a probe can be deleted on its own is described two ways, see [ZDX collections: default collections, membership, ranking, criteria, deletion and limits](kb:zdx.probes.collections). Preset probe configurations cannot be reconfigured, some fields cannot be edited because of the previously selected probe configuration, and Zscaler recommends waiting at least 30 minutes after editing probe settings before expecting to see changes in the dashboard. [zdx.probes.configuration:edit-probe]

## From Top Private Apps

In the Top Private Apps wizard's Web probe step, the Probe Name, Application Name and Request Type cannot be configured. [zdx.probes.configuration:tpa-fixed-fields] In the Top Private Apps probe wizard, HTTP codes not in the default list can be added by entering any number from 100 to 499. [zdx.probes.configuration:tpa-status-codes] In the Top Private Apps probe wizard the Cloud Path protocol options include Adaptive, ICMP, TCP and UDP, and choosing TCP shows the standard HTTPS TCP port 443, which can be edited; the list of Top Private Apps is created from readily available Private Access data. [zdx.probes.configuration:tpa-protocols] In the Top Private Apps probe wizard, for Private Access the recommended packet count is 3 packets with a maximum of 6, and the recommended timeout setting is 500. [zdx.probes.configuration:tpa-private-access] If only the Web probe was selected in the Top Private Apps wizard's previous step, the option to configure a Cloud Path probe is not offered. [zdx.probes.configuration:tpa-cloud-path-optional] The Top Private Apps list itself is in [The list of Top Private Apps is created with readily available data from Private Access; it is searched by the port numbers a private application uses, separated by commas, sorted by users (the default) or bandwidth, and shows each application's protocol, bandwidth and Configured for ZDX status; an application whose Configured for ZDX is Yes cannot have its probe configured on the Top Private Apps page and is reached in Configuration > Probes.](kb:zdx.applications:top-private-apps).

Sources disagree (name both sides):
- The range for adding custom HTTP status codes to a Web probe: Configuring a Probe says 100-599, and the Top Private Apps probe wizard says 100 to 499. [divergence:zdx.probes.configuration:custom-status-code-range]
  - zscaler-help: Codes not in the default list can be added with any number from 100 to 599.
  - zscaler-help: Codes not in the default list can be added with any number from 100 to 499.
  Impact: A 5xx code can be added to a probe in one article's range and not in the other's; the pages do not say whether the Top Private Apps wizard is narrower or the text is a slip.
- Adaptive mode for Private Access applications: Evaluating the Cloud Path says it is not supported for internal applications through Private Access, while the Top Private Apps wizard, which configures probes for Private Access applications, offers Adaptive as a Cloud Path protocol. [divergence:zdx.probes.configuration:adaptive-private-access]
  - zscaler-help: Adaptive mode is not supported for internal applications through Private Access; only ICMP, TCP and UDP are.
  - zscaler-help: The Top Private Apps probe wizard, whose list is built from Private Access data, offers Adaptive, ICMP, TCP and UDP.
  Impact: Whether Adaptive can be used for a Private Access application's Cloud Path probe is not settled; the wizard may offer an option the Cloud Path article says is unsupported.
