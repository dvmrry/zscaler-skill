# Reading the Cloud Path: the Hop View and Command Line View, tunnels, protocols, edges, and the error messages (zdx.probes.cloud-path)
Also called: hop view; command line view; cloud path errors; cloud path error messages; cloud path tunnel information; z-tunnel cloud path; cloud path ipv6; no default route cloud path; private access errors zdx

The Cloud Path view is the console's rendering of a Cloud Path probe's route; the probe itself is defined in [ZDX probes: Web and Cloud Path probes, what they measure and how they run](kb:zdx.probes). The Cloud Path view has a graph of latency or packet loss for a time period and a Hop View and Command Line View of the path from the user's device to the application or destination; selecting a point in the graph updates the path shown. [zdx.probes.cloud-path:path-view] The Command Line View gives each hop's direction (client to egress, Public or Private Service Edge back to egress, Service Edges to destination), region and geolocation, packet loss percentage, packets failed and latency, with error icons beside IP addresses. [zdx.probes.cloud-path:command-line-view]

**Hops and tunnels.** The Hop View shows differential latency per leg with the highest-latency leg in orange; the latency over a Public Service Edge is between the Public Service Edge and the first router in the Zscaler data center and might indicate congestion. [zdx.probes.cloud-path:hop-latency] The Hop View shows traffic through the tunnels the configured policies apply: for GRE it shows the underlay hops for more accurate latency and packet loss, and for an Internet & SaaS Private Service Edge on a private network with a private IP it shows the path from the client to the Private Service Edge. [zdx.probes.cloud-path:hop-tunnels] A client reaches the Internet & SaaS Public Service Edge by Z-Tunnel 1.0 or Z-Tunnel 2.0, or by a location tunnel such as GRE or IPSec; the tunnel information lists GRE and IPSec tunnels and Z-Tunnel 1.0 or 2.0 over GRE or IPSec, and a Direct Request bypasses the tunnel and shows no tunnel graphic in the Hop View. [zdx.probes.cloud-path:tunnel-types] With Citrix as the network interface for TCP or UDP probes, ZDX shows the path to the VPN Concentrator, including traffic from the concentrator to the Public Service Edge over GRE or IPSec; with an External Proxy detected in the path, the Hop View supports several proxy topologies. [zdx.probes.cloud-path:citrix-proxy]

**Interfaces and locations.** Network interface types that are neither Wi-Fi nor Ethernet show a cellular (SIM card), Bluetooth or USB icon above the client icon in the Hop View, or an unknown-type icon when the type cannot be detected; geolocation and the Zscaler location are shown for the device, and geolocation is also shown for the Zscaler node in both the Hop View and the Command Line View. [zdx.probes.cloud-path:interface-icons] For an internet application the path shows any Public Service Edge for Internet & SaaS or for Private Access in it; for a private application it runs from Client Connector to the Public Service Edge or Private Service Edge for Private Access, and when a path is configured through the Public Service Edge for Internet & SaaS both edges appear; both views show a 4-digit internal hash for the Internet & SaaS or Private Access Public Service Edge that helps Zscaler Support. [zdx.probes.cloud-path:edges-in-path]

**Protocols.** Both views show the protocol per leg: ICMP, TCP or UDP as selected, or under Adaptive mode the protocol each leg used, with legs grouped by tunnel type also showing their protocol; Adaptive mode is not supported for internal applications through Private Access, for which only ICMP, TCP and UDP are supported. [zdx.probes.cloud-path:leg-protocol] The Top Private Apps probe wizard offers Adaptive for Private Access applications, see [zdx.probes.configuration:adaptive-private-access](kb:zdx.probes.configuration:adaptive-private-access). For traffic routed to an internal or external destination through Internet & SaaS Source IP Anchoring, the Cloud Path detects network issues (latencies, packet loss, jitter) and shows a path with full end-to-end visibility; the feature is in Limited Availability and enabled by contacting Zscaler Support. [zdx.probes.cloud-path:sipa] When a test target resolves to an IPv6 address, ZDX traces the end-to-end path and measures latency, packet loss and jitter across each IPv6 hop; ZDX shows dual-stack or IPv6-only configurations, relies on Internet & SaaS to route and inspect IPv6 for clients inside a location and on Client Connector for clients outside one, and the configuration article lists Enable IPv6 for Internet & SaaS and Enable IPv6 for Zscaler Client Connector. [zdx.probes.cloud-path:ipv6] The probe configuration articles say the Cloud Path host is IPv4 only, see [Whether a Cloud Path host that is an FQDN can resolve to IPv6](kb:zdx.probes.configuration:cloud-path-ipv6).

**Subscription.** The subscription table lists the Hop View (Granular Expanded Cloud Path) as supported on Standard, Microsoft 365, Advanced and Advanced Plus (columns in the order of the table's header row). [zdx.probes.cloud-path:hop-view-tier]

## Cloud Path error messages

Cloud Path errors show as icons under the hop in the Hop View and next to the IP address in the Command Line View, at three levels: informational (no action required), warning (action might be necessary to achieve accurate Cloud Path results) and critical (an issue that could affect the user experience). [zdx.probes.cloud-path:error-levels]

**Client and reachability.** Client and reachability errors: a Client Connector internal error (contact Zscaler Support); a network communication failure, where an interface is down, probes get no response or ISP upstream connectivity might be down (verify ISP connectivity and that the probe's ICMP or UDP protocol is not blocked); an invalid or unresolvable domain (verify the domain name or DNS configuration); a failed proxy connection (verify the proxy policy, authentication and that access is allowed for the application URL); and an invalid HTTP URL in the Web probe. [zdx.probes.cloud-path:client-errors] A probe result is discarded when the network changes during the Cloud Path run: the sample's Cloud Path probes were aborted, Client Connector detected the change, and no action is required. [zdx.probes.cloud-path:discarded-on-network-change]

**Client egress.** Client egress errors: when the egress IP is tunneled the path to the client egress cannot be traced correctly (configure an access list on the router or SD-WAN device to bypass ICMP or UDP from the GRE or IPSec tunnel for the egress IP); when Client Connector cannot fetch ZDX service data from the Zscaler cloud the path to the egress cannot be traced and end-to-end latency does not include the client-to-egress latency (contact Zscaler Support); when egress detection fails with the configured protocol, try ICMP or UDP; and when the egress router does not answer Cloud Path probes from the ZIA Public Service Edge with an ICMP TTL expired message, configure it to return ICMP TTL expired messages for packets with IP TTL 1. [zdx.probes.cloud-path:egress-errors]

**Service Edge and protocol.** Service Edge and protocol errors: ZDX does not collect hop information from the ZPA Public Service Edge to the application (no action required); a Public Service Edge unreachable from Client Connector means the TCP traceroute to it was dropped (check the network connection); ICMP and UDP probes are not supported in a No Default Route (NDR) environment (run probes via TCP); and traceroute packets not reaching the Zscaler Service Edge mean the ICMP, TCP or UDP protocol traceroute might not be supported on the network (ensure the network permits the configured protocol). [zdx.probes.cloud-path:edge-protocol-errors]

**External proxy.** External proxy errors: the legs from the external proxy to the destination, to the egress or to the data center egress, and from the data center egress or the egress to the destination when an external proxy is present, are not discoverable (path not available, no action required); Cloud Path packets not reaching the external proxy mean the ICMP protocol might not be supported on the network (ensure it allows ICMP packets). [zdx.probes.cloud-path:external-proxy-errors]

**Private Access.** ZDX can report Private Access errors from the Public Service Edge or Private Service Edge for Private Access: an internal error and an unreachable application (contact Zscaler Support); a failure to retrieve customer information (ask the user to reauthenticate, and contact Support if it persists); an expired user session, where a data connection cannot be set up because reauthentication is required; and a failure to fill assistant groups due to a configuration error (ask the user to validate configuration). [zdx.probes.cloud-path:pa-errors] Private Access policy errors: no valid policy matches the application request (a missing or mismatched setting in policy, SAML or SCIM attributes, Posture Profiles, Trusted Networks, Client Types, Cloud Connector Groups or Machine Groups, or a disabled App Segment or App Group Segment); no App Connector group in the Server group (edit the Server group to add them); the application policy or the timeout policy blocked the request (the user is not allowed, or must reauthenticate in Client Connector); the application is not configured; and a connection request timed out waiting for a data connection request from an App Connector (ensure the App Connectors can reach the edge and the application). [zdx.probes.cloud-path:pa-policy-errors]
