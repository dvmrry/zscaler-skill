# How DSPM covers on-premises data: data centers, scanner integrations and the scanner VM, and evidence settings (dspm.on-premises)
Also called: dspm on-premises data center; dspm premises scanner; dspm scanner integration; dspm scanner vm; zds init; dspm evidence settings; dspm evidence rule

**Data centers.** DSPM scans the databases in on-premises data centers; the data center page gives this as the scanned content. [dspm.on-premises:dc-scope] The Managing On-Premises Data Center page lists as prerequisites an account onboarded with a custom model for connectivity, security groups allowing the scanner or orchestrator subnets, a custom role to configure SQL authentication, and SQL connection strings and credentials. [dspm.on-premises:dc-prereqs] The unmanaged database prerequisites are the same list in [How to register unmanaged databases, Snowflake and Databricks in DSPM, with credentials and the database roles the pages give](kb:dspm.service-registration-databases). Changes to an on-premises data center configuration take effect only at the next scheduled scan. [dspm.on-premises:dc-edit-effect] An on-premises data center associated with any unmanaged databases cannot be deleted; the Delete option is grayed out. [dspm.on-premises:dc-delete-restriction]

**Scanner integrations.** On-premises scanners deployed in the organization's network scan data in on-premises systems such as file servers and unmanaged resources. [dspm.on-premises:scanner-purpose] The scanner list shows Scanner Status as operational or pending and Last Connected On, the last successful connection of the scanner instance to DSPM. [dspm.on-premises:scanner-status-fields] The scanner image is an OVA for VMware or a VHD for Hyper-V, and a checksum is shown to verify the downloaded image. [dspm.on-premises:scanner-image] The scanner's API key is not recoverable and regenerating it invalidates all existing scanners using the current key; the integration name cannot be changed after saving. [dspm.on-premises:scanner-api-key] The page gives compromise, exceeding the rotation threshold, or rotating credentials per policy as reasons to regenerate the scanner API key. [dspm.on-premises:scanner-regenerate-reasons] A scanner integration's details cannot be edited; the API key can be regenerated and the image downloaded again to reinstall or redeploy the scanner. [dspm.on-premises:scanner-not-editable]

**Scanner VM requirements.** The scanner VM minimum is 16 virtual cores (Intel Xeon or AMD EPYC; ARM not supported), 32 GB RAM and 100 GB SSD, with Ubuntu 22.04 embedded in the OVA and no separate OS license. [dspm.on-premises:scanner-vm-reqs] The scanner VM needs a dedicated 10 GbE network interface (wired preferred), a static IP address and DNS resolution of internal and external hosts. [dspm.on-premises:scanner-network-reqs] The scanner VM's required outbound ports are 443 to the DSPM Cloud Management Platform, 445 (SMB) and 2049 (NFS) to file servers, 53 to DNS, 88 to Kerberos and 111 for the NFS portmapper. [dspm.on-premises:scanner-outbound-ports] The file-server scanner supports SMB versions 2.0, 2.1, 3.0, 3.02 and 3.1.1 and NFS v4.0, v4.1 and v4.2. [dspm.on-premises:scanner-protocols] Outbound destination addresses and scan scale are open [gap:dspm.on-premises:scanner-sizing].

**Initializing the scanner VM.** Initializing the scanner VM needs an API key generated in the Zscaler Admin Console and outbound internet connectivity to the DSPM services. [dspm.on-premises:scanner-init-prereqs] The scanner VM's default login is username zdspmuser with password zscaler@scanner, and the first login prompts for a new password for zdspmuser. [dspm.on-premises:scanner-default-login] The VM is configured with `sudo zds preconfigure` (static IP/CIDR, gateway, primary DNS, optional secondary DNS, optional HTTPS proxy), initialized with `sudo zds init <API_KEY>`, and optionally checked with `sudo zds healthcheck`. [dspm.on-premises:scanner-init-commands] Configuring an HTTPS proxy during preconfigure restarts the VM automatically; without a proxy the network settings apply without a restart. [dspm.on-premises:scanner-proxy-restart] After initialization the scanner VM registers with the DSPM tenant and its status becomes Operational in the Zscaler Admin Console. [dspm.on-premises:scanner-registered]

**Evidence.** Evidence is the data captured when sensitive information is found during an on-premises scan; the snippets are stored in the organization's cloud storage and not in Zscaler infrastructure. [dspm.on-premises:evidence-definition] Evidence storage is either Zscaler Managed (DSPM creates and manages a bucket in the customer's cloud account, the recommended simple option) or Custom (an existing S3 bucket the customer provides). [dspm.on-premises:evidence-storage-options] Evidence configuration is linked to specific on-premises data centers, and any scanner assigned to a rule's data centers uses that rule for evidence uploads. [dspm.on-premises:evidence-linked-dc] Evidence is routed through the existing DSPM service connection, so the on-premises scanner network need not be opened to external cloud storage IP addresses. [dspm.on-premises:evidence-path] The evidence IAM role (example name z-dspm-evidence-role) is created in the customer's cloud and lets the scanner upload findings and the Zscaler Admin Console read them; a CloudFormation template automates provisioning the required IAM roles and policies, and a Terraform template can also be downloaded. [dspm.on-premises:evidence-iam-role]

**Evidence rules.** Adding an evidence rule needs an on-premises data center configured in DSPM and a cloud storage bucket available for the evidence data. [dspm.on-premises:evidence-rule-prereqs] A custom-bucket rule takes the S3 bucket name, bucket account ID and KMS key ARN used to encrypt the evidence; a Zscaler-managed rule takes the AWS account ID where the template is deployed; the IAM role name has a prefilled default. [dspm.on-premises:evidence-rule-fields] A new evidence rule is enabled by default and should be validated to confirm the template deployment succeeded, after which DSPM uploads evidence from its data centers to the configured bucket. [dspm.on-premises:evidence-rule-enabled-validate] DSPM validates evidence rules every 4 hours; Connection Status is Success (template deployed and S3 connection works), Pending (template not yet deployed or validation incomplete) or Failed (connection failed, details in the Error column), and evidence is collected only when the connection succeeds. [dspm.on-premises:evidence-validation] Evidence data is cached for 60 minutes: after a rule is disabled, evidence continues to be collected and stored for 60 minutes, and collection does not start until the cache clears. [dspm.on-premises:evidence-cache] Other clouds and bucket limits are open [gap:dspm.on-premises:evidence-clouds]. Whether disabling stops collection at once is open [gap:dspm.on-premises:evidence-disable-timing].

What to check:
1. Which on-premises content is in scope: the data center page names databases, and the scanner page names file servers and unmanaged resources.
2. The scanner VM's CPU, RAM, storage, network interface, outbound ports and SMB and NFS versions against the documented minimums.
3. The Connection Status of the evidence rule (Success, Pending or Failed) and the Error column.

Not known (open gaps):
- Scanner outbound IPs, scan scale and status wording [gap:dspm.on-premises:scanner-sizing]: settled by source-read
- Evidence clouds, snippet limits and retention [gap:dspm.on-premises:evidence-clouds]: settled by source-read or tenant-data
- Whether disabling an evidence rule stops collection at once or after 60 minutes [gap:dspm.on-premises:evidence-disable-timing]: settled by lab-test or support-ticket
