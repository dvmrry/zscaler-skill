# How to onboard a GCP organization or project to DSPM: prerequisites, APIs, OAuth scopes, service account and key maintenance, error resolutions and the service account roles (dspm.onboarding-gcp)
Also called: dspm gcp onboarding; dspm gcp organization; dspm gcp project; dspm gcp service account; dspm gcp errors; dspm gcp iam roles; dspm terraform gcp error

Onboarding a GCP organization requires Super Admin access to the Google Admin console and both a GCP Organization Administrator role and an owner role; the page lists Terraform CLI v1.7.5 or later for Windows and the gcloud CLI. [dspm.onboarding-gcp:org-prereq-admin] The scan orchestrator is in [Scans are performed by a local scan orchestrator deployed in the customer's AWS, Azure, GCP or on-premises data center account during onboarding; resources are scanned against a set of standard security policies and a scan schedule, and scan rules select the resources, the scan type and the scan frequency.](kb:dspm.scanning:orchestrator); whether project onboarding is a listed type is open [gap:dspm.onboarding-gcp:project-onboarding-type-listing]; service accounts are named in [Scans authenticate either cloud-natively (cross-account IAM roles in AWS, service principals or managed identities in Azure, service accounts in GCP) or by bring-your-own identity: credentials (username or password or access keys stored in the vault, mostly for unmanaged databases) or certificate-based mutual TLS.](kb:dspm.scanning:authentication); the hub is [Data Security Posture Management (DSPM): what it finds in stored data, how it differs from inline DLP, and what can be automated](kb:dspm.overview) and the scanning subject is [How DSPM scans: onboarding scope, the in-account orchestrator, data stores, authentication, classification and data residency](kb:dspm.scanning).

**Roles and policy.** The custom role in the Google Admin console is an optional step; the resulting roles give read access to user data, group and member data, and domain resources, and if it is skipped DSPM cannot gain read-only access to this resource data. [dspm.onboarding-gcp:org-custom-admin-role] The Disable service account key creation organization policy blocks service account key creation by default and must be overridden for the project where the service account is created, ending in a Not enforced status. [dspm.onboarding-gcp:sa-key-policy-override] For a single GCP project, mandatory roles include GCP Owner (orchestrator project), Project IAM Admin (target project) and Storage Object Admin (Terraform state bucket project); Organization Policy Administrator and Super Admin are optional. [dspm.onboarding-gcp:project-required-roles] The GCP organization onboarding page says "Under Select Onboarding Type, click the Project tile.", and the GCP project page gives the same tile instruction, "For Select Onboarding Type, click the Project tile.". [dspm.onboarding-gcp:select-project-tile]

**APIs and scopes.** On the GCP organization page, admin.googleapis.com is enabled on the Tree Discovery and Target projects, serviceusage.googleapis.com on Tree Discovery, Orchestrator and Target, cloudkms.googleapis.com on Orchestrator and Target, and aiplatform.googleapis.com on Target. [dspm.onboarding-gcp:org-api-table] networkmanagement.googleapis.com is enabled on the Orchestrator project and is described as required for BYON, and servicenetworking.googleapis.com on the Orchestrator for private connections between the VPC network and DSPM. [dspm.onboarding-gcp:api-networkmanagement-byon] compute.googleapis.com is needed to enable notebooks.googleapis.com and compute resources on the target project, requires the project to be linked to billing, and must be enabled on the target project before notebooks.googleapis.com. [dspm.onboarding-gcp:api-compute-billing] On the single GCP project page, admin.googleapis.com, serviceusage.googleapis.com and iam.googleapis.com are each listed for the Orchestrator and Target projects (the organization page lists admin.googleapis.com for Tree Discovery and Target). [dspm.onboarding-gcp:project-api-table] When terraform plan or terraform apply runs for the tree discovery template, Terraform verifies that the required APIs are enabled and shows an error prompting to enable any missing API. [dspm.onboarding-gcp:terraform-api-check] DSPM uses OAuth scopes including cloud-platform and the read-only admin.directory scopes for user, group member and domain for API authentication. [dspm.onboarding-gcp:oauth-scopes]

**Details and templates.** In the GCP organization details, the role and service account names may contain only alphabetic characters, numbers, hyphens and underscores; the organization name is validated against the Organization ID; and up to 30 notification emails can be added. [dspm.onboarding-gcp:org-details-naming] Applying the tree discovery template returns JSON containing the project ID, private key ID, private key and client email, which is pasted under Generated JSON in DSPM. [dspm.onboarding-gcp:tree-discovery-json] On the GCP organization page the custom network configuration is selected by default, and using the Zscaler configuration requires contacting Zscaler Support. [dspm.onboarding-gcp:org-network-config-default] For a single GCP project, the Zscaler network configuration makes DSPM automatically provision network resources in the orchestrator project after the template is deployed, while Custom uses the organization's resources and takes a VPC Selflink. [dspm.onboarding-gcp:project-network-config] The GCP Log Bucket Name must be unique or DSPM shows an error; the log bucket stores the target projects' activity logs and is created when the onboarding template is deployed, and DSPM automatically excludes Cloud Storage buckets used for storing logs. [dspm.onboarding-gcp:log-bucket-name] For a GCP organization, selecting the main project group scans all projects under it, Autodetection includes new projects added to the management group, and the business unit assigned to a management group applies to all its projects. [dspm.onboarding-gcp:org-monitoring-scope-autodetect] For GCP evidence storage the Custom Bucket type is selected by default; Zscaler Managed Bucket makes DSPM create a new bucket in the orchestrator project. [dspm.onboarding-gcp:evidence-default-custom] On the single GCP project page, evidence storage is Custom (name of a storage account in the orchestrator project) or Zscaler (DSPM creates a storage container in the orchestrator project). [dspm.onboarding-gcp:project-evidence] On the GCP organization page the evidence template is described as available "only if you have configured an S3 bucket to store evidence data", while the same page's evidence step describes a Custom Bucket or Zscaler Managed Bucket in the orchestrator project. [dspm.onboarding-gcp:org-evidence-template-s3-wording] When running the GCP onboarding template, DSPM creates resources required for scanning only in the regions entered at the prompt, and network analysis is enabled or disabled by setting enable_test_connectivity to true or false. [dspm.onboarding-gcp:onboarding-template-regions] Clicking Validate for the GCP template takes a couple of minutes, and DSPM also validates the deployment every hour by checking the created roles and granted permissions. [dspm.onboarding-gcp:validation-timing] For a single GCP project, the Custom Role Name Prefix is added as a prefix to all custom roles created during onboarding and the Service Account Prefix to the service account created. [dspm.onboarding-gcp:project-prefixes]

**Maintenance.** Managing the GCP monitoring scope requires an Administrator role or any role with the Configure Monitoring Scope permission. [dspm.onboarding-gcp:monitoring-scope-prereq] After a GCP project is added to the monitoring scope it cannot be removed; to stop monitoring it the project must be deleted from the DSPM organization. [dspm.onboarding-gcp:monitoring-scope-no-remove] The GCP monitoring scope page tells the reader to enable Autodetection so DSPM detects and onboards any new "subscriptions" added in the future. [dspm.onboarding-gcp:monitoring-scope-subscription-wording] Adding target projects to an onboarded GCP account requires an Administrator role or a custom role with the Configure Monitoring Scope permission. [dspm.onboarding-gcp:target-projects-prereq] Adding GCP target projects takes Project ID, optional Project Name and a Business Unit, and the GCP Onboarding template on the Roles and Templates tab is then downloaded and deployed. [dspm.onboarding-gcp:target-projects-fields] Changing the GCP orchestrator project is available only for tenants onboarded through Zscaler network configuration mode and needs an administrator role or a custom role with the Configure New Orchestrator permission. [dspm.onboarding-gcp:change-orchestrator-scope] Until the new GCP orchestrator project is validated, the existing orchestrator is disabled, the DSPM connection status is Waiting for Connection and Configuration status Pending, data scans stop, and target projects are Needs Attention. [dspm.onboarding-gcp:change-orchestrator-interim-states] Before running the template on a new GCP orchestrator project the previous template is purged with terraform destroy, and the Log Bucket Name entered must be unique or DSPM shows an error message. [dspm.onboarding-gcp:change-orchestrator-purge] If the GCP service account is accidentally deleted, DSPM access to the onboarded account is impacted and all onboarded projects move to Needs Attention until the service account details are updated; after the template is successfully deployed, access is restored and the projects move to Successfully Configured. [dspm.onboarding-gcp:service-account-deleted] For a GCP organization, updating the service account means running the Tree Discovery template and the GCP Onboarding template; for a GCP project, the GCP Onboarding template is run. [dspm.onboarding-gcp:service-account-update-paths] The service account private key is generated in JSON format when the tree discovery template is applied; it can be replaced at any time by uploading a JSON key file in the Update Private Key window, and DSPM shows an error if the key is invalid or does not match the service account. [dspm.onboarding-gcp:private-key-update]

**Errors.** The GCP configuration issues page lists error messages shown in the CLI app during onboarding, each with a resolution. [dspm.onboarding-gcp:error-table-scope] Error 403 creating a Subnetwork (permission denied on locations/[REGION]) is resolved by running terraform destroy, changing the orchestrator in the console, deploying a new GCP template, and ensuring the selected region has the necessary permissions. [dspm.onboarding-gcp:err-subnetwork-403] In the error table row for Error 400 "Only buckets in state ACTIVE can be deleted" on a Logging Bucket Config with [BUCKET_LOCATION]/[BUCKET_NAME] placeholders, the resolution is to restore the bucket on the Logs Storage page in the Google Cloud console and run terraform destroy. [dspm.onboarding-gcp:err-logging-bucket-not-active] Error 400 "Buckets must be in an ACTIVE state to be modified" when updating a Logging Bucket Config is resolved by restoring the log bucket, running terraform destroy and rerunning the template. [dspm.onboarding-gcp:err-logging-bucket-modify] The error "Failed to query available provider packages" (locked hashicorp/google 5.40.0 does not match configured constraint 6.0.0) is resolved by running terraform init -upgrade to allow selection of new versions. [dspm.onboarding-gcp:err-provider-version-lock] The error "Networks specified in new and old network interfaces must be the same" while updating managed group instances is caused by a mismatch between old and new network interfaces of the managed instance group; the fix is to stop the impacted VM, delete its template and the instance group, then redeploy the template. [dspm.onboarding-gcp:err-managed-group-network-mismatch] Error 409 "KeyRing ... already exists" (duplicate KeyRing name conflict) is resolved by changing the orchestrator in the Zscaler Admin Console and downloading and deploying the new GCP template. [dspm.onboarding-gcp:err-keyring-409] Error 404 creating an instance template is caused by a specified network resource that does not exist; the fix is to verify the network resource and update its reference in the instance template configuration. [dspm.onboarding-gcp:err-instance-template-404] "Unable to Remove Service Networking Connection" (Error code 3, a peering operation in progress) is caused by an ongoing operation and is resolved by rerunning the template. [dspm.onboarding-gcp:err-service-networking-peering] The error table is not a full list [gap:dspm.onboarding-gcp:error-table-incomplete], which resolution applies to the repeated 400 message is open [gap:dspm.onboarding-gcp:logging-bucket-400-two-resolutions], and the provider version is open [gap:dspm.onboarding-gcp:provider-version].

**IAM roles and permissions.** The GCP Discovery service account discovers resources in GCP projects and instructs the Local Scanner Platform; its managed roles include Organization Policy Viewer, Security Reviewer and Cloud Asset Viewer. [dspm.onboarding-gcp:discovery-sa-roles] The GCP Orchestrator service account is used by the orchestrator instance for scan and management operations; its managed roles include Cloud KMS CryptoKey Encrypter or Decrypter and Service Account Token Creator. [dspm.onboarding-gcp:orchestrator-sa-roles] The Orchestrator service account holds logging.sinks.update and logging.sinks.list at GCP Organisation scope to update the DSPM org log sink for bucket incremental scans. [dspm.onboarding-gcp:orchestrator-logging-sinks] The GCP Scanner service account is used by the scanner instance for scan tasks (its roles include Logs View Accessor), and the Target role service account performs scan tasks on data stores. [dspm.onboarding-gcp:scanner-and-target-sa] Scanning GCP BigQuery projects requires permissions including bigquery.tables.getData (read table contents for scanning), bigquery.models.getData (read ML model data for scanning) and bigquery.jobs.create (run BigQuery jobs). [dspm.onboarding-gcp:bigquery-permissions] For Cloud SQL scanning the Target role holds cloudsql.backupRuns.create and cloudsql.backupRuns.delete on monitored projects, and the orchestrator service account holds cloudsql.instances.restoreBackup in the orchestrator project. [dspm.onboarding-gcp:cloudsql-backup-permissions]
