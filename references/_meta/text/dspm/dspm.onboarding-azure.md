# How a Microsoft Azure tenant, management group or subscription is onboarded to DSPM, and the Azure roles and API permissions it needs (dspm.onboarding-azure)
Also called: dspm azure onboarding; microsoft entra tenant onboarding dspm; tree discovery template; azure onboarding template; dspm azure custom roles; dspm azure permissions; dspm orchestrator subscription

You can onboard a Microsoft Entra tenant or management group and their associated subscriptions; DSPM monitors and scans the data stores (for example databases, virtual machines, storage accounts) in the onboarded subscriptions for sensitive data, misconfigurations and vulnerabilities. [dspm.onboarding-azure:tenant-scope] Onboarding requires an Administrator role or any role with Add Accounts permissions in the Zscaler Admin Console. [dspm.onboarding-azure:tenant-admin-console-role] The wider DSPM subjects are [Data Security Posture Management (DSPM): what it finds in stored data, how it differs from inline DLP, and what can be automated](kb:dspm.overview) and [How DSPM scans: onboarding scope, the in-account orchestrator, data stores, authentication, classification and data residency](kb:dspm.scanning).

**Tenant prerequisites.** The tenant onboarding prerequisites table lists Global Administrator at Root for tenant or management group onboarding, User Access Administrator at Root for tenant onboarding, and for management group onboarding Contributor on the orchestrator subscription and User Access Administrator on the management group; Key Vault Administrator is also required. [dspm.onboarding-azure:tenant-azure-roles] The orchestrator region must offer the Standard_D2s_v3 virtual machine instance type, which is required to run the orchestrator instance. [dspm.onboarding-azure:tenant-vm-size] Tenant onboarding requires Access management for Azure resources to be enabled (to manage access to all subscriptions and management groups in the tenant) and the Microsoft.Storage resource provider registered in the orchestrator template subscription (so DSPM can validate the storage account created while onboarding). [dspm.onboarding-azure:tenant-access-mgmt-and-provider] Terraform state files must be stored in an identified storage container; they are required to manage resources created by the DSPM Terraform templates and to upgrade to new templates, and if they are lost or deleted the resources must be purged and the onboarding templates downloaded and rerun. [dspm.onboarding-azure:tenant-state-files] The page says to install the latest versions and tabulates the versions it was captured with: Mac Terraform v1.10.3 and Azure CLI 2.65.0; Cloud Shell (Bash and PowerShell) Terraform v1.9.5 and Azure CLI 2.65.0; Windows command line Terraform v1.7.5 and Azure CLI 2.67.0; Windows PowerShell Terraform v1.9.8 and Azure CLI 2.67.0. [dspm.onboarding-azure:tenant-tool-versions] Zscaler recommends enabling Terraform debug logs while onboarding, by setting TF_LOG to TRACE and TF_LOG_PATH to a log file path. [dspm.onboarding-azure:tenant-debug-logs] The prerequisites table is garbled in the capture [gap:dspm.onboarding-azure:tenant-roles-table-garbled].

**Cleanup.** A cleanup procedure in the tenant prerequisites lists resources to delete or purge in Azure: resource groups z-dspm-{integration-id}-auth-plane-rg, -worker-plane-rg and -control-plane-rg, key vaults named z-dspm-{integration-id}-secrets to purge, and the roles <role_name>-access-role, -analyzer-role, -orchestrator-role and <role_name>-target-role. [dspm.onboarding-azure:tenant-cleanup-resources] When the cleanup applies is not stated [gap:dspm.onboarding-azure:cleanup-trigger].

**Tenant details.** In the Tenant Details step the role name and service principal name may contain only letters, numbers, hyphens and underscores; the role name is a prefix for all custom roles created during onboarding; the Management Group ID field is shown only for management group onboarding and accepts several IDs; Notification Emails is optional and takes up to 30 addresses. [dspm.onboarding-azure:tenant-details-fields]

**Tree discovery template.** The tree discovery template includes policies and permissions to create the service principal, a resource discovery role and managed identities, and generates the application ID and client secret; its ZIP holds two Terraform files (backend.tf and azure_tf_basic.tf). [dspm.onboarding-azure:tree-discovery-template] After deploying the tree discovery template, API permissions must be granted to the service principal through admin consent in Microsoft Entra ID; validation in the Admin Console verifies the application ID, client secret and the custom roles created, and on an error the template is rerun. [dspm.onboarding-azure:tree-discovery-consent-validate] If AI service data collection is enabled, the Custom Role (AI Agent) is assigned to the Tree Discovery service principal at the subscription level. [dspm.onboarding-azure:tree-discovery-ai-role]

**Orchestrator and monitoring scope.** On the tenant or management group orchestrator and monitoring scope page, network configuration is Zscaler (Zscaler resources) or Custom (the organization's resources); Custom is selected by default and the Zscaler configuration requires contacting Zscaler Support. [dspm.onboarding-azure:network-config] In the Zscaler network configuration text, the orchestrator storage account name must not exceed 16 characters; DSPM shows an error if the name is already registered with Microsoft.Storage. [dspm.onboarding-azure:orch-storage-account-name] The Deploy private endpoint for secure communication checkbox establishes a private connection between DSPM and Azure resources and restricts communication over public IP addresses; it can be set or removed after onboarding. [dspm.onboarding-azure:orch-private-endpoint] On the tenant or management group services page all services are selected by default and DSPM permissions are restricted to monitoring and scanning only the selected services; Azure Storage accounts used for storing logs are excluded automatically, and the Leverage MIP Label checkbox allows applying MIP sensitivity labels to Azure File Share. [dspm.onboarding-azure:services-to-monitor] In tenant or management group onboarding, the Unmanaged Database service is disabled for Zscaler network configuration. [dspm.onboarding-azure:unmanaged-db-zscaler-network] DSPM creates and deploys scanning resources only in the selected regions, which must be specified again when deploying the orchestrator template; with Custom network configuration each region takes a Subnet ID and Network Security Group ID, and the optional Postgres Delegated Subnet ID is available only if Database was selected. [dspm.onboarding-azure:regions-and-custom-network-fields] With Custom network configuration, the per-region storage account creation option can be disabled to supply existing storage account details for scan logs, and it is available only if Storage was selected on the services page. [dspm.onboarding-azure:custom-scan-log-storage] Selecting Autodetection at the management group level makes DSPM automatically include and scan new subscriptions added to the management group; all subscriptions in the group are mapped to the business unit assigned to it, the default business unit is assigned initially, and it can be changed after onboarding. [dspm.onboarding-azure:monitoring-scope-autodetect] Custom tags are attached to resources created by DSPM; up to 15 tags can be added to Private DNS zone resources, numeric-only values do not count toward that limit, and Managed Identity resources get only predefined tags. [dspm.onboarding-azure:custom-tags] Evidence storage holds snippets of evidence data for files and tables containing sensitive data; the container cannot be changed after it is added, a Custom Managed Container takes a key vault resource ID used to encrypt the evidence data, and a Zscaler Managed Container is created in the orchestrator account. [dspm.onboarding-azure:evidence-storage] The storage account name rules and tag guidelines are only partly captured [gap:dspm.onboarding-azure:name-and-tag-rules].

**Azure onboarding template.** Deploying the Azure onboarding template creates custom roles for orchestrator, target and scanner, virtual machine scale sets for the orchestrator, blob containers for diagnostic logs, a queue receiving scan requests from DSPM, VNET peering and a NAT gateway. [dspm.onboarding-azure:onboarding-template-resources] Running the Azure onboarding template prompts for the IPv4 address of the system running Terraform; DSPM validates the deployment every hour by checking the roles created and permissions granted, and Validate takes a couple of minutes. [dspm.onboarding-azure:onboarding-template-prompts-validate] The template files are not vendored [gap:dspm.onboarding-azure:terraform-templates-not-vendored].

**Changing the orchestrator subscription.** Changing the orchestrator subscription applies when the existing subscription is being decommissioned or deleted or was selected incorrectly, and is available only for tenants onboarded through Zscaler network configuration mode. [dspm.onboarding-azure:change-orchestrator-scope] Until the new orchestrator subscription is validated, the existing orchestrator is disabled, the connection status is Waiting for Connection, the configuration status is Pending, data scans stop and the target subscriptions are Needs Attention; after successful deployment the subscriptions return to Successfully Configured and scanning begins. [dspm.onboarding-azure:change-orchestrator-effects] Changing the orchestrator subscription requires an administrator role or a role with the Configure New Orchestrator permission, and the system IP address added to the Azure storage account and Key Vault IP networks before redeploying (needed when multiple users apply Terraform from different IP addresses); the previous template is purged with terraform destroy and the random_seed in terraform.tfvars is changed. [dspm.onboarding-azure:change-orchestrator-prereqs]

**Monitoring scope, application details and client secrets.** Once a subscription is added to the monitoring scope it cannot be removed from it; to stop monitoring, the subscription must be deleted from the DSPM tenant. Managing the scope requires an Administrator role or a custom role with the Configure Monitoring Scope permission. [dspm.onboarding-azure:monitoring-scope-no-remove] The monitoring scope can be extended with Autodetection, which lets DSPM automatically detect and onboard new subscriptions added in the future. [dspm.onboarding-azure:monitoring-scope-autodetection-enable] If the service principal is accidentally deleted, DSPM access to the tenant is impacted and all onboarded subscriptions move to Needs Attention; updating the application details restores access and the subscriptions move to Successfully Configured. [dspm.onboarding-azure:service-principal-deleted] A service principal client secret has an expiration date and must be renewed for the service principal to remain functional, and the secret provided while onboarding a tenant can be updated; validation of an updated secret shows an error if it is invalid or does not match the service principal. [dspm.onboarding-azure:client-secret-update-tenant] The client secret of the application created while onboarding an Azure subscription has an expiration date and must be renewed for the application to retain DSPM access; validation checks it against the application ID and shows an error if it is invalid or does not match the application. [dspm.onboarding-azure:client-secret-update-subscription]

**Subscription onboarding.** A single Azure subscription can be onboarded for DSPM to monitor and scan its data stores for sensitive data, misconfigurations and vulnerabilities; the application (client) ID is saved from the Entra ID app registration because onboarding requires it. [dspm.onboarding-azure:subscription-onboarding-scope] For subscription onboarding the Microsoft Graph permissions Application.Read.All (Application) and User.Read (Delegated) are Mandatory and AuditLog.Read.All, Directory.Read.All, InformationProtectionPolicy.Read.All, Organization.Read.All, Reports.Read.All, RoleManagement.Read.Directory, RoleManagementPolicy.Read.Directory and UserAuthenticationMethod.Read.All (Application) are Optional; entitlements are affected if the optional ones are not configured, and granting admin consent requires the Privileged Role Administrator role. [dspm.onboarding-azure:subscription-graph-permissions] For subscription onboarding the User Access Administrator role is assigned to the created application on the orchestrator and target subscriptions with the condition Allow user to assign all roles (highly privileged), repeated for every subscription DSPM monitors. [dspm.onboarding-azure:subscription-role-assignment] To deploy the DSPM templates for subscription onboarding: User Access Administrator, Contributor and Key Vault Administrator on the orchestrator subscription; User Access Administrator on target subscriptions; Storage Account Contributor on the backend storage account; Application Administrator in Microsoft Entra ID, required if the MIP service is selected. [dspm.onboarding-azure:subscription-deploy-roles] Subscription onboarding takes a Custom Role Name Prefix added to all custom roles created, optional Notification Emails (up to 30), and a network configuration for the orchestrator: Custom (the organization's resources) or Zscaler (Zscaler resources). [dspm.onboarding-azure:subscription-fields] Diagnostic logs identify new, modified or deleted files from monitored storage accounts and are stored with Custom (an existing storage account resource ID per region of the target subscription) or Zscaler (a storage account DSPM creates in the orchestrator subscription after template deployment); evidence is Custom (existing container) or Automated (DSPM creates a container in the orchestrator account), and the Evidence template is available only if evidence is configured. [dspm.onboarding-azure:subscription-diagnostic-logs-evidence] Adding target subscriptions to an onboarded Azure account takes a Subscription ID, an optional Subscription Name and a Business Unit, requires an Administrator role or a custom role with Configure Monitoring Scope, and is followed by deploying the Azure Onboarding template from the Roles and Templates tab. [dspm.onboarding-azure:add-target-subscriptions]

**Roles and permissions.** The IAM roles and permissions page says the DSPM templates create a service principal (enterprise application), custom roles and managed identities in Microsoft Entra ID (the subscription onboarding page has the user register the application), which DSPM needs to connect to the tenant, discover resources and collect metadata. [dspm.onboarding-azure:purpose] The Resource Discovery Role is assigned at the management group level and identifies resources in the onboarded subscriptions; its permissions are */read, Microsoft.Insights/DiagnosticSettings/read, Microsoft.Insights/eventtypes/values/read, Microsoft.Resources/subscriptions/resourceGroups/read, Microsoft.Storage/storageAccounts/blobServices/containers/read and Microsoft.Storage/storageAccounts/listkeys/action. [dspm.onboarding-azure:resource-discovery-role] The DSPM Access Role sends data scan requests to the storage account queues used by the orchestrator subscription, is assigned at the DSPM resource group level, and holds Microsoft.Compute permissions virtualMachines/read, virtualMachineScaleSets/deallocate/action, virtualMachineScaleSets/virtualMachines/delete and virtualMachineScaleSets/write. [dspm.onboarding-azure:access-role] The Target Role is required by the orchestrator subscription to scan data stores and is assigned at the monitoring scope or target subscriptions level; its Actions include disks/beginGetAccess/action (SAS URI of the disk), DBforPostgreSQL flexibleServers/write and Sql servers/databases/write (restoring into the orchestrator subscription), Insights/DiagnosticSettings/write and Storage listkeys/action. [dspm.onboarding-azure:target-role] The Target Role DataActions include Key Vault keys/read, keys/unwrap/action and keys/wrap/action, Storage blobServices/*/read, and Key Vault secrets/getSecret/action, which is conditional and required only if Custom Network is used with Unmanaged DB Scanning. [dspm.onboarding-azure:target-role-dataactions] The Orchestrator Role is used by the orchestrator instance to scan data and is assigned at the DSPM resource group level; among its permissions it creates snapshots and virtual machines for scanning, the PostgreSQL flexible server and SQL server for scanning, and the private endpoint for scanning. [dspm.onboarding-azure:orchestrator-role-scope] In the Orchestrator Role, Microsoft.Compute/virtualMachines/extensions/write is conditional and required only if Custom Network is selected; the Storage DataActions that write MIP labeled files and the file backup semantics privilege are scoped to Monitored Subscriptions. [dspm.onboarding-azure:orchestrator-role-conditional-mip] MIP labeling needs these application permissions on the Orchestrator Managed Identity: Azure Rights Management Services Content.Writer, Microsoft Information Protection Sync Service UnifiedPolicy.Tenant.Read, and Microsoft Graph InformationProtectionPolicy.Read.All. [dspm.onboarding-azure:mip-api-permissions] The Scanner Role is used by scanner instances launched in the orchestrator subscription, assigned at the DSPM resource group level, with Key Vault secrets/getSecret/action and Storage blobServices/*/read DataActions. [dspm.onboarding-azure:scanner-role] The Custom Network Configuration Role lists, at the subscription level for the orchestrator, networkSecurityGroups/join/action, virtualNetworks/subnets/join/action and subnets/joinViaServiceEndpoint/action on the orchestrator subscription; these permissions are conditional and required only if Custom Network is selected. [dspm.onboarding-azure:custom-network-role] The Encryption Role is used by the Local Scanner Platform for CMK encryption tasks on instances, at the DSPM resource group scope, and includes Key Vault keys/decrypt/action and keys/encrypt/action. [dspm.onboarding-azure:encryption-role] The Custom Role (AI Agent) collects data from AI services and is assigned to the Tree Discovery service principal for each subscription; it is required only when AI service data collection is enabled and is assigned at the subscription level, not the root management group. [dspm.onboarding-azure:ai-agent-role] Among the permissions the AI Agent role lists are Microsoft.MachineLearningServices/workspaces/*/read (with Type notActions) and DataActions to read OpenAI assistants, thread runs and vector stores and Microsoft.CognitiveServices/accounts/AIServices/agents/read. [dspm.onboarding-azure:ai-agent-permissions] The IAM roles and permissions page lists as required for the DSPM service principal in Microsoft Entra ID, without naming an onboarding type, the Application permissions Application.Read.All, AuditLog.Read.All, Directory.Read.All, InformationProtectionPolicy.Read.All, Organization.Read.All, Reports.Read.All, RoleManagement.Read.Directory, RoleManagementPolicy.Read.Directory and UserAuthenticationMethod.Read.All, plus the Delegate permission User.Read. [dspm.onboarding-azure:sp-api-permissions] Authentication in general is in [Scans authenticate either cloud-natively (cross-account IAM roles in AWS, service principals or managed identities in Azure, service accounts in GCP) or by bring-your-own identity: credentials (username or password or access keys stored in the vault, mostly for unmanaged databases) or certificate-based mutual TLS.](kb:dspm.scanning:authentication).

Errors met while onboarding are in [Which errors the vendor documents while onboarding Azure to DSPM, and the resolution each row gives](kb:dspm.onboarding-azure-errors).

What to check:
1. Which prerequisite roles the tenant or management group page lists, and which roles the subscription page lists for deploying the templates.
2. Which Microsoft Graph permissions the subscription page marks Mandatory or Optional, and the permissions the IAM roles page lists as required for the DSPM service principal.
3. Whether the orchestrator network configuration is Zscaler or Custom: only Zscaler-mode tenants can change the orchestrator subscription, and Unmanaged Database is disabled for Zscaler.

Sources disagree (name both sides):
- The IAM roles page lists ten Microsoft Graph permissions as required for the DSPM service principal and names no onboarding type; the subscription onboarding page marks eight of them Optional. [divergence:dspm.onboarding-azure:sp-graph-permissions-required]
  - zscaler-help: The API permissions listed, including AuditLog.Read.All, are required for the DSPM service principal.
  - zscaler-help: In subscription onboarding AuditLog.Read.All is Optional.
  Impact: Whether all ten Graph permissions are needed depends on the page read; the IAM page does not say it is scoped to tenant or management group onboarding.
