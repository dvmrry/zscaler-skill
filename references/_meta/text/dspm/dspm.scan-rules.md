# How DSPM scan rules are configured per resource type, how scans are run and stopped, and how scan scopes select DLP engines (dspm.scan-rules)
Also called: dspm scan rule; dspm scan settings; dspm scan scope; dspm scan status; dspm on-demand scan; dspm delta scan; dspm malware scanning; dspm scan schedule

Scan rules select the resources, the scan type and the scan frequency: [Scans are performed by a local scan orchestrator deployed in the customer's AWS, Azure, GCP or on-premises data center account during onboarding; resources are scanned against a set of standard security policies and a scan schedule, and scan rules select the resources, the scan type and the scan frequency.](kb:dspm.scanning:orchestrator). A scan rule needs a unique name, and its optional description is limited to 500 characters (AWS cloud storage rule page). [dspm.scan-rules:rule-name-description] Resource types covered by the rule pages: AWS-managed databases (MySQL, Aurora MySQL, Aurora PostgreSQL), AWS NoSQL (DynamoDB), Azure-managed databases (Azure SQL and PostgreSQL Flexible servers), Azure Cosmos DB, GCP-managed databases (SQL, MySQL, PostgreSQL), GCP BigQuery, Microsoft Foundry projects and Azure OpenAI services. [dspm.scan-rules:resource-types-by-page]

**Before and while configuring.** Before configuring a scan rule, the AWS and Azure Databricks workspaces and the on-premises file servers must be configured, Azure Cosmos DB accounts must be registered in the Admin Console, the Snowflake account must be configured, and the on-premises data center must be configured for on-premises unmanaged databases. [dspm.scan-rules:prerequisite-registration] Microsoft Foundry and Azure OpenAI rules use the Resource Category AI & Machine Learning. [dspm.scan-rules:ai-services-category] On the AWS Databricks rule page, Scan All Resources covers all onboarded and future workspaces and catalogs. [dspm.scan-rules:databricks-scan-all]

**Scan types.** For AWS cloud storage rules the Scan Type page offers Full, Full + Incremental, Incremental, Historical and Historical + Incremental scans; Incremental Scan takes a duration of 1 Day, 1 Week, 1 Month, Continuous or Custom Duration. [dspm.scan-rules:file-scan-types] The incremental options on AWS need CloudTrail integration: [With CloudTrail integration enabled DSPM gets read-only access to the CloudTrail logs needed for incremental scans on the S3 bucket; when disabled, DSPM supports only full scans (organization onboarding page).](kb:dspm.onboarding-aws-cloudtrail:integration-incremental-vs-full). Historical + Incremental scans take a lookback period of 1 to 365 days in the AWS cloud storage, Azure Blob Storage, Azure file shares and Google Cloud Storage rule pages; on the AWS cloud storage page Historical + Incremental also takes a duration in days for the incremental part. [dspm.scan-rules:lookback-range] For Azure NFS file shares, DSPM does not support incremental scans (Incremental, Full + Incremental, Historical + Incremental); the page suggests running periodic historical scans or scheduling frequent full scans instead. The rule scans Azure file shares over SMB and NFS. [dspm.scan-rules:azure-nfs-no-incremental] For AWS-managed databases, Azure-managed databases, GCP-managed databases and AWS NoSQL data stores, the Scan Type page offers a Data Sampling Scan (a sample of recent data) or a Full Scan. [dspm.scan-rules:managed-db-scan-types] The GCP and DynamoDB options are in dispute [divergence:dspm.scan-rules:gcp-managed-db-sampling] [divergence:dspm.scan-rules:dynamodb-recent-data]. On the Scan Type page of the AWS Databricks, Azure Databricks, Azure NoSQL, GCP BigQuery and Snowflake rule pages, the instruction is to select Data Sampling Scan to scan a sample of recent data. [dspm.scan-rules:sampling-scan-type] On the Scan Type page of the AWS unmanaged, Azure unmanaged and on-premises unmanaged database rule pages, the Scan Type page lists Data Sampling Scan: scan a sample of recent data in the database. [dspm.scan-rules:unmanaged-db-scan-type] How sampling relates to relational databases is in [The About Scan Settings page says that when scanning relational databases such as PostgreSQL, Oracle, SQL Server and MySQL, DSPM scans a sample of the data instead of the whole database, to avoid affecting database operations.](kb:dspm.scanning:database-sampling). In the supported-data-stores tables, Azure Cosmos DB for NoSQL, GCP BigQuery, Snowflake on AWS and Databricks on AWS list Sampling Scan as the data classification method, and the unmanaged databases list Supported by Sampling scan. [dspm.scan-rules:matrix-sampling-only] The About Scan Settings Scan Types table gives Unmanaged Database only the Data Sampling Scan: scan a subset of data. [dspm.scan-rules:about-unmanaged-sampling] Whether Full Scan is unavailable where only sampling is shown is open [gap:dspm.scan-rules:full-scan-availability]. The limits and syntax the pages leave undefined are open [gap:dspm.scan-rules:undefined-options]. The rule pages for AWS cloud storage, AWS-managed databases, Azure Blob Storage, Azure-managed databases, Google Cloud Storage, GCP BigQuery, Snowflake and on-premises file servers each state that DSPM cannot detect files that are deleted in the source (the AWS, Azure or GCP console, the Snowflake database or the file server). [dspm.scan-rules:deleted-files-not-detected]

**Schedules.** In the scan schedule step of the AWS virtual machine, AWS-managed database, Azure virtual machine, GCP virtual machine and GCP BigQuery rule pages, On Demand is the default frequency; the AWS virtual machine page also lists Weekly (day chosen from a drop-down) and Monthly. [dspm.scan-rules:schedule-default-on-demand] On the Microsoft Foundry, Azure OpenAI, Snowflake and on-premises unmanaged database rule pages, the Weekly schedule frequency asks for the day from a drop-down menu and a time. [dspm.scan-rules:schedule-weekly-time] On the AWS Databricks rule page, On-Demand Scan is the default schedule, and the schedule is set in the selected local timezone and displayed in it. [dspm.scan-rules:schedule-aws-databricks] On the AWS unmanaged database rule page, On-Demand Scan is the default schedule and Monthly takes the day of the month plus a time. [dspm.scan-rules:schedule-aws-unmanaged] The lookback range on the file server page is open [gap:dspm.scan-rules:file-server-lookback].

**Selecting and excluding.** In the AWS cloud storage, Google Cloud Storage and GCP BigQuery rule pages, when several key-value pairs are entered to include resources, DSPM scans every resource that matches at least one pair (OR logic); the exclude list works the same way on the AWS cloud storage and Google Cloud Storage pages. [dspm.scan-rules:tag-or-logic] On the Google Cloud Storage rule page, buckets are selected and excluded by labels (key-value pairs); excluding by labels is disabled by default. [dspm.scan-rules:gcp-labels] In the AWS S3 rule, a folder is excluded by entering the bucket name followed by the folder and a forward slash (example my-bucket/reports/); wildcard exclusions on bucket names (example *logs*) match both existing buckets and ones added in the future. [dspm.scan-rules:storage-exclusion-formats] On the exclusion step of the AWS cloud storage and AWS-managed databases rules, if a full scan is already initiated or completed, the excluded bucket, folder or database is excluded in the next incremental scan. [dspm.scan-rules:exclusion-next-incremental] For AWS cloud storage rules, DSPM automatically excludes active CloudTrail and VPC flow log buckets from sensitive data scans even if they match the criteria, and the same page also says DSPM excludes AWS workloads created using the AWS Marketplace from scanning. [dspm.scan-rules:aws-storage-auto-exclusions] In the AWS, Azure and GCP virtual machine rule pages, Exclude Operating System Directories Files from Scanning is enabled by default (disable it to scan OS directories); the excluded directories include Linux /usr/local/ and /usr/share/, the Windows Program Files and Windows directories, and the package path /opt/elasticbeanstalk/. [dspm.scan-rules:vm-os-directory-exclusion] For VM rules (AWS, Azure and GCP pages), Exclude Folders / Directories accepts an exact path, which excludes only that directory (example /var/log/), or a wildcard path, which excludes all files and subdirectories within it (example /var/log/*). [dspm.scan-rules:vm-folder-exclusion-formats] Overlapping rules are in [Overlapping scan rules are allowed but can cause duplicate scans and higher compute costs; DSPM warns during rule creation.](kb:dspm.scanning:overlapping-rules).

**Systems the rule pages exclude or require.** The Azure virtual machine rule page lists systems excluded from scanning: VMs encrypted using ADE, Windows 10 or 11 desktop VMs, Windows Server 2012 VMs, Azure VMs created using unmanaged disks (.vhd from storage account), and storage accounts with public network access disabled. [dspm.scan-rules:azure-vm-excluded-systems] The GCP virtual machine rule page says DSPM supports scanning attached GCP disks, and that FreeBSD, virtual appliances, Windows desktops, and filesystems like BitLocker or CryptoDM are not supported. [dspm.scan-rules:gcp-vm-disk-support] Azure-managed database rules require the Azure SQL database to have a Role-Based Access Control (RBAC) policy for the Key Vault; DSPM does not support scanning Azure SQL databases encrypted with a Customer-Managed Key (CMK) without that policy. [dspm.scan-rules:azure-sql-cmk-rbac] On the Azure-managed database rule page, after completing the scan DSPM deletes the restored servers, databases and File System (FS) Analyzer to reduce the cost for customers. [dspm.scan-rules:azure-db-restore-cleanup] Vulnerability scanning support is in [What DSPM vulnerability scanning supports: virtual machine platforms, operating systems, file systems, libraries, encryption and regions](kb:dspm.vulnerability-scanning).

**Malware scanning.** DSPM supports malware scanning for six resource types: AWS S3 Bucket, AWS EC2 Instance, Azure Storage Account, Azure Virtual Machine, Google Cloud Storage and GCP Compute Engine (VM). [dspm.scan-rules:malware-resource-types] In the scan rule wizard for AWS cloud storage, AWS virtual machines, Azure Blob Storage, Azure file shares, Azure virtual machines, Google Cloud Storage and GCP virtual machines, Enable Malware Scanning is an option that is disabled by default. [dspm.scan-rules:malware-opt-in] Malware and sensitive data scanning run on the same scan schedule, with the malware scan before, concurrently with, or immediately after the sensitive data scan; malware results appear on the Data Inventory page. [dspm.scan-rules:malware-schedule] Zscaler says it uses an industry-leading AV vendor for signature-based detection, plus malware feeds from trusted partners such as Microsoft and Adobe and its own technologies. [dspm.scan-rules:malware-engine]

**Running and stopping scans.** DSPM scan statuses are Disabled (scan turned off and does not run), Scheduled (planned to run at a specified time), On-Demand (manually triggered by the user) and In Progress (actively running, for both full and incremental scans). [dspm.scan-rules:scan-statuses] The scan status page says that if there are issues in the data stores DSPM cannot complete the process, which can result in different scan statuses. [dspm.scan-rules:status-issues] Which other statuses exist is open [gap:dspm.scan-rules:scan-status-others]. After a scan rule is configured it must be enabled to run on its schedule; disabling pauses scanning without deleting the rule. [dspm.scan-rules:enable-required] Disabling a scan rule lets in-progress full scans complete but disables subsequent incremental scans; to stop a full scan immediately, first stop it from the Actions menu on the Scan Settings page. [dspm.scan-rules:disable-effect] The running-an-On-Demand-scan page says an On-Demand scan runs instantly on any configured scan rule, regardless of resource type; that it does not affect the configured schedule (the next scheduled scan runs as planned); and that results show on the Resource Inventory page. [dspm.scan-rules:on-demand] Which resource types allow it is in dispute [divergence:dspm.scan-rules:on-demand-resource-types]. Starting a scan uses the On-Demand Scan option, and the configured scan rule is then queued for scanning. [dspm.scan-rules:start-queued] The Stop Scan option is only visible when a scan is In-Progress, and stopping only stops the scan in progress; upcoming scans continue as scheduled. [dspm.scan-rules:stop-scan] A Delta scan (Only New Files scan, covering only new and modified files on the selected cloud storage resource) cannot be stopped; to stop it entirely the scan rule must be disabled. [dspm.scan-rules:delta-scan] New S3 buckets added to the scan rule are included in the Delta scan automatically and scanned with the latest DLP engine configuration; removing an S3 bucket from the rule stops the scan for that bucket. [dspm.scan-rules:delta-s3-membership]

**Editing and deleting scan rules.** A scan rule is edited from the Scan Rules tab, by Actions on the rule or from the scan rule details drawer, on the Edit Scan Rules page, and finished after a review. [dspm.scan-rules:scan-rule-edit] Deleting a scan rule asks for a click on Confirm in the Delete Scan Rule confirmation window, after which the rule is deleted from the Zscaler Admin Console. [dspm.scan-rules:scan-rule-delete]

**Scan scope.** A scan scope selects the DLP engines used to detect and classify sensitive data in specific file types, and DSPM uses only the specified DLP engines to scan the resources. [dspm.scan-rules:what-scope-does] The scan scope Select Criteria page has a DLP Engine choice (All or Specific DLP Engines), a File Type selection and a Machine Learning Document Scan toggle; when editing a scope, the Specific DLP Engines list is enabled only when specific engines are chosen. [dspm.scan-rules:criteria-fields] A DLP engine must be enabled to be selected in a scan scope (a non-enabled engine is grayed out); a disabled engine already selected is shown grayed out with a partial selection indicator and the scanner does not evaluate it; a deleted engine is removed from all existing scan scopes. [dspm.scan-rules:engine-states] Scan scope documents DSPM OCR for image files (examples .png, .jpeg, .tiff, .bmp, .gif) and images embedded in documents (examples .pdf, .docx, .pptx). [dspm.scan-rules:ocr-file-types] File type filters and machine learning document scans are optimized for cloud storage and VM resources. [dspm.scan-rules:optimized-resources] A scan scope is created first and applied while configuring a scan rule, by choosing it from a drop-down on the rule's Scan Scope page. [dspm.scan-rules:applied-in-rule] The engines themselves are in [DLP engines: the unit a rule references](kb:zia.dlp.engines), and classification and OCR in [Data is classified with Zscaler's DLP engines and dictionaries, through full, incremental, historical or sampling scans.](kb:dspm.scanning:classification) and [DSPM uses OCR to find sensitive data in image files and in images embedded in PDF or Microsoft Office documents.](kb:dspm.scanning:ocr).

What to check:
1. Which Scan Type options the rule page for the resource type lists.
2. Whether the rule is enabled and whether a scan is In-Progress before expecting it to run or stop.
3. Whether the resource is one of the six types malware scanning supports and whether Enable Malware Scanning is on for the rule.
4. Whether a DLP engine in the scan scope is enabled; the scanner does not evaluate a disabled one.

Sources disagree (name both sides):
- The running-an-On-Demand-scan page says an On-Demand scan can run on any configured scan rule regardless of resource type; the About Scan Settings page says it can be performed only on databases and virtual machines. [divergence:dspm.scan-rules:on-demand-resource-types]
  - zscaler-help: An On-Demand scan runs instantly on any configured scan rule, regardless of resource type.
  - zscaler-help: An on-demand scan can be performed only on databases and virtual machines.
  Impact: Whether an On-Demand scan can be started on a storage rule is not settled by the pages; check the Actions menu for the rule before promising one.
- The GCP-managed database rule page offers Data Sampling Scan or Full Scan; the supported-data-stores matrix lists GCP Cloud SQL with Full, Incremental and Historical scans and no sampling. [divergence:dspm.scan-rules:gcp-managed-db-sampling]
  - zscaler-help: The GCP-managed databases Scan Type page offers a Data Sampling Scan or a Full Scan.
  - zscaler-help: The matrix lists GCP Cloud SQL with Full Scan, Incremental Scan and Historical Scan as its data classification methods.
  Impact: Which scan types a GCP Cloud SQL rule really offers is not settled; read the Scan Type page in the console.
- The AWS NoSQL rule page offers Data Sampling Scan (a sample of recent data) or Full Scan for DynamoDB; the matrix and About Scan Settings give it a Full Scan plus a Recent Data scan (new or modified files since the previous scan), not sampling. [divergence:dspm.scan-rules:dynamodb-recent-data]
  - zscaler-help: The AWS NoSQL data stores Scan Type page offers a Data Sampling Scan of a sample of recent data, or a Full Scan of all DynamoDB tables.
  - zscaler-help: The matrix lists DynamoDB with Full Scan and Recent Data Scan.
  - zscaler-help: About Scan Settings gives NoSQL data stores Full Scan or Scan Only Recent Data, defined as files newly added or modified since the previous scan.
  Impact: A sample of recent data and only the data changed since the previous scan are different coverage; which one a DynamoDB rule runs is not settled.
