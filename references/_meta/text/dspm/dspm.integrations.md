# What DSPM integrations do: cloud storage, ITSM, ChatOps and Amazon Security Lake export (dspm.integrations)

DSPM integrations share findings (alerts) with other tools: cloud storage (Amazon S3, Azure Blob Storage, Amazon Security Lake), ITSM (Jira, ServiceNow) and ChatOps (Slack). [dspm.integrations:purpose-and-tools] See also [Data Security Posture Management (DSPM): what it finds in stored data, how it differs from inline DLP, and what can be automated](kb:dspm.overview), [How DSPM scans: onboarding scope, the in-account orchestrator, data stores, authentication, classification and data residency](kb:dspm.scanning) and [How DSPM alerts work: risk level, statuses, snooze and resolve, alert details, and the alert rules and ignore alert filters that act on them](kb:dspm.alerts).

**Status and lifecycle.** On the Integrations page the Status column, listed for Cloud Storage, ITSM and ChatOps (Slack) integrations, shows Success, Failed, Paused or Pending for the previous data transfer, with the failure reason on hover. [dspm.integrations:status-values] Data transfer is enabled by default on a cloud storage integration; disabling it pauses transfer without deleting the integration, and a transfer in progress completes first. [dspm.integrations:data-transfer-toggle] Only users with the administrator role can configure cloud storage integrations. [dspm.integrations:admin-role] After changing values in an integration, the connection must be tested again. [dspm.integrations:edit-retest] An integration associated with alert rules cannot be deleted; the alert rules must first be moved to another integration, and the Delete button stays disabled until then. [dspm.integrations:delete-blocked-by-alert-rules]

**Cloud storage.** A new Amazon S3 integration shows Pending until alert notification rules are associated with it and DSPM sends data logs, after which the status changes to Success. [dspm.integrations:initial-pending] For the Amazon S3 integration the bucket default encryption must be Amazon S3 managed keys (SSE-S3); selecting AWS KMS (SSE-KMS) makes the connection fail. [dspm.integrations:s3-sse-kms-fails] The Amazon S3 integration gives DSPM access through a bucket policy copied from the Admin Console and pasted into the bucket in AWS, and takes the bucket Folder Location. [dspm.integrations:s3-bucket-policy] The Azure Blob Storage integration uses a storage account connection string; the Container Location is optional, but a folder must first be created in Blob Storage before entering its name. [dspm.integrations:blob-connection-string] The Azure Blob Storage integration sends alert data logs to Blob Storage containers for analysis by third-party SIEM or ITSM tools. [dspm.integrations:blob-purpose]

**ITSM tools.** Depending on configuration, DSPM creates ITSM tickets when a misconfiguration or vulnerability is first detected, updates them as scans continue, and closes them when a posture change or manual remediation resolves the issue. [dspm.integrations:itsm-lifecycle] Jira integration needs an OAuth 2.0 (3LO) app in the Atlassian Developer console with Jira API scopes and the Admin Console application URL as Callback URL; its Client ID and Client Secret are entered in DSPM, and Jira cloud versions are supported, provided there is support for the required authentication mechanism and APIs to create a Jira task. [dspm.integrations:jira-oauth] The ServiceNow integration needs an online ServiceNow instance and takes a hostname, username and password, with a Test Connection step. [dspm.integrations:servicenow-fields]

**Slack.** The Slack integration uses an incoming webhook, only one webhook per Slack channel, and up to 10 channels per integration. [dspm.integrations:slack-webhook-limits] For Slack, data is sent only once alert notification rules are configured and associated with the integration. [dspm.integrations:data-flow-needs-alert-rules] The Slack integrations list shows Channels as the number of channels added for sending notifications. [dspm.integrations:slack-channel-count-column]

**Limits.** Slack and Jira limits beyond those above are not covered [gap:dspm.integrations:limits-and-alert-rules]. The alert rules that send to these integrations are in [The ITSM/Ticketing channel of an alert rule takes ServiceNow, JIRA or both, an assignee email, and optional notifications for closed and resolved alerts; ticking Remediation includes remediation steps in the alert payload.](kb:dspm.alerts:rule-channel-itsm) and [An alert rule can also send to a Cloud Storage service through an integration account (with an optional Remediation payload checkbox) or to ChatOps, where Slack and its channels are selected.](kb:dspm.alerts:rule-channel-storage-chatops).

**Amazon Security Lake.** Amazon Security Lake uses OCSF for alert information and requires Parquet for stored alerts; DSPM exports alerts to a pre-configured S3 bucket. [dspm.integrations:overview-ocsf-parquet] Zscaler is set up as a custom source in Security Lake using the Security_Finding event class, in the region where the AWS console is connected; the source name determines the S3 path. [dspm.integrations:custom-source] The custom source takes the account ID and external ID copied from the Cloud Storage page in the Admin Console, which identify DSPM as the source writing to the data lake. [dspm.integrations:custom-source-ids] The Security Lake Test Connection validates that the S3 bucket exists. [dspm.integrations:test-connection-checks-bucket] Files are posted when they reach 256 MB or after 5 minutes, under region=<awsregion>/accountid=<cloudaccountid>/eventDay=<YYYYMMDD> in the custom source root path. [dspm.integrations:partitioning] Alerts are written with static OCSF values category_uid 2, class_uid 2001, metadata.product.name dspm and metadata.version 2.2. [dspm.integrations:ocsf-static-values] OCSF fields map from DSPM alert fields: severity from risk, finding.uid from alert_id, finding.title from policy_name, and time from csp_event_timestamp. [dspm.integrations:ocsf-field-map] OCSF activity maps from the DSPM alert_status field and status_detail from alert_status_description. [dspm.integrations:ocsf-status-map]

**OCSF mapping.** The mapping table is incomplete on the page [gap:dspm.integrations:ocsf-mapping-incomplete].

**Security Lake troubleshooting.** If alert data is in the Security Lake bucket but the Glue Crawler fails to parse it, the cause is typically a custom source created with the wrong event class; it must use the Security Finding event class. [dspm.integrations:troubleshoot-glue-crawler] A Failed status on the Security Lake integration indicates DSPM lacks permission to access the Amazon Security Lake S3 bucket; the page tells readers to apply the required policy granting DSPM access. [dspm.integrations:troubleshoot-failed-status] The page does not define the policy it names [gap:dspm.integrations:security-lake-failed-policy]. If new alerts appear in the Admin Console but are not exported to Security Lake, the alert rule notification configuration and the alert rule scope should be checked. [dspm.integrations:troubleshoot-not-exported]

What to check:
1. Whether alert notification rules are associated with an integration that still shows Pending, since the pages say data is sent only after they are.
2. Whether the Amazon S3 bucket default encryption is SSE-S3, since selecting SSE-KMS makes the connection fail.
