# How to register unmanaged databases, Snowflake and Databricks in DSPM, with credentials and the database roles the pages give (dspm.service-registration-databases)

Adding unmanaged databases requires onboarding the account with a custom model, security groups allowing the scanner or orchestrator subnets, a custom role to configure SQL authentication, and SQL connection strings with credentials. [dspm.service-registration-databases:unmanaged-prereqs] The other registration types are in [What DSPM service registration covers: supported services, connection tests, Cosmos DB, on-premises file servers, NFS and LDAP](kb:dspm.service-registration); see also [Data Security Posture Management (DSPM): what it finds in stored data, how it differs from inline DLP, and what can be automated](kb:dspm.overview), [Scans authenticate either cloud-natively (cross-account IAM roles in AWS, service principals or managed identities in Azure, service accounts in GCP) or by bring-your-own identity: credentials (username or password or access keys stored in the vault, mostly for unmanaged databases) or certificate-based mutual TLS.](kb:dspm.scanning:authentication) and [The About Scan Settings page says that when scanning relational databases such as PostgreSQL, Oracle, SQL Server and MySQL, DSPM scans a sample of the data instead of the whole database, to avoid affecting database operations.](kb:dspm.scanning:database-sampling).

**Engines and credentials.** Database engine choices for an unmanaged database are MS SQL, PostgreSQL, Oracle, MySQL or MongoDB; for Oracle the connection string type is selectable. [dspm.service-registration-databases:unmanaged-engines] Authentication Type options for Azure Key Vault or AWS Secrets Manager providers are SQL Authentication, Microsoft Entra Service Principal, Microsoft Entra Authentication with user-managed identity, SCRAM Authentication or X.509 Authentication; SCRAM and X.509 are for the MongoDB engine only. [dspm.service-registration-databases:unmanaged-auth-types] The Microsoft Entra Service Principal section is headed for Azure only, yet it also has an AWS Secret Manager ARN (for AWS) field; its Key Vault URI (for Azure) must be available in the same account as the unmanaged database, with the Key Vault expected to follow the Azure role-based access control permission model. [dspm.service-registration-databases:unmanaged-entra-sp] The SQL authentication table on the Adding Unmanaged Databases page says where the password secret must be stored depends on the database type: unmanaged databases use the target AWS account or any Key Vault of the target subscription; on-premises databases use the orchestrator account, the worker plane resource group Key Vault in Azure, or the orchestrator GCP project. [dspm.service-registration-databases:unmanaged-secret-location] The Azure location for an unmanaged database is stated two ways on the page [divergence:dspm.service-registration-databases:azure-unmanaged-secret-location]. With a self-hosted HashiCorp Vault, network policies must allow inbound connectivity from the DSPM scanner subnets to the Vault and the databases, and a DSPM user must be created in the Vault. [dspm.service-registration-databases:unmanaged-hashicorp]

**Bulk, on-premises and edits.** Bulk registration uses a downloaded ZIP of two templates, cloud_unmanageddb.xlsx and onprem_unmanageddb.xlsx; the uploaded file name must be exactly one of these names to prevent errors. [dspm.service-registration-databases:unmanaged-bulk-template] For an on-premises unmanaged database, the On-Premise Scanner section is populated automatically if the data center has on-premises scanners; otherwise a scanner must be integrated with the data center. [dspm.service-registration-databases:unmanaged-onprem-scanner] Unmanaged database configuration changes take effect only at the next scheduled scan. [dspm.service-registration-databases:unmanaged-edit-timing]

**Database roles.** For unmanaged MS SQL, a server role (ReadOnlyServerRole) is granted VIEW ANY DATABASE, CONNECT ANY DATABASE and VIEW ANY DEFINITION, and a login is created for SQL, managed identity or service principal authentication. [dspm.service-registration-databases:mssql-role] A server-level trigger GrantReadAccessOnNewDatabase is created so that read access is assigned automatically to newly created MS SQL databases. [dspm.service-registration-databases:mssql-new-db-trigger] For unmanaged PostgreSQL, read-only access is given by granting SELECT on all tables in the public schema to the user. [dspm.service-registration-databases:postgres-role] For unmanaged MongoDB, a user needs readAnyDatabase (read-only on all databases except local and config) and clusterMonitor (monitoring and cluster metadata), both assigned in the admin database. [dspm.service-registration-databases:mongo-roles] For unmanaged Oracle (on-premises, AWS EC2 or Azure VM), a common user C##READ_USER is created with CONTAINER=ALL and granted SELECT_CATALOG_ROLE and SELECT ANY TABLE, and CONTAINER_DATA=ALL is set; the default listener port is 1521. [dspm.service-registration-databases:oracle-user]

**Snowflake.** Snowflake registration needs a dedicated warehouse (created x-small by default) and a role granted MONITOR SECURITY and MONITOR USAGE on the account and the SNOWFLAKE.SECURITY_VIEWER database role. [dspm.service-registration-databases:snowflake-warehouse-role] A z_dspm_grant_db_read procedure runs grants on non-shared Snowflake databases; an optional Snowflake task re-runs it (the example schedule is daily at 2am UTC) to cover newly added databases. [dspm.service-registration-databases:snowflake-grant-procedure] The Snowflake DSPM user authenticates with either a programmatic access token (PAT) or an RSA key pair (generated as unencrypted or passphrase-encrypted). [dspm.service-registration-databases:snowflake-user-auth] A Snowflake network rule allowing ingress from the public IP of the NAT used for scanning is attached as a network policy to the DSPM user. [dspm.service-registration-databases:snowflake-network-policy] When DSPM components are deployed in Azure, the private key secret is created with the Azure CLI because the Azure portal does not support multiple inputs for secrets. [dspm.service-registration-databases:snowflake-azure-cli] Snowflake credentials must be stored in the AWS account, Azure worker plane resource group Key Vault, or GCP project where the orchestrator account is present. [dspm.service-registration-databases:snowflake-secret-location] Snowflake account configuration changes take effect only at the next scheduled scan. [dspm.service-registration-databases:snowflake-edit-timing]

**Snowflake edit page.** The add and edit pages name the secret store ambiguously [gap:dspm.service-registration-databases:snowflake-edit-secret-wording].

**Databricks.** After a Databricks account is onboarded, DSPM automatically discovers its workspaces and creates the SQL warehouses and access permissions for scans; findings are reported on the Resource Inventory page. [dspm.service-registration-databases:overview-auto-discovery] Registering a workspace requires being a workspace admin in the Databricks workspace, who is granted USE CATALOG access to all catalogs. [dspm.service-registration-databases:workspace-admin] For Azure workspaces, the orchestrator and scanner managed identities are each added as Microsoft Entra ID managed service principals with the Databricks SQL access and Workspace access entitlements. [dspm.service-registration-databases:azure-managed-identity] For AWS workspaces, the service principal is added to the admin group so DSPM can calculate entitlements, given Databricks SQL Access and Workspace Access entitlements, and its OAuth secret is stored in the orchestrator account. [dspm.service-registration-databases:aws-service-principal] The JDBC connection string comes from an existing Serverless SQL Warehouse or, if none exists, a new single-node compute with Databricks Runtime 17.1, node type Standard_D2ds_v6 (Azure) or m5d.large (AWS) and termination after 20 minutes of inactivity; the JDBC URL is copied without its last three properties. [dspm.service-registration-databases:connection-string-compute] For AWS customer-managed VPCs, the DSPM orchestrator and scanner subnets must be allowed by network policies or AWS private link. [dspm.service-registration-databases:aws-private-link] For an AWS Databricks account, the service principal needs the Account Admin permission and Metastore Admin on the associated workspaces, because a workspace admin does not have access to all catalogs and schemas in the metastore. [dspm.service-registration-databases:account-metastore-admin] The Databricks Account registration type is available only for AWS. [dspm.service-registration-databases:account-type-aws-only] About 15 minutes after a Databricks account is added, DSPM discovers its workspaces, grants the service principal Workspace Admin on each, creates a dedicated 2X-Small SQL warehouse per workspace that auto-terminates after 10 minutes of inactivity, and grants read access to catalogs and schemas. [dspm.service-registration-databases:account-discovery-actions] For AWS workspaces a Databricks job is recommended to run the permission script because it grants access to newly added catalogs; without a job the script must be re-run for each new catalog. [dspm.service-registration-databases:permission-script-job] In the Databricks workspace details drawer, the Integration Details and 'Execute the script in the Databricks Workspace' sections apply only to Azure cloud account configurations; this does not say AWS workspaces have no permission script. [dspm.service-registration-databases:integration-details-azure-only] The AWS permission-script job is named with the prefix zdspm-job, uses a single-node m5d.large job cluster, runs as the Metastore Admin service principal, and the DSPM service principal is given Can Manage Run. [dspm.service-registration-databases:aws-job-config] If the IP Access List is enabled in the workspace and has rules that might block access, the scanner and orchestrator egress IPs must be allowlisted at the workspace and also at the account level. [dspm.service-registration-databases:ip-access-list] When editing a Databricks workspace, Client ID and Client Secret ARN are editable for AWS only and Connection String for AWS and Azure; the connection must be verified after updating. [dspm.service-registration-databases:edit-fields]

**Databricks gaps.** Whether a GCP Databricks workspace is supported is open [gap:dspm.service-registration-databases:databricks-gcp]. The permission script contents are not shown [gap:dspm.service-registration-databases:databricks-script-contents].

What to check:
1. Where the credential secret must be stored for the database type: unmanaged, on-premises or Snowflake; for an Azure unmanaged database the page gives two different locations, so see the divergence.
2. Whether the Databricks registration type is Account, which the page says is available only for AWS.

Sources disagree (name both sides):
- For an Azure unmanaged database the Adding Unmanaged Databases table says any Key Vault of the target subscription; prerequisite 6 says the Key Vault of the worker plane resource group in the orchestrator subscription. [divergence:dspm.service-registration-databases:azure-unmanaged-secret-location]
  - zscaler-help: For an Azure unmanaged database, the secret is created and stored in any Key Vault of the target subscription.
  - zscaler-help: For Azure the secret is stored in the Key Vault of the worker plane resource group in the subscription where the orchestrator account is present; prerequisite 6 gives an unmanaged/on-premises split only for AWS.
  Impact: Which Key Vault holds an Azure unmanaged database's secret is read two ways on one page; check the console rather than assume either.
