# How to onboard an AWS organization or standalone account to DSPM: prerequisites, templates, orchestrator, monitoring scope and the IAM roles and condition keys involved (dspm.onboarding-aws)
Also called: dspm aws onboarding; dspm aws organization; dspm standalone aws account; dspm stackset; dspm aws iam roles; dspm orchestrator account aws

Onboarding an AWS organization requires an Administrator role or any role with Add Accounts permissions, an AWS account identified as the orchestrator account (where the DSPM template is deployed to scan the target accounts), and target accounts that DSPM defines as the monitoring scope. [dspm.onboarding-aws:org-prereq-roles-accounts] The onboarding types and the scan orchestrator are in [The models that can be onboarded are an AWS Organization or Standalone Account, an Azure Tenant or Management Group, and a GCP Organization.](kb:dspm.scanning:onboarding-types) and [Scans are performed by a local scan orchestrator deployed in the customer's AWS, Azure, GCP or on-premises data center account during onboarding; resources are scanned against a set of standard security policies and a scan schedule, and scan rules select the resources, the scan type and the scan frequency.](kb:dspm.scanning:orchestrator); cross-account authentication is in [Scans authenticate either cloud-natively (cross-account IAM roles in AWS, service principals or managed identities in Azure, service accounts in GCP) or by bring-your-own identity: credentials (username or password or access keys stored in the vault, mostly for unmanaged databases) or certificate-based mutual TLS.](kb:dspm.scanning:authentication); the hub is [Data Security Posture Management (DSPM): what it finds in stored data, how it differs from inline DLP, and what can be automated](kb:dspm.overview) and the scanning subject is [How DSPM scans: onboarding scope, the in-account orchestrator, data stores, authentication, classification and data residency](kb:dspm.scanning).

**Prerequisites.** For the CloudFormation template, two IAM roles (AWSCloudFormationStackSetAdministrationRole and AWSCloudFormationStackSetExecutionRole) are created in the orchestrator account, and the execution role is also created in every target account. [dspm.onboarding-aws:org-cft-stackset-roles] Organization onboarding with the CloudFormation template requires each AWS region to have at least two default subnets in the default VPCs; DSPM creates subnets to launch AWS cloud resources. [dspm.onboarding-aws:org-cft-default-subnets] The Terraform template for an AWS organization needs the Terraform CLI and AWS CLI 2.22 or later locally, plus storage in the primary region of the orchestrator account for Terraform state files (an S3 bucket and a DynamoDB table whose partition key is LockID). [dspm.onboarding-aws:org-terraform-prereq]

**Organization details.** In the AWS organization details, Role Name is added as a prefix to all roles created during onboarding, Management Account ID is the 12-digit account ID, and Notification Emails (optional) takes up to 30 addresses that are notified of configuration or permissions issues. [dspm.onboarding-aws:org-details-fields] The External ID shown during AWS organization onboarding is an optional, autopopulated identifier used in an IAM role trust policy to designate a specific user to assume the IAM role. [dspm.onboarding-aws:org-external-id] The CloudTrail fields of this step are in [How DSPM uses AWS CloudTrail and data events for incremental scans, and what changes when CloudTrail details are reset](kb:dspm.onboarding-aws-cloudtrail). For an organization, DSPM generates only the tree discovery template when the CloudTrail S3 bucket is in the management account, and both a CloudTrail template and a tree discovery template when it is in another account; the CloudTrail template is deployed first in the account holding the bucket. [dspm.onboarding-aws:org-tree-discovery-templates] DSPM validates the tree discovery template deployment every hour by checking the IAM roles and permissions, and the template can be validated immediately with Validate. [dspm.onboarding-aws:org-tree-discovery-validation]

**Orchestrator and monitoring scope.** In organization onboarding, the optional network configuration is either Zscaler (Zscaler resources deploy the orchestrator and monitoring scope) or Custom (the organization's own resources are used). [dspm.onboarding-aws:network-config-options] In the Zscaler Network Configuration steps all services are selected by default, and DSPM permissions are restricted to monitor and scan data only in the selected services. [dspm.onboarding-aws:org-services-default-all] In the Custom Network Configuration steps, DSPM automatically excludes Amazon S3 buckets used for storing logs. [dspm.onboarding-aws:org-s3-log-buckets-excluded] With the Custom network configuration, the orchestrator needs a private Subnet ARN and Security Group ID, each monitored region needs scanner Subnet ARN and Security Group ID, and a DB Subnet Group ARN that DSPM requires to scan RDS databases. [dspm.onboarding-aws:org-custom-network-fields] In the Zscaler Network Configuration steps, DSPM creates and deploys the resources required for scanning only in the selected regions, and the primary region chosen on the Configure an Orchestrator Account page is the one to specify when creating the StackSets. [dspm.onboarding-aws:regions-scope-resources] Selecting an organizational unit scans all its accounts; Autodetection at the OU level makes DSPM include and scan accounts added to the OU later, and automatic deployment must be activated in AWS to deploy stack instances for them. [dspm.onboarding-aws:org-ou-autodetection] On an organization's Assign Business Units page, one business unit is assigned to the OU and all its accounts are mapped to it; the default business unit is assigned initially and can be changed after onboarding. [dspm.onboarding-aws:org-business-unit-default]

**Additional configuration.** In organization onboarding, the Additional Configuration section (custom tags, evidence storage, and data events) can be skipped with Skip This Step and configured after onboarding; custom tags are attached to the resources DSPM creates. [dspm.onboarding-aws:additional-config-skippable] For AWS evidence storage, a Custom S3 bucket (name, 12-digit account ID and a KMS key ARN that encrypts the evidence) or a Zscaler Managed S3 bucket created in the orchestrator account can be chosen; once configured the bucket cannot be modified, only the evidence configuration enabled or disabled. [dspm.onboarding-aws:evidence-storage-options] In standalone onboarding the evidence KMS Key ARN is described as a symmetric KMS key ARN used to encrypt the evidence data in the S3 bucket. [dspm.onboarding-aws:standalone-evidence-kms]

**Deploying the templates.** When creating the orchestrator StackSet, the primary region of the orchestrator is selected first, followed by other regions, and the page says DSPM supports all 29 global regions supported by AWS; Sequential region concurrency deploys one region at a time. [dspm.onboarding-aws:orchestrator-region-order] Before creating a StackSet for a new orchestrator account the old orchestrator infrastructure should be deleted to avoid conflicts, and a conflicting S3 bucket error during StackSet creation is addressed by deleting the existing bucket and retrying. [dspm.onboarding-aws:stackset-conflict-fixes] In organization onboarding, the orchestrator Terraform template is applied with the variable enable_test_connectivity set to true to deploy resources with network analysis enabled and set to false to deploy with it disabled. [dspm.onboarding-aws:terraform-network-analysis] The evidence template is available only when an S3 bucket is configured to store evidence data; it is deployed in the orchestrator account for a Zscaler Managed S3 bucket, or in the account holding the bucket for a Custom S3 bucket. [dspm.onboarding-aws:evidence-template-conditional] The monitoring scope StackSet uses Service managed permissions with automatic deployment Activated and account removal behavior Delete stacks, and its name must be unique and friendly because it is needed when adding target accounts after onboarding. [dspm.onboarding-aws:monitoring-scope-stackset-settings] A monitoring scope StackSet deployment is complete only when all individual stack instances are deployed successfully. [dspm.onboarding-aws:stackset-complete-condition] After the orchestrator and monitoring scope templates are deployed, DSPM validates the deployment every hour by checking roles and permissions; an error message appears if there is a deployment issue and the template is rerun in the root account. [dspm.onboarding-aws:org-template-validation-errors] Deploying the orchestrator and monitoring scope templates creates resources in the AWS orchestrator account including an SQS queue for scan requests, an EventBridge rule forwarding CloudTrail data events to the orchestrator account, a customer managed KMS key, and a NAT gateway preventing inbound public connectivity to orchestrator or scanner instances. [dspm.onboarding-aws:orchestrator-account-resources]

**Managing the monitoring scope.** New AWS accounts can be added to the monitoring scope but existing target accounts cannot be removed; managing it needs an Administrator role or a role with Configure Monitoring Scope permission. [dspm.onboarding-aws:monitoring-scope-add-only] Autodetection at the organization or OU level lets DSPM automatically detect and onboard accounts added in future, and automatic deployment must be activated in AWS for stack instances to be deployed for them. [dspm.onboarding-aws:monitoring-scope-autodetection] For CloudFormation, the monitoring scope template is downloaded as a ZIP file containing a CSV file listing the target accounts to scan and a YAML file with the policies and permissions DSPM needs; adding accounts means replacing the template of the existing monitoring scope StackSet. [dspm.onboarding-aws:monitoring-scope-template-contents]

**Changing the orchestrator account.** Changing the AWS orchestrator account is available only for AWS accounts onboarded through Zscaler network configuration mode, and requires an administrator role or a custom role with the Configure New Orchestrator permission. [dspm.onboarding-aws:change-orchestrator-scope] Until the new AWS orchestrator account is validated, the existing orchestrator is disabled, the DSPM connection status is Waiting for Connection and Configuration status is Pending, data scans stop, and target accounts are in the Needs Attention state. [dspm.onboarding-aws:change-orchestrator-interim-states] Before running the template on the new AWS orchestrator account, the template on the existing one is purged by deleting the stackset or running terraform destroy depending on template type; after validation the target accounts become Successfully Configured and scanning resumes. [dspm.onboarding-aws:change-orchestrator-purge-old]

**Standalone accounts.** Standalone AWS onboarding has three steps: provide orchestrator details, select the network configuration and configure regions (DSPM generates a template in both CloudFormation and Terraform format); deploy the template on the orchestrator account; then add the target accounts and deploy their templates. [dspm.onboarding-aws:standalone-workflow] The standalone AWS account page states two role prerequisites: an Administrator role to onboard the account, and an Administrator role or any role with Add Accounts permissions. [dspm.onboarding-aws:standalone-prereq-roles] Which role the pages require is in dispute [divergence:dspm.onboarding-aws:onboarding-role-prereq]. In standalone AWS onboarding, Role Name is added as a prefix to all IAM roles created during onboarding, and up to 30 notification email addresses can be entered. [dspm.onboarding-aws:standalone-orchestrator-details] In standalone onboarding with the Custom network configuration, the DB Subnet Group ARN is marked optional but is required for DSPM to scan RDS databases, and the Unmanaged Database service is disabled for the Zscaler network configuration. [dspm.onboarding-aws:standalone-db-subnet-group] Standalone orchestrator template deployment: the primary region goes first among the 29 global AWS regions the page says DSPM supports, and a successful deployment leads to the Overview page where target accounts are added. [dspm.onboarding-aws:standalone-orchestrator-validate] Adding a standalone target account takes Account Name, a 12-digit Account ID, a business unit (a default is assigned) and Organization ID, with an optional data events setting. [dspm.onboarding-aws:standalone-account-details] For a standalone account the CloudTrail template is available only if CloudTrail integration is enabled and the Data Events template only if data events is configured. [dspm.onboarding-aws:standalone-conditional-templates] For standalone target accounts DSPM validates the template deployment every hour by checking the roles created and permissions assigned, and an on-demand validation is also possible. [dspm.onboarding-aws:standalone-validation]

**IAM roles.** The AWS resource discovery role is needed to discover resources in onboarded accounts and collect CloudTrail logs, and its permission table (columns Permission, Effect, Scope, Purpose) lists s3:GetObject, dynamodb:BatchGetItem, dynamodb:GetItem, dynamodb:Query and dynamodb:Scan with effect Deny and scope Monitored Accounts. [dspm.onboarding-aws:discovery-role-deny] If AWS Bedrock resources are encrypted with KMS keys, DSPM fails to collect their metadata until kms:Decrypt and kms:GenerateDataKey are explicitly added to the resource discovery role (policy DSPM-BASIC-CUSTOM-POLICY). [dspm.onboarding-aws:bedrock-kms-fix] The orchestrator instance profile role is used by the orchestrator instance in the primary region to organize data scanning, and the scanner instance profile role is used by scanner instances to perform data scanning. [dspm.onboarding-aws:orchestrator-role-purpose] The ec2:CreateNetworkInsightsPath and tiros:CreateQuery permissions of the orchestrator instance profile role are conditional and only required if Custom Network is used. [dspm.onboarding-aws:orchestrator-role-custom-network-perms] In the target role, secretsmanager:GetSecretValue for Unmanaged Database is conditional and only required if Custom Network is used with Unmanaged DB Scanning. [dspm.onboarding-aws:unmanaged-db-secret-perm] The kms:PutKeyPolicy, kms:CreateKey, kms:TagResource, kms:EnableKeyRotation and kms:ScheduleKeyDeletion permissions are scoped exclusively to KMS keys created and tagged by DSPM (z-dspm-resource: true) and do not apply to customer-managed KMS keys. [dspm.onboarding-aws:kms-permissions-scope] The target role is an IAM role created in the target accounts; its DynamoDB export permissions write to a DSPM S3 export bucket in the orchestrator account. [dspm.onboarding-aws:target-role-purpose] The Put Evidence role lets DSPM store evidence snippets in the specified S3 bucket (including deleting objects in the evidence bucket), and the Get Evidence role lets DSPM retrieve them. [dspm.onboarding-aws:evidence-roles]

**IAM condition keys and operators.** For IAM policy conditions DSPM supports String, ARN and Boolean operators (including StringEqualsIfExists and ArnLikeIfExists), and does not support Numeric, Date, IP Address or Binary operators. [dspm.onboarding-aws:condition-operators] The supported keys include aws:PrincipalTag/tag-key, aws:PrincipalOrgID and aws:PrincipalArn under Principal-Based Keys, and aws:ResourceTag/tag-key, aws:ResourceAccount and aws:ResourceOrgID under Resource-Based Keys. [dspm.onboarding-aws:condition-keys-supported] Unsupported condition keys include aws:PrincipalOrgPaths, network keys such as aws:SourceIp, aws:CurrentTime, aws:MultiFactorAuthPresent and aws:CalledVia; when a key is unsupported, evaluation of the condition is skipped. [dspm.onboarding-aws:condition-keys-unsupported] DSPM supports the NotPrincipal element in IAM policies, and does not support dynamic conditions where a value must be deduced. [dspm.onboarding-aws:notprincipal-and-dynamic]

What to check:
1. What each page states as the role prerequisite for onboarding an AWS account: the organization page lists an Administrator role or any role with Add Accounts permissions, and the standalone page lists both that and an Administrator role alone.
2. Which network configuration the account was onboarded with, since changing the orchestrator account is available only for Zscaler network configuration mode, and the Custom configuration asks for subnet, security group and DB Subnet Group values.
3. The states the pages give for target accounts while an orchestrator change is not yet validated: existing orchestrator disabled, Waiting for Connection, Pending, scans stopped and Needs Attention.
4. Whether a monitoring scope change adds accounts (existing target accounts cannot be removed) and whether automatic deployment is activated in AWS for autodetected accounts.
5. Whether Bedrock resources are KMS-encrypted when metadata collection fails, and which permissions the page says to add.

Sources disagree (name both sides):
- The standalone AWS page lists an Administrator role as the requirement to onboard the account, while the organization page (and the standalone page's second prerequisite) allows an Administrator role or any role with Add Accounts permissions. [divergence:dspm.onboarding-aws:onboarding-role-prereq]
  - zscaler-help: An Administrator role is required to onboard the AWS account.
  - zscaler-help: Either an Administrator role or any role with Add Accounts permissions suffices.
  Impact: An admin with Add Accounts permissions but not the Administrator role may or may not be able to onboard a standalone account; the pages do not settle it.
