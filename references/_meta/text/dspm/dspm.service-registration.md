# What DSPM service registration covers: supported services, connection tests, Cosmos DB, on-premises file servers, NFS and LDAP (dspm.service-registration)

DSPM service registration supports managed and unmanaged databases, Snowflake, on-premises file servers, Databricks workspaces and LDAP servers; unmanaged database servers can be added individually or in bulk with templates. [dspm.service-registration:supported-services] The database, Snowflake and Databricks registration is in [How to register unmanaged databases, Snowflake and Databricks in DSPM, with credentials and the database roles the pages give](kb:dspm.service-registration-databases), and the scanning side is in [How DSPM scans: onboarding scope, the in-account orchestrator, data stores, authentication, classification and data residency](kb:dspm.scanning) and [Data Security Posture Management (DSPM): what it finds in stored data, how it differs from inline DLP, and what can be automated](kb:dspm.overview).

**Connection test.** The connection test checks network connectivity and credentials of a registered service before scans; the page says it is automatic for on-premises unmanaged databases and manual for cloud unmanaged databases, Snowflake and Databricks. [dspm.service-registration:test-connection-scope] DSPM runs the connection test automatically after registration for on-premises unmanaged databases; for Snowflake and Databricks the test must be run manually. [dspm.service-registration:auto-test-onprem] The connection test can be started from the Unmanaged Databases, Snowflake or Databricks tab, for one service or several selected services. [dspm.service-registration:test-connection-tabs] Test results appear on the service tab as Last Tested, Status and Status Message; the Status Message gives a description of the test result such as a connection timeout. [dspm.service-registration:test-connection-results]

**Connection test status values.** The test status values are not listed [gap:dspm.service-registration:test-status-values].

**Cosmos DB.** For Azure Cosmos DB, DSPM supports scanning resources through its NoSQL API. [dspm.service-registration:cosmos-nosql-api] Registering Cosmos DB accounts requires the Microsoft Entra tenant hosting them to be onboarded to DSPM. [dspm.service-registration:cosmos-prereq] DSPM does not configure Azure Cosmos DB data plane permissions automatically; they are granted manually, using the Terraform template or Azure CLI command from the Admin Console. [dspm.service-registration:cosmos-permissions-manual] The Terraform template applies permissions across multiple Cosmos DB accounts and creates a custom data plane reader role assigned to the scanner managed identity; the Azure CLI command configures a single account. [dspm.service-registration:cosmos-terraform-vs-cli] If Cosmos DB permissions are not granted, scans fail with a permissions error in the scan logs; removing access means deleting the role assignment in Azure, with no action in the Admin Console. [dspm.service-registration:cosmos-failure-and-removal]

**Cosmos DB permissions.** The exact data plane permissions are not listed [gap:dspm.service-registration:cosmos-permission-list].

**Tab columns.** The On-Premises File Servers and LDAP Servers tabs show a Discovery Status of Completed, Failed or In Progress, with an Error column giving the reason discovery failed. [dspm.service-registration:discovery-columns] On the On-Premises File Servers tab, Detected Shares is the number of file servers discovered during the last scan. [dspm.service-registration:detected-shares]

**Databricks edits.** Changes to the Databricks configuration take effect at the next scheduled scan. [dspm.service-registration:databricks-edit-effective-next-scan] Deleting a Databricks workspace or account in the Admin Console requires typing CONFIRM in the confirmation window. [dspm.service-registration:delete-confirm]

**On-premises file servers.** Before adding an on-premises file server, an on-premises scanner must be integrated, a data center created and associated with the scanner, the NFS client configured for NFS-based servers, and an LDAP server added to map identities to file share entitlements; the file server's own LDAP server selection is optional and available only for SMB. [dspm.service-registration:prereqs] File server type choices are Windows, Linux or NetApp for NFS and Windows or NetApp for SMB; the default ports are 445 for SMB and 2049 for NFS, and a custom port can be entered. [dspm.service-registration:types-and-defaults] The NFS version field appears only when the NFS protocol is selected; for NFS with the NetApp file server type, only a hostname is entered. [dspm.service-registration:version-and-hostname] Authentication Type (Kerberos, AUTH_SYS, NTLMv2) is available only for NetApp file servers: Kerberos for NFS or SMB, AUTH_SYS for NFS only, NTLMv2 for SMB only. [dspm.service-registration:auth-availability] Username applies to Windows or Linux file servers, or to NetApp with Kerberos or NTLMv2; Group IDs (comma-separated GIDs) apply only with AUTH_SYS. [dspm.service-registration:creds-and-gids] The optional LDAP server selection on a file server is available only for the SMB protocol. [dspm.service-registration:ldap-selection-smb] After a file server is added DSPM starts discovering it, and a discovery failure is shown in the Error column. [dspm.service-registration:post-add-discovery] Changes to an on-premises file server take effect only at the next scheduled scan. [dspm.service-registration:edit-timing]

**NFS client.** DSPM supports NFS shares hosted on Linux and Windows servers, using Kerberos for authentication, which requires configuring the Key Distribution Center (KDC). [dspm.service-registration:nfs-support-kerberos] NFS client configuration lists ports 53 TCP/UDP (DNS), 88 TCP/UDP (Kerberos), 111 and 2049 TCP/UDP (NFS portmapper and mount) and 135 TCP (RPC) from the VNet in its ports table. [dspm.service-registration:nfs-ports] On a Linux KDC, a Kerberos principal nfs/<scanner hostname> is created with addprinc -randkey, plus a read-only principal whose credentials are given when registering the file server. [dspm.service-registration:nfs-linux-kdc] On Windows AD, a read-only user is created with uidNumber and gidNumber 1000 and a scanner computer account with uidNumber and gidNumber 0. [dspm.service-registration:nfs-windows-kdc]

**NFS client page.** The ports table also carries rows the page does not explain [gap:dspm.service-registration:nfs-page-unexplained].

**LDAP servers.** An LDAP server lets DSPM discover identities (users, groups, computer accounts) and entitlement data needed to analyze permissions on file shares. [dspm.service-registration:ldap-purpose] The LDAP server type selectable is Active Directory, and a PEM Root CA certificate can optionally be uploaded to verify the server SSL certificate. [dspm.service-registration:ldap-type-cert] A registered LDAP server can be selected when adding an on-premises file server, to analyze entitlements assigned to identities in SMB file shares. [dspm.service-registration:ldap-smb-entitlements] Editing an LDAP server can update the Server Logical Name, the Hostname (IP address or FQDN), the Domain Name, the Username and Password, an optional Root CA Cert PEM file and the associated Data Center. [dspm.service-registration:ldap-edit-fields] In the Edit LDAP Server drawer the Secret Provider Type is autopopulated with the provider that manages authentication secrets, typically Zscaler DSPM. [dspm.service-registration:ldap-secret-provider] Deleting an LDAP server requires entering CONFIRM in the text box of the Delete LDAP Server confirmation window; the server is then deleted from the Zscaler Admin Console. [dspm.service-registration:ldap-delete-confirm]

What to check:
1. Whether the connection test has been run manually for a Snowflake or Databricks service, which the page says DSPM does not run automatically.
2. Whether the file server type and protocol allow the field being filled: Authentication Type is available only for NetApp, and the LDAP server selection only for SMB.
