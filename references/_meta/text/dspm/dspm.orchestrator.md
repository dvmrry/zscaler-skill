# What the DSPM orchestrator and scanner instances are: architecture, sizing, default scanner types, tags and DSPM service IPs (dspm.orchestrator)
Also called: local scanner platform; orchestrator account; dspm scanner instances; orchestrator instance; dspm service ips

The DSPM local scanner platform, called the orchestrator, consists of an orchestrator instance and scanner instances; the orchestrator instance creates the scanner instances, which launch in the regions where DSPM scans resources. [dspm.orchestrator:architecture] The orchestrator account is an account the customer chooses, together with a primary region, to host Zscaler's DSPM orchestrator template; the orchestrator instance is backed by an autoscaler that ensures at least one orchestrator is running. [dspm.orchestrator:orchestrator-account] DSPM supports scanning data stores in all global regions of AWS, Azure and GCP. [dspm.orchestrator:all-regions] [Scans are performed by a local scan orchestrator deployed in the customer's AWS, Azure, GCP or on-premises data center account during onboarding; resources are scanned against a set of standard security policies and a scan schedule, and scan rules select the resources, the scan type and the scan frequency.](kb:dspm.scanning:orchestrator) [Data Security Posture Management (DSPM): what it finds in stored data, how it differs from inline DLP, and what can be automated](kb:dspm.overview)

**Scanner instances.** Scanner instances are launched in the orchestrator account's regions that match the regions of the target data stores, and are terminated when the scan completes; this avoids interregional data transfer costs. [dspm.orchestrator:scanner-regions] DSPM creates transitory scanner instances, up to a maximum of 10 per data store, which the article gives as 16 vCPU and 32 GiB memory each, depending on the number of data stores to scan, and the orchestrator account needs sufficient vCPU quotas. [dspm.orchestrator:scanner-max-instances] The size of a scanner instance is disputed [divergence:dspm.orchestrator:scanner-size]. Scanner instances are created with tags that must not be deleted or tampered with, and inbound access to them is restricted to the orchestrator instance. [dspm.orchestrator:scanner-access-tags] Scanner instances carry the tags z-dspm-resource, z-dspm-scanner-resource, z-dspm-tenant-id, z-dspm-tenant-name and z-dspm-scan-id, which can be enabled in AWS to track DSPM cost allocation. [dspm.orchestrator:scanner-tags]

**Orchestrator instance.** The orchestrator instance carries tags that must not be deleted or tampered with, and its image is Zscaler's property shared with the customer's orchestrator account. [dspm.orchestrator:orchestrator-tags-image] Supported orchestrator instance types: AWS t3.large (20 GB GP3 root, 16 GB GP3 data), Azure Standard_D2s_V3 (30 GB and 10 GB Standard HDD LRS), GCP e2-standard-2 (20 GB and 10 GB standard persistent disk), each with 2 vCPUs and 8 GiB memory. [dspm.orchestrator:orchestrator-instance-types]

**Network access.** The orchestrator instance needs only outbound internet access to DSPM, and its outbound connections to download scanner images and upload results and logs are limited to specific DSPM service IPs. [dspm.orchestrator:outbound-only] DSPM service IPs for the US Cluster are 54.188.198.110, 52.38.65.228, 35.162.237.153, 54.203.244.84, 100.20.13.195 and 44.232.83.106. [dspm.orchestrator:ips-us] DSPM service IPs for the Europe Cluster are 3.78.36.199, 18.153.255.114, 18.193.231.22, 35.157.194.12, 35.159.181.237 and 3.78.50.170. [dspm.orchestrator:ips-eu] DSPM service IPs for the India Cluster are 13.201.160.201, 13.204.227.105, 13.235.175.179, 35.154.135.171, 43.204.164.52 and 65.0.50.177. [dspm.orchestrator:ips-india] [How to set up a custom DSPM network on AWS, Azure and GCP (control plane and worker plane) and change the orchestrator network (AWS and Azure)](kb:dspm.network-configuration)

**Default scanner instances.** Default AWS scanner instances: S3 full c5a.4xlarge and incremental t3.xlarge; EC2 full c6in.4xlarge; RDS full c5a.4xlarge and sampling t3.medium (both with db.r6g.large); DynamoDB full and sampling t3.xlarge; unmanaged database sampling t3.xlarge. [dspm.orchestrator:default-scanners-aws] Default Azure scanner instances: Blob Container and File Share full Standard_F16s_v2 and incremental Standard_D4s_v3; Virtual Machine full Standard_F16s_v2; SQL Server PostgreSQL-Flexible Server full Standard_F16s_v2 and sampling Standard_B2ls_v2; Cosmos DB for NoSQL sampling Standard_B2ls_v2; unmanaged database sampling Standard_D4s_v3. [dspm.orchestrator:default-scanners-azure] Default GCP scanner instances: Cloud Storage Bucket full e2-standard-16 and incremental e2-standard-4; Compute full e2-standard-16; Cloud SQL full e2-standard-16 and sampling e2-standard-2; BigQuery sampling e2-standard-2; unmanaged database sampling e2-medium. [dspm.orchestrator:default-scanners-gcp] Whether e2-medium has 4 vCPUs is open [gap:dspm.orchestrator:e2-medium-specs].

What to check:
1. Which cluster list the DSPM service IPs come from (US, Europe or India) before quoting addresses for the orchestrator to reach.
2. Which default scanner instance type the cloud and data store use, and the scanner maximum, before quoting scanner sizing.

Sources disagree (name both sides):
- What size a scanner instance is: the maximum-instances paragraph gives 16 vCPU and 32 GiB each, while the default scanner tables list 4-vCPU and 2-vCPU types for incremental and sampling scans. [divergence:dspm.orchestrator:scanner-size]
  - zscaler-help: For each data store DSPM creates up to 10 scanner instances, each with 16 vCPU and 32 GiB memory.
  - zscaler-help: The default scanner tables list incremental scanners at 4 vCPUs and 16 GiB (S3 t3.xlarge) and sampling scanners at 2 vCPUs and 4 GiB (RDS t3.medium).
  Impact: Quote 16 vCPU and 32 GiB only as the article's maximum-instances figure; for a given cloud, data store and scan type use the default scanner claims.

Not known (open gaps):
- Whether the GCP unmanaged database scanner e2-medium really has 4 vCPUs and 16 GiB [gap:dspm.orchestrator:e2-medium-specs]: settled by source-read
