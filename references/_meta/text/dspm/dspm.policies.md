# How DSPM data posture policies work: threat categories, custom policy queries, managing policies, and the compliance frameworks that map to them (dspm.policies)
Also called: dspm data posture policies; dspm custom policy; dspm threat categories; dspm compliance frameworks; dspm custom compliance framework; dspm security policies

Data Posture policies are queries or rules DSPM defines to protect cloud resources, and predefined policies are aligned with benchmarks such as NIST, GDPR and PCI. [dspm.policies:policy-definition] DSPM defines these threat categories: Risky Credentials, Public Exposure, Data Loss, Data Governance, Malicious Access and External Users. [dspm.policies:threat-categories] The Policies page's Primary Resource Type column (the type of resource on which the policy is applied) has a list of supported resource types: EC2 Instance, RDS Cluster, RDS Instance, S3 Bucket, SQL Server, Storage Account, Virtual Machine. [dspm.policies:primary-resource-types]

**Managing policies.** Predefined policies cannot be edited, deleted or have their severity changed; custom policies can be edited and deleted, and a policy can be cloned. [dspm.policies:predefined-restrictions] A policy's query can be viewed only for custom policies, and policies that are temporarily hidden cannot be viewed. [dspm.policies:view-policy-query] A predefined or custom policy can be cloned by reusing its query structure; policies that are temporarily hidden cannot be cloned. [dspm.policies:clone-policy] The Managing Policies page says disabled policies generate no new alerts, and existing alerts keep their status. [dspm.policies:disable-policy] Deleting a custom policy closes all alerts it generated. [dspm.policies:delete-custom-policy] The Managing Policies page says editing a custom policy's title or remediation procedure updates the information shown on the Alerts page and dashboard, while editing its query logic closes all existing alerts and generates new ones. [dspm.policies:edit-custom-policy] Changing a policy's severity affects the risk level of alerts triggered by its findings. [dspm.policies:change-severity]

How the alert status page reads a disabled or edited policy is in [How DSPM alerts work: risk level, statuses, snooze and resolve, alert details, and the alert rules and ignore alert filters that act on them](kb:dspm.alerts).

**Custom policies.** Custom security policies can be added for resources that already have predefined policies or for resources that have none. [dspm.policies:custom-policy-purpose] A custom policy needs a name and a severity (Critical, High, Medium or Low, a static value); the description, threat category and MITRE ATT&CK technique are optional, and the remediation procedure is entered in Markdown. [dspm.policies:custom-policy-fields] Primary resources are the main data stores DSPM scans for sensitive data; investigation queries and custom policies can identify the secondary resources and entities with access to them. [dspm.policies:primary-resource-definition] The query builder offers predicates and operators in several categories, and the combination of predicates and operators is specific to each primary resource. [dspm.policies:predicate-categories] Multiple values can be selected with the Like (%), Not Like !(%), iLike (i%) and Not iLike !(i%) operators. [dspm.policies:multi-value-operators]

**Predicates.** The Has Data predicate checks whether a resource contains sensitive data, document types and categories, matching DLP engines and dictionaries, and the volume of sensitive data. [dspm.policies:has-data-predicate] The Has Vulnerability predicate takes a CVE ID as defined in the National Vulnerability Database (NVD) and a Fix Available flag that is true when a fix is available per the NVD. [dspm.policies:has-vulnerability-predicate] The Has Malware predicate states that malware is detected in AWS S3 buckets, Azure virtual machines and storage accounts, and GCP storage buckets. [dspm.policies:malware-detection-scope] The Has Models predicate is available only for AI-related resource types such as AWS Bedrock, Azure AI Foundry and Vertex AI resources, and its LLM Safety Risk takes CRITICAL, HIGH, MEDIUM or LOW. [dspm.policies:ai-predicates] Posture predicates include Guardrails (checked for an AWS Bedrock Agent), Exposed to AI service (true when exposed to an AI service such as Azure AI Foundry) and, with no cloud named in their rows, Is Dormant (checks whether the user has logged in over the last 90 days) and Stale Access Keys (checks whether the access keys were rotated in the last 90 days). [dspm.policies:posture-predicates-notable] Which predicate tables belong to which cloud is open [gap:dspm.policies:posture-tables]. Which resource types policies cover is open [gap:dspm.policies:resource-type-lists].

**Compliance.** DSPM supports many compliance frameworks across categories such as cybersecurity health, finance, data protection, CIS and AI benchmarks. [dspm.policies:supported-frameworks-categories] The supported compliance frameworks table lists these frameworks: CIS Controls v8.1; GDPR; HIPAA; NIST SP 800-53 Rev. 5; PCI DSS 4.0.1; AICPA SOC 2; CCPA; DPDP Act, 2023; CSA CCM v4; CJIS Security Policy v6; CRI Profile v2.0; CMMC v2.0; FFIEC-CAT May 2017; ISACA - COBIT 19; ISO/IEC 27001:2022; NYDFS - 23 NYCRR Part 500; NZISM v3.8; NIST CSF 2.0; NERC-CIP Standards; UK NCSC - CAF v.3.2; UK NCSC Cyber Essentials v3.2; NIST SP 800-171 Rev. 3; CISA CPG v1.0.1; NIST AI 600-1; ASD Essential Eight; TSA Security Directive Pipeline 2021-02; HPH CPGs; DORA; HITRUST CSF v11.5.0; RBI CSF; SEBI CSCRF; NIS2 Directive; EU AI ACT. [dspm.policies:supported-frameworks-list] A mapped policy that is disabled is excluded from compliance calculations but still counted in a framework's total policies; a deleted mapped policy is removed from the framework, and in the page's example deleting 2 of 100 policies leaves a total of 98. [dspm.policies:compliance-counts] Failed policies are not calculated for a disabled framework, and clicking one opens its Configuration tab with the Summary, Policies and Resources tabs disabled. [dspm.policies:disabled-framework] On a framework's detail page, the Summary shows the mapped DLP engines, the number of noncompliant data stores and a failed-compliance trend selectable over the last 7, 15, 30, 60 or 90 days. [dspm.policies:summary-tab] On the compliance detail tabs, search and Excel export do not apply to the Summary tab. [dspm.policies:detail-search-export]

**Custom frameworks.** A custom framework is created either by cloning a predefined framework (only its policies are copied) or from scratch; it has categories with control numbers, maps each policy to a category and control number, needs at least one DLP engine, and is enabled by default. [dspm.policies:custom-framework-build] Limits on custom frameworks are open [gap:dspm.policies:compliance-limits].

What to check:
1. Whether the policy is predefined or custom: predefined policies cannot be edited, deleted or have their severity changed, and the query is viewable only for custom policies.
2. What happens to existing alerts when a policy is disabled, deleted or has its query logic edited; the DSPM pages disagree on disabling and editing.
3. Whether a framework is disabled, or a mapped policy is disabled or deleted, before reading its compliance counts.
