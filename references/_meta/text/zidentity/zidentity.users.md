# Authentication Service users: where they come from, status, bulk actions and admin-side actions (zidentity.users)
Also called: ZIdentity users; Authentication Service users; user source; SCIM user; JIT user; deactivate user; disable user ZIdentity; skip MFA for user; reset user password ZIdentity; bulk delete users

The Authentication Service user directory is shared by every subscribed service. Users are added to Authentication Service either by creating them locally in it or through an external identity provider. [zidentity.users:created-locally-or-idp]

**Where a user came from.** A user record's source says how it was created: UI (created or managed via a user interface), API (created or managed through API calls), SCIM (provisioned via SCIM) or JIT (created or updated via Just-in-Time). [zidentity.users:source-values] Whether the idp field and the source track each other, and whether a source can change, is open [gap:zidentity.users:source-and-idp]. Provisioning by JIT and SCIM, and what IdP removals do to users, is in [Getting users into and out of Authentication Service: JIT, SCIM, and what IdP removals do to admins](kb:zidentity.users.provisioning). Whether a SCIM-provisioned user can be edited here without the IdP undoing it is open [gap:zidentity.users:scim-user-mutation]; the group question is [Whether SCIM-provisioned groups can be changed in Authentication Service](kb:zidentity.groups:scim-group-mutation).

**What a user can be given.** Admin and service entitlements: [A user can be given admin entitlements, which make them an administrator of a Zscaler service such as ZIA or ZPA, or service entitlements, which let them authenticate to a Zscaler service as an end user.](kb:zidentity.entitlements:two-kinds). A user can be assigned to one or several Zscaler services, and managing users in Authentication Service replaces keeping a separate user database in each subscribed service. [zidentity.users:assign-services] Group membership, and the per-user group limit on which help pages differ: [The About User Groups page says a user can be in up to 1,000 groups. Each service needs a matching limit; where a service's per-user limit is lower, it counts the user's group assignments only up to that limit (the help's example: a user in 500 groups on a Private Access subscription for 128 groups per user has only the first 128 assignments considered there).](kb:zidentity.groups:membership-limit).

**Adding one in the console.** A user's login ID consists of a username and a domain name in email format, where the username must be unique and its domain must belong to the organization. [zidentity.users:login-id-format] If a user's login ID has a guest domain, authentication for that user is not managed by Zscaler, and the password option remains disabled on the Security Settings tab. [zidentity.users:guest-domain-user] Adding a user in the console takes a status (enable or disable), primary and secondary email addresses, first and last names (from which the Display Name is built), a Department (a system-defined attribute), a manager and additional attributes already created in Authentication Service by admins. [zidentity.users:profile-fields] Super admin privileges come from group membership: [To give users super admin privileges for Authentication Service and all the services linked to it, the help says to add them to the Zscaler Global Administrators group.](kb:zidentity.groups:global-admins-super-admin). The password option and skipping second-factor authentication are in [A user's security settings in Authentication Service: initial password option, skipping second-factor authentication and MFA authenticators](kb:zidentity.users.security-settings).

**Active or inactive.** A user is Active or Inactive and is activated or deactivated from the console; in the API the status is a boolean, true for active and false for disabled. [zidentity.users:status]

**Attributes and SCIM.** The user attributes a profile can carry are in [User and session attributes in Authentication Service: system-defined sets, custom attributes, device-attribute values and where each is used](kb:zidentity.attributes), and the SCIM server that provisions them is in [The Authentication Service SCIM server: operations, attribute mapping, authentication and rate limits](kb:zidentity.users.provisioning.scim).

**The dashboard.** The user dashboard (Administration > Authentication > Overview) gives a view of all users managed from Authentication Service, their authentication status and user management activities, over a selected duration of 1 to 90 days. [zidentity.users:dashboard] The dashboard counts Total Users (managed from Authentication Service), IdP Users (registered and guest users accessing a Zscaler service through Authentication Service) and Hosted Users (registered and guest users hosted on Authentication Service), split into registered domain users, whose login IDs use the organization's registered domain, and guest domain users. [zidentity.users:dashboard-user-counts] The Service Entitlements widget counts users assigned to each Zscaler service and is visible only when service entitlement is enabled for the tenant. [zidentity.users:dashboard-service-entitlements] The dashboard shows the authentication status (Success or Failure) of hosted and external IdP users, graphing the users who logged in to the Admin Console with each authentication method with the date and time of the attempt; External IdP applies only to Zscaler services not migrated to Experience Center. [zidentity.users:dashboard-auth-status] The dashboard shows statistics for successful and for failed user management activities (Created, Updated and Deleted) by date and time. [zidentity.users:dashboard-user-management] Retention beyond 90 days and any export are open [gap:zidentity.users:dashboard-retention].

**Guest domains.** Guest domains let third-party (guest) users access the Zscaler service; they can be assigned only to guest users who do not use Client Connector for authentication, and those guest users cannot be given administrative entitlements. [zidentity.users:guest-domains] Arbitrary Guest Domains, optional, lets third-party users authenticate with any domain even if it is not in the guest domain list, and is supported only with Privileged Remote Access (PRA). [zidentity.users:arbitrary-guest-domains] After adding guest domains, the third-party users are added to the Admin Console and the guest domains are added to the required IdP so those users can authenticate with SSO. [zidentity.users:guest-domains-next] How many guest domains can be listed is open [gap:zidentity.users:guest-domain-limit].

**Departments.** Departments can define an administrator's scope, giving the admin control over a set of users in a department; an administrator can belong to only one department. [zidentity.users:departments-admin-scope] A department has a name and an optional description of up to 10,240 characters, and a user can belong to only one department. [zidentity.users:departments] Up to 1,000 departments can be imported by CSV, and the sample template is also used to add many users to an existing department or change the department of many users; Override Existing Entries replaces the existing department list with the file's. [zidentity.users:departments-csv] Which product's admin scope a department applies to, and how it relates to ZIA departments, is open [gap:zidentity.users:department-scope].

**Bulk work in the console.** The Users page imports new users or modifies existing ones from a CSV file, resets the password of several selected users at once, and activates, deactivates or deletes several selected users in one bulk action. [zidentity.users:console-bulk] The help says up to 1,000 users can be imported at one time by CSV file, from a template downloaded with Download Sample in the Import User drawer; the header row is retained, the file name has a .csv extension, each user is on a separate line with an email domain defined in the portal, and in the Action column + adds a user (Primary Email, Login Name, First Name and Last Name filled in) and - deletes one (Login Name filled in). [zidentity.users:csv-import-format] In the CSV the Secondary Email can specify any domain but must be a valid email address; if the authentication method is a one-time token or one-time link the Primary Email must be a valid email address; and a Password Reset value of True emails the user to set their password while False does not send the email. [zidentity.users:csv-email-and-password] Override Existing Entries is selected to update existing user details, delete users or add new users, and is not selected to only add new users; without it, adding a user who already exists shows an error message stating that identical users cannot be imported. [zidentity.users:csv-override] The Experience Center onboarding Upload CSV template's header row is Action, Login Name, Display Name, First Name, Last Name, Primary Email, Secondary Email, Language, Department, Timezone, Password Reset and Group Names; a - row needs only the Login Name of the user being deleted. [zidentity.users:onboarding-csv-header] Whether the Import User drawer's CSV can assign groups, and its full column set, are open [gap:zidentity.users:csv-columns].

**Creating one through the API.** Creating a user through the API requires `loginName`, `displayName`, `primaryEmail` and `status`; the create request has no `id` field, which appears in the response. [zidentity.users:create-fields] So the service assigns the user's ID when the user is created. [zidentity.users:id-assigned] What the service does with a caller-supplied ID is open [gap:zidentity.users:caller-id].

**Admin-side actions.** Besides create, read, update and delete, the API can initiate a password reset for a user, set a flag to skip MFA for a user (the request carries a timestamp of when the skip was set), and set a user's password, optionally requiring the user to reset it at the next login. [zidentity.users:user-actions] Which clients wrap these actions is in [Which clients cover which parts of the ZIdentity API: Python, Go and the MCP server](kb:zidentity.api.client-coverage).

Endpoint, filter and SDK details are in the generated surface (`node scripts/kb.mjs surface zid`) and in [Which clients cover which parts of the ZIdentity API: Python, Go and the MCP server](kb:zidentity.api.client-coverage).
