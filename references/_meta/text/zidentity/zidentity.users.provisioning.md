# Getting users into and out of Authentication Service: JIT, SCIM, and what IdP removals do to admins (zidentity.users.provisioning)
Also called: ZIdentity SCIM; ZIdentity JIT; just-in-time provisioning; SCIM vs JIT; SCIM deprovisioning admin; admin removed from IdP group; user sync lag ZIdentity; user not in policy dropdown; users not syncing from idp

This covers how users arrive from an external IdP and what removals in the IdP do to them. Authentication Service synchronizes users with identity providers automatically through SAML just-in-time (JIT) provisioning or SCIM provisioning. [zidentity.users.provisioning:jit-or-scim]

**Which to use.** Zscaler recommends SCIM over JIT provisioning: SCIM synchronizes identities proactively through APIs at scheduled or on-demand intervals, while JIT updates identities reactively from the attributes received during login. [zidentity.users.provisioning:scim-recommended] So a user provisioned only by JIT is created or updated when they log in, and does not exist in Authentication Service before their first login; SCIM is the path that puts users there ahead of login and removes them without one. [zidentity.users.provisioning:jit-reactive]

**JIT in the IdP form.** With JIT Provisioning enabled on an OIDC or SAML IdP, users not yet provisioned are provisioned automatically when they first try to access Authentication Service, the user database being created in real time from the OP's response (OIDC) or the SAML assertion with user information; if the option is disabled, unprovisioned users are denied access until they are configured in the Zscaler Admin Console. [zidentity.users.provisioning:jit-first-access] JIT provisioning for primary IdPs does not support provisioning or updating system-defined groups such as Zscaler Global Administrators. [zidentity.users.provisioning:jit-no-system-groups] The PingOne guide says users created in Authentication Service through SCIM cannot be updated through JIT provisioning and their records must be updated through SCIM provisioning only. [zidentity.users.provisioning:scim-users-not-updated-by-jit] Whether secondary IdPs provision system-defined groups is open [gap:zidentity.users.provisioning:jit-secondary-groups].

**JIT attribute mapping.** JIT takes a JIT user group attribute from the IdP and maps JIT attributes from the IdP to user attributes in Authentication Service; the SAML page lists First Name, Last Name, Primary Email, Login Name and Display Name among its default attributes. [zidentity.users.provisioning:jit-mapping] The Auth0 guide says mapping the Primary Email attribute is mandatory because password resetting and multi-factor authentication need it. [zidentity.users.provisioning:primary-email-mandatory] The OneLogin guide says that if the external IdP sends different attributes for First Name, Last Name or Display Name those attributes must be mapped, and the Auth0 guide says the attributes entered in the Just-in-time Attribute field must match exactly the attributes received in the ID tokens. [zidentity.users.provisioning:attribute-names-exact] The Auth0 guide's OIDC attribute table maps First Name from given_name, Last Name from family_name and Display Name from name by default, lists nickname, phone_number, email, locale and zoneinfo against Nick Name, Mobile Phone, Primary Email, Language and Timezone, says Department, Organization, Title, Division, Cost Center, User Type, Formatted Name and Manager need a custom claim, and says Manager must be in email address format. [zidentity.users.provisioning:default-oidc-claims] The AD FS guide's SAML attribute table maps First Name from firstName, Last Name from lastName and Display Name from displayName by default, and lists mobile or telephoneNumber, email or mail, locale or preferredLanguage, timezone, department, organization or company, title, division, costCenter, userType or employeeType, formattedName and manager for Mobile Phone, Primary Email, Language, Timezone, Department, Organization, Title, Division, Cost Center, User Type, Formatted Name and Manager, with Manager in email address format. [zidentity.users.provisioning:default-saml-attributes] What the SAML default attribute Name means is open [gap:zidentity.users.provisioning:saml-name-attribute].

**SCIM in the IdP form.** Enabling SCIM Provisioning on an IdP gives a SCIM Endpoint URL, the base URL of the SCIM server needed when configuring SCIM-based provisioning with the external IdP, which appears only if the IdP's Basic tab configuration is completed and saved; the authentication options are Bearer Token and Oauth 2 Client Credentials. [zidentity.users.provisioning:scim-endpoint-and-auth] The SCIM bearer token is a unique alphanumeric string the SCIM client uses to make authenticated API calls to the Zscaler SCIM server; a new one can be generated for security reasons, and for an existing SCIM configuration the token must be updated in the IdP. [zidentity.users.provisioning:scim-bearer-token] Who may see the token differs between pages [divergence:zidentity.users.provisioning:bearer-token-visibility]. With Oauth 2 Client Credentials the console's Token Endpoint URL appears only when the external identity configuration is saved, and the client secret's expiration date can be customized with the Expires On drop-down menu. [zidentity.users.provisioning:scim-client-credentials] The Auth0 guide says the Addresses attribute in Authentication Service is supported only with SCIM provisioning, and the PingOne guide says the SCIM attribute mapping is required only for attributes that need to be mapped to a custom user attribute in Authentication Service. [zidentity.users.provisioning:addresses-scim-only] Vendor-specific SCIM settings are in [Per-IdP integration specifics for Authentication Service: Okta, Microsoft Entra ID, AD FS, PingOne, PingFederate, Auth0 and OneLogin](kb:zidentity.overview.external-idps.integrations). The SCIM server itself, with its operations, attribute mapping and rate limits, is in [The Authentication Service SCIM server: operations, attribute mapping, authentication and rate limits](kb:zidentity.users.provisioning.scim).

**JIT through a device token.** Authentication Service manages device token authentication for Client Connector: device tokens created in Client Connector are passed to Authentication Service to be authenticated for registered domains, so the token is created in Client Connector first. [zidentity.users.provisioning:device-token-auth] The device token setting authenticates either all registered domains or only the selected domains (the Domains choice appears only when all domains is off), and Enable for JIT Provisioning enrolls users into Authentication Service automatically. [zidentity.users.provisioning:device-token-domains-jit] With device tokens, users need not be tied to the organization's standard IdP to authenticate to Client Connector: where the organization uses SAML-based SSO, Authentication Service can use a device token to auto-provision and silently authenticate users and devices. [zidentity.users.provisioning:device-token-saml-sso] With JIT provisioning on, the device-token user is created in Authentication Service as <name-of-machine>@<domain> as defined at installation (the page's example: machine Alice and domain example.com give alice@example.com), and must be assigned the service entitlement for the login to succeed. [zidentity.users.provisioning:device-token-user] Instead of entitling each device-token user, the Dynamic Group Registered Domains group, which holds all users of the tenant's registered domains, can be assigned the service entitlement, so all its users get it automatically. [zidentity.users.provisioning:device-token-dynamic-group] To use Authentication Service as the users' IdP, the device token copied from Client Connector, the user domain and the cloud name are passed to users' devices during installation; the page points to install options for Windows MSI and EXE, macOS, and Android and iOS through MDM. [zidentity.users.provisioning:device-token-install] Whether device-token users count as hosted or IdP users on the dashboard is open [gap:zidentity.users.provisioning:device-token-dashboard].

**When an IdP is removed.** Users and groups of the primary IdP stay, those of a secondary IdP do not: [Users and groups from the primary IdP are kept in Authentication Service if the primary IdP is removed, to ease moving the primary IdP to another provider; users and groups from a secondary IdP are not kept when that IdP is removed.](kb:zidentity.overview.external-idps:idp-removal-retention).

## When the IdP removes an admin

The help's table covers removal of an admin group in the external IdP, for a user in both an admin group and a user group that are assigned to Authentication Service in the IdP, and splits the outcome by Authentication Service for Admins versus for Admins and Users. [zidentity.users.provisioning:scim-scope]

- **Deactivate or disable.** When the IdP sends a SCIM deactivate or disable request (the help's examples are Entra ID and Okta): with Authentication Service for Admins, the admin is deactivated in Authentication Service but stays enabled in ZIA admin and user management, and in ZPA is disabled in admin management only, so their internet and private-application access is not cut; with Authentication Service for Admins and Users, the admin is disabled in both admin and user management in ZIA and ZPA. [zidentity.users.provisioning:scim-deactivate]
- **Delete.** When the IdP sends a SCIM delete request (the help's example is Ping Identity): with Authentication Service for Admins, all administrative entitlements to all services are removed for the group's users; with Authentication Service for Admins and Users, the admin is deleted in Authentication Service and from ZIA and ZPA admin management but stays enabled in their user management. [zidentity.users.provisioning:scim-delete]

**Reaching the products.** How long a provisioning or deprovisioning change in Authentication Service takes to show in ZIA and ZPA is open [gap:zidentity.users.provisioning:propagation]; ZPA's own SCIM timing is in [When SCIM data is ready for ZPA policy](kb:zpa.scim.provisioning-timing).

What to check:
1. Whether the user exists yet: a JIT-only user appears after their first login.
2. For an admin removed in the IdP, whether the IdP sent a deactivate or a delete, and whether the tenant uses Authentication Service for admins only or for admins and users; with admins only and a deactivate, ZIA and ZPA user access stays enabled.
3. Whether the change has had time to reach the product before concluding it failed.

  Impact: Trusting the IdP pages, an agent says a View Only admin cannot see the token; trusting the matrix, it says they can. The matrix does not name the token for View Only, so the two may be reconcilable, but no page says so.
