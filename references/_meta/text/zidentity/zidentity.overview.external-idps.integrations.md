# Per-IdP integration specifics for Authentication Service: Okta, Microsoft Entra ID, AD FS, PingOne, PingFederate, Auth0 and OneLogin (zidentity.overview.external-idps.integrations)
Also called: Okta with Authentication Service; Entra ID with Authentication Service; AD FS with Authentication Service; PingOne with Authentication Service; PingFederate with Authentication Service; Auth0 with Authentication Service; OneLogin with Authentication Service; Okta OIN app; Entra Gallery app; cloud_displayname; acceptMappedClaims

The per-IdP fields every guide shares are in [Configuring an external IdP in Authentication Service: domains, login ID attribute, OIDC and SAML fields, admin MFA enforcement, signing certificates and IdP-initiated sign-in](kb:zidentity.overview.external-idps.configuration); this subject holds what each vendor's guide says differently. The provisioning attribute tables are in [Getting users into and out of Authentication Service: JIT, SCIM, and what IdP removals do to admins](kb:zidentity.users.provisioning).

**Okta, which app.** The Okta guide's decision table chooses by protocol and by whether Private Access policies use custom session attributes: OIDC without them takes a single OIDC OIN app with built-in SCIM provisioning; the next row, whose protocol cell is blank and whose first cell reads only "Yes", takes with SCIM a custom OIDC app for authentication plus an OIN app for SCIM and without SCIM a single custom OIDC app with JIT (the row's text names OIDC apps); SAML with them takes with SCIM a custom SAML app plus an OIN app for SCIM and without SCIM a single custom SAML app with JIT. [zidentity.overview.external-idps.integrations:okta-app-choice] Zscaler recommends the Okta OIN-based integration, which uses SCIM-based provisioning and needs a SCIM provisioning subscription for Okta; if the Okta subscription does not include SCIM provisioning, Zscaler recommends the custom OIDC application because Okta does not support sending custom claims such as Groups or Departments with the OIN application. The guide's Supported Features sections list JIT Provisioning and SP-Initiated SSO under OIDC and Create Users, Update User Attributes, Deactivate Users and Group Push under SCIM. [zidentity.overview.external-idps.integrations:okta-oin-recommended] Okta does not support SCIM provisioning for custom OIDC applications, and for SCIM with Okta Zscaler recommends a SAML app integration; a tenant that uses Private Access policies with custom session attributes and prefers SCIM can create an OIN app for SCIM provisioning in addition to the custom Okta app for authentication. [zidentity.overview.external-idps.integrations:okta-custom-oidc-no-scim]

**Okta, settings.** After the OIN-based integration is set up, Authentication Service administrators can log in to the Zscaler Admin Console using Okta at `https://customername.zslogin.net/` and, if the username is valid, are redirected to the Okta page for authentication. [zidentity.overview.external-idps.integrations:okta-oin-login] For the Okta OIN app's SCIM provisioning the guide has the admin select Enable API integration, paste the bearer token into the API Token field and enable Create Users, Update Users to Attributes and Deactivate Users; for the SCIM connection it has Unique identifier field for users set to userName, the Push New Users and Push Groups provisioning actions, and HTTP Header as the authentication mode. [zidentity.overview.external-idps.integrations:okta-scim-settings] For the Okta custom OIDC app the guide has the grant type set to Authorization Code and the Enable immediate access with Federation Broker Mode option disabled, a custom authorization server's Audience set to api://zscaler, and the claim name created for group retrieval (i.e., Groups) entered as the Just-in-time User Group Attribute. [zidentity.overview.external-idps.integrations:okta-custom-app-values] Authentication Service requires the Manager attribute in email address format; in Okta the Manager attribute is the manager's display name and ManagerId is the manager's username, so the guide has the manager's email address mapped to the ManagerId profile attribute. [zidentity.overview.external-idps.integrations:okta-manager-attribute] Mapping the Okta custom profile user attributes with the custom profile app attributes is necessary to use custom session attributes in Private Access policies. [zidentity.overview.external-idps.integrations:okta-session-attributes]

**Entra ID, apps and SCIM.** The Entra ID guide says the provisioning mode (JIT or SCIM) determines the number of apps in Entra ID, one for JIT and two for SCIM; for OIDC apps via the Microsoft Entra App Gallery only JIT provisioning is supported, and SCIM with OIDC needs a custom Entra ID app for SCIM in addition to the Gallery app for authentication. [zidentity.overview.external-idps.integrations:entra-app-count] On the Entra ID OIDC path, when migrating from an existing custom app-based SCIM configuration, selecting OAuth2 Client Credentials as the Authentication Method warns that the configuration would be overwritten, and on Confirm the existing SCIM configurations, including the current bearer token, are discarded and synchronization with Entra ID is interrupted temporarily. The Token Endpoint field is visible only after saving once the client secret is generated; Zscaler recommends scheduling provisioning in a maintenance window because the initial synchronization might take several hours and could cause service disruption, and says users must not be changed in Entra ID or they are duplicated in Authentication Service. If migrating from an existing custom app-based SCIM configuration, users and groups must be assigned app-based roles and customizations such as SCIM transformations must be replicated in the new application. [zidentity.overview.external-idps.integrations:entra-scim-oidc] The Entra ID SCIM attribute mappings map user userName from userPrincipalName (matching), active from a Switch expression on IsSoftDeleted, displayName, emails[type eq "work"].value from mail, name.givenName from givenName, name.familyName from surname, externalid from objectId and the enterprise extension's department; group displayName (matching), externalId from objectId and members. [zidentity.overview.external-idps.integrations:entra-scim-mappings] In the guide's SAML-based section, the SCIM setup selects Automatic as the Provisioning Mode and enters the bearer token as the Secret Token; it also offers failure email notification, an optional accidental-deletion threshold above which deleting groups and users needs admin approval, and an optional scope of Sync only assigned users and groups, which Zscaler recommends. [zidentity.overview.external-idps.integrations:entra-scim-settings] Whether the Gallery app now carries SCIM is open [gap:zidentity.overview.external-idps.integrations:entra-gallery-scim].

**Entra ID, OIDC and SAML.** For Entra ID over OIDC the guide selects the email and preferred_username claims for the ID token, the Groups assigned to the application option, and Group ID for groups because Entra ID does not support sending group names with OIDC when groups are created in the Entra cloud (sAMAccountName instead when group names arrive via Entra ID sync); it modifies the manifest to include cloud_displayname so group names are sent instead of IDs, sets acceptMappedClaims to true (to accept custom claims such as department and title) and requestedAccessTokenVersion to 2, and enters groups as the Just-in-time User Group Attribute with Primary Email mapped to the email JIT attribute. [zidentity.overview.external-idps.integrations:entra-oidc-claims] The Entra ID guide has the admin click Grant admin consent for the Entra ID tenant, which it says is required so end users do not get the prompt to accept the grant at login; the saved configuration takes a few hours to take effect, and the Client ID is the Application (Client) ID and the Client Secret the Value from the Client secrets tab. [zidentity.overview.external-idps.integrations:entra-app-registration] For Entra ID over SAML the guide leaves the Namespace empty for additional attributes (Department from user.department, emailaddress from user.mail, givenname, name from user.userprincipalname and surname), uses Cloud-only group display names as the group source attribute, renames the certificate file to .pem, selects Sign SAML response and assertion with SHA-256, and, for IdP-initiated SSO, disables Require verification certificates. [zidentity.overview.external-idps.integrations:entra-saml]

**Entra ID, step-up.** For step-up with Entra ID the guide selects an authentication context ID from C1 to C99 with Publish to apps enabled, each authentication context corresponding to an ACR value in the Zscaler Admin Console; the Conditional Access grant is Grant access with Require multifactor authentication, the Authentication Context ID is entered for each level under Levels to Authentication context mapping, and the highest level is mapped to the context ID for the strongest context. [zidentity.overview.external-idps.integrations:entra-step-up-contexts]

**AD FS.** For AD FS over OIDC the well-known URL format is `https://<host>/adfs/.well-known/openid-configuration`; the client ID starts as a random value and is overridden with the actual client ID created in the AD FS Management Console; the application uses the Server application template with permitted scopes allatclaims, email, openid and profile and the LDAP Attributes as Claims claim rule template; and the relying party trust identifier is `https://<adfs_endpoint>/adfs/services/trust`, where the AD FS endpoint is publicly resolvable with a valid certificate signed by a trusted CA. [zidentity.overview.external-idps.integrations:adfs-oidc] For AD FS over SAML the typical federation metadata path is /FederationMetadata/2007-06/FederationMetadata.xml, uploaded through Upload Metadata; the console's SP Metadata is downloaded and imported as a relying party from a file with SAML Request Signing enabled; custom user attributes such as Department must already be configured in the Zscaler Admin Console before mapping; and the claim rule template is Send LDAP Attributes as Claims. [zidentity.overview.external-idps.integrations:adfs-saml]

**PingOne.** The PingOne guide covers PingOne as the OpenID Provider (OP) for Authentication Service; the PingOne application type is OIDC Web App, with email and Profile selected as allowed scopes. [zidentity.overview.external-idps.integrations:pingone-oidc] For PingOne SCIM the guide selects Identity Store as the connection type and the SCIM Outbound app; with a bearer token it is pasted into the Oauth Access token field, with client credentials the console's Token Endpoint, Client ID and Client Secret go to Oauth Token Request, Oauth Client ID and Oauth Client Secret, and switching from the bearer token method to client credentials requires removing the bearer token configurations in PingOne first. [zidentity.overview.external-idps.integrations:pingone-scim] In a PingOne provisioning rule the user filter can be configured with conditions, for example filtering users by specific Group Names, the groups to be provisioned for Authentication Service are selected, and group overwriting is confirmed for the matching groups. [zidentity.overview.external-idps.integrations:pingone-provisioning-rule] The PingOne guide's example maps the name attribute in Authentication Service by combining the Given Name and Family Name attributes in PingOne. [zidentity.overview.external-idps.integrations:pingone-name-expression] For PingOne step-up the authentication policy's Policy Name is the ACR value mapped to the authentication level in the Zscaler Admin Console, with step type Multi-Factor Authentication, an MFA Policy and a Required When condition (the guide's examples: always, last sign-on older than 1 hour); the user is prompted with all options configured in the MFA step, and the highest level is mapped to the ACR value for the strongest context. [zidentity.overview.external-idps.integrations:pingone-step-up]

**PingFederate.** The PingFederate guide's page-level Prerequisites, "Ensure that you have configured:", list a datastore, an LDAP connection for the datastore to the directory server, a password credential validator, an IdP adapter, a policy contract, an authentication policy, an access token management instance, an OpenID connect policy and access token mappings. [zidentity.overview.external-idps.integrations:pingfed-oidc-prereqs] For PingFederate over OIDC the well-known URL format is `https://<host>/.well-known/openid-configuration`; the client ID starts as a random value generated later in the PingFederate Admin Console; the client uses Client Secret authentication, Bypass for authorization approval, the Authorization Code grant and a chosen default access token manager; email, profile and openid are added as common scopes; and groups is the JIT User Group Attribute from IdP with Primary Email mapped to the email JIT attribute. [zidentity.overview.external-idps.integrations:pingfed-oidc-client] PingFederate provisioning uses an Outbound Provisioning connection of type SCIM Connector, and the SCIM Provisioner must be installed if that option is not available; the target is SCIM Version 2.0 with OAuth 2 Bearer Token authentication, Max Threads is set to 1 and Timeout (Secs) to 60, userName is mapped to userPrincipalName, the Email attribute mapping is mandatory, objectGUID is added as a binary attribute on the LDAP Binary Attributes tab, and the Synchronization Frequency can be customized on the Outbound Provisioning tab. [zidentity.overview.external-idps.integrations:pingfed-scim-channel] For PingFederate over SAML a random IdP Metadata URL is entered for generating SP Metadata in the Zscaler Admin Console and is later replaced; the connection uses the Browser SSO Profiles template with SAML 2.0, IdP-Initiated and SP-Initiated SSO, the POST method only, an attribute contract whose values must match the values on the Zscaler Admin Console, and optionally an encryption policy for the entire assertion. [zidentity.overview.external-idps.integrations:pingfed-saml]

**Auth0 and OneLogin.** The Auth0 guide covers Auth0 as the OpenID Provider (OP); the application type is Regular Web Application, the Input Method is Metadata URL with the OpenID Configuration value from the Auth0 Dashboard, the token authentication method is Client Secret Basic, and the console's Redirect URI is pasted into the Application Login URI and Allowed Callback URLs fields. [zidentity.overview.external-idps.integrations:auth0-oidc] The OneLogin guide covers OneLogin as the OpenID Provider (OP), using the OpenID Connect (OIDC) app found by searching the Find Applications window for oidc; the Metadata URL is the Issuer URL copied from the Well-known configuration link, and the console's Redirect URI is pasted into the app's Redirect URI's field. [zidentity.overview.external-idps.integrations:onelogin-oidc]

**Coverage.** Which protocol and provisioning mode each guide documents, against the table of supported IdPs, is open [gap:zidentity.overview.external-idps.integrations:guide-coverage].

What to check:
1. For Okta, whether the tenant needs custom session attributes in Private Access policies and whether it has SCIM, since those choose between the OIN app, a custom app and a second app.
2. For Entra ID, whether the tenant wants JIT (one app) or SCIM (two apps), and, before switching a custom-app SCIM configuration to OAuth2 Client Credentials, that doing so discards the current bearer token.
3. For a missing group name or manager in the JIT mapping, the vendor's group and manager attribute form.

Not known (open gaps):
- Whether the Entra ID Gallery app carries SCIM through OAuth2 client credentials [gap:zidentity.overview.external-idps.integrations:entra-gallery-scim]: settled by lab-test or support-ticket. Blocks: telling a tenant whether SCIM needs the second custom Entra ID app
- Which protocol and provisioning each vendor guide documents [gap:zidentity.overview.external-idps.integrations:guide-coverage]: settled by source-read. Blocks: telling a tenant that SCIM or SAML is documented for a given vendor
