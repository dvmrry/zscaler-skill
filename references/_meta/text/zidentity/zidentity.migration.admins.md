# How Zscaler admins are migrated to Authentication Service, and the automatic upgrade to the Zscaler Admin Console (zidentity.migration.admins)
Also called: Migrating Zscaler Service Admins to Authentication Service; admin migration; Automatic Upgrade to Zscaler Admin Console; break-glass super admin

Authentication Service migration includes customer-driven migration: customers that authenticate their Zscaler administrators with an external IdP can request it, by contacting their Zscaler Account team to provision an Authentication Service tenant linked to all their Zscaler tenants. [zidentity.migration.admins:customer-driven] End user migration follows admin migration: [How end users are migrated to Authentication Service: eligibility, prerequisites, the wizard's audits, test users and rollback](kb:zidentity.migration.end-users).

**Process.** Zscaler emails the customer to specify the service tenants to link and the new Authentication Service super admin's name and email ID, then provisions the Authentication Service tenant and links the customer's service tenants. [zidentity.migration.admins:zscaler-email-and-provision] The new Authentication Service super admin follows the registration email's instructions, connects the external IdP and provisions admins, has the other admins test Authentication Service from their IdP tile, and, once all admins confirm access, uses the link in the Zscaler Admin Console banner to proceed with the admin migration. [zidentity.migration.admins:super-admin-steps] The Zscaler service tiles are disabled until the migration is completed; if admins do not see the assigned tiles, the super admin can review entitlements on the Entitlements tab in the Authentication Service Admin Portal and adjust them on the Administrative Entitlements page. [zidentity.migration.admins:tiles-disabled] With admin migration, administrator data and role assignments are transferred from the Zscaler services and synced to Authentication Service, and admins can access all service admin portals with a single set of credentials. [zidentity.migration.admins:admin-data-transfer]

**Rollout.** The help says Authentication Service has been provisioned for all new customers since January 2024, existing customers began upgrading in June 2024, and the majority of customers are upgraded. [zidentity.migration.admins:rollout-timeline]

**Roles.** Administrator roles for Authentication Service and some Zscaler services are managed on a different Role Management page for an organization that uses Unified RBAC, a feature in limited availability available by contacting the Zscaler Account team. [zidentity.migration.admins:unified-rbac-roles] Admin roles are in [Authentication Service admin roles: predefined and custom roles, and how they relate to product roles](kb:zidentity.admin-rbac).

**Break-glass account.** Authentication Service creates a default super admin account for tenant recoverability that cannot be deleted or disabled and is intended only for emergency (break-glass) use; named admin accounts are for daily operations. [zidentity.migration.admins:break-glass-super-admin]

**MFA.** All administrators must use MFA, either Zscaler's MFA or MFA enforced at the external IdP, or both; administrators hosted in Authentication Service must use Zscaler's MFA because they do not use SSO with an external IdP. [zidentity.migration.admins:admin-mfa-required] After migration, admins with credentials hosted at Zscaler must use MFA for admin login, with the supported MFA options including security key or biometric, Google Authenticator, and email OTP. [zidentity.migration.admins:admin-mfa-options] The factors are in [Authentication Service authentication methods: MFA and FIDO2 setup, admin MFA registration and skip, and the password policy](kb:zidentity.authentication-methods); the MFA enrollment timing differs from [An admin can skip MFA for a grace period of 7 days, after which MFA must be configured in Authentication Service; admins using MFA through their external IdP can disable the Enforce Zscaler Admin MFA option to prevent additional authentication verification from Authentication Service.](kb:zidentity.authentication-methods:skip-mfa-grace) [divergence:zidentity.migration.admins:mfa-enrollment-timing].

**Logging in.** Admins can log in through any of the Internet & SaaS, Private Access, ZDX, Branch Connector, Cloud Connector or Deception admin portals after entering their login ID, and on first login after migration the Internet & SaaS or Private Access admin's password stored in that portal is synced to the Authentication Service Admin Portal, which then validates it. [zidentity.migration.admins:login-two-step-portals] The page lists ways for admins to authenticate after migration, including the Zscaler tile at the external IdP (for example Okta) and the Zscaler-assigned vanity domain (for example https://acme.zslogin.net), and recommends using a vanity domain for simplicity. [zidentity.migration.admins:login-paths] In both the external IdP login path and the Authentication Service vanity domain login path, the Authentication Service page can be accessed only if someone from the service tenant accepts the EUSA. [zidentity.migration.admins:eusa-access]

**Passwords and API authentication.** When Cloud & Branch Connector attempts to authenticate to the Internet & SaaS admin API and Internet & SaaS is linked to Authentication Service, Internet & SaaS attempts to validate the credentials with Authentication Service, which succeeds if it has a hosted user with that username and password. [zidentity.migration.admins:api-auth-flow] Authentication Service does not support users with both IdP mapping and passwords, but Internet & SaaS passwords are still synced even when the user's domain is mapped to an IdP, retaining some password-managed functions; the page recommends that customers with users holding both a password and an IdP mapping migrate away from that configuration, and says those customers must make necessary changes to use user identities under a vanity domain that cannot be mapped against an IdP. [zidentity.migration.admins:password-and-idp-mapping] For admins originally synced from Internet & SaaS or Cloud & Branch Connector where an admin API authentication attempt used their old passwords, Authentication Service requests the local password from that service and copies it to validate current and subsequent API authentication calls, and enables changing passwords for admins even if their login ID domain is mapped to an external IdP. [zidentity.migration.admins:password-copy-from-downstream] Admins synced through external IdPs can change their password from My Profile in the Authentication Service Admin Portal, and admins with the Users and Groups permission can change it by editing the user entry; if Authentication Service holds no local password from an API authentication event, this is not supported. [zidentity.migration.admins:password-change-paths] Password management for users and admins synced via external IdPs works only when the identities were synced from downstream services (for example Cloud & Branch Connector), and is not supported for identities provisioned from external IdPs via SCIM or JIT provisioning. [zidentity.migration.admins:password-mgmt-scim-jit]

**Force sync.** For existing customers, identities might not sync if removed from Authentication Service during migration, which needs a support ticket to force sync the users from the downstream service; the scenario is Authentication Service in the provisioned state, an IdP configured for it, a user deleted manually from the Authentication Service Admin Portal, and admin migration completed with the Zscaler services. [zidentity.migration.admins:force-sync-ticket]

**Automatic upgrade.** The help says that starting September 6, 2026 some organizations are scheduled for an automatic upgrade to the Zscaler Admin Console, and Zscaler emails the organization's admin accounts the schedule. [zidentity.migration.admins:auto-upgrade-schedule] Organizations can do a self-managed upgrade ahead of the scheduled date (recommended; contact the Zscaler Account team) or take no action, in which case Zscaler performs the upgrade automatically on the scheduled date. [zidentity.migration.admins:auto-upgrade-options] End-user authentication and access to Internet & SaaS and Private Access are stated to be uninterrupted throughout the automatic upgrade. [zidentity.migration.admins:auto-upgrade-end-users] After the automatic upgrade, admin access via the external IdP to the legacy service admin portals is discontinued, admins are directed only to the Zscaler Admin Console and registered as hosted admins on Authentication Service (which "can be removed when you reconfigure the IdP"), and the IdP must be reconfigured in the Authentication Service tenant. [zidentity.migration.admins:auto-upgrade-idp] After the automatic upgrade all admins must enroll in Zscaler MFA at initial login to the Zscaler Admin Console, as a one-time requirement. [zidentity.migration.admins:auto-upgrade-mfa] If Internet & SaaS API authentication is configured in the legacy Authentication Service Admin Portal (the page's wording), the same password must be used at first login after the automatic upgrade, because creating a new password loses access to the legacy APIs; without Internet & SaaS API authentication a new password can be created. [zidentity.migration.admins:auto-upgrade-api-password] After the automatic upgrade: if the IdP is configured in Authentication Service and the admin starts an IdP-initiated login from Authentication Service, the admin goes to the IdP and then MFA; if the password is already configured in Authentication Service and the login starts from the Internet & SaaS or Private Access tile in the IdP, the admin goes to the Zscaler Admin Console login page and logs in with the password, then MFA; if neither an IdP nor a password is set up and the login starts from the Internet & SaaS or Private Access tile in the IdP, the admin logs in with the existing Internet & SaaS or Private Access password (which is migrated) or creates a new password. [zidentity.migration.admins:auto-upgrade-redirects] What admins must do after the upgrade differs from [Upgrading to Experience Center requires administrative users who have already migrated to Authentication Service, for a centralized identity experience to access ZIA, ZPA, Digital Experience (ZDX), Client Connector and other Admin Portals; admins take no further action and, on receiving the migration notification, log in to the Zscaler Admin Console with their existing Authentication Service credentials; the page also tells the organization to migrate its end users to Authentication Service.](kb:unified.admin-console.sign-in:upgrade-prerequisites) [divergence:zidentity.migration.admins:upgrade-admin-action]. The legacy service admin portals are not defined [gap:zidentity.migration.admins:legacy-portals-undefined].

**Console names.** What the Authentication Service Admin Portal, the Zscaler Admin Console and the legacy Authentication Service Admin Portal each refer to is open [gap:zidentity.migration.admins:admin-portal-names]. What happens to API clients, Terraform or SDK-driven identities during admin migration is open [gap:zidentity.migration.admins:api-identities-during-migration].

Sources disagree (name both sides):
- The automatic upgrade page has admins reconfigure the IdP and enroll in MFA, while the Experience Center upgrade page has already-migrated admins take no further action. [divergence:zidentity.migration.admins:upgrade-admin-action]
  - zscaler-help: After the automatic upgrade admins must reconfigure the IdP in the new Authentication Service tenant and enroll in Zscaler MFA at initial access.
  - zscaler-help: Admins who have already migrated to Authentication Service take no further action and log in with their existing credentials.
  Impact: An admin cannot tell from the pages whether they must reconfigure the IdP and enroll in MFA; the pages may address admins in different states, which neither says.
- The admin migration pages require MFA enrollment at initial access, while the Multi-Factor Authentication page lets an admin skip MFA for 7 days and lets IdP-MFA admins disable Enforce Zscaler Admin MFA. [divergence:zidentity.migration.admins:mfa-enrollment-timing]
  - zscaler-help: Admins must enroll in Zscaler MFA during the initial login after the automatic upgrade.
  - zscaler-help: An admin can skip MFA for 7 days, and admins using MFA through their external IdP can disable the Enforce Zscaler Admin MFA option.
  Impact: Whether an admin can reach the Zscaler Admin Console before enrolling in Zscaler MFA is not settled by the pages; the migration pages' enrollment requirement and the 7-day skip cannot both apply at initial access.
