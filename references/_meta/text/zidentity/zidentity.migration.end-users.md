# How end users are migrated to Authentication Service: eligibility, prerequisites, the wizard's audits, test users and rollback (zidentity.migration.end-users)
Also called: Migrating End Users to Authentication Service; end user migration; migrate end users to ZIdentity; test users; pilot users; end user migration rollback

Customers who have already completed admin migration can migrate their end users, after Zscaler Support enables the tenant for end user migration. [zidentity.migration.end-users:eligibility] The Private Access guidelines for the same migration are in [The Private Access guidelines for end user migration to Authentication Service: test users, SCIM, policies, backup and restore, and rollback](kb:zidentity.migration.end-users.private-access), and migrating admins is in [How Zscaler admins are migrated to Authentication Service, and the automatic upgrade to the Zscaler Admin Console](kb:zidentity.migration.admins).

**Not eligible, not supported, and the Okta and emergency-domain conditions.** Privileged Remote Access (PRA) or emergency access users are not eligible for end user migration; they are synced with Authentication Service after migration completes and must reauthenticate as hosted users or guest users with the external IdP, depending on the organization's configuration. [zidentity.migration.end-users:pra-emergency-users] The allowlisted domains for Private Access emergency access are synchronized as Authentication Service guest domains. [zidentity.migration.end-users:emergency-domains] The Deception landmine client is not supported for end user migration. [zidentity.migration.end-users:deception-landmine] Okta customers must use the Okta Integration Network (OIN) Zscaler App; customers that previously set up an Okta integration using any other service need to change to it; the page states that Okta's group membership provisioning over SCIM using a custom app results in incomplete group memberships. [zidentity.migration.end-users:okta-oin-app]

**What users get.** After end user migration users can enroll into Zscaler services with one set of credentials, and Authentication Service for users also enables step-up authentication and the Adaptive Access Engine; the page says the stronger-safeguards benefit (enforce MFA at Zscaler) is applicable only for hosted users (created in Authentication Service). [zidentity.migration.end-users:benefits-mfa-hosted-only]

**Client Connector versions.** The end user migration page says migration does not disrupt users and they need not log out and in again to Client Connector during or after migration, provided the supported Client Connector versions are used: Windows 4.8 or later, macOS 4.8 or later, Android 4.1 or later, iOS 4.4.4 or later, and Linux 3.7.2 or later. [zidentity.migration.end-users:cc-versions-no-relogin] The Linux minimum differs between the migration pages [divergence:zidentity.migration.end-users:linux-minimum-version]. Whether users must reauthenticate after migration differs between the pages [divergence:zidentity.migration.end-users:reauth-after-migration].

**Prerequisites.** Before end user migration, all IdPs configured in Zscaler services like Internet & SaaS, Private Access, etc. must be the same IdPs that are used by admins and be configured in the exact same way in Authentication Service, and the same domains mapped to the external IdP in Internet & SaaS and Private Access must be mapped to the IdP in Authentication Service. [zidentity.migration.end-users:prereq-idps] Before end user migration, SCIM groups used in policies must be configured in Authentication Service, all end user and group data must be provisioned there, and if SAML attributes are used in policies those attributes must be configured in Authentication Service; end user systems must run the required Client Connector versions. [zidentity.migration.end-users:prereq-groups-attrs-users] The page gives the reason for correlating groups: if a group is not correlated on Authentication Service, users in the group might be blocked because the group does not exist there; its example is an Internet & SaaS policy defined for certain groups. [zidentity.migration.end-users:prereq-why-group-correlation] In the page's Private Access policy case, a user attribute or session attribute was previously referred to as SCIM attribute and SAML attribute respectively. [zidentity.migration.end-users:attribute-renames]

**The wizard.** An admin with the Super Admin role completes the end user migration wizard, starting from the link in the email that the organization is set up for end user migration, sent from no-reply@zscaler.com with the subject line "Authentication Service End User Migration." [zidentity.migration.end-users:wizard-super-admin-email] The first three audits (IdPs, groups, user attributes) must each be completed successfully before the wizard moves on to review service entitlements; the next step is allowed only after the IdPs, the groups and the user attributes match. [zidentity.migration.end-users:wizard-audits-gate] In the IdP audit, the default IdP in Internet & SaaS must be mapped to the primary IdP in Authentication Service so groups can be mapped without issues. [zidentity.migration.end-users:audit-default-idp-primary] In the page's example where Internet & SaaS has two domains mapped and Authentication Service has one, the admin can add the missing domain to the IdP in Authentication Service, remove it from the IdP in Internet & SaaS, or select it in the Skipped Domains drop-down menu. [zidentity.migration.end-users:audit-domain-mismatch-example] The user attribute audit covers user attributes and, for Private Access, session attributes; to match attributes the admin defines the attribute in the Advanced section of the Edit External Identity page and removes the attribute from the Internet & SaaS or Private Access policy rule if it is no longer used. [zidentity.migration.end-users:audit-session-attributes] The Skipped Domains drop-down and the Session Attributes Audit link are not defined [gap:zidentity.migration.end-users:audit-terms-undefined].

**Entitlements.** The End User Entitlement page is visible only when end user migration is enabled for the tenant; entitlements must be assigned manually the first time, and Zscaler recommends assigning service entitlements to groups. [zidentity.migration.end-users:entitlements-manual-first-time] Zscaler might not have complete information on users historically assigned to services because some users are assigned directly to Internet & SaaS or Private Access at the external IdP, and the page says admins must review the service entitlement assignments in Authentication Service. [zidentity.migration.end-users:entitlements-incomplete-history] For Client Connector users the admin syncs enrolled services by creating a group per service named "Migrated [service] Service Entitlements - [cloud-orgid]" (for example "Migrated Internet Access Service Entitlements - zscalertwo.com-123987456") and, on the Service Entitlements page, assigning user groups to the service; users who do not use Client Connector are first assigned to the corresponding service. [zidentity.migration.end-users:entitlement-group-naming]

**Test users.** A minimum of one and a maximum of 1,000 test users can be selected; the next step becomes available 24 hours after the test users are migrated (the Next button is disabled until then), and only 1000 test users can be migrated before the remaining users are migrated by the end user migration. [zidentity.migration.end-users:test-users-limits] Before selecting test users, the user details must be provisioned from the external IdP to Authentication Service using SCIM; test users should be assigned the right service entitlement, and Zscaler recommends (but does not require) that they log out and in to confirm enrollment. [zidentity.migration.end-users:test-users-prereq-scim] For Private Access test users, only existing users from the external IdP can be selected, at least one test user is required before full migration, and Private Access emergency access users cannot be selected. [zidentity.migration.end-users:test-users-pa-rules] Group mappings for pilot users must exactly match the existing groups in the external IdP; if there is a group mismatch, the pilot users cannot be migrated even if Authentication Service allows it. [zidentity.migration.end-users:test-users-pilot-group-mapping] Migrated test users are not changed again at complete migration; once test user migration has started, new changes to device tokens, device groups and service entitlements in Client Connector are not synced with Authentication Service. [zidentity.migration.end-users:test-users-after-migrate] What the 24-hour wait gates beyond the disabled Next button is open [gap:zidentity.migration.end-users:test-user-wait-gates].

**Complete migration.** The page says to make sure the policy audits do not have any errors before migration, and that the migration process can take several minutes or hours to complete. [zidentity.migration.end-users:complete-migration-duration] What happens to API clients, Terraform or SDK-driven identities during the migration is open [gap:zidentity.migration.end-users:api-identities-during-migration].

**Rollback.** Rollback after end user migration is requested through Zscaler Support and is allowed only for 14 days after migration; it reverts users to the existing external IdP and restores their pre-migration state. [zidentity.migration.end-users:rollback-window] After a rollback, if users and groups changed on the external IdP the admin must sync them again before re-initiating end user migration, and a 24-hour wait applies before re-initiating. [zidentity.migration.end-users:rollback-resync-wait] The sync requirement differs from the Private Access page [divergence:zidentity.migration.end-users:rollback-sync-requirement], which also has Adaptive Access and Step-Up Authentication configurations deleted for rollback eligibility: [To be eligible for rollback after complete migration, configurations of Authentication Service-specific features (Adaptive Access and Step-Up Authentication) must be deleted, because rollback is unsupported when they are used after migration without clearing them; policies associated with Authentication Service must be removed before reattempting migration, and a complete IdP sync is required after migration or rollback.](kb:zidentity.migration.end-users.private-access:rollback-requirements).

What to check:
1. Which Client Connector versions the end user machines run, against the minimums the migration pages list.
2. Whether the rollback window after migration has passed, and whether 24 hours have passed since a rollback before re-initiating.

Sources disagree (name both sides):
- The two end user migration pages give different minimum Linux Client Connector versions. [divergence:zidentity.migration.end-users:linux-minimum-version]
  - zscaler-help: Linux 3.7.2 or later, as the supported Client Connector version for end user migration.
  - zscaler-help: Linux 4.2.1 or later, as the version end users' machines must run before migration.
  Impact: A Linux Client Connector between 3.7.2 and 4.2.1 meets one page's minimum and not the other's; neither page says which applies when both do.
- The end user migration page says users need not log out and in again, while the Private Access page forces all users and devices to reauthenticate after 7 days and has Client Connector trigger a mandatory reauthentication period for test users. [divergence:zidentity.migration.end-users:reauth-after-migration]
  - zscaler-help: Users are not required to log out and in again to Client Connector during or after end user migration, on the supported versions.
  - zscaler-help: After migration all users and devices are forced to reauthenticate at a staggered period after 7 days, and test users face a mandatory reauthentication period.
  Impact: Whether Private Access users reauthenticate after migration is not settled; the pages may mean a manual log out and in against a forced reauthentication, which neither says.
- The end user migration page requires a re-sync after rollback only if users or groups changed on the external IdP, while the Private Access page requires a complete IdP sync after migration or rollback. [divergence:zidentity.migration.end-users:rollback-sync-requirement]
  - zscaler-help: Users and groups must be synced again only if they changed on the external IdP.
  - zscaler-help: A complete IdP sync is required after migration or rollback.
  Impact: An admin of a Private Access tenant cannot tell whether a sync is needed when nothing changed on the IdP.
