# What ZIdentity (Authentication Service) is, and where each part of it is covered (zidentity.overview)
Also called: ZIdentity; Authentication Service; Zscaler Authentication Service; ZID; ZIAM; Zscaler identity platform; single login across Zscaler services; ZIdentity MFA; Experience Center login; ZIdentity vanity domain; zidentity audit logs; authentication service audit logs; migrate to zidentity; mfa methods

This walks what Authentication Service does for the other Zscaler products and points to the subject for each part. ZIdentity has been renamed Authentication Service. [zidentity.overview:renamed]

**What it is.** Authentication Service is a unified identity and authentication service that centralizes identity management, user authentication and entitlement assignment for users to Zscaler services such as Internet & SaaS (ZIA) and Private Access (ZPA); the services are managed in the Zscaler Admin Console. [zidentity.overview:unified-service] Users log in once with a single authentication and reach the Zscaler services their organization uses; an organization subscribed to more than one service, or to one service for several organizations, reaches them with a single set of login credentials. [zidentity.overview:single-login] Users can be enrolled to the subscribed Zscaler services from the Authentication Service user database, instead of creating a separate user database in each service. [zidentity.overview:user-database]

**Admin controls.** Its listed features include controlling admin roles and access to Zscaler services, limiting administrator access by source IP address so that admins access it from authorized locations, and audit reports of configuration changes in Authentication Service. [zidentity.overview:admin-controls] Its own admin roles are in [Authentication Service admin roles: predefined and custom roles, and how they relate to product roles](kb:zidentity.admin-rbac), and who administers which product is decided by entitlements, in [Administrative and service entitlements: who administers and who may use each Zscaler service](kb:zidentity.entitlements). Its audit log is a permission module of its own, [Authentication Service has an Audit Logs permission module whose levels are View Only (view audit logs) and None.](kb:shared.audit-logs:zidentity-audit-module), with no API: [No audit log endpoint is documented for Authentication Service: its API specification has no audit path and neither SDK has an audit client for it.](kb:shared.audit-logs:zid-no-audit-api); what it records and how it streams are in [Authentication Service audit logs and log streaming: what is recorded, record fields, filters and export, and NSS streaming](kb:zidentity.audit-logs). Source-IP limits on admins are the sign-on policy in [Admin sign-on policy: allow/deny rules, exemptions, limits, and the trusted IP locations and location groups they match on](kb:zidentity.sign-on-policy), and session timeouts are in [Authentication Service sessions: admin inactivity timeout, the service-enrollment session and forced Private Access reauthentication](kb:zidentity.authentication-session).

**Authentication factors.** Authentication Service supports MFA and requires it by default, and Zscaler strongly recommends enabling it; users can authenticate with a password, or with a password and a second factor such as Google Authenticator (TOTP) or FIDO. [zidentity.overview:mfa-default] Whether admin MFA is on is shown per IdP: [The External Identities page shows, for the primary IdP and for each secondary IdP, whether Authentication Service MFA is enabled or disabled for admins.](kb:zidentity.overview.external-idps:admin-mfa-per-idp). The MFA and FIDO2 setup and the password policy are in [Authentication Service authentication methods: MFA and FIDO2 setup, admin MFA registration and skip, and the password policy](kb:zidentity.authentication-methods). Whether SMS is also a factor is open [gap:zidentity.overview:otp-factors].

**Users, groups and IdPs.** Users: [Authentication Service users: where they come from, status, bulk actions and admin-side actions](kb:zidentity.users), and how they are provisioned: [Getting users into and out of Authentication Service: JIT, SCIM, and what IdP removals do to admins](kb:zidentity.users.provisioning). Groups: [Authentication Service user groups: predefined and custom groups, dynamic groups, membership and limits](kb:zidentity.groups). External OIDC and SAML IdPs: [External IdPs in Authentication Service: OIDC and SAML, primary and secondary, limits and retention](kb:zidentity.overview.external-idps). User and session attributes: [User and session attributes in Authentication Service: system-defined sets, custom attributes, device-attribute values and where each is used](kb:zidentity.attributes). The SCIM server: [The Authentication Service SCIM server: operations, attribute mapping, authentication and rate limits](kb:zidentity.users.provisioning.scim).

**Token validators.** JWT claim and signature checks for access to a Zscaler service, with Internet & SaaS as the page's example, are in [Token validators: JWT claim and signature checks for access to a Zscaler service (the page's example is Internet & SaaS), and the Test Token decoder](kb:zidentity.token-validators).

**Linked Services.** The Linked Services page (Administration > Subscription > Linked Services) shows the organization's subscribed Zscaler service tenants, each with its product, tenant ID, cloud name, organization name, Authentication Service migration status and whether it is linked or unlinked from Authentication Service. [zidentity.overview:linked-services-page] The Authentication Service copy of the Linked Services page says that if a tenant is unlinked, the users under that tenant cannot access the Zscaler service through Authentication Service. [zidentity.overview:unlinked-tenant-no-access] The Linked Services page in the Zscaler Admin Console help (help.zscaler.com/unified) says that if a tenant is unlinked, the users under that tenant cannot access the Zscaler Admin Console. [zidentity.overview:unlinked-tenant-no-console-access] The Linked Services page in the Zscaler Admin Console help (help.zscaler.com/unified) places it at Administration > Account Management > Linked Services, describes the Authentication Service Migration Status column as whether the tenant has been migrated fully to Authentication Service and the Status column as whether the tenant is linked or unlinked, and lets the page be refreshed to sync any new data. [zidentity.overview:linked-services-experience-center] The copies differ in what they name as lost, and give different menu paths [divergence:zidentity.overview:linked-services-path]. The values of the migration status column are open [gap:zidentity.overview:migration-status-values].

**Step-up.** ZIA and ZPA policy can demand a stronger authentication level through it: [Step-up authentication: when Authentication Service asks for a stronger login, and why a prompt may not appear](kb:zidentity.step-up).

**OneAPI.** It is the authorization server for OneAPI: [OneAPI uses the OAuth 2.0 Client Credentials flow, with Authentication Service, Zscaler's unified identity platform, as the authorization server: a client exchanges its credentials at the token endpoint for an access token, with no user authentication involved.](kb:shared.oneapi.authentication:client-credentials-flow). So the vanity domain enters only the token endpoint's host (`<vanity>.zslogin.net` in production); the OneAPI gateway host (`api.zsapi.net` in production) does not carry it. [zidentity.overview:vanity-token-host-only] Hosts by cloud, government clouds included, are in [OneAPI hosts and per-product base paths](kb:shared.oneapi.base-urls) and [Reaching OneAPI on government (FedRAMP) and non-production clouds](kb:shared.oneapi.government-clouds).

**Its own API.** The Authentication Service API and API clients are covered in [The ZIdentity (Authentication Service) admin API from a client's side: route, coverage and wire notes](kb:zidentity.api) and [ZIdentity API clients: what one is, how it authenticates, its resources and scopes, and its token lifetime](kb:zidentity.api-clients).

**Setup.** The configuration guide recommends these Client Connector versions for new Authentication Service deployments: Windows 4.8, macOS 4.8, iOS 4.4.4, Android 4.1 and Linux 4.2.1. [zidentity.overview:setup-cc-versions] Domains are automatically synced from Internet & SaaS and Private Access every 24 hours, and the Domains page is at Administration > Authentication > Domains. [zidentity.overview:setup-domains-sync] The configuration guide says the Authentication Methods page has an optional Allow FIDO2 as Primary Authenticator option (to allow admins to use FIDO as the primary authenticator without the password requirement) and an optional Multi-Factor Authentication (MFA) for Service Enrollment option (prompts users for MFA enrollment during authentication); all admins including the super admin must enroll an MFA authenticator after first setting a password. [zidentity.overview:setup-hosted-user-options] The configuration guide lists optional steps: authentication session controls (such as the administrator's Idle Session Timeout, Authentication Session for Service Enrollment, and Force Authentication for Private Access Reauthentication), updating the password policy, and Admin Sign-On policies, which are created using IP locations or IP location groups. [zidentity.overview:setup-optional-controls] The configuration guide says that to configure step-up authentication with external IdPs the necessary authentication levels must be configured in Authentication Service and access policies in supported Zscaler services, users must have Authentication Service access, and Authentication Service with User Single Sign-On (SSO) is required to enable step-up authentication for the tenant. [zidentity.overview:setup-step-up-prereqs] The FIDO and service enrollment options for users are in [With Allow FIDO2 as Primary Authenticator enabled, users can skip the password and configure any FIDO2 method available on their device at their next login, for a passwordless Authentication Service account.](kb:zidentity.authentication-methods:fido2-primary) and [Enable Multi-Factor Authentication (MFA) for Service Enrollment, on the Authentication Methods page, is shown only when the user single sign-on (SSO) feature is enabled for the tenant, and can be disabled for users.](kb:zidentity.authentication-methods:mfa-for-service-enrollment), step-up in [Step-up authentication: when Authentication Service asks for a stronger login, and why a prompt may not appear](kb:zidentity.step-up), and the MFA enrollment timing differs from [An admin can skip MFA for a grace period of 7 days, after which MFA must be configured in Authentication Service; admins using MFA through their external IdP can disable the Enforce Zscaler Admin MFA option to prevent additional authentication verification from Authentication Service.](kb:zidentity.authentication-methods:skip-mfa-grace) [zidentity.migration.admins:mfa-enrollment-timing](kb:zidentity.migration.admins:mfa-enrollment-timing).

**Migration.** Admin migration and the automatic upgrade to the Zscaler Admin Console are in [How Zscaler admins are migrated to Authentication Service, and the automatic upgrade to the Zscaler Admin Console](kb:zidentity.migration.admins). End user migration is in [How end users are migrated to Authentication Service: eligibility, prerequisites, the wizard's audits, test users and rollback](kb:zidentity.migration.end-users), with the Private Access guidelines in [The Private Access guidelines for end user migration to Authentication Service: test users, SCIM, policies, backup and restore, and rollback](kb:zidentity.migration.end-users.private-access).

**Which logins go through it.** Which admin and end-user logins go through Authentication Service on a given tenant is open [gap:zidentity.overview:auth-path-coverage].

What to check:
1. Whether MFA is still required for admins on each IdP, since it is on by default and can be turned off.
2. For a OneAPI client that cannot get a token, whether the vanity domain is set to the organization's own subdomain and not to the API gateway host.
3. Whether the tenant (admins, end users or both) has actually moved to Authentication Service before reasoning from it.
