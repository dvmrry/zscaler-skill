# The Private Access guidelines for end user migration to Authentication Service: test users, SCIM, policies, backup and restore, and rollback (zidentity.migration.end-users.private-access)
Also called: Migrating Private Access End Users to Authentication Service; Private Access end user migration; ZPA migration to ZIdentity

The Private Access migration page lists the Client Connector versions end user machines must run before migration: Windows 4.8 or later, macOS 4.8 or later, Android 4.1 or later, iOS 4.4.4 or later, and Linux 4.2.1 or later. [zidentity.migration.end-users.private-access:cc-versions] The general end user migration is in [How end users are migrated to Authentication Service: eligibility, prerequisites, the wizard's audits, test users and rollback](kb:zidentity.migration.end-users), with the Linux minimum in [zidentity.migration.end-users:linux-minimum-version](kb:zidentity.migration.end-users:linux-minimum-version), reauthentication in [zidentity.migration.end-users:reauth-after-migration](kb:zidentity.migration.end-users:reauth-after-migration) and the rollback sync in [zidentity.migration.end-users:rollback-sync-requirement](kb:zidentity.migration.end-users:rollback-sync-requirement); moving a Private Access IdP is in [Migrating Private Access to a new IdP](kb:zpa.authentication.idp-migration).

**Test users.** During test user migration, test users appear under the Authentication Service IdP instead of the external IdP, and authentication for them is handled by Authentication Service; only existing users from the external IdP can be designated. [zidentity.migration.end-users.private-access:test-users-identity] For test users, SCIM profile assignment fails for users associated with any Private Access application; SCIM group mappings must match the existing external IdP groups or they prevent migration eligibility; and test users migrated from Okta are not displayed through SCIM group mappings. [zidentity.migration.end-users.private-access:test-users-scim] During test user migration, any new IdP added in the Zscaler Admin Console must first be configured in Authentication Service, and all existing IdPs, including disabled ones, must be configured in Authentication Service. [zidentity.migration.end-users.private-access:test-users-idps] Zscaler Client Connector triggers a mandatory reauthentication period for test users based on the configured timeout policy. [zidentity.migration.end-users.private-access:test-users-reauth] During test user migration, policies referencing the Authentication Service IdP cannot be created; the Authentication Service IdP is visible in the IdP drop-down on the Access Policy page but cannot be edited; policies for external IdPs remain valid and usable. [zidentity.migration.end-users.private-access:test-policies] Customers using Private Access Partner Logins are ineligible for test user migration. [zidentity.migration.end-users.private-access:partner-logins] At least one user must be designated as a test user before a complete migration is initiated. [zidentity.migration.end-users.private-access:one-test-user-required]

**Complete migration.** Policy creation, IdP configuration and SCIM sync updates are restricted during complete migration or rollback; after a successful migration the external IdP and its attributes cannot be edited and new rules cannot use external IdPs, and the Authentication Service IdP and its attributes can be changed only in Authentication Service. [zidentity.migration.end-users.private-access:complete-migration-restrictions] After complete migration only Authentication Service-specific policies can be created and policies referencing an external IdP are unsupported; a rollback does not cover policies created or updated after migration, which are deleted manually by filtering them on the Access Policy page. [zidentity.migration.end-users.private-access:post-migration-policies] After migration certain Zscaler Admin Console pages are read only, and labels for certain pages and fields are updated to Authentication Service terminology. [zidentity.migration.end-users.private-access:console-read-only] All users must be assigned to Private Access services in Authentication Service to avoid session termination; after migration all users and devices are forced to reauthenticate at a staggered period after 7 days; new users created during migration are logged out if a rollback occurs and must log in again. [zidentity.migration.end-users.private-access:session-and-reauth] What the staggered period after 7 days means in hours is open [gap:zidentity.migration.end-users.private-access:staggered-period-hours].

**SCIM.** After migration, SCIM Sync requests from external IdPs to Private Access are blocked, so users or groups provisioned via SCIM fail with errors such as HTTP 429 (Too Many Requests), and existing SCIM applications enter an error state; a forced sync is required if a rollback occurs. [zidentity.migration.end-users.private-access:scim-sync-blocked] In the page's Complete Migration section on user identity and SCIM behavior for Private Access SCIM applications, Zscaler recommends stopping SCIM sync or provisioning from the IdP before starting the migration process to avoid sync errors, token regeneration and unnecessary operational overhead. [zidentity.migration.end-users.private-access:stop-scim-before] Each IdP (Okta, Azure AD, Ping given as examples) has different retry mechanisms and thresholds on SCIM errors like HTTP 429; for Okta a new SCIM authentication token must be generated after SCIM provisioning is disabled; admins might need to remove and reassign users or groups to the Private Access SCIM application or provision impacted objects manually if SCIM sync errors continue to occur. [zidentity.migration.end-users.private-access:scim-caveats] The SCIM server and its setup are in [Enabling SCIM for Private Access: endpoint, token, policy setting and IdP guides](kb:zpa.scim.setup); the SCIM provisioning to Authentication Service needed before selecting test users is in [Before selecting test users, the user details must be provisioned from the external IdP to Authentication Service using SCIM; test users should be assigned the right service entitlement, and Zscaler recommends (but does not require) that they log out and in to confirm enrollment.](kb:zidentity.migration.end-users:test-users-prereq-scim).

**Backup and restore.** Backup and restore is supported between systems in the same migration stage (not started, test user migration, or completed); restoring a backup from a system that has not started migration onto one that has completed it, or a backup from a system with an incomplete rollback onto one that completed rollback after complete migration, leads to data inconsistencies and is unsupported. [zidentity.migration.end-users.private-access:backup-restore]

**Rollback.** To be eligible for rollback after complete migration, configurations of Authentication Service-specific features (Adaptive Access and Step-Up Authentication) must be deleted, because rollback is unsupported when they are used after migration without clearing them; policies associated with Authentication Service must be removed before reattempting migration, and a complete IdP sync is required after migration or rollback. [zidentity.migration.end-users.private-access:rollback-requirements] After a successful rollback the external IdP and its attributes can be edited but new rules cannot use Authentication Service; users synced from new IdPs added in Authentication Service appear as ZID IDP users on the IdP Configuration page and are deleted after rollback; users assigned the Authentication Service application at the external IdP must be assigned the Private Access application to complete the rollback. [zidentity.migration.end-users.private-access:rollback-caveats] Starting a new migration is not possible if Authentication Service-associated policies are still present after a successful rollback. [zidentity.migration.end-users.private-access:new-migration-blocked]
