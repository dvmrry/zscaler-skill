# The Authentication Service SCIM server: operations, attribute mapping, authentication and rate limits (zidentity.users.provisioning.scim)
Also called: Authentication Service SCIM server; ZIdentity SCIM server; SCIM API Examples; scim_externalid

This is the SCIM server Authentication Service exposes to an IdP, as against the IdP-side form in [Getting users into and out of Authentication Service: JIT, SCIM, and what IdP removals do to admins](kb:zidentity.users.provisioning). Authentication Service SCIM provisions users and groups, updates a user's group and department to follow the user directory, and deprovisions users deleted from the directory, through one of the IdPs partnered with Zscaler (the page links the Okta, Entra ID, AD FS and PingOne guides). [zidentity.users.provisioning.scim:uses] When SCIM creates a user, the domain in the username must already be registered with Authentication Service (the page's example: test@zscalerexample.com needs zscalerexample.com registered with the tenant). [zidentity.users.provisioning.scim:domain-preregistered]

**Operations.** On /Users the SCIM server supports POST to create, GET for all users (up to 100 entries), GET with startIndex and count=1000 for 1,000 users from an index, GET by user ID, filters on userName eq and externalID eq, PUT or PATCH to update and DELETE. [zidentity.users.provisioning.scim:user-operations] On /Groups it supports POST, GET for all groups (up to 1,000 entries), GET with startIndex for 1,000 groups from an index, GET by group ID, a filter on displayName eq and members.value eq, PUT or PATCH and DELETE. [zidentity.users.provisioning.scim:group-operations] The server also supports POST /Bulk, GET /Schemas and /Schemas/{SchemaID}, GET /ServiceProviderConfig, GET /ResourceTypes and /ResourceTypes/{ResourceTypeID}, and POST on [prefix]/.search. [zidentity.users.provisioning.scim:other-endpoints] The filter operators, bulk limits and how PATCH is handled beyond these tables are open [gap:zidentity.users.provisioning.scim:filters-and-bulk].

**Attributes.** The Understanding SCIM page maps system-defined user attributes to SCIM as, among others: Display Name to displayName and Primary Email to emails[type eq "work"].value (both mandatory), Login ID to userName, STATUS to active, Secondary Email to `Emails[type eq “home”].value` (so spelled), Department to the enterprise extension's department, and Manager to the enterprise extension's manager.value (the manager's user ID). [zidentity.users.provisioning.scim:system-attribute-map] How many user attributes count as system-defined differs between pages: [User and session attributes in Authentication Service: system-defined sets, custom attributes, device-attribute values and where each is used](kb:zidentity.attributes). Default SCIM user attributes are id (the unique identifier assigned to the user), the client-assigned External ID stored as scim_externalid, meta.created, meta.lastModified, meta.location, meta.version (updated with every modification), meta.resourceType (User) and groupIds, the user's group memberships. [zidentity.users.provisioning.scim:default-user-attributes] Authentication Service classes these SCIM attributes as custom user attributes: honorificPrefix, honorificSuffix, profileUrl, locale, ims, photos, entitlements, roles, x509Certificates and employeeNumber. [zidentity.users.provisioning.scim:custom-user-attributes] Administrators can define any custom attributes; the page's examples (Tshirtsize, Officebuilding, Keyshare) map in the IdP to urn:ietf:params:scim:schemas:extension:zscaler:1.0:User.<name> (the page writes the names as tshirtsize, officebuilding and Keyshare). [zidentity.users.provisioning.scim:admin-defined-attributes] SCIM group attributes: ID is a unique ID generated by Zscaler, EXTERNALID is the client's external ID stored as scim_externalid, the resource type is Group, DISPLAYNAME is displayName and Members the users or resources in the group. [zidentity.users.provisioning.scim:group-attributes]

**Authentication and limits.** SCIM calls need SCIM-based provisioning enabled, the Base URL and the Bearer Token; most calls require the Bearer Token, but informational ones such as /Schemas, /ServiceProviderConfig and /ResourceTypes need no authentication. [zidentity.users.provisioning.scim:auth] The Authentication Service SCIM API examples page gives rate limits of 50 read requests (GET) and 50 write requests (POST/PUT/DELETE) per IdP per second, and says to configure the application to comply to avoid retries. [zidentity.users.provisioning.scim:rate-limits] ZIA's SCIM server has its own limit, stated separately: [Zscaler SCIM servers have a rate limit of 5 requests per second, and applications should be configured to comply to avoid retries.](kb:zia.scim.operations:rate-limit). Whether PATCH counts as a write is open [gap:zidentity.users.provisioning.scim:patch-rate-limit]. How the Base URL is formed is open [gap:zidentity.users.provisioning.scim:base-url-formation].

**What the examples page shows.** The page's GET /Users response example is a SCIM ListResponse with totalResults, startIndex, Resources and itemsPerPage 100, and one user's location is https://<subdomain>.zslogin.net/scim/h1gkrvmic07od/Users/ihgkrqp5tg7o5. [zidentity.users.provisioning.scim:list-response] The create-user example POSTs with Content-Type application/scim+json, and the group-membership PATCH example uses a PatchOp with op Add on members and Content-Type application/json-patch+json. [zidentity.users.provisioning.scim:create-content-type] Adding a member to a group and deleting a user each return 204 No Content on success. [zidentity.users.provisioning.scim:no-content-responses] The page's example user list includes a user __remote_assistance@<subdomain>.zslogin.net with display name Remote Assistance. [zidentity.users.provisioning.scim:remote-assistance-user] Status and error codes beyond 204 are open [gap:zidentity.users.provisioning.scim:status-codes]. The group update example states PUT yet sends PATCH, and the user update example sends PUT with a PatchOp body [divergence:zidentity.users.provisioning.scim:update-method]; the attribute table types active as a string while the create example sends a boolean [divergence:zidentity.users.provisioning.scim:active-type].

What to check:
1. Which product's SCIM server the client calls before applying a rate limit; the 50-per-IdP-per-second limits are this server's.
2. Whether the call needs the Bearer Token; informational calls such as /Schemas do not.
3. Before copying an update or create example, the page's own inconsistencies on the update method and the type of active.

Sources disagree (name both sides):
- Which method the SCIM API Examples page uses to update: both update sections say the PUT request is used, the group example sends PATCH, and the user example sends PUT with a PatchOp body. [divergence:zidentity.users.provisioning.scim:update-method]
  - zscaler-help: The group section says the PUT request is used, and its command is a PATCH.
  - zscaler-help: The user section says PUT and sends PUT, but its body is a PatchOp message.
  Impact: The examples do not show which method a PatchOp body needs; the operations table lists PUT or PATCH for updates without saying how they differ.
- The type of active: the attribute table types it as a string, while the create-user example sends a boolean. [divergence:zidentity.users.provisioning.scim:active-type]
  - zscaler-help: The Understanding SCIM table types STATUS, mapped to active, as String.
  - zscaler-help: The new user file example sends active as the boolean true.
  Impact: A client that follows the table sends a string where the example sends a boolean; neither page says which the server accepts. ZPA's examples have the same open question: zpa.scim.server-operations:example-inconsistencies.
