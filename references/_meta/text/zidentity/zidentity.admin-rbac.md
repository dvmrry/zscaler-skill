# Authentication Service admin roles: predefined and custom roles, and how they relate to product roles (zidentity.admin-rbac)
Also called: ZIdentity admin roles; Authentication Service admin roles; ZIdentity RBAC; Super Admin; View Only Admin; User Admin; CXO Insight User; ZIdentity custom roles; who can administer ZIdentity

This covers the admin roles of Authentication Service itself and where they stop. Role-based administration assigns Authentication Service users or user groups admin roles and permissions that control their level of access to the Zscaler Admin Console. [zidentity.admin-rbac:role-based-administration]

**The roles.** There are four predefined admin roles: Super Admin (full permissions, assignable to other admins), View Only Admin (view-only permissions), User Admin (user management permission) and CXO Insight User (CXO insight permission). [zidentity.admin-rbac:predefined-roles] Admins can also add their own roles: the Roles page adds, edits and deletes roles, predefined roles cannot be deleted, and an admin cannot edit the custom role assigned to them individually. [zidentity.admin-rbac:custom-roles] Per-module permissions and how several roles combine are in [Authentication Service permission modules and levels, and the cross-module dependencies](kb:zidentity.admin-rbac.permissions).

**Executive Insights.** The CXO Insight User role lets executive users access the Executive Insights mobile app; the executives are also assigned to a Zscaler service in Authentication Service (the page names Internet & SaaS), which lets them reach that service in the app. The role is assigned to users or groups on the Authentication Service Administration entry of the Administrative Entitlements page. [zidentity.admin-rbac:cxo-insight-user] Executive users must also be assigned the Executive Insights App role on every Internet & SaaS tenant they need to access, on the Zscaler Internet Access entry of the Administrative Entitlements page; before the role is assigned, the executives might need to be authorized for Internet & SaaS on the Executive Insights App. [zidentity.admin-rbac:executive-insights-app-role] Without Internet & SaaS access an Authentication Service role with the app permission gets the message in [Some users can log in successfully but get the error "Contact your IT admin to provide you access to a tenant." The page says this happens only in the case of Authentication Service-based authentication, when the user has been given an Authentication Service role with permission to access the app but no Internet & SaaS Administration Management access for any tenant. The remedy is to go, in the Admin Console, to Administration > Legacy Admin Management > Internet & SaaS and ensure two things: the user exists, and the user has a role with permission to access the app.](kb:zia.reports.executive-insights-app:auth-service-access).

**Order of operations.** Users and user groups must be added to Authentication Service before admin roles are assigned to them. [zidentity.admin-rbac:users-first] On Authentication Service tenants migrated to the Zscaler Admin Console, submitting a Zscaler Support ticket in the console needs at least View Only permission on the Users and User Groups modules. [zidentity.admin-rbac:support-ticket]

**Unified RBAC.** Where the limited-availability Unified RBAC feature is in use, roles are managed on a different page: [Where an organization uses Unified Role-Based Access Control, a feature in limited availability obtained through the Zscaler Account team, admin roles for ZIA, ZPA and Authentication Service are managed on a different Role Management page.](kb:shared.admin-rbac:unified-rbac).

**Product roles.** Admins of a product are assigned on the Administrative Entitlements page with a role created for that product: [The Administrative Entitlements page lists the subscribed Zscaler services; Authentication Service users or user groups are assigned there as service admins of a service with a role created in the Admin Console, and admins see only their assigned services in the Admin Console.](kb:shared.admin-rbac:entitlement-assigns-service-admins), [So on an Authentication Service tenant the admin identity and the product assignment are made centrally, while what the admin can do inside a product is still that product's role (and, for ZIA, the scope, which is edited on the ZIA Administrators page).](kb:shared.admin-rbac:identity-central-role-in-product). So an Authentication Service role, User Admin included, sets permissions on Authentication Service's own modules; access inside ZIA or ZPA comes from the product role chosen when the administrative entitlement is assigned. [zidentity.admin-rbac:own-roles-not-product-scope] Whether anything carries over automatically from an Authentication Service role to a product's scope is still open [gap:zidentity.admin-rbac:product-scope].

**Through the API.** The published Authentication Service API reference has paths for API clients, groups, resource servers and users and none for roles or role assignments, so roles are not managed through the published API. [zidentity.admin-rbac:no-role-paths] Whether an unpublished endpoint manages roles is open [gap:zidentity.admin-rbac:role-api], and so is whether role assignments are recorded in the audit log [gap:zidentity.admin-rbac:assignment-audit].

What to check:
1. Whether the question is about Authentication Service's own modules (its admin roles) or about what an admin can do in a product (the product role assigned with the administrative entitlement).
2. Whether the tenant uses Unified RBAC, which moves role management to a different page.
3. Whether the user or group exists in Authentication Service before a role is assigned to it.
