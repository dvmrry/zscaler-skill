# Go SDK for ZIdentity (ziam services): name lookups, write models and where its paths depart from the contract (zidentity.sdk-go)
Also called: zscaler/ziam; ziam services go; zidentity go sdk; GetByName zidentity; SetSkipMFA ResetPassword UpdatePassword path; ServiceEntitlement go

The Go SDK reaches ZIdentity through the `zscaler/ziam/services` packages; their functions and endpoints are generated (`node scripts/kb.mjs surface zid`). Behavior shared by every Go product, retries and error decoding included, is in [How the Go SDK retries requests (and replays writes)](kb:shared.sdk-go.retries) and [How the Go SDK builds requests and interprets responses: client options, bodies, status codes, bulk deletes](kb:shared.sdk-go.request-handling).

**Name lookups.** The Go `GetByName` functions for API clients, groups, resource servers and users request pages of 100 records, moving the offset on by each page's record count until a page comes back short or with no next link, and keep the records whose name contains the search string, ignoring case; for users the compared field is the display name, not the login name; they return the matches collected with a nil error, so no match is not an error. [zidentity.sdk-go:getbyname-client-side] `GetPage` (API clients) returns one page together with its paging metadata, `results_total`, `next_link` and `prev_link`, for callers that page by hand or want the record count. [zidentity.sdk-go:getpage-metadata] Why the API-client lookup avoids the server filter: [The Go API-client `GetByName` does not use the server-side `name[like]` filter because its matching semantics are undocumented; it pages through all clients and matches on the client instead.](kb:zidentity.api.query-filters:go-getbyname-avoids-like). Paging is in [The Go SDK's list helper `ReadAllPagesWithPagination` requests 100 records per page when the caller passes no parameters, stops at the first page shorter than the limit or with an empty `NextLink`, advances the offset by the number of records received, and applies any JMESPath filter only after collecting every page.](kb:zidentity.api.pagination:go-walk).

**Writing.** The Go API client and user models hold `Status` as a pointer so that disabling is expressible: as a plain bool with `omitempty`, a false would be indistinguishable from unset and dropped from the request body (the user model's comment says it was), making it possible to enable a client or user but never to disable one. [zidentity.sdk-go:status-pointer] The general reason a plain false is lost is in [In every product, where a writer marshals the caller's struct and a field's type has no MarshalJSON of its own, a field tagged `omitempty` is left out of the request body when it holds false, 0, an empty string, or a nil or empty slice. So when a provider rebuilds such a struct from Terraform state and sends it as a full PUT, a user's change to false, zero, empty string or empty list reaches the SDK but never reaches the wire.](kb:shared.sdk-go.zero-value-writes:omitempty-drops-zero-values). The Go model tags `accessTokenLifeTime` without `omitempty`; its comment says this is so that a caller who leaves it at zero gets the API's range error rather than have the field silently vanish and the server apply a default. [zidentity.sdk-go:lifetime-always-sent] When an update's PUT answers with no body, the Go `Update` for API clients (and for users) returns a nil object and a nil error: the update succeeded and the caller has to read the record again to see it. [zidentity.sdk-go:update-nil-on-empty-body] The secret calls are in [ZIdentity API client secrets: creation, expiry, the two-secret limit, rotation and masked reads](kb:zidentity.api-clients.secrets).

**Groups.** The Go groups `Update` takes `groupID int` and builds its path with `%d`, while `Get`, `Delete` and the membership functions take the group ID as a `string` and the `Groups` struct types `ID` as a string, so an ID read from the API has to be converted to an integer to update the group. [zidentity.sdk-go:groups-update-int-id] The Go groups `Update` takes the result with `updatedGroup, _ := resp.(*Groups)` and logs `updatedGroup.ID` on the next statement, with no nil check between, while the shared PUT helper (`UpdateWithPut`) returns a nil object and no error for an empty response body; the users `Update` checks for nil because, its comment says, a `204 No Content` answer would otherwise dereference nil and panic the calling process. [zidentity.sdk-go:groups-update-no-nil-check] So a group update whose PUT answers with no body panics the calling process after the update has been applied, instead of returning the nil result the users and API-client updates return. [zidentity.sdk-go:groups-update-panics] The Go groups `Create` logs the new group's string `ID` with a `%d` verb, while `Get` and the user-list functions `AddUserListToGroup` and `ReplaceUserListInGroup` log a group `ID` with `%s`. [zidentity.sdk-go:groups-create-log-verb] The Go `AddUserToGroup` posts an empty struct through the shared `Create` helper and returns `httpResp, _ := resp.(*http.Response)`; `Create` returns the decoded payload when the response has a body and a `Content-Type` of `application/json`, and the `*http.Response` otherwise. [zidentity.sdk-go:add-user-to-group-response] So when adding one user answers with a JSON body, `AddUserToGroup` returns a nil `*http.Response` with a nil error, and a caller that reads the status from the returned response dereferences nil. [zidentity.sdk-go:add-user-to-group-nil-response] The same exact content-type test in the shared create helper is in [The ZIA `Create` helper has the same exact-match `Content-Type` comparison and the same raw-response fallback, and ZIA service create methods type-assert its result the same way. The ZIA provider builds on v3.8.44 and reaches it wherever its resources call these service create methods (75 files use `Client.Create`, not individually traced).](kb:shared.sdk-go.request-handling:zia-create-same-exact-content-type).

**User actions.** The Go user actions send POST to `/setskipmfa` and `/resetpassword`, and PUT to `/updatepassword`, appended to the user's path after a slash. [zidentity.sdk-go:user-action-paths-go] The contract writes these routes with a colon [divergence:zidentity.sdk-go:user-action-paths].

**Entitlements.** Go reads service entitlements as a list of objects that each wrap a `service`; the package's comment says it once read the array into bare service objects, which matched no keys and produced one zero-valued service per entitlement, losing the entire response without an error. [zidentity.sdk-go:service-entitlement-envelope] The Go SDK's comment says an administrative entitlement for the ZIAM service carries no `scope` key at all, and the Go model holds `Scope` and `Service` as pointers because as value types the absence could not be told apart from `{"id": ""}`. [zidentity.sdk-go:admin-scope-optional]

What to check:
1. Whether a Go name lookup that returned several results was meant as an exact match; `GetByName` is a substring match, and for users it matches the display name.
2. For a failed user action from Go, whether the slash-form path is what the tenant accepts, compared with the contract's colon form.

Inferred, not quoted (say so when an answer rests on one):
- [zidentity.sdk-go:groups-update-panics] Tier B: Follows from Go evaluating `updatedGroup.ID` on a nil pointer, the failure the users package's comment describes for its own function; whether the groups PUT ever answers without a body is not observed.
- [zidentity.sdk-go:add-user-to-group-nil-response] Tier B: Follows from a failed Go type assertion yielding the zero value (nil) when `Create` returns the decoded struct; what the add-user response carries is not observed.

Sources disagree (name both sides):
- The contract writes the user actions as colon suffixes on the user path (`/users/{id}:setskipmfa`), while the Go SDK sends them as a further path segment after a slash. [divergence:zidentity.sdk-go:user-action-paths]
  - api-specs: Skip MFA is POST /users/{id}:setskipmfa; reset and update password take the same colon form.
  - sdk-go: Skip MFA is POST /users/<id>/setskipmfa.
  Impact: If the API routes only the colon form, every Go user action fails; a raw caller should follow the contract until a trace shows which form a tenant accepts.
