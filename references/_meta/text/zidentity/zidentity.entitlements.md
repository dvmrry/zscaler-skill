# Administrative and service entitlements: who administers and who may use each Zscaler service (zidentity.entitlements)
Also called: ZIdentity entitlements; administrative entitlements; admin entitlements; service entitlements; end user entitlements; admin-entitlements; service-entitlements; which services can this user use; is this user an admin of ZIA
Former IDs: zid-05, zid-08

Authentication Service keeps two kinds of entitlement per user, and they answer different questions. A user can be given admin entitlements, which make them an administrator of a Zscaler service such as ZIA or ZPA, or service entitlements, which let them authenticate to a Zscaler service as an end user. [zidentity.entitlements:two-kinds]

**Administrative entitlements.** Users and groups are made service admins of a subscribed service, with a role created for that service: [The Administrative Entitlements page lists the subscribed Zscaler services; Authentication Service users or user groups are assigned there as service admins of a service with a role created in the Admin Console, and admins see only their assigned services in the Admin Console.](kb:shared.admin-rbac:entitlement-assigns-service-admins). The Administrative Entitlements page also controls which users in the organization have access to Authentication Service, shows the users and groups assigned as service admins of each service, and lists each subscribed service with its name, cloud name and organization name. [zidentity.entitlements:admin-page]

**Definition and services.** Entitlements are the access privileges and permissions assigned to Authentication Service users and groups, of two kinds, Administrative and Service; administrative entitlements give a user or group administrative access to a Zscaler service with a role created in that service. [zidentity.entitlements:definition] The Managing Entitlements page lists the services whose roles are added for administrative entitlements: Authentication Service, Internet & SaaS, Private Access, ZDX, Client Connector, Cloud & Branch Connector, Deception, DSPM, Business Insights, Risk360, Workflow Automation, Breach Predictor, EASM, Zero Trust Branch, the Management Portal for Partners and Zscaler Cellular. [zidentity.entitlements:services-with-roles] Authentication Service supports login to Breach Predictor through Risk360 even if the Risk360 or Breach Predictor tenants have not been migrated to Authentication Service. [zidentity.entitlements:breach-predictor-via-risk360]

**Assigning.** The Assigning Entitlements page repeats that an individually assigned service admin role takes precedence over a different role from the user's group, and requires users and groups to be added to Authentication Service before they are assigned. [zidentity.entitlements:individual-over-group] Assigning a user group an administrative entitlement gives all users in the group administrative privileges for the service, with the role chosen per group. [zidentity.entitlements:admin-group-assignment] Service entitlements assign individual users to a Zscaler service as end users; user groups can be assigned to the Zscaler service too. [zidentity.entitlements:service-entitlement-assignment] On tenants without Unified RBAC, admins cannot create, modify or delete the administrative entitlement and role assigned to them. [zidentity.entitlements:own-entitlement-locked] When assigning administrative entitlements, the Microtenant column appears only for Private Access; with Full an admin assigns, edits or deletes any Microtenant for other admins, as does Restricted Full with the Default Microtenant assigned, while Restricted Full with a non-default Microtenant reaches only the assigned Microtenant; with no Microtenant configured in Private Access, Default is selected. [zidentity.entitlements:zpa-microtenant]

**Role sync and precedence.** Product roles are synced into Authentication Service automatically at regular intervals, and a manual sync can be run from the View Roles page. [zidentity.entitlements:role-sync] The interval is open [gap:zidentity.entitlements:role-sync-interval]. When a user is in several groups with different levels of access, the group assigned first takes precedence; a role assigned to the user individually as a service admin role takes precedence over a different admin role from a group. [zidentity.entitlements:role-precedence] What first means is open [gap:zidentity.entitlements:first-meaning].

**Device group restrictions.** An Authentication Service admin can restrict which devices are used to access a Zscaler service so that only users on authorized devices can enroll: Enable Device Group Restrictions, set per service, lists the registered device IDs, the selected devices are allowed, and users then access the service from their registered device. [zidentity.entitlements:device-group-restrictions] An admin who can access service entitlements but has no permission to view device groups sees only whether Enable Device Group Restrictions is on, and cannot change it. [zidentity.entitlements:device-group-permission] Which module grants viewing device groups is open [gap:zidentity.entitlements:device-group-module], and whether restrictions reach administrative entitlements is open [gap:zidentity.entitlements:device-restriction-admin].

**Service entitlements.** The Service Entitlements page lists the subscribed Zscaler services, each with its name, cloud name and organization name, and assigns end users and user groups to them; it is available only if the organization is provisioned with Authentication Service for end users. [zidentity.entitlements:service-page]

**Reading them.** The API reference has only a GET operation for a user's administrative entitlements and for their service entitlements; neither path has a write operation. [zidentity.entitlements:read-only-api] A user's administrative entitlements come back as a list of records, each with the service (its ID, name, cloud name, cloud domain name, organization name and organization ID), one scope object and a list of role objects, each with an ID, a name and a display name. [zidentity.entitlements:admin-shape] A user's service entitlements come back as a list of records that each carry a service object (the same service fields), with no roles and no scope. [zidentity.entitlements:service-shape] So the role names in an administrative entitlement are the roles each product defines (a ZIA admin role is chosen when the Internet & SaaS entitlement is assigned), not a fixed list; the API reference gives the role objects no enumeration. [zidentity.entitlements:roles-from-products] The API reference documents a 200 and a 401 response for the administrative and the service entitlement reads, and no 400, 403, 404, 429 or 500. [zidentity.entitlements:documented-responses] The Go SDK notes that an entitlement for the ZIAM service has no scope, [The Go SDK's comment says an administrative entitlement for the ZIAM service carries no `scope` key at all, and the Go model holds `Scope` and `Service` as pointers because as value types the absence could not be told apart from `{"id": ""}`.](kb:zidentity.sdk-go:admin-scope-optional).

**On a user.** Each Authentication Service user can be assigned different service and administrative entitlements depending on the role; to view them an admin first adds users, assigns them to the subscribed Zscaler services and opens the Users page, where the Entitlements tab shows the assigned services, and administrative entitlements are displayed only for users with admin roles. [zidentity.entitlements:user-entitlements-tab]

**Open.** What an entitlement's scope means is not documented [gap:zidentity.entitlements:scope-meaning], and whether the results differ by how the user was provisioned is open [gap:zidentity.entitlements:by-source].

How the SDKs model these responses is covered with the SDKs in [Which clients cover which parts of the ZIdentity API: Python, Go and the MCP server](kb:zidentity.api.client-coverage).

What to check:
1. For a question about a user's admin access to a product, read the user's administrative entitlements and the role on each; for whether a user may sign in to a service as an end user, read the service entitlements.
2. Whether the entitlement comes from a group assignment rather than the user directly, since both pages assign users and user groups.
3. Whether the tenant is provisioned with Authentication Service for end users, without which the Service Entitlements page does not exist.
