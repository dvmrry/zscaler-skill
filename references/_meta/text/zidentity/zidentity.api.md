# The ZIdentity (Authentication Service) admin API from a client's side: route, coverage and wire notes (zidentity.api)
Also called: zidentity api; ziam api; authentication service api; ziam admin api v1; how to automate zidentity; zidentity api divergences; client.zid

Endpoint lists, HTTP methods, request and response fields, and the Go and Python SDK functions for ZIdentity are generated from the captured contract and the SDKs: run `node scripts/kb.mjs surface zid` and read `vendor/zscaler-api-specs/automate-zscaler/openapi/zid.openapi.json`. This subject family holds only the behavior around them and the places where those sources disagree.

**What the API manages.** The Authentication Service API manages API clients, users, groups and resource servers; resource servers (API resources) are the Zscaler APIs available through the OneAPI gateway. [zidentity.api:feature-areas]

**Route.** The ZIdentity contract declares the server https://api.zsapi.net/ziam/admin/api/v1, described as the Authentication Service endpoint. [zidentity.api:contract-server] The Python SDK's ZIdentity service classes set the base endpoint `/ziam/admin/api/v1`, and its request executor resolves the OneAPI gateway base URL to a dedicated gateway for a government (FedRAMP) cloud, otherwise to https://api.<cloud>.zsapi.net when a cloud other than `production` is configured, and to https://api.zsapi.net by default. [zidentity.api:python-route] The Go SDK's `ziam` service packages for users, groups, API clients, resource servers and user entitlement each declare their endpoint under `/ziam/admin/api/v1`. [zidentity.api:go-route] The Go client's routing of the `ziam` prefix is in [The Go SDK's OneAPI client checks for the `ziam` prefix before the `zia` prefix so that ZIdentity calls are not metered against ZIA's rate limiter, and sends `ziam` and `admin` paths through its default HTTP client.](kb:shared.oneapi.base-urls:go-ziam-routing), and the hosts for other clouds are in [Reaching OneAPI on government (FedRAMP) and non-production clouds](kb:shared.oneapi.government-clouds). Whether tenants still answer the older Go releases' vanity-admin route is open [gap:zidentity.api:legacy-go-route].

**Signing in.** The ZIdentity contract defines an HTTP bearer security scheme named `BearerAuth`. [zidentity.api:bearer-scheme] Creating an API client through the API (POST /api-clients) requires a bearer token, as do the contract's other API client, group, resource server and user operations, so the first API client cannot be created through the API and has to come from the Admin Console. [zidentity.api:bearer-on-every-operation] Getting a token is shared with every OneAPI product: [How a client gets and uses a OneAPI access token](kb:shared.oneapi.authentication). The API client object itself, its scopes and its token lifetime are in [ZIdentity API clients: what one is, how it authenticates, its resources and scopes, and its token lifetime](kb:zidentity.api-clients).

**Limits.** No source gives rate limits for this API [gap:zidentity.api:rate-limits]; the per-product limits that are documented are in [OneAPI rate limits by product, and how the Go SDK throttles](kb:shared.oneapi.rate-limits).

**Surface boundaries.** The contract has no bulk user-create or user-import operation: users are created one at a time with POST /users, and the only list-shaped writes are the group membership POST and PUT on /groups/{id}/users. [zidentity.api:no-bulk-user-create] The contract has no operations for access tokens (listing or revoking them) or for API client access policy rules; those are managed only in the Admin Console as far as the captured sources show. [zidentity.api:no-token-or-policy-paths] The contract has no bulk user delete: a user is deleted one at a time with DELETE on /users/{id}, and /users itself has no DELETE; the only users bulk delete in the OneAPI Postman collection is ZIA's (`{{ZIABaseUrl}}/users/bulkDelete`). The console's bulk delete has no API counterpart. [zidentity.api:no-bulk-user-delete]

What to check:
1. Whether the request goes to the `/ziam/admin/api/v1` base on the OneAPI gateway, not to a vanity-admin host an older Go release used.
2. Whether the operation needed (token revocation, access policy, bulk user create) exists in the contract at all before looking for a client wrapper.

Inferred, not quoted (say so when an answer rests on one):
- [zidentity.api:bearer-on-every-operation] Tier B: 28 of the contract's 31 operations list BearerAuth under security (checked across the zid contract at the pin); the three user action routes (reset password, skip MFA, update password) declare no security, which the contract leaves unexplained. The bootstrap consequence is inferred, not stated by a source.
- [zidentity.api:no-bulk-user-create] Tier B: Absence from the complete path list of the zid contract at the pin (18 paths, the same list `node scripts/kb.mjs surface zid` shows); SCIM provisioning is outside this API.
- [zidentity.api:no-token-or-policy-paths] Tier B: Absence from the complete path list of the zid contract at the pin: its 18 paths are under /api-clients, /groups, /resource-servers and /users only. The console pages are in zidentity.api-clients.access-tokens and zidentity.api-clients.access-policy.
- [zidentity.api:no-bulk-user-delete] Tier B: Absence from the complete path list of the zid contract at the pin (18 paths, as `node scripts/kb.mjs surface zid` shows) and from a search of the Postman collection for bulkDelete, which finds only ZIA and ZPA requests.

Not known (open gaps):

- What rate limits apply to the Authentication Service API [gap:zidentity.api:rate-limits] (data gap): filled by operator; settled by source-read or lab-test. Blocks: sizing bulk user or group automation against the API
