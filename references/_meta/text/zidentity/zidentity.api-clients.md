# ZIdentity API clients: what one is, how it authenticates, its resources and scopes, and its token lifetime (zidentity.api-clients)
Also called: zidentity api client; oneapi api client; api client scopes; accessTokenLifeTime; access_token_life_time; clientResources selectedScopes; zs:config scope; ziam:0 scope; api client authType JWKS PUBKEYCERT SECRET; first api client bootstrap

An API client is the identity a script, SDK or provider uses to call any Zscaler API through OneAPI. API clients or AI agents can access Zscaler API resources; Authentication Service includes an OAuth 2.1 authorization server that validates authorization requests by API clients and AI Agents and issues access tokens that authorize clients accessing the API resources via the OneAPI server. [zidentity.api-clients:definition]

**Where clients come from.** Applications, services, and AI agents that need to access Zscaler API resources must be provisioned in the Zscaler Admin Console, and Authentication Service administrators with Full permission on the API Clients and API Resources modules can configure API clients. [zidentity.api-clients:console-provisioning] On the API Clients and AI Agents page an admin can search, export the list as CSV, add, edit, delete, and disable API clients and AI agents; the list shows each client's name, status (Active or Inactive) and client ID. [zidentity.api-clients:console-page] To use OneAPI, the Zscaler services must be linked to Authentication Service, and RBAC restricts an API client's access to specific API resources. [zidentity.api-clients:linked-services-required] Creating one through the API needs a token from an existing client, so the first one comes from the console: [Creating an API client through the API (POST /api-clients) requires a bearer token, as do the contract's other API client, group, resource server and user operations, so the first API client cannot be created through the API and has to come from the Admin Console.](kb:zidentity.api:bearer-on-every-operation). Deleting an API client asks for CONFIRM in the Delete API Client window; the page that lists clients is titled API Clients and AI Agents. [zidentity.api-clients:delete-confirm] A deleted API client cannot be recovered. [zidentity.api-clients:delete-unrecoverable] What an AI agent is on that page is open [gap:zidentity.api-clients:ai-agents]. Editing an API client can change its client information, client authentication and resources (a different role); after a different role is assigned, the access token Authentication Service issues applies to the new scope for that service. [zidentity.api-clients:edit-role-scope]

**Status.** An enabled status lets the API client authenticate and use the API resources; while the status is disabled, the client cannot get access tokens from Authentication Service. [zidentity.api-clients:disabled-no-tokens] Disabling or deleting a client also revokes its tokens: [ZIdentity-issued access tokens: the Tokens page, when tokens are revoked, and who can revoke them](kb:zidentity.api-clients.access-tokens).

**How it authenticates.** A client's `clientAuthentication.authType` is one of `SECRET`, `PUBKEYCERT` or `JWKS`, beside the fields `clientJWKsUrl`, `publicKeys` and `clientCertificates`. [zidentity.api-clients:auth-type-enum] The Go SDK documents the three values as mutually exclusive, each deciding which other fields the API expects: `SECRET` uses a secret managed through `AddSecret`, `GetSecrets` and `DeleteSecret`, `PUBKEYCERT` a certificate in `ClientCertificates` or `PublicKeys`, and `JWKS` keys published at `ClientJWKsURL` (wire key `clientJWKsUrl`). [zidentity.api-clients:go-auth-type-fields] The methods and how each is used at the token endpoint are in [Authentication Service accepts a client secret, which needs manual rotation, or a private key JWT assertion. The assertion is validated either with public keys fetched from a JWKS URL the client hosts, which lets the client rotate keys with no change in Authentication Service, or with public keys or X.509 certificates uploaded to Authentication Service, where rotation needs a manual update.](kb:shared.oneapi.authentication:client-auth-methods). A JWKS client's body has not been seen in a capture [gap:zidentity.api-clients:jwks-body-unobserved], and the Python SDK sends the JWKS URL under a different key: [So a Python client created as documented sends the JWKS URL as `clientJwKsUrl`, not the contract's `clientJWKsUrl`; the model reads `clientJWKsUrl` back correctly.](kb:zidentity.sdk-python:jwks-url-key). Secrets have their own lifecycle: [ZIdentity API client secrets: creation, expiry, the two-secret limit, rotation and masked reads](kb:zidentity.api-clients.secrets).

**Resources and scopes.** Each API client is assigned one or more roles (API resources), which define the specific endpoints and operations the client is permitted to access; the resources selected decide its permissions (scope) for each Zscaler service. [zidentity.api-clients:roles-define-access] Before an API client can be given a product's resource, an API role has to exist in that Zscaler service; the roles are synced to Authentication Service, and assigning resources without them fails with an error. [zidentity.api-clients:api-roles-first] One resource per product: [API resources pair a Zscaler service with an RBAC role. An API client can be assigned one resource per product, which defines what it can do (read, write or restricted access), and can hold resources of several different products.](kb:shared.oneapi.authentication:one-resource-per-product). On create and update, each `clientResources` entry takes the resource `id` and `selectedScopes`, each scope given by `id`; the Go SDK notes that only `ID` and `SelectedScopes` are accepted on write, and that the name and `defaultApi` of a resource and the name of a scope are reported on read. [zidentity.api-clients:resource-request-shape] A selected scope's ID is the composite ID the resource servers report, passed through unchanged: its shape is `<serviceId>:<zpaScopeId>:<id>` with the middle segment empty for every service except ZPA. The Go SDK records, as confirmed against a tenant, that splitting it into separate fields is rejected with "400 Invalid Input for clientResources". [zidentity.api-clients:scope-id-composite] The Python SDK's create example pairs scope IDs with scope names: `hhlm44raf07ps::hpopqi71j075n` with `zs:config:zia.zscalerbeta.net:8061240:config:33860:ZIA_API_Role01`, and `hhlm44rae07ib:mplm44rqi07jb:hplm44rqvg7n5` with `zs:config:zpa.zpabeta.net:72058304855015424:config:Default:Default:28:FullAccess`; it also selects the scope named `zs:config:ziam:0:config:9h6p7ebv903k4:Super Admin`. [zidentity.api-clients:scope-examples] To call the ZIdentity admin API itself, a client needs a ZIdentity resource among its selected resources (the `ziam` scope in the example); a client holding only other products' resources, such as ZPA, is not permitted those endpoints. [zidentity.api-clients:ziam-scope-for-self] A client whose resources do not cover a product can still obtain a token, since the token request names no scope; the failure appears when the token is presented, as a 403 for a client without access to the resource. [zidentity.api-clients:scope-checked-at-call] The resources and scopes a client can select are listed by [ZIdentity resource servers (API resources): a read-only registry of the scopes API clients can select](kb:zidentity.resource-servers).

**Writing a client.** The Python SDK reaches API clients as `client.zid.api_client` (singular): the client's `zid` property returns a `ZIdService`, and its `api_client` property returns the `APIClientAPI`. [zidentity.api-clients:python-accessor] Creating and updating a client both require `name`, `accessTokenLifeTime`, `clientAuthentication` and `clientResources` in the body. [zidentity.api-clients:required-fields] The Python SDK's docstring marks most of them optional [divergence:zidentity.api-clients:required-fields-docstring]. An update is a full replace: the Go SDK says to build the PUT body by reading the live client and overlaying the changes, because fields left out are dropped. [zidentity.api-clients:put-full-replace]

**Token lifetime.** `accessTokenLifeTime` is the lifetime of the access token issued to the client, between 60 and 86400; the create description gives it in seconds and its example as "60 for 60 minutes". [zidentity.api-clients:lifetime-range] In the Admin Console the Access Token Validity is entered in minutes, from 1 minute to 24 hours. [zidentity.api-clients:console-lifetime] The sources disagree on the unit, and the Python SDK describes the field as something else [divergence:zidentity.api-clients:lifetime-unit]; which unit the API applies is open [gap:zidentity.api-clients:lifetime-unit-on-wire]. The token's `expires_in` reflects the configured lifetime: [The token response carries `access_token`, `token_type` Bearer and `expires_in`; `expires_in` is the token expiration time configured for the API client in Authentication Service (3600 in the examples).](kb:shared.oneapi.authentication:expires-in-configured). A tenant-wide default lifetime is unconfirmed [gap:zidentity.api-clients:tenant-default-lifetime].

**Access policy.** Rules that limit when a client may reach which resources are in [The API Client Access Policy: rules that allow or block a client's resources within time frames](kb:zidentity.api-clients.access-policy).

What to check:
1. Whether the client is enabled; a disabled client gets no tokens and its issued tokens are revoked.
2. For a 403 after a successful token request, whether the client holds a resource for the product being called (for the ZIdentity API itself, a `ziam` resource).
3. Before creating a client through the API, whether the product's API role exists, since the resources come from those roles.
4. When setting the token lifetime through the API, which unit the value was meant in; the update description says minutes and the create description seconds.
5. For an update, whether the PUT body was built from a fresh read of the client, since omitted fields are dropped.

Sources disagree (name both sides):
- What unit `accessTokenLifeTime` carries: the create and response schemas say seconds, the update schema says minutes, the console takes minutes, and the Python SDK's docstring describes the field as an active flag. [divergence:zidentity.api-clients:lifetime-unit]
  - api-specs: Seconds, 60 to 86400, with the example "60 for 60 minutes".
  - api-specs: Minutes, with the same 60 to 86400 range.
  - zscaler-help: The console takes minutes, from 1 minute to 24 hours (the same span as 60 to 86400 seconds).
  - sdk-go: Seconds is the reading consistent with the range, but unverified against a tenant.
  - sdk-python: The parameter is described as whether the client is active, which matches neither.
  Impact: A caller that sends minutes where the API reads seconds gets a token sixty times shorter than intended (or a range error below 60); the Python docstring's description should be ignored, since every other source makes the field a token lifetime.
- The contract requires `accessTokenLifeTime`, `clientAuthentication` and `clientResources` on create and update, while the Python SDK's `add_api_client` docstring marks them optional. [divergence:zidentity.api-clients:required-fields-docstring]
  - api-specs: All four are required.
  - sdk-python: Only `name` is unmarked; the other three are optional.
  Impact: A Python call that follows the docstring and leaves these out is rejected by an API that enforces the contract; supply all four.
