# Step-up authentication: when Authentication Service asks for a stronger login, and why a prompt may not appear (zidentity.step-up)
Also called: step-up authentication; ZIdentity step-up; step-up not prompting; Conditional Access step-up; require authentication level; re-authenticate with MFA for sensitive app; step-up with SAML
Former IDs: zid-29, zid-31

Step-up is configured in Authentication Service and demanded by ZIA and ZPA policy; the ZIA-side subject [Step-up authentication and ZIdentity authentication levels](kb:zia.authentication.step-up) holds the core statements this one builds on.

**What it is.** [Step-up authentication prompts a user to reauthenticate with a higher assurance level (for example, using MFA) when accessing specific resources. It is configured with authentication levels that are hierarchical: higher levels are stronger, and a user authenticated at a higher level satisfies policies requiring a sub-level. The levels are mapped to access policies in supported Zscaler services.](kb:zia.authentication.step-up:what-it-is) The help names three uses: access to critical applications as defined by ZIA and ZPA access policies, which integrate with Authentication Service to enforce them; increased risk, where unusual behavior or a changed environment such as an unrecognized device or location might trigger a request for a higher level; and compliance, where certain data must be protected with MFA. [zidentity.step-up:use-cases] The Configuring Step-Up Authentication page describes step-up as allowing dynamic requests for stronger authentication when users attempt to access sensitive resources or when risk signals indicate a potential threat. [zidentity.step-up:purpose]

**The flow.** [The flow is: the user logs in with standard credentials; on reaching a sensitive resource defined by Internet & SaaS (ZIA) or Private Access (ZPA) policy, the Authentication Service checks the required level; if the current level is insufficient it prompts re-authentication, typically MFA through Zscaler Client Connector; on success access is granted.](kb:zia.authentication.step-up:flow) [When an application requires additional authentication, Zscaler Client Connector shows a pop-up notification prompting the user to verify access with a Verify Now button; for Private Access this needs Client Connector 4.6 or later on Windows or 4.7 or later on macOS (and Client Connector 4.2 on Android and Android on ChromeOS, also for Internet & SaaS), and the requirement is set up in the Admin Console and available only with a subscription to Authentication Service.](kb:zpa.troubleshooting.authentication:verify-now-prompt)

**Where policy asks for it.** In ZIA, the URL Filtering Conditional action: [Conditional enforces step-up authentication before access. It needs Authentication Service for end users and Client Connector forwarding; through Private or Virtual Service Edges the category is blocked instead, and it does not apply to isolation traffic.](kb:zia.url-filtering.actions:conditional-prereqs). In ZPA, the Conditional Access action: [Conditional Access applies step-up authentication, is available only with an Authentication Service subscription, and prompts the user to reinforce their authentication if they are not at the defined level.](kb:zpa.policy.actions:conditional-access-step-up), and for Privileged Remote Access [A Conditional Access rule can require a step-up authentication level, available only to tenants subscribed to Authentication Service. A user who is not at the defined level is prompted to reinforce authentication, and the level must be configured in the Zscaler Admin Console.](kb:zpa.pra.access-policy:step-up-level).

**OIDC.** [Step-up authentication is supported only with OIDC-based external IdP integrations; when an external IdP is used via OIDC, each authentication level must be mapped to its acr value in the IdP.](kb:zia.authentication.step-up:oidc-only) The Configuring Step-Up Authentication page says step-up is supported only with OIDC-based external IdP integrations and that any IdP that supports OIDC authentication with ACR values can be configured for it, beyond the Entra ID and PingOne guides it lists. [zidentity.step-up:oidc-acr-any-idp] Another help page puts it as a recommendation, because most IdPs support step-up only over OIDC [divergence:zidentity.step-up:oidc-strictness]. What a SAML-only tenant sees when a rule demands a level is not documented [gap:zidentity.step-up:saml-outcome].

**Setting it up.** The Auth0 guide's step-up section and the Configuring Step-Up Authentication page list as prerequisites Zscaler Client Connector version 4.7 or later deployed for the users, Authentication Service enabled for both admins and users, and step-up authentication enabled for Authentication Service, Internet & SaaS (ZIA) and Private Access (ZPA) tenants; the Entra ID guide gives the third without the word tenants. [zidentity.step-up:prerequisites] The Auth0 guide and the Configuring Step-Up Authentication page give step-up setup as four steps: configure authentication levels, enable ACR values and configure policies in the external IdPs, map authentication levels and ACR values (the Auth0 guide places the first and third of these steps in the Zscaler Admin Console), and configure access policies in supported Zscaler services; for Private Access that is Access Policies with Conditional Access as the Rule Action and the Step-up Authentication Level field, and for Internet & SaaS the URL Filtering Policy and Cloud App Control Policies with Conditional Access as the Action and the Authentication Level field. [zidentity.step-up:setup-order] Per-vendor ACR mappings are in [Per-IdP integration specifics for Authentication Service: Okta, Microsoft Entra ID, AD FS, PingOne, PingFederate, Auth0 and OneLogin](kb:zidentity.overview.external-idps.integrations).

**Levels.** The levels a policy asks for, their tree, validity and acr mapping are in [Authentication levels: the level tree, validity periods, acr mapping and the message to users](kb:zidentity.step-up.levels).

**When no prompt appears.** What a user without a Client Connector channel gets is open beyond ZIA's documented case [gap:zidentity.step-up:no-client-connector]. Whether risk signals can trigger step-up without a policy rule is open [gap:zidentity.step-up:risk-trigger]. Whether SCIM-provisioned users without a mapped IdP identity can step up at all is open [gap:zidentity.step-up:scim-users].

**Seeing it afterwards.** Where a step-up elevation is logged is open [gap:zidentity.step-up:elevation-logging].

What to check:
1. Whether the tenant authenticates users through an OIDC external IdP.
2. For ZIA, whether the user forwards through Client Connector and not through a Private or Virtual Service Edge, where Conditional blocks instead.
3. For ZPA, whether the rule's action is Conditional Access with a defined level and the tenant subscribes to Authentication Service.
4. Whether the level the rule asks for exists, is mapped to its acr value in the IdP, and is still valid for the user's last authentication.

Sources disagree (name both sides):
- Whether step-up works only with OIDC IdPs, or is merely recommended with OIDC because most IdPs support it only there. [divergence:zidentity.step-up:oidc-strictness]
  - zscaler-help: Step-up is supported only with OIDC-based external IdP integrations.
  - zscaler-help: The Configuring Step-Up Authentication page repeats that step-up is supported only with OIDC-based external IdP integrations, and that any IdP supporting OIDC with ACR values can be configured for it.
  - zscaler-help: OIDC is recommended for step-up because most IdPs support step-up only over OIDC; SAML is recommended where no OIDC integration is possible.
  - zscaler-help: The Okta guide repeats the recommendation, without the sentence about SAML as a fallback. The Entra ID, AD FS and PingFederate guides carry the same sentence, and the step-up sections of the vendor guides sit only in their OIDC paths.
  Impact: Trusting the first page, an agent says a SAML tenant can never step up; trusting the second, it may tell a SAML tenant step-up could work with their IdP. Neither page says what happens when a SAML-only tenant's rule demands a level.

Not known (open gaps):

- Whether risk signals trigger step-up on their own [gap:zidentity.step-up:risk-trigger]: settled by source-read or lab-test. Blocks: explaining a step-up prompt that no rule asked for
