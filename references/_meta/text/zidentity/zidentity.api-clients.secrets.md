# ZIdentity API client secrets: creation, expiry, the two-secret limit, rotation and masked reads (zidentity.api-clients.secrets)
Also called: api client secret rotation; add_api_client_secret; expiresAt client secret; zidentity secret expires_at; forgot api client secret; AddSecret GetSecrets
Former IDs: zid-13

Secrets belong to clients whose authentication type is `SECRET`. Creating a secret for an API client applies only when the client's authentication type is `SECRET`. [zidentity.api-clients.secrets:secret-auth-only]

**Creating one.** The create-secret body requires `expiresAt`, the secret's expiry as an integer UNIX epoch timestamp in seconds. [zidentity.api-clients.secrets:expires-at-required] In the console a secret is auto-generated and shown with its validity period; it is generated once and cannot be updated, and its validity runs from a minimum of 30 days to a maximum of 365 days. [zidentity.api-clients.secrets:console-secret-rules] A secret is shown only when it is created: [A client secret can be seen in Authentication Service only when it is first created.](kb:shared.oneapi.authentication:secret-shown-once). The API's acceptable expiry range is open [gap:zidentity.api-clients.secrets:expires-at-range].

**Reading them back.** Listing a client's secrets returns them masked, so only the create response carries the value: [GET /api-clients/{id}/secrets lists an API client's secrets with the secret values masked, and applies only when the client's authentication type is SECRET.](kb:shared.secret-surfaces.withheld:zid-secrets-masked) and [So the full secret value is available only in the response to creating it; a read of the client or its secrets does not return it.](kb:shared.secret-surfaces.withheld:zid-full-only-on-create). The Go SDK's `GetSecrets` comment records that the endpoint answers with a bare JSON array rather than the paginated envelope the rest of the package uses, and that the values in it are masked, so it shows which secrets exist and when they expire, not what they are. [zidentity.api-clients.secrets:go-secrets-array] The Go `AddSecret` bypasses `service.Client.Create` in favour of `ExecuteRequest`, because Create unmarshals the response body into the request struct's type (`AddSecretRequest`, with nothing but `ExpiresAt`) and would discard the secret value; an empty response body is treated as success, and the caller is warned that the secret value cannot be recovered. [zidentity.api-clients.secrets:go-add-secret-raw] The Python SDK parses that list as a single secret: [So `get_api_client_secret` returns one secret object whose `id`, `created_at`, `expires_at` and `value` are all None, with no error, instead of the client's secrets: on a list, the key tests never match.](kb:zidentity.sdk-python:secrets-list-into-object). The Python SDK passes `add_api_client_secret` keyword arguments through as the body, and its example gives `expires_at` as the string '1785643102' rather than an integer. [zidentity.api-clients.secrets:python-expires-at-example]

**Timestamps.** The Go SDK keeps the secret's `createdAt` and `expiresAt` as int64 UNIX epochs in seconds, noting that the console shows them in milliseconds and that a 32-bit int would fail to decode expiries past January 2038 on 386 and arm builds. [zidentity.api-clients.secrets:go-timestamps-seconds]

**Rotation.** A client can hold at most two secrets: adding a third replaces the most recent one, so at any time there are only two. [zidentity.api-clients.secrets:two-secret-rotation] Whether deleting a secret also revokes the tokens issued with it is open [gap:zidentity.api-clients.secrets:secret-delete-token-effect]. A deleted secret cannot be recovered. [zidentity.api-clients.secrets:delete-unrecoverable]

What to check:
1. For a lost secret, whether a new one was added (the API returns its value once) rather than read back from the list, which is masked.
2. Before adding a secret, how many the client already has; a third replaces the most recent one.
3. Whether `expiresAt` was sent as an integer epoch in seconds, not a string or milliseconds.
4. Rotate a client secret in this order: add the new secret, update the consumer, confirm a call succeeds, then delete the old secret. A deleted secret cannot be recovered.
5. Set the rotation schedule on the operator's own terms: the 90-day and yearly cadences in the legacy notes are not captured.

Not known (open gaps):
- Which `expiresAt` values the create-secret API accepts [gap:zidentity.api-clients.secrets:expires-at-range] (data gap): filled by operator; settled by lab-test. Blocks: automating secret rotation through the API
- Whether deleting or replacing a secret revokes tokens already issued with it [gap:zidentity.api-clients.secrets:secret-delete-token-effect]: settled by lab-test. Blocks: planning a rotation cut-over without a service gap
- Whether a rotated client secret takes time to propagate [gap:zidentity.api-clients.secrets:propagation-delay]: settled by source-read
- Whether an old client secret stays valid after rotation [gap:zidentity.api-clients.secrets:secret-grace-window]: settled by source-read
- Recommended rotation cadence for client secrets and JWT keys [gap:zidentity.api-clients.secrets:rotation-cadence]: settled by source-read
