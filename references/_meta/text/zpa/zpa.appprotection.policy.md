# AppProtection policy rules: actions, criteria and operators (zpa.appprotection.policy)
Also called: appprotection policy rule; inspect or bypass inspection; appprotection criteria; copy criteria from access policy; appprotection rule order; zpa inspection policy rule; appprotection policy limits

A rule decides which traffic is inspected, and by which profile. AppProtection policy rules set up AppProtection controls for Private Access web applications, and apply a previously created profile with its actions. [zpa.appprotection.policy:rules-purpose] A rule's action is Inspect or Bypass Inspection, and a profile is chosen for the rule. [zpa.appprotection.policy:rule-actions]

**Order.** Private Access applies AppProtection policy rules in the order they are listed, and the order number is changed by entering a new value. [zpa.appprotection.policy:rule-order-listed] Private Access policy rules, a set that includes AppProtection policy, are evaluated top-down and the first matching rule is enforced. [zpa.appprotection.policy:first-match]

**Reusing access criteria.** AppProtection policy works similarly to access policy, and a rule can copy its criteria from an existing access policy rule and then adjust them, which lets the two policies be matched up. [zpa.appprotection.policy:reuse-access-criteria] Whether access policy and AppProtection policy are evaluated independently on one connection is open [gap:zpa.appprotection.policy:independent-of-access-policy].

**Criteria.** A user's application request must match all the conditions within an AppProtection policy rule. [zpa.appprotection.policy:criteria-all-match] The criteria types are Applications (segments and segment groups), Client Connector Posture Profiles, Client Connector Trusted Networks, Client Types, Cloud Connector Groups, External IAM IdP, Federated Applications, Machine Groups, Platforms, and SAML and SCIM Attributes. [zpa.appprotection.policy:criteria-types] A rule can have up to 10 condition sets, and up to 10 Client Connector Posture Profile condition sets. [zpa.appprotection.policy:condition-set-limits]

**Operators.** [Multiple client types, platforms, trusted networks, application segments or segment groups in one rule are joined by OR, and multiple SAML or SCIM attributes, groups or IdPs are joined by OR by default, with a toggle to AND.](kb:zpa.policy.conditions:or-within-most-criteria) [Multiple Cloud Connector groups and multiple posture profile condition sets in one rule are joined by AND, while profiles inside one condition set are joined by OR by default with a toggle to AND.](kb:zpa.policy.conditions:and-within-some-criteria)

**Combinations that are not allowed.** A rule with the Web Browser or Internet & SaaS Service Edge client type cannot also use posture profile or trusted network criteria, which only work with Client Connector. [zpa.appprotection.policy:client-type-exclusions] The Cloud Connector Group criteria cannot be combined with SAML and SCIM Attributes criteria. [zpa.appprotection.policy:cc-group-vs-saml] [In the console, when a machine group is selected in an access policy or AppProtection policy rule, the Machine Tunnel client type is also required.](kb:zpa.machine-groups.policy-use:console-pairs-client-type)

**Values.** The valid client types are Client Connector, Cloud Browser, Cloud Connector, Machine Tunnel, Web Browser, and Internet & SaaS (ZIA) Service Edge. [zpa.appprotection.policy:client-types] The platform values are Windows, macOS, Linux, iOS and Android. [zpa.appprotection.policy:platform-values] With a subscription to Authentication Service for users, SAML and SCIM Attributes is replaced by Session and User Attributes. [zpa.appprotection.policy:auth-service-attributes]

**Limits.** The limit for AppProtection policy is 500 policy rules, with 1,000 application segments per policy rule. [zpa.appprotection.policy:limits]

**Dynamic rules.** Once access policies are created and an AppProtection profile is set up, dynamic rules can automatically create AppProtection policies to inspect the traffic of the domains. Access policies enabled with privileged approvals do not appear, as dynamic rules bypass them. [zpa.appprotection.policy:dynamic-rules] A dynamic rule's AppProtection Profile Type is Default or Existing: Default gives an error if a default AppProtection profile already exists, and Existing requires selecting an existing AppProtection profile. The Auto create AppProtection policies checkbox creates the policies automatically. [zpa.appprotection.policy:dynamic-profile-type] What the Default type creates, and whether a dynamic rule tracks later access policy changes, is open [gap:zpa.appprotection.policy:dynamic-rule-behavior].

**Editing.** Editing application segments that have Active Directory Inspection enabled shows a warning that the application segments and segment groups are inspected for Active Directory Protection traffic. [zpa.appprotection.policy:edit-ad-warning]

Profiles a rule can select: [AppProtection profiles: control selection, paranoia level, actions and the default profile](kb:zpa.appprotection.profiles). The segment-side switch that makes traffic eligible: [Enabling AppProtection on an application segment](kb:zpa.appprotection.segment-opt-in). Rule-order behavior of the Terraform provider is in [How the ZPA Terraform provider applies policy rule order (BulkReorder)](kb:zpa.terraform.rule-order) and its write behavior in [What the ZPA Terraform provider sends and loses when writing policy rules](kb:zpa.terraform.policy-rule-writes).

What to check:
1. The rule action, and the profile when the action is Inspect.
2. Whether the rule order in the console puts the rule ahead of the one expected to match.
3. Each criterion type on the rule and the operator between its values, since criteria must all match.
4. Exclusions: Web Browser and Internet & SaaS Service Edge client types with posture or trusted networks, Cloud Connector groups with SAML or SCIM, machine groups without Machine Tunnel.
5. The rule count against the limits.
