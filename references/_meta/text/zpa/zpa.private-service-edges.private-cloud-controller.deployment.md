# Private Cloud Controller sizing, network requirements, platforms and enrollment (zpa.private-service-edges.private-cloud-controller.deployment)
Also called: private cloud controller sizing; private cloud controller prerequisites; private cloud controller deployment guide; deploying private cloud controllers; pcc software by platform

Deploying a Private Cloud Controller means installing and enrolling it, which lets it obtain a TLS client certificate to authenticate itself to the Private Access cloud: it generates a local private key encrypted with a hardware fingerprint, uses it to generate a Certificate Signing Request, and uses a provisioning key to authenticate the CSR to the Private Access cloud. The signed certificate is pinned to the controller's hardware fingerprint, and once enrolled the controller is paired with a single customer account and cannot be enrolled again. [zpa.private-service-edges.private-cloud-controller.deployment:enrollment] To add a Private Cloud Controller to an existing group with a provisioning key, choose an existing provisioning key associated with the appropriate Private Cloud Controller group, then copy the key and enter it when deploying the Private Cloud Controller. [zpa.private-service-edges.private-cloud-controller.deployment:add-to-existing-group]

**Sizing and count.** The prerequisites page says each Private Cloud Controller supports between 100 to 250 Mbps of SIEM throughput; its table gives, by number of users: up to 2,000 users need 16 GB and 4 vCPUs or CPUs (100 Mbps), up to 4,000 need 32 GB and 8 (150 Mbps), up to 10,000 need 64 GB and 16 (250 Mbps). Disk space is 64 GB thin provisioned for all deployment platforms and the minimum is 1 NIC. [zpa.private-service-edges.private-cloud-controller.deployment:sizing] Zscaler recommends that Private Cloud Controllers be deployed in pairs (N+1), where N is the number of controllers the sizing requirements give, to ensure continuous availability during software upgrades. [zpa.private-service-edges.private-cloud-controller.deployment:pairs] More Private Cloud Controllers can be deployed at any time using the same provisioning key to add them to the existing group. Throughput numbers are aggregate (total inbound and outbound), and Zscaler recommends more controllers with lower specifications rather than fewer with higher specifications. [zpa.private-service-edges.private-cloud-controller.deployment:scale-out] The AWS guide ties 400 to 500 Mbps per controller to about 50% CPU [zpa.private-service-edges.private-cloud-controller.deployment:aws-auto-scaling], which the same page's 250 Mbps SIEM throughput does not match [divergence:zpa.private-service-edges.private-cloud-controller.deployment:aws-throughput]. No PCC page gives a CPU-based scaling signal tied to SIEM throughput [gap:zpa.private-service-edges.private-cloud-controller.deployment:pcc-scaling-signal].

**Network.** Depending on the deployment use case, each Private Cloud Controller must be able to accept incoming connections from either internal or external sources or both on TCP port 443. Controllers are reachable over the internet for remote users in Business Continuity. For each controller placed behind a firewall, the conditions are that it accepts incoming connections from internal sources, remote users and on-premises users (as applicable and dependent on the use case) on TCP port 443 and has a unique private IP address that can be reached over the internal network. [zpa.private-service-edges.private-cloud-controller.deployment:inbound-443] In the scenario where a Private Cloud Controller is deployed behind a firewall, the firewall performs destination network address translation (DNAT) for its private IP address, and the public IP address advertised by the firewall must be configured as a publish IP address of the respective controller; in the case of disaster recovery this IP address must be added as the A record for that controller. [zpa.private-service-edges.private-cloud-controller.deployment:dnat-publish-ip] Firewalls must be configured to let the Private Cloud Controller establish outbound connections to the IP addresses of the Public Service Edge for Private Access, and inbound connections from App Connectors, Private Service Edges and Client Connector. All Zscaler data centers containing Public Service Edges must be allowed, and Zscaler gives a 90-day notice for activating additional IP CIDR ranges. Controllers do not function if the TLS certificates presented by the Public Service Edges do not cryptographically verify against Zscaler-trusted public keys, and *.prod.zpath.net should be in the SSL bypass list for traffic originating from the controller. [zpa.private-service-edges.private-cloud-controller.deployment:firewall] After a Private Cloud Controller is enrolled, an outbound TLS tunnel over TCP port 443 is established to the Private Access cloud infrastructure, carrying periodic keepalives to the Public Service Edge, tenant-specific configuration and policy download, and controller software upgrades completed on a weekly schedule. [zpa.private-service-edges.private-cloud-controller.deployment:control-tunnel] Which sources reach a controller differs between pages [divergence:zpa.private-service-edges.private-cloud-controller.deployment:inbound-sources]. Where the publish IP is set is open [gap:zpa.private-service-edges.private-cloud-controller.deployment:publish-ip-location].

**Prerequisites.** The prerequisites page lists an Intel x86_64/AMD 64-based architecture, root or sudo access to configure a new package repository and install packages, DNS resolution and network access, a static MAC address, and either an OAuth 2.0 enrollment token from a hyperscaler marketplace, virtual image or RPM installer provided by Zscaler or a provisioning key from the Admin Console. OAuth 2.0 enrollment needs Manager software and Private Cloud Controller version 25.47.3 or later, and a controller that only has an IPv6 address cannot access the OAuth server. [zpa.private-service-edges.private-cloud-controller.deployment:platform-prereqs] Private Cloud Controllers require that Client Connector is at least on version 4.6 or later for Windows. [zpa.private-service-edges.private-cloud-controller.deployment:client-connector-version]

**Platforms.** Private Cloud Controllers are supported on Linux operating systems. The software page lists a STIG OVA for VMware, STIG Marketplace images for Amazon Web Services, Google Cloud Platform and Microsoft Azure, and an RPM package for RHEL 9-based deployments. [zpa.private-service-edges.private-cloud-controller.deployment:software-by-platform] Azure has an image but no captured guide [gap:zpa.private-service-edges.private-cloud-controller.deployment:azure-guide].

**What differs by platform.** The Linux guide's repository definition uses baseurl https://yum.private.zscaler.com/yum/el9 with gpgcheck=1 and has the reader ensure that the GPG fingerprint matches (a6fe 2422 fce7 e8ac 672e 9e51 644e a315 8765 e1dd). The provisioning key file is created with 644 permissions at /opt/zscaler/var/pcc/provision_key. If the controller cannot download the RPM package, the package is downloaded on a server and the steps run iptables -I INPUT 1 -j ACCEPT. [zpa.private-service-edges.private-cloud-controller.deployment:linux-rpm] The Linux guide verifies memory against the prerequisites sizing: total available memory should be at least 16 GB, 32 GB or 64 GB as shown in the total column. [zpa.private-service-edges.private-cloud-controller.deployment:verify-memory] The AWS guide says Private Cloud Controllers must be deployed in the customer's VPCs, and that for each VPC there should be a pair deployed for resilience and scalability; Zscaler automatically load balances across them. Their security group should accept incoming connections from Client Connector and Public Service Edges, permit inbound and outbound access on port 443 and allow inbound SSH. The instance is launched from the AWS Marketplace AMIs, and Auto-assign Public IP set to Disable assigns a private IP address, which is recommended. [zpa.private-service-edges.private-cloud-controller.deployment:aws-placement] In the AWS guide's auto scaling steps, the desired capacity is 2 for the initial number of instances to launch and the target value is 50. The guide says each Private Cloud Controller is capable of passing 400 to 500 Mbps traffic, which occurs when it runs at about 50% CPU utilization, and that OAuth 2.0 enrollment is unavailable with auto scaling. [zpa.private-service-edges.private-cloud-controller.deployment:aws-auto-scaling] The AWS guide says the image attempts to use OAuth enrollment tokens by default but applies a provisioning key first if one is available. The token appears after a login prompt in the software component's virtual serial console, is valid for 2 hours, and is entered on the Add Private Cloud Controller page. [zpa.private-service-edges.private-cloud-controller.deployment:oauth-token] The GCP guide says the Private Cloud Controller must have ingress and egress traffic directions on TCP port 22 for SSH, and egress traffic directions on TCP port 443 to reach Private Access. Its autoscaling steps select a minimum and maximum of 2 and 4 instances, enter 80 in the Target CPU utilization field and 300 in the Initialization period field. [zpa.private-service-edges.private-cloud-controller.deployment:gcp-network-autoscaling] The GCP machine types are worded two ways [divergence:zpa.private-service-edges.private-cloud-controller.deployment:gcp-machine-types]. The GCP firewall sentence is open [gap:zpa.private-service-edges.private-cloud-controller.deployment:gcp-firewall-wording]. The VMware guide requires VMware vCenter version ESXi 7.0 Update 2 or later, and says RHEL 9 deployments are supported on ESXi 7.0 Update 2 or later. The guide has the reader enter the Private Cloud Controller image URL https://dist.private.zscaler.com/vms/VMware/2026.07/zpa-pcc-el9-2026.07.ova. [zpa.private-service-edges.private-cloud-controller.deployment:vmware]

What to check:
1. Which throughput figure a controller's sizing rests on: the prerequisites page's SIEM throughput table or the AWS guide's 400 to 500 Mbps, which the pages do not reconcile.
2. Whether the firewall allows the controller's outbound connections to the Public Service Edges and does not intercept TLS for traffic from it.
3. Whether the sources allowed in to a controller match the pages, which differ on Public Service Edges.
4. Whether the enrollment method is a provisioning key or an OAuth token, and the Manager software and controller version that OAuth enrollment needs.

Sources disagree (name both sides):
- The AWS Private Cloud Controller guide's auto scaling step gives 400 to 500 Mbps per controller; its prerequisites text gives up to 250 Mbps of SIEM throughput. [divergence:zpa.private-service-edges.private-cloud-controller.deployment:aws-throughput]
  - zscaler-help: Each Private Cloud Controller supports up to 250 Mbps SIEM throughput, with aggregate throughput numbers.
  - zscaler-help: Each Private Cloud Controller is capable of passing 400 to 500 Mbps traffic.
  Impact: The page gives 250 Mbps of SIEM throughput as the controller's support figure and 400 to 500 Mbps of traffic in the auto scaling step; it does not say how the two measures relate.
- The AWS guide lists Public Service Edges among the sources a Private Cloud Controller accepts connections from; the prerequisites page makes Public Service Edges an outbound destination. [divergence:zpa.private-service-edges.private-cloud-controller.deployment:inbound-sources]
  - zscaler-help: The security groups accept incoming connections from Client Connector and Public Service Edges.
  - zscaler-help: Outbound connections go to the Public Service Edges; inbound connections come from App Connectors, Private Service Edges and Client Connector.
  - zscaler-help: Inbound connections come from end users, App Connectors and Private Service Edges on port 443.
  Impact: An AWS security group built from the AWS guide admits Public Service Edges inbound and omits App Connectors and Private Service Edges, which the prerequisites and Business Continuity pages list; the pages do not say which governs.
- The GCP guide recommends n2-standard-4 or n2-highcpu-8, but the list under it describes n2-standard-4 and n2-standard-8. [divergence:zpa.private-service-edges.private-cloud-controller.deployment:gcp-machine-types]
  - zscaler-help: The recommended machine types are n2-standard-4 or n2-highcpu-8.
  - zscaler-help: The specifications listed are for n2-standard-4 (4 vCPU, 2 core, 16 GB) and n2-standard-8 (8 vCPU, 4 core, 32 GB).
  Impact: The page gives no specification for n2-highcpu-8 and recommends no n2-standard-8, so the machine type for a larger controller is unclear.
