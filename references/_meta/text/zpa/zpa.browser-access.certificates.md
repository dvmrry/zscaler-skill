# Certificates for Browser Access applications: wildcards, managed and custom (zpa.browser-access.certificates)
Also called: browser access wildcard certificate; wildcard certificate one level; app1.local.example.com certificate; browser access zscaler managed certificate; browser access cname; browser access web server certificate; wildcard cert does not cover subdomain

Which certificate a Browser Access application presents decides whether a wildcard application can be served. Wildcard certificates have a one-level rule that wildcard applications do not.

**Wildcard certificates.** A wildcard certificate can be used for multiple FQDNs within one application segment or across several application segments, for example the same *.example.com certificate on a segment for app1.example.com and another for app2.example.com. [zpa.browser-access.certificates:wildcard-multiple-fqdns] A wildcard application such as *.example.com matches app1.example.com, app2.example.com and app1.local.example.com, but a *.example.com wildcard certificate matches only one level. It does not match app1.local.example.com, and Private Access does not consider it valid for that name. [zpa.browser-access.certificates:wildcard-one-level] To enable Browser Access for a particular subdomain such as local.example.com, define a separate wildcard application (*.local.example.com) in an application segment that includes the equivalent wildcard certificate. [zpa.browser-access.certificates:subdomain-needs-own-wildcard]

**Certificate type.** For each Browser Access application the admin chooses either a Custom certificate, where a web server certificate is selected, or a Zscaler-managed certificate. [zpa.browser-access.certificates:certificate-type] Enrollment (CA) certificates cannot be used for Browser Access. [zpa.browser-access.certificates:no-enrollment-certificates]

**Uploading web server certificates.** If the web server certificate is signed by a public certificate authority, Private Access encrypts traffic using HTTPS; if it is self-signed, or Private Access cannot verify the chain of trust to the public CA, HTTP is used. The upload page gives the same rule as the protocol to select for a Browser Access application, and adds that Private Access inserts a Via header in HTTP requests (example: Via: 1.1 Zscaler-p.zpa-auth.net). [zpa.browser-access.certificates:https-or-http] An uploaded web server certificate must be a single Base64-encoded ASCII .pem file that includes the certificate and unencrypted private key. Up to 1,000 certificates can be uploaded, and the ranges page lists the same figure. Once uploaded, a certificate can be selected when defining an application within an application segment. [zpa.browser-access.certificates:upload-format-and-limit] A web server CSR's subject has the form CN=<Common Name>,O=<Organization>,ST=<State>,C=<Country>,L=<Location>,OU=<Organizational Unit>, with CN listed first and the other attributes optional. The common name does not need to be a wildcard domain. A SAN, which takes domains only, lets the certificate cover multiple hostnames. The certificate can be signed by a public CA or be self-signed with trust established by the organization's PKI. [zpa.browser-access.certificates:csr-subject-san] An expired web server certificate can be replaced only by uploading a new one. [zpa.browser-access.certificates:replace-expired] Whether a web server certificate is required is stated two ways [divergence:zpa.browser-access.certificates:web-server-cert-required]. Enrollment certificates are in [Enrollment (CA) certificates in Private Access](kb:zpa.certificates.enrollment); the certificate overview is [ZPA certificates: enrollment (CA) certificates and web server certificates](kb:zpa.certificates).

**CNAME and DNS.** After saving a segment with a Browser Access application, the admin copies its CNAME from the Browser Access page. With a custom certificate the CNAME goes into public DNS and the application FQDN must resolve to it, while with a Zscaler-managed certificate Zscaler manages the public DNS entries and verifies the FQDN. The page's example record is marketing.mockcompany.com. CNAME 3077.217246660302995456.h.d.zpa-app.net. [zpa.browser-access.certificates:cname-in-dns] Whether the CNAME reveals the Zscaler relationship is open [gap:zpa.browser-access.certificates:cname-visibility].

**Zscaler-managed certificates.** A Zscaler-managed certificate has prerequisites: the internal FQDN must be owned by the tenant and resolvable by the App Connectors, the web server must use relative URLs and be single-tenant with a single hostname, and wildcard cookies, wildcard Browser Access applications, IP-address applications and domains not registered to the account are not supported. [zpa.browser-access.certificates:managed-prerequisites] With a Zscaler-managed certificate, an internal application cannot send CORS requests to another internal Browser Access application, and an application that uses a Content-Security-Policy header must accept the external FQDN in the host and origin headers. [zpa.browser-access.certificates:managed-cors-and-csp] For Zscaler-managed Browser Access applications Zscaler rewrites headers: the Host header is set to host:port, the domain attribute is removed from Set-Cookie so only strict cookies are allowed, and the Origin header is set to scheme://host:port. [zpa.browser-access.certificates:managed-header-rewrites]

The external versus internal hostname choice is in [External versus internal hostname for a Browser Access application](kb:zpa.browser-access.hostnames).

What to check:
1. Whether the failing FQDN is more than one label below the wildcard certificate's name, in which case it needs its own *.sub wildcard application and certificate.
2. Whether the application uses a Zscaler-managed certificate, and if so whether it is a wildcard, an IP address or uses absolute URLs, none of which the managed path supports.
3. Whether the CNAME copied from the Browser Access page was added to public DNS for a custom certificate.

Sources disagree (name both sides):
- The web server CSR page says a web server certificate must be uploaded to enable Browser Access for an application, while the application segment page offers a Zscaler-managed certificate as an alternative to a custom one. [divergence:zpa.browser-access.certificates:web-server-cert-required]
  - zscaler-help: To enable Browser Access for an application, you must upload its web server certificate.
  - zscaler-help: The certificate type is Custom (with a web server certificate selected) or Managed, a Zscaler-managed certificate.
  Impact: The two pages differ on whether an upload is needed when a Zscaler-managed certificate is chosen; neither page says the CSR page's rule is limited to custom certificates.

Not known (open gaps):
- Hiding the Zscaler relationship behind a customer-managed CNAME [gap:zpa.browser-access.certificates:cname-visibility]: settled by source-read or operator-experience
