# Paging through ZPA lists with the Python SDK (zpa.sdk-python.pagination)
Also called: zpa python sdk pagination; page_size 500 zpa; resp.next StopIteration zpa; emergency access page_id; tag namespace list all pages; list returns only first page zpa; has_next totalPages; search name+EQ python; search quoted string zpa python; zpa next page starts at 2; plain search is exact name match

A ZPA list call in the Python SDK returns one page, and a few modules page differently from the rest. The contract is in [ZPA list pagination, search syntax and client-side filtering](kb:zpa.api.pagination), the Go equivalents are [How the Go SDK pages through ZPA, ZCC and ZTC lists, and when it stops early](kb:shared.sdk-go.list-pagination), and the ZIA behavior is [Paging through ZIA lists with the Python SDK](kb:zia.sdk-python.pagination).

**Walking pages.** [A Python SDK list method that supports pagination returns only the first page of results initially.](kb:zia.sdk-python.pagination:first-page-only) [The response object carries has_next and next methods to fetch the following pages.](kb:zia.sdk-python.pagination:has-next-next) For a ZPA response, `next()` increments the wrapper's page counter and sends it as the `page` parameter, and `has_next()` is true while that counter is below the `totalPages` read from the body (default 1). [zpa.sdk-python.pagination:next-uses-page] [`next()` raises `StopIteration("No more pages available.")` when `has_next()` is false, and otherwise returns the tuple (results, response, error).](kb:shared.sdk-python.pagination:next-stopiteration) The response object's page counter starts at 1 and, for ZPA, the next-page fetch increments it and sets the `page` parameter to the new value; ZIA (from `pageNumber`) and ZCC (from `page`) initialize the counter from a caller-supplied value. [zpa.sdk-python.pagination:zpa-next-counter] Only ZIA and ZCC initialize the page counter from a caller-supplied value, so a ZPA list that began at a later `page` continues from page 2 when followed with `next()`. [zpa.sdk-python.pagination:zpa-later-page-restarts] [The response object's search method applies a JMESPath expression to the current page of results only, so filtering across a collection means searching each page.](kb:shared.sdk-python.response-handling:search-current-page)

**Page size.** The response wrapper's table gives ZPA a page-size ceiling of 500 and the wrapper clamps a caller-supplied size into its internal limit, but for ZPA that limit is never sent: the first request carries the caller's raw `pagesize`, and the ZPA `next()` branch reuses the same parameters with only `page` changed. The limit is read only in the ZIA next-page branch and in the has-next fallback that ZPA responses never reach, since ZPA's has-next check compares the page with the total page count. [zpa.sdk-python.pagination:page-size-clamp] When the caller gives no page size the wrapper keeps none and leaves the API default in force; the table default of 100 is not applied. [zpa.sdk-python.pagination:no-size-sent] For ZPA requests the executor sends the page size as the lowercase query key `pagesize`, except on the emergencyAccess/users endpoint, where it is renamed `pageSize`. [zpa.sdk-python.pagination:pagesize-lowercase] A Python `page_size` argument, including the `page_size` that the MCP list tools forward to the SDK, therefore reaches a ZPA list endpoint as the `pagesize` query parameter that the contract names; the two spellings are an argument-versus-wire difference, not a disagreement about the wire. [zpa.sdk-python.pagination:arg-name-not-wire-name] The ZPA list-method docstrings of `list_scim_groups`, `list_connectors` and `list_groups` (server groups) state a default page size of 20 and a maximum of 500. [zpa.sdk-python.pagination:docstring-default-20] The administrator list docstring says the maximum page size is 200, and the SDK enforces no ceiling for that call: `list_administrators` passes the caller's query parameters to the executor, which sends the page size as given. [zpa.sdk-python.pagination:admin-page-ceiling] The SDK's default numbers disagree: [divergence:zpa.sdk-python.pagination:default-page-size]

**Search strings.** The executor strips surrounding whitespace from a ZPA `search` string and checks it, ignoring case, for a filter operator: +EQ+, +NE+, +GT+, +LT+, +GE+, +LE+, +CONTAINS+, +STARTSWITH+, +ENDSWITH+, or the URL-encoded %2BEQ%2B, %2BNE%2B, %2BGT%2B, %2BLT%2B, %2BGE%2B and %2BLE%2B. A string with none is rewritten to `name+EQ+<value>`; a string with one is sent as stripped. [zpa.sdk-python.pagination:search-name-wrap] Before that check, a ZPA search value wrapped in double quotes has the quotes removed. [zpa.sdk-python.pagination:search-quotes-stripped] The contract's search format is [ZPA search strings follow the format fieldName operator fieldValue, and the Python SDK converts a plain name into name+EQ+<name>.](kb:zpa.api.pagination:search-format), and the Go helper does something similar: [ZPA Go SDK service functions that return partial results, send wrong keys, or reject valid input](kb:zpa.sdk-go.service-defects).

**Emergency access.** The page key the SDK documents for the emergency-access user list is [The Python ZPA services document the pagination key as page everywhere except emergency_access.py, which documents page_id.](kb:zpa.emergency-access.api-surface:only-page-id-service). Following an emergency-access list with `next()` advances the `page` parameter, not `pageId`. [zpa.sdk-python.pagination:emergency-next-page]

**POST-search lists.** The module-level helper `_post_search_all_pages` in `tag_namespace.py` posts a `pageBy` body with a fixed page size of 100, appends every page, and stops when the page number reaches the `totalPages` of the body (default 1). [zpa.sdk-python.pagination:post-search-helper] `list_tag_groups` builds a fixed name-ascending search body and passes only the microtenant ID as a request parameter, and returns what `_post_search_all_pages` returns; its body after the docstring, quoted in full, reads no other query parameter. [zpa.sdk-python.pagination:post-search-callers] The C2C IP range `list_ip_ranges` takes no arguments and issues a plain GET to `/ipRanges`; a POST search to `/ipRanges/search` is a separate method whose body the caller builds. [zpa.sdk-python.pagination:c2c-plain-list]

What to check:
1. Whether the caller loops on has_next and next, since a single list call is one page.
2. Whether a page_size above the documented ceiling was requested, since the SDK sends a ZPA page size as given without clamping it.
3. Whether the emergency-access list was paged with page_id and then continued with next.
4. Whether a tag namespace, group or key list passed filters that the POST-search wrapper ignores.
5. Whether a name search was an exact-name filter, because a plain string is rewritten to name+EQ+value.
6. Whether a follow-on page call started from the page the caller asked for, because the counter always starts at 1.
