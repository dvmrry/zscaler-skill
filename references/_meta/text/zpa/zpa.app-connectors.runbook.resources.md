# How the App Connector runbook checks high CPU, memory and disk utilization: process checks, thresholds, local memory endpoints and cleanup (zpa.app-connectors.runbook.resources)
Also called: Managing high CPU, memory, and disk utilization concerns

**CPU.** For high CPU the runbook uses ps aux --sort=-pcpu | head -5: if zpa-connector-child is not at the top and another process consumes the CPU, the problem might not be related to the Zscaler service. [zpa.app-connectors.runbook.resources:cpu-process-check] Top can show CPU utilization above 100% on a multi-core host; the runbook's example is 4 cores with top showing 200%, which means 50%, and lscpu gives the number of cores. [zpa.app-connectors.runbook.resources:cpu-multicore] When CPU utilization is consistently high (more than 80% normalized CPU) over a sustained period and affects users, the runbook says to collect the data listed under "Collecting Logs from the App Connector" and raise a Zscaler Support case; that list shows vmstat output and the memory information read from curl -s 127.0.0.1:9000/memory/status and curl -s 127.0.0.1:9000/memory/argo. [zpa.app-connectors.runbook.resources:cpu-support-threshold] [gap:zpa.app-connectors.runbook.resources:memory-threshold] The group-level CPU headroom limit is in [Monitoring App Connector performance: CPU, memory, throughput, source ports, application targets, disk and file descriptors](kb:zpa.app-connectors.performance).

**Memory.** Memory information for the App Connector processes is read on the host with curl -s 127.0.0.1:9000/memory/status and curl -s 127.0.0.1:9000/memory/argo. [zpa.app-connectors.runbook.resources:local-memory-endpoints] When memory is reported high on the Private Access Health dashboard or an alert fires for high memory utilization, the runbook runs cat /proc/meminfo, and treats a larger gap between MemTotal and MemAvailable (relative to total RAM) as possible memory pressure. [zpa.app-connectors.runbook.resources:meminfo] To find which process uses memory the runbook runs ps aux --sort=-pmem | head -5 and checks for third-party processes; in its example omiagent uses 84.7% of memory. [zpa.app-connectors.runbook.resources:memory-by-process] To reduce memory use on a connector host the runbook lists increasing host memory, deploying more App Connectors into the group, and deploying dedicated App Connector Groups for specific application segments; if these do not help, collect the memory utilization output (the runbook lists lscpu, ps aux --sort=-pmem, curl -s 127.0.0.1:9000/memory/status, curl -s 127.0.0.1:9000/memory/arg and sudo journalctl > dump-of-journalctl.txt) and raise a Support case. [zpa.app-connectors.runbook.resources:memory-remedies]

**Disk.** Disk utilization issues can make App Connectors throw errors, fail upgrades or hit logging failures; the runbook says to keep at least 100 MB free (otherwise the App Connector might automatically restart) and to treat Use% near 100% on critical filesystems such as / or /var as a risk of disk exhaustion. [zpa.app-connectors.runbook.resources:disk-impact-and-floor] For disk cleanup the runbook uses sudo journalctl --vacuum-size=1G to clear space in /var/log/journal, prevents Zscaler processes from using syslogd (journald already stores their logs) and restarts rsyslogd, and, because other processes on the Linux box can still log and use disk space, gives a daily logrotate configuration keeping 7 backlogs in /etc/logrotate.conf as an example. [zpa.app-connectors.runbook.resources:disk-cleanup]

Not known (open gaps):
- What MemTotal to MemAvailable gap counts as memory pressure, and how long CPU must stay above 80% [gap:zpa.app-connectors.runbook.resources:memory-threshold]: settled by support-ticket or source-read
