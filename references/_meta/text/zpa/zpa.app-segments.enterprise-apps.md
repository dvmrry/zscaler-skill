# Configuring application segments for specific enterprise applications: unified communications, FTP, RDP, DFS with Kerberos, Windows domain join, Citrix, GPO, Configuration Manager, IWA with Kerberos reauthentication and SAP (zpa.app-segments.enterprise-apps)
Also called: unified communications bypass; UC traffic; passive FTP; RDP application segment; distributed file servers; DFS Kerberos; SRV records; domain join remote users; Citrix ICA; GPO traffic; Configuration Manager; SCCM; IWA Kerberos reauthentication; SAP application segment

Unified communications (UC) traffic for off-network and on-network users should use edge servers, externally accessible Session Border Controllers or UC gateways, and Zscaler recommends not sending UC traffic to Private Access, as this has the potential to add latency and jitter. If a wildcard or IP subnet (for example *.company.com or 10.0.0.0/8) is used to discover applications through Private Access, the UC traffic applications must be defined with bypass settings that exclude the hosts from being discovered, and the page selects Always from the Bypass menu. [zpa.app-segments.enterprise-apps:unified-communications]

**FTP and RDP.** Private Access only supports passive FTP mode; active mode, which needs a TCP connection initiated from the server to the client, is not supported, and an attempt fails if an FTP client tries active mode or sends an active mode request in parallel to the passive request. Only IP-based passive FTP applications are supported; the segment uses TCP port ranges 1 to 65535, App Connector health reporting None because each FTP data channel is pseudo-random and opened per client, and Bypass Use Client Forwarding Policy with a client forwarding policy rule Forward to ZPA. [zpa.app-segments.enterprise-apps:ftp-passive-only] Zscaler recommends that users access a proper FTP client (for example FireFTP, FileZilla or CuteFTP), because command line FTP on Windows and macOS does not implement passive FTP correctly. [zpa.app-segments.enterprise-apps:ftp-clients] For RDP applications, TCP port ranges are entered under Client Connector Access, the UDP port ranges are left empty, and Zscaler recommends that only TCP port ranges be used. [zpa.app-segments.enterprise-apps:rdp-tcp-only] The RDP article recommends Client Connector version 2.0.1 or later with the Windows Filter Driver enabled. [zpa.app-segments.enterprise-apps:rdp-legacy-client-version]

**Distributed file servers.** Access to Distributed File Servers while using Kerberos for authentication can be configured with a wildcard domain, with separate applications for DFS (with Kerberos) and SRV resolution (when the same server is both file server and domain controller), or with separate applications for file servers, domain controllers and SRV resolution (when they are on separate servers). Private Access requires an application defined as a wildcard with any port to resolve SRV records, for which the page uses a dummy port (Port 1). [zpa.app-segments.enterprise-apps:dfs-kerberos] The DFS article lists these ports: TCP 88 (Kerberos), 464 (Kerberos Password Change), 389 (LDAP), 3268 (Global Catalog), 3269 (Global Catalog SSL, optional), 135 (MSRPC), 139 and 445 (CIFS); and UDP 88 (Kerberos), 464 (Kerberos Password Change), 389 (LDAP), 636 (LDAPS, optional), 138 (NetBT datagram, file server) and 123 (NTP). It lists no UDP 445. [zpa.app-segments.enterprise-apps:dfs-ports] Zscaler recommends a dedicated App Connector group for the File Server applications, because these applications can be latency sensitive and experience performance degradation if the associated App Connectors also provide access to other applications. [zpa.app-segments.enterprise-apps:dfs-dedicated-connectors] The ports for LDAPS differ between this article and the IWA reauthentication one [divergence:zpa.app-segments.enterprise-apps:port-636].

**Windows domain join and GPO.** For remote users on Windows devices logging in to an Active Directory domain for the first time, the device is provisioned by IT with a local account; the user logs in with it, enrolls in Private Access using Client Connector on the local account, updates cached credentials (a PowerShell script, the RunAs command in the Windows UI, or the RunAs command in a batch file), logs out of Client Connector and the local account, and then logs in with the Windows domain account. Using the Private Access connection the device can be joined to the domain, the remote user can log in and their credentials can be cached. [zpa.app-segments.enterprise-apps:windows-domain-join] A PowerShell script or the RunAs command can cache credentials on Windows 7 and 10; neither requires local administrator rights, and the local account can be limited so users do not continue to use it after enrollment. If the remote user's password is expired and they cannot log in to Windows, the password reset can be done in Private Access even when the device's Client Connector is not connected to Private Access. [zpa.app-segments.enterprise-apps:cached-credentials-methods] Microsoft Group Policy Object (GPO) network traffic is supported in Private Access with no additional configuration steps, and Zscaler recommends optimizing GPO performance in the environment if client-to-server network traffic is used. [zpa.app-segments.enterprise-apps:gpo-supported] Why Active Directory logon depends on a connection before login is still open [gap:zpa.app-segments.enterprise-apps:gpo-delivery-link].

**Citrix.** Citrix App and Desktop applications are not accessible through Private Access when a wildcard (for example *.domain.com) or FQDN application (for example citrix.domain.com) is defined within an application segment, because Citrix's default ICA file returns the IP address of the Citrix server in the data center that services the request. The page says to configure Citrix to return the servers' FQDN instead, which lets XenApp establish a new connection to the FQDN that Private Access passes through; reaching them by IP address is described as not an ideal solution. [zpa.app-segments.enterprise-apps:citrix-ica-fqdn]

**Configuration Manager.** Configuration Manager clients use boundary groups to identify the assigned distribution point; with a traditional VPN it is selected from the client IP address the VPN gateway assigns, but with Private Access the client is never placed on the network and never gets a data center network IP address. The article says Configuration Manager deployments can still be supported, with boundaries based on Active Directory site names (Zscaler's recommendation) or on a VPN interface. [zpa.app-segments.enterprise-apps:sccm-no-client-ip] A domain-joined device detects its Active Directory site with DNS SRV record requests and then an LDAP ping, which does not send the IP address in its header, so the domain controller relies on the packet's source IP; for Private Access that is the App Connector's source IP, which needs to be added to the Active Directory site. The article's steps are to create an application segment that resolves SRV records (a wildcard covering the root of the AD domains is recommended), add the interface IP address of every App Connector that requires Configuration Manager updates to the correct AD site, and confirm the boundary type is Active Directory site. [zpa.app-segments.enterprise-apps:sccm-ad-site-boundaries] Private Access does not create a local interface or assign a unique IP address by default, but can be configured to, creating a hidden virtual interface on the Windows endpoint whose IP follows the client-to-client IP bindings and can be used for Configuration Manager boundaries and client-to-client communication. Separate IP bindings are needed for each region assigned to a Configuration Manager boundary and distribution point group; the IP group uses Send Location Hint to Client Connector with a Location Hint matching the VPN Boundary name, and the boundary group type is VPN with the VPN setting Auto Detect and a Connection Name equal to the Location Hint text. [zpa.app-segments.enterprise-apps:sccm-vpn-boundaries] The Configuration Manager article lists these server-to-client and peer-to-peer scenarios as not supported: Client to Client (Wake On LAN), Site server to Client (Wake On LAN) and Configuration Manager console to Client (Remote Assistance - Remote Desktop Protocol); if they are required it says to use VPN for Legacy Apps. [zpa.app-segments.enterprise-apps:sccm-unsupported] The server-to-client article names Configuration Manager as a remote assistance tool [divergence:zpa.app-segments.enterprise-apps:sccm-remote-assistance]. How the hidden virtual interface is switched on is open [gap:zpa.app-segments.enterprise-apps:sccm-virtual-interface].

**IWA with Kerberos reauthentication.** When SSO uses Microsoft IWA with Kerberos, three application segments are created, each with Bypass set to On Corporate Network, one per domain if FQDNs are used: the ADFS FQDN on TCP 443, the LDAP/Active Directory FQDN on TCP and UDP 389, 636 and 3268-3269, and the KDC FQDN on TCP and UDP 88. A timeout policy rule with Authentication Timeout Never applies to their segment groups. Without the application segment and the associated timeout access policy rule, an error message displays in Client Connector whenever users attempt to reauthenticate. [zpa.app-segments.enterprise-apps:iwa-kerberos-reauth]

**SAP.** To control access to SAP applications, application segments must be created and DNS search domains configured. A wildcard with a wide port range allows broad access to SAP apps; the best-practice list says to create application segments using FQDNs, and to use a Wireshark trace or SAP configurations to identify the IP addresses of all SAP servers and create a segment that includes only those IP addresses and the appropriate TCP ports, without advertising the entire subnet range (for example 192.168.1.0/24). [zpa.app-segments.enterprise-apps:sap-segments] With the SAP client, the connection is made to an SAP message server that returns a list of applications, and after the user selects one the client attempts to connect to the hostname or IP address on a specified port. If the SAP hostname is not an FQDN a DNS search domain is required; if the client has no search suffix it cannot complete the FQDN and falls back to the IP address provided by the message server, which might not be desirable or routable over Private Access. Configuring SAP to provide an FQDN instead of a short name removes the need for the search domain. [zpa.app-segments.enterprise-apps:sap-dns-search-domain] If an access control list is configured in the SAP message server or application server, the App Connector IP addresses are added to it: Private Access performs a source NAT for the client so all traffic is seen from the App Connector's IP address, and because it load balances user requests across the App Connectors in the segment's App Connector group, Zscaler recommends adding the IP addresses of all of the App Connectors in that group to the ACL. [zpa.app-segments.enterprise-apps:sap-acl-connector-ips] The article recommends both per-application segments and a single segment [divergence:zpa.app-segments.enterprise-apps:sap-segment-layout].

Which segment wins when the same FQDN is defined twice is in [The application segment Bypass setting and how it ranks](kb:zpa.app-segments.bypass); the IP ranges and location hint are in [Peer-to-peer connectivity: client-to-client and server-to-client remote assistance, their requirements and setup, and Client Connector IP assignment](kb:zpa.peer-to-peer); the cases Configuration Manager cannot cover go to [ZPA VPN (for Legacy Apps): what it is, its components and where each question goes](kb:zpa.vpn).

What to check:
1. Whether UC applications sit in a segment with Bypass Always when a wildcard or subnet segment would otherwise discover them.
2. Whether an FTP failure is active mode or command-line FTP before looking at connectors, since only passive FTP is supported.
3. Whether Citrix is returning the server IP address in its ICA file rather than an FQDN.
4. Whether a Configuration Manager scenario is one the Configuration Manager article lists as unsupported, and how the server-to-client article treats remote assistance.
5. Whether a port list for LDAPS rests on the DFS article or the IWA article, since they differ on 636.
6. Whether SAP servers' ACLs include every App Connector in the group, since the servers see the connector's address.

Sources disagree (name both sides):
- The server-to-client article offers Configuration Manager remote assistance as its example tool; the Configuration Manager article lists console-to-client remote assistance as unsupported and sends it to VPN for Legacy Apps. [divergence:zpa.app-segments.enterprise-apps:sccm-remote-assistance]
  - zscaler-help: An admin uses Microsoft Configuration Manager to launch remote assistance to workstations using the FQDNs or virtual Zscaler IP addresses.
  - zscaler-help: Configuration Manager console to Client remote assistance over RDP is not supported.
  Impact: One page names Configuration Manager as the remote assistance tool for server-to-client, and the other lists console-to-client remote assistance over RDP as unsupported; neither page reconciles the two or says which is current. Do not state that Configuration Manager remote assistance works or does not work over server-to-client without both articles.
- The SAP article says it is more secure to create application segments for individual apps, and its best practices also say to create a single application segment for all SAP applications. [divergence:zpa.app-segments.enterprise-apps:sap-segment-layout]
  - zscaler-help: Segments for individual SAP apps are more secure than a wildcard with a wide port range.
  - zscaler-help: A single segment for all SAP applications lets Private Access load balance requests; multiple segments are needed where segmentation is required.
  Impact: The two recommendations are not reconciled in the article; keep both attributed and tie the choice to whether segmentation is required.
- The DFS article lists port 636 (LDAPS, optional) under UDP only; the IWA reauthentication article enters 636 in both the TCP and UDP port range fields. [divergence:zpa.app-segments.enterprise-apps:port-636]
  - zscaler-help: Port 636 is listed for LDAPS under UDP, as optional, and no TCP 636 appears in the list.
  - zscaler-help: Port 636 is entered in the TCP and UDP port range fields for the LDAP/Active Directory FQDN.
  Impact: The articles serve different setups, so the difference may be intentional; do not add TCP 636 to the DFS list or drop it from the IWA list on the strength of the other article.
