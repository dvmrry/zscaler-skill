# What Private Access is, its components, how a connection is made and the documented configuration order (zpa.overview)
Also called: what is private access; what is zpa; zpa components; zpa connection flow; zpa step-by-step configuration; zpa setup order; zpa vs vpn; universal ZTNA

Private Access (ZPA) gives users policy-based access only to the internal apps they need, as an alternative to VPNs; per the page, application access does not require network access. [zpa.overview:what-it-is] Private Access connects users to an enterprise's internal applications, while Internet & SaaS (ZIA) connects users to public applications on the internet. [zpa.overview:zia-contrast]

**What it offers.** Servers and applications can be discovered automatically when users request them or configured manually; the central Admin Console holds settings, policies and dashboards of users, apps and server health. [zpa.overview:discovery-and-visibility] Private Access is based on the Zero Trust Exchange, so no additional hardware or upgrades to existing hardware are required. [zpa.overview:no-extra-hardware] Users install Client Connector and log into an application using SAML 2.0-based SSO credentials. [zpa.overview:login-sso]

**Components.** Key components: Zscaler Client Connector on user devices; App Connectors (lightweight VMs in the data centers hosting the apps; the step-by-step guide also names virtual private clouds) that connect to Public or Private Service Edges and accept no inbound connections; and the global Zscaler cloud, which stitches all components together. The Central Authority provides a central location for software updates and policy and configuration settings; the Public or Private Service Edges enforce user policies and provide secure transport to the App Connectors. [zpa.overview:components] The connectors are in [ZPA App Connectors](kb:zpa.app-connectors) and the edges in [ZPA Private Service Edges](kb:zpa.private-service-edges).

**How a connection is made.** When a user requests an internal application, Client Connector uses geolocation to find the closest Public or Private Service Edge, presents its certificate and establishes a tunnel; the Service Edge retrieves the user's policies from the CA and contacts the appropriate App Connector, which presents its certificate before the Service Edge lets it connect. [zpa.overview:connection-flow] The closest edge is not always the one used: see [A Private Service Edge group can be mapped to the organization's trusted networks; the mapping prioritizes Private Service Edges matching a trusted network when users connect from it.](kb:zpa.private-service-edges.client-selection:trusted-network-priority), [Grace distance (console: Public Service Edge Proximity Override) allows a Private Service Edge group within a specified distance of the user to be prioritized over a closer Public Service Edge for Private Access.](kb:zpa.private-service-edges.client-selection:grace-distance) and [A group that has trusted networks mapped but not Publicly Accessible is not offered to users outside those trusted networks.](kb:zpa.private-service-edges.client-selection:outside-users-excluded). Per this page, once the connection between the user's device and the application is established, traffic traversing the solution remains completely isolated, including from Zscaler, because Private Access is built on Zero Trust for private applications. [zpa.overview:traffic-isolation] Standard traffic's in-memory handling at the Service Edge is in [By default, traffic between Zscaler Client Connector and an App Connector is encrypted using TLS 1.2 tunnels between Client Connector and the Public or Private Service Edge, and between the App Connector and the Service Edge; standard Private Access application traffic is not encrypted by Zscaler as it transits the Service Edge in memory and is never written to disk. Enabling double encryption when defining an application adds a layer of encryption inside the outer TLS tunnels, so that traffic is encrypted in memory as it transits the Service Edge.](kb:zpa.app-segments.double-encryption:default-tls-and-in-memory).

**Reference architectures.** Per the user-to-app segmentation reference architecture, VPNs assign a user an IP address and place the user on the network, while ZPA lets users connect only to allowed applications, with no access to adjacent applications or systems. [zpa.overview:vpn-vs-zpa-segmentation] The Universal ZTNA reference architecture describes ZTNA, also known as the software-defined perimeter (SDP), as operating on an adaptive trust model in which trust is never implicit and access is granted on a least-privileged basis defined by granular policies; ZPA delivers ZTNA for internal applications in public clouds, private clouds and data centers. [zpa.overview:ztna-definition] The architecture pages hold no configuration values [gap:zpa.overview:architecture-detail].

**Configuration order.** The step-by-step guide orders configuration as: (1) company and administrator information, (2) certificates, (3) SAML single sign-on, (4) Zscaler Client Connector, (5) App Connectors; certificates authenticate the App Connector and the user's device before each connection and provide access to web applications via internet browser. [zpa.overview:config-order-1-5] The guide continues: (6) applications, (7) SAML attributes, (8) policies (access, timeout, client forwarding), (9) log streaming (LSS), (10) user portals; users cannot access applications until policies are configured. [zpa.overview:config-order-6-10] Why the guide orders the steps this way is open [gap:zpa.overview:config-order-reason]. The detail for steps 2, 3, 5, 6, 8 and 9 is in [ZPA certificates: enrollment (CA) certificates and web server certificates](kb:zpa.certificates), [ZPA authentication: IdP configuration, authentication settings and user risk scores](kb:zpa.authentication), [ZPA App Connectors](kb:zpa.app-connectors), [ZPA application segments](kb:zpa.app-segments), [ZPA policy evaluation](kb:zpa.policy) and [ZPA log receivers and the Log Streaming Service](kb:zpa.log-receivers); steps 1, 4, 7 and 10 have no linked subject here.

What to check:
1. Whether a user who cannot reach an application has a policy configured for it, since users cannot access applications until policies are configured.
2. Whether the connection path involves a Public or a Private Service Edge; the page says Client Connector locates the closest of either, but trusted-network mapping and grace distance can change which is used.
