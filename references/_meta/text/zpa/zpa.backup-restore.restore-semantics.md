# What restoring a ZPA backup does: overwrite and removal, legacy backups, reports, the pre-restore backup, the documented inconsistencies and failure reasons (zpa.backup-restore.restore-semantics)
Also called: zpa restore; restore inconsistency; pre-restore backup; restore report; legacy backup; restore activities; restore failed

Restoring application segments, policies and configuration settings from a backup overwrites all current ones, including all rules and their components, and a component in the current configuration that is not in the backup is removed when the backup is applied; Zscaler therefore says to review the policies in the backup before restoring it. [zpa.backup-restore.restore-semantics:overwrites-and-removes]

**Backups and limits.** A backup created before some of the additional features were introduced is a legacy backup that can only restore the policies and configurations that belonged to it, and applying it does not override policies and configurations that were not supported in the platform version at the time of the backup creation. [zpa.backup-restore.restore-semantics:legacy-backups] Policies and configurations can be restored from a backup a maximum of 10 times per day. [zpa.backup-restore.restore-semantics:restore-limit-per-day] The backups themselves are in [ZPA Backup and Restore: what a backup covers, the 10-backup limit, the golden backup, expiry, schedules and the PRA-tenant exclusion](kb:zpa.backup-restore).

**Before and after.** Restoring verifies certain conditions before applying the backup, for example that all provisioned static IP addresses in the backup are still associated with the current tenant and the expiration timestamp of the certificates persisted in the backup. While a backup is created or a restore is applied, a banner shows that the Backup and Restore page is read-only. [zpa.backup-restore.restore-semantics:pre-checks-and-read-only] Before a restore, an Inconsistency Report shows inconsistencies in application management and policy management if the backup is applied, and can be downloaded as a CSV file; a Full Report shows inconsistencies and modifications from the current backup in application management and policy management if the backup is applied. [zpa.backup-restore.restore-semantics:pre-restore-reports] Before restoring a backup, a pre-restore backup of the existing configuration is automatically created, for use in case the restored backup has post-restore issues, and it has the Pre-Restore Configuration naming convention followed by a timestamp. [zpa.backup-restore.restore-semantics:pre-restore-backup] The timestamp format is given two ways [divergence:zpa.backup-restore.restore-semantics:pre-restore-timestamp]. Each backup's Restore Activities list shows the Admin ID of the admin who restored it, when the restore was initiated and its status (Completed, Failure or In Progress). The restore report lists the configurations changed, with their status after the restore; unchanged configurations are not listed, and the full report can be downloaded as a CSV file. [zpa.backup-restore.restore-semantics:restore-activities] A restore is reported as failed when the pre-restore backup failed or because of an unexpected exception. [zpa.backup-restore.restore-semantics:restore-failures]

**Documented inconsistencies: application segments.** An application segment inconsistency occurs when the restore is applied and the number of applications exceeds the maximum limit, or when the application that has a server group which was deleted is restored (the server group having been added in the Default Microtenant after the backup was created and then used in a different application within a Microtenant). [zpa.backup-restore.restore-semantics:inconsistency-app-segments] When two or more application segments contain the same domain they must have Double Encryption set to the same value; the documented resolution is to ensure Double Encryption is set to the same value (Enabled or Disabled) for those segments. [zpa.backup-restore.restore-semantics:inconsistency-same-domain-double-encryption] Application segments with the same domain and the Bypass setting are documented against another rule [divergence:zpa.backup-restore.restore-semantics:same-domain-bypass]. A restore also raises application segment inconsistencies when the TCP or UDP port range of an application overlaps the port range of an existing application in a different Microtenant, when the segment's application domain already exists as an FQDN in a user portal or privileged portal (the resolution is to update the portal to use a different FQDN), when the segment references policies within a Microtenant (remove the segment from the policies), or when a duplicate DNS search domain exists for an application within a Microtenant (remove the duplicate domain from the Microtenant). [zpa.backup-restore.restore-semantics:inconsistency-microtenant-conflicts] A Browser Access application segment raises an inconsistency when its Browser Access FQDN is used in other tenants before the restore is applied (the resolution is to remove the Browser Access application from the other tenants), when a wildcard domain exists for its domain or vice versa in a different Microtenant (remove the wildcard domain of the Browser Access application from the other Microtenant), or when its associated web server certificate is deleted. [zpa.backup-restore.restore-semantics:inconsistency-browser-access]

**Documented inconsistencies: groups, servers, certificates, policies and portals.** Other documented restore inconsistencies: a segment group that is deleted but linked with policies other than access, timeout and client forwarding policies within the same Microtenant, or a Default Microtenant segment group linked with any policies in another Microtenant; a server linked to a server group referenced by Internet & SaaS (the resolution is to remove the server from that group); a server group that has no App Connector group or is used in an application segment within a Microtenant; and a certificate when a Certificate Signing Request with the same subject exists, when a Browser Access application references the certificate within a Microtenant, or when a user portal within a Microtenant references it. [zpa.backup-restore.restore-semantics:inconsistency-groups-servers-certificates] The restoring article lists inconsistencies for an access policy when a backup is applied if the application or segment group, IdP, trusted network, posture, location, Branch Connector group, Cloud Connector group, SAML attribute name, SCIM attribute name, SCIM attribute value (removed in the latest SCIM sync), risk score, machine group, or App Connector group or server group is no longer present; traffic fails if an App Connector group or server group is used in the policy and there are no App Connectors. Client forwarding and timeout policies have their own lists, and a policy using an application segment no longer shared to it, or an application moved to another Microtenant, is also inconsistent (the resolution for the move is to move the application back to the current Microtenant). [zpa.backup-restore.restore-semantics:inconsistency-policies] A user portal raises a restore inconsistency when its associated web server certificate is deleted, or when its portal URL has a domain that conflicts with an application segment used by a Microtenant (the resolution is to update the user portal to use another domain). [zpa.backup-restore.restore-semantics:inconsistency-user-portals] Whether policies, certificates and user portals are backed up at all is disputed in [ZPA Backup and Restore: what a backup covers, the 10-backup limit, the golden backup, expiry, schedules and the PRA-tenant exclusion](kb:zpa.backup-restore). Whether pre-restore backups count toward the backup limit is open [gap:zpa.backup-restore.restore-semantics:pre-restore-limits].

What to check:
1. Whether the backup is current before restoring, since a restore overwrites everything and removes components that are not in it.
2. Whether the inconsistency report was downloaded and read before the restore, and whether the pre-restore backup was created.
3. Whether segments with the same domain disagree on Bypass, since the restore article and the segment-precedence claim describe that differently.
4. Whether a restore stopped by an inconsistency matches one of the documented rows, and which of them name a fix.

Sources disagree (name both sides):
- The restoring article says application segments with the same domain must use the same Bypass setting; the application segment article says that when the same FQDN is in several segments and one has Bypass Always, that segment takes precedence. [divergence:zpa.backup-restore.restore-semantics:same-domain-bypass]
  - zscaler-help: Segments with the same domain must use the same Bypass setting; the row's enumeration of conflicting Bypass settings is Use Client Forwarding Policy, Always or On Corporate Network, and its resolution names Use Client Forwarding Policy or On Corporate Network.
  - zscaler-help: If the same FQDN is defined in several segments and one has Bypass Always, that segment takes precedence (the claim zpa.app-segments.bypass:same-fqdn-always).
  Impact: The two articles describe segments that share a domain differently; neither says how the other applies. The existing claim zpa.app-segments.bypass:same-fqdn-always is not changed; an answer about Bypass settings on segments sharing a domain uses this divergence rather than either statement alone.
- The restoring article gives the pre-restore backup timestamp format with hyphens in the time, while its example uses colons and stamps the restored backup's creation time. [divergence:zpa.backup-restore.restore-semantics:pre-restore-timestamp]
  - zscaler-help: The timestamp is in the MM-DD-YYYY hh-mm-ss format.
  - zscaler-help: The example separates the time with colons and uses the creation time of the restored backup.
  Impact: Matching pre-restore backups by name should not rely on the separator or on which time is stamped; the format sentence does not say which time is used.

Not known (open gaps):
- Whether pre-restore backups count toward the 10-backup limit, and what the 10-restores-a-day limit counts [gap:zpa.backup-restore.restore-semantics:pre-restore-limits]: settled by source-read or lab-test
