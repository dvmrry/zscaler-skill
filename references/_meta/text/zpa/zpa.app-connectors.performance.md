# Monitoring App Connector performance: CPU, memory, throughput, source ports, application targets, disk and file descriptors (zpa.app-connectors.performance)
Also called: app connector cpu; app connector memory; app connector cpu steal; app connector port exhaustion; app connector 6000 targets; app connector file descriptors; app connector snmp

Within the Admin Console the App Connector Dashboard and Health Dashboard help monitor an organization's App Connectors; the page's most important point is that App Connectors are deployed following Zscaler's recommendations for image sizing and scalability, supported platform requirements, deployment best practices, networking configurations and other essential guidelines. [zpa.app-connectors.performance:surfaces]

**Headroom.** Peak CPU utilization should be less than 75%, taking into account all connectors in the group, so that each App Connector can operate under 75% utilization if one of the group's App Connectors becomes unavailable; in the page's example, two App Connectors both at 50% are below the 75% threshold, but if one goes down the other runs above 75%. [zpa.app-connectors.performance:cpu-headroom] Peak memory utilization should be less than 90%, and the memory of the group's App Connectors should allow each App Connector to operate under 90% utilization if one of them becomes unavailable. [zpa.app-connectors.performance:memory-headroom] Peak throughput based on recommended App Connector specifications should be less than 500 Mbps, and the 500 Mbps is an aggregate of multiple streams of traffic. [zpa.app-connectors.performance:throughput-ceiling] The thresholds that the notification events watch are in [ZPA event notifications: the catalog, thresholds, throttling and recipients](kb:zpa.troubleshooting.events).

**Where the numbers are.** App Connector Status logs can be streamed to a SIEM or syslog server using the Log Streaming Service (LSS) and are generated periodically for each connector; the field CPUUtilization displays the App Connector host's CPU utilization at that instance, MemUtilization its memory utilization and TotalBytesRx and TotalBytesTx its throughput. [zpa.app-connectors.performance:lss-status-fields] App Connector logs can be viewed on the App Connector host whenever the App Connector is running; CPU steal percentage, the CPU time stolen from the VM by a hypervisor, is reported every minute in the status log. When it is high the hypervisor is busy, resulting in degraded performance for the App Connector, and the page says to ensure the hypervisor is healthy and change the hypervisor setup accordingly. [zpa.app-connectors.performance:cpu-steal] The top command reports the sum of utilization across all cores on all processors, so a CPU utilization above 100% might be due to multiple CPU cores on the App Connector host (for example, 4 cores could show usage at 400%); the lscpu command shows the number of CPU cores, and the calculation of peak CPU should be normalized across the number of cores. [zpa.app-connectors.performance:cpu-normalize-cores] The page lists Linux SNMP OIDs for host monitoring: percentage of user CPU time .1.3.6.1.4.1.2021.11.9.0, system CPU time .1.3.6.1.4.1.2021.11.10.0 and idle CPU time .1.3.6.1.4.1.2021.11.11.0; total RAM in machine .1.3.6.1.4.1.2021.4.5.0, total RAM used .1.3.6.1.4.1.2021.4.6.0 and total RAM free .1.3.6.1.4.1.2021.4.11.0; bytes received on the interface .1.3.6.1.2.1.2.2.1.10 and transmitted .1.3.6.1.2.1.2.2.1.16; available space on the disk .1.3.6.1.4.1.2021.9.1.7.1 and percentage of space used on disk .1.3.6.1.4.1.2021.9.1.9.1. [zpa.app-connectors.performance:snmp-oids] No console or LSS metric for source-port or file-descriptor use is named [gap:zpa.app-connectors.performance:port-and-fd-metrics].

**Reducing load.** Under each of the CPU, memory and data throughput headings the page recommends deploying additional App Connectors into the App Connector group to distribute users across additional connectors, and deploying dedicated App Connector groups for specific application segments to reduce the number of applications requested through each App Connector group; for memory it also recommends increasing the amount of available memory on the App Connector host. [zpa.app-connectors.performance:scale-out-remedies]

**Source ports.** If the in-use count for either TCP or UDP ports is equal or close to the available ports, the App Connector host is likely to experience port exhaustion and the App Connector might not be able to connect to the application servers; in the page's example the difference 60999-32768=28231 is the number of ports available on that host. The page's remedies are to increase the available maximum number of ports (a non-permanent increase does not persist across the App Connector host restart; a permanent one is added to /etc/sysctl.conf), assign a secondary IP address to the existing interface, or create an additional interface; the page says the secondary address and the additional interface each give the host an additional set of TCP ports. [zpa.app-connectors.performance:source-port-exhaustion]

**Application targets.** Starting with App Connector version 20.11.20, each App Connector records the number of applications it is currently monitoring for reachability. An App Connector can monitor at most 6,000 application targets at any time, so application definitions must be distributed across multiple application segments and App Connector groups to keep each connector under 6,000; if an App Connector reaches 6,000 targets, the On Access health reporting of the application is converted to None, which means the App Connector does not check and report reachability to the application. [zpa.app-connectors.performance:application-target-limit] The monitoring page says the monitored-application count is stored in the current_target_count field of the App Connector status logs. [zpa.app-connectors.performance:target-count-field-name] No field table lists that field [gap:zpa.app-connectors.performance:current-target-count-field]. On the host, the page's example greps the journal for target (journalctl -n1000 | grep target) and shows a line with registered apps count 1, alive apps 1, apps with on-access health 1, service count 0, target count 3466 and target alive 3466. [zpa.app-connectors.performance:target-count-on-host]

**Disk and file descriptors.** The App Connector process restarts if there is less than 100 MB of disk space left, and generates a log in /var/log/message to reflect the cause, so that software updates for the App Connector can download successfully. If the App Connector runs other software it can generate large volumes of logs that fill the disk; Zscaler recommends at least disabling rsyslogd to reduce disk space, and the page's example is that deleting /var/log/messages has no functional implication. [zpa.app-connectors.performance:disk-restart] How the 100 MB floor relates to the Disk Space Exceeded Limit event is open [gap:zpa.app-connectors.performance:disk-floor-vs-event]. If the number of file descriptors is not sufficient on the App Connector host, transactions can fail due to file descriptor exhaustion; the page's fix is to increase the SYSTEM_FD limit with sudo sysctl -w fs.file-max=1000000. [zpa.app-connectors.performance:file-descriptors]

What to check:
1. Whether peak CPU and memory stay under the group-wide thresholds with one App Connector of the group unavailable, and whether a CPU figure above 100% is normalized by the core count.
2. Whether a high CPU steal percentage in the local status log points to the hypervisor rather than the App Connector.
3. Whether the in-use TCP or UDP port count is equal or close to the available ports on the host.
4. Whether any App Connector approaches 6,000 application targets, at which On Access health reporting becomes None.
