# Private Access user portals and portal links: what they are, how users reach them, certificates and DNS, links, download links and the acceptable use policy (zpa.user-portal)
Also called: user portal; user portals; clientless portal; portal links; user portal links; portal CNAME; Client Connector download links; user portal acceptable use policy

User portals provide visibility to authorized applications for an organization's employees and partners. From a portal users can launch web applications (Browser Access-enabled applications, web applications set up for Client Connector access, and public SaaS websites) and download Client Connector. [zpa.user-portal:what-it-is]

**How users reach it.** When a user tries to access the user portal, their browser resolves the portal's domain name to an IP address for Private Access. Before accessing the portal the user is prompted to authenticate against the IdP configured for their organization, then Private Access serves the portal and its portal links; the user can only view links to applications they are allowed to access. [zpa.user-portal:access-flow] For an end user to access a user portal, at least one SAML attribute needs to be configured for the IdP in Private Access. [zpa.user-portal:saml-attribute-required] The authentication timeout for a user portal session is based on the default timeout policy rule. Editing the rule does not immediately affect currently authenticated portal sessions, and when a session expires the portal might become unresponsive until the user reauthenticates. [zpa.user-portal:session-timeout]

**Configuring a portal.** A user portal takes a name (which cannot contain special characters other than periods, hyphens and underscores), a Status (a disabled portal is inaccessible to users), an optional description, and an optional notification banner (Status Enabled plus message text) that end users can dismiss from the top of the page. [zpa.user-portal:portal-fields] The portal Certificate Type is Managed or Custom. With Managed, the certificate is managed by Zscaler and the portal URL is a domain prefix plus a domain suffix chosen from a drop-down. With Custom, an existing certificate is selected, it must support the portal FQDN, and the full portal URL must use HTTPS and be an FQDN. [zpa.user-portal:certificate-type] For user portals with a custom certificate, the admin adds the copied CNAME information to public DNS and verifies that the portal FQDN resolves to the record. Zscaler automatically manages the public DNS for the FQDN of user portals with a Zscaler-managed certificate. [zpa.user-portal:dns] The CNAME publication step is worded differently between the articles [divergence:zpa.user-portal:cname-publication]. A user portal's FQDN cannot be configured as an application within an application segment. [zpa.user-portal:fqdn-not-in-segment] The User Portals page lists each portal with its Status (Enabled or Disabled), the URL users access and the Notification Banner status, and shows the Browser Access (web server) certificate associated with the portal and its canonical name (CNAME). [zpa.user-portal:portals-page] Which domain suffixes a Managed certificate offers is open [gap:zpa.user-portal:managed-suffixes].

**What the end user sees.** After login, a list of the applications available to the user, based on the access policies for the application segments, is displayed; applications with a policy rule set to Deny are not visible. Link icons mark private applications reachable only through Client Connector, private web applications reachable through Browser Access, and public SaaS or other public websites; all link types are shown by default and the user can filter the list. [zpa.user-portal:end-user-view] A link that is displayed but inactive (grayed out) cannot be launched directly from the portal, and the user might require a native client for that application (for example SSH or RDP). The user also needs Client Connector installed and enrolled on the device, and the admin can let them download it from the portal. [zpa.user-portal:inactive-links] The Client Connector Download Links page takes a link to the proper installer for Google Android, Apple iOS, Linux, Apple macOS and Microsoft Windows, copied from the Client Connector App Store or any other valid download URL. The organization determines which installer versions are approved and is responsible for keeping the links current as newer versions become available. [zpa.user-portal:client-connector-download-links]

**Portal links.** Within the Admin Console a user portal can hold up to 500 links, and during configuration only up to 150 links can be added at a time. [zpa.user-portal:link-limits] A portal link of type Web can be viewed and clicked by users to launch an application (Browser Access-enabled applications, web applications set up for Client Connector access, and public SaaS websites); a Display link can be viewed but not clicked to launch the application in a browser, and is associated with internal applications that can only be accessed using Client Connector. [zpa.user-portal:web-and-display-links] A link's App Type is Private Applications, for applications configured in Private Access and chosen by user portal, application segments and applications, or Public Applications, for applications accessible to users but not configured in Private Access, given as a protocol (HTTP or HTTPS) and an FQDN. For Public Applications links, more than one user portal can be selected. [zpa.user-portal:private-and-public-links] To avoid incorrect or inconsistent policy evaluation, a private application should not be used to create a Public Applications link; the page's remedy is to delete the public applications link, enter the application when configuring an application segment, and create a private applications link with the application configured in the segment. [zpa.user-portal:no-private-app-as-public-link] For private applications where Browser Access is not enabled the link protocol can be HTTP or HTTPS; where Browser Access is enabled it defaults to the protocol configured in the application segment and cannot be changed; for a Public Applications link HTTP or HTTPS must be specified. [zpa.user-portal:link-protocol] For a private application the link name and domain default to those in the application segment (the FQDN for a Browser Access-enabled application, the IP address or FQDN for an application reached only with Client Connector) and can be changed; Path defaults to forward slash (/); Display on Portal set to Disabled does not display the link; an uploaded image may be a .ico, .jpg or .png of 32x32 pixels or smaller. [zpa.user-portal:link-defaults] A user connecting to Private Access through Client Connector on at least one device sees links for applications they can access across all devices, while an access policy can restrict access to an application, for example based on the Client Connector Posture Profile criteria. In the documented example the user sees the HR and sales application links but can access an application only when using the proper device. [zpa.user-portal:links-across-devices] The Portal Links page can be filtered to show links for a specific user portal (all available links by default), shows whether each link is enabled and displayed on a user portal, and can copy a link configuration to create a new link; editing a link offers Preview Link to see how it will appear in the portal. [zpa.user-portal:portal-links-page] How the Web and Display types map to the Private and Public App Types is open [gap:zpa.user-portal:link-type-mapping].

**Company profile branding.** On the Private Access tenant's Company page (Administration > Private Access Tenant), an organization logo of any valid image file type 300x150 pixels or smaller is shown in the user portal and the Privileged Remote Access (PRA) Portal, and a favicon of a valid image file type 32x32 pixels or smaller appears as the icon on a user portal browser tab, the PRA Portal browser tab and privileged console browser tabs. [zpa.user-portal:company-profile-branding] The Company page takes the organization's name, which cannot contain special characters other than periods, hyphens and underscores, and shows the ZPA tenant ID of the organization's Private Access tenant, which cannot be edited. [zpa.user-portal:company-profile-fields] Whether the branding applies per Microtenant is open [gap:zpa.user-portal:company-profile-microtenant].

**Acceptable use policy.** An acceptable use policy (AUP) can be created that users must accept before they connect to a user portal and a Privileged Remote Access Portal: its Frequency, how often the portals display it, is Once or Never, and it carries the AUP display text and the support team's email address and phone number. After a user logs in and authenticates through SSO an AUP can be displayed, and if it is, the user must read and accept the terms. [zpa.user-portal:acceptable-use-policy] Whether a tenant can hold more than one is open [gap:zpa.user-portal:aup-count].

A restore that finds a portal's certificate deleted or its domain in conflict is in [What restoring a ZPA backup does: overwrite and removal, legacy backups, reports, the pre-restore backup, the documented inconsistencies and failure reasons](kb:zpa.backup-restore.restore-semantics); the certificate side of Browser Access is in [Certificates for Browser Access applications: wildcards, managed and custom](kb:zpa.browser-access.certificates).

What to check:
1. Whether the portal's FQDN is also defined as an application in an application segment, since that is not allowed.
2. Whether the portal uses a Managed or Custom certificate before asking who publishes the public DNS record.
3. Whether a user who cannot reach the portal has at least one SAML attribute configured for the IdP in Private Access.
4. Whether a grayed-out link needs a native client and an enrolled Client Connector.

Sources disagree (name both sides):
- About User Portals says Private Access generates a CNAME that must be published to public DNS without a condition; Configuring User Portals scopes manual publication to custom certificates and says Zscaler manages the public DNS for Zscaler-managed certificates. [divergence:zpa.user-portal:cname-publication]
  - zscaler-help: A generated CNAME must be published to the organization's public DNS, with no certificate condition.
  - zscaler-help: The configuring article's introduction also says the generated CNAME must be published in the public DNS without a condition, while its steps say Zscaler manages the public DNS for portals with a Zscaler-managed certificate and the manual CNAME steps are given for custom certificates.
  Impact: Both articles state the unconditional publication sentence, and the configuring article's own steps scope manual publication to custom certificates, so whether an admin publishes the CNAME for a Zscaler-managed certificate is unsettled. The Browser Access side of the CNAME is the claim zpa.browser-access.certificates:cname-in-dns, which may bear on portals since the portal certificate is a Browser Access web server certificate; the pages do not say it does.
