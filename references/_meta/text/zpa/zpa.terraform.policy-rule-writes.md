# What the ZPA Terraform provider sends and loses when writing policy rules (zpa.terraform.policy-rule-writes)
Also called: zpa policy rule update clears fields; terraform zpa policy rule drift; operand name erased; idp condition missing after refresh; import global policy rule; import reauth policy rule; microtenant_id unsupported argument policy rule v2; credential policy rule stale reference; preflight get error ignored update

The ZPA provider builds every rule resource's create and update from Terraform state alone and sends it through SDK helpers that change it further. Ordering of rules is covered in [How the ZPA Terraform provider applies policy rule order (BulkReorder)](kb:zpa.terraform.rule-order); deleting objects that rules refer to is covered in [What the ZPA Terraform provider does when deleting objects with dependents](kb:zpa.terraform.delete-paths). This subject is about what a single rule write contains.

**Fields Terraform does not model.** The v1 forwarding rule update builds its request from Terraform state only and does not read the existing rule to merge: its expander sets a handful of scalar fields and the conditions, and its update calls the SDK without a preceding read. The SDK request type tags `devicePostureFailureNotificationEnabled`, `appServerGroups`, `appConnectorGroups` and `serviceEdgeGroups` without `omitempty`, so they are always serialized, including when the provider left them unset. [zpa.terraform.policy-rule-writes:v1-update-sends-fresh-request] A v2 forwarding rule update does read the rule first, but only to detect a deleted rule: the response is thrown away and the request sent is again built from Terraform state. The v2 SDK request type has the same always-serialized fields (`devicePostureFailureNotificationEnabled`, `appServerGroups`, `appConnectorGroups`, `serviceEdgeGroups`). [zpa.terraform.policy-rule-writes:v2-update-reads-then-discards] The same fresh-request pattern, with none of the four always-serialized SDK fields populated, is in the forwarding, inspection, isolation and timeout rule resources (v1 and v2 where both exist), the v2 browser-protection, capabilities, portal and credential rule resources. The access rule (v1 and v2) populates the device-posture flag, server groups and connector groups from its own schema; the redirection rule populates only service edge groups. [zpa.terraform.policy-rule-writes:unmanaged-fields-same-pattern] So an update that changes only a name, action or condition sends `null` association lists and a `false` device-posture flag. Whether ZPA then clears the remote values, keeps them, or rejects the request is not shown by the client code. [zpa.terraform.policy-rule-writes:unmanaged-fields-may-be-cleared] Whether ZPA replaces the whole rule or merges null and false fields on a PUT is open [gap:zpa.terraform.policy-rule-writes:api-put-semantics]. The SDK's tags are the same mechanism described for ZIA in [How the Go SDK encodes ZIA writes (omitted zero values, empty responses)](kb:zia.sdk-go.write-encoding).

**Operand names in the SDK.** The pinned v1 SDK's `UpdateRule` blanks every non-empty operand name in the request just before the PUT. The provider does expose operand `name` as an optional, computed field and passes it into the request, so a configured or refreshed name never reaches ZPA on a v1 rule update. [zpa.terraform.policy-rule-writes:v1-sdk-erases-operand-names] The v2 SDK's `UpdateRule` clears operand IDs, not names. The v2 provider schemas model operands by object type and values rather than a writable name. [zpa.terraform.policy-rule-writes:v2-sdk-clears-operand-ids-not-names] Every provider path that updates a v1 rule goes through that SDK function: the access, forwarding, inspection, isolation, redirection and timeout rule resources, and the cleanup code that edits rules when a segment group, application segment, server group, app connector group or PRA credential is deleted. [zpa.terraform.policy-rule-writes:operand-name-erasure-reaches-all-v1-writers]

**Read-back converter.** Up to v4.4.15 the converter that turns a policy rule read from the API into a v2 request keeps operands only for a fixed list of object types, and has no case for `IDP` or `WORKLOAD_TAG_GROUP`. Both types are accepted by the v2 access rule schema, so a condition built from them is accepted in configuration and then not carried through the converter. v4.4.16 adds `IDP`, `WORKLOAD_TAG_GROUP`, `ENTITY_TAG_GRP` and `ENTITY_TAG_VAL` to the converter's ID and values case, and its changelog says such operands are no longer dropped when the rule is read. [zpa.terraform.policy-rule-writes:v2-conversion-drops-idp-and-workload-tag] In `ConvertV1ResponseToV2Request` the converter up to v4.4.14 appended only an operand's `RHS`, so an operand that carried a list of values lost them when the rule was converted; v4.4.15 appends all of the operand's `Values` when it has any and falls back to `RHS` otherwise. [zpa.terraform.policy-rule-writes:v2-conversion-values-list-4-4-15] The v2 access rule's read converts the API response and builds the `conditions` state from the converted rule, so a condition the converter dropped is absent from refreshed state. [zpa.terraform.policy-rule-writes:v2-read-state-comes-from-converter] When a segment group is deleted, the provider reads the v2 rules of the ACCESS, TIMEOUT, SIEM, CLIENT_FORWARDING and INSPECTION policy types, removes the segment group operand, converts the whole rule with ConvertV1ResponseToV2Request and PUTs the converted rule. [zpa.terraform.policy-rule-writes:cleanup-rewrites-rule-from-converter] So whatever the converter drops from a rule is also missing from the PUT that rewrites it, and is lost from the stored rule if the API treats that PUT as a full replacement. [zpa.terraform.policy-rule-writes:cleanup-put-omits-converter-drops] The converter is used by the read function of the v2 access, timeout, forwarding, inspection, isolation, browser-protection, capabilities, credential and portal rule resources, and by cleanup code in the app connector group, segment group and PRA console resources, which write the converted rule back. [zpa.terraform.policy-rule-writes:converter-callers] So up to v4.4.15 a v2 rule with an `IDP` or `WORKLOAD_TAG_GROUP` condition can refresh to state without that condition, and a delete-time cleanup that touches such a rule can PUT it back without the condition; v4.4.16 adds those object types to the converter. [zpa.terraform.policy-rule-writes:idp-condition-lost-from-state-and-cleanup-writes] How ZPA represents identity provider and workload tag operands on a read is open [gap:zpa.terraform.policy-rule-writes:api-idp-operand-shape].

**Import and schema.** The access rule importers (v1 and v2) accept the policy types `ACCESS_POLICY` and `GLOBAL_POLICY`, and the timeout rule importers accept `TIMEOUT_POLICY` and `REAUTH_POLICY`. Read always resolves the policy set for `ACCESS_POLICY` or `TIMEOUT_POLICY` and writes `policy_set_id` (the resolved set's ID, except the v1 timeout rule, which writes the policy set ID from the rule it read); in the v1 resources, create, update and delete use a configured `policy_set_id` first, and the v2 resources resolve the fixed type unconditionally. A numeric import ID never consults the types; they matter only for lookup by name. [zpa.terraform.policy-rule-writes:import-accepts-types-crud-ignores-them] An imported `GLOBAL_POLICY` or `REAUTH_POLICY` rule is therefore looked up, updated and deleted in the `ACCESS_POLICY` or `TIMEOUT_POLICY` policy set. If ZPA keeps those as separate policy sets, the rule is not found there and refresh fails or removes it from state; if it treats them as the same set, nothing goes wrong. [zpa.terraform.policy-rule-writes:import-type-mismatch-effect] Whether ZPA keeps those policy types as separate policy sets is open [gap:zpa.terraform.policy-rule-writes:api-policy-set-types]. The v2 access rule's create, read, update and delete read `microtenant_id` from the resource data and select a microtenant with it, but the resource's schema has no `microtenant_id` attribute. A configuration cannot set it, so the microtenant it would select is never the one configured. The v2 timeout rule, by contrast, defines the attribute. [zpa.terraform.policy-rule-writes:v2-access-microtenant-id-not-in-schema]

**Preflight reads.** Several update functions read the object first and treat only a not-found error as meaningful: not found clears the ID and returns success, and any other error from the read falls through to the update call. The PRA credential update and the redirection policy rule update are examples. [zpa.terraform.policy-rule-writes:update-ignores-non-404-preflight-error] The same swallowed-preflight shape is in the update function of 22 resources: app connector assistant schedule, app connector group, application server, application segment, CBI banner, CBI certificate, CBI external profile, emergency access, inspection custom controls, inspection profile, microtenant, redirection policy rule, PRA approval, PRA console, PRA credential, PRA credential pool, PRA portal, provisioning key, segment group, server group, service edge assistant schedule and service edge group. The v2 forwarding rule update, by contrast, returns every non-404 error from its read. [zpa.terraform.policy-rule-writes:ignored-preflight-error-places]

**Credential rules.** Deleting a PRA credential or credential pool first runs one helper that reads the v1 `CREDENTIAL_POLICY` rules and removes only an operand with object type `APP`, `lhs` `id` and `rhs` equal to the ID. Both delete functions call that same helper. [zpa.terraform.policy-rule-writes:credential-delete-scans-v1-operands] The credential policy rule resource does not store the credential or pool as an operand. It writes them as the rule's top-level `credential` and `credentialPool` fields. [zpa.terraform.policy-rule-writes:credential-reference-is-top-level-field] So deleting a credential or pool that a credential policy rule uses does not clear the rule's reference: the helper never looks at the top-level fields. The delete then proceeds if ZPA accepts it, or fails if ZPA rejects a delete of a referenced object. [zpa.terraform.policy-rule-writes:credential-delete-leaves-reference] What ZPA does when a referenced credential or pool is deleted is open [gap:zpa.terraform.policy-rule-writes:api-delete-referenced-credential].

**Changing the reference.** The credential rule schema requires exactly one of `credential` or `credential_pool`, and the update code, when its request has neither (a block whose `id` is empty), copies the credential or pool from the rule it just read; it then returns an error only if neither carries an ID. [zpa.terraform.policy-rule-writes:credential-update-restores-remote-association] So a rule cannot be written without an association, and an update with an empty block keeps the remote credential or pool without an error. [zpa.terraform.policy-rule-writes:credential-empty-block-keeps-remote] Changing a rule from a credential to a credential pool (or the reverse) sends only the new pointer; the other field is left out of the JSON by `omitempty`, with no explicit clear. Whether ZPA drops the old association or keeps both is not shown by the client code. [zpa.terraform.policy-rule-writes:credential-swap-does-not-clear-old]

What to check:
1. Whether the server groups, connector groups and device-posture flag of a rule are unchanged after an apply that changed only its name or conditions, by re-reading the rule.
2. Which provider version is in use, then whether a rule with identity provider or workload tag conditions still holds them, by comparing the stored rule with the configuration after a plan that touches it or a destroy of an object it might reference.
3. Which credential policy rules reference a PRA credential or pool through their `credential` and `credentialPool` fields, not their conditions, before the credential or pool is deleted.
