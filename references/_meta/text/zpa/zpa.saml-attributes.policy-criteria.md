# How SAML attributes act as policy criteria (zpa.saml-attributes.policy-criteria)
Also called: saml criteria in access policy; any saml attribute; saml attributes for policy; saml rule never matches; multiple idp policy; saml log streaming criteria

SAML attributes act in policy as criteria on a rule.

**Choosing criteria.** A rule's SAML and SCIM criteria are chosen per IdP: the admin selects the IdP configuration, which must be configured for User SSO, selects more than one IdP when needed, and then picks the criteria, which appear under SAML and SCIM Attributes and the IdP name. [zpa.saml-attributes.policy-criteria:idp-selection] After a specific SAML attribute is chosen for a rule, the SAML attribute value, meaning the users to whom the rule applies, is entered in a text field. [zpa.saml-attributes.policy-criteria:attribute-value-entry] Leaving the attribute unselected is covered in [In the console, leaving the Application Segments, Segment Groups and SAML Attributes fields unselected makes the rule apply to any user from any IdP and any application segment and segment group.](kb:zpa.policy.conditions:blank-criteria-mean-any), and the exclusion with Cloud Connector Groups in [The Cloud Connector Groups criteria cannot be configured with the SAML and SCIM Attributes criteria.](kb:zpa.policy.criteria:cloud-connector-groups-exclude-saml).

**Combining.** Default operators are in [Multiple client types, platforms, trusted networks, application segments or segment groups in one rule are joined by OR, and multiple SAML or SCIM attributes, groups or IdPs are joined by OR by default, with a toggle to AND.](kb:zpa.policy.conditions:or-within-most-criteria). In a rule that selects several IdPs, each IdP carries its own criteria, and Private Access joins the IdPs with OR by default, so a user authenticating from one IdP is matched by that IdP's criteria; the operator can be toggled to AND. [zpa.saml-attributes.policy-criteria:idp-scope] Under the default OR between IdPs, a user who authenticates through one IdP is not matched by attribute criteria chosen only under a different IdP, even when an attribute there has the same name. [zpa.saml-attributes.policy-criteria:other-idp-no-match] Zscaler recommends not using the AND operator between policy rules when the SSO configuration includes SAML or SCIM attributes from multiple IdPs. [zpa.saml-attributes.policy-criteria:multi-idp-and-advice]

**IdP setting.** For Private Access to process SAML and SCIM criteria in a rule, the SAML Attributes for Policy setting must be enabled for SAML and the SCIM Attributes and Groups for Policy setting for SCIM on the IdP. [zpa.saml-attributes.policy-criteria:idp-setting-required] What a disabled setting does to a rule is in [If the IdP's SAML Attributes for Policy (or SCIM Attributes and Groups for Policy) setting is disabled but a rule has criteria of that kind, an OR operator skips those criteria and evaluates the other kind, while an AND operator makes Private Access not evaluate the rule at all.](kb:zpa.policy.criteria:idp-policy-setting-disabled). The same setting exists for SCIM in [SCIM groups and attributes as ZPA policy criteria](kb:zpa.scim.policy-criteria).

**Other uses and renames.** SAML attributes can also be used to define a streaming policy when configuring a log receiver. [zpa.saml-attributes.policy-criteria:streaming-criteria] With a subscription to Authentication Service and the feature enabled, the SAML and SCIM Attributes criteria is replaced by Session and User Attributes, and the SAML Attributes option by Session Attributes. [zpa.saml-attributes.policy-criteria:auth-service-replaces-criteria]

**In Terraform.** In the Terraform provider a SAML criterion is an operand with object_type SAML whose lhs is the SAML attribute's ID (the zpa_saml_attribute data source's id) and whose rhs is the value to match; the v1 resources also carry idp_id, and the v2 resources take the pair in entry_values. [zpa.saml-attributes.policy-criteria:operand-form] When a v1 policy resource is created or updated, the provider looks the SAML operand's lhs up with samlattribute.Get and fails on an unknown ID or an empty rhs; the v2 resources call `ValidatePolicyRuleConditions` instead, whose SAML case, quoted from `case "SAML":` to the next case, checks that entry_values is present and that lhs and rhs are not empty, with no lookup. [zpa.saml-attributes.policy-criteria:v1-validates-lookup] A rule that combines different object types in one conditions block with OR is valid through Terraform and the API, but the Admin Console criteria builder cannot always represent it, and re-saving it there may silently drop the operands it cannot render. [zpa.saml-attributes.policy-criteria:mixed-block-gui] Sharing a block with SCIM groups is in [SAML and SCIM_GROUP operands can share one condition block as identity types and are ORed within it.](kb:zpa.policy.conditions:saml-scim-group-share-block), and rule-writing defects of the provider are in [What the ZPA Terraform provider sends and loses when writing policy rules](kb:zpa.terraform.policy-rule-writes).

What to check:
1. Which IdP the user authenticated with, and whether the rule's SAML criteria were chosen under that IdP.
2. Whether the IdP's SAML Attributes for Policy setting is enabled, and what operator the rule uses, since a disabled setting skips the criteria under OR and stops the rule being evaluated under AND.
3. Whether the rule joins criteria or IdPs with AND where OR was intended, since OR is the default.
4. Whether the tenant has Authentication Service, which changes the criteria names the rule shows.
5. For a Terraform-managed rule, which resource generation wrote it and whether the lhs is the attribute ID rather than the attribute name.
6. Whether a rule mixing SAML with other object types was re-saved in the console.
