# Which object a ZPA Terraform data source actually returns (zpa.terraform.data-source-selection)
Also called: zpa data source returns wrong object; data source id and name both set; data source name overrides id; zpa data source wrong microtenant; microtenant_id data source ignored; assistant schedule data source id ignored; application_segment_by_type first result; microtenant name resolution returns nothing; ZPA_MICROTENANT_ID overrides

A ZPA data source is a lookup, and its result is whatever object the provider happens to select. In the cases below the read finishes without an error but the object is not the one the configuration identified.

## Two selectors, one result

A segment group data source given both `id` and `name` runs the ID lookup, then runs the name lookup as well, and the name result replaces the ID result. If the name lookup returns an error the read fails even though the ID lookup succeeded. Nothing compares the two results. [zpa.terraform.data-source-selection:id-and-name-both-run-name-wins] The same structure (an `id` block assigning `resp`, then an independent `name` block assigning `resp` again, with no conflict constraint on the schema) is present in 44 data source files, including connector groups, server groups, service edge groups, user portal objects, tag objects, PRA objects and the main application segment data sources. [zpa.terraform.data-source-selection:overwrite-pattern-is-widespread] The CBI certificate, SCIM group and location summary data sources look up by `id` when it is non-empty and run the `name` lookup only otherwise, so a `name` given with an `id` is not used for the lookup and no error reports it. [zpa.terraform.data-source-selection:id-wins-name-ignored]

**Name as fallback.** The Cloud Browser Isolation region data source scans the full region list for the given `id`; if no region has that ID it does not fail but runs the name lookup, so a wrong or stale ID with a valid name returns the name-selected region. [zpa.terraform.data-source-selection:invalid-id-falls-back-to-name-region] The isolation profile data source has the same fallback: an `id` that matches no profile in the list is ignored and the `name` lookup supplies the result. [zpa.terraform.data-source-selection:invalid-id-falls-back-to-name-isolation-profile] These two are the only data sources that explicitly gate the name lookup on the ID finding nothing. List-scan data sources whose name block is unconditional (workload tag group and branch connector group, for example) also fall through to the name lookup when the ID matches nothing; the location summary data source instead returns an error when the ID matches nothing. [zpa.terraform.data-source-selection:id-fallback-only-two-sites]

## Selectors that select nothing, and first-of-many

The App Connector assistant schedule data source accepts optional `id` and `customer_id`, but its `id` branch, its `customer_id` branch and its default branch all make the identical call to the SDK's `GetSchedule`, which takes no selector and reads one fixed path built from the client's own customer ID. A wrong ID or customer ID is never sent and cannot cause an error. [zpa.terraform.data-source-selection:app-connector-schedule-selectors-ignored] The Service Edge assistant schedule data source has the same three branches, and the SDK's `GetSchedule` for Service Edges likewise takes no selector. [zpa.terraform.data-source-selection:service-edge-schedule-selectors-ignored]

The application-segment-by-type data source passes the `name` as a search term to the SDK, which returns every segment of that type matching the search. Up to v4.4.14 it used the first element of the list. From v4.4.15 it prefers the segment whose name equals the given name, ignoring case, and falls back to the first element when none does. The SDK sends the name both as a search term and as a `name+EQ+` filter. With no `name`, it returns the first segment of the type. [zpa.terraform.data-source-selection:by-type-takes-first-element] The browser protection data source, given no `name`, takes the first profile of the list the SDK returns. The source comment says this is "typically the default/active one", which is an assumption about API ordering. [zpa.terraform.data-source-selection:browser-protection-no-name-takes-first] Which segment the by-type data source returns for a name that no segment equals (ignoring case), or for no name, depends on how the ZPA API matches the search term and orders its results, which the client does not control. A multi-word name whose search fails is retried with its first two words, which widens the match further. [zpa.terraform.data-source-selection:by-type-result-depends-on-api-order] Search matching and result order of the list endpoints are open [gap:zpa.terraform.data-source-selection:api-list-order-and-search-match].

Across all of these: In each selection defect above (name overriding ID, unmatched ID falling back to name, first-of-many) the read finishes without an error and sets the data source ID and attributes from an object the configuration did not identify, so downstream references use the wrong object's ID. The ignored schedule selectors are different: a tenant has one schedule, so they return the right object and only give false assurance that the selector was checked. [zpa.terraform.data-source-selection:success-shaped-wrong-object]

## Microtenant scope

The PRA approval data source declares `microtenant_id` as Computed only, with no Optional, yet its read branches on `d.Get("microtenant_id")` to scope the service to a microtenant. [zpa.terraform.data-source-selection:microtenant-input-computed-only-pra-approval] A computed-only attribute cannot be set in configuration, so that microtenant branch cannot be driven from the configuration. [zpa.terraform.data-source-selection:microtenant-input-pra-approval-not-settable] The same dead input recurs: `microtenant_id` is Computed only for the BA certificate, PRA approval, PRA console, PRA credential controller, PRA credential pool, PRA portal controller and User Portal AUP data sources, and is missing from the top-level schema for application segment inspection, multimatch bulk, service edge group and trusted network, while each of those reads `d.Get("microtenant_id")`. [zpa.terraform.data-source-selection:microtenant-input-unavailable-pattern] The managed browser profile data source declares `microtenant_id` as Computed only and its read calls the SDK with the unmodified client service, with no microtenant scoping at all. [zpa.terraform.data-source-selection:managed-browser-profile-never-scoped] For these data sources an operator cannot choose the microtenant per data source: the read uses the unscoped service, so a name, ID or list lookup is made in whatever scope the client defaults to, and can return an object from a different microtenant than the one intended or miss one that exists only in the intended microtenant. [zpa.terraform.data-source-selection:reads-run-unscoped-wrong-microtenant] What a read with no microtenant returns is open [gap:zpa.terraform.data-source-selection:api-unscoped-read-scope].

**Request microtenant precedence.** When a ZPA request has no `microtenantId` query parameter, the SDK takes it from the request body, then from the `ZPA_MICROTENANT_ID` environment variable, and only then from the client's configured microtenant. A set environment variable therefore overrides the configured value. One call site passes an empty string for the configured value, so on that path the configuration is never used. [zpa.terraform.data-source-selection:inject-precedence-env-over-config] A request body whose `microtenantId` is the number 0 is treated as a real value: it is non-empty after generic JSON decoding, is formatted as the string "0", and is injected ahead of the environment variable and the configured microtenant. A body value of 0 therefore replaces a configured microtenant. [zpa.terraform.data-source-selection:inject-numeric-zero-overrides-config] How the API treats `microtenantId=0` is open [gap:zpa.terraform.data-source-selection:api-microtenant-zero].

**Microtenant name resolver.** When a `MicroTenantName` filter is supplied and the name lookup succeeds, the SDK's paged-list helper returns immediately with a nil list and a nil error. The caller sees a successful empty result, and the resolved microtenant ID is never applied. [zpa.terraform.data-source-selection:sdk-microtenant-name-success-returns-nothing] When the name lookup fails (no such microtenant, or an API error), the error is discarded and the helper goes on to list objects with no microtenant in the filter, so the request carries no microtenant unless the injection precedence supplies one. [zpa.terraform.data-source-selection:sdk-microtenant-name-failure-falls-through-unscoped] No ZPA service in the SDK and no provider data source sets the `MicroTenantName` filter, so the name resolver is reachable only by direct SDK callers. [zpa.terraform.data-source-selection:sdk-microtenant-name-resolver-has-no-active-callers]

What to check:
1. Whether the ID returned by a data source given both `id` and `name` is the one intended, since the name result replaces the ID result.
2. Whether a microtenant-scoped lookup declares `microtenant_id` as an input, and whether the returned `microtenant_id` is the one intended.
3. Whether `ZPA_MICROTENANT_ID` is set in the process environment, since it overrides the configured microtenant when the request has no `microtenantId` query parameter.
4. Whether a by-type or no-name lookup is pinned to an ID once it is known, since it returns some match rather than the intended object.
