# How the App Connector runbook checks Public Service Edge connectivity: Diagnostics filter, MTR, TCP and TLS tests, packet capture TTL and control connection journal lines (zpa.app-connectors.runbook.connectivity)
Also called: Troubleshooting Public Service Edge connectivity issues

**Console check.** To check the broker control connection in the Admin Console, go to Logs > Insights > Private Applications > Diagnostics, choose App Connector Status as the Log Type, and filter App Connector: Connection Type Equals Control Connection. [zpa.app-connectors.runbook.connectivity:diagnostics-control-connection]

**MTR.** The runbook's MTR example (mtr -rzwbec100 165.225.112.252) and guidance read Loss% as packet loss per hop, Snt as packets sent, Last/Avg/Best/Wrst as latency in milliseconds, and StDev as the standard deviation of the latencies. [zpa.app-connectors.runbook.connectivity:mtr-columns] Loss at a single MTR hop can be ICMP rate limiting rather than real loss: some providers rate limit the ICMP traffic MTR uses, and if the subsequent hop shows 0.0% loss it is likely rate limiting. [zpa.app-connectors.runbook.connectivity:mtr-loss-rate-limit]

**TCP, TLS and packet capture.** TCP checks to the broker on port 443 use telnet or mtr with --tcp -P443, and a TLS check uses the openssl command; if the earlier command does not present a certificate, the TLS connection is interrupted or a device in the path is doing SSL inspection. [zpa.app-connectors.runbook.connectivity:tcp-tls-checks] In a packet capture (sudo tcpdump -i any -w output.pcap) an incomplete TCP handshake while ICMP works points to a firewall blocking TCP to the Broker, on an external device or onboard iptables (checked with sudo iptables -nvL). [zpa.app-connectors.runbook.connectivity:pcap-handshake] When the App Connector sends a TCP SYN and gets a TCP RST from the Broker, the runbook compares 64 - TTL or 128 - TTL of the RST against the MTR hop count; in its example a TTL of 62 or 126 is 2 hops away, and if they do not match the mtr hop count some device in between is blocking the TCP connection and sending a TCP RST. [zpa.app-connectors.runbook.connectivity:pcap-rst-ttl] In the connectivity section, the runbook's SSL interception example log shows BEV_EVENT_READING BEV_EVENT_ERROR with 'self signed certificate in certificate chain', and the runbook says to allowlist the Private Access domains or IP addresses on the SSL interception device. [zpa.app-connectors.runbook.connectivity:ssl-interception-log] [divergence:zpa.app-connectors.runbook.connectivity:self-signed-log-two-causes]

**Journal lines.** Connector journal logs are exported with sudo journalctl > dump-of-journalctl.txt, and older App Connector logs are automatically stored in /var/log/messages; the runbook's disk cleanup step also says to prevent Zscaler processes from using syslogd, because journald already stores their logs. [zpa.app-connectors.runbook.connectivity:journal-export] Broker control connections are found in the journal with the keywords 'Broker control connection'; the working example shows state fohh_connection_connected with uptime, RTT (tcp|app) and disconnect_duration_s 0, and the non-working example logs the connection closed with FOHH_CLOSE_REASON_SOCKET_ERR. [zpa.app-connectors.runbook.connectivity:broker-control-log-lines] The runbook says a change, or frequent changes, in the control connection's uptime indicates the App Connector control channel was down; in its example log the connected uptime rises each minute (33M:8S, 34M:8S, 35M:8S), and the log also shows a close with FOHH_CLOSE_REASON_SOCKET_ERR, a broker_redirect for the control connection, a close with FOHH_CLOSE_REASON_REDIRECT, and a new connection whose uptime is 13S. [zpa.app-connectors.runbook.connectivity:uptime-changes] The runbook's Rx/Tx counter example shows log lines for a connection in fohh_connection_connected state with rx = 195538 and tx = 855420 and one in fohh_connection_backoff state with rx, tx and tx_drop at 0. [zpa.app-connectors.runbook.connectivity:fohh-counters-example] [gap:zpa.app-connectors.runbook.connectivity:status-line-meanings]

Sources disagree (name both sides):
- The runbook prints the same journal line, self signed certificate in certificate chain from co2br.prod.zpath.net, as the log for SSL interception and again as the log for an App Connector clock out of sync, so the line alone does not tell the two causes apart. [divergence:zpa.app-connectors.runbook.connectivity:self-signed-log-two-causes]
  - zscaler-help: The runbook presents the line as what the App Connector prints when an intermediate device performs SSL interception.
  - zscaler-help: The runbook presents the same line, under the heading for invalid certificate, as what the App Connector prints when its time is not in sync with the Private Access back-end servers.
  Impact: Seeing this line in the journal does not by itself show SSL interception; the clock on the connector host is a second cause the runbook gives for it, and the captured page does not say what else distinguishes them.
