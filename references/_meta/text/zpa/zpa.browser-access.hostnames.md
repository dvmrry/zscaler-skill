# External versus internal hostname for a Browser Access application (zpa.browser-access.hostnames)
Also called: browser access web server certificate error; browser access different external internal hostname; cert error browser access internal app; browser access internal hostname public dns; backend ssl cannot be verified

Whether the external and internal hostnames match decides what end users see and what public DNS exposes.

**Different hostnames.** When a Browser Access application uses different external and internal hostnames, the internal hostname is not exposed and has no record in public DNS. Backend SSL cannot be verified, so end users see a web server certificate error because the application's hostname does not match the certificate's hostname. [zpa.browser-access.hostnames:different-hostnames] What remedies exist is partly answered below and partly open [gap:zpa.browser-access.hostnames:backend-cert-remedies].

**Different external and internal domains.** For different external and internal domains, the internal FQDN must be properly named and the App Connectors must resolve it through the internal DNS. The desired external FQDN must be properly named; ideally the internal and external FQDNs use similar names, but split DNS (the domain and top-level domain are the same but the hostname varies) and separate DNS (the domain and top-level domain differ) also function. An SSL certificate must be created for the external FQDN, with CN=[external FQDN] and SAN=[internal FQDN]. [zpa.browser-access.hostnames:different-domains-prerequisites] Private Access does not transform the external FQDN, so a multihomed web server that expects a Host header matching the internal FQDN needs the external FQDN added as an additional header. Internal web servers must serve pages with objects linked as relative URLs, absolute URLs are not supported, and internal web servers must be single tenant. [zpa.browser-access.hostnames:different-domains-web-server] Whether that holds for Zscaler-managed certificates is open [gap:zpa.browser-access.hostnames:external-fqdn-and-managed-certificates]. One method disables dynamic server discovery and defines the target servers manually, which supports multiple web servers with no external load balancing; with several web servers behind one application, a server is added in the Admin Console for each internal FQDN. The certificate must match the external FQDN, HTTPS is selected as the protocol, and the Use Untrusted Certificates checkbox must be selected. [zpa.browser-access.hostnames:different-domains-static-servers] The other method enables dynamic server discovery and manually defines an A record in the internal DNS for the external FQDN, pointing to the IP address or load balancer virtual IP address of the internal web server hosting the application. It supports only one web server, unless third-party load balancing places multiple web servers behind a single IP address referenced by the A record. [zpa.browser-access.hostnames:different-domains-a-record] The certificate's CN and SAN are in [A web server CSR's subject has the form CN=<Common Name>,O=<Organization>,ST=<State>,C=<Country>,L=<Location>,OU=<Organizational Unit>, with CN listed first and the other attributes optional. The common name does not need to be a wildcard domain. A SAN, which takes domains only, lets the certificate cover multiple hostnames. The certificate can be signed by a public CA or be self-signed with trust established by the organization's PKI.](kb:zpa.browser-access.certificates:csr-subject-san).

**Several ports on one host.** For Browser Access-enabled applications, Service Edges listen only on ports 80 and 443 for inbound connections from web browsers. A port 80 connection is redirected to port 443, and a port 443 connection does domain virtualization through the provided Server Name Indication (SNI). As a consequence, Private Access receives only one domain name and one port, so mapping that domain and port combination to multiple ports is not possible, though ports can be mapped through multiple domain names. [zpa.browser-access.hostnames:ports-80-443-only] Zscaler recommends the unique hostname method for several ports on one host: unique hostnames per application, using internal DNS or explicitly defined static servers, advertise a unique external hostname that matches an internal hostname and port combination. In the page's example, dynamic server discovery works for all three applications as long as an internal DNS exists for their hostnames; otherwise static servers must be defined in the Admin Console. [zpa.browser-access.hostnames:unique-hostnames-method] FQDNs defined in an application segment must map to the Browser Access (web server) certificate selected for Private Access to maintain the chain of trust. In the page's example, crm.corp.com and webadmin.corp.com do not match the web server certificate, so Use Untrusted Certificates is selected for both. [zpa.browser-access.hostnames:fqdns-must-match-certificate] The alternative method maps several external hostnames to one internal server, which can also be specified by IP address, and all the applications can use the same server group. This causes certificate validation problems because the hostname check fails, so users see web server certificate errors for each of the example's three applications, and web server certificates cannot be verified. [zpa.browser-access.hostnames:defining-applications-method]

**Same hostname.** When the external and internal hostnames are the same, the internal hostname is exposed on public DNS. Backend SSL can be verified, so end users do not get a web server certificate error. [zpa.browser-access.hostnames:same-hostname]

The setting that tolerates an unverifiable backend certificate is in [Use Untrusted Certificates and unauthenticated OPTIONS for Browser Access](kb:zpa.browser-access.backend-options).

What to check:
1. Whether the application's external and internal hostnames differ, which alone explains a web server certificate error.
2. Whether exposing the internal hostname in public DNS is acceptable before moving to the same hostname.
3. Whether several applications on one host use unique hostnames, and whether each FQDN in the segment maps to the selected Browser Access certificate.
4. Which method an external versus internal domain setup uses, and whether the certificate has the external FQDN as CN and the internal FQDN as SAN.
5. Whether a proposed remedy is stated by a source or is the unverified backend-certificate option.

Not known (open gaps):
- Whether the external FQDN is left untransformed for Zscaler-managed certificates [gap:zpa.browser-access.hostnames:external-fqdn-and-managed-certificates]: settled by lab-test or source-read
- Remedies for the certificate error with different hostnames [gap:zpa.browser-access.hostnames:backend-cert-remedies]: settled by lab-test
