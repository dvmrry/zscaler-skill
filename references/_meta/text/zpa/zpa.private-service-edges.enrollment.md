# Enrolling a Private Service Edge (zpa.private-service-edges.enrollment)
Also called: pse enrollment; pse provisioning key; oauth2 user code private service edge; enrollment token; pse clone; private service edge deleted by mistake; pse not listed in console; enrollment_cert_id service edge
Former IDs: zpa-48, zpa-55

Enrolling a Private Service Edge is the step that gives an added instance its identity in a group.

**Console side.** Configuring a Private Service Edge involves adding it in the Admin Console, which includes applying enrollment tokens (preferred) or obtaining a Private Service Edge provisioning key, and then deploying it on a supported platform. [zpa.private-service-edges.enrollment:enrollment-tokens-preferred] OAuth-enabled Private Service Edges are added with a name in the format GroupName-UserCode-TimeStamp. [zpa.private-service-edges.enrollment:oauth-name-format] The Private Service Edges page lists deployed instances; instances that were added but not deployed are not listed. [zpa.private-service-edges.enrollment:listed-only-when-deployed] A Private Service Edge shows the enrollment certificate used to authenticate it during enrollment. [zpa.private-service-edges.enrollment:enrollment-cert-shown]

**Terraform side.** The Terraform Service Edge group resource supports two onboarding methods: OAuth2 user codes, recommended for new deployments, and a provisioning key, described as legacy and still supported. [zpa.private-service-edges.enrollment:tf-two-methods] For the provisioning-key method, a zpa_provisioning_key is created after the group that references the group's ID and the SERVICE_EDGE_GRP association type; the key is injected into the Private Service Edge VM at deployment. [zpa.private-service-edges.enrollment:tf-provisioning-key] [When the value is missing or empty, the resolver looks the certificate up by name, fails the operation on a lookup error or an empty ID, and otherwise sets enrollment_cert_id to the resolved ID.](kb:zpa.terraform.group-enrollment:resolver-lookup-by-name) Failure to verify user codes after the group is written is a provider behavior: [For private cloud groups and Service Edge groups, user code verification is a second request sent after create, and after update when `user_codes` changed. When it fails the resource returns an error: the group (and, on update, its new settings) is already written, and nothing is rolled back.](kb:zpa.terraform.resource-fidelity:user-code-verification-after-write). Association types for provisioning keys: [The provisioning-key lookups that do not take an association type (`GetByNameAllAssociations`, `GetByIDAllAssociations`) iterate a fixed SDK list of three association types: CONNECTOR_GRP, SERVICE_EDGE_GRP, NP_ASSISTANT_GRP. They also treat any error from one type's lookup (not only not-found) as a reason to try the next, and return the last attempt's error. A key stored under any other association type cannot be found through these helpers.](kb:zpa.sdk-go.service-defects:provisioning-key-all-associations-fixed-list). OAuth2 licensing beyond the version is open [gap:zpa.private-service-edges.enrollment:oauth2-prerequisites]. The module's OAuth2 default and provider minimum are in [Reference Terraform modules for Private Service Edges on AWS and Azure](kb:zpa.private-service-edges.reference-modules).

**Identity and cloning.** A Private Service Edge first generates a local private key encrypted with a hardware fingerprint, then enrolls: it generates a Certificate Signing Request, authenticates it with the provisioning key from the Admin Console, receives a signed TLS client certificate from the Private Access cloud, and the certificate is pinned to its hardware fingerprint. Once enrolled it is paired with a single customer account and cannot be enrolled again. [zpa.private-service-edges.enrollment:enrollment-steps] The Private Service Edge AWS guide says the image attempts to use OAuth enrollment tokens by default but applies a provisioning key first if one is available; the token is valid for 2 hours and is entered on the Add Private Service Edge page. [zpa.private-service-edges.enrollment:oauth-image-default] The AWS guide has the provisioning key file created with 644 permissions at /opt/zscaler/var/service-edge/provision_key; if the key is not detected when the Private Service Edge first starts, it is in a sleep cycle and looks for the key again every 24 hours. SSH access is required when enrolling with a provisioning key, and after the initial boot it might take up to 15 minutes for the admin credentials to apply. [zpa.private-service-edges.enrollment:key-file-and-sleep] Private Service Edges running in VM environments should never be cloned, because the keys will no longer match the virtual hardware fingerprints. [zpa.private-service-edges.enrollment:pse-clone-rule] Additional Private Service Edges can be deployed at any time with the same provisioning key to join the existing group. [zpa.private-service-edges.enrollment:same-provisioning-key-scales] OAuth 2.0 enrollment requires Manager software and Private Service Edge version 25.48.4 or later, and an enrollment token from a hyperscaler marketplace, virtual image or RPM installer provided by Zscaler (or a provisioning key); the OAuth server supports IPv4 only. [zpa.private-service-edges.enrollment:oauth-min-version]

**Recovery.** A Private Service Edge deleted from the console by accident is immediately refused by Private Access and cannot be recovered; the instance must be cleaned on the host (service stopped, /opt/zscaler/var/* removed, service restarted) and the configure-and-deploy process restarted. [zpa.private-service-edges.enrollment:deleted-pse-unrecoverable] To completely replace a deployed Private Service Edge, its configuration must be deleted and it must be re-enrolled; the new Private Service Edge provisioning key can be applied to the virtual machine (VM) image already deployed by replacing the old key. [zpa.private-service-edges.enrollment:replace-by-reenroll] The key itself is described in [Private Service Edge provisioning keys: what a key is, reuse limits, naming, View or Export, signing certificate and the keys page](kb:zpa.private-service-edges.provisioning-keys).

What to check:
1. Whether the Private Service Edge appears on the console page: only deployed instances are listed, so an added but undeployed one is absent.
2. Which enrollment method the instance used, from its name: OAuth-enabled instances are named GroupName-UserCode-TimeStamp.
3. Whether a Private Service Edge deleted from the console is still running; it cannot be recovered and must be removed on the host and redeployed.
4. Whether the Terraform group was applied with user codes and the verification step failed after the group was created, which leaves the group written.
5. Whether a cloned VM is the reason an instance fails to enroll.
