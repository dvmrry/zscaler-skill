# Constraints the ZPA Terraform docs and provider code place on individual resources (zpa.terraform.resource-constraints)
Also called: zpa terraform tcp_quick_ack inconsistent; zpa terraform provisioning key state; zpa_private_cloud_group site_id; zpa_ba_certificate import; zpa terraform inspection certificate_id HTTP; zpa_pra_approval_controller start_time

These are provider-side constraints the Terraform docs or code state for individual ZPA resources. Each resource's arguments, enums and defaults are generated from the provider code (`node scripts/kb.mjs surface <resource name>`); these are the constraints the schema does not show.

**Application segments.** The segment resource docs say application segments must have unique ports and cannot have overlapping domain names using the same TCP or UDP ports across segments; the docs do not say when the API enforces it. [zpa.terraform.resource-constraints:segment-unique-ports-domains] The segment docs recommend the tcp_port_range and udp_port_range blocks over the older tcp_port_ranges and udp_port_ranges string lists. [zpa.terraform.resource-constraints:port-range-blocks-recommended] The Browser Access segment doc says that when removing TCP or UDP ports the parameter must still be defined but set empty, because of current API behavior. [zpa.terraform.resource-constraints:browser-empty-ports-to-clear] Whether the empty-assignment rule holds for the other segment kinds is open [gap:zpa.terraform.resource-constraints:empty-ports-other-segment-kinds]. For inspection and PRA segments the docs say the domain configured on each nested apps_config entry must also be in domain_names and its ports must also be in the segment's port list. [zpa.terraform.resource-constraints:subapp-domain-ports-in-parent] Whether the same holds for Browser Access is open [gap:zpa.terraform.resource-constraints:browser-clientless-domain-in-domain-names]. On an inspection segment the nested app's certificate_id is not supported when application_protocol is HTTP, and the provider rejects it at plan time. Up to v4.4.11 the docs said it is required whenever application_protocol is HTTPS; from v4.4.12 it is required for HTTPS only when auto_app_protect_enabled is unset or false, which the provider enforces at plan time, and not required when auto_app_protect_enabled is true because the API manages the certificate (#690). [zpa.terraform.resource-constraints:inspection-certificate-https-only] On a PRA segment connection_security is required when application_protocol is RDP and is accepted only for RDP, so it must not be set for SSH. [zpa.terraform.resource-constraints:pra-connection-security-rdp-only] Segment write behavior is in [What the ZPA Terraform provider sends, keeps and cleans up for application segments and their associations](kb:zpa.terraform.app-segment-lifecycle).

**Server groups.** Whether extranet_dto needs extranet_enabled is open [gap:zpa.terraform.resource-constraints:extranet-dto-needs-extranet-enabled]. Dynamic discovery rules are in [Dynamic discovery versus explicit servers on a server group](kb:zpa.server-groups.discovery-mode) and destroy behavior in [Deleting a server group through Terraform](kb:zpa.server-groups.delete).

**Connector and edge groups.** The App Connector group resource rejects, on create and update, a request whose three tcp_quick_ack flags are not all equal, with the provider-side error that the tcpQuickAck flags need to be consistent; the docs say the three fields must share one value. [zpa.terraform.resource-constraints:quick-ack-flags-checked-by-provider] The ZPA error code AST_MT_SETUP_ERR_PRA_UNAVAILABLE, named "AC: Connector cannot establish PRA m_tunnel", gives the admin action to check whether the PRA capability is enabled on the App Connector group; the provider's pra_enabled attribute is documented as whether PRA is enabled on the group. [zpa.terraform.resource-constraints:pra-unavailable-error-points-to-group] Whether a PRA segment fails outright through a group with pra_enabled false is still open [gap:zpa.terraform.resource-constraints:pra-enabled-required-for-pra]. The App Connector and Service Edge assistant schedule resources need customer_id the first time the schedule is enabled, unless ZPA_CUSTOMER_ID supplies it. [zpa.terraform.resource-constraints:assistant-schedule-customer-id] An assistant schedule's frequency is days, and frequency_interval is 5, 7, 14, 30, 60 or 90, with a minimum of 5. [zpa.terraform.resource-constraints:schedule-minimum-5-days] The enrollment certificate is in [How the ZPA Terraform provider resolves the enrollment certificate for connector, service edge and private cloud groups](kb:zpa.terraform.group-enrollment).

**Keys, certificates and identities.** The provisioning_key value is stored in Terraform state even though the attribute is marked sensitive; the doc says the ZPA API returns it in clear text and advises an encrypted remote backend, max_usage limits and ip_acl. [zpa.terraform.resource-constraints:provisioning-key-in-state] The zpa_ba_certificate cert_blob is PEM content, and the Certbot example builds it from both cert.pem and privkey.pem. [zpa.terraform.resource-constraints:ba-certificate-blob-key-and-cert] zpa_ba_certificate's cert_blob carries the certificate's private key, but the schema does not mark it Sensitive, so Terraform shows it in plan output and stores it in state as plain text. [zpa.terraform.resource-constraints:ba-certificate-blob-not-sensitive] The microtenant controller resource is in limited availability and requires an additional license. [zpa.terraform.resource-constraints:microtenant-controller-license] The docs say import is unsupported but the code defines importers [divergence:zpa.terraform.resource-constraints:docs-no-import-but-importer-exists]. On zpa_ba_certificate, cert_blob is an Optional, ForceNew argument and the update function is a no-op; Read sets name, description, certificate and microtenant_id from the API response. [zpa.terraform.resource-constraints:ba-certificate-blob-forcenew] Read never fills cert_blob, so after importing a BA certificate a configuration that sets cert_blob plans a replacement of the certificate; recovering lost state in practice means uploading the certificate again. [zpa.terraform.resource-constraints:ba-certificate-import-replaces] Other secret handling is in [How the Zscaler Terraform providers store, log, and send secrets](kb:shared.terraform.credential-handling).

**PRA.** The PRA credential resource's credential_type and its associated attributes cannot be updated after creation, and the credential pool's credential_type cannot be updated either. [zpa.terraform.resource-constraints:pra-credential-type-not-updatable] A PRA console's pra_application.id is documented as the ID of an apps_config block inside the segment's common_apps_dto. [zpa.terraform.resource-constraints:pra-console-application-is-apps-config-id] A PRA approval takes a list of email IDs but the ZPA API supports a single address; the docs say start_time cannot be more than one hour in the past and end_time cannot be more than one year or 365 days away. [zpa.terraform.resource-constraints:pra-approval-single-email-window]

**AppProtection and CBI.** An inspection profile must always include the default Preprocessors predefined control, and paranoia_level is 1 to 4 inclusive. [zpa.terraform.resource-constraints:inspection-profile-preprocessors-mandatory] An inspection custom control's default_action is PASS, BLOCK or REDIRECT, and default_action_value is the redirect URL used when the action is REDIRECT; the resource code passes the value through without checking it against the action. Its create function has a REDIRECT check, but that check tests `Action` and `ActionValue`, which the expander never sets, so the value passes unchecked. [zpa.terraform.resource-constraints:custom-control-redirect-value] What the API does with a stray redirect value is open [gap:zpa.terraform.resource-constraints:api-redirect-value-with-other-action]. The CBI external profile docs say flattened_pdf must be false when upload_download is all and upload_download must be none or upstream when flattened_pdf is true; they also say at least two regions are required. [zpa.terraform.resource-constraints:cbi-profile-constraints] The CBI banner logo must be a .jpeg or .png image of at most 100KB. [zpa.terraform.resource-constraints:cbi-banner-logo-limit]

**Tags.** The tag namespace, tag key and tag group resources are Early Access; a tag key's namespace_id is ForceNew, and a tag key imports with the composite namespace ID and tag key ID or name. [zpa.terraform.resource-constraints:tags-early-access-key-import] Provider issue #696 asked for tags on `zpa_policy_access_rule_v2` and `zpa_application_segment`, saying the reporter had found no way to apply them to segments and policies managed in Terraform without an API call after Terraform; it was closed as completed on 2026-10-22 with a reply from a member of the repository's organization, signed Zscaler DevRel, to upgrade to v4.4.15. [zpa.terraform.resource-constraints:tags-on-rules-and-segments-request] Provider v4.4.15 added a `tags` argument to the `zpa_application_segment` resource and data source. Each `tags` block pairs a `tag_key_id` with a `tag_value_id`, so one block attaches one tag value of a tag key to the segment. [zpa.terraform.resource-constraints:app-segment-tags-4-4-15] Provider v4.4.15 added the policy condition object types `ENTITY_TAG_GRP` and `ENTITY_TAG_VAL` to the `zpa_policy_access_rule` and `zpa_policy_access_rule_v2` resources, whose object_type validators list them after `WORKLOAD_TAG_GROUP`; the same release added the `tags` attribute to `zpa_application_segment`. [zpa.terraform.resource-constraints:access-rule-entity-tag-types-4-4-15] Provider v4.4.16 fixed `zpa_policy_access_rule` so the object types LOCATION, BRANCH_CONNECTOR_GROUP, CHROME_POSTURE_PROFILE, WORKLOAD_TAG_GROUP, ENTITY_TAG_GRP and ENTITY_TAG_VAL no longer fail on apply with `invalid operand object type`, and fixed the v2 policy rule resources to stop dropping IDP, WORKLOAD_TAG_GROUP, ENTITY_TAG_GRP and ENTITY_TAG_VAL operands when a rule is read. [zpa.terraform.resource-constraints:access-rule-object-type-fixes-4-4-16] At v4.4.16 the access rule docs tie ENTITY_TAG_GRP to the `zpa_tag_group` data source and `tag_group_id`, and ENTITY_TAG_VAL to the `zpa_tag_key` data source and `tag_value_id`, in both the v1 and v2 pages. [zpa.terraform.resource-constraints:access-rule-entity-tag-docs-4-4-16] At v4.4.16 the v1 operand validator checks ENTITY_TAG_GRP and ENTITY_TAG_VAL operands with `acceptAnyID`, a getter that looks nothing up, so the operand's rhs is not checked against the API. [zpa.terraform.resource-constraints:entity-tag-v1-validation-4-4-16] Whether the API accepts zpa_tag_group IDs under ENTITY_TAG_GRP is open [gap:zpa.terraform.resource-constraints:tag-group-in-policy-conditions].

**ZIA link and private cloud.** The provider doc says zpa_zia_cloud_config, which stores ZIA credentials and a sandbox API token in the ZPA tenant, is required when configuring zpa_policy_capabilities_rule. [zpa.terraform.resource-constraints:zia-cloud-config-needed-for-capabilities] zia_cloud_domain accepts only zscaler, zscloud, zscalerone, zscalertwo, zscalerthree, zscalerbeta, zscalergov, zscalerten and zspreview, written without .net; the provider appends .net to the stored and sent value. [zpa.terraform.resource-constraints:zia-cloud-domain-values] The private cloud group doc and schema disagree about site_id [divergence:zpa.terraform.resource-constraints:private-cloud-site-id].

**LSS.** The LSS doc pages other than zpa_lss_config_controller (audit logs, web browser and the rest) declare the same zpa_lss_config_controller resource with a different source_log_type, and the provider registers zpa_lss_config_controller as the LSS resource. [zpa.terraform.resource-constraints:lss-aliases-one-resource] The LSS User Activity example sets a policy_rule_resource whose action is LOG, and the same doc lists LOG as the supported action value. [zpa.terraform.resource-constraints:lss-policy-rule-action-log] The Audit Logs doc gives two different tokens for Audit Logs [divergence:zpa.terraform.resource-constraints:lss-doc-token-inconsistent]. Which log types accept a policy rule is in [Narrowing a ZPA log stream: status codes and streaming policy](kb:zpa.log-receivers.filtering), and the log type codes are in [Log types a ZPA log receiver can carry, and their codes](kb:zpa.log-receivers.log-types).

Inferred, not quoted (say so when an answer rests on one):
- [zpa.terraform.resource-constraints:ba-certificate-blob-not-sensitive] Tier B: The schema block and the docs' example (a PRIVATE KEY block in cert_blob) are quoted; that a non-Sensitive argument appears in plan output and in state is Terraform behavior, not shown in a captured source.
- [zpa.terraform.resource-constraints:ba-certificate-import-replaces] Tier B: Follows from Read setting only the four listed attributes and cert_blob being ForceNew. It assumes Terraform plans a replacement when a configured ForceNew argument differs from the empty imported value, which is Terraform behavior not shown in a captured source.

Sources disagree (name both sides):
- The docs say the assistant schedules, BA certificate and emergency access user cannot be imported, but each resource defines an importer. [divergence:zpa.terraform.resource-constraints:docs-no-import-but-importer-exists]
  - tf-zpa: The App Connector and Service Edge assistant schedule docs say import is not currently supported.
  - tf-zpa: The BA certificate doc says the resource does not support importing.
  - tf-zpa: The emergency access user doc says it does not support resource import.
  - tf-zpa: The BA certificate resource defines a passthrough importer.
  - tf-zpa: The App Connector assistant schedule resource also sets the passthrough importer.
  - tf-zpa: The emergency access resource also sets an Importer.
  Impact: terraform import is not blocked by the provider for these resources even though the docs say it is unsupported; what the import then produces is separate (the schedule read, for example, never writes the ID: zpa.terraform.resource-fidelity). For the BA certificate the import succeeds, but Read never sets the ForceNew cert_blob, so the next plan replaces the certificate and the docs' advice to re-upload it is in effect right.
- The Private Cloud group doc documents a site_id argument, but the resource schema has it commented out. [divergence:zpa.terraform.resource-constraints:private-cloud-site-id]
  - tf-zpa: The doc lists site_id as a String, the Site ID for the Private Cloud Group, and uses it in both examples.
  - tf-zpa: The schema entry and the read and expand statements for site_id are commented out, so the resource has no site_id argument.
  Impact: A configuration that sets site_id on zpa_private_cloud_group, as the doc examples do, would be rejected as an unsupported argument, and the legacy reference's statement that site_id links the group to a Site Controller site cannot be used.
- The LSS docs give conflicting source_log_type tokens for the same log type. [divergence:zpa.terraform.resource-constraints:lss-doc-token-inconsistent]
  - tf-zpa: The Audit Logs doc's introduction and the source_log_type entry in its Optional section say to use zpn_http_trans_log for Audit Logs.
  - tf-zpa: The same doc's Required section says to use zpn_audit_log for Audit Logs, and its example sets source_log_type to zpn_audit_log.
  Impact: Two places in the doc (the introduction and the Optional section) give the Web Browser token zpn_http_trans_log for Audit Logs, while the Required section and the example use zpn_audit_log; a reader following the Optional section would configure the wrong log type.
