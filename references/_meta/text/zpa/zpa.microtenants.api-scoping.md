# How an API call selects a Microtenant (zpa.microtenants.api-scoping)
Also called: microtenantId query parameter; microtenant_id; ZPA_MICROTENANT_ID; microtenant scope api; add_microtenant microtenantId; update_microtenant; microtenants/search; microtenant default 0

Scope travels as a query parameter, and several layers can supply it.

**Values.** The ZPA API reference describes the `microtenantId` query parameter on the application move operation as the Microtenant's unique identifier, where 0 is passed for the Default Microtenant and null for the customer data Microtenant. [zpa.microtenants.api-scoping:scope-param-values] The ZPA API reference for the application federation and tenant federation operations (`application/federate`, `application/host/{host_id}` and the `tenant-federation` paths) says that if you are within a Microtenant you must pass `microtenantId` to retrieve that Microtenant's data, and that a create or update that omits it takes effect in the Default Microtenant. [zpa.microtenants.api-scoping:omitted-scope-defaults-default]

**Python.** [The executor picks the microtenant ID from the request body's `microtenantId` first, then from the params' `microtenantId`, then from the client configuration.](kb:zpa.sdk-python.microtenant-scoping:executor-precedence) [The Python LegacyZPAClient reads its settings from the configuration or from the environment variables ZPA_CLIENT_ID, ZPA_CLIENT_SECRET, ZPA_CUSTOMER_ID, ZPA_MICROTENANT_ID and ZSCALER_PARTNER_ID, and takes the cloud from ZSCALER_CLOUD with PRODUCTION as the default.](kb:zpa.sdk-python.client-configuration:legacy-client-env) [In the Python SDK's update_microtenant, the microtenant_id argument used to build the URL is reassigned from the request body's microtenant_id key (kept in the body) before the query parameter and the 204 stand-in object are built, so a caller who does not also pass microtenant_id as a keyword gets no microtenantId query parameter and a stand-in object whose id is None.](kb:zpa.api.microtenants-wire:update-rebinds-id) `add_microtenant` sends its keyword arguments as the request body and builds no `microtenantId` query parameter itself, and the OpenAPI create operation declares only the customer ID parameter. [zpa.microtenants.api-scoping:add-method-builds-no-scope]

**Search and models.** `POST /microtenants/search` takes a body of `filterBy` (name, operator and values per condition), `pageBy` and `sortBy` (`sortName`, `sortOrder`); the Python SDK's `get_microtenant_search` documents a `filter_and_sort_dto` keyword argument, which its docstring example passes the whole DTO under, and sends its keyword arguments as the body. [zpa.microtenants.api-scoping:search-filter-shape] A call shaped like that docstring example therefore sends the DTO nested under one `filterAndSortDto` key, rather than `filterBy`, `pageBy` and `sortBy` at the top level of the body. [zpa.microtenants.api-scoping:search-dto-nested] [The Go and Python segment models carry `readOnly`, `zscalerManaged` and `restrictionType`.](kb:zpa.app-segments.api-fields:governance-fields) What those fields signal is in [Sharing and moving between Microtenants](kb:zpa.microtenants.share-and-move), and a missing `microtenantId` on a response is open [gap:zpa.microtenants.api-scoping:unset-microtenant-id-meaning].

**Resolver defects.** The data-source and name-resolver behavior that picks the wrong Microtenant is held in [For these data sources an operator cannot choose the microtenant per data source: the read uses the unscoped service, so a name, ID or list lookup is made in whatever scope the client defaults to, and can return an object from a different microtenant than the one intended or miss one that exists only in the intended microtenant.](kb:zpa.terraform.data-source-selection:reads-run-unscoped-wrong-microtenant), [When a ZPA request has no `microtenantId` query parameter, the SDK takes it from the request body, then from the `ZPA_MICROTENANT_ID` environment variable, and only then from the client's configured microtenant. A set environment variable therefore overrides the configured value. One call site passes an empty string for the configured value, so on that path the configuration is never used.](kb:zpa.terraform.data-source-selection:inject-precedence-env-over-config) and [When a `MicroTenantName` filter is supplied and the name lookup succeeds, the SDK's paged-list helper returns immediately with a nil list and a nil error. The caller sees a successful empty result, and the resolved microtenant ID is never applied.](kb:zpa.terraform.data-source-selection:sdk-microtenant-name-success-returns-nothing), not restated here.

On the credential move operation the microtenantId query parameter is described as taking 0 for the Default Microtenant and null for the customer data Microtenant, while targetMicrotenantId is described as taking 0 for the Default Microtenant and says nothing about null. [zpa.microtenants.api-scoping:credential-move-target-zero-only]

[gap:zpa.microtenants.api-scoping:schedule-microtenant-id-convention]

What to check:
1. Which scope the request targets: the specification's 0 for the Default Microtenant, null for customer data, and, on the application federation and tenant federation operations, the Default Microtenant for creates and updates that omit the parameter.
2. Where the Python SDK takes the scope from, in order, and whether the legacy client environment variable is set.
3. Whether an update_microtenant call passes `microtenant_id` as a keyword argument, since the positional ID does not become the query parameter.
4. Whether the create call should be scoped, noting the method builds no scope of its own.
5. Which Terraform and Go SDK lookups can run unscoped or in the wrong Microtenant.
6. Whether a response without a `microtenantId` can be read as belonging to the Default Microtenant.
