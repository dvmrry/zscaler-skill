# Tunnels, certificates and firewall requirements on the Private Service Edge path (zpa.private-service-edges.data-path)
Also called: z-tunnel; m-tunnel; microtunnel; ssl inspection breaks zpa; pinned certificates; pse firewall rules; pse cannot connect to zpa cloud; pb2br; pse not connected to private access cloud

The path between a user and a private application is a pair of Z-Tunnels joined by an M-Tunnel at the Service Edge.

**Tunnels.** All communication between Private Access components travels within a mutually pinned, client and server certificate-verified TLS connection, and a microtunneling protocol runs inside that Zscaler Tunnel (Z-Tunnel). [zpa.private-service-edges.data-path:ztunnel-mutual-tls] The Z-Tunnel is defined as a mutually authenticated point-to-point connection between Zscaler Client Connector and a Zscaler-managed Public Service Edge, or between an App Connector and an organization-managed Private Service Edge. It carries no direct IP data and can carry multiple Microtunnels. [zpa.private-service-edges.data-path:ztunnel-endpoints] Which hop Client Connector terminates on is not settled [gap:zpa.private-service-edges.data-path:ztunnel-zcc-to-pse]. An M-Tunnel originates in Zscaler Client Connector, extends to the Private or Public Service Edge using a tag Client Connector created, extends to the App Connector using a different tag the connector chose, and the App Connector connects it to the application server. At no point is actual IP identification data passed. [zpa.private-service-edges.data-path:mtunnel-stitching] [Private Access selects the closest App Connector given the location of the user and the App Connector-to-application latency.](kb:zpa.app-connectors.selection:closest-by-location-and-latency)

**Certificates.** Zscaler Client Connector and App Connectors authenticate with the organization's public key infrastructure (PKI); Public Service Edges and Private Service Edges authenticate with Zscaler's PKI. The Z-Tunnel is further authenticated using SAML 2.0. [zpa.private-service-edges.data-path:pki-roles] Public and Private Service Edges use only public keys to authenticate remote systems and clients; no private key is stored or used except the Service Edge's own identity. [zpa.private-service-edges.data-path:identity-key-only] Because client and server use pinned certificates, it is cryptographically impossible for Private Access to experience a Man-in-the-Middle (MITM) attack: client certificates are verified against the organization's CA and server certificates against Zscaler's CA. [zpa.private-service-edges.data-path:no-mitm-pinning] Whether the Private Service Edge ever terminates application content is not stated [gap:zpa.private-service-edges.data-path:not-a-proxy].

**Interception and firewalls.** Private Access does not support SSL interception: a device that intercepts SSL between the Private Service Edge and the Zscaler cloud makes the connection fail. The Private Access domains or IP addresses must be allowlisted on the interception device so that the Private Service Edge and Zscaler URLs are bypassed. [zpa.private-service-edges.data-path:ssl-interception-unsupported] A Private Service Edge deployed behind a firewall needs the firewall to allow outbound connections to the Public Service Edge IP addresses and inbound connections from App Connectors and Zscaler Client Connectors. [zpa.private-service-edges.data-path:firewall-requirements] App Connectors never communicate with each other and accept no inbound connections; they need only an outbound connection to reach Public or Private Service Edges, and they stay authenticated to the nearest Public or Private Service Edge. [zpa.private-service-edges.data-path:app-connector-outbound-only] Each Private Service Edge must accept incoming connections from internal sources, remote users or both, as the use case needs, on TCP port 443, and behind a firewall it needs a unique private IP reachable on the internal network. [zpa.private-service-edges.data-path:tcp-443-inbound] When a Private Service Edge sits behind a firewall that performs destination NAT, the public IP the firewall advertises must be configured as a publish IP of that Private Service Edge. [zpa.private-service-edges.data-path:dnat-publish-ip] After enrollment a Private Service Edge opens an outbound TLS tunnel over TCP port 443 to the Private Access cloud, carrying keepalives to the Public Service Edge, policy configuration download and software upgrades. [zpa.private-service-edges.data-path:outbound-tunnel-443] A Private Service Edge can be deployed where outbound internet traffic is restricted, provided it can reach all Zscaler data centers containing Public Service Edges; a partial firewall configuration causes end-user connectivity problems. [zpa.private-service-edges.data-path:restricted-outbound] The Private Service Edge Linux guide says all of the Zscaler data centers containing Public Service Edges must be allowed, that a partial firewall configuration will result in connectivity problems for end users, and that Zscaler provides a 90-day notice for activating additional IP CIDR ranges. [zpa.private-service-edges.data-path:cidr-notice] All inline or man-in-the-middle TLS interception must be disabled, and *.prod.zpath.net must be in the SSL bypass list for traffic from the Private Service Edge. [zpa.private-service-edges.data-path:tls-bypass-list] UDP is not stated [gap:zpa.private-service-edges.data-path:dtls-udp].

**Published and listen addresses.** A deployed Private Service Edge's Publish IPs or Domains are the IP addresses and domains that clients and App Connectors can use to open a connection to it; if not specified, they try to connect using the Listen IPs. The page's primary use case is specifying a Private Service Edge by name and using DNS to find it, and another is an IP address that is a static external IP address controlled by the Private Service Edge system (e.g., AWS) rather than part of the Private Service Edge. [zpa.private-service-edges.data-path:publish-ips-or-domains] Automatically Publish IPv6, disabled by default, publishes both IPv4 and IPv6 addresses if a Publish IP address or domain isn't configured, so Zscaler Client Connector can receive both; disabled, only IPv4 addresses are published. The Private Service Edges must be set up for IPv6 to use it. [zpa.private-service-edges.data-path:automatically-publish-ipv6] Listen IPs are the interface addresses of the Private Service Edge system on which it listens for connection requests from clients and App Connectors; if not configured, it automatically listens on all interfaces, and the page says the common use case is to specify no Listen IPs. [zpa.private-service-edges.data-path:listen-ips] The API and Terraform fields behind these settings were not checked [gap:zpa.private-service-edges.data-path:publish-listen-api-fields].

**Diagnostics.** Connectivity from a Private Service Edge to its upstream Public Service Edge is tested by querying pb2br.prod.zpath.net from the Private Service Edge host, which returns two IPs when healthy, and by opening a TLS connection with openssl, which returns a certificate subject from the Public Service Edge. [zpa.private-service-edges.data-path:upstream-connectivity-test] Running curl localhost:8500/fohh/servers?small on the Private Service Edge confirms which App Connectors it is connected to. [zpa.private-service-edges.data-path:connected-app-connectors-command]

Behavior when an App Connector cannot reach the Private Service Edge is in [When the Private Service Edge has no direct connection to the App Connector serving an application, or no App Connector can establish a data connection to the Private Service Edge where the user is connected, the Private Service Edge forwards the request to a Public Service Edge (the nearest one, in the no-direct-connection case). The Public Service Edge connects to the closest App Connector it can reach and completes the request through the Private Service Edge with an additional hop.](kb:zpa.private-service-edges.what-it-is:relay-via-public).

What to check:
1. Whether an SSL interception device sits between the Private Service Edge and the Private Access cloud; the error shows a self-signed certificate in the chain.
2. Whether name resolution of pb2br returns two addresses from the host that runs the Private Service Edge, then whether a TLS connection to it returns a Zscaler certificate subject.
3. Which App Connectors a Private Service Edge is currently connected to, from the local status endpoint.
4. Whether the firewall allows outbound to the Public Service Edge IPs and inbound from App Connectors and Zscaler Client Connector.
