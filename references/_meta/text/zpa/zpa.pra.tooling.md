# PRA operations in the Python SDK and Ansible approvals (zpa.pra.tooling)
Also called: get_credential_pool_info; expired_approval; add_bulk_console; credential_move; pra_approval working_hours; zpa_pra_approval ansible; pra bulk console; purge expired privileged approvals api

SDK and Ansible calls for PRA objects map onto a few operations. Terraform behavior for PRA is in the provider-defect subjects, and the segment reconciliation in Ansible is in [How the Ansible Browser Access, PRA and Inspection modules reconcile child applications](kb:zpa.app-segments.ansible-children).

**Python SDK operations.** The Python SDK's get_credential_pool_info(pool_id) calls GET /credential-pool/{pool_id}/credential and returns the credential information mapped to the pool. [zpa.pra.tooling:pool-credential-info] The Python SDK's expired_approval(microtenant_id) deletes all expired privileged approvals through DELETE /approval/expired. [zpa.pra.tooling:expired-approval-cleanup] The Python SDK's add_bulk_console(consoles) creates several PRA consoles in one call through POST /praConsole/bulk. [zpa.pra.tooling:bulk-console-add] [POST /credential/{id}/move has no request body and returns 204; the destination is the targetMicrotenantId query parameter, where 0 means the Default microtenant. The Python SDK raises an error when target_microtenant_id is falsy; the Go SDK appends the parameter only when the string is non-empty. The contract also takes an optional microtenantId query parameter. The Python SDK forwards microtenant_id as microtenantId; Go's CredentialMove has no per-call microtenantId parameter and ignores the service's microtenant, so microtenantId reaches the request only from the ZPA_MICROTENANT_ID environment variable or the client's configured microtenant.](kb:zpa.api.pra-wire:credential-move)

**Approvals and working hours.** In the Python SDK pra_approval, working_hours is optional: time conversion defaults to UTC when it is omitted, and workingHours is sent only when the caller supplies it, because the API rejects a partial or empty workingHours object. The 1.9.34 release note records a working_hours fix. [zpa.pra.tooling:working-hours-optional] The ZPA Ansible collection made working_hours optional for zpa_pra_approval in 2.2.5 and fixed update to send the intended payload instead of the raw existing approval. [zpa.pra.tooling:ansible-working-hours] The Ansible zpa_pra_approval module selects an existing approval by email_ids and, when supplied, application_ids. An approval with the same email set and a different application set is skipped, so the requested approval is created rather than overwriting the unrelated one. [zpa.pra.tooling:ansible-approval-match]

Terraform delete and credential-rule defects are in [What the ZPA Terraform provider does when deleting objects with dependents](kb:zpa.terraform.delete-paths) and [What the ZPA Terraform provider sends and loses when writing policy rules](kb:zpa.terraform.policy-rule-writes); approval validation and PRA console read defects are in [ZPA Terraform resources: fields not sent, not read back, or written in several non-atomic steps](kb:zpa.terraform.resource-fidelity); secret handling is in [How the Zscaler Terraform providers store, log, and send secrets](kb:shared.terraform.credential-handling).

Two approvals with the same emails and applications are indistinguishable to the module: The Ansible approval lookup compares the sorted email set and, when application IDs are supplied, the sorted application ID set, and does not compare the approval's start or end window. [zpa.pra.tooling:ansible-approval-lookup-ignores-windows]

Whether the module can pick between approvals that differ only by window is open [gap:zpa.pra.tooling:approval-identity-windows].

Whether the credential-pool endpoints the SDKs call are a supported API surface is open [Whether the undocumented waap-pra-config credential-pool endpoints are a supported API surface](kb:zpa.api.pra-wire:credential-pool-not-in-contract).

What to check:
1. Whether a pool-exhaustion investigation can read which credentials the pool holds through the pool-info operation.
2. Whether an approval payload omits working_hours, which current SDK and Ansible versions allow.
3. Whether two Ansible approvals for the same emails but different applications are intended.

Not known (open gaps):
- Whether approvals may share an email set and application set while having different time windows [gap:zpa.pra.tooling:approval-identity-windows]: settled by lab-test. Blocks: selecting the right existing approval when only the window differs
