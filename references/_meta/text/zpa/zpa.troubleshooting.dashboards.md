# Applications, Users, Health, Extranet and Source IP Anchoring dashboards (zpa.troubleshooting.dashboards)
Also called: health dashboard; applications dashboard; users dashboard; extranet dashboard; source ip anchoring dashboard

These are the console dashboards for applications, users, application and connector health, extranet resources and Source IP Anchoring. The App Connector, Private Service Edge and Private Cloud Controller dashboards are in [App Connector, Private Service Edge and Private Cloud Controller dashboards](kb:zpa.troubleshooting.component-dashboards), and health probing itself is in [App Connector health, status values and telemetry](kb:zpa.app-connectors.health).

**Applications.** The Applications dashboard shows data over 1 Hour to 14 Days or a Custom Range whose start and end date are within the last 14 days, and by default the last hour. Its log information is limited to 14 days, and the Log Streaming Service gives longer access. [zpa.troubleshooting.dashboards:apps-range] One Applications dashboard count is based on the applications accessed by users and includes all successful and unsuccessful transactions, while another is based only on successful transactions. [zpa.troubleshooting.dashboards:apps-counts] The Applications dashboard displays a minimum of 4 and a maximum of 8 selected charts, and the Users dashboard a minimum of 3 and a maximum of 6. [zpa.troubleshooting.dashboards:chart-limits] The Applications dashboard's Federated By filter separates applications federated by the tenant (My Tenant) from those federated by a partner (Partner), and Partner requires the Partner filter with a valid value in addition. [zpa.troubleshooting.dashboards:federated-by] A widget on the Applications dashboard shows the top errors users experienced per connection status code, application, App Connector and Private Service Edge over the selected time frame, and another shows the top access policy and timeout policy blocks. [zpa.troubleshooting.dashboards:top-errors] A widget lists the applications Zscaler has discovered for the organization in the past 14 days, most recently discovered first. An application not accessed in the last 14 days has no data in Diagnostics, and the widget's CSV export of the applications discovered in the last 14 days gives the application domain name, port number, protocol and internal application ID. [zpa.troubleshooting.dashboards:discovered-apps] Application categories such as Database, Finance, HR Management and AI/ML are identified using App Type Fingerprinting, and the AI-Powered Recommendations by Attack Surface Reduction % widget needs AI-Powered Recommendations to be activated to display and populate. [zpa.troubleshooting.dashboards:app-type-fingerprinting] A widget compares Defined Application Segments with Discovered Applications in two-week increments over the past 3 months, and the page says that ideally for Zero Trust the defined count should increase while the discovered count decreases. [zpa.troubleshooting.dashboards:app-config-3-months]

**Users.** The Users dashboard shows user data over 1 Hour to 14 Days or a Custom Range. [zpa.troubleshooting.dashboards:users-range] The time-range filter applies to all Users dashboard widgets except Current Connected Users, which shows users for up to the last 30 minutes and counts users who are logged in to Client Connector and authenticated and connected to Private Access. A widget for users that requested applications and successful machine tunnel connections always ends at the current time even when a custom range with another end time is selected. [zpa.troubleshooting.dashboards:current-connected] Users dashboard widgets include users blocked by the organization's configured policies, the top 10 policies that blocked users, and the top users by tunnel count in the selected time frame. [zpa.troubleshooting.dashboards:users-widgets]

**Health.** On the Health dashboard, application health is checked and reported by the App Connectors the organization has deployed. Applications that are up are functioning as expected, and applications that are down are not accessible to users, most likely because a server that hosts the application is down or unhealthy. [zpa.troubleshooting.dashboards:health-app-states] An application can have several hosting servers; when at least one is unhealthy or down but at least one is up, users can still access the application. [zpa.troubleshooting.dashboards:health-partial] One Health dashboard application status is shown only for applications on segments with Health Reporting set to On Access. It indicates Private Access has stopped reporting the application's health because more than 30 minutes have passed since a user accessed it, and health is reported again as soon as a user accesses the application. [zpa.troubleshooting.dashboards:health-unknown] The page also says an On Access segment shows no state [divergence:zpa.troubleshooting.dashboards:health-no-state]. An application with Client Hostname Validation enabled to facilitate client-to-client remote assistance is not shown on the Health dashboard. [zpa.troubleshooting.dashboards:health-hostname-validation] App Connector health on the Health dashboard is checked and reported by the Private Access cloud, and a down connector is not functional. A Disabled label appears under a disabled App Connector not yet processed as Down, and a Disconnected label under a stopped Private Service Edge not yet processed as Down. Details include Up Time, how long the App Connector has been enrolled and running, and Active Apps. [zpa.troubleshooting.dashboards:health-components] The Health Status filters are not displayed when more than 2,000 applications or more than 2,000 App Connectors are listed. [zpa.troubleshooting.dashboards:health-2000] An application's graphical view shows the servers hosting it and the App Connectors providing access to them, to pinpoint a down or unhealthy application, and Last Updated is the last time the App Connector reported the application's health. [zpa.troubleshooting.dashboards:health-graph] The probe cadence behind these states is open [gap:zpa.troubleshooting.dashboards:probe-cadence].

**Extranet and Source IP Anchoring.** The Extranet dashboard shows data over 30 Minutes to 14 Days or a Custom Range, applied to all its widgets, and by default the last hour. [zpa.troubleshooting.dashboards:extranet-range] The Extranet dashboard uses information gathered from Internet & SaaS to show extranet resources and locations with the lowest health score. The score represents the health of an IPSec connection between the extranet resource's data center and the Zscaler cloud, is the minimum over all tunnels, and each of the VPN and IPSec scores runs from 0 (unhealthy) to 100 (optimal) for a maximum combined 200, with the 5 lowest shown. [zpa.troubleshooting.dashboards:extranet-score] The Source IP Anchoring dashboard shows data over 7 Days to 6 Months or a Custom Range, by default the last 7 days, with the number of users per day or month, total and per-user average bandwidth consumption, and the total unique Source IP Anchoring users. [zpa.troubleshooting.dashboards:sipa] The Extranet page has a copy defect [gap:zpa.troubleshooting.dashboards:extranet-copy].

What to check:
1. Whether an application shown without a state sits on an On Access segment or was never accessed, using both Health dashboard statements.
2. Whether the time range asked about is inside the 14-day dashboard window, with LSS for older data.

Sources disagree (name both sides):
- The Health dashboard page says one application status is shown only for On Access segments, and also that an application on an On Access segment shows no state. [divergence:zpa.troubleshooting.dashboards:health-no-state]
  - zscaler-help: A status is shown only for applications on segments with Health Reporting set to On Access.
  - zscaler-help: If the application was not accessed, or its segment is configured with Health Reporting set to On Access, no state is displayed.
  Impact: An On Access application can be read as showing a status or showing none; the page does not say which holds, or whether the no-state sentence applies only before the first access.
