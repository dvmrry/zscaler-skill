# Segment matching and policy search with and without Multimatch (zpa.policy.multimatch)
Also called: multimatch; app segment multimatch; exact match vs multimatch; carved out wildcard segment; dropped at the client level; matchStyle; EXCLUSIVE INCLUSIVE; policy evaluation under multimatch

The segment a request maps to decides which rules are searched, and Multimatch changes that mapping.

**Without Multimatch.** Without Multimatch a request is mapped to a single application segment and the policy search is then performed; Multimatch allows a request to match multiple application segments. [zpa.policy.multimatch:multimatch-definition] Exact match is the default application match behavior, in which Zscaler Client Connector attempts to match traffic to the more granular of two segments covering the same destination address. [zpa.policy.multimatch:exact-match-default] By default, once a specific FQDN is configured in an application segment, the destination is removed from the wildcard application segment. [zpa.policy.multimatch:carved-out-by-default] Under Exact Match, the default application match behavior, when the more specific segment lacks the requested port, the access is dropped at the client level, traffic is not sent to the Private Access cloud, and the attempt is not visible in the diagnostics. [zpa.policy.multimatch:port-mismatch-dropped]

**With Multimatch.** Application segment Multimatch is in limited availability, and the help points to Zscaler Support to learn more. [zpa.policy.multimatch:limited-availability] After Multimatch is enabled, the wildcard application segment catches the UDP or TCP ports that are not configured in the more specific application segment. [zpa.policy.multimatch:multimatch-catches-undefined-ports] Multiple matches apply from the most specific application to the least specific, and multimatching stops at the first application that does not support Multimatch. [zpa.policy.multimatch:match-order] With Multimatch a request that matches a specific and a broader segment can be allowed by a rule on the broader one when it fails the specific segment's rule, whereas without Multimatch the same request meets only the specific segment's rules and falls to the implicit block. [zpa.policy.multimatch:rules-of-all-matched-segments] Whether a block rule on the specific segment fires first is open [gap:zpa.policy.multimatch:block-rule-with-multimatch].

**API values.** The application segment request field `matchStyle` takes the values EXCLUSIVE and INCLUSIVE. [zpa.policy.multimatch:match-style-values] A domain can only be INCLUSIVE or EXCLUSIVE for the `matchStyle` field, and any application segment can only contain inclusive or exclusive domains. [zpa.policy.multimatch:match-style-domain-constraint] The link to the console setting is open [gap:zpa.policy.multimatch:match-style-vs-multimatch].

Which server group serves a Multimatch segment is in [Several server groups on one application segment](kb:zpa.server-groups.multiple-on-segment). The rule search itself is in [Evaluation order across ZPA policy types](kb:zpa.policy.evaluation-order).

What to check:
1. Check whether the matching segments have Multimatch enabled; without it only the most specific segment is matched.
2. If the request port is not defined on the most specific segment under Exact Match, check whether traffic is dropped at the client, where it is not sent to the Private Access cloud and is not visible in the diagnostics.
3. With Multimatch, list the rules of every matching segment in rule order and take the first one that matches the user.
4. If a block rule on the specific segment is being relied on, check whether it sits above the allow rules of the broader segment.
