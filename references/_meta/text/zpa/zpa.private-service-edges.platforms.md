# Private Service Edge software and deployment steps by platform (zpa.private-service-edges.platforms)
Also called: private service edge software by platform; private service edge deployment guide; pse on aws; pse on azure; pse on gcp; pse on hyper-v; pse on nutanix; pse on vmware; pse docker

The Private Service Edge software page lists STIG OVAs for Nutanix AHV and VMware, AWS, GCP and Microsoft Azure Marketplace STIG images, RHEL 9 VHDX images for Microsoft Azure Local and for Microsoft Hyper-V, Docker Hub for Docker, and RPM packages for RHEL 8-based and RHEL 9-based deployments. [zpa.private-service-edges.platforms:software-by-platform] The About page's STIG list [Security Technical Implementation Guide (STIG) images are available for AWS, GCP, Microsoft Azure and VMware by default.](kb:zpa.private-service-edges.deployment:stig-images) differs from the Linux guide's and the software page's on Nutanix [divergence:zpa.private-service-edges.platforms:stig-images-nutanix], and its platform list [Zscaler distributes Private Service Edge images for enterprise data centers and local private cloud environments such as VMware, and the platforms listed as supported by Private Access are AWS, Docker, GCP, Linux, Microsoft Azure, Microsoft Azure Local, Microsoft Hyper-V and VMware platforms.](kb:zpa.private-service-edges.deployment:supported-platforms) differs from the software page's [divergence:zpa.private-service-edges.platforms:platform-list-nutanix].

**Linux and RPM.** The Linux guide's repository definition uses baseurl https://yum.private.zscaler.com/yum/el9 with gpgcheck=1, and for RHEL 8-based deployments the baseurl must be https://yum.private.zscaler.com/yum/el8. The console asks for confirmation twice and the GPG fingerprint should match a6fe 2422 fce7 e8ac 672e 9e51 644e a315 8765 e1dd. If the Private Service Edge cannot download the RPM package, the guide has the package downloaded on a server, chmod 777 applied to zpa-service-edge.rpm, yum localinstall run, and iptables -I INPUT 1 -j ACCEPT run. [zpa.private-service-edges.platforms:linux-rpm] The Linux guide names two repositories for RHEL 9 [divergence:zpa.private-service-edges.platforms:yum-repository].

**Amazon Web Services.** The AWS guide says Private Service Edges must be deployed in the customer's VPCs, with a pair deployed for each VPC for resilience and scalability, and that they should be deployed across Availability Zones. Their security groups should accept incoming connections from Client Connector and App Connectors and permit inbound and outbound access on port 443, and allow inbound SSH. The AMI is currently available under Community AMIs for us-west-2 and us-east-1, with other regions requested through Zscaler Support, and if IMDSv2 is enabled the Private Service Edges will fetch the AWS VM ID. [zpa.private-service-edges.platforms:aws] In the AWS guide's auto scaling steps the AMI is filtered for zpa-service-edge-2025.12, the security group's Inbound tab allows access to the public IP address on port 443, the group size is 2 and the target value is 50. The guide says each Private Service Edge is capable of passing 400 to 500 Mbps traffic, and that OAuth 2.0 enrollment is unavailable with Auto Scaling. [zpa.private-service-edges.platforms:aws-auto-scaling]

**Microsoft Azure.** The Azure guide has the reader search for Red Hat and select a RHEL 9.x that meets the requirements in the prerequisites, create a rule allowing inbound SSH connections for port 22 and HTTPS connections for port 443 and one allowing outbound connections for port 443, and disable inbound access on port 22 for the security group associated with the Private Service Edge in Azure. [zpa.private-service-edges.platforms:azure]

**Google Cloud Platform.** The GCP guide says for each VPC there must be at least a pair of Private Service Edges, and that they should be deployed across regions and zones. Zscaler recommends the n2-standard-4 or n2-highcpu-4 machine types, and n2-highcpu-4 is given as 4 vCPU, 2 core and 4 GB memory. Its autoscaling steps select a minimum and maximum of 2 and 4 instances, enter 80 in the Target CPU utilization field and 300 in the Initialization period field. [zpa.private-service-edges.platforms:gcp] The GCP firewall step names the Private Cloud Controller [gap:zpa.private-service-edges.platforms:gcp-firewall-wording].

**Microsoft Hyper-V.** The Hyper-V guide uses the VHDX https://dist.private.zscaler.com/vms/Azure/2026.09/zpa-service-edge-el9-2026.09.vhdx, selects Generation 1, enters 4096 for startup memory and enters 2 for the number of virtual processors. [zpa.private-service-edges.platforms:hyper-v]

**Nutanix AHV.** The Nutanix AHV guide uses the image URL https://dist.private.zscaler.com/vms/VMware/2026.07/zpa-service-edge-el9-2026.07.ova, has the VMDK file extracted from the OVA, selects DISK as the Image Type, requires a minimum of 4 for Number Of Cores Per vCPU, and runs systemctl daemon-reload and systemctl start zpa-service-edge. [zpa.private-service-edges.platforms:nutanix]

**VMware.** The VMware guide requires VMware vCenter version ESXi 7.0 Update 2 or later and says RHEL 9 deployments are only supported on ESXi 7.0 Update 2 or later. Its vCenter steps use the OVA https://dist.private.zscaler.com/vms/VMware/2026.07/zpa-service-edge-el9-2026.07.ova. [zpa.private-service-edges.platforms:vmware]

**Docker.** The Private Service Edge Docker image is available on Docker Hub for both the AMD64 and ARM64 platforms and requires an environment variable named ZPA_PROVISION_KEY. A Publish IP must be configured in the Admin UI, a public IP address that receives requests for port 443 from clients and App Connectors, and Docker restarted afterwards with docker restart <container_name>. A minimum of 4 cores and 8 GB RAM is required for x86-64 systems, 2 cores and 4 GB RAM for ARM64 systems, and only one container per host is allowed. [zpa.private-service-edges.platforms:docker] The procedures' memory and processor values sit below the recommended sizing table [For up to 500 Mbps per Private Service Edge: up to 2,000 active users need 8 GB RAM (10 GB with ZDX) and 4 vCPUs; up to 4,000 need 16 GB (18 GB) and 8 vCPUs; up to 10,000 need 32 GB (34 GB) and 16 vCPUs; disk is 64 GB thin provisioned and at least 1 NIC.](kb:zpa.private-service-edges.deployment:sizing-table) [divergence:zpa.private-service-edges.platforms:minimum-resources]. The software page lists no Kubernetes or OpenShift image for Private Service Edges [gap:zpa.private-service-edges.platforms:pse-containers].

Capacity, the host OS and limits are in [Private Service Edge platforms, host OS maintenance, capacity and limits](kb:zpa.private-service-edges.deployment) and enrollment in [Enrolling a Private Service Edge](kb:zpa.private-service-edges.enrollment). The Private Cloud Controller's equivalent is [Private Cloud Controller sizing, network requirements, platforms and enrollment](kb:zpa.private-service-edges.private-cloud-controller.deployment).

What to check:
1. Whether a Nutanix question rests on the About page's lists or on the software page and the Nutanix guide, which differ.
2. Which repository the host points at for RHEL 9, since the Linux guide names two.
3. Whether a VM sized from a platform procedure (Hyper-V, GCP, Docker on ARM64) is below the sizing table's recommended smallest row.
4. Whether an AWS instance's AMI is available in its region: the guide names two regions and others are by request.

  Impact: The Hyper-V, GCP and Docker ARM64 values are below the sizing table's recommended smallest row; only the Docker ARM64 line is stated as a minimum, and the pages do not say how the procedures relate to the recommendation.
