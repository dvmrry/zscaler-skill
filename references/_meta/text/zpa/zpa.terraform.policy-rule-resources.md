# ZPA Terraform policy rule resources: v1 and v2 conditions, operand types and provider changes (zpa.terraform.policy-rule-resources)
Also called: duplicate.operand.found; operator.or.not.supported.policy.rule; zpa_policy_access_rule_v2 operator; EDGE_CONNECTOR_GROUP BRANCH_CONNECTOR_GROUP terraform; device_posture_failure_notification_enabled; zpa_policy_capabilities_rule join_session
Former IDs: zpa-10

The provider exposes a v1 and a v2 resource for most policy rule types; the pages below record what the docs and code say about them, and each resource's arguments, operand object types and other enums are generated from the provider code (`node scripts/kb.mjs surface <resource name>`). Field-level write behavior is in [What the ZPA Terraform provider sends and loses when writing policy rules](kb:zpa.terraform.policy-rule-writes) and ordering in [How the ZPA Terraform provider applies policy rule order (BulkReorder)](kb:zpa.terraform.rule-order).

**v1 and v2.** The access, timeout, forwarding, inspection and isolation v2 policy rule docs, and the browser protection rule doc, describe the resource as recommended, not required, when a rule needs more than 1000 resource criteria. [zpa.terraform.policy-rule-resources:v2-recommended-over-1000] The access rule docs say policy_set_id is optional since provider v3.2.0, is determined from the policy type, and is kept for backwards compatibility. In the schema it is optional and computed only on the v1 resources (access, forwarding, timeout, redirection, inspection and isolation rules); on every v2 rule and on the capabilities, credential, portal and browser protection rules it is computed only and cannot be set. [zpa.terraform.policy-rule-resources:policy-set-id-optional-3-2] The removal schedule for v1 is open [gap:zpa.terraform.policy-rule-resources:v1-removal-schedule].

**Condition structure in v2.** On a v2 rule the top-level operator joins the separate conditions blocks and supports only AND; OR is rejected by the API with operator.or.not.supported.policy.rule, and omitting the argument lets ZPA set AND. [zpa.terraform.policy-rule-resources:v2-rule-level-operator-and-only] Each conditions block has its own AND or OR operator for the operands inside it, and multiple entry_values or values inside one operand are always ORed regardless of the block operator. [zpa.terraform.policy-rule-resources:v2-block-operator-and-operand-or] The API rejects the same object_type appearing in more than one operands block inside a single conditions block with duplicate.operand.found; aggregate the values under one operand, or use separate conditions blocks for independent groups of the same type. [zpa.terraform.policy-rule-resources:v2-duplicate-object-type] The console cannot always render a mixed OR block: [How SAML attributes act as policy criteria](kb:zpa.saml-attributes.policy-criteria).

**Operands.** The v1 access rule doc says microtenant_id is not supported inside operands when object_type is SAML, SCIM, SCIM_GROUP, IDP, POSTURE or TRUSTED_NETWORK, and follows it directly with the sentence that ZPA automatically assumes the posture profile ID that belongs to the parent tenant. [zpa.terraform.policy-rule-resources:operand-microtenant-unsupported-types] The primary operand validator resolves EDGE_CONNECTOR_GROUP IDs against the cloud connector group getter. Up to v4.4.15 it had no BRANCH_CONNECTOR_GROUP case; at v4.4.16 it has one that requires lhs `"id"` and looks the rhs up nowhere. BRANCH_CONNECTOR_GROUP is a distinct object type, checked only for a nonempty value in the resource-level validator and mapped in the v1-to-v2 operand aggregation. [zpa.terraform.policy-rule-resources:edge-vs-branch-connector-group-validators] The rule-type docs list these operand object types: portal access rules PRIVILEGE_PORTAL, SCIM_GROUP, SCIM, SAML and COUNTRY_CODE; browser protection rules APP, APP_GROUP, USER_PORTAL, CLIENT_TYPE, SCIM_GROUP, SCIM and SAML; redirection rules CLIENT_TYPE, IDP, SAML, SCIM, SCIM_GROUP and COUNTRY_CODE; and the v2 isolation rule APP, APP_GROUP, CLIENT_TYPE, EDGE_CONNECTOR_GROUP, IDP, PLATFORM, SCIM_GROUP, SCIM, SAML, CHROME_ENTERPRISE and CHROME_POSTURE_PROFILE (eleven types at v4.4.16; up to v4.4.15 its doc listed MACHINE_GRP, POSTURE and TRUSTED_NETWORK instead of IDP). [zpa.terraform.policy-rule-resources:rule-type-object-types]

**Rule types.** The v1 timeout rule takes reauth_timeout and reauth_idle_timeout in seconds, where -1 means Never for reauth_timeout and Default for the idle timeout, and the v2 rule takes strings with a unit such as Days, with Never allowed and a minimum interval of 10 minutes. [zpa.terraform.policy-rule-resources:timeout-v1-seconds-v2-strings] A policy inspection rule needs zpn_inspection_profile_id when its action is INSPECT; inspection rule actions are INSPECT or BYPASS_INSPECT, and isolation rule actions are ISOLATE or BYPASS_ISOLATE. [zpa.terraform.policy-rule-resources:inspection-profile-required-for-inspect] The redirection rule doc lists exactly five CLIENT_TYPE values: zpn_client_type_machine_tunnel, zpn_client_type_edge_connector, zpn_client_type_zapp, zpn_client_type_zapp_partner and zpn_client_type_branch_connector. [zpa.terraform.policy-rule-resources:redirection-client-types] The redirection rule resource's conditions schema accepts the operand object types CLIENT_TYPE, IDP, SAML, SCIM, SCIM_GROUP and COUNTRY_CODE. Up to v4.4.14 it accepted only CLIENT_TYPE; v4.4.15 added IDP, SAML, SCIM, SCIM_GROUP and COUNTRY_CODE. [zpa.terraform.policy-rule-resources:redirection-object-types-4-4-15] A credential rule needs a first conditions block with object_type CONSOLE referencing PRA console IDs; the other documented conditions are SAML, SCIM_GROUP and SCIM. [zpa.terraform.policy-rule-resources:credential-rule-console-first] The capabilities rule documents conditions for APP, APP_GROUP, SAML, SCIM and SCIM_GROUP only, with a separate conditions block per object type. [zpa.terraform.policy-rule-resources:capabilities-conditions-limited]

**Provider changes by version.** Provider v4.4.9 added the optional boolean device_posture_failure_notification_enabled to zpa_policy_access_rule and zpa_policy_access_rule_v2; the shared schema declares it and the v1 resource reads and writes it. [zpa.terraform.policy-rule-resources:device-posture-notification-4-4-9] Provider issue #674 reported that before v4.4.9 a Terraform update of an access rule sent a full object without `devicePostureFailureNotificationEnabled`, so a rule with it enabled in the Admin Portal was silently reverted to disabled by any unrelated update. It was closed as completed on 2026-07-24 with a reply from a member of the repository's organization, signed Zscaler DevRel, to upgrade to v4.4.9, adding that the feature is not available to all customers and is enabled on a tenant only on explicit request. [zpa.terraform.policy-rule-resources:device-posture-notification-request-674] The capabilities rule's privileged_capabilities block has join_session and control_session booleans (added in v4.4.8); when true each appends JOIN_SESSION or CONTROL_SESSION to the capability list sent. [zpa.terraform.policy-rule-resources:capabilities-join-control-session] The changelog names the wrong block [divergence:zpa.terraform.policy-rule-resources:capabilities-block-name]. Provider v4.4.7 added UPLOAD_INSPECTED_SANDBOX and UPLOAD_INSPECTED_SCAN to the portal access rule; its privileged_portal_capabilities block carries access_uninspected_file_sandbox, upload_inspected_sandbox and upload_inspected_scan booleans. [zpa.terraform.policy-rule-resources:portal-rule-upload-capabilities-4-4-7]

**Ordering resource and doc layout.** The reorder resource doc lists policy_type values that name some policies two ways (ACCESS_POLICY or GLOBAL_POLICY, TIMEOUT_POLICY or REAUTH_POLICY, BYPASS_POLICY or CLIENT_FORWARDING_POLICY) plus INSPECTION_POLICY, ISOLATION_POLICY, CREDENTIAL_POLICY, CAPABILITIES_POLICY and CLIENTLESS_SESSION_PROTECTION_POLICY; the resource's validator accepts all of these and also REDIRECTION_POLICY, which the doc omits. The doc says a Zscaler Deception access rule cannot be reordered and that a regular rule's order must be greater than a Deception rule's. [zpa.terraform.policy-rule-resources:reorder-policy-types-deception] The access rule variant doc pages (application segment, browser access, posture profile, risk factor, SAML, SCIM attribute, SCIM group, trusted networks) are usage examples that configure the same zpa_policy_access_rule resource; the provider registers no resources of those names. [zpa.terraform.policy-rule-resources:access-rule-variant-docs-are-examples]

What to check:
1. Whether the rule is v1 or v2, and whether a v2 rule keeps one object_type per conditions block.
2. Whether any operand uses SAML, SCIM, SCIM_GROUP, IDP, POSTURE or TRUSTED_NETWORK with microtenant_id set.
3. The provider version, which decides whether the device posture notification, session and portal upload capabilities exist.

Sources disagree (name both sides):
- The v4.4.8 changelog names the wrong block for the new session capabilities. [divergence:zpa.terraform.policy-rule-resources:capabilities-block-name]
  - tf-zpa: The changelog says the options were added to privileged_portal_capabilities on zpa_policy_capabilities_rule.
  - tf-zpa: The capabilities rule schema declares the block as privileged_capabilities; privileged_portal_capabilities belongs to the portal access rule.
  Impact: Configuration for the new session options goes in privileged_capabilities; following the changelog wording would put it in a block the capabilities rule does not have.
