# App Connector provisioning keys (zpa.app-connectors.provisioning-keys)
Also called: provisioning key; app connector provisioning key; maximum reuse of provisioning key; provisioning key utilization count; provisioning key exhausted; connector will not enroll key; view or export provisioning key after creation; http status 401 enroll

A provisioning key is one of the two ways to enroll a connector; this subject covers what the key is and how it is consumed.

**What a key is.** A provisioning key is a text string that enrolls an App Connector; it works as the connector's credential, letting the Private Access cloud verify the connector and complete deployment. [zpa.app-connectors.provisioning-keys:key-enrolls-connector] Each key is associated with a specific App Connector group, so the key tells the Private Access cloud which group a connector is deployed into. [zpa.app-connectors.provisioning-keys:key-names-group] A provisioning key lets the admin select the signing certificate used to enroll App Connector certificates. [zpa.app-connectors.provisioning-keys:key-selects-signing-cert] The help's example key is pipe-separated: a leading number, the API host api.private.zscaler.com, then a long base64 payload. The enrollment error output shows the same host in its nonce. [zpa.app-connectors.provisioning-keys:key-format-example]

**Handling.** Provisioning keys should be treated as secrets because they can create a resource for a tenant, and must not be transmitted or stored in clear text. [zpa.app-connectors.provisioning-keys:key-is-secret] If View or Export Provisioning Key After Creation was disabled, the key column is blank and the copy and download icons are hidden. Unless a backup is in an external credential vault, a new key must be generated, and it can be attached to the same App Connector. [zpa.app-connectors.provisioning-keys:key-hidden-after-creation] The pages differ on whether such a key still appears in the table [divergence:zpa.app-connectors.provisioning-keys:hidden-key-in-table]. View or Export Provisioning Key After Creation is enabled by default; if enabled it can be disabled at a later time, but if disabled it cannot be enabled again. Disabling it hides the provisioning key from the Provisioning Key column of the table and disables copying or downloading the key after creation. [zpa.app-connectors.provisioning-keys:view-export-one-way] A provisioning key configured with Zscaler Deception, or managed by Zscaler, has its edit and delete options unavailable. [zpa.app-connectors.provisioning-keys:deception-managed-read-only]

**Editing and naming.** On the Edit App Connector Provisioning Key page only these fields can be modified: Name, Maximum Reuse of Provisioning Key, App Connector Group, Signing Certificate and View or Export Provisioning Key After Creation. [zpa.app-connectors.provisioning-keys:editable-fields] The provisioning key name cannot contain special characters, with the exception of periods, hyphens and underscores. [zpa.app-connectors.provisioning-keys:name-rules] The signing certificate (the enrollment (CA) certificate) of a key signs the certificates of all App Connectors deployed with the key. If App Connectors were deployed with a signing certificate that has expired and a new certificate is configured, they automatically redeploy using the new certificate. [zpa.app-connectors.provisioning-keys:signing-cert-redeploy]

**Use limits.** A key can be limited to a number of uses when it is generated (Maximum Reuse of Provisioning Key), and Private Access tracks the count and shows it as the Provisioning Key Utilization Count. [zpa.app-connectors.provisioning-keys:max-reuse] Zscaler recommends setting Maximum Reuse of Provisioning Key to the number of App Connectors planned for immediate deployment, to reduce the possibility of compromise. [zpa.app-connectors.provisioning-keys:max-reuse-recommendation] For an App Connector provisioned in an AWS IMDSv2 required environment with version 24.566.1 or earlier, a new App Connector is automatically created during re-enrollment due to a hardware fingerprint change, so the provisioning key value should be increased to account for the additional key's creation. [zpa.app-connectors.provisioning-keys:imdsv2-headroom] When a key has been used its maximum number of times it cannot deploy more App Connectors, but its maximum can always be edited. The Copy icon is disabled with a Warning icon at that point. [zpa.app-connectors.provisioning-keys:exhausted-key-blocks-deploy] Several provisioning keys can be associated with one App Connector group. [zpa.app-connectors.provisioning-keys:multiple-keys-per-group] Whether moving a connector between groups needs a new key is not stated [gap:zpa.app-connectors.provisioning-keys:cross-group-move].

**Adding to an existing group.** To add an App Connector to an existing group with a provisioning key, verify in the Provisioning Key Utilization column that the key has enough available reuses (if not, edit the key's maximum reuse value), then copy the key and use it when deploying the App Connector. [zpa.app-connectors.provisioning-keys:add-to-existing-group] Cloud Connector and Branch Connector groups are in [Cloud Connectors, Cloud Connector groups and Branch Connector groups under Private Access > Private Infrastructure](kb:zpa.private-infrastructure.cloud-branch-connectors).

**When enrollment fails on the key.** The MCP server's connector troubleshooting skill calls provisioning key issues the leading cause of enrollment failure and lists three: max_usage reached, a key copied incorrectly, and a key associated with the wrong connector group. [zpa.app-connectors.provisioning-keys:mcp-skill-key-issues-first] The same skill tests exhaustion by comparing the key's max_usage with its current enrollment count: if equal, no new enrollments can use the key. A ZMS skill in the same repository writes the test as usageCount >= maxUsage. [zpa.app-connectors.provisioning-keys:mcp-skill-exhaustion-test] A key that was copied incorrectly shows up in the App Connector console as an enrollment attempt ending in a 401 login failure and Certificate enrollment failed. [zpa.app-connectors.provisioning-keys:incorrect-copy-error] What an exhausted key looks like on the connector, and whether copied whitespace breaks a key, are not sourced [gap:zpa.app-connectors.provisioning-keys:exhausted-key-symptom] [gap:zpa.app-connectors.provisioning-keys:trailing-whitespace].

How the SDKs and the MCP server model keys is in [Provisioning key fields and tool behavior across SDKs, provider and MCP](kb:zpa.app-connectors.provisioning-key-tooling); association types and provider lookups are in [ZPA Go SDK service functions that return partial results, send wrong keys, or reject valid input](kb:zpa.sdk-go.service-defects); the `enabled = false` write is in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes). The wider enrollment sequence is in [App Connector enrollment, certificates and re-enrollment](kb:zpa.app-connectors.enrollment).

What to check:
1. The key's maximum and utilization count, before blaming the connector for a failed enrollment.
2. Whether the connector console shows the 401 enrollment failure that the help attributes to an incorrectly copied key.
3. Whether the key column is blank because the View or Export option was disabled, which makes the key unrecoverable.
4. Whether the key is Deception-configured or Zscaler-managed before planning to edit or delete it.
