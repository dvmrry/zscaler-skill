# When a Private Service Edge is warranted (zpa.private-service-edges.when-to-deploy)
Also called: should we deploy a zpa pse; why deploy a private service edge; pse use cases; zpa data residency pse; zpa business continuity pse; air gapped zpa

A Private Service Edge question starts with which documented benefit applies.

**Documented benefits.** A Private Service Edge lets an organization implement Zero Trust Network Access (ZTNA) for on-premises users. [zpa.private-service-edges.when-to-deploy:onprem-ztna] A Private Service Edge gives access to applications when Public Service Edges in data centers are not conveniently located between users and the applications they need to reach. [zpa.private-service-edges.when-to-deploy:poor-public-placement] A Private Service Edge helps ensure business continuity and continued access to critical applications during disaster events. [zpa.private-service-edges.when-to-deploy:disaster-continuity] A Private Service Edge keeps application data traffic local to help meet compliance and regulatory requirements. [zpa.private-service-edges.when-to-deploy:local-application-traffic]

**Limits on those benefits.** Residency of session metadata is not established [gap:zpa.private-service-edges.when-to-deploy:session-metadata-residency]. A Private Service Edge still needs outbound reach to a Public Service Edge ([A Private Service Edge deployed behind a firewall needs the firewall to allow outbound connections to the Public Service Edge IP addresses and inbound connections from App Connectors and Zscaler Client Connectors.](kb:zpa.private-service-edges.data-path:firewall-requirements)), though outbound may be filtered if all Public Service Edge data centers stay reachable ([A Private Service Edge can be deployed where outbound internet traffic is restricted, provided it can reach all Zscaler data centers containing Public Service Edges; a partial firewall configuration causes end-user connectivity problems.](kb:zpa.private-service-edges.data-path:restricted-outbound)), and client-side isolation is unverified [gap:zpa.private-service-edges.when-to-deploy:air-gapped-networks]. Interconnect-only routing is unverified [gap:zpa.private-service-edges.when-to-deploy:private-interconnect-routing], and so is serving through degraded connectivity [gap:zpa.private-service-edges.when-to-deploy:survives-degraded-pop].

What a Private Service Edge is: [What a ZPA Private Service Edge is](kb:zpa.private-service-edges.what-it-is). Disaster recovery mode: [Disaster recovery mode and Private Service Edge groups](kb:zpa.private-service-edges.disaster-recovery).

What to check:
1. Which of the four documented benefits the request is actually about, since each leads to different settings.
2. Whether the request assumes the Private Service Edge removes the need to reach Zscaler: it must still connect outbound to a Public Service Edge.
3. Whether a residency requirement covers only application data traffic or also session brokering and metadata.

Not known (open gaps):
- Whether clients and App Connectors can reach only the Private Service Edge [gap:zpa.private-service-edges.when-to-deploy:air-gapped-networks]: settled by lab-test or support-ticket. Blocks: advising a restricted-network site
- Whether a Private Service Edge keeps ZPA session metadata in-country [gap:zpa.private-service-edges.when-to-deploy:session-metadata-residency]: settled by support-ticket or source-read. Blocks: regulatory sign-off on control-plane location
- Private-interconnect-only routing as a reason to deploy [gap:zpa.private-service-edges.when-to-deploy:private-interconnect-routing]: settled by source-read. Blocks: design advice for interconnect-only sites
- Whether a local Private Service Edge keeps serving sessions when PoP connectivity is degraded [gap:zpa.private-service-edges.when-to-deploy:survives-degraded-pop]: settled by lab-test or source-read. Blocks: promising availability during partial outages
