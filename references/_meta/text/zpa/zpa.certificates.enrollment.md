# Enrollment (CA) certificates in Private Access (zpa.certificates.enrollment)
Also called: enrollment certificate; enrollment ca certificate; signing certificate; preloaded enrollment certificate; client certificate type; appprotection ca; isolation client certificate; store in hsm

**What they are.** App Connectors, Private Service Edges, Private Cloud Controllers, Network Connectors and Zscaler Client Connector are issued certificates that are sent by an enrollment certificate, which must be capable of acting as a certificate authority for processing certificate signing requests (CSRs). Enrollment and other certificates uploaded to Private Access must be encoded in PEM format. [zpa.certificates.enrollment:what-it-is] A CA certificate is required for enrolling Zscaler Client Connector, enrolling AppProtection-enabled application segments, and when configuring an App Connector, a Private Service Edge, Network Connectors and a Private Cloud Controller for enrollment. Enrollment certificates differ from web server certificates. [zpa.certificates.enrollment:required-for]

**Where they come from.** An enrollment certificate is either Zscaler-issued, as a Zscaler-issued root certificate or an intermediate certificate authority whose root (parent) is one of the preloaded Private Access certificates or another Zscaler-issued certificate, or created by creating CSRs that are signed with the organization's own signing certificate, which can be a root or intermediate. The page says to make sure the same root certificate is used by the enrollment certificates for enrolling software components, and recommends the preloaded enrollment certificates when evaluating Private Access. [zpa.certificates.enrollment:two-workflows] For the organization's own signed certificates, Zscaler must verify the chain of trust, so every certificate must be present from the signed certificate up to and including the root. The chain needs uploading only once, either prepended to each signed certificate (Method 1) or uploaded separately with the signed certificates (Method 2). [zpa.certificates.enrollment:chain-of-trust]

**The Enrollment Certificates page.** The Enrollment Certificates page shows Expiration Date, Common Name, Stored in HSM (whether both the public and private keys are stored in a hardware security module) and Parent Certificate. The Name column carries a Client Connector icon or a Zero Trust Browser icon when the certificate is a signing certificate for those clients, and a red Warning icon if the certificate has expired, a yellow Caution icon with less than 7 days before expiration and an orange Info icon with less than 30 days. Enrollment certificates managed by Zscaler are read only. [zpa.certificates.enrollment:page-fields]

**Preloaded certificates.** The preloaded Zscaler-issued signing certificates are Root, the parent certificate for the Client and Connector signing certificates, Client, which Private Access automatically uses to sign certificates issued to Zscaler Client Connector unless another Zscaler-issued certificate is configured, and Connector. The signing certificates are 2048-bit RSA certificates which support TLS 1.2 connections with cipher suite ECDHE-RSA-AES128-GCM-SHA256. The certificate used to enroll a Private Service Edge must have the same root certificate used by the enrollment certificate for enrolling App Connectors and Zscaler Client Connector. [zpa.certificates.enrollment:preloaded] The page's own wording on what the Connector certificate enrolls is not consistent [divergence:zpa.certificates.enrollment:preloaded-connector-scope].

**Zscaler-issued certificates.** Generating a Zscaler-issued enrollment certificate takes a Type of Root CA, or Intermediate CA with a Parent Certificate that can be a preloaded or another Zscaler-issued certificate, a Client Certificate Type and Store in HSM (True stores both the public and private keys in a hardware security module). The Client Certificate Type is None to enroll App Connectors, Private Service Edges or Private Cloud Controllers, Client Connector to enroll Zscaler Client Connector, Isolation Client to enroll Zero Trust Browser clients, or AppProtection CA to enroll AppProtection-enabled application segments, where a new AppProtection CA certificate replaces an existing one. [zpa.certificates.enrollment:generate] The Generating Zscaler-Issued Enrollment Certificates page recommends creating a certificate for Zscaler Client Connector, another for App Connectors, a third for Private Service Edges, a fourth for Network Connectors and a fifth for Private Cloud Controllers, with an additional certificate if AppProtection is enabled. [zpa.certificates.enrollment:per-component-recommendation] How many certificates the pages recommend differs [divergence:zpa.certificates.enrollment:recommended-count]. The validity of Zscaler-generated certificates is open [gap:zpa.certificates.enrollment:generated-validity].

**Certificates signed by the organization's own CA.** A CSR for an enrollment certificate cannot use a canonical name (CNAME) that duplicates another CSR's CNAME, and the CNAME stays the same if the CSR's name is updated; the page's example is that a CSR named test has the CNAME {domain}/test. Store in HSM True stores both keys in a hardware security module. The CSR is signed using the organization's signing CA, which can be a root or intermediate CA, and the pending CSR then appears in the Enrollment Certificates table, where the signed certificate and the certificate chain must be uploaded. [zpa.certificates.enrollment:csr] The page's CNAME example reads against its own rule [gap:zpa.certificates.enrollment:cname-example]. Up to 1,000 enrollment (CA) certificates can be uploaded, and the ranges page lists 1,000 certificates. The uploaded signed certificate must include the private key. The intermediate certificates and the root are downloaded as Base64-encoded ASCII PEM files, with the order within the file starting from the intermediate certificate, and the root file must be uploaded before the PEM file or the PEM file will not upload. [zpa.certificates.enrollment:upload] Whose private key the upload carries is open [gap:zpa.certificates.enrollment:upload-private-key]. After uploading the signed CA certificate, the Edit icon opens it again to make sure Client Certificate Type is set correctly: Client Connector for Zscaler Client Connector, Isolation Client for Zero Trust Browser clients and None for App Connectors and Private Service Edges. [zpa.certificates.enrollment:client-type-after-upload] The Client Certificate Type for a Network Connector certificate is open [gap:zpa.certificates.enrollment:network-connector-type].

**Editing.** The edit window shows more details about the certificate, including its expiration date and whether it is being used as the signing certificate for App Connectors, AppProtection, Zscaler Client Connector or Network Connectors. To replace an expired certificate a new one must be uploaded, and saving a certificate with the Auto AppProtection CA for Client Certificate Type replaces an existing AppProtection CA certificate. [zpa.certificates.enrollment:edit-and-replace]

Web server certificates for Browser Access, which differ from these, are in [Certificates for Browser Access applications: wildcards, managed and custom](kb:zpa.browser-access.certificates); the wire keys are in [Enrollment and Browser Access certificate API: wire keys, paths and client quirks](kb:zpa.api.certificates-wire); the preloaded names the Go test expects are open [gap:zpa.certificates.enrollment:preloaded-names]; the connector side is in [App Connector enrollment, certificates and re-enrollment](kb:zpa.app-connectors.enrollment); the hub is [ZPA certificates: enrollment (CA) certificates and web server certificates](kb:zpa.certificates).

What to check:
1. Which Client Certificate Type the certificate carries (None, Client Connector, Isolation Client or AppProtection CA) for the component it is meant to enroll.
2. Whether the chain of trust up to and including the root was uploaded, and the root before the chain file.
3. Whether all software components and Client Connector enroll from certificates with the same root, and whether the preloaded Connector certificate is meant for App Connectors.
4. How many separate enrollment certificates to create, which the pages state differently.
5. Whether an expired certificate was replaced by uploading a new one, and the expiry icons on the Name column.

Sources disagree (name both sides):
- The preloaded certificates page says its signing certificates can enroll Zscaler Client Connector and App Connectors, but its Connector entry describes that certificate as for certificates issued to Zscaler Client Connectors. [divergence:zpa.certificates.enrollment:preloaded-connector-scope]
  - zscaler-help: The preloaded signing certificates can be used to enroll Zscaler Client Connector and App Connectors.
  - zscaler-help: The Connector certificate can be used for enrollment certificates issued to Zscaler Client Connectors.
  Impact: Whether the preloaded Connector certificate enrolls App Connectors is not settled by the page; the existing claims zpa.app-connectors.connector-groups:ansible-resolves-cert and zpa.api.certificates-wire:system-provisioned-names side with App Connectors.
- The Generating page recommends five separate certificates (plus one for AppProtection), while the CSR page recommends a certificate for Client Connector and another for App Connectors. [divergence:zpa.certificates.enrollment:recommended-count]
  - zscaler-help: Create a certificate for Client Connector and one each for App Connectors, Private Service Edges, Network Connectors and Private Cloud Controllers.
  - zscaler-help: Create a CA certificate for Client Connector and another for App Connectors.
  Impact: The pages do not say whether the CSR page's two-certificate wording is limited to that workflow or whether Private Service Edges, Network Connectors and Private Cloud Controllers need their own certificates there.
