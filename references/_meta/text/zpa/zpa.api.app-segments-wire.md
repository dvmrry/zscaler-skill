# Application segment wire behavior: what each SDK sends, drops and matches across the four segment kinds (zpa.api.app-segments-wire)
Also called: browser access pra inspection segment update; commonAppsDto empty object; deletedInspectApps; deleted_pra_apps; app_types injected; segmentGroupId omitempty; deleteAppByType; application/provision; bulkUpdateMultiMatch; getAppsByType applicationType invalid; connectionSecurity NLA; GetApplicationSummary 400

Core, Browser Access, Inspection and PRA segments share one endpoint, and the SDK models differ in what they send, drop and match on update. Field listings are in the generated surface layer; this subject holds only the behavior. The Go core, Browser Access, Inspection and PRA application segment packages all use the same `/application` endpoint under the customer path, and the API's create body takes the sub-application lists (`inspectionApps`, `praApps`, `clientlessApps`) and `commonAppsDto` in one schema whose `appsConfig` entries carry an `appTypes` list of BROWSER_ACCESS, SIPA, INSPECT or SECURE_REMOTE_ACCESS. [zpa.api.app-segments-wire:variants-share-endpoint]

## Model tags that change the wire

The Go Inspection and PRA segment models read their sub-applications from `inspectionApps` and `praApps` respectively, and write them through `commonAppsDto.appsConfig`; the API create body defines `appsConfig` entries as CommonAppConfigDto. [zpa.api.app-segments-wire:subapp-read-write-fields] Both the Go Inspection and PRA segment models hold `CommonAppsDto` by value, the Inspection tag with `omitempty` and the PRA tag without it, so every create or update from either carries a `commonAppsDto` object, `{}` when no sub-applications are set. The Inspection tag does not make the object optional. [zpa.api.app-segments-wire:common-apps-dto-always-emitted]

The Go PRA and core segment models send `segmentGroupId` without `omitempty` (an empty string goes on the wire), while the Inspection and Browser Access models tag it `omitempty`. [zpa.api.app-segments-wire:segment-group-id-tags] The Go Inspection model tags `adpEnabled` and `autoAppProtectEnabled` with `omitempty`, so an explicit false is not sent, while the core application segment model sends both without `omitempty`. [zpa.api.app-segments-wire:inspection-protection-flags-tags] The Go PRA, Browser Access and core segment models carry `zpnErId` as a pointer without `omitempty`, so an unset value is sent as JSON null, and the Inspection model has no `zpnErId` field. [zpa.api.app-segments-wire:zpn-er-id-by-variant] In the Go sub-application config, the Inspection entry sends `inspectAppId` and `enabled` without `omitempty` and tags `appId` `omitempty`, while the PRA entry sends `appId` and `praAppId` without `omitempty` and tags `enabled` `omitempty`, so an explicit false `enabled` on a PRA sub-application is not sent. [zpa.api.app-segments-wire:subapp-config-tags]

The `bypassOnReauth` tag differences are in [What the Python and Go SDKs send for application segments](kb:zpa.app-segments.sdk-behavior), the always-serialized parent flags in [What the ZPA Terraform provider sends, keeps and cleans up for application segments and their associations](kb:zpa.terraform.app-segment-lifecycle), and the Go rule that a value struct tagged `omitempty` is still sent in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes).

The Go core application segment model tags `shareToMicrotenants` without `omitempty`, while the neighbouring `clientlessApps` and `sharedMicrotenantDetails` tags carry it. [zpa.api.app-segments-wire:share-to-microtenants-tag] A create or update from that struct therefore always carries the shareToMicrotenants member: null for a nil slice, [] for an empty one. [zpa.api.app-segments-wire:share-to-microtenants-always-sent] Whether the API treats that as removal is open [gap:zpa.api.app-segments-wire:put-share-removal]. Move and share bodies are in [Sharing and moving between Microtenants](kb:zpa.microtenants.share-and-move). The API documents No Content (204) as the success response of both the application segment move and share calls. [zpa.api.app-segments-wire:move-share-return-204]

## Updating sub-applications

The Go PRA `Update` computes `DeletedPraApps` from the existing PRA sub-applications whose IDs are not among the remaining `appsConfig` entries, and sends them. Before v3.8.49 the Go Inspection `Update` never set `DeletedInspectApps`, so a caller had to supply it to remove an Inspection sub-application; from v3.8.49 (#464) it computes `DeletedInspectApps` the same way, from the existing inspection apps whose IDs are not among the remaining `appsConfig` entries. [zpa.api.app-segments-wire:go-deleted-subapps] The Python PRA, Inspection and Browser Access v2 segment updates fetch the existing sub-applications by type (SECURE_REMOTE_ACCESS, INSPECT, BROWSER_ACCESS), match each `apps_config` entry to them by domain, set the matched ID (or an empty string when the domain is new), and set `deleted_pra_apps`, `deleted_inspect_apps` or `deleted_ba_apps` to the existing sub-applications whose domain is no longer listed. [zpa.api.app-segments-wire:python-update-matches-by-domain] The Python Inspection update sets `inspect_app_id` to the segment ID and then overwrites it with the matched existing sub-application ID or an empty string; it never assigns `app_id` on the `apps_config` entries, unlike the PRA and Browser Access v2 updates, which set `app_id` to the segment ID. [zpa.api.app-segments-wire:python-inspection-update-ids]

The Python PRA, Inspection, Browser Access and Browser Access v2 segment updates set each of `tcpPortRanges`, `tcpPortRange`, `udpPortRanges` and `udpPortRange` to an empty list when it is not passed, so omitting ports in an update clears them. [zpa.api.app-segments-wire:python-update-clears-ports-all-variants] When an `apps_config` entry has no `app_types`, the Python PRA, Inspection and Browser Access v2 create and update functions set it to SECURE_REMOTE_ACCESS, INSPECT or BROWSER_ACCESS respectively before sending. [zpa.api.app-segments-wire:python-app-types-injection]

## Lookup, delete and other endpoints

The Go `GetByApplicationType` and `DeleteByApplicationType` reject any application type other than BROWSER_ACCESS, INSPECT or SECURE_REMOTE_ACCESS before sending a request, while the Python `get_segments_by_type` only requires a non-empty type and `delete_segments_by_type` does not check it; the API documents `applicationType` as a required string without an enum. [zpa.api.app-segments-wire:application-type-validation] Deleting by application type is `DELETE /application/{id}/deleteAppByType` with the application type as a query parameter; the Go function sends only the type and the Microtenant filter, while Go's application segment, browser access, inspection and PRA deletes pass `ForceDelete: true`, and the Python function sends `applicationType` and an optional `microtenantId`. [zpa.api.app-segments-wire:delete-by-type-request] What the delete removes is open [gap:zpa.api.app-segments-wire:delete-by-type-scope].

The API's `connectionSecurity` on a PRA sub-application takes ANY, NLA, NLA_EXT, TLS, VM_CONNECT or RDP, and the Python docstring lists the same six; the Go PRA sub-application field is a plain string with no value list. [zpa.api.app-segments-wire:connection-security-values] The `icmpAccessType` values are in [Application segment settings that interact: health reporting, connector selection, CNAME, ICMP, encryption and anchoring](kb:zpa.app-segments.settings).

[divergence:zpa.api.app-segments-wire:bulk-multimatch-id-type]

The Go `GetApplicationSummary` carries the source comment 'Need to review as the API is returning 400 error' and reads the application summary path through `common.GetAllPagesGenericWithCustomFilters`, with a filter holding the service's microtenant ID. [zpa.api.app-segments-wire:application-summary-comment] The Python SDK has an `add_segment_provision` that posts to `/application/provision`, a path the OpenAPI document does not define. [zpa.api.app-segments-wire:provision-python-only] The weighted load balancer update that returns a nil object is in [ZPA Go SDK service functions that return partial results, send wrong keys, or reject valid input](kb:zpa.sdk-go.service-defects).

What to check:
1. Whether an update from the Go SDK or Python SDK to a PRA, Inspection or Browser Access segment will drop or clear sub-applications, ports or flags, before blaming the API.
2. Whether the sub-application names or domains in the update match the existing ones, since Go matches by name and Python by domain.
3. Whether a call using an application type fails client-side in Go because the type is outside the three accepted values.
4. Whether the failing request sends `commonAppsDto: {}` or a null `zpnErId` that the variant's model always emits.
