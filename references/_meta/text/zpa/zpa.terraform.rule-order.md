# How the ZPA Terraform provider applies policy rule order (BulkReorder) (zpa.terraform.rule-order)
Also called: zpa_policy_access_rule_reorder; terraform zpa reorder; zpa rules reordered unexpectedly; BulkReorder; zpa policy rule order drift; rule moved below configured rules

The ZPA provider orders policy rules differently from the ZIA provider described in [How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order). The reorder resource computes one complete ordered list of rule IDs and replaces the policy set's order with a single request. The ZPA reorder resource does not write a position per rule. `BulkReorder` reads the policy set and every rule of the policy type, sorts the IDs locally, and sends one PUT to the policy set's `reorder` endpoint whose body is a bare ordered list of rule IDs. The configured numbers never go on the wire. The reorder resource `zpa_policy_access_rule_reorder` imports and calls the version 1 policy-set controller (`policysetcontroller`, not `policysetcontrollerv2`); the version 2 controller's `BulkReorder` is not covered here. [zpa.terraform.rule-order:sends-id-list-only] Unlike the ZIA provider's background worker, the ZPA resource applies the order inside the apply call: a failed PUT comes back as an error from the update, and, only when the PUT succeeds (the update returns the error first otherwise), the update then reads the rules back before returning. On the OneAPI client a non-2xx status reaches the update as the error returned by `NewRequestDo`, not through a status check in `BulkReorder`. [zpa.terraform.rule-order:synchronous-and-reports-failure] `BulkReorder`, in both the policysetcontroller and policysetcontrollerv2 packages, checks the reorder PUT for a non-2xx status after `NewRequestDo` returns, but on the OneAPI client that check never fires: `ExecuteRequest` turns any status of 300 or above into an error, which `BulkReorder` returns with a nil response before the check, and `NewRequestDo` reports every success as `StatusCode` 200. [zpa.terraform.rule-order:bulk-reorder-status-check-unreachable] Destroying the reorder resource only removes it from state. The delete function makes no API call, so the policy keeps whatever order was last applied. [zpa.terraform.rule-order:delete-is-a-noop] The ZIA provider can finish an apply with rules out of their declared order and report success; the ZPA provider instead sends every rule it does not manage below the configured ones as a side effect of a successful call. [zpa.terraform.rule-order:zia-zpa-failure-contrast]

**Sort order of the list.** The local sort compares two rules by their configured numbers only when both are in the provider's map. When exactly one is in the map it sorts first, so every rule the provider does not manage sorts after every rule it does. When neither is, the comparison falls back to the two rules' positions in the slice being sorted. [zpa.terraform.rule-order:comparator-managed-first] After sorting, the one rule whose name is exactly `Default_Rule` is taken out and appended last. No other rule is pinned by name or attribute inside `BulkReorder` (the provider separately pins an unconfigured Deception rule that sits at order 1 to 1 through the map). If several rules carry that name, only the last one's ID is appended and the others are left out of the list. [zpa.terraform.rule-order:default-rule-pinned-last-by-name] The map handed to `BulkReorder` is filled from the configured `rules` blocks, plus a pin of a rule named "Zscaler Deception" at order 1 to 1 when that rule is not itself configured. Up to v4.4.15 the configured numbers were offset by one whenever that rule sat at order 1, configured or not, and from v4.1.13 through v4.4.15 a configured Deception rule was left out of the map; from v4.4.16 the map holds every configured rule, and the offset and pinning the Deception rule to 1 apply only when the Deception rule is at order 1 and not configured. The provider adds no other policy rules to it. [zpa.terraform.rule-order:map-holds-configured-rules] So the list sent is: every configured rule in numeric order (from v4.1.13 through v4.4.15, a configured Deception rule at order 1 goes with the other rules instead), then every other rule of the policy type in its current relative order, then `Default_Rule` (placed last even when it is configured with another number). Rules interleaved with configured rules, and any terminal rule not named exactly `Default_Rule`, end up below all configured rules. [zpa.terraform.rule-order:unmanaged-rules-sent-below-managed] An apply of the reorder resource can therefore move a terminal or safety rule that is not named exactly `Default_Rule` out of last place, and still report success. [zpa.terraform.rule-order:terminal-rule-can-be-displaced] From v4.1.13 through v4.4.15, if the rule named "Zscaler Deception" at order 1 is itself listed in the configuration, it is neither pinned to 1 nor added to the map: the loop skips it, and the comparator then treats it as an unmanaged rule. From v4.4.16 the loop has no skip, so a configured Deception rule is neither pinned nor does it trigger the offset, and goes into the map at its configured number like any other configured rule. [zpa.terraform.rule-order:configured-deception-rule-treated-as-unmanaged]

**Configured numbers.** The provider checks that each order is greater than zero and that no two rules share a number. It does not check that the numbers are contiguous, start at 1, or fit within the number of rules. [zpa.terraform.rule-order:validates-positive-and-unique-numbers] The configured numbers only decide the relative order of the configured rules. Orders 1 and 3 with nothing at 2 produce the same list as orders 1 and 2, and 999 produces the same list as the last position. [zpa.terraform.rule-order:numbers-are-relative-only] Because Read replaces each configured number with the order the API reports (less the Deception offset from v4.4.16, when an unconfigured Deception rule is at order 1), a configuration with gaps (1 and 3) or out-of-range numbers can apply cleanly and then show a difference on every later plan. [zpa.terraform.rule-order:gapped-numbers-drift] Up to v4.4.15, when the "Zscaler Deception" rule sat at order 1, Update sent every configured rule at its configured number plus one, but Read wrote back the API's number unchanged, so a configuration that numbers its rules from 1 could show a difference on every plan. From v4.4.16 Read subtracts the same offset, and the provider's changelog says such a configuration no longer shows a change in every plan. [zpa.terraform.rule-order:deception-offset-drift]

**Configured IDs.** The list sent is built by iterating the rules read from the API. A configured ID that is not among them is never added to the body. [zpa.terraform.rule-order:sdk-sends-only-listed-ids] The update reads the existing rules, but only to look for the Deception rule. It never checks that each configured ID is among them before calling `BulkReorder`. [zpa.terraform.rule-order:provider-does-not-check-ids-exist] Read overwrites a configured rule's order only when the rules read from the API contain its ID, and then writes every configured entry back to state. An ID the API no longer has keeps its configured order in state. From v4.4.16 the overwrite also requires the API's order to be above the Deception offset, and stores that order less the offset. [zpa.terraform.rule-order:read-keeps-configured-value-when-id-missing] A configured rule ID that does not exist is left out of the PUT body without any diagnostic and is kept in state as if it were ordered, so state can list a rule the policy does not contain. [zpa.terraform.rule-order:nonexistent-id-persists] How the reorder endpoint applies a submitted list, including nonexistent IDs and gapped numbers, is open [gap:zpa.terraform.rule-order:api-bulk-reorder-semantics].

**Duplicate IDs.** The configured rules are a set, but `getRules` stores them in a map keyed by ID. Two blocks with the same ID and different orders collapse into one entry (which one survives depends on set iteration order), and `validateRuleOrders` receives only the collapsed map. [zpa.terraform.rule-order:duplicate-ids-collapse-into-map] A configuration that lists the same rule ID twice with different orders therefore passes validation with one of the two orders silently dropped. [zpa.terraform.rule-order:duplicate-ids-pass-validation]

**Context and unparseable orders.** `BulkReorder` fetches the policy set and the full rule list with `context.Background()`; only the final PUT uses the caller's context. [zpa.terraform.rule-order:first-two-reads-ignore-caller-context] Read parses each API rule's order with `strconv.Atoi` and, if that fails, leaves the rule out of the current-order map with no log or diagnostic. A configured rule whose API order cannot be parsed keeps its configured number in state. [zpa.terraform.rule-order:read-skips-unparseable-order]

**Concurrency.** `BulkReorder` takes no lock. Create, update, delete and the single-rule reorder in the same package each take a mutex first: up to v3.8.50 the package-level `ruleMutex`, and from v3.8.51 (#466) `common.PolicyRuleMutex`, which the v2 package's writes share. A comment in `GetPolicyRule` says only create, update and delete need it because of API restrictions, although the single-rule `Reorder` takes it too. [zpa.terraform.rule-order:reorder-not-under-rule-mutex] A bulk reorder can run while another reorder resource, or a policy rule update, is in flight in the same provider process. Its PUT carries a list built from an earlier read, so whichever request lands last determines the final order. [zpa.terraform.rule-order:concurrent-bulk-reorder-last-writer-wins] What the API does with overlapping rule writes is open [gap:zpa.terraform.rule-order:api-concurrent-writes].

What to check:
1. Whether the whole policy type's order is re-read after an apply of a reorder resource, and terminal rules such as `Default_Rule` are still last.
2. Whether the configured numbers are contiguous from 1 and list every rule that matters, so that the configuration matches the list sent.
3. Which provider version produced a plan that shows an order difference when the Deception rule sits at order 1: up to v4.4.15 the unreversed offset explains it, and v4.4.16 reads the offset back.
4. Whether a reorder resource depends on the rule resources it orders, and whether two reorder resources share one policy type.

- [zpa.terraform.rule-order:bulk-reorder-status-check-unreachable] Tier B: Read from the code at v3.8.58, not exercised. The legacy ZPA client ends the same way: its `do` returns `errorx.CheckErrorInResponse`'s error for any status outside 200-299, so `BulkReorder` again returns nil and that error before its own check. The 403 LIMIT_EXCEEDED, 409/412 edit-lock and 5xx branches of `ExecuteRequest` either retry or return an error; none returns a non-2xx response without one.
- [zpa.terraform.rule-order:unmanaged-rules-sent-below-managed] Tier B: Follows from the comparator, the name pin and the provider's map as read at the audited refs. From v4.1.13 through v4.4.15 a configured Deception rule at order 1 was not in the map and so counted among the other rules; from v4.4.16 it is a configured rule. The sort is sort.SliceStable, and its fallback for two unmanaged rules compares their current slice positions, so unmanaged rules keep their relative order; read, not run. Applies to whatever list the rules read returned.
- [zpa.terraform.rule-order:terminal-rule-can-be-displaced] Tier C: Depends on the API applying the submitted ID list as the new order (gap api-bulk-reorder-semantics); on the terminal rule not being in the configuration; and on its name differing from `Default_Rule`.
- [zpa.terraform.rule-order:configured-deception-rule-treated-as-unmanaged] Tier B: Depends on a rule with that exact name at order "1" in the list read at update time. Read from the code at the audited refs; not run. The v4.4.16 changelog describes only the Read offset, not this change to Update; the evidence for it is the code and the unit test.
- [zpa.terraform.rule-order:provider-does-not-check-ids-exist] Tier B: An absence: in `resourcePolicyAccessReorderUpdate` at v4.4.10 and v4.4.15, read in full, `existingRules` is used only in the Deception loop shown. From v4.4.16 that loop is in `deceptionRuleAtOrderOne`, `existingRules` is only passed to it, and the helper reads only each rule's name, order and ID and whether the Deception ID is configured.
- [zpa.terraform.rule-order:nonexistent-id-persists] Tier C: Depends on the API accepting a reorder PUT that carries the complete current list as it would any other (gap api-bulk-reorder-semantics); a rejection would surface as an error instead.
- [zpa.terraform.rule-order:validates-positive-and-unique-numbers] Tier B: An absence: `validateRuleOrders` and the schema's order validator, read in full at v4.4.10 and at the pin, contain only the positivity and duplicate checks.
- [zpa.terraform.rule-order:numbers-are-relative-only] Tier B: Follows from the comparator and the bare ID list; the equivalence is read from code, not run.
- [zpa.terraform.rule-order:gapped-numbers-drift] Tier C: Depends on the API assigning contiguous positions from the submitted list and reporting them in `RuleOrder` (gap api-bulk-reorder-semantics).
- [zpa.terraform.rule-order:duplicate-ids-pass-validation] Tier B: Assumes the two blocks are distinct set elements (a set's identity covers all nested attributes, which is the Terraform plugin SDK's behavior and is not quoted here) and that the schema has no per-ID uniqueness rule, as read in the schema at the audited refs.
- [zpa.terraform.rule-order:reorder-not-under-rule-mutex] Tier B: The absence of any lock in `BulkReorder`, `GetByPolicyType` and `GetAllByType` is from reading those functions in full at v3.8.42, v3.8.47, v3.8.48 and v3.8.55; a search for `ruleMutex` (v3.8.48) and `PolicyRuleMutex` (v3.8.55) in the file found uses only in the four functions quoted. - [zpa.terraform.rule-order:concurrent-bulk-reorder-last-writer-wins] Tier C: Depends on Terraform running the resources concurrently (no dependency between them) and on the API replacing the whole order with the submitted list (gap api-concurrent-writes). The mutex is per process, so it would not serialize separate runs either way.
- [zpa.terraform.rule-order:deception-offset-drift] Tier C: Depends on the API reporting each rule's position in `RuleOrder` after the reorder (gap api-bulk-reorder-semantics). The offset and the missing reverse offset up to v4.4.15 are read from the code; the v4.4.16 outcome is stated by the changelog, and the unit tests mock the post-reorder orders.
- [zpa.terraform.rule-order:zia-zpa-failure-contrast] Tier B: The ZPA half depends on the API applying the submitted ID list as the new order (gap api-bulk-reorder-semantics).
