# App Connector deployment, redundancy and limits (zpa.app-connectors.deployment)
Also called: app connector deployment; app connector outbound only; app connector n+1; how many app connectors; app connector platforms; app connector limit 100; app connector sizing; app connector ssl interception
Former IDs: zpa-29

Where an App Connector runs, what it needs from the network, and how many a deployment needs.

**Network behavior.** App Connectors only make outbound connections and need no inbound open ports to operate. [zpa.app-connectors.deployment:outbound-only] After enrollment, the App Connector's TLS client certificate maintains its authentication with the nearest Public or Private Service Edge, which supplies its configuration. [zpa.app-connectors.deployment:connects-to-nearest-service-edge] Private Access does not support SSL interception between an App Connector and the Zscaler cloud: the connection uses TLS with pinned certificates, so an intercepting device makes it fail. [zpa.app-connectors.deployment:no-ssl-interception] The App Connector Linux guide says that after enrollment an outbound TLS tunnel over port 443 is established to the Private Access cloud infrastructure, uses minimal bandwidth, and carries periodic keepalives to Public or Private Service Edges, application learning, application health reporting, and App Connector software upgrades completed on a weekly schedule. [zpa.app-connectors.deployment:control-channel-traffic] The App Connector Linux guide says all Zscaler data centers containing Public Service Edges for Private Access must be allowed because a partial firewall configuration can result in connectivity problems for end users, and a 90-day notice is provided for activating additional IP CIDR ranges. [zpa.app-connectors.deployment:firewall-all-data-centers] The App Connector Linux guide says *.prod.zpath.net must be in the SSL bypass list for traffic originating from the App Connector, and that if OAuth 2.0 is used the OAuth server FQDN zpa-oauth.private.zscaler.com must be in the allowlist and user devices must be allowed to make an outbound connection to it. [zpa.app-connectors.deployment:ssl-bypass-and-oauth-fqdn] The App Connector Linux guide says that for Private Access integration with ZDX the App Connector firewall requirements must align with the ZDX configuration, the firewall must allow egress traffic on the TCP, UDP and ICMP protocols, and App Connectors must be able to egress traffic to port 443 for Zscaler Service Edge connections and the ports of all configured applications. [zpa.app-connectors.deployment:zdx-firewall]

**Redundancy.** App Connectors are always active, so they are typically deployed in a redundant configuration. [zpa.app-connectors.deployment:always-active] Zscaler's architecture article recommends redundant (N+1) deployments, where N is the number of App Connectors needed to support the applications, because connectors are always active. [zpa.app-connectors.deployment:n-plus-1] App Connectors never communicate with each other. [zpa.app-connectors.deployment:never-communicate]

**Placement.** App Connectors can be co-located with the enterprise applications or deployed in any location that has connectivity to them; they are typically placed on network segments that reach both the secured applications and the Private Access cloud, such as a DMZ. [zpa.app-connectors.deployment:placement] App Connector groups must be associated only with applications that their App Connectors can actually reach. [zpa.app-connectors.deployment:reach-only-what-it-can-reach]

**Forms and platforms.** Zscaler distributes a standard VM image for data centers, local private clouds such as VMware, and public clouds such as AWS EC2, and also provides packages installable on supported Linux distributions. [zpa.app-connectors.deployment:distribution-forms] The help lists these platforms as supported by Private Access: AWS, Docker, GCP, Kubernetes, Linux (RHEL 8 or 9), Microsoft Azure, Microsoft Azure Local, Microsoft Hyper-V, Nutanix, OpenShift, and VMware vCenter or vSphere (ESXi). [zpa.app-connectors.deployment:supported-platforms] Private Access provides STIG images for AWS, GCP, Microsoft Azure, Nutanix, and VMware by default. [zpa.app-connectors.deployment:stig-images] The STIG password rules and the 2024 password-expiration issue are in [STIG-hardened ZPA images: password rules and the 2024 password-expiration issue](kb:zpa.software-components.stig-images). In other hypervisor or cloud environments (for example Oracle Cloud), an App Connector is built by deploying a Linux instance and following the RPM-based deployment instructions. [zpa.app-connectors.deployment:other-environments-use-rpm] Per-platform procedures are in [App Connector deployment by VM and cloud platform](kb:zpa.app-connectors.platforms) and container deployments in [App Connectors on Docker, Kubernetes and OpenShift](kb:zpa.app-connectors.containers).

**Editing a deployed connector.** App Connectors managed by Zscaler are read only. On a deployed App Connector the editable fields are Name (no special characters other than periods, hyphens and underscores), Status, Description, Application Shield Scanning (designates the connector as an App Scanner for Autonomous Application Shield) and IP Address Settings (DHCP or Static IP); the page also lists Operating System SSH Setting as Inherit or Override. [zpa.app-connectors.deployment:editable-fields]

**Host security and disk.** The App Connector Linux guide says App Connector VMs distributed by Zscaler for private clouds run without remotely accessible services and with swap partitions disabled, the passwd command must be used to change the credentials on the default admin account, the operating systems are essentially unmodified (currently based on RHEL 9.x) and patchable with yum, and Zscaler recommends hardening the OS, including the sshd-config file, after initial deployment. [zpa.app-connectors.deployment:os-security] The App Connector Linux guide says Zscaler recommends treating access to App Connectors as privileged so only authorized personnel can access an App Connector's console. [zpa.app-connectors.deployment:privileged-console] The App Connector Linux guide recommends a minimum disk size per directory of 10 GB for /, 10 GB for /tmp, 10 GB for /home, 5 GB for /var, 5 GB for /var/tmp, 10 GB for var/log and 10 GB for var/log/audit, and says Disk Space Exceeded Limit notifications only consider the partition where the App Connector's binary file (image.bin) is located. [zpa.app-connectors.deployment:disk-by-directory]

**Limits and sizing.** A tenant can have up to 100 App Connectors in the Admin Console by default; the total counts active connectors and connectors that are disabled but not deleted. Zscaler Support can raise it. [zpa.app-connectors.deployment:tenant-limit-100] The ranges and limitations help article, whose values are per organization unless noted otherwise, lists in its Private Access (ZPA) section 100 App Connectors, 100 App Connector groups and 100 App Connector provisioning keys under App Connector Management. [zpa.app-connectors.deployment:ranges-limits-100] The group-level maximum is open, and the container guides' per-group threshold of 100 for provisioning-key use is quoted in the gap [gap:zpa.app-connectors.deployment:max-connectors-per-group]. The help points to its App Connector Deployment Prerequisites article for VM image sizing and scalability, supported platform requirements and deployment best practices. [zpa.app-connectors.deployment:sizing-lives-in-prerequisites] Zscaler's recommended App Connector specification is 4 GB RAM, 2 CPU cores (Xeon E5 class) on physical machines without hyperthreading or 4 cores on VMs with hyperthreading, 64 GB thin-provisioned disk and at least 1 NIC; AWS and GCP require at least 4 cores, and Azure VMs older than V3 need 2 cores while V3 and later need 4. [zpa.app-connectors.deployment:sizing-baseline] Recommended instance types: AWS t3.xlarge (non-production or low traffic) or m5a.xlarge (production or high traffic); GCP n2-standard-4 or n2-highcpu-4 with a Linux RPM; Azure Standard_D4s_v4 or Standard_D4s_v5 or later. [zpa.app-connectors.deployment:sizing-instance-types] Zscaler recommends a minimum PassMark CPU Mark score of 2640 and requires the Intel AES-NI instruction set to be enabled. [zpa.app-connectors.deployment:sizing-cpu-benchmark] For ZDX deployments Zscaler recommends 8 GB RAM and 4 CPU cores per App Connector; scaling should be reconsidered beyond 2,000 ZDX probes at a 5-minute interval, and 32 GB RAM when alerts exceed a configured 250 Mbps on a connector. [zpa.app-connectors.deployment:sizing-zdx] To enable AppProtection with the default profile, Zscaler recommends at least 8 CPU cores and 8 GB memory per connector, with peak CPU and memory under 40%; throughput may be 100 to 200 Mbps with AppProtection, based on a mix of 85% GET and 15% POST with 32 KB payloads. [zpa.app-connectors.deployment:sizing-appprotection] On VMware, dynamic resource allocation is not recommended: reserve 8 GB RAM and CPU equal to cores times GHz per core. [zpa.app-connectors.deployment:sizing-vmware-reservation] With the baseline specification each App Connector supports up to 500 Mbps aggregate throughput, which can reach 1 Gbps per connector with 8 vCPU (or 4 physical cores) and 8 GB RAM and a faster link. [zpa.app-connectors.deployment:throughput-500] Per-connector throughput falls with the share of applications using double encryption: 500 Mbps at 0%, 437.5 at 25%, 375 at 50%, 312.5 at 75% and 250 at 100%; a 1 Gbps link needs 2 to 3 connectors without double encryption and 4 to 6 with it (including N+1). [zpa.app-connectors.deployment:throughput-double-encryption] Exact throughput also depends on internal network setup, latency, and whether double encryption, AppProtection or ZDX is enabled. [zpa.app-connectors.deployment:throughput-varies] Zscaler recommends more connectors with lower specifications over fewer large ones, and a minimum of two healthy connectors to always ensure an available path; more connectors can be added at any time with the same provisioning key. [zpa.app-connectors.deployment:scale-out-small-and-two-minimum] Platform prerequisites include x86_64/AMD64, systemd, root or sudo, DNS and network access, a static MAC address, and for OAuth 2.0 enrollment Manager software and connector version 25.46.3 or later; the OAuth server supports only IPv4. [zpa.app-connectors.deployment:platform-prerequisites] The Hyper-V guide's own core counts differ [divergence:zpa.app-connectors.deployment:hyper-v-vm-cores], and the architecture requirement differs from the Docker page [divergence:zpa.app-connectors.deployment:docker-arm64]. A concurrent-user sizing statement is unsourced [gap:zpa.app-connectors.deployment:vm-sizing].

**Reference Terraform modules and July 2026 remote settings.** The AWS module README says that as of module version 1.4.0 all App Connectors are deployed on Red Hat Enterprise Linux 9; the Azure README says the same as of 1.1.0. [zpa.app-connectors.deployment:module-rhel9] The AWS module's example deployment types are base (VPC, subnets, NAT gateway, bastion, no connectors), base_ac (base plus connector subnets and VMs behind the NAT gateways), base_ac_asg (base plus connectors from a launch template in an Auto Scaling Group), and brownfield ac and ac_asg. [zpa.app-connectors.deployment:module-aws-example-types] The Azure module's examples are base (resource group, VNet, bastion; no connectors), base_ac (connectors in an availability set, or zones when supported), and base_ac_vmss, ac and ac_vmss variants. [zpa.app-connectors.deployment:module-azure-example-types] AWS module defaults: standalone instance type m5.large, ac_count 1, ASG min_size 2, max_size 4 and target CPU utilization 50. [zpa.app-connectors.deployment:module-aws-defaults] Azure module defaults: instance size Standard_D4s_v5, ac_count 1 (valid 1 to 250), VMSS default, minimum and maximum of 2, 2 and 10, scale-out at 70% and scale-in at 50% evaluated over PT5M, with PT15M cooldowns. [zpa.app-connectors.deployment:module-azure-defaults] Module network defaults: the AWS security group allows all egress and SSH (22/tcp) only from the VPC CIDR; the Azure NSG allows inbound SSH and ICMP from VirtualNetwork and all outbound. [zpa.app-connectors.deployment:module-network-defaults] AWS module hardening defaults: imdsv2_enabled is true for standalone and ASG instances; the ASG module encrypts EBS volumes by default (ebs_encrypted true, AWS managed key when ebs_kms_key_arn is null); the standalone module's instance resource sets no EBS or root block device encryption; the instance role trusts ec2.amazonaws.com. [zpa.app-connectors.deployment:module-aws-hardening] Azure module: the VMSS OS disk is Premium_LRS with ReadWrite caching, and the default marketplace image is publisher zscaler, offer zscaler-private-access, SKU zpa-con-azure, pinned to a version rather than latest: 2025.11.12 at v1.3.1, and 2026.07.07 from v2.0.0 (#31). [zpa.app-connectors.deployment:module-azure-hardening] Up to AWS module v2.0.1 the App Connector Auto Scaling Group referenced the launch template at var.launch_template_version and no file in the module repository contained an instance_refresh block. v2.1.0 adds an opt-in rolling instance refresh (#52): instance_refresh_enabled defaults to false, and when true the group uses the launch template's latest version number and declares a Rolling instance_refresh block. [zpa.app-connectors.deployment:asg-no-instance-refresh] What an apply does to running ASG instances comes from an upstream issue and is open [gap:zpa.app-connectors.deployment:aws-asg-instance-refresh]. The July 13, 2026 release added remote network commands: The July 13, 2026 release summary lists support for a Get Network Interfaces command that collects a list of the network interfaces an App Connector uses, to help with remote troubleshooting. [zpa.app-connectors.deployment:get-network-interfaces-july13] The July 13, 2026 release summary lists network settings for App Connectors that can run remote commands to enable SSH on the OS and update software interface settings across Private Access virtual machines such as AWS, Azure, and GCP. [zpa.app-connectors.deployment:network-settings-july13] Issue #24 on the Azure module reported that the bastion VM's default `Standard_B1s` size failed with `SkuNotAvailable` in most regions, including through the `zsac` script, and was closed as completed on 2026-07-07 with a reply to upgrade to v1.3.1; the module's changelog records that v1.3.1 changed the bastion default to `Standard_B2ts_v2`, and the module's `instance_size` variable now defaults to that size and can be overridden with any size available in the target region. [zpa.app-connectors.deployment:azure-bastion-b1s-sku-unavailable]

Enrollment and group membership are in [App Connector enrollment, certificates and re-enrollment](kb:zpa.app-connectors.enrollment) and [App Connector groups](kb:zpa.app-connectors.connector-groups); how a session picks a connector is in [How a session is assigned to an App Connector](kb:zpa.app-connectors.selection).

What to check:
1. How many connectors the group runs against the N needed, since connectors are always active and never share load state with each other.
2. Whether the tenant is close to the App Connector total, counting disabled connectors that were never deleted.
3. Which core count and architecture apply to a Hyper-V or Docker connector, since the guides disagree with the sizing and platform rules.
4. Whether the firewall allows every Zscaler data center with Public Service Edges and the SSL bypass list holds *.prod.zpath.net for connector traffic.
5. Whether a device on the path intercepts TLS to the Zscaler cloud before concluding the connector itself is faulty.
6. Whether the connector meets the recommended CPU, memory, AppProtection and ZDX sizing and the double-encryption throughput table.

Sources disagree (name both sides):
- The App Connector Hyper-V guide's own prerequisites give 4 CPU cores for virtual machines with hyperthreading (the rule in sizing-baseline), while its procedure enters 2 virtual processors. [divergence:zpa.app-connectors.deployment:hyper-v-vm-cores]
  - zscaler-help: The prerequisites call for 4 CPU cores for VMs with hyperthreading.
  - zscaler-help: The Hyper-V procedure enters 2 for the number of virtual processors.
  Impact: A Hyper-V connector built exactly by the procedure has 2 virtual processors, half the rule for VMs with hyperthreading; the guide does not say whether the procedure's 2 is a starting value or the intended size.
- The platform prerequisites (platform-prerequisites) require an Intel x86_64/AMD64-based architecture, while the App Connector Docker guide offers the image for ARM64 as well. [divergence:zpa.app-connectors.deployment:docker-arm64]
  - zscaler-help: The platform prerequisites list an Intel x86_64/AMD64-based architecture.
  - zscaler-help: The Docker image is available for ARM64 as well as AMD64, with a stated ARM64 minimum of 2 cores and 4 GB RAM.
  Impact: The x86_64/AMD64 requirement cannot be read as covering every App Connector form: the Docker page supports ARM64, while the Kubernetes and OpenShift guides allow only x86 for the same image. The prerequisites page does not say it excludes the Docker deployment.
