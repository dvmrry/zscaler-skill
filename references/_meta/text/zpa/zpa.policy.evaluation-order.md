# Evaluation order across ZPA policy types (zpa.policy.evaluation-order)
Also called: zpa policy order; policy evaluation order; forwarding before access; client forwarding policy first; bypass skips access policy; default block; implicit block access; most specific segment first-match; when both fqdns are equal

Several ZPA policy types exist, and they do not run as one list.

**The policy types.** Private Access has separate policy types, including access, client forwarding, isolation, timeout, redirection, AppProtection and Browser Protection policy. [zpa.policy.evaluation-order:policy-types]

**Within a type.** Private Access evaluates policy rules using the most specific application segment and a top-down, first-match principle: the first rule whose criteria match is enforced and all later rules, including conflicting ones, are disregarded. [zpa.policy.evaluation-order:first-match-most-specific-segment] When a request arrives, Private Access identifies the matching rule first, choosing the rule that corresponds to the most specific application segment for the domain name or IP address if segments are part of the criteria. [zpa.policy.evaluation-order:segment-then-rules]

**Specific against broad.** The Access Policy Deployment and Operations Guide says rules process on a specific and top-down methodology: if rule 1 blocks `*.web.com` and rule 2 allows `specific.web.com`, rule 2 allows `specific.web.com` and every other subdomain is blocked. [zpa.policy.evaluation-order:specific-segment-beats-rule-order] The same guide says that when both FQDNs are equal ZPA ranks top-down, so if rule 1 is `*.specific.web.com` and rule 2 is `specific.web.com`, rule 1 applies because it is processed first. [zpa.policy.evaluation-order:equal-fqdn-top-down] Whether a wildcard entry matches the bare domain is open [gap:zpa.policy.evaluation-order:wildcard-matches-bare-domain].

**Across types.** Client forwarding policy rules are evaluated before access policy rules, and a match in client forwarding policy makes Private Access disregard the other policy rules, including conflicts. [zpa.policy.evaluation-order:client-forwarding-before-access] If a forwarding rule bypasses the traffic, the access policy rule is never evaluated for it, so a bypass for an application defeats an access rule that would block it. [zpa.policy.evaluation-order:bypass-skips-access] Bypass wins over forwarding on different ports: [If there are multiple client forwarding policies with both Bypass ZPA and Forward to ZPA rules for a given domain with different ports, the Bypass ZPA rule action takes precedence.](kb:zpa.policy.forwarding-rules:bypass-beats-forward-on-ports). Global rules apply before policy group rules: [Global rules define access policies that apply across all policy groups, and can be created to enforce organization-wide access requirements before policy group rules are evaluated.](kb:zpa.policy.policy-groups:global-rules-scope). How the other types order against access policy is not stated [gap:zpa.policy.evaluation-order:remaining-type-order].

**When nothing matches.** If no access policy rule matches, or no rule is defined at all, access to the application is implicitly set to Block Access. [zpa.policy.evaluation-order:default-access-block] If no client forwarding rule matches, or none is defined, access to the application is implicitly set to Forward to Private Access. [zpa.policy.evaluation-order:default-forwarding] If no timeout rule matches, Private Access applies the default timeout policy rule, which requires authentication every 7 days for any application and never ends a session for idle time. [zpa.policy.evaluation-order:default-timeout-rule] If no isolation rule matches, Private Access applies the default isolation policy rule. [zpa.policy.evaluation-order:default-isolation]

**Microtenants.** The order for a custom microtenant user is in [A user in a custom Microtenant accessing a Default Microtenant segment is evaluated against the Default Microtenant first, and only if there is no match does Private Access evaluate access, timeout and client forwarding policy within the custom Microtenant.](kb:zpa.microtenants.policy-evaluation:default-first-for-custom-user).

Rule order inside the access policy is in [Access policy rule order](kb:zpa.policy.access-rule-order). How the segment is chosen is in [Segment matching and policy search with and without Multimatch](kb:zpa.policy.multimatch).

What to check:
1. Whether a client forwarding rule matched first, since a match there decides before any access rule is read.
2. Which application segment the request mapped to, because rules are searched by the most specific segment.
3. Whether any rule matched at all; if none did, the result is the policy type's default.
4. Whether the user sits in a custom microtenant, which changes which tenant is searched first.
5. Whether the order of the remaining policy types relative to access policy is being relied on; no source states it.

Not known (open gaps):
- Evaluation order of timeout, isolation, inspection and the other policy types relative to access policy [gap:zpa.policy.evaluation-order:remaining-type-order]: settled by support-ticket or lab-test. Blocks: saying whether a timeout, isolation or inspection rule can act on a request an access rule has already blocked
- Whether a wildcard entry such as *.specific.web.com also matches the bare specific.web.com [gap:zpa.policy.evaluation-order:wildcard-matches-bare-domain]: settled by lab-test
