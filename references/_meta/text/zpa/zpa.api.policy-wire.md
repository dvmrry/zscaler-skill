# ZPA policy rule wire behavior: routes, request fields and ordering (zpa.api.policy-wire)
Also called: policy rule v1 v2 path; policy rule update returns 204; bulk reorder Default_Rule; policy rule disabled field type; python isolation rule client type injected; privileged capabilities file_upload false; policy count shape; stepup auth level

This subject records how the ZPA policy rule endpoints behave on the wire as the Go SDK, the Python SDK and the OpenAPI document show them. Rule semantics are in [ZPA policy evaluation](kb:zpa.policy), ordering in [Access policy rule order](kb:zpa.policy.access-rule-order) and [How the ZPA Terraform provider applies policy rule order (BulkReorder)](kb:zpa.terraform.rule-order), and the provider's use of these calls in [What the ZPA Terraform provider sends and loses when writing policy rules](kb:zpa.terraform.policy-rule-writes).

## Routes

In the Go SDK's v2 policy package, rule create is a POST and rule update a PUT on the v2 path, while single-rule read and delete use the v1 path. The OpenAPI document has POST and PUT for rules under both v1 and v2, and GET and DELETE for a single rule only under v1. [zpa.api.policy-wire:rule-route-versions] `GetPolicyByApplication` and `GetPolicyCount` live in the v2 Go package but build v1 paths (`policySet/rules/policyType/{type}/application/{id}` and `.../count`), and the Python SDK's matching methods also call the v1 base endpoint. The OpenAPI document has neither path. [zpa.api.policy-wire:lookups-use-v1-paths] The count response shape differs between the SDKs [divergence:zpa.api.policy-wire:policy-count-shape].

The Python SDK maps friendly names to policy types, including `PRIVILEGED_PORTAL_POLICY`, `VPN_TUNNEL_POLICY` and `USER_PORTAL`. The OpenAPI policy-type parameter lists `PRIVILEGED_PORTAL_POLICY` and the other ten types of the Go edge-case test, but neither `VPN_TUNNEL_POLICY` nor `USER_PORTAL`. [zpa.api.policy-wire:python-policy-type-map] Whether the two extra values are accepted is open [gap:zpa.api.policy-wire:policy-type-extra-values].

## What the request carries

The v2 Go package has a response struct and a request struct for a rule, and their tags differ. On the response struct `conditions`, `appServerGroups`, `appConnectorGroups`, `serviceEdgeGroups`, `microtenantId` and `credentialPool` have no `omitempty`. On the request struct `conditions` and `credentialPool` do have it, while `appServerGroups`, `appConnectorGroups`, `serviceEdgeGroups`, `microtenantId` and `devicePostureFailureNotificationEnabled` do not. [zpa.api.policy-wire:v2-struct-serialization] Both `UpdateRule` functions replace a rule with no conditions (and a condition with no operands) by an empty slice before the PUT. In the v1 package the tags are `json:"conditions"` and `json:"operands"`, so an empty array is sent. In the v2 package the request tags are `omitempty`, so the empty slice is dropped and the key is absent from the body. [zpa.api.policy-wire:conditions-empty-slice-wire] Whether an absent conditions key clears the conditions is open [gap:zpa.api.policy-wire:v2-empty-conditions-meaning].

The v1 condition has a `microtenantId` and flat operands that carry `lhs` and `rhs`. The v2 condition has no `microtenantId` and adds `setIds` in the OpenAPI document. The Go v2 operand adds `values` and `entryValues` (a list of `lhs`/`rhs` pairs) alongside `lhs`/`rhs`, while the contract v2 operand has `values` and `entryValues` and no `lhs` or `rhs`. [zpa.api.policy-wire:condition-shapes-v1-v2] [The Python SDK's v2 condition builder emits `entryValues` (pairs of `lhs` and `rhs`) for the object types posture, trusted_network, country_code, platform, risk_factor_type, saml, scim, scim_group and chrome_enterprise, and a `values` list for every other type. Its v1 builder emits flat `{objectType, lhs, rhs}` operands.](kb:zpa.sdk-python.policy-helpers:python-v2-operand-forms) [The pinned v1 SDK's `UpdateRule` blanks every non-empty operand name in the request just before the PUT. The provider does expose operand `name` as an optional, computed field and passes it into the request, so a configured or refreshed name never reaches ZPA on a v1 rule update.](kb:zpa.terraform.policy-rule-writes:v1-sdk-erases-operand-names) [The v2 SDK's `UpdateRule` clears operand IDs, not names. The v2 provider schemas model operands by object type and values rather than a writable name.](kb:zpa.terraform.policy-rule-writes:v2-sdk-clears-operand-ids-not-names)

`PrivilegedCapabilities.MicroTenantID` is tagged `omitempty` in the v1 package and not in the v2 package, so a v2 request always carries a `microtenantId` key inside `privilegedCapabilities`, empty when unset. `PrivilegedPortalCapabilities.MicroTenantID` has `omitempty` in both. [zpa.api.policy-wire:capabilities-microtenant-tag] The OpenAPI document describes the privileged capabilities list as taking CLIPBOARD_COPY, CLIPBOARD_PASTE, FILE_DOWNLOAD, FILE_UPLOAD, INSPECT_FILE_DOWNLOAD, INSPECT_FILE_UPLOAD, MONITOR_SESSION, RECORD_SESSION and SHARE_SESSION. [zpa.api.policy-wire:contract-capability-values-described] The Python builder produces the same nine values [The Python capability rule builder turns its flags into the strings CLIPBOARD_COPY, CLIPBOARD_PASTE, FILE_DOWNLOAD, FILE_UPLOAD, INSPECT_FILE_UPLOAD, INSPECT_FILE_DOWNLOAD, MONITOR_SESSION, RECORD_SESSION and SHARE_SESSION, and maps `file_upload=False` to INSPECT_FILE_UPLOAD (not to nothing), while `file_upload=True` gives FILE_UPLOAD. The OpenAPI document types `capabilities` as a free list of strings, and the Go SDK tests exercise five of the values.](kb:zpa.sdk-python.policy-helpers:python-capabilities-mapping).

The OpenAPI v2 rule POST body declares an integer `version`. The Go v2 `PolicyRule` request struct has no `version` field: `version` is tagged on the response struct `PolicyRuleResource` instead. [zpa.api.policy-wire:version-field-response-only] Whether the backend needs it is open [gap:zpa.api.policy-wire:version-required].

The `disabled` type differs between sources [divergence:zpa.api.policy-wire:disabled-wire-type] and which form the API takes is open [gap:zpa.api.policy-wire:disabled-wire-form]. For the reauth timeouts see the divergence in [ZPA timeout policy rules](kb:zpa.policy.timeout-rules); whether both string and integer are accepted is open [gap:zpa.api.policy-wire:reauth-accepted-types].

The Go policy request structs type rule `id` and `policySetId` as strings, and the Python access rule builders call `transform_common_id_fields` with `coerce_ids=False`, which passes ID values through verbatim rather than coercing them to integers. [zpa.api.policy-wire:policy-ids-strings]

## Updates and ordering

A rule update returns no resource: the OpenAPI v2 PUT documents 204, the Go `UpdateRule` returns only the HTTP response, and the Python v1 update returns an object holding just the rule id when the response body is empty. [zpa.api.policy-wire:rule-update-no-body] Up to v3.8.50 the Go v2 package takes its own package-level `ruleMutex` in create, update, delete, reorder and `BulkReorder`, and the v1 package takes a separate one in create, update, delete and reorder, so a v1 write and a v2 write to the same policy set can run concurrently. From v3.8.51 (#466) both packages take one shared `common.PolicyRuleMutex` in those functions instead. Both before and after that change the v1 `BulkReorder` starts without taking a lock. Reads do not lock. The Python SDK wraps `add_access_rule`, `update_access_rule`, `add_access_rule_v2`, `delete_rule`, `reorder_rule` and `bulk_reorder_rules` in one module-level lock; its `add_app_protection_rule` carries no lock decorator, unlike `add_app_protection_rule_v2`. [zpa.api.policy-wire:rule-mutex-coverage]

In both Go packages `BulkReorder` reads the policy set and every rule of the type, sorts them by the caller's order map, takes out the rule named exactly `Default_Rule`, appends its id last, and PUTs a bare ordered list of rule ids to the policy set's `reorder` endpoint. [zpa.api.policy-wire:go-bulk-reorder-default-last] [The Python `bulk_reorder_rules` PUTs the caller's `rules_orders` list to the policy set's `reorder` endpoint unmodified: it does not look for or move `Default_Rule`, which the Go SDK's `BulkReorder` takes out and appends last.](kb:zpa.sdk-python.policy-helpers:python-bulk-reorder-passthrough) The OpenAPI document describes the bulk reorder as 'Execute this API only once to reorder the rules', takes the new order as an array of rule ids, and answers 204. [zpa.api.policy-wire:bulk-reorder-api-text] The id type of the body differs [divergence:zpa.api.policy-wire:reorder-body-id-type], and how safe a repeated call is remains open [gap:zpa.api.policy-wire:bulk-reorder-repeat-safety].

## Python SDK

The Python builders' defaults, checks and policy type handling are held with the Python helpers: [The Python policy_type argument of list_rules is a lowercase alias looked up in the SDK's policy map, and a wire value such as ACCESS_POLICY raises ValueError('Incorrect policy type provided'); list_rules returns PolicySetControllerV1 objects.](kb:zpa.sdk-python.policy-helpers:python-list-rules-alias-required), [The Python get_policy_rule_count accepts a policy type already in wire form, because it checks the values of the policy map before looking up an alias.](kb:zpa.sdk-python.policy-helpers:python-count-accepts-wire-values), [The Python credential rule builder first fetches the credential policy set with a GET through `get_policy`; then, before sending the rule, it refuses when both or neither of `credential_id` and `credential_pool_id` are given, returning the message as a string in the error slot rather than raising. It sends the id as `credential` or as `credentialPool`.](kb:zpa.sdk-python.policy-helpers:python-credential-exclusive), [If an isolation rule or a v2 browser protection rule built by the Python SDK has no `CLIENT_TYPE` condition, the builder appends an OR condition for `zpn_client_type_exporter` (flat lhs/rhs in v1, a `values` list in v2) and goes straight on to build the request. The Go SDK's `CreateRule` and `UpdateRule`, in both policy packages, add no condition.](kb:zpa.sdk-python.policy-helpers:python-isolation-client-type), [The Python capability rule builder turns its flags into the strings CLIPBOARD_COPY, CLIPBOARD_PASTE, FILE_DOWNLOAD, FILE_UPLOAD, INSPECT_FILE_UPLOAD, INSPECT_FILE_DOWNLOAD, MONITOR_SESSION, RECORD_SESSION and SHARE_SESSION, and maps `file_upload=False` to INSPECT_FILE_UPLOAD (not to nothing), while `file_upload=True` gives FILE_UPLOAD. The OpenAPI document types `capabilities` as a free list of strings, and the Go SDK tests exercise five of the values.](kb:zpa.sdk-python.policy-helpers:python-capabilities-mapping), [The Python redirection rule builder rejects `redirect_default` when `service_edge_group_ids` is given, requires `service_edge_group_ids` for `redirect_preferred` and `redirect_always`, checks the first value of each `CLIENT_TYPE` operand, and only the first, against five client types, and rejects the branch and edge connector client types when the action is `redirect_always`. The OpenAPI document lists REDIRECT_DEFAULT, REDIRECT_PREFERRED and REDIRECT_ALWAYS as actions.](kb:zpa.sdk-python.policy-helpers:python-redirection-rules), [The Python `add_timeout_rule_v2` and `update_timeout_rule_v2` send `reauthTimeout` 172800 and `reauthIdleTimeout` 600 when the caller does not pass them.](kb:zpa.sdk-python.policy-helpers:python-timeout-defaults) and [The Python `reformat_params` table maps `app_connector_group_ids` to the wire key `PolicySetControllers`, but the access rule builders set `appConnectorGroups` directly from their named argument before the table is used.](kb:zpa.sdk-python.policy-helpers:python-reformat-params-key).

## Step-up authentication levels

The two SDKs disagree on what the level list returns [divergence:zpa.api.policy-wire:step-up-auth-shape].

What to check:
1. Whether a rule write was sent to the v2 or v1 route, and that a v2 update returns no body, before reading the response as the stored rule.
2. Whether a v2 PUT left conditions out because the Go request omits an empty slice, before concluding the API ignored them.
3. Whether a reorder through the Go SDK moved a rule named exactly Default_Rule last, and that the Python call sends the order as given.
4. Whether concurrent writers share a process, since the locks do not cover other processes and v1 BulkReorder takes none.
5. Whether an unexpected CLIENT_TYPE condition, reauth value or capability on a Python-built rule came from the builder's defaults.

Sources disagree (name both sides):
- The type of a policy rule's `disabled` field in the OpenAPI document versus the Go SDK [divergence:zpa.api.policy-wire:disabled-wire-type]
  - api-specs: The OpenAPI v2 rule POST body declares `disabled` as an integer.
  - sdk-go: The Go v2 request struct declares `Disabled` as a string with omitempty.
  Impact: A caller building a raw request from the spec sends a number, one using the Go SDK sends a string. Which form the API accepts is not shown (gap disabled-wire-form).
- The shape returned by the step-up authentication level list [divergence:zpa.api.policy-wire:step-up-auth-shape]
  - sdk-go: The Go `GetStepupAuthLevel` decodes the response into a list of strings; its `StepAuthLevel` struct is not used by the function.
  - sdk-python: The Python SDK builds a `StepUpAuthLevel` object for each item of the response.
  Impact: If the endpoint returns objects, the Go decode into strings fails or yields nothing useful; if it returns plain names, the Python objects are built from strings. The OpenAPI document has no step-up path to settle it.
- The shape of the policy rule count response [divergence:zpa.api.policy-wire:policy-count-shape]
  - sdk-go: The Go v2 `GetPolicyCount` pages the count URL into a list of `PolicyRuleResource`.
  - sdk-python: The Python docstring says the response is a dictionary with a `count` key holding the count as a string.
  Impact: The Go function cannot return the count if the Python description is right; use the Python shape or a raw call. The OpenAPI document does not define this endpoint.
- The type of rule ids in the bulk reorder body [divergence:zpa.api.policy-wire:reorder-body-id-type]
  - api-specs: The OpenAPI document types the reorder body as an array of int64 integers.
  - sdk-go: Both Go `BulkReorder` functions build the body as a list of string rule ids.
  Impact: The Go SDK sends the ids as JSON strings. Whether the API accepts quoted ids is not recorded; the SDK's reorder is used in practice (see zpa.terraform.rule-order).

Not known (open gaps):
- What an absent conditions key means on a v2 rule PUT [gap:zpa.api.policy-wire:v2-empty-conditions-meaning]: settled by lab-test. Blocks: telling whether the Go v2 UpdateRule clears conditions or leaves them unchanged when the caller has none
- Whether the backend needs `version` on a v2 rule update [gap:zpa.api.policy-wire:version-required]: settled by lab-test or source-read. Blocks: deciding whether the Go v2 request omitting `version` can lose updates
- Which form of `disabled` the ZPA API accepts [gap:zpa.api.policy-wire:disabled-wire-form]: settled by lab-test. Blocks: choosing between string and integer for a raw rule request
- Whether the API accepts reauth timeouts as both strings and integers [gap:zpa.api.policy-wire:reauth-accepted-types]: settled by lab-test. Blocks: choosing the wire type for reauthTimeout and reauthIdleTimeout in raw requests
- What happens when the bulk reorder is sent twice in quick succession [gap:zpa.api.policy-wire:bulk-reorder-repeat-safety]: settled by lab-test or support-ticket. Blocks: deciding whether a retried bulk reorder is safe
- Whether VPN_TUNNEL_POLICY and USER_PORTAL are accepted policy types [gap:zpa.api.policy-wire:policy-type-extra-values]: settled by lab-test. Blocks: using the Python friendly names vpn_policy and user_portal
