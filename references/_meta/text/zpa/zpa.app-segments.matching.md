# Which application segment a destination maps to when several overlap (zpa.app-segments.matching)
Also called: most specific segment wins; more granular application segment; port mismatch bypass; traffic goes direct instead of through zpa; wildcard segment not matching; specific fqdn segment removes host from wildcard; no match in this application segment; works by hostname but not by ip; ssh to ip address fails; raw ip not going through zpa
Former IDs: zpa-04

This subject covers how a destination is mapped to one application segment when several overlap.

**Selection.** Exact match is the default, and it attempts the more granular segment: [Exact match is the default application match behavior, in which Zscaler Client Connector attempts to match traffic to the more granular of two segments covering the same destination address.](kb:zpa.policy.multimatch:exact-match-default). Granularity is judged on the domain or address: an exact host is more specific than a wildcard that contains it, and for IPs a /32 host is more specific than the /24 that contains it. [zpa.app-segments.matching:granularity-ranking] Ties and the part port ranges play are open [gap:zpa.app-segments.matching:same-specificity-tie] [gap:zpa.app-segments.matching:granularity-port-narrowness].

**Names and addresses.** A connection made to a raw IP address sends no DNS request, so Client Connector's DNS interception never hands it a synthetic address: a segment defined only by FQDN does not capture it, and Private Access carries it only if an IP-based segment covers that address. [zpa.app-segments.matching:raw-ip-no-dns-interception] When configuring DNS search domains in the Admin Console, a Private Access DNS search domain can be marked Domain Validation so that Client Connector can resolve invalid domains as NXDOMAINs. When a DNS request reaches the app, it checks whether the domain matches any such search domain, by a full match or a subdomain match; for the search domain corp.zscaler.com the page's example succeeds for internal.corp.zscaler.com and fails for my-corp.zscaler.com and it.my-corp.zscaler.com. Wildcard entries are not supported in the DNS Search Domains list. [zpa.app-segments.matching:domain-validation-match] If the domain matches one in the Private Access DNS search domain list, Client Connector performs additional checks to determine if it needs to respond with NXDOMAIN, and for a matched domain checks its validity through the Private Access service. If the domain does not match any DNS search domain, the app does not respond to the DNS request and continues DNS processing with Internet & SaaS or passes the request to the local client configured DNS server for resolution. [zpa.app-segments.matching:domain-validation-outcome] Which outcome follows for a valid internal domain is open [gap:zpa.app-segments.matching:domain-validation-outcome-pairing]. The DNS search domains these checks use: [What DNS search domains do for application segments and how they must match](kb:zpa.app-segments.dns-search-domains). Routing by returned CNAME: [How private link domains route CNAME-matched traffic to private link resources](kb:zpa.app-segments.private-link-domains).

**When the port is not listed.** If there is no match in the more granular application segment for the destination port, Zscaler Client Connector bypasses Private Access and sends the traffic directly. [zpa.app-segments.matching:port-mismatch-bypass] In the documented example, Segment 1 is `*.example.com` on TCP and UDP 1-65535 and Segment 2 is `www.example.com` on TCP 8843; a request to `www.example.com:80` resolves to Segment 2, fails at the closed port, and is not forwarded to Segment 1. [zpa.app-segments.matching:example-no-fallback] Under Exact Match the client drops the access and sends nothing to the cloud: [Under Exact Match, the default application match behavior, when the more specific segment lacks the requested port, the access is dropped at the client level, traffic is not sent to the Private Access cloud, and the attempt is not visible in the diagnostics.](kb:zpa.policy.multimatch:port-mismatch-dropped). The sources word the outcome two ways [divergence:zpa.app-segments.matching:bypass-or-drop], and what happens to the bypassed traffic is open [gap:zpa.app-segments.matching:post-bypass-outcome].

**Carve-outs.** A specific FQDN is removed from the wildcard segment by default: [By default, once a specific FQDN is configured in an application segment, the destination is removed from the wildcard application segment.](kb:zpa.policy.multimatch:carved-out-by-default). The same carve-out applies to IP addresses: the moment an application segment is created for 10.0.0.1/32, that host is carved out of the segment for 10.0.0.0/24. [zpa.app-segments.matching:carve-out-ip] Without Multimatch, a wildcard segment never receives a request for a host that has its own segment on any port that segment does not list; the request is not forwarded to the wildcard segment. [zpa.app-segments.matching:wildcard-dead-for-carved-ports] Private Access does not apply the ports specified in application segments that contain IP subnets or wildcards toward application segments that contain more specific IP addresses or FQDNs, so the ports must be explicitly specified in the application segment that contains the IP addresses or FQDNs. [zpa.app-segments.matching:ports-not-inherited] The page says Private Access always matches an application to the most specific application segment, even if the application could match a wildcard application segment, and evaluates policy with the most specific application segment; in the page's example, a new segment file.exapp.company.com created under a wildcard segment *.exapp.company.com is not covered by the access policy. The Multimatch article says that with Multimatch, multiple matches apply to applications from most specific to least specific. [zpa.app-segments.matching:specific-segment-escapes-wildcard-policy] The documented fixes for a carved-out host are to configure the missing port on the specific segment, or to enable Multimatch, which makes the wildcard segment catch ports the specific segment does not define. [zpa.app-segments.matching:fix-for-carve-out] What Multimatch changes is in [Multimatch: one request matching several application segments](kb:zpa.app-segments.multimatch).

**What outranks granularity.** The Bypass setting is covered in [The application segment Bypass setting and how it ranks](kb:zpa.app-segments.bypass). Access policy runs on the chosen segment: [Evaluation order across ZPA policy types](kb:zpa.policy.evaluation-order). The access log schema for checking which segment matched is [What a ZPA User Activity log record says and does not say](kb:zpa.logs.user-activity).

What to check:
1. Whether the destination port is listed on the most granular segment that covers the host, since a miss there ends in a client-side bypass and never reaches a wider segment.
2. Whether a specific-FQDN or /32 segment exists for the host, because it removes the host from the wildcard or subnet segment for every port it does not list.
3. Whether the request appears in Private Access diagnostics at all; under Exact Match, the default, a port mismatch is not sent to the cloud, so absence there points at segment selection.
4. Whether two overlapping segments are equally granular, which no source ranks.
