# Access policy rule order (zpa.policy.access-rule-order)
Also called: rule order; ruleOrder; why does my allow rule win; block rule after allow; reorder zpa rule; zpa rule precedence; deception rule order; priority vs rule_order

Access policy rules are evaluated by their order number, and the first matching rule decides.

**The order number.** The Rule Order of an access policy rule is its policy evaluation order number; Private Access applies rules in the order listed, and the number can be changed by entering a new value. [zpa.policy.access-rule-order:rule-order-is-evaluation-number] A rule carries a `priority` field alongside `ruleOrder` in the API document, the Python model and the Terraform schema; the Terraform schema types `priority` as a string and the API document as an int32 integer. [zpa.policy.access-rule-order:priority-field-exists] What priority does is open [gap:zpa.policy.access-rule-order:priority-meaning].

**Changing the order in place.** An access policy rule's place in the Rule Order can be changed by manually entering a new value on the Access Policy page, without opening the Edit Rule window. [zpa.policy.access-rule-order:inline-rule-order-access] On the page for editing access policy global rules and policy groups, a rule's Rule Order can be changed by entering a new value on the Global Rules or Policy Groups page; the page carries a banner that global rules and policy groups ("This feature") are in limited availability, with contact Zscaler Support to learn more. [zpa.policy.access-rule-order:global-rules-limited-availability] Whether global rules and policy groups are in limited availability is in [Global rules and policy groups for access policy are in limited availability, and the pages say to contact Zscaler Support to learn more.](kb:zpa.policy.policy-groups:limited-availability). Rule Order can be changed by entering a new value on the policy's own page, without opening the rule editor, for client forwarding, isolation and Browser Protection policy rules, and for the consoles policy and privileged credentials policy (Privileged Credentials Policy page). [zpa.policy.access-rule-order:inline-rule-order-other-policies] For redirection policy rules the Rule Order can be changed by entering a new value on the Redirection Policy page, except that redirection policy rules managed by Zscaler are read only; for VPN access policy rules, by clicking the value in the Rule Order column. [zpa.policy.access-rule-order:inline-rule-order-redirection-vpn] Zscaler-managed redirection rules are read only [Redirection policy rules that are managed by Zscaler are read only and cannot be configured, edited, or deleted.](kb:zpa.policy.redirection-rules:managed-read-only). [zpa.policy.access-rule-order:deception-order-constraint]

**Extranet in the editor.** Extranet Resource options appear in the access policy Edit Rule window only if the Extranet feature is enabled in the organization. [zpa.policy.access-rule-order:extranet-edit-option]

**Shadowed rules.** If an allow-any rule is listed above a rule that blocks the Sales group, Sales users match the first rule and are not blocked; moving the block rule above the allow rule resolves it. [zpa.policy.access-rule-order:allow-first-shadows-block] An allow rule for all applications for Marketing, listed above a rule denying Marketing the Operations Apps segment group, leaves Marketing with access to that group, because Private Access stops at the first matching rule. [zpa.policy.access-rule-order:segment-group-allow-shadows-deny] A block rule for specific users must be listed before an allow rule that also covers them, because policy rules are enforced in the order listed. [zpa.policy.access-rule-order:block-before-allow]

**Deception rules.** The rule order of an access policy configured using Zscaler Deception cannot be updated, and a regular access policy's rule order must be greater than that of a Deception-configured policy; copy, edit and delete are unavailable on Deception-configured rules. [zpa.policy.access-rule-order:deception-order-constraint] The reason for the constraint is not in a captured source [gap:zpa.policy.access-rule-order:deception-rule-ordering-rationale].

**Reordering by API.** The Go SDK's policysetcontrollerv2 package has two reorder calls: `Reorder`, which moves one rule with a PUT to `.../rule/{ruleId}/reorder/{newOrder}`, and `BulkReorder`, which takes a map of rule ID to order and PUTs to the policy set's `reorder` endpoint. [zpa.policy.access-rule-order:go-reorder-calls] The Python SDK has `reorder_rule(policy_type, rule_id, rule_order)`, which PUTs to `.../rule/{rule_id}/reorder/{rule_order}` for the access, timeout, client forwarding, isolation, inspection, redirection, credential, capabilities and siem policy types. [zpa.policy.access-rule-order:python-reorder-rule] In the Terraform provider the `rule_order` argument is deprecated on all ZPA access policy resources in favour of the `zpa_policy_access_rule_reorder` resource. [zpa.policy.access-rule-order:tf-rule-order-deprecated] The MCP server's forwarding and timeout rule skills state that new rules are appended at the end of the policy by default. [zpa.policy.access-rule-order:new-rules-appended] The order type differs between sources [divergence:zpa.policy.access-rule-order:rule-order-type-wire].

**Gapped numbers.** What the API does with absent slots is not established [gap:zpa.policy.access-rule-order:gap-slot-reordering]. What the provider does with gapped numbers and the Deception offset is in [How the ZPA Terraform provider applies policy rule order (BulkReorder)](kb:zpa.terraform.rule-order).

How the layouts are used is in [Common ZPA access rule patterns and their ordering](kb:zpa.policy.patterns).

What to check:
1. List the rules in order and find the first one whose criteria match the request; rules after it never run.
2. If a block rule seems ignored, check whether an allow rule that also matches the user sits above it.
3. If a Deception-configured rule exists, check that regular rules are ordered after it and that it has not been edited.
4. Before reordering by API, check which call is used and what it sends; the effect on the rest of the list is in the Terraform subjects.
5. Compare the rule's ruleOrder and priority values and the type each client uses for them.

Sources disagree (name both sides):
- The OpenAPI document gives ruleOrder and priority as integers, while the Go SDK and Terraform schema use strings. [divergence:zpa.policy.access-rule-order:rule-order-type-wire]
  - api-specs: ruleOrder is an int32 integer in the v2 rule request.
  - sdk-go: The Go SDK sends ruleOrder as a string.
  Impact: A client that writes the order as a number may not match what the Go SDK, the Python SDK and the provider send, and a reader comparing exports to the specification sees two types for the same field.

Not known (open gaps):
- Why Deception rules must evaluate before regular access rules [gap:zpa.policy.access-rule-order:deception-rule-ordering-rationale]: settled by support-ticket
- Whether the API fills absent rule_order slots, so gapped numbers reorder unpredictably [gap:zpa.policy.access-rule-order:gap-slot-reordering]: settled by lab-test
- What the priority field on a rule does [gap:zpa.policy.access-rule-order:priority-meaning]: settled by lab-test or support-ticket
