# Reference Terraform modules for App Connectors on GCP (zpa.app-connectors.gcp-reference-modules)
Also called: terraform gcp app connector module; gcp app connector managed instance group; gcp app connector autoscaler; zsac gcp; acvm_instance_type; terraform-gcp-zpa-app-connector-modules; gcp app connector mig; module defaults app connector gcp

The GCP reference modules deploy App Connector VMs as zonal managed instance groups behind a Cloud NAT and create the ZPA App Connector Group and Provisioning Key. They are the GCP counterpart of the AWS and Azure modules described in [App Connector deployment, redundancy and limits](kb:zpa.app-connectors.deployment).

**Prerequisites.** As of module version 1.1.0 the GCP App Connector module deploys all App Connectors on Red Hat Enterprise Linux 9. [zpa.app-connectors.gcp-reference-modules:rhel9-since-1-1-0] The README lists the Google provider v7.31.x, random v3.8.x, local v2.8.x, null v3.2.x, tls v4.2.x and the ZPA provider v4.4.x, with Terraform v1.1.9 and any Terraform version 0.13.7 generally supported. [zpa.app-connectors.gcp-reference-modules:provider-versions] The examples need a GCP project with billing enabled and the compute.googleapis.com, iam.googleapis.com and cloudresourcemanager.googleapis.com APIs enabled; authentication is Application Default Credentials (recommended) or a service account keyfile with at least roles/compute.admin and roles/iam.serviceAccountUser. [zpa.app-connectors.gcp-reference-modules:gcp-prereqs] The module authenticates the ZPA provider through OneAPI (OAuth2 via Zidentity), which the README recommends for new deployments; the provider keeps the legacy ZPA API framework for tenants not yet migrated, and OneAPI and Zidentity are not supported in the GOV and GOVUS clouds. [zpa.app-connectors.gcp-reference-modules:oneapi-auth] The examples/zsac wrapper script supports ZPA provider authentication through OneAPI/Zidentity (ZSCALER_CLIENT_ID, ZSCALER_CLIENT_SECRET, ZSCALER_VANITY_DOMAIN) or the legacy ZPA framework (ZPA_CLIENT_ID, ZPA_CLIENT_SECRET, ZPA_CUSTOMER_ID, ZPA_CLOUD with ZSCALER_USE_LEGACY_CLIENT=true), the latter for tenants still on the legacy framework or GOV/GOVUS. [zpa.app-connectors.gcp-reference-modules:wrapper-auth]

**Examples.** The GCP module ships four examples: base_ac and base_ac_asg (greenfield, with a Management VPC, Cloud Router, NAT and a bastion host) and ac and ac_asg (brownfield, no bastion, every network primitive reusable through byo_* variables); the base_ac and ac examples run a fixed ac_count per zone and the _asg examples add a Compute Autoscaler per zone. [zpa.app-connectors.gcp-reference-modules:example-types] The examples validate name_prefix to 12 or fewer characters matching ^[a-z][a-z0-9-]+$, with default zsac. [zpa.app-connectors.gcp-reference-modules:name-prefix] [divergence:zpa.app-connectors.gcp-reference-modules:wrapper-script-name]

**VMs.** The GCP App Connector VM module defaults acvm_instance_type to n2-standard-4 and validates it against n2-standard-4, n2-highcpu-4, n1-standard-4, n1-highcpu-4, n2-standard-8, n2-highcpu-8, n1-standard-8 and n1-highcpu-8. [zpa.app-connectors.gcp-reference-modules:vm-size] Each App Connector instance template boots from a pd-balanced boot disk whose size defaults to 64 GB, with automatic_restart true and on_host_maintenance MIGRATE. [zpa.app-connectors.gcp-reference-modules:vm-template] The fixed-size module creates one zonal managed instance group per zone, each with target_size equal to ac_count (default 1), so total connectors are ac_count times the number of zones. [zpa.app-connectors.gcp-reference-modules:fixed-mig-layout] The examples create zonal groups in the first az_count available zones of the region (az_count defaults to 1 and is validated between 1 and 3), or in the distinct zones listed in the zones variable when it is non-empty. [zpa.app-connectors.gcp-reference-modules:zones-az-count] The MIG update policy defaults to type OPPORTUNISTIC, replacement method SUBSTITUTE, maximum surge 1 and maximum unavailable 1, with minimal and most-disruptive action REPLACE; per the variable description OPPORTUNISTIC means no action is proactively executed and an update happens as part of other actions such as resizes or recreateInstances calls. [zpa.app-connectors.gcp-reference-modules:update-policy]

**Image and bootstrap.** The examples look up a specific named image, zpa-connector-el9-2025-11, in the Google Marketplace project mpi-zpa-gcp-marketplace when use_zscaler_image is true (the default), although the image_name variable description says templates always pull the latest from Google Marketplace. [zpa.app-connectors.gcp-reference-modules:image-pinned] With use_zscaler_image false the examples use the latest rhel-9 family image from the rhel-cloud project and a startup script that writes the Zscaler yum repository https://yum.private.zscaler.com/yum/el9 and installs zpa-connector. [zpa.app-connectors.gcp-reference-modules:image-rhel9-fallback] The startup scripts in all four examples (ac, ac_asg, base_ac and base_ac_asg, in both their appuserdata and RHEL9 user data) stop the zpa-connector service, write the Terraform-managed provisioning key to /opt/zscaler/var/provision_key, run yum update -y, start zpa-connector, sleep 60 and restart it. [zpa.app-connectors.gcp-reference-modules:bootstrap-provision-key] The GCP App Connector group module declares user_codes (default an empty list), described as OAuth2 user codes retrieved from the deployed VMs' /etc/issue for enrolling with the OAuth2 method, and passes them to the zpa_app_connector_group resource. [zpa.app-connectors.gcp-reference-modules:group-user-codes] How the user codes are collected is open [gap:zpa.app-connectors.gcp-reference-modules:oauth-flow-on-gcp]; see [App Connector enrollment, certificates and re-enrollment](kb:zpa.app-connectors.enrollment).

**Autoscaling.** The autoscaling module defaults min_size to 2 and max_size to 4, both per zone, with target_cpu_util_value 50, cooldown_period 60 seconds and health_check_grace_period 300 seconds. [zpa.app-connectors.gcp-reference-modules:asg-defaults] The autoscaling module accepts target_tracking_metric ASGAverageCPUUtilization (the default and the recommended one), ASGAverageNetworkIn or ASGAverageNetworkOut; the CPU target is a percentage divided by 100 internally, and for the network metrics the same target_cpu_util_value is read as bytes per second per instance. [zpa.app-connectors.gcp-reference-modules:asg-metrics] Autoscaling-group autohealing uses a TCP health check on port 22 (timeout 5 seconds, interval 10 seconds, healthy threshold 2, unhealthy threshold 3) with initial_delay_sec equal to health_check_grace_period, because the module's comment says the App Connector listens on no externally-routable port. [zpa.app-connectors.gcp-reference-modules:asg-health-check] In the autoscaling module the autoscaler owns the group size: target_size is left unset on each MIG and ignored in lifecycle changes so Terraform does not fight the autoscaler, and one MIG is created per zone with one autoscaler per MIG. [zpa.app-connectors.gcp-reference-modules:asg-owns-size]

**ZPA objects.** The group module hardcodes the enrollment certificate lookup to the name Connector and pins version_profile_id to the id of the customer version profile named Default, neither exposed as a variable. [zpa.app-connectors.gcp-reference-modules:group-fixed-lookups] The GCP group module defaults upgrade_day to SUNDAY, upgrade_time_in_secs to 66600 (a string, valid from 0 to under 86400 in 15 minute intervals) and dns_query_type to IPV4_IPV6, validated against IPV4_IPV6, IPV4 and IPV6. [zpa.app-connectors.gcp-reference-modules:group-defaults] [divergence:zpa.app-connectors.gcp-reference-modules:override-version-profile-default] The provisioning key module hardcodes the Connector enrollment certificate, accepts only association type CONNECTOR_GRP, binds the key to the group through zcomponent_id, and with byo_provisioning_key true creates no key and only references an existing one by name. [zpa.app-connectors.gcp-reference-modules:key-module] The provisioning key max_usage defaults to 10 in the fixed examples and 100 in the autoscaling examples; each App Connector consumes one slot at enrollment and instance churn (image upgrades, scale-in and scale-out, MIG replacements) consumes more, and when the key runs out new VMs come up healthy at the OS level but show as disconnected in the ZPA portal. [zpa.app-connectors.gcp-reference-modules:key-max-usage]

**Network.** The network module creates a custom-mode VPC (auto_create_subnetworks false, routing_mode REGIONAL by default), one App Connector subnet, a Cloud Router and a Cloud NAT gateway with AUTO_ONLY address allocation for all subnetworks and ERRORS_ONLY logging; each of VPC, subnet, router and NAT can instead be referenced with byo_* variables. [zpa.app-connectors.gcp-reference-modules:network-resources] The module's management firewall allows tcp on allowed_ports (an empty default list means all ports) and icmp (icmpv6 in the IPv6 rule) only from allowed_ssh_from_internal_cidr, split into an IPv4 rule and an IPv6 rule because GCP firewall rules cannot mix address families; all four examples set that source list to `[var.subnet_bastion]`, which the ac, base_ac and base_ac_asg examples describe as the subnet CIDR for the greenfield/test bastion host and the ac_asg example as an SSH allow-list reference (it creates no bastion). [zpa.app-connectors.gcp-reference-modules:network-firewall] In the greenfield examples (base_ac and base_ac_asg) the bastion host gets an ephemeral public IP and firewall rules allowing tcp/22 from bastion_ssh_allow_ip (IPv4 and IPv6 ranges in separate rules), which defaults to 0.0.0.0/0. [zpa.app-connectors.gcp-reference-modules:bastion-open]

**Teardown.** Destroying an example removes the App Connectors and also the ZPA App Connector Group and Provisioning Key; access policies that reference the group must be detached first or the destroy fails on the ZPA side. [zpa.app-connectors.gcp-reference-modules:destroy-removes-zpa]

What to check:
1. Which VM size and disk the module deploys.
2. Whether the deployment is fixed-size or autoscaling and what the min and max apply to (per zone).
3. Whether the provisioning key max_usage leaves headroom for scale-out and replacement.
4. What the autohealing health check actually probes.
5. Which version profile the module-created group ends up with.

Sources disagree (name both sides):
- What the interactive wrapper script is called. [divergence:zpa.app-connectors.gcp-reference-modules:wrapper-script-name]
  - tfmod-gcp-zpa-app-connector: The README calls the wrapper zsac.
  - tfmod-gcp-zpa-app-connector: The examples README documents it as zsec, with a .zsecrc cache.
  - tfmod-gcp-zpa-app-connector: The script file itself is examples/zsac, with the usage line ./zsac and a .zsacrc cache.
  Impact: Commands copied from the examples README (./zsec up, ./zsec destroy, deleting .zsecrc) do not match the script that ships; use ./zsac and .zsacrc.
- Whether the group module overrides the version profile by default. [divergence:zpa.app-connectors.gcp-reference-modules:override-version-profile-default]
  - tfmod-gcp-zpa-app-connector: The variable description says the default is false.
  - tfmod-gcp-zpa-app-connector: The variable default is true.
  Impact: A group created with the module defaults has override_version_profile true and a version_profile_id pinned to the profile named Default, not the false the description implies; confirm the group in the ZPA Admin Portal before assuming it follows the tenant default.
