# PRA application segments: protocols, ports, connection security and constraints (zpa.pra.app-segments)
Also called: pra application segment; zpa_application_segment_pra; connection_security; NLA_EXT; VM_CONNECT; SECURE_REMOTE_ACCESS; pra rdp connection security; realvnc terraform; pra multimatch; pra application protocol

A PRA application is a protocol and port on a segment, and the segment is a PRA-enabled variant. This subject holds what the help and the Terraform resource say about that configuration.

**Application settings.** Privileged Remote Access allows temporary remote access to specific applications with Private Access, including for contractors and third-party users. Privileged portals and privileged consoles must be set up first. [zpa.pra.app-segments:pra-purpose-and-prereq] Enabling Privileged Remote Access for an application means choosing a protocol (VNC, RealVNC, SSH or RDP) and a port; the defaults are 5900 for VNC and RealVNC, 3389 for RDP and 22 for SSH. [zpa.pra.app-segments:enable-and-defaults] The Privileged Applications page lists the applications specifically configured for PRA within an application segment, with each application's Domain (FQDN), Application Protocol (VNC, RealVNC, SSH or RDP), Application Port, Segment Group and Server Groups. [zpa.pra.app-segments:privileged-applications-page] For an RDP application the Connection Security options are Any, TLS, RDP and NLA. Any is for Windows 10, 11 and Server 2016 or later and uses the strongest mutually supported protocol including NLA, while RDP is for Windows Server 2012 R2 and earlier or Windows 7 and 8.x, which do not support TLS, NLA or Any. If the application server has network-level authentication enabled, select Any to provide access to the server. [zpa.pra.app-segments:connection-security-help] The extra ports for VNC and RealVNC file transfer also differ [divergence:zpa.pra.app-segments:vnc-file-transfer-ports].

**Terraform and API.** In the Terraform PRA segment resource, each app's application_protocol is validated against RDP, SSH and VNC, and connection_security against ANY, NLA, NLA_EXT, TLS, VM_CONNECT and RDP. [zpa.pra.app-segments:tf-protocol-enum] When it updates a segment, the Terraform PRA segment resource sets app_types to SECURE_REMOTE_ACCESS on each configured PRA app whose app_types is empty, and it sets app_types to SECURE_REMOTE_ACCESS on every PRA app it reads back into state. [zpa.pra.app-segments:tf-app-types-forced] The help and the resource disagree on RealVNC [divergence:zpa.pra.app-segments:realvnc-validation].

**Constraints.** Whether Source IP Anchoring is allowed on a PRA segment is open [gap:zpa.pra.app-segments:sipa-on-pra]. The Multimatch restriction, where two captures disagree about PRA, is in [Multimatch prerequisites, restrictions and App Connector selection](kb:zpa.app-segments.multimatch-requirements). A PRA application that matches a valid client hostname for peer-to-peer connectivity is covered in [Privileged Remote Access is not supported when an application configured for PRA matches a valid client hostname configured for peer-to-peer connectivity and the user's device is also configured for peer-to-peer connectivity.](kb:zpa.peer-to-peer:pra-conflict).

Other settings blocked by Browser Access are in [Browser Access applications on a segment: per-application keys and where the constraints live](kb:zpa.browser-access.segment-constraints). VNC file transfer needs SSH on port 22, covered in [PRA consoles policy: file transfer, clipboard, recording and sharing](kb:zpa.pra.consoles-policy). Update behavior of nested PRA apps in Terraform is in [What the ZPA Terraform provider sends, keeps and cleans up for application segments and their associations](kb:zpa.terraform.app-segment-lifecycle).

The contract lists the protocol values a PRA application can carry: The OpenAPI document gives PRA application `applicationProtocol` fourteen values: HTTP, HTTPS, FTP, RDP, SSH, WEBSOCKET, VNC, REALVNC, NONE, AUTO, DYNAMIC, KRB, LDAP and SMB. [zpa.pra.app-segments:contract-application-protocol-enum]

What to check:
1. Whether the RDP connection security matches the Windows version of the target.
2. Which ports a VNC or RealVNC application with file transfer carries, since the captures differ.
3. Whether Terraform input uses only RDP, SSH or VNC and a connection_security value in the validated list, and whether the application is RealVNC.
4. Whether a Source IP Anchoring question rests on the unverified exclusivity statement.

Sources disagree (name both sides):
- The extra ports needed for VNC or RealVNC file transfer: port 22 on both TCP and UDP, or TCP port 22 for SFTP [divergence:zpa.pra.app-segments:vnc-file-transfer-ports]
  - zscaler-help: Additionally enter TCP port 22, used for SFTP file transfer.
  - zscaler-help: Additionally enter port 22 for both the TCP and UDP port ranges.
  Impact: One page asks for port 22 on TCP only and names SFTP; the other asks for port 22 in both the TCP and UDP port ranges. Whether UDP port 22 is needed is not settled by either page.
- Whether RealVNC is a PRA application protocol [divergence:zpa.pra.app-segments:realvnc-validation]
  - zscaler-help: The help lists RealVNC next to VNC, SSH and RDP as a protocol for a PRA application and privileged console.
  - tf-zpa: The Terraform PRA segment resource validates application_protocol against RDP, SSH and VNC only.
  Impact: A RealVNC application configured in the console cannot be expressed through this Terraform resource as written, and a plan that reads one back may not validate. Check the provider version and the resource schema before importing RealVNC applications.

Not known (open gaps):
- Source IP Anchoring on a PRA segment [gap:zpa.pra.app-segments:sipa-on-pra]: settled by lab-test or source-read
