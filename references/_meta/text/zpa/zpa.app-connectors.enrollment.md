# App Connector enrollment, certificates and re-enrollment (zpa.app-connectors.enrollment)
Also called: app connector enrollment; connector will not enroll; oauth user code enrollment; enrollment certificate; connector certificate; app connector allow list; re-enroll app connector; delete app connector re-enroll; clone app connector vm

How an App Connector gets its identity: the two enrollment methods, the certificate it receives, and what blocks or repeats enrollment.

**Methods.** An App Connector is enrolled with either an OAuth 2.0 enrollment token or a provisioning key; the help calls OAuth tokens preferred. [zpa.app-connectors.enrollment:two-methods] OAuth-enabled App Connectors are added with a name of the form GroupName-UserCode-TimeStamp. [zpa.app-connectors.enrollment:oauth-name-format] The ZPA Ansible App Connector Group module takes OAuth user codes generated from deployed App Connector VMs and verifies them after create or update. [zpa.app-connectors.enrollment:groups-accept-user-codes] Both reference modules' base_ac examples take onboarding_method as oauth (the default) or provisioning_key. With oauth, AWS connectors publish their user code to SSM Parameter Store using the instance role, and Azure connectors publish to a Key Vault secret using the VM's user-assigned managed identity; Terraform reads the codes back to create the group. [zpa.app-connectors.enrollment:module-onboarding-default] The AWS module README says both methods are selectable per deployment through onboarding_method and that you can switch between them per deployment (not a one-way migration at the module level), but that switching on an existing App Connector Group typically requires re-deploying the connectors. [zpa.app-connectors.enrollment:module-onboarding-switch] The App Connector AWS guide says the image attempts to use OAuth enrollment tokens by default but applies a provisioning key first if one is available; the OAuth token appears after a login prompt in the virtual serial console, tokens are valid for 2 hours, and the token is entered on the Add App Connectors page. [zpa.app-connectors.enrollment:oauth-image-default] The App Connector AWS guide says a provisioning key file is created with 644 permissions at /opt/zscaler/var/provision_key, and that if the key is not detected when the App Connector first starts it is in a sleep cycle and looks for the key again every 24 hours. [zpa.app-connectors.enrollment:key-file-and-sleep] The App Connector AWS guide says the domain in the provisioning key echo statement (its example is api.private.com) depends on which Private Access cloud the tenant is on. [zpa.app-connectors.enrollment:key-cloud-domain] The App Connector Nutanix AHV guide says SSH is not enabled by default on Zscaler-provided virtual appliances and is required for a short time to configure the provisioning key, that after the initial boot it might take up to 15 minutes for the admin credentials to apply, and that SSH is to be disabled after the App Connector is enrolled. [zpa.app-connectors.enrollment:ssh-for-key] The Configuring App Connectors page says OAuth enrollment is available for supported Zscaler VM images, and that the Add App Connectors page takes an App Connector group, the group's signing certificate (shown if one is associated, otherwise selected) and up to 20 OAuth 2.0 enrollment tokens copied from the App Connector virtual serial console, valid for 2 hours. [zpa.app-connectors.enrollment:add-page-oauth] When an App Connector is provisioned, the provisioning key's name is assigned as a prefix of the name of each App Connector enrolled with it, followed by a number marking it as the nth connector enrolled with the key. A rename should keep the prefix and number, as in the page's example Amazon EC2 AMI-based connectors key - Oregon-1. [zpa.app-connectors.enrollment:key-name-prefix] Provisioning keys are covered in [App Connector provisioning keys](kb:zpa.app-connectors.provisioning-keys). The enrollment certificates themselves are in [Enrollment (CA) certificates in Private Access](kb:zpa.certificates.enrollment), and the OAuth rules shared by all software components are in [OAuth 2.0 enrollment for ZPA software components and its troubleshooting](kb:zpa.software-components.oauth-enrollment).

**Certificate and trust.** During enrollment the App Connector and Zscaler verify each other using a provisioning key and a corresponding TLS client certificate. [zpa.app-connectors.enrollment:mutual-verification] Private Access accepts App Connector connections only when the client certificate is signed by a CA associated with the tenant. [zpa.app-connectors.enrollment:cert-signed-by-tenant-ca] An App Connector group selects the Signing Certificate that Private Access uses to sign the certificates it issues to its App Connectors. [zpa.app-connectors.enrollment:signing-cert-on-group] Private keys for certificates used in the Private Access infrastructure, including organization-operated systems, never leave the physical device where they were generated. [zpa.app-connectors.enrollment:private-keys-stay-on-device] All Zscaler certificates are signed through an offline-only, air-gapped, signing ceremony. [zpa.app-connectors.enrollment:offline-signing] The certificate lifetime and renewal are open [gap:zpa.app-connectors.enrollment:certificate-validity-window].

**Restricting enrollment.** The App Connector Allow List (limited availability) restricts enrollment to the listed IP address or subnet: enrollment stays pending for an address not on the list, and a DHCP or network change of the address makes the group fail to enroll. [zpa.app-connectors.enrollment:allow-list]

**Replacing and re-enrolling.** A deployed App Connector is replaced by deleting the App Connector and re-enrolling it; when a provisioning key is used, the new provisioning key can be applied to the already-deployed VM image in place of the old key. [zpa.app-connectors.enrollment:replace-by-reenroll] A connector deleted from the Admin Console, even accidentally, is cut off immediately and cannot be recovered; the deployed instance's local state must be removed and the connector enrolled again. [zpa.app-connectors.enrollment:deleted-connector-unrecoverable] Re-enrolling a stuck connector with a provisioning key means wiping the connector's local state, writing the key to /opt/zscaler/var/provision_key, and starting the service; the key's enrolled count must first be below its maximum. [zpa.app-connectors.enrollment:wipe-and-rebuild] An AWS connector provisioned in an IMDSv2-required environment on version 24.566.1 or earlier creates a new App Connector on re-enrollment because its hardware fingerprint changed (IMDSv2 support arrived in 24.650.1); Zscaler recommends deleting the original manually to avoid consuming provisioning key uses. [zpa.app-connectors.enrollment:imdsv2-reenroll-creates-new] A first-installed connector generates a local private key encrypted with a hardware fingerprint, creates a CSR, authenticates it to the cloud with the provisioning key, and receives a signed TLS client certificate that is pinned to the connector's hardware fingerprint. [zpa.app-connectors.enrollment:csr-and-fingerprint] An enrolled connector is paired with a single customer account and cannot be enrolled again; connectors in VMs should never be cloned because the keys no longer match the virtual hardware fingerprints. [zpa.app-connectors.enrollment:single-account-never-clone] What happens to clones that were made anyway is unsourced [gap:zpa.app-connectors.enrollment:vm-clone-fingerprint].

**When a new connector will not enroll.** When bringing up a new App Connector fails, the help says to check that the primary domain name length is less than 36 characters (longer names can cause problems forming a certificate), that the zscaler user can read /etc/resolv.conf, and that the zscaler user can write /opt/zscaler/var. [zpa.app-connectors.enrollment:new-connector-prechecks] If the connector's clock does not match the Private Access back-end, the certificate can be not yet valid, delaying enrollment; the fix is a correct, maintained time on the connector. [zpa.app-connectors.enrollment:clock-skew-delays-cert]

Terraform and SDK behavior around `enrollment_cert_id` and `user_codes` is in [App Connector groups](kb:zpa.app-connectors.connector-groups) and [ZPA Terraform resources: fields not sent, not read back, or written in several non-atomic steps](kb:zpa.terraform.resource-fidelity).

What to check:
1. Whether the connector was enrolled with a provisioning key or an OAuth token, since the failure checks differ.
2. The connector's clock, domain name length and the zscaler user's file permissions before suspecting the key.
3. Whether an Allow List restricts enrollment to addresses that no longer match the connector.
4. Whether a re-enrollment created a second connector that now consumes a key use and counts toward the tenant limit.
