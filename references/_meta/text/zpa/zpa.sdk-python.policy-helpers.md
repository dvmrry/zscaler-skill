# Python SDK policy rule helpers: policy types, write lock, condition tuples and rule builders (zpa.sdk-python.policy-helpers)
Also called: global_rule_lock; policy conditions tuple python; conditions silently ignored python; _create_conditions_v1; _create_conditions_v2; get_rule two requests; policy type map python; add_app_protection_rule lock; POLICY_MAP; portal_policy user_portal policy type; vpn_policy; PRIVILEGED_PORTAL_POLICY; get_policy policy_type values; policy rule concurrent writes python; synchronized decorator zpa; threading lock policy rules

These are claims about the Python SDK's policy rule helpers. Rule ordering semantics are in [How the ZPA Terraform provider applies policy rule order (BulkReorder)](kb:zpa.terraform.rule-order), and the wire shapes are in [ZPA policy rule wire behavior: routes, request fields and ordering](kb:zpa.api.policy-wire).

**Policy types.** The map of friendly names to policy types is [The Python SDK maps friendly names to policy types, including `PRIVILEGED_PORTAL_POLICY`, `VPN_TUNNEL_POLICY` and `USER_PORTAL`. The OpenAPI policy-type parameter lists `PRIVILEGED_PORTAL_POLICY` and the other ten types of the Go edge-case test, but neither `VPN_TUNNEL_POLICY` nor `USER_PORTAL`.](kb:zpa.api.policy-wire:python-policy-type-map). `get_policy` and `list_rules` look the type up in `POLICY_MAP` without further filtering, and `delete_rule` resolves its policy set through `get_policy(policy_type, ...)`. [zpa.sdk-python.policy-helpers:generic-calls-use-map] The Python policy_type argument of list_rules is a lowercase alias looked up in the SDK's policy map, and a wire value such as ACCESS_POLICY raises ValueError('Incorrect policy type provided'); list_rules returns PolicySetControllerV1 objects. [zpa.sdk-python.policy-helpers:python-list-rules-alias-required] The Python get_policy_rule_count accepts a policy type already in wire form, because it checks the values of the policy map before looking up an alias. [zpa.sdk-python.policy-helpers:python-count-accepts-wire-values] Several add and update rule methods resolve their policy set with a fixed type: `add_access_rule` and `update_access_rule` with `get_policy("access", ...)`, `add_timeout_rule` and `update_timeout_rule` with `get_policy("timeout", ...)`, and `update_app_protection_rule` with `get_policy("inspection")`. [zpa.sdk-python.policy-helpers:fixed-type-writes] An unknown key raises, see [Where ZPA Python SDK wrappers raise and where they return errors](kb:zpa.sdk-python.error-handling). Whether portal writes work is open [gap:zpa.sdk-python.policy-helpers:portal-rule-writes].

**Write lock.** `policies.py` defines one module-level `Lock()` named `global_rule_lock`, and a `synchronized` decorator that runs a function inside `with lock:`. [zpa.sdk-python.policy-helpers:lock-object] The decorator is applied to the v1 method `add_access_rule` and to the v2 methods `update_access_rule_v2` and `add_browser_protection_rule_v2`. [zpa.sdk-python.policy-helpers:lock-add-update] The same decorator is applied to `delete_rule`, `reorder_rule` and `bulk_reorder_rules`. [zpa.sdk-python.policy-helpers:lock-delete-reorder] The lock serializes threads of one Python process only. [zpa.sdk-python.policy-helpers:lock-process-local] The v1 `add_app_protection_rule` has no lock decorator, although the other add and update helpers do. [zpa.sdk-python.policy-helpers:rule-lock-gaps]

**Condition tuples.** The v1 condition builder accepts a tuple of three elements (object type, lhs, rhs), optionally wrapped as ("AND" or "OR", tuple), and a dictionary with id, negated, operator and operands; operands of the same object type are grouped into one block with that type's operator, defaulting to OR. [zpa.sdk-python.policy-helpers:v1-conditions-forms] A v1 condition that is neither a three-element tuple nor a dictionary is skipped without an error: for example the two-element form ("client_type", [...]) used by the v2 builder, or a condition given as a list, as conditions loaded from JSON are, whether a three-element list or one wrapped with "AND" or "OR". [zpa.sdk-python.policy-helpers:v1-conditions-dropped] The changelog says lists are now accepted [divergence:zpa.sdk-python.policy-helpers:v1-list-conditions]. The v2 condition builder reads a tuple as the object type (lower-cased) followed by its values; since v1.11.1 it reads a list the same way, where up to v1.10.0 it accepted only tuples and a list-shaped condition was dropped (#583). It puts app and app_group values in one block, puts console, location, machine_grp, client_type and user_portal each in their own block with the operator, and turns posture, trusted_network, country_code, platform, risk_factor_type, saml, scim and scim_group lists of (lhs, rhs) pairs into entryValues. [zpa.sdk-python.policy-helpers:v2-conditions-forms] The Python SDK's v2 condition builder emits `entryValues` (pairs of `lhs` and `rhs`) for the object types posture, trusted_network, country_code, platform, risk_factor_type, saml, scim, scim_group and chrome_enterprise, and a `values` list for every other type. Its v1 builder emits flat `{objectType, lhs, rhs}` operands. [zpa.sdk-python.policy-helpers:python-v2-operand-forms] `add_access_rule` builds its conditions with the v1 builder. [zpa.sdk-python.policy-helpers:access-rule-v1-uses-v1]

**Rule builders.** The Python credential rule builder first fetches the credential policy set with a GET through `get_policy`; then, before sending the rule, it refuses when both or neither of `credential_id` and `credential_pool_id` are given, returning the message as a string in the error slot rather than raising. It sends the id as `credential` or as `credentialPool`. [zpa.sdk-python.policy-helpers:python-credential-exclusive] If an isolation rule or a v2 browser protection rule built by the Python SDK has no `CLIENT_TYPE` condition, the builder appends an OR condition for `zpn_client_type_exporter` (flat lhs/rhs in v1, a `values` list in v2) and goes straight on to build the request. The Go SDK's `CreateRule` and `UpdateRule`, in both policy packages, add no condition. [zpa.sdk-python.policy-helpers:python-isolation-client-type] The Python capability rule builder turns its flags into the strings CLIPBOARD_COPY, CLIPBOARD_PASTE, FILE_DOWNLOAD, FILE_UPLOAD, INSPECT_FILE_UPLOAD, INSPECT_FILE_DOWNLOAD, MONITOR_SESSION, RECORD_SESSION and SHARE_SESSION, and maps `file_upload=False` to INSPECT_FILE_UPLOAD (not to nothing), while `file_upload=True` gives FILE_UPLOAD. The OpenAPI document types `capabilities` as a free list of strings, and the Go SDK tests exercise five of the values. [zpa.sdk-python.policy-helpers:python-capabilities-mapping] The Python redirection rule builder rejects `redirect_default` when `service_edge_group_ids` is given, requires `service_edge_group_ids` for `redirect_preferred` and `redirect_always`, checks the first value of each `CLIENT_TYPE` operand, and only the first, against five client types, and rejects the branch and edge connector client types when the action is `redirect_always`. The OpenAPI document lists REDIRECT_DEFAULT, REDIRECT_PREFERRED and REDIRECT_ALWAYS as actions. [zpa.sdk-python.policy-helpers:python-redirection-rules] The Python `add_timeout_rule_v2` and `update_timeout_rule_v2` send `reauthTimeout` 172800 and `reauthIdleTimeout` 600 when the caller does not pass them. [zpa.sdk-python.policy-helpers:python-timeout-defaults] So an update through `update_timeout_rule_v2` that omits the timeouts writes those default values rather than leaving the rule's current ones. [zpa.sdk-python.policy-helpers:python-timeout-update-overwrites] The Python `reformat_params` table maps `app_connector_group_ids` to the wire key `PolicySetControllers`, but the access rule builders set `appConnectorGroups` directly from their named argument before the table is used. [zpa.sdk-python.policy-helpers:python-reformat-params-key] Python SDK issue #579 reported that the SDK's v2 timeout rule method documents an `action` keyword but hard-codes the action; it was closed as completed on 2026-10-06 with a reply from a member of the repository's organization, signed Zscaler DevRel, that the timeout policy only supports RE_AUTH so the SDK always sets it, and v1.11.1 removed `action` from the v2 timeout docstrings. [zpa.sdk-python.policy-helpers:timeout-action-fixed-re-auth] Python SDK issue #574 reported that `update_isolation_rule` and `update_isolation_rule_v2` raise AttributeError when `action` is omitted; it was closed as completed on 2026-10-06, and the v1.11.1 changelog lists the fix. [zpa.sdk-python.policy-helpers:isolation-update-action-guard] Python SDK issue #571 asked for a way to update a ZPA policy rule from the object `get_rule` returns; it was closed as completed on 2026-10-06 with a reply from a member of the repository's organization, signed Zscaler DevRel, that the `update_*_rule` methods are intentionally declarative, replace the rule with the state passed in, are not patch operations, and will not get an update-from-object variant. [zpa.sdk-python.policy-helpers:update-rules-are-full-replacements]

**Reordering.** The Python `bulk_reorder_rules` PUTs the caller's `rules_orders` list to the policy set's `reorder` endpoint unmodified: it does not look for or move `Default_Rule`, which the Go SDK's `BulkReorder` takes out and appends last. [zpa.sdk-python.policy-helpers:python-bulk-reorder-passthrough]

**Rule lookup.** `get_rule` first calls `get_policy` for the policy type to find the policy set ID and then requests the rule under that policy set, so one lookup is two requests. [zpa.sdk-python.policy-helpers:get-rule-two-calls]

What to check:
1. Whether a rule's conditions all reached the request: the v1 builder keeps only three-element tuples and dictionaries.
2. Whether a v1 App Protection rule add was serialized with the other rule writes; it is not.
3. Whether the policy type name is a key of POLICY_MAP, not the API enum name.
4. Whether a rule write for portal or user portal policy was expected from the generic delete and reorder calls.
5. Whether several processes or hosts write policy rules at the same time, since the lock does not cover them.
6. Whether concurrent threads in one process call delete or reorder, which take the same lock as add and update.

Inferred, not quoted (say so when an answer rests on one):
- [zpa.sdk-python.policy-helpers:v1-conditions-dropped] Tier B: The skip follows from the builder having no else branch after the tuple and dictionary cases, and from both the operator unwrap and the three-element case testing for a tuple; it was not run. The list case was added because the v1.11.1 changelog says conditions now accept lists while the v1 builder still does not (divergence v1-list-conditions); previously "A v1 condition that is neither a three-element tuple nor a dictionary, for example the two-element form (\"client_type\", [...]) used by the v2 builder, is skipped without an error."
- [zpa.sdk-python.policy-helpers:python-timeout-update-overwrites] Tier B: Follows from python-timeout-defaults and the update's request: update_timeout_rule_v2 puts the defaulted values in its payload and sends the payload as a PUT without reading the rule first. That the API stores the PUT body's timeouts in place of the current ones rests on the PUT replacing the rule, which the SDK maintainers describe in update-rules-are-full-replacements; no source states it for the timeout fields.
- [zpa.sdk-python.policy-helpers:lock-process-local] Tier B: Follows from the lock being a threading.Lock held in module memory. Another process, host or tool writing rules at the same time is not covered.

Sources disagree (name both sides):
- The v1.11.1 changelog says ZPA policy conditions now accept lists, but the v1 condition builder still accepts only tuples and dictionaries. [divergence:zpa.sdk-python.policy-helpers:v1-list-conditions]
  - sdk-python: The changelog says policy conditions now accept lists as well as tuples, and that list-shaped conditions were previously dropped.
  - sdk-python: `_create_conditions_v1` still tests for a three-element tuple or a dictionary, so a list-shaped condition is still dropped there; only the v2 builder accepts lists.
  Impact: A rule written through a v1 helper (add_access_rule, add_timeout_rule, add_client_forwarding_rule, add_isolation_rule, add_app_protection_rule or their update methods) with conditions loaded from JSON is sent without those conditions, and no error is returned. Convert each condition to a tuple, or use the v2 helpers.
