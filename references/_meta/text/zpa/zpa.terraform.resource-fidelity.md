# ZPA Terraform resources: fields not sent, not read back, or written in several non-atomic steps (zpa.terraform.resource-fidelity)
Also called: terraform zpa state does not match api; service edge assistant schedule destroy does nothing; assistant schedule empty id; redirection rule policy_set_id empty; private cloud fire drill follow-up; user code verification failed after create; provisioning key import fails; privileged portal capabilities lost; pra console application stale; server group name blank on update; lss config policy_rule_resource missing; zia cloud config read error ignored

Several ZPA resources do not do what their schema promises: an argument is dropped on the way out, a response field is dropped on the way back, or one logical write is split into several requests with no way back. Application segment resources have their own version of this problem in [What the ZPA Terraform provider sends, keeps and cleans up for application segments and their associations](kb:zpa.terraform.app-segment-lifecycle).

**Where refreshed state comes from.** From v4.4.13 (#694), refresh of application segments, application servers, segment groups, server groups, App Connector groups and the v1/v2 access, timeout and forwarding policy rules reads each object from one paginated list fetched per run and per microtenant, instead of one GET per object. App Connector groups read only from the list, also after create and update. For the other types the provider reads an object by ID when the list call fails or the object is not in the list, and create and update read the object back individually. [zpa.terraform.resource-fidelity:refresh-from-list-index] Whether the list responses carry every field a by-ID read did is open [gap:zpa.terraform.resource-fidelity:list-vs-get-field-parity].

**Success-shaped results.** Up to v4.4.14, the ZIA cloud config Read returned success on any error from the SDK call, without setting a diagnostic or clearing the ID. Create finishes by calling this Read, so a failure to read back what was just written also looked like success. v4.4.15 fixes this: a not-found error removes the config from state, and any other error is returned as a diagnostic. [zpa.terraform.resource-fidelity:cloud-config-read-error-is-success] The ZIA cloud config resource registers a delete function that does nothing but return success, so destroy succeeds without any API request. [zpa.terraform.resource-fidelity:cloud-config-destroy-is-noop] Destroying the Service Edge assistant schedule resource makes no API call: the delete function returns nil. Terraform drops the resource from state while the remote schedule is untouched. [zpa.terraform.resource-fidelity:schedule-delete-is-noop] The SDK's refusal to update a disabled schedule is in [Both `appconnectorschedule.UpdateSchedule` and `serviceedgeschedule.UpdateSchedule` return an error before sending anything when `assistantSchedule.Enabled` is false (`cannot update a disabled schedule`). A false value cannot be written through either update.](kb:zpa.sdk-go.service-defects:assistant-schedule-update-rejects-disabled). Up to v4.4.14, creating the Service Edge assistant schedule discarded the object the SDK returns from the POST, then stored the ID of the request as the resource ID. The request ID is read from the resource's own computed `id`. Only the already-exists branch set an ID taken from the server, by reading the singleton schedule. v4.4.15 fixes this for the Service Edge and the App Connector assistant schedules: create stores the ID of the schedule the POST returned (`created.ID`). [zpa.terraform.resource-fidelity:schedule-create-discards-server-id] Up to v4.4.14, on a first create the resource's computed `id` was still empty, so the first-create path set an empty ID, which probably made Terraform report an inconsistent result rather than record the resource. v4.4.15 sets the ID the POST returned instead. [zpa.terraform.resource-fidelity:schedule-create-empty-id] The schedule resource accepts any ID on import (passthrough importer), and its Read fetches the singleton schedule but never writes the singleton's ID back. Update then builds the PUT path from `d.Id()`. [zpa.terraform.resource-fidelity:schedule-read-never-sets-id] The App Connector and Service Edge assistant schedule SDK packages each define an `AssistantSchedule` type with the same fields (id, customerId, deleteDisabled, enabled, frequency, frequencyInterval) and the same UpdateSchedule checks (interval validation and a refusal to update a disabled schedule), and differ in the endpoint, /connectorSchedule and /serviceEdgeSchedule. [zpa.terraform.resource-fidelity:assistant-schedules-share-one-shape]

**Arguments that never reach the API.** Up to v4.4.14, creating a redirection rule never resolved `policy_set_id`. The schema makes it optional and computed, the create path expanded it straight from the resource data, and the SDK builds the POST URL from it. The forwarding rule resource, by contrast, looks the policy set up by type when the argument is unset. v4.4.15 fixes the redirection rule: when `policy_set_id` is not set, create resolves the `REDIRECTION_POLICY` policy set. [zpa.terraform.resource-fidelity:redirection-create-skips-policy-set-lookup] The redirection rule's service edge group argument is an unbounded list of blocks, each holding a set of IDs. Expansion reads only the first block, and flattening emits one block per group with a single ID in it. A second configured block is never sent, and a first block with several IDs comes back from Read as several blocks. [zpa.terraform.resource-fidelity:redirection-edge-group-expand-flatten-asymmetry] The SDK's private cloud model has a `PrivateExporterGroupIDs` field and the provider's documentation names Private Exporter among the groups the resource associates, but the resource defines no argument for it and its Read and expand never touch it. A Private Exporter association cannot be configured, is not read into state, and is not part of what Terraform sends. [zpa.terraform.resource-fidelity:private-cloud-no-exporter-group-field] The server group expander sets `Name` only when `d.HasChange("name")`, and the SDK tags `name` `omitempty`. An update that changes anything else sends the PUT without a name. [zpa.terraform.resource-fidelity:server-group-update-name-only-on-change] The create path goes through the same expander and still sends the configured name, because Terraform reports every configured attribute of a new resource as changed. [zpa.terraform.resource-fidelity:server-group-create-sends-name] How ZPA treats a server group PUT without a name is open [gap:zpa.terraform.resource-fidelity:api-server-group-put-name]. The LSS config expander passes `enabled` and `use_tls` from the resource data, and the SDK tags both fields `omitempty`, so a false value sends no key. This is the zero-value write mechanism of [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes) applied to the LSS config. [zpa.terraform.resource-fidelity:lss-false-values-not-sent] The wider omission mechanism is in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes).

**Response fields that never reach state.** The redirection rule Read writes name, description, action, operator, policy set, policy type, conditions and service edge groups to state, but not `microtenant_id`, although the resource reads `microtenant_id` to pick the microtenant for every call. A microtenant returned by the API is not persisted. [zpa.terraform.resource-fidelity:redirection-read-omits-microtenant] The privileged portal rule Read guards on the length of the generic `PrivilegedCapabilities.Capabilities` but flattens `PrivilegedPortalCapabilities`. These are separate fields of the SDK response. A response with only portal capabilities is not written to state, and one with only generic capabilities sets the portal capabilities attribute to nil (the flattener returns nil for an empty list). [zpa.terraform.resource-fidelity:portal-capabilities-read-checks-wrong-field] The capabilities rule Read sets `privileged_capabilities` only when the response lists at least one capability, and has no other branch: when the response has none, Read does not touch the attribute. [zpa.terraform.resource-fidelity:capabilities-read-never-clears] The PRA console Read sets `pra_application` only when the flattener returns a value, and the flattener returns nil when the response application has no ID. A response without an application ID leaves `pra_application` untouched. [zpa.terraform.resource-fidelity:pra-console-read-never-clears-application] Where a Read sets a block only inside a condition on the response, a block or capability removed out of band leaves the previous value in state, so a plan can show no difference from a configuration that still holds it. [zpa.terraform.resource-fidelity:stale-state-hides-out-of-band-removal] The LSS config Read writes `policy_rule_id`, `config` and `connector_groups`, but never `policy_rule_resource`, though the SDK response carries a `PolicyRuleResource`. The policy-rule block is therefore taken from configuration or prior state only, and an imported LSS config has none. [zpa.terraform.resource-fidelity:lss-read-drops-policy-rule-resource] Policy rule reads that go through the v2 converter have a related loss, covered in [What the ZPA Terraform provider sends and loses when writing policy rules](kb:zpa.terraform.policy-rule-writes).

**One logical write, several requests.** Creating a private cloud with fire drill enabled is two writes. The provider clears `FireDrillEnabled` and the fire drill site from the POST, then sends them in a separate PUT after storing the new ID. If that PUT fails, the provider returns an error that says the cloud was created and to run apply again; it does not delete the cloud. The provider's comments say the API rejects fire drill on create; that is the provider's statement, not shown here. [zpa.terraform.resource-fidelity:private-cloud-create-then-fire-drill-put] For private cloud groups and Service Edge groups, user code verification is a second request sent after create, and after update when `user_codes` changed. When it fails the resource returns an error: the group (and, on update, its new settings) is already written, and nothing is rolled back. [zpa.terraform.resource-fidelity:user-code-verification-after-write] Cleanup sequences that fail midway on destroy are in [What the ZPA Terraform provider does when deleting objects with dependents](kb:zpa.terraform.delete-paths).

**Import and validation.** The PRA approval time validator, called from create and update, checks that the start is not more than an hour in the past and that the end is at most a year after the start. It does not compare the end with the start, so an end before or equal to the start passes it. [zpa.terraform.resource-fidelity:pra-approval-end-not-checked-against-start] Whether the API rejects an end before the start is open [gap:zpa.terraform.resource-fidelity:api-approval-window-validation].

What to check:
1. Whether the remote object matches the configuration after an apply on these resources, by reading it from the API rather than trusting state.
2. Whether the remote schedule setting is read directly after create, import or destroy, since on provider v4.4.14 or older an empty resource ID is the first symptom of the create path.
3. Whether the object exists and holds the first request's changes before a failed multi-request write is retried.
4. Whether an imported provisioning key of an association type the import does not probe was actually found, rather than assuming its type was read.

Same at HEAD.
- [zpa.terraform.resource-fidelity:lss-false-values-not-sent] Tier B: Chain of evidence: the quoted tags plus the omission claim it derives from, which holds where the writer marshals the caller's struct and the field's type has no MarshalJSON of its own. Both fields are plain `bool`, and the SDK's LSS config Update passes the struct it is given to `NewRequestDo` (zpa.api.lss-wire:update-returns-no-body), which marshals the caller's struct (zpa-writes-marshal-caller-struct); that the provider hands the expander's struct to that Update unchanged is not quoted here. Whether ZPA keeps or clears a stored true when the key is absent is server behavior (see the omission-semantics gap in shared.sdk-go.zero-value-writes).
- [zpa.terraform.resource-fidelity:stale-state-hides-out-of-band-removal] Tier B: Assumes the plan compares the configuration with the refreshed state and that the configuration still holds the removed value; that plan behavior is Terraform core, not shown by these sources.
