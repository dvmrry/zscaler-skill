# App Connectors on Docker, Kubernetes and OpenShift (zpa.app-connectors.containers)
Also called: app connector deployment guide for docker; app connector deployment guide for kubernetes; app connector deployment guide for openshift; app connector helm chart

The Docker, Kubernetes and OpenShift guides give App Connector container deployments their own prerequisites, resource limits, Helm charts and capability rules; VM and cloud platforms are in [App Connector deployment by VM and cloud platform](kb:zpa.app-connectors.platforms).

**Docker.** The App Connector Docker image is available on Docker Hub for both the ARM64 and AMD64 platforms, pulled as zscaler/zpa-connector:latest.arm64 or zscaler/zpa-connector:latest.amd64. [zpa.app-connectors.containers:docker-images] The App Connector Docker guide requires an environment variable named ZPA_PROVISION_KEY; only one container per host is allowed, deployed in a Docker Community Edition (CE) environment rather than an orchestration tool like Docker Swarm or Kubernetes; x86-64 and ARM64 systems each need a minimum of 2 cores and 4 GB RAM; and --init must be included in the run command. [zpa.app-connectors.containers:docker-prereqs] The App Connector Docker guide's capability table describes CAP_NET_RAW as fundamental to Private Access networking, says CAP_NET_BIND_SERVICE is required to bind to a port below 1024 and should be removed for a service on a port above 1024, says CAP_SYS_BOOT is optional and can be turned off in the container, says Private Access forks new processes and assigns the CPU affinity under CAP_SYS_NICE, and also lists CAP_SYS_TIME and CAP_SYS_RESOURCE. [zpa.app-connectors.containers:docker-capabilities] The App Connector Docker guide says Docker logs do not rotate by default and can keep growing until the root partition is full, which can cause servers to power down; its rotation example runs the container with the json-file log driver and a max-size, and sets a maximum of 10 log files of 500 MB each. [zpa.app-connectors.containers:docker-log-rotation] The Docker page's statement about Kubernetes and the Kubernetes guide's use of the Docker image differ [divergence:zpa.app-connectors.containers:docker-for-kubernetes].

**Kubernetes.** The App Connector Kubernetes guide lists a metrics server, says Kubernetes version 1.30 is the minimum recommended version, says that for Kubernetes deployment only the Docker image is supported on x86_64 systems and arm64 systems are not supported, and says RISE with SAP App Connector deployments are supported on SAP-managed Kubernetes clusters. [zpa.app-connectors.containers:kubernetes-prereqs] The App Connector Kubernetes guide recommends a minimum of 2 cores and 4 GB RAM for each pod, says CPU and memory are the only resources that can be changed, and shows limits of memory 8000Mi and cpu 8000m with requests of memory 4000Mi and cpu 2000m. [zpa.app-connectors.containers:kubernetes-resources] The Kubernetes and OpenShift guides both say the Horizontal Pod Autoscaler is supported per deployment based on CPU and memory metrics, with 2 as the minimum recommended replicas for the App Connector and an average utilization of 80% as the threshold. [zpa.app-connectors.containers:hpa] The App Connector Kubernetes guide adds the Helm repository https://dist.private.zscaler.com/helm-charts/k8s/ and installs with zsglobal.provisionkey.value set to the provisioning key; zscaler-zpa is the namespace added when the chart is installed, only one Helm installation can be performed with the default chart, multiple connectors use the multiConnector values with enabled: true, and Horizontal Pod Autoscaling occurs in each App Connector group per deployment. [zpa.app-connectors.containers:helm-install] The App Connector Kubernetes guide says active sessions with applications are terminated when its scale-down command is run. [zpa.app-connectors.containers:scale-down-drops-sessions] The App Connector Kubernetes guide says to use a tag with a dated version rather than latest.amd64 so the tag is a recent version, and to update the image version in the Helm chart to the corresponding Docker tag; a sentence beside the rollback instruction says it is not applicable to the initial version. [zpa.app-connectors.containers:image-tags-and-updates] The App Connector Kubernetes guide says Zscaler does not explicitly add node affinity for the App Connector Helm chart; its example labels nodes with kubectl label nodes <Node-name> type=zpa-app-connector and sets kubernetes.io/node-selector: "type=zpa-app-connector". [zpa.app-connectors.containers:node-affinity]

**OpenShift.** The App Connector OpenShift guide lists OpenShift 4.11 and later and Kubeadmin access on the default namespace, and says the Docker image is only supported for x86 systems and not for arm64 systems. [zpa.app-connectors.containers:openshift-prereqs] The App Connector OpenShift guide says the recommended resource limit (rlimit) on open files for the App Connector application is 512K and that OpenShift's default limit of 1,048,576 allows 2 pods on each node without changes to any settings. [zpa.app-connectors.containers:openshift-file-descriptors] The App Connector OpenShift guide says that starting with Manager software version 25.46.3 the Helm Chart for OpenShift and Kubernetes is combined into a single unified chart renamed zpa-app-connector, and that the directory zscaler-et-dist/helm-charts/openshift/ is deprecated. [zpa.app-connectors.containers:unified-chart] The App Connector OpenShift guide's capabilityMode is minimal (retains only CAP_NET_RAW, requires Manager software 25.46.3 or later), full (retains all previously existing capabilities) or custom (user-defined list, requires Manager software 25.46.3 or later, with CAP_NET_RAW injected automatically if omitted); OpenShift deployments default to full to maintain compatibility with platform restrictions. [zpa.app-connectors.containers:capability-mode]

**Provisioning keys and ephemeral pods.** The Kubernetes and OpenShift guides both say the threshold for App Connectors using the provisioning keys in an App Connector group is 100 and that the pods are ephemeral and consume a provisioning key utilization count each time they run; the Kubernetes guide adds that Zscaler recommends configuring Auto Delete in the App Connector settings to remove App Connectors with a disconnected status after a set number of days. [zpa.app-connectors.containers:key-threshold-auto-delete] Whether that threshold of 100 is a per-group maximum or the tenant limit is open in [App Connector deployment, redundancy and limits](kb:zpa.app-connectors.deployment).

What to check:
1. Whether the pod or container meets the minimum cores and memory and whether the Docker run command includes --init.
2. Whether ephemeral pods have used up the provisioning key's utilization count, and whether Auto Delete removes disconnected connectors.
3. Whether the container host is x86_64 and which guide's architecture statement applies to it.
4. Whether Docker logs are rotated so they do not fill the root partition.

Sources disagree (name both sides):
- The App Connector Docker guide says Docker support is not available for Kubernetes, while the Kubernetes guide deploys the App Connector Docker image. [divergence:zpa.app-connectors.containers:docker-for-kubernetes]
  - zscaler-help: Docker support is not available for Kubernetes.
  - zscaler-help: For Kubernetes deployment only, the Docker image is supported on x86_64 systems; arm64 systems are not supported.
  Impact: Read together, the Docker page's sentence cannot mean the Docker image is unusable on Kubernetes; the pages do not say whether it refers to the standalone Docker CE deployment. The architecture limits also differ: the Docker page offers ARM64, the Kubernetes guide does not.
