# Reference Terraform modules for Private Service Edges on GCP (zpa.private-service-edges.gcp-reference-modules)
Also called: terraform gcp private service edge module; gcp private service edge managed instance group; zspse gcp; psevm_instance_type gcp; terraform-gcp-zpa-private-service-edge-modules; gcp pse mig; module defaults private service edge gcp

The GCP reference modules deploy Private Service Edge VMs as zonal managed instance groups behind a Cloud NAT and create the ZPA Service Edge Group and Provisioning Key. They are the GCP counterpart of the AWS and Azure modules in [Reference Terraform modules for Private Service Edges on AWS and Azure](kb:zpa.private-service-edges.reference-modules), and the App Connector equivalent is [Reference Terraform modules for App Connectors on GCP](kb:zpa.app-connectors.gcp-reference-modules).

**Prerequisites.** As of module version 1.0.0 the GCP Private Service Edge module deploys all Service Edges on Red Hat Enterprise Linux 9; 1.0.0 (2024-09-30) is the initial release in the changelog. [zpa.private-service-edges.gcp-reference-modules:rhel9-since-1-0-0] The README lists the Google provider v6.4.x, random v3.6.x, local v2.5.x, null v3.2.x, tls v4.0.x and the ZPA provider v3.33.x, with Terraform v1.1.9 and any Terraform version 0.13.7 generally supported. [zpa.private-service-edges.gcp-reference-modules:provider-versions] The README requires a ZPA subscription with portal access and ZPA API keys (Client ID, Client Secret and Customer ID), and an existing Service Edge Group and Provisioning Key is optional; the GCP requirements are an account with Administrator Access, a service account keyfile and a region. [zpa.private-service-edges.gcp-reference-modules:api-keys]

**Examples.** The GCP Private Service Edge module's README, for deploying a Service Edge cluster, describes a greenfield deployment type under the label base_ac (a new management VPC with a management and a bastion subnet, a Cloud Router and NAT gateway, and a bastion host), with one Service Edge instance template across zonal managed instance groups, and a brownfield type whose network resources have conditional byo variables; the zspse wrapper prompts for the types as base_pse and pse. [zpa.private-service-edges.gcp-reference-modules:example-types] The examples validate name_prefix to 12 or fewer characters matching ^[a-z][a-z0-9-]+$, with default zspse. [zpa.private-service-edges.gcp-reference-modules:name-prefix] [divergence:zpa.private-service-edges.gcp-reference-modules:wrapper-deployment-types]

**VMs.** The GCP Private Service Edge VM module defaults psevm_instance_type to n2-standard-4 and validates it against n2-standard-4, n2-highcpu-4, n1-standard-4, n1-highcpu-4, n2-standard-8, n2-highcpu-8, n1-standard-8 and n1-highcpu-8. [zpa.private-service-edges.gcp-reference-modules:vm-size] Each Private Service Edge instance template boots from a pd-balanced boot disk whose size defaults to 64 GB, with automatic_restart true and on_host_maintenance MIGRATE. [zpa.private-service-edges.gcp-reference-modules:vm-template] The VM module creates one zonal managed instance group per zone, each with target_size equal to pse_count (default 1), so total Service Edges are pse_count times the number of zones. [zpa.private-service-edges.gcp-reference-modules:mig-layout] The examples create zonal groups in the first az_count available zones of the region (az_count defaults to 1 and is validated between 1 and 3), or in the distinct zones listed in the zones variable when it is non-empty, in which case each example's tfvars comment says az_count is ignored. [zpa.private-service-edges.gcp-reference-modules:zones-az-count] The MIG update policy defaults to type OPPORTUNISTIC, replacement method SUBSTITUTE, maximum surge 1 and maximum unavailable 1, with minimal and most-disruptive action REPLACE; per the variable description OPPORTUNISTIC means no action is proactively executed and an update happens as part of other actions such as resizes or recreateInstances calls. [zpa.private-service-edges.gcp-reference-modules:update-policy]

**Image and bootstrap.** The examples look up a specific named image, zpa-service-edge-el9-2024-08, in the Google Marketplace project mpi-zpa-gcp-marketplace when use_zscaler_image is true (the default), although the image_name variable description in each example and in the VM module says templates always pull the latest from Google Marketplace. [zpa.private-service-edges.gcp-reference-modules:image-pinned] With use_zscaler_image false the examples use the latest rhel-9 family image from the rhel-cloud project and a startup script that writes the Zscaler yum repository https://yum.private.zscaler.com/yum/el9 and installs zpa-service-edge. [zpa.private-service-edges.gcp-reference-modules:image-rhel9-fallback] The two startup scripts write the provisioning key to different files: /opt/zscaler/var/service-edge/provision_key for the Zscaler image and /opt/zscaler/var/provision_key for the RHEL 9 fallback image; both stop zpa-service-edge, run yum update -y, start the service, sleep 60 and restart it. [zpa.private-service-edges.gcp-reference-modules:bootstrap-key-paths] The RHEL 9 startup script (rhel9userdata) downloads and installs AWS CLI v2 from awscli.amazonaws.com before installing the Service Edge packages. [zpa.private-service-edges.gcp-reference-modules:rhel9-installs-aws-cli] Enrollment uses a provisioning key here; see [Enrolling a Private Service Edge](kb:zpa.private-service-edges.enrollment) for the other methods.

**ZPA objects.** The provisioning key module hardcodes the enrollment certificate name Service Edge (validated to that value), accepts only association type SERVICE_EDGE_GRP, binds the key to the group through zcomponent_id, and with byo_provisioning_key true creates no key and only references an existing one by name. [zpa.private-service-edges.gcp-reference-modules:key-module] The example provisioning_key_max_usage defaults to 10. [zpa.private-service-edges.gcp-reference-modules:key-max-usage] The GCP Private Service Edge group wrapper defaults pse_group_enabled to true, pse_is_public to false, pse_group_upgrade_day to SUNDAY, pse_group_upgrade_time_in_secs to "66600" (valid from 0 to under 86400 in 15 minute intervals) and pse_group_version_profile_id to "2"; its code comments name 0 Default, 1 Previous Default and 2 New Release. [zpa.private-service-edges.gcp-reference-modules:group-defaults] [divergence:zpa.private-service-edges.gcp-reference-modules:override-version-profile-default] The group wrapper attaches a ZPA trusted network only when zpa_trusted_network_name is non-empty, looking it up by name; the variable description says the cloud name must be appended to the trusted network name, as in "Corporate-Network (zscalertwo.net)". [zpa.private-service-edges.gcp-reference-modules:trusted-network]

**Network.** The network module creates a custom-mode VPC (auto_create_subnetworks false, routing_mode REGIONAL by default), one Private Service Edge subnet, a Cloud Router and a Cloud NAT gateway with AUTO_ONLY address allocation for all subnetworks and ERRORS_ONLY logging; each of VPC, subnet, router and NAT can instead be referenced with byo_* variables. [zpa.private-service-edges.gcp-reference-modules:network-resources] The module's firewall rule allows icmp and tcp on allowed_ports (an empty default list means all ports) from allowed_ssh_from_internal_cidr, and the examples set that source list to the bastion subnet CIDR (subnet_bastion). [zpa.private-service-edges.gcp-reference-modules:network-firewall] [gap:zpa.private-service-edges.gcp-reference-modules:client-inbound] In the base_pse example the bastion host gets an ephemeral public IP and a firewall rule allowing tcp/22 from bastion_ssh_allow_ip, which defaults to 0.0.0.0/0. [zpa.private-service-edges.gcp-reference-modules:bastion-open]

What to check:
1. Which VM size and disk the module deploys.
2. How many Service Edges the example creates (pse_count per zone) and whether the zones come from az_count or zones.
3. Which version profile the module-created group ends up with.
4. Whether the wrapper script can run the example the operator picked.
5. Whether the firewall opens the ports user traffic needs.

Sources disagree (name both sides):
- Whether the group wrapper overrides the version profile by default. [divergence:zpa.private-service-edges.gcp-reference-modules:override-version-profile-default]
  - tfmod-gcp-zpa-service-edge: The variable description says the default is false.
  - tfmod-gcp-zpa-service-edge: The variable default is true.
  Impact: A group created with the module defaults has override_version_profile true with version_profile_id "2" (New Release), not the false the description implies; confirm the group in the ZPA Admin Portal before assuming it follows the tenant default.
- Which deployment type names the zspse wrapper accepts. [divergence:zpa.private-service-edges.gcp-reference-modules:wrapper-deployment-types]
  - tfmod-gcp-zpa-service-edge: The examples README and the example directories name the deployment types base_pse and pse.
  - tfmod-gcp-zpa-service-edge: The same script accepts only base_ac for greenfield and ac for brownfield, and runs terraform with -chdir set to that name.
  - tfmod-gcp-zpa-service-edge: The examples README describes the deployment as base_ac and ac.
  Impact: Following the wrapper prompt for a base_pse or pse deployment is rejected by its case statement, and a dtype it does accept (base_ac, ac) names a directory this repository does not contain; set dtype to base_pse or pse in the environment (the script then skips that validation) or run Terraform directly in the example directory.
