# Provisioning key fields and tool behavior across SDKs, provider and MCP (zpa.app-connectors.provisioning-key-tooling)
Also called: provisioning key python sdk fields; provisioning key go sdk struct; provisioning key mcp; provisioning key secret in terraform state; mcp delete provisioning key already deleted; max_usage string
Former IDs: zpa-30, zpa-31

How the Python SDK, the Go SDK, the Terraform provider and the MCP server model a provisioning key, and where they disagree.

**Field sets.** The Python SDK ProvisioningKey model reads thirteen attributes from the response: id, name, creationTime, modifiedTime, modifiedBy, enabled, usageCount, maxUsage, zcomponentId, zcomponentName, provisioningKey, enrollmentCertId and enrollmentCertName. [zpa.app-connectors.provisioning-key-tooling:python-model-fields] The Go SDK ProvisioningKey struct defines eleven further fields: appConnectorGroupId, appConnectorGroupName, expirationInEpochSec, ipAcl, uiConfig, associationType, readOnly, restrictionType, zscalerManaged, microtenantId and microtenantName. [zpa.app-connectors.provisioning-key-tooling:go-struct-extra-fields] The eleven Go-only fields are absent from the Python model, so a key read through the Python SDK cannot report its group, ACL, expiry, read-only or Zscaler-managed state. [zpa.app-connectors.provisioning-key-tooling:python-model-lacks-go-fields] The two are in [divergence:zpa.app-connectors.provisioning-key-tooling:python-vs-go-key-fields]. maxUsage is a string in the Go struct, untyped in the Python model, and an integer in the MCP create tool's input. [zpa.app-connectors.provisioning-key-tooling:max-usage-types]

**The secret on read.** Both SDK models carry the provisioningKey value in the key object, so the secret is returned by a read, not only at creation. [zpa.app-connectors.provisioning-key-tooling:key-readable-on-get] The Terraform provider marks provisioning_key Sensitive but documents that the value is stored in the state file and can be retrieved with terraform output or by referencing the attribute. [zpa.app-connectors.provisioning-key-tooling:provider-stores-key-in-state] Credential handling in Terraform state is covered in [How the Zscaler Terraform providers store, log, and send secrets](kb:shared.terraform.credential-handling).

**Association types.** The Python SDK's provisioning key module accepts only the key types connector and service_edge, mapping them to CONNECTOR_GRP and SERVICE_EDGE_GRP, and raises ValueError for anything else; the module has no provisioning key path for NP_ASSISTANT_GRP, which the Go SDK lists. [zpa.app-connectors.provisioning-key-tooling:python-key-types] The provider's zpa_provisioning_key data source requires association_type and validates it against only CONNECTOR_GRP and SERVICE_EDGE_GRP, while the resource accepts five (see the service-defects subject). [zpa.app-connectors.provisioning-key-tooling:provider-data-source-two-types] Discovery through the data source therefore cannot look up provisioning keys of the SITE_CONTROLLER_GRP, EXPORTER_GRP or NP_ASSISTANT_GRP types. [zpa.app-connectors.provisioning-key-tooling:data-source-other-types-unreachable] The Go lookup helpers and the provider's five-value schema are in [ZPA Go SDK service functions that return partial results, send wrong keys, or reject valid input](kb:zpa.sdk-go.service-defects); the `enabled = false` write is in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes).

**Create and delete.** [add_provisioning_key adds name, maxUsage, enrollmentCertId and zcomponentId to the request body, taking the last two from the enrollment_cert_id and component_id arguments, and treats enrollment_cert_id as a plain optional argument for both key types.](kb:zpa.sdk-python.provisioning-keys:python-create-body) The MCP create tool raises an error when key_type is connector and enrollment_cert_id is missing; the function body opens with a name and component_id check, then this connector-only check, then gets the client. The rule is enforced in the tool, not in the SDK. [zpa.app-connectors.provisioning-key-tooling:mcp-requires-cert-for-connector] Whether the API itself requires the certificate is open [gap:zpa.app-connectors.provisioning-key-tooling:api-requires-cert-for-connector-key]. The MCP delete tool looks the key up first and, if the lookup returns an error or no object, reports success with 'does not exist or was already deleted' without calling delete; any lookup error is therefore reported as an already-deleted key. [zpa.app-connectors.provisioning-key-tooling:mcp-delete-masks-lookup-errors] The Python SDK's delete_connector_group takes only group_id and microtenant_id; it has no cascade or force argument. [zpa.app-connectors.provisioning-key-tooling:python-group-delete-no-cascade] Whether group deletion removes keys is open [gap:zpa.app-connectors.provisioning-key-tooling:group-delete-removes-keys].

**Listing.** [The MCP list tools for BA certificates, AppProtection profiles, enrollment certificates, posture profiles, SAML attributes, SCIM attributes, SCIM groups, trusted networks, PRA credentials, PRA portals and provisioning keys each declare the same `page` (at least 1) and `page_size` (1 to 500, API default 20) inputs and forward `page_size` to the SDK as a string.](kb:zpa.api.pagination:mcp-list-tools-same-inputs) The AWS reference module's provisioning-key variable accepts only CONNECTOR_GRP, while the Azure module accepts CONNECTOR_GRP or SERVICE_EDGE_GRP, so a SERVICE_EDGE_GRP key cannot be created through the AWS module's key sub-module. [zpa.app-connectors.provisioning-key-tooling:module-key-association-validation] An unverified legacy note about group-level fields in the Go SDK is [gap:zpa.app-connectors.provisioning-key-tooling:sdk-go-group-fields].

What a key is and how it is consumed is in [App Connector provisioning keys](kb:zpa.app-connectors.provisioning-keys).

What to check:
1. Which SDK or tool produced a key listing, because the Python model and the MCP server drop eleven fields.
2. Whether a delete reported as 'already deleted' came from a real absence or from a failed lookup.
3. Which association types a key lookup can reach: the data source validates association_type against two, and the Python SDK's provisioning key module accepts two.
4. Whether read access to keys is treated as enrollment capability, including Terraform state.

Inferred, not quoted (say so when an answer rests on one):
- [zpa.app-connectors.provisioning-key-tooling:python-model-lacks-go-fields] Tier B: Rests on the Python model reading exactly the thirteen listed keys; no other file in the SDK was searched for a second reader.
- [zpa.app-connectors.provisioning-key-tooling:data-source-other-types-unreachable] Tier B: Follows from provider-data-source-two-types: association_type is required and its validator accepts only CONNECTOR_GRP and SERVICE_EDGE_GRP, so a configuration naming one of the resource's other three types fails validation before any lookup. No source states the consequence for discovery, and no such lookup was run.

Sources disagree (name both sides):
- The Python and Go SDKs model different field sets for the same provisioning-key object. [divergence:zpa.app-connectors.provisioning-key-tooling:python-vs-go-key-fields]
  - sdk-python: The Python model reads thirteen attributes and stops at enrollmentCertName.
  - sdk-go: The Go struct also defines group id and name, expiry, ipAcl, uiConfig, associationType, readOnly, restrictionType, zscalerManaged and the microtenant fields.
  Impact: Anything that audits keys through the Python SDK or the MCP server (which returns the Python model) cannot see the Go-only fields; read them through the Go SDK or the raw API response.
