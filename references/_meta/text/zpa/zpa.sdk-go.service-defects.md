# ZPA Go SDK service functions that return partial results, send wrong keys, or reject valid input (zpa.sdk-go.service-defects)
Also called: provisioning key import not found; provisioning key GetAll partial; udpPortRangesg; cannot update a disabled schedule; assistant schedule enabled false; ApplicationValidation 400; UpdateWeightedLoadBalancerConfig nil; predefined control double encoded

These are separate defects in individual ZPA SDK service packages and the shared search helpers, not one mechanism. What they share is that the SDK's own helper decides what a caller sees, and the caller cannot tell. Zero-value writes are in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes), paging is in [How the Go SDK pages through ZPA, ZCC and ZTC lists, and when it stops early](kb:shared.sdk-go.list-pagination), and policy rule ordering (including the `BulkReorder` context defect) is in [How the ZPA Terraform provider applies policy rule order (BulkReorder)](kb:zpa.terraform.rule-order). The ZIA counterpart is [ZIA Go SDK service functions that return wrong results, mutate inputs, or reject valid input](kb:zia.sdk-go.service-defects).

## Partial or incomplete results reported as success

In the ZPA OpenAPI document the provisioning-key list is GET .../associationType/{associationType}/provisioningKey, with associationType a required path parameter, so the documented list is per association type. [zpa.sdk-go.service-defects:provisioning-key-api-requires-association-type] The provisioning-key lookups that do not take an association type (`GetByNameAllAssociations`, `GetByIDAllAssociations`) iterate a fixed SDK list of three association types: CONNECTOR_GRP, SERVICE_EDGE_GRP, NP_ASSISTANT_GRP. They also treat any error from one type's lookup (not only not-found) as a reason to try the next, and return the last attempt's error. A key stored under any other association type cannot be found through these helpers. [zpa.sdk-go.service-defects:provisioning-key-all-associations-fixed-list] The provider's `zpa_provisioning_key` schema accepts five `association_type` values, including SITE_CONTROLLER_GRP and EXPORTER_GRP, and its importer resolves the association type with the all-associations helpers whenever the import is by name or by numeric ID without `association_type` set. So the provider offers types the importer cannot find. Create, read, update and delete pass the configured association type directly and do not use the helpers. [zpa.sdk-go.service-defects:provider-provisioning-key-schema-and-importer] Keys of the two unprobed association types cannot be imported by name or by numeric ID without `association_type` set [zpa.sdk-go.service-defects:provisioning-key-all-associations-fixed-list]. Whether keys are stored under those two types, and how the API lists them, is open [gap:zpa.sdk-go.service-defects:provisioning-key-association-types].

`provisioningkey.GetAll` loops over the same fixed association list and assigns each type's result with the error discarded (`items, _ :=`). It always returns a nil error, so a failing association endpoint yields a shorter list reported as success. [zpa.sdk-go.service-defects:provisioning-key-get-all-discards-errors]

## Wrong keys on the wire

The segment group's nested `Application` struct tags its UDP port ranges `udpPortRangesg`. Responses carrying `udpPortRanges` do not fill the field, and a populated field is written under the misspelled key. The sibling TCP field uses `tcpPortRanges`, and the application segment SDK tags its UDP port ranges `udpPortRanges`. [zpa.sdk-go.service-defects:segment-group-udp-key-misspelled] The provider's segment group data source declares a computed `udp_port_ranges` attribute for each application, but the function that flattens the applications into state lists `tcp_port_ranges`, `tcp_ports_in` and `tcp_ports_out` and does not set `udp_port_ranges`. The attribute is therefore never populated, independently of the SDK key. The resource manages application membership and does not expose the field for writing. [zpa.sdk-go.service-defects:provider-segment-group-data-source-omits-udp] The provider's segment group resource declares each application with only an `id`, expands each one into a `segmentgroup.Application` with only its ID, and reads back only the ID. [zpa.sdk-go.service-defects:provider-segment-group-resource-writes-application-ids-only]

## Valid input rejected before any request

Both `appconnectorschedule.UpdateSchedule` and `serviceedgeschedule.UpdateSchedule` return an error before sending anything when `assistantSchedule.Enabled` is false (`cannot update a disabled schedule`). A false value cannot be written through either update. [zpa.sdk-go.service-defects:assistant-schedule-update-rejects-disabled] Both provider assistant-schedule resources declare `enabled` as Optional without a default, copy `d.Get("enabled").(bool)` into the request, and call the SDK update. So `enabled = false`, and an omitted `enabled` (which reads as false), make every update that reaches the SDK update fail there, before its PUT is sent. An empty or invalid `frequency_interval` fails the same way, and a create that finds the schedule already exists falls into this update path; the SDK create has no such check, so a first create with `enabled = false` is not refused client-side. [zpa.sdk-go.service-defects:provider-schedule-resources-pass-enabled-through] Whether the API accepts `enabled = false` on a schedule update is open [gap:zpa.sdk-go.service-defects:schedule-disable-contract].

## Search and query encoding

Paging itself is covered in [How the Go SDK pages through ZPA, ZCC and ZTC lists, and when it stops early](kb:shared.sdk-go.list-pagination).

`applicationsegmentbytype.GetByApplicationType` puts the raw name in the request URL as `search=<name>` and also passes the same name as `Filter.Search`. The shared pager rewrites that into `name+EQ+<name>` and appends it as a second `search` parameter, so one request carries two `search` values, one plain and one in filter syntax. [zpa.sdk-go.service-defects:application-type-lookup-duplicate-search]

`inspection_predefined_controls.GetByName` applies `url.QueryEscape` to the name and then stores the result with `queryParams.Set`, whose `Encode` escapes it again. A `+` in the name is therefore escaped twice on the wire. The request path re-parses and re-encodes the query but does not undo the first escape. [zpa.sdk-go.service-defects:predefined-control-name-escaped-twice] A `+` in a predefined control name is sent as `%252B` on the wire (`url.QueryEscape` gives `%2B`, and `Encode` escapes its `%` as `%25`). [zpa.sdk-go.service-defects:predefined-control-plus-wire-form]

For ZPA list endpoints (other than SCIM) the shared pager rewrites a plain search string into `name+EQ+<value>` after deleting every character outside letters, digits, whitespace, `_`, `/`, `-` and `.`. The segment group lookup by name, for one, then compares the listed results to the original name case-insensitively. [zpa.sdk-go.service-defects:search-sanitizer-strips-name-characters] A name such as `a+b (prod)` is therefore searched as `ab prod`: the sanitizer deletes `+`, `(` and `)` and keeps the space. [zpa.sdk-go.service-defects:search-sanitizer-example] The provider's segment group importer by name and its data source by name call `segmentgroup.GetByName`, so a segment group whose name contains characters the sanitizer removes goes through the altered search. [zpa.sdk-go.service-defects:provider-segment-group-lookups-use-sanitized-search]

For ZPA endpoints the OneAPI request path (`NewRequestDo`) parses the query and re-encodes it with `encodeQueryWithSpacesAsPercent20`, whose name and comment say spaces become `%20`, but which writes each value with `url.QueryEscape`. [zpa.sdk-go.service-defects:query-encoder-emits-plus-for-space] `encodeQueryWithSpacesAsPercent20` therefore encodes a space as `+`, not `%20`, and does not do what its name and comment say. [zpa.sdk-go.service-defects:query-encoder-space-as-plus] How the list search treats `+` versus `%20` and the removed characters is open [gap:zpa.sdk-go.service-defects:search-filter-semantics].

## Context ignored

`GetByNameAndTypes` in both policy set controller packages receives a caller `ctx` and calls `GetByNameAndType` with `context.Background()` for each policy type it tries, so cancellation and deadlines do not reach those requests. The provider calls them from its policy rule importers when importing by name. [zpa.sdk-go.service-defects:policy-type-lookups-drop-context] Within the ZPA SDK, outside client construction (`config_scim.go`, `v2_config.go`), the only places that replace a caller's context with `context.Background()` are `GetByNameAndTypes` and `BulkReorder` in the two policy set controller packages (three sites each). [zpa.sdk-go.service-defects:zpa-context-background-sites]

## Panics on nil input

Both `UpdateRule` functions guard only the empty-conditions branch with `policySetRule != nil`; any other path, including a nil pointer, falls to the `else` branch that ranges over `policySetRule.Conditions`, which panics for nil. [zpa.sdk-go.service-defects:policy-update-rule-nil-deref] Other ZPA mutators dereference a pointer argument with no nil check: the inspection profile `setVersion` (called first by `Update`, `PutAssociate`, `PutDeassociate` and `Patch`) reads `inspectionProfile.PredefinedControlsVersion`, and tag key `Update` copies `*tagKey`. A nil argument panics rather than returning an error. [zpa.sdk-go.service-defects:other-mutators-dereference-unchecked-pointers] What such a panic does to the provider process is open [gap:zpa.sdk-go.service-defects:panic-effect].

## Response shape

`ApplicationValidation` decodes into an `ApplicationValidationError` and treats a nil error as the validation-error case, with the comment `For validation, we expect either success (200) or validation error (400)`. The OneAPI executor returns an error with a nil body for a 4xx that reaches the generic client-error branch (401, 429 and edit-lock 409/412 are handled earlier; the legacy client is not covered), so a 400 never reaches the decoder; only a 2xx response is decoded into the error type and returned as if it were a validation failure. [zpa.sdk-go.service-defects:application-validation-cannot-return-typed-error]

`UpdateWeightedLoadBalancerConfig` is declared to return the configuration but sends the PUT with a nil response target and returns `nil, resp, nil` on success, so a caller that uses the returned object gets nil. [zpa.sdk-go.service-defects:weighted-lb-update-returns-nil-object]

The OpenAPI associationType enum is ASSISTANT_GRP, NP_ASSISTANT_GRP, BROKER_GRP, SITE_CONTROLLER_GRP, EXPORTER_GRP. It includes ASSISTANT_GRP, BROKER_GRP, SITE_CONTROLLER_GRP and EXPORTER_GRP, which the SDK's fixed list does not contain, and it omits CONNECTOR_GRP and SERVICE_EDGE_GRP, which the SDK probes and the provider accepts. The parameter description names CONNECTOR_GRP, NP_ASSISTANT_GRP and SERVICE_EDGE_GRP. [zpa.sdk-go.service-defects:openapi-association-enum-includes-unprobed-types] So the enum does not settle whether provisioning keys are stored under SITE_CONTROLLER_GRP or EXPORTER_GRP [gap:zpa.sdk-go.service-defects:provisioning-key-association-types].

What to check:
1. Whether a key of one of the two unprobed association types must be managed, by creating it in Terraform, or left unmanaged.
2. Whether `frequency_interval` is valid before a schedule update, since an empty or invalid value fails the same way as a disabled schedule.
3. Whether the error reads `cannot update a disabled schedule` before a failed schedule update is attributed to the server.
4. Whether a lookup by a name containing punctuation failed with `no ... named ... was found`, which points at the search sanitizer.
