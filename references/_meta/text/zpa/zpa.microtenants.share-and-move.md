# Sharing and moving between Microtenants (zpa.microtenants.share-and-move)
Also called: share application segment to microtenant; move application segment to microtenant; app_segment_move; app_segment_share; credential_move; shareToMicrotenants; sharedMicrotenantDetails; AppSegmentMicrotenantMove; AppSegmentMicrotenantShare; microtenant readOnly segment

Sharing keeps the segment in its owner and lets another Microtenant use it, and moving changes the owner.

**Share.** Applications can be shared explicitly between Microtenants; the Share icon appears only inside a Microtenant, and a segment can be shared from one Microtenant to the Default Microtenant. [zpa.microtenants.share-and-move:share-explicit] An application segment carries `sharedMicrotenantDetails` with `sharedFromMicrotenant` (id and name of the source) and `sharedToMicrotenants` (the Microtenants it was shared to). [zpa.microtenants.share-and-move:shared-details-fields] Whether a shared-in segment is editable is open [gap:zpa.microtenants.share-and-move:readonly-semantics]. Whether the console's Microtenant drop-down lists Default is open [gap:zpa.microtenants.share-and-move:default-share-target].

**Move.** An application that is not shared with any other Microtenant can be moved to the Default Microtenant. [zpa.microtenants.share-and-move:unshared-can-move] Before moving a defined application segment, the target segment group and server group must be configured and the associated policy must be deleted; before moving a privileged credential, the associated privileged credential policy must be deleted. [zpa.microtenants.share-and-move:move-prerequisites] From inside a Microtenant, the only Microtenant option to move an application segment to is Default. [zpa.microtenants.share-and-move:move-targets] The Python docstring gives the opposite direction [divergence:zpa.microtenants.share-and-move:move-direction]. Browser Access on a segment does not persist when it is moved from the Default Microtenant, so the web server certificate must be selected again; moving a segment referenced in a privileged approval is not supported; moving a segment whose Privileged Remote Access application is used in a privileged console is not supported. [zpa.microtenants.share-and-move:move-unsupported-cases]

**Python.** The Python SDK's `app_segment_move` posts to `/application/{id}/move` with `targetSegmentGroupId`, `targetMicrotenantId` and `targetServerGroupId` in the body and the source scope as the `microtenantId` query parameter. [zpa.microtenants.share-and-move:python-move] The Python SDK's `app_segment_share` puts `shareToMicrotenants` to `/application/{id}/share`, and its docstring says to send the attribute as an empty list to remove the share. [zpa.microtenants.share-and-move:python-share] [POST /credential/{id}/move has no request body and returns 204; the destination is the targetMicrotenantId query parameter, where 0 means the Default microtenant. The Python SDK raises an error when target_microtenant_id is falsy; the Go SDK appends the parameter only when the string is non-empty. The contract also takes an optional microtenantId query parameter. The Python SDK forwards microtenant_id as microtenantId; Go's CredentialMove has no per-call microtenantId parameter and ignores the service's microtenant, so microtenantId reaches the request only from the ZPA_MICROTENANT_ID environment variable or the client's configured microtenant.](kb:zpa.api.pra-wire:credential-move)

**Go.** The Go SDK exposes `AppSegmentMicrotenantMove` (POST `/application/{id}/move`) and `AppSegmentMicrotenantShare` (PUT `/application/{id}/share`), each taking the scope from the request struct or else the service's Microtenant and sending it as the `microtenantId` query filter. [zpa.microtenants.share-and-move:go-move-and-share] The Go share request declares `ShareToMicrotenants` with `omitempty`, and the application segment struct declares the same field without it. [zpa.microtenants.share-and-move:go-share-body-omitempty] Whether Go can remove a share is open [gap:zpa.microtenants.share-and-move:go-unshare-empty-list]. The move body differs from the specification [divergence:zpa.microtenants.share-and-move:move-body-shape].

**Terraform.** Sharing from Terraform is a second write after the segment: [Sharing a main application segment to microtenants is a second API call made after the segment is written. On create, the ID is set before the share call, and a share failure returns an error with the segment already created. On update, a share failure returns an error after the parent PUT has been applied. Neither path rolls back.](kb:zpa.terraform.app-segment-lifecycle:main-share-separate-write), with a spurious `sharedMicrotenantDetails` object in [Each of the four request structs holds `SharedMicrotenantDetails` by value with `omitempty`, which Go's JSON encoder does not omit. The provider never assigns it on a write (it only reads `SharedToMicrotenants` from a response), so every create and update carries `sharedMicrotenantDetails` with an empty `sharedFromMicrotenant` object.](kb:zpa.terraform.app-segment-lifecycle:phantom-shared-microtenant-object).

The id types differ between contract and Go SDK [divergence:zpa.microtenants.share-and-move:share-move-id-types].

Whether the extra body fields are ignored is open [gap:zpa.microtenants.share-and-move:move-body-extra-fields].

What to check:
1. Whether the segment is shared or must be moved, and whether it is currently shared to another Microtenant before it is moved.
2. The direction of the move: from a custom Microtenant the console offers only Default, while the Python docstring says Default to a child only.
3. Whether a policy, privileged approval or privileged console references the segment, since those block or require deletion before a move.
4. Which SDK builds the request, and whether the move body carries applicationId and microtenantId.
5. Whether the Go SDK can send an empty share list to remove a share.
6. Whether a segment seen as shared in is editable in the receiving Microtenant.

Sources disagree (name both sides):
- The console lets a Microtenant user move a segment only to Default, while the Python SDK docstring says a move can only go from Default to a child Microtenant. [divergence:zpa.microtenants.share-and-move:move-direction]
  - zscaler-help: From inside a Microtenant the only move target is Default.
  - sdk-python: Moves go only from the Default Microtenant (microtenant_id 0) to a child Microtenant.
  Impact: A script that moves a segment from one custom Microtenant back to Default, or one that assumes only Default to child works, follows the wrong source; neither source says which direction the API rejects.
- The Go move request struct carries five fields including `applicationId` and `microtenantId`, while the OpenAPI move body defines three target fields. [divergence:zpa.microtenants.share-and-move:move-body-shape]
  - sdk-go: The Go body can carry applicationId and microtenantId besides the three target IDs.
  - api-specs: The documented body has only targetMicrotenantId, targetSegmentGroupId and targetServerGroupId; the application ID is in the path and the scope is a query parameter.
  Impact: Both fields are omitted when empty, so the extra fields change the wire body only if a caller sets them; the specification does not say whether the API ignores or rejects them.
- The OpenAPI document types the share and move body identifiers as 64-bit integers, while the Go SDK models them as strings. [divergence:zpa.microtenants.share-and-move:share-move-id-types]
  - api-specs: The contract types the entries of shareToMicrotenants as int64 integers.
  - api-specs: The contract types targetSegmentGroupId in the move body as an int64 integer.
  - sdk-go: The Go share request holds the microtenant IDs as a list of strings.
  - sdk-go: The Go move request holds the target IDs as strings.
  Impact: Raw-HTTP callers follow the contract and send numbers; the Go SDK sends numeric strings. Whether the API accepts both is not shown by either source.
