# What the ZPA Terraform provider sends, keeps and cleans up for application segments and their associations (zpa.terraform.app-segment-lifecycle)
Also called: application segment update clears flags; terraform zpa app segment extranet false; clientless app hidden; pra app segment update ignored; browser access wrong clientless app id; sharedMicrotenantDetails empty; inspection profile associate_all_controls false; custom control not attached to profile; app segment destroy leaves policy rule operand; server_groups second block ignored

ZPA application segments come in four kinds (main, browser access, inspection, PRA), each with its own Terraform resource and SDK package. All four update by sending a full struct rebuilt from Terraform arguments, so what the schema cannot express goes out as Go zero values. The omitempty clears themselves are in [Why Terraform cannot clear some fields: omitted zero values and empty objects in SDK writes](kb:shared.sdk-go.zero-value-writes); this subject covers what is specific to segments and the objects hanging off them.

**Parent flags.** The SDK request structs for the four application segment kinds declare some API flags without `omitempty`, so they are always in the request body, as false when the caller leaves them unset: `extranetEnabled`, `apiProtectionEnabled`, `autoAppProtectEnabled` and `adpEnabled` on the main segment; `extranetEnabled`, `apiProtectionEnabled` and `bypassOnReauth` on browser access; `extranetEnabled` and `apiProtectionEnabled` on inspection and PRA. [zpa.terraform.app-segment-lifecycle:parent-flags-always-serialized] The four resources build the request from Terraform arguments and never assign the unmodeled flags: the main segment expander sets `APIProtectionEnabled` and `BypassOnReauth` but not `ExtranetEnabled`, `AutoAppProtectEnabled` or `ADPEnabled`; the browser access expander sets none of its three; the inspection and PRA expanders set neither `ExtranetEnabled` nor `APIProtectionEnabled`. The schemas have no matching arguments to read. [zpa.terraform.app-segment-lifecycle:parent-flags-never-set] The main application segment update builds its request from Terraform arguments: its expander reads the existing segment, but uses that segment's TCP and UDP port ranges only to choose between the two configured port-range forms. The update then reads the segment again only to detect that it is gone, ignores any other error from that read, discards the result, and sends the rebuilt struct as the PUT body. The SDK's `Update` sends the struct it is given as the PUT body. [zpa.terraform.app-segment-lifecycle:main-update-builds-from-state] So an update that changes only an unrelated argument sends `false` for flags the Terraform schema cannot express, which can switch off extranet, API protection, auto AppProtection, ADP or bypass-on-reauth behavior that was enabled outside Terraform. [zpa.terraform.app-segment-lifecycle:unrelated-update-may-blank-flags] What ZPA does with a false value for these flags on a PUT is open [gap:zpa.terraform.app-segment-lifecycle:api-app-segment-put-semantics].

**Empty objects.** Each of the four request structs holds `SharedMicrotenantDetails` by value with `omitempty`, which Go's JSON encoder does not omit. The provider never assigns it on a write (it only reads `SharedToMicrotenants` from a response), so every create and update carries `sharedMicrotenantDetails` with an empty `sharedFromMicrotenant` object. [zpa.terraform.app-segment-lifecycle:phantom-shared-microtenant-object]

**Nested apps.** The inspection nested-app struct (`AppsConfig`) sends `enabled`, `adpEnabled`, `allowOptions`, `hidden`, `trustUntrustedCert` and `portal` without `omitempty`. The SDK's inspection `Update` only injects `appId` and `inspectAppId` into those entries, matching by name; it does not copy the other fields from the existing app. [zpa.terraform.app-segment-lifecycle:inspection-subapp-flags-always-serialized] The inspection resource's expander builds each nested app from a subset of fields (ids, name, port, protocol, certificate, domain, trust-untrusted-cert, app types; up to v4.4.11 also description, which v4.4.12 dropped from the schema and the expander). It does not assign `Enabled`, `AdpEnabled`, `AllowOptions`, `Hidden` or `Portal`, and the `Protocols` assignment is commented out in the expander. Up to v4.4.11 it was also commented out in the flattener; v4.4.12 rewrote the flattener (#690), which maps no protocols field. [zpa.terraform.app-segment-lifecycle:inspection-subapp-expand-subset] So updating an inspection segment sends every nested app with `enabled`, `adpEnabled`, `allowOptions`, `hidden`, `portal` false and no protocol list, whatever those apps hold remotely. [zpa.terraform.app-segment-lifecycle:inspection-update-may-reset-subapp-state] The browser access resource has no `hidden` argument. Its expander for clientless apps assigns `AllowOptions`, `Enabled` and others but not `Hidden`, and the SDK declares `Hidden` without `omitempty`, so every clientless app in a create or update carries `hidden: false`. [zpa.terraform.app-segment-lifecycle:browser-hidden-sent-false] On a PRA segment update, every configured nested app is sent. If its domain already exists remotely, its IDs, enabled, and description are taken from the remote object, and its name is taken from the configured name if present, otherwise the remote name; its port, protocol, connection security, and domain are taken from the configuration. Apps whose configured domain is not present remotely are sent with empty IDs, and remote apps whose domain is no longer configured are marked for deletion. A change to an existing app's enabled or description is therefore not sent, while changes to port, protocol, connection security, or name are sent. [zpa.terraform.app-segment-lifecycle:pra-update-sends-remote-values] The PRA segment update's error returns cover only its initial Get, port validation and the SDK Update; on its normal path it ends by returning the result of a Read, with existing apps matched by domain to keep their IDs but no comparison of the configured nested apps against what was sent. [zpa.terraform.app-segment-lifecycle:pra-update-returns-read-after-update] The `zpa_application_segment` resource documents that a segment on which Auto App Protection or Active Directory Inspection has been enabled, for example in the Admin Portal, becomes an inspection segment that only `zpa_application_segment_inspection` supports: it must be imported there and removed from `zpa_application_segment`, because any update the main resource applies disables the feature and leaves the per-domain inspection configuration invalid. Issue #687 reported that an unrelated update did exactly that and also made the segment vanish from the console's main list; it was closed as completed on 2026-10-01 with a reply from a member of the repository's organization, signed Zscaler DevRel, naming `zpa_application_segment_inspection` and its `trust_untrusted_cert` setting as the supported way to manage such a segment. [zpa.terraform.app-segment-lifecycle:main-resource-unsupported-for-appprotection-segments]

**Child identity.** For a clientless app with an empty ID, the browser access SDK `Update` assigns the ID of the existing app at the same list position. The provider fills IDs by name first, so only apps whose name matches no existing app (new or renamed) reach the positional fallback. Those apps come from a Terraform set, read as a list. [zpa.terraform.app-segment-lifecycle:browser-child-id-positional-fallback] Their list position therefore follows the set's own ordering, not the order of the remote list. [zpa.terraform.app-segment-lifecycle:browser-set-order-not-remote] So adding or renaming a clientless app can give it the ID of an existing app that another entry in the same request already carries by name, producing a request in which two entries have one ID and one existing app is replaced or overwritten. [zpa.terraform.app-segment-lifecycle:browser-child-id-may-duplicate] The inspection and PRA SDK `Update` functions find each existing nested app through a map keyed by name. Two desired apps with the same name both receive the same ID, and a renamed app is treated as new. The inspection resource sets each nested app's name to its domain, so the identity in practice is the domain. [zpa.terraform.app-segment-lifecycle:nested-apps-matched-by-name]

**Sharing and associations.** Sharing a main application segment to microtenants is a second API call made after the segment is written. On create, the ID is set before the share call, and a share failure returns an error with the segment already created. On update, a share failure returns an error after the parent PUT has been applied. Neither path rolls back. [zpa.terraform.app-segment-lifecycle:main-share-separate-write] The helper that turns the `server_groups` argument into a request indexes only the first block (`blocks[0]`) and builds its server groups from the `id` set in that block; it returns only a slice, no error. The schema declares `server_groups` as an optional list with no item limit before its element. [zpa.terraform.app-segment-lifecycle:association-block-first-only] So any `server_groups` block after the first is dropped without an error, and only the IDs in the first block reach the request. [zpa.terraform.app-segment-lifecycle:association-block-first-only-drops-rest] The same first-block-only read is in the other association expanders in `common.go` (app connector groups, app server groups, service edge groups), which feed the v1 and v2 access policy rules, the redirection rule and the server group resource, and in the server group, service edge group (`trusted_networks`) and user portal link expanders, where the schema allows several blocks (the private cloud and `service_edges` expanders are single-block by schema). [zpa.terraform.app-segment-lifecycle:association-block-first-only-places]

**Deletes.** Segment group, server group and connector group cleanups are in [What the ZPA Terraform provider does when deleting objects with dependents](kb:zpa.terraform.delete-paths). Deleting a main application segment calls a cleanup that returns nothing. The cleanup lists rules of five policy types through the v1 policy controller, skips a policy type when listing its set or rules fails, skips a rule when its update fails, and the delete then runs regardless. [zpa.terraform.app-segment-lifecycle:main-delete-v1-cleanup-ignores-errors] Up to v4.4.14 the main application segment's policy cleanup set each condition's operands to the ones left after removing the segment (`rule.Conditions[i].Operands = operands`), so a condition could be left with no operands, and the v4.4.15 changelog says deleting a segment no longer fails in that case. From v4.4.15 the cleanup skips a condition left with no operands and sends the remaining conditions. [zpa.terraform.app-segment-lifecycle:detach-drops-emptied-conditions-4-4-15] The browser access, inspection and PRA delete functions do not call the policy cleanup. Browser access calls the SDK delete directly, inspection first removes the segment from its segment group when `segment_group_id` is set, and PRA has a policy-detach call commented out (named for connector groups, not for application segments). All three SDK delete calls pass `ForceDelete: true`. [zpa.terraform.app-segment-lifecycle:other-segment-deletes-skip-policy-detach] So a destroy of a main segment can finish successfully while a policy rule still has an APP operand for it (a cleanup step was skipped or failed), and a destroy of a browser access, inspection or PRA segment does not remove such operands before asking ZPA to delete the segment with force. [zpa.terraform.app-segment-lifecycle:delete-can-leave-policy-references] Whether the v1 policy listing returns rules written through the v2 endpoints is open [gap:zpa.terraform.app-segment-lifecycle:api-v1-listing-covers-v2-rules]. Operand rewriting by the v1 cleanup is covered in [What the ZPA Terraform provider sends and loses when writing policy rules](kb:zpa.terraform.policy-rule-writes).

**Inspection profile and custom control associations.** The inspection profile resource calls `PutAssociate` only when `associate_all_controls` is true, in both create and update, and never calls the SDK's `PutDeassociate`. Read sets the argument from its own configured value, not from the API. Changing it from true to false therefore sends nothing that de-associates, and state shows false. [zpa.terraform.app-segment-lifecycle:associate-all-controls-no-false-branch] The result of `PutAssociate` is discarded in create and update. The SDK function returns an error, but the call is a bare statement, so a failed association is not reported and the resource finishes as created or updated. [zpa.terraform.app-segment-lifecycle:associate-error-ignored] Associating an inspection custom control with its profiles is done by a helper with no return value: it logs a failed control lookup and returns, logs a failed profile lookup and continues to the next profile, and logs a failed profile patch, the loop's last statement, before the loop and the function close; create and update call it without a result to check. On delete, the loop that removes the control from each profile skips a profile whose lookup fails and ignores the error from the profile update, then deletes the control. [zpa.terraform.app-segment-lifecycle:custom-control-association-errors-logged]

On read the provider merges the returned server groups into one block: On read, the provider turns the server groups the API returns for a segment into one `server_groups` block whose `id` is a set of the non-empty group IDs, and into nothing when none has an ID; the base, Browser Access, PRA and Inspection segment resources all set `server_groups` this way. [zpa.terraform.app-segment-lifecycle:server-groups-flatten-single-block]

**Segment group applications.** What the segment group resource sends is in [The Terraform resource takes a required `name` and optional `description`, `enabled`, `microtenant_id` and an `applications` list of objects with a single `id` attribute; an `enabled` left out is sent as false. Before v4.4.14 every write, create and update, built each application from its `id` alone; v4.4.14 deprecates `applications`, sends the application IDs only on create, never sends them on update, and rejects adding or removing applications on an existing group at plan time (#695).](kb:zpa.segment-groups.api-surface:tf-resource-schema). The segment group resource's Read sets applications to the IDs of the applications the API returns for the group. At v4.4.11 to v4.4.13 an update sent the configured applications list through UpdateV2. From v4.4.14 the argument is deprecated, the docs say to manage membership with segment_group_id on zpa_application_segment, and on an existing group the plan fails when the configured application IDs add to or remove from the IDs in state; the IDs are compared as sets, so order alone is not a change. [zpa.terraform.app-segment-lifecycle:segment-group-membership-check] From v4.4.14 a segment group whose configuration lists applications does not drift silently: when a segment joins or leaves the group through its segment_group_id, the next Read changes the IDs in state, the configured list no longer matches them as a set, and the plan fails with the membership error until the list is corrected or the block is removed. [zpa.terraform.app-segment-lifecycle:segment-group-membership-change-fails-plan] Whether a reordered list plans an update on every run is open [gap:zpa.terraform.app-segment-lifecycle:segment-group-applications-drift].

What to check:
1. Whether extranet, API protection, AppProtection and reauth flags are unchanged after an apply that changed only a name or port range, by re-reading the segment.
2. Whether every configured server group reached ZPA, since only the IDs in the first `server_groups` block are sent.
3. Which policy types hold APP operands that name the ID of a destroyed segment.
4. Whether the remote inspection profile association is set, by reading the profile from the API, since state reflects the configured value.
