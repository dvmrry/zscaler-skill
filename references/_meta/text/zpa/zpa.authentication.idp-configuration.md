# Configuring an IdP for Private Access single sign-on (zpa.authentication.idp-configuration)
Also called: IdP configuration; IdP Configuration page; add an IdP; Use with Arbitrary Domains; Force Authentication; Login Hint; SAML Attributes for Policy; SCIM Attributes for Policy; admin SSO; user SSO

An IdP configuration is the Private Access object that ties an identity provider to single sign-on. The IdP must be configured to recognize Zscaler as a valid SP, and the IdP's full details must be configured in the Admin Console. IdP configuration also enables SCIM so that users and groups can be provisioned. [zpa.authentication.idp-configuration:both-sides-configured] The published configuration guides cover specific IdPs, but ZPA can support any IdP. The IdP must already be in place before an IdP configuration is added, and the private.zscaler.com references in the article's examples might differ with the organization's assigned cloud. [zpa.authentication.idp-configuration:any-idp] Up to 10 IdP configurations can be added for single sign-on, and the ranges and limitations page lists 10 IdP configurations. [zpa.authentication.idp-configuration:limit-10]

**How users and admins sign in.** Users must authenticate into Zscaler Client Connector through a SAML 2.0-compliant IdP with the SP-initiated model. Private Access user SSO is SP initiated, while admin SSO can be SP initiated (Single Sign-On Using IdP on the Admin Console's Sign In page) or IdP initiated (logging in directly to the IdP). [zpa.authentication.idp-configuration:sp-initiated-model] The Client Connector error list reads differently from this page on IdP-initiated sign-in [divergence:zpa.authentication.idp-configuration:sp-initiated-scope]; the error is in [42017 occurs when the IdP sends Private Access a SAML response without the Private Access authentication service initiating it; only service provider (SP) initiated SSO is supported with Private Access. 42018: the service failed to look up the SAML request corresponding to the response (contact Zscaler Support). 42019: the assertion consumer endpoint of the authentication service is not properly configured in the IdP (review the SP configuration in the IdP).](kb:zcc.troubleshooting.private-access-auth-errors:sp-initiated-only).

**User or Admin.** Each IdP configuration is set to User or Admin for Single Sign-On. Using the same IdP for both needs a configuration for each, different IdPs can serve admin and user SSO, and SCIM is only available for user SSO. [zpa.authentication.idp-configuration:user-or-admin] A configuration set to use Both (admin and user SSO) shows Both selected under Single Sign-On, and changing it needs a new IdP configuration. On the IdP Configuration page such a configuration is listed with Admin, User in that column. [zpa.authentication.idp-configuration:legacy-both]

**Fields.** An IdP configuration's name cannot contain special characters other than periods, hyphens and underscores. [zpa.authentication.idp-configuration:name-rules] The Domains field shows the primary and secondary authentication domains configured for the organization, and a domain can be associated with only one IdP. [zpa.authentication.idp-configuration:domains] Uploading the IdP metadata file fills in the SAML configuration; the Single Sign-On URL (the IdP portal users are directed to) and the IdP Entity ID are entered otherwise. For users to authenticate from the internet the URL must be publicly resolvable, and it must be protected with HTTPS. [zpa.authentication.idp-configuration:saml-fields] The configuration selects whether Private Access sends a Signed or Unsigned SAML request and whether HTTP-Redirect is used. Force Authentication defaults to Disabled and, when enabled, makes users of that IdP re-enter credentials at reauthentication regardless of SAML IdP session state. Login Hint defaults to Enabled and sends the username in the authentication request so the IdP can prepopulate it. [zpa.authentication.idp-configuration:request-and-session-options]

**Arbitrary domains.** Use with Arbitrary Domains lets third-party users use SSO with any authentication domain without adding it to the selected domains, for clientless access (browser-based access, Privileged Remote Access and Cloud Browser Isolation). The option appears only when Single Sign-On is User, and it does not work with Zscaler Client Connector. [zpa.authentication.idp-configuration:arbitrary-domains-purpose] Only one IdP configuration can have arbitrary domains enabled unless the existing one is deleted or disabled. A single IdP created without a domain and with Use with Arbitrary Domains enabled makes the Client Connector login fail, so a domain must be configured on at least one IdP. For some tenants the option is unavailable with a single IdP and more than one IdP must be configured. The option cannot be disabled on an IdP configured for emergency access. [zpa.authentication.idp-configuration:arbitrary-domains-constraints] Which tenants cannot use the option with a single IdP is open [gap:zpa.authentication.idp-configuration:arbitrary-domains-tenants].

**Setup flow and status.** The SP metadata and certificate information is specific to the IdP and the Single Sign-On selection. Setup can be paused with Pause to add the SP information to the IdP first, and the status of a configuration paused during setup shows as resume. [zpa.authentication.idp-configuration:sp-metadata-pause] After saving, the status can be changed to Disabled at any time by editing the configuration. Changing it from Enabled to Disabled applies to SAML authentication and, with clientless access, to arbitrary domains (Privileged Remote Access, Browser Access and Cloud Browser Isolation). [zpa.authentication.idp-configuration:status-and-disable] A user SSO configuration is verified by importing SAML attributes: if Private Access is correctly configured as the SP, the link redirects to the IdP's SSO login page. For an admin SSO test, the NameID in the SAML assertion must be set to the username of a Private Access admin. The test URLs are https://samlsp.private.zscaler.com/auth/v2/login?domain=<domain name>&ssotype=test and https://adminsamlsp.private.zscaler.com/auth/v2/login?domain=<domain name>&ssotype=test. [zpa.authentication.idp-configuration:verify]

**Policy settings on the IdP.** SAML Attributes for Policy on the IdP allows that IdP's SAML attributes in Access, Client Forwarding and Timeout Policies. After it is first enabled Zscaler requires the user to reauthenticate in Client Connector, and the page says policies with SCIM criteria are evaluated for that user only after the user successfully reauthenticates. Zscaler recommends disabling the setting only after SAML attributes are removed as policy criteria, because with it disabled a rule with SAML attribute criteria might not be evaluated. [zpa.authentication.idp-configuration:saml-attributes-for-policy] The page's mention of SCIM criteria under the SAML setting may be a copy error [gap:zpa.authentication.idp-configuration:scim-criteria-under-saml-setting]. On the IdP configuration page the setting that allows SCIM attributes and SCIM groups from the IdP in Access, Client Forwarding and Timeout Policies is labelled SCIM Attributes for Policy. Zscaler recommends disabling it only after SCIM attributes and SCIM groups are removed as policy criteria in a rule. [zpa.authentication.idp-configuration:scim-attributes-for-policy] The page recommends not enabling SCIM when first setting up an IdP, and says the SCIM-for-policy setting applies only if SCIM Sync is enabled as well. [zpa.authentication.idp-configuration:scim-not-at-first-setup] The SCIM setting is named differently on the access policy page [divergence:zpa.authentication.idp-configuration:scim-policy-setting-name]; that page's claim is [For Private Access to process SAML and SCIM criteria in a rule, the SAML Attributes for Policy setting must be enabled for SAML and the SCIM Attributes and Groups for Policy setting for SCIM on the IdP.](kb:zpa.saml-attributes.policy-criteria:idp-setting-required).

**Authentication Service.** IdPs migrated to Authentication Service are disabled, marked with an orange Info icon, and deleted 30 days after migration. An IdP configured for both admin and user SSO is updated to User SSO after 30 days, and the Add button is hidden when subscribed to Authentication Service for users. [zpa.authentication.idp-configuration:auth-service-migrated-idps] The page itself is described two ways [divergence:zpa.authentication.idp-configuration:idp-page-under-auth-service]. IdP configurations managed by Zscaler are read only and cannot be edited. An IdP cannot be deleted if it is used for emergency access or managed by Zscaler. [zpa.authentication.idp-configuration:managed-and-delete]

**Best practices.** The user SSO best practices say that, if Client Connector is also used for Internet & SaaS, its authentication should also use SAML and ideally the same IdP as Private Access to avoid a double login. A Private Access account cannot be associated with a Client Connector account on a different cloud. With the same IdP in both products users reach applications through Client Connector or Browser Access; if Internet & SaaS does not use the Private Access IdPs, authentication domains must be configured in Private Access and users reach applications through Browser Access only. If a Private Access IdP's authentication domain is not associated with the Internet & SaaS IdP, users see an error using that domain in Internet & SaaS. [zpa.authentication.idp-configuration:with-internet-saas] For admin SSO a Private Access admin account must exist and the NameID in the SAML assertion must match it. Zscaler recommends configuring multiple IdPs for users authenticating through Browser Access who do not require Client Connector, and for organizations using Client Connector only for Private Access. [zpa.authentication.idp-configuration:admin-sso-and-multiple-idps]

Certificates are in [IdP certificates and service provider certificate rotation in Private Access](kb:zpa.authentication.idp-certificates), moving to another IdP in [Migrating Private Access to a new IdP](kb:zpa.authentication.idp-migration), the per-IdP guides in [Per-IdP setup guides for Private Access SSO (Okta, OneLogin, PingOne, Azure AD, ADFS, SafeNet)](kb:zpa.authentication.idp-guides), and enabling SCIM in [Enabling SCIM for Private Access: endpoint, token, policy setting and IdP guides](kb:zpa.scim.setup).

What to check:
1. Whether the configuration is for User or Admin SSO, and whether a legacy Both configuration is involved, before reasoning about SCIM or arbitrary domains.
2. Whether the tenant is on Authentication Service, which changes what the page offers; the sources differ on read only against hidden.
3. Whether the setting that allows SCIM attributes and groups in policy is enabled and the user has reauthenticated, keeping in mind that the pages name it differently.
4. Whether an IdP-initiated sign-in is being attempted by a user or an admin, since the sources scope IdP-initiated sign-in differently.

Sources disagree (name both sides):
- Whether the IdP Configuration page is read only or hidden for a tenant subscribed to Authentication Service. [divergence:zpa.authentication.idp-configuration:idp-page-under-auth-service]
  - zscaler-help: The page is read only if subscribed to Authentication Service for users.
  - zscaler-help: The page is hidden if subscribed to Authentication Service and the feature is enabled for the tenant.
  Impact: The pages differ on the state (read only against hidden) and on the condition (a subscription for users against a subscription plus the feature enabled); neither says which holds for a given tenant.
- Whether Private Access accepts only SP-initiated sign-in or also IdP-initiated sign-in for admin SSO. [divergence:zpa.authentication.idp-configuration:sp-initiated-scope]
  - zscaler-help: The Client Connector error list gives, for error 42017 (IdP originated SSO not supported), that only SP-initiated SSO is supported with Private Access.
  - zscaler-help: User SSO is SP initiated; admin SSO can be SP initiated or IdP initiated.
  Impact: The two may differ only in scope, since error 42017 sits in the Client Connector error list, but neither page states that scope; an IdP-initiated admin sign-in is therefore not settled by either alone.
- The name of the IdP setting that allows SCIM attributes and groups in policy. [divergence:zpa.authentication.idp-configuration:scim-policy-setting-name]
  - zscaler-help: The access policy page calls it SCIM Attributes and Groups for Policy.
  - zscaler-help: The IdP configuration page calls it SCIM Attributes for Policy.
  - zscaler-help: The SCIM enabling page also calls it SCIM Attributes for Policy.
  Impact: A search for the setting by one label misses the pages that use the other; the descriptions are the same, so they most likely name one setting, but no page says so.

Not known (open gaps):
- Whether policies with SCIM criteria under the SAML Attributes for Policy setting is a copy error [gap:zpa.authentication.idp-configuration:scim-criteria-under-saml-setting]: settled by support-ticket or lab-test
- Which tenants cannot use Use with Arbitrary Domains with a single IdP [gap:zpa.authentication.idp-configuration:arbitrary-domains-tenants]: settled by support-ticket
