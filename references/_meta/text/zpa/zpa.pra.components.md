# PRA components: portals, consoles, approvals, credentials, policies and limits (zpa.pra.components)
Also called: privileged portal; privileged console; pra portal; pra components; pra limits; emergency access pra; arbitrary authentication domains; pra user activity diagnostics; pra console per protocol; delete privileged console

PRA is built from a portal, consoles, approvals, credentials, PRA policies and PRA-enabled application segments.

**Portal.** A privileged portal is what end users use to reach designated servers. It has a URL and a Browser Access certificate that Private Access uses when a user opens the portal, and it can be branded with the customer's domain and text. [zpa.pra.components:portal] The PRA Portal is a catalog that shows the privileged consoles an end user can access after authenticating to the configured IdP. It also shows future and expired consoles, the live privileged sessions the user has access to if given permission for live sessions, and a notification banner if one is set. [zpa.pra.components:portal-catalog] A privileged portal must exist before a privileged console is created, because a console is assigned to existing portals, and the same console can appear in more than one portal. [zpa.pra.components:portal-before-console] The portal's fields, certificates and what end users see are in [PRA privileged portals and the PRA Portal: fields, certificates and DNS, what end users see, and console login](kb:zpa.pra.portals).

**Setup.** Using PRA requires authorization, and the Zscaler Account team is the contact for more information. [zpa.pra.components:authorization-prerequisite] The step-by-step guide has the admin first create a privileged portal, then select the application segments the portal includes and assign PRA-enabled segments to a privileged console, with the protocol set up beforehand because a console must be assigned one. After the PRA basics it adds PRA-specific policies, then Step 5 Add Privileged Approvals and Step 6 Emergency Access and Arbitrary Domains. [zpa.pra.components:setup-order] The pages disagree on whether the portal or the application segment comes first [divergence:zpa.pra.components:portal-or-segment-first].

**Console.** A privileged console is what the end user selects in the PRA Portal. Each console is assigned a protocol, a domain and a port number, and users can reach only the consoles they have been granted. [zpa.pra.components:console] A host that must be reached over two protocols, such as one bastion with SSH and RDP, needs two privileged consoles, one per protocol. [zpa.pra.components:console-per-host-protocol] A privileged console takes a name that cannot contain special characters other than periods, hyphens and underscores, Display on Console (shows the console on the end user's Privileged Remote Access portal), a protocol of VNC, RealVNC, SSH or RDP, a valid domain name, a port number and a description; its logo represents whether it is a VNC, RealVNC, SSH or RDP connection. [zpa.pra.components:console-fields] A privileged console is assigned to existing portals, which can be both the Default Microtenant portal and the Microtenant portals the Default Microtenant has assigned to Microtenants, and to applications from the Default Microtenant or a shared Microtenant. When a console created in a Microtenant uses an application segment inherited from the Default Microtenant, the page says to check with the Default Microtenant admin whether a privileged approval is required. [zpa.pra.components:console-portals-and-apps] SSH-enabled privileged consoles support the modern elliptic-curve host algorithms ecdsa-sha2-nistp521, ecdsa-sha2-nistp384 and ecdsa-sha2-nistp256. [zpa.pra.components:ssh-host-algorithms] Whether RSA or Ed25519 host keys work is open [gap:zpa.pra.components:ssh-host-algorithms-complete]. Deleting a privileged console stops new connections and removes it from the end user's PRA Portal. Connections that already exist stay accessible until the browser is closed. [zpa.pra.components:console-delete]

**Time and credentials.** A privileged approval is a set start and end date and time during which an end user has access to a privileged console. After the window expires the user can no longer access the console. [zpa.pra.components:approvals-def] Privileged credentials give short-term end users (such as contractors and third-party users) access without a personalized login. To set a privileged credential with a privileged console, a privileged credentials policy must be created. [zpa.pra.components:credentials-def]

**Policies and segments.** There are three PRA-specific policies, privileged credentials policies, consoles policies and portals policies. An admin console may show all, one or none, depending on how those policy options are enabled for the tenant. [zpa.pra.components:two-pra-policies] The Consoles Policy and Privileged Credentials Policy pages are displayed if the account has those features enabled, and with only one of them the other page is not visible; if neither is enabled the Privileged Policy tab is not shown. The Consoles Policy page contains the File Transfer feature and the Privileged Credentials Policy page the Credential Mapping feature. [zpa.pra.components:privileged-policy-tab] Portals policies manage user permissions for PRA Portal features, including My Approvals and the PRA File Transfer System, and a portals policy can be configured once the privileged portals it controls have been created. [zpa.pra.components:portals-policy] The portals policy options are in [PRA portals policy: file, inspection and approval permissions in the PRA Portal](kb:zpa.pra.portals-policy). When configuring a defined application segment an admin can enable PRA and assign a protocol; a PRA-enabled segment is then selectable when creating a privileged console, and selecting the console in the PRA Portal takes the user to that segment. [zpa.pra.components:segment-enablement]

**Supporting features.** [One existing IdP is designated for emergency access, and a privileged approval can select it to apply its date and time rules to the emergency access users, who are managed in an Okta IdP and viewed on the Emergency Access Users page.](kb:zpa.emergency-access.scope:one-idp) Arbitrary authentication domains let third-party users sign in to a privileged portal with single sign-on for any authentication domain without naming a specific one, and can be enabled for one IdP at a time. [zpa.pra.components:arbitrary-auth-domains]

**Visibility and limits.** PRA data appears on the User Activity Diagnostics page, which covers session recordings, credentials policies, consoles policies, file transfer and PRA errors, and on the Privileged Sessions page for recorded sessions. [zpa.pra.components:diagnostics] The documented PRA limits are 100 privileged portals (a portal within the Default Microtenant can link a maximum of 9,000 privileged consoles), 10 privileged consoles by default (raisable by license to 9,000), 10,000 privileged credentials, 500 credential pools with 100 credentials each, and 20,000 privileged approvals with 200 application segments per approval. [zpa.pra.components:limits] The cap on consoles for a portal outside the Default Microtenant is open [gap:zpa.pra.components:consoles-per-portal-microtenant]. The segments-per-approval figure is disputed by the Configuring Privileged Approvals page, recorded in [PRA approvals: requesting, reviewing and expiry](kb:zpa.pra.approvals).

**Files page.** The PRA Files page shows data for files uploaded to My Files in the PRA File Transfer System. Files uploaded through a default PRA Portal can be viewed only in the Global tenant, and files uploaded through a Microtenant PRA Portal only on that Microtenant's Files page. It covers 1 Hour to 14 Days and counts Malicious, Success (successfully inspected) and Uninspected files. [zpa.pra.components:files-page] A file record on the PRA Files page gives, among other fields, the file size, with a maximum upload of 1 GB, the MD5 hash value and the country selected for the portal policy of the portal the file was uploaded to. The ampersand (&) character cannot be used in the Add Filters field. [zpa.pra.components:files-fields]

The path a session takes is open [gap:zpa.pra.components:data-path]. Terraform behavior when portals and consoles are deleted is in [What the ZPA Terraform provider does when deleting objects with dependents](kb:zpa.terraform.delete-paths).

What to check:
1. Whether the portal exists and the console is assigned to it before looking at policy.
2. Whether a host reached over two protocols has a console for each.
3. Whether a limit is the cause of a failed create, using the documented counts; the segments-per-approval figure is disputed in zpa.pra.approvals.
4. Whether the setup order assumed by an answer rests on one page, since the pages disagree on whether the portal or the application segment comes first.
5. Whether a missing Consoles Policy or Privileged Credentials Policy page is because the account lacks that feature.
6. Whether a question about the session path rests on the unverified gateway description.

- Whether the privileged portal is created before the PRA application segment: the step-by-step guide puts the portal first, and the Configuring Privileged Portals page starts from an application segment already added with PRA. [divergence:zpa.pra.components:portal-or-segment-first]
  - zscaler-help: The privileged portal is created first, and application segments are selected after it exists.
  - zscaler-help: The Privileged Portals page is reached after an application segment with PRA has been added.
  Impact: This is a sequencing conflict: the second page's sentence is a page-access precondition, but it puts an application segment before the portal where the guide puts the portal first. An answer about a setup order should not state either order as the one that is required.
