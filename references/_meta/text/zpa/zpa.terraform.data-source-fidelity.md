# What ZPA Terraform data sources return, drop, or get wrong (zpa.terraform.data-source-fidelity)
Also called: zpa data source missing field; zpa data source empty block; zpa data source panic; zpa_policy_type data source error; zpa_lss_config_controller name not supported; zpa data source set error ignored; zpa data source partial state; zpa lss status codes wrong; zpa segment group data source udp port ranges; zpa cbi external profile banner_id empty; zpa data source phantom block; microtenant data source user block empty

A ZPA data source is only as good as the copy it makes of the API object. Each data source is hand-written: a schema, a read function, and flatteners that copy SDK fields into Terraform state. Which object a data source returns is a separate question, covered in [Which object a ZPA Terraform data source actually returns](kb:zpa.terraform.data-source-selection); this subject is about the content of the object once it has been chosen.

## Reads that fail or crash on ordinary data

Up to v4.4.14, the `zpa_policy_type` flattener put keys into every rule map (`microtenant_id`, `microtenant_name`, `zpn_isolation_profile_id`, `zpn_inspection_profile_name`), and into every condition and operand map (`microtenant_id`), that the nested `rules` schema did not declare. The read checks the error of `d.Set("rules", ...)`, so a policy set that contained a rule was expected to return a diagnostic instead of state. v4.4.15 declares all of those keys in the schema, and its changelog says the data source no longer fails when the policy set has rules. [zpa.terraform.data-source-fidelity:policy-type-flattener-emits-undeclared-keys] What the plugin SDK does with a nested map that has undeclared keys is open [gap:zpa.terraform.data-source-fidelity:plugin-sdk-set-unknown-key]. Up to v4.4.14, the LSS config data source read looked up by name through `d.Get("name")` and `GetByName`, but the schema's only top-level selector was `id`: `name` was declared only inside the nested `config`, `policy_rule` and operand blocks. A configuration that set `name` at the top level, as the provider's documentation example does, was not a valid argument, so only the ID path was reachable and the plan failed validation. v4.4.15 adds an optional, computed top-level `name` argument. [zpa.terraform.data-source-fidelity:lss-name-selector-not-top-level]

**Nil dereferences.** The SDK declares an LSS resource's `config` as a pointer with no `omitempty`, and the data source and the `zpa_lss_config_controller` resource's Read both pass it straight to `flattenLSSConfig`, which reads its fields with no nil check. A decoded response with no `config` (absent or null) makes either read dereference nil and panic. [zpa.terraform.data-source-fidelity:lss-config-flattened-without-nil-check] The SDK's LSS `GetByName` scans the full list and compares `lss.LSSConfig.Name` with no nil check on the pointer, so one list item without a `config` object panics the name lookup before the provider sees a result. [zpa.terraform.data-source-fidelity:lss-by-name-dereferences-config] The SDK declares a policy-rule condition's `operands` as `*[]Operands`, and the LSS data source's `flattenLSSConditionOperands` reads it as `len(*operands.Operands)` on its first line and then ranges over `*operands.Operands`; its caller calls it for each condition inside the map literal it builds, with no check first. [zpa.terraform.data-source-fidelity:lss-condition-operands-dereferenced] So a condition whose operands are absent or null panics the read. [zpa.terraform.data-source-fidelity:lss-condition-null-operands-panic] How often these fire is open [gap:zpa.terraform.data-source-fidelity:api-omits-nested-objects].

## Objects that appear when they should not

**Blocks built from zero values.** `flattenLSSConfig` returns a one-element list unconditionally, so a non-nil but empty `config` object becomes a `config` block of zero values. The sibling `flattenLSSPolicyRule` does check for nil and returns nothing, so the two nested objects of one response are treated differently. [zpa.terraform.data-source-fidelity:lss-empty-config-becomes-a-block] The app connector controller data source takes the address of the SDK's value-typed `AssistantVersion` and passes it to `flattenAssistantVersion`, whose only guard is a nil-pointer check. The pointer is never nil, so the helper builds a map and the data source reports an `assistant_version` block even when the API sent no such object. [zpa.terraform.data-source-fidelity:app-connector-assistant-version-always-a-block] Every service edge in a service edge group is flattened by passing the address of its value-typed `PrivateBrokerVersion` to a helper that only checks for a nil pointer, so each edge reports a `private_broker_version` block even when it has none. The single service edge data source handles the same shape correctly by testing the broker's `ID` first. [zpa.terraform.data-source-fidelity:service-edge-group-brokers-always-blocks] The CBI external profile data source flattens `security_controls` and `user_experience` whenever the SDK pointer is non-nil, and each flattener returns one outer block with every scalar copied. A decoded empty object therefore appears as a block of zero values. The same file's `flattenDebugMode`, called when `resp.DebugMode` is non-nil, likewise returns one block with both fields copied. [zpa.terraform.data-source-fidelity:cbi-external-profile-empty-objects-become-blocks] So the three blocks cannot tell "not configured" from "all off". [zpa.terraform.data-source-fidelity:cbi-external-profile-blocks-ambiguous] The customer version profile flattener returns a block when either request-ID string is non-empty and then calls `strings.Split(..., ",")` on both. [zpa.terraform.data-source-fidelity:customer-version-profile-empty-side-becomes-empty-id] Go's `strings.Split` returns `[""]` for an empty string, so a profile with only one side set reports the other side as a list holding one empty customer ID. [zpa.terraform.data-source-fidelity:customer-version-profile-one-side-empty-id]

## Fields that never arrive

The CBI external profile data source declares `banner_id` and `certificate_ids` as outputs and the SDK profile model carries both, but the read sets only name, description, default flag, href, regions and the three nested blocks. A profile's banner and certificate associations are never returned. [zpa.terraform.data-source-fidelity:cbi-external-profile-associations-never-set] Many ZPA data sources return a smaller object than the SDK model holds: a field is declared in the schema (or exists in the SDK struct) but the read or its flattener never sets it, so it reads as empty or absent with no error. Representative cases: application segment `default_idle_timeout` and `default_max_age`; Browser Access nested `clientless_apps` `certificate_name`, `hidden`, `local_domain`, `path`; PRA application segment (no `creation_time`, `modified_time`, `icmp_access_type`, `use_in_dr_mode`, `is_incomplete_dr_config`); inspection profile `common_global_override_actions_config` and WebSocket controls; app connector group `version_profile_visibility_scope`; cloud connector group `signing_cert`; customer version profile all seven `number_of_*` counters; IDP `sp_entity_id` in user metadata; CBI banner `persist`; segment group `dynamic_discovery` (and `udp_port_ranges`); PRA portal `user_portal_name`; service edge group nested `publish_ipv6`, `runtime_os`, `microtenant_id`, `microtenant_name`; LSS policy rule `bypass_default_rule`, `default_rule`, `name`, `lss_default_rule`; `zpa_policy_type` rule `bypass_default_rule`, `isolation_default_rule`, `zpn_cbi_profile_id`. [zpa.terraform.data-source-fidelity:fields-declared-or-in-sdk-but-not-set] Up to v4.4.14, the LSS status-codes data source set `zpn_auth_log` from `resp.ZPNAstAuthLog`, the same value it then set `zpn_ast_auth_log` from. The SDK keeps a separate `ZPNAuthLog` field, so the ordinary auth-log mapping was never returned and the AST mapping was returned twice. v4.4.15 sets `zpn_auth_log` from `resp.ZPNAuthLog`. [zpa.terraform.data-source-fidelity:lss-status-codes-auth-log-mapped-from-ast] The SDK half of the segment group UDP defect is [The segment group's nested `Application` struct tags its UDP port ranges `udpPortRangesg`. Responses carrying `udpPortRanges` do not fill the field, and a populated field is written under the misspelled key. The sibling TCP field uses `tcpPortRanges`, and the application segment SDK tags its UDP port ranges `udpPortRanges`.](kb:zpa.sdk-go.service-defects:segment-group-udp-key-misspelled).

## Mismatched schema and flattener

Up to v4.4.14, the microtenant data source's user flattener wrote keys and types that did not match its own schema: one key was `"operation_type"` followed by a tab character, the modification user was written as `modified_by` where the nested schema declared `modifiedby`, and `phone_number` and `pin_session` (and `role_id`) were declared with types that differed from the SDK's string and bool fields. v4.4.15 fixes the key, adds `modified_by` to the nested schema and declares `phone_number` as a string, `pin_session` as a bool and `role_id` as a string. [zpa.terraform.data-source-fidelity:microtenant-user-flattener-keys-mismatch-schema] The microtenant data source discards the result of setting the `user` block (`_ = d.Set("user", ...)`). Up to v4.4.14 that meant the key and type mismatches in the user flattener could not surface as an error, and a rejected block left the read successful and `user` empty or partial; v4.4.15 fixes those mismatches, but a block rejected for another reason would still go unreported. [zpa.terraform.data-source-fidelity:microtenant-user-set-error-discarded]

## Why none of this is loud

Almost every ZPA data source discards `d.Set` errors with `_ = d.Set(...)` for scalar and nested fields alike, so a field the schema cannot accept is lost without a diagnostic and the read still returns success with partial state. Unchecked calls exist in almost every data source; only two check every one. [zpa.terraform.data-source-fidelity:set-errors-ignored-across-data-sources] The service edge group data source discards the errors of `d.Set` for `service_edges` and `trusted_networks`, the two nested lists built by flatteners. The `zpa_policy_type` and app connector controller data sources check the equivalent nested sets, so the handling differs between data sources of the same family. [zpa.terraform.data-source-fidelity:service-edge-group-nested-sets-ignored]

What to check:
1. Whether a field that reads empty is declared and set by the read path, before it is treated as unconfigured.
2. Whether a block made only of zero values is treated as unknown rather than as a configured object.
3. Whether a block the data source reports is configured, before a consumer tests whether it exists or takes an ID from it.
4. Whether the `zpa_policy_type` rules and the microtenant `user` block populate on the plugin SDK and provider versions in use, before either is used as an input.
5. Whether `zpn_auth_log` on `zpa_lss_config_status_codes` is used as the auth log, since on provider v4.4.14 or older it carries the AST mapping rather than the ordinary one.
