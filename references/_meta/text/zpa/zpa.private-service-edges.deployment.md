# Private Service Edge platforms, host OS maintenance, capacity and limits (zpa.private-service-edges.deployment)
Also called: private service edge platforms; pse vm image; pse sizing; pse host os update; pse capacity; pse high availability; how many private service edges; pse limits; pse n+1; rhel 9 pse; pse image distribution

Planning a Private Service Edge deployment is a question of platform, host maintenance, capacity and limits.

**Platforms.** Zscaler distributes Private Service Edge images for enterprise data centers and local private cloud environments such as VMware, and the platforms listed as supported by Private Access are AWS, Docker, GCP, Linux, Microsoft Azure, Microsoft Azure Local, Microsoft Hyper-V and VMware platforms. [zpa.private-service-edges.deployment:supported-platforms] The software page and the Nutanix guide differ from this list: [Private Service Edge software and deployment steps by platform](kb:zpa.private-service-edges.platforms). Security Technical Implementation Guide (STIG) images are available for AWS, GCP, Microsoft Azure and VMware by default. [zpa.private-service-edges.deployment:stig-images] The Linux guide's STIG list differs from this one: [Private Service Edge software and deployment steps by platform](kb:zpa.private-service-edges.platforms). The console shows each Private Service Edge's run-time OS (for example Enterprise Linux 9) and the compile-time package OS on which its RPM binary is packaged (for example Red Hat Enterprise Linux 9). [zpa.private-service-edges.deployment:host-os-enterprise-linux] [A ZPA Appliance is a Private Service Edge host platform: the console shows "ZT-8010-Zscaler Red Hat Image" as the host platform for one.](kb:zpa.private-service-edges.what-it-is:zpa-appliance) The July 23, 2026 release summary lists a Private Service Edge Docker image updated to use high ciphers for microdnf calls, and updated Red Hat Enterprise Linux 9 Private Service Edge images for AWS, GCP, Microsoft Azure, Nutanix AHV and VMware that include a 4 GB boot partition, which exceeds Red Hat's recommendations to help support seamless OS updates. [zpa.private-service-edges.deployment:images-july23] The August RPM release is not in the current capture [gap:zpa.private-service-edges.deployment:release-images]. The reference Terraform modules are in [Reference Terraform modules for Private Service Edges on AWS and Azure](kb:zpa.private-service-edges.reference-modules).

**Sizing and limits.** Each Private Service Edge supports up to 500 Mbps aggregate (inbound plus outbound) throughput, so a 1 Gbps connection needs 2 to 3 Private Service Edges; throughput varies with double encryption, AppProtection and ZDX. [zpa.private-service-edges.deployment:throughput-sizing] For up to 500 Mbps per Private Service Edge: up to 2,000 active users need 8 GB RAM (10 GB with ZDX) and 4 vCPUs; up to 4,000 need 16 GB (18 GB) and 8 vCPUs; up to 10,000 need 32 GB (34 GB) and 16 vCPUs; disk is 64 GB thin provisioned and at least 1 NIC. [zpa.private-service-edges.deployment:sizing-table] Some platform procedures give lower values than this table: [Private Service Edge software and deployment steps by platform](kb:zpa.private-service-edges.platforms). A platform needs Intel x86_64/AMD64, systemd, root or sudo, DNS resolution, a provisioning key or OAuth token, and a static MAC address. [zpa.private-service-edges.deployment:platform-prereqs] Session limits are not stated [gap:zpa.private-service-edges.deployment:session-limits]. The ranges and limitations table lists 100 Private Service Edges, 100 Private Service Edge groups and 100 Private Service Edge provisioning keys. [zpa.private-service-edges.deployment:tenant-limits] The per-group maximum is open [gap:zpa.private-service-edges.deployment:max-per-group].

**Capacity and availability.** Zscaler recommends deploying Private Service Edges in groups for high availability and horizontal scaling, and every Private Service Edge belongs to a group. [zpa.private-service-edges.deployment:groups-for-ha] Service Edges are deployed in active-active mode for availability and redundancy. [zpa.private-service-edges.deployment:active-active] Peak sustained CPU utilization should stay below 70% taking into account all Private Service Edges in the group, so that each stays below 70% if one becomes unavailable; two Private Service Edges both at 50% would exceed 70% on the survivor. [zpa.private-service-edges.deployment:cpu-headroom] To reduce CPU on individual Private Service Edges, add a Private Service Edge to the group, or deploy dedicated groups for specific application segments. [zpa.private-service-edges.deployment:scale-out-options] Zscaler recommends deploying Private Service Edges in pairs (N+1), where N is the number needed by the sizing requirements, to keep availability during software upgrades. [zpa.private-service-edges.deployment:pairs-n-plus-one] Zscaler recommends more Private Service Edges with lower specifications over fewer with higher specifications, because a failure of a large one affects more traffic; they scale elastically within a group. [zpa.private-service-edges.deployment:scale-out-small] Selection among members is unverified [gap:zpa.private-service-edges.deployment:selection-within-group].

**Host OS maintenance.** Host OS and software-package updates are the organization's responsibility, while Zscaler updates the component software; the captured procedure takes RHEL 9.4 and 9.5 to RHEL 9.6 and later, and Zscaler recommends updating the OS at least every 5 weeks. [zpa.private-service-edges.deployment:org-owns-host-os] [Zscaler recommends updating the OS at least every 5 weeks and validating connectivity to the update servers; prebuilt images must be provisioned to a Private Access tenant to receive updates through the OS package manager. The captured procedure moves RHEL 9.4 and 9.5 to 9.6 and later.](kb:zpa.app-connectors.upgrades:os-update-cadence) Automated OS security updates are available only for prebuilt Private Service Edge images on RHEL 9.x; a Private Service Edge installed manually from an RPM on a custom RHEL 9.x build is not supported. [zpa.private-service-edges.deployment:prebuilt-os-updates] A host OS update is scheduled by local policy; users should be warned of rolling reconnections, and each component is estimated to be down for 20 minutes. [zpa.private-service-edges.deployment:os-update-downtime] [A host OS update is estimated at 20 minutes of downtime per component; all connectors in a group should not be updated at once, though several may be updated together if enough running connectors remain to carry the traffic.](kb:zpa.app-connectors.upgrades:os-update-concurrency)

**Linux guide requirements.** The Private Service Edge Linux guide says Security Technical Implementation Guide (STIG) images are provided for AWS, GCP, Microsoft Azure, Nutanix and VMware by default, and that the remaining private and public cloud VM images provided by Zscaler are essentially unmodified operating systems (currently based on RHEL 9.x). [zpa.private-service-edges.deployment:stig-images-guides] The Linux guide says the Private Service Edge VMs distributed by Zscaler for use in private clouds are configured without any remotely accessible services running, swap partitions are disabled on the Private Service Edge and its VMs, and the credentials on the default admin account must be changed with the passwd command. [zpa.private-service-edges.deployment:os-security] The Linux guide says Private Service Edges require that Client Connector be at least on version 2.1.2. [zpa.private-service-edges.deployment:client-connector-version] The Linux guide says Private Service Edges are reachable over the internet for remote users in a disaster recovery scenario, or when the Private Service Edge is the closest Service Edge. [zpa.private-service-edges.deployment:internet-reachable] Per-platform steps and where the pages disagree are in [Private Service Edge software and deployment steps by platform](kb:zpa.private-service-edges.platforms).

**RHEL 9 migration.** The Private Service Edge RHEL 9 migration page says to use a fresh install for all deployments, that the EL9 repository must be used with a RHEL 9 base OS and older platform binaries (EL7/EL8) are not supported, that /opt/zscaler/var must be empty before install, that yum upgrades from EL7/EL8 to RHEL9 are not supported, and that it requires ESXi version 7.0 Update 2 or newer, including ESXi 8.x. [zpa.private-service-edges.deployment:rhel9-migration-rules] The migration page's steps ensure the yum repository points to https://yum.zpagov.net/yum/el9, add trusted networks and enable Publicly Accessible (if applicable) on the new Private Service Edge groups, optionally disable the groups 15 minutes before the regional off-hours maintenance window to let connections drain, and during regional off hours remove trusted networks and disable public access (if applicable) on CentOS 7 groups. [zpa.private-service-edges.deployment:rhel9-migration-steps] The repository address conflicts with the install step, recorded in [Private Service Edge software and deployment steps by platform](kb:zpa.private-service-edges.platforms).

**Editing a deployed instance.** On the Edit Private Service Edge page only these fields can be modified: Name, Description, Publish IPs or Domains, Automatically Publish IPv6, Listen IPs and Status (enable or disable the Private Service Edge). Private Service Edges that are managed by Zscaler are read only and cannot be edited. [zpa.private-service-edges.deployment:editable-fields] The meaning of the address fields is in [Tunnels, certificates and firewall requirements on the Private Service Edge path](kb:zpa.private-service-edges.data-path).

Enrolling a new instance: [Enrolling a Private Service Edge](kb:zpa.private-service-edges.enrollment). Software update scheduling for the group: [Private Service Edge groups: membership, software updates and version profiles](kb:zpa.private-service-edges.groups).

What to check:
1. Which platform the Private Service Edge reports (host platform, host OS, package OS) before choosing an update or support path.
2. Whether the host was built from the prebuilt image or installed manually from an RPM, since automated OS security updates apply only to prebuilt RHEL 9.x images.
3. Whether peak sustained CPU stays under 70% across the group with one Private Service Edge down, which sets the headroom.
4. Whether the tenant is near the 100 Private Service Edge, group or provisioning key limit.
5. Whether a planned host OS update touches every member of a group at once.
