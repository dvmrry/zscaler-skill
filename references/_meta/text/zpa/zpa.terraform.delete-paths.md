# What the ZPA Terraform provider does when deleting objects with dependents (zpa.terraform.delete-paths)
Also called: terraform destroy zpa; terraform destroy partial detach; zpa delete leaves references; delete pra portal deleted console; server group delete reported success; segment group delete partially detached; detach from policy rules on delete

Before deleting a PRA portal, PRA console, segment group or server group, it walks the objects that reference it and rewrites them. The outcome depends on how each of those cleanups handles failure, and they differ.

**PRA portals.** Deleting a PRA portal first runs a cleanup that walks every PRA console, and returns an error without deleting the portal if that cleanup fails. [zpa.terraform.delete-paths:portal-delete-detaches-first] When removing the portal from a console would leave that console with no portals, the cleanup deletes the whole console instead of updating it. The only test is the remaining portal count. [zpa.terraform.delete-paths:portal-cleanup-deletes-emptied-console] A PRA console is also managed as its own Terraform resource, with its own name, description, icon text, application and portal list. The portal cleanup reads none of those before deleting a console: it checks only the remaining portal count. [zpa.terraform.delete-paths:console-is-its-own-resource] So deleting a portal that is the only portal of a console also deletes that console, including a console Terraform manages as its own resource (in another configuration or state, or when the portal is removed or targeted alone). On the next refresh that console drops out of state and the plan recreates it. [zpa.terraform.delete-paths:portal-delete-can-delete-console] The portal cleanup updates or deletes consoles one at a time in a loop and returns on the first failure. Consoles handled earlier in the loop keep their change, and the resource's delete returns that error at once; the portal's `praportal.Delete` call comes after it, under the comment that deletion proceeds after successful detachment. [zpa.terraform.delete-paths:portal-cleanup-partial-on-failure] A console deleted by the portal cleanup is deleted with a direct API call, not through the console resource's delete, so the credential-policy detach that the console resource runs first is skipped. [zpa.terraform.delete-paths:portal-deleted-console-skips-policy-detach] Whether the API allows a console with no portals is open [gap:zpa.terraform.delete-paths:api-console-without-portals].

**PRA consoles.** Deleting a PRA console first removes it from policy rules of one type only, CREDENTIAL_POLICY, and aborts the delete if that cleanup fails. [zpa.terraform.delete-paths:console-delete-cleans-credential-policy-only] The console's policy cleanup rewrites matching rules one at a time, making up to three attempts at each, and returns on the first rule that still fails. Rules rewritten earlier stay changed and the console is not deleted. [zpa.terraform.delete-paths:console-policy-cleanup-partial-on-failure]

**Segment groups.** Deleting a segment group first rewrites policy rules in two sequential loops, version 1 rules and then version 2 rules, and each loop returns an error on the first rule update that fails, except a not-found update, which is skipped. The group delete call comes only after both succeed. [zpa.terraform.delete-paths:segment-group-delete-two-loops] In the segment-group cleanup, a failure to fetch the policy set or the rules of one policy type is logged as a warning and that type is skipped. No error is returned, so the delete proceeds without having cleaned that type. [zpa.terraform.delete-paths:segment-group-list-failures-skipped]

A failed segment-group, PRA portal or PRA console destroy can leave the object detached from some rules or consoles and still attached to others. A retry starts from that partially changed state and is not equivalent to one atomic operation. [zpa.terraform.delete-paths:cleanups-can-leave-partial-detach]

**Server groups.** Deleting a server group logs and ignores an error from the connector-group cleanup, calls the policy-rule and application-segment cleanups (which return nothing), and then deletes the group regardless. [zpa.terraform.delete-paths:server-group-delete-ignores-cleanup] Every failure inside the three server-group cleanups is logged and dropped: listing or updating policy rules, listing or updating application segments, and fetching or updating individual connector groups. The connector-group helper returns nil after its loop whatever happened there; only a failure to fetch the server group itself returns an error, and the caller logs and ignores that too. [zpa.terraform.delete-paths:server-group-cleanup-failures-only-logged] So a server-group destroy can finish successfully in Terraform while policy rules, application segments or connector groups still reference the deleted group, with the only trace in the provider's debug log. [zpa.terraform.delete-paths:server-group-delete-can-succeed-with-references] What the API does when a referenced server group is deleted is open [gap:zpa.terraform.delete-paths:api-delete-referenced-object].

For the same pattern in another product, where a background step cannot report failure, see [How the ZIA Terraform provider applies rule order](kb:zia.terraform.rule-order).

What to check:
1. Which consoles list the portal as their only portal, since those consoles are deleted with it.
2. Which rules, application segments and connector groups still reference a destroyed server group, by re-reading them after the destroy.
