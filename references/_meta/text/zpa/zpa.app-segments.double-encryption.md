# What Double Encryption does, when to use it and what it costs (zpa.app-segments.double-encryption)
Also called: double encryption; doubleEncrypt; double_encrypt; additional layer of encryption inside the outer TLS tunnels

By default, traffic between Zscaler Client Connector and an App Connector is encrypted using TLS 1.2 tunnels between Client Connector and the Public or Private Service Edge, and between the App Connector and the Service Edge; standard Private Access application traffic is not encrypted by Zscaler as it transits the Service Edge in memory and is never written to disk. Enabling double encryption when defining an application adds a layer of encryption inside the outer TLS tunnels, so that traffic is encrypted in memory as it transits the Service Edge. [zpa.app-segments.double-encryption:default-tls-and-in-memory] When double encryption is enabled on an application segment, traffic for applications matching that segment is encrypted using Client Connector and App Connector certificates signed by the intermediate signing certificates, and is sent to the Service Edges through TLS sessions initially set up between Client Connector and the App Connector. [zpa.app-segments.double-encryption:mechanism]

**When to use it.** Double encryption is recommended only for sensitive data transmitted over unencrypted protocols such as HTTP, FTP or telnet, and is not needed for end-to-end encrypted protocols such as HTTPS, SSH or RDP; using it for end-to-end protocols is strongly discouraged because it gives three layers of encryption, an unnecessary performance cost and possible MTU issues. [zpa.app-segments.double-encryption:when-to-use] Enabling double encryption requires additional App Connector processing; typically the traffic counts double against the App Connector's capacity compared with standard Private Access traffic, so 100 Mbps of double encryption traffic has the same performance cost as 200 Mbps of standard application traffic. [zpa.app-segments.double-encryption:connector-capacity]

**Requirements and scope.** To enable double encryption on relevant applications, the certificates used to sign the connector and client certificates must share a certificate authority, either the default CA created within Private Access at provisioning time or a custom PKI CA from the customer, so default-provisioned tenants can use it simply by enabling it; double encryption fails if the client and App Connector certificates do not share a common root CA. [zpa.app-segments.double-encryption:shared-ca] Double encryption occurs at the FQDN level: if it is enabled for an application segment containing an FQDN, all application segments sharing that FQDN have double encryption enabled. In the page's example, a segment app1.company.com on TCP port 80 with double encryption on means a different segment with the same FQDN on TCP port 22 also has it on. [zpa.app-segments.double-encryption:fqdn-level] How the spread shows on the other segments is open [gap:zpa.app-segments.double-encryption:fqdn-spread-visibility].

**Where it is off.** By default, if a Browser Access-enabled application was defined, Double Encryption is disabled. [zpa.app-segments.double-encryption:browser-access-default-off] Double encryption is associated with the data traffic over an App Connector; because extranet does not use a traditional App Connector, double encryption is not supported for it. [zpa.app-segments.double-encryption:extranet-unsupported] The combinations the console refuses are in [Application segment settings that interact: health reporting, connector selection, CNAME, ICMP, encryption and anchoring](kb:zpa.app-segments.settings).
