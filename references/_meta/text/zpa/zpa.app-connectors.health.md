# App Connector health, status values and telemetry (zpa.app-connectors.health)
Also called: app connector disconnected; connection health; controlChannelStatus; runtime_status; ZPN_STATUS_AUTHENTICATED; AliveTargetCount; app connector metrics log; app connector status log; connector paused; lss retransmit 15 minutes; app connector cpu memory
Former IDs: zpa-20

Where an App Connector's health is reported, which fields mean what, and which status values come from which source.

**Console and alerts.** The App Connectors page shows each connector's Connection Health as Connected or Disconnected, separately from its Status (enabled or disabled). [zpa.app-connectors.health:connection-health-column] If any connectors have been disconnected for a year or more, an alert on Admin Console login links to a page filtered to them for review or deletion. [zpa.app-connectors.health:disconnected-year-alert] A connector that logged a successful connection but shows as disconnected in the Admin Console most likely is not getting CPU cycles or its VM is frozen; stopping and restarting the VM is the suggested remedy. [zpa.app-connectors.health:logged-but-disconnected] A connector can be paused for certificate expiry, software upgrade, session process restart or session system restart; it logs 'entering PAUSE mode because of' with the reason, and a paused connector can reject remote session commands. [zpa.app-connectors.health:pause-reasons] A running connector periodically writes a status message to the local logs that includes how long its certificate has left. [zpa.app-connectors.health:cert-expiry-in-status-output] A disconnected connector with a running VM is not tied to a cause by the sources [gap:zpa.app-connectors.health:cert-or-firewall-disconnect].

**Deleting disconnected connectors.** Disconnected App Connectors are deleted from the Disconnected filter, choosing a disconnection period (the page's examples are 14, 30, 60 or 90 days). Zscaler recommends evaluating the service configuration to confirm there is no service outage before deleting them. [zpa.app-connectors.health:delete-disconnected] App Connector Settings can enable Auto Delete for App Connectors with a disconnected status; Auto Delete is Disabled by default. The settings set the expiration for deleting them and can optionally include disabled App Connectors. [zpa.app-connectors.health:auto-delete] The tenant connector limit is in [A tenant can have up to 100 App Connectors in the Admin Console by default; the total counts active connectors and connectors that are disabled but not deleted. Zscaler Support can raise it.](kb:zpa.app-connectors.deployment:tenant-limit-100).

**Log fields.** The App Connector Status log's SessionType is ZPN_ASSISTANT_BROKER_CONTROL, the session from the connector to the closest Public Service Edge, and SessionStatus is one of ZPN_STATUS_AUTHENTICATED, ZPN_STATUS_AUTH_FAILED or ZPN_STATUS_DISCONNECTED. [zpa.app-connectors.health:status-log-control-session] The metrics log counts active and disconnected Microtunnel (M-Tunnel) connections separately to Public and Private Service Edges (ActiveConnectionsToPublicSE, DisconnectedConnectionsToPublicSE, ActiveConnectionsToPrivateSE, DisconnectedConnectionsToPrivateSE). [zpa.app-connectors.health:metrics-mtunnel-counts] The App Connector Metrics log reports TargetCount, the targets configured for access via the connector, and AliveTargetCount, the targets alive for access via it. [zpa.app-connectors.health:metrics-target-counts] AliveTargetCount below TargetCount means some configured targets are not alive for access via that connector at that time. [zpa.app-connectors.health:alive-below-target] An application segment's health_reporting accepts NONE, ON_ACCESS or CONTINUOUS. [zpa.app-connectors.health:health-reporting-values] The probe cadence per value is unsourced [gap:zpa.app-connectors.health:health-reporting-cadence].

**Status names across tools.** Both SDKs expose the connector's control-connection state as controlChannelStatus (Python control_channel_status, Go ControlChannelStatus). [zpa.app-connectors.health:control-channel-field] The OpenAPI connector GET response marks controlChannelStatus read-only and enumerates UNKNOWN, ZPN_STATUS_AUTHENTICATED and ZPN_STATUS_DISCONNECTED. [zpa.app-connectors.health:control-channel-status-values] The MCP troubleshooting skill's connector status table gives ZPN_STATUS_AUTHENTICATED as healthy, ZPN_STATUS_DISCONNECTED as lost connection, ZPN_STATUS_NOT_ENROLLED as never enrolled or enrollment failed, and ZPN_STATUS_PENDING as enrollment in progress; the command document lists only the first three. [zpa.app-connectors.health:mcp-status-table] Neither SDK nor the Terraform provider defines a field named runtime_status or runtimeStatus for connectors; that name and the ZPN_STATUS_* table used with it appear in the MCP server's skill and command markdown. [zpa.app-connectors.health:no-runtime-status-field] The LSS SessionStatus list includes ZPN_STATUS_AUTH_FAILED, which is not in the MCP connector status table, so the two lists are not identical (they share AUTHENTICATED and DISCONNECTED). [zpa.app-connectors.health:lss-status-set-differs] The Python SDK's `get_status_codes` returns LSS session status codes read from the `/statusCodes` endpoint, filtered by log type when a `log_type` is given. [zpa.app-connectors.health:lss-codes-fetched] The full set of LSS session status codes cannot be listed from the Python SDK's source, because the SDK holds no list of them. [zpa.app-connectors.health:lss-codes-not-in-sdk-source] Whether PENDING exists, and how it differs from NOT_ENROLLED, are open [gap:zpa.app-connectors.health:status-pending-unverified] [gap:zpa.app-connectors.health:not-enrolled-vs-pending].

**Version and connection fields.** The Python connector model carries current and expected version, last upgrade time, last broker connect and disconnect times with durations, platform and Sarge upgrade fields, all read from the response. [zpa.app-connectors.health:connector-object-fields] The OpenAPI connector GET response enumerates upgradeStatus as COMPLETE, IN_PROGRESS, FAILED, UNKNOWN, RESTARTING, PARTIAL_FAILURE and REMOVAL_IN_PROGRESS, and each zpnSubModuleUpgradeList entry's role as ASSISTANT, PRIVATE_BROKER, MMDB_GEOIP, MMDB_ISP, GUACD and SITE_CONTROLLER. [zpa.app-connectors.health:upgrade-status-values]

**Connectivity checks.** For a connector that cannot reach the cloud, the help checks that the firewall allows the published Private Access address ranges, that co2br.prod.zpath.net resolves to two addresses, and that an openssl TLS connection to a Public Service Edge returns a certificate subject. [zpa.app-connectors.health:cloud-connectivity-checks]

**Streaming limits.** After a connection loss between Private Access and the App Connectors, LSS does not send the log data generated during the loss; after the connection is restored it can retransmit the last 15 minutes of log data, with delivery not guaranteed. During a loss between the App Connector and the SIEM, LSS sends nothing for that period except audit logs. [zpa.app-connectors.health:lss-retransmit-limits]

How the status feeds session assignment is in [How a session is assigned to an App Connector](kb:zpa.app-connectors.selection); update status values are in [App Connector software and host OS updates](kb:zpa.app-connectors.upgrades).

The Status log's ServiceCount counts the domain or IP and port services the connector monitors [In the App Connector Status log ServiceCount is the number of services, meaning combinations of domains or IP addresses and TCP or UDP ports, being monitored by the App Connector.](kb:zpa.logs.control-session-status:service-count-monitored).

The Status and Metrics logs describe CPUUtilization differently: [The three status logs carry CPUUtilization and MemUtilization described only as the utilization in %, alongside interface byte, packet, error and discard counters; the App Connector Metrics CPUUtilization is instead the maximum CPU usage in the past 5 minutes.](kb:zpa.logs.control-session-status:resource-fields-at-event) [So each status record includes a resource snapshot: its CPU and memory utilization and interface counters as of that record.](kb:zpa.logs.control-session-status:status-resource-snapshot); see [What the ZPA App Connector Metrics log reports and what it leaves open](kb:zpa.logs.app-connector-metrics).

What to check:
1. Whether Connection Health, the Status log SessionStatus and the control session agree, using the Status log rather than M-Tunnel counts to judge whether the connector is connected.
2. Whether AliveTargetCount trails TargetCount for the connector in question.
3. Whether the connector is paused, and for which reason, before treating it as down.
4. Which code family a status value belongs to before comparing an MCP status with an LSS SessionStatus.
5. Whether a log gap overlaps a connection loss between Private Access and the App Connectors, since LSS does not send the data generated during the loss and, once the connection is restored, can retransmit the last 15 minutes of it, with delivery not guaranteed.
