# Boolean logic and operand forms of ZPA policy conditions (zpa.policy.conditions)
Also called: zpa and or logic; condition blocks; operands; entry_values; values vs entry_values; objectType; APP_GROUP; CLIENT_TYPE; POSTURE lhs rhs; PLATFORM rhs true; RISK_FACTOR_TYPE; CHROME_ENTERPRISE; empty conditions; rule with no conditions
Former IDs: zpa-46, zpa-73

A rule's conditions combine by fixed AND and OR logic, and each operand has one of two forms.

**Between and inside criteria.** Private Access uses an implicit OR between multiple application segments, and between multiple segment groups, in one rule. [zpa.policy.conditions:segments-or] Private Access uses an explicit OR between the application segment criteria and the segment group criteria, so a request matches the application scope if its segment or its segment group is present. [zpa.policy.conditions:segment-or-group-or] Where a rule has additional criteria, Private Access uses an explicit AND between them. [zpa.policy.conditions:criteria-and] Multiple client types, platforms, trusted networks, application segments or segment groups in one rule are joined by OR, and multiple SAML or SCIM attributes, groups or IdPs are joined by OR by default, with a toggle to AND. [zpa.policy.conditions:or-within-most-criteria] Multiple Cloud Connector groups and multiple posture profile condition sets in one rule are joined by AND, while profiles inside one condition set are joined by OR by default with a toggle to AND. [zpa.policy.conditions:and-within-some-criteria]

**On the global rules and policy groups page.** That page's feature is in limited availability [Global rules and policy groups for access policy are in limited availability, and the pages say to contact Zscaler Support to learn more.](kb:zpa.policy.policy-groups:limited-availability). On the global rules and policy groups configuration page, nested criteria sets and the and not and or not operators are supported only for SAML Attributes and Client Connector Posture Profiles, and a nested set takes a logical operator (and, or, and not, or or not) that defines how it evaluates relative to the preceding criteria set. [zpa.policy.conditions:nested-sets-operators] On the global rules and policy groups configuration page the operators mean: and, the user must match both attribute conditions; or, the user can match either attribute condition; and not, the user must match the preceding condition and must not match this attribute condition; or not, the user matches if they meet the preceding condition or do not meet this attribute condition. [zpa.policy.conditions:operators-defined] In the global rules instructions, multiple IdPs in a rule are joined by an OR Boolean operator by default, and the operator can be toggled to select a different logical operator (and, or, and not, or or not) between the IdPs. [zpa.policy.conditions:idp-operator-toggle] In the policy group instructions the page's example is a rule that applies to a user authenticating from the first IdP with the specified First Name OR Last Name, or to any user authenticating from the second IdP, and it says the operator can be toggled to AND. [zpa.policy.conditions:policy-group-idp-example] If the corresponding IdP setting (SAML Attributes for Policy) is disabled for SAML but a global rule has criteria for SAML attributes, the or not operator makes Private Access skip evaluating the SAML attribute criteria and continue with the SCIM attributes and SCIM groups, while the and not operator makes it not evaluate the rule until the criteria under SAML Attributes are removed. [zpa.policy.conditions:saml-setting-disabled-negated]

**Condition set limit.** The access global rules and policy groups, timeout, client forwarding and Browser Protection rule editors each say the criteria drop-down only displays criteria not already in use by the rule, except for Client Connector Posture Profile condition sets, and that up to 10 condition sets can be added; the redirection editor says the drop-down only displays unused criteria and up to 10 condition sets can be added, with no exception for posture stated. [zpa.policy.conditions:condition-set-limit]

**Condition blocks in the API format.** In the MCP server's v2 access rule format each condition block holds a single object type, multiple blocks are ANDed, and multiple operands or entry values inside one block are ORed. [zpa.policy.conditions:condition-block-single-type] SAML and SCIM_GROUP operands can share one condition block as identity types and are ORed within it. [zpa.policy.conditions:saml-scim-group-share-block] Value-based object types such as APP, APP_GROUP and CLIENT_TYPE use `values`, and entry-based types such as SAML, SCIM_GROUP and PLATFORM use `entry_values` with `lhs` and `rhs`. [zpa.policy.conditions:values-vs-entry-values]

**Entry values.** PLATFORM, COUNTRY_CODE, POSTURE and TRUSTED_NETWORK operands carry the identifier in lhs (the platform name, an ISO country code, the posture profile's posture_udid, the trusted network's network_id) and the string true or false in rhs. [zpa.policy.conditions:boolean-rhs-entry-types] A RISK_FACTOR_TYPE operand has lhs ZIA and rhs one of UNKNOWN, LOW, MEDIUM, HIGH or CRITICAL. [zpa.policy.conditions:risk-factor-entry]

**Chrome operands.** The Terraform provider's policy rule validator (`ValidatePolicyRuleConditions`) requires CHROME_POSTURE_PROFILE operands to carry a profile ID in values, and CHROME_ENTERPRISE operands to carry entry_values with lhs managed and rhs true or false. [zpa.policy.conditions:chrome-operand-forms] Whether the API enforces the same split is open [gap:zpa.policy.conditions:chrome-operand-form-api-enforcement]. Whether it rejects a mixed operand is open [gap:zpa.policy.conditions:mixed-forms-invalid].

**Other policy types.** Which condition types an inspection rule accepts is open [gap:zpa.policy.conditions:inspection-condition-set].

**Blank and empty.** In the console, leaving the Application Segments, Segment Groups and SAML Attributes fields unselected makes the rule apply to any user from any IdP and any application segment and segment group. [zpa.policy.conditions:blank-criteria-mean-any] An access rule with no conditions applies to all users and all applications, a forwarding rule with no conditions applies globally (a global bypass if the action is BYPASS), and a timeout rule with no conditions applies as the default timeout for all users and applications. [zpa.policy.conditions:empty-conditions-match-all]

The list of criteria is in [Criteria available on ZPA access policy rules](kb:zpa.policy.criteria).

The Terraform v2 access rule validates a condition's object_type against these values: APP, APP_GROUP, LOCATION, IDP, SAML, SCIM, SCIM_GROUP, CLIENT_TYPE, POSTURE, TRUSTED_NETWORK, BRANCH_CONNECTOR_GROUP, EDGE_CONNECTOR_GROUP, MACHINE_GRP, COUNTRY_CODE, PLATFORM, RISK_FACTOR_TYPE, CHROME_ENTERPRISE, CHROME_POSTURE_PROFILE, WORKLOAD_TAG_GROUP, ENTITY_TAG_GRP and ENTITY_TAG_VAL; v4.4.14 lacked the last two, which v4.4.15 added. [zpa.policy.conditions:tf-v2-object-type-values]

What to check:
1. Read each condition block as one criterion with one object type, ORed inside the block and ANDed with the other blocks.
2. For a POSTURE, PLATFORM, COUNTRY_CODE or TRUSTED_NETWORK operand, check lhs for the identifier and rhs for the string true or false.
3. For a Chrome rule checked by the Terraform provider's v2 policy validator, check that CHROME_POSTURE_PROFILE uses values and CHROME_ENTERPRISE uses entry_values with lhs managed.
4. Check whether the rule has no conditions at all, since an access rule then applies to all users and applications, a forwarding rule globally, and a timeout rule as the default timeout for all users and applications.
5. If a rule uses nested criteria sets or the and not and or not operators, check that the criteria are SAML attributes or Client Connector posture profiles, and which of the four operators links each set.
6. If a rule has more than 10 condition sets, check the rule type's editor limit.
7. Do not rely on the API refusing mixed operand forms or the Chrome form split until the open gaps are closed.
