# Peer-to-peer connectivity: client-to-client and server-to-client remote assistance, their requirements and setup, and Client Connector IP assignment (zpa.peer-to-peer)
Also called: client-to-client; client to client; C2C; server-to-client; server to client; S2C; remote assistance zpa; Zscaler IP; virtual Zscaler IP; Client Connector IP assignment; IP bindings; IP ranges

In addition to connecting users to private applications, Private Access supports connecting users to other Private Access-enabled devices for remote assistance or remote troubleshooting: an IT admin can initiate an RDP or Microsoft Remote Assistance (MSRA) connection to a remote end user's device, the connection is established by the Zero Trust Exchange, and client-based remote assistance allows troubleshooting on an end user's Windows, Mac or Linux device. [zpa.peer-to-peer:client-to-client]

**Client-to-client requirements.** Client-to-client needs end users' machines running Client Connector 3.9.0.169 or later for Windows, 1.4 or later for Linux, or 3.7 or later for macOS, with Windows and Linux devices having the primary DNS suffix properly configured and Client Connector run with Private Access enabled. The configuring article adds that Mac devices must be domain-joined. [zpa.peer-to-peer:c2c-client-versions] Zscaler recommends that destination Windows devices for client-to-client be Active Directory domain-joined; it can also work with Windows or Linux hybrid-joined or Azure cloud-joined devices, in which case the organization must ensure the completeness and uniqueness of the destination FQDNs (for example, on Windows, that the DNS primary suffix field is entered and valid). [zpa.peer-to-peer:c2c-destination-join] For client-to-client, Client Connector on the destination machine must have a machine tunnel deployed, or the destination machine must be logged in to Private Access in Client Connector, which ensures the destination's connection to Private Access without the local user logging in to Windows. [zpa.peer-to-peer:c2c-destination-connected] The validating page names only the machine tunnel [divergence:zpa.peer-to-peer:destination-machine-tunnel-or-login]. Validating a client hostname enrolls endpoints for peer-to-peer connectivity so that they can accept incoming connections through Private Access from other clients. A regular expression of allowed hostnames is configured per tenant; it controls the endpoints to which Client Connector allows peer-to-peer connectivity, and endpoints whose FQDNs match it are enrolled. [zpa.peer-to-peer:hostname-validation-enrollment] Validating a client hostname needs Client Connector 3.9.0.169 or later installed on the destination machine, and endpoints or devices with valid, complete and unique FQDNs. [zpa.peer-to-peer:validation-prerequisites] Client-to-client needs a regular expression configured for Client Hostname Validation, and the hostnames or FQDNs configured in client-to-client application segments must match it (for example testPC.example.com matches .*\.example\.com). Client Connector must be set to collect machine hostname information, and with a wildcard domain such as *.example.com in the segment plus a more specific expression, only devices matching both are enabled for remote assistance. [zpa.peer-to-peer:hostname-regex] The validating page's example enters the regular expression .*.example.com to establish a peer-to-peer connection for devices joined with matching domains such as test.example.com. For remote assistance to work, the application segment designated for peer-to-peer connectivity must match the regular expression entered. [zpa.peer-to-peer:regex-example-and-segment] A client-to-client application segment does not need a server group, because no App Connector has to be assigned. If applications and workstations share a namespace, Zscaler recommends separate application segments for client-based remote assistance and for application access, with separate FQDNs or wildcard subdomains if possible. [zpa.peer-to-peer:c2c-segments] Client-based remote assistance is available only to end users connecting to Private Access using Client Connector, and the Server Groups tab offers Skip to enable client-to-client remote assistance. [zpa.peer-to-peer:c2c-client-connector-only] Privileged Remote Access is not supported when an application configured for PRA matches a valid client hostname configured for peer-to-peer connectivity and the user's device is also configured for peer-to-peer connectivity. [zpa.peer-to-peer:pra-conflict] On the Defined Application Segments page, the Validate a client hostname option is hidden if a Microtenant is in use. [zpa.peer-to-peer:hidden-in-microtenant] The destination endpoint's host-based firewall must allow access from the localhost using the interface IP address from the ports or protocols expected over client-to-client access. For RDP shadowing, Remote Desktop is enabled by an account with local administrator permissions, the File and Printer Sharing (SMB-In) and Remote Desktop - Shadow (TCP-In) rules are enabled, and the session is opened with mstsc /shadow. [zpa.peer-to-peer:c2c-endpoint-firewall] For Microsoft Remote Assistance the invitation file must be edited to remove the LHTICKET attribute and to replace the IP address in the RCTICKET value with the registered hostname in Private Access for client-to-client, edited by the destination or source user, or with the Zscaler IP for Zscaler IP-based server-to-client, edited by the destination user. [zpa.peer-to-peer:msra-invitation] If access policies have not been created or updated for client-to-client, any user in the organization can use the feature to connect to any endpoint enrolled in it, and an access policy controls who can connect to the remote users. For server-to-client the article says the same of any user when its access policies are not created or updated, and an existing policy can control which servers can connect. [zpa.peer-to-peer:open-without-policy]

**Verifying.** To verify that a user's device is registered for remote assistance, the article says to confirm that the Valid Hostname field is True for the user's session in User Status Diagnostics; Client Connector also shows the device's FQDN in the Client field on its Private Access tab if the registration is successful. A successful client-to-client connection shows the Access Type Client to Client in the User Activity Log, and server-to-client shows the value Client to Client for the Access Type field in user activity diagnostics and live logs. [zpa.peer-to-peer:verification] What the console's Valid Hostname and Access Type labels correspond to in the log fields is open [gap:zpa.peer-to-peer:field-mapping]. The hostname regular expression rules are open [gap:zpa.peer-to-peer:hostname-regex-rules].

**Server-to-client.** Server-to-client connectivity, a feature in limited availability, allows applications on internal servers to connect through Branch Connectors and Cloud Connectors to endpoints running Client Connector, using a Zscaler IP address or FQDN from servers that do not have Client Connector installed, for use cases such as remote troubleshooting and software distribution. This differs from client-to-client, where the connectivity is between two endpoints running Client Connector. [zpa.peer-to-peer:server-to-client] With virtual Zscaler IP connectivity, an endpoint enrolls in peer-to-peer connectivity when validating a client hostname and Zscaler assigns it a virtual Zscaler IP address from the configured IP range; applications initiate connectivity to the client over that address on a specific port, and the Cloud or Branch Connector, based on policy criteria, intercepts the requests and forwards them to the Zscaler cloud. The same workflows can be achieved with FQDN connectivity, depending on how the tools connect with the endpoints. [zpa.peer-to-peer:s2c-flow] Server-to-client needs a deployed Cloud Connector or Branch Connector (the license to be confirmed with the Zscaler Account team), Client Connector 4.2 for Windows or later on the destination with Private Access enabled and a user logged in, a configured and validated client hostname, routing so that the Zscaler IP ranges traverse the connector, and application segments and access policies built with endpoint FQDNs or the virtual IP ranges or subnets assigned to Client Connector. For FQDN-based deployment Zscaler recommends conditional DNS forwarding so only the DNS requests of applications requiring server-to-client connections go to the connector. [zpa.peer-to-peer:s2c-requirements] For Zscaler IP-based server-to-client the servers' IP gateway is pointed to the Branch or Cloud Connector's service IP: on Windows with route add 0.0.0.0 mask 0.0.0.0 <service IP> metric 30 if 2, checked with route print, and on Linux with sudo route add default gw <service IP>, checked with route -n. [zpa.peer-to-peer:s2c-server-routing] Server-to-client connectivity based on the virtual Zscaler IP does not support configuring a ZIA forwarding profile action using DTLA, Disaster Recovery, machine tunnels, Microtenants, or Client Connector support for multiple tenants when those tenants are partner tenants or the user is logged in to a partner tenant. [zpa.peer-to-peer:s2c-unsupported] The version floors for macOS and Linux destinations are open [gap:zpa.peer-to-peer:s2c-platforms]. Whether Configuration Manager remote assistance works over it is in [Configuring application segments for specific enterprise applications: unified communications, FTP, RDP, DFS with Kerberos, Windows domain join, Citrix, GPO, Configuration Manager, IWA with Kerberos reauthentication and SAP](kb:zpa.app-segments.enterprise-apps).

**IP assignment.** Client Connector IP Assignment controls the Zscaler virtual IP addresses assigned to clients during connectivity to the Zero Trust Exchange. The addresses do not appear in Client Connector's interface list but are unique within each Client Connector, and are used for server-to-client and client-to-client connectivity where applications cannot use FQDNs; for server-to-client the ranges must be non-overlapping and routed to the Branch or Cloud Connector as next hop router. [zpa.peer-to-peer:ip-assignment-purpose] An IP range takes a name, a Status (Enabled by default; active IP addresses are unavailable to users after the range is disabled), and either an IP Range (selected by default; the beginning address must be less than or equal to the ending address) or an IP Subnet in CIDR notation used for server-to-client connectivity, plus a description and an IP Range Location, whose Latitude, Longitude, Country Code and Location Details fields are populated when the map marker is clicked. IPv6 ranges and subsets are not supported. [zpa.peer-to-peer:range-fields] IP address ranges must be non-overlapping. Zscaler recommends that the ranges be broad enough to cover the endpoints based on geolocation criteria; otherwise the IP address from another available range is assigned. [zpa.peer-to-peer:non-overlapping-and-geolocation] Send Location Hint to Client Connector is optional: the location hint is sent along with a Zscaler IP address to Client Connector, and a Client Connector that receives it creates a pseudo network adapter and applies the hint to the adapter's name for the System Center Configuration Manager (SCCM) location boundary. [zpa.peer-to-peer:location-hint] The IP Ranges page lists each range or subnet with its Location Details (City, State, Country), Total IPs, Used IPs and Status (Enabled or Disabled), and can copy (opening the Add IP Range window with the details duplicated), edit, delete or enable a range. [zpa.peer-to-peer:ip-ranges-page] IP bindings indicate that a Zscaler IP address is bound to the client's destination device through Client Connector, and devices can be traced by the Zscaler IP addresses used for server-to-client or client-to-client connectivity. The page shows the Zscaler IP, range name and location, username, Client Connector platform, client hostname and last update; a CSV download is not possible when the records exceed one million, so Zscaler recommends filtering first. [zpa.peer-to-peer:ip-bindings] Range limits and binding lifetime are open [gap:zpa.peer-to-peer:ip-range-limits].

What to check:
1. Whether access policies exist for the feature, since without them any user in the organization can connect to any enrolled endpoint.
2. Whether the destination's FQDN matches the Client Hostname Validation regular expression and, for a wildcard segment, the segment's domain as well.
3. Whether the destination's Client Connector meets the per-OS version floor and the machine tunnel or logged-in requirement for the direction in use.
4. Whether the case uses a feature the Zscaler IP-based server-to-client mode does not support.

Sources disagree (name both sides):
- What the destination machine needs for peer-to-peer connectivity: a machine tunnel, or a machine tunnel or a login [divergence:zpa.peer-to-peer:destination-machine-tunnel-or-login]
  - zscaler-help: Client Connector on the destination machine must have a machine tunnel deployed.
  - zscaler-help: Client Connector on the destination machine must have a machine tunnel deployed, or the machine must be logged in to Private Access in Client Connector.
  Impact: The validating page names only the machine tunnel, while the client-to-client configuring page also accepts a logged-in destination machine. Neither says that the validating page's requirement is limited to a particular direction, so a machine that is only logged in may or may not be enrolled; the configuring page states the wider condition for client-to-client.
