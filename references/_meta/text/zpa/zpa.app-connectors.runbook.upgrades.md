# What the App Connector runbook checks for upgrade problems: the healthy status block, clean restart, update servers, revert to default version and rebuild (zpa.app-connectors.runbook.upgrades)
Also called: Recognizing a Healthy App Connector

**Upgrade process.** The Upgrade Manager selects an App Connector and instructs it to download the latest software, moves on to the next App Connector in the group after the connector confirms the upgrade, and pauses the process for the group if an upgrade fails for any App Connector. [zpa.app-connectors.runbook.upgrades:upgrade-process] [divergence:zpa.app-connectors.runbook.upgrades:failure-handling] Upgrade failures are shown as failure notices in the Admin Console under Infrastructure > Private Access > Component > App Connectors. [zpa.app-connectors.runbook.upgrades:failure-visibility]

**Healthy connector.** The runbook's healthy-connector example is a status block that the connector writes to the zpa-connector journal once per minute (followed with sudo journalctl -u zpa-connector -f); the block's Control connection state of fohh_connection_connected shows the connector has its control connection to the Private Access cloud, and the console entry shows Authenticated. [zpa.app-connectors.runbook.upgrades:healthy-status-block] [divergence:zpa.app-connectors.runbook.upgrades:console-state-label] The runbook's connector status block example includes the connector ID, name and version, a certificate expiry countdown, RPC message counters, the broker data connection count with backed_off connections, mtunnel totals, registered-app and target counts, and the time skew. [zpa.app-connectors.runbook.upgrades:healthy-status-fields] [gap:zpa.app-connectors.runbook.upgrades:status-field-meanings]

**Remediation.** The first remediation for an upgrade problem is a clean service restart: stop zpa-connector, verify with ps wU zscaler that no processes remain under the Zscaler user account (ending any by process ID), then start it again. [zpa.app-connectors.runbook.upgrades:clean-restart] For software update problems the runbook checks connectivity to the upstream Public Service Edge for Private Access (dig +short co2br.prod.zpath.net, and an openssl TLS test), then ICMP and telnet TCP connectivity to dist.private.zscaler.com and yum.private.zscaler.com. [zpa.app-connectors.runbook.upgrades:update-server-connectivity] An App Connector that cannot reach the Private Access cloud receives no upgrade instructions from the Upgrade Manager; to force a fallback to the default version, stop the service, remove /opt/zscaler/var/image.bin, version and metadata, and start the service, after which the connector re-downloads a default version from the CDN. [zpa.app-connectors.runbook.upgrades:revert-default-version]

**Rebuild.** When rebuilding an App Connector it must be redeployed into the same group it was in before, because with a different group some internal applications might not be reachable depending on the policies configured; the group is assigned from the provisioning key. [zpa.app-connectors.runbook.upgrades:rebuild-same-group] To determine the App Connector Group the connector belongs to, the runbook locates the connector by the App Connector Name repeated once per minute in the status block under sudo journalctl -u zpa-connector, or by its private IP address, visible under the expanded view. [zpa.app-connectors.runbook.upgrades:identify-connector] Each provisioning key has a Maximum # of App Connectors and a Provisioning Key Utilization Count that increments each time a connector enrolls with the key; the maximum must be at least 1 greater than the enrolled count for a rebuild, and the runbook's example of 16 enrolled out of 16 allocated has Private Access reject a rebuild. [zpa.app-connectors.runbook.upgrades:key-enrollment-capacity] The wipe-and-rebuild procedure stops the service, runs sudo rm /opt/zscaler/var/*, creates the provision_key file with 644 permissions so the zpa-connector service can modify it when provisioning completes, pastes in the key, and restarts the service, which re-enrolls itself under the appropriate App Connector group. [zpa.app-connectors.runbook.upgrades:wipe-and-rebuild]

Sources disagree (name both sides):
- What happens to the rest of a group after one App Connector's software update fails: the runbook pauses the process for the group, while the connector software update page retries the update at every periodic update. [divergence:zpa.app-connectors.runbook.upgrades:failure-handling]
  - zscaler-help: The runbook says the Upgrade Manager pauses the upgrade process for the group when an upgrade fails for any App Connector.
  - zscaler-help: The connector software update page says an unsuccessful update is retried in every periodic software update until all components are upgraded, and mentions no pause.
  Impact: Whether a failed connector holds back the other connectors in its group until someone intervenes, or the group is retried at the next periodic update, is not settled by the captured pages.
- What the Admin Console shows for an App Connector whose control connection is established: the runbook says the entry is Authenticated, while the App Connectors page lists Connection Health as Connected or Disconnected. [divergence:zpa.app-connectors.runbook.upgrades:console-state-label]
  - zscaler-help: The runbook says a healthy App Connector's entry is Authenticated.
  - zscaler-help: The App Connectors page lists Connection Health as Connected or Disconnected.
  Impact: A search of the console for Connected will not match the runbook's Authenticated label; which column or state the runbook means is not shown.
