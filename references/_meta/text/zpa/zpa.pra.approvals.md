# PRA approvals: requesting, reviewing and expiry (zpa.pra.approvals)
Also called: privileged approval; pra approval request; my requests pra portal; pra approval expires; pra approval window; approve pra access; expired privileged approvals; pra multiple approvers

Approvals bound when a user can reach a console. A user requests a window, an admin approves it, and access ends when the window does.

**What an approval is.** Privileged approvals allow third-party users and contractors to log in to a PRA Portal, maintain a secure access point only for the email addresses included in a privileged approval, and give those users entry to the specific applications they need to access. [zpa.pra.approvals:email-scoped] An admin can create privileged approvals with a set amount of time that one or more designated application segments can be accessed, delete existing approvals to revoke access to those segments, and delete all expired approvals. [zpa.pra.approvals:admin-actions] The Privileged Approvals page lists each approval's User Email, Application Segments, Start Time and End Time, and an approval status of Active (currently available), Expired (no longer available) or Future (available at a set time in the future). Approvals with an Expired status cannot be edited, and only Active and Future approvals include the Edit icon. [zpa.pra.approvals:approvals-table]

**Creating one.** After a privileged portal and privileged console are created, privileged approvals can be created. A privileged approval needs an access policy that uses the Conditional Access rule action with the Allow for Privileged Approval checkbox selected to take effect, and an approval created before that access policy and its application segments cannot take effect until the policy is created. The access policy page names the same checkbox Allow with Privileged Approval, so the label differs between pages. [zpa.pra.approvals:access-policy-required] The user email on a privileged approval should match the tenant's identity provider (IdP), specifically the NameID attribute in the SAML Assertion. [zpa.pra.approvals:user-email-nameid] The page's statement that there is no limit on segments conflicts with the documented figure [divergence:zpa.pra.approvals:segments-per-approval]. An approval's time window has a start and end date, time and time zone; the end user cannot use the console before the scheduled time and loses access after it expires. For windows spanning multiple days, optional working hours set the hours and days of the week of access, with a default of 9:00 start time and 17:00 end time for a 24-hour window. [zpa.pra.approvals:time-window] Which time zone applies by default is open [gap:zpa.pra.approvals:working-hours-default].

**Users that do not exist yet.** When Emergency Access is not configured, Private Access does not validate that users exist before a privileged approval is created, and those users are managed in the IdP. When Emergency Access is configured, Private Access validates only users from arbitrary authentication domains, and if the user does not exist in the IdP enabled for Emergency Access it offers to create the user when the approval is created, after which the user can be managed on the Emergency Access Users page. [zpa.pra.approvals:user-validation] The Add Emergency Access User window appears only if the email address does not match the authentication domain of the primary or secondary domain, Emergency Access is already configured, the specified email domain is added to the Emergency Authentication Domains field, and the user does not exist in the IdP enabled for Emergency Access. After the admin fills in the email address, first name and last name and clicks OK, the user is added to the Emergency Access Users page. [zpa.pra.approvals:emergency-user-window] When the window appears is described two ways [divergence:zpa.pra.approvals:emergency-window-domains].

**Microtenants.** If Privileged Approvals are disabled in a Microtenant, only users with the matching authentication domains are applicable, and a third-party user or contractor using such a Microtenant cannot add or edit a privileged approval. [zpa.pra.approvals:microtenant-disabled]

**Requesting.** Once an admin has enabled privileged requests in a portals policy, a user creates an approval request on the My Requests page of the PRA Portal by choosing a microtenant (Default is preselected) and consoles, a start date and a duration, and optionally a reason, then saving it for review. [zpa.pra.approvals:request-flow] If an admin has enabled privileged requests and approvals for the PRA Portal and a user has the My Approvals feature enabled, the user can access and manage privileged requests and approvals on the My Requests and My Reviews pages. The admin must also configure a portals policy to enable requesting and reviewing approvals. [zpa.pra.approvals:my-approvals-prerequisites] The My Requests page displays the privileged approval requests a user has created and the My Reviews page those the user has permission to approve and reject. My Requests lists Console, Microtenant, Start Date, Requested Duration, Approved Duration (access ends after it) and a status of Pending, Approved, Expired or Rejected, My Reviews adds the Requester, and request analytics are on the Requests page. [zpa.pra.approvals:my-requests-and-reviews] The characters & and + cannot be used in the filter search field of the My Requests page or the My Reviews page. [zpa.pra.approvals:my-approvals-filter]

**Reviewing.** Requests are reviewed on the Approval Requests page, which can be filtered by console and requester, where each one can be approved or rejected. The table shows requested duration and approved duration separately. [zpa.pra.approvals:approver-view] Each request records the requester, policy name, approval ID, start and end time, duration, console, requested and approved duration, reason, status (Approved or Rejected) and the time it was requested. [zpa.pra.approvals:request-metadata] After the admin has enabled privileged approvals in a portals policy, a reviewer can access the My Approvals page in the PRA Portal. When approving, Modify Time adjusts the time window of the request, an optional message can be included to the requester on approving or rejecting, and the request is then displayed as Approved or Rejected on the My Approvals page. [zpa.pra.approvals:portal-review] Whether more than one approver can be required is open [gap:zpa.pra.approvals:multi-approver].

**Expiry.** After the approved window ends the user loses access to the console. Approvals whose window has ended show as Expired, upcoming ones show as Future, and an admin can purge expired approvals to clean up the table. [zpa.pra.approvals:window-expiry] Each user can create up to 20 privileged approval requests on the My Requests page, and only approvals in Future or Active status count toward the 20,000-approval limit. [zpa.pra.approvals:request-limit]

Which consoles require an approval is open [gap:zpa.pra.approvals:approval-optional]. The SDK and Ansible handling of approvals, including working hours, is in [PRA operations in the Python SDK and Ansible approvals](kb:zpa.pra.tooling). The portals policy that enables requesting and reviewing is in [PRA portals policy: file, inspection and approval permissions in the PRA Portal](kb:zpa.pra.portals-policy), the Emergency Access side of creating users is in [Configuring Emergency Access: availability, settings, authentication domains, Microtenants](kb:zpa.emergency-access.configuration), and the approvals limit is in [The documented PRA limits are 100 privileged portals (a portal within the Default Microtenant can link a maximum of 9,000 privileged consoles), 10 privileged consoles by default (raisable by license to 9,000), 10,000 privileged credentials, 500 credential pools with 100 credentials each, and 20,000 privileged approvals with 200 application segments per approval.](kb:zpa.pra.components:limits).

The Terraform PRA approval doc limits an approval to one email address, a start no more than an hour in the past and an end within 365 days [A PRA approval takes a list of email IDs but the ZPA API supports a single address; the docs say start_time cannot be more than one hour in the past and end_time cannot be more than one year or 365 days away.](kb:zpa.terraform.resource-constraints:pra-approval-single-email-window).

What to check:
1. Whether the user's window has started or ended, since an expired approval removes access and an upcoming one shows as Future.
2. Whether an approval is Active, Future or Expired and so editable, and whether an access policy with the privileged approval option exists, since without it the approval does not take effect.
3. Whether a segment count answer rests on the limit or on the page that says there is none.
4. Whether the user can see My Requests and My Reviews, which need the admin enablement, the My Approvals feature and a portals policy.
5. Whether the Add Emergency Access User window should have appeared, given the two descriptions of when it does.
6. Whether the request exists in the Approval Requests table and with which status.
7. Whether the per-user request count or the tenant approval count is at its limit.
8. Whether an answer assumes multi-approver support or per-console approval requirements, which no source states.

Sources disagree (name both sides):
- How many application segments a privileged approval can include: the Configuring Privileged Approvals page says there is no limit to the number that can be selected, and the Ranges and Limitations table gives 200 application segments per privileged approval. [divergence:zpa.pra.approvals:segments-per-approval]
  - zscaler-help: There is no limit to the number of application segments that can be selected for an approval (said of the Application Segments field).
  - zscaler-help: A privileged approval can have 200 application segments (see zpa.pra.components:limits).
  Impact: An answer that a segment count caused a failed create, or that none can, should name both pages.
- Whether the Add Emergency Access User window needs the email domain to be in the Emergency Authentication Domains field: the Configuring Privileged Approvals page lists that as a condition, and the Emergency Access page says, in its section for Private Access end users who have not migrated to Authentication Service, that users can be created from any non-primary, non-secondary domain when no domains are specified. [divergence:zpa.pra.approvals:emergency-window-domains]
  - zscaler-help: One of the four conditions for the window to appear is that the email domain is added to the Emergency Authentication Domains field.
  - zscaler-help: In the Emergency Access page section for Private Access end users who have not migrated to Authentication Service, when no authentication domains are specified users can be created from any authentication domain that is not an existing primary or secondary one (see zpa.emergency-access.configuration:domains-semantics).
  Impact: With the field empty it is not settled whether the window appears for a new domain. An answer about a missing window should not state either behaviour as fact.
