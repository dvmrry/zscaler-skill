# VPN redundancy: failure scenarios, BGP group settings, platform settings, replacing and migrating Network Connectors (zpa.vpn.redundancy)

The redundancy guide says Network Connectors that support redundancy within a Network Connector group solve these failures: a Network Connector link failure, an internal link failure towards a customer router, an external link failure towards the VPN Service Edge, a complete Network Connector node failure, and a data center failure with traffic being rerouted towards another data center. The replace article says the redundancy design is based on External Border Gateway Protocol (EBGP) routing. [zpa.vpn.redundancy:failure-scenarios] The redundancy guide says that with the help of BGP, the network can be scaled with Equal-Cost Multi-Path (ECMP) to load balance traffic to the Network Connectors from the VPN Service Edges, and the traffic from the routers to the Network Connectors. [zpa.vpn.redundancy:ecmp-scaling] What a group's Redundant Mode means differs between the help pages, as recorded in [Network Connectors and Network Connector groups (VPN for Legacy Apps)](kb:zpa.vpn.network-connectors).

**Order.** With a BGP router, the redundancy guide gives these steps in order: add VPN Service Edges, configure BGP for VPN Service Edges, add external routers, add Network Connectors, deploy Network Connectors by platform, configure BGP for Network Connectors, add network segments, view the BGP dashboard, and add access policies. [zpa.vpn.redundancy:order] The routes the BGP routers advertise must match the network segments, per [The routes advertised by the BGP routers must match the IP subnets defined in the Network segments for BGP to work.](kb:zpa.vpn.network-segments:bgp-routes-match).

**Group settings.** For BGP, the redundancy guide says to ensure these Network Connector group settings: External Routers (the routers to associate with the group), Keepalive (the frequency and wait time for the keepalive message, in seconds, before a session times out), Enable Multi-Hop (to allow BGP sessions with external routers that are not directly connected on the same network subnet) and Interface (the interface name that has connectivity to the BGP router). [zpa.vpn.redundancy:group-settings] The option that turns BGP on is named and described differently across the pages, as recorded in [BGP for VPN Service Edges and Network Connectors: AS numbers, failure detection, external routers](kb:zpa.vpn.bgp). The redundancy guide says to ensure the Manager software version for the new Network Connectors is 25.46.2 or later. [zpa.vpn.redundancy:manager-version]

**Platform settings.** Under its list of settings to ensure based on the platform, the redundancy guide's VMware entry says to assign a static private IP address, use only one network interface and use VMware ESXi 7.0 Update 2 or later. The same list also says to ensure, for the deployed Network Connector instance, that the Source / destination checking option is disabled, and, for the deployed Network Connector VMs, that the IP forwarding option is enabled. [zpa.vpn.redundancy:platform-settings] The redundancy guide says that when Network Connectors are installed without the prebuilt virtual image from Zscaler, the Zscaler repository must be configured so the Network Connector can download and install the FRR package, which is essential for BGP to work. [zpa.vpn.redundancy:frr-package] The prerequisites article says that if a Network Connector is installed from an RPM and firewalld is used on a Network Connector using VPN redundancy, extra steps modify the firewall filter rule. They are to ensure NftablesTableOwner is set to no in firewalld.conf, and to create a systemd service file at /etc/systemd/system/network-connector-firewall.service. Its script adds UDP ports 51820, 3784 and 4784 with firewall-cmd and inserts nftables rules allowing all traffic in both directions on the npwg0 interface, and the page says the script reapplies these configurations after any firewalld reload event. [zpa.vpn.redundancy:firewalld]

**Replacing or migrating.** The replace article says that if BGP is enabled on the tenant, the tenant is running the latest version of VPN Service Edges and a BGP Configuration tab appears on the VPN Service Edges page; if that tab appears, new VPN Service Edges are added and the old VPN Service Edges deleted. If BGP is not enabled, Zscaler Support or the Zscaler Account team is contacted to enable the redundancy capability, and the VPN (for Legacy Apps) redundancy flag must be enabled. [zpa.vpn.redundancy:enablement] To replace existing Network Connectors, the replace article has the admin create a new Network Connector group and a new provisioning key associated with it for redundancy, edit the existing network segments to map them to the new group without deleting the mapping to the old groups, and add the new BGP-capable VPN Service Edges without a client subnet. The existing client subnet is then moved from the old VPN Service Edge to the new one, and additional Network Connectors and VPN Service Edges are deployed until the original configuration is replicated, after which the originals are deprecated. To force the client to reconnect to the new gateway, no older gateway with the client subnet may run in the same region, otherwise the client might switch to the older gateway. [zpa.vpn.redundancy:replace-path] The replace article says the clients previously connected to the old VPN Service Edge automatically switch to the new VPN Service Edge. [zpa.vpn.redundancy:client-switch] To migrate existing Network Connectors, the replace article says not to delete any Network Connectors, only the Network Connector groups; to delete all VPN Service Edges and add new ones based on them; and to create a new Network Connector group and provisioning key. On the connector it has the admin remove the old provisioning key file with sudo bash -c "rm -rf /opt/zscaler/var/*", reboot the appliance, create a new provisioning key file with 644 permissions at /opt/zscaler/var/provision_key, and update the Manager software and Network Connector. [zpa.vpn.redundancy:migrate-path]

What to check:
1. Before telling an operator which group option turns BGP on, give the option's name and purpose as each page states them (see [[zpa.vpn.bgp]]).
2. Before describing what Redundant Mode does in normal operation, give both the standby description and the ECMP load balancing description (see [[zpa.vpn.network-connectors]]).
3. Before replacing connectors, check no older gateway holding the client subnet runs in the same region, and that the old group mappings are kept until the new group works.
