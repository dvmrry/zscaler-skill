# ZPA timeout policy rules (zpa.policy.timeout-rules)
Also called: zpa timeout policy; reauth_timeout; reauth_idle_timeout; authentication timeout zpa; idle connection timeout; default timeout rule; session re-authenticating sooner than rule; timeout rule conditions

Timeout rules are a separate rule set that controls re-authentication, not access.

**What they control.** A timeout policy controls the authentication timeout, after which a user must reauthenticate, and the idle connection timeout, whose expiry does not force reauthentication. [zpa.policy.timeout-rules:auth-vs-idle] The authentication timeout is evaluated only when a user attempts to access an application. [zpa.policy.timeout-rules:evaluated-on-access] A timeout rule's Message to User is optional and is displayed to users when they need to reauthenticate based on the Authentication Timeout setting; the page says to ensure the message helps the user identify the application that requires reauthentication. If additional timeout rules are created, each can set its own notification message, so that users know which application requires reauthentication. [zpa.policy.timeout-rules:message-to-user]

**Why sessions re-authenticate sooner.** A single reauthentication gets a new SAML assertion and resets the reauthentication timer for all applications. [zpa.policy.timeout-rules:reauth-resets-all] Reauthentication settings are defined per segment group, so activity in one application counts as activity in all applications of the same group. [zpa.policy.timeout-rules:activity-counts-per-group]

**The reauthentication timestamp.** The help names two different timestamps [divergence:zpa.policy.timeout-rules:reauth-timestamp]. The configuring page says identity providers typically issue SAML assertions using a timestamp that is in the past by approximately 5 minutes. [zpa.policy.timeout-rules:assertion-timestamp-skew] If a configuration change on an IdP also causes a change to the SAML assertion, the updated assertion is applied to Private Access policies after the user reauthenticates. [zpa.policy.timeout-rules:idp-change-applies-after-reauth]

**Defaults.** The default rule is in [If no timeout rule matches, Private Access applies the default timeout policy rule, which requires authentication every 7 days for any application and never ends a session for idle time.](kb:zpa.policy.evaluation-order:default-timeout-rule). The MCP skill's defaults differ [divergence:zpa.policy.timeout-rules:timeout-defaults]. The pages also use the word default for the idle timeout in two ways [divergence:zpa.policy.timeout-rules:default-idle-timeout].

**Intervals and idle sessions.** When the Authentication Timeout or the Idle Connection Timeout is set to a Specific Interval in days, hours or minutes, each interval must be at least 10 minutes. [zpa.policy.timeout-rules:minimum-interval] On the configuring page, if Default is selected for the Idle Connection Timeout, an open TCP session times out after 2 hours, a half-closed TCP session after 6 minutes, a fully-closed TCP session is terminated immediately, and a UDP session times out after 60 seconds. [zpa.policy.timeout-rules:default-idle-session-timeouts] The Idle Connection Timeout value can be increased granularly per application segment for long-lived sessions, and the TCP sessions ended by the default idle timeout of 2 hours are found in User Activity Diagnostics with the Connection: Status Code filter equal to SE: Timeout policy closed idle connection and the Application Duration filter greater than 7,200,000. [zpa.policy.timeout-rules:idle-increase-per-segment] The default timeout policy rule can also be edited. [zpa.policy.timeout-rules:default-rule-editable]

**Certificates, Never and special cases.** Zscaler Client Connector certificates have a validity of 365 days from the date of enrollment; if the authentication timeout is set to Never, users are only prompted to re-enroll to renew device certificates. In some cases the certificate renewal might fail because of connectivity issues to the IdP, and the user might then need to log out of Client Connector and log back in. [zpa.policy.timeout-rules:certificate-validity-never] If VMware's Unified Access Gateway (UAG) is used for application access, a separate rule must be created with the Authentication Timeout set to Never. [zpa.policy.timeout-rules:uag-never] The page says the Authentication Timeout setting can be used within a policy rule only if users are running Zscaler Client Connector version 1.2.1 or later. [zpa.policy.timeout-rules:auth-timeout-client-version] The recommended time interval for the Cloud Browser client type is one day; once the user is authenticated the session timeout value is the minimum timeout across the configured timeout policies, and after the timeout the user must reauthenticate with Private Access to reach applications through Isolation. [zpa.policy.timeout-rules:cloud-browser-recommended]

**Building a rule.** The only action the MCP skill supports on a timeout rule is RE_AUTH. [zpa.policy.timeout-rules:action-re-auth-only] The MCP skill writes timeout values as strings in the form N Minutes, N Hours or N Days, or as Never, with a 10 minute minimum. [zpa.policy.timeout-rules:timeout-value-format] The v2 Terraform timeout rule reads the API's timeouts back as strings of seconds and treats "-1" as never. [zpa.policy.timeout-rules:tf-read-seconds-as-strings] The numeric type differs between sources [divergence:zpa.policy.timeout-rules:reauth-value-type]. A timeout rule name cannot contain special characters except hyphens and underscores. [zpa.policy.timeout-rules:name-characters] Whether a period is rejected in a timeout rule name is open [gap:zpa.policy.timeout-rules:timeout-name-period].

**Conditions.** The MCP skill lists these condition types for timeout rules: APP, APP_GROUP, CLIENT_TYPE, SAML, SCIM, SCIM_GROUP, PLATFORM and POSTURE. [zpa.policy.timeout-rules:condition-types-supported] Which types a rule rejects is open [gap:zpa.policy.timeout-rules:timeout-condition-restriction]. The console's timeout rule criteria cover SAML and SCIM attributes (replaced by Session and User Attributes with Authentication Service), an external IAM IdP, application segments and segment groups, Client Connector Posture Profile condition sets, trusted networks, client types, an application federated by a partner, and platforms. [zpa.policy.timeout-rules:console-criteria] The client types listed for a timeout rule are Client Connector, Cloud Browser, Web Browser and Internet & SaaS Service Edge, and rules using the Web Browser or Internet & SaaS (ZIA) Service Edge client types can not also use posture profiles. [zpa.policy.timeout-rules:client-types] When timeout policies use the Federated Applications criteria, only the Client Type criteria set to Client Connector is supported for the host partner, only the host partner can configure timeout policies for guest partners, and the guest partner's end users are also evaluated against the host partner's timeout policies. [zpa.policy.timeout-rules:federated-applications] The 10-condition-set limit is in [The access global rules and policy groups, timeout, client forwarding and Browser Protection rule editors each say the criteria drop-down only displays criteria not already in use by the rule, except for Client Connector Posture Profile condition sets, and that up to 10 condition sets can be added; the redirection editor says the drop-down only displays unused criteria and up to 10 condition sets can be added, with no exception for posture stated.](kb:zpa.policy.conditions:condition-set-limit). The MCP skill's posture example gives devices that pass a posture check a longer timeout and non-compliant devices a shorter one, using two rules with the POSTURE rhs set to true and to false. [zpa.policy.timeout-rules:posture-tiering-example]

Fields and Terraform replacement are in [Rule fields beyond criteria: reauth, posture notification and profile IDs](kb:zpa.policy.rule-fields).

What to check:
1. Read the matching timeout rule and the default rule, since the default applies to every user a rule does not cover.
2. If a user is re-authenticating sooner than the rule says, check for a recent reauthentication in another application, which resets the timer for all of them.
3. When building a rule programmatically, check the timeout value type each client uses.
4. If a rule uses country or trusted network conditions, check the rule's condition types against the supported list.
5. If a session ends or reauthenticates at an unexpected time, compare the rule's Specific Interval values with the 10 minute minimum, the Default idle timeouts, and the two named reauthentication timestamps.
6. If users on Client Connector must renew a certificate or reach an application through VMware's Unified Access Gateway, check the rule's Authentication Timeout and the certificate renewal conditions.

Sources disagree (name both sides):
- The Configuring Timeout Policies page says the reauthentication interval is based on the SAML assertion's issue date, while About Timeout Policy says the Private Access Public Service Edge uses the notBefore timestamp in the SAML assertion response. [divergence:zpa.policy.timeout-rules:reauth-timestamp]
  - zscaler-help: The reauthentication interval is based on the SAML assertion's issue date.
  - zscaler-help: The Public Service Edge uses the notBefore timestamp to calculate whether reauthentication is necessary.
  Impact: The pages name different timestamps for the reauthentication timer and do not say whether the issue date and notBefore are the same value, so which one the timer uses is unresolved.
- The Configuring Timeout Policies page calls 2 hours for an open TCP session the default idle timeout, while About Timeout Policy says the default rule's sessions never end due to an idle connection timeout expiration. [divergence:zpa.policy.timeout-rules:default-idle-timeout]
  - zscaler-help: The default idle timeout is 2 hours for an open TCP session, when Default is selected for the Idle Connection Timeout.
  - zscaler-help: The default rule's sessions never end due to an idle connection timeout expiration. The same claim is zpa.policy.evaluation-order:default-timeout-rule.
  Impact: The pages may mean two different things, the Default option of the Idle Connection Timeout and the default timeout policy rule, but neither page says how the two relate, so whether an idle session under the default rule ends after 2 hours is unresolved.
- The help describes the default timeout rule as 7 days and never idle, while the MCP skill gives parameter defaults of 2 days and 10 minutes. [divergence:zpa.policy.timeout-rules:timeout-defaults]
  - zscaler-help: The default timeout policy rule is 7 days for authentication and no idle expiry.
  - mcp-server: The session timeout parameter defaults to 172800 seconds (2 days).
  - mcp-server: The idle timeout parameter defaults to 600 seconds (10 minutes).
  Impact: The legacy statement that 2 days and 10 minutes apply when a rule's reauth fields are unset cannot be reconciled with the help's 7 days and never; the skill's values are parameter defaults of its tool, not a documented tenant default.
- The OpenAPI document declares reauthTimeout an integer, while the Go SDK uses a string and the MCP skill uses N Minutes strings. [divergence:zpa.policy.timeout-rules:reauth-value-type]
  - api-specs: reauthTimeout is an int32 integer.
  - sdk-go: The Go SDK sends reauthTimeout as a string.
  - mcp-server: The MCP skill writes the value as an N Minutes string.
  Impact: A programmatic constructor that follows the OpenAPI integer type may not match what the SDK and provider send, and the provider reads values back as seconds strings.
