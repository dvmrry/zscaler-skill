# The Cloud Run provisioning pipelines that deploy the AI Guard Apigee patterns: what they create, the KVM they write, and the cloud the SharedFlow pipeline leaves at us1 (ai-security.ai-guard.integrations.google-cloudrun)
Also called: ai guard cloud run; ai guard cloud build; aiguard-apigee-provisioner; provision_org.py; ai guard apigee pipeline

The Cloud Run folder automates deploying the two Apigee patterns; it adds no scanning logic of its own. Each pipeline is Cloud Build building a provisioner image and running it as a Cloud Run Job that enables APIs, creates the Vertex service account and its IAM bindings, writes the encrypted KVM, and imports and deploys the bundles: `flow/` deploys the SharedFlow and the `vertex-aiguard-sync` proxy, `proxy/` the inline `vertex-aiguard` proxy. [ai-security.ai-guard.integrations.google-cloudrun:pipelines] Each pipeline carries its own copy of the Apigee bundles under `bundles/`, and the README says to update the matching copy when the canonical bundle under `Google/apigee` changes. [ai-security.ai-guard.integrations.google-cloudrun:bundle-copies] At the pin the pipelines' bundle copies are identical to the canonical SharedFlow, `vertex-aiguard-sync` and inline-proxy bundles, so the Apigee subjects describe what the pipelines deploy. [ai-security.ai-guard.integrations.google-cloudrun:bundle-copies-identical]

**What they need.** The pipelines configure an existing Apigee X organization and do not create one; the separate `provision_org.py` creates the organization, runtime instance, environment, environment group and both attachments, and the README warns the runtime instance takes 20 to 40 minutes and the region must match any existing API Hub instance. [ai-security.ai-guard.integrations.google-cloudrun:org-not-created] The bootstrap script stores the AI Guard key in Secret Manager as `aiguard-api-key` and Cloud Build injects it into the Job; it is not a trigger substitution. [ai-security.ai-guard.integrations.google-cloudrun:api-key-secret]

**The KVM they write.** The SharedFlow pipeline writes only `aiguard_api_key`, plus `aiguard_policy_id` when one is given, to the `aiguard-config` KVM; the inline-proxy pipeline also writes `aiguard_cloud` (substitution `_AIGUARD_CLOUD`, default `us1`), `vertex_project` and `vertex_model`. [ai-security.ai-guard.integrations.google-cloudrun:kvm-entries] As deployed by the SharedFlow pipeline, scans go to `api.us1.zseclipse.net`: the pipeline has no cloud setting, the SharedFlow takes the cloud only from an `aiguardCloud` flow variable, and the shipped `vertex-aiguard-sync` proxy sets none, so a tenant on another cloud gets authentication failures, which fail closed, until the calling proxy sets `aiguardCloud`. [ai-security.ai-guard.integrations.google-cloudrun:flow-cloud-us1]

**What gets deployed.** The scanning behavior is the inline proxy's ([The inline Apigee X proxy for Vertex AI with AI Guard: the policy flow, what it extracts, when it blocks, and what passes unscanned](kb:ai-security.ai-guard.integrations.google-apigee-proxy)) or the SharedFlow's ([The ZSCALER-AIGUARD Apigee SharedFlow: dialects, what each leg scans, MCP tool calls, verdict handling, and the traffic it lets through unscanned](kb:ai-security.ai-guard.integrations.google-apigee-sharedflow)).

What to check:
1. For the SharedFlow pipeline, which AI Guard cloud the tenant is on; outside us1 the deployed proxy must be given an aiguardCloud flow variable.
2. After changing a canonical bundle under Google/apigee, that the pipeline's copy under bundles/ was updated too.
