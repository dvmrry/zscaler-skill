# How are onboarded AWS, Azure and GCP accounts managed in AI Security: the Cloud Accounts page, validation, status, issues, deletion, orchestrator changes and the orchestrator itself? (ai-security.asset-management.cloud-accounts)
Also called: Cloud Accounts page ai security; Account Onboarding; ai security orchestrator; scanner instances; local scanner platform; delete onboarded account; change orchestrator account

AI Security supports onboarding AWS accounts, Microsoft Azure subscriptions and GCP projects; it continuously monitors and scans onboarded cloud accounts for sensitive data and vulnerabilities and generates issues from data security policy violations. [ai-security.asset-management.cloud-accounts:providers-and-monitoring] The per-provider onboarding is in [How AI Asset Management onboards AWS accounts and organizations: prerequisites, templates, CloudTrail, network and IAM roles](kb:ai-security.asset-management.onboarding-aws), [How is a Microsoft Azure tenant, management group or subscription onboarded to AI Security: roles, templates, network and error fixes?](kb:ai-security.asset-management.onboarding-azure) and [How AI Asset Management onboards GCP organizations: prerequisites, templates, service account, network, IAM roles and errors](kb:ai-security.asset-management.onboarding-gcp), and the hub is [AI Asset Management in the AI Security Admin Portal: what it inventories, signing in, first-time configuration order, table behavior](kb:ai-security.asset-management).

**Cloud Accounts page.** On the Cloud Accounts page (Administration > Account Onboarding) each provider has its own extra management actions: AWS has Manage CloudTrail, Manage Services, Manage Evidence and Manage Data Events; Azure has Change Application Details, Manage Private Endpoint, Manage Services and Manage Evidence; GCP has Update Service Account and Update Private Key. [ai-security.asset-management.cloud-accounts:provider-specific-manage-actions] The Managing Orchestrator Network (Custom) action configures the orchestrator network and is applicable only if the AI Security Connection Status is failed. [ai-security.asset-management.cloud-accounts:orchestrator-network-custom] After onboarding completes successfully, a selected cloud account shows an Overview tab (onboarding status and orchestrator details), an Issues tab (issues encountered while onboarding) and a Roles and Templates tab (roles created while onboarding and templates generated by AI Security). [ai-security.asset-management.cloud-accounts:account-detail-tabs] The accounts list is on the Accounts tab for AWS, Subscriptions tab for Azure and Projects tab for GCP; its columns include name, ID, business unit, status (Successfully Configured, Pending Configuration, Needs Attention) and Last Validated. [ai-security.asset-management.cloud-accounts:account-list] An account's detail page shows CloudTrail Bucket Name, Prefix and Bucket Account ID only for AWS accounts; its Issues view lists onboarding configuration issues with resolution steps. [ai-security.asset-management.cloud-accounts:account-cloudtrail]

**Validation and status.** AI Security validates cloud accounts every hour to check the onboarding templates are deployed and roles and permissions configured, and an on-demand validation can be run for a single account or for all accounts in the organization. [ai-security.asset-management.cloud-accounts:validation] The Overview tab donut chart counts accounts as Successfully Configured, Needs Attention (misconfigurations or permission issues) or Pending Configuration (roles and permissions not yet configured and validated); a health validation service checks template deployment and roles. [ai-security.asset-management.cloud-accounts:overview-status] On the onboarding status page, which shows an AWS account as its example and says field names vary by cloud account, the Overview tab's Orchestrator Details show Account Name, Account ID, Custom Tags count, primary Region, Network Type, AI Security Connection Status (Successful or Failed), Configuration Status (Successful, Warning, Failed or Pending Validation) and Last Connected. [ai-security.asset-management.cloud-accounts:overview-orchestrator] The Overview tab's CloudTrail section is available only for AWS organizations and shows bucket name, prefix, bucket account ID and a status of Enabled or Failed. [ai-security.asset-management.cloud-accounts:overview-cloudtrail] On the onboarding status page, which shows an AWS account as its example and says field names vary by cloud account, the Overview tab's Evidence section shows S3 bucket name, storage type (Zscaler or Custom) and S3 bucket account ID. [ai-security.asset-management.cloud-accounts:overview-evidence] After onboarding, the services to scan can be selected for a cloud account (Manage Services is listed in the account actions for AWS and Azure), and AI Security permissions are restricted to monitoring and scanning data only in the selected services. [ai-security.asset-management.cloud-accounts:manage-services]

**Issues.** AI Security lists onboarding issues for an AWS organization, GCP organization or Azure tenant on an Issues tab with resolution steps; unaddressed issues might affect scanning, and affected target accounts or projects move to Needs Attention until resolved. [ai-security.asset-management.cloud-accounts:issue-types] The onboarding issues table has AWS, Microsoft Azure and GCP columns. Role or permission issues are listed in all three; Orchestrator validation is pending and Orchestrator unable to communicate with AI Security are in the AWS and GCP columns (the Azure column in those rows gives a role issue in the orchestrator subscription and a suspended account); Onboarded account is deleted is in the Azure and GCP columns (AWS gives Resources missing in the orchestrator account). [ai-security.asset-management.cloud-accounts:issue-list]

**Roles and templates.** For AWS the Roles and Templates tab offers a CloudFormation or Terraform template for Tree Discovery, Orchestrator, Monitoring Scope and Evidence, and shows the role's external ID. [ai-security.asset-management.cloud-accounts:templates-aws] For Microsoft Azure the Roles and Templates tab offers the Tree Discovery, Azure Onboarding and Evidence templates to run on the Azure tenant. [ai-security.asset-management.cloud-accounts:templates-azure] For GCP the Roles and Templates tab offers the Tree Discovery and GCP Onboarding templates to run on the GCP organization. [ai-security.asset-management.cloud-accounts:templates-gcp] A banner on the Overview tab announces a new template when one is available; closing it removes it only for the current session. [ai-security.asset-management.cloud-accounts:new-template-banner] Clicking Acknowledge makes a new template override the existing one; only an Administrator role can acknowledge, a role with View Cloud Accounts permission can only view or download, and acknowledging for one organization or tenant updates all. [ai-security.asset-management.cloud-accounts:template-acknowledge] Templates can be redeployed to upgrade to a new template, when custom roles created during onboarding have issues, or to modify or delete a role. [ai-security.asset-management.cloud-accounts:redeploy]

**Deleting an account.** Deleting an onboarded account cannot be reverted, so the account must be onboarded again to be scanned; it does not delete resources created while deploying templates, which must be deleted manually (the page names the terraform destroy command). [ai-security.asset-management.cloud-accounts:delete-effects] Deleting an account closes all issues generated for it, disables an alert rule or ignore alert filter whose scope was only that account (marked invalid), disables a scan configuration whose only selected account it was, and marks existing custom policies created for it as invalid. [ai-security.asset-management.cloud-accounts:delete-module-impact] Deleting needs the Administrator role or any role with Delete Account permissions; deleting an organization or tenant deletes it and all associated accounts from the AI Security Admin Portal. [ai-security.asset-management.cloud-accounts:delete-permission-and-confirmation] Deleting a single account or multiple accounts removes them only from the AI Security Admin Portal, with no impact on those accounts at the cloud service provider. [ai-security.asset-management.cloud-accounts:delete-single-no-csp-impact] [gap:ai-security.asset-management.cloud-accounts:delete-resources-wording]

**Changing the orchestrator.** Changing the orchestrator requires an administrator role or a role with the Configure New Orchestrator permission (AWS and GCP: in the AI Security Admin Portal; Azure: in the Zscaler Admin Console). [ai-security.asset-management.cloud-accounts:change-orchestrator-permission] Until a new orchestrator is validated after a change, the existing orchestrator is disabled, the AI Security connection status is Waiting for Connection and Configuration status is Pending, data scans stop, and the target accounts (AWS), subscriptions (Azure) or projects (GCP) move to Needs Attention; this is stated on the AWS, Azure and GCP change-orchestrator pages. [ai-security.asset-management.cloud-accounts:orchestrator-change-effects] After the new orchestrator template is validated, AWS target accounts (and Azure onboarded subscriptions) move to Successfully Configured, AI Security begins the data scan, and on the AWS page the orchestrator AI Security Connection and Configuration Status move to Successful; the AWS, Azure and GCP change pages each say AI Security validates the template deployment every hour. [ai-security.asset-management.cloud-accounts:orchestrator-change-success-state]

**The orchestrator and scanner instances.** The local scanner platform is an orchestrator instance plus scanner instances; the orchestrator is an EC2 instance, virtual machine or cloud storage that organizes scanning across the selected AWS, Azure and GCP regions, and it creates the scanner instances. [ai-security.asset-management.cloud-accounts:orch-architecture] The orchestrator account is the account and primary region where Zscaler's AI Security orchestrator template is deployed; AI Security uses that template to scan target accounts' data stores, and an autoscaler keeps at least one orchestrator running. [ai-security.asset-management.cloud-accounts:orch-account] Scanner instances launch in the orchestrator account in the regions where the target account's data stores are, are terminated after the scan, and keep scanning inside the customer's cloud, which avoids interregional data transfer costs; scanning of all global regions of AWS, Azure and GCP is supported. [ai-security.asset-management.cloud-accounts:orch-scan-regions] The orchestrator instance needs only outbound internet access to AI Security; for the US Cluster its outbound connections are limited to six listed service IPs and two FQDNs. [ai-security.asset-management.cloud-accounts:orch-egress] Supported orchestrator instance types: AWS t3.large, Azure Standard_D2s_V3 and GCP e2-standard-2, each 2 vCPUs and 8 GiB, with the listed root and data disks. [ai-security.asset-management.cloud-accounts:orch-sizes] The scanner instances page says that for each data store AI Security creates up to 10 scanner instances of 16 vCPU and 32 GiB, depending on how many data stores need scanning, and that the orchestrator account needs sufficient vCPU quotas. [ai-security.asset-management.cloud-accounts:orch-scanner-max] Scanner instances are transitory and use a Zscaler-owned image shared with the customer's orchestrator account; inbound access to them is restricted to the orchestrator instance, and their tags must not be deleted or tampered with. [ai-security.asset-management.cloud-accounts:orch-scanner-security] Scanner instances carry five tags (z-ais-resource, z-ais-scanner-resource, z-ais-tenant-id, z-ais-tenant-name, z-ais-scan-id) that can be enabled in AWS to track cost allocation for AI Security. [ai-security.asset-management.cloud-accounts:orch-scanner-tags] [gap:ai-security.asset-management.cloud-accounts:scanner-size-figures]

**Default scanner instance types.** Default AWS scanner instance types by data store and scan type: S3 full c5a.4xlarge, S3 incremental t3.xlarge, EC2 full c6in.4xlarge, RDS full c5a.4xlarge db.r6g.large, RDS sampling t3.medium db.r6g.large, DynamoDB full and sampling t3.xlarge. [ai-security.asset-management.cloud-accounts:orch-scanner-default-aws] Default Azure scanner instance types: Blob Container, Virtual Machine and File Share full scans Standard_F16s_v2; Blob Container and File Share incremental Standard_D4s_v3; SQL Server PostgreSQL-Flexible Server full Standard_F16s_v2; SQL Server PostgreSQL-Flexible Server and Azure Cosmos DB for NoSQL sampling Standard_B2ls_v2. [ai-security.asset-management.cloud-accounts:orch-scanner-default-azure] Default GCP scanner instance types: Cloud Storage Bucket full e2-standard-16 and incremental e2-standard-8; Compute and Cloud SQL full e2-standard-16; Cloud SQL and BigQuery sampling e2-standard-2. [ai-security.asset-management.cloud-accounts:orch-scanner-default-gcp]

**Orchestrator network and status.** The orchestrator network can be modified when the existing network is being decommissioned or deleted or the wrong network was selected, only when the AI Security Connection Status is failed for the custom network configuration type; the orchestrator template must then be rerun. It needs an Administrator role or a custom role with the Configure Monitoring Scope permission. [ai-security.asset-management.cloud-accounts:orch-network-change] When modifying the orchestrator network, AWS asks for a Subnet ARN; Azure asks for Subnet ID, Network Security Group ID and a Storage Account Name of at most 16 characters, and with a new subnet from a different VNet the scale-set terraform destroy command must run before deploying the new template. [ai-security.asset-management.cloud-accounts:orch-network-fields] The orchestrator status page lists the orchestrator's AI Security Connection Status as Successful, Failed (cannot establish a connection) or Waiting for connection (orchestrator template not yet deployed in the cloud service provider). [ai-security.asset-management.cloud-accounts:orch-connection-status] The orchestrator Configuration Status is Successful, Warning, Failed or Pending: Warning means some resources or permissions are unavailable, tampered with or not visible; Failed means scanner instances cannot be launched or roles and permissions are missing; Pending means the orchestrator account changed or the template is yet to be deployed. [ai-security.asset-management.cloud-accounts:orch-config-status] [gap:ai-security.asset-management.cloud-accounts:orch-other-clusters]
