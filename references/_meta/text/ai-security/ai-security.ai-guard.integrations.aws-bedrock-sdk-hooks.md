# The AI Guard boto3 hook for Amazon Bedrock: before-call and after-call scanning, what the content walkers read, block styles, and what is not scanned (ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks)
Also called: ai guard boto3 hook; ai guard bedrock sdk hooks; aiguard_boto3_hook.py; protect_client; protect_session; ai guard bedrock converse; ai guard invoke_model; apply_masked_data

The boto3 hook attaches to the botocore event system of a bedrock-runtime client, so every model call through that client is scanned, including calls a framework makes. `protect_client` (one client) or `protect_session` (every bedrock-runtime client created from the session afterwards) registers before-call and after-call handlers for Converse, ConverseStream, InvokeModel and InvokeModelWithResponseStream under fixed unique IDs; protecting the same client or session twice is a no-op, not a double scan; other clients, processes and raw HTTPS calls are not covered. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:registration] The prompt is scanned in before-call; a block returns before botocore signs or sends the request, so nothing reaches AWS or is billed. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:prompt-before-signing]

**The prompt leg.** For Converse calls the prompt leg scans the system prompt and every user-role message; assistant-role turns and the tool specifications in `toolConfig.tools[].toolSpec` are sent to the model unscanned. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:prompt-coverage] The content walker is an allowlist: it reads text, guardContent text, toolUse name and arguments, toolResult text, JSON and search results, reasoning text, searchResult passages and citation text; documents, images, video, audio, redacted reasoning and any unrecognized block are flagged opaque, except a `cachePoint` holding only `type` and `ttl`. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:block-walker] For InvokeModel the prompt is taken from the messages dialect, from Cohere's `message` with `chat_history`, `documents` and `tool_results`, or from `inputText` or `prompt`; a body in no known dialect, or one that is not JSON, is scanned whole as raw text. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:invoke-dialects] On the prompt leg any opaque content blocks the call when `on_unscannable` is `"block"` (the default), even when the request also carries text. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:prompt-opaque-blocks]

**The response leg.** The response leg scans the assistant text with direction OUT and sends only that text; the prompt the hook stores for the response leg is not included in the request. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:response-only-text-sent] The README says the prompt rides along as context [divergence:ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:response-context]. The response leg discards the walker's opaque flag: a reply with no extractable text follows `on_unscannable`, but a reply that mixes text with a block the walker cannot inspect (such as a document, an image or an unrecognized block) is scanned on its text alone. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:response-opaque-ignored] For ConverseStream and InvokeModelWithResponseStream only the prompt is scanned; the streamed response is still on the wire when after-call fires, so the hook logs a skipped-stream line and returns without scanning it. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:stream-response-skipped] An AWS error response (a parsed `Error` or an HTTP status of 300 or more) is not scanned: the hook steps aside so botocore raises the genuine exception (a throttle, auth failure or validation error) instead of masking it with a scan verdict. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:aws-errors-pass]

**Blocking.** With `on_block="raise"` (the default) a block raises `AIGuardBlocked`; with `"respond"` the hook returns a well-formed reply instead: a Converse message with `stopReason` `content_filtered`, a JSON body for InvokeModel, or a minimal event stream for the streaming operations, with the verdict under `ResponseMetadata.AIGuard`; a blocked response is replaced the same way. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:block-styles]

**Options.** The hook accepts only `app_name`, `policy_id`, `session_id`, `app_user`, `on_block`, `on_verdict`, `on_error`, `on_unscannable`, `strict_verdict`, `scan_prompt`, `scan_response` and `timeout`, and raises TypeError for any other option. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:unknown-options-rejected] Passing `apply_masked_data`, which the README documents for masking, makes `protect_client` or `protect_session` raise TypeError, and the module contains no masking path. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:masking-option-rejected] The README documents a masking mode [divergence:ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:masking]. The README's configuration example has two bare `policy_id=` lines, so it is not valid Python as written, and one describes the policy ID as an "AI profile UUID" while the module parses it with int(). [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:readme-invalid-python] `session_id`, `app_name` and `app_user` are accepted and stored but never used: each call gets a fresh uuid4 transaction ID, and neither the scan request nor the log line carries them. [ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:session-unused]

**Shared behavior.** Endpoint, verdicts, the on_error switch and the timeout default are in [Zscaler's AWS AI Guard examples (Lambda decorator, boto3 Bedrock hook, AgentCore guard, Strands hooks): seats, the shared scan client, verdict and failure handling](kb:ai-security.ai-guard.integrations.aws).

What to check:
1. Whether the application streams (ConverseStream or InvokeModelWithResponseStream); for those only the prompt is scanned.
2. Whether a protected client is the only path to Bedrock; other clients, processes and raw HTTPS calls are not covered.
3. Whether the request carries assistant turns or tool specifications built outside this client; those reach the model unscanned.
4. That the hook is constructed only with the options its code accepts; apply_masked_data from the README raises TypeError.

Sources disagree (name both sides):
- Whether the response scan carries the prompt as context. [divergence:ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:response-context]
  - zguard-integrations: The README's sequence diagram shows the after-call scan sending the response with the prompt as context when prompt scanning is on.
  - zguard-integrations: The code stores the prompt with the response but sends only the response text.
  Impact: Detections that need the prompt beside the response see only the response on this seat; the Lambda decorator and the AgentCore guard do send both.
- Whether the boto3 hook can apply AI Guard masking to a response. [divergence:ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks:masking]
  - zguard-integrations: The README documents apply_masked_data=True: masked text replaces the response's text blocks on mask-and-allow profiles, and InvokeModel gets a replacement envelope.
  - zguard-integrations: The module's option set has no apply_masked_data and it rejects unknown options.
  - zguard-integrations: The Apigee example's architecture note says AI Guard returns a verdict, not a rewritten payload, so there is no masking path.
  Impact: Following the README's masking setup fails at construction with TypeError. Whether the detection API returns masked content at all is not settled by these examples; the SDK's response model (ai-security.ai-guard.runtime-api:response-fields) lists no masked-content field.
