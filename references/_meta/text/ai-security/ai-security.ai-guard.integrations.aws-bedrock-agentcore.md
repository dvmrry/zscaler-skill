# The AI Guard guard for Amazon Bedrock AgentCore agents: the four legs you call, the tool wrapper, and what each leg sends (ai-security.ai-guard.integrations.aws-bedrock-agentcore)
Also called: ai guard bedrock agentcore; AIGuardGuard; aiguard_agentcore.py; guard_tool; scan_tool_output; ai guard agentcore tool_event

The AgentCore integration is a guard object that an agent's own loop calls; AgentCore Runtime hosts the code but offers no interception point. The integration is a guard the agent's own loop calls at four legs (scan the prompt before the model, the response after it, a tool's input before it runs, its output before it re-enters the model); nothing is automatic beyond tools wrapped with `guard_tool`. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:guard-not-hook] Each `scan_*` method returns the verdict on allow and raises `AIGuardBlocked`, carrying the leg, the verdict and the transaction ID, on a block; under the default postures a scan error or unscannable content raises it too. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:blocked-raises]

**Wrapping tools.** `guard_tool` scans a tool's input before it runs and its output before returning, binding arguments to parameter names and dropping a `self` or `cls` receiver; an async tool is awaited and its scans run in a worker thread, and a generator or async-generator tool is drained so its whole output is scanned once before the first item is yielded. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:guard-tool-shapes] A wrapped tool that returns a coroutine or a generator instead of a value is treated as unscannable output and follows `on_unscannable` (block by default); other lazy iterators such as `map` or `filter` are not recognized and are serialized as they stand, usually as their repr. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:lazy-result-unscannable]

**What each leg sends.** On the prompt and response legs an empty text follows `on_unscannable` (block by default), each judged on its own field, so a prompt passed as context does not satisfy an empty response; the tool legs always scan, since a tool event names the tool even with no arguments or result. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:empty-model-legs] `scan_response` sends the prompt, when one is passed, and the response joined into one `content` string with direction OUT; its `context` argument is stored but not sent, because the payload builder reads only the `prompt`, `response` and `tool_event` keys. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:response-leg-content] A tool leg builds a tool event with metadata (ecosystem `mcp`, method `tools/call`, the server name, default `agent-tools`, and the tool name), the input and, on the output leg, the output, then serializes it with json.dumps into the `content` string; the API receives text, not a separate tool-event field. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:tool-event-serialized] The README describes the tool legs as structured tool events [divergence:ai-security.ai-guard.integrations.aws-bedrock-agentcore:tool-event-shape].

**Runtime context.** Inside AgentCore Runtime the guard takes the request and session IDs from `BedrockAgentCoreContext` and the agent ARN from `cloud.resource_id` in `OTEL_RESOURCE_ATTRIBUTES`, cutting a runtime-endpoint ARN back to the runtime ARN; off-runtime it falls back to a generated ID. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:runtime-ids]

**Limits.** Non-streamed model calls are covered; for a streamed response the guard intercepts nothing, and the agent code chooses whether to scan each buffered chunk or the assembled text. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:streaming-caller] The README reports that on a profile with the source-code detector enabled, tool input, which is a serialized JSON object, can be flagged on its own (arguments as plain as `{"x": "x"}`), so the input leg blocks before the tool runs and a benign tool call is denied; it advises a profile without that detector for tool legs, or scanning tool output only. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:source-code-detector] Each leg adds one scan and each tool round two; `timeout=` bounds the connect and, separately, the response read, so a peer trickling bytes costs at most about twice the timeout. [ai-security.ai-guard.integrations.aws-bedrock-agentcore:latency] The call, verdict handling, timeout and failure switches shared by the AWS examples are in [Zscaler's AWS AI Guard examples (Lambda decorator, boto3 Bedrock hook, AgentCore guard, Strands hooks): seats, the shared scan client, verdict and failure handling](kb:ai-security.ai-guard.integrations.aws).

What to check:
1. That every model call and every tool in the agent loop goes through a scan_* call or a guard_tool-wrapped function; a leg the code does not call is not scanned.
2. For a streamed model response, where the agent scans the text (per chunk or assembled), since the guard does not intercept streams.
3. Whether the tool-leg policy has the source-code detector enabled, which can block benign tool calls before they run.

Sources disagree (name both sides):
- Whether the AgentCore and Strands tool legs reach AI Guard as a structured tool event that gets a tool-specific verdict. [divergence:ai-security.ai-guard.integrations.aws-bedrock-agentcore:tool-event-shape]
  - zguard-integrations: The AgentCore README says the tool input is sent as a tool_event, which lets AI Guard return a tool-specific verdict such as context poisoning or credential leakage instead of treating the result as plain text.
  - zguard-integrations: The Strands README says the same of its tool-output leg.
  - zguard-integrations: Both modules serialize the tool event into the single content string, noting that AI Guard scans one string per call, and their notes also say the API rejects any tool ecosystem but mcp with HTTP 400, a check that would need a structured field.
  Impact: What AI Guard receives at the pin is text in content (tool-event-serialized); whether it recognizes that text as a tool event and returns tool-specific detections is not shown by the code, the SDK or Help. The modules' log code reads a tool_detected field that their verdict parser never fills.
