# The AI Red Teaming Onboarding Agent: generating a Proxy SDK proxy for a non-standard app, its spec gate, versions and local skill (ai-security.ai-red-teaming.onboarding-agent)
Also called: onboarding agent; ai red teaming onboarding agent; generate proxy; red teaming proxy; onboarding agent skill; download skill; onboarding agent prompting guide

During Red Teaming tests AI Red Teaming acts as a client connecting to the application; the intermediary layer that translates for a non-standard application is called a proxy, and custom-built apps need custom-built proxies while other apps can be connected with AI Security's prebuilt connectors; building one means collecting the application's connection protocol, authentication method, session behavior, message format and rate limits. [ai-security.ai-red-teaming.onboarding-agent:why-a-proxy] The Onboarding Agent is a chat-based assistant in the AI Security Admin Portal that guides the user through collecting the proxy specification with structured questions and generates a complete, ready-to-deploy Python project, using the responses along with any API documentation uploaded. [ai-security.ai-red-teaming.onboarding-agent:what-it-is]

**Sessions and the spec gate.** A session is Private, accessible only to the user who creates it, or Public, visible and accessible to all users within the organization or tenant; a session also takes a Business Unit. [ai-security.ai-red-teaming.onboarding-agent:sessions] The agent adapts follow-up questions to previous answers and tracks spec completeness as a percentage, and code generation cannot proceed until the spec is 100% complete, with every required field having a value; the spec covers connectivity (connection protocol, such as REST, WebSocket or SSE, and endpoints), authentication, message handling, session behavior, multimodal support and rate limits. [ai-security.ai-red-teaming.onboarding-agent:spec-gate]

**Output.** The agent produces a full Python project built on the proxy SDK containing main.py (a server subclass implementing open_session, send_message, and close_session), pyproject.toml, a Dockerfile, .env / .env.example, README.md and .vscode/launch.json; it is downloaded as a ZIP. [ai-security.ai-red-teaming.onboarding-agent:generated-project] The proxy is run locally or deployed with the provided Dockerfile, then a new connection with type Proxy SDK is created on the Configure your connection page pointing to the proxy's URL, which the platform must be able to reach (public URL, IP whitelisting, or broker). [ai-security.ai-red-teaming.onboarding-agent:connect-proxy] The Proxy SDK connection fields are in [Red Teaming connection types and the fields each needs (REST API, Proxy SDK, OpenAI REST API, Copilot Studio, Glean, Microsoft Teams, Agentforce, Amazon Bedrock AgentCore and Agents), and the connection test](kb:ai-security.ai-red-teaming.connections).

**Versions and the local skill.** Each generation creates a numbered version (v1, v2, v3...) with a timestamped history from which any previous version downloads as a ZIP; the prompting guide says the agent applies a focused patch to the existing code rather than rewriting from scratch. [ai-security.ai-red-teaming.onboarding-agent:versions] Skill is a downloadable package installed in a local coding agent environment (such as Claude Code, Cursor, or Copilot) that runs the same guided proxy-building experience on the user's machine without the AI Security Admin Portal; it runs a test script to validate the proxy's three endpoints, looks up common failures in a known-problems database if a test fails, and fixes the code automatically or asks a targeted follow-up question. [ai-security.ai-red-teaming.onboarding-agent:skill]

**What to trust.** The agent's automated check catches obvious mistakes such as bad imports and syntax errors but does not validate behavioral correctness, and the chat summary describes what the agent intended to build, not verified behavior. [ai-security.ai-red-teaming.onboarding-agent:check-limits] Zscaler's prompting guide says to test with two known-good tests and at least two failure modes (an authentication failure and a not-found or invalid-ID case), confirming the returned status codes match what was specified; it says distinct upstream failures such as bad authentication, not-found and rate-limiting have a tendency to collapse into a single generic error response, even when the summary states otherwise, and never to paste real credentials or customer data into the chat. [ai-security.ai-red-teaming.onboarding-agent:verify-guidance]

What to check:
1. That a generated proxy was run against the real target or a sandbox with known-good and failing cases before it is connected, since the agent's automated check and chat summary do not establish behavior.
