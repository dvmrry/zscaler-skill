# The AI Guard HookProvider for Strands Agents: which hook events it uses, how each leg can block, and what stays out of reach (ai-security.ai-guard.integrations.aws-strands-agents)
Also called: ai guard strands; ai guard strands agents; AIGuardHooks; aiguard_strands.py; AIGuardResponseBlocked; ai guard strands retry_limit

The Strands integration is one HookProvider passed to the agent; each leg's enforcement is limited by what the Strands event for that leg lets a hook write. `AIGuardHooks` registers callbacks on BeforeInvocationEvent (which only resets the response retry budget), BeforeModelCallEvent, AfterModelCallEvent, BeforeToolCallEvent and AfterToolCallEvent. [ai-security.ai-guard.integrations.aws-strands-agents:hook-events]

**Prompt.** Before each model call the provider scans the system prompt plus every user-role message it has not yet scanned (tracked by each message's `tracking_id`) and blocks by setting `cancel`, so the model is not called; a blocked turn is remembered and keeps cancelling, without a new scan, until it is removed from `agent.messages`. [ai-security.ai-guard.integrations.aws-strands-agents:prompt-leg] Content that cannot be read as text (a document, image or video block, encrypted reasoning, or any block type the framework adds later) is checked before the text: when `on_unscannable` is `"block"` (the default) it cancels the prompt leg, and on the response leg it raises `AIGuardResponseBlocked` at once, without retrying. [ai-security.ai-guard.integrations.aws-strands-agents:opaque-model-legs]

**Response.** AfterModelCallEvent lets a hook write only `retry`, so a blocked response is discarded and the model is called again, up to `retry_limit` (default 2) per invocation; after that the provider raises `AIGuardResponseBlocked`. [ai-security.ai-guard.integrations.aws-strands-agents:response-retry] Strands streams tokens to the agent's callback handler as the model produces them, so a stream consumer may already have received a response's tokens when the response leg discards it; the README quotes the Strands SDK's own note to that effect. [ai-security.ai-guard.integrations.aws-strands-agents:stream-before-verdict] A response retry re-enters the model-call loop at BeforeModelCallEvent and repeats both scans, so with `retry_limit=2` and a response that stays blocked one invocation issues six scans. [ai-security.ai-guard.integrations.aws-strands-agents:retry-scan-count]

**Tools.** A blocked tool input sets `cancel_tool`, so the tool does not run. [ai-security.ai-guard.integrations.aws-strands-agents:tool-input-cancel] A blocked tool output, or one carrying a member other than `text` or `json` when `on_unscannable` is `"block"` (the default), is replaced by an error tool result whose text is the block reason, so it never re-enters the model. [ai-security.ai-guard.integrations.aws-strands-agents:tool-output-replace] By the after-tool leg a tool's side effect has already happened; that leg protects the model from the result, and the README points to scanning the tool's input (the before-tool leg) to gate the call itself. [ai-security.ai-guard.integrations.aws-strands-agents:side-effects] The tool event is sent as text, as in the AgentCore guard: [A tool leg builds a tool event with metadata (ecosystem `mcp`, method `tools/call`, the server name, default `agent-tools`, and the tool name), the input and, on the output leg, the output, then serializes it with json.dumps into the `content` string; the API receives text, not a separate tool-event field.](kb:ai-security.ai-guard.integrations.aws-bedrock-agentcore:tool-event-serialized), with the README disagreement in [ai-security.ai-guard.integrations.aws-bedrock-agentcore:tool-event-shape](kb:ai-security.ai-guard.integrations.aws-bedrock-agentcore:tool-event-shape).

**Out of reach.** `Agent.structured_output()` and `structured_output_async()` call the model outside the agent loop, fire neither model-call event, and so reach the model unscanned; the README points to `agent(prompt, structured_output_model=MyModel)`, which runs through the loop. [ai-security.ai-guard.integrations.aws-strands-agents:structured-output] In a caller-supplied history, assistant-role turns are not scanned and a `toolResult` block inside a seeded user turn is not walked. [ai-security.ai-guard.integrations.aws-strands-agents:seeded-history]

**Options.** The constructor takes `app_name`, `policy_id`, `session_id`, `app_user`, `ai_model`, `agent_arn`, `agent_id`, `agent_version`, `on_error`, `on_unscannable`, `strict_verdict`, `on_verdict`, `retry_limit`, `tool_server` (default `strands-tools`) and `timeout`; it has no option to turn off the tool-input leg. [ai-security.ai-guard.integrations.aws-strands-agents:constructor-options] The README names an option the class lacks [divergence:ai-security.ai-guard.integrations.aws-strands-agents:scan-tool-input]. The README's configuration example has two bare `policy_id=` lines, so it is not valid Python as written; one calls the value an "AI profile UUID", while the module parses the policy ID with int(). [ai-security.ai-guard.integrations.aws-strands-agents:readme-invalid-python] The callbacks are coroutines that hand the blocking scan to the running event loop's default executor; the leg still waits for the verdict, but other sessions on the loop keep running. [ai-security.ai-guard.integrations.aws-strands-agents:async-executor] Shared behavior, including the 10-second timeout that ignores AIGUARD_TIMEOUT, is in [Zscaler's AWS AI Guard examples (Lambda decorator, boto3 Bedrock hook, AgentCore guard, Strands hooks): seats, the shared scan client, verdict and failure handling](kb:ai-security.ai-guard.integrations.aws).

What to check:
1. Whether a stream consumer (the default printing callback handler, a UI) can show response tokens before the response leg's verdict; the retry cannot unsend them.
2. Whether the application calls Agent.structured_output() or structured_output_async(); those bypass every leg.
3. After a blocked prompt, whether the turn was removed from agent.messages; until it is, every later invocation on that agent is cancelled.

Sources disagree (name both sides):
- Whether the Strands provider can turn off the tool-input leg. [divergence:ai-security.ai-guard.integrations.aws-strands-agents:scan-tool-input]
  - zguard-integrations: The README's Limitations advise setting scan_tool_input=False to keep only the output leg when the source-code detector blocks benign tool input.
  - zguard-integrations: The constructor has no scan_tool_input parameter.
  Impact: Passing scan_tool_input raises TypeError for an unexpected keyword; the remaining workaround is a policy profile without the source-code detector.
