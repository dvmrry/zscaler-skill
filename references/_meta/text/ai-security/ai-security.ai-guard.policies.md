# AI Guard policies: detector settings, policy control rules, first-match order, applications and testing (ai-security.ai-guard.policies)
Also called: ai guard policy; ai guard policy configuration; ai guard policy control; policy match rule; ai guard rule order; ai guard first match; ai guard policy not applied; ai guard policy testing; detector threshold; ai guard allow block detect; ai guard applications; application groups; match criteria

An AI Guard policy is a set of detector settings; it applies to traffic only through a policy control rule that matches it. Both halves are covered here.

**Policy configurations.** A policy is set by enabling detectors on prompts and responses; a tenant can have several policies, apply one per app, several to one app, or one to several apps. [ai-security.ai-guard.policies:policy-is-detectors] Most prompt detectors share Enabled (on by default), Severity, Threshold (the page words it as: the lower the threshold setting, the more strict AI Guard is with activating the policy) and Action: Allow lets the prompt proceed, Block blocks it, Detect flags it as detected, and some detectors also offer Disabled. [ai-security.ai-guard.policies:detector-settings] What strict means for the threshold depends on the page [divergence:ai-security.ai-guard.policies:strict-direction]. In the PII detector the Person's name category defaults to Disabled. [ai-security.ai-guard.policies:pii-name-disabled] Competition and Topic accept at most 10 entries at a time in a single policy, and the Topic/Off Topic runbook gives the Off Topic topic definitions up to 10 topics as well. [ai-security.ai-guard.policies:ten-limit] The detectors themselves are in [AI Guard's detectors: the capabilities Help lists and the detectors the policy editor configures](kb:ai-security.ai-guard.detectors).

**Threshold scale and roll-out.** The PII runbook defines the threshold as a number between 0.0 and 1.0 that controls how confident the model must be before it calls a prompt a match, comparing it to a volume knob: turned up, only very obvious mentions trigger; turned down, more borderline cases trigger too. [ai-security.ai-guard.policies:threshold-scale] Each of the PII, IP, Competition and Topic/Off Topic runbooks gives Severity as LOW for initial deployments, raised to MEDIUM or HIGH only after a user confirms the false-positive rate is acceptable, and says to validate in Policy Testing with five to ten sample prompts; each describes the detector's default on triggering as Detect (log only), Allow (pass through) or Block (stop the prompt), labeled Default State in the PII, Competition and Topic/Off Topic runbooks and Action in the IP runbook; the PII runbook adds that after creating a policy and confirming it works the next step is to create a policy match. [ai-security.ai-guard.policies:runbook-rollout] Per-detector settings are in [The AI Guard PII detector: categories, what it catches and misses, masking, entities and threshold](kb:ai-security.ai-guard.detectors.pii), [The AI Guard Intellectual Property detector: reproduction of a confidential context, what it ignores, sensitive context and threshold](kb:ai-security.ai-guard.detectors.intellectual-property), [The AI Guard Competition detector: the evidence rule, competitor list, tickers, languages, threshold and the scoreByCompetitor log field](kb:ai-security.ai-guard.detectors.competition) and [The AI Guard Topic and Off Topic detectors: OR and AND triggering, topic definitions, limits, threshold and languages](kb:ai-security.ai-guard.detectors.topic).

**Policy control.** A policy configuration is applied by attaching it through policy control to an LLM provider, user or user group; policy controls are evaluated top to bottom and evaluation stops at the first match. [ai-security.ai-guard.policies:control-binding] A user policy control needs a rule name, a policy configuration, a rule order and a rule status (enabled or disabled), and at least one match criterion among LLM provider and models (with Account Type when Organization Restrictions are on), users and user groups. [ai-security.ai-guard.policies:user-control-fields] In the API a match rule's criteria have one of three types: `APPLICATION` targets LLM applications (optionally specific application credentials), application groups, LLM providers, source IPs and optional custom request headers; `DAS_APPLICATION` targets DAS applications the same way without providers; `USER` targets Zscaler users and user groups, optionally narrowed by LLM provider. [ai-security.ai-guard.policies:criteria-types] Creating a match rule through the API requires the detection policy and any LLM applications it names to exist already; otherwise the request is rejected with a message naming the missing item. [ai-security.ai-guard.policies:match-rule-references] A policy configuration applies to traffic only through an enabled policy control that matches it first; a policy with no such rule, a disabled rule, or a rule below an earlier match is not applied to that traffic. [ai-security.ai-guard.policies:no-match-unapplied] What applies when no rule matches is open [gap:ai-security.ai-guard.policies:no-match-default].

**Application policy control.** On the AI Guard for Apps page, a policy configuration is attached to an application by adding policy control, on the AI Applications tab in Proxy mode (for DAS mode the page says to skip to the next step); the rule takes a rule name, a policy configuration, a rule order and a rule status (enabled or disabled), and at least one match criterion defined among LLM Provider & Models (Proxy Only), Applications & Credentials, Application Groups, Custom Request Headers and their values, and source IPv4 addresses; the new policy control appears at the Rule Order number entered. [ai-security.ai-guard.policies:app-control-criteria]

**Prompt allowlist.** The prompt allowlist holds prompts to allow that may otherwise be blocked by an existing AI Guard policy; it is available only in Proxy mode, and prompts sent to the allowlist endpoint are fully encrypted so the prompt content remains protected end to end. [ai-security.ai-guard.policies:allowlist] Using the allowlist requires Store Prompts/Responses and Enable Data Sharing for AI Training enabled under Security Settings and the System Administrator role with all-write access; individual actions are governed by the Default Access permission: View to see allowlisted prompts, Create to add to the allowlist and Delete to delete a prompt from it. [ai-security.ai-guard.policies:allowlist-prereqs] A blocked prompt is added to the allowlist from the Transaction Details window: under Prompt Details, Reveal Prompt, then Add to Allowlist if the blocked prompt is the one to add; added prompts are found on the Prompt Allowlist page, where a prompt is deleted with Delete in the Action column. [ai-security.ai-guard.policies:allowlist-add] Whether responses can be allowlisted is disputed [divergence:ai-security.ai-guard.policies:allowlist-scope]. The Competition runbook says allowlisting is not supported at the Competition-detector level, and the Topic/Off Topic runbook says it is not supported at the detector level; both point to policy-level exceptions (exclude a user group, restrict to certain apps), and the Competition runbook adds a sentence-level allow rule if you have those. [ai-security.ai-guard.policies:no-detector-allowlist]

**Enabling and disabling.** Enabling or disabling a detection policy through the API turns every match rule that references it on or off, and the response lists those rules with their new state; disabling does not delete the policy. [ai-security.ai-guard.policies:enable-disable-match-rules]

**Applications.** AI applications such as chatbots are added while configuring AI Guard so a policy can be applied to them; they can be grouped into application groups; in DAS/API mode an application carries API keys, and in Proxy mode an identity broker. [ai-security.ai-guard.policies:ai-applications]

**Testing.** Policy Testing, available once an LLM provider, its credentials and a policy exist, sends a prompt through a chosen provider credential, policy and LLM model and shows what was allowed or blocked together with the prompt and response without guardrails. [ai-security.ai-guard.policies:testing]

**Configuration actions.** A policy configuration's View Details button under Action opens the View Configuration Details window, which shows, among other things, its description, controls, prompt detectors and response detectors. [ai-security.ai-guard.policies:config-view-details] A policy configuration can be edited or copied from the Action column, each opening an Edit Policy or Copy Configuration page; deleting one requires typing Delete into a text field and then clicking Delete. [ai-security.ai-guard.policies:config-edit-copy-delete] What deleting a configuration that a policy control references does in the portal is open [gap:ai-security.ai-guard.policies:config-delete-referenced]; the API's answer is in [Deleting a policy, provider, provider credential, application or application credential that an active configuration references is blocked with 409 while `deleteReferences` is false, the default; where supported, `deleteReferences=true` removes the references before the delete.](kb:ai-security.ai-guard.admin-api:delete-409).

**Quick start example.** The ChatGPT and Microsoft 365 Copilot quick starts' example policy configuration enables the Toxicity prompt detector and skips response detectors, then, if everything looks correct, clicks Submit Policy; the Review tab shows a summary of the policy configuration. [ai-security.ai-guard.policies:quickstart-example-policy]

What to check:
1. The rules above the expected one in policy control order, since evaluation stops at the first match.
2. That the rule is enabled and its criteria match the traffic: provider and model, account type, users or groups for user rules; applications, credentials, application groups, source IPs or custom headers for application rules.
3. The detector's Action (Block, Detect or Allow) and threshold in the policy; Detect only flags. Which direction counts as strict for the threshold is disputed, so state the direction by what triggers rather than by strict.
4. Run the policy through Policy Testing with the same provider credential and model before relying on it.

Sources disagree (name both sides):
- Which direction of the detector threshold is strict: the policy page says a lower threshold is more strict, the PII runbook calls the high end stricter. [divergence:ai-security.ai-guard.policies:strict-direction]
  - zscaler-help: The policy configuration page says the lower the threshold setting, the more strict AI Guard is with activating the policy (allowing, blocking or detecting the prompt).
  - zscaler-help: The PII runbook labels the 0.7 to 1.00 range Stricter, where only high-confidence matches trigger, and describes turning the threshold up as meaning only very obvious mentions trigger.
  Impact: On the mechanics the pages agree that a lower threshold makes more prompts trigger; they differ on whether strict means more enforcement (lower) or tighter matching (higher), so describe the direction by what triggers rather than by strict.
- Whether the allowlist covers responses as well as prompts: the allowlist page names only prompts, the detection summary says a blocked prompt or response can be added. [divergence:ai-security.ai-guard.policies:allowlist-scope]
  - zscaler-help: The allowlist page describes it as an allowlist of prompts that an AI Guard policy may otherwise block, and its add and delete steps name only prompts.
  - zscaler-help: The detection summary page says that with the proper permissions, revealing a blocked prompt or response offers Add to Allowlist for the prompt or response.
  Impact: Whether a blocked response can be allowlisted is unsettled; answer for prompts and say the detection summary page also mentions responses.
