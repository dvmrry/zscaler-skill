# The AI Guard policy fragment for Azure API Management (AI Gateway): which calls it scans, what it extracts, its fail-open switch, and what the example policy ships with (ai-security.ai-guard.integrations.azure-apim)
Also called: ai guard azure; ai guard azure apim; ai guard azure ai gateway; zscaler-aiguard-scan; AIGUARD-API-KEY named value; FailOpen apim; currentPolicy

The Azure integration is one APIM policy fragment that an API includes twice, inbound to scan the prompt and outbound to scan the response. The fragment `zscaler-aiguard-scan` reads the named values `AIGUARD-API-KEY` (secret) and `AIGUARD-CLOUD` and is included in the inbound section with `ScanType` `prompt` and in the outbound section with `ScanType` `response`. [ai-security.ai-guard.integrations.azure-apim:fragment] The fragment acts only on POST requests whose path ends in `/completions`, `/chat/completions` or `/responses`; anything else passes untouched. [ai-security.ai-guard.integrations.azure-apim:paths]

**What it extracts.** The prompt scanned is the request's `input` field as a string, else the `content` of the last message whatever its role, as a string; no other message is scanned (so a system message is scanned only when it is the last one), and an extraction error yields empty content. [ai-security.ai-guard.integrations.azure-apim:prompt-extraction] The outbound scan runs only when the backend answered HTTP 200 and scans the text of the last content item of the last `output` entry or the `message.content` of the last choice, using an empty string when that value is missing. [ai-security.ai-guard.integrations.azure-apim:response-extraction] A reply carrying only tool calls has no text at either path, so its outbound scan sends empty content. [ai-security.ai-guard.integrations.azure-apim:tool-call-reply-empty] A streamed (SSE) response body does not parse as a JSON object, so the outbound extraction falls into its catch branch and the fragment sends an empty `content` for the response scan. [ai-security.ai-guard.integrations.azure-apim:sse-empty] What AI Guard returns for empty content is open [gap:ai-security.ai-guard.integrations.azure-apim:empty-content].

**The call.** Every scan, prompt or response, POSTs to `https://api.{cloud}.zseclipse.net/v1/detection/resolve-and-execute-policy` with the key as a Bearer token, a 10-second timeout and errors ignored; a `currentPolicy` value is added to the body as `policyId` (int.Parse) but does not change the endpoint. [ai-security.ai-guard.integrations.azure-apim:endpoint] Issue #10 on the integrations repository reported that the per-cloud AI Guard endpoint the Azure README and policy fragment use no longer works; it was closed as completed on 2026-09-02 with a reply from a member of the repository's organization, signed Zscaler DevRel, to upgrade to v0.2.0, and the policy fragment still builds the host from `{cloud}`. [ai-security.ai-guard.integrations.azure-apim:cloud-host-reported-dead-issue-10] Whether the per-cloud host still answers is open [gap:ai-security.ai-guard.integrations.azure-apim:cloud-host-still-accepted]. The scan body is `content` and `direction` (IN for prompts, OUT for responses), plus `policyId` when `currentPolicy` is set; no transaction ID is sent. [ai-security.ai-guard.integrations.azure-apim:scan-body] Setting `currentPolicy` most likely has no effect: the fragment sends the ID only to resolve-and-execute-policy, which the Apigee example reports ignores `policyId` and applies the key's own policy. [ai-security.ai-guard.integrations.azure-apim:current-policy-ignored] The README says currentPolicy selects a policy [divergence:ai-security.ai-guard.integrations.azure-apim:current-policy]. The fragment builds a `requestMetadata` object (session ID from `x-session-id`, app name, model, client IP and `x-user-id`) but never sends or logs it, so AI Guard sees no session or user from this integration. [ai-security.ai-guard.integrations.azure-apim:session-not-sent] The README promises session grouping [divergence:ai-security.ai-guard.integrations.azure-apim:session-tracking].

**Verdicts and failures.** On an HTTP 200 scan reply the fragment lets ALLOW and DETECT through, returns 403 for BLOCK or any other action, and treats an empty action as no verdict, which returns 403 unless `FailOpen` is true. [ai-security.ai-guard.integrations.azure-apim:verdict] When the scan call fails (errors are ignored) or returns a non-200, the fragment answers 503 with the body "ZSCALER AI GUARD: Security scanner unavailable. Request blocked for safety." unless `FailOpen` is true, in which case it writes an error trace and lets the request or response through; `FailOpen` defaults to false. [ai-security.ai-guard.integrations.azure-apim:scanner-unavailable] The shipped example policy and the README's quick start set `FailOpen` to true on the inbound (prompt) scan and false on the outbound one. [ai-security.ai-guard.integrations.azure-apim:example-fail-open]

**Block details.** The block body's `details` is built by reading `detectorResponses` as an array of objects with `detectorName` and `action` and listing each detector whose action is BLOCK, with its description from the `aiguardDescriptions` variable when that is set, otherwise from the fragment's own `scanDescriptions`, and "Blocked by security policy." when the chosen table has no entry for that detector. [ai-security.ai-guard.integrations.azure-apim:detector-details] Since AI Guard returns `detectorResponses` as a map keyed by detector name, the array cast yields null and a block's `details` is always empty, as in the README's own sample block. [ai-security.ai-guard.integrations.azure-apim:details-empty] The README's response sample disagrees with the SDK on the detector shape [divergence:ai-security.ai-guard.integrations.azure-apim:detector-shape].

What to check:
1. Whether the inbound policy sets FailOpen to true, as the shipped example and the README quick start do; then an unreachable or erroring AI Guard lets prompts through.
2. That the API's operations end in /completions, /chat/completions or /responses; other operations are not scanned.
3. Do not rely on currentPolicy to select a policy; the fragment always calls resolve-and-execute-policy.
4. Whether clients stream or receive tool-call-only replies; those responses are scanned as empty content.

Sources disagree (name both sides):
- Whether a policy ID sent to resolve-and-execute-policy selects that policy. [divergence:ai-security.ai-guard.integrations.azure-apim:current-policy]
  - zguard-integrations: The Azure README says including policyId in the resolve-and-execute request targets a specific policy, and lists separate prompt and response policies as a feature.
  - zguard-integrations: The Apigee example's architecture note says resolve-and-execute-policy ignores policyId outright and resolves the key's own policy.
  Impact: If the Apigee note is right, currentPolicy is silently ignored and both legs use the key's bound policy; the SDK's resolve_and_execute_policy takes no policy ID at all.
- Whether the Azure fragment groups a conversation's scans by x-session-id. [divergence:ai-security.ai-guard.integrations.azure-apim:session-tracking]
  - zguard-integrations: The README lists session tracking via the x-session-id header as a feature and shows multi-turn requests carrying it.
  - zguard-integrations: The fragment reads x-session-id into requestMetadata, which nothing sends; the scan body is content, direction and an optional policyId.
  Impact: Scans from one conversation are not linked in the AI Guard console by this integration.
- The shape of detectorResponses in a detection reply. [divergence:ai-security.ai-guard.integrations.azure-apim:detector-shape]
  - zguard-integrations: The Azure README's sample response shows detectorResponses as an array of objects with detectorName and action.
  - sdk-python: The Python SDK's response model reads detectorResponses as a dictionary keyed by detector name.
  Impact: Code written to the Azure README's sample, like the fragment itself, finds no detectors; the SDK's map shape is the one the other examples and the Kong README's sample use.
