# Calling AI Guard at runtime: the proxy endpoint, the DAS detection API, its host, direction and policy ID, and throttling in the Python SDK (ai-security.ai-guard.runtime-api)
Also called: execute-policy; resolve-and-execute-policy; ai guard detection api; ai guard das api; /v1/detection/execute-policy; api.zseclipse.net; proxy.zseclipse.net; LegacyAIGuardClient; policy_detection; ai guard direction IN OUT; ai guard policyId; ai guard throttling; retryAfterMillis; X-ApiKey; AIGUARD_CLOUD; ai guard api divergences

Applications reach AI Guard at runtime in one of two ways: as a proxy in front of the LLM provider, or by calling its detection API around their own LLM calls. These calls are not part of the OneAPI configuration API.

**Proxy mode.** In proxy mode the application sends requests to `https://proxy.zseclipse.net` on a proxy path per provider; the proxy page lists Anthropic (`/v1/messages`), AWS Bedrock Agent, AWS Bedrock Anthropic, AWS Bedrock Invoke, Azure Foundry (`/openai/v1/chat/completions`), Google Gemini, Google Vertex and OpenAI (`/v1/chat/completions`). [ai-security.ai-guard.runtime-api:proxy-paths] A proxy-mode request authenticates to AI Guard with the AI Guard application key in an `X-ApiKey` header; the Anthropic example also sends an `anthropic-version` header giving the Anthropic version in use, such as 2023-06-01. [ai-security.ai-guard.runtime-api:proxy-key-header] The mode itself is described in [In Proxy mode the application sends its model requests to AI Guard at `https://proxy.zseclipse.net` instead of to each provider, and AI Guard proxies them to the upstream LLM provider, sitting inline for routing, inspection and enforcement.](kb:ai-security.ai-guard:proxy-single-destination).

**DAS endpoints.** DAS mode has two endpoints: `execute-policy` checks content against one specific policy ID, for deterministic use of a known policy; `resolve-and-execute-policy` sends no policy ID and lets AI Guard resolve and apply the matching policy. [ai-security.ai-guard.runtime-api:two-endpoints] Resolve-and-execute needs DAS/API policies to exist in AI Guard; AI Guard evaluates them and determines the matching one; several DAS/API policies may apply, and the application should not hard-code a single policy ID. [ai-security.ai-guard.runtime-api:resolve-requirements] The DAS page calls both endpoints on the host `https://api.zseclipse.net`, authenticating with the AI Guard API key as a Bearer token and sending `direction` and `content` in the body. [ai-security.ai-guard.runtime-api:help-host] The application should inspect both sides: the prompt before it is sent to the model and the response before it is shown to the user; skipping the response call gives up output enforcement. [ai-security.ai-guard.runtime-api:both-directions] The DAS page advises a short request timeout for the inspection call, explicit handling of AI Guard failures, error handling for failed inspections and return-message wording for blocked inspections in the application, and logging blocked events without exposing sensitive content broadly. [ai-security.ai-guard.runtime-api:failure-handling] In DAS mode AI Guard only recommends: the quick start says it cannot perform enforcement actions and that the application must check the response for `action: ALLOW` or `action: BLOCK`, and the architecture article likewise has the application enforce the decision before calling the LLM or returning the response. [ai-security.ai-guard.runtime-api:das-recommends-only] From the AI Guard for Apps release of September 11, 2026, a DAS resolve-and-execute call can include optional `user`, `clientName` and `appName` fields, which also appear in the dashboard's Transaction Details window. [ai-security.ai-guard.runtime-api:resolve-optional-fields]

**The Python SDK.** In the Python SDK the detection endpoints are not exposed through OneAPI: they are called with `LegacyAIGuardClient` and an AI Guard API key, while every other AI Guard resource is OneAPI-only through `ZscalerClient`. [ai-security.ai-guard.runtime-api:sdk-legacy-client] The SDK's legacy client sends detection calls to `https://api.<cloud>.zseclipse.net`, taking the cloud from the config's `cloud`, else `AIGUARD_CLOUD`, else `us1`; an `override_url` or `AIGUARD_OVERRIDE_URL` replaces the whole base URL. [ai-security.ai-guard.runtime-api:sdk-host] The legacy helper sets an Authorization header carrying the API key as a Bearer token on each detection request; detection calls are dispatched through it since release 1.9.44, which fixed them falling through to the standard OneAPI session without the AI Guard API key. [ai-security.ai-guard.runtime-api:sdk-bearer] The SDK documents `direction` as `IN` or `OUT` for both detection methods, and each method's minimal-payload example passes `direction="IN"`. [ai-security.ai-guard.runtime-api:sdk-direction-doc] `execute_policy` takes `policy_id` as optional and puts `policyId` in the body only when it is given; `transactionId` is likewise added only when given. [ai-security.ai-guard.runtime-api:sdk-policy-id-optional] `resolve_and_execute_policy` accepts an optional `user` since release 1.10.0, recorded on the detection event so the user appears on the dashboard, and optional extra `headers` since release 1.10.1, which are merged into the request and let a caller send the tenant's configured custom request headers, including the one AI Guard reads a conversation ID from to correlate multi-turn interactions. [ai-security.ai-guard.runtime-api:resolve-user-headers] The Python SDK's `resolve_and_execute_policy` takes `content`, `direction`, `transaction_id`, `user` and `headers`; it has no `clientName` or `appName` argument. [ai-security.ai-guard.runtime-api:sdk-no-client-app-name] The deprecated `client.zguard` alias is in [In the Python SDK, `client.zguard` is a deprecated alias for the `aiguard` property.](kb:shared.terminology.product-names:zguard-alias).

**Responses.** The SDK's response models read `transactionId`, `statusCode`, `errorMsg`, `detectorErrorCount`, `action`, `severity`, `direction`, a map of per-detector `detectorResponses` (each with `triggered`, `action`, `severity`, `latency` and an optional `contentHash`), and a list of `throttlingDetails` with `rlcId`, `metric` and `retryAfterMillis`. [ai-security.ai-guard.runtime-api:response-fields] The resolve-and-execute response model also reads `policyId`, `policyName` and `policyVersion`, naming the policy AI Guard resolved. [ai-security.ai-guard.runtime-api:resolve-policy-fields] The DAS/API quick start's sample allowed and blocked responses each give the toxicity detector's entry a `latency` of 43 and a `deviceType` of `cuda`, and the Python SDK's `DetectorResponse` reads `deviceType`; no captured AI Guard Help page defines the field or its values. [ai-security.ai-guard.runtime-api:sample-detector-device-type]

**Throttling.** The legacy helper's throttling handler treats a `metric` of `rq` as a request-count limit and `cs` as a content-size limit and sleeps for the longest retry-after value when `auto_retry_on_rate_limit` is on (the default); it also records, per metric, when that limit resets, and each later request first waits until both recorded resets have passed. [ai-security.ai-guard.runtime-api:throttle-metrics] The detection methods pass a response's throttling details to `_handle_throttling_details` on the request executor's `zguard_legacy_client` only if the request executor has an attribute of that name; the request executor stores the legacy helper as `aiguard_legacy_client`. [ai-security.ai-guard.runtime-api:throttle-hook-name] At v1.11.3-1-g4f8f54df of the Python SDK, a throttled detection response never reaches the helper's handler: the SDK neither sleeps on `retryAfterMillis` nor delays later requests, so a caller has to read `throttlingDetails` and wait itself. [ai-security.ai-guard.runtime-api:throttle-hook-skipped] A test of it is open [gap:ai-security.ai-guard.runtime-api:throttle-handling].

**Other entry points.** The Anthropic inference-hook endpoint is in [AI Guard can evaluate prompts through Anthropic Claude's inference hooks and answer allow or deny: in Claude the hook endpoint is `https://api.zseclipse.net/v1/webhook/execute` with Enforce verdicts on and a 1000 ms prompt verdict timeout, and Claude's signing secret is added in AI Guard with the organization's Anthropic UUID; a policy and policy control must then target the webhook traffic.](kb:ai-security.ai-guard.tenant-settings:anthropic-webhook), and Zscaler's integration examples in [Zscaler's AI Guard integration examples (zguard-ai-integrations): the catalog, the promised fail-closed posture against what each example does, and where each intercepts](kb:ai-security.ai-guard.integrations).

**What the integration examples say.** Zscaler's integration examples build the DAS host from the cloud name as `https://api.{cloud}.zseclipse.net` (the repository's agent notes and the Cursor, n8n and Azure AI Gateway READMEs); the CI scanner treats a blank cloud as `us1` because an empty one yields `api..zseclipse.net`. [ai-security.ai-guard.runtime-api:examples-regional-host] That host form matches the SDK's regional host, not the global host the Help DAS page uses. [ai-security.ai-guard.runtime-api:examples-match-sdk] The examples do not show whether the global host also works, so host selection stays open [gap:ai-security.ai-guard.runtime-api:host-selection]. They also state, at rank 4, that a policy ID the key cannot use comes back as "Policy not found" in an HTTP 200 with no action ([The example documents say a policy ID the key cannot use comes back as "Policy not found" inside an HTTP 200 with no `action` field, so reading a verdict-less 200 as permission silently disables scanning.](kb:ai-security.ai-guard.integrations:soft-failure)), that a non-UUID transactionId gets HTTP 500 ([The example documents say the API answers HTTP 500 to a `transactionId` that is not a standard 36-character UUID; the 0.2.0 fix hashes such values with `uuid5` or omits them.](kb:ai-security.ai-guard.integrations:transaction-id-uuid)), and that resolve-and-execute ignores a policyId in the body ([The example's architecture note says resolve-and-execute-policy ignores a `policyId` in the body without an error and applies the key's own policy, which is why a pinned ID is routed to execute-policy instead.](kb:ai-security.ai-guard.integrations.google-apigee-proxy:resolve-ignores-policy-id)); their statement that the API takes only content, direction, transactionId and policyId conflicts with the SDK's `user` field and with Help's September 11, 2026 release ([ai-security.ai-guard.runtime-api:resolve-optional-fields]) ([ai-security.ai-guard.integrations.google-apigee-sharedflow:api-fields](kb:ai-security.ai-guard.integrations.google-apigee-sharedflow:api-fields)). The native LiteLLM guardrail defaults to execute-policy with `policy_id` optional ([The example native configuration notes that `api_base` defaults to `https://api.us1.zseclipse.net/v1/detection/execute-policy` and marks `policy_id` optional, and the README's comparison lists the native plugin's policy selection as an explicit policy ID.](kb:ai-security.ai-guard.integrations.litellm:native-endpoint)).

What to check:
1. That the application calls AI Guard on both the prompt and the response, and treats a failed inspection explicitly rather than passing content through.
2. Which host the client uses: Help's global api.zseclipse.net or the SDK's api.<cloud>.zseclipse.net (cloud us1 unless set); pin it with the override when they differ.
3. That direction is IN for prompts and OUT for responses when using the SDK, and that execute-policy calls carry a policy ID.
4. That the caller reads throttlingDetails and waits retryAfterMillis itself; at the pin the SDK's helper does not act on it.

Sources disagree (name both sides):
- Which host serves the DAS detection endpoints. [divergence:ai-security.ai-guard.runtime-api:das-host]
  - zscaler-help: Help calls both endpoints on the global host api.zseclipse.net.
  - sdk-python: The Python SDK builds a per-cloud host, api.<cloud>.zseclipse.net, with cloud us1 unless configured.
  Impact: A client following one source may call a host the other source does not use; no source says whether both hosts accept the calls or which is preferred. The SDK's override URL can pin the Help host.
- Which values the direction field takes; Help's own pages differ. [divergence:ai-security.ai-guard.runtime-api:direction-literals]
  - sdk-python: The Python SDK documents IN or OUT.
  - zscaler-help: The DAS Help page's examples pass "request" and "response", and its prose speaks of the outbound prompt and the inbound response.
  - zscaler-help: The DAS/API quick start's example passes "IN" and says IN refers to the prompt and OUT to the response.
  Impact: Help is on both sides: the DAS/API quick start agrees with the SDK (IN for the prompt, OUT for the response), while the test page passes "request" and "response" and calls the prompt outbound and the response inbound, the opposite of reading IN as the prompt. Whether the API accepts both sets is unknown.
- Whether execute-policy requires a policy ID. [divergence:ai-security.ai-guard.runtime-api:policy-id-required]
  - zscaler-help: The DAS Help page says policyId is required for execute-policy.
  - sdk-python: The Python SDK makes policy_id optional and omits policyId when it is not given.
  Impact: An SDK call to execute_policy without a policy ID sends a request Help calls invalid; resolve_and_execute_policy is the documented call when no ID is intended.
