# Zscaler's AWS AI Guard examples (Lambda decorator, boto3 Bedrock hook, AgentCore guard, Strands hooks): seats, the shared scan client, verdict and failure handling (ai-security.ai-guard.integrations.aws)
Also called: ai guard aws; ai guard aws integrations; aiguard_agentcore; aiguard_boto3_hook; aiguard_decorator; aiguard_strands; AIGUARD_TIMEOUT; ai guard on_error allow; ai guard on_unscannable; ai guard strict_verdict

The AWS folder of Zscaler's integration examples holds four single-file Python integrations that call the DAS detection API directly, without the Zscaler SDK. This subject covers what they share; each has its own subject. The AWS folder holds four integrations at different seats: a decorator on the Lambda handler and an interceptor on the boto3 Bedrock client, both scanning prompt and response, and a guard called at the legs of an AgentCore agent loop and a Strands Agents HookProvider, both scanning prompt, tool input, tool output and response. [ai-security.ai-guard.integrations.aws:seats] Each AWS integration is one Python file using only the standard library plus the host it plugs into (botocore for the Bedrock hook, the Strands SDK for the hook provider); none uses the Zscaler Python SDK. [ai-security.ai-guard.integrations.aws:stdlib-only]

**Legs and directions.** Each leg is one detection call: the prompt and tool input legs are sent with direction `IN`, the tool output and response legs with `OUT`; the Lambda decorator and the boto3 hook have only the prompt and response legs. [ai-security.ai-guard.integrations.aws:leg-directions] Per integration: [The AI Guard decorator for AWS Lambda handlers: prompt and response scanning at the function boundary, default extractors, and block shapes](kb:ai-security.ai-guard.integrations.aws-lambda-decorator), [The AI Guard boto3 hook for Amazon Bedrock: before-call and after-call scanning, what the content walkers read, block styles, and what is not scanned](kb:ai-security.ai-guard.integrations.aws-bedrock-sdk-hooks), [The AI Guard guard for Amazon Bedrock AgentCore agents: the four legs you call, the tool wrapper, and what each leg sends](kb:ai-security.ai-guard.integrations.aws-bedrock-agentcore), [The AI Guard HookProvider for Strands Agents: which hook events it uses, how each leg can block, and what stays out of reach](kb:ai-security.ai-guard.integrations.aws-strands-agents).

**The call.** All four modules POST to `https://api.<cloud>.zseclipse.net`, taking the cloud from `AIGUARD_CLOUD` (default `us1`) unless `AIGUARD_OVERRIDE_URL` gives a full base URL, and call `/v1/detection/execute-policy` when a policy ID is configured, otherwise `/v1/detection/resolve-and-execute-policy`. [ai-security.ai-guard.integrations.aws:endpoint-selection] The scan request carries the key as a Bearer token; the client refuses an endpoint that is not `https://` (reported as a scan error) and refuses HTTP redirects, so the key is never re-sent to another host. [ai-security.ai-guard.integrations.aws:bearer-https] The scan response is read against one wall-clock deadline rather than a per-read socket timeout, and a body over 10 MB is refused; either outcome is a scan error. [ai-security.ai-guard.integrations.aws:read-bounds] Every module's scan body is `content` and `direction`, plus `transactionId` when it has one and `policyId` when a policy ID is configured; a leg's text is flattened into the single `content` string. [ai-security.ai-guard.integrations.aws:payload-fields] An ID that does not parse as a UUID is hashed into a UUID with uuid5 before it is sent as `transactionId` (one that parses is sent in canonical form); the modules' notes say AI Guard rejects a non-UUID `transactionId` with HTTP 500 and that callers pass request IDs and session strings (the Lambda decorator, `aws_request_id`). [ai-security.ai-guard.integrations.aws:transaction-id]

**Policy ID.** Each module takes the policy ID from the `policy_id` argument it is given in code, else `AIGUARD_POLICY_ID`, strips surrounding quotes, and converts it with int(); an empty value or one int() rejects becomes None, the no-policy-ID path. [ai-security.ai-guard.integrations.aws:policy-id-parsing] A non-numeric AIGUARD_POLICY_ID (a policy name, a UUID, a typo with letters) is dropped without a warning and the integration calls resolve-and-execute-policy, so the key's bound policy is applied instead of failing; only a numeric ID the key cannot use reaches execute-policy and fails closed on the verdict-less reply. [ai-security.ai-guard.integrations.aws:malformed-id-autoresolves]

**Verdicts and failures.** The verdict's `action` is upper-cased: BLOCK blocks, ALLOW and DETECT allow (DETECT is treated as monitor-only), a response with no action is a scan error that names the in-body `statusCode` and `errorMsg` when the body carries either, and any other action is an 'unknown scan action' error. [ai-security.ai-guard.integrations.aws:verdict-mapping] A missing `AIGUARD_API_KEY`, a network or HTTP error, a timeout, an oversized or non-JSON response, a verdict-less response and an unknown action are all scan errors, which block under the default `on_error="block"` and pass unscanned under `on_error="allow"`, the explicit opt-out every module accepts. [ai-security.ai-guard.integrations.aws:on-error] With `strict_verdict=True` (default False) an allow verdict that carries an `errorMsg` is treated as a scan error and follows `on_error`. [ai-security.ai-guard.integrations.aws:strict-verdict]

**Timeouts.** The AgentCore guard and the Strands provider default `timeout` to 10.0 seconds in their constructors; the boto3 hook and the Lambda decorator default it to `_default_timeout()`, which reads `AIGUARD_TIMEOUT` and falls back to 30. [ai-security.ai-guard.integrations.aws:timeout-defaults] In the AgentCore guard and the Strands provider `AIGUARD_TIMEOUT` has no effect: each module defines `_default_timeout()` but never calls it, so a scan is bounded by the constructor's 10 seconds unless `timeout=` is passed. [ai-security.ai-guard.integrations.aws:timeout-env-ignored] The documentation states other defaults [divergence:ai-security.ai-guard.integrations.aws:timeout-default].

**What does not reach AI Guard.** App name, end user, model and agent identifiers never reach AI Guard: the AgentCore guard and the Lambda decorator write them only to their local log line, and the boto3 hook and the Strands provider store them and use them nowhere. [ai-security.ai-guard.integrations.aws:identity-not-sent] A caller-supplied session ID never becomes the `transactionId`: AgentCore, Lambda and Strands send `transaction_id or session_id`, and the transaction ID is always set first (an explicit ID, the AgentCore or Lambda request ID, or a fresh uuid4), so the session only reaches the log line, if anywhere. [ai-security.ai-guard.integrations.aws:session-not-sent] The READMEs describe these fields as scan metadata [divergence:ai-security.ai-guard.integrations.aws:scan-metadata].

**Logging.** Each leg writes one JSON line on the `aiguard` logger, allows and other neutral outcomes at INFO and blocks and errors at WARNING. The AgentCore, Lambda and Strands lines carry the integration's own `transaction_id` and, as `scan_transaction_id`, the ID AI Guard assigned, which is the one to search in the console; the boto3 hook writes the API's ID over `transaction_id` when the verdict has one. Without a configured handler Python prints only WARNING and above, so allows are dropped. [ai-security.ai-guard.integrations.aws:logging]

What to check:
1. Whether AIGUARD_POLICY_ID is set and numeric: a non-numeric value is dropped silently and the key's own policy is applied, while a numeric ID the key cannot use fails closed.
2. Whether on_error is "allow" anywhere the integration is constructed; that turns a missing key, an unreachable API or a verdict-less response into a pass.
3. The per-scan timeout the integration really uses (10 s for AgentCore and Strands regardless of AIGUARD_TIMEOUT, AIGUARD_TIMEOUT or 30 s for the boto3 hook and the Lambda decorator) before sizing a Lambda or agent time budget.
4. To find a scan in the AI Guard console, use the scan_transaction_id the API returned, not the app name, session or user, which never reach AI Guard.

Sources disagree (name both sides):
- What per-scan timeout the AWS integrations use by default. [divergence:ai-security.ai-guard.integrations.aws:timeout-default]
  - zguard-integrations: The AWS README and each module's docstring say AIGUARD_TIMEOUT sets the per-scan timeout and defaults to 30 seconds.
  - zguard-integrations: The AgentCore guard's constructor defaults timeout to 10.0 and stores it; its AIGUARD_TIMEOUT reader is never called.
  - zguard-integrations: The boto3 hook's README gives a 10-second default, while its code falls back to AIGUARD_TIMEOUT or 30.
  - zguard-integrations: The Lambda decorator's README configuration block shows timeout=10.0, while its code defaults to AIGUARD_TIMEOUT or 30 (as its own Limitations section says).
  Impact: A time budget sized from the README is wrong for at least one integration: AgentCore and Strands ignore AIGUARD_TIMEOUT and wait 10 s per scan, the boto3 hook and the Lambda decorator wait 30 s unless AIGUARD_TIMEOUT or timeout= is set. The code paths are timeout-defaults and timeout-env-ignored.
- Whether the AWS integrations send app, user, model, agent and session identifiers to AI Guard. [divergence:ai-security.ai-guard.integrations.aws:scan-metadata]
  - zguard-integrations: The Lambda decorator's README says every parameter maps to a field of the scan API's request and that a session_id_from callable makes a session's scans correlate in the AI Guard console.
  - zguard-integrations: The Strands README maps app_name, session_id, app_user, ai_model and agent_arn onto metadata and session fields.
  - zguard-integrations: The Lambda decorator's code says the detection API carries no metadata field, only content, direction, transactionId and policyId, so identity stays on the log line.
  Impact: An operator expecting app, user or session attribution in the AI Guard console for these integrations gets none; only the transaction ID correlates a scan with the integration's log line. What the code sends is in payload-fields, identity-not-sent and session-not-sent.
