# Jenkins policy validation for AI Guard (Zscaler example): the declarative pipeline around the shared scan_policy.py (ai-security.ai-guard.integrations.jenkins)
Also called: aiguard jenkins; jenkinsfile aiguard; aiguard-api-key credential; FORCE_RUN

Zscaler's Jenkins example runs the same AI Guard policy validation as the GitHub Actions example, from a Declarative Pipeline.

**When it scans.** The Jenkins example's Declarative Pipeline polls SCM every five minutes and runs the AI Guard scan stage only when `FORCE_RUN` is set or a change touches `config/model-config.yaml`, `config/test-prompts.yaml`, `scripts/scan_policy.py` or the `Jenkinsfile`; the key comes from the `aiguard-api-key` secret-text credential and the cloud and policy ID from build parameters (cloud default `us1`). [ai-security.ai-guard.integrations.jenkins:pipeline] The optional Vertex AI deploy and endpoint-test stages run only when `SCAN_NEEDED` is true (the condition the scan stage runs on), `SKIP_DEPLOY` is off and the branch is main. [ai-security.ai-guard.integrations.jenkins:deploy-stages]

**What the scan checks.** The Jenkins `scan_policy.py` is the GitHub Actions scanner with only comment changes, so test-case format, pass and fail rules and configuration are those of [GitHub Actions policy validation for AI Guard (Zscaler example): a CI gate that tests a policy with sample prompts, not runtime interception](kb:ai-security.ai-guard.integrations.github-actions). [ai-security.ai-guard.integrations.jenkins:same-scanner] The gate's weaknesses are in [Because required cases accept `DETECT`, a policy whose detectors only monitor passes the gate, and because benign cases are optional, a policy that blocks everything passes it too: the shipped suite checks that detections happen, not that content is blocked.](kb:ai-security.ai-guard.integrations.github-actions:detect-passes-gate).
