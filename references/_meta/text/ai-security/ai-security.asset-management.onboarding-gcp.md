# How AI Asset Management onboards GCP organizations: prerequisites, templates, service account, network, IAM roles and errors (ai-security.asset-management.onboarding-gcp)
Also called: AI Security GCP onboarding; GCP service account private key AI Security; LOCATION_POLICY_VIOLATED

GCP organization onboarding needs Super Admin access to the Google Admin console, a GCP Organization Administrator role and an owner role, Terraform CLI v1.7.5 or later to run Terraform on a Windows system, and a GCP project with the required roles linked to a billing account to deploy the orchestrator template. [ai-security.asset-management.onboarding-gcp:prereq-access] By default the Disable service account key creation policy prevents creating a service account key, so it must be overridden for the project, and its status must read Not enforced. [ai-security.asset-management.onboarding-gcp:key-policy] The AWS and Azure counterparts are in [How AI Asset Management onboards AWS accounts and organizations: prerequisites, templates, CloudTrail, network and IAM roles](kb:ai-security.asset-management.onboarding-aws) and [How is a Microsoft Azure tenant, management group or subscription onboarded to AI Security: roles, templates, network and error fixes?](kb:ai-security.asset-management.onboarding-azure), and the product overview is in [AI Asset Management in the AI Security Admin Portal: what it inventories, signing in, first-time configuration order, table behavior](kb:ai-security.asset-management).

**APIs, scopes and the custom role.** The required GCP APIs are scoped by project type: for example admin.googleapis.com and cloudasset.googleapis.com for Tree Discovery and Target projects; networkmanagement.googleapis.com (required for BYON) for the Orchestrator; aiplatform.googleapis.com for the Target project only. [ai-security.asset-management.onboarding-gcp:api-scope] compute.googleapis.com applies to Orchestrator and Target projects, needs the project linked to billing, and must be enabled on the target project before notebooks.googleapis.com (Vertex AI resources) can be enabled; serviceusage.googleapis.com and iam.googleapis.com apply to Tree Discovery, Orchestrator and Target. [ai-security.asset-management.onboarding-gcp:api-compute] Zscaler AI Security uses six OAuth scopes for GCP API authentication: cloud-platform, userinfo.email, and read-only admin.directory user, group, group.member and domain. [ai-security.asset-management.onboarding-gcp:oauth-scopes] Creating the custom role in the Google Admin console is optional; if skipped, AI Security cannot gain read-only access to user, group and domain resource data. The role holds DOMAIN_MANAGEMENT, GROUPS_RETRIEVE and USERS_RETRIEVE privileges, read-only for domain, group and user data. [ai-security.asset-management.onboarding-gcp:custom-role] Terraform verifies that all the required APIs are enabled and, if any is missing, shows an error message prompting you to enable the APIs. [ai-security.asset-management.onboarding-gcp:terraform-api-check]

**Organization details and configuration.** GCP role and service account names may contain only alphabetic characters, numbers, hyphens and underscores; the Organization Name is validated against the Organization ID on the GCP console, and up to 30 notification emails can be added. [ai-security.asset-management.onboarding-gcp:org-details] GCP onboarding offers Zscaler or Custom network configuration, Custom is selected by default, and changing it resets existing configurations; Custom requires VPC and Subnet selflinks. [ai-security.asset-management.onboarding-gcp:network-config] GCP monitoring scope: selecting the main project group scans all its projects, Autodetection includes new projects added later, all projects in a management group share one business unit, and a default is assigned. [ai-security.asset-management.onboarding-gcp:monitoring-scope] GCP evidence storage is a Custom Bucket (existing bucket, selected by default) or a Zscaler Managed Bucket that AI Security creates in the orchestrator project to hold evidence snippets. [ai-security.asset-management.onboarding-gcp:evidence-storage]

**Templates.** The GCP onboarding template prompts for the regions to monitor and creates scanning resources only there, and terraform apply takes enable_test_connectivity=true or false to deploy with network analysis enabled or disabled; AI Security validates the deployment every hour. [ai-security.asset-management.onboarding-gcp:template-deploy] When running the GCP onboarding Terraform template, terraform plan and terraform apply prompt for regions as a list in the format ["region name1", "region name2", ...]; AI Security creates resources required for data scanning only in the specified regions. [ai-security.asset-management.onboarding-gcp:template-regions-prompt] GCP projects added to the monitoring scope cannot be removed; to stop monitoring a project it must be deleted from the AI Security organization. Managing scope needs the Administrator role or any role with the Configure Monitoring Scope permission. [ai-security.asset-management.onboarding-gcp:monitoring-scope-add-only]

**Changing the orchestrator.** When changing the GCP orchestrator project, the Log Bucket Name must be unique (otherwise AI Security shows an error); the bucket stores the activity logs of the target projects and is created while deploying the onboarding template. [ai-security.asset-management.onboarding-gcp:orchestrator-change-log-bucket] Before running the GCP template on a new orchestrator project, the template deployed on the existing orchestrator is purged with terraform destroy; AI Security validates the deployment every hour by checking created roles and granted permissions, and starts scanning the onboarded projects once the template is deployed. [ai-security.asset-management.onboarding-gcp:orchestrator-change-purge-validation]

**Service account and private key.** If the GCP service account is accidentally deleted, AI Security's access is impacted and all onboarded projects in the organization move to Needs Attention; updating the service account details restores access. [ai-security.asset-management.onboarding-gcp:service-account-deleted] Updating the GCP service account means pasting the JSON output into Generated JSON in the Update Service Account window, then running the GCP Onboarding template from the Roles and Templates tab; after deployment access is restored and projects return to Successfully Configured. It needs an Administrator role or any role with permission to add accounts. [ai-security.asset-management.onboarding-gcp:service-account-update-flow] The GCP service account private key is generated in JSON format when the tree discovery template is applied; it can be updated at any time if keys need updating or have expired, by uploading the downloaded JSON key, and AI Security validates it against the service account and shows an error if it is invalid or does not match. [ai-security.asset-management.onboarding-gcp:private-key] Updating the private key needs an Administrator role or any role with permission to add accounts, and a service account private key downloaded in JSON format from the Google Cloud Console. [ai-security.asset-management.onboarding-gcp:private-key-perm]

**Custom network.** The GCP network page's introduction says a custom network needs a Control Plane VPC created only in the primary region where the orchestrator runs and a Worker Plane VPC in all the regions where the resources exist, both in the orchestrator project, with non-overlapping CIDR ranges; its steps build the worker plane as one VPC with an added subnet per additional region and create Cloud NAT for the new subnet and region. [ai-security.asset-management.onboarding-gcp:network-vpc-topology] The worker plane firewall rule allow-db-outbound-rule allows outbound communication from the scanner to GCP Cloud SQL instances on ports 3306, 5432 and 1433. [ai-security.asset-management.onboarding-gcp:network-db-firewall] Private service access in the worker plane VPC is used for scanning GCP Cloud SQL instances; it allocates an IP range named private-service-access-ip-range with Automatic range and prefix length 16, and Google then adds peering from the worker plane VPC to servicenetworking. [ai-security.asset-management.onboarding-gcp:network-private-service-access] The peering status in the control plane VPC is Inactive after the peering is added there; after successful configuration of the peering the status is Active for both the control plane VPC and the worker plane VPC. [ai-security.asset-management.onboarding-gcp:network-peering-status] Cloud NAT is a region-specific and network-specific resource that must be created for each combination; a Control Plane NAT Gateway is created, and the steps are repeated for a Worker Plane Cloud NAT Gateway for each region where data stores are present. [ai-security.asset-management.onboarding-gcp:network-cloud-nat]

**IAM roles.** The GCP Discovery Service Account is used by AI Security to discover resources in the GCP projects and to instruct the Local Scanner Platform to perform scan-related instructions; its managed roles include Cloud Asset Viewer, Security Reviewer, Organization Policy Viewer and Folder Viewer. [ai-security.asset-management.onboarding-gcp:iam-discovery-service-account] The GCP Orchestrator Service Account is used by the orchestrator instance to perform scan and management operations; its logging.sinks.get, logging.sinks.list and logging.sinks.update permissions are scoped to the GCP Organisation to update the org log sink for buckets incremental scans. [ai-security.asset-management.onboarding-gcp:iam-orchestrator-log-sink] The GCP Scanner Service Account is used by the scanner instance to perform scan-related tasks and its permission table lists logging.logEntries.list and secretmanager.versions.access with scope Monitored Projects; the Target Role service account performs scan-related tasks on data stores. [ai-security.asset-management.onboarding-gcp:iam-scanner-and-target] Scanning GCP BigQuery projects needs, among others, bigquery.datasets.get, bigquery.jobs.create, bigquery.models.getData and bigquery.tables.getData on Monitored Projects. [ai-security.asset-management.onboarding-gcp:iam-bigquery]

**Configuration errors.** The GCP error 403 LOCATION_POLICY_VIOLATED (permission denied on locations/REGION) while creating a subnetwork is fixed by terraform destroy, changing the orchestrator in the Admin Portal, deploying the new GCP template and ensuring the region has the necessary permissions. [ai-security.asset-management.onboarding-gcp:err-location-policy] For the GCP error 400 'Only buckets in state ACTIVE can be deleted', the error table says to restore the bucket on the Logs Storage page and run terraform destroy; the error 'Buckets must be in an ACTIVE state to be modified' is resolved by restoring the log bucket, running terraform destroy and rerunning the template. [ai-security.asset-management.onboarding-gcp:err-logging-bucket] The error table gives two different fixes for the same bucket error [divergence:ai-security.asset-management.onboarding-gcp:active-bucket-delete-fix].The Terraform error that locked provider hashicorp/google 5.40.0 does not match constraint 6.0.0 is fixed with terraform init -upgrade, which updates the locked provider version to match the configured version. [ai-security.asset-management.onboarding-gcp:err-provider-lock] The managed group instances error that networks in new and old network interfaces must be the same is due to a mismatch between old and new network interfaces; the fix is to stop the VM, delete its template and the orchestrator instance group, then redeploy the template. [ai-security.asset-management.onboarding-gcp:err-network-mismatch] A GCP Service Networking error because a peering operation is in progress is fixed by rerunning the template; an instance template error (specified network resource does not exist) is fixed by verifying the network resource, updating the reference and deploying the new GCP template. [ai-security.asset-management.onboarding-gcp:err-misc] The local-exec provisioner error in the test-connectivity module (Connectivity test failed) is resolved by rerunning the template; the check passes only if the gcloud connectivity test reachabilityDetails.result is REACHABLE. [ai-security.asset-management.onboarding-gcp:err-connectivity]

What to check:
1. Whether the Disable service account key creation policy reads Not enforced for the project before creating the service account key.
2. That a GCP project added to the monitoring scope cannot be removed from it; stopping monitoring means deleting the project from the AI Security organization.
3. Whether the GCP service account was deleted when all onboarded projects show Needs Attention.

Sources disagree (name both sides):
- Two rows of the GCP configuration-issues error table carry the error 'Only buckets in state ACTIVE can be deleted' with different resolutions. [divergence:ai-security.asset-management.onboarding-gcp:active-bucket-delete-fix]
  - zscaler-help: Restore the bucket on the Logs Storage page, then run terraform destroy.
  - zscaler-help: For an attempt to delete a Logging Bucket Config not in the ACTIVE state, change the orchestrator in the Admin Portal and deploy the new GCP template.
  Impact: The page does not say which fix applies to which situation, so the resolution for this error cannot be chosen from the page alone.
