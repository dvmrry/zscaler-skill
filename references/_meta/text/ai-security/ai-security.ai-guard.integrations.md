# Zscaler's AI Guard integration examples (zguard-ai-integrations): the catalog, the promised fail-closed posture against what each example does, and where each intercepts (ai-security.ai-guard.integrations)
Also called: zguard-ai-integrations; ai guard integrations; ai guard fail closed; failClosedOnUnknown; ai guard bedrock agentcore; ai guard strands; ai guard lambda; ai guard codex hooks; ai guard claude code hooks; ai guard apigee; ai guard cloud run; ai guard windsurf; ai guard n8n; AIGUARD_POLICY_ID; ai guard cursor hooks; ai guard cline

Zscaler publishes example integrations that call AI Guard's detection API from developer tools, gateways, agent frameworks, workflow tools and CI pipelines. This page lists them, sets the posture their documents promise against what each example's code does, and compares where each one intercepts. Zscaler publishes these integrations as community examples and reference implementations, to be reviewed, adapted and validated before production use. [ai-security.ai-guard.integrations:examples-not-product]

**What the repository offers.** The root README lists as complete: Claude Code and OpenAI Codex CLI hooks, an Azure AI Gateway APIM policy fragment, Cursor, Cline and Windsurf hooks, GitHub Actions and Jenkins pipelines, a Google Apigee X proxy and SharedFlow, Google Cloud Run provisioning pipelines, AWS Bedrock, Lambda and Strands components, a Kong Lua plugin, LiteLLM, NeMo Guardrails, Portkey and TrueFoundry integrations, and an n8n node; LangChain callbacks are planned. The Anthropic directory adds an on-demand Claude Code skill. [ai-security.ai-guard.integrations:catalog] The root README's architecture section says AI Guard uses a DAS pattern in which each AI application integrates independently, with no proxy infrastructure required. [ai-security.ai-guard.integrations:das-pattern] How DAS differs from proxy mode is in [In DAS/API mode AI Guard is not inline: the application keeps calling the LLM directly and calls AI Guard before sending the prompt and again on the model's response before returning it.](kb:ai-security.ai-guard:das-not-inline).

**How they call AI Guard.** The Python examples call AI Guard through `zscaler-sdk-python`; the AWS components instead call the API with `urllib` and the standard library only, and the n8n node uses Node.js's native `https` module. [ai-security.ai-guard.integrations:client-kinds] Release 0.2.0 requires `zscaler-sdk-python>=1.9.44` for every Python integration, because earlier SDK releases never attached the Bearer token to AI Guard policy-detection calls and every scan failed with 401 Unauthorized. [ai-security.ai-guard.integrations:sdk-floor] Of the SDK-based gateway examples, Portkey requires zscaler-sdk-python>=1.9.44 and TrueFoundry >=1.10.0 (for user forwarding), while the LiteLLM callback image and the NeMo install line leave the SDK unpinned; the AWS and Apigee examples do not use the SDK. [ai-security.ai-guard.integrations:sdk-pins] The SDK fix behind that floor is [The legacy helper sets an Authorization header carrying the API key as a Bearer token on each detection request; detection calls are dispatched through it since release 1.9.44, which fixed them falling through to the standard OneAPI session without the AI Guard API key.](kb:ai-security.ai-guard.runtime-api:sdk-bearer). The examples call `resolve_and_execute_policy` when `AIGUARD_POLICY_ID` is unset, letting the API resolve the policy bound to the key, and switch to `execute_policy` against a configured ID; the documents recommend leaving it unset. [ai-security.ai-guard.integrations:policy-id-switch] Across the Python examples a non-numeric `AIGUARD_POLICY_ID` is treated as unset and the call auto-resolves, so a malformed ID quietly applies the key's bound policy; only a numeric ID the key cannot use reaches the verdict-less 200 the README warns about. The Claude Code response hook is the exception and crashes instead. [ai-security.ai-guard.integrations:malformed-policy-id] Per host: the AWS modules drop a non-numeric ID and apply the key's policy ([A non-numeric AIGUARD_POLICY_ID (a policy name, a UUID, a typo with letters) is dropped without a warning and the integration calls resolve-and-execute-policy, so the key's bound policy is applied instead of failing; only a numeric ID the key cannot use reaches execute-policy and fails closed on the verdict-less reply.](kb:ai-security.ai-guard.integrations.aws:malformed-id-autoresolves)), the NeMo custom action ignores it ([The custom action calls `resolve_and_execute_policy` through the SDK's `LegacyZGuardClientHelper` unless `AIGUARD_POLICY_ID` holds an integer, in which case it calls `execute_policy` with it; a non-integer value is logged as a warning and ignored. No transaction ID is sent.](kb:ai-security.ai-guard.integrations.nemo-guardrails:config-endpoint)), and the Apigee and Azure examples parse it as an integer ([The policy ID comes only from the KVM and is converted with parseInt; a caller cannot choose a policy per request (an earlier revision honoured an `X-AIGuard-Policy` header).](kb:ai-security.ai-guard.integrations.google-apigee-proxy:policy-id-from-kvm), [Every scan, prompt or response, POSTs to `https://api.{cloud}.zseclipse.net/v1/detection/resolve-and-execute-policy` with the key as a Bearer token, a 10-second timeout and errors ignored; a `currentPolicy` value is added to the body as `policyId` (int.Parse) but does not change the endpoint.](kb:ai-security.ai-guard.integrations.azure-apim:endpoint)). The Apigee example records that resolve-and-execute ignores a policy ID [The example's architecture note says resolve-and-execute-policy ignores a `policyId` in the body without an error and applies the key's own policy, which is why a pinned ID is routed to execute-policy instead.](kb:ai-security.ai-guard.integrations.google-apigee-proxy:resolve-ignores-policy-id). The example documents say the API answers HTTP 500 to a `transactionId` that is not a standard 36-character UUID; the 0.2.0 fix hashes such values with `uuid5` or omits them. [ai-security.ai-guard.integrations:transaction-id-uuid] The endpoints, hosts and response fields are in [Calling AI Guard at runtime: the proxy endpoint, the DAS detection API, its host, direction and policy ID, and throttling in the Python SDK](kb:ai-security.ai-guard.runtime-api).

**Directions.** ARCHITECTURE.md defines direction `IN` as data coming into the system (user prompts, MCP tool parameters) and `OUT` as data going out (tool responses, URLs being fetched). [ai-security.ai-guard.integrations:direction-convention] The Cursor example departs from it [divergence:ai-security.ai-guard.integrations:tool-output-direction]. The agentic AI guide labels an agent's prompt to its LLM direction `OUT` (to the external LLM), and its example agent scans that prompt with `OUT` and returns the generated reply without scanning it. [ai-security.ai-guard.integrations:agentic-guide] That contradicts the other examples [divergence:ai-security.ai-guard.integrations:llm-prompt-direction]; the both-directions advice is [The application should inspect both sides: the prompt before it is sent to the model and the response before it is shown to the user; skipping the response call gives up output enforcement.](kb:ai-security.ai-guard.runtime-api:both-directions).

## Fail posture: what the documents say

The root README says every integration fails closed: `ALLOW` is allowed, `DETECT` is allowed as monitor-only (reported and logged, not enforced), `BLOCK` is blocked, and a missing API key, an unreachable API, a timeout or network error, HTTP 401 or 403, an HTTP 200 carrying no `action`, and any unrecognised verdict are all blocked. [ai-security.ai-guard.integrations:posture-table] The example documents say a policy ID the key cannot use comes back as "Policy not found" inside an HTTP 200 with no `action` field, so reading a verdict-less 200 as permission silently disables scanning. [ai-security.ai-guard.integrations:soft-failure] The README names two exceptions: the Windsurf and Cline post-hooks and the Codex `Stop` hook are audit-only because those events cannot block, and unclassifiable gateway traffic is passed unscanned unless `failClosedOnUnknown` is set. [ai-security.ai-guard.integrations:posture-exceptions]
