# The zscaler-aiguard-intercept Lua plugin for Kong Gateway: access and response phase scans, its configuration, and where it blocks or lets traffic pass (ai-security.ai-guard.integrations.kong-plugin)
Also called: ai guard kong; ai guard kong plugin; zscaler-aiguard-intercept; ai guard kong lua; ai guard konnect hybrid

The Kong plugin is Lua code for self-managed Kong Gateway nodes, including Konnect hybrid data planes; Konnect's SaaS gateways cannot run custom Lua and use [The Kong Konnect Request Callout recipe for AI Guard: a prompt-only scan described in a README, how it extracts the prompt, and where it passes traffic](kb:ai-security.ai-guard.integrations.kong-request-callout) instead. In the access phase the plugin enables request buffering, takes the content of the last user-role message of the body's `messages` array and scans it with direction IN; in the response phase it takes the first choice's `message.content` (or `delta.content`) from the buffered body and scans it with direction OUT. [ai-security.ai-guard.integrations.kong-plugin:phases] The plugin is version 0.1.0 with priority 1000 and is documented as compatible with Kong Gateway 3.4 and later. [ai-security.ai-guard.integrations.kong-plugin:compat]

**Configuration.** The configuration has four fields: `api_key` (required, encrypted), `api_endpoint` (default `https://api.us1.zseclipse.net/v1/detection/resolve-and-execute-policy`), `ssl_verify` (default true) and `timeout_ms` (default 10000); there is no policy-ID or cloud field. [ai-security.ai-guard.integrations.kong-plugin:schema] With no policy-ID or cloud field and no `policyId` in the scan body, the plugin cannot pin a policy, and reaching another cloud means setting `api_endpoint` to that cloud's URL. [ai-security.ai-guard.integrations.kong-plugin:endpoint-only-knob] The scan body is `content` and `direction`, plus `transactionId` only when the `Kong-Request-ID` header (or Kong's request ID) is a UUID. [ai-security.ai-guard.integrations.kong-plugin:transaction-id] The README shows a different field [divergence:ai-security.ai-guard.integrations.kong-plugin:payload-field].

**The prompt.** On the prompt, an unreadable body or one with no user message gets HTTP 400; a failed call, a non-200 reply, an empty or non-JSON body and a reply with no `action` are scan errors that block; and any action other than ALLOW or DETECT, compared in lower case, gets HTTP 403. [ai-security.ai-guard.integrations.kong-plugin:prompt-fail-closed]

**The response.** The response scan is skipped and the response returned unscanned when the buffered body is missing, the request context was not stored, or no message or delta content can be extracted (a body that does not decode or has no `choices`, or a first choice with no message or delta content). [ai-security.ai-guard.integrations.kong-plugin:response-skips] When the response scan returns anything but allow or detect, the plugin calls `kong.response.exit` with HTTP 403 "Response blocked by Zscaler AI Guard security policy." from its response phase. [ai-security.ai-guard.integrations.kong-plugin:response-block] The README says the response phase cannot change the status [divergence:ai-security.ai-guard.integrations.kong-plugin:response-status], and what the client receives is open [gap:ai-security.ai-guard.integrations.kong-plugin:response-block-delivery].

What to check:
1. That api_endpoint names the tenant's cloud; the default is the us1 resolve-and-execute URL and the plugin has no cloud or policy-ID setting.
2. Whether the upstream answers in OpenAI chat-completion shape with message content; any other response, including a tool-call-only reply, is returned unscanned.
