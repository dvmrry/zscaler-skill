# AI Guard dashboards, Insights, Token Usage and log exports (ADX, CrowdStrike, S3, Splunk) (ai-security.ai-guard.observability)
Also called: ai guard dashboard; ai guard insights; ai guard token usage; ai guard log export; ai guard siem; ai guard splunk; ai guard crowdstrike; ai guard s3 export; ai guard adx event hub; export tools field; ai guard conversation view; reveal prompt; ai guard detection latency; crwd siem export; crwd event export; ai guard release notes
Former IDs: release-notes

AI Guard reports on its own console and exports events to SIEMs and storage. Help documents a Users version and an Apps and Infrastructure version of each page.

**Dashboard.** The dashboard's Users tab covers a date range of up to 90 days, counts users, LLMs, policy detections and transactions, can be exported to PDF, and lists each transaction with date and time, user, policy name, severity (Info, Low, Medium, High or Critical), prompt and response detections, LLM, and prompt and response actions (Allowed or Blocked); Details opens Overview, Detection Summary, Performance & Network Stats, Custom Request Headers and Prompt/File Details. [ai-security.ai-guard.observability:dashboard-users] The Secure AI Apps and Infrastructure dashboard article's AI Applications tab counts applications and can show entries as individual prompt transactions or as connected multi-prompt conversation threads; a message icon gives a conversation's transaction count, Reveal Prompt shows the exchange in chat layout, and conversation grouping follows existing session boundary logic. [ai-security.ai-guard.observability:dashboard-apps] The Users dashboard article documents no conversation view; only the Apps and Infrastructure article does. [ai-security.ai-guard.observability:users-no-conversations] Which modes the conversation view covers is open [gap:ai-security.ai-guard.observability:conversation-mode-scope].

**Transaction details.** In the AI Guard for Apps article a transaction's details window opens from the dashboard's Details column with View Details and shows the Transaction ID; an Overview with date, policy triggered, LLM, app, severity (Info > Low > Medium > High > Critical), LLM model and user agent; Prompt Detections and Response Detections with each prompt or response action (blocked, allowed or just detected) and prompt tags; custom request headers set up in the tenant settings; the prompt and response text; and, with the proper permissions, Add to Allowlist for a revealed blocked prompt or response. [ai-security.ai-guard.observability:transaction-details] The AI Guard for Apps detection summary's Performance & Network Stats show prompt size, response size, total time taken by the LLM, the LLM provider's HTTP status code, detection time on request and on response, the region of the app's server, and the protocol used by the transaction. [ai-security.ai-guard.observability:performance-stats] In the AI Guard detection summary found in the transaction details window, a transaction's Transaction Details window opens from the dashboard's Details column with View Details, and its Overview shows date, user (who submitted the prompt or received the response), severity (Info > Low > Medium > High > Critical), policy, LLM, LLM model and user agent. [ai-security.ai-guard.observability:detection-summary-users-overview] In the AI Guard detection summary's Detection Summary section, Prompt Detections and Response Detections show which detectors were triggered, and Prompt Action and Response Action show whether the prompt or response was blocked, allowed, or just detected, alongside prompt and response tags. The same page also gives the Transaction ID, the prompt and response text and, with the proper permissions, Add to Allowlist for a revealed blocked prompt or response. [ai-security.ai-guard.observability:detection-summary-users-actions] The detection summary lists the prompt and response actions as blocked, allowed or just detected, while the Users dashboard lists them as Allowed or Blocked [divergence:ai-security.ai-guard.observability:action-values]. In the AI Guard detection summary, Performance & Network Stats list prompt size, response size, total time taken by the LLM, the LLM provider's HTTP status code, detection time on request and on response, the region of the user's server, and the protocol; Custom Request Headers shows headers set up in the AI Guard tenant settings. [ai-security.ai-guard.observability:detection-summary-users-stats]

**Latency.** On the Latency page, a user's request is first analyzed by AI Guard to see whether it triggers any detectors; if the prompt is not blocked, the LLM provider processes it and returns a response to AI Guard for analysis, and if the response is not blocked it is sent to the user. Depending on prompt complexity, speed of analysis and internet speed this can cause latency, and AI Guard includes Total Time Taken By LLM, Detection Time on Request and Detection Time On Response in the details of every logged transaction. [ai-security.ai-guard.observability:latency] What is still unstated about expected latency is kept in [AI Guard: runtime guardrails on prompts and responses, its Proxy and DAS/API modes, and where each part is documented](kb:ai-security.ai-guard).

**Insights.** Insights reports total and blocked prompts and responses, approximate prompt and response tokens, average tokens per prompt and per response, average prompt and response detection latency in milliseconds, active users and LLMs, and graphs of trend over time, transactions by LLM, transactions by users, top detectors, PII detections by user or user group, and PII categories, plus the most common prompt categories. [ai-security.ai-guard.observability:insights] On the AI Guard for Apps Insights page, over a selected date range and exportable to PDF, Active Apps gives the total number of active AI applications; Transactions by Application shows the total number and percentage of transactions; Top Applications ranks applications by transaction volume; PII Detections by Application gives PII detections per application; and Transactions by LLM shows the active LLMs, colored by how many are Low Risk, High Risk or Critical Risk. [ai-security.ai-guard.observability:insights-apps] The Security Posture chart shows the share of Allowed, Blocked and Passthrough transactions across all AI traffic. [ai-security.ai-guard.observability:security-posture]

**Token Usage.** Token Usage shows prompt and response tokens across the tenant or for one user: total tokens, top user, busiest day, average per user, activity by day and hour (with hourly or 5-minute granularity), LLM provider distribution, the top 10 users, and exportable raw data. [ai-security.ai-guard.observability:token-usage] On the AI Guard for Apps Token Usage page, usage can be viewed across the entire tenant or for a single application; Top App is the app that used the most tokens, Avg. per App is the average tokens used by each app on the leaderboard, and Top usage by app lists the 10 applications that used the most tokens, with a label at the end of each bar showing when usage peaked. [ai-security.ai-guard.observability:token-usage-apps]

**Topology.** The AI Guard for Apps Topology page gives a system overview of the data flow between all AI apps and the LLM providers managed by AI Guard in Proxy mode; AI apps are blue circles and LLM providers purple hexagons, nodes can be searched by AI App, LLM Providers or All Types, and clicking a node highlights the direct connections to and from it. [ai-security.ai-guard.observability:topology] The AI Guard for Users Topology page gives a system overview of the data flow between all user groups and the LLM providers managed by AI Guard in Proxy mode; users or user groups are green circles, LLM providers purple hexagons, and data flow lines connecting them. [ai-security.ai-guard.observability:topology-users] On the Users tab of the Topology page the view can be searched by a specific user group or LLM provider and limited to Users, LLM providers or All Types, and clicking a node highlights the direct connections to and from it. [ai-security.ai-guard.observability:topology-users-search]

**Audit log.** The Audit Log page tracks changes users make inside AI Guard, from updating a policy control to signing in; over a selected date range it lists each action's initiator (the email address of the user that triggered it), action (such as Update, View or Create) and entity type (more granular detail about the action), and Export CSV downloads the filtered audit log. [ai-security.ai-guard.observability:audit-log] An audit log entry's details show the Entity ID (the ID number associated with the action), a change table in which nested fields are a single level deep and only relevant changes are shown (noise such as id or lastUpdatedAt fields with no changes is hidden), the full JSON changes under Advanced, and Revert, which undoes Create, Update or Delete on all supported detectors after asking for confirmation. [ai-security.ai-guard.observability:audit-details-revert]

**Log exports.** Log exports go to Azure Data Explorer through Event Hubs (a metadata hub, and an optional content hub), CrowdStrike SIEM Direct Export (event metadata to the CrowdStrike HTTP Event Collector), CrowdStrike SIEM Export via S3 (metadata to the HEC, event contents to an S3 bucket), S3 (separate metadata and content buckets), and Splunk (a metadata HEC, and an optional content HEC). [ai-security.ai-guard.observability:export-targets] Each of the five export types (ADX, CrowdStrike direct, CrowdStrike via S3, S3, Splunk) has Export Allowed/Detected Prompts and Export Blocked Prompts options, an Export Tools Field option that is enabled by default and, when disabled, removes the Tools field from the exported metadata, and a Validate Connection check. [ai-security.ai-guard.observability:export-filters] The S3 export assumes an IAM cross-account role in the customer's AWS account (its external ID fills in automatically), object tags need the role to allow `s3:PutObjectTagging`, and the Apps and Infrastructure article points to a CloudFormation template in the AI Guard portal for the roles and policies. [ai-security.ai-guard.observability:s3-export] The exported record format is open [gap:ai-security.ai-guard.observability:export-schema].

**The S3 runbook.** The S3 integration runbook's prerequisites are an AI Guard subscription, AWS S3 Metadata and Content buckets in the same region, and a cross-account IAM role; its example trust policy lets the Zscaler AI Guard AWS account root call sts:AssumeRole, its example permissions policy grants s3:ListBucket and s3:GetBucketLocation on each of the content and metadata buckets and s3:GetObject, s3:PutObject and s3:DeleteObject on their objects, and it says the IAM role policy is in many cases sufficient, especially when the role and buckets are in the same AWS account. [ai-security.ai-guard.observability:s3-runbook-iam] For an AssumeRole failure, which the S3 runbook describes as an AWS Security Token Service (STS) AssumeRole request being rejected, it lists checking that the trust policy includes the correct Zscaler AI Guard AWS account from the Add Integration window, that the role ARN entered in the UI is correct, that no AWS Organizations Service Control Policy (SCP) or permission boundary blocks sts:AssumeRole, and that no incorrect sts:ExternalId condition was added, with the IAM Cross-Account Role External ID field left at its default value. [ai-security.ai-guard.observability:s3-runbook-assume-role] For S3 access errors the S3 runbook lists checking that the bucket names are entered correctly, that the IAM role policy includes both bucket-level and object-level permissions, and that there is no explicit Deny in the bucket policy or organization policy; it says a case where listing works but writing fails usually means s3:ListBucket is present but s3:PutObject is missing or incorrectly configured, and for encrypted objects it lists checking that SSE-KMS is enabled in the buckets, whether the role has KMS permissions and whether the KMS key policy allows the role. [ai-security.ai-guard.observability:s3-runbook-s3-access] The runbook's tag setting against the export page's permission is open [gap:ai-security.ai-guard.observability:s3-tagging-permission]. Competition triggers carry a scoreByCompetitor dict in log exports: [The Competition detector's triggers are tagged with a per-competitor scoreByCompetitor dict, so individual competitors can be pivoted on in a BI tool or spreadsheet; the runbook's support-ticket list for persistent false positives includes the confidence score from scoreByCompetitor and whether the prompt was in English or another language.](kb:ai-security.ai-guard.detectors.competition:score-field). The Topic runbook's detection-log statement is [The runbook says the detection log contains the full response JSON, including confidence scores per topic, which is the same data the policy engine uses.](kb:ai-security.ai-guard.detectors.topic:log-scores).
