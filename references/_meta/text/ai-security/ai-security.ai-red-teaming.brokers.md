# The AI Red Teaming broker: outbound WSS tunnel to private apps, provisioning, run manifest, allow-lists and troubleshooting codes (ai-security.ai-red-teaming.brokers)
Also called: ai red teaming broker; red teaming broker; airt broker; ai security broker; register broker; broker run manifest; airt-broker diagnose; broker gateway; broker wss

The AI Red Teaming Broker enables Zscaler's AI Red Teaming (AIRT) workers, which run in the Zscaler cloud, to reach private AI applications hosted inside a customer's network without any firewall changes to allow inbound connections originating from the Internet: the customer deploys a lightweight broker agent inside the network, which opens a single outbound connection to the Zscaler cloud. [ai-security.ai-red-teaming.brokers:purpose] The broker opens one outbound WebSocket Secure (WSS) connection to the Broker Gateway running in the Zscaler infrastructure and keeps it open; the AI Red Teaming Worker sends commands to the Broker Agent via the gateway, the agent forwards them to the customer AI app and returns the app's responses the same way, and no service is exposed to the internet in the customer's network since the broker makes only outbound connections on port 443. [ai-security.ai-red-teaming.brokers:tunnel]

**Setup.** Provisioning a broker creates a new broker entry in the AI Security Admin Portal to generate the credentials and configuration for deployment; the broker authenticates with an OAuth API Client created in the Authentication Service Admin Portal with the AI Red Teaming Viewer scope under AI Security and Validation Type Secret, which can be reused across multiple brokers; the run manifest is then downloaded and deployed in the private network, the broker is confirmed Online (an outbound WebSocket connection to the Zscaler cloud gateway), and the private AI application is added as a target and associated with the broker. [ai-security.ai-red-teaming.brokers:provisioning] A broker is registered before AI Red Teaming traffic can be routed through the AI Security Admin Portal, under Administration > AI Red Teaming > Brokers, with a Name, Business Units and a Description (what the broker connects to, where it runs, and who runs it). [ai-security.ai-red-teaming.brokers:registration] The pages name the Brokers page two ways [divergence:ai-security.ai-red-teaming.brokers:console-path-names]. The OAuth API client is a ZIdentity one, covered in [ZIdentity API clients: what one is, how it authenticates, its resources and scopes, and its token lifetime](kb:zidentity.api-clients). Which apps a broker can serve is in [Connecting an AI app for red teaming: network type, private access, and the application profile that shapes tests](kb:ai-security.ai-red-teaming.assets).

**Run manifest.** A broker's Commands/Instruction tab provides a run manifest for Docker, Docker Compose, or Kubernetes with all required variables pre-filled, where only the Authentication Service OAuth credentials are supplied by the customer: GATEWAY_URL (the WSS gateway endpoint), BROKER_ID (issued at registration) and OAUTH_TOKEN_URL (the Authentication Service OAuth token endpoint) come from the AI Security Admin Portal, and OAUTH_CLIENT_ID and OAUTH_CLIENT_SECRET come from the customer. [ai-security.ai-red-teaming.brokers:run-manifest] The page's example Docker command runs the container as airt-broker with --restart unless-stopped, sets SSL_VERIFY="true", LOG_LEVEL="INFO" and HEALTHZ_PORT="8080", gives the example gateway as wss://airt-gw.us2.zscaler.net:443/ws/broker, and names the image nexus.corp.zscaler.com:9016/airt/airt-broker:<tag>. [ai-security.ai-red-teaming.brokers:manifest-example] The other manifests and a healthy diagnose output are not in the capture [gap:ai-security.ai-red-teaming.brokers:captured-gaps].

**Brokers page.** The Brokers page lists each broker's Broker Name, Description, Business Unit, Connected AI Apps (private AI applications currently linked), Status (Online, an active WebSocket Secure (WSS) connection to the gateway, or Offline, the connection lost or the broker stopped), Last Seen (when the broker last successfully communicated with the Broker Gateway), Version of the broker agent and Source IP (the public IP address its outbound connection originates from); the Show Revoked toggle shows revoked brokers. [ai-security.ai-red-teaming.brokers:broker-list] On a selected broker, Revoke Broker temporarily disables an active broker's connection to the platform, Reinstate Broker restores a previously revoked broker and re-enables its connection, and Delete Broker permanently removes a broker and all its associated configuration. [ai-security.ai-red-teaming.brokers:actions] A broker's Audit Log tab displays a time-stamped record of all significant activities and changes made to broker instances, filterable by time range, event type and actor; an entry's actor is either a broker (an automated action triggered by the broker agent itself) or a user (a platform administrator who made a manual change). [ai-security.ai-red-teaming.brokers:audit-log] The Pending and Revoked statuses beyond those the list names are open [gap:ai-security.ai-red-teaming.brokers:status-values].

**Allow-lists.** A broker's configuration holds an Allowed Source CIDR list, the ranges the broker may connect from, and an Allowed Targets list, the only targets it may reach, where an empty list means no restriction; after a broker is attached to an AI target, all test traffic is automatically routed through it without manual URL configuration. [ai-security.ai-red-teaming.brokers:allow-lists] The two pages label them differently [gap:ai-security.ai-red-teaming.brokers:allow-list-labels]. The troubleshooting page adds the broker's public egress IP under Source-IP Allow-list, and allow-list changes apply immediately and no broker restart is required; a broker showing Revoked is reinstated from Administration > Red Teaming > Brokers by opening the broker and selecting Reinstate. [ai-security.ai-red-teaming.brokers:allow-list-immediate]

**Troubleshooting.** For any broker issue the first step is the built-in diagnostic tool, which checks connectivity, certificates, OAuth credentials, and DNS without disrupting a live broker, run within the container as docker exec <broker-container> python -m airt_broker diagnose. [ai-security.ai-red-teaming.brokers:diagnose] The troubleshooting table gives these causes: a broker that stays Pending or Offline with repeated opening wss and no wss connected cannot reach or authenticate to the gateway (check egress to GATEWAY_URL:443 and run the diagnose tool); an auth token returning 401 invalid_client is an incorrect OAUTH_CLIENT_ID or OAUTH_CLIENT_SECRET; WSS rejected 4403 (gateway_cidr_rejected) means the broker's egress IP is not in the source-IP allow-list; WSS rejected 4401 (gateway_broker_unregistered / _revoked) means a BROKER_ID mismatch, or the broker revoked or deleted. [ai-security.ai-red-teaming.brokers:symptom-codes] Tests returning 403 while the broker is Online mean the target base URL is not in the broker's target allow-list (add it, or correct X-Target-Url); tests timing out (504) or failing 502 mean the target is slow or unreachable from the broker's network (verify the broker can reach the target, and raise TARGET_REQUEST_TIMEOUT for slow applications); periodic idle disconnects with close_code:null come from an intermediary's idle or max-connection timeout, are benign because the broker reconnects automatically, and the intermediary's idle timeout can be raised if frequent. [ai-security.ai-red-teaming.brokers:symptom-traffic] TLS errors at the broker (certificate verify failed, unable to get local issuer) have the cause of a corporate TLS inspection proxy or private Certificate Authority intercepting the broker's outbound connection; the table's remedies are to set EXTRA_CA_CERTS to the PEM file path and mount it into the container, disable SSL inspection for the broker traffic, and set HTTPS_PROXY if an outbound proxy is required, and the page says not to set SSL_VERIFY to false because disabling certificate validation removes a critical security control and is not supported in production environments. [ai-security.ai-red-teaming.brokers:tls-inspection] For a support request the page asks for the diagnostic report from diagnose --json (docker exec <broker-container> python -m airt_broker diagnose --json > diag.json), the last 500 lines of the container log, the BROKER_ID and the approximate date and time of the incident; the diag.json output is automatically redacted and does not contain OAUTH_CLIENT_SECRET. [ai-security.ai-red-teaming.brokers:support-bundle]
