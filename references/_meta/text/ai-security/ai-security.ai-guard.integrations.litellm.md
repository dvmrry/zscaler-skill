# AI Guard with the LiteLLM proxy: LiteLLM's native zscaler_ai_guard guardrail as the README describes it, and the SDK-based callback example (ai-security.ai-guard.integrations.litellm)
Also called: ai guard litellm; zscaler_ai_guard guardrail; litellm zscaler ai guard; aiguard_guardrail.py; ZSCALER_AI_GUARD_API_KEY; zguard_policy_id

The LiteLLM folder offers two routes: a guardrail that ships inside LiteLLM itself, whose code is not in this repository, and an example callback built on the Zscaler Python SDK. The README describes LiteLLM's built-in `zscaler_ai_guard` guardrail, configured in config.yaml with `mode` `during_call` for input and `post_call` for output, an API key, an optional base URL and policy ID, per-request overrides through `metadata.zguard_policy_id`, per-team and per-key policies, and forwarding of user information. [ai-security.ai-guard.integrations.litellm:native] The example native configuration notes that `api_base` defaults to `https://api.us1.zseclipse.net/v1/detection/execute-policy` and marks `policy_id` optional, and the README's comparison lists the native plugin's policy selection as an explicit policy ID. [ai-security.ai-guard.integrations.litellm:native-endpoint] Whether execute-policy works without a policy ID is open in [What execute-policy does without a policy ID](kb:ai-security.ai-guard.runtime-api:execute-without-policy-id).

**The SDK callback.** The example callback is a LiteLLM CustomLogger: `async_pre_call_hook` scans the last user message (text parts joined) with direction IN, and `async_post_call_success_hook` scans the first choice that has message content with direction OUT, each through the SDK's `LegacyZGuardClientHelper` `resolve_and_execute_policy` with a fresh uuid4 transaction ID, run in a worker thread. [ai-security.ai-guard.integrations.litellm:callback-hooks] When the request has no user content, or the response has no choice with message content, the callback returns without scanning. [ai-security.ai-guard.integrations.litellm:callback-skips] A tool-call-only reply, whose message carries no content, is therefore returned unscanned. [ai-security.ai-guard.integrations.litellm:tool-call-reply-unscanned] The callback raises an HTTP 403 `HTTPException` unless the action is ALLOW or DETECT, so a missing action blocks; an SDK error is logged and raised as a plain Exception carrying the error text. [ai-security.ai-guard.integrations.litellm:callback-verdict] What LiteLLM does with the callback's exceptions, and whether the hooks run for streamed responses, is open [gap:ai-security.ai-guard.integrations.litellm:hook-behavior].

**SDK version.** The callback's Dockerfile extends the LiteLLM `main-stable` image and installs `zscaler-sdk-python` with no version constraint; the key and cloud come from `AIGUARD_API_KEY` and `AIGUARD_CLOUD` (default us1). [ai-security.ai-guard.integrations.litellm:sdk-unpinned] The SDK release that fixed detection authentication is in [The legacy helper sets an Authorization header carrying the API key as a Bearer token on each detection request; detection calls are dispatched through it since release 1.9.44, which fixed them falling through to the standard OneAPI session without the AI Guard API key.](kb:ai-security.ai-guard.runtime-api:sdk-bearer).

What to check:
1. For the native guardrail, whether a policy_id is configured; its default endpoint is execute-policy.
2. For the callback image, which zscaler-sdk-python version pip installed; the Dockerfile does not pin it.
3. Whether clients stream; the callback's response behavior for streams is not established.
