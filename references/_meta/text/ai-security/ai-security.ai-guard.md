# AI Guard: runtime guardrails on prompts and responses, its Proxy and DAS/API modes, and where each part is documented (ai-security.ai-guard)
Also called: ai guard; aiguard; zguard; what is ai guard; ai guard proxy mode; ai guard daas; ai guard das mode; detection as a service; ai guard deployment modes; ai guard configuration steps; llm guardrails; ai guard for users; ai guard apps and infrastructure; ai guard gov cloud; ai guard government cloud

AI Guard inspects the prompts sent to large language models and the responses that come back. This subject covers what it is and how it is placed; its children cover each part.

**What it does.** AI Guard provides run-time protection for AI applications by enforcing enterprise policies on the prompts users enter and the responses they receive, using intent-based detectors on both. [ai-security.ai-guard:runtime-protection] AI Guard enforces policies on prompts and responses both between users and public AI apps (such as ChatGPT, Perplexity and Claude) and between private AI apps and foundation LLMs (such as OpenAI and Anthropic). [ai-security.ai-guard:policy-scope] Its detectors are in [AI Guard's detectors: the capabilities Help lists and the detectors the policy editor configures](kb:ai-security.ai-guard.detectors) and its policies in [AI Guard policies: detector settings, policy control rules, first-match order, applications and testing](kb:ai-security.ai-guard.policies).

**Two modes.** AI Guard has two deployment modes: in Proxy mode it is an inline reverse proxy between the AI application and the LLM provider; in DAS/API (Detection-as-a-Service) mode it is an API endpoint that the application must call for every prompt and every response. [ai-security.ai-guard:two-modes] In Proxy mode the application sends its model requests to AI Guard at `https://proxy.zseclipse.net` instead of to each provider, and AI Guard proxies them to the upstream LLM provider, sitting inline for routing, inspection and enforcement. [ai-security.ai-guard:proxy-single-destination] In DAS/API mode AI Guard is not inline: the application keeps calling the LLM directly and calls AI Guard before sending the prompt and again on the model's response before returning it. [ai-security.ai-guard:das-not-inline] A DAS/API deployment does not depend on ZIA forwarding: the inspection happens because the application calls AI Guard, wherever the application runs. [ai-security.ai-guard:das-no-zia-dependency] LLM provider and provider-credential objects are a Proxy-mode requirement: in Proxy mode AI Guard stores the provider credentials and uses them to forward requests, while in DAS/API mode the application keeps its direct provider connection and credentials, and no captured page asks for provider objects. [ai-security.ai-guard:providers-proxy-only] In Proxy mode AI Guard acts as a reverse proxy for the LLM provider, so an LLM provider and its credentials must be added before a Proxy-mode AI application. A provider has a name, a provider type and a Public or Private deployment; its credential has a name, names the provider, has an optional expiry date and holds, in its API Key field, the keys or IAM roles copied from the provider's dashboard, which AI Guard uses to authenticate to the provider. [ai-security.ai-guard:provider-objects] The Secure Access to AI Apps release summary's entry for AI Guard 2.13.1 says all default LLM providers are now provisioned automatically and pre-configured during AI Guard tenant creation, with no impact on existing customers. The Proxy-mode quick start's credential and identity-broker steps select "Default Anthropic Provider", and none of its five steps adds a provider. [ai-security.ai-guard:default-providers] Whether the mode is set per tenant or per application differs between pages [divergence:ai-security.ai-guard:mode-scope], and what the Tenant Settings mode governs is open [gap:ai-security.ai-guard:tenant-mode-effect]. The API side of providers and credentials is in [The AI Guard configuration API: behavior the contract states, limits and errors, and what the Python SDK covers](kb:ai-security.ai-guard.admin-api). A third, on-premises mode is a legacy statement no current page carries [gap:ai-security.ai-guard:onprem-mode].

**Users' traffic through ZIA.** For users of public AI apps, ZIA proxy-chains their traffic to AI Guard: [Sending ZIA users' AI traffic to AI Guard by proxy chaining: prerequisites, proxy, QUIC rule and forwarding](kb:ai-security.ai-guard.zia-integration).

**Setting it up.** The quick-start guides order setup by mode. Proxy mode: set the Mode to Proxy in Tenant Settings and enable Store Prompts/Responses; add the LLM provider's credentials; add the AI application and an application identity broker linking it to the provider, whose API key the application uses; create a policy configuration and a policy control that applies it to the application; then test and validate on the Dashboard. DAS/API mode: set the Mode to DAS and enable Store Prompts/Responses; add the AI application and its API key; create a policy and note its Policy ID; then test and validate. [ai-security.ai-guard:config-sequence] Tenant-wide settings are in [AI Guard tenant settings: prompt storage, encryption keys, ZIA sync, block messages, organization restrictions, Anthropic webhook](kb:ai-security.ai-guard.tenant-settings) and administrator roles in [Who administers AI Guard: system users and RBAC roles](kb:ai-security.ai-guard.admin-access).

**Watching it.** Dashboards, Insights, Token Usage and log exports are in [AI Guard dashboards, Insights, Token Usage and log exports (ADX, CrowdStrike, S3, Splunk)](kb:ai-security.ai-guard.observability).

**Programming it.** Runtime calls, the proxy endpoint and the DAS detection API, are in [Calling AI Guard at runtime: the proxy endpoint, the DAS detection API, its host, direction and policy ID, and throttling in the Python SDK](kb:ai-security.ai-guard.runtime-api); the configuration API and what the Python SDK covers are in [The AI Guard configuration API: behavior the contract states, limits and errors, and what the Python SDK covers](kb:ai-security.ai-guard.admin-api); Zscaler's public integration examples are in [Zscaler's AI Guard integration examples (zguard-ai-integrations): the catalog, the promised fail-closed posture against what each example does, and where each intercepts](kb:ai-security.ai-guard.integrations).

**Not settled.** How detection runs (models, GPUs) and what latency it adds are open [gap:ai-security.ai-guard:inference-and-latency]. Whether AI Guard is offered in government clouds is open [gap:ai-security.ai-guard:gov-cloud]. The Topology and Audit Log pages are in [AI Guard dashboards, Insights, Token Usage and log exports (ADX, CrowdStrike, S3, Splunk)](kb:ai-security.ai-guard.observability) and prompt allowlisting is in [AI Guard policies: detector settings, policy control rules, first-match order, applications and testing](kb:ai-security.ai-guard.policies).

**Adjacent ZIA controls.** Access control for public AI apps, and ZIA's own prompt capture, belong to ZIA Cloud App Control: [AI & ML Applications rules: granular actions, prompt capture, tenant profiles](kb:zia.cloud-app-control.ai-ml-rules).

What to check:
1. Which mode the application uses; Tenant Settings shows Proxy or DaaS while the architecture article and the configuration API treat the mode as per application (which of the two governs is open), and the call path, the provider objects and the credentials differ between the modes.
2. For DAS/API, that the application calls AI Guard on both the prompt and the response; AI Guard sees nothing the application does not send.

- [ai-security.ai-guard:providers-proxy-only] Tier B: The credential page, the Proxy-mode application page and the architecture article tie providers and their credentials to Proxy mode (quoted); that DAS/API mode needs none rests on their absence from the DAS/API application page and quick-start guide, whose steps add no provider or credential.

Sources disagree (name both sides):
- Whether the Proxy or DAS/API mode is set once for the tenant or per application. [divergence:ai-security.ai-guard:mode-scope]
  - zscaler-help: Tenant Settings (AI Guard for Apps) lists one Mode for the tenant, Proxy or DaaS.
  - zscaler-help: The Proxy quick start's first step sets the Mode to Proxy under Tenant Settings > Security.
  - zscaler-help: The DAS/API quick start's first step sets the same Mode to DAS.
  - zscaler-help: The architecture article says a tenant need not choose one mode: some applications can use Proxy mode and others DAS mode at the same time.
  - api-specs: The configuration API issues each application credential for a mode, PROXY or DETECTIONS.
  Impact: No page says what the Tenant Settings Mode governs when both modes are in use (every application, a default, or a display), so following both quick starts on one tenant sets the same control twice.
