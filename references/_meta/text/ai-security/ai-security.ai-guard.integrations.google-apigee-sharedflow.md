# The ZSCALER-AIGUARD Apigee SharedFlow: dialects, what each leg scans, MCP tool calls, verdict handling, and the traffic it lets through unscanned (ai-security.ai-guard.integrations.google-apigee-sharedflow)
Also called: ZSCALER-AIGUARD; ai guard apigee sharedflow; vertex-aiguard-sync; failClosedOnUnknown; failOpen apigee; blockStatus; ai guard mcp gateway; forceAgentHarness

The SharedFlow is one Apigee bundle that any proxy calls with a FlowCallout on its request leg, its response leg, or both; the shipped `vertex-aiguard-sync` proxy calls it in front of Vertex AI. A proxy invokes the flow with a FlowCallout whose `type` parameter is `user-prompt` (request leg), `response-prompt` (response leg) or `both`, or with a `scanType` flow variable; the phase sets the direction, prompt IN and response OUT, and one invocation scans one direction. [ai-security.ai-guard.integrations.google-apigee-sharedflow:invocation]

**Configuration.** Flow variables set before the callout configure it: `aiguardCloud` (default `us1`) or a full-host `aiguardEndpoint`, `aiguardPolicyId` (else the KVM's `aiguard_policy_id`), `failOpen` (default false), `blockStatus` (default `native`), `appName` (default `Gateway`), `scanTools` (default true), `failClosedOnUnknown` (default false) `forceAgentHarness` (default false) and `aiguardUser` (default empty). [ai-security.ai-guard.integrations.google-apigee-sharedflow:config-vars] The flow reads only `aiguard_api_key` and `aiguard_policy_id` from the environment KVM `aiguard-config`, cached for 300 seconds; the cloud comes from the `aiguardCloud` flow variable, not the KVM. [ai-security.ai-guard.integrations.google-apigee-sharedflow:kvm-keys] The inline proxy's README says the KVM is shared alike [divergence:ai-security.ai-guard.integrations.google-apigee-sharedflow:shared-kvm].

**Which traffic is scanned.** The flow classifies a request as `mcp` (JSON-RPC method `tools/call`), `gemini` (path containing generateContent), `llm` (paths ending /chat/completions, /responses or /v1/messages, or an Anthropic rawPredict on Vertex) or `unknown`; any non-POST request and any count-tokens call is unknown. [ai-security.ai-guard.integrations.google-apigee-sharedflow:dialects] An unknown request is not scanned and passes through by default; with `failClosedOnUnknown=true` it is refused with HTTP 403. [ai-security.ai-guard.integrations.google-apigee-sharedflow:unknown-passes] A request is treated as coming from a coding-agent harness when it carries an `x-claude-code-session-id` header, an `x-app` header equal to `cli`, or `forceAgentHarness` is set; for such a request the flow skips scanning entirely when it has no tools, a `max_tokens` that is set and 4096 or less, or a last user message containing `[SUGGESTION MODE:`, and otherwise strips `<system-reminder>` blocks from user text and does not fold tool results into the prompt scan. [ai-security.ai-guard.integrations.google-apigee-sharedflow:harness-skip] On a proxy that serves ordinary clients, any caller can send `x-app: cli` (or an `x-claude-code-session-id` header) with no tools or a small `max_tokens` and have its prompt forwarded without a scan, and can hide text from the scan inside `<system-reminder>` tags. [ai-security.ai-guard.integrations.google-apigee-sharedflow:harness-bypass]

**What each leg reads.** The prompt leg scans only the newest turn: the parts of the last `contents` entry for Gemini, or the last message for OpenAI and Anthropic, read only when it is a user turn or a tool result; system prompts and earlier turns are not read. [ai-security.ai-guard.integrations.google-apigee-sharedflow:newest-turn] A caller that supplies its own history can put content in earlier turns or the system prompt and have it reach the model unscanned, since the flow assumes earlier turns were scanned when they were new. [ai-security.ai-guard.integrations.google-apigee-sharedflow:history-not-rescanned] The response scan includes the argument values of tool calls the model emits (Gemini functionCall, OpenAI tool_calls and Responses function_call, Anthropic tool_use, and streamed tool-call arguments) whatever `scanTools` says; with `scanTools` on, the prompt scan also includes Gemini functionResponse and, unless the flow has flagged the request as coming from the agent harness (`aiguard.isCC`), Anthropic tool_result and OpenAI tool-role results. [ai-security.ai-guard.integrations.google-apigee-sharedflow:inline-tools] The response leg reassembles a streamed (SSE or JSON-array) response before scanning it, and a blocked streaming request gets an SSE refusal that completes the stream; the README notes tokens already emitted upstream cannot be recalled. [ai-security.ai-guard.integrations.google-apigee-sharedflow:sse-response]

**MCP tool calls.** For MCP `tools/call` the flow builds a tool event from `params.name` and `params.arguments`; on the request leg it is scanned with direction IN before the tool server runs, and on the response leg the tool result's text is added as output and scanned with direction OUT, taking only `result.content` entries of type `text`; the `both` phase does not scan MCP. [ai-security.ai-guard.integrations.google-apigee-sharedflow:mcp] An MCP tool result with no text entries (only images, resources or other content types) leaves the tool event without output, so the response-leg scan re-sends the arguments with direction IN and the result itself returns to the caller unscanned. [ai-security.ai-guard.integrations.google-apigee-sharedflow:mcp-nontext-output] MCP arguments given as an object are serialized with JSON.stringify into the tool event's `input` string, and the scan content is built by collecting the event's values, which keeps that string whole and adds the metadata values (`mcp`, `tools/call`, the proxy name and the tool name). [ai-security.ai-guard.integrations.google-apigee-sharedflow:mcp-args-serialized] The architecture note says scalar values are sent instead [divergence:ai-security.ai-guard.integrations.google-apigee-sharedflow:mcp-args].

**The request to AI Guard.** The scan request carries `content` and `direction`, `transactionId` only when the request's `x-request-id` (or the Apigee message ID) is already a UUID, and `policyId` (parseInt) only when a policy ID is set; a set ID routes the call to execute-policy, otherwise to resolve-and-execute-policy, each with a 5000 ms timeout. [ai-security.ai-guard.integrations.google-apigee-sharedflow:scan-body] When `aiguardUser` is set, the scan body also carries it as `user`, so the detection is attributed to that person on the AI Guard dashboard; the flow's comments say the proxy should set it from the identity its own authentication established, such as a verified JWT claim, because a client-supplied header can name anyone. [ai-security.ai-guard.integrations.google-apigee-sharedflow:user-identity] The notes' account of the API's fields differs from the SDK [divergence:ai-security.ai-guard.integrations.google-apigee-sharedflow:api-fields].

**Verdicts and failures.** The scan callouts continue on error, and the verdict step blocks unless the callout returned HTTP 200 with an action of ALLOW or DETECT: BLOCK blocks, and a missing, unrecognized or non-200 result fails closed unless `failOpen=true`, which allows it. [ai-security.ai-guard.integrations.google-apigee-sharedflow:verdict] A policy block is returned in the caller's own dialect at HTTP 200 (a Gemini candidates envelope, an OpenAI chat completion or Responses object, an Anthropic message, an MCP JSON-RPC error -32000, or an SSE refusal for streaming callers) with `x-aiguard-blocked`, `x-aiguard-category`, `x-aiguard-severity` and `x-aiguard-transaction-id` headers; a numeric `blockStatus` forces that status on non-streaming blocks. [ai-security.ai-guard.integrations.google-apigee-sharedflow:block-shape] When the scan did not complete (a non-200 or a verdict-less reply) and `failOpen` is off, the fail-closed response is HTTP 500 JSON naming the cause ("HTTP" with the callout status, "no verdict returned" with the in-body statusCode and errorMsg, or "AI Guard API unreachable"), or for MCP a JSON-RPC error -32603 at HTTP 200, which a numeric `blockStatus` replaces as on any non-streaming 200. [ai-security.ai-guard.integrations.google-apigee-sharedflow:fail-closed-shape] With no API key in the KVM and `failOpen` false the flow answers HTTP 500 before any scan; with `failOpen` true it proceeds, and the unauthenticated scan then fails open. [ai-security.ai-guard.integrations.google-apigee-sharedflow:config-error]

What to check:
1. That every proxy calling the flow sets aiguardCloud when the tenant is not on us1; the flow reads no cloud from the KVM.
2. Whether failClosedOnUnknown is on; with the default, requests on unrecognized paths or with non-POST verbs pass unscanned.
3. On a general-purpose proxy, whether clients can send x-app: cli or x-claude-code-session-id; those headers make small or toolless requests skip scanning.
4. Whether callers can supply conversation history or system prompts; only the newest turn is scanned.

Sources disagree (name both sides):
- Whether the SharedFlow scans MCP tool arguments as serialized JSON or as their scalar values. [divergence:ai-security.ai-guard.integrations.google-apigee-sharedflow:mcp-args]
  - zguard-integrations: The architecture note says the flow collects the JSON's scalar values for tool calls, not its serialization, because a JSON wrapper reads as code and false-positives benign calls.
  - zguard-integrations: For MCP the extractor stringifies object arguments before the collector runs, so the collector keeps the serialized string.
  Impact: MCP arguments reach the detectors as JSON text, the shape the note says false-positives benign calls; inline tool calls in LLM responses are collected as values (inline-tools).
- Whether one aiguard-config KVM configures the inline proxy and the SharedFlow alike. [divergence:ai-security.ai-guard.integrations.google-apigee-sharedflow:shared-kvm]
  - zguard-integrations: The inline proxy's README says its KVM uses the same map and key names as the SharedFlow and both Cloud Run pipelines, so one provisioned environment serves any of them.
  - zguard-integrations: The SharedFlow reads only the API key and policy ID from that KVM and takes the cloud from the aiguardCloud flow variable, defaulting to us1.
  Impact: An aiguard_cloud KVM entry set for the inline proxy does nothing for the SharedFlow; a tenant outside us1 must set aiguardCloud in each calling proxy (see ai-security.ai-guard.integrations.google-cloudrun:flow-cloud-us1).
- Which request fields the DAS detection API accepts. [divergence:ai-security.ai-guard.integrations.google-apigee-sharedflow:api-fields]
  - zguard-integrations: The SharedFlow's architecture design note (not a description of the flow's current behaviour), like the inline proxy's and the AWS modules', says the API accepts content, direction, transactionId and policyId and no other field, so there is no place for user or session identity.
  - sdk-python: The Python SDK's resolve_and_execute_policy sends a user field when one is given, recorded on the detection event since release 1.10.0, and can add tenant-configured request headers.
  - zguard-integrations: The SharedFlow's own scan-body builder adds a `user` field to the scan body when one is set.
  - zscaler-help: Help's AI Guard for Apps release of September 11, 2026 says resolve-and-execute takes optional user, clientName and appName fields.
  Impact: The architecture note's four-field account is out of date for resolve-and-execute: Help and the SDK both have it take a `user`, and the SharedFlow itself forwards `user`; Help adds `clientName` and `appName` (ai-security.ai-guard.runtime-api:resolve-optional-fields), which are absent from the SharedFlow's code. No source says whether execute-policy takes `user`, `clientName` or `appName` (the SharedFlow sends `user` on both endpoints). Integrations built on the four-field assumption leave attribution unused.
