# OpenAI Codex CLI hooks for AI Guard (Zscaler example): hooks, block mechanisms, the fail-open Stop scan, and what content is scanned (ai-security.ai-guard.integrations.codex)
Also called: codex hooks aiguard; codex-hooks; scan_stop_response.py; scan_bash_command.py; codex cli aiguard

Zscaler's Codex CLI example is six Python hooks that send prompts, Bash and MCP tool input and output, and the final reply to AI Guard's detection API through the Python SDK.

**What is hooked, and when.** The example's `hooks.json` runs `scan_user_input.py` on `UserPromptSubmit` (direction `IN`), `scan_bash_command.py` and `scan_mcp_request.py` on `PreToolUse` for `Bash` and `mcp__.*` (`IN`), `scan_bash_response.py` and `scan_mcp_response.py` on `PostToolUse` for the same matchers (`OUT`), and `scan_stop_response.py` on `Stop` (`OUT`), each with a timeout of 15. [ai-security.ai-guard.integrations.codex:hooks] The README says `apply_patch` file edits are not scanned, `PreToolUse` and `PostToolUse` do not intercept non-MCP, non-Bash tools such as `WebSearch`, Codex exposes no streaming interception hook, `Stop` fires after the response has been streamed and displayed, and post-tool blocking cannot undo a completed call's side effects. [ai-security.ai-guard.integrations.codex:coverage-limits]

**Which call it makes.** `aiguard_utils.py` reads `.env` files next to `.codex/`, in the working directory, in `.codex/` and in `.codex/hooks/` (first definition wins, the real environment wins, an `export` prefix is tolerated); `AIGUARD_CLOUD` defaults to `us1` and `AIGUARD_TIMEOUT` to 30; an `AIGUARD_POLICY_ID` that parses as an integer selects `execute_policy`, anything else `resolve_and_execute_policy`; the log is `SECURITY_LOG_PATH`, default `.codex/hooks/aiguard.log`. [ai-security.ai-guard.integrations.codex:config] The hooks send a transaction ID taken from `turn_id`, else `tool_use_id`, else the session, hashing any non-UUID value into a deterministic UUID (`uuid5`) and passing a UUID unchanged. [ai-security.ai-guard.integrations.codex:transaction-id] Why the IDs are hashed is in [The example documents say the API answers HTTP 500 to a `transactionId` that is not a standard 36-character UUID; the 0.2.0 fix hashes such values with `uuid5` or omits them.](kb:ai-security.ai-guard.integrations:transaction-id-uuid). Running `python3 .codex/hooks/aiguard_utils.py` prints where `.env` was searched, the resolved settings (whether the API key is set, the cloud, the timeout and the policy ID) and, when the API key is set, the result of a live test scan; without a key it reports that the hooks will fail closed. [ai-security.ai-guard.integrations.codex:self-check] The README says the `hooks.json` commands are relative to the directory Codex is started in, so Codex must be launched from the project root that contains `.codex/`. [ai-security.ai-guard.integrations.codex:relative-commands] The README says the Codex feature flag is named `hooks`, stable and on by default in current versions; the 0.2.0 changelog corrected it from `codex_hooks`. [ai-security.ai-guard.integrations.codex:feature-flag] The README's `cp example.env .env` step names a file the codex-hooks directory does not ship at the pin. [ai-security.ai-guard.integrations.codex:example-env-missing]

**Verdicts and failures.** `scan_content` reports an error for a missing key, a missing SDK, an SDK error, a response without an action, or an exception, and `verdict_blocks` blocks on any error and on any action other than `ALLOW` or `DETECT`. [ai-security.ai-guard.integrations.codex:fail-closed] The prompt and pre-tool hooks block by exiting 2 with the reason on stderr; `scan_bash_response.py` prints `decision` block with the reason, which the README says replaces the tool result; `scan_mcp_response.py` prints `continue` false, halting the turn; both post-tool hooks exit 0. [ai-security.ai-guard.integrations.codex:block-mechanisms] `scan_stop_response.py` scans `last_assistant_message` with direction `OUT` after streaming; a blocking verdict prints `continue` false with the reason, but a scan error lets the turn finish (fail-open), and it does not scan when `stop_hook_active` is set or the message is under 5 characters. [ai-security.ai-guard.integrations.codex:stop-hook]

**What content is scanned.** Each of the six hook scripts (user input, Bash command, Bash response, MCP request, MCP response, stop response) truncates content to 20000 characters; tool input is the first non-empty of command, query, prompt, message, content, body and url, else the whole input as JSON; tool output is the first of output, stdout, content, text, result and data with at least 5 characters, else every string in it (up to 50, depth 6), else the raw JSON; Bash and MCP response output under 5 characters is not scanned. [ai-security.ai-guard.integrations.codex:content] An MCP call carrying any of the named input fields is scanned on that one field; its other arguments are sent to the MCP server unscanned. [ai-security.ai-guard.integrations.codex:mcp-partial-scan] The README understates the truncation [divergence:ai-security.ai-guard.integrations.codex:readme-truncation]. The comparison with other hosts is in [Zscaler's AI Guard integration examples (zguard-ai-integrations): the catalog, the promised fail-closed posture against what each example does, and where each intercepts](kb:ai-security.ai-guard.integrations).

What to check:
1. That Codex is launched from the project root holding .codex/ and the .env, and run the self-check before relying on the hooks.
2. Treat the Stop scan as after-the-fact: the reply is already displayed, and a scan error lets it through.
3. Whether file edits (apply_patch), WebSearch or other non-Bash, non-MCP tools need coverage; these hooks do not see them.
