# The AI Guard decorator for AWS Lambda handlers: prompt and response scanning at the function boundary, default extractors, and block shapes (ai-security.ai-guard.integrations.aws-lambda-decorator)
Also called: ai guard lambda; ai guard lambda decorator; aiguard_protect; aiguard_decorator.py; ai guard lambda 403; AIGuardBlocked lambda

The Lambda decorator guards the function boundary: it sees the event entering the handler and the result leaving it, and nothing the handler does in between. The decorator scans the extracted prompt before the handler body runs, so a blocked prompt never reaches the handler or its model, and scans the handler's returned text before Lambda returns it; model and tool calls inside the handler are not seen. [ai-security.ai-guard.integrations.aws-lambda-decorator:boundary]

**Finding the text.** The default extractors parse an API Gateway or ALB proxy body as JSON (base64-decoded when flagged; a flagged body that does not decode to UTF-8 is unscannable), fall back to the raw body when it is not JSON, and take the first non-empty string among `prompt`, `message`, `input`, `query`, `question`, `text` for the prompt and `response`, `completion`, `output`, `answer`, `reply`, `message`, `text` for the response. [ai-security.ai-guard.integrations.aws-lambda-decorator:default-extractors] A handler result with a `statusCode` of 400 or more is not scanned (the decorator treats it as the handler's own error path), and a custom extractor can return `SKIP` to pass a leg deliberately; otherwise an empty extraction follows `on_unscannable`, blocking by default. [ai-security.ai-guard.integrations.aws-lambda-decorator:error-results-skipped]

**What is sent.** The response scan sends the response text together with the prompt, and with any `context_from` grounding text and `code_response_from` text, joined into one `content` string with direction OUT; the prompt scan can likewise carry `code_prompt_from` text. [ai-security.ai-guard.integrations.aws-lambda-decorator:response-leg-content] The transaction ID is the Lambda request ID (`context.aws_request_id`), else a fresh uuid4, so a scan matches a CloudWatch request; a `session_id_from` value is written to the log line. [ai-security.ai-guard.integrations.aws-lambda-decorator:transaction-request-id] Content is sent as-is without truncation; if the API rejects an oversized payload the leg follows `on_error`, blocking by default. [ai-security.ai-guard.integrations.aws-lambda-decorator:no-truncation]

**Blocking.** By default an HTTP proxy event (recognized from envelope keys such as `httpMethod`, `routeKey`, `requestContext.http` or `requestContext.elb`, even without a body) gets a 403 JSON response naming the leg, severity, policy and detectors, and every other event raises `AIGuardBlocked`; the README's reason is that an asynchronous source treats a returned value as success and would delete the blocked message. An `on_block` callable replaces both. [ai-security.ai-guard.integrations.aws-lambda-decorator:block-shapes]

**Timeouts and degraded verdicts.** With no `timeout=` argument the scan timeout is `AIGUARD_TIMEOUT`, else 30 seconds, read once when the handler is decorated; the README sizes a Lambda timeout as handler time plus two scans. [ai-security.ai-guard.integrations.aws-lambda-decorator:timeout] Under `strict_verdict=True` the decorator treats an allow verdict that carries an `errorMsg` as a degraded scan and handles it per `on_error`. [ai-security.ai-guard.integrations.aws-lambda-decorator:strict-verdict-errormsg] The README describes a wider check [divergence:ai-security.ai-guard.integrations.aws-lambda-decorator:strict-verdict-scope]. Shared behavior is in [Zscaler's AWS AI Guard examples (Lambda decorator, boto3 Bedrock hook, AgentCore guard, Strands hooks): seats, the shared scan client, verdict and failure handling](kb:ai-security.ai-guard.integrations.aws).

What to check:
1. That prompt_from and response_from read the same fields the handler reads; the default extractors take the first non-empty string from a fixed key list.
2. For an asynchronous event source, that a block raises (the default) rather than returning a value, so Lambda's retry and dead-letter handling applies.
3. That the function timeout covers the handler plus two scans of up to the scan timeout each.

Sources disagree (name both sides):
- What strict_verdict treats as a degraded scan in the Lambda decorator. [divergence:ai-security.ai-guard.integrations.aws-lambda-decorator:strict-verdict-scope]
  - zguard-integrations: The README says strict_verdict rejects a verdict whose detection services report trouble: timeout or error flags, an error or timeout category, or a populated per-service errors array.
  - zguard-integrations: The code checks only whether an allow verdict carries errorMsg; its verdict parser keeps no timeout, error or errors field.
  Impact: A degraded scan that reports trouble only through per-detector fields passes as allow even under strict_verdict.
