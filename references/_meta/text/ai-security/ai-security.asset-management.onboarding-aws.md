# How AI Asset Management onboards AWS accounts and organizations: prerequisites, templates, CloudTrail, network and IAM roles (ai-security.asset-management.onboarding-aws)
Also called: AI Security AWS onboarding; AI Security CloudTrail details; AIS-CLOUDTRAIL-KMS-POLICY

Standalone AWS onboarding generates a template in both CloudFormation and Terraform format; the template, deployed on the orchestrator account, creates roles that give AI Security read-only permissions, and target accounts that must be monitored are added with their templates deployed. [ai-security.asset-management.onboarding-aws:standalone-workflow] The standalone page names the required role in two different ways [divergence:ai-security.asset-management.onboarding-aws:standalone-onboarding-role]. For standalone AWS accounts CloudTrail must be configured for management and data events so AI Security can run incremental scans on S3 buckets; for data events, select the Write checkbox for All current and future S3 buckets. [ai-security.asset-management.onboarding-aws:cloudtrail-prereq] The Azure and GCP counterparts are in [How is a Microsoft Azure tenant, management group or subscription onboarded to AI Security: roles, templates, network and error fixes?](kb:ai-security.asset-management.onboarding-azure) and [How AI Asset Management onboards GCP organizations: prerequisites, templates, service account, network, IAM roles and errors](kb:ai-security.asset-management.onboarding-gcp), and the product overview is in [AI Asset Management in the AI Security Admin Portal: what it inventories, signing in, first-time configuration order, table behavior](kb:ai-security.asset-management).

**Organization onboarding.** For an AWS organization, identify an orchestrator account and the target accounts (the monitoring scope), and hold an Administrator role or any role with Add Accounts permissions in the AI Security Admin Portal. [ai-security.asset-management.onboarding-aws:org-prereqs] Onboarding an AWS organization consists of: provide organization details, deploy the tree discovery template, select the network configuration, orchestrator account, monitoring scope and business unit, then deploy the orchestrator and monitoring scope templates. [ai-security.asset-management.onboarding-aws:org-workflow] Onboarding an AWS organization asks for a role name (added as a prefix to all roles created during onboarding), the 12-digit management account ID, an optional notification list of up to 30 email addresses, and an autopopulated optional External ID used in the IAM role trust policy. [ai-security.asset-management.onboarding-aws:org-details] For AWS organizations, CloudTrail must be configured for management and data events so AI Security can run incremental scans on S3 buckets, with the Write checkbox selected for All current and future S3 buckets. [ai-security.asset-management.onboarding-aws:org-cloudtrail-prereq]

**CloudFormation and Terraform prerequisites.** The CloudFormation path for an AWS organization needs the AWSCloudFormationStackSetAdministrationRole and AWSCloudFormationStackSetExecutionRole IAM roles in the orchestrator account, and the execution role on every target account, to deploy stacks and StackSets. [ai-security.asset-management.onboarding-aws:cfn-roles] For an AWS organization with the CloudFormation template, each AWS region needs at least two default subnets in the default VPCs; AI Security creates subnets to launch AWS cloud resources in specific subnets. [ai-security.asset-management.onboarding-aws:cfn-subnets] With the Terraform template for an AWS organization, install Terraform CLI and AWS CLI 2.22 or later, and identify storage in the orchestrator account's primary region for Terraform state, for example an S3 bucket and a DynamoDB table whose partition key is LockID. [ai-security.asset-management.onboarding-aws:terraform-prereqs]

**Templates.** During initial onboarding AI Security looks for log files at prefix/<organization ID>/<management account ID> for an Organization CloudTrail and prefix/<management account ID> for an Account CloudTrail; after onboarding it checks each target account. If the CloudTrail is part of AWS Control Tower, the organization ID is entered as prefix. [ai-security.asset-management.onboarding-aws:cloudtrail-type-and-paths] If the CloudTrail S3 bucket is in the management account AI Security generates only the tree discovery template (deployed in the AWS root account); if it is in another account it generates both a CloudTrail template, deployed in the account holding the bucket, and the tree discovery template. [ai-security.asset-management.onboarding-aws:cloudtrail-bucket-account-templates] The tree discovery template includes the policies and permissions to create IAM roles in the AWS root account plus the CloudTrail details for incremental data scans; the IAM roles give AI Security read-only access to discover resources in the AWS organization. Validation runs every hour and can be triggered with Validate. [ai-security.asset-management.onboarding-aws:tree-discovery-template-contents] When deploying the AWS orchestrator template the primary region of the orchestrator is selected first, followed by other regions, and the pages state that AI Security supports "all the 29 global regions that are supported by AWS". [ai-security.asset-management.onboarding-aws:orchestrator-regions] In the organization orchestrator Terraform deployment, terraform apply is run with -var=‘enable_test_connectivity=true’ to deploy with network analysis enabled and with enable_test_connectivity=false to deploy with it disabled. [ai-security.asset-management.onboarding-aws:orchestrator-terraform-network-analysis] The evidence template is available only if an S3 bucket to store evidence data is configured; it is deployed in the orchestrator account for a Zscaler Managed S3 Bucket and in the account holding the bucket for a Custom S3 Bucket (organization page). [ai-security.asset-management.onboarding-aws:evidence-template]

**Monitoring scope template.** The organization monitoring scope StackSet is created with Service managed permissions, Deploy to organization, and Automatic deployment Activated so stack instances deploy for new accounts added to the OU; Account removal behavior Delete stacks removes instances when an account leaves the OU. The StackSet name must be unique and friendly because it is needed to add target accounts after onboarding. [ai-security.asset-management.onboarding-aws:monitoring-scope-stackset-settings] After the orchestrator and monitoring scope templates are deployed, resources created in the AWS orchestrator account include an auto scaling group for the orchestrator instance, a NAT gateway that prevents inbound connectivity from the public internet to orchestrator or scanner instances, an SQS queue for scan requests from AI Security, and an Event bridge rule forwarding CloudTrail data events to the orchestrator account. [ai-security.asset-management.onboarding-aws:orchestrator-account-resources] AI Security validates the AWS orchestrator and monitoring scope template deployment every hour by checking roles and permissions; a deployment issue shows an error, and Validate verifies whether the template is deployed. [ai-security.asset-management.onboarding-aws:template-validation-hourly] A conflicting S3 bucket error during orchestrator StackSet creation (organization page) is addressed by deleting the existing bucket and retrying; before creating a StackSet for a new orchestrator account the old orchestrator account's infrastructure must be deleted to avoid conflicts. [ai-security.asset-management.onboarding-aws:stackset-conflicting-bucket]

**CloudTrail.** CloudTrail events can be recorded by Event History (last 90 days, single account), CloudTrail Lake or Trails; AI Security uses trails to analyze logs and perform incremental scans on S3 buckets. [ai-security.asset-management.onboarding-aws:cloudtrail-use] A trail created through an organization is created in each member account, with events delivered to the S3 bucket, which allows logs from multiple accounts and regions to be aggregated into a single bucket. [ai-security.asset-management.onboarding-aws:cloudtrail-org] Resetting an organization's AWS CloudTrail details disables the existing CloudTrail and moves all onboarded accounts to Needs Attention until the new CloudTrail validates; updating a single account's CloudTrail disables it only for that account. [ai-security.asset-management.onboarding-aws:cloudtrail-change-org-effect] After changing the organization CloudTrail, Validate on the Overview tab sets the CloudTrail status to Enabled on success and to Failed if validation finds an issue, in which case the template is downloaded and run again before validating again. [ai-security.asset-management.onboarding-aws:cloudtrail-change-validation-status] Changing CloudTrail needs the Administrator role or any role with Edit Cloud Accounts permission; a cross-account CloudTrail whose S3 bucket is in a different account than the onboarded member account needs three settings: CloudTrail Permissions for Member Accounts, Cross-Account Log Decryption and KMS Key ID. [ai-security.asset-management.onboarding-aws:cloudtrail-change-permission-crossaccount] For KMS-encrypted cross-account CloudTrail, the resource discovery role created by AI Security carries an AIS-CLOUDTRAIL-KMS-POLICY, edited in the account holding the S3 bucket to add the S3 bucket account ID where the KMS key is present. [ai-security.asset-management.onboarding-aws:cloudtrail-kms-policy]

**Changing scope and orchestrator.** New AWS accounts can be added to the monitoring scope but existing target accounts cannot be removed; autodetection can be enabled at organization or OU level, and automatic deployment must be activated in AWS for stack instances to deploy to newly added accounts. Needs the Administrator role or any role with Configure Monitoring Scope permission. [ai-security.asset-management.onboarding-aws:monitoring-scope-add-only] The AWS monitoring scope CloudFormation download is a ZIP holding a CSV of target accounts to scan and a YAML with the policies and permissions to connect to the AWS organization; the Terraform download holds a CSV, multiple Terraform files and a README. [ai-security.asset-management.onboarding-aws:monitoring-scope-template-zip] Before running the template on a new AWS orchestrator account, the template previously deployed on the existing orchestrator account must be purged, by deleting the corresponding stackset or running terraform destroy depending on template type; the orchestrator account can be changed if the old one is being decommissioned, deleted, or was selected incorrectly, and the existing orchestrator account checkbox is disabled. [ai-security.asset-management.onboarding-aws:orchestrator-change-purge]

**Custom network.** A custom AWS network needs a Control Plane VPC created only in the primary region where the orchestrator runs and a Worker Plane VPC in every region where the resources exist, both in the orchestrator account, with non-overlapping CIDR ranges. [ai-security.asset-management.onboarding-aws:network-vpc-topology] In the manual AWS worker plane VPC procedure, at least 2 Availability Zones and 2 public and 2 private subnets are selected and at least 50 IPs must be available in the private subnet. [ai-security.asset-management.onboarding-aws:network-worker-sizing] A DB subnet group is required for AI Security to scan RDS databases; it uses the worker plane VPC with at least two AZs and their private subnets and is created in each target region. [ai-security.asset-management.onboarding-aws:network-db-subnet-group] The control plane security group has no inbound rules; the worker plane security group allows inbound HTTPS from the control plane VPC and PostgreSQL and MYSQL/Aurora from the worker plane VPC. [ai-security.asset-management.onboarding-aws:network-security-groups] The control plane and worker plane VPCs must be peered (manual and template-based configurations alike); a new peering connection is in the Pending acceptance state until accepted, and route tables on both VPCs must be updated. [ai-security.asset-management.onboarding-aws:network-vpc-peering] The AWS network CloudFormation download is a ZIP with two YAML files (aws_control_plane_network_components_cft.yml and aws_worker_plane_network_components_cft.yml); the Terraform download is a ZIP with a worker-plane and a control-plane folder. [ai-security.asset-management.onboarding-aws:network-templates]

**IAM roles and conditions.** The AWS templates create a Resource Discovery Role, an Orchestrator Instance Profile Role (used by the orchestrator instance in the primary region to organize data scanning), a Scanner Instance Profile Role, a Target Role created in target accounts, a Put Evidence role (stores evidence snippets in the specified S3 bucket) and a Get Evidence role (retrieves them). [ai-security.asset-management.onboarding-aws:iam-role-list] The AWS resource discovery role is required to discover resources in the onboarded accounts and collect CloudTrail logs; its permissions table lists Deny for s3:GetObject, dynamodb:BatchGetItem, dynamodb:GetItem, dynamodb:Query and dynamodb:Scan on Monitored Accounts. [ai-security.asset-management.onboarding-aws:iam-resource-discovery-deny] If AWS Bedrock resources are encrypted with KMS keys, AI Security fails to collect their metadata unless kms:Decrypt and kms:GenerateDataKey are explicitly added to the resource discovery role (via the AIS-BASIC-CUSTOM-POLICY). [ai-security.asset-management.onboarding-aws:iam-bedrock-kms] The orchestrator instance profile role's ec2:CreateNetworkInsightsPath permission and its tiros:CreateQuery permission are conditional and only required if Custom Network is used; the target role's secretsmanager:GetSecretValue is conditional and only required if Custom Network is used with Unmanaged DB Scanning. [ai-security.asset-management.onboarding-aws:iam-custom-network-conditional] The orchestrator instance profile role's rds:DeleteDBInstance permission is Allow scoped to only resources created by AI Security (based on tags), to delete the RDS database instance created for scanning. [ai-security.asset-management.onboarding-aws:iam-tag-scoped-delete] The Put Evidence role's s3:PutObject and the Get Evidence role's s3:GetObject are Allow on the Evidence Bucket only. [ai-security.asset-management.onboarding-aws:iam-evidence-roles-scope]

**Condition keys and operators.** Among the condition operators AI Security supports are StringNotEqualsIgnoreCaseIfExists, StringLikeIfExists, ArnNotLikeIfExists and Boolean, and it supports the NotPrincipal element; it does not support Numeric, Date, IP Address or Binary operators. [ai-security.asset-management.onboarding-aws:iam-operators] Supported principal-based condition keys include aws:PrincipalTag/tag-key, aws:PrincipalOrgID, aws:PrincipalArn, aws:PrincipalAccount and aws:PrincipalIsAWSService. [ai-security.asset-management.onboarding-aws:iam-keys-principal-a] Supported principal-based condition keys also include aws:PrincipalServiceName, aws:PrincipalServiceNamesList, aws:PrincipalType, aws:userid and aws:username. [ai-security.asset-management.onboarding-aws:iam-keys-principal-b] Supported resource-based condition keys are aws:ResourceTag/tag-key, aws:ResourceAccount and aws:ResourceOrgID. [ai-security.asset-management.onboarding-aws:iam-keys-resource] Unsupported condition keys include aws:PrincipalOrgPaths, aws:ResourceOrgPaths, network and request context keys such as aws:SourceIp and aws:CurrentTime, and advanced keys such as aws:CalledVia and aws:MultiFactorAuthPresent; when a key is not supported, evaluation of the condition is skipped. [ai-security.asset-management.onboarding-aws:iam-unsupported-keys]

What to check:
1. Whether the CloudTrail S3 bucket is in the management account, which decides whether one or two templates are generated.
2. Whether a CloudTrail change is for the organization or a single account: resetting the organization's details moves all onboarded accounts to Needs Attention.
3. That existing target accounts cannot be removed from the AWS monitoring scope, only added.

Sources disagree (name both sides):
- The standalone AWS account onboarding page states the required role twice: Administrator only in the prerequisites, and Administrator or any role with Add Accounts permissions further down. [divergence:ai-security.asset-management.onboarding-aws:standalone-onboarding-role]
  - zscaler-help: An Administrator role is required to onboard the AWS account.
  - zscaler-help: Either an Administrator role or any role with Add Accounts permissions is sufficient.
  Impact: Whether a non-Administrator role with Add Accounts permissions can onboard a standalone account cannot be read from the page; the organization page states only the second form.
