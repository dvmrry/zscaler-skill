# GitHub Actions policy validation for AI Guard (Zscaler example): a CI gate that tests a policy with sample prompts, not runtime interception (ai-security.ai-guard.integrations.github-actions)
Also called: aiguard github actions; scan_policy.py; test-prompts.yaml; aiguard ci gate; model-security-scan.yml

Zscaler's GitHub Actions example tests an AI Guard policy in CI before an AI application is deployed. It inspects no live traffic.

**What it does.** In the GitHub Actions example, `scan_policy.py` sends a suite of test prompts and responses to AI Guard and checks that the policy returns the expected `ALLOW`, `BLOCK` or `DETECT`, exiting non-zero to stop a deployment when a case fails. [ai-security.ai-guard.integrations.github-actions:purpose] The example sits in no request path: it scans only the test cases in its config file, so a passing run says nothing about live traffic. [ai-security.ai-guard.integrations.github-actions:not-inline] Each case in the test-prompts file gives `content`, a `direction` (default `IN`), an `expected_action` (default `ALLOW`, a string or a list of acceptable actions, overridden by `expected_actions`) and an optional `optional` flag; a case with empty content is skipped. [ai-security.ai-guard.integrations.github-actions:test-cases] The policy testing AI Guard itself offers is in [Policy Testing, available once an LLM provider, its credentials and a policy exist, sends a prompt through a chosen provider credential, policy and LLM model and shows what was allowed or blocked together with the prompt and response without guardrails.](kb:ai-security.ai-guard.policies:testing).

**Pass and fail.** A case fails when its scan errors, including a response without an action, which the scanner records as `BLOCK` with an error, even when the case is optional; otherwise a mismatch fails a required case and only warns for an optional one; the script exits 1 when any case failed. [ai-security.ai-guard.integrations.github-actions:pass-fail] Setting `settings.scan_enabled` false in the test file makes the scanner print that the scan is disabled and exit 0 without calling AI Guard; a missing `AIGUARD_API_KEY` exits 1. [ai-security.ai-guard.integrations.github-actions:scan-disabled] The shipped suite's ALLOW cases for benign text are marked optional, and its required toxicity case accepts either `BLOCK` or `DETECT`. [ai-security.ai-guard.integrations.github-actions:shipped-suite] Because required cases accept `DETECT`, a policy whose detectors only monitor passes the gate, and because benign cases are optional, a policy that blocks everything passes it too: the shipped suite checks that detections happen, not that content is blocked. [ai-security.ai-guard.integrations.github-actions:detect-passes-gate]

**Configuration and triggers.** The scanner loads a `.env` with python-dotenv, treats a blank `AIGUARD_CLOUD` as `us1`, defaults `AIGUARD_TIMEOUT` to 30, calls `execute_policy` when `AIGUARD_POLICY_ID` parses as an integer and `resolve_and_execute_policy` otherwise, and waits 0.5 seconds between cases by default (`--delay`). [ai-security.ai-guard.integrations.github-actions:config] The workflow runs on pushes and pull requests to main that touch the test config, model config, workflow, scripts or requirements, and on manual dispatch; the scan job runs when such a change is detected or on dispatch, and the Vertex AI deploy job needs the scan job and runs only when the repository variable `ENABLE_VERTEX_DEPLOY` is true on a main push or dispatch. [ai-security.ai-guard.integrations.github-actions:workflow] The endpoints are in [Calling AI Guard at runtime: the proxy endpoint, the DAS detection API, its host, direction and policy ID, and throttling in the Python SDK](kb:ai-security.ai-guard.runtime-api).

What to check:
1. Remove optional from the cases that matter and decide whether DETECT should pass; the shipped suite passes monitor-only and block-everything policies.
2. That settings.scan_enabled is not false in the test file, which turns the gate into a pass.
