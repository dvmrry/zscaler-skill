# The inline Apigee X proxy for Vertex AI with AI Guard: the policy flow, what it extracts, when it blocks, and what passes unscanned (ai-security.ai-guard.integrations.google-apigee-proxy)
Also called: ai guard apigee; ai guard apigee inline proxy; vertex-aiguard; ai guard vertex ai; aiguard-config kvm; x-aiguard-blocked

The inline proxy is a single Apigee X bundle that fronts Vertex AI generateContent and carries its scanning policies itself; the reusable variant is [The ZSCALER-AIGUARD Apigee SharedFlow: dialects, what each leg scans, MCP tool calls, verdict handling, and the traffic it lets through unscanned](kb:ai-security.ai-guard.integrations.google-apigee-sharedflow). The proxy listens on base path `/vertex` and targets Vertex AI `generateContent` in `us-central1` for the KVM's project and model; its request PreFlow scans the prompt (direction IN) and its response PostFlow scans the answer (direction OUT), each with a ServiceCallout to AI Guard. [ai-security.ai-guard.integrations.google-apigee-proxy:flow]

**Configuration.** Configuration comes from the environment-scoped encrypted KVM `aiguard-config`: `aiguard_api_key`, `aiguard_cloud`, `aiguard_policy_id` (optional), `vertex_project` and `vertex_model`, cached for 300 seconds. [ai-security.ai-guard.integrations.google-apigee-proxy:kvm] Each leg calls `https://api.{cloud}.zseclipse.net/v1/detection/resolve-and-execute-policy` when no policy ID is configured and `/v1/detection/execute-policy` when one is, with the key as a Bearer token; the prompt callout times out after 5000 ms and the response callout after 6000 ms. [ai-security.ai-guard.integrations.google-apigee-proxy:endpoint] The policy ID comes only from the KVM and is converted with parseInt; a caller cannot choose a policy per request (an earlier revision honoured an `X-AIGuard-Policy` header). [ai-security.ai-guard.integrations.google-apigee-proxy:policy-id-from-kvm] The example's architecture note says resolve-and-execute-policy ignores a `policyId` in the body without an error and applies the key's own policy, which is why a pinned ID is routed to execute-policy instead. [ai-security.ai-guard.integrations.google-apigee-proxy:resolve-ignores-policy-id]

**What is scanned.** The prompt script concatenates the text of every part of every `contents` entry, of any role, with no separator; the raw body is scanned only when parsing or walking it throws (as for a body that does not parse), and when nothing is extracted it marks the prompt absent, which skips the scan and block steps. [ai-security.ai-guard.integrations.google-apigee-proxy:prompt-extraction] A request body that parses as JSON but has no Gemini text parts (an OpenAI-, Anthropic- or MCP-shaped body, image-only parts, or only a `systemInstruction`) is forwarded to Vertex without a prompt scan. [ai-security.ai-guard.integrations.google-apigee-proxy:no-text-passes] The README says other dialects are scanned raw [divergence:ai-security.ai-guard.integrations.google-apigee-proxy:non-gemini-bodies]. The response leg runs only for a 2xx response from the Vertex target and scans the concatenated text of every candidate's parts; a response with no text parts skips the scan and block steps. [ai-security.ai-guard.integrations.google-apigee-proxy:response-extraction] The scan request body holds `content`, `direction`, `policyId` when a policy ID is set in the KVM, and `user` when the `aiguardUser` flow variable is set (on both the prompt and the response scan); the session ID the script reads from `X-Session-ID` is stored in a flow variable and not sent. [ai-security.ai-guard.integrations.google-apigee-proxy:scan-body] Because the proxy sends no `transactionId`, the transaction ID it returns in its block headers and body is the one AI Guard put in the verdict, not one the gateway chose. [ai-security.ai-guard.integrations.google-apigee-proxy:api-transaction-id] The proxy handles synchronous generateContent only: `streamGenerateContent`, tool calls and other dialects are left to the SharedFlow, and block messages carry no detector names. [ai-security.ai-guard.integrations.google-apigee-proxy:no-streaming]

**Verdicts and failures.** On both legs the proxy blocks unless the scan callout returned HTTP 200 and the action is ALLOW or DETECT, so BLOCK, any other action, a 200 without an action and a non-200 all block. [ai-security.ai-guard.integrations.google-apigee-proxy:block-rule] A block returns HTTP 403 with headers `x-aiguard-blocked`, `x-aiguard-severity` and `x-aiguard-transaction-id` and a JSON body giving the direction, action, severity, policy, transaction ID and the API's in-body `statusCode` and `errorMsg` as `scan_status` and `scan_detail`. [ai-security.ai-guard.integrations.google-apigee-proxy:block-body] With no API key in the KVM the proxy answers HTTP 500 `ZSCALER AI GUARD: NOT CONFIGURED` before any scan and does not proxy the request. [ai-security.ai-guard.integrations.google-apigee-proxy:config-error] A scan callout that times out or cannot connect faults the flow, so on the request leg Vertex is never called. [ai-security.ai-guard.integrations.google-apigee-proxy:timeout-faults]

**Cost.** Two synchronous scans sit on the critical path of each request, which the README estimates at roughly 100 to 300 ms each. [ai-security.ai-guard.integrations.google-apigee-proxy:latency]

What to check:
1. That callers send Gemini-shaped bodies with text parts; a JSON body with no contents text, or only system instructions or images, is forwarded to Vertex unscanned.
2. Whether aiguard_policy_id is set in the aiguard-config KVM; a stale ID blocks every request with scan_detail "Policy not found", and a KVM change takes up to 300 s to apply.

Sources disagree (name both sides):
- What the inline proxy does with request bodies that are not in the Gemini dialect. [divergence:ai-security.ai-guard.integrations.google-apigee-proxy:non-gemini-bodies]
  - zguard-integrations: The README's Limitations say OpenAI, Anthropic and MCP request shapes fall back to scanning the raw body.
  - zguard-integrations: The extraction script falls back to the raw body only when JSON.parse throws; valid JSON without contents yields an empty prompt and the scan is skipped.
  Impact: Those request shapes are JSON, so they are forwarded unscanned rather than scanned raw (no-text-passes); the architecture note's own wording, raw fallback only for a body that will not parse, matches the code.
