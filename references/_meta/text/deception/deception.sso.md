# Deception and ITDR single sign-on and authentication settings: Authentication Service, SAML and OpenID identity providers, password login, OTP and support access (deception.sso)
Also called: ITDR SSO; ITDR SAML; ITDR OpenID; ITDR identity providers; ITDR authentication settings; Deception SSO; Deception SAML; Deception identity providers; IdP Providers; Authentication Service; Disable password login; Support Access Settings

The product hubs are [Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview) and [Identity Protection (ITDR): how it reads identity stores and endpoints, what it needs, and what can be automated](kb:identity-protection.overview). Zscaler recommends using Authentication Service to configure primary and secondary external identity providers; Authentication Service supports SAML and OpenID configurations, and a subscription is arranged through Zscaler Support. The Deception and ITDR IdP pages say this alike (ITDR names it the Authentication Service Admin Portal). [deception.sso:auth-service-recommended] When Authentication Service is enabled, SSO with third-party IdPs cannot be configured in the Deception (or ITDR) admin portal and must be configured in the Zscaler Admin Console (Deception page) or the Authentication Service Admin Portal (ITDR page); the existing SSO third-party IdPs are disabled. [deception.sso:auth-service-locks-portal-idps]

**Identity providers page.** The IdP Providers page lists each configured IdP with its Name, Type, Issuer (the URL of the IdP issuer) and Enabled status. [deception.sso:idp-page-columns] The Okta SAML page names a different path to the SSO page than the other pages [divergence:deception.sso:okta-sso-path].

**SAML.** In the SAML Provider Details window, Encryption lets the IdP send the SAML assertion encrypted and is to be enabled only if the IdP supports encryption; Sign GET Request lets the portal send a signed SAML request and is to be enabled only if the IdP supports signed requests; Use Dedicated Certificate has the portal create a long-lived self-signed certificate for the SAML provider instead of the portal's certificate. [deception.sso:saml-provider-toggles] The admin portal uses a Let's Encrypt certificate with a 90-day expiration period, and Zscaler recommends enabling Use Dedicated Certificate to generate a long-lived certificate dedicated to SAML authentication. [deception.sso:saml-lets-encrypt-90-day] In the SAML Provider Details window, the Setup Instructions section shows the Service Provider Entity ID and Service Provider Assertion URL and offers the encryption certificate and an XML file for download (the ITDR page says Copy for the first two). [deception.sso:saml-setup-instructions] The ITDR SAML page says the ITDR Admin Portal supports configuring SAML for Okta and Microsoft Entra ID, and the ITDR OpenID page says it supports configuring SAML for Okta and Google. [deception.sso:itdr-saml-supported-idps]

**Group-based SAML login.** With group-based SAML login, Deception and ITDR create new users and assign them a role if their SAML responses contain one or more predefined group attributes; group mapping is cumulative, so a user in several groups gets the roles of each matching group. [deception.sso:saml-group-mapping-cumulative] The Group-Based SAML Login section has Auto Create User (automatically creates users in the specified groups), SAML Response Group Attribute and SAML Response Name Attribute (attribute names that depend on the identity provider), plus a list of group names each mapped to one or more roles. [deception.sso:saml-group-fields] While configuring group-based SAML login, a user who is not in any group has their roles revoked and can be locked out during authentication; the page says to keep a second super-admin account that uses a username and password and not to use SAML on it until testing is done. [deception.sso:saml-group-lockout] A user created through SAML group-based login has username-and-password login disabled by default; a user with no matching group has no roles and cannot log in; roles are updated on every SAML sign-in, whether the user was created manually or by group-based login. [deception.sso:saml-group-user-lifecycle]

**Okta SAML.** In the Okta SAML app, Name ID format is EmailAddress; the Single sign on URL entered at creation is https://<instance name>/saml/id/1/assert (the ITDR page labels it Single sign-on URL), and it and the Audience URI are placeholder values that must be changed later to the service provider assertion URL and entity ID obtained from the portal. [deception.sso:okta-saml-app-values] For Okta SAML, Assertion Encryption is set to Encrypted and the encryption certificate downloaded from the admin portal is uploaded to Okta. [deception.sso:okta-saml-assertion-encryption] For Okta SAML group provisioning, the Okta attribute statement FullName uses the value String.join(" ", user.firstName, user.lastName) and the group attribute statement Group uses the filter Matches regex .*; in the portal, SAML Response Group Attribute is entered as Group and SAML Response Name Attribute as FullName. [deception.sso:okta-saml-group-attributes] On the Okta SAML page, if the group attribute is not part of the SAML assertion or does not match a group configured in the portal, all roles mapped to the user are removed, which can lock the user out; the page advises testing with a separate user and contacting Zscaler Support if locked out. [deception.sso:okta-saml-group-lockout]

**Azure AD and Microsoft Entra ID SAML.** Azure AD SAML (Microsoft Entra ID in the ITDR page) needs access to the Azure service with a privileged role, preferably Global Administrator; the guide lists *.azure.com and *.illusionblack.com and says to remove any proxy restrictions on these URLs. [deception.sso:azure-saml-prereqs] For an Azure AD SAML provider (Microsoft Entra ID in the ITDR page), the guide says to unselect Encryption and Sign Get Request and select Use Dedicated Certificate; the Azure metadata XML file is downloaded from the URL in App Federation Metadata Url. [deception.sso:azure-saml-provider-settings] The User Principal Name of the user in the Azure portal must match the Email field of the user created in the admin portal. [deception.sso:azure-saml-upn-email] For Azure SAML group provisioning, the group claim returns Groups assigned to the application with Group ID as the source attribute; the portal's SAML Response Group Attribute is the claim name of user.groups [All], the Name Attribute is the claim name of user.givenname, and each group name is the group's Object Id. [deception.sso:azure-saml-group-claims]

**ADFS SAML.** For ADFS SAML, the Federation Metadata XML file is downloaded from https://<ADFS hostname>/FederationMetadata/2007-06/FederationMetadata.xml on the ADFS server; the Relying Party Trust is added as Claims aware, importing a Metadata XML file downloaded from the portal, and Permit everyone is selected. [deception.sso:adfs-saml-trust] The ADFS claim rules include a rule named User Principal Name mapping the LDAP attribute User-Principal-Name to the E-Mail Address outgoing claim type, and a rule named Email that takes incoming claim type E-Mail Address and outputs outgoing claim type Name ID with outgoing name ID format Email, passing through all claim values. [deception.sso:adfs-saml-claim-rules] For optional ADFS group provisioning, a Send Group Membership as Claim rule uses outgoing claim type Group, and a further rule maps the LDAP attribute Given-Name to the Name outgoing claim type. [deception.sso:adfs-saml-group-rules]

**OpenID.** An OpenID provider needs the IdP's Client ID, Client Secret, Issuer, Authorization Endpoint, Token Endpoint and JWKS URI. [deception.sso:openid-provider-fields] Use Proxy Settings is enabled if the admin portal requires a proxy to reach the OpenID SSO servers, and is optional for a SaaS-hosted deployment. [deception.sso:openid-proxy-setting] For OpenID with Okta, the Okta application type is Web Application with sign-in redirect URI https://<instance>/oauth; after entering https://<Okta instance>.okta.com/.well-known/openid-configuration in the browser, the authorization_endpoint, token_endpoint and jwks_uri values are copied from the configuration file. [deception.sso:openid-okta] For OpenID with Google, after entering https://accounts.google.com/.well-known/openid-configuration in the browser, the authorization_endpoint, token_endpoint and jwks_uri values are copied from the configuration file. [deception.sso:openid-google] The ITDR page for OpenID for Google says to make sure to configure Google OAuth 2.0 before configuring OpenID for Google. [deception.sso:itdr-google-oauth-prereq]

**Authentication settings.** With SSO enabled, local-credential login to the admin portal can be turned off by selecting Disable password login; at least one SSO feature should be configured and tested first, and afterwards local username and password cannot be used to log in. Changes to these settings apply to all users. [deception.sso:disable-password-login] The password expiration period is 90 days by default and can be changed for all users; it counts from the day each account was created, and users older than the period are prompted to reset their passwords. [deception.sso:password-expiration] Each user must configure 2FA with an authenticator app when signing in for the first time; each OTP is valid for a 30-second window, and by default OTPs from the previous and next two windows are accepted to accommodate possible clock skew. [deception.sso:otp-window] When OTP errors occur because of clock skew, the number of windows can be increased; Zscaler recommends not modifying the default OTP duration, and if needed increasing the window number by 1 until the clock skew problem is resolved. [deception.sso:otp-window-tuning] Support users can be blocked from the admin portal with Disable Support Access under Support Access Settings; this might delay assistance, and Zscaler Support might ask for access to be re-enabled when a help ticket is submitted. [deception.sso:support-access] Whether the ITDR wording differences are behavior differences is open [gap:deception.sso:itdr-copy-drift].

What to check:
1. Whether Authentication Service is enabled, since then third-party IdPs are configured in the Zscaler Admin Console (Deception page) or the Authentication Service Admin Portal (ITDR page), not in the admin portal.
2. Whether at least one SSO feature has been configured and tested before Disable password login is selected.
3. Whether a second super-admin account with username and password exists before group-based SAML login is tested.
4. Which path to the SSO page the answer cites, since the Okta SAML page and the IdP Providers page differ.

Sources disagree (name both sides):
- The Deception Okta SAML page sends the reader to Settings > User & Roles > SSO; the Deception IdP page names the IdP Providers page at Settings > Users & Roles > IdP Providers. [divergence:deception.sso:okta-sso-path]
  - zscaler-help: Group provisioning for Okta SAML starts at Settings > User & Roles > SSO.
  - zscaler-help: The IdP Providers page, where SAML and OpenID IdPs are managed, is at Settings > Users & Roles > IdP Providers.
  - zscaler-help: The SAML single sign-on configuration page starts at Settings > User & Roles > IdP Providers.
  Impact: An answer giving the console path to a SAML configuration cites one path or the other; the Deception pages do not say whether SSO is a separate page or an older name for IdP Providers. The ITDR release note dated August 18, 2025 records Settings > User & Roles > SSO being renamed IdP Providers in ITDR ([[identity-protection.release-notes:2025-08-18-tab-renames]]); no captured Deception page records the rename, though the Deception SAML configuration page already uses IdP Providers.

Not known (open gaps):
