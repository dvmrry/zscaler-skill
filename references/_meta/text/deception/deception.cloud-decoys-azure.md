# Azure Cloud Deception: setup, deployment-script resources, logging, decoy types and lures (deception.cloud-decoys-azure)

Azure setup requires a Microsoft Azure account with a valid subscription, an Azure user with Cloud Device Administrator and Global Administrator roles to run the deployment script, the Restrict access to Azure AD administration portal option enabled under User settings (to restrict decoy users from the administrator portal), and Microsoft.Web and Microsoft.Insights registered as resource providers in the subscriptions. [deception.cloud-decoys-azure:prerequisites] The required roles are worded differently across pages [divergence:deception.cloud-decoys-azure:azure-admin-roles]. Cloud Deception for Azure is set up and managed separately per combination of Tenant ID and Subscription ID, so several accounts can share a Tenant ID with different Subscription IDs. [deception.cloud-decoys-azure:account-key] Azure Terraform-based deployment downloads a ZIP containing azure-decoys.tf.json, the admin adds back-end details to its backend block, and `terraform output -json decoys_output > deployment-output.json` produces the JSON file whose upload updates the status in the Admin Portal. [deception.cloud-decoys-azure:terraform-package] The shared model is [Cloud Deception model shared by Azure, AWS and GCP: detection, deployment, status and deletion](kb:deception.cloud-decoys); the other providers are [AWS Cloud Deception: setup, tags, logging resources, decoy types and lures](kb:deception.cloud-decoys-aws) and [GCP Cloud Deception: setup, log permissions, decoy types and lures](kb:deception.cloud-decoys-gcp); plan decoy totals are in [Deception Standard and Advanced plans: decoy counts, Gen AI decoys, orchestration and API access](kb:deception.plans) and the product is introduced in [Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview).

**Obtaining the deployment script.** For Cloud Shell-based deployment, the Azure deployment script, which propagates changes and syncs settings between Deception and Azure, is obtained either as a PowerShell command that downloads and runs it in Azure Cloud Shell, or as a PSM1 file uploaded to Azure Cloud Shell and run with a PowerShell command from the Admin Portal. [deception.cloud-decoys-azure:deployment-script-methods]

**Deployment script resources.** The Azure deployment script creates a Management Resource Group (holding the function app, logging storage account, app service plan and other management resources) and a Decoy Resource Group in which all decoys are created, whose prefix string is specified during setup. [deception.cloud-decoys-azure:management-resources] For Azure decoys the deployment script enables diagnostic settings that push diagnostic logs to a Logging Storage Account, and the Admin Portal polls logs from the logging resources every 3 minutes to generate events. [deception.cloud-decoys-azure:log-collection] The Client ID and Client Secret created by the Azure deployment script are a service principal with access to poll log files from the logging storage account. [deception.cloud-decoys-azure:log-service-principal] The Decoy Access Role has full access to the Decoy Resource Group and is associated with the user and service principal decoys created in the Admin Portal. [deception.cloud-decoys-azure:decoy-access-role] The Azure Decoy Health Check Function App is triggered every 15 minutes from the Admin Portal to check whether deployed decoys exist in Azure and does not check the actual health of the deployed Azure resources. [deception.cloud-decoys-azure:health-check-scope] The health check is described two ways [divergence:deception.cloud-decoys-azure:azure-health-check-meaning]. The Azure deployment script creates a user decoy as an Azure AD (Entra ID) user with the Decoy Access Role and diagnostic setting for logging, a service principal decoy (Client ID and Client Secret) with the Decoy Access Role and diagnostic setting, and a managed identity decoy as a user-assigned managed identity with the Decoy Access Role. [deception.cloud-decoys-azure:workflow-identities] The deployment script builds an app service decoy as a web app with a managed identity holding the Contributor and Website Contributor roles, a storage account file share decoy with the TransactionOptimized access tier, and a container registry decoy as an empty container registry. [deception.cloud-decoys-azure:workflow-resources] The key vault decoy workflow adds passwords or keys of the created user or service principal decoys as decoy datasets; the ARM template decoy workflow creates a deployment template that deploys no actual resources but creates an entry in the template deployment history. [deception.cloud-decoys-azure:workflow-key-vault-arm] For an Azure VM image decoy the script deploys a Standard VM instance to create the snapshot, the instance persists for 5 minutes and is terminated after the snapshot is built, and public VM image decoys also get a shareable link for use as a landmine lure. [deception.cloud-decoys-azure:vm-image-workflow]

**Identity decoys.** An Azure user decoy is an Azure AD (Entra ID) user used to detect sign-in attempts with its credentials; it has access to all other Azure decoys in the Decoys Resource Group, and the name typically has the form <username>@<domainname> with lure names such as admin, administrator, cloud-admin and db-admin recommended. [deception.cloud-decoys-azure:user-decoy] For Azure user decoys the Entra ID diagnostic setting selects SignInLogs and NonInteractiveUserSignInLogs and archiving them to the integration's logging storage account; this configuration is not handled via the deployment script, as enabling diagnostic settings via API requires a P1 or P2 subscription. [deception.cloud-decoys-azure:entra-diagnostics-manual] A service principal decoy carries credentials, any sign-in attempt with them is detected as an attack or compromise, it has access to all other Azure decoys in the Decoys Resource Group, and a Client ID is associated with it automatically. [deception.cloud-decoys-azure:service-principal-decoy] For Azure service principal decoys the Entra ID diagnostic setting selects ServicePrincipalSignInLogs to send logs to the integration's logging storage account; this configuration is not handled via the deployment script, as enabling diagnostic settings via API requires a P1 or P2 subscription. [deception.cloud-decoys-azure:entra-diagnostics-sp] A managed identity decoy is a user-defined managed identity with access to all other decoy resources in the Decoys Resource Group; an alert is generated if an adversary uses it to access decoy resources, and Deception does not associate it with any production resources. [deception.cloud-decoys-azure:managed-identity-decoy]

**Resource decoys.** The documented attack paths of app service decoys are commands executed via a hosted web shell, commands executed via the Kudu endpoint if misconfigured, and theft of the token of the attached managed identity (which has access to all other decoys in the decoy resource group) for privilege escalation; the URI and Source Control Manager URI are generated after deployment. [deception.cloud-decoys-azure:app-service-attack-paths] Storage account container decoys detect public-container enumeration by organization keywords and private-container access via compromised identities; the ACL choices are Container (anonymous access to container and blobs), Blob (anonymous access to blobs only) and Private (no anonymous access). [deception.cloud-decoys-azure:storage-container-decoy] A storage account file share decoy is a file share mountable on endpoints over SMB or NFS that holds a decoy file dataset. [deception.cloud-decoys-azure:file-share-decoy] A key vault decoy includes credential files with URLs to Threat Intelligence decoys containing random user names and passwords, and acts as a cloud lure. [deception.cloud-decoys-azure:key-vault-decoy] ARM template decoys embed lures for user decoys, service principal decoys and Azure IaaS URLs of key vaults and storage account file shares; the documented attack paths are plaintext credentials in template specs and deployment histories; they always fail when deployed and generate no event in Deception. [deception.cloud-decoys-azure:arm-template-decoy] What the ARM template history entry itself does is open [gap:deception.cloud-decoys-azure:arm-history-event]. Azure container registry decoys (public or private) detect image pulls to extract credentials or steal code and image pushes for supply chain persistence, and a URI is generated after deployment. [deception.cloud-decoys-azure:container-registry-decoy] A VM image decoy snapshot (public or private) creates a VM temporarily, adds a callback script for detection and creates a snapshot; Public makes the image accessible to anyone using the Disk URI while Private limits access to internal adversaries, and the Disk URI is generated after deployment. [deception.cloud-decoys-azure:vm-image-decoy] An Azure Gen AI decoy uses Azure OpenAI models in Azure AI Foundry, the selected model must be available in the selected Azure region, and Azure obfuscates the last octet of the IP addresses of users who interact with Gen AI decoys, and Zscaler recommends avoiding containment of these IP addresses from the Investigate page or through Orchestration rules. [deception.cloud-decoys-azure:gen-ai-decoy] In the Azure managed identity, app service, storage account container, storage account file share and key vault decoy windows, a new resource group is created in the region selected for the decoy, while with an existing resource group the decoy's region and the group's region can differ. [deception.cloud-decoys-azure:resource-group-region]

**Lures.** Per the Azure lures page, user decoys are lured by placing their credentials on endpoints via landmine policies using Cloud Lures, Session Lures via Bash History and File Decoys via Credential Files, and service principal decoys can be lured on endpoints using the same three methods; landmine agents create a logged-on session with the user decoy credentials, which reaches other decoy resources such as storage account containers and file shares. [deception.cloud-decoys-azure:lure-methods-identity] Per the Azure lures page, app service decoys use Browser Lures and Session Lures; private storage account container decoys use Cloud Lures and Session Lures via Bash History (cloud lures make the container accessible via Azure File Explorer); container registry decoys use browser lures, file decoys and session lures; VM image decoys use browser lures or session lures. [deception.cloud-decoys-azure:lure-methods-resources] A key vault decoy's lures use file decoys or session lures, and its enumeration and subsequent interaction with other decoy resources are logged as attacks; a VM image decoy logs an attack when an adversary boots it to launch an instance and it communicates with Deception. [deception.cloud-decoys-azure:lure-key-vault-vmimage] The Azure lures page's storage account file share entry and container registry entry each say "An interaction with the storage account container decoy is logged as an attack.", and the VM image decoy entry is followed by the link line "To learn more about container registries, refer to the Microsoft documentation.". [deception.cloud-decoys-azure:lure-page-copy-text]

**Deleting.** During Azure account deletion in Cloud Shell, entering n at the continue-with-deletion prompt aborts the deletion and the configuration is enabled again in the Admin Portal; Admin Portal deletion disables the configuration. [deception.cloud-decoys-azure:delete-abort] Resource groups created by Deception are listed on the Resource Group Management tab and can be deleted there; if the group was not yet created in Azure (No in the Created column) deletion completes in the portal, otherwise the admin signs in to the Azure Portal as a Cloud Device Administrator or Global Administrator and runs the deployment script in Cloud Shell, entering the option to sync settings. [deception.cloud-decoys-azure:resource-group-delete] The roles are worded differently here too [divergence:deception.cloud-decoys-azure:azure-admin-roles].

What to check:
1. Which Azure roles the deployment script needs, since the pages word them as both roles and as either role.
2. That Microsoft.Web and Microsoft.Insights are registered as resource providers in the subscriptions.
3. That the Entra ID diagnostic settings were configured by hand for user and service principal decoys, since they are not handled via the deployment script.

Sources disagree (name both sides):
- The Azure setup page requires a user with Cloud Device Administrator and Global Administrator roles to run the deployment script; the user decoy page and the resource group page have the admin sign in as a Cloud Device Administrator or Global Administrator. [divergence:deception.cloud-decoys-azure:azure-admin-roles]
  - zscaler-help: The user running the deployment script needs the Cloud Device Administrator and Global Administrator roles.
  - zscaler-help: The user decoy page has the admin sign in to the Azure Portal as a Cloud Device Administrator or Global Administrator.
  Impact: Whether the deployment script needs both roles or either one is not settled by the pages.
- The Azure integration page says the health check function app monitors and updates the health status of the deployed decoys; the deployment-script page says the function app does not check the actual health of the deployed Azure resources. [divergence:deception.cloud-decoys-azure:azure-health-check-meaning]
  - zscaler-help: The health check function app monitors and updates the health status of the deployed decoys every 15 minutes.
  - zscaler-help: The function app does not check the actual health of the deployed Azure resources.
  Impact: Whether a healthy status in the Admin Portal reflects the health of the Azure resources, or only that they exist, is not settled by the pages.

Not known (open gaps):
