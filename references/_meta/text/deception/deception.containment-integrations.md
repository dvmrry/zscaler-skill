# Deception and ITDR containment integrations: supported solutions, per-solution setup, identity-based containment (ZIA, ZPA, Okta SSF) and blocked identities (deception.containment-integrations)
Also called: itdr containment; itdr containment integrations; deception containment; containment integration; blocked identities; okta ssf containment; identity threat protection with okta ai; crowdstrike containment

This subject covers the Deception and Identity Protection (ITDR) containment pages ([Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview), [Identity Protection (ITDR): how it reads identity stores and endpoints, what it needs, and what can be automated](kb:identity-protection.overview)); rules that use them are in [Deception and ITDR orchestration rules: the Orchestrate menu, rule pipeline, actions, testing, pausing and event notification templates](kb:deception.orchestration-rules). Containment integrations forward the attacker's identity to an integrated security solution, which isolates the attacker's system from the network; containment is done from the Rules page by a response or containment rule, or manually from the Investigate dashboard. [deception.containment-integrations:containment-overview]

**Supported solutions.** The Deception Containment page lists Check Point Firewall, CrowdStrike Falcon Insight, Fortinet, Microsoft Defender, Palo Alto Networks, VMware Carbon Black EDR, VMware Carbon Black Endpoint Standard, Internet & SaaS (ZIA) and Private Access (ZPA) as supported solutions. [deception.containment-integrations:containment-supported-list] The ITDR Containment page lists CrowdStrike Falcon Insight, Okta (SSF), Zscaler Internet Access (ZIA) and Zscaler Private Access (ZPA) as supported solutions, and its columns are Enabled, Settings and Blocked Identities. [deception.containment-integrations:itdr-containment-sources] The Deception Containment page lists each integration with Status (enabled or not), Containment Type (the third-party solution) and Blocked Identities (the total number of blocked attackers, clickable to view the contained attacker). [deception.containment-integrations:containment-page-columns]

**Rule options.** In a rule's Respond section, Palo Alto Networks - NGFW can contain attackers by hostname or IP address per the External Dynamic List, and Fortinet by domain or IP address per the Threat Feeds (Deception page). [deception.containment-integrations:rule-respond-options-network] In the Deception guides, the Palo Alto Networks and Fortinet integrations take a Default expiration (in hours) for how long IP addresses or hostnames stay in the containment list, and an Infinite Expiration checkbox keeps them until manually deleted. [deception.containment-integrations:list-expiration]

**Check Point Firewall.** In the Deception guide, Check Point Firewall integrates over its API: the Decoy Connector's management IP must reach the Check Point API server on port 443, credentials need web API permission, and policies must already exist on Check Point; a Rule Name that does not exist on the firewall is created automatically, and the Set Policy policy and layer lists are retrieved from Check Point through its APIs. [deception.containment-integrations:checkpoint-setup]

**CrowdStrike.** The CrowdStrike integration needs network connectivity from the admin portal to CrowdStrike Falcon Insight on HTTPS port 443; the URL field takes the CrowdStrike API endpoint URL, with https://api.crowdstrike.com as the example. [deception.containment-integrations:crowdstrike-connection] The CrowdStrike API client needs Detections: Read, Hosts: Read and Write, and IOCs (Indicators of Compromise): Read and Write; the Deception guide also lists Custom IOA Rules: Read and Write. [deception.containment-integrations:crowdstrike-api-scopes] Under the rule options, when the same IP address belongs to more than one CrowdStrike-managed device none of these devices is isolated and a containment failure is recorded as a system message; the Deception guide's Investigate page steps say that in this case the containment action with Falcon Insight fails and an error is displayed. [deception.containment-integrations:crowdstrike-duplicate-ip] A rule's IOC Hash action options for CrowdStrike include Block (add to the denylist and show as a detection), Block, Hide Detection (add to the denylist and do not detect) and Allow (add to the allowlist and do not detect), with an IOC Hash Severity of Informational, Low, Medium, High or Critical. [deception.containment-integrations:crowdstrike-ioc-hash-actions] The CrowdStrike IOC IP option shares IP addresses that are indicators of compromise with CrowdStrike, with an IOC IP Severity of Informational, Low, Medium, High or Critical (Deception page). [deception.containment-integrations:crowdstrike-ioc-ip] The CrowdStrike IOA Process Tree option shares process trees as indicators of attack with an IOA Action of Detect (show as a detection only), Monitor (informational, not shown as a detection) or Block Execution (kill the process and show the indicator as a detection); Block Execution kills all processes matching the process tree on all endpoints in the network (Deception page). [deception.containment-integrations:crowdstrike-ioa-actions] IOA safe processes (a Name and a Process Path of the executable) are optional entries that avoid sharing legitimate process trees with CrowdStrike; a process is marked safe only if every element of its process tree has an entry in the safe processes list (Deception page). [deception.containment-integrations:crowdstrike-ioa-safe-processes] From the Investigate page the CrowdStrike Falcon drop-down menu offers Contain with CrowdStrike Falcon Insight or Create IoC IP Indicator in CrowdStrike (Deception guide); the ITDR guide offers Contain with CrowdStrike Falcon Insight. [deception.containment-integrations:crowdstrike-manual-actions] The ITDR CrowdStrike integration shares intelligence with suggested actions for indicators of compromise (IOC), and the blocked-identities view for CrowdStrike offers the IOC Hash list of file hashes shared by ITDR. [deception.containment-integrations:itdr-crowdstrike-ioc-hash]

**Amazon GuardDuty.** The Amazon GuardDuty integration sends the source IP address of detected malicious activity to the GuardDuty threat list, which GuardDuty uses to block or flag traffic from those addresses. [deception.containment-integrations:guardduty-threat-list] GuardDuty needs AWS accounts with GuardDuty enabled and the Detector ID for each region of each account to be protected; each account entry takes a name, AWS Account ID, region and Detector ID, and Show Commands provides commands that create a role, its access permission, an S3 bucket for the threat IP list and a policy for bucket access, run in AWS CloudShell for each region. [deception.containment-integrations:guardduty-setup]

**Fortinet and Palo Alto Networks.** In the Deception guide, Fortinet integration needs connectivity from Fortinet to the admin portal on HTTP port 80; there are Threat Feeds - Attacker IPs and Threat Feeds - Attacker Domains entries, and after saving Deception generates a URL that is configured as an external threat feed on Fortinet. [deception.containment-integrations:fortinet-threat-feed] In the Deception guide, Palo Alto Networks integration needs connectivity from the Palo Alto Networks platform to the admin portal on HTTPS port 443; there are External Dynamic List - Attacker IPs and - Attacker Hostnames entries, and the generated URL is configured as an external threat feed, selecting IP List for attacker IPs or Domain List for the attacker hostname version. [deception.containment-integrations:pan-external-dynamic-list]

**Microsoft Defender.** In the Deception guide, Microsoft Defender containment needs the Windows Defender ATP agent on endpoints and connectivity from the admin portal to the Defender API servers; the Azure application registration requests the WindowsDefenderATP application permissions Machine.Isolate, Machine.Read.All and Machine.ReadWrite.All with admin consent granted. [deception.containment-integrations:defender-app-registration] In the Deception guide, the Microsoft Defender integration takes the Directory (tenant) ID as Tenant ID, the Application (client) ID as API ID and the client secret value as App Secret, and Zscaler recommends the maximum expiration period for the client secret. [deception.containment-integrations:defender-portal-fields]

**VMware Carbon Black.** In the Deception guide, VMware Carbon Black EDR integrates over its API; a Decoy Connector's management IP must reach it on port 443, an API token and host-isolation policies are required, and the configuration takes the console URL, the API token as API Key and a Decoy Connector. [deception.containment-integrations:carbon-black-edr] In the Deception guide, VMware Carbon Black Endpoint Standard needs an Org key and a Device API key; its Action Type is Apply Policy (using a Policy API key with read permissions plus Isolate Policy and Unisolate Policy names) or Quarantine, and Quarantine is not supported on Linux. [deception.containment-integrations:carbon-black-endpoint-standard]

**Internet & SaaS (ZIA).** The Internet & SaaS (ZIA) containment guide requires an IdP configured with SCIM provisioning enabled, the IdP's Base URL and Bearer Token from the Zscaler Admin Console, a user group with a firewall filtering policy of Block/Drop, and Zscaler Client Connector 4.1 or later on all endpoints (Deception page). [deception.containment-integrations:zia-prereqs] In the Deception guide, when Client Connector users interact with landmine decoys the activity is logged as an attack and the user information is shared with Internet & SaaS (ZIA), which blocks those users' internet access across devices by moving them to a restricted group; the Deception and ITDR guides both give the portal fields SCIM Base URL, SCIM Bearer Token and SCIM User Group. [deception.containment-integrations:zia-effect] The ITDR ZIA containment form has an ITDR Identity Metadata section whose Enabled option syncs with ZIA to fetch traffic-violation or bad-activity data, with the ZIA Admin Portal Base URL, Username and Password, and a Keep existing value option for the bearer token and for the password. [deception.containment-integrations:itdr-zia-identity-metadata]

**Private Access (ZPA).** ZPA containment needs an IdP configured for SSO in Private Access and the Private Access tenant ID; in the configuration window Customer ID is verified against that tenant ID, the IdPs to integrate are selected, and a SAML attribute name is entered if SCIM Sync or SCIM Attributes for Policy are disabled in the IdP. [deception.containment-integrations:zpa-prereqs-fields] A user contained with Private Access can no longer reach real apps and only app decoys remain accessible; if Authentication Service is enabled, its IdP appears automatically in the Zscaler Private Access configuration window and cannot be edited or deleted. [deception.containment-integrations:zpa-effect-auth-service] The ITDR ZPA containment form has an ITDR Identity Metadata option whose Enabled setting syncs and fetches data from ZPA for traffic violations or bad activities. [deception.containment-integrations:itdr-zpa-identity-metadata]

**Console paths in ITDR.** The ITDR ZIA guide gets the IdP Base URL and Bearer Token from Administration > Authentication Settings > Identity Providers in the ZIA Admin Portal, and the ITDR ZPA guide gets the ZPA tenant ID from Administration > Company in the ZPA Admin Portal. [deception.containment-integrations:itdr-zia-zpa-console-paths]

**Okta (SSF).** Identity Threat Protection with Okta AI containment pushes user risk scores to Okta for Zscaler Client Connector users (the risk score is pushed via SSF), needs 64-bit Windows 10 endpoints with 64-bit Client Connector 4.2.1.212 or later, 4.3.0.202 or later, or 4.4.0.285 or later, and an Okta account with admin privileges and the Okta tenant URL. [deception.containment-integrations:okta-ssf-client-connector] In Okta a Security Events Provider is created under Security > Device Integrations > Receive shared signals with a Well-known URL (https://zscaler.ssf.transmitter.smokescreen.io/.well-known/sse-configuration); in the portal the Okta (SSF) entry takes the Okta tenant URL as Base URL. [deception.containment-integrations:okta-ssf-security-events-provider] Manual containment from the dashboard is not supported for Okta (SSF); an orchestration rule must be created to push the user risk score, with a User Risk Level of Low, Medium or High and a Risk Change Reason, both shared with Okta. [deception.containment-integrations:okta-ssf-rule-only] Based on the risk score and Okta policies, Okta can end the user's sessions, prompt a Multi-Factor Authentication challenge, or invoke a workflow. [deception.containment-integrations:okta-ssf-user-risk-response]

**Blocked identities.** Contained entries show details such as IP address, hostname or username (Deception page), the time added to the containment list and the containment expiration date; for integrations other than CrowdStrike, clicking the Blocked Identities number lists them and the Delete icon removes an entry. [deception.containment-integrations:blocked-identities-view] For CrowdStrike the view offers Contained IP, IOC Hash, IOC IP and IOA Process Tree lists (Deception page; the ITDR page offers IOC Hash); when containment is lifted directly from the CrowdStrike Falcon console the portal entry is removed by a scheduled job that typically runs every hour. [deception.containment-integrations:crowdstrike-blocked-view]

What to check:
1. For which solutions a Containment page offers, read the page of the product in use: the Deception and ITDR lists differ, and the GuardDuty and Okta (SSF) guides exist alongside lists that do not all name them.
2. For Okta (SSF) containment, that manual containment from the dashboard is not supported and an orchestration rule pushes the risk score.
3. For a Client Connector based containment, the Client Connector version and operating system the guide names.
