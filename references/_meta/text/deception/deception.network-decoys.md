# Network decoys (Internal and Zero Trust Network): personalities, creation, AD join, MITM detection, RADIUS and management (deception.network-decoys)
Also called: Internal decoy; Zero Trust Network decoy; ZTN decoy

An Internal decoy is configured with a hostname or FQDN and a MAC address matching a manufacturer or vendor; a Zero Trust Network decoy uses Private Access to create decoy applications and is configured with an FQDN. [deception.network-decoys:internal-vs-ztn] Zscaler recommends at least two network decoys in each business-critical network segment. [deception.network-decoys:two-per-segment]

**The page.** The Network Decoys page marks each decoy with one of five status icons: not deployed, successfully deployed, partially deployed, not connected to an aggregator, or disabled. [deception.network-decoys:status-icons] The Network Decoys page lists FQDN and IP, Personality (the predefined template and its configured services), Network Decoy Groups and Network Name for each decoy. [deception.network-decoys:page-columns] Selecting a personality auto-configures hostname or FQDN, MAC address and the default services tagged to it; services can be enabled, disabled or have their content changed. [deception.network-decoys:personality-defaults]

**Internal decoys.** An Internal decoy needs a Decoy Connector deployed on VMware vSphere Hypervisor (ESXi), Microsoft Hyper-V, Microsoft Azure or Amazon Web Services (AWS). [deception.network-decoys:internal-connector-platforms] Zscaler recommends two free IP addresses per VLAN or subnet for Internal decoys; the IP field is left blank where the network has DHCP enabled, and IPv6 requires an IPv6 subnet. [deception.network-decoys:internal-ips] For an Internal decoy's MAC, selecting or autogenerating a manufacturer makes Deception generate a MAC address belonging to that manufacturer; a MAC can also be entered manually. [deception.network-decoys:internal-mac]

**Zero Trust Network decoys.** Zero Trust Network decoys run on a dedicated cloud environment hosted by Zscaler and are made available to an adversary using Private Access via Zscaler Client Connector; they can be created on a production application segment. [deception.network-decoys:ztn-where] A Zero Trust Network decoy requires a provisioned Private Access tenant ID, Client Connector installed on endpoints, and free FQDNs not assigned to existing Private Access systems; for real applications the ports must be free on the production segment (the example: port 3306 free on a segment using 80 and 443); the page adds that this prerequisite is not applicable to new Private Access decoys for real applications in Private Access. [deception.network-decoys:ztn-prereqs] For a Zero Trust Network decoy of a production application, only application segments with at least one FQDN are supported, and the search needs at least three characters. [deception.network-decoys:ztn-app-segment] AI-powered Zero Trust Network decoy recommendations need at least 5 application segments with non-wildcard FQDNs in Private Access; they use hostnames (FQDNs) and port configurations from those segments. [deception.network-decoys:ztn-ai-min] The vendor says to make sure there are no FQDN-port combinations conflicting with existing Private Access application segments, and the Deception filter on the Private Access Application Segments page shows the Zero Trust Network decoys. [deception.network-decoys:ztn-conflict-filter]

**Active Directory.** An Internal network decoy can be added to an AD domain and AD DNS as a decoy computer object; the AD domain must be added first, and the deployment script creates the object with OS and OU details. [deception.network-decoys:ad-join] For an AD decoy computer the OU path is listed automatically if the AD domain has credentials and entered manually if it has none. [deception.network-decoys:ad-join-ou] For AD decoy computers in domains managed by server agents the deployment scripts do not have to be run manually, as the server agent automates the deployment. [deception.network-decoys:ad-join-server-agent]

**Managing.** A single network decoy is disabled by deselecting Enabled, which turns its status icon gray, and a disabled decoy cannot be deployed until enabled again; all decoys can be stopped at once via the Summary page. [deception.network-decoys:disable] Network decoy configuration details are exported as a CSV file with Export Decoy Configuration from the Internal or Zero Trust Network tab. [deception.network-decoys:export-config] Decoys configured with other services can be tested, but those services must be accessed using their respective applications. [deception.network-decoys:test-other-services]

**MITM detection.** Deception detects LLMNR, NBT-NS and mDNS poisoning by having internal network decoys broadcast decoy name resolution requests at specified intervals; a response from a tool such as Responder or Inveigh is logged as an MITM attack. [deception.network-decoys:mitm-what] Responders to LLMNR queries listen on UDP 5355, to NBT-NS queries on UDP 137 and to mDNS queries on UDP 5353. [deception.network-decoys:mitm-ports] LLMNR and NBT-NS are recommended for Windows environments and mDNS for environments with macOS systems. [deception.network-decoys:mitm-os-recommendation] Request hostnames are picked at random from the configured list, or generated by the service per request when the field is blank; they must be unique and not assigned to real hosts. [deception.network-decoys:mitm-hostnames] MITM detection is not supported for decoys connected to Threat Intelligence, Private Access (ZPA) or cloud-based Decoy Connectors, so their subnets are not listed. [deception.network-decoys:mitm-unsupported-connectors] The Broadcast Interval is set in minutes and controls how often network decoys broadcast decoy name resolution requests. [deception.network-decoys:mitm-interval]

**RADIUS decoys.** RADIUS encrypts only the password in authentication requests, which leaves servers open to packet forgery and MITM attacks without TLS or IPSec; adversaries use Nmap to enumerate the server username, password and secret. [deception.network-decoys:radius-why] RADIUS decoys are high-interaction and are deployed on an internal network via Internal decoys. [deception.network-decoys:radius-internal-only] Authentication attempts against a RADIUS decoy are enriched by the RADIUS Authentication ThreatParse rule, which scores a successful attempt higher than a failed or unknown one. [deception.network-decoys:radius-threatparse] When the RADIUS service is enabled on an Internal decoy it starts on ports 1812 and 1813. [deception.network-decoys:radius-ports] Testing a RADIUS decoy needs UDP ports 1812 and 1813 open, and the decoy automatically starts FreeRADIUS when enabled. [deception.network-decoys:radius-test-prereqs] With the documented test credentials (admin / radius / secret testing123), correct values return Access-Accept, a wrong password Access-Reject, and a wrong shared secret no reply. [deception.network-decoys:radius-test-responses]
