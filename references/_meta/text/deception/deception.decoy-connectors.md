# Decoy Connectors: platforms, sizing, connectivity, connection and credentials (deception.decoy-connectors)
Also called: decoy connector; appliance; deception appliance; recovery console; connection code

Decoy Connectors (formerly Appliances) are lightweight VMs that host network decoys and act as a network broker connecting the Deception service to on-premises systems and Active Directory decoys; a standard VM image is distributed for data centers and cloud environments. [deception.decoy-connectors:what-it-is] The Decoy Connectors page lists image downloads for VMware vSphere Hypervisor (ESXi), Microsoft Hyper-V, Microsoft Azure and Amazon Web Services (AWS). [deception.decoy-connectors:page-image-platforms] [divergence:deception.decoy-connectors:aws-image-delivery] The Decoy Connectors page shows each connector's name with a connection-status icon (connected, not connected, not connected to an aggregator, update in progress or failed), version, management IP and last connected time. [deception.decoy-connectors:page-columns-and-icons]

**Sizing and connectivity.** The VMware, Hyper-V and Nutanix AHV deployment guides each require a VM with 2 CPU cores, 4 GB RAM, 50 GB disk and two or more network interfaces, one of which can serve as a dedicated management interface. [deception.decoy-connectors:vm-sizing] Each deployment guide (VMware, Hyper-V, AWS, Azure, Nutanix AHV) requires outbound TCP 443 from the Decoy Connector management IP address or interface to the following hosts: Deception Admin Portal, Aggregator, ib.smokescreen.io and rs.smokescreen.io. [deception.decoy-connectors:outbound-443-hosts] An HTTP proxy is required if the Decoy Connector cannot establish a direct connection via port 443 to the Zscaler Deception Admin Portal, Aggregator, ib.smokescreen.io and rs.smokescreen.io; on the Configuring Proxy Settings page, all inspection features for those hosts must be off and the proxy must give unfiltered TCP 443 access to them. [deception.decoy-connectors:proxy-inspection] On the Configuring Proxy Settings page, the proxy is configured from the Recovery Console (via VM console or SSH), taking the proxy IP or FQDN, port, and optional username and password. [deception.decoy-connectors:proxy-menu]

**Connecting.** The management network is set from recovery console menu option 2 with IP address, subnet mask, default router, a single DNS server and a management interface (em0 on VMware). [deception.decoy-connectors:management-network] The recovery console's default username and password are both recovery; once a Decoy Connector is connected to the Admin Portal its recovery and diagnostic passwords are randomized (the username stays recovery), the new credentials are obtained from the portal, and only users with the super admin role can view recovery credentials. [deception.decoy-connectors:recovery-credentials] Connecting a Decoy Connector uses an 8-digit connection code from Actions > Connection Code that is valid for up to 12 hours; the code is needed when connecting from the Recovery Console, where the Admin Portal hostname (FQDN/DNS name) and the code are entered; a newly added connector shows a red status until connected and a green status after. [deception.decoy-connectors:connection-code] The proxy article says to enter 3 on the recovery console main menu to connect the Decoy Connector to the Admin Portal and press Enter, and a later step says to enter Yes to enable proxy. [deception.decoy-connectors:recovery-console-menu-3] The connect-a-Decoy-Connector article says to enter 4 on the recovery console main menu to connect the Decoy Connector to the Admin Portal. [deception.decoy-connectors:recovery-console-menu-4] [divergence:deception.decoy-connectors:connect-menu-option]

**VMware.** The VMware guide requires promiscuous mode or MAC learning, forged transmits, MAC address changes and (only when decoys are on more than one VLAN) VLAN trunking on the port group. [deception.decoy-connectors:vmware-network-security] In the VMware guide the image is the .ova from Download Image > VMware, VLAN trunking on a standard port group uses VLAN ID 4095, and disk provisioning is Thick. [deception.decoy-connectors:vmware-deploy-details]

**Hyper-V.** In the Hyper-V deployment guide, the platform is Microsoft Hyper-V on Windows Server 2012 R2 or later, the image is the HyperV .vhd.zip file on a Generation 1 VM, the MAC address spoofing option is enabled on the network adapter, and Decoy Connectors do not support VLAN trunking on Hyper-V, so a virtual NIC per VLAN is configured for two or more VLANs. [deception.decoy-connectors:hyperv-details]

**AWS.** The AWS guide requires inbound TCP 22 to the management IP, an AWS account with admin privileges (view account ID, create EC2 instances, manage security groups, use T3.small or larger), and 50 GB disk. [deception.decoy-connectors:aws-prereqs] For AWS, the customer shares the AWS account ID and region with the Zscaler Deception team, who share an AMI into the account to launch the EC2 instance from. [deception.decoy-connectors:aws-ami-sharing] On AWS each additional interface can host only one network decoy, instance type limits the number of attachable interfaces (a T3 small allows three), Zscaler recommends an Allow All security group on decoy interfaces, and the instance must be stopped and started after attaching interfaces. [deception.decoy-connectors:aws-interfaces]

**Azure.** The Azure guide uses the HyperV .vhd.zip image, uploaded as a blob and made into a Linux, Gen 1, Standard SSD image, with VM size Standard_B2s (2 vCPUs, 4 GiB). [deception.decoy-connectors:azure-image] On Azure the Decoy Connector VM does not use the administrator credentials entered at VM creation, SSH (22) is selected for inbound ports, and Public inbound ports can be set to None after the connector is connected. [deception.decoy-connectors:azure-access] On Azure each Decoy Connector VM needs at least two network interfaces, interfaces may be in different subnets but the same virtual network, Standard_B2s allows three interfaces, and each interface can host one network decoy. [deception.decoy-connectors:azure-interfaces]

**Nutanix AHV.** The Nutanix AHV guide uses the Xen/KVM .tar.gz image containing a .qcow2 file, a VM with 2 CPUs and 4 GiB memory (memory overcommit not enabled), a SCSI disk cloned from the image, Legacy BIOS boot, UTC time zone, and not an Agent VM. [deception.decoy-connectors:nutanix-image-and-vm] The Nutanix AHV guide requires VLAN trunking on the decoy interface to use more than one VLAN on a single interface. [deception.decoy-connectors:nutanix-vlan-trunking]

**Managing.** The connect-a-Decoy-Connector page says App Connectors and TI Decoy Connectors cannot be added or connected to the Admin Portal by the customer; the Managing Decoy Connectors page says Private Access or Threat Intelligence Decoy Connectors cannot be edited or deleted and Zscaler Support manages them. [deception.decoy-connectors:zpa-and-ti-connectors-managed] App Connectors are in [Topology: subnets and interfaces, aggregator sinkholes, ZPA App Connectors and Windows high-interaction VM credentials](kb:deception.topology). A Decoy Connector can be rebooted from Actions > Reboot, and its update logs viewed from Logs > View update logs to troubleshoot Decoy Connector update issues. [deception.decoy-connectors:reboot-update-logs] Decoy Connector debug logs are stored on the connector and copied to the portal on request; recent debug logs are the last 1,000 lines of each log file, all debug logs are the complete files, the connector must be connected, and the download is a .tar.xz file. [deception.decoy-connectors:debug-logs]

What to check:
1. Which recovery console menu option connects a Decoy Connector to the Admin Portal: the proxy article and the connect article name different numbers.
2. How the AWS image is obtained and which platforms a page lists: the Decoy Connectors page lists four image downloads, the Nutanix AHV guide is a separate article.
3. Whether the Decoy Connector can reach the four hosts on TCP 443 directly, since a proxy is required if it cannot.

Sources disagree (name both sides):
- The Decoy Connectors page lists AWS among the platforms with a VM image file to download, while the AWS deployment guide has the customer share an account ID and region and the Deception team share an AMI. [divergence:deception.decoy-connectors:aws-image-delivery]
  - zscaler-help: A VM image file is downloaded for AWS along with VMware, Hyper-V and Azure.
  - zscaler-help: For AWS the Deception team shares an AMI on the customer's account after the account ID and region are shared.
  Impact: The two pages give different delivery for the AWS image: a downloaded image file or a shared AMI; the captures do not say which applies.
- The proxy article and the connect-a-Decoy-Connector article give different recovery console main menu options for connecting the Decoy Connector to the Admin Portal. [divergence:deception.decoy-connectors:connect-menu-option]
  - zscaler-help: Enter 3 on the recovery console main menu to connect the Decoy Connector to the Deception Admin Portal.
  - zscaler-help: Enter 4 on the recovery console main menu to connect the Decoy Connector to the Deception Admin Portal.
  Impact: The two articles name a different menu number for the same action; the captures do not say which is current.
