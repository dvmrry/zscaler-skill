# AWS Cloud Deception: setup, tags, logging resources, decoy types and lures (deception.cloud-decoys-aws)

AWS setup requires access to an AWS account with an Administrator role and the AWS region information. [deception.cloud-decoys-aws:prerequisites] AWS Terraform-based deployment downloads a ZIP containing aws-decoys.tf.json and the admin adds back-end details to its backend block (an S3 bucket-based back end is the documented example). [deception.cloud-decoys-aws:terraform-package] The DB Option and Parameter group suffix entered in the AWS account settings is used with the option group and parameter group for RDS decoys to prevent name conflicts. [deception.cloud-decoys-aws:rds-suffix] Enable GenAI Prompt Logging (optional) records Gen AI decoy prompts and responses on the ThreatParse page as aws gen ai input and aws gen ai ouput under the AWS GenAI Model was Invoked rule. [deception.cloud-decoys-aws:genai-prompt-logging] With Gen AI prompt logging enabled, an S3 bucket stores prompts and responses of all Gen AI applications in the AWS account including legitimate ones, but only those for Deception's Gen AI decoys are sent to the Admin Portal; the page advises a separate AWS account without legitimate Gen AI applications to avoid storing legitimate applications' temporary prompts. [deception.cloud-decoys-aws:genai-logging-bucket] If no default VPC is found in the selected region the AWS deployment script prompts to create a new VPC, which requires running the script again with the --cidr-block parameter given an IP range in CIDR notation. [deception.cloud-decoys-aws:default-vpc] The shared model is [Cloud Deception model shared by Azure, AWS and GCP: detection, deployment, status and deletion](kb:deception.cloud-decoys); the other providers are [Azure Cloud Deception: setup, deployment-script resources, logging, decoy types and lures](kb:deception.cloud-decoys-azure) and [GCP Cloud Deception: setup, log permissions, decoy types and lures](kb:deception.cloud-decoys-gcp); plan decoy totals are in [Deception Standard and Advanced plans: decoy counts, Gen AI decoys, orchestration and API access](kb:deception.plans) and the product is introduced in [Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview).

**Obtaining the deployment script.** For CloudShell-based deployment, the AWS deployment script, which propagates changes and syncs settings between Deception and AWS, is obtained either as a CloudShell command that downloads and runs it, or as a ZIP file uploaded to AWS CloudShell and run with a bash command from the Admin Portal. [deception.cloud-decoys-aws:deployment-script-methods]

**Logging and health.** AWS logging uses a Logging Bucket (S3) that collects logs for S3 and DynamoDB decoys via CloudTrail, CloudTrail also listening to logs for ECR and IAM decoys, a Log Access IAM User (a CLI user) with access keys to poll the bucket and CloudTrail, and DB Option and Parameter groups for raw RDS log files. [deception.cloud-decoys-aws:logging-resources] The Admin Portal polls logs from CloudTrail and the Logging S3 bucket every 3 minutes. [deception.cloud-decoys-aws:log-polling-3min] The AWS security group created for Cloud Deception opens inbound connections to ports 3306 (MySQL) and 5432 (PostgreSQL). [deception.cloud-decoys-aws:security-group-ports] The AWS Health Check Lambda Function is triggered every 15 minutes from the Admin Portal to check whether deployed decoys are present in the AWS account. [deception.cloud-decoys-aws:health-check-scope] The health check is described two ways [divergence:deception.cloud-decoys-aws:aws-health-check-meaning]. Per the AWS resources page, an IAM decoy creates an IAM decoy user with access keys and attaches the IAM Decoy User Access Policy, an S3 decoy creates an S3 bucket and enables CloudTrail logging, and a DynamoDB decoy creates a DynamoDB instance and enables CloudTrail logging. [deception.cloud-decoys-aws:decoy-workflows] The AWS VM image decoy deploys an EC2 instance using the t3.small/t2.small series available in the deployment region; it persists for 5 minutes and is terminated after the snapshot is built. [deception.cloud-decoys-aws:vm-image-instance]

**Tags.** Tags configured in the portal for AWS resources deployed by Deception are of two types: Decoy Tags (added to decoy resources and the IAM Decoy User Access Policy) and Management Tags (added to all other resources); Zscaler recommends configuring them before setting up the integration because they are added only when resources are created. [deception.cloud-decoys-aws:tags-types] Tag keys and values should not use words such as decoy, deception or active defense because they can hint to adversaries about the nature of decoy resources. [deception.cloud-decoys-aws:tags-naming] New decoy tags are not applied to existing decoys, so applying them to all decoys requires deleting and redeploying them, although tags are added to the IAM Decoy User Access Policy on any later deployment-script operation; edited decoy tags apply only to decoy resources created after the edit; edited management tags are applied to existing management resources on later deployment-script operations; deleting a tag does not remove it from existing resources. [deception.cloud-decoys-aws:tags-not-retroactive]

**Decoy types.** An AWS IAM decoy is a decoy IAM user used to detect sign-in attempts with its credentials and has access to all other AWS decoys; it has no region option because IAM users are common to all regions in an account, and an Access Key value is automatically generated and associated with it. [deception.cloud-decoys-aws:iam-decoy] S3 decoys detect enumeration of public buckets by organization keywords and access to private buckets through compromised identities; the ACL is Public (accessible to anyone) or Private (accessible only to internal adversaries). [deception.cloud-decoys-aws:s3-decoy] RDS decoys are MySQL or PostgreSQL databases (public or private) on the db.t3.micro instance type; Publicly Accessible enabled makes the decoy accessible to anyone, otherwise only to internal adversaries, and the URI value is generated for public RDS decoys during the subsequent health check. [deception.cloud-decoys-aws:rds-decoy] For RDS decoys, Subnet Group deploys the decoy into a subnet group of an existing VPC; VPC CIDR (a new VPC is created if none is available) is available only if Subnet Group is disabled, and Subnet CIDRs is available only if VPC CIDR is configured. [deception.cloud-decoys-aws:rds-vpc-options] ECR decoys (public or private) detect image pulls to extract credentials or steal code and image pushes for supply chain persistence; Visibility Public makes the decoy accessible to anyone using the URI, Private limits it to internal adversaries, and a URI is generated for public ECR decoys. [deception.cloud-decoys-aws:ecr-decoy] The ECR decoy page's first CloudShell deploy sequence says "Enter the option to deploy RDS database decoys and press Enter." and that the script "deploys the RDS decoys to the selected regions", before a second sequence that says "Enter the option to deploy ECR decoys and press Enter.". [deception.cloud-decoys-aws:ecr-page-rds-step] A DynamoDB decoy is configured with a partition key and its type and a sort key and its type. [deception.cloud-decoys-aws:dynamodb-decoy] An AWS VM image decoy (public or private) creates an EC2 instance temporarily, adds a callback script and creates a snapshot; setting Visibility to Public requires the Block public access for AMIs setting to be disabled in the deployment region, and the Snapshot ID and AMI ID are associated with the decoy after deployment. [deception.cloud-decoys-aws:vm-image-decoy] For AWS VM image decoys, Subnet ID deploys into a subnet of an existing VPC; VPC CIDR (a new VPC is created if none is available) is available only if Subnet ID is disabled, and Subnet CIDRs is available only if VPC CIDR is configured. [deception.cloud-decoys-aws:vm-image-vpc-options] An AWS Gen AI decoy uses Amazon Bedrock-optimized foundation models, only models optimized for Amazon Bedrock are supported, the model must be available in the selected region, and default instructions must have their placeholder texts replaced. [deception.cloud-decoys-aws:gen-ai-decoy]

**Lures.** Per the AWS lures page, IAM decoys use Cloud Lures, Session Lures via Bash History and File Decoys via Credential Files; private S3 decoys, RDS decoys and ECR decoys use Browser Lures, Session Lures via Bash History and File Decoys via Credential Files; DynamoDB decoys use Session Lures via Bash History and File Decoys via Credential Files; VM image decoys use browser lures or session lures. [deception.cloud-decoys-aws:lure-methods]

What to check:
1. Whether AWS tags were configured before the integration was set up, since they are added to resources only when the resources are created.
2. Whether Block public access for AMIs is disabled in the deployment region before deploying a public VM image decoy.

  - zscaler-help: The health check lambda function monitors and updates the health status of the deployed decoys every 15 minutes.

  Impact: Whether a healthy status in the Admin Portal reflects the health of the AWS resources, or only that they are present, is not settled by the pages.
