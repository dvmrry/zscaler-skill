# Cloud Deception model shared by Azure, AWS and GCP: detection, deployment, status and deletion (deception.cloud-decoys)
Also called: Cloud Deception

Cloud Deception is a set of tools to configure and deploy decoys that mimic legitimate resources in public cloud platforms; depending on the type of decoy and its configuration an adversary can access, interact or perform malicious operations with the cloud decoys, and such activities are logged as attacks viewable on the Deception dashboard. [deception.cloud-decoys:what-it-is] Lures for Azure or AWS decoys configured with landmine policies can detect malicious activity by users in the organization because landmine policies are deployed on devices the organization manages; decoys with public visibility can detect external adversaries who enumerate them. [deception.cloud-decoys:internal-vs-external] The providers are [Azure Cloud Deception: setup, deployment-script resources, logging, decoy types and lures](kb:deception.cloud-decoys-azure), [AWS Cloud Deception: setup, tags, logging resources, decoy types and lures](kb:deception.cloud-decoys-aws) and [GCP Cloud Deception: setup, log permissions, decoy types and lures](kb:deception.cloud-decoys-gcp); the decoy totals per plan are in [Deception Standard and Advanced plans: decoy counts, Gen AI decoys, orchestration and API access](kb:deception.plans) and the product is introduced in [Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview).

**Deploying.** For Azure and AWS the Deployment Method (Terraform or CloudShell) cannot be changed for the same configuration; to change it, delete the old configuration and create a new one. [deception.cloud-decoys:deployment-method-fixed] The GCP page offers Terraform-based deployment to set up the integration and deploy decoys in GCP. [deception.cloud-decoys:gcp-terraform-only] For Terraform-based deployment the Azure, AWS and GCP pages tell the admin to use the same back end for all configurations relating to the same Azure account, AWS account or GCP project respectively. [deception.cloud-decoys:tf-same-backend]

**Health and status.** The Azure and AWS integration pages say a health check function app (Azure) and a health check lambda function (AWS) are deployed and monitor and update the deployed decoys' health status to the Admin Portal every 15 minutes; the GCP management page says a health check lambda function deployed at the time of integration updates GCP decoy statuses every 15 minutes. [deception.cloud-decoys:health-check-15min] The Azure health check is described two ways [deception.cloud-decoys-azure:azure-health-check-meaning](kb:deception.cloud-decoys-azure:azure-health-check-meaning) and so is the AWS one [deception.cloud-decoys-aws:aws-health-check-meaning](kb:deception.cloud-decoys-aws:aws-health-check-meaning). A decoy shown as inactive no longer exists in the cloud or a property used to reference it does not exist, which happens when the decoy or its resources are manipulated directly in the cloud (stated on the Azure, AWS and GCP management pages). [deception.cloud-decoys:status-inactive] Pending deployment means a decoy was created or modified in the Admin Portal but the deployment script has not propagated the change to the cloud; pending deletion means it was deleted in the portal but the script has not propagated that (Azure, AWS and GCP management pages). [deception.cloud-decoys:status-pending] What Not Deployed means next to these states is open [gap:deception.cloud-decoys:not-deployed-state].

**Editing and deleting.** Edits and deletions of Azure and AWS decoys made in the Admin Portal reach the cloud only after the deployment script is run in the cloud shell (Azure Cloud Shell, AWS CloudShell); on GCP, the edit and delete steps end with downloading the Terraform files, running terraform apply and uploading the exported state JSON, after which the page says the changes are propagated to the GCP cloud. [deception.cloud-decoys:edits-need-deploy] An Azure decoy to be edited must be in the Not Deployed state; the AWS and GCP pages say the decoy must not be deployed. [deception.cloud-decoys:edit-requires-not-deployed] Editing an account or project is a single-step process if nothing was propagated to the cloud and a two-step process if it was propagated at least once; the Azure page words this by whether the deployment script was used. [deception.cloud-decoys:two-step-edit] Cloud Deception settings for an account or project can be deleted only if no decoys are deployed: Azure requires deleting all decoys and running the deployment script first; AWS requires deleting all decoys and completing the deletion in AWS (Terraform or CloudShell script) first; GCP requires deleting all decoys and completing the deletion in GCP first. [deception.cloud-decoys:delete-account-needs-no-decoys] If the deployment script fails to remove entries of resources marked for deletion in the Admin Portal, the Force Delete option is needed; the pages give manual removal of interdependent resources in the cloud as an example of how entries can be left, and the option appears once deletion has started (Azure and AWS settings pages). [deception.cloud-decoys:force-delete]

**Plans and unstated limits.** Whether GCP decoys count toward the plan total is open [gap:deception.cloud-decoys:gcp-plan-count]. Several specifics are not stated [gap:deception.cloud-decoys:unstated-specifics].

What to check:
1. Whether the deployment script has been run after a portal edit or deletion of an Azure or AWS decoy, or the Terraform steps after one of a GCP decoy.
2. Whether any decoys remain deployed before deleting an account or project's Cloud Deception settings.
3. What the Azure and AWS health checks check, since the pages describe each two ways.

Not known (open gaps):
- What the Not Deployed state is next to the status icons [gap:deception.cloud-decoys:not-deployed-state]: settled by lab-test or source-read
- Whether GCP decoys count toward the Standard or Advanced decoy total [gap:deception.cloud-decoys:gcp-plan-count]: settled by support-ticket or tenant-data
- Specifics the cloud decoy pages do not state [gap:deception.cloud-decoys:unstated-specifics]: settled by source-read or lab-test
