# GCP Cloud Deception: setup, log permissions, decoy types and lures (deception.cloud-decoys-gcp)

The GCP page says Cloud Deception configures decoys that mimic legitimate GCP resources, such as service accounts, cloud storages, cloud SQLs, secret managers and artifact registries. [deception.cloud-decoys-gcp:decoy-types] GCP setup requires access to a GCP project with an Administrator role. [deception.cloud-decoys-gcp:prerequisites] GCP Terraform deployment uses gcp-decoys.tf.json, requires setting export TF_APPEND_USER_AGENT="<value_from_ui>" before running Terraform, and exports the state as JSON with `terraform output -json gcp_terraform_output > deployment-output.json`. [deception.cloud-decoys-gcp:terraform-package] The GCP Project Setting asks for a Region for the resources (health check function and logging bucket); the integration creates a Service Account Email for logging resources, a Logging Bucket for gathering logs, and a cloud Health Check Function, which the management page calls a health check lambda function. [deception.cloud-decoys-gcp:project-settings] On the GCP projects list, Enabled indicates whether logs for the GCP project are being polled. [deception.cloud-decoys-gcp:enabled-meaning] Editing a GCP project in the Admin Portal exposes the Enabled setting, which modifies the status of Cloud Deception for the project. [deception.cloud-decoys-gcp:edit-project-field] The shared model is [Cloud Deception model shared by Azure, AWS and GCP: detection, deployment, status and deletion](kb:deception.cloud-decoys); the other providers are [Azure Cloud Deception: setup, deployment-script resources, logging, decoy types and lures](kb:deception.cloud-decoys-azure) and [AWS Cloud Deception: setup, tags, logging resources, decoy types and lures](kb:deception.cloud-decoys-aws); plan decoy totals are in [Deception Standard and Advanced plans: decoy counts, Gen AI decoys, orchestration and API access](kb:deception.plans) and the product is introduced in [Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview).

**Logging.** Deception fetches only decoy-associated logs from GCP using Logging query language, using a logging bucket for public cloud storage decoys and audit logs for all other decoys. [deception.cloud-decoys-gcp:log-collection] The permissions used for the service account created during GCP integration are LogViewer (read-only access to standard logs), privateLogViewer (read-only access to private logs such as Data Access audit logs, required to determine who accesses the decoys) and view access for the _AllLogs view in the _Default logging bucket (required to retrieve all access logs associated with the decoys). [deception.cloud-decoys-gcp:service-account-permissions] The log polling interval is not stated [gap:deception.cloud-decoys-gcp:log-polling-interval].

**Decoy types.** A GCP service account decoy carries API credentials that can be placed in credential files on endpoints using landmine decoys; any enumeration using the credentials is logged as an attack. [deception.cloud-decoys-gcp:service-account-decoy] Cloud storage decoys detect public cloud storage enumeration by organization keywords and private storage access through compromised identities; ACL Public is accessible to anyone and Private only to internal adversaries. [deception.cloud-decoys-gcp:cloud-storage-decoy] Cloud SQL decoys are MySQL or PostgreSQL databases (public or private) with ACL Public (accessible to anyone) or Private (internal adversaries only) and a root password; the VPC Network Name field appears only if ACL is Private. [deception.cloud-decoys-gcp:cloud-sql-decoy] Removing a PostgreSQL Cloud SQL decoy can fail with 'failed to delete user postgres ... role "postgres" cannot be dropped because some objects depend on it'; the documented fix is to find google_sql_user.sql-user-<decoy-name> in `terraform state list`, remove it with `terraform state rm <resource_id>`, and run `terraform apply`, noting that deleting the entire instance also deletes the exploitable user and is considered the safest operation. [deception.cloud-decoys-gcp:cloud-sql-postgres-delete-error] Secret manager decoys contain fake secret identifiers or access references, and any attempt to access or enumerate them is logged as an attack. [deception.cloud-decoys-gcp:secret-manager-decoy] An artifact registry decoy holds decoy artifacts and any attempt to access or enumerate it is logged as an attack; the Repository Format field takes a format, with docker, python and npm given as examples. [deception.cloud-decoys-gcp:artifact-registry-decoy]

**Lures.** Per the GCP lures page, service account decoys with API credentials are placed on endpoints using the landmine decoys Cloud Lures and File Decoys via Credential Files. [deception.cloud-decoys-gcp:lure-methods] The GCP lures page's Cloud SQL, Secret Manager and Artifact Registry entries each say "Any interaction with the cloud storage decoy is logged as an attack.". [deception.cloud-decoys-gcp:lure-page-copy-text]

What to check:
1. Whether the service account created during the integration has the permissions the integration uses.
2. Whether TF_APPEND_USER_AGENT was set before running Terraform for the GCP deployment.
