# Best-practice guides: decoy minimums, landmine policy tables, containment rule expressions per decoy type, and the use-case recipes still open (deception.best-practices)

The network decoy guide recommends at least 50 network decoys: 10 file servers with business-critical shares, 10 web servers, 5 business-critical applications, 5 services (SSH, Telnet, FTP), 5 high-interaction Windows servers, 5 database servers, 5 dev servers, 2 IoT devices, 2 custom servers and 1 PAM server. [deception.best-practices:network-minimum-mix] Network decoys should cover each key zone and segment and each service, and AD can host network decoys too; hostnames can be generated from keyword datasets such as company name, location and business keywords. [deception.best-practices:network-coverage] High-interaction Windows server decoys allow full telemetry capture, video recording and malicious program capture. [deception.best-practices:network-hi-windows] The database server decoy use case recommends enabling SSH, MySQL and Web, with Web set to the apache server type, the PHPmyadmin dataset and ports 80 and 8080. [deception.best-practices:network-database-example] Hub: [Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview).

**Threat Intelligence decoys.** The TI decoy guide recommends at least 10 TI decoys across public-facing infrastructure, including at least one each of CMS, development, email, VPN and file share server decoys. [deception.best-practices:ti-minimum] TI decoy domain names resembling backup servers or deprecated services are recommended, because access to them indicates the attacker scraped the DNS A record. [deception.best-practices:ti-naming]

**Active Directory decoys.** The AD decoy guide recommends at least 10 AD decoys, including one business-critical, Unix and well-known user account, one with a fake password description, two privileged, service and persona accounts, two with a distinct decoy share path, and two with Can Password Expire enabled. [deception.best-practices:ad-minimum] AD decoys should follow internal naming conventions, sit in OUs that host high-value users, have logon workstations configured for OPSEC safety on privileged accounts, and avoid the keywords decoys, Zscaler and Deception. [deception.best-practices:ad-opsec] The AD guide ties Make Account Kerberoastable to Kerberoasting, Pre-auth Not Required to AS-REP roasting, and Profile Path (File Share Discovery Lure) to a network decoy with the Shares service. [deception.best-practices:ad-attack-lures]

**Landmine decoys.** The landmine guide recommends one simple-detection policy needing no customization and one advanced-detection policy needing minimal customization, plus custom per-department policies: typically a department can have up to 4 policies, and at least two must be configured for business-critical departments. [deception.best-practices:landmine-two-policies] The landmine guide's simple-detection policy table enables MITM detection with LLMNR poisoning at a 5-minute interval, a hidden credential file decoy password1.txt at %userprofile%\Imp, and, if there is no AD password policy, a password policy requiring special characters with minimum length 8 and maximum length 12. [deception.best-practices:landmine-simple-policy] The landmine guide's advanced-detection policy table enables Fake Security Processes at paths similar to, but not the same as, legitimate applications' default paths, and enables PsExec Detection, Ransomware Detection and Triage. [deception.best-practices:landmine-advanced-policy] Customize the landmine installer name before configuring a landmine policy, and deploy in phases per department starting from the highest priority based on security risk; the guide's example prioritization from highest to lowest is Security and AD administrators, network infrastructure, IT or critical application administrators, senior management, marketing, others. [deception.best-practices:landmine-rollout] Policies are in [Landmine policies: what they deploy, which endpoints they select, and how the Windows endpoint deployment is set up](kb:deception.landmine-policies), decoys in [Landmine decoy modules and lures: what each deploys, on which operating systems, and how it is tested](kb:deception.landmine-decoys) and agents in [Landmine agent and agentless: install, requirements, proxies, management and OS feature support](kb:deception.landmine-agents).

**Containment, TI and network decoys.** For TI decoys, a credential submitted with a username in the organization's domain is matched with recon.post_data.username like /.*\@<your_Org_Domain>\.com.*/ and can feed Palo Alto EDLs, Fortinet threat feeds or Check Point Firewall. [deception.best-practices:ti-credential-submit] For TI decoys, payloads from a source denylisted on AbuseIPDB are matched with abuseip.abuseConfidenceScore greater than 74 and recon.method in ["PUT","POST"]. [deception.best-practices:ti-abuseipdb] For TI and network decoys, known web application CVE exploits are matched with mitre_ids in ["T1190","T1595.002"] and VPN CVE exploits with mitre_ids in ["T1133","T1595.002"]. [deception.best-practices:cve-exploit-rules] In the network decoy table, the first database scenario lists CrowdStrike (based on IP address), Microsoft Defender and VMware Carbon Black as integrations, and the database command scenarios use sub_type is "mysql", type is "postgresql" and sub_type is "connect", and type is "mongodb". [deception.best-practices:network-database-rules] For network decoys, SSH authentication is type is "ssh" and sub_type is "auth", anonymous FTP login is ftp.command is "USER anonymous", SMB session enumeration is "NetrSessionEnum" in dce_rpc.operation, and web payloads are web.method in ["POST","PUT"]. [deception.best-practices:network-service-rules] Target discovery on network decoys is matched with (sub_type is "scan" and scan.type is "port_scan") or (type is "network" and sub_type is "scan" and scan.type is "ip_scan"). [deception.best-practices:target-discovery-rule]

**Containment, Zero Trust, AD, endpoint and cloud.** In the Zero Trust decoy table, the first database scenario's integrations are CrowdStrike (based on IP address), Private Access (ZPA), Microsoft Defender and VMware Carbon Black. [deception.best-practices:zero-trust-adds-zpa] In the AD decoy table, a login with a decoy account is type is "credtheft" and credtheft.event_id is not "4769" and sub_type is not "honeypot-buster", Kerberoasting is credtheft.event_id is "4769", and AS-REP roasting is type is "credtheft" and credtheft.event_id is "4768" and credtheft.pre_auth_type is "0". [deception.best-practices:ad-rules] In the endpoint deception table, LSASS credential harvesting with decoy breadcrumbs is type is "endpoint" and sub_type is "imc", LLMNR poisoning is type is "endpoint" and sub_type is "mitm", and PSexec is sub_type is "psexec"; the first scenario lists CrowdStrike, Private Access and Internet & SaaS (ZIA) as integrations. [deception.best-practices:endpoint-rules] For cloud deception, Azure user and service principal decoys use threat_parse_ids in ["azure_user","azure_service_principal"], and private S3 and ECR access use threat_parse_ids is "aws_s3" or "aws_ecr" with decoy.public is false. [deception.best-practices:cloud-rules] Integrations are in [Deception and ITDR containment integrations: supported solutions, per-solution setup, identity-based containment (ZIA, ZPA, Okta SSF) and blocked identities](kb:deception.containment-integrations) and rules in [Deception and ITDR orchestration rules: the Orchestrate menu, rule pipeline, actions, testing, pausing and event notification templates](kb:deception.orchestration-rules).
