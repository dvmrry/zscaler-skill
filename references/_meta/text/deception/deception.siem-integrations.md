# Deception and ITDR SIEM integrations: supported SIEMs, the integration list, filters, and the ArcSight, QRadar, Sentinel, DNIF, Splunk, Syslog and Sumo Logic guides (deception.siem-integrations)
Also called: ITDR SIEM integration; ITDR SIEM integrations; Deception SIEM integration; SIEM Integrations page; Include Safe Events

The product hubs are [Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview) and [Identity Protection (ITDR): how it reads identity stores and endpoints, what it needs, and what can be automated](kb:identity-protection.overview). SIEM integrations can be added for ArcSight, IBM QRadar, Microsoft Azure Sentinel, Netmonastery DNIF, Splunk, Syslog and Sumo Logic, to transmit logs in real time (the ITDR page says event logs). [deception.siem-integrations:siem-supported-platforms] The SIEM Integrations page lists Name, Type (the SIEM solution), Connector (the Service Connector forwarding logs), Source (type of log, such as Events or Audit Logs), Last Failure (the last error message, if any) and Enabled. [deception.siem-integrations:siem-list-columns]

**Options common to the guides.** Every SIEM guide (ArcSight, IBM QRadar, Microsoft Sentinel, Netmonastery DNIF, Splunk, Syslog, Sumo Logic) has an Include Safe Events option that forwards events marked as safe to the SIEM. [deception.siem-integrations:include-safe-events] In every SIEM guide (ArcSight, IBM QRadar, Microsoft Sentinel, Netmonastery DNIF, Splunk, Syslog, Sumo Logic) a blank Filter field means all logs are sent to the SIEM (all event logs in the ArcSight, QRadar, Sentinel, DNIF and Syslog guides; all logs in the Splunk and Sumo Logic guides, which also say the Filter option is available only for event logs). [deception.siem-integrations:filter-blank-sends-all] The Filter option is available only for event logs, per the ArcSight, Microsoft Sentinel, Netmonastery DNIF, Splunk, Syslog and Sumo Logic guides (Deception and ITDR) and the ITDR IBM QRadar guide. [deception.siem-integrations:filter-event-logs-only] The ArcSight, IBM QRadar, Netmonastery DNIF and Syslog guides each say to use TCP or UDP according to the SIEM server's configuration, and the ArcSight and Syslog guides have a Transport field with TCP or UDP. [deception.siem-integrations:transport-tcp-udp] The ArcSight, IBM QRadar, Netmonastery DNIF and Syslog guides require network connectivity between the Service Connector and the SIEM server on the port the SIEM is listening on. [deception.siem-integrations:siem-port-connectivity]

**Syslog.** The Syslog guide (Deception and ITDR) offers Events and Audit Logs as the log types to send. [deception.siem-integrations:log-type-choices] In the Syslog guide, if the selected Service Connector is configured in the admin portal, the admin portal sends the logs to Syslog. [deception.siem-integrations:connector-in-portal-sends] In the Deception Syslog guide, if the selected Service Connector is configured on a Decoy Connector, the selected Decoy Connector sends the logs to Syslog. [deception.siem-integrations:connector-on-decoy-connector-sends] For Syslog, Zscaler recommends TCP to avoid issues with the UDP protocol's unreliability, frame limits and fragmented packets. [deception.siem-integrations:syslog-prefer-tcp] The Syslog guide has a Facility field (each event is labeled with a facility code indicating the type of software generating the event logs), a Severity field (each event is labeled with a severity) and an App Name log identifier; the IBM QRadar guide has the same three fields. [deception.siem-integrations:syslog-labels] The Syslog guide gives the command tcpdump -n host <IP address of the Service Connector> and states that the Syslog server receives the event logs. [deception.siem-integrations:syslog-tcpdump-test]

**IBM QRadar.** The QRadar guide goes to Admin > DSM Editor; the log source's Protocol Configuration is Syslog and its Log Source Identifier is service-connector, and Deploy Changes activates the new log source. [deception.siem-integrations:qradar-log-source]

**Microsoft Sentinel.** In the Deception guide, Microsoft has deprecated the legacy log ingestion method, so a Microsoft Sentinel integration configured with it must be reconfigured to use data collection rule-based log ingestion; the guide selects Sentinel DCR from the Add Integration drop-down menu. [deception.siem-integrations:sentinel-dcr-deprecated-legacy] In the Deception Sentinel guide, the integration needs the TCP protocol, a log analytics workspace with Microsoft Sentinel enabled, connectivity between the Service Connector and the Sentinel API server on TCP port 443, an Azure contributor with access to the resource group, and a sample JSON log file for events or audit logs to define the schema; the integration is proxy aware if direct network connectivity is not available. [deception.siem-integrations:sentinel-prereqs] In the Deception Sentinel DCR setup, the Region selected must match the log analytics workspace, Azure automatically appends _CL to the end of the table name, the transformation is source | extend TimeGenerated = now(), and the immutableId value and streamDeclarations name are copied from the data collection rule's JSON View. [deception.siem-integrations:sentinel-azure-objects] The Deception Sentinel DCR guide searches for and reviews the Monitoring Metrics Publisher role, selects the data collection rule created in the previous step, opens Access Control (IAM) and selects the application created in the previous step (for example Zscaler-Deception-Sentinel-App). [deception.siem-integrations:sentinel-rbac] The Deception Sentinel DCR integration form takes Tenant ID, Client ID, Client Secret, DCR Immutable ID, DCE Endpoint (the log ingestion URI) and Stream Name, plus Use Proxy Settings if the Service Connector requires a proxy to connect to the Sentinel server. [deception.siem-integrations:sentinel-portal-fields] The Sentinel guide (Deception and ITDR) says Sentinel starts receiving the logs in 10 to 15 minutes. [deception.siem-integrations:sentinel-latency] The ITDR Microsoft Sentinel guide takes the Log Analytics Workspace ID and Primary key (copied from Settings > Agents management, Windows servers tab) and a Log Type identifier, and selects Sentinel from the Add Integration drop-down menu. [deception.siem-integrations:itdr-sentinel-workspace-key] Whether the ITDR key-based method is the legacy method is open [gap:deception.siem-integrations:itdr-sentinel-legacy].

**Splunk.** The Splunk guide sets up the HTTP Event Collector: All Tokens set to Enabled, Default Source Type _json, the Enable SSL checkbox selected, and a new token with source type _json whose token ID is copied. [deception.siem-integrations:splunk-hec-token] The Splunk guide needs network connectivity between the Service Connector and the Splunk server on a TCP port whose default is 8088, uses HTTP or HTTPS according to the Splunk configuration, and has the Port field set to 8088. [deception.siem-integrations:splunk-port-protocol] For the Splunk cloud platform, http-input- is added to the beginning of the URL; Strict SSL, when enabled, validates the Splunk server's SSL certificate against a list of public certificate authorities, and when disabled turns certificate verification off; Key takes the token ID generated. [deception.siem-integrations:splunk-cloud-host-and-ssl]

**Sumo Logic.** The Sumo Logic guide selects Hosted Collector in the Select Collector Type window and selects the Multiline Processing checkbox; HTTP Collector Endpoint takes the HTTP Source Address URL that was copied, and Use Proxy Settings (if available) enables proxy settings on the Service Connector, if available. [deception.siem-integrations:sumo-http-source]

**ITDR tests for ArcSight and Splunk.** The ITDR ArcSight and Splunk guides test the integration by generating events on the Investigate page. [deception.siem-integrations:itdr-test-from-investigate]

What to check:
1. Whether a Microsoft Sentinel integration in Deception was configured with the legacy log ingestion method Microsoft has deprecated.
2. Whether the Filter field applies to the log type chosen, since the guides say Filter is available only for event logs.
3. Which product the Sentinel answer is about, since the Deception guide selects Sentinel DCR and the ITDR guide uses a Workspace ID and Primary key.

Not known (open gaps):
- Whether the ITDR Sentinel Workspace ID and Primary key method is the legacy ingestion method Microsoft deprecated [gap:deception.siem-integrations:itdr-sentinel-legacy]: settled by support-ticket or lab-test
