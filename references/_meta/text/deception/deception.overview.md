# Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated (deception.overview)
Also called: deception; zscaler deception; decoys; lures; landmine; zero trust network decoys; ztn decoys; decoy connector; threatparse; miragemaker; deception api; zscaler deception rule

Deception is an active-defense product with its own admin portal; it touches Private Access and Client Connector but is managed separately. Zscaler Deception is a targeted threat detection solution that uses lures and decoys to detect and disrupt threats that bypass traditional defenses, such as APTs, exploits, reconnaissance, lateral movement, Active Directory and supply-chain attacks, human-operated ransomware, and SCADA and ICS attacks. [deception.overview:what-it-is] As an integral part of the Zscaler Zero Trust Exchange, Deception tracks the full attack sequence and initiates automated response actions across the Zscaler platform. [deception.overview:zte-response]

**Deployment.** Deception is cloud-delivered, needs minimal on-premises computing and no additional hardware upgrades. [deception.overview:deployment] Network decoys are placed through Decoy Connectors connected to the Deception Admin Portal, with VLANs configured in the environment. [deception.overview:decoy-connectors] The Deception standalone architecture's Admin Portal is a Zscaler-hosted cloud UI and central point of management and analysis that Decoy Connectors and software agents connect to; Decoy Connectors are virtual appliances that create decoys within trunked VLANs and can relay integrations to applications such as AD, SIEM and firewalls. [deception.overview:portal-and-connector-components] In the standalone architecture, the Landmine component is a software agent installed on endpoints such as desktops or laptops that deploys decoy credentials, files, processes, and lures to other decoys. [deception.overview:landmine-component] In the ZPA-integrated architecture, when an adversary breaks into the network and interacts with a decoy, Deception uses Zero Trust access policies to block the adversary's traffic to legitimate applications and contain the adversary to one system, building the picture from ZPA user and device identity; ZPA-based decoys are described as giving better visibility, intelligence and containment than non-ZPA decoys. [deception.overview:zpa-integrated-containment] With the ZPA integration, no additional Decoy Connectors or network configuration changes are needed to add deception to the environment, and the Landmine agent's lures direct adversaries toward decoy applications. [deception.overview:zpa-no-extra-connectors] Decoy Connector platforms, sizing and connection are in [Decoy Connectors: platforms, sizing, connectivity, connection and credentials](kb:deception.decoy-connectors), subnets and interfaces in [Topology: subnets and interfaces, aggregator sinkholes, ZPA App Connectors and Windows high-interaction VM credentials](kb:deception.topology), and the Landmine agents in [Landmine agent and agentless: install, requirements, proxies, management and OS feature support](kb:deception.landmine-agents) with their settings in [Endpoint settings (installer, lure refresh, update groups, safe processes) and Admin Portal settings (audit, error and debug logs, license, event and evidence export and delete, retention)](kb:deception.endpoint-settings).

**Setup.** The step-by-step configuration guide lists six steps: log in to the Admin Portal, configure users and roles, optionally configure single sign-on, launch the deception campaign, configure SIEM integration, and configure alert notifications. [deception.overview:configuration-guide-steps] The configuration guide lists ArcSight, IBM QRadar, Microsoft Azure Sentinel, Netmonastery DNIF, Splunk, Syslog and Sumo Logic as supported SIEM integration platforms, configured through a Service Connector that forwards logs in real time. [deception.overview:configuration-guide-siem-platforms] Email alert notifications can be configured per user and are sent when there is an issue with the decoys, license, or system, not when something happens on the decoys; Orchestrate rules can be added to create alerts when something happens on the decoys. [deception.overview:configuration-guide-notification-scope] Sign-in, users and roles, account settings and allowed IPs are in [Deception Admin Portal: sign-in, navigation, users and roles, account settings, allowed IPs and QoS events](kb:deception.admin-portal), single sign-on in [Deception and ITDR single sign-on and authentication settings: Authentication Service, SAML and OpenID identity providers, password login, OTP and support access](kb:deception.sso), and recommended deployments in [Best-practice guides: decoy minimums, landmine policy tables, containment rule expressions per decoy type, and the use-case recipes still open](kb:deception.best-practices).

**Decoys.** Decoy types are network, Threat Intelligence (TI), Active Directory (AD), endpoint and cloud decoys; Miragemaker datasets make them more realistic. [deception.overview:decoy-types] Deceive configures and deploys decoys across public-facing endpoints, network, cloud and AD; its stated key features are stopping lateral movement, disrupting ransomware, detecting compromised users, detecting prebreach threats via TI decoys, and detecting enumeration activity and malicious access via AD decoy users. [deception.overview:deceive-key-features] A Deception Strategy configures Network, TI and AD decoys and Landmine policies on one page from predefined personalities (built-in or custom strategies), and is deployed as Internal or Zero Trust Network (ZTN) decoys. [deception.overview:strategy] The attacker-facing MCP server decoy is in [Deception's MCP server decoy: an attacker-facing Gen AI service, not a management interface](kb:deception.mcp-server-decoys); what each plan includes is in [Deception Standard and Advanced plans: decoy counts, Gen AI decoys, orchestration and API access](kb:deception.plans). The decoy types are in [Network decoys (Internal and Zero Trust Network): personalities, creation, AD join, MITM detection, RADIUS and management](kb:deception.network-decoys), [Threat Intelligence (internet-facing) decoys: what they detect, how they are created, exported and tested](kb:deception.ti-decoys), [Active Directory decoys: domains, decoy users and computers, the deployment script, and the alert triggers that feed them](kb:deception.ad-decoys), [Interactive and file-based Gen AI decoys: types, datasets, limits, deployment targets and testing](kb:deception.gen-ai-decoys), [Cloud Deception model shared by Azure, AWS and GCP: detection, deployment, status and deletion](kb:deception.cloud-decoys), [Landmine policies: what they deploy, which endpoints they select, and how the Windows endpoint deployment is set up](kb:deception.landmine-policies) and [Landmine decoy modules and lures: what each deploys, on which operating systems, and how it is tested](kb:deception.landmine-decoys), and Miragemaker and its datasets in [Deception Miragemaker: strategies, decoy personalities, banners, tags, datalists and ThreatParse rules](kb:deception.miragemaker) and [Deception datasets: application, high-interaction container, SCADA/IoT, keyword, custom service and file datasets, and CVE handlers](kb:deception.datasets). Decoy deployment is in [Deploying and stopping decoys, the Deploy Strategy wizard, and Deceive Settings (blocklists, hashed passwords, hostname resolution, decoy groups)](kb:deception.decoy-deployment).

**Detection and response.** When an attacker interacts with decoys, Deception collects the attacker's actions and intentions and generates high-fidelity, real-time alerts; because no legitimate traffic goes to decoys, any interaction is a high-confidence signal. [deception.overview:detect] ThreatParse reconstructs attacks in natural language, summarizing log information in plain English to help the SOC and analysts understand what the attacker is trying to accomplish. [deception.overview:threatparse] Orchestration rules take immediate automated actions when events are discovered, and once an attacker's targets are known Deception deploys additional decoys to validate remediation. [deception.overview:orchestrate-remediate] Rules, actions and event templates are in [Deception and ITDR orchestration rules: the Orchestrate menu, rule pipeline, actions, testing, pausing and event notification templates](kb:deception.orchestration-rules), containment integrations in [Deception and ITDR containment integrations: supported solutions, per-solution setup, identity-based containment (ZIA, ZPA, Okta SSF) and blocked identities](kb:deception.containment-integrations), and Service Connectors in [Deception and ITDR Service Connectors: built-in and external connectors, API tokens, command line and deletion](kb:deception.service-connectors). The dashboard is in [Deception Investigate: the dashboard, containment actions, event logs and evidence](kb:deception.investigate), SIEM integrations in [Deception and ITDR SIEM integrations: supported SIEMs, the integration list, filters, and the ArcSight, QRadar, Sentinel, DNIF, Splunk, Syslog and Sumo Logic guides](kb:deception.siem-integrations), enrichment integrations in [Deception and ITDR enrichment integrations: supported sources, credentials needed, and the event-log fields each adds](kb:deception.enrichment-integrations), and the query syntax used in filters and conditions in [Deception query language: operators, constants, precedence and flags used in filters, rule conditions and ThreatParse rules](kb:deception.query-language).

**Roles.** Roles are Administrator (configures Decoy Connectors, deploys decoys, analyzes events, orchestrates actions), Analyst (investigates, blocks attackers, exports logs), Responder (analyzes events, orchestrates actions), Super admin (manages all features, including user roles, APIs, decoys and audit logs), and custom roles with chosen read and write permissions. [deception.overview:roles] Predefined roles, custom roles and users are in [Deception Admin Portal: sign-in, navigation, users and roles, account settings, allowed IPs and QoS events](kb:deception.admin-portal).

## What it changes in Private Access

Where Private Access (ZPA) is deployed, Deception can integrate with it to deploy Zero Trust Network decoys without installing additional network components or changing the network configuration. [deception.overview:zpa-integration] Objects Deception creates in Private Access are locked in the console: a Deception access rule's order cannot be updated and regular rules must order after it ([The rule order of an access policy configured using Zscaler Deception cannot be updated, and a regular access policy's rule order must be greater than that of a Deception-configured policy; copy, edit and delete are unavailable on Deception-configured rules.](kb:zpa.policy.access-rule-order:deception-order-constraint)), and Deception segment groups, connector groups, provisioning keys and log receivers cannot be edited or deleted ([If a segment group is configured using Zscaler Deception, the console's edit and delete options are unavailable.](kb:zpa.segment-groups.scope:deception-locked), [A group configured with Zscaler Deception, or managed by Zscaler, has its edit and delete options unavailable.](kb:zpa.app-connectors.connector-groups:managed-read-only), [A provisioning key configured with Zscaler Deception, or managed by Zscaler, has its edit and delete options unavailable.](kb:zpa.app-connectors.provisioning-keys:deception-managed-read-only), [If a log receiver is configured using Zscaler Deception, the copy, edit and delete options are unavailable.](kb:zpa.log-receivers.admin-console:deception-readonly)). The MCP server's access-policy skill places a licensed Deception rule first in the order, as an auto-provisioned tenant feature whose default rule must not be modified. [deception.overview:mcp-zpa-skill] The ZPA Terraform provider's handling of the rule named Zscaler Deception, which differs between v4.4.15 and v4.4.16, is in [From v4.1.13 through v4.4.15, if the rule named "Zscaler Deception" at order 1 is itself listed in the configuration, it is neither pinned to 1 nor added to the map: the loop skips it, and the comparator then treats it as an unmanaged rule. From v4.4.16 the loop has no skip, so a configured Deception rule is neither pinned nor does it trigger the offset, and goes into the map at its configured number like any other configured rule.](kb:zpa.terraform.rule-order:configured-deception-rule-treated-as-unmanaged) and [Up to v4.4.15, when the "Zscaler Deception" rule sat at order 1, Update sent every configured rule at its configured number plus one, but Read wrote back the API's number unchanged, so a configuration that numbers its rules from 1 could show a difference on every plan. From v4.4.16 Read subtracts the same offset, and the provider's changelog says such a configuration no longer shows a change in every plan.](kb:zpa.terraform.rule-order:deception-offset-drift).

## What it changes in Client Connector

Deception is a Client Connector service entitlement ([Service entitlement selects which user groups or device groups can enroll into Private Access (ZPA), Digital Experience (ZDX) and Zscaler Deception; Internet & SaaS (ZIA) enrollment is enabled for all users by default.](kb:zcc.entitlements:services-gated)); a device's Deception settings OTP is `deceptionSettingsOtp` ([By name, the response's `logoutOtp`, `revertOtp`, `uninstallOtp`, `exitOtp`, `ziaDisableOtp`, `zpaDisableOtp`, `zdxDisableOtp`, `deceptionSettingsOtp` and `antiTemperingDisableOtp` are the portal's Logout, Revert, Uninstall, Exit, Disable ZIA, Disable ZPA, Disable ZDX, Deception Settings and Disable Anti-Tampering OTPs.](kb:zcc.passwords-and-otp.otp:otp-field-mapping)), and the password that disables Deception is `zdpDisablePass` ([The `managePass` contract describes `zadDisablePass` as the password to disable Zscaler Active Defense (ZAD) and `zdpDisablePass` as the password to disable Zscaler Deception.](kb:zcc.passwords-and-otp.password-api:zad-zdp-names)). The MCP server's ZCC OTP skill describes `deception_settings_otp` as the OTP that modifies Deception settings on the device. [deception.overview:mcp-zcc-otp]

## Automation

No vendored client manages Deception itself: the Go and Python SDKs, the Terraform providers, the Ansible collections, the MCP server and the OneAPI Postman collection mention Deception only through Private Access and Client Connector objects, not through decoys, strategies or alerts. [deception.overview:no-client-surface] Token fields and expiry are in [Deception and ITDR API tokens: OpenAPI scope, token fields, expiry and one-time display](kb:deception.api-tokens). API access exists in the product (Super admin manages APIs, and only the Advanced plan includes it: [In the Enterprise settings table, single sign-on and audit logs are supported on both plans; API access is not supported on the Standard Plan and supported on the Advanced Plan; custom roles are listed only in the Advanced Plan column (Standard lists predefined only).](kb:deception.plans:enterprise)), but its endpoints and the lifecycle of the Private Access objects Deception owns are open [gap:deception.overview:admin-api].

What to check:
1. Before changing Private Access policy order, segment groups, connector groups, provisioning keys or log receivers, whether the object was created by Deception, which the console treats as read-only.
2. For a Terraform plan that keeps renumbering access rules, which ZPA provider version is in use and whether a rule named Zscaler Deception sits at order 1.
3. Answer Deception automation questions as unsupported by any vendored client, and say that the product's API needs the Advanced plan and is not documented in any capture.
