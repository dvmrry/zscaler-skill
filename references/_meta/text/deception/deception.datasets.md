# Deception datasets: application, high-interaction container, SCADA/IoT, keyword, custom service and file datasets, and CVE handlers (deception.datasets)
Also called: application datasets; cve datasets; vulnerable application datasets; cve handler; high-interaction containers; scada/iot datasets; file templates

See also [Zscaler Deception: decoys and lures, the Private Access integration, roles, and what can be automated](kb:deception.overview), [Deception Miragemaker: strategies, decoy personalities, banners, tags, datalists and ThreatParse rules](kb:deception.miragemaker) and [Deception Investigate: the dashboard, containment actions, event logs and evidence](kb:deception.investigate).

**Application datasets.** Application datasets are static (front ends of static HTML, CSS and JavaScript files), vulnerable application datasets (CVE datasets; requests and responses mimicking dynamic applications), dynamic (a static front end combined with a vulnerable dataset's interactions) and high-interaction container (docker-based) datasets, and the page describes deploying the datasets using TI decoys or web services on network decoys, and the custom protocol container page describes deploying that non-web container dataset as a network decoy. [deception.datasets:application-dataset-kinds] Static application datasets configure the front ends of web applications deployed through TI decoys and network decoys via web services; they consist of static HTML, CSS and JavaScript files used to engage adversaries submitting credentials or attempting text-based web application attacks, and can be associated with dynamic or high-interaction applications to make responsive decoys. [deception.datasets:static-application-purpose] A static application dataset is uploaded as a .zip whose files must be at the root of the archive, not in a subdirectory. [deception.datasets:static-zip-root] A static application dataset has a web server banner, hostname keywords and subdomains (used by the Admin Portal to recommend hostnames and subdomains for decoys) and a MAC manufacturer. [deception.datasets:static-dataset-fields] Deception provides a few predefined static application datasets that can be used to deploy network decoys. [deception.datasets:static-dataset-predefined] A dynamic application dataset takes a vulnerable application dataset for its dynamic interactions and, optionally, a fallback static application dataset to render the front-end UI, plus an optional web server banner. [deception.datasets:dynamic-dataset-composition] Dynamic application datasets are used in TI decoys and network decoys, with the dynamic interactions configured through vulnerable application datasets and the front-end UI through associated static application datasets. [deception.datasets:dynamic-dataset-uses]

**Vulnerable application datasets.** Vulnerable application datasets are typically based on CVE disclosures but can also mimic any vulnerability, even without a CVE disclosure. [deception.datasets:vulnerable-dataset-no-cve-needed] A vulnerable application dataset requires a Python handler created beforehand and uploaded as a .py file no larger than 5 MB; vulnerability classification and CVE ID are optional. [deception.datasets:vulnerable-dataset-handler-upload] The Vulnerable Application Datasets page lists Name, Vulnerability Classification, CVE ID, Linked Dynamic Applications and Description. [deception.datasets:vulnerable-dataset-list-columns] Whether the handler file name must match its CVE ID [gap:deception.datasets:handler-file-name].

**CVE handlers.** A CVE handler is a Python file that teaches a decoy how to respond to exploit attempts targeting a specific vulnerability; each lives at datasets/aicve/<CVE-ID>.py and is validated by an AST parser before upload. [deception.datasets:handler-location-and-validation] A handler file requires three top-level pieces: a CVE_ID string constant, one or more async handler functions, and a ROUTES list; imports, constants and helper functions are allowed and not inspected. [deception.datasets:handler-required-pieces] CVE_ID must be a plain string literal at module level, not computed from a function call, read from a file or defined inside a conditional block. [deception.datasets:handler-cve-id-literal] Each routed handler function must be declared async def, accept exactly one argument (the Starlette Request object) and be annotated -> Response, although any Starlette response subclass can be returned at runtime. [deception.datasets:handler-function-rules] ROUTES is a module-level list literal of dicts each with METHOD (GET, POST, PUT, DELETE, PATCH, HEAD or OPTIONS), PATH (a string literal starting with /, supporting Starlette path parameters) and HANDLER (a bare function reference); duplicate method and path pairs in one file are rejected. [deception.datasets:handler-routes-rules] A function not referenced in ROUTES is ignored by the validator, which checks only CVE_ID, ROUTES and the functions referenced by ROUTES. [deception.datasets:handler-unrouted-ignored] A {name} path segment matches a single path component and {name:path} matches everything including slashes; captured values are read through request.path_params. [deception.datasets:handler-path-params] Handlers get an in-memory session store at request.state.sessions with async create(data, ttl=300), get(key), set(key, data, ttl=300) and delete(key) methods; its data is lost on decoy restart. [deception.datasets:handler-session-store] The handler validator is downloaded as TXT, renamed to .py and run with python3 <validator>.py --file-path <handler>.py, printing OK: <file> on success or FAIL: <error-message> on failure. [deception.datasets:handler-validator-run] Validator errors include 'Handler must assign CVE_ID as a string', 'Handler must define ROUTES as a list literal', 'ROUTES entry N: duplicate route', and handler must accept exactly 1 parameter and have return type annotation -> Response. [deception.datasets:handler-validation-errors]

**High-interaction containers.** High-interaction container datasets are Web (web application containers, deployable as TI or network decoys) or Custom (custom protocol containers for non-web applications such as a PostgreSQL server, deployed as network decoys). [deception.datasets:hic-types-and-deployment] A high-interaction container dataset is a single docker image holding all components the application needs, saved with docker save and compressed with gzip before upload; the ENTRYPOINT script must not exit or the service stops. [deception.datasets:hic-image-requirements] The page's example for a docker container that runs a WordPress instance builds the image with docker build --tag <image-name> . and then saves it with docker save wordpress:latest > <image-name>. [deception.datasets:hic-image-example-commands] The port of a web application container dataset cannot be changed after saving; changing it requires deleting the container and uploading the docker image again. [deception.datasets:hic-port-immutable] Some high-interaction container datasets might capture fewer metrics than their static counterparts, because the request data format varies from application to application. [deception.datasets:hic-metrics-caveat]

**SCADA/IoT datasets.** Deception provides device-based datasets that mimic specific SCADA/IoT devices and protocol-based datasets that mimic generic SCADA/IoT devices, and custom datasets can be uploaded. [deception.datasets:scada-default-datasets] The SCADA/IoT page's table of supported protocols lists BACnet, DNP3, EtherNet/IP, Guardian AST, HTTP, IEC 60870-5-104, IEC 61850, IPMI, Kamstrup, Modbus, OPC UA, PROFINET, S7comm and SNMP. [deception.datasets:scada-protocols] The SCADA/IoT page labels two protocols differently in its two tables: the protocol table has IEC 60870-5-104 and Guardian AST, while the datasets table has a dataset named IEC 104 whose Protocols Supported column lists IEC 104, and a dataset named Guardian AST whose Protocols Supported column lists GUARDIAN_AST. [deception.datasets:scada-protocol-labels] The Building Automation - Siemens PLC dataset lists Modbus, OPC UA, PROFINET, S7comm, ENIP, BACnet, HTTP, IPMI and SNMP as its supported protocols. [deception.datasets:scada-dataset-example-multiprotocol] A custom SCADA/IoT dataset is made by downloading an existing dataset as a .zip, changing it as needed, and uploading it under Dataset/Templates (Zip File); it is then used in network decoys. [deception.datasets:scada-custom-dataset-workflow] Dataset rows beyond the example [gap:deception.datasets:scada-dataset-rows].

**Keyword and custom service datasets.** Keyword datasets take one keyword per line and are used to autogenerate recommendations for decoy parameters such as hostnames, file and folder names and network decoy names. [deception.datasets:keyword-config] Configured keywords are included in addition to randomly generated recommendations; a keyword is part of the generated text and never used alone, only one keyword is used per recommendation, and with multiple keywords one is chosen randomly. [deception.datasets:keyword-recommendation-rules] A custom service dataset creates custom network services with customized requests and responses over any binary or text-based application-layer protocol, deployed through network decoys on a configured port and TCP or UDP. [deception.datasets:custom-service-purpose] A custom service dataset has a Binary or Text protocol type and optional banner and default response; for binary protocols the banner, default response and request and response messages must be Base64-encoded text. [deception.datasets:custom-service-fields]

**File datasets and templates.** File datasets configure network decoys (services that host files, such as Shares and FTP) and landmine decoys, and a GenAI icon marks a generative AI file dataset. [deception.datasets:file-dataset-uses] A static file dataset gives each decoy an exact copy of its uploaded .zip files, while a dynamic file dataset generates a new set of files every time a decoy is deployed. [deception.datasets:file-dataset-static-dynamic] A dynamic file dataset is parameterised by file classification by department, file templates, custom keywords used in file name permutations, a minimum and maximum date, and folder and file-per-folder ranges used to randomly select a few folders and files each time an instance is generated for a decoy. [deception.datasets:file-dataset-dynamic-fields] A file template is uploaded as a .zip and is used as a baseline when adding dynamic file datasets. [deception.datasets:file-template-baseline] The File Templates page (Miragemaker > Files > File Templates) lists predefined and custom file templates, which are a baseline for file datasets; from it you can add a custom file template, download a file template, and edit or delete a file template. [deception.datasets:file-templates-page]

**Defaults and downloads.** Default static application, vulnerable application, dynamic application, high-interaction container, SCADA/IoT, custom service and file datasets and file templates cannot be edited or deleted. [deception.datasets:default-datasets-readonly] Static application, vulnerable application, SCADA/IoT and file datasets and file templates, both default and custom, download individually as a ZIP file. [deception.datasets:download-formats] Upload size limits [gap:deception.datasets:zip-upload-limits].

What to check:
1. Whether a dataset is a default one before advising an edit or deletion.
2. Whether the files of a static application dataset zip sit at the archive root.
3. Whether a CVE handler declares CVE_ID as a string literal, routes async functions annotated -> Response and passes the validator.
4. Whether a web application container's port is final before saving, since changing it means uploading the docker image again.
5. Whether a protocol name is read from the protocol table or the datasets table, since the two label some protocols differently.
