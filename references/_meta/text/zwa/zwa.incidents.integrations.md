# Workflow Automation integrations: DLP GCP privacy settings, Slack, Microsoft Teams, ServiceNow and Jira Software (zwa.incidents.integrations)
Also called: zwa integrations; dlp gcp integration; zwa slack integration; zwa teams integration; zwa servicenow; zwa jira; integration users; jira cloud integration; labels not supported; hide evidence data

The Integration page adds the source of DLP incidents to Workflow Automation, and the Integration page lists ServiceNow and Jira Software as the applications available within Workflow Automation. [zwa.incidents.integrations:integration-kinds] [divergence:zwa.incidents.integrations:integration-app-list] The AWS, Azure and GCP integrations are in [The AWS DLP application integration for Workflow Automation: the two forwarding methods, the three AWS resources, regions, support role and validation](kb:zwa.aws-dlp-integration), [The Azure DLP application integration for Workflow Automation: the two forwarding methods, required outputs, fields, validation and privacy settings](kb:zwa.azure-dlp-integration) and [The GCP DLP application integration for Workflow Automation: Cloud-to-Cloud only, fields, validation and privacy settings](kb:zwa.gcp-dlp-integration), and incident ingestion is in [Workflow Automation incidents: where they come from, who gets them, statuses, search limits and closing or deleting](kb:zwa.incidents). Who can configure them differs between pages [divergence:zwa.incidents.integrations:integration-admin-access].

**DLP GCP integration.** Super admins or admins with Full or Restricted access to Workflow Automation can configure the DLP GCP application integration, which must exist before incidents are available on the Incidents page. [zwa.incidents.integrations:gcp-admin-access] Adding a DLP GCP integration requires GCP cloud resources and the client_email, private_key and project_id from the service account key; the integration also takes a prefix for the storage bucket and topic. [zwa.incidents.integrations:gcp-prerequisites] A DLP GCP integration can be added only if Validate passes; on the add page, after a failed validation or wrong values the integration must be disabled, corrected and re-enabled, and on the edit page the values are corrected first and the integration then disabled and re-enabled. [zwa.incidents.integrations:gcp-validate] DLP GCP connected accounts show Enabled, Disabled or Failed; only those can be deleted, and Deleted accounts can have only their data privacy settings edited. [zwa.incidents.integrations:gcp-statuses] On the tile, the connected-accounts count excludes accounts with a Failed or Deleted status. [zwa.incidents.integrations:gcp-connected-count]

**DLP GCP privacy settings.** Admin privacy settings on the DLP GCP integration: Hide Evidence Data - Admin and Hide Trigger Data - Admin are selected by default; Hide Policy Details - Admin and Hide Policy Details for Non-Triggered Matches - Admin are not. [zwa.incidents.integrations:gcp-privacy-admin] End user privacy settings on the DLP GCP integration: Hide Evidence Data, Hide Trigger Data and Hide Policy Details are selected by default; the non-triggered-matches setting is available only when Hide Policy Details - End User is not selected. [zwa.incidents.integrations:gcp-privacy-end-user] Manager/Approver privacy settings on the DLP GCP integration: Hide Evidence Data, Hide Trigger Data and Hide Policy Details are selected by default; the non-triggered-matches setting is available only when Hide Policy Details - Manager/Approver is not selected. [zwa.incidents.integrations:gcp-privacy-manager] Hide Policy Details for Non-Triggered Matches - Admin hides the Non-Triggered Engines and Dictionaries section and the Other Matched Rules section of the policy details. [zwa.incidents.integrations:gcp-non-triggered-scope] If Hide Evidence Data or Hide Trigger Data is disabled but read access to the storage accounts was not enabled when the cloud resources were created, no one can generate evidence links or view trigger data in the Admin Console. [zwa.incidents.integrations:gcp-no-read-access] The same flags as the admin sees them in the drawer are in [The Incident Details drawer: fields by Source DLP type, actions and status changes, quarantine release errors, tickets and privacy gates](kb:zwa.incidents.details); as end users see them in notifications, in [User, escalation and digest notifications and reminders as the recipient sees them: contents, link lifetime, privacy gates, quarantine release and policy exceptions](kb:zwa.incidents.notifications). Their defaults for the non-triggered end user and manager settings are open [gap:zwa.incidents.integrations:gcp-non-triggered-defaults].

**Slack and Microsoft Teams.** Slack, Microsoft Teams, ServiceNow and Jira Software integrations each require a DLP application integration (AWS, Azure or GCP) to be configured first, and admin credentials for the application. [zwa.incidents.integrations:dlp-integration-first] Slack and Microsoft Teams are integrated by adding them as SaaS application tenants under Data Security > DSPM > SaaS Application Tenants with the Workflow Automation checkbox selected under Select Features, which authorizes them with Internet & SaaS (ZIA). [zwa.incidents.integrations:slack-teams-tenant] With Slack or Teams integrated, user, escalation and digest notifications can be delivered as messages, and workflow definitions can select Slack or Teams messages instead of email. [zwa.incidents.integrations:chat-uses] Where Channel Type appears in the drawer is in [The Incident Details drawer: fields by Source DLP type, actions and status changes, quarantine release errors, tickets and privacy gates](kb:zwa.incidents.details).

**ServiceNow.** ServiceNow and Jira Software are added as SaaS application tenants with the Workflow Automation checkbox in Select Features; the ServiceNow tile then appears under Connected Apps, and for Jira the tile is named Jira Cloud. [zwa.incidents.integrations:ticketing-tenant] The user a ServiceNow ticket is assigned to must exist in ServiceNow and already be on the Integration Users page in Workflow Automation. [zwa.incidents.integrations:servicenow-ticket-user] ServiceNow ticket-status sync is optional and runs daily; when the ticket is closed in ServiceNow only the Closed status appears on the drawer, and an optional setting closes the incident when Workflow Automation receives Closed. [zwa.incidents.integrations:servicenow-sync] ServiceNow integrations show Enabled or Disabled statuses, and deleted integrations cannot be enabled or disabled. [zwa.incidents.integrations:servicenow-deleted]

**Jira Software.** A Jira ticket assignee must exist in Jira Software and already be on the Integration Users page, and the admin chooses the Jira project when creating the ticket. [zwa.incidents.integrations:jira-user-project] Before a Jira ticket can be created from the Incident Details drawer, project settings must be configured, including field mappings and a complete status; all projects and their metadata sync when the integration is first enabled, and the project list can be synced manually with Sync Project List. [zwa.incidents.integrations:jira-project-settings] Jira project-list and ticket-status syncs are optional and each run daily; only the project's chosen complete status appears in the Ticket section, and Close incident when ticket is closed is a further option, without which Workflow Automation does not automatically close. [zwa.incidents.integrations:jira-sync-settings] Jira field mapping is per project and issue type: required Jira fields are listed and cannot be deleted (only edited), Issue Type is auto-mapped and not editable, and optional field mappings can be edited or deleted. [zwa.incidents.integrations:jira-field-mapping] A Jira project's Auto Sync is disabled when its field mapping is empty or when the Labels field is not supported for the project; Workflow Automation uses labels to find and sync tickets, and for Labels Not Supported the fix is to add the Labels field to the Jira project. [zwa.incidents.integrations:jira-autosync-disabled] Each Jira project has a Complete Status chosen from the project's statuses; until one is selected the field shows Click to change status. [zwa.incidents.integrations:jira-complete-status] Deleted Jira Cloud integrations cannot be enabled or disabled. [zwa.incidents.integrations:jira-deleted] How often the syncs run and which complete statuses exist is only partly stated [gap:zwa.incidents.integrations:sync-schedule-and-statuses].

What to check:
1. Whether the DLP application integration is configured before looking at a Slack, Teams, ServiceNow or Jira integration, since each page lists it first.
2. For a Jira project whose Auto Sync is disabled, whether the field mapping is empty or the Labels field is missing from the project.
3. When evidence links or trigger data are missing in the Admin Console, the Hide Evidence Data and Hide Trigger Data settings on the DLP GCP integration and whether read access to the storage accounts was enabled.

Sources disagree (name both sides):
- The Integration page names ServiceNow and Jira Software as the applications available within Workflow Automation, while the Slack and Microsoft Teams pages integrate those two applications as SaaS application tenants. [divergence:zwa.incidents.integrations:integration-app-list]
  - zscaler-help: The applications available within Workflow Automation are ServiceNow and Jira Software.
  - zscaler-help: Slack is added as a SaaS application tenant and integrated with Workflow Automation; the Teams page says the same for Microsoft Teams.
  Impact: ServiceNow and Jira Software are not the only applications that integrate with Workflow Automation; Slack and Microsoft Teams are integrated through the same SaaS tenant route.
- The Integration page says all admins can configure the AWS, Azure and GCP integrations, while the GCP page limits configuration to super admins or admins with Full or Restricted access to Workflow Automation. [divergence:zwa.incidents.integrations:integration-admin-access]
  - zscaler-help: All admins can configure the DLP AWS, Azure and GCP application integrations.
  - zscaler-help: Super admins or admins with Full or Restricted access to Workflow Automation can configure the DLP GCP application integration.
  Impact: Which admins can configure an integration is not settled between the overview and the GCP page; an admin without Full or Restricted access may or may not be able to.
