# The AWS DLP application integration for Workflow Automation: the two forwarding methods, the three AWS resources, regions, support role and validation (zwa.aws-dlp-integration)
Also called: aws dlp integration; dlp aws application integration; zir aws; zscaler incident receiver aws; cloud-to-cloud incident forwarding aws; workflow automation s3 bucket; iam cross-account role external id

Configuring the AWS DLP application integration through Zscaler Incident Receiver means deploying a Zscaler Incident Receiver (ZIR) AWS EC2 instance, so that the organization can receive incident metadata files and the evidence file from ZIR and upload them to its S3 buckets. [zwa.aws-dlp-integration:ir-method] The Cloud-to-Cloud Incident Forwarding page introduces the AWS DLP application integration with an AWS EC2 instance using Cloud-to-Cloud Incident Forwarding as enabling the organization to send DLP incident metadata and evidence files to its S3 buckets in its AWS account without deploying appliances. [zwa.aws-dlp-integration:c2c-method] Zscaler recommends the AWS S3 storage bucket when configuring the ZIR for Workflow Automation; the Cloud-to-Cloud page gives the same recommendation for Cloud-to-Cloud Incident Forwarding. [zwa.aws-dlp-integration:recommend-s3-for-zir]

**Resources.** The AWS integration requires three AWS resources: S3 buckets, an SNS topic that the metadata bucket pushes notifications to (subscribed by the Workflow Automation SQS queue), and an IAM cross-account role for the Workflow Automation AWS account's access to the data and metadata buckets, which the page describes as read-only. [zwa.aws-dlp-integration:three-resources] The data and metadata buckets are named <bucketNamePrefix>-data and <bucketNamePrefix>-metadata; the service reads and stores the incident metadata file (trigger data stripped) but never reads and stores the incident data files. [zwa.aws-dlp-integration:bucket-names] The metadata S3 bucket publishes ObjectCreated notifications to the SNS topic, and the Zscaler service subscribes an SQS queue in the Zscaler AWS account to that topic. [zwa.aws-dlp-integration:notification-flow]

**Access and regions.** Read permission on the data S3 bucket is only required if users who respond to incidents are to view incident data files through short-lived presigned S3 URL links. [zwa.aws-dlp-integration:data-bucket-read-optional] Zscaler recommends the metadata bucket and the SNS topic always be in the same region; if Workflow Automation is to generate presigned links, the data buckets must also be in that region. [zwa.aws-dlp-integration:same-region] On the add integration page the IAM Cross-Account Role External ID is automatically populated and cannot be changed; it is the same value as the Customer GUID on the Account Settings page. [zwa.aws-dlp-integration:external-id]

**Support role.** The CloudFormation createSupportRole option creates an additional support role that Zscaler Support can assume and use to assist with troubleshooting; the role is restricted and cannot access incidents or their data, and creating it is optional (default true). [zwa.aws-dlp-integration:support-role] For a manually created support role, the documented policy lists six S3 actions (s3:GetBucketPolicyStatus, s3:GetBucketOwnershipControls, s3:GetBucketAcl, s3:GetBucketNotification, s3:GetBucketLocation, s3:GetBucketPolicy), three SNS actions (sns:ListSubscriptionsByTopic, sns:GetTopicAttributes, sns:GetSubscriptionAttributes) and four IAM actions (iam:GetRole, iam:GetRolePolicy, iam:ListRolePolicies, iam:ListAttachedRolePolicies). [zwa.aws-dlp-integration:manual-support-role-policy]

**Validation.** Validate checks that the IAM cross-account role ARN entry is valid and the SNS topic ARN format is correct, and the integration can only be added if it passes; after a validation failure or wrong values the integration must be disabled and enabled once corrected. [zwa.aws-dlp-integration:validate-before-add] What a Validate failure reports is open [gap:zwa.aws-dlp-integration:validation-failure-detail]. What to check:
1. Which method the integration uses: the Zscaler Incident Receiver method deploys a ZIR AWS EC2 instance, and the Cloud-to-Cloud page is inconsistent on whether that method needs an EC2 instance.
2. Whether the metadata bucket and SNS topic are in the same region, and the data buckets too when presigned links are wanted.
3. Whether Validate passed, and whether the integration was disabled and enabled after the values were corrected.

Sources disagree (name both sides):
- The Cloud-to-Cloud page ties the AWS integration to an EC2 instance and also says it deploys no appliances. [divergence:zwa.aws-dlp-integration:c2c-ec2-appliances]
  - zscaler-help: The introduction and step 3 place the Cloud-to-Cloud integration on an AWS EC2 instance.
  - zscaler-help: The same introductory sentence says the files are sent to the S3 buckets without deploying appliances.
  Impact: Whether the Cloud-to-Cloud method needs an EC2 instance is not settled by the page; the ZIA Cloud-to-Cloud forwarding subject does not mention EC2.
