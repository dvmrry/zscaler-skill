# Workflow Automation incidents: where they come from, who gets them, statuses, search limits and closing or deleting (zwa.incidents)
Also called: workflow automation; zwa; dlp incident management; zwa incidents; incident groups; zwa incident status; zwa delete incident; zwa search limit; unassigned dlp incident; zscaler workflow automation; transaction id search; dlp triggered but no zwa incident

Workflow Automation lets governance admins automate the management and resolution of DLP incidents, through an Incidents page that lists all the Data Protection incidents with their details: the metadata for each incident and the data that triggered it. [zwa.incidents:purpose] Where its incidents come from is in [Workflow Automation integrates with ZIA to capture the Data Protection incidents generated from the DLP policies defined in ZIA, and its Incidents page covers Inline, Endpoint, Email and SaaS Security DLP.](kb:zia.dlp.incident-forwarding:zwa-captures-incidents); how they are ingested is below ([zwa.incidents:dlp-integration-required]).

## Ownership

Individual incidents can be grouped into incident groups, the groups given priorities, and the groups assigned to different admins. [zwa.incidents:incident-groups] Workflow Automation assigns an incident to an admin with edit access to its incident group; if the violated rules belong to an incident group not mapped to an admin, the incident is not assigned automatically and super admins assign it manually. [zwa.incidents:assignment] A restricted admin can only assign an incident to a super admin, and only DLP admins with full access can assign incidents to DLP admins with restricted access. [zwa.incidents:restricted-admin] An incident's priority is derived from its incident groups; when the groups have different priorities, the highest is used, so changing an incident's groups can change its priority. [zwa.incidents:group-priority] Group mappings, rule order and priorities are in [Incident groups, group mappings (properties, operations, rule order, default group) and priorities](kb:zwa.incidents.group-mapping).

## Handling an incident

Admins can notify the end user and request justification, or escalate to the user's manager or another approver and request justification, and can also configure workflows that perform actions automatically. [zwa.incidents:manual-features] Closing an incident takes optional notes, a resolution label and a False Positive flag; after it is closed (status Resolved), every other action except Investigating and Escalate is still available, and the status stays Resolved. [zwa.incidents:close-semantics] Incidents can be deleted in any status, only by admins whose role has delete access permission for the Incidents category, and deletion is permanent: deleted incidents cannot be recovered. [zwa.incidents:delete-permanent] Release Email Quarantine releases quarantined emails to all recipients for Email incidents whose action is Quarantine; applied to other incidents, the action completes successfully but nothing is done to them, and an error details window lists why. [zwa.incidents:quarantine-release] When closing an incident, only one label value can be associated with a resolution label. [zwa.incidents:resolution-label-one-value]

**Labels.** Labels are optional in Workflow Automation: admins with access manage custom labels and their values, then assign the labels to incidents from the Incidents page and the Incident Details drawer. [zwa.incidents:labels-optional] Deleting a label deletes its values; incidents previously assigned to the deleted label might remain and must be found and the label removed manually. [zwa.incidents:labels-delete-leftover]

The drawer's fields, actions and quarantine errors are in [The Incident Details drawer: fields by Source DLP type, actions and status changes, quarantine release errors, tickets and privacy gates](kb:zwa.incidents.details); the notifications it sends are in [User, escalation and digest notifications and reminders as the recipient sees them: contents, link lifetime, privacy gates, quarantine release and policy exceptions](kb:zwa.incidents.notifications); ticketing and chat integrations are in [Workflow Automation integrations: DLP GCP privacy settings, Slack, Microsoft Teams, ServiceNow and Jira Software](kb:zwa.incidents.integrations).

Automated handling is in [Workflow Automation workflows: the nine templates, custom workflows, mappings and what the API does not cover](kb:zwa.workflows); the API equivalents are in [DLP incident API wire behavior: list envelopes, paging, close, delete, triggers and evidence, and where the SDKs part from the contract](kb:zwa.api.incidents-wire). The organization-level dashboard of incident counts and times is in [Workflow Automation Incident Analytics dashboard: access by workflow permission, time ranges, KPI tiles, triage and resolve times, and top-10 views](kb:zwa.incident-analytics).

## Finding incidents

In the portal, priorities are Critical, High, Medium and Low; severities are High, Medium and Low; source DLP types are Inline, Email, Endpoint and SaaS Security; and statuses are New, Investigating, Validating with User, Justification Response Received, Escalated and Resolved. [zwa.incidents:values] The Open widget counts incidents with status New, Investigating or Received Justification Response; Waiting Feedback counts Validating with User or Escalated; Response Available counts Received Justification Response. [zwa.incidents:status-widgets] The All search takes free-form text, is not case sensitive, and ANDs the strings entered; incidents cannot be found by user attributes chosen for obfuscation; the Transaction ID search takes transaction IDs separated by commas, for up to 10 incidents. [zwa.incidents:search] The Incidents page searches by System Creation Date and sorts by Incident Date by default, shows the current calendar week (Sunday through Saturday) by default, and its custom date range supports only incidents up to 6 months old within a window of at most three months. [zwa.incidents:date-range] At most three bulk activities, incident downloads and bulk actions together, can be in progress at once. [zwa.incidents:bulk-limit] If the evidence file for a DLP incident exceeds 100 MB, the service replaces it with a placeholder evidence file that keeps the original name with .txt appended. [zwa.incidents:evidence-placeholder] Filters, duplicate incidents and the Incident Summary page are in [Incidents-page filters, the Incident Summary page and duplicate incidents](kb:zwa.incidents.filters-summary).

**Getting incidents into Workflow Automation.** DLP incident transactions appear as incidents in Workflow Automation only once a DLP application integration is configured for the organization, using AWS, GCP or Microsoft Azure; Internet & SaaS and its DLP policies have to be configured before Workflow Automation, and managing incidents needs an Internet & SaaS admin role with the Workflow Access permission. [zwa.incidents:dlp-integration-required] On AWS, the DLP application integration uses Zscaler's incident-forwarding methods, Zscaler Incident Receiver or Cloud-to-Cloud Incident Forwarding, which send information about policy violations to the organization's S3 buckets. [zwa.incidents:integration-methods] Cloud-to-Cloud forwarding itself is in [Where a DLP match goes: notification, ICAP, Incident Receiver and Cloud-to-Cloud](kb:zia.dlp.incident-forwarding).

What to check:
1. When a DLP violation shows in Internet & SaaS logs but no incident appears in Workflow Automation: the logged violation already shows the DLP rule matched (and, for HTTPS, that the transaction was decrypted), so the next check is the organization-level path into Workflow Automation, its DLP application integration (Zscaler Incident Receiver or Cloud-to-Cloud Incident Forwarding), before any per-rule receiver setting or the workflow mappings, which act only on incidents that arrived.
2. Whether the incident's group is mapped to an admin, since incidents in unmapped groups are not assigned automatically.
3. Whether the search's date range reaches incidents older than six months or spans more than three months.
4. Whether an incident that seems missing was deleted, which cannot be undone, rather than closed.
5. For a DLP violation with no incident in Workflow Automation, whether the DLP rule fired and recorded an incident upstream, and for inline web DLP whether the transaction was decrypted, before looking in Workflow Automation.
