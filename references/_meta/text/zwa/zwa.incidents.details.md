# The Incident Details drawer: fields by Source DLP type, actions and status changes, quarantine release errors, tickets and privacy gates (zwa.incidents.details)
Also called: incident details drawer; zwa incident drawer; release email quarantine; quarantine release failed; state changes tab; zwa ticket action

On the Incident Details drawer, severities are Critical, High, Low, Medium and Info; priorities are Critical, High, Medium and Low. [zwa.incidents.details:severity-values] The severity list differs between pages [divergence:zwa.incidents.details:severity-list]. The default Incident Details tab is set with a star icon and stored in the browser's local storage, so it is lost if the cache is cleared or another browser is used. [zwa.incidents.details:default-tab] The Incidents page that opens the drawer is in [Workflow Automation incidents: where they come from, who gets them, statuses, search limits and closing or deleting](kb:zwa.incidents).

**Fields by Source DLP type.** Several drawer fields are limited by Source DLP type: Client IP to Inline; Device Name, Device OS and Device Trust Level to Endpoint; the Action field is not shown for Email. [zwa.incidents.details:source-scoped-fields] Originating User attributes depend on how information was imported through the primary user data source (SCIM or CSV); the additional information shown for an incident does not change if the source is changed, which affects only new incidents; Retrieve User Email from Primary Data Source can override the shown email. [zwa.incidents.details:originating-user-source] The Overview tab shows a duplicate-incidents message and a Duplicate Incidents dialog listing each duplicate's Transaction ID and Transaction Time (local time zone of the user); the first incident is the one that appears on the Incidents page. [zwa.incidents.details:duplicates-dialog]

**Actions and status.** Notify User moves the status to Validating with User and Escalate to Escalated; a user, manager or approver response then moves it to the status this page names Received Justification Response; Investigating sets Investigating; Reopen moves a Resolved incident to Investigating. [zwa.incidents.details:status-transitions] A closed (Resolved) incident gets a Reopen action in the Incident Details drawer, and an incident can be reopened only from that drawer. [zwa.incidents.details:reopen] Actions need not be performed in menu order, and all actions except Delete are logged on the State Changes tab, which acts as an audit log of the incident. [zwa.incidents.details:action-order-logging] When an incident is marked as a false positive and closed, it is shown in the False Positive Incidents By Rule and False Positive Incidents By Dictionary widgets on the Incident Analytics dashboard. [zwa.incidents.details:false-positive-widgets]

**Assigning and updating groups.** The Assign DLP Admin menu lists only DLP admins with edit access to the incident group. [zwa.incidents.details:assign-admin-scope] In Update Incident Group, all incident groups assigned to at least one admin appear in alphabetical order; at least one group must stay assigned; and deleting the group used for admin assignment warns that the assigned admin will be removed. [zwa.incidents.details:update-groups]

**Notify User and Escalate.** The Escalate User Type field appears only when additional Workflow Automation user attributes are mapped in Azure SCIM provisioning, otherwise escalation is to an Approver only; Manager appears only when a manager exists; the approver must exist on the Approvers page. [zwa.incidents.details:escalate-options] Where the manager comes from when the user data is not mapped in Azure SCIM is open [gap:zwa.incidents.details:escalate-user-type-sources]. Channel Type (Email, Slack, Teams) appears in the Notify User and Escalate windows only when Workflow Automation is integrated with Slack or Microsoft Teams; otherwise notification is by email. [zwa.incidents.details:channel-type] With the Slack channel type, the address entered for the approver (Escalate) or the user (Notify User) must be associated with a Slack user of the organization; with the Teams channel type in the Notify User and Escalate windows, it must be associated with a Microsoft Teams user. [zwa.incidents.details:slack-teams-addresses] For time-related merge tags in a manually created notification, the system uses the time zone chosen in the drawer, else the notification template's, else the admin's on the Admin Assignment page, else UTC+00:00 by default. [zwa.incidents.details:time-zone-precedence] The notifications as the recipient sees them are in [User, escalation and digest notifications and reminders as the recipient sees them: contents, link lifetime, privacy gates, quarantine release and policy exceptions](kb:zwa.incidents.notifications).

**Policy exception.** The Create Policy Exception action is limited to Inline and Email incidents, takes a duration in days, hours and minutes, and creates a subrule of the incident's rule that applies only to the associated user. [zwa.incidents.details:policy-exception-action]

**Quarantined email.** Release Email Quarantine takes a justification of at most 250 characters, can mark the incident False Positive (adding a False Positive label), and its per-recipient option is unavailable when Recipient Email is obfuscated. [zwa.incidents.details:release-quarantine-limits] An end user or approver/manager can be allowed to release a quarantined email from their notification; for an end user notification this page says it is enabled with the option it names Enable Email Quarantine Release for End Users in the Incident Management section of Account Settings. [zwa.incidents.details:quarantine-release-end-user] For Email incidents, Quarantined Email Status shows per-recipient statuses Quarantined, Quarantine Release Failed, Quarantine Release In Progress and Quarantine Release Success, with a Message giving the reason a release failed. [zwa.incidents.details:quarantine-status] For failed quarantine release, the Message column reason is documented with a cause for each error: No recipients matched for release (recipient not in the message's list), No messages matched the MessageId, MessageId is null or whitespace (missing required parameter), Error getting quarantined messages (permission or Exchange Online service problems), No quarantine messages found, Exchange Online connection failure (authentication or connectivity), Error releasing message to a specific recipient or to all recipients, General error in message processing, and Something went wrong. [zwa.incidents.details:quarantine-errors] Troubleshooting tips for release failures name the Exchange.ManageAsApp permission for Error getting quarantined messages and Exchange.ManageAsApp and Directory.Read.All for Exchange Online connection failure. [zwa.incidents.details:quarantine-error-permissions]

**Tickets.** The Ticket section appears only after a ticketing integration exists and the Ticket action has run; on the Incident Details page Ticket Status displays the status of Closed (after the ticket is closed and synced), and Project shows only for Jira tickets. [zwa.incidents.details:ticket-section] Which status the Ticket section shows differs between pages [divergence:zwa.incidents.details:ticket-status-shown]. The Ticket action cannot associate multiple incidents with one ticket through the Incidents page; only users on the Integration Users page for the application are selectable; notes appear as a comment in the ticket; adding a ticket does not change the incident status. [zwa.incidents.details:ticket-action] The integrations behind tickets are in [Workflow Automation integrations: DLP GCP privacy settings, Slack, Microsoft Teams, ServiceNow and Jira Software](kb:zwa.incidents.integrations).

**Privacy and sections.** The evidence link lets admins automatically download the actual data only if Hide Evidence Data - Admin is not selected on the DLP integration and Evidence Data Privacy is not enabled for the admin on Admin Assignment; otherwise the admin can copy the link and paste it after logging in to AWS or Azure. [zwa.incidents.details:evidence-privacy-admin] The manual path for GCP is not stated [gap:zwa.incidents.details:gcp-manual-evidence-path]. View Trigger Data is available only if Hide Trigger Data - Admin is not selected on the DLP integration and Trigger Data Privacy is not enabled for the admin; the Policy section is available only if Hide Policy Details - Admin is not selected. [zwa.incidents.details:trigger-privacy-admin] For SaaS Security incidents the Recipients section appears only when the application category is Email, and the Attachments section is only for SaaS incidents with the Email category; an Other Recipients section is available for Email incidents; the presigned-link section is not available for Email incidents. [zwa.incidents.details:saas-email-sections] In the Recipients section for Email incidents, Action Taken is Allow, Block, Quarantine or Custom Header Insertion, Content Location is Email Attachments or Email Body, and severity per recipient can be Critical, High, Low, Medium or Info. [zwa.incidents.details:email-recipient-values] In the User Activity section, ZDP modes can be Block or Exemption. [zwa.incidents.details:endpoint-saas-values] Under View Trigger Data, the Inline Source DLP Type shows File Content, File Metadata, File Name and HTML Location tabs, and the Email Source DLP Type shows Email Subject, Email Body and Email Attachments tabs, with a subtab for each attachment that caused a violation. [zwa.incidents.details:trigger-data-tabs] The privacy settings on the integration are in [Workflow Automation integrations: DLP GCP privacy settings, Slack, Microsoft Teams, ServiceNow and Jira Software](kb:zwa.incidents.integrations).

**User notifications.** The User Notifications section logs the incident's notifications to the originating user and escalations to the user's manager or approver; its table has Role (Originating User, Manager or Approver), Channel, Status, No. of Attempts and User Response columns, and is sorted by initial notification date. [zwa.incidents.details:user-notifications-table] What the table's Status values are is open [gap:zwa.incidents.details:notification-status-values].

What to check:
1. Whether the incident's Source DLP type scopes the field or section being looked for: Client IP is Inline only, the device fields are Endpoint only, and the Action field is not shown for Email.
2. For a failed quarantine release, the reason in the Message column against the documented error list.
3. Whether Channel Type is missing from the Notify User or Escalate window because Slack or Microsoft Teams is not integrated, in which case the notification is by email.

Sources disagree (name both sides):
- The Incident Details page lists Critical, High, Low, Medium and Info as severities, while the Incidents page lists High, Medium and Low and the Incident Summary page's severity grouping lists High, Medium, Low and Info. [divergence:zwa.incidents.details:severity-list]
  - zscaler-help: Severities are Critical, High, Low, Medium and Info.
  - zscaler-help: Severities are High, Medium and Low.
  - zscaler-help: Grouping by severity breaks out High, Medium, Low and Info.
  Impact: Whether Critical is a severity value, and whether Info is one on the Incidents page, is not settled between the pages.
- The Incident Details page says only the Closed status displays in the Ticket section, while the Jira Software page says the project's chosen complete status appears there. [divergence:zwa.incidents.details:ticket-status-shown]
  - zscaler-help: Only the Closed status displays for tickets.
  - zscaler-help: Only the complete status specified for the Jira project appears in the Ticket section.
  Impact: For a Jira ticket whose project complete status is not Closed, the status the Ticket section shows is not settled; the ServiceNow page does say only Closed appears.
