# The Azure DLP application integration for Workflow Automation: the two forwarding methods, required outputs, fields, validation and privacy settings (zwa.azure-dlp-integration)
Also called: azure dlp integration; dlp azure application integration; zir azure; zscaler incident receiver azure; cloud-to-cloud incident forwarding azure

Workflow Automation's DLP application integration with Azure uses Zscaler incident forwarding methods to send information about policy violations to the organization's Azure storage containers, and can be configured with either Zscaler Incident Receiver or Cloud-to-Cloud Incident Forwarding. [zwa.azure-dlp-integration:methods] To configure the Azure DLP application integration with Zscaler Incident Receiver (ZIR), a ZIR Azure instance must be deployed; it lets the organization receive DLP incident metadata files and the evidence file from ZIR and upload them to its Azure storage containers. [zwa.azure-dlp-integration:zir-path-overview] Super admins, and admins with Full or Restricted access to Workflow Automation, can configure the DLP Azure application integration, which must be configured before the organization's DLP incidents are available on the Incidents page. [zwa.azure-dlp-integration:who-can-configure]

**Network.** The Azure introduction page says the NAT Gateway IPs of the organization's Workflow Automation cloud must be allowed on the Azure storage account; the cloud is identified from the admin login URL (that page's example: logging in at https://app.us1.zsworkflow.net/ gives the cloud produs1). Separately, the ZIA-side Cloud-to-Cloud page says the storage account must be accessible to the necessary IP addresses and points to Zscaler Hub IP Addresses for them. [zwa.azure-dlp-integration:nat-gateway-ips] Whether the allowlisting is unconditional or only when the storage account is restricted differs between the pages [divergence:zwa.azure-dlp-integration:nat-allowlist-conditional], and so do the example login URLs [divergence:zwa.azure-dlp-integration:cloud-url-example]. The Custom Storage Endpoint URL field of the DLP Azure integration is optional: it takes a URL in the format https://<custom endpoint> when Workflow Automation should not use the default public endpoint, and is left blank to use the public endpoint. [zwa.azure-dlp-integration:custom-storage-endpoint]

**Adding the integration.** Adding a DLP Azure application integration on the Integrations dashboard needs values from the Azure stack creation (or manual creation): TenantId, applicationClientId, applicationClientSecret, storageAccountName and the system topic resource ID. [zwa.azure-dlp-integration:required-outputs] Validate checks the account credentials entered for the Azure integration and the format of the Event Grid System Topic Resource ID, and the integration can only be added if it passes; if validation fails or wrong values were saved, the Incident Receiver page says you must disable the integration, correct the values and re-enable it. [zwa.azure-dlp-integration:validate-before-add] The pages word the correct-and-re-enable step in a different order [divergence:zwa.azure-dlp-integration:reenable-order].

**Privacy settings.** In the Privacy Settings section of the DLP Azure integration, Hide Evidence Data and Hide Trigger Data are selected by default for admins, end users and managers/approvers, and Hide Policy Details is not selected by default for admins but is selected by default for end users and managers/approvers. [zwa.azure-dlp-integration:privacy-hide-defaults] The Hide Policy Details for Non-Triggered Matches checkboxes (Admin, End User, Manager/Approver) hide the Non-Triggered Engines and Dictionaries and Other Matched Rules sections of the policy details, and each is only available when the matching Hide Policy Details checkbox is not selected; the Admin one is not selected by default. [zwa.azure-dlp-integration:privacy-non-triggered] The defaults of the End User and Manager/Approver non-triggered checkboxes are open [gap:zwa.azure-dlp-integration:non-triggered-defaults]. If Hide Evidence Data or Hide Trigger Data is disabled in the integration but read access to the data blob was not enabled when creating the resource manager stack, no one can generate evidence links or view trigger data in the Zscaler Admin Console. [zwa.azure-dlp-integration:privacy-read-access-dependency]

What to check:
1. Which method the integration uses: Zscaler Incident Receiver or Cloud-to-Cloud Incident Forwarding.
2. Whether the NAT Gateway IPs of the Workflow Automation cloud are allowed on the storage account (always, per the intro page; when the storage account is restricted to selected IP addresses, per the Incident Receiver page), and whether the Zscaler Hub IP addresses are accepted for the ZIA-side Cloud-to-Cloud forwarding.
3. Whether Validate passed, and whether the integration was disabled and re-enabled after wrong values were corrected; the pages differ on whether the values are corrected before or after the disable.
4. Whether read access to the data blob was enabled when the resource manager stack was created, if Hide Evidence Data or Hide Trigger Data is disabled.

Sources disagree (name both sides):
- The Azure introduction page's example login URL for identifying the cloud differs from the Incident Receiver page's example. [divergence:zwa.azure-dlp-integration:cloud-url-example]
  - zscaler-help: Logging in at app.us1.zsworkflow.net gives the cloud produs1.
  - zscaler-help: Logging in at app.produs1.zsworkflow.net gives the cloud produs1.
  Impact: The cloud name produs1 is the same in both, but the login hostname differs (us1 versus produs1), so the pages do not settle which hostname admins of that cloud use; read the cloud from the tenant's own login URL.
- The Azure introduction page states the NAT Gateway IP allowlisting unconditionally, but the Incident Receiver page applies it only when the storage account is restricted to selected IP addresses. [divergence:zwa.azure-dlp-integration:nat-allowlist-conditional]
  - zscaler-help: The NAT Gateway IPs must be allowed on the storage account, with no condition.
  - zscaler-help: The allowlisting is required only if the storage account is restricted to selected IP addresses; the note says 'this field' under the Create Private DNS Zone parameter and names no other toggle.
  Impact: Whether an unrestricted storage account also needs the allowlisting is not settled; which template parameter 'this field' refers to is not named (see zwa.azure-dlp-integration.resources).
- The Incident Receiver and Cloud-to-Cloud pages say to disable, correct and re-enable the integration after a failed validation; the Azure managing page says to disable and re-enable it after correcting the values. [divergence:zwa.azure-dlp-integration:reenable-order]
  - zscaler-help: Disable the integration, correct the values, then re-enable it (the Cloud-to-Cloud page words it the same way).
  - zscaler-help: Disable and re-enable the integration after correcting the values.
  Impact: Whether the values are corrected before or after the disable is not settled; the shared requirement is that the integration is disabled and re-enabled once the values are right.
