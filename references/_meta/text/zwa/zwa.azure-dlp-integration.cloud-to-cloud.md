# The Azure DLP integration through Cloud-to-Cloud Incident Forwarding: separate versus shared credentials, templates, roles and the automatically created integration (zwa.azure-dlp-integration.cloud-to-cloud)
Also called: azure cloud-to-cloud; create-app-registration-c2c.sh; aes_certificate.sh; ZscalerAzureIntegrationRM_C2C.json

Cloud-to-Cloud Incident Forwarding sends DLP incident metadata and evidence files to the organization's Azure storage containers without deploying appliances. [zwa.azure-dlp-integration.cloud-to-cloud:overview-no-appliances] The integration can use separate service principals for Internet & SaaS (ZIA) and Workflow Automation, or shared credentials between them (certificate-based authentication). [zwa.azure-dlp-integration.cloud-to-cloud:auth-modes]

**Credentials.** The Azure client certificate is generated with the aes_certificate.sh shell script when shared credentials are wanted, by creating a private key and self-signed certificate in Azure; otherwise the step is not required. [zwa.azure-dlp-integration.cloud-to-cloud:client-certificate-optional] When using shared credentials, the manual app registration does not need the client secret steps after the registration details are saved. [zwa.azure-dlp-integration.cloud-to-cloud:shared-no-client-secret]

**Script, templates and roles.** The Cloud-to-Cloud path uses the create-app-registration-c2c.sh script, with the ZscalerAzureIntegrationRM_C2C.json template for separate service principals and ZscalerAzureIntegrationRM_C2C_shared.json for shared credentials. [zwa.azure-dlp-integration.cloud-to-cloud:script-and-templates] On the Cloud-to-Cloud page the deploying user needs Owner permission in Azure, because role definitions and assignments are added during the procedure. [zwa.azure-dlp-integration.cloud-to-cloud:owner-permission] The storage account name for the Cloud-to-Cloud template deployment and for the manual storage account creation must not contain dots (.). [zwa.azure-dlp-integration.cloud-to-cloud:storage-account-name-no-dots] On the Cloud-to-Cloud path the data and metadata containers are named <storageAccountNamePrefix>-data and <storageAccountNamePrefix>-metadata, and the Zscaler DLP Incident Management service reads and stores the incident metadata file (with trigger data stripped) but never reads or stores the incident data files; the manual procedure says two containers must be created for the storage account. [zwa.azure-dlp-integration.cloud-to-cloud:containers] The custom role JSON depends on the mode: for separate service principals it lists container read, generateUserDelegationKey and Event Grid eventSubscriptions write/read/delete actions with the blobs read data action; for shared credentials the JSON lists containers write among its actions and blobs read and blobs write among its dataActions. [zwa.azure-dlp-integration.cloud-to-cloud:role-by-mode] The Cloud-to-Cloud page's manual resource-group step says the resource group must be the same one used for creating the VM, although the page says it works without deploying appliances. [zwa.azure-dlp-integration.cloud-to-cloud:resource-group-vm-reference]

**The integration object.** With shared credentials, onboarding an Azure tenant in Internet & SaaS automatically adds a DLP Azure integration in disabled state, which is edited instead of adding a new one; with separate service principals a new integration is added. The ZIA-side page adds the condition that the Azure application tenant was onboarded for Workflow Automation (the optional Workflow Automation checkbox) and that a private key was used. [zwa.azure-dlp-integration.cloud-to-cloud:shared-credentials-auto-integration] For the integration that Internet & SaaS creates automatically, the integration name is the tenant name (editable), and the Enterprise Tenant ID and Tenant Name in the ZIA Tenant Information section are synced from Internet & SaaS; Enable Integration changes the status to Enabled. [zwa.azure-dlp-integration.cloud-to-cloud:synced-fields]

The shared integration object is in [The Azure DLP application integration for Workflow Automation: the two forwarding methods, required outputs, fields, validation and privacy settings](kb:zwa.azure-dlp-integration); the Azure resources common to this path and the Zscaler Incident Receiver path (Event Grid, data-container read, manual storage networking, Front Door) are in [Azure resources for the DLP integration: app registration, permissions, containers, Event Grid, custom role, storage networking and Front Door](kb:zwa.azure-dlp-integration.resources), and the ZIA-side onboarding in [Cloud-to-Cloud Incident Forwarding: storage onboarding for AWS, Google Cloud and Azure](kb:zia.dlp.cloud-to-cloud-forwarding).

What to check:
1. Whether the deployment uses separate service principals or shared credentials, which decides the template, the role JSON and whether an integration already exists.
2. Whether the storage account name contains dots.
