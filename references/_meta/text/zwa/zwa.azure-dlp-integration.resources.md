# Azure resources for the DLP integration: app registration, permissions, containers, Event Grid, custom role, storage networking and Front Door (zwa.azure-dlp-integration.resources)

**Identity and permissions.** The create-app-registration.sh script (ZIR path) creates app registrations and client secrets for both the DLP Integration and the Filewatcher; the secret is valid for one year by default (changeable with -y), and the customer display name entered is used for the containers and storage accounts in Azure. [zwa.azure-dlp-integration.resources:app-registration-script] In the manual app registration, the supported account type is Accounts in any organizational directory and personal Microsoft accounts (a multitenant application), and the client secret value must be copied on the Certificates & secrets page because it cannot be viewed again after leaving that page. [zwa.azure-dlp-integration.resources:manual-app-registration] In the ZIR-path procedure the Filewatcher template is deployed by a user with Contributor permission in Azure, and the DLP Integration template is deployed by a user with Owner permission because role definitions and assignments are added during that procedure. [zwa.azure-dlp-integration.resources:azure-permissions] The secret expiry and rotation are open [gap:zwa.azure-dlp-integration.resources:secret-expiry].

**Containers and notifications.** On the Zscaler Incident Receiver path the data and metadata containers are named <containerNamePrefix>-data and <containerNamePrefix>-metadata, and the Zscaler DLP Incident Management service reads and stores the incident metadata file (with trigger data stripped) but never reads or stores the incident data files; the manual procedure also creates a third container, <containerName>-checkpoints. [zwa.azure-dlp-integration.resources:zir-containers] The same page calls the shared part of the names both a prefix and a suffix [divergence:zwa.azure-dlp-integration.resources:container-prefix-or-suffix]. On both the Zscaler Incident Receiver and the Cloud-to-Cloud pages, the metadata storage container publishes BlobCreated notifications to an Event Grid topic; the Zscaler service subscribes through its own Webhook endpoint and, on a notification, reads the associated metadata file from the storage container; a service principal created in the Azure account has permissions to read from the metadata container and, optionally, the data container. [zwa.azure-dlp-integration.resources:event-grid-flow] Read permission on the data storage container is only required if users who respond to incidents should be able to view incident data files through short-lived, pre-signed Shared Access Signature (SAS) URL links; the Incident Receiver and Cloud-to-Cloud pages both say this. [zwa.azure-dlp-integration.resources:data-container-read-sas]

**Template and role.** In the ZIR-path DLP integration resource manager template deployment, Enable Read Access To Data Blob is yes by default and gives read access to the incident violation details in the Zscaler Admin Console; the template also takes the service principal object IDs of the DLP app and the Filewatcher, and privatelink.blob.core.windows.net is the Private DNS Zone to select for the storage account's private endpoint. [zwa.azure-dlp-integration.resources:zir-template-fields] On the ZIR path the custom role for the DLP application grants container read, generateUserDelegationKey, and Event Grid system-topic eventSubscriptions write, read and delete actions, plus the blobs read data action. [zwa.azure-dlp-integration.resources:dlp-custom-role] On the Zscaler Incident Receiver page the example output of the DLP integration app-registration script lists tenantId, appName, applicationObjectId and servicePrincipalObjectId but no applicationClientId, although a later step says to copy the applicationClientId output from that script as the Client ID; the Filewatcher example output on the same page and the Cloud-to-Cloud example include applicationClientId. [zwa.azure-dlp-integration.resources:dlp-output-example-missing-client-id]

**Storage networking.** In the ZIR-path DLP template deployment, restricting the storage account to selected IP addresses (the page's note says 'select true for this field' under the Create Private DNS Zone parameter) requires allowlisting the IP addresses of the organization's Workflow Automation cloud, which are listed on NAT Gateway IP addresses. [zwa.azure-dlp-integration.resources:storage-ip-restriction] In the manual storage account creation on both the Zscaler Incident Receiver and the Cloud-to-Cloud pages, Network access is set to Enable public access from selected virtual networks and IP address and the Routing preference to Microsoft network routing. [zwa.azure-dlp-integration.resources:manual-storage-networking] In the manual ZIR-path procedure, the Private DNS zone is named privatelink.blob.core.windows.net, and the storage account's private endpoint uses the target sub-resource blob with dynamic private IP allocation and integration with the private DNS zone. [zwa.azure-dlp-integration.resources:manual-private-endpoint] On both the Zscaler Incident Receiver and the Cloud-to-Cloud pages, setting up Azure Front Door Premium (pricing tier Azure Front Door Premium Security optimized) is optional and only needed for Workflow Automation to access the storage account through private endpoints, and the new private endpoints must be approved before they can be used in the integration. [zwa.azure-dlp-integration.resources:front-door-private-endpoint]

The integration object is in [The Azure DLP application integration for Workflow Automation: the two forwarding methods, required outputs, fields, validation and privacy settings](kb:zwa.azure-dlp-integration), the Filewatcher VM in [The Filewatcher VM and container for the Zscaler Incident Receiver path to Azure: template parameters, recommendations, prerequisites, prompt defaults, upgrade and SFTP settings](kb:zwa.azure-dlp-integration.filewatcher) and the Cloud-to-Cloud variant in [The Azure DLP integration through Cloud-to-Cloud Incident Forwarding: separate versus shared credentials, templates, roles and the automatically created integration](kb:zwa.azure-dlp-integration.cloud-to-cloud).

What to check:
1. Which Azure permission the deploying user holds for each template on the Zscaler Incident Receiver path.
2. Whether the Workflow Automation cloud's IP addresses are allowlisted when the storage account is restricted to selected IP addresses.
3. Whether read permission on the data container was granted, if responders should view incident data files.

Sources disagree (name both sides):
- The Incident Receiver page describes the shared part of the data and metadata container names as a name prefix in one place and a name suffix in another. [divergence:zwa.azure-dlp-integration.resources:container-prefix-or-suffix]
  - zscaler-help: The containers share a common name prefix.
  - zscaler-help: The containers share a common name suffix (and the same sentence calls them the data bucket and the metadata bucket).
  Impact: The names given on the page, <containerNamePrefix>-data and <containerNamePrefix>-metadata, follow the prefix reading; the page does not say which wording is intended.
