Operator Guide

How to ask the Zscaler skill for useful work: pick the right surface, give the agent enough context, keep tenant access bounded, and read the answer without mistaking sourced evidence for runtime proof.

Best first move
Use @zscaler for grounded Q&A; switch to a slash role when you need a durable artifact.
Tenant data
Mount snapshots under _data/; prefer read-only validation commands before any write-lane test.
Read with
Reader's Guide for concepts; verification protocol for source discipline.
Canonical logic
agents/ owns the workflows; runtime adapters are loaders, not the source of truth.

At a glance

  • Ask from evidenceProduct behavior should be answered from references, snapshots, captured contracts, or source citations. If none exist, expect an explicit gap.
  • Start read-onlyMost questions can be narrowed with references, _data/ snapshots, zscalerctl reads, or curl GETs. Treat writes as a last-mile confirmation path.
  • Use the companion splitzscalerctl observes tenant state; this skill interprets it with policy semantics, source tiers, and clarification boundaries.
  • Name the task shapeDebugging, posture review, architecture, reference expansion, and doc audit are different workflows. The more specific the shape, the better the output.
  • Preserve uncertaintyContract metadata can prove documented paths, fields, enums, and readonly flags. It cannot prove live backend acceptance unless the tenant is tested.

§ 2 · Request shape

Write a useful request

The skill is strongest when the prompt names the product, the observed condition, and the evidence boundary.

Product and tenant cloud
Say ZIA, ZPA, ZCC, ZTW, ZID, or ZDX, and include the cloud or portal family when known.
Scope
Give affected users, groups, apps, locations, forwarding profiles, segments, connectors, devices, or rule names.
Timeframe
For investigations, include when it started, whether it is still happening, and any known change window.
Evidence source
Name the snapshot, file, log export, API output, Terraform plan, PR, or reference path the agent should inspect.
Desired artifact
Ask for a short answer, a command checklist, a journal, a posture register, a PR review, or reference edits.
Access boundary
Say read-only, no tenant calls, curl only, zscalerctl only, or write test allowed. When in doubt, keep it read-only.
Observation source
If this is tenant-specific, say whether the agent should use a local snapshot, a recent zscalerctl dump/diff, or draft an on-demand read command.

Good request patterns

@zscaler In our ZIA snapshot, why would the URL Filtering deny rule not block example.com? Read-only; cite the rule path.

/z-investigator ZPA users in Finance cannot reach payroll.internal since 14:00 ET. Scope: Finance group, payroll app segment, New York users. Use _data/cases/payroll-2026-06-18/.

/z-soc Review ZCC forwarding profile exposure for least privilege. Use the mounted snapshot only; produce a posture register.

@zscaler Draft curl or zscalerctl GET commands to verify whether these read-only fields appear in our tenant. Do not file vendor issues.
Avoid vague asks "Check Zscaler" is too broad. Say what product, what object, what symptom or question, and what evidence the answer may use.
§ 3 · Reading output

Read the answer

The skill separates evidence from interpretation. Keep those layers separate when acting on an answer.

SignalMeaningOperator action
confidenceHow strong the cited evidence is for the claim.Use high-confidence claims operationally; treat low-confidence claims as hypotheses.
source-tierWhether the claim came from docs, SDK code, Terraform, Ansible, MCP, captured contracts, snapshots, or synthesis.Prefer executable source and captured tenant data over prose when they conflict.
Clarification IDA known ambiguity in references/_meta/clarifications.md.Do not treat the item as closed unless the ledger says resolved.
Partial resolutionSome documented evidence is known, but runtime behavior or backend acceptance is still unverified.Use read-only checks first; escalate to lab tests only if the answer depends on live acceptance.
Open questionThe sources do not currently prove the behavior.Preserve the uncertainty in downstream docs, tickets, and runbooks.
§ 4 · Tenant-aware work

Tenant-aware work

Tenant truth lives outside the public references. The skill should read a mounted snapshot or explicit command output, not imagine your environment.

Mount or point at data.Use zscaler-skill-setup when _data/ is missing or stale.
State the boundary.Tell the agent whether it may inspect snapshots only, run read-only commands, or draft commands for a human to run.
Prefer read validation.Use zscalerctl reads or curl GETs to observe fields, enums, and object shape before any write-lane test.
Use cached dumps when fresh.A recent zscalerctl dump or diff in _data/ is faster than a live read and should be the normal path for broad inventory questions.
Record the result.When a read narrows a clarification, update the ledger as partially resolved unless it proves the whole behavior.
§ 5 · Validation passes

Validation passes

When the answer proposes a command checklist, review the command intent before running it on a work machine.

Read-only validation checklist

  • No writesGET/list/search/export only. No create, update, delete, enable, disable, move, share, rotate, or activate calls.
  • No secrets in chatKeep tokens, cookies, API keys, and tenant-private payloads out of the public repo and conversation transcript.
  • Minimal object setProbe the smallest object set that answers the question. Avoid broad tenant dumps unless the task truly needs them.
  • Capture provenanceRecord command, endpoint, timestamp, tenant cloud, and sanitized response shape.

§ 7 · Guardrails

Guardrails

The skill is useful because it refuses to smooth over missing evidence. Keep that refusal intact.

Good operator discipline Ask the agent to say what it knows, what source proves it, what remains unknown, and what read-only observation would narrow the unknown. That is usually more valuable than asking for a confident yes/no.
  • Do not convert a documented enum into proof that the backend accepts every value.
  • Do not convert absence in one tested tenant into global deprecation or removal.
  • Do not file vendor issues directly from a worklist unless the human explicitly authorizes filing.
  • Do not let an agent infer tenant state without a mounted snapshot, explicit command output, or a human-provided artifact.
  • Do not hide uncertainty. Carry it into the answer, the clarification ledger, and any downstream ticket.
